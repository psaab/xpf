# userspace-dp/src/ — feature modules

The single-file feature modules sit at the crate root and are
consumed by the per-worker hot path in `afxdp/`. They're intentionally
flat: each owns one feature's lookup tables and decision logic, with
no internal sub-modules. Test layout is mixed: most feature modules
have a sibling `<feature>_tests.rs` (`nat`, `nat64`, `nptv6`,
`policy`, `screen`, `prefix_set`); some keep their tests
inline (`fairness`, `slowpath`, `protocol`, `prefix`); and a few have
neither (`state_writer`, `xsk_ffi`).

## Stages mirroring the BPF pipeline

These mirror the BPF-side stage modules in `bpf/xdp/` and `bpf/tc/`.
The table is a simplified map of feature areas — the actual order
the worker hot path runs them in is interleaved across the
session-hit and session-miss branches in
`afxdp/poll_descriptor.rs`. Read that file for the authoritative
ordering.

| File | Stage | What it does |
|------|-------|--------------|
| `screen.rs` | screen | Pre-session attack-protection checks (land, TCP SYN+FIN, no-flag, FIN-without-ACK, WinNuke, syn-frag, ping-of-death, teardrop, ICMP frag, IP source-route, plus rate-limits). Mirrors `bpf/xdp/xdp_screen.c`. **#2215 parity fixes:** `ping-of-death` now ports the #893 IPv4 fragment-reassembly formula — any IPv4 fragment where `((frag_off & 0x1FFF) << 3) + ip_total_len > 65535` drops (the prior userspace port was an ICMP-only `pkt_len > 65535` predicate that is structurally unsatisfiable on a `u16`, so fragment ping-of-death went undetected); `land` now drops on `src_ip == dst_ip` alone for IPv4/IPv6 (the prior port additionally required `src_port == dst_port`, admitting same-IP different-port spoofed frames the BPF screen dropped). **#3119:** `teardrop` now screens IPv6 as well as IPv4 — a non-first IPv6 Fragment-header fragment whose data contribution (`ip_payload_len - frag_data_off`, saturating) is `< 8` bytes drops, mirroring the #2293 dual-family `ping-of-death` coverage and the #3027 zero/under-length IPv4 case; the prior port gated `teardrop` on `AF_INET` only, so IPv6 teardrop fragments bypassed the screen. Also contains the #1374 userspace SYN-cookie runtime: deterministic cookie mint/validate, fixed-size validated-client admission table, session-miss ACK validation with current/previous/next wall-clock epoch tolerance and standby prefilter/rate-limiting, bounded SYN-ACK/RST reply enqueue, snapshot-published key derived from cluster-synced root encrypted-password material, and per-binding sent/valid/invalid/bypass/budget counters. The Go `syn-cookie` capability gate admits active SYN-cookie screen profiles only after secret material exists; missing secret material fails closed and remaining #1374 work is live HA/flood evidence before BPF source removal. **#6238 source-independent single-sourcing:** the flow-present (`check_packet_with_zone_id_opts`) and flowless (`check_flowless_screens_opts`) entry points no longer hand-mirror the shared source-independent checks — the already-contiguous stateless tail (ping-of-death → teardrop → icmp-fragment → source-route) is extracted to `stateless::check_fragment_and_route` and the ICMP/UDP flood block to `ZoneScreenState::enforce_common_rate_floods`, each called at the SAME precedence slot on both paths, so a future addition covers both entry points by construction (the #3902 fail-open class). LAND (unconditional full / `addrs_known`-gated flowless), the TCP-flag screens, the SYN-flood/cookie block, and the `skip_rate_flood` fabric gate stay per-path by necessity — a contiguous LAND-through-source-route mega-helper was rejected because it would flip drop precedence and thus the per-reason drop-counter ordinal (`screen_reason_drop_index`). Precedence pinned by multi-trigger tests (LAND+SYN-FIN → `land-attack`; SYN-FIN+LSRR → `tcp-syn-fin`) + fail-on-revert binding tests on both paths. |
| `policy.rs` | policy | Zone-pair → permit/deny + forwarding-class + DSCP-rewrite + filter chaining. `ZonePairKey` is a `u32` (`from_id << 16 \| to_id`); `JUNOS_GLOBAL_ZONE_ID = u16::MAX` is the sentinel for the global zone. Zone ids are a **stable name-hash** (`config.StableZoneID`, FNV-1a folded into `[1, ZONE_ID_RESERVED_MIN-1] = [1, 65533]`, a pure function of the zone NAME) carried on the event-stream wire as **u16** (#3075 widened the former u8 chokepoints — the event-stream SessionOpen/SessionClose delta, the forwarding-snapshot zone table, and the fabric zone-encoded MAC — to u16; this SUPERSEDES the #2391 u8 count cap, so `MaxUsableZoneID` is now `ZONE_ID_RESERVED_MIN-1` and a commit-time collision gate rejects two zone names that fold to the same id). `SnapshotIntegrityError::InterfaceUnknownZone` fails the snapshot CLOSED when an interface names a zone absent from the zone table instead of collapsing it to zone 0. **#2410 (validated narrowing newtypes):** the forwarding-build conversion (`afxdp/forwarding_build/validated.rs` — `VlanId`/`TunnelTtl`/`QueueId`, decoded ONCE with a checked `try_from_snapshot`) fails the snapshot CLOSED on an out-of-range integer at the second trust boundary instead of narrowing it with an unchecked `as` cast: a VLAN id > 65535 (`InterfaceVlanOutOfRange`) no longer wraps to a different L2 domain, a tunnel TTL > 255 (`TunnelTtlOutOfRange`) no longer wraps 256→0 (blackhole), and a CoS forwarding-class queue id outside 0..=255 (`CosQueueIdOutOfRange`) is no longer silently dropped from `class_to_queue`. **#2409 (fail-silent drop):** an interface address that fails `IpNet` parse (`InterfaceAddressUnparseable`) and a CoS scheduler-map entry referencing a forwarding-class absent from the class-to-queue table (`SchedulerMapUnknownClass`) now fail the snapshot CLOSED instead of `continue`-ing — the pre-fix skips lost connected-route material or partially installed a scheduler while the apply still succeeded. All five are helper-boundary backstops to the Go commit-time gates, consistent with the #2173/#2212/#2240/#2391 fail-closed family; the apply preflight catches the Err and keeps the previous live forwarding state. **#3367/#3711 (malformed-address fail-closed):** every address parse path REPORTS an unparseable token and fails the snapshot CLOSED instead of silently dropping it — legacy `source_addresses`/`destination_addresses` (`UnrepresentableLegacyAddress`, #3367), v3 `source_literals`/`destination_literals` (`UnrepresentableV3Address`, #3711), and address-book `prefixes_v4`/`prefixes_v6` (`UnrepresentableAddressBookPrefix`, #3711). Silent-drop is a fail-OPEN: a v3 side / book collapses to `MatchNone` (a `deny` then matches nothing and falls through to default-permit), and the legacy empty→`MatchAny` path widens a deny to match-all. `UnrepresentableAddressBookPrefix` also ENFORCES the declared family (M02 — a wrong-family token is rejected, not routed to the other family's set). The `__unsupported_address__` sentinel preflight (`UnrepresentableAddress`, #3261) is checked first so its more-specific diagnostic wins. **#3771 (route/neighbor wire-struct integrity):** `populate_routes`/`populate_neighbors` (afxdp/forwarding_build/fib.rs) are now fallible and fail the snapshot CLOSED on self-contradicting metadata — a route whose non-empty `family` disagrees with its parsed destination prefix (`RouteFamilyMismatch`, M4), a route with a negative `preference` that would sort ahead of every route in the `sort_routes` tie-break (`RoutePreferenceOutOfRange`, L1; Go primary gate = `schema_routing.go` `ValidateInteger(0, i32max)` on the route `preference` leaf), and a neighbor whose non-empty `family` disagrees with its parsed `ip` (`NeighborFamilyMismatch`, M11). An EMPTY `family` is unconstrained (parse-only). Separately (M12) `neighbor_state_usable`/`classify_neighbor_state` (afxdp/forwarding/mod.rs) became an ALLOWLIST (`reachable`/`stale`/`delay`/`probe`/`permanent`/`noarp`): `failed`/`incomplete` are skipped silently, and an empty/`none`/future/corrupt state is skipped AND counted by the `NEIGHBOR_UNKNOWN_STATE_SKIPPED` diagnostic atomic (the pre-fix denylist installed every unrecognized state carrying a parseable IP+MAC). |
| `nat.rs` | NAT44 | Source / destination / static NAT decisions. `NatDecision` carries `rewrite_src` and `rewrite_dst` Options the TX path consumes. **#2394:** the DNAT table (`nat/destination.rs`) matches a rule on `(protocol, dst_ip, dst_port)` AND its `match source-address` constraint — a source-scoped DNAT (`DnatEntry.source_v4/source_v6`, CIDR or bare-host /32 /128) fires only for packets whose source IP falls in a configured prefix. `DnatEntry.source_constrained` distinguishes an UNSCOPED rule (no `source-address` -> match any source, unchanged behavior) from a SCOPED rule whose entries all failed to parse (-> match NOTHING, fail closed — never match-any). Before #2394 the source constraint was dropped at the Go->Rust snapshot boundary, so a source-scoped DNAT became destination-only and published the internal service to every source (fail-open). **#2398 (SNAT sibling):** the SNAT match logic (`nat/source.rs`) gets the same fail-closed treatment for BOTH its source AND destination match sets. `SourceNatRule.source_constrained`/`destination_constrained` (derived at decode from the snapshot match list being non-empty — no wire field) drive `nets_match_v4`/`nets_match_v6`: no match set -> match any (unscoped, unchanged); a non-empty match set whose prefixes ALL fail to parse -> match NOTHING (fail closed). Match prefixes also parse a bare host IP -> /32 (v4) or /128 (v6). Before #2398 an empty parsed list collapsed to match-any, so a SNAT rule whose match prefixes were all typo'd silently translated all traffic in the zone pair (fail-open broadening). **Synced reservation skips a quarantined pool BY CONTRACT (#7076):** `reserve_synced_on_first_pool_owner` gated only on `pool_mode`, so since #6812 — which marks a budget-refused rule `OverBudget` while deliberately keeping `pool_mode`, the fully expanded pool, and the DEFAULT `PortAllocator` — the standby could offer a reservation to a rule owning the translated address on paper with no allocator any packet path consults. It was inert only by accident of `impl Default for PortAllocator` (`occupancy: Vec::new()` fails the port arm closed, `max_tracked_flows: 0` fails the address-only arm closed); neither is a stated contract and neither was bound. The loop now checks `pool_failure`, mirroring the ACTIVE node's `SourceNatLookup::Unavailable`. **It skips the ALLOCATOR, not the CANDIDACY** — `saw_candidate` stays set, which is load-bearing: skipping before it (the obvious one-line fix) turns the outcome from `Refused` into `NothingToReserve`, and pass 2 answers that by falling through to `reserve_synced_interface_identity`. Measured on master with that variant applied: `may_publish` flips false -> true on BOTH arms, handing a pool-domain address to the INTERFACE domain — the two-domains-one-identity leak the pass-2 comment forbids. Pinned by `synced_reservation_refuses_a_quarantined_owner_with_a_working_allocator_7076` (the cell that separates contract from accident: the quarantined rule is given a FULLY FUNCTIONAL allocator that would accept, so only a `pool_failure` check refuses — RED at master) / `..._with_the_default_allocator_7076` (both allocator shapes reach one verdict) / `synced_reservation_quarantined_owner_is_not_nothing_to_reserve_7076` (three states — healthy reserves, quarantined REFUSES, foreign-pool falls through to the interface domain — asserted at the `may_publish` consumption point). **A pool RENAME carries its live reservations (#6979 F6):** `previous_allocators` is keyed by `SourceNatPoolAllocatorKey` = pool NAME + address vectors + port range, so two rules with identical addresses under different pool names are two keys. Renaming one onto the other collapsed both new rules onto the surviving key and DROPPED the renamed pool's allocator — its live translated identity became free and reissuable while the session owning it was still in the table. Measured: gen 1 with pools `a` (idle) and `b` holding `203.0.113.1:20000`, gen 2 renaming `b`->`a`, both rules return with ZERO live flows. `carry_renamed_pool_reservations` merges the vanished pool's live set into the surviving allocator instead of widening the key — two rules naming one pool SHOULD share one allocator, and keeping them apart would give one address two independent occupancy domains, which is the collision the key exists to prevent. Addresses and range are identical by construction (they are part of the matched key) so the index map is the identity; a genuine conflict is refused and counted by `reseed_retained_from` rather than silently freeing both. **The discriminator is whether the previous pool NAME survives into this generation** — absent means renamed, present means a coexisting peer that merely shares an address. Without that check the fix over-reaches and copies a peer pool's reservation, which is never released when the original is (separate allocators) and leaks a phantom; that over-reach was real and caught by a control. Pinned by `renamed_pool_carries_live_reservations_6979` (reuse branch, RED at master) / `rename_onto_a_new_pool_name_carries_live_reservations_6979` (fresh-allocator branch, RED at master) / `coexisting_pools_sharing_an_address_do_not_cross_pollinate_6979` (the paired cell — passes at master by design, since it guards the fix's over-reach rather than the original defect). **The LOCAL PAT mint refuses an identity a peer pool's occupancy bitmap already holds (#6979 F6, second half):** the allocator key carries the pool NAME, so two rules whose pools share an address under DIFFERENT names are two keys and therefore two `PortAllocator`s — two independent occupancy bitmaps over one address, each blind to the other, so both publish `203.0.113.1:20000` for a different live flow and the reverse index cannot attribute their replies. F6 attributes that to a MATCH-ONLY rule edit; measured, the edit is NOT load-bearing (the same two pools duplicate with no edit at all) and the SINGLE-pool version of the edit produces no defect whatsoever — the key does not change, the allocator is reused by `Arc`, and its live reservation answers `AllocatorExhausted`. So adding match criteria or zone scope to the key, which is what the finding proposes, would have broken carryover across every match-only edit while fixing nothing. The key is therefore left BYTE-IDENTICAL (retention must stay wider than minting — `drain_allocator_key`, #7717 — and any key change moves carryover for every allocator in a running process); what narrows is MINTING. `wire_overlap_peers` builds, per apply, ONE index of the pool addresses that more than one DISTINCT allocator covers — every (allocator, occupancy index) that owns each shared address — shared by `Arc` with the rules that touch one (static relation, resolved once; occupancy read at mint). Keying the count pass by distinct ALLOCATOR rather than by rule is what bounds it to #6812's aggregate ADDRESS budget: a first version indexed per rule and built a directed rule-peer map per pair, which a strict-VALID config of 1024 rules over one `/16` pool blew up to 67,108,864 entries (Codex round 1, finding 4). Then `reject_peer_owned_identity` rolls back and fails an allocation that lands on an identity a peer already owns (`PoolPeerAddressOverlap` / `source_nat_pool_peer_address_overlap`). The check runs AFTER the allocation deliberately: check-then-mint has a window where two workers on two peer allocators both see the tuple free, while mint-then-check means at least one sees the other and rolls back — worst case a refused flow, never a published duplicate, with no cross-allocator lock. That argument needs a `SeqCst` fence between the claiming `fetch_or` and the peer read, and both sides run it: the two workers store to DIFFERENT bitmaps and then load the other's, which is the store-buffer litmus test and is NOT forbidden by the bitmap's existing `fetch_or(AcqRel)` / `load(Acquire)` pair — without the fence both could observe the peer free and both publish. The fence sits after the empty-peer early-out, so no config a strict commit accepts executes it, and it cannot be bound by a test (on x86-64 the `lock`-prefixed `fetch_or` is already a full barrier); it is there for the memory model, not for an observed failure. Peer identity is the ALLOCATOR INSTANCE (`same_allocator`, Arc pointer identity), not the key: two rules naming one pool share an allocator and are ONE domain, and comparing keys instead would make every mint on a shared pool check its own just-set bit and refuse. A QUARANTINE of the later pool (the #7717 shape) was built first and rejected on evidence — it reds 16 merged tests, because #6211's pass-1 narrowing exists precisely for "two rules with overlapping pools in SEPARATE allocators" (`overlapping_pool_rules_6211`) and #6876's release sweep frees from every allocator for the same reason; overlapping pools are a shape this dataplane resolves, not one it refuses. Empty peer list on every config a strict commit accepts (the Go #5144 gate rejects the overlap at commit on ADDRESS alone), so the hot-path cost there is one `Vec::is_empty`. NOT COVERED, and each is a separate ROUTE to the same duplicate rather than a rounding error (Codex round 1 on PR #8111): the ADDRESS-ONLY path (`port no-translation` / port-less protocols) mints an `address_only_owners` reverse-identity token and claims no occupancy bit, so it is invisible to this query in BOTH directions; the HA synced reserve (`source/synced.rs`) calls `reserve_flow` on one allocator directly and never reaches the check, so an imported flow can take a tuple a LOCAL flow already owns in a peer pool; and NAT64 prefixes are their own allocators (`nat64.rs`), not indexed here. A pool whose own configured members put ONE address at several positions is also still self-colliding — `expand_pool_address` does not deduplicate and each POSITION gets its own bitmap — which is a pre-existing single-pool defect this change neither introduces nor fixes (the PEER side of it IS fixed: the index records every position, not `.position()`'s first). And the deterministic-v4 refusal costs the colliding subscriber its whole block rather than one port, because `allocate_deterministic_v4` restarts its scan at the block start; pinned by `a_deterministic_collision_refuses_the_subscriber_6979` rather than left to be discovered. Pinned by `overlapping_pools_do_not_both_mint_one_identity_6979` (RED at master) / `a_match_only_edit_keeps_the_reservation_and_mints_no_second_identity_6979` (RED at master, and also reds a widened key) / `an_overlapping_pool_still_mints_an_identity_its_peer_does_not_own_6979` (reds any quarantine-shaped fix) / `two_rules_naming_one_pool_are_not_peers_6979` / `disjoint_pools_are_not_peers_6979` / `a_refused_mint_leaves_no_reservation_behind_6979` / `the_identity_is_mintable_again_once_the_peer_releases_it_6979`. |
| `nat64.rs` | NAT64 | RFC 6052/7915 IPv4↔IPv6 translation. `Nat64Prefix` is the 96-bit + IPv4-pool config; `Nat64ReverseInfo` carries the original IPv6 tuple for reverse translation. **No per-packet heap alloc on the transit path (#2211):** `write_v6_to_v4_into`/`write_v4_to_v6_into` translate directly into a caller buffer with a streamed pseudo-header checksum; the frame builders make exactly one output allocation (`TxRequest.bytes`). **Fail-scoped config parse (#2212, refined by #3888):** `from_snapshots` is INFALLIBLE (`-> Self`) and SKIPS the offending NAT64 rule (logging a loud one-line warning naming the rule + reason) on a bad prefix or a non-host pool address, publishing the remaining NAT64 rules AND every other rule type. The whole rule is dropped all-or-nothing — a single bad pool entry drops its rule rather than silently NARROWING the pool (preserving #2212's intent) — mirroring the sibling `DnatTable`/`StaticNatTable`/source-NAT skip-and-continue posture (#1960 lenient-load doctrine). Pre-#3888 the fallible `try_from_snapshots` returned `SnapshotIntegrityError::Nat64UnparseableRule` that propagated via `?` out of `build_reconcile_forwarding`, so ONE bad NAT64 rule (from a mixed-version HA peer-sync or a corrupt snapshot — paths the Go gate doesn't cover) froze the ENTIRE control→dataplane pipeline, blocking every other rule type + every later commit. The Go #2173/#3886 commit-time gate remains the primary defense; this is the helper-boundary backstop, now scoped to a NAT64-only degradation. NPTv6 (`nptv6.rs`) intentionally stays fail-CLOSED (abort-all) — its #2241 overlap rejection is order-dependent so a blind per-rule skip would be ambiguous (flagged follow-up). **RFC 7915 fragment translation (#2488):** v6→v4 derives the IPv4 MF/offset/Identification (low 16 bits of the 32-bit id) from the IPv6 Fragment Header when present (`ipv6_fragment_header`), falling back to the `no-v6-frag-header` atomic-datagram policy only when absent; v4→v6 inserts an 8-byte IPv6 Fragment Header (next-header 44) for a fragmented IPv4 input, copying offset/MF and zero-extending the 16-bit id. A first-fragment TCP/UDP checksum is adjusted incrementally for the v4↔v6 pseudo-header address delta (RFC 1624) since the full payload is absent; a v4 UDP fragment with a zero checksum is dropped (cannot synthesize the mandatory v6 checksum). **Non-first fragment traversal (#2562):** a stateful fragment-association cache (`Nat64FragAssoc`, port-free key `(family, src, dst, ip_id)`, bounded LRU + ~2s TTL, cross-worker via the shared `Arc<ForwardingState>`, NOT HA-synced) lets a non-first TCP/UDP fragment INHERIT the first fragment's translation and translate L3-only (`write_v6_to_v4_nonfirst_into`/`write_v4_to_v6_nonfirst_into` — payload verbatim, no L4 checksum, IPv4 ident = low-16 of the v6 ident / v6 ident = v4 ident zero-extended) so the whole datagram reassembles: the FIRST fragment installs the association on the cold path, and a non-first fragment consults it on the flowless arm. The FORWARD (v6→v4) direction is wired end to end; the REVERSE (v4→v6) translator + frame-builder are in place with the reverse-reply install/consult a follow-up. A non-first fragment with NO association (reorder / orphan / eviction / cross-node failover) still drops fail-closed (#4617, `nat64_frag_dropped`) — never forwarded to a wrong source. Fragmented ICMP/ICMPv6 stays dropped both directions (below); true IP reassembly (`force-ip-reassembly`) remains a separate feature. **#5689 — ordinary same-family NAT / NPTv6 fragment consistency (SAME cache):** `Nat64FragAssoc` is deliberately generic — its port-free key `(family, src, dst, ip_id)` and full `SessionDecision` value are family-agnostic — so an ORDINARY same-family SNAT / DNAT / static-NAT / NPTv6 forward flow now installs a fragment association too (`nat_install_forward_fragment_assoc`, called at the cold-path forward-commit point where the composed NAT decision is final) and its non-first fragments consult it on the flowless arm (`nat_consult_forward_fragment_assoc`, tried after the NAT64 consult, for BOTH IPv4 and IPv6). A hit inherits the first fragment's permitted verdict + egress resolution and the forward-build path applies an ADDRESS-ONLY L3 rewrite (`apply_nat_ipv4` / `apply_nat_ipv6` already SKIP the L4-checksum + port rewrite for a non-first fragment, #1852), so the whole datagram reassembles TRANSLATED at the receiver. Before #5689 a non-first fragment of an ordinary-NAT'd flow resolved `NatDecision::default()` on the flowless arm and was forwarded UNTRANSLATED (leaking the internal source / pre-DNAT destination). The `nat64` flag on the cached decision keeps NAT64 and ordinary-NAT associations from aliasing (a given datagram installs exactly one entry; the ordinary consult filters out `nat64` entries and vice-versa), and the shared `build_generation` guard — which advances on EVERY config commit (`snapshot.generation`), not only NAT64 changes — invalidates a stale ordinary-NAT association after a SNAT / DNAT rule change. FORWARD-only, mirroring the NAT64 forward-first wiring (the reverse-reply association is a deferred increment). **Miss-path fail-CLOSED (#6122, closing the #5689 residual):** unlike the pre-#6122 fail-OPEN arm, an ordinary same-family NAT'd non-first fragment that MISSES the cache (reorder / >~2s TTL straddle / shard-cap eviction / config-generation bump / a first fragment that never forwarded) is NO LONGER forwarded UNTRANSLATED. The flowless arm now runs a read-only NAT'd-miss vs no-NAT-miss discriminator (`flowless_fragment_requires_nat_translation` in `poll_descriptor`): it re-checks the fragment's L3 identity (source / destination / protocol / ingress+egress zones / interface + routing-instance scope — every part a non-first fragment carries) against the SNAT / static-NAT / DNAT / NPTv6 rule tables. If a rule WOULD translate this flow, the permitted-but-untranslatable fragment is DROPPED fail-closed (counted `nat_frag_untranslated_dropped`, mirroring the NAT64 sibling's `nat64_frag_dropped`) instead of leaking the internal source (SNAT / NPTv6) or the pre-NAT destination (DNAT); if NO rule matches, the plain fragment forwards exactly as before, so ordinary un-NAT'd fragmented traffic is never blackholed. The discriminator is side-effect-free (source NAT is consulted with `non_first_fragment=true`, which reports without minting a pool mapping; DNAT/static/NPTv6 are read-only lookups) and scoped to genuine non-first fragments (`frame_is_non_first_fragment`) — a first fragment / full-L4 packet is translated on the flow-backed arm and installs the association, so it never reaches here. Because a non-first fragment has no L4 ports, the discriminator matches only ADDRESS/zone-scoped rules; a strictly PORT-scoped DNAT rule does not match `dst_port==0` and is intentionally not flagged (a documented residual — the common in-order case is covered by the association HIT path, and forwarding such a fragment reaches the pre-DNAT public destination, not an internal source). This brings the same-family arm into line with the NAT64 fail-CLOSED miss (#4617). Pinned by `flowless_non_first_fragment_inherits_ordinary_snat_translation_5689` (HIT still translates) + `nat_nonfirst_fragment_assoc_miss_fails_closed_6122` (NAT'd miss drops) + `nonnat_nonfirst_fragment_assoc_miss_still_forwards_6122` (plain miss still forwards). **#2562 fail-closed ICMP fragment drop + counter:** a REAL fragment (Fragment Header present with MF=1 OR a non-zero offset) carrying ICMP/ICMPv6 is now DROPPED both directions — the ICMP checksum covers the WHOLE datagram, so `translate_icmpv6_message_to_icmpv4` / `translate_icmpv4_message_to_icmpv6` over a single fragment's bytes would emit a FIRST fragment with a wrong checksum the receiver discards (the pre-#2562 behavior). An ATOMIC fragment (MF=0, offset 0 — RFC 6946) carries the complete message and still translates; a first-fragment TCP/UDP keeps its incremental-checksum translation. The fail-closed drop — the today-silent non-first-fragment drop AND the new ICMP-fragment drop — is now OBSERVABLE: `nat64::frame_is_nat64_fragment_drop` (the SSOT predicate mirroring the translator guards, `v6_to_v4_is_fragment_drop`/`v4_to_v6_is_fragment_drop`) attributes a NAT64 `build_nat64_forwarded_frame`-returned-`None` at the TX dispatcher to a new per-binding `nat64_frag_dropped` counter (`BatchCounters::record_nat64_frag_dropped`, wired through the #4520 plumbing — live atomic, snapshot, wire `BindingStatus`, summed as the `NAT64 fragment drops` row in `format/status.go`). This is the observable-drop half of #2562; the stateful frag-association cache that lets real TCP/UDP fragments traverse end-to-end (the #3291 stage-4 principled fix) is now built — see **Non-first fragment traversal (#2562)** above — with fragmented ICMP staying the fail-closed drop (the ICMP checksum covers the whole datagram). **RFC 6146 BIB — stateful port/identifier translation (#4381):** NAT64 is a many-to-one (v6→v4) translation, so two IPv6 clients behind ONE pool v4 address that share a TCP/UDP source port or ICMP echo identifier would otherwise produce an identical reverse (v4→v6) 5-tuple and the server's replies would be mis-associated. Each `Nat64Prefix` now owns a `PortAllocator` — the SAME pool-mode SNAT allocator (`nat/allocator.rs`) — and `Nat64State::allocate_source` hands every admitted forward flow a UNIQUE `(pool v4 address, translated source port / ICMP identifier)`. `forward_decision` carries the translated value in `rewrite_src_port`; the frame builder (`afxdp::frame::build_nat64_forwarded_frame`) rewrites the L4 SOURCE via the same-family `apply_nat_port_rewrite`/`apply_nat_icmp_identifier_rewrite` (incremental checksum) on the forward path, and `NatDecision::reverse` restores the ORIGINAL client port/id on the L4 DESTINATION on the reverse path. The reverse session key therefore keys on the TRANSLATED value (what the server replies to). ## Where these are called from

The worker poll loop drives the per-packet stages from
`afxdp/worker/lifecycle.rs::poll_binding` and the per-descriptor
dispatch in `afxdp/poll_descriptor.rs`. The stages above approximate
the "session-hit" fast path; the real session-miss order interleaves
DNAT, NPTv6 inbound, NAT64, FIB / forwarding resolution, policy, and
SNAT decisions across multiple branches in `poll_descriptor.rs`. Read
that file for the authoritative order — the tabular pipeline above is
intentionally simplified.

`fairness` is an auxiliary surface consumed by the `fairness-eval`
binary. (Flow export — NetFlow v9 / IPFIX — is NOT a dataplane module:
it is owned entirely by the Go control plane `pkg/flowexport`, driven by
SESSION_CLOSE events. The dead Rust `flowexport.rs` exporter was removed
in #2130; the dataplane emits no flow records.)
