r5 MAJOR: RESOLVED. v8 removes the success-path `t7_arm` clear: §5.2 now says success drains request edges only and explicitly relies on authenticated receive to clear stale `t7_arm` before same-iteration TUN egress.

New MAJOR: success edge-drain is not universally safe. The plan itself says attempt success can be caused by the peer’s initiation creating a fresh responder-role session, and that session may be unconfirmed; existing code treats unconfirmed egress as `NoSession`, and `encap_and_send` arms `request_handshake`. Since socket burst precedes TUN burst and `attempt.drive` runs after both, v8 can still erase a legitimate same-iteration NoSession edge in the peer-beat-us success path. The “age ≈ 0, session confirmed” proof only holds for our `consume_response`/initiator-success path, not the responder-success path.

PLAN-NEEDS-REVISION: Move success request-edge draining to the authenticated completion/install site, before same-iteration TUN egress, or make the later success cleanup conditional so it cannot clear a post-completion NoSession edge from an unconfirmed responder session. The `t7_arm` fix is correct, but the same after-bursts cleanup ordering bug still exists for request edges in the peer-initiated success case.
