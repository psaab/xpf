# Codex hostile plan-review — #6371 r4 (VERDICT: PLAN-NEEDS-REVISION)

Direction affirmed (seed/ownership-reconcile viable); 5 BLOCKER + 2 HIGH implementation-completeness gaps. Drove the r5 boot-pin-quarantine + convergent-retry redesign.

---

R4 is directionally faithful to the r3 blocker, but Path D is not yet sound or implementation-complete.

1. **BLOCKER — startup fix works mechanically, but not as claimed.** Seeding `applied`, not `active`, is conceptually correct: after authoritative `Reconcile`, `applied=true`, `desired=false` sets pending and triggers the clear ([rg_state.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/daemon/rg_state.go:250)). But `NeedsApply` returns sticky `applyPending`, not a live comparison, so `SeedApplied` must recompute that invariant atomically ([rg_state.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/daemon/rg_state.go:202)).

2. **BLOCKER — “hitless legitimate owner” is false.** Fresh RGs start Secondary, and non-preempt boot remains Secondary pending peer evidence; a never-seen peer has a 30-second startup floor ([group_state.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/cluster/group_state.go:23), [election.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/cluster/election.go:419), [heartbeat.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/cluster/heartbeat.go:58)). Therefore even the legitimate previous owner can initially have `desired=false`; seed-from-map clears it until election. That is a valid fail-closed policy, but it breaks the explicit HA `hitless-restart` behavior and can cause a long outage. R4 must choose and document the safety/availability invariant rather than promise both.

3. **BLOCKER — re-arm-to-clear is not bounded.** The helper replays the pin during initial config apply ([manager_compile.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/dataplane/userspace/manager_compile.go:360)); reconciliation starts substantially later, after more startup work, while the watchdog starts earlier ([daemon_run.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/daemon/daemon_run.go:380), [daemon_run.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/daemon/daemon_run.go:561)). “Before the immediate reconcile pass” is not a wall-clock bound; a stall between replay and that pass keeps renewing the stale state. Seed and corrective reconciliation must be adjacent to replay and precede watchdog/status publication, with explicit failure behavior.

4. **BLOCKER — the advertised alternative does not close the defect.** Merely skipping `manager_compile` replay leaves the pin at one. The one-second status poll rereads it and may publish it, while the watchdog publishes the full group set on its backstop ([process_status.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/dataplane/userspace/process_status.go:208), [manager_ha.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/dataplane/userspace/manager_ha.go:781)). That alternative must quarantine/clear the pin or suppress every map-derived publication until ownership is established.

5. **BLOCKER — peer-fence remains an undisclosed one-shot failure.** `fenceAllRedundancyGroups` logs a failed clear and returns without changing `rgStateMachine` or scheduling retry ([daemon_ha_sync.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/daemon/daemon_ha_sync.go:1267)). If desired/applied remain true, reconciliation never retries. Thus one transient peer-fence map error—not a persistent failure—can remain active indefinitely. Alarm-only debt does not close this. The debt needs a retry consumer that retains `false` until convergence or an explicit later ownership epoch supersedes it.

6. **HIGH — alarm convergence is insufficient.** Helper-reported inactive alone cannot clear debt while `rg_active` remains one: the poll can reload and re-arm it. Resolution must confirm, for the same clear generation, both pinned map zero and helper `Active=false`; mere lease expiry/`ForwardingActive=false` is insufficient. The plan must also choose the state owner, preserve the first failure timestamp across retries, specify `T`, define removal/restart/supersession, and treat shutdown separately—an in-memory hysteresis alarm cannot mature after shutdown monitoring has stopped.

7. **HIGH — inventory and API gaps remain.** `rg_active` is a fixed 16-entry array and map merge republishes every key ([manager_ha.go](/home/ps/git/bpfrx/.claude/worktrees/6371-research/pkg/dataplane/userspace/manager_ha.go:325)). A stale-active removed/unconfigured RG is absent from fresh reconciliation unless seeding explicitly creates a tombstone for every active pinned key. Also, daemon `HAController` is currently write-only, while `mergeHAStateFromMaps` is private; r4 must define the snapshot API, locking/order, and fail-closed map-read-error behavior.

Deferring a genuinely persistent map-write failure can be defensible after retry, detection, named security/HA-owner acceptance, and a concrete follow-up issue. Those prerequisites are not currently evidenced: the plan provides no follow-up ID or signer. “Stuck ownership” also produces no clear debt, so it is not operationally surfaced by this alarm and should be treated as a separate election/VRRP risk.

The historical corrections are otherwise sound: #485’s preflight comments are stale after `fce172532`; #5640’s ACK is not a promotion fence; #5079 is an owner eligibility lease; #1928’s cluster-only guard must remain; and #3917 is exactly why peer-fence retry is required. The revised ~11-second wording is correct when measured from the last applied active IPC and limited to new ordinary admission.
