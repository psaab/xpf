# Plan: Centralize the managed-binary upgrade manifest (#1982)

## 1. Problem

The managed upgrade binary list `{xpfd, cli, xpf-userspace-dp,
xpf-day0-config}` is duplicated across six independent edit sites with no
single source of truth and no drift guard:

- `pkg/upgrade/runner.go:54` — `var managedBins` (unexported)
- `pkg/upgrade/runtime/seed.go:58` — duplicate `managedBins`
  (comment: "Defined here too because upgrade.managedBins is unexported")
- `debian/xpf.preinst:44` — `BINS="xpfd cli xpf-userspace-dp xpf-day0-config"`
- `debian/xpf.postinst:35` — same `BINS`
- `debian/xpf.postrm:40` — same `BINS`
- `debian/rules:80-84` — `install -m 0755` of each binary individually

The upgrade flow treats these binaries as a version-locked unit (seed,
copy, flip, cleanup, package). Adding a future helper requires editing all
six. A one-file miss ships a green build that leaves an old helper in
service, fails rollback cleanup, or omits a binary from first-install
seeding.

## 2. Hypothesis

A single exported Go manifest + a build-time generated shell fragment +
a Go drift canary eliminates the divergence class. Because the list is
identical at all sites today, the consolidation is behavior-preserving;
the only new runtime artifact is a generated shell `BINS` definition the
maintainer scripts source.

## 3. Goal / acceptance criteria

- One exported SSOT for the managed-binary list with per-binary metadata.
- `runner.go` and `seed.go` consume the SSOT (no local slices).
- The three maintainer scripts + `debian/rules` derive `BINS` from the
  SSOT (generated fragment), not a hand-typed literal.
- A Go test FAILS the suite if the Go manifest, the shell `BINS`, and the
  `debian/rules` install set diverge.
- `make build` + `go test ./pkg/upgrade/...` green; the produced .deb's
  maintainer scripts contain the same four binaries as today
  (byte-equivalent behavior).

## 4. Approach

### 4.1 New package `pkg/upgrade/manifest`

```go
package manifest

// Binary is one managed upgrade binary.
type Binary struct {
    Name        string // sbin/staged basename, e.g. "xpfd"
    StagedSrc   string // build-output path relative to repo root for debian/rules
    LockstepCut bool   // true: cut in version lockstep (xpfd, xpf-userspace-dp);
                       // false: operator tool (cli, xpf-day0-config)
}

// Managed is the SSOT ordered list.
var Managed = []Binary{
    {Name: "xpfd",             StagedSrc: "xpfd",                              LockstepCut: true},
    {Name: "cli",              StagedSrc: "cli",                              LockstepCut: false},
    {Name: "xpf-userspace-dp", StagedSrc: "xpf-userspace-dp",                LockstepCut: true},
    {Name: "xpf-day0-config",  StagedSrc: "scripts/image/xpf-day0-config",  LockstepCut: false},
}

// Names returns just the basenames in order (for the copy/link/cleanup loops).
func Names() []string { ... }

// ShellBINS renders the maintainer-script BINS literal:
//   BINS="xpfd cli xpf-userspace-dp xpf-day0-config"
func ShellBINS() string { ... }
```

`runner.go` and `seed.go` replace their local `managedBins` with
`manifest.Names()`. (Keep `managedBins` as a thin local alias only if a
hot loop wants the slice; otherwise call `manifest.Names()` once.)

### 4.2 Generated shell fragment

A tiny generator (a Go program under `pkg/upgrade/manifest/cmd/genbins`
invoked via `go generate` / a Makefile rule, OR a `debian/rules` step
that runs `go run`) emits `debian/xpf.bins` containing exactly:

```sh
# CODE GENERATED by pkg/upgrade/manifest; DO NOT EDIT.
BINS="xpfd cli xpf-userspace-dp xpf-day0-config"
```

The three maintainer scripts replace their literal `BINS=...` with
`. /usr/local/share/xpf/xpf.bins` — OR, to avoid shipping a sourced file
and a runtime dependency, debhelper substitution at BUILD time: `debian/rules`
runs the generator and seds the fragment into each maintainer script
before packaging. **Decision deferred to plan review** (sourced-at-runtime
vs build-time-inlined; build-time inline keeps the scripts self-contained
with no new shipped file, which matches the existing `debian/rules`
ExecStartPre sed pattern at `rules:61`).

### 4.3 debian/rules install set

`rules:80-84` becomes a loop driven by the generator output (a generated
`.install`-style fragment or a generated make variable
`XPF_MANAGED_BINS := ...` that the install recipe iterates). Same staged
target dir, same modes.

### 4.4 Drift canary (Go test)

`pkg/upgrade/manifest/drift_test.go`:

- Parse `BINS="..."` out of `debian/xpf.preinst`, `xpf.postinst`,
  `xpf.postrm` (regex `^BINS="(.*)"`).
- Parse the `install -m 0755 ... debian/xpf$(STAGED)/<name>` lines (and/or
  the generated make var) out of `debian/rules`.
- Assert each parsed set == `manifest.Names()` (order-insensitive for the
  scripts, since the loops are order-free; `debian/rules` install order is
  irrelevant).
- The test reads the repo files relative to the test file location (the
  package sits at a known depth from repo root).

If the build-time-inline approach is taken, the canary instead asserts the
GENERATOR output equals `manifest.Names()` and that the committed maintainer
scripts contain the generator's exact `BINS` line (so an editor who hand-edits
a script is caught).

## 5. Alternatives rejected

- **Leave as-is.** Six lists drift silently; the next added helper is a
  latent half-managed-binary bug. Rejected per engineering-style "One
  source of truth / Helpers over duplication."
- **Go SSOT only, scripts still hand-typed.** Halves the duplication but
  the shell side (the side most likely to be missed, since it's three
  files) stays manual. Rejected — the canary is the point.
- **Source a shipped `/usr/local/share/xpf/xpf.bins` at runtime.** Adds a
  runtime file dependency for the maintainer scripts and a failure mode if
  it's missing mid-upgrade. Build-time inline is preferred (no new runtime
  surface), pending review.

## 7. Test strategy

- `drift_test.go` — the canary. Strong test: deliberately mutate a copy of
  one maintainer-script BINS string in a table-driven sub-case and assert
  the canary's comparator REPORTS the divergence (counter-factual: prove
  the canary would fail if a real script drifted).
- `go test ./pkg/upgrade/...` — existing runner/seed tests still pass with
  `manifest.Names()`.
- `make build` then inspect the staged maintainer scripts in the built
  .deb (`dpkg-deb -e`) — assert the four binaries are present and
  unchanged from the pre-refactor package (behavior-preserving).

## 8. Invariants

- The four-binary set is IDENTICAL before/after (no binary added or
  dropped in this PR — pure consolidation; scope discipline).
- Generator output is deterministic and committed/regenerated only via the
  pinned path (no hand-edit of generated regions).
- The canary runs on `go test` (CI gate), not just locally.

## 9. Risk

LOW. Pure consolidation of an identical list. The only behavioral surface
is HOW the maintainer scripts obtain `BINS`; build-time inline keeps them
self-contained. Main risk is a parser mismatch in the canary (regex must
match the actual script syntax) — covered by the counter-factual test.

## 10. Rollout / validation

- Unit tests + .deb inspection (above). No live cluster lane needed (no
  runtime forwarding behavior changes); state so in the PR body.
- `make test-deploy` standalone ping-between-zones as a smoke that the new
  scripts still install cleanly.

## 11. Disposition

engineer-now after plan review. Well-bounded, behavior-preserving, high
maintainability payoff.
