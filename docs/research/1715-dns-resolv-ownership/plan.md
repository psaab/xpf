## 1. Problem statement

On `loss:xpf-userspace-fw0` the box has **no working resolver**:
`/etc/resolv.conf` is a dangling symlink to
`/run/systemd/resolve/stub-resolv.conf`, but `systemd-resolved` is
`inactive` AND `disabled`, and `/run/systemd/resolve/` does not exist.
`cat /etc/resolv.conf` → `No such file or directory`. xpf never
reconciles it.

## 2. Independently verified diagnosis (against master ac6991c3b + live fw0)

### 2a. Live state (read-only, fw0, 2026-05-30)
- `/etc/resolv.conf -> /run/systemd/resolve/stub-resolv.conf` (symlink, base image default).
- `systemctl is-active systemd-resolved` → **inactive**; `is-enabled` → **disabled** (preset: enabled).
- `/run/systemd/resolve/` **absent** → symlink dangling → ENOENT on read.
- Drop-ins present: `xpf.conf` (`# Generated by xpfd`, `DNS=1.1.1.1`) AND legacy `bpfrx.conf` (`# Generated by bpfrxd`, `DNS=1.1.1.1`). Both inert because resolved is off.
- `/etc/.resolv.conf.systemd-resolved.bak` present (924 B; the original stub-resolv content — a base-image artifact, not xpf's).
- Running config: `system name-server { 1.1.1.1; }`; **no `system services dns` stanza** (the `dns-server 8.8.8.8` seen in greps is the `dhcp-local-server` pool option, unrelated).
- `fxp0` is bootstrap DHCPv4 (no explicit `interfaces fxp0` stanza).

### 2b. Causal chain (CONFIRMED by code read end-to-end)
`daemon_apply.go:885-888` applies in this order on every commit/boot:
```
886: d.applySystemDNS(cfg)   // writes xpf.conf drop-in, then `systemctl restart systemd-resolved`
887: d.applySystemNTP(cfg)
888: d.applyDNSService(cfg)   // if !DNSEnabled: `systemctl disable --now systemd-resolved`
```
With `name-server 1.1.1.1` set but **no `services dns`** stanza
(`DNSEnabled == false`, `compiler_system.go:328` only sets it true when
the stanza exists):
1. `applySystemDNS` (`:235-272`) writes `xpf.conf` and calls
   `restartResolved()` → resolved comes up, `/run/systemd/resolve/`
   created, stub target valid.
2. **Two lines later** `applyDNSService` (`:421-429`) sees
   `DNSEnabled == false` → `systemctl disable --now systemd-resolved`
   → resolved stops → `/run/systemd/resolve/` torn down → the symlink
   target vanishes → **dangling**.

This is a deterministic self-inflicted race in apply order, not a
timing fluke. Every apply re-creates the dangling state.

### 2c. installDNS is NOT the v4 culprit — it never runs on fw0
`pkg/dhcp/dhcp.go:454` `installDNS` writes a plain `/etc/resolv.conf`
via `os.WriteFile`. It is wired **only from the DHCPv6 path**
(`dhcp.go:728-730`, gated `v6opts.UpdateDNS`). The DHCPv4 path
(`runDHCPv4`) **never calls `installDNS`**, and `daemon_dhcp.go:65`
constructing `DHCPv4Options` **never sets `UpdateDNS`** (the field
exists at `dhcp.go:67` but is dead for v4). So on fw0 (fxp0 =
DHCPv4 mgmt) `installDNS` is never invoked. The issue body's
"installDNS writes through the dangling symlink and fails ENOENT"
is the *latent* failure mode for the v6 path; the *actual* fw0
breakage is the apply-order conflict in 2b. **Both must be fixed.**

If `installDNS` *did* run while the symlink is dangling, `os.WriteFile`
follows the symlink and targets `/run/systemd/resolve/stub-resolv.conf`
whose parent dir is absent → ENOENT → silent `slog.Warn` → resolv.conf
stays dangling. Confirmed by reading the full function body (no
symlink check, no MkdirAll, no O_NOFOLLOW).

### 2d. Verified side effect of investigation
A diagnostic `systemctl restart systemd-resolved` was run on fw0 during
verification (to confirm exit code). It succeeded (exit 0) and left
resolved **active** with a valid `/run/systemd/resolve/`. This is
benign and self-correcting: the next `applyDNSService` (commit/restart)
will re-disable it per the bug, OR the chosen fix will set the correct
end-state. No persistent config was changed. **Noted for honesty; the
box's broken-state reproduction is fully captured above from the
pre-restart reads.**

### 2e. Legacy `bpfrx.conf` drop-in
`bpfrx.conf` (`# Generated by bpfrxd`) is a stale artifact from the
pre-rename era. Current code only writes/removes `xpf.conf`
(`daemon_system.go:237`). Nothing ever removes `bpfrx.conf`. It is
inert today (resolved off) but would double-apply `DNS=` if resolved
were ever the owner. Must be cleaned up.

## 4. Design question
Should xpf **own `/etc/resolv.conf` as a managed plain file** (no
resolved dependency), or **commit to systemd-resolved** as the single
DNS owner? The current code straddles both and the straddle is the bug.

## 5. Multiple Path Options

### Option A — Own /etc/resolv.conf as a managed plain file (NO resolved)
xpf becomes the single owner of `/etc/resolv.conf`.
- New pure renderer `pkg/daemon/system/dns.go`:
  `RenderResolvConf(nameservers, domainName, domainSearch []string) string`
  emitting `nameserver` + `search`/`domain` lines.
- New `reconcileResolvConf(content string)`:
  - If `/etc/resolv.conf` is a symlink (any target) → `os.Remove` it
    (using `os.Lstat`, NOT follow).
  - Atomically write a real file (write temp + `os.Rename`), 0644.
  - Idempotent: compare via `Lstat`+read; only rewrite on change.
- `applySystemDNS` renders from `system name-server` + domain config and
  calls `reconcileResolvConf`. **Remove `restartResolved()`.**
- Resolved is deterministically `disable --now` + **masked** (no
  hybrid; see §5b). 
- **DHCP does NOT write the file.** It stores DNS in the lease and fires
  the existing debounced `onAddressChange` (`dhcp.go:1172`); the central
  locked `reconcileDNS` reads `dhcpMgr.Leases()` and merges. `installDNS`
  file write is removed. (See §5b for the full converged design.)
- **Startup reconcile** (Option C, folded in): `reconcileDNS` runs at
  daemon init, repairing a dangling/resolved-stub symlink to a managed
  merged file immediately — independent of DHCP/commit timing.
- Remove legacy `bpfrx.conf` drop-in on startup.

**Tradeoffs**: + Deterministic, no resolved race, no stub dependency,
survives deploy-wipe (boot reconcile). + Matches "xpf owns ALL of the
box" philosophy (it already owns interfaces, FRR, networkd). − Loses
resolved features (LLMNR, per-link DNS, DNSSEC stub, split-DNS). − Must
define DHCP-vs-static precedence + dual-stack merge. − Race with any
other writer of resolv.conf (mitigated: xpf owns the box).

### Option B — Commit to systemd-resolved as sole owner
Make resolved authoritative; `/etc/resolv.conf` stays the resolved
symlink and we guarantee resolved is up.
- `applySystemDNS` writes `xpf.conf` (renderer shared with #1713).
- Whenever a drop-in is written (DNS configured), `enable --now`
  resolved so the stub target always exists. **Resolve the
  applySystemDNS-vs-applyDNSService contradiction**: `applyDNSService`
  must NOT `disable --now` when xpf has DNS config; `DNSEnabled`
  semantics redefined or the two functions merged into one
  resolved-state machine.
- `installDNS` (DHCP) must push DNS into resolved via `resolvectl dns
  <iface> <servers>` rather than writing the file (writing the file
  fights resolved). This is a larger behavioral change to the DHCP path.
- Ensure `/etc/resolv.conf` symlink points at the resolved stub and is
  repaired if a prior Option-A run replaced it with a file.

**Tradeoffs**: + Keeps resolved features; idiomatic on systemd boxes.
+ Single renderer reuse with #1713. − Adds a hard runtime dependency on
a service xpf otherwise doesn't need; more moving parts. − DHCP→resolved
push (`resolvectl`) is a new integration surface. − A failed/slow
resolved restart = no DNS (vs. a static file that just works). − Heavier
than the problem warrants for a firewall appliance.

### Option C — Startup symlink reconciler only (narrow)
Just add a boot-time check: if `/etc/resolv.conf` is dangling or points
at the resolved stub while resolved is off, replace with a managed file.
Leave applySystemDNS/applyDNSService as-is.
- **Tradeoffs**: + Minimal. − Does NOT fix the apply-order race
  (`applyDNSService` re-breaks it on the next commit). − Leaves three
  owners. **Insufficient alone** — at best a sub-component of A.

### Option D — (found) Merge into one DNS state machine + renderer extraction
The cleanest framing of A: extract `pkg/daemon/system/dns.go` with (1) a
pure renderer (shared with #1713's Domains= fix) and (2) a single
`reconcileDNS(cfg)` that owns the full decision: pick owner model from
config, do exactly one of {write managed file + disable resolved} or
{write drop-in + enable resolved}, never both, and run at startup +
every apply. `applySystemDNS` + `applyDNSService` collapse into it.
This is Option A's implementation shape and is the recommended vehicle.

## 5b. ROUND-1 OUTCOME — hybrid killed; converged remediation

Round-1 reviewers (Claude-SMR + AGY, both PLAN-NEEDS-MAJOR) verified the
diagnosis but found the r1 *implementation shape* reintroduced the
multi-owner bug. Verified flaws:
- **F1 hidden third owner**: `dhcp.Manager` is config-blind
  (`dhcp.New(stateDir, onAddressChange)`, `dhcp.go:103` — no `cfg`/
  `DNSEnabled`). A hybrid that keeps resolved when `services dns` is set
  would still have the async DHCP path delete the resolved symlink and
  write a plain file → breaks resolved mode.
- **F2 async write outside the lock**: `applyConfig` holds `applySem`
  (`daemon_apply.go:69-70`); `installDNS` runs in the per-iface DHCP
  goroutine (`runDHCPv6` `dhcp.go:728`) with no shared lock → clobber
  race even with atomic rename.
- **F3 dual-stack clobber**: v4 + v6 goroutines each write only their
  own lease's servers → mutual wipe; `installDNS(lease)` takes one lease
  and has no merge.
- **F4 boot/commit blank-write**: first `applyConfig` runs before DHCP
  clients start; a DHCP-only box (no static `name-server`) gets a blank
  file on boot and on every later commit.

**Feasibility confirmed**: `dhcp.Manager.Leases()` (`dhcp.go:428`)
returns `[]*Lease`, each with `DNS []netip.Addr` + `Family` — a central
reconciler can read ALL v4+v6 leases and merge. The debounced
`onAddressChange` callback already exists (`dhcp.go:1172-1181`, wired at
`daemon_dhcp.go:36-41`) — the right hook to route DNS reconcile through
the locked path.

### Converged r2 design (REPLACES the r1 hybrid)
1. **Pure Option A only — drop the hybrid in this PR.** xpf owns
   `/etc/resolv.conf` as a managed plain file. `systemd-resolved` is
   `disable --now` + **masked** (defeats socket-activation re-creating
   the stub). Document: "resolved is not the DNS owner; remove the
   `services dns` resolved path or treat it as a separate future PR."
   Do NOT ship Option B's resolved-owner branch here.
2. **One `reconcileDNS(cfg)` under `applySem`.** Collapse
   `applySystemDNS` + `applyDNSService` into a single function called
   from `applyConfigLocked`. It: (a) merges static `cfg.System.NameServers`
   + live `dhcpMgr.Leases()` DNS (precedence: static first, then v4,
   then v6, de-duplicated); (b) renders via `pkg/daemon/system/dns.go`
   `RenderResolvConf`; (c) Lstat-guards (`os.Lstat`, no follow), removes
   a symlink, writes temp + `os.Rename` atomically, compare-before-write
   for idempotence; (d) disables+masks resolved deterministically;
   (e) removes legacy `bpfrx.conf`.
3. **DHCP never writes resolv.conf.** Delete the `installDNS` file
   write; the DHCP path stores DNS in the lease (already does) and fires
   the existing debounced `onAddressChange`. Route that callback so it
   triggers `reconcileDNS` (directly or via the recompile path) under
   `applySem`. Wire v4 DNS into the lease so v4 contributes
   (close the `DHCPv4Options.UpdateDNS` gap or always-merge from leases).
4. **Boot reconcile + merge**: `reconcileDNS` runs early in daemon init
   AND merges leases, so neither boot nor a later unrelated commit ever
   blanks the file. Because it reads live leases (not just `cfg`), a
   DHCP-only box stays resolvable across commits.

This eliminates F1-F4: one writer, one lock, full v4+v6+static merge,
no resolved dependency, idempotent, boot-safe.

## 6. Recommendation: **Option A via a single locked `reconcileDNS` (no hybrid)**

Rationale:
1. xpf already owns ALL interfaces, FRR, networkd configs (CLAUDE.md).
   Owning `/etc/resolv.conf` as a plain managed file is consistent and
   removes a runtime service dependency on a firewall appliance.
2. A plain file is the most robust resolver: no service to crash, no
   stub-dir lifecycle, survives deploy-wipe via the boot reconcile.
3. It directly kills the apply-order race (one reconciler, never
   enable-then-disable) AND the dangling symlink (Lstat-guard + remove)
   AND the silent installDNS failure (atomic write, MkdirAll-free since
   /etc exists, no symlink follow).
4. Resolved's advanced features (split-DNS, DNSSEC stub) are unused on
   this appliance; `system services dns` (DNSEnabled, the dns-proxy
   path) remains the explicit opt-in to the resolved-owner branch
   (hybrid), so we don't regress operators who want it.

**No hybrid in this PR** (killed round 1, §5b). If `system services dns`
is configured, the simplest correct behavior is a commit-check warning
("`services dns` resolved-owner mode not supported; xpf manages
`/etc/resolv.conf` directly") rather than a config-blind DHCP path that
fights resolved. A true resolved-owner mode, if ever wanted, is a
separate future PR with DHCP→`resolvectl` push (NOT file writes) and
must not share the file-writing reconciler.

## 9. Risks / gotchas
- **Deploy-wipe**: deploy may reset /etc; the boot reconcile must run
  early in daemon init so DNS is repaired before anything needs it.
- **Atomic write across symlink**: must `Lstat` + `Remove` the symlink
  BEFORE writing, then write temp + `Rename` onto the path; never
  `WriteFile` through a symlink (the silent-ENOENT bug).
- **Dual-stack / DHCP timing**: v4 + v6 leases can land at different
  times; reconciler must merge (not clobber) and define precedence
  (static name-server first, then v4 DHCP, then v6 — documented).
- **Idempotence**: compare-before-write; no `restartResolved` churn.
- **Hybrid branch correctness**: when `DNSEnabled == true`, do NOT also
  write the plain file (would fight resolved) — exactly one owner.
- **Don't break #1713**: renderer must emit combined Domains=/search.
- **Masking resolved**: decide mask vs. plain-disable; masking is more
  robust against socket-activation re-creating the stub dir, but is
  heavier-handed — evaluate at engineer time.

## 10. Acceptance criteria
1. On a box with `name-server` set and no `services dns`:
   `/etc/resolv.conf` is a real file with the configured servers; no
   dangling symlink; resolved inactive; resolution works.
2. Re-running commit/apply does not re-break DNS (no enable→disable
   race); idempotent (no needless rewrites/restarts).
3. Startup repairs a pre-existing dangling/stub symlink.
4. DHCP-learned DNS (v4 AND v6) installs without ENOENT through a
   symlink; merges with static name-server.
5. Legacy `bpfrx.conf` drop-in removed.
6. `system services dns` opt-in still selects the resolved-owner branch
   with exactly one owner (no file+drop-in conflict).
7. #1713 Domains= fix preserved/included.
8. Render + reconcile unit tests pass; smoke passes on loss cluster.

## 11. Resolved decisions (were open questions; settled round 1)
- **A vs B**: ship pure A (single locked file reconciler). No hybrid.
  A resolved-owner mode is a separate future PR if ever needed
  (DHCP→`resolvectl`, not file writes).
- **Mask vs disable**: mask AND disable — masking defeats
  socket-activation (`systemd-resolved-varlink.socket` /
  `-monitor.socket`, seen on fw0) re-creating the stub dir.
- **Precedence**: static `name-server` first, then DHCPv4, then DHCPv6,
  de-duplicated. Static is authoritative; DHCP augments. (DHCP does not
  override static.)
- **v4 DNS**: always merge DHCP-learned DNS from `Leases()` regardless
  of a req-options flag, so the box is never resolver-less; the
  `DHCPv4Options.UpdateDNS` field can be retired or repurposed.
- **#1713**: sequence #1713 (renderer extraction + Domains= fix) before
  #1715; #1715 absorbs the #1713 fix if not yet landed. Not one PR.
