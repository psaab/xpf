Verdict: **PLAN-KILL**

The plan introduces a critical correctness bug for NAT64 + PBR while chasing a microscopic performance gain (~0.001% of a core on the session-miss slow path). The core claim that `canonical_route_table` allocation can be entirely skipped on the hot path is empirically false due to NAT64 interactions. 

Here is the item-by-item verification with line-by-line evidence:

1. **Perf justification**: The plan correctly identifies that `flow_cache_hit.rs:93` (`flow_state.flow_cache.lookup_counted(...)`) short-circuits this logic for established flows. The hot call site at `poll_descriptor/mod.rs:1010` (`lookup_forwarding_resolution_in_table_with_dynamic`) is ONLY hit on session miss. A gain of ~100 cycles per session-miss is negligible at absolute scale.
2. **String allocation on the hot path**: The plan correctly observes that `lookup_forwarding_resolution_inner` unconditionally allocates today. At `forwarding/mod.rs:881-883`, the fallback `unwrap_or_else(|| DEFAULT_V4_TABLE.to_string())` allocates a `String` even when `table` is `None`.
3. **Cycle detection semantics**: Current code at `forwarding/mod.rs:1260` (`if next_table_name == table`) indeed only catches immediate self-loops. The test `forwarding_resolution_rejects_next_table_loop` at `forwarding/tests.rs:2128` relies on `forwarding_snapshot_with_next_table_loop` (`test_fixtures.rs:319-328`), which configures `next_table: "inet.0"` inside `"inet.0"`. Preserving the depth=8 cap for longer cycles is correct for Junos parity.
4. **v4/v6 namespace**: A shared map is perfectly safe and won't conflate routing tables. As seen in `types/forwarding.rs:21-22`, `routes_v4` and `routes_v6` are distinct `FastMap`s today. If a shared `route_table_name_to_id` map assigns ID 5 to `"my-vrf"`, the plan's `routes_v4_by_id[5]` and `routes_v6_by_id[5]` remain disjoint vectors, exactly mirroring the current FastMap architecture. 
5. **canonical_route_table semantics (THE FATAL FLAW)**: The plan claims the hot path at `poll_descriptor/mod.rs:1006` "already knows the family from the IP" and doesn't need `canonical_route_table`. **This is wrong due to NAT64.** 
   - Upstream, `route_table_override` is generated by `ingress_route_table_override` (`mod.rs:914-980`). If the original packet is IPv6, it returns `Some(format!("{routing_instance}.inet6.0"))` (an allocated string).
   - However, NAT64 pre-routing (`poll_descriptor/mod.rs:920-940`) translates the destination IP, so `effective_resolution_target` becomes IPv4.
   - The current code at `forwarding/mod.rs:881-884` correctly handles this mismatch: it matches on the *new* IPv4 destination, calls `canonical_route_table("foo.inet6.0", false)`, and rewrites it to `"foo.inet.0"`.
   - The plan's shortcut (`state.route_table_name_to_id.get(table)`) would look up `"foo.inet6.0"`, get the v6 table ID, and search for v4 routes in the v6 table (which will be empty). To fix this, you must run `canonical_route_table` on the hot path whenever `route_table_override` is present, breaking the "zero allocation" hot-path claim for PBR.
6. **Wire protocol risk**: `RouteSnapshot.next_table` remains a `String` on the wire (no changes proposed to the config snapshot), so there is no protocol breakage. `RouteEntryV4.next_table` (types/forwarding.rs:92) is purely internal.
7. **Go-side pre-flattening**: The issue body lists three proposed fixes. Deferring Go-side pre-flattening (Option 1) is a valid Rust-side decision, as Options 2 and 3 are self-contained alternatives designed to eliminate the same String-hash IPC cost. 
8. **Architectural mismatch**: The precedent is valid. The proposed shape exactly matches `#921 zone_id_to_u16` (`zone_name_to_id: FastMap<String, u16>` at `types/forwarding.rs:34`). 
9. **Snapshot rebuild cost**: HA failover timing is ~60ms (evidenced across `docs/ha-cluster-test-plan.md` and `CLAUDE.md`). A snapshot rebuild currently takes <1ms; doubling it for a second pass safely remains well within the 60ms budget.
10. **Test plan completeness**: The test plan misses NAT64 + PBR (`next_table`) interactions, which would have caught the fatal flaw identified in #5.

Because the hot-path zero-allocation claim is fundamentally broken for NAT64 + PBR, and the absolute perf gain is too small (~0.001% of a core on session-miss) to justify adding new structural complexity to fix it, this is an inflated issue that should be killed at the plan stage.
