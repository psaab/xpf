# #14641 — Port-mirror clone reads ingress UMEM chunk after possible FILL publish

## Defect
`enqueue_pending_forwards` (`userspace-dp/src/afxdp/tx/dispatch/mod.rs`)
ran the success-path `recycle_ingress_frame` before
`commit_staged_mirror_clone(..., source_frame)`. `recycle_ingress_frame`
pushes the ingress offset onto `pending_fill_frames` and, at the
1024-entry `FILL_BATCH_SIZE` threshold, synchronously calls
`drain_pending_fill`, which publishes the chunk to the kernel FILL ring
(`userspace-dp/src/afxdp/tx/rings.rs`). On the non-in-place arm
(cross-UMEM / tunnel / NAT64) the staged mirror clone holds no snapshot
— only the in-place arm snapshots first — so
`commit_staged_mirror_clone` then copies bytes out of live ingress UMEM
that may already be kernel-owned. The kernel can DMA a different packet
into the chunk in between, so the analyzer receives another flow's
bytes: wrong mirror content and cross-flow disclosure to the mirror
target. Forwarding itself is not corrupted. The in-tree invariant
comment claimed the frame is "not yet returned to fill ring (that
happens after this function completes)" — false on this arm.
`neighbor_dispatch.rs` already commits before recycling; only the
dispatch site was exposed.

## Fix
Move `commit_staged_mirror_clone` above the success-path
`recycle_ingress_frame` in `enqueue_pending_forwards`, matching
`neighbor_dispatch.rs`, and correct the frame-safety invariant comment
to state the real guarantee (success-path recycle is deferred until
after the mirror commit; the retained/in-place arm keeps the chunk
owned by the prepared TX request; failure/drop arms recycle with no
later read). A `#[cfg(test)]` `FILL_PUBLISH_HOOK` seam in
`drain_pending_fill` fires immediately after a batch is published to
FILL so a test can model kernel DMA ownership; it adds no release-build
state or call.

NOT changed: `recycle_ingress_frame` batching, `drain_pending_fill`
itself, the build-failed recycle (no later read on that arm), the
in-place snapshot arm, and mirror sampling/counting (`#11432`,
`#13656` counting/perf issues are untouched).

## Tests
`mirror_clone_copies_frame_before_fill_publish_14641`
(`userspace-dp/src/afxdp/tx/dispatch/tests/ptb.rs`): three bindings with
distinct UMEMs (non-in-place arm, no snapshot), a 60-byte UDP frame at
ingress offset 0, 1023 stale `pending_fill_frames` entries cycling the
256 valid frame bases so the success-path recycle crosses the 1024
threshold, and the `FILL_PUBLISH_HOOK` scribbling `0xA5` over the source
chunk the instant it is published to FILL (modelled kernel DMA).

- **RED** (production fix reverted, hook + test present):
  `mirror_clone_copies_frame_before_fill_publish_14641` failed at the
  `mirror == frame` assertion — mirror bytes were all `0xA5` (165)
  instead of the frame starting `aa bb cc dd ee ff ...` (170, 187, ...).
- **GREEN** (fix applied): the same test passes — the clone is copied
  while the chunk is still userspace-owned; the publish then runs only
  at the function-tail drain.
- Controls `successful_forward_commits_one_mirror_clone_11432` and
  `mtu_signalled_forward_does_not_enqueue_mirror_clone_11432` stay green
  before and after: the defect is ordering, not counting/suppression.

## Risk
The success-path recycle now happens a few instructions later (after
the mirror commit), within the same request iteration and before the
tail fill drain — chunk return latency is unchanged in aggregate.
In-place (retained) forwards are unaffected. Mirror clones on the
non-in-place arm now always carry the pre-publish bytes, as the
analyzer contract already assumed.
