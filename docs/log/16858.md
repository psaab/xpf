# #16858 — R3-B04-02: one-shot / rollback signing-key change produces a key the peer's active config does not accept

- **Timestamp**: 2026-10-25
  - **Action**: Added the candidate-vs-active transition interlock `validateClusterAuthKeyTransitionStrict` (`pkg/config/compiler_validate_strict_cluster_auth.go`): on the strict candidate pipeline, a candidate may only sign with a key already in the ACTIVE config's accepted set {`authentication-key`, `additional-authentication-key`}. From active {A}, `set authentication-key B; commit` is now refused with a pointer to the five-step #6630 procedure (previously it committed silently and each node rejected the other's heartbeats until the peer committed, the pre-#6630 dual-master window); rollback from a finalized {B} to a pre-rotation {A} config and the same candidate staged by `load override` are refused at the commit that promotes them (both only stage the candidate). Steps 1/2 (sign A), 3/4 (sign the staged B), 5 (finalize, sign B), rollback while the overlap is open, routine same-key commits, first keying (no active cluster/key), and cluster removal all pass. The active accepted set is plumbed alongside the existing #16025 current-primary through `currentClusterOpts` / `compileOpts.currentClusterAccepted16858`, supplied only by configstore's candidate pipeline (`s.compiled`) including the #9619 peer view; fresh/day-0/`CheckText` compiles have no current and keep the gate closed. Tolerant load/peer-sync (`SyncApply`) still boots a mismatched config with the rejection downgraded to a warning (#1960 no-brick). Error never echoes key material.
