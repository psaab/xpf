# #12648 — packed static route next-hop and qualified next-hop

## Red before

A hierarchical one-liner

```text
routing-options { static { route 10.5.0.0/16 next-hop 10.0.0.1 qualified-next-hop 10.0.0.2 preference 250; } }
```

parsed into one route `next-hop` node whose keys included the later
`qualified-next-hop`, gateway, and preference tokens. Compilation succeeded but
published all five tokens as plain gateways. The equivalent unpacked hierarchy
and flat `set` statements produced a primary gateway plus a qualified backup
with preference 250.

## Change

The compact normalizer now splits a complete packed `qualified-next-hop`
statement from the route's multi-value `next-hop` property before both strict
schema validation and compilation. Its gateway and optional interface,
preference, and metric are represented as the existing qualified-next-hop node
and modifier children, preserving the same per-next-hop backup semantics as
unpacked syntax. Incomplete or unsupported suffixes remain fused, so the
existing schema walker rejects them rather than the normalizer guessing.

Added regression tests to compare packed and unpacked forms through both
`SchemaValidate` and compilation, reject missing/keyword gateways and unsupported
suffixes, and ensure the normalizer leaves unrelated `route` nodes untouched.
