# #12648 — packed static route next-hop and qualified next-hop

## Red before

A hierarchical one-liner

```text
routing-options { static { route 10.5.0.0/16 next-hop 10.0.0.1 qualified-next-hop 10.0.0.2 preference 250; } }

parsed into one route `next-hop` node whose keys included the later
`qualified-next-hop`, gateway, and preference tokens. Compilation succeeded but
published all five tokens as plain gateways. The equivalent unpacked hierarchy
and flat `set` statements produced a primary gateway plus a qualified backup
with preference 250.

## Change

In `compileStaticRoutes`, the `next-hop` child reader now recognizes a packed
`qualified-next-hop` clause in the same property key run. It retains the
qualified gateway's optional interface, preference, and metric as per-next-hop
settings, appending the qualified entry after the plain next-hop entries. The
fix is confined to this inline packed-key shape; the existing hierarchical and
flat-set qualified-next-hop handlers are unchanged.

Added `TestPackedStaticRouteNextHopAndQualifiedNextHop_12648`, which compares
the packed one-liner and unpacked control against the expected primary and
floating-backup entries.

## Validation

- Before the fix, the probe compiled the packed one-liner with five plain
  next-hop addresses; the unpacked and flat controls each produced the expected
  two entries.
- `go test ./pkg/config -run '^TestPackedStaticRouteNextHopAndQualifiedNextHop_12648$' -count=1` — passed.
- `go test ./pkg/config -count=1` — failed in the repository-wide package suite
  at its 10-minute timeout. It reported failures in inventory census,
  duplicate-name / API-auth validation, packed-routing-instance controls, and
  schema coverage gates. The focused #12648 regression passed independently.
