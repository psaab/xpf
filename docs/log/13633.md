# Issue #13633 — classify generated TCP replies with their flags

## Why

Locally generated TCP replies are parsed by `generated_reply_session_key` before output-filter evaluation. The parser populated tuple and IP metadata but left `ForwardPacketMeta::tcp_flags` at its default zero. `term_match_extra_from_frame` trusts that metadata field, so a `filter output` term matching the reply's actual TCP flags (for example, `tcp-flags rst then discard`) did not match and the reply could bypass the configured filter.

## What

The shared generated-reply parser now reads the TCP flags byte from its parsed L4 offset and carries it into `ForwardPacketMeta`, covering IPv4, IPv6 (including the existing extension-header walk), and every local-reply generator using the common classifier. The read is bounded by the IP-declared packet length; a TCP reply whose declared datagram ends before the flags byte fails closed. Non-TCP replies retain zero flags. Added parser regressions for v4/v6 flags and short declared lengths, plus an output-filter regression proving a generated TCP RST matches a `tcp-flags rst` discard.
