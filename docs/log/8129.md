# #8129 — delete the #7342 tcp-session enforcement advisory

- **Timestamp**: 2026-10-14 (`fix/8129-campaign-pub`)
- **Action**: deleted `tcpSessionTimeoutAdvisory`, its call site, and the cells
  that pinned it. Nothing else.

## Why now

The advisory was #7342's upgrade posture: the population carrying a configured
`security flow tcp-session initial/closing/time-wait-timeout` was exactly the
operators who set one while #6539 was telling them it did nothing, and the
upgrade across #7342 activates that value. The advisory said so at commit,
inverted from #6539's accepted-only text.

It was temporary by construction and this issue was its deletion object. The
deferral was **"one release past the boundary"**: v0.9.3-ha-perf-hardened
shipped 2026-03 and master is far past it. #7342 landed 2026-08-30; master has
carried the advisory for six weeks of daily commits since, and no tag has been
cut in seven months. The issue's own 2026-09-04 comment flagged that the
tag-shaped gate ("a tag past v0.9.3 has shipped and deployed") requires a
manual tagging action nobody is taking and proposed restating it as the
property actually cared about — the advisory having been in shipped builds
long enough that operators have seen it. That restated gate is met.

Recorded rather than papered over: no tag past v0.9.3 exists as of this
deletion (`git tag --list 'v*' --sort=-v:refname | head -1` still prints
`v0.9.3-ha-perf-hardened`). If a v0.10 is ever cut, an operator upgrading from
a pre-#7342 build straight to it will not see the commit-time line — the
release note for that release should carry the #7342 activation note instead.
