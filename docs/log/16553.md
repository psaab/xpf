# #16553: honor server-supplied T1/T2 (IA_NA, IA_PD, DHCPv4 options 58/59)

- **Timestamp**: 2026-10-24
- **Problem**: The client never read server T1/T2. `renewalTimers` was
  always 50%/87.5% of the single IA_NA `LeaseTime`, so a delegated
  prefix whose valid lifetime ended before that T1 was pruned and
  withdrawn from LAN RA (`DelegatedPrefixesForRA`), only re-requested
  at the IA_NA T1 — recurring every cycle. Servers using a short T1 to
  drive renewal/renumbering were likewise ignored. This violates
  RFC 8415 §18.2.4 (Renew/Rebind not later than the earliest T1/T2 of
  any binding) and RFC 2131 §4.4.5 (0.5/0.875 are only defaults when
  options 58/59 are absent).
- **Fix**: Carry server T1/T2 per binding and schedule off the
  earliest. `Lease.RenewAt/RebindAt` holds the IA_NA T1/T2 (via a new
  `ianaTimers` walk matching `selectIANAAddress`'s chosen address) or
  DHCPv4 options 58/59 (`IPAddressRenewalTime`/`IPAddressRebindingTime`);
  `DelegatedPrefix.RenewAt/RebindAt` holds each IA_PD's T1/T2.
  `carryForwardV6IANA` preserves the timers across address-less
  renewals. A new `renewalSchedule(leaseTime, pds, srvT1, srvT2)` in
  `commit.go` takes the earliest non-zero T1/T2 across the lease and
  all held prefixes, falls back per-tier to 50%/87.5% of the shortest
  held valid lifetime when the server left a tier at zero, and clamps
  so `0 < T1 < T2 < shortest-valid` for finite lifetimes (server
  T1/T2 at/after expiry or T2 ≤ T1 pulled back to defaults; the
  infinite sentinel keeps T1 < T2 only). `renewalTimers` is now the
  no-server-timer wrapper, so existing callers/tests are unchanged.
  Both run loops call `renewalSchedule` (v6 passes the committed PD
  set). `LeaseTime` remains the expiry anchor (IA_NA valid; shortest
  PD valid on PD-only/address-less leases) — only the schedule reads
  the extra bindings, so #14598 per-prefix pruning and #14998 anchored
  waits are preserved; the #14998 prune test's assertion is updated
  because an already-expired PD now correctly drives an immediate
  Renew instead of merely a ~1s remaining IA_NA wait. PD T1/T2 join
  `delegatedPrefixesChanged` so a timer-only change propagates.

  `pkg/dhcp/dhcp.go`, `pkg/dhcp/dhcpv6.go`, `pkg/dhcp/dhcpv4.go`,

  `pkg/dhcp/dhcpv6_coheld_invalidate_14998_test.go`,

- **Validation**: New `server_t1t2_16553_test.go`: a 13-row
  `renewalSchedule` table (RFC-default control, IA_NA T1=60s
  acceptance, honored T2, short-PD fallback at 50s, IA_PD T1=1s defect
  cell, earliest-across-prefixes, one-sided fallbacks, degenerate
  at-expiry/T2<T1 clamps, zero-lease invalid, infinite sentinel);
  parse-level Reply carrying IA_NA T1=60s + IA_PD T1=1s/T2=80s/valid
  100s asserts both timer sets and the effective 1s/80s schedule; a
  no-T1/T2 control Reply keeps defaults; DHCPv4 ACK with options
  58/59 asserts (60s,120s) and a bare ACK stays zero; two run-loop
  cells through `runDHCPv6` with the exchange/`after` seams assert
  the recorded T1 wait is ~1s (server) / ~50s (fallback) and
  `DelegatedPrefixesForRA` still holds the PD at Renew. RED-on-revert
  verified by neutralizing the server/PD terms in `renewalSchedule`:
  all five new test entry points failed, then passed again on restore.
  Full package: `go test ./pkg/dhcp/ -count=1` green (including the
  updated #14998 cell); `go vet ./pkg/dhcp/` clean.
- **Residuals**: The run loop anchors T1/T2 at `committed.Obtained`
  (the IA_NA grant instant); IA_PD T1/T2 values are applied as
  durations from that same anchor even though each PD carries its own
  `Obtained` (in practice replies grant IA_NA+IA_PD together and
  renewals refresh both, so the anchors coincide). No lab/end-to-end
  RA-withdrawal re-verification was performed; the RA leg is covered
  at component scope via `DelegatedPrefixesForRA` as in #14598.
