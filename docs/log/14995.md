# #14995 — cross-family DDNS sibling claims hijack names and poison DHCID prerequisites (D40-01)

## Defect

Unauthenticated cross-family DDNS hostname hijacking and RFC 2136
multi-RR DHCID prerequisite poisoning via `crossTypeSiblingOwned`
(report claim D40-01, severity Critical, 3-way MATERIAL consensus in
validator run `tpzkKgAuZL`).

The manager's sibling scan (`pkg/ddns/manager.go`, pre-fix
`crossTypeSiblingOwned`) matched on canonical FQDN + opposite
address family ONLY — not on client identity, subnet, scope, or
endpoint. A bare DHCP REQUEST is the only input that creates a Kea
lease row (leases are unauthenticated), so any LAN client that
merely REQUESTED a victim's hostname from the opposite family
became a trusted "sibling" in the ownership store. `upsertLocked`
then stamped `LeaseDNSRecord.SiblingFamilyOwned=true` and the
RFC 2136 backend (`pkg/ddns/backend_rfc2136.go`) downgraded the
foreign claim:

- `sendAddOwned` sibling branch: inserted the foreign A/AAAA plus a
  FOREIGN DHCID at the victim's name under a per-type
  `RRsetNotUsed` prerequisite — a second DHCID RR at one owner name,
  in violation of RFC 4701 §3.5 / RFC 4703 (DHCID is one RR), and
- `sendAdd` (skip-existing/strict-fail): downgraded the name-level
  `NameNotUsed` guard to per-type `RRsetNotUsed`.

`upsertLocked` recorded phantom ownership for the foreign tuple, and
the foreign client's later release aimed `sendRemoveForward`'s
DHCID-match prerequisite at the victim's name (real deletes never
carry a sibling signal — the bypass was add-only). RED proof
(pre-fix, `origin/master` 291ddb0066): all three new
`TestCrossFamily*14995` cells fail — foreign AAAA/A published at the
victim's name under both `replace-owned` and `skip-existing`.

## Fix

The store is demoted from proof to candidate source; the wire
DHCID is the proof.

- `crossTypeSiblingOwned` now returns the sibling RECORD, narrowed to
  same scope (every `ScopeKey` axis except Family) + same backend
  endpoint (`BackendFingerprint`), and `upsertLocked` threads its
  `ClientID` as `LeaseDNSRecord.SiblingClientID` (upsert-only;
  deletes are untouched — `sendRemoveForward` still replays the
  publishing identity and never receives a sibling signal).
- Same-pass pairing: `reconcileOnceLocked` stamps
  `LeaseDNSRecord.PairedClientID` when the opposite family's desired
  record in THIS pass is the same device (`sameDeviceClient`) at the
  same scope+endpoint — covering the first pass, before any store
  row exists. A foreign REQUEST never pairs (different device).
- Device pairing (`pairedIdentityKey`, `pkg/ddns/state.go`):
  verbatim-equal identities pair; a MAC-based DUID (LLT/LL) pairs
  with the v4 `mac:`/Ethernet-client-id MAC; anything unpairable
  fails closed.
- Device DHCID (`dhcidDigestClientID`): the digest folds the DEVICE
  key, so one device writes ONE identical DHCID RR across both
  families (second Insert is idempotent). Add/delete are symmetric
  through `dhcidRR`; `dhcidSharedWithOther`/`dhcidStillWanted`
  compare device digests so the shared DHCID survives a partial
  teardown and is removed by the last family.
- Wire proof (`proveSiblingDHCID`): before any downgrade, the
  backend sends a prerequisite-only `Used(sibling-DHCID)` UPDATE —
  NOERROR proves, NX/YX refuses. Only a proven sibling reaches the
  per-type adds (`sendAddSiblingProven` / skip-existing
  `RRsetNotUsed`); an unproven claim falls through to the unchanged
  Attempts A/B / `NameNotUsed` guards and is refused with
  `errDDNSConflictRefused` (no phantom ownership).
- skip-existing/strict-fail write no DHCID on the normal path, so a
  successful same-device first-family add publishes the device
  marker once per updater (`siblingMarkerRR`) as the sibling's
  proof target.

Legitimate dual-stack behaviour is preserved, not re-broken:
`TestDualStackProductionIdentitiesBothPublishReplaceOwned` (#14602)
and `TestPartialDualStackTeardownKeepsSharedDHCID` (#2700) stay
green (fixtures strengthened to a genuinely paired device:
Ethernet-client-id v4 + DUID-LL v6 embedding the same MAC — the
pre-#14995 opaque fixtures could not prove same-device and now
correctly fail closed).

## Residual

- Pre-#14995 wire records carry the legacy per-identity DHCID
  digest; a guarded delete computes the device digest, so a legacy
  record's delete is a counted skip (ownership dropped, stale RR
  remains for the operator; a same-device re-publish converges the
  name). Documented in `pkg/ddns/README.md`.
- Opaque client pairings (v4 opaque client-id vs opaque DUID with
  no embedded MAC) cannot be proven same-device and fail closed:
  the second family is refused until an operator-visible same-device
  proof exists. This is the safe direction (refuse, never hijack).
