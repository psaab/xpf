# Issue #13476: claim eligible flow heads atomically

- **Root cause:** `dispatchEligible` selected flow heads under `p.mu` but did not mark them claimed before unlocking. Concurrent Poll, ingress, or scoped-cancel dispatch calls could therefore select and dispatch the same head. The duplicate enforcing dispatch then observed the winner's `flow.pending` and terminalized the original packet while admission was still in progress; D11 had the analogous failure path.
- **Change:** Added per-flow `dispatching` state. `eligibleLocked` atomically marks only the returned, batch-cap-limited flow heads while holding `p.mu`; competing dispatchers skip claimed heads. Ordinary and D11 admission replace the claim with the pending reinject, while `finishFrame` releases a claim when the head is terminalized. This does not serialize Poll behind the submitter call.
- **Regression:** `TestCapturePipelineConcurrentDispatchClaimsFlowHead13476` holds the first dispatch in zone evaluation and invokes a second dispatcher. RED on pristine `origin/master` (`9836528dd`): `concurrent dispatch evaluated 2 times and terminalized 2 times, want 1 each`. GREEN after fix; also passes under `-race`.
- **Review coverage:** Added enforcing-path coverage confirming the first dispatcher retains the single `flow.pending` admission and no DROP occurs, plus a batch-cap test confirming a second eligible flow head remains available. Both new tests fail on pristine `9836528dd` and pass on the merged fix.
