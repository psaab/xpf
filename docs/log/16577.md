# #16577: routing-policy `from protocol` tolerant downgrade + Junos ospf3/ospf2 aliases

- **Timestamp**: 2026-10-24
- **Problem**: The #7121 gate `validateRoutingPolicyProtocolsStrict` ran
  unconditionally in `runEarlyStrictAndFolds`, unlike its lenient-flagged
  neighbours. A persisted (Store.Load) or peer-synced (HA SyncApply) config
  carrying a Junos source protocol FRR cannot emit — `aggregate`,
  `local`, `access-internal`, or a typo — failed compilation with
  `ErrConfigCompile`, putting the daemon into the bootstrap/lifeline state
  with no forwarding config (#1960 no-brick violation). Junos `ospf3` was
  also strict-rejected although it is a valid OSPFv3 spelling.
- **Fix**: (1) `FRRRoutingProtocolKeyword` (the SSOT) now aliases Junos
  `ospf3`→`ospf6` and `ospf2`→`ospf`, so `from protocol ospf3`
  strict-commits as OSPFv3 through the gate, route-map rendering,
  sequence counting, and redistribute resolution. (2) New
  `lenientRoutingPolicyProtocols16577` opt (registered in
  `lenientCompileOpts()`, pinned by the #16166 completeness test): on
  tolerant load / peer-sync the gate warns and
  `failClosedRoutingPolicyProtocols16577` forces each offending term to
  `reject` (clearing `NextPolicy`), mirroring the #11779
  UnknownFrom poison. (3) Render belt in `pkg/frr/policy_render.go`: an
  unresolvable token never emits a `match source-protocol` line; the
  poisoned sequence renders as a bare deny.
- **Audit of sibling no-downgrade early validators** (named in the
  issue): `validateClassOfServiceStrict`, `validateThreeColorPolicersStrict`,
  `validateRPMProbePinsStrict`, and `validateIPMonitoringStrict` were
  inspected and left strict on all paths. Rationale: their rejected
  shapes are typed-model invariants (mutually-exclusive rate modes,
  NaN/out-of-range percents, missing required rates, probe-table band
  overflow, dangling rpm-probe references, unparseable destinations)
  with no older-binary-accepted spelling to downgrade to, and several
  already carry dedicated lenient siblings for their downgradeable
  sub-checks (`lenientCoSSchedulerPriority`, `lenientRPMSourceAddress`,
  `lenientRPMRoutingInstance`, …). No legacy token class was found that
  an older binary persisted and these gates now reject; downgrading them
  would publish ambiguous CoS/RPM/IP-monitoring state instead of a
  contained per-term reject. This is a deliberate scope boundary, not an
  oversight.

  `pkg/configstore/routing_policy_protocol_16577_test.go` (new),
  `pkg/frr/policy_protocol_tolerant_16577_test.go` (new),

- **Validation**: `go vet` clean on the three touched packages; targeted
  `go test` green — config (`TestRoutingPolicyProtocol*16577`,
  `TestJunosOSPFVersionAliases_16577`, extended #7121 domain table,
  lenient-completeness), configstore (Store.Load + SyncApply rows for
  aggregate/local/access-internal + ospf3), frr (render belt). The frr
  subset `Redist|PolicyRender|RouteMap|Export` shows exactly one failure,
  `TestBGPNoExportNeighborGetsDefaultExport15157`, which fails
  identically on unmodified origin/master (pre-existing; unrelated).
- **Risk**: Tolerant paths now boot configs strict commit still rejects;
  the poisoned term rejects routes its authored accept would have
  permitted until the operator fixes the token — the fail-closed
  direction, and the warning names statement/term/token. `ospf3` as a
  bare `export` token now resolves as an OSPFv3 source (previously
  skip-and-warn), matching Junos semantics. Strict-path behaviour for
  every previously accepted token is unchanged.
