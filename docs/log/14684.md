# Chained flat IPsec run bypasses traffic-selector/plaintext gates (#14684)

## Why

`compileIPsec` iterates `expandIPsecVPNRun9088(inst.node)`, which flattens
a chained flat `set` run under `security ipsec vpn <name>` into one node
per leaf, so every leaf in

```
set security ipsec vpn v1 gateway gw1 ipsec-policy epol1 bind-interface st0.0 local-identity corp.example.com remote-identity 10.0.0.0/008
```

lands on the typed VPN (`BindInterface="st0.0" LocalID="corp.example.com"
RemoteID="10.0.0.0/008"`). Two sibling gates read only DIRECT children,
so the same values escaped them while the braced/split spelling of the
same values was rejected/warned:

- `validateIPsecTrafficSelectorsStrict` used
  `vpnInst.node.FindChildren(leafName)` for `local-identity` /
  `remote-identity`. Chained, those leaves are nested inside the run, so
  the #8003 gate (FQDN identity — strongSwan discards the whole
  connection for it as `local_ts`), the #12507 gate (helper-refused
  zero-padded mask `/008`), and the #4098 value rules behind them never
  saw the value.
- `warnSecureTunnelPlaintextUnadjudicatedAST` used
  `inst.node.FindChild("bind-interface")`. Chained after `gateway`, the
  bind is invisible, so the #5619 unadjudicated-plaintext advisory was
  suppressed for exactly the tunnels it exists for.

The #2933 bind-interface gate already read the run via
`findChildInRun9088`/`findChildrenInRun9088`; these two gates did not.

## What

- `pkg/config/compiler_ipsec_trafficselector.go`: the
  `local-identity`/`remote-identity` loop now iterates
  `findChildrenInRun9088(vpnInst.node, leafName)` — the same
  `expandIPsecVPNRun9088` segmentation the compiler uses — so every
  occurrence the compiler could install is validated, in run order, on
  both the strict (error) and lenient (warning) paths. Value rules
  (`trafficSelectorValueReject`: control/whitespace, selector shape,
  helper-refused padding) are unchanged.
- `pkg/config/compiler_ipsec_plaintext_warn.go`:
  `warnSecureTunnelPlaintextUnadjudicatedAST` now collects every
  `bind-interface` occurrence via `findChildrenInRun9088` and keeps the
  last non-empty value (the compiler installs the last). Still
  warning-only, still no error return — the #1960 no-brick posture is
  structural and unchanged.
- Tests: new `pkg/config/compiler_ipsec_flatrun_gates_14684_test.go`
  with the named fixture
  `TestIPsecVPNFlatRunTrafficSelectorAndPlaintextWarn9088`: strict
  chained FQDN rejection naming #8003 (with a split-form control),
  strict chained `/008` rejection naming #12507, lenient chained
  warnings for both with the compiled values asserted as the premise,
  #5619 advisory for chained and mid-chain bind-interface, braced and
  chained valid-selector controls that stay clean, and a repeated
  chained identity whose last (compiler-installed) value is gated.

NOT changed: `expandIPsecVPNRun9088`/`expandFlatRun` segmentation, the
traffic-selector (`local-ip`/`remote-ip`) arm (already run-aware via
#8939), the #2933 bind gate, schema declarations, or any renderer.
No other VPN-leaf gate reads direct children for these leaves (audited
`FindChild`/`FindChildren` over `security ipsec vpn` readers).

## Risk

The selector gate now also validates identity leaves that arrive via
the compact hierarchical tail (`vpn <name> gateway …` on the VPN node's
own Keys), because `expandIPsecVPNRun9088` covers that shape too — that
is the same class, not new scope: the compiler already installed those
values. The plaintext advisory now fires for chained binds it
previously missed; it remains advisory-only and cannot reject. Lenient
load/peer-sync still warns instead of erroring, so persisted chained
configs still boot (#1960).
