# #14425 — Routing policy-statement same-term conflicting `then` (DR16-H3)

## Mechanism (re-anchored at origin/master 9908466d9)

- `parsePolicyTermChildren` (`pkg/config/compiler_routing.go`) assigned
  `term.Action = "accept"` / `"reject"` unconditionally per arm, and
  `parsePolicyTermInlineKeys` did the same for packed/flat spellings.
  `PolicyTerm` had a single `Action` field, no accumulation, no gate.
- Two producers lose the conflict before the compiler even sees it:
  1. Braced/hand-authored twin (`then { accept; reject; }`, flat-set twin):
     compiler last-write-wins.
  2. Group merge: `mergeNodes` inline-wins override silently DROPPED the
     group `then accept` leaf beside an inline `then reject` leaf (probe:
     expanded tree kept only `then reject`, `from` unioned bgp+ospf).
     The work-package claim "merge SUCCEEDS, group wins" was inaccurate
     at current master for the leaf spelling — measured override drops
     the group side; either way no conflict evidence survived.

## Fix

- `PolicyTerm.TerminalActions []string` (`json:"-"`) accumulates every
  accept/reject in both readers (children + inline keys).
- `validateRoutingTermTerminalConflictStrict` (mirrors #4375/#3043):
  strict-reject naming statement, term, both actions. Wired in
  `runUniformGatesRoutingRibRPM` after #11779; lenient opt
  `lenientRoutingTermTerminalConflict` warns + `failClosedRoutingTermTerminalConflicts`
  forces reject / clears NextPolicy.
- Group terminal adoption (`group_routing_term_then_14425.go`):
  mergeNodes adopts a group routing-term terminal (then leaf/container,
  accept/reject inside then, then-first packed term leaf) beside any
  peer instead of dropping it via the inline-wins override, so the
  compiler gate decides. Same-action repeats stay legal;
  statement-level default `then` is DR17-H4 (#14433), untouched.
