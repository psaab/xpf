# Issue #16218 — Synced flows deleted at RG1 failover

## Finding

FZDiag3 proved the four synced P4 flows were deleted from both nodes
within <=3s of the RG1 move with `snat_revoked=0`, but cell1 did not
collect the `session_gc_*` counters (its metrics regex omitted them), so
the deleter could not be named from that evidence. The timer wheel's
normal-expiry classification (`WheelPopStats.expired`) was also never
exported, leaving no counter that could separate normal Age expiry from
the standby-gate reaps.

Code inspection found the failover-shaped deleter in
`SessionTable::standby_gate_decision`: any peer-synced TCP row still in
its opening/handshake-pending window (`!established || handshake_pending`,
20s default) that crossed its idle deadline returned `ReapStaleSynced`
immediately, before the promotion SelfHeal arm and before the standby
Hold arm. A promoted copy whose local handshake never completed (hits
crossed the fabric or the flow cache) therefore reaped at the first GC
pass after the move instead of self-healing; the demoted copy on the old
owner reaped instead of holding.

## Changes

- Opening/handshake-pending peer-synced rows now take the same
  SelfHeal/Hold path as established rows. The lost-Close bound is
  preserved through the Hold ceiling: `min(3 x opening window, 7d)` from
  `first_held_ns`, never the application timeout.
- Exported the wheel's normal-expiry count end-to-end as
  `xpf_userspace_session_gc_expired_total` (Rust worker runtime ->
  protocol status -> Go status -> Prometheus), so a failover loss can be
  attributed among expired / reaped-stale-synced / held / healed counters.
- Updated the #10888 opening test to held-then-ceiling-reap and added
  `promoted_opening_gc_16218_tests.rs`: promotion self-heals, demotion
  holds, both bounded.

## Validation

Instrumented live cell (deb `99.16218.1.dirty`, evidence
`/var/worktrees/fzreaper/cell1/`): aged P4 flows still zeroed permanently
at the RG1 move, and the pre-failover rate tax persisted (3.65 Gbps vs
14.4 Gbps on restored clean master). The GC counters were FLAT across
the failover on both nodes (`reaped_stale_synced` 0 throughout,
`expired` and `healed_on_promote` unchanged pre/post move,
`snat_revoked` 0/1), so in THIS run the GC gate did not delete the flows
and this fix alone does not restore failover forwarding; the remaining
death is downstream of session existence (forwarding/fabric stage) and
needs a further instrumented run with fabric counters at 1s cadence.
The GC change stands as a correctness fix for the promotion window
(unit-tested), not as the proven failover cure. Cluster was restored to
clean master `working-20889-g2c8575b70e` (dp sha `2f2f5cbf...`) with
P4 verified at 14.4 Gbps.
