- **Timestamp**: 2026-11-16 (fold cycle 1, Codex review of b7e, findings 3

- **Action**: The text census stripped only `//` comments, so a `/* ... */`
  block comment or a string literal containing a hook's name counted as a
  caller. It also keyed hooks by bare name: `Monitor.SetTickForTest` in
  pkg/clockskew and in pkg/natpoolalarm shared one counter. And it never
  checked a baseline row's file against the definition.
- **Action**: Replaced it with a Go test, `internal/fortestcensus`, using the
  stdlib only:
  - every module file is parsed with go/parser, and every package group
    (in-package tests included, plus each external `_test` package) is
    type-checked with go/types. A module-internal importer type-checks
    imports from the parsed ASTs, the standard library comes from the
    toolchain's export data, and third-party imports are stubbed;
  - a reference is an identifier that resolves to the hook, so comments and
    strings can never count;
  - a hook is keyed by package directory, receiver type and name;
  - a reference types cannot resolve (a call through an interface) falls
    back to the unique hook of that name, then to the file's own package and
    its imports. An ambiguity is a FAIL, never a guess;
  - a baseline row must name the defining file, so a moved hook fails.
  - The baseline row is now
    `pkg/linuxsock.(PpollRecv).AttachRecvFnForTest`.
  - The Python census and its selftest are deleted. The two make targets run
    the Go test; it also runs in `make test-go`. Needs the Go toolchain, so
    it runs on a runner.
  - My first two drafts had false "dead" results, caught on the real tree
    before landing:
    - an import-scoped syntactic match missed six pkg/cluster/pkg/ddns
      hooks reached through `d.cluster.X()`;
    - stubbing the standard library left `atomic.Pointer[T].Load()`
      untyped, so one pkg/logging `SyncForTest` call read as ambiguous.
