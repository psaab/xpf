# #14578 — Commit-confirmed timeout revert rewrites active.json without rebinding rollback-meta.json

## Defect
`PromoteRollback` (`store_commit.go`), expired-window boot recovery
(`recoverPendingConfirmLocked`, `store_persist.go`) and the persist-retry heal
(`retryActiveConfigPersistLocked`) rewrite `active.json` via `writeActive`/
`writeActiveMarker` without calling `saveRollbackFiles`. `fsatomic` creates a
new inode per write, so `rollback-meta.json` (bound to hash+dev+inode+mtime of
the old active file, #10723 F2) mismatches on the next restart:
`loadRollbackHistory` tombstones every slot, `rollback N` reports unreadable,
and the next commit persists tombstone markers. The rollback ladder is lost
in exactly the recovery scenario it exists for.

RED on `origin/master` (a615690ed): three new tests fail with
`rollback slot does not match its saved generation` (slots 1-3) and
`rollbackEntry(1): rollback slot 1 is unreadable`.

## Fix
- `pkg/configstore/rollback_metadata.go`: new `rebindRollbackMetadataLocked()`.
  After a successful active rewrite that does not shift history, it bumps the
  sidecar generation and rewrites `rollback-meta.json` binding the existing
  in-memory history to the current on-disk active hash/inode. Slot bytes are
  re-read from disk (not re-rendered), missing slot files are rewritten, and
  tombstone entries keep their marker bytes. Failure is degrade-not-fail
  (`RollbackHistoryDegraded` + `rollback_persist_error` journal), mirroring
  `saveRollbackFiles`.
- `pkg/configstore/store_commit.go`: `PromoteRollback` success arm calls rebind.
- `pkg/configstore/store_persist.go`: boot-recovery success arm and
  `retryActiveConfigPersistLocked` heal call rebind (unconditional in retry —
  idempotent, covers commit/sync heals as well as rollback heals).

NOT changed: the generation/inode binding itself (still rejects genuinely
stale sidecars, #10723 tests pass), history shifting (PromoteRollback still
does not push a history entry — the reverted-from config is not added, per
issue scope), `Save()` (has no production callers; documented if it ever gains
one it must rebind), and the api-auth migration writer (already rebinds via
`Load`'s `saveRollbackFiles`).
