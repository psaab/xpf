# #15100 — exact queue self-park lag vs fixed K/STALL carry windows (A70-02)

- **Timestamp**: 2026-10-19
- **Action**: make the v8 lease rotation's lag (K) and stall windows
  rate-relative and size the carry reservoir in bytes at lease
  creation, so a backlogged exact queue parked for its own frame-refill
  time recovers its full rate credit on revisit instead of being
  credited 1.6 ms, banking a sub-frame residue, and dropping it at the
  next equally-lagged visit.
- **Files**: `userspace-dp/src/afxdp/types/shared_cos_lease/epoch.rs`,
  `userspace-dp/src/afxdp/types/shared_cos_lease/lease.rs`,
  `userspace-dp/src/afxdp/types/shared_cos_lease/mod.rs`,
  `userspace-dp/src/afxdp/types/shared_cos_lease/rotate_epoch_v8.rs`,
  `userspace-dp/src/afxdp/types/shared_cos_lease/shared_cos_lease_tests.rs`,
  `userspace-dp/src/afxdp/cos/queue_service/settle.rs`,
  `userspace-dp/src/afxdp/cos/queue_service/mod.rs`,
  `userspace-dp/src/afxdp/cos/token_bucket_tests.rs`.

## Defect

A backlogged exact queue parks for its own refill time: when
`queue.hot.tokens < head_len` the selectors / waterfill park it through
`estimate_cos_queue_wakeup_tick`, i.e. until a full head frame refills
at the configured rate (`cos_refill_ns_until`). That park is the
rotation lag the v8 lease sees, because `maybe_rotate_epoch_v8` is only
called from `acquire_v8`.

Pre-fix, the rotation's windows were fixed epoch counts
(EPOCH = 200 µs, K = 8, STALL = 256): a wake lag above 1.6 ms
(K×EPOCH) was credited only 1.6 ms of rate with the residual banked
but not drawn, and a lag above 51.2 ms (STALL) got one epoch with the
carry dropped. At 64 kbps the self-park for a 1500 B frame is
187.5 ms, so every revisit cold-resumed; the epoch-sized carry caps
(K×rate×EPOCH = 12.8 B at 8000 B/s) could never reassemble even one
frame. Measured on the real code at filing, 64k/128k exact classes
delivered 0 % and 1 Mbps delivered 29.5 %.

## Fix

- `epoch.rs`: `FRAME_BYTES` (4096, one UMEM frame — the lease bank's
  own frame unit), `lag_window_ns_for_rate(rate)` =
  `max(K×EPOCH, FRAME_BYTES×1e9/rate)`, and
  `stall_window_ns_for_rate(rate)` =
  `max(STALL_THRESHOLD_EPOCHS×EPOCH, 2×lag_window)`. Rate 0 keeps the
  fixed windows (transparent leases have no self-park to protect).
- `lease.rs` (`new_v8_with_rate_mode_and_policy`): compute the
  rate-relative windows once at lease creation and store them on
  `V8State`: `lag_window_ns`, `carry_max_bytes =
  max(rate×lag_window, CARRY_FRAME_BYTES)`, and `carry_drain_max_bytes`
  (the (K−1)/K proportion, floored at one frame when the reservoir is
  floored). Whenever the fixed K×EPOCH window already covers a frame,
  all three equal the pre-#15100 values exactly.
- `rotate_epoch_v8.rs`: the rotation reads the stored
  `v8.lag_window_ns` as its K window and
  `stall_window_ns_for_rate(rate)` as its stall cutoff (must sit above
  the lag window or a self-parked class cold-resumes between them).
  Regime structure, seqlock discipline, carry privacy, and the
  (2K−1)-style burst bound are unchanged in shape: the per-rotation
  byte burst is now bounded by `max(K×rate×EPOCH, FRAME_BYTES)` of base
  plus the bounded drain, and a lag beyond the stall window still
  cold-resumes to exactly one epoch and drops the carry.
- `settle.rs` (`estimate_cos_queue_wakeup_tick`): park-aware demand
  scheduling made explicit — a queue already at or above `need_bytes`
  is woken on the next tick, never parked for a frame refill it does
  not need; only an actually-short queue parks, for its own deficit
  time. Transparent (rate 0) behaviour (#916) is unchanged.

NOT changed: the acquire path, the share formula, equal-flow
suppression, the root lease, non-exact queues, and any window for
rates whose fixed K window already covers a frame (verified by the
high-rate controls; the full pre-existing carry suite is byte-identical
for those rates).

## Risk

- For sub-frame-threshold rates the per-rotation burst ceiling rises
  from K epochs of rate (e.g. 12.8 B at 8000 B/s) to one frame
  (4096 B) plus a bounded carry drain — that is precisely the frame
  the class is parked waiting to send, so the "burst" is one frame
  per self-park interval, i.e. exactly the configured rate. The long-
  run hard cap (Σ granted ≤ rate × wall-time + carry_max) is
  preserved: the reservoir is still clamped, it is just clamped in
  bytes that can actually be spent.
- The rate-relative stall window lengthens the cold-resume cutoff
  for very low rates (up to 2× the frame time, e.g. ~1 s at
  8000 B/s). A genuinely stalled worker at such a rate now banks at
  most one frame of extra credit before cold-resuming, instead of
  dropping it — bounded by `carry_max_bytes` as before.
