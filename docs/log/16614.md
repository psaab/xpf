# #16614: next-table target miss fell through to inet.0 (WAN leak)

- **Timestamp**: 2026-10-25
  - **Action**: A config `next-table` static was only an RPDB ip rule
    ahead of `main` (kernel) and a stage-1 leak with fall-through on
    target miss (AF_XDP FIB). A hole in the target VRF therefore
    egressed via inet.0's default (usually WAN, often SNATed), and the
    leak beat every more-specific inet.0 route. Fix, by plane:
    (1) Kernel: `nextTableManager.Apply` now installs, per admitted
    leak and ingress interface, a selector-identical `unreachable`
    shadow at `config.NextTableMissTerminatorPriority` (32765,
    immediately before main at 32766), shadow-first in the PBR #11394
    posture; shadows do not consume admission slots. Clear owns them
    via `isNextTableMissTerminatorShape` with an action-aware delete
    (RuleList does not decode the fib-rule action). A target miss now
    ends ENETUNREACH instead of reaching main's default.
    (2) AF_XDP: `RouteSnapshot.next_table_route` (protocol v73, Go
    `NextTableRoute`) marks config-authored statics. The Rust builder
    puts them in the source table's ordinary LPM (`RouteEntry.next_table_route`)
    instead of the stage-1 leak index; `junos_next_table_winner_*` in
    `forwarding/fib.rs` hands a winning route's lookup to its target
    and converts a target `NoRoute` into terminal `RejectRoute`.
    Kernel-model leaks (rib-group, returns, live mirrors) keep the
    #9955 stage-1 fall-through bit-identically.
    (3) Measured kernel limitation (netns probe, this host's kernel):
    the RPDB walk cannot express "inet.0 LPM decides" — with the leak
    rule installed, an inet.0 /16 carve-out does NOT rescue a hole on
    the kernel path (the 32765 shadow fires first; fail-closed, never
    a WAN leak). Junos LPM rescue is exact on the AF_XDP fast path,
    which is the supported transit plane; the kernel path's residual
    is a blackholed carve-out, documented here and in
    `pkg/routing/README.md`, not a leak. Installing the Junos route
    solely as a VRF-device route in main was rejected: `ip route get`
    shows `dev vrf-red` without recursive resolution proof being a
    forwarding guarantee for all ingress shapes, and it would fight
    FRR/zebra's ownership of main.
