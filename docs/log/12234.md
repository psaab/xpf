# #12234 — quarantine enforcement-like unknown policy children

- **Timestamp**: 2026-10-08 (`fix/12234-policy-typo`)
- **Action**: fail closed when an unknown direct policy child can carry or name enforcement content; retain advisory-only behavior for unrelated unknown scalar metadata.

## Red before

On pristine base `a714c90d4`, a tolerant compile of a permit with a defined `permit-window` and `scheduler-nam permit-window` produced `Action=permit`, an empty `SchedulerName`, `LenientContentDropped=false`, and only the #4232 advisory. The configured window was therefore omitted while the permit remained active. `SchemaValidate` rejected the unknown keyword on the strict path.

Added `TestUnknownEnforcementSecurityPolicyChildrenPoisonLenientCompile12234` and ran it before the fix on that base. All three cases (`scheduler-nam`, nested `mach`, and `thne deny`) failed because the policy was not poisoned.

## Change

- Add `policyUnknownEnforcementChildren`: unknown nested direct children and one-edit misspellings of enforcement-bearing policy keywords (`match`, `then`, `scheduler-name`, `term`, and `session-options`) are treated as dropped enforcement. Unrelated unknown scalar metadata remains advisory-only.
- Feed this predicate to the shared strict/tolerant enforcement gate and `compilePolicy`'s `LenientContentDropped` decision. Strict compilation/schema validation rejects; tolerant compilation records a named warning and poisons the rule so the userspace snapshot is refused.
- Add regression coverage for the defined scheduler reference typo and inserted-letter variant (`scheduler-nam`, `scheduler-naeme`), a misspelled match subtree, a misspelled `then` with an added deny action, strict rejection, and an unrelated `descripton` advisory control.
