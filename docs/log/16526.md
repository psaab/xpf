# #16526 — WireGuard cookie replies: remove the spoofable per-source reply bucket

## Scope and verified mechanism

At base `15bbdf1b0c` (branch point):

- `userspace-dp/src/afxdp/wg/engine.rs` `classify_initiation`: under
  load, a valid-MAC1 initiation with no valid MAC2 was gated by
  `CookieChecker::source_reply_allowed(from.ip(), now_ns)` before a
  cookie reply was built; exhaustion bumped
  `hs_cookie_reply_budget_drops` and returned `Drop` (silent, no
  cookie).
- `userspace-dp/src/afxdp/wg/cookie.rs`: `source_reply_allowed` keyed a
  20/s, burst-5 token bucket on `source_bucket_key(src_ip)` — IPv4 /32,
  IPv6 /64 (host bits zeroed), port never part of the key.
- MAC1 keys on the responder's static *public* key, so the source key
  is unauthenticated: an off-path spoofer who knows the responder
  public key (public by design) forges valid-MAC1 initiations with the
  victim's address (any port, or any address in the victim's /64) and
  spends the victim's reply budget. The victim's own initiations are
  then dropped without a cookie for the length of the flood, blocking
  victim-initiated handshakes (roaming / remote-access peers hardest;
  xpf-initiated handshakes are unaffected — type-2 responses are not
  under-load gated).

Reference behaviour (per the issue, read from source): wireguard-go
`SendHandshakeCookie` has no limiter and `rate.limiter.Allow` runs
only after `CheckMAC2` succeeds; Linux `wg_cookie_validate_packet`
runs `wg_ratelimiter_allow` only after the MAC2 compare and sends the
cookie whenever `packet_needs_cookie`. A cookie reply (64 B) is
smaller than the triggering initiation (148 B), so an unthrottled
reply is not amplification.

## Fix

Match the references: send a cookie reply for every valid-MAC1,
MAC2-absent initiation under load; keep per-source limiting only on
MAC2-valid admissions (`source_handshake_allowed`, #9908, unchanged).

- `engine.rs` `classify_initiation`: the `source_reply_allowed` gate
  is deleted. The MAC2-absent arm now goes straight to
  `build_cookie_reply`; `Drop` remains only for a reply that cannot be
  built (fail-closed on a broken CSPRNG, #4094 BUG-2). No other arm
  changes: not-under-load `Process`, bad-MAC1 `Process` with no reply
  (no reflection), valid-MAC2 → #9908 admission bucket → `Process`.
- `cookie.rs`: `source_reply_allowed`, the reply bucket map, the reply
  token constants (`SOURCE_REPLIES_PER_SEC`, `SOURCE_REPLY_BURST`,
  `PACKET_COST_NS`, `MAX_TOKENS_NS`) and the reply test hooks are
  removed (clean cutover — no dead bucket left behind). The #9908
  handshake bucket keeps explicit 20/s + burst-5 constants
  (`SOURCE_HANDSHAKES_PER_SEC` / `SOURCE_HANDSHAKE_BURST`), the same
  /64-aggregated keying, GC, cap and LRU eviction. Module doc records
  the #16526 removal and why the #4332/#13958 reply-bucket rationale
  is superseded.
- `counters.rs`: `hs_cookie_reply_budget_drops` keeps its wire name
  (control-protocol field, Prometheus series) but now counts only
  cookie-reply construction failures; the doc says so. No gate was
  weakened: MAC1, MAC2, under-load trigger, #9908 admission, secret
  rotation and cookie source binding (full IP+port) are untouched.
- `docs/wireguard-interop.md`: the per-source reply-bucket bullet is
  replaced with the unthrottled-reply behaviour and counter semantics.

Deliberate scope cuts: no global reply-rate ceiling was added (the
acceptance permits one only if it cannot be first-come starved; the
references have none and the 64 B < 148 B size ratio removes the
amplification motive). No change to peer/handshake logic outside the
classifier arm above.

## Tests

- New `classify_initiation_spoofed_source_cannot_starve_victim_cookie_16526`
  (engine level, frozen clock): trip under-load, flood valid-MAC1
  initiations spoofing the victim's IPv4 source, then assert the
  victim's own tries all return `SendCookie`
  (`victim_cookies == victim_tries`); IPv6 arm floods other addresses
  in the victim's /64 with the same assertion. RED pre-fix (shared
  bucket drains at burst 5, victim tries `Drop`), GREEN post-fix.
- `classify_initiation_rotating_source_flood_keeps_legit_challenge`
  strengthened to an exact count (`3000 - threshold` replies — the
  pre-threshold arrivals take the not-under-load path), pinning that
  no reply limiter remains.
- Cookie unit tests that exercised only the removed reply bucket
  (`source_bucket_*`, `source_table_cap_evicts_for_new_sources`,
  `source_gc_reclaims_idle_buckets`,
  `source_bucket_ignores_backwards_clock`, reply halves of the #14639
  cells) were deleted or migrated to the surviving handshake bucket
  (`handshake_gc_reclaims_idle_buckets`,
  `handshake_bucket_ignores_backwards_clock`); #9908 burst/cap and
  #14639 /64-sharing/v4-mapped pins are unchanged in substance.
- Existing pins still exercised: `classify_initiation_under_load_requires_mac2`,
  the #9908 admission cells (valid-MAC2 replay flood stays bounded by
  `source_handshake_allowed`), bad-MAC1 no-reflection, CSPRNG
  fail-closed, initiator cookie round-trip.

## Validation

- Targeted GREEN: `cargo test --bin xpf-userspace-dp --
  afxdp::wg::engine::engine_internal_tests::classify
  afxdp::wg::engine::engine_internal_tests::handshake_admission
  afxdp::wg::engine::engine_internal_tests::initiator_consume
  afxdp::wg::cookie` — **32 passed, 0 failed** (22 cookie unit tests
  in that set plus the classify/admission/initiator engine cells;
  9514 filtered out). This includes
  `classify_initiation_under_load_requires_mac2`, the new
  `classify_initiation_spoofed_source_cannot_starve_victim_cookie_16526`,
  and the three #9908 admission cells.
- RED evidence: the `engine_tests.rs` diff alone applied onto pristine
  base `15bbdf1b0c` in a scratch worktree fails the new spoof test and
  the strengthened rotating-source count (victim tries `Drop` once the
  shared reply bucket drains); the same tests pass with the fix. See
  the PR body for the recorded output.

## Residuals

- End-to-end lab handshake flood against a deployed tunnel was not
  run; the decisive behaviour is pinned by the frozen-clock engine
  cells (the va69 probe's classifier seam) plus the #9908 real-key
  admission cells.
- Unthrottled replies mean a valid-MAC1 flood draws one 64 B reply
  per 148 B initiation — reference behaviour, not amplification; CPU
  cost per reply is one keyed hash + one AEAD seal, far below the
  Noise handshake the cookie path exists to avoid.
