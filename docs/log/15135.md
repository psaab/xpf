# #15135 — Bare `bfd peer X multihop` (no local-address) rejected by bfdd, failing every commit (A89-03)

- **Timestamp**: 2026-10-19
  - **Action**: `bfdSection.render()` in `pkg/frr/bfd.go` now omits a multihop BFD peer entirely when it has no valid `localAddress` (empty, or failing the #9493 single-token belt — the same validity test the BGP `update-source` line uses). Previously #14587 keyed every iBGP neighbor and every `MultihopTTL > 0` neighbor as multihop and appended `local-address` only when non-empty, so a routine Junos shape (directly-connected iBGP, or multihop eBGP, with `bfd-liveness-detection` and no `local-address`) rendered the bare line `peer X multihop`, which bfdd 10.7.1 rejects; `frr-reload.py` exited 1 and every commit failed with a degraded "did not fully converge" retry that could never converge. The `neighbor X bfd profile <p>` binding is unchanged, so the configured timers still reach bgpd's own dynamic multihop session via the profile and the `bfd` block survives on the profile alone; a warning names the omitted peer. A single-hop fallback stanza was deliberately NOT emitted — it is the proven #14587 orphan. Neighbors WITH a valid local-address render `peer X [vrf V] multihop local-address L` byte-identically, and single-hop peers are untouched. No commit gate was added (fix direction's primary option, not the alternative).
  - **File(s)**: `pkg/frr/bfd.go`, `pkg/frr/bgp_bfd_multihop_14587_test.go`, `docs/log/15135.md`

## Regression

Added `TestBGPBFDMultihopNoLocalAddress15135` to `pkg/frr/bgp_bfd_multihop_14587_test.go`, and flipped the one pre-existing assertion that pinned the defective line (`TestBGPBFDMultihopProfile14587`'s iBGP-without-update-source cell, formerly expecting ` peer 10.255.0.9 multihop\n`):

- (a) iBGP without `local-address`: profile still bound, no static peer line at all, no bare `multihop` line.
- (b) eBGP-multihop (`MultihopTTL 5`) without `local-address`: same omission, profile still bound.
- (c) iBGP with a whitespace-bearing (persisted pre-gate) `local-address`: same omission.
- (d) Direct `bfdSection` unit cells: VRF-scoped multihop peer without local-address omitted; controls — VRF multihop WITH local-address renders ` peer 10.255.0.21 vrf vrf-blue multihop local-address 10.255.0.1`, single-hop bare peer unchanged.

RED on current `origin/master` (tests kept, fix withheld): (a)/(b) fail rendering ` peer 10.255.0.9 multihop` / ` peer 192.0.2.10 multihop`. GREEN after the fix. Controls inside `TestBGPBFDMultihopProfile14587` (multihop iBGP/eBGP WITH local-address, default timers, single-hop eBGP) stay green unchanged.

## Risk

Only the no-valid-local-address multihop leg changes: those neighbors lose the (invalid, reload-breaking) static peer stanza and keep timer delivery through the bound BFD profile. Directly-connected iBGP without `local-address` previously rendered the rejected line, so this is strictly convergent; operators wanting the static stanza keyed in bfdd set `local-address` (Junos `local-address`), which renders exactly as before.
