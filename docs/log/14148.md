# 14148 — interactive CLI persistent-NAT clear drops peer generation fence

Interactive `clear security nat persistent-nat-table`
(`(*CLI).clearPersistentNAT`, `pkg/cli/cli_clear.go`) asserted only the
legacy `ClearPersistentNATLeases() (uint64,error)` and then called
`requestPeerSystemAction(ctx,"clear-persistent-nat")`
(`pkg/cli/peer.go`), which appended only `x-peer-forwarded`. The gRPC
twin (`pkg/grpcapi/server_diag_system_action.go`) asserts
`ClearPersistentNATLeasesWithGeneration`, captures
`(origin,generation)`, and forwards both as
`x-peer-persistent-nat-{origin,generation}` so the peer records a
durable replay floor (`RemoteGenerations` in
`pkg/dataplane/userspace/manager_idle_leases_8121.go`). On the CLI
path the peer therefore never learned the initiator's post-clear
generation, so pre-clear HA lease frames still in flight from the
initiator could be re-imported on the peer after its clear —
resurrecting a revoked persistent-NAT binding. The import-side fence
itself already existed and was tested (#11486); only the CLI
initiator failed to feed it.

Fix: `clearPersistentNAT` now prefers
`ClearPersistentNATLeasesWithGeneration("",0)` (mirroring the gRPC
twin's local-clear call), capturing `(clearOrigin,clearGeneration)`.
Legacy-only backends keep the old `ClearPersistentNATLeases()` path
and non-userspace backends keep `table.Clear()`. When generation-
capable, the peer leg uses the new
`requestPeerSystemActionWithPersistentNatGeneration` in
`pkg/cli/peer.go`, which appends
`x-peer-persistent-nat-origin`/`x-peer-persistent-nat-generation`
(only when origin is non-empty, matching grpcapi's
`proxyPeerSystemActionWithPersistentNatGeneration`) on top of
`x-peer-forwarded`; `requestPeerSystemAction` delegates to it with
empty origin so chassis/failover callers are unchanged. If the local
generation-capable backend returns an empty origin (no durable
identity), no generation headers are sent — same fail-closed
degradation as the gRPC path. The peer's gRPC handler already parses
and enforces the fence, so no wire or peer-side change was needed.

Regression (`pkg/cli/cli_clear_persistent_nat_14148_test.go`, RED on
base `0db0fa57c`: `generationCalls=0 legacyCalls=1`, no
`x-peer-persistent-nat-*` headers):
`TestClearPersistentNATForwardsGenerationToPeer14148` uses a fake
backend implementing both clear interfaces plus a capturing
`peerSystemActionFn` and asserts the CLI calls `WithGeneration`
(not the legacy method) and forwards both metadata headers with the
returned origin/generation. `TestClearPersistentNATLegacyBackendForwardsNoGeneration14148`
asserts a legacy-only backend forwards no generation headers.
`TestClearPersistentNATGenerationErrorPropagates14148` asserts a
generation-clear error propagates, does not forward to the peer, and
leaves the SHOW mirror intact. The import-side rejection of a
pre-clear-generation lease once the floor is recorded was already
covered by `pkg/dataplane/userspace/persistent_nat_generation_11486_test.go`
and `pkg/grpcapi/server_diag_system_action_11486_test.go`, which are
unchanged.

Validation: `go test ./pkg/cli/ -run TestClearPersistentNAT -count=1`
— 5 passed (2 existing #10784 + 3 new #14148), RED-verified on a
separate base worktree at `0db0fa57c` (2 of 3 new tests fail there;
the legacy test passes on both by design). Full `./pkg/cli/` and
`./pkg/grpcapi/` suites plus `go vet ./pkg/cli/` run before PR.
