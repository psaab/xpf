# Issue #15090 — early boot fences exec through /var with no mount ordering (A57-02)

- **Timestamp**: 2026-10-18
- **Action**: `scripts/image/xpf-input-closed.service` and
  `scripts/image/xpf-transit-closed.service` are `DefaultDependencies=no`
  units whose `ExecStart=/usr/local/sbin/xpfd …` resolves, after
  first-install seeding (`debian/xpf.postinst` → `xpfd seed-runtime`),
  through `/var/lib/xpf/versions/current` (`pkg/upgrade/runner.go:35,37`
  `DefaultVersionsDir`/`DefaultSbinDir`). Neither unit carried any mount
  ordering, so on a foreign host with a separate `/var` the fences could
  exec before `var.mount`, fail to resolve their binary, and — via
  `RequiredBy=systemd-networkd.service` (and `RequiredBy=xpfd.service`
  for the input fence) — stop networkd (and xpfd) from starting at all:
  a total boot outage needing the console. The baked appliance image
  (single root) is unaffected. Fixed by adding
  `RequiresMountsFor=/var/lib/xpf /usr/local/sbin` to the `[Unit]`
  section of both fences, which pulls in and orders after the mount(s)
  backing the sbin symlink and the versioned runtime it resolves to,
  while the existing `Before=network-pre.target …` keeps the
  pre-networkd position. Added `Description=` lines alongside (neither
  unit had one). NOT changed: `After=nftables.service`,
  `DefaultDependencies=no`, Exec lines, `RequiredBy=` edges, staging in
  `debian/rules`/`bake.py`/Incus harnesses (they copy these same source
  units), and the daemon/barrier Go code.
- **File(s)**: `scripts/image/xpf-input-closed.service`,
  `scripts/image/xpf-transit-closed.service`,
  `pkg/daemon/barrier_mount_ordering_15090_test.go` (new),
  `docs/log/15090.md`
- **Validation**: RED on pre-fix tree (fix stashed, test present):
  `TestBarrierMountOrdering15090` failed both subtests with
  `[Unit] missing "RequiresMountsFor=/var/lib/xpf /usr/local/sbin"`.
  GREEN after the fix: both subtests pass, and the control assertions
  (`DefaultDependencies=no`, `After=nftables.service`,
  `Before=network-pre.target systemd-networkd.service frr.service
  xpfd.service`, bare Exec lines, `Type=oneshot`/`RemainAfterExit=yes`,
  `RequiredBy=` edges) stay green. `systemd-analyze --root=<stub root
  with xpfd stub> verify` exits 0 for both units, and
  `systemctl --root=<stub> enable` creates the expected
  `sysinit.target.wants` + `.requires` links. Neighbouring suites:
  `go test ./pkg/daemon -run TestTransitBarrierBootUnitFailsClosed9852|TestEarlyInputBarrierBootUnitAndStaging10751|TestBarrierMountOrdering15090`.
- **Risk**: On a separate-`/var` host the fences now also order after
  the `/usr/local/sbin`-backing mount (root fs in practice); if `/var`
  fails to mount, the fences and therefore networkd fail closed at
  boot (same fail-closed posture as a barrier failure — console
  recovery via the existing disable/mask procedure in
  `docs/log/9852.md`). Operators must verify on a separate-`/var`
  foreign host that `systemctl show -p After
  xpf-input-closed.service` lists `var.mount` and a reboot leaves both
  fences `active (exited)`; that lab check is the only outstanding
  item and cannot run in this checkout.
