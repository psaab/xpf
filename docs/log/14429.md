# Issue #14429 — DDNS `conflict-policy` garbage value silently disables the DNS-ownership guard (INSERT side)

## Why

`rfc2136Updater.sendAdd` (`pkg/ddns/backend_rfc2136.go`) branched on the
conflict policy as: `replace-owned` → the DHCID ownership-proving path
(`sendAddOwned`); `skip-existing` / `strict-fail` → an UPDATE carrying an
RRset-not-used prerequisite; **anything else → a bare `Insert` with no
prerequisite at all**. `policyFromConfig` (`pkg/ddns/manager.go`) only
defaulted the empty string, so any typo that survived to the backend —
`skip-existng`, `none`, `skip_existing`, a case/padding variant — silently
disabled the DNS-ownership guard on the INSERT side: xpf adopted a third
party's pre-existing record, the manager recorded phantom ownership, and
a later release could take the plain exact-RR delete and remove a record
xpf never created (the #2648/#2660 boundary breach, re-opened by a typo).

The strict commit path already rejects such values via the schema enum
(`conflict-policy` in `pkg/config/schema_system.go`), but the tolerant
load / peer-sync path (`CompileConfigLenient` / `Store.Load` /
`Store.SyncApply`, #1960 no-brick) downgrades that reject, and direct
programmatic callers bypass it entirely — with no commit warning and no
runtime guard, the garbage value was invisible end to end.

Sibling #14432 tracks the same garbage value on the DELETE side
(`sendRemoveForward`'s unguarded branch).

## What

- `pkg/ddns/manager.go`: new `validConflictPolicy` SSOT (exactly
  `replace-owned` | `skip-existing` | `strict-fail`; empty is invalid
  there because `policyFromConfig` has already defaulted it).
- `pkg/ddns/backend_rfc2136.go`:
  - `newRFC2136Updater` refuses construction with a non-empty invalid
    policy (error names the value and the valid set). The manager's
    `resolveFamilyUpdater` already falls back to the no-op updater on a
    factory error, so no UPDATE is emitted and no ownership is recorded
    that cycle.
  - `sendAdd` defense-in-depth: an updater built outside the constructor
    (struct literal) with an invalid policy returns an error instead of
    falling through to the bare `Insert`.
  - `sendRemoveForward` same-root guard: an invalid policy fails closed
    rather than taking the plain delete branch (keeps this fix from
    leaving a same-root delete hole; #14432 remains the delete-side
    audit owner).
- `pkg/config/compiler_validate_warn_ddns.go`:
  `ddnsBackendWarningsForPolicy` now warns (both families) when
  `conflict-policy` is set to a value outside the valid set, naming the
  value and the consequence — so the tolerant load path surfaces the
  typo instead of silently honouring it. Valid policies and the unset
  (defaulted) policy stay silent.
- Regression tests:
  - `pkg/ddns/conflict_policy_14429_test.go` — garbage values
    (`skip-existng`, `none`, `skip_existing`, `replace`, `SKIP-EXISTING`,
    `" replace-owned "`) must refuse (construction error or ADD error,
    and never publish); the three valid policies plus the empty default
    publish a fresh record exactly as before.
  - `pkg/config/conflict_policy_14429_test.go` — garbage values warn via
    `ValidateConfig` on the lenient compile path; valid policies do not
    warn.

NOT changed: the strict schema enum (already rejects garbage at
commit), the three valid policies' wire behaviour, and `policyFromConfig`
defaulting.

## Validation

- RED on base `e7a473021`: all six garbage subtests fail with
  `UpsertLease succeeded (unguarded bare Insert)`; the config test fails
  with no `conflict-policy` warning. Valid-policy controls pass pre-fix.
- GREEN after the fix: `go test ./pkg/ddns/ -run
  'TestRFC2136GarbageConflictPolicyRefusesAdd14429|TestRFC2136ValidConflictPoliciesUnchanged14429|TestRFC2136SkipExistingConflictSkips|TestRFC2136StrictFailConflictErrors|TestRFC2136ReplaceOwned'`
  and `go test ./pkg/config/ -run
  'TestDHCPDDNSGarbageConflictPolicyWarns14429|TestDHCPDDNS'` both pass;
  full `go test ./pkg/ddns/` passes. The full `pkg/config` suite shows
  pre-existing IPsec failures (e.g. TestSecureTunnelBindIfaceValidCommits)
  that fail identically on unmodified base `e7a473021` — base-attributed,
  unrelated to this change.

## Risk

- Behaviour delta: a DDNS block with a garbage `conflict-policy` that
  previously published (unguarded) now publishes nothing and logs the
  no-op fallback each reconcile cycle, plus a commit warning. That is
  the intended fail-closed posture; fixing the typo restores publishing.
- Records published pre-fix under a garbage policy are not retroactively
  withdrawn by this change; their ownership entries age out through the
  normal lease-release path, whose delete is now also guarded.
