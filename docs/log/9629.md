## Analysis: three stacked convoys, not one mutex

The issue frames the outage as helper-mutex queueing (H2). Verified in code
that production stacks THREE serializations, and a helper-only fix removes
only the last (least-engaged) one:

- G1 — Go `m.mu` held across the apply RPC. `requestApplySnapshotLocked` +
  comment ("worst-case m.mu hold … is therefore two round trips")
  (`pkg/dataplane/userspace/apply_snapshot_identity_9520.go:84`). ALL HA
  senders need `m.mu`: `UpdateHAWatchdog` locks it (`manager_ha.go:916`),
  the status-poll tick holds it across `syncHAWatchdogOnlyLocked`
  (`process_status.go`, `m.mu.Unlock()` at tick end), the apply path holds it.
  During a 10s apply, NO HA refresh is even SENT.
- H1 — helper main accept loop is serial. Both socket loops call
  `serve_one_catch_unwind` inline (`server/lifecycle.rs:620,675`; guards.rs:
  no thread spawn). A main-socket HA behind a 10s apply waits in the kernel
  backlog regardless of the mutex. Cross-socket concurrency (session thread
  vs main thread) is the ONLY concurrent accept path.
- H2 — helper `ServerState` mutex (`served_off_lock = request ==
  "sync_session"`, `server/handlers/mod.rs:174`; `update_ha_state` takes the
  lock; `apply_snapshot` holds it across the 10s worker-readiness barrier).

Consequence: helper-only off-lock serve (H2) is production-inert — Go sends
nothing during the apply (G1), and anything sent would serialize in the
accept loop (H1) before reaching the mutex. The complete fix needs an
independent channel end-to-end: Go sends the watchdog IPC without `m.mu`
(G1), via the session socket (H1), served off-lock (H2). No wire change in
any leg; each side alone degrades to today's behavior (upgrade matrix below).

Separability answer (the issue's first question): the lease REFRESH is fully
separable — with no active-flag/membership change, `update_ha_state` touches
exactly one shared cell (`ha.rg_runtime` store; no worker fan-out, no epoch
bumps, no cache flush, no warm pass — all gated on non-empty demoted/
activated sets). Transitions stay on the locked main-socket path with
identical semantics. Full-move alternative (transitions off-lock too)
costed and rejected for blast radius: it would need published-forwarding
threading through `demote_shared_owner_rgs`/`prewarm_…` (both take
`&ForwardingState`; off-lock must read the published `RuntimeView`, not the
owned mid-apply field), sharing of `warm_queue: Option<SyncSender>` (not
shared, reassigned on bringup/teardown), and `rg_epochs`/`last_cache_flush_at`
sharing. The lease-only fast path needs none of it.

## Plan (sent to 2 hostile reviewers BEFORE implementing)

### Helper (Rust)

1. `SessionDomain::try_refresh_ha_leases(&groups)` (name TBD) — lease-only
   fast path over the already-shared `rg_runtime` cell:
   - stored empty + groups non-empty → store all fresh (post-restart
     self-heal), Served;
   - RG-id membership differs → NeedsLock (covers the standalone CLEAR:
     empty groups must go through the locked path, never silently skip);
   - per-RG active differs → keep the STORED entry (skip); else mint fresh
     lease via `active_lease_until` (receipt-anchored, as today). Store. Served.
   - Never changes active flags or membership off-lock → a stale refresh can
     never revert a landed transition by content; see (4) for the µs race.
2. Dispatch split by accepting socket (`handle_stream` gains a mode param;
   lifecycle passes per-loop; test harness call sites plumbed, assertions
   untouched):
   - MAIN socket `update_ha_state`: today's exact behavior (blocking lock,
     full serve, status attach, persist). Justification: main accept is
     serial, so off-lock buys nothing there, and the session thread never
     takes the mutex in this design, so the main lock is uncontended. Zero
     risk to `UpdateRGActive` (authoritative transition publish, keeps status
     apply) and to `update_ha_state_populates_status_ha_groups`.
   - SESSION socket `update_ha_state`: fast-path only. Served → `ok:true`,
     no status attach (Go session path ignores status — precedent:
     `requestSessionSyncLocked`), no persist (`write_state` re-locks; setting
     it would re-block — same reason `sync_session` doesn't persist).
     NeedsLock → `ok:false` "requires control socket": transitions/clears are
     covered by the main-path senders (`UpdateRGActive` + 2s reconcile retry
     with applied-gate, apply-path replay, `#5487` clear debt). Session HA
     NEVER takes the ServerState mutex → no head-of-line stall for `sync_session`
     (the #7209 regression a blocking fallback would reintroduce).
3. `Coordinator::update_ha_state` (locked path): identical behavior; the
   load→diff→store (+epoch bumps) section runs under a new leaf `ha_mutex`
   (`Arc<Mutex<()>>` on `HaState`, cloned into `SessionDomain::new` which
   already takes `&HaState`). Side effects stay after release, keyed off the
   diff (only the locked path runs side effects, still serialized by
   `ServerState`). Readers (packet path, `ha_group_status`) stay lock-free.
4. Why the mutex: closes the W-stores-between-T-load-and-T-store µs race
   (stale refresh overwriting a just-landed transition with no retry armed —
   T succeeded so the reconcile applied-gate clears; permanent loss).
   Lock order ServerState→ha (leaf) is acyclic; hold is µs (no slow ops
   inside); poison → recover (`worker_queue::lock_recover` precedent), never
   propagate. W-vs-W needs no mutex (idempotent full-state refresh) but gets
   serialization for free.
5. Rust cells: seam cell RED→GREEN + (a) session transition → changed RG
   kept, unchanged RG fresh, ok; (b) session membership-diff → ok=false fast
   while locked; (c) empty-stored fresh-inventory via session; (d) main-mode
   behavior unchanged (existing tests); (e) race closer — TBD per review
   (deterministic ordering cell preferred over hammer).

   success, 2s ticker). Transition senders (`UpdateRGActive`, apply-path and
   poll-path `syncHAStateLocked`, clear paths) UNCHANGED on the main socket.
8. Go tests: session path has no `controlRequestHook` — strategy TBD per
