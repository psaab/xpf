# Issue #18857 — keep RIP and IS-IS secrets in legal fixtures

## Why

Commit `ca712ef0e6` (#17735) rejects an active RIP/IS-IS pair in one routing
instance: FRR fixes IS-IS at distance 115 while the managed RIP stanza renders
distance 100, reversing Junos's IS-IS 15/18-before-RIP-100 ordering. The RIP
schema (`pkg/config/schema_routing.go`, RIP leaves) and compiled `RIPConfig`
(`pkg/config/types_routing.go`) expose no RIP preference setting; the renderer
pins RIP to 100 (`pkg/frr/protocols_render_rip.go`). A preference above 115 is
therefore not legal in this Junos schema.

## What

- Kept both protocols' authentication sentinels active, but staged RIP and
  IS-IS in separate virtual-router instances in the shared API secret fixture
  and the daemon provenance fixture. The instances have matching interface
  membership so the fixture follows the real protocol ownership/render path.
- Added in-memory coverage that the shared API fixture compiles the RIP key,
  IS-IS area key, and IS-IS interface key in cleartext. Existing redaction
  assertions and daemon `$9$` provenance/render assertions remain intact.
- Pinned the API fixture's IKE/IPsec test VPN to its configured gateway and
  existing local address because the new virtual-router members make the
  routing-instance-aware IPsec guard applicable.

  `GOTMPDIR=/wtgt`, and `TMPDIR=/var/worktrees/.cache/tmpdir`.
- RED-on-revert: temporarily restored active global RIP and IS-IS staging in
  both fixtures. `TestConfigHandlerRedactsSecrets` failed at commit with the
  #17735 same-table conflict; the strict daemon copy test failed compilation
  with the same conflict. Restored the split fixture afterward.
- Sentinel grep counts were unchanged before/after: API
  `LEAK-RIP-AUTHKEY`, `LEAK-ISIS-AREA-AUTHKEY`, and
  `LEAK-ISIS-IFACE-AUTHKEY` each appeared twice; the daemon `$9$` sentinel

## Risk

Test fixtures only; no production behavior changed. Each fixture still stages
and exercises both protocol secrets while no longer asking strict commit to
accept the unsupported same-table distance ordering.
