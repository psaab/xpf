# Issue #16668: nested `commit confirmed` pre-flights the retained rollback target

- **Timestamp**: 2026-10-25
- **Branch**: `fix-16668`
- **Issue**: #16668 — a nested `commit confirmed` pre-flighted the unconfirmed
  active config instead of the store's retained original rollback target, so
  extending a window was falsely refused (and the true target was never
  re-checked at the nested arm).
- **Change**: `commitConfirmedAndApply` in `pkg/daemon/daemon_apply_commit.go`
  now resolves the rollback target via the new atomic
  `Store.RollbackTargetForArm` (`pkg/configstore/confirm_target_9615.go`:
  the retained `confirmPrevCfg` when a window is pending, the active config
  otherwise, with the pending generation check folded under the same lock)
  and passes that single target to both `rollbackTargetAppliablePreflight`
  and `deviceMapCommitPreflight`. Refusal wording in
  `rollback_target_appliable_6707.go` and `device_map.go` now names the
  rollback target rather than the active/current config, which was wrong
  on a nested arm. `pkg/daemon/README.md` documents the nested-arm target.
- **RED→GREEN**: New `pkg/daemon/nested_commit_confirmed_target_16668_test.go`
  drives the production `commitConfirmedAndApply` twice over a real
  configstore: C1 healthy committed, C2 feed-bound (`dyn1`, no feed
  snapshot) armed, nested C3 arm succeeds against retained C1 (pre-fix:
  refused naming `dyn1`); the opposite cell arms C2 at store level over a
  tolerant-only unappliable C1 and the nested daemon arm is refused naming
  C1's `gone` zone without promoting C3; a third cell pins
  `RollbackTargetForArm` for the non-nested and ordinary pending cases.
- **Files**: `pkg/configstore/confirm_target_9615.go`,
  `pkg/daemon/daemon_apply_commit.go`, `pkg/daemon/device_map.go`,
  `pkg/daemon/rollback_target_appliable_6707.go`,
  `pkg/daemon/nested_commit_confirmed_target_16668_test.go` (new),
  `pkg/daemon/README.md`, `debian/changelog`, `docs/log/16668.md`.
- **Risk**: Only the target selection at a nested arm changes; a
  non-nested arm resolves to the same `ActiveConfig` as before. A nested
  arm whose retained target is unappliable or device-map-unsafe is now
  refused where it was previously (incorrectly) cleared against the
  unconfirmed config — that is the intended fail-closed direction, and a
  plain `commit` remains the workaround.
