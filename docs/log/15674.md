# #15674 — NAT address ranges rewrite masks, reject IPv6, brick lenient load

- **Issue**: #15674 — `expandAddressRange`/`appendPoolAddresses` silently rewrote non-`/32` endpoint masks to `/32` (`net.ParseCIDR` discards the mask), rejected valid Junos IPv6 pool ranges ("only supports IPv4"), and hard-failed `CompileConfigLenient` on malformed or reversed ranges.

## What

- `expandAddressRange` (pkg/config/compiler_nat_helpers.go) now parses endpoints with `netip.ParseAddr`/`netip.ParsePrefix` via `parseRangeEndpoint`: bare IP or host prefix only (`/32` IPv4, `/128` IPv6); any other explicit prefix length, malformed endpoint, mixed family, or `high < low` is an error, and oversized (>256) keeps the `errNATAddressRangeTooLarge` sentinel. IPv6 ranges expand to `/128` members; count is computed by bounded `Next()` iteration (no 128-bit overflow).
- All range errors are now recorded instead of returned: pools get `NATPool.InvalidAddressRanges`, proxy-ARP entries get `ProxyARPEntry.InvalidRangeSpecs` (both `json:"-"`, alongside the existing `OversizedAddressRanges`/`OversizedRangeSpecs`). Both call sites (`appendPoolAddresses`, both proxy-ARP branches in compiler_nat_source.go) record and continue, so the lenient chain (no compileOpts) loads.
- `validateNATPoolAddressRangeStrict` rejects pools carrying `InvalidAddressRanges` (strict rejects; the existing uniform-gate call site downgrades to a warning on tolerant load). `validateProxyARPAddressesStrict` does the same for `InvalidRangeSpecs`. A pool consisting solely of an invalid range has no members, so `SourceNATPoolUnusableReason` already reports `empty_pool` — no new wire reason; a pool mixing a valid member with an invalid range keeps the valid member on the lenient path.
- NOT changed: destination-NAT pools (single `Address`, no range expansion — a `to` range there is already an `AddressInvalidSpec`); the 256 cap and its oversized recording; single (non-range) pool addresses (a lone `address 10.0.0.0/24` remains a valid prefix member expanded by the Rust dataplane).

## Validation

- GREEN: `go test ./pkg/config -run '15674|8814|5194' -count=1` — new `nat_address_range_15674_test.go` (expander unit cells + pool/proxy strict+lenient cells incl. acceptance (a)/(b)/(c)), updated `TestMalformedRangesStillFailOnBothPaths8814` (malformed/reversed now record + strict-reject + lenient-load; IPv6 leg now valid), existing 8814/5194 cells.
- Rebase onto d555361869: master's #15677 (ffc9c7edec) had already added IPv6 range expansion; conflicts in `expandAddressRange` and the proxy-ARP callers were resolved by keeping this PR's netip host-mask validation + Invalid-recording on top (master's big.Int IPv6 expansion superseded), unioning the changelog. `go test ./pkg/config -run '15674|15677|8814|5194|4422' -count=1` re-run after the rebase.

## Risk

Strict commits carrying a previously-silently-rewritten `/24`-style range endpoint now reject — intended (Junos would reject or honor the mask; silent rewrite was wrong either way). Tolerant loads of such persisted configs warn and install nothing for that range (fail-closed, no ARP/ND or NAT for it) instead of bricking. IPv6 source-pool ranges now expand and reach the dataplane, which already expands `/128` members via `expand_pool_address`.
