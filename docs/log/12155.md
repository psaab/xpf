# #12155 — Tear down takeover state after durable FIRST-window expiry

- **Issue**: #12155 — a FIRST commit-confirmed window expiring while xpfd is down reverted the store but left takeover artifacts behind.
- **Branch**: `fix/12155-firstwindow-teardown`
- **Worktree**: `/var/worktrees/12155-firstwindow-teardown`
- **Base**: `a714c90d472a3c3d98a3799831cfef3ec311a61c`, stacked on #12154 commit `8af3548eb37c84e275eaca78ae9bd25b2c4e46e5`.

## Why

`Store.Load` durably rolls an expired FIRST window back to the empty bootstrap config, but unlike the live timer path it never entered `enterBootstrapMode`. Bootstrap suppresses normal config apply, so abandoned xpf `.network` files and the FRR managed section were not swept. A crash between store recovery and daemon teardown would also lose any in-memory-only cleanup signal.

## What

- Persist a separate `.configdb/first-commit-teardown.json` debt marker after the rollback active write is durable and before removing `confirm.json`. If marker publication fails, retain `confirm.json` and use the existing persistence retry path; `Load` re-arms debt from the marker on later boots.
- Keep the daemon fail-closed and suppress day-0 import while cleanup is owed. After manager initialization, run the same full bootstrap teardown used by live rollback (including networkd artifacts and FRR), before dataplane setup. After bootstrap dataplane construction, tear down that unarmed backend too. Clear the debt only after teardown converges; failures retain retry state.
- Add configstore durability/recovery tests and a bounded daemon fake-root regression that includes a valid day-0 file, abandoned `.network` content, FRR managed content, and dataplane teardown accounting.
