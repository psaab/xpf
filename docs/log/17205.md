# Issue #17205 — DHCPv6 relay gate shares the compilers' shape readers

- **Issue:** `validateDHCPRelayDHCPv6AST` re-walked the dhcpv6 relay tree by hand instead of using the compilers' shape readers, so it rejected configuration both compilers read correctly: the canonical Junos `server-group { SG6 { addr; } }` block (it reported the first server address as an unsupported keyword) and a flat-set/display-set `interface a b` list (it told a list from a scalar-plus-option by `KeyBracketed` provenance, which `FormatSet` does not carry — so xpf's own display-set output could not be reloaded).
- **STEP-0 (defect live on origin/master `c4e12aafc3`):** a temporary probe (`TestProbe17205`, deleted after use) reproduced all rows: v6 canonical server-group block strict-rejected with `"2001:db8:9::9" is not in xpf's implemented RFC 8415 relay subset`; v6 hierarchical bracket compiled but its display-set replay strict-rejected with `"ge-0/0/2.0" is not in …`; v6 flat-set extra-token and flat-set bracket interface lines both rejected naming the second interface; the v4 canonical block and every v4 shape compiled clean.

## What

1. Extracted `dhcpRelayGroupInterfaces(prop *Node) []string` in `compiler_dhcp_relay_dhcpv6_9553.go` (Keys[1:] plus every child key, empty-filtered) as the single source of truth for a relay group's interface member list, and routed both compilers through it: `compileDHCPRelayV6Group9553` (was Keys[1:] + child `Name()`, Keys[1:] retained on a multi-key flat-set child) and `compileDHCPRelay` in `compiler_services.go` (was the hand copy). No new copy of the pattern remains.
2. Rewrote the gate's `server-group` and `group` iteration in `compiler_dhcp_relay_dhcpv6_9411.go` over `namedInstances(...)`, so it judges exactly the instances the compilers compile — the canonical block and compact shapes normalise onto one instance node. The nested-leaf guards (a braced address/member carrying its own child) are preserved per instance.
3. Made `checkInterface` validate the members of `dhcpRelayGroupInterfaces` via the new `dhcpRelayInterfaceMemberValid` (interface-shaped base per `ValidateInterfaceName`, valid logical unit per `ValidateLogicalUnit`, bare members must carry a digit with `irb` the reserved exception) instead of key position and `KeyBracketed`. A packed remainder token behind the values (`interface ge-0/0/0.0 disable`, the flat packed-tail cell) is still refused by name; `interface ge-0/0/0.0 { disable; }` and `interface { ge-0/0/0.0 { disable; } }` stay refused via the retained children guards. `grep -n KeyBracketed pkg/config/compiler_dhcp_relay_dhcpv6_9411.go` now matches only the scalar gate's `KeyBracketed(1)` in `checkScalar` — the interface path consults no bracket provenance (the issue's census targeted the interface/server-group hand-walk; `checkScalar` is untouched).
4. Added `pkg/config/dhcp_relay_shape_parity_17205_test.go`: a {v4, v6} × {canonical server-group block, compact, flat-set repeated, flat-set bracket, hierarchical bracket} table, each row also driven through a `FormatSet` → `ParseSetCommand`/`SetPath` display-set replay, asserting strict acceptance with unchanged compiled server-group/group values; plus `TestDHCPRelayV6GateNoKeyBracketed17205` pinning the gate directly on the canonical block and its replay.

## Risk

Strict commits now REFUSE only at the fail-closed boundary the compilers already enforce: a v6 relay group whose packed tail carries an unsupported knob, a packed remainder behind a unit-carrying interface value, a braced child behind a scalar/member, or a non-interface-shaped member — each refused by name. Digit-less bare members (`uplink`, `vrf-mgmt`) and every valid spelling in the parity table (canonical block, compact, flat-set repeated/bracket, hierarchical bracket, display-set replay) now commit with the values both compilers install; this widens acceptance ONLY for names that pass `ValidateInterfaceName`, the repo-wide interface-name gate. The v4 compiler's child-key reading widening (child `Name()` → every child key) is unchanged from the first head and pinned by the named neighbours. Lenient paths keep warning-not-brick disposition.
