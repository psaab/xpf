## Why

Chained IPv6 Fragment headers overwrote the screen extractor's fragment fields per sighting (`userspace-dp/src/screen/extract.rs`). On `[real-first (offset=0,M=1)][ATOMIC (offset=0,M=0)]` the trailing ATOMIC header cleared `is_fragment`/`is_first_fragment`/`ip_frag_off`/`frag_data_off`, so a configured `syn-frag` (TCP SYN + `is_first_fragment`) or `icmp-fragment` (`is_fragment` + ICMP/ICMPv6) screen in `userspace-dp/src/screen/stateless.rs` saw a non-fragment even though a real non-atomic fragment and terminal L4 bytes were present. The forwarding predicates and overlap tracker already used the first non-ATOMIC sighting (#10661); only the screens diverged, and the `[real-first][ATOMIC]` divergence was pinned as a tolerated residual in `tests_10661_atomic_chain.rs`.

## What

Make the screen extractor sticky on the first non-ATOMIC Fragment sighting, matching the tracker/forwarding canonical rule: a chain containing any non-ATOMIC header is a fragment governed by the first such header; ATOMIC headers (offset 0, M 0, an RFC 8200 no-op) never set, clear, or replace the governing fields. Sizing (`frag_data_off`) is taken from the governing header. Non-first handling (break, protocol recovery) and the TCP gate are unchanged — a chained non-first fragment now correctly suppresses L4-derived TCP screens as a non-first fragment.

Regression (`userspace-dp/src/screen/tests_14129_chained_frag.rs`, plus the superseded residual cell in `tests_10661_atomic_chain.rs`): a valid first fragment with a trailing ATOMIC header and TCP SYN through `extract_screen_info` -> `ScreenState::check_packet` with `syn-frag` enabled must drop exactly like the plain single-header control; repeat with ICMPv6 / `icmp-fragment`. Pure-ATOMIC guard included.
