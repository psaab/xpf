# #9508 — the session-sync readiness barrier carries no connection identity

## 2026-09-10 — Action: re-verify at base (origin/master d1266ee79)

- **File(s):** `docs/log/9508.md` (new),
  `pkg/cluster/barrier_connection_causal_9508_test.go` (new, acceptance first).
- **The spec.** The issue body; it has no comments.
- **The chain, read at base.**
  - `sendLoop` picks `getActiveConn()` separately for EVERY dequeued message. On a
    write error it disconnects that connection and re-sends the same message on
    whatever is active next.
  - `WaitForPeerBarrier` queues the barrier through `sendCh`, then waits.
  - The `syncMsgBarrierAck` handler advances the GLOBAL `barrierAckSeq` by CAS, and
    completes the waiter with no check of which connection delivered the ack.
  - A woken waiter reports success exactly when `barrierAckSeq >= seq`.
  - `handleDisconnect` aborts fence waiters on ANY fabric drop (#7147), but clears
    barrier waiters only `if !connected`, on a full disconnect.
- **Two ways the active fabric changes.**
  - **A partial drop.** fab0 lost, fab1 remaining.
  - **No drop at all.** `preferredFabricLocked` prefers a current-incarnation
    connection, fab0 before fab1, so a fab0 connection installed while fab1 carries
    the stream takes over at once.
  - `installConn` arms the cold-prime latch only on a full-disconnect-to-connect
    edge, so neither route ever re-sends the deltas in flight on the other
    connection.
- **Why the issue's "minimal version" cannot be the fix.** Aborting barrier waiters on
  any fabric drop helps only if the drop is noticed BEFORE the other connection's ack
  arrives, and the no-drop route has no drop at all. The issue's own acceptance
  (hold A's receive loop, ACK on B, readiness must not succeed) has no drop in it.
- **The harness the issue said did not exist.** `net.Pipe` cannot model this: its
  writes block until the reader reads, so "written, but not yet processed by the
  peer" never exists.
  - `heldConn9508` accepts writes at once into a buffer, as a TCP socket does, and
    parses whole frames from the 12-byte header.
  - The TEST decides when the peer processes a connection. It ACKs each barrier once
    through the real `handleMessage(conn, syncMsgBarrierAck, …)`.
  - `barrierOutcome9508` does not require a barrier to be written, so a fixed sender
    that refuses the barrier outright still scores correctly.
- **RED at base, with the intended messages:**
  - `TestBarrierIsNotSatisfiedAfterADeltaWasLostWithADroppedFabric_9508`: "the
    barrier succeeded on fab1 although the delta written on fab0 was never processed
    by the peer; readiness would permit a demotion that loses that session".
  - `TestBarrierIsNotSatisfiedWhenTheActiveFabricChangedWithoutADrop_9508`: "the
    barrier succeeded on fab0 while the delta written on fab1 was still unprocessed
    by the peer".
- **GREEN at base, and they must stay green:**
  - `TestBarrierCompletesOnASingleFabric_9508`;
  - `TestBarrierCompletesOnDualFabricWithoutASwitch_9508`, which stops a fix that
    refuses every dual-fabric barrier.
- **The recovery the fix can lean on.** #9482 ("the HA cold-prime bulk sync never
  runs") is CLOSED by #9537, so the cold-prime bulk now runs on master. A fence that
  requires a re-prime after a fabric change therefore cannot strand planned failover
  forever, which it would have while #9482 was open.

## 2026-09-10 — Action: the barrier fence

- **File(s):**
  - `pkg/cluster/sync_barrier_fence_9508.go` (new);
  - `pkg/cluster/sync.go` (one field);
  - `pkg/cluster/sync_conn_write.go`, `pkg/cluster/sync_bulk.go`,
    `pkg/cluster/sync_conn_read.go`;
  - `pkg/cluster/barrier_connection_causal_9508_test.go` (two cells added);
  - `pkg/cluster/README.md`, `docs/session-sync-architecture.md`.
- **Design.** The connection a frame travelled on is not on the wire, and adding it
  would not help the lost-connection route. So the SENDER tracks the move and refuses
  readiness until the peer provably has a snapshot taken after it.
  - **Arming.** `noteStreamConnLocked` runs under `writeMu` before an
    ordered-stream write (`sendOne`, BulkStart) and bumps `fence.epoch` when the
    connection differs from the last one noted. The bump precedes the write, so an
    ACK for a frame on the new connection cannot be observed without it.
  - **Refusal.** `WaitForPeerBarrier` snapshots the epoch BEFORE checking it (a move
    in between is still seen at wake-up). It fails when the epoch moved while the
    barrier was pending, and refuses at once while `epoch != cleared`.
  - **Recovery.** A move closes the pending barrier waiters and starts one
    single-flight re-prime. Every refused barrier re-kicks it. The daemon cannot own
    this: `prepareUserspaceRGDemotionWithTimeout` restarts its prime-retry loop after
    a failed barrier only when `syncPeerBulkPrimed` is false, and a primed peer is the
    normal case, so an undischarged fence would refuse demotion indefinitely.
  - **Discharge.** A bulk discharges only the epoch it captured BEFORE reading its
    session source.
    - `doBulkSync` captures before `BulkSnapshotSource`: its snapshot is read before
      the window, and a capture at BulkStart would let a delta written between the
      read and BulkStart go uncovered.
    - The store walk reads during the window and captures at BulkStart.
    - A direct `BulkSyncSnapshot` captures nothing.
    - The capture is stored after `pendingBulkAckEpoch` and loaded before it in the
      BulkAck arm. Every interleaving then either matches one bulk's own pair or
      fails the epoch match.
- **Cells added:**
  - `TestBarrierCompletesAgainOnceTheFenceRePrimeIsAcked_9508`: the fence is not a
    permanent refusal. After a move, the re-prime runs on the current connection, and
    once it is ACKed a barrier completes.
  - `TestAnAckedBulkWhoseSnapshotPredatesTheMoveKeepsTheFence_9508`: the move happens
    INSIDE the snapshot read. The move's own re-prime is parked so exactly one bulk is
    ACKed, and its ACK must leave the fence armed.
  - Neither compiles at base (they read `barrierFenced`), so the mutation matrix is
    what validates them.
- **Results:**
  - All six `_9508` cells pass: the two RED-at-base route cells, the two controls,
    and the two new cells.
  - `go test -json ./pkg/cluster/`: 1284 started, 0 failed. No existing cell changed
    verdict.
  - pkg/daemon `Barrier|Demotion|Readiness|ManualFailover|PeerSync|SessionSync`:
    ok.
  - `go vet ./pkg/cluster/`: no diagnostics.
- **Not claimed.** A frame from a superseded connection that is still up can reach
  the peer after the re-prime and be applied after it. That ordering exists without
  the fence and is unchanged. Written into the architecture doc.
