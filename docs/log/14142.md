# Issue #14142 — hierarchical event-policy quarantine

## Why

`pkg/config/event_plant_class_9984.go:eventPolicyNodes9984` indexed only
`policy` AST nodes with at least two keys (`policy p { ... }`).
`compileEventOptions` (`compiler_services.go:2625`) compiles both that direct
shape and the one-key-container shape `policy { p { ... } }` via
`namedInstances` (`compiler_protocols.go:1230`), including `plant-class`.

Consequences at origin/master (0db0fa57c):

- A solely nested `plant-class super-user` was invisible to
  `QuarantineUntrustedEventPlantClasses`, so the unauthenticated HA ingress
  (`daemon_ha_comms_wiring.go:handleConfigSyncWithProvenance`) passed it to
  `SyncApply` (`configstore/store.go:SyncApply`), lenient compilation retained
  it, and `eventengine.validatePlantClass` skips class-target authorization
  for `super-user` — unauthenticated peer config could execute
  change-configuration commands as root.
- In a mixed tree, `setEventPlantClass9984` edited only direct instances and
  ignored nested ones, so a later nested `plant-class` could override the
  stamp (compiler merges same-named policies, last plant-class wins), and
  quarantine could likewise leave a nested super-user marker behind.

Verified by probe against the parser: `policy { p { plant-class super-user;
... } }` compiles to `PlantClass="super-user"` while
`eventPolicyNodes9984` returned an empty map.

## What

- `eventPolicyNodes9984`: resolve each `policy` node through the existing
  `namedInstances` helper — the same shape resolution the compiler uses — so
  direct, nested-container, flat-set, group-owned, and wildcard instances are
  indexed under their policy name. All consumers (quarantine,
  stamp/clear, command census, plant-class reader) share this census, so the
  fix is one site with no special-casing of any spelling.

Regression tests in `pkg/config/event_plant_class_9984_test.go`:
- `TestNestedPolicySuperuserIsQuarantined14142` (decisive check from the issue)
- `TestMixedDirectAndNestedSuperuserIsQuarantined14142`
- `TestNestedPolicyIsStamped14142`

## Validation

- New tests pass with the fix; on a separate pristine origin/master worktree
  (test file copied over, production code untouched) all three fail:
  `nested super-user PlantClass="super-user"`, `mixed-tree PlantClass=
  "super-user"`, `nested legacy laundering persisted PlantClass="super-user"`.
- Existing plant-class tests (`TestFlat*9984`, `TestChildShape*`,
  `TestApplyGroupsEventPolicyStamp9984`, `TestUncompileable*`,
  `TestUntrustedSuperuserWithInheritedCommandsIsQuarantined10870`) still pass.
- Suites: `pkg/configstore` and `pkg/eventengine` pass. `pkg/config` fails
  only the pre-existing `TestSchemaSpellingGateCoverageIsGated_7484`
  (flag blind spot 196 vs ceiling 194), reproduced identically on a
  pristine origin/master worktree at 0db0fa57c (base-attributed).

## Risk

`namedInstances` on a `policy` node with neither a name key nor children
yields no instances (previously also unindexed). Group (`groups { ... }`)
and wildcard (`<*>`) shapes flow through the same walk and were verified by
probe. No compiler, engine, or sync-path changes; tolerant/strict doctrines
unchanged and fail-closed (quarantined policies compile to empty PlantClass,
which the engine refuses at fire time).
