# #15163 — reap single-path IPv6 and backup-router mgmt statics (B21-01)

- **Timestamp**: 2026-10-19
- **Issue**: B21-01 — when an IPv6 single-path management static or an IPv6
  `system backup-router` in table 999 is deleted or changed, the old route
  stays forever. The IPv6 FIB drops `RTA_FLOW`, so the realm
  (`mgmtStaticRouteRealm`) the stale-route reaper relies on never survives
  the kernel round-trip for IPv6, and `mgmtStaticRouteOwned`
  (`RTPROT_STATIC` + realm) never claims the pre-fix read-back form
  (`RTPROT_STATIC`, realm 0).
- **Base at filing/validation**: `origin/master` `27b8cba22d` (validator base
  for the deep-review claim). At that base
  `pkg/daemon/mgmtvrf_static_routes.go` built single-path routes as
  `RTPROT_STATIC` + realm (desired builder and `mgmtBackupRouterRoute`), and
  the only other delete path (`daemon_flow.go` `reconcileMgmtVRFRouteDeletes`)
  handles `RTPROT_DHCP` only — so nothing reaped a deleted/changed IPv6
  single-path route.

## Disposition: already fixed on master by #14972 / PR #15339 — this lane lands the #15163 regression proof and closes the dedup gap

The mechanism fix itself (stamp every management static, including the
single-path backup-router, with `config.ManagementVRFMultipathStaticProtocol`
0x58 as `rtm_protocol`, keeping the realm on single-path routes) already
landed as `2c0e039020` ("daemon: reap single-path IPv6 and backup-router mgmt
static routes (#14972) (#15339)", merged 2026-10-19T04:19Z) **shortly after**
this issue was filed (2026-10-18T23:56Z) from the same validator finding
under its D31-04 name. #15163's own dedup list (#11449, #12539, #12583,
#5108, #5867) does not cite #14972 because that PR had not merged yet.
Re-implementing the fix would duplicate merged code; this lane therefore
lands the issue's required acceptance artifact — a B21-01 regression test
that fails on the validator base and passes on current master — and records
the equivalence here. **No production code changes.**

Verified on current master (`ada5f856da`):

- `mgmtStaticRoutesDesired` stamps every desired route (both families, both
  shapes) with `config.ManagementVRFMultipathStaticProtocol`
  (`mgmtvrf_static_routes.go:286`); single-path routes additionally carry
  `Realm: mgmtStaticRouteRealm` (`:294`).
- `mgmtBackupRouterRoute` stamps the backup-router the same way (`:500-501`).
- `mgmtStaticRouteOwned` claims protocol 0x58 unconditionally and legacy
  `RTPROT_STATIC` + realm (IPv4 legacy installs) (`:599-608`); an operator
  `RTPROT_STATIC` route without the realm — including the realm-0 IPv6
  read-back form — is never claimed in either family.
- Table 999 is shared with operator routes (`networkd` `[Route]` sections
  and `ip route`, both `RTPROT_STATIC`), and the protocol also scopes the
  kernel delete match, so a stale xpf delete returns `ESRCH` against an
  operator route at the same slot instead of removing it.

## Bounded residual (unchanged, by design)

An IPv6 single-path route installed by a pre-#14972 build reads back as
plain `RTPROT_STATIC` realm 0, indistinguishable from an operator route in
shared table 999. The issue's fix direction permits a one-time migration
that adopts such routes "matching a previously applied key"; xpf persists
no previously-applied-key state for table-999 statics (the reconcile is
stateless against the live kernel listing), so there is no safe key to
match against, and claiming every realm-0 `RTPROT_STATIC` IPv6 route would
delete operator routes — the exact fail-open direction #14972 and this
issue forbid ("operator RTPROT_STATIC IPv6 routes stay untouched"). The
pre-existing routes age out on reboot or manual `ip route del`; every route
installed by a current build is reaped correctly. This residual is pinned
by `TestMgmtV6LegacyUnmarkedStaticNotClaimed15163`.
