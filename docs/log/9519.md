# 9519 — a session HIT was never validated against the packet's live ingress zone

- **Timestamp**: 2026-09-10
- **Action**: validate ingress AUTHORITY on every established-session hit, before
  anything acts on the entry; adjudicate a foreign-zone packet by its own zone's
  policy instead of trusting the entry; close the #9384 revocation DoS this
  exposed, and its #7212 filter and host-inbound twins; correct the rationale of
  `the_policy_stamp_does_not_vary_with_the_arrival_interface_8356`

## Re-verification at base, measured before any design

The issue body is the spec (no comments). A temporary probe, deleted before commit,
drove one TCP ACK through the real poll path (`txn_run_descriptor`) on `3b24fe26e`
against a `lan`-zoned session installed with `ingress_ifindex = reth1.0`, with only
`lan -> wan` permitted:

| scenario | hit | revoked | rows left | reading |
| --- | --- | --- | --- | --- |
| S: stale entry, packet on a `dmz` interface | 1 | **1** | **0** | a packet spoofed onto a DENIED zone tore down `lan`'s session |
| F: fresh entry, packet on `dmz` | 1 | 0 | 1 | accepted, no zone consulted — the issue's claim |
| C: stale entry, packet on `reth1.0` (control) | 1 | 0 | 1 | |
| R: `reth1.0` itself re-zoned to `dmz` | 1 | 1 | 0 | #9384's intended revocation |
| P: stale entry, packet on `dmz`, `dmz` permitted | 1 | 0 | 1 | survives, re-stamped by `dmz`'s verdict (read from code; pinned by a cell below) |

`tx` read 0 in every row, the control included: `policy_deny_snapshot` has no
neighbours, so that probe could not see forwarding at all. The acceptance cells
therefore use the #9382 inbound-DNAT fixture, whose control demonstrably forwards.

**S is a defect I introduced.** #9384 (merged) made the Stale branch judge the
from-zone by the packet's arrival interface. With no check that the packet belongs
to the session, that turned the re-derivation into a revocation primitive a host in
any denied zone could fire at another zone's live flow. The issue does not name it;
the measurement found it.

The same shape exists at two more sites, found by reading the hit path rather than by
the probe:

- #7212: `filter_revalidation_target(key, <this packet's logical ifindex>)` reads
  Stale for any foreign interface, re-evaluates THAT interface's static filter, and
  on a discard returns `revoked_key` for the owner's session.
- The host-inbound gate judged a host-bound hit by `resolved.metadata.ingress_zone`,
  the OWNER's zone, and its deny arm tore the session down.

## Census: what every install records as `ingress_zone`

A zone-equality check is only safe if every install records the zone its later
packets resolve to. Every non-test `SessionMetadata` construction:

| site | records | later packets resolve to | agrees |
| --- | --- | --- | --- |
| `poll_descriptor/mod.rs` host-bound install | `from_zone_id` (live arrival) | the same derivation | yes |
| `poll_descriptor/mod.rs` forward install | `from_zone_id` | the same derivation | yes |
| `poll_descriptor/mod.rs` reverse install | `to_zone_id` = `egress_zone_id(egress)` | replies arrive on that egress | yes — the rule #7169 already enforces for NAT replies |
| `shared_ops.rs` reverse from a forward NAT match | `forward_match.metadata.egress_zone` | #7169 validated the arrival against it before installing | yes |
| `forwarding/fabric.rs` punt seed | the peer's zone stamp | fabric packets are exempt; after failover the same zone, since zone ids are `StableZoneID` (FNV of the name) | yes |
| `neighbor_dispatch.rs` missing-neighbor seed | the admission's zone | the same derivation | yes |
| `server/helpers/session_sync.rs` import | the peer's `ingress_zone_id`, or the name lookup | the same zone on a node with the same config | yes, unless config drift |
| `tunnel.rs` local-origin tunnel TX | the tunnel egress zone | keyed on a host-originated inner flow, never presented on AF_XDP ingress by its owner | n/a |

Tunnels needed checking rather than assuming: `gre.rs` never assigns
`ingress_ifindex`, which looked like decapped packets would resolve to the UNDERLAY's
zone while a reverse entry for a flow into the tunnel records the TUNNEL's. They do
not — GRE and WireGuard decap both build the inner meta through
`logical_ingress::build_logical_ingress_packet`, which sets
`ingress_ifindex: params.logical_ifindex` (the tunnel's logical interface).

Embedded ICMP errors do not take the direct hit (`try_reverse_embedded_icmp_error`
runs on the miss path), so PMTUD is not constrained.

## The host-bound cell, and a defect it found that is not #9519's

The first targeted run passed 99 of 100. It failed
`a_foreign_zone_is_held_to_its_own_host_inbound_services_9519` on its first foreign
assertion: the dmz packet did not HIT lan's host-bound session at all. A diagnostic
probe (deleted before commit) printed the poll counters for every packet and showed
why. The cell's own OWNER control, lan's ACK, hit the session and tore it down
(`local=0`, zero rows), so the dmz packet that followed had nothing to hit. With the
foreign packet sent first, on a session nothing else had touched, #9519 behaved as
designed: dmz (no host-inbound services) got `host_inbound_deny = 1` and the session
survived; wan (any-service) was delivered and the session survived.

The same probe run standalone on `origin/master` `5fafce23f` shows the owner's first
ACK revoking the host-bound session there too (`policy_revoked_sessions = 1`). The
#8356 re-derivation judges a `LocalDelivery` session by
`(from_zone -> the local interface's own zone)`, a pair host-bound admission never
asks, and install stamps generation 0, so the first hit always re-derives. The live
ledger reads `egress_zone_id(24) = 1`, so both zones are non-zero and this predates
#9513's zone-0 change.

Filed as #9563, not fixed here. It is an OWNER-path defect in #8356's scope, and
#9519 deliberately leaves owner behaviour unchanged. The cell now runs the owner
control on its own table, so it measures the foreign-authority rule rather than
#9563.

## A full-suite red the filtered runs could not see: the NAT64 counter cell

The targeted runs, filtered by issue number, never executed `afxdp::tests_nat64_tunnel`.
The mutant runs execute the whole bin suite, and one test outside the matrix failed in
ten of twelve completed runs: `txn_nat64_translation_bumps_counter_both_directions`
("the v4->v6 reverse translation must bump the counter exactly once", left 0, right 1).
It PASSED in exactly the two runs that disable the foreign verdict — N1 severs the
authority check and N13 forwards every foreign packet — and `make test` on `36bc489de`
failed on it alone (5,655 passed). So it was #9519's refusal, not a flake.

The cause was the fixture, and the production path agrees with #9519. The cell sent the
v6 SYN on the lan binding (`reth1.0`, ifindex 24) and then delivered the v4 server's
REPLY with the same `txn_meta_v4(24, ...)`. The NAT64 reverse companion records
`ingress_zone: to_zone_id`, the zone the translated flow left through: wan, since the
forward leg went out `reth0.80` by the default route. In production a reply to the pool
address `172.16.80.50`, which sits on `reth0.80`'s subnet, arrives on the WAN interface
and is the owner. Delivering it on lan made it a reply from a zone the flow did not go
to, which #9519 refuses by design.

The cell now delivers the reply on a WAN binding (`reth0.80`, ifindex 12), with a comment
saying why. Nothing in the cell claimed that lan delivery was deliberate: its comments
explain only the neighbour seed and the translated port. Checked both ways before committing: with the corrected fixture the whole `afxdp::tests_nat64_tunnel` module passes, 32 of 32, at `origin/master` `1b5b4c291`, which has no #9519, so the change hides nothing the cell caught before; and it passes, 32 of 32, at `36bc489de`, with #9519.

## Cost, measured

Established before the design: the check runs on every session hit on the SLOW path
(a flow-cache miss, or a packet the cache never takes), and a packet the flow cache
serves pays nothing. An owner verdict is the two hash probes admission itself pays, the
logical-unit resolve and the zone ledger; the policy walk runs only for a foreign packet
and is `#[cold]`.

Then measured on the final code with a release-build probe (deleted before commit), in
one run on a loaded machine (load average 29 on 16 cores), so the ratios carry the claim:

| operation | ns/op |
| --- | --- |
| owner verdict, forward entry | 27.6 |
| owner verdict, reverse entry | 24.2 |
| foreign classification (without the policy walk) | 37.7 |
| one `resolve_ingress_logical_ifindex` | 11.4 |
| loop floor | 4.2 |
| one `SessionTable::lookup` in a 10,000-entry table | 176.8 |

An owner verdict is roughly 15% of the table lookup every slow-path hit already performs,
and that lookup is only one stage of a slow-path hit. The identity fast path that would
have saved the two probes for a packet on its admitting interface was rejected for
CORRECTNESS: after a re-zone it puts two owners with different from-zones under one
generation-only stamp. Cost was not the reason.
