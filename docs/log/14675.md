# #14675 — WG control loop / DNS resolver stale peer capture

## Defect (origin/master 4c6c8fb)
- `init_consumer_state` (wg_control/mod.rs:486) called once at loop start;
  `peer_pubkeys`/`effective_endpoints` frozen for thread lifetime.
- `WgEndpointResolver::spawn` captures `endpoint_hosts` once
  (wg_control/mod.rs:267, tunnel_supervision.rs:1024); resolver thread
  iterates that fixed target list forever.
- `spawn_wg_control_threads` stale reasons (tunnel_supervision.rs:682-741):
  removed / engine_changed / attachment / outer_mtu / bind_device /
  kernel_transport. No peer-set / endpoint / hostname reason.
- `wg_peers_eq` (tunnels.rs:264) does NOT compare `endpoint_host`, so a
  hostname-only peer change reuses the engine Arc verbatim
  (`wg_identity_unchanged`); literal endpoint changes rebuild the engine
  (already covered by `engine_changed` — narrowed: literal-only changes
  are not the live same-Arc bug; `wg_peers_eq` compares `endpoint`).
  `populate_wg_engines` rebuilds on any other peer difference, so the
  engine table always matches config; the control thread and resolver
  are the only stale consumers. This is also why the coordinator
  restart must compare the FORWARDING peer config (which carries
  `endpoint_host`), not the engine table (which does not).

## Fix plan (decision)
Follow the established #2921/#5291/#10196 precedent — the coordinator
already restarts the control thread for every other spawn-time capture
(outer MTU, per-peer MTU, bind device, kernel transport). The peer
configuration is one more spawn-time capture (`peer_pubkeys`,
`effective_endpoints`, `endpoint_hosts`), so it gets the same treatment,
plus an in-loop self-heal so a surviving thread also converges:

1. Coordinator: snapshot the tunnel's peer config at spawn
   (`Vec<WgPeerSpawnConfig{pubkey, endpoint, endpoint_host}>` from
   `forwarding.tunnel_endpoints[id].wg_peers`, sorted by pubkey) into
   `WgControlEntry::spawned_peer_config`; stale-prune gains a
   `peer_config_changed` reason comparing a fresh snapshot. Any peer
   add/remove, literal-endpoint change, or hostname add/remove/rename
   on a reused engine Arc now restarts the thread, which re-seeds
   `init_consumer_state` and respawns the resolver with fresh
   `endpoint_hosts`.
2. Control loop: per-timer-tick `refresh_consumer_peers` re-reads
   `engine.peer_pubkeys()` + a new engine accessor
   `peer_configured_endpoints()` (config.endpoint only, no live
   overlay):
   - new pubkey: adopt; seed effective from configured; BringUp attempt.
   - surviving pubkey whose CONFIGURED endpoint changed: reset
     effective to the new configured value (or remove it when now
     responder-only/hostname) and drop any in-flight attempt. A live
     roam/DNS adoption is not in the configured map, so it survives a
     no-config-change tick untouched.
   - removed pubkey: drop from pubkeys/effective/heard/attempts.
   This covers the window between `reconcile_peers` and the next spawn
   pass and any future spawn-time capture.
3. Resolver: no change needed once the coordinator restarts (respawn
   re-captures hosts). The in-loop refresh handles peers; hostname
   changes flow through the restart. (Dynamic resolver targets were
   considered and rejected as a second mechanism for the same job.)

Residual (documented, #7158 last-good policy): on a hostname rename the
restarted thread seeds effective from `live.or(config)`; the old host's
last-good address can serve until the new host's first resolution
adopts (no authenticated-rx anchor at init, so adoption is immediate
on first answer; retry cadence 5s while unaddressed in the new
resolver). Same failure shape as a DDNS move today.

- Hardening over the original plan (from re-anchoring on current
  master): on a configured-endpoint change/removal the in-loop
  refresh also (a) aborts the engine pending handshake reservation
  via `abort_pending_for_peer`, (b) clears the peer's adopted live
  endpoint (`WgEngine::clear_live_endpoint` / `Peer::clear_live_endpoint`,
  new) so dataplane `peer_for_dest` (live-over-configured) follows
  the operator's new value, and (c) drops the stale
  `last_authenticated_rx` stamp when the peer becomes endpoint-less
  so a renamed hostname's first DNS answer is not roam-held 90s.
  A replaced BringUp attempt for a re-added pubkey also aborts its
  prior reservation. Production note: `populate_wg_engines` rebuilds
  the engine on any `wg_peers_eq` difference and only reuses the Arc
  when the tuple is identical except `endpoint_host`; the coordinator
  restart is therefore the production mechanism, and the in-loop
  refresh is the convergence guarantee for any thread that survives
  an in-place `reconcile_peers` (the unit-level mechanism).
