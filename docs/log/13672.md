# #13672 — serialize shared-session removal with reverse-prewarm cleanup

- **Base**: `5e8c92302` (origin/master at branch start)
- **Branch**: `fix/13672-campaign`

## Why

`remove_shared_session_if` released `shared_sessions` before un-filing its
key from `reverse_prewarm_sessions`. A concurrent publish could replace the
shared row and file its live reverse-prewarm candidate in that gap; the older
removal then erased the new filing, leaving the live session absent from the
activation-prewarm candidate set.

## What

- Keep `shared_sessions` locked through the authoritative reverse-prewarm
  un-file so publish and removal cannot interleave in the unsafe order.
- Remove a redundant post-removal prewarm refresh in the HA delete path; the
  shared removal already performs this cleanup under the synchronization lock.
- Add a deterministic interleaving regression for removal racing a same-key
  republish.

## Validation

- RED: `remove_shared_session_if_serializes_prewarm_cleanup_with_republish_13672`
  failed without the lock-scope fix with the missing-filing assertion.
- GREEN: targeted regression passed; `afxdp::ha::tests::` passed 156 tests.

## Risk

Removal briefly holds the prewarm index mutex while holding `shared_sessions`.
Publishers release `shared_sessions` before updating the prewarm index, and
prewarm readers acquire them in this order, avoiding an inverse nested lock
order.
