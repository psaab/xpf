# #10014 — sole drop binding in nested address-set renders refuse instead of drop

## Summary

A `fail-mode drop` dynamic-address binding whose feed was dropped by its
hold-interval is intentionally published by `SnapshotForBindings` as a
present-but-empty overlay row. A direct policy token already treats that row as
match-none (the requested drop), but a nested address-set walked the empty
feed member as representable-but-not-concrete and failed the top-level
`r && c` gate. The whole snapshot was therefore refused instead of publishing
the configured drop.

The dataplane representability walk now treats a present-empty row as a
concrete drop only when the same name is a declared `fail-mode drop` binding.
An omitted declared binding remains structurally unresolved and still emits
the unsupported-address sentinel, preserving fail-closed behavior for
never-fetched, unknown, or otherwise genuinely unresolved feeds. Ordinary and
undeclared present-empty overlays remain non-concrete and refuse in nested
sets.

## RED / GREEN proof

- RED baseline: the new `TestSoleDropBindingInNestedSetPublishesDrop10014`
  failed because the nested set emitted `SourceLiterals=[__unsupported_address__]`
  and `SourceAddresses=[__unsupported_address__]`. The two new refusal controls
  passed on the same baseline run.
- GREEN targeted proof: the sole-drop publish test, genuinely-unresolved
  omission controls, and present-empty non-drop controls passed in
  `go test ./pkg/dataplane/userspace -run
  'Test(SoleDropBindingInNestedSetPublishesDrop10014|SoleUnreadyBindingInNestedSetStillRefuses10014|NestedPresentEmptyNonDropBindingStillRefuses10014)$' -count=1`.
- Direct-token control: the existing `TestDropModeEmptyRowKeepsTheSnapshotEnforceable9689`
  passed alongside the nested-feed and empty-set controls; the direct token
  remains match-none without the unsupported-address sentinel.
- Full affected suites: `go test ./pkg/dataplane/userspace -count=1` passed;
  `go test ./pkg/feeds -count=1` passed.
