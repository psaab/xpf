# 12620 — gate AppID conntrack restamps on catalog changes

- **Action:** eliminate the per-new-connection conntrack-map lookup when the compiled AppID catalog is unchanged.
- **Files:** userspace-dp `AppCatalog`, `SessionTable`, poll-descriptor revalidation, associated regression tests; this record.

## Why

#12191 correctly refreshed stored AppIDs after an allowed stale zone-policy hit, but every newly installed session starts with an unvalidated policy stamp. The first stale permit therefore entered the restamp path for every new connection. The equal-AppID optimization avoided the map write, not the lookup syscall, leaving the measured steady-state conntrack read per connection.

## What

- `AppCatalog` now has a nonzero fingerprint of its compiled lookup representation, excluding reserved AppID zero. This preserves order independence where lookup behavior is unchanged, while detecting first-writer-wins exact-port collision reorderings that change the selected AppID.
- Each local session records the worker's current catalog fingerprint at install. Imported sessions start unvalidated (epoch zero), since peer-derived state has not been checked against the local catalog.
- The poll pass publishes the current catalog fingerprint to its worker-owned `SessionTable`. Forward and reverse permitted-hit paths reconcile the conntrack AppID only when the canonical session's label epoch differs. A successful/best-effort no-map operation records the fingerprint; a failed live-map read/update leaves it stale and remains eligible for retry even after policy freshness is restored. Zone-policy permit/revoke semantics and reverse-to-forward tuple resolution are unchanged.
- The regression drives two distinct newly installed connections under one unchanged catalog and asserts zero restamp lookups. It also fails a reverse lookup, restores the row, and verifies a later fresh-policy hit retries; the forward path has the same recovered-map coverage. Reverse-DNAT/IPv6 cases pin canonical row and post-NAT resolution.

## RED / GREEN

- **RED / mutant:** removing the catalog-epoch condition from the reverse restamp gate made `new_pair_same_app_id_skips_restamp_write_and_later_restock_works_12191` fail: a second new connection performed one conntrack lookup where zero was expected.
- **RED / failure recovery:** before the retry fix, the recovered-map case failed after the first missing-row lookup had already made policy fresh; the second permitted hit left the AppID at 11 instead of updating it to 22.
- **GREEN:** removing policy-freshness from the label-reconciliation gate keeps catalog-stale rows eligible for retry. The focused regression passes for both reverse and forward retries. The `policy_revalidation` filter passed 44 tests; `app_catalog` passed 16; the AppCatalog epoch test covers lookup-order stability, catalog changes, the zero default sentinel, and conflicting exact-port order.

## Validation

- Focused checks: `policy_revalidation` 44 passed; `app_catalog` 16 passed; `12191` 6 passed.
- Full `cargo test --manifest-path userspace-dp/Cargo.toml --bins --tests`: 7765 passed, 7 ignored, 1 failed. The sole failure is existing unrelated `afxdp::coordinator::fib_dump::tests::fib_dump_refuses_over_budget_without_returning_partial_rows_11767`, which fails while publishing its test fixture due to `RouteEmptyNextHops` for `203.0.113.0/24`; no fib-dump files were changed.
- `cargo fmt --check` fails on widespread formatting differences across the repository; no formatter was run. `git diff --check` passed.

## Risk

The fingerprint is process-local and is only used for equality checks; it is not serialized or exposed as a protocol field. Catalog compilation is a config-apply operation and owns the fingerprint allocation/sort; packet processing remains allocation-free. Imported sessions deliberately pay one local reconciliation the first time a stale permitted hit reaches this path. No live-cluster mutation was performed.
