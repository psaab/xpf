# Issue #10427: Independent route-based IPsec selector defaults

- **Timestamp**: 2026-09-19T06:50Z
- **Problem**: `effectiveTrafficSelectors` applied the route-based wildcard only when both identity-derived selector sides were empty. A route-based VPN with a selector-shaped local identity and omitted remote identity therefore emitted no `remote_ts`; strongSwan's `dynamic` default narrowed the remote side to the peer endpoint `/32`, suppressing routed transit.
- **Change**: In route-based mode (`if_id > 0`), default each empty local or remote side independently to `0.0.0.0/0,::/0`. Explicit selector-shaped identities continue to win, and policy-based VPNs remain unchanged. The regression matrix covers local-only, remote-only, both-empty, both-set, invalid-remote belt fallthrough, and policy-based controls.

## RED -> GREEN proof

- **RED**: With `TestEffectiveTrafficSelectorsOneSidedWildcard10427` added against the pre-fix implementation, `go test -count=1 -run TestEffectiveTrafficSelectorsOneSidedWildcard10427 ./pkg/ipsec` exited 1 at the rendered swanctl layer. The local-only child had no `remote_ts` (keys: `esp_proposals`, `if_id_in`, `if_id_out`, `local_ts`), the remote-only child had no `local_ts`, and the selector-shaped-local/FQDN-remote belt child had no `remote_ts`; each expected `0.0.0.0/0,::/0`. The both-empty and both-set controls passed.
- **GREEN**: After the independent per-side default, the same rendered-output command exited 0. The complete `go test -count=1 ./pkg/ipsec` package suite exited 0; verbose capture reported `go test: 1 packages ok`.
