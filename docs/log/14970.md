- **Timestamp**: 2026-10-18
  - **Action**: Blocked symlink traversal through the user-writable `/home/<user>/.ssh` in login apply and deprovision (D31-02, #14970). `applySystemLogin`'s key-install leg ran `os.Chown` on the `.ssh` path (follows links — re-owns the target directory), then `fsatomic.WriteFileDurable` created its temp file inside the (possibly symlinked) directory and renamed it over the target's `authorized_keys` (root overwrite of an arbitrary path); the emptied-key revocation in `applySystemLogin` and the key removal in `deprovisionLoginUser` ran `os.Remove(managedAuthorizedKeysPath)`, which unlinks the RESOLVED victim file when `.ssh` is a symlink (root deletion of an arbitrary file). The fix adds `checkSSHPathNotSymlink`/`ensureSSHDirSafeForWrite`/`removeManagedAuthorizedKeys` in `pkg/daemon/login_password.go`: every daemon operation on a login user's `.ssh` now `Lstat`s the `.ssh` directory (and `authorized_keys` itself for writes/removals) and refuses a symlink — the apply/revocation fails, the key claim is rolled back (write leg) or the provenance markers are retained for retry (removal legs), and nothing outside the user's own `.ssh` tree is touched. The write leg checks before `MkdirAllDurable`/`Chown` and again immediately before `WriteFileDurable`. `docs/system-login.md` documents the refusal under "A symlinked `.ssh` is refused, never followed (#14970)".
