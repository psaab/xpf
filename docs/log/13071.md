# Issue #13071 — epoch-consistent equal-flow worker cap in `equal_flow_cap_v8`

Source finding: deep-review `D2-06` (run `review-work.2e4cldwkh1`, worker `d2`,
`gemini-4-argon-high`), validated by the three-way research gate and filed as
#13071.

## Defect

`SharedCoSQueueLease::equal_flow_cap_v8`
(`userspace-dp/src/afxdp/types/shared_cos_lease/lease.rs`) multiplied the
published `current_target_per_flow` by the live instantaneous
`worker_active_flow_buckets[worker_id]` count. Under
`V8RateMode::EqualFlowSuppress`, a worker whose peer flow drained mid-epoch
(after consuming its per-flow target) had its live count decremented while the
epoch's fair budget had been computed for — and partially consumed by — the
original count. The cap therefore collapsed retroactively below bytes already
spent and the remaining flows were starved for the rest of the 200 µs epoch,
while the artificially low grants fed the next epoch's `Slowest`/`Mean`
target calculation (progressive downward ratchet). A live count that reached 0
at cap-evaluation additionally produced a synthetic `Some(0)` cap: every
remaining byte of the epoch was denied and `cap_hit_events` /
`suppressed_grant_bytes` recorded suppression telemetry for a cap that was zero
only because the flow count was.

## Fix

`equal_flow_cap_v8` now derives the cap denominator from the epoch-consistent
flow count: `max(live worker_active_flow_buckets, worker_equal_flow_active_samples
for the current epoch tag)` — the same #1745 sticky-max acquire-time sample the
rotation publisher uses as the epoch denominator — so the cap can only stay at
or above the count the epoch's budget was sized for. The sample slot is read
with tag EQUALITY against the acquirer's epoch tag (wrap-safe discipline of
`record_equal_flow_active_sample`); a mismatched slot reads as 0 and falls back
to the live count. A worker with no live flows and no epoch sample returns
`None` instead of `Some(0)`, matching the existing read-only `target == 0` /
stale-tag doctrine (rotation owns fail-open publication), which also removes
the false suppression telemetry. Only `V8RateMode::EqualFlowSuppress` is
affected; `CstructDefault` behavior is unchanged.

## Regression coverage

- `v8_equal_flow_cap_preserves_remaining_flow_share_when_sibling_flow_drains_mid_epoch`
  reproduces the probe from the finding: worker 0 carries 4 flows with a
  published 1_800 B/flow target; three flows consume their shares, one drains
  (live 4 -> 3), and the fourth must still receive its full 1_800 B share in
  the same epoch with no cap-hit/suppressed-grant telemetry; the cap itself
  must stay `Some(7_200)`, including after the live count drains to 0.
- `v8_equal_flow_cap_is_none_for_worker_with_no_flows_and_no_epoch_sample`
  pins the zero-denominator doctrine: `None`, never a synthetic `Some(0)`.

Both tests failed on pristine `origin/master` (`Some(5_400)` collapsed cap /
`Some(0)` synthetic zero) and pass with the fix.

## Risk

Contained to the acquire-side equal-flow cap evaluation in
`EqualFlowSuppress` mode. The cap is now monotonically wider within an epoch
(sticky-max over the live count), so the equal-flow enforcement can only
suppress less within a draining epoch, never more; class-level bounds (epoch
cap, outstanding-leased cap, per-worker fair share) are unchanged. The
`Some(0)` -> `None` change affects only a worker with zero live flows and zero
epoch samples, which previously received no bytes at all.
