# Issue #14689: Fallback and partial IKE policy proposal chain validation bypasses dangling-proposal, proposal-agreement, and missing-PSK commit gates

- **Timestamp**: 2026-10-17
  - **Action**: closed the three fail-open arms of D10-04 so commit and render agree on IKE Phase-1 resolution. (1) `chainResolves` in `validateIKEPolicyChainReferencesStrict` no longer falls through to a same-named ESP (`cfg.Proposals`) entry when an ike-policy was authored — the legacy direct-proposal fallback is consulted only when `ikePolicies[name]` is absent, and a nil-valued IKE proposal entry no longer counts as resolving. (2) Proposal agreement (`validateIKEProposalSettingsAgree`) now runs over every resolved proposal of an authored policy before the chain verdict, so a partially-dangling list (or the former shadowed-ESP rescue) can no longer skip the authentication/lifetime conflict check; the existing helper already skips missing/nil entries, matching the runtime's resolved-entries-only conflict enforcement. (3) `ipsecVPNAuthNeedsPSK` now skips missing/nil/unknown-auth entries exactly like `resolveIKESettings` instead of returning `false` on the first dangling entry, returning PSK-needed if any resolved proposal needs PSK and undecided (`false`) only when nothing resolves. (4) Runtime belt: `resolveIKESettings` consults the `cfg.Proposals` legacy fallback only when no ike-policy of that name was authored, so Phase-1 is never rendered from the ESP table when `cfg.IKEPolicies[name]` exists — it falls through to `errIKEChainUnresolved` and the VPN is skipped. Legacy fallback with no authored ike-policy, the no-policy strongSwan-default case, pubkey VPNs, and partially-dangling lists with a resolvable IKE proposal are unchanged. Regression cells are distinct per claim: shadowed-dangling, shadowed-conflicting, partially-dangling PSK, direct gate pins, and the runtime never-render-ESP pin (plus its legacy control).
