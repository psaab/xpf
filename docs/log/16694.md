# #16694 — DHCP server and relay on one device: strict commit gate with lenient twin

- **Timestamp**: 2026-10-25
- **Action**: refuse a resolved kernel device appearing in both a dhcp-local-server group and a dhcp-relay group of the same family (v6: dhcpv6-local-server vs dhcp-relay dhcpv6) at strict commit, warn on the tolerant path and on the recompute-from-active alarm surfaces.
- **File(s)**: listed under Change.

## Defect

No validator compared `system services dhcp-local-server` /
`dhcpv6-local-server` group interfaces with `forwarding-options
dhcp-relay` (and `dhcp-relay dhcpv6`) group interfaces. Kea binds
`<iface-addr>:67` (raw fallback / udp service socket; v6: 547) and
the relay binds `0.0.0.0:67` per interface with
SO_REUSEADDR+SO_REUSEPORT+SO_BINDTODEVICE (`pkg/dhcprelay`), so on a
shared device whichever service binds second gets EADDRINUSE: Kea
keeps running with no sockets (still passing the unit-active check)
or the relay session fails. Commit showed nothing and status read
healthy, so a leftover stanza made a segment's DHCP behaviour depend
on start order — clients got no lease or were served by the wrong
service.

## Design notes

- **Same-family only.** DHCPv4 (67) and DHCPv6 (547) bind different
  ports, so a v4 server group and a v6 relay group on one device is
  legal and pinned as a survivor.
- **No runtime arbitration.** On the tolerant path both services
  keep their authored groups; which one wins the bind remains
  start-order dependent there, exactly as today. Arbitrating at the
  daemon would invent a precedence (server-wins vs relay-wins) no
  contract states; the fix the issue asks for is the commit gate,
  with the warning keeping the persisted case audible. Cross-family
  and disjoint rows are untouched.
- **No interfaces stanza.** Wildcards match nothing (no declared set
  to expand over) and only refs that resolve identically without any
  declaration collide, so the gate never invents devices.

## Risk

Configs that today commit clean with the same device in both a
DHCP-server group and a same-family relay group now fail commit
naming the device; such a config never served that segment from
both services. Tolerant loads still boot with a warning.
