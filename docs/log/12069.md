# #12069 — resolve community names in policy set actions

- **Timestamp**: 2026-10-07 (original implementation; review follow-up folded 2026-10-09, stacked on #12068)
- **Action**: for policy `then community` set-clause operands (not `from community` match operands), resolve authored names exactly once in the compiler post-pass; strict validation and rendering consume only resulting FRR literals. Strict commit rejects failed/invalid/empty/regex-backed operands; tolerant load warns and omits a failed action. Unicode separators unsupported by emitted FRR are rejected rather than accepted as token separators.

## Red before

On the PR's pre-fold tip `2e7fb03fe` (whose parent is `aa9b5f418`), the new focused regressions failed for both review findings: add/set/bare `CUST` expanded to `no-export` and then rendered as `65000:999`; a numeric literal collision was re-expanded; a colliding regex definition false-rejected a resolved literal; and U+00A0/U+2003/U+2028 passed the literal gate and were emitted unchanged. These failures were reproduced on the actual PR tip that introduced the defects; `aa9b5f418` predates that PR implementation.

## Change

- `ResolveCommunityValue` remains the name-first resolver used only by the compiler's fully-compiled-config post-pass. `ValidCommunityValueLiteral` is used by strict validation and the FRR renderer, which consume compiled operands without a second community-name lookup. Failed lookup preserves the authored operand in `PolicyTerm.Community`/`CommunityAdd` and sets compiler-only `CommunityResolutionFailed` state (`json:"-"`).
- Narrowed `frrStandardCommunityLiteral` to ASCII spaces plus C0/DEL controls that the render sanitizer converts to ASCII spaces; Unicode separators are rejected.
- Added collision regressions for add/set/bare, numeric-literal/name, and regex-member false-reject cases; added empty-definition rejection and explicit name-first precedence coverage. Strengthened non-literal diagnostics, corrected the use-before-definition test description, and restored the valid as-path-prepend injection assertion.
- Updated the policy community contract in config/FRR/schema docs; tolerant paths warn and omit malformed community set clauses. This resolution and omission behavior is limited to set-clause operands; `from community` match operands remain separate.

## Operator-visible upgrade note

A config accepted by the base that has a set-clause operand whose spelling also names an empty, regex-backed, or otherwise non-literal community definition is now rejected at commit. On tolerant boot, the affected `then community` set action is warned about and omitted until the definition or operand is fixed; it is no longer emitted as though the literal-shaped spelling had resolved successfully. This applies to set-clause operands, not `from community` matches.
