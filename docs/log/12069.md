# #12069 — resolve community names in policy set actions

- **Timestamp**: 2026-10-07 (stacked on #12068)
- **Action**: resolve defined community names used by `then community add|set` and the legacy bare replacement form to their literal members; reject operands that are neither valid FRR community literals nor defined all-literal communities; omit and warn on invalid tolerant-path render values.

## Red before

Focused config and FRR regression tests failed on base `0b5c55fb1`: compilation stored `CUST` unchanged for add, set, and bare forms; an undefined `NOPE` operand was accepted; and the renderer emitted no resolved `set community 65000:100 additive` clause and did not omit a raw `NOPE` value. The issue report describes the resulting FRR `Malformed communities attribute` at exec and exported routes missing the requested community.

## Change

- Added shared `config.ResolveCommunityValue`, which accepts FRR standard literal values or expands a single defined community name only when every definition member is a standard literal. Multi-member definitions are emitted as space-separated values in authored order. The shared literal predicate now scans without allocating temporary mapped/word slices.
- Added a fully-compiled-config post-pass before strict validation, so add/set/bare references resolve regardless of policy/community authoring order or policy-options root. The strict community gate now rejects undefined values, invalid literals, empty definitions, and named definitions containing non-literal members; the existing tolerant-path downgrade remains unchanged.
- Added renderer defense-in-depth for add/set/bare: resolve or validate the value, otherwise warn and omit only the malformed set clause. `delete` remains list-name based; `none` remains unchanged. The schema leaf remains multi-token because it encodes both operation and operand; cross-reference and literal validation occur after compilation.
- Added focused config and FRR regressions for defined-name expansion, use-before-definition across roots, multiple members, invalid/non-literal operands, strict rejection, literal rendering, and warning/omission without dropping sibling clauses. Updated the #6714 and #9620 parser-equivalence fixtures to define their community names while retaining their original parser/field assertions. The bracket-list slot sweep now uses the production grouped set parser so reserved words in a list remain operands.
