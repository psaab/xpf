# #12069 — resolve community names in policy set actions

- **Timestamp**: 2026-10-07 (original implementation; review follow-up folded 2026-10-09, stacked on #12068)
- **Action**: resolve authored community names exactly once in the compiler post-pass; strict validation and rendering accept only the resulting FRR literals. Reject invalid/empty/regex-backed operands at commit, omit them on tolerant rendering, and reject Unicode separators that do not survive the render sanitizer as FRR separators.

## Red before

On the PR's pre-fold tip `2e7fb03fe` (whose parent is `aa9b5f418`), the new focused regressions failed for both review findings: add/set/bare `CUST` expanded to `no-export` and then rendered as `65000:999`; a numeric literal collision was re-expanded; a colliding regex definition false-rejected a resolved literal; and U+00A0/U+2003/U+2028 passed the literal gate and were emitted unchanged. These failures were reproduced on the actual PR tip that introduced the defects; `aa9b5f418` predates that PR implementation.

## Change

- `ResolveCommunityValue` remains the name-first resolver used only by the compiler's fully-compiled-config post-pass. Added `ValidCommunityValueLiteral` for strict validation and the FRR renderer; both validate/emit compiled operands without a second community-name lookup, so authored-name and resolved-literal roles cannot collapse.
- Narrowed `frrStandardCommunityLiteral` to ASCII spaces plus C0/DEL controls that the render sanitizer converts to ASCII spaces; Unicode separators are rejected.
- Added collision regressions for add/set/bare, numeric-literal/name, and regex-member false-reject cases; added empty-definition rejection and explicit name-first precedence coverage. Strengthened non-literal diagnostics, corrected the use-before-definition test description, and restored the valid as-path-prepend injection assertion.
- Updated the policy community contract in config/FRR/schema docs; tolerant paths warn and omit malformed community set clauses.
