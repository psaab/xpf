# Issue #14326 — WG endpoint lookup ignores outer destination IP and ingress zone

- **Issue:** `wg_endpoint_for_listen_port` selected the first `wg_engines`
  (HashMap order) entry matching only `(wg_listen_port, transport_instance)`,
  taking no `dst_ip`; the `forwarding.tunnel_endpoints.get(id)?` inside the
  loop aborted the whole lookup when one engine lacked an endpoint row.
  `wg_outer_zone_matches` compared only the zones of `dst_ip` and
  `endpoint.source`, never requiring `endpoint.source == dst_ip`. With two
  WireGuard tunnels sharing a listen port in one transport instance bound to
  different local IPs, decap / underlay-exemption selection was
  non-deterministic: the wrong engine was fed the record (WG AEAD fails —
  fail-closed availability loss), the wrong `logical_ifindex` was attempted,
  and `is_wg_listener_tuple` inherited the mis-selection.
- **Fix (userspace-dp/src/afxdp/wg/decap.rs):**
  - `wg_endpoint_for_listen_port` now takes `dst_ip: IpAddr`; a candidate
    must match port, WireGuard mode, transport instance,
    `endpoint.source == dst_ip` (same family; unspecified allowed and then
    failed closed by the zone check), and `wg_outer_zone_matches(...)`.
    A missing endpoint row is skipped with `continue` instead of `?`.
  - `wg_outer_zone_matches` additionally requires
    `endpoint.source.is_unspecified() || endpoint.source == dst_ip` within
    one address family. Cross-family sources are deliberately not an
    equality gate: a v4-bound listener also serves records arriving as
    mapped v6 (#10686), admitted on the v6 destination's owner zone alone
    (pre-existing behaviour, pinned by
    `mapped_ipv6_wg_underlay_candidate_stays_outside_inner_ingress_gate_10686`).
  - Callers updated: `is_wg_listener_tuple` passes its `dst_ip`;
    `is_wg_underlay_frame` parses the v6 destination before the lookup;
    `try_wg_decap_from_frame_with_input_filter` resolves
    `outer_destination_ip` before selecting the endpoint. The explicit
    zone gate at the AEAD boundary is retained (fail-closed).
  - No other callers of `wg_endpoint_for_listen_port` exist (internal fn).
- **Regression (userspace-dp/src/afxdp/wg/decap_tests.rs):**
  - `wg_same_port_multi_tunnel_selects_exact_dst_ip_14326`: two tunnels
    (ids 1/2, ifindexes 400/401, sources 172.16.80.8/.9, same port 51820,
    same WAN zone and transport instance, independent established engine
    pairs). Asserts `is_wg_listener_tuple` for both destinations, decap of
    each tunnel's record under its own logical ifindex, and fail-closed
    cross-addressing. Messages carry no test-input special-casing in
    production code.
  - `wg_same_port_lookup_skips_engine_without_endpoint_14326`: an orphan
    engine (id 99, no endpoint row) must not abort the lookup.

## RED -> GREEN proof

- **RED (on origin/master, test only):** `cargo test --bin xpf-userspace-dp wg_same_port`
  — both tests FAILED
  (`wg_same_port_multi_tunnel_selects_exact_dst_ip_14326`:
  "record for tunnel B at IP_B must decap via engine B";
  `wg_same_port_lookup_skips_engine_without_endpoint_14326`:
  "orphan engine row must not abort the listener lookup").
- **GREEN (with fix):** same command — 2 passed.
- **Regression suite:** `cargo test --bin xpf-userspace-dp decap` —
  151 passed, 2 failed. The 2 failures
  (`gre_tun_origin_pair_needs_no_permit_10038`,
  `gre_tun_origin_vrf_reverse_resolves_local_10038`, both
  `local_tunnel_resolution:ha_inactive`) fail identically on a pristine
  origin/master base worktree (149 passed / same 2 failed), i.e.
  pre-existing and unrelated. `cargo test --bin xpf-userspace-dp wg_` —
  199 passed, 2 failed; those 2
  (`wireguard_segmentation_*`) also fail identically on base.
- **Note:** `cargo fmt` was NOT run crate-wide: the repo tree is not
  rustfmt-clean under the installed toolchain and a crate-wide format
  touches ~500 unrelated files. Only the two touched files were formatted
  with `rustfmt --edition 2024 <file>`, and pre-existing fmt churn in
  `decap_tests.rs` was stripped so the diff contains only the fix and the
  new tests.
