# #12143 — persist and surface deferred binary upgrades

- **Issue**: #12143 — postinst could return success after a publish or cut failure without durable staged-versus-running status.
- **Branch**: `fix/12143-postinst-marker`
- **Worktree**: `/var/worktrees/12143-postinst-marker`
- **Base**: `a714c90d472a3c3d98a3799831cfef3ec311a61c`

## Why

The Debian postinst intentionally preserves exit 0 when binary-generation publish or cut-over fails, avoiding a half-configured package. Before this change, generic failures were log-only and lock-contention hints lived under `/run`; no binary-channel consumer could report after reboot whether the staged generation differed from the running daemon.

## What

- Atomically persist a mode-0600 `/var/lib/xpf/upgrade-deferred` record for generic and lock-busy publish/cut failures, including staged and live daemon versions (or `unknown` when no running executable can be proven), stable reason, recovery command, and UTC time. Keep the deliberate exit-0 contract; clear the record after a successful cut or rollback. Intentional clustered and `XPF_NO_POSTINST_CUT=1` stage-only paths do not create a failure record.
- Add `xpfd upgrade status` to render pending or unreadable durable state, and expose readable/pending state plus staged/running versions, failure reason, and timestamp on `/health`. This is informational and does not mark a still-forwarding old generation unhealthy. The daemon reports its in-memory build version rather than inferring the live process from `versions/current`.
- Document the recovery/status contract and cover postinst failure/control cases, status rendering, clearing, daemon version selection, and health reporting.

## Validation

### RED before the fix

At the clean base `a714c90d472a3c3d98a3799831cfef3ec311a61c`, the throwaway postinst probe observed exit 0, staged `v2`, running/current `v1`, and no durable marker for generic publish failure, publish-lock busy, generic cut failure, pre-cut lock busy, and an inner cut-lock race. STEP-0 also found no `upgrade-deferred` reader in `pkg/`, `cmd/`, or `scripts/`. The same probe confirmed intentional clustered stage-only, manual stage-only, and successful postinst controls did not leave a marker.

### GREEN after the fix

- `python3 /tmp/xpf-12143-marker-probe.py debian/xpf.postinst` — PASS for all five failure arms; cluster-stage-only, manual-stage-only, and success controls remained marker-free.
- `sh -n debian/xpf.postinst && sh test/debian/postinst-test.sh` — PASS, all postinst scenarios.
- `dash -n debian/xpf.postinst && dash test/debian/postinst-test.sh` — PASS, all postinst scenarios.
- `go test ./pkg/upgrade ./pkg/api ./pkg/daemon ./cmd/xpfd -count=1` — PASS for all four scoped packages.
- `go run ./cmd/xpfd upgrade status` — PASS; actual CLI reported `No unresolved postinst publish/cut failure` on the clean host state.
- `gofmt` completed on all changed Go files.

No broader scoped reds occurred, so same-base attribution was not needed. No live-cluster mutation was performed.

## Risk / remaining acceptance

If `/var/lib/xpf` cannot be written or synced, postinst still returns success by design and emits a warning; status consumers report unreadable state rather than claiming no failure. `/health` remains HTTP 200 for this informational skew because the previous binary remains the running forwarding generation. Clustered rollout behavior was not exercised against a live cluster.
