# Issue #12525 — accept non-zone source-NAT scopes in compileNAT

## Why

`assignZoneIDs` registers only configured zone names, never the empty string.
`compileNAT` nevertheless required both `FromZone` and `ToZone` to be present in
that map. Source-NAT rule-sets scoped by interface or routing-instance carry an
empty zone field on that side; an unscoped side is represented by the same empty
fields. As a result, the #12085 to-interface, to-routing-instance, and unscoped
rows failed in the NAT validation pre-pass with `source NAT to-zone "" not
found`, before the userspace snapshot builder could receive them.

## What

The source-NAT gate checks a zone ID only for a non-empty zone name. Scope
provenance comes from either a non-empty typed zone/interface/routing-instance
field or a private compiler stamp for an implicit unscoped default. The config
compiler sets that stamp while applying an absent `from` or `to` clause; it is
not operator-settable. This accepts legitimate empty zone fields, including
the #12085 unscoped row whose six public scope fields remain empty, without
confusing it with a zero-value `NATRuleSet` that has no compiler provenance.
Named zone references still require a registered zone ID. The marker is
intentionally not serialized, so losing it on an all-empty rule-set fails
closed at the dataplane gate.

## Risk

The gate accepts non-empty typed scopes or compiler-stamped implicit unscoped
defaults; it does not insert a synthetic empty zone ID or relax named-zone
lookup. Missing provenance on an all-empty rule-set fails closed, including
after serialization drops the private stamp. The legacy interface-mode
compiler still has its existing zone-address resolution behavior; this change
lets the userspace snapshot path consume the compiled typed scope. No live
cluster forwarding test was run.
