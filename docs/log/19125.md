# #19125: CLI loopback owner check refuses xpfd while the server half is SYN_RECV

- **Timestamp**: 2026-11-16 07:55Z (lane H2)
  - **Action**: Took #19125 from the coordinator (it cost a VOID H11 move
    on tcp in G6's integ2 gate: s5-from0 move 2). Branched
    `fix/19125-authz-synrecv` on master c61aa074f0. The issue has no
    comments.
  - **Read** (at c61aa074f0):
    - `pkg/authz/client.go` `VerifyLoopbackServerConn` runs on every
      loopback dial (`DialContext`, used by `cmd/cli/main.go:61` and
      `pkg/upgrade/cluster_cli.go:77`). It calls `LookupPeer` with the
      mirrored 4-tuple and refuses unless the server row is attributed;
    - `pkg/authz/peer.go` `LookupPeer` attributes only
      `found && state == tcpEstablished`. Any other found state returns
      "peer socket is in TCP state %d, not established";
    - `pkg/authz/socketscan.go`: a query is answered only from a table
      read that STARTED after it, so a re-read is a fresh observation.
  - **Mechanism.** `connect()` returns when the client has the SYN-ACK
    and has sent the final ACK. The SERVER half leaves TCP_SYN_RECV (3)
    only when its kernel processes that ACK, which on loopback is softirq
    work. A read right after the dial can land first, more often on a
    loaded box (fw0's loadavg reached 9.7 in the original record). A
    persistently full accept queue would also hold the server half in
    SYN_RECV (the ACK is dropped until the queue drains).
    - The client's own comment claimed "a dialed connection we hold open
      is ESTABLISHED"; that is true of OUR half only.
    - The server side (#5278 / #5561) cannot hit this: the caller it
      attributes finished its handshake before `accept()` returned.
  - **Fix** (client half only; attribution not weakened):
    - `LookupPeer` is unchanged in what it attributes. It only flags a
      found row in TCP_SYN_RECV (unexported `PeerIdentity.synRecv`, never
      with OK).
    - `verifyLoopbackServerConn(ctx, conn)` re-reads the table, ONLY while
      the row is SYN_RECV, on a bounded backoff
      (`synRecvRereadDelays19125`: 1, 2, 5, 10, 20, 50, 100, 200, 300 and
      300 ms; 988 ms in total) that honours the dial's context. It then
      applies the unchanged checks: ESTABLISHED, uid 0. Nothing is
      attributed from the SYN_RECV row.
    - Every other non-established state is refused at once, as before;
      TIME_WAIT's mini-socket reports uid 0.
    - A server half still in SYN_RECV past the bound is refused, and the
      error says "still SYN_RECV after N re-reads over T (#19125)".
    - `DialContext` passes its context (the gRPC dial deadline);
      `VerifyLoopbackServerConn` keeps its signature (Background).
    - `loopbackDialer19125` is DialContext's dialer, a zero `net.Dialer`
      in production, made a variable so a cell can pin the client port.
  - **Cells** (`pkg/authz/client_synrecv_19125_test.go`; the fixture is
    rewritten through the re-read seam):
