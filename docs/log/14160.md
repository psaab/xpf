# 14160 — sendFailoverBatchResult keeps broken ackConn on fallback success; unreachable else-if on dual failure

`sendFailoverBatchResult` (`pkg/cluster/sync_failover.go`) diverged from
its single-result twin `sendFailoverResult` in two ways. First, when the
write to the active conn (`ackConn`, from `getActiveConn`) failed and the
fallback write to the receiving `conn` succeeded, the batch path returned
success without `handleDisconnect(ackConn)`: the known-broken connection
stayed installed as the active conn, so every subsequent failover/sync
write paid a failed first attempt (or a write-timeout stall on a
blackholed conn). The twin disconnects `ackConn` on any first error
regardless of the fallback outcome. Second, on dual failure the batch
path's `if ackConn != nil { handleDisconnect(ackConn) } else if conn !=
nil { handleDisconnect(conn) }` could never take the `else if` — `ackConn`
was forced non-nil a few lines above (early return when both are nil) —
so the fallback `conn` was never disconnected there, while the twin
disconnects `ackConn` on the first error and `conn` on the final error.

Fix: mirror the twin exactly. After releasing `writeMu`,
`if firstErr != nil && ackConn != nil && ackConn != conn {
handleDisconnect(ackConn) }` runs unconditionally of the fallback result,
and the `err != nil` arm now warns, counts `stats.Errors`, and calls
`handleDisconnect(conn)` unconditionally (matching the twin, which passes
a possibly-nil `conn` that `handleDisconnect` harmlessly ignores via its
stale-disconnect branch). The unreachable `else if` is deleted. No other
behavior changes: the oversized-batch refusal, payload encoding, logging
fields (plus the retained first-error warn on dual failure), and error
counting are unchanged. Fail-closed direction preserved: a conn that
provably failed a write is always torn down; a healthy fallback that
delivered the result is never disconnected.

Regression (`pkg/cluster/sync_failover_batch_result_14160_test.go`): a
fake `net.Conn` (`failoverResultConn14160`) with a configurable write
error and observable `Close`, installed as `conn0` (active ack conn) and
`conn1` (fallback) on a real `SessionSync`, with `outboundBulkAcked`
pre-set so the partial-disconnect branch does not schedule a bulk
re-drive. `TestSendFailoverBatchResultDisconnectsBrokenAckConn14160`
(failing ack + succeeding fallback: ack closed and evicted from `conn0`,
fallback untouched, no error counted),
`TestSendFailoverBatchResultDualFailureDisconnectsBoth14160` (both conns
closed and evicted, one error counted),
`TestSendFailoverBatchResultHealthyAckKeepsConns14160` (control: success
disconnects nothing), and `TestSendFailoverResultDisconnectsBrokenAckConn14160`
(twin guard so the two paths cannot drift apart again).

RED-verified in a separate base worktree at origin/master (55e93ffec)
with only the test file copied: the two batch tests fail there
("broken ack conn was not disconnected after fallback success",
"fallback conn was not disconnected on dual failure") and pass with the
fix; the control and twin tests pass on both, as designed.

Closes #14160
