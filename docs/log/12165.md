# #12165 — re-arm heartbeat suppression after recovery

- **Issue**: #12165 — heartbeat suppression's 5s cap remains consumed across heartbeat recovery, allowing a later heartbeat-only gap to trigger takeover immediately.
- **Branch**: `fix/12165-hb-stamp`
- **Worktree**: `/var/worktrees/12165-hb-stamp`
- **Base**: `1c384b9a47ff7d6e567fa50632faa75c3995ae87`

## Why

`hbSuppressStart` was cleared on sync connection lifecycle changes but not when an admitted heartbeat proved the peer had recovered. A later heartbeat-only gap on the same still-fresh sync connection therefore inherited the earlier suppression timestamp; once that stamp was older than 5s, timeout suppression ended immediately and the secondary could take over. The cap is intended to bound one continuous interval, not all separate outages on one sync connection.

## What

- Added a peer-heartbeat-admission notification on the cluster Manager and wired it to the daemon's lock-free `hbSuppressStart` reset. Every admitted heartbeat clears the current stamp, so an actual recovery ends that suppression interval while back-to-back heartbeat loss without recovery remains continuously capped.
- Re-check heartbeat freshness after a suppressing timeout guard and repeat the idempotent recovery notification under `m.mu` when a heartbeat landed during the guard. This prevents a guard's late stamp write from surviving recovery.
- Updated the hook installation inventory and binding assertions for the new recovery notification. Added narrow test seams to exercise the real heartbeat admission and timeout handlers without sockets.
- Added a repeat-gap regression fixture: with the same connected, fresh session-sync connection, interval one is suppressed, a heartbeat is admitted, more than 5s passes while heartbeats are healthy, and interval two must be suppressed under a newly anchored cap. Afterward, the second interval's own expired cap permits takeover. The fixture asserts peer/election state, not timing-log sentinels.
- Updated the restart comment to describe heartbeat-recovery clearing rather than claiming the cap has no sticky state.
