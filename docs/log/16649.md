# #16649 — clear-all helper cap

- **Timestamp**: 2026-10-25
  - **Action**: Paged `clear security flow session` (clear-all) inside the
    Rust helper under one clear fence: `SessionDomain::clear_mirror` now
    loops bounded key batches (`CLEAR_MIRROR_KEY_CAP` = 262,144 keys per
    round, ~18MB transient Vec max per round) until the shared table is
    empty, instead of refusing tables above 262,144 entries with
    `clear-cap-exceeded` and revoking nothing. The BPF sweep still runs
    first and exactly once (fail-closed: a sweep failure touches no
    authority); per-round per-key deletes use the existing fenced
    `delete_synced_session_gen_marked`, then owner-RG indexes, NAT and
    forward-wire maps are cleared as before. Go's single
    `mirror_clear_chunk` round trip is unchanged — paging is invisible
    to CLI/gRPC/REST, so peer clear and policy-invalidation debt
    retirement (`retirePolicyInvalidationScanDebtAfterFullClearLocked`,
    which keys off a successful `ClearAllSessions`) now happen at any
    admitted table size. `batch=0` is refused (`clear-batch-zero`)
    before the fence/sweep and touches nothing. Replaced the Rust
    over-cap fail-closed cell with an over-old-cap paged-to-empty cell
    (5 rows, batch=2, three rounds) plus a zero-batch refusal cell.

    tests, as before. Residual: a table at the production batch

    the batch seam at small scale, not by seeding 262k+ rows in CI;
    cluster verification at >131k concurrent sessions remains a lab
