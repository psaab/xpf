# #13222 — account for and order kernel-hold failovers

## Finding

The D4-04 source finding identified two HA state-transition defects in
`pkg/cluster/kernel_selfrecover.go`. `SetKernelUpgradeHold` directly demoted
primary RGs without incrementing `FailoverCount` or clearing the committed
transfer-role pin, and iterated the groups map nondeterministically.
`ResetAllFailover` first cleared the upgrade hold and ran an election while all
RGs were still manually drained, then reset RGs in map order. Consequently the
first election could not rejoin any RG, and a data RG could be reset before RG
0 on later elections.

## Change

`SetKernelUpgradeHold` now snapshots and sorts RG IDs before demotion; each
actual Primary-to-Secondary transition clears `transferCommitRolePinned`,
increments `FailoverCount`, and emits the event in stable RG order.
`ResetAllFailover` sorts its snapshot and resets RGs in order, letting the
existing per-RG reset clear the hold as it resets RG 0 first. The empty-group
case still clears the hold explicitly. Regression tests cover demotion
accounting, stable event/promotion order, hold release, restored weight, and
successful single-node re-election.

## Validation

- RED on pristine master: `go test ./pkg/cluster -run
  'Test(SetKernelUpgradeHoldDemotionCountsFailover|ResetAllFailoverRejoinsAllDrainedRGs|ResetAllFailoverSortedRejoin)13222' -count=1`
  failed because the hold demotions left `FailoverCount` at zero and kept
  `transferCommitRolePinned` set.
- GREEN: `GOCACHE=/var/worktrees/.cache/go-build
  GOTMPDIR=/var/worktrees/.cache/go-tmp go test ./pkg/cluster -count=1`
  — passed (`ok github.com/psaab/xpf/pkg/cluster`, 126.588s).

## Risk

No intended operator-visible behavior change beyond correct HA failover
accounting and deterministic RG ordering. The reset-all behavior still uses the
existing per-RG reset and election machinery; this change does not alter the
normal single-RG reset path.
