# #14351 — junos-host deny ignores bound secure-tunnel units

## Defect
`junosHostZoneNetdevCoverageMap`, `junosHostZoneByInterface`, and
`junosHostZoneExemptNetdevs` walked only `cfg.Interfaces.Interfaces`
declared units. A route-based IPsec tunnel authored only via
`security ipsec vpn <v> bind-interface st0.0` (no `interfaces st0 unit 0`
stanza, or only a bare `interfaces st0 { description ... }` parent) was
scoped to the nonexistent `st0` netdev (or to nothing), so the
`to-zone junos-host` deny could not fire on `st0.0` while
`RenderedPolicyKeys` suppressed the #4168 warning. `InterfaceUnitRefKeys`
also only ran its IPsec bind walk when no interface stanza existed.

## Fix
- `pkg/config/host_inbound_effective_view.go`: `InterfaceUnitRefKeys`
  now runs the bind-interface walk whenever the base is a secure-tunnel
  name (declared units deduped downstream), gated by
  `SecureTunnelNetdevForRef` (unbound/colliding units never invented).
- `pkg/config/junos_host_deny.go`:
  - `junosHostZoneByInterface`: bare refs fan down via
    `InterfaceUnitRefKeys` instead of only declared units.
  - `junosHostZoneNetdevCoverageMap`: no early return when
    `cfg.Interfaces` is empty; synthetic rows for
    `ZoneAuthoredBoundSecureTunnelUnitRefs` (skipping declared Shape-A
    units and quarantined refs) with netdev from
    `SecureTunnelNetdevForRef` (authored spelling, e.g. `st0.0`).
  - `junosHostZoneExemptNetdevs`: same synthetic rows so IKE/ident
    exemptions reach `st0.0`.

## Regression
`TestJunosHostDenyBoundSecureTunnelUnitCoverage` in
`pkg/config/junos_host_deny_14351_test.go`: bare `st0` with parent
stanza, explicit `st0.0` without stanza, bare `st0` without stanza, and
a `from-zone any` suppression case.
- RED on master: IngressNetdevs=[st0] (bare+parent) / [] (no stanza),
  coverage empty, RenderedPolicyKeys missing.
- GREEN with fix: IngressNetdevs includes `st0.0`, rendered keys set.
