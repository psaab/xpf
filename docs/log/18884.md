# #18884 — route reth VRID overflow fixtures to the VRID gate

- **Timestamp**: 2026-11-02 (`wt-18884`, base `5e65228f29`)

## Why

#17910 (`bb30dcb6dd`) added chassis redundancy-group declarations to the reth
VRID fixtures so they would satisfy the defined-RG contract. Those declarations
used the same 156/200/255 ids as the reth under test. The later #8317 dataplane
array bound now rejects those declarations at 0..15 before the reth-derived
VRID ceiling (155) can run, making the overflow integration pin exercise the
wrong validator. The 100/155 boundary rows and both RG-200 skip-mode siblings
were blocked by the same fixture premise.

## Gate-order proof

`runUniformGates` runs the cluster/zone segment before routing/RIB/RPM. Within
that order:

1. `validateChassisClusterStrict` (`compiler_uniformgates_cluster_zone.go:103`)
   rejects an overflowing chassis RG declaration at the 0..15 array bound.
2. `validateRethVRRPGroupIDStrict` (`compiler_uniformgates_cluster_zone.go:215`)
   checks the reth target's derived VRID.
3. `validateRethRedundancyGroupStrict` (`compiler_uniformgates_routing_rib_rpm.go:484`)
   later rejects a reth target with no matching chassis RG declaration.

The preferred path is therefore reachable: declare only in-range chassis RG 1,
leave the reth pointed at 156/200/255, and the VRID gate fires before the later
undefined-RG gate. The rejected fallback of merely asserting the chassis range
error was not used.

## What

- `TestRethRedundancyGroupIDOverflowsVRIDFailsCommit`: touched all 156/200/255
  rows through their shared fixture. Only chassis RG 1 is declared; the reth
  retains the overflowing id. Strengthened the strict error assertion to
  require the 1..155 VRID-overflow signature and retained lenient no-brick and
  warning assertions.
- `TestRethRedundancyGroupIDInRangeCommits`: retained id=1 as a full compile
  integration cell. Converted ids 100 and 155 to direct
  `validateRethVRRPGroupIDStrict` cells because those ids cannot be declared as
  chassis RGs without tripping the earlier array gate.
- `TestRethRedundancyGroupIDOverflowSkippedWhenRGElectionPrivate` and
  `TestRethRedundancyGroupIDOverflowSkippedUnderNoRethVRRP`: converted both
  RG-200 siblings to direct typed validator cells for the same reason. Their
  private-election and no-reth-VRRP skip premises are unchanged.
- No production behavior changed.

## Validation

All Go tests used the required guard and environment:
`GOCACHE=/var/worktrees/.cache/go-build GOTMPDIR=/wtgt
./scripts/testguard-run.sh go test ...`.

- **STEP-0 RED**: `go test ./pkg/config -run
  '^(TestRethRedundancyGroupIDOverflowsVRIDFailsCommit|TestRethRedundancyGroupIDInRangeCommits)$'
  -count=1 -v`. Overflow ids 156/200/255 and in-range ids 100/155 failed with
  `chassis cluster: redundancy-group id ... is out of range 0..15`; id=1 passed.
  A baseline `^TestRethRedundancyGroupID` run also showed both RG-200 skip-mode
  siblings failing at that chassis gate.
- **Named GREEN**: the same two-test command passed all overflow and in-range
  rows after the fixture correction.
- **FAIL-ON-REVERT mutant**: temporarily replaced the VRID dispatch expression
  at `compiler_uniformgates_cluster_zone.go:215` with `error(nil)`, then ran
  `go test ./pkg/config -run '^TestRethRedundancyGroupIDOverflowsVRIDFailsCommit$'
  -count=1 -v`. All three overflow rows went RED: execution fell through to the
  #15199 undefined-RG error, which lacks the required VRID out-of-range
  signature. Restored the real dispatch immediately.
- **Whole-file GREEN after mutant restoration**: `go test ./pkg/config -run
  '^TestRethRedundancyGroupID' -count=1 -v` passed all four tests, including
  both RG-200 siblings.

## Risk and gaps

Test fixtures and assertions only; no runtime or operator-facing behavior
changed. Direct cells deliberately isolate VRID behavior that a full compile
cannot reach under the independent chassis 0..15 bound. No broader package or
repository suite was run; validation was limited to the brief's named cells and
whole-file sibling set.
