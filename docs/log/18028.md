# #18028 — Snapshot accepted keys under writeMu in ReconcileConnectionAuth

- **Timestamp**: 2026-10-27
  - **Action**: Moved the accepted-key snapshot in `ReconcileConnectionAuth` from before the per-connection `writeMu` sections into ONE `writeMu` section covering the whole connection batch (snapshot once per reconcile under the lock, not per connection), mirroring the #18016 rule in `enforceStrictSessionAuth`. The upgrade prompts (`beginAuthUpgrade`) stay in a separate pass — `writeMu` is a non-reentrant `sync.Mutex` and `beginAuthUpgrade` takes it itself. Added a deterministic interleaving regression (`TestRetirementGraceSurvivesConcurrentReconcileSnapshot18028`) proving a fresh #16857 retirement grace survives a concurrent stale-snapshot reconcile and still expires into eviction, and rebased `TestRetirementGraceSurvivesConcurrentEnforcementSnapshot18016` on the new ordering: the reconcile now parks on `writeMu` BEFORE snapshotting, so its fresh-ring snapshot (`secondSnapshot`) is observed after the enforcement gate opens, not before. That reordering is exactly why the naive per-connection move broke the gated test — it demanded the reconcile's snapshot while enforcement held the lock, which the fixed ordering makes impossible by construction.
