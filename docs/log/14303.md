# Stamp the PPTP call-id pair on HA bulk export and tunnel purge (#14303)

- **Issue**: #14303, follow-up of #13965/#14228.
- **Cause**: #14228 taught the incremental `SessionDelta` producers to stamp
  `pptp_call_ids` from the live worker association table
  (`pptp_call_ids_wire_for`), and the HA import gate withholds any
  `Pptp(handle)` record whose pair is absent (`pptp-call-ids-not-carried`).
  Two producers were missed: `snapshot_all_sessions_export` (the HA bulk
  export / full-resync Open deltas in `afxdp/ha/export.rs`) and the
  tunnel-remap purge Close delta (`afxdp/ha/tunnel_purge.rs`) both hardcoded
  `pptp_call_ids: 0`. A PPTP session reaching the standby only via bulk
  export — after an event-stream reconnect or peer restart, precisely when
  incremental deltas were missed — arrived with pair 0 and was withheld:
  PPTP session loss on failover-after-resync (fail-closed, no aliasing).
- **The access problem**: the two missed producers iterate the coordinator's
  shared `SyncedSessionEntry` map, which has no `SessionTable` and therefore
  no association table to consult. The pair is a pure function of the
  association (`PptpCall`), and the handle is derived from it, so the pair
  can be carried on the shared entry itself and re-derived nowhere.
- **Change**:
  - `SyncedSessionEntry` gains `pptp_call_ids: u64` (0/absent for non-PPTP).
  - `build_synced_session_entry` stamps it from the verified wire pair
    (`req.pptp_call_ids`) at HA import — the one place the pair crosses into
    the shared map.
  - The local forward-flow publish (`poll_descriptor`), the forwarding-learn
    publish (`local_delivery`), and the shared-promote publish (`promote`)
    stamp it from the live table via `pptp_call_ids_wire_for`, matching the
    incremental producers. Every other construction site (reverse companions,
    tunnel/TUN origins, seeds, fixtures) carries 0, which is correct: a
    reverse or non-PPTP entry's pair is never read.
  - `snapshot_all_sessions_export` and `purge_remapped_tunnel_sessions` stamp
    `entry.pptp_call_ids` instead of 0. NOT changed: the Close wire frame
    (it encodes no pair today; the purge delta now carries the value in
    process, symmetric with the other Close producers, and encoding it is a
    separate wire change), and the owner-RG worker export (already stamps
    via `open_export_delta_with_provenance`).
- **Regression coverage** (`userspace-dp/src/afxdp/ha_tests.rs`):
  `bulk_exported_pptp_session_carries_its_call_id_pair_14303` — builds a PPTP
  GRE sync record carrying its pair, imports it through the real
  `build_synced_session_entry`, publishes it as a locally-owned forward
  session on an active RG, runs the real `snapshot_all_sessions_export`, and
  asserts the exported Open delta carries the pair; then re-imports the
  exported pair on the peer and asserts it is admitted under the same handle
  instead of withheld. FAIL-ON-REVERT: restoring `pptp_call_ids: 0` in the
  bulk export (or dropping the field at import) reads 0 and fails.
- **RED evidence**: with only the export stamp reverted to
  `pptp_call_ids: 0`, `bulk_exported_pptp_session_carries_its_call_id_pair_14303`
  FAILED at the exported-delta assertion (`left: 0, right: 4581302818`).
  With the fix it passes; `afxdp::ha::` suite 200 passed / 0 failed.
- **Blast radius / risk**: one added `u64` on an in-process shared entry (no
  wire, BPF ABI, or Go change); non-PPTP sessions carry 0 exactly as before.
  A PPTP session whose association was never imported or learned still
  exports 0 and is still withheld — fail-closed is preserved; only sessions
  whose pair this node actually holds now survive the resync path.
