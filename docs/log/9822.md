# 9822 — a barrier released by the stream-move sweep reported a disconnect

- **Timestamp**: 2026-09-12T08:05Z
- **Action**: made a barrier waiter carry WHY it was woken, instead of inferring
  it from the fence epoch.
- **File(s)**: `pkg/cluster/sync_bulk.go`, `pkg/cluster/sync_barrier_fence_9508.go`,
  `pkg/cluster/sync_conn.go`, `pkg/cluster/sync.go`,
  `pkg/cluster/barrier_move_window_9822_test.go`, `pkg/cluster/sync_test.go`,
  `docs/log/9822.md`.

## What the issue left open, and the answer

The issue recorded two unknowns: the failure rate and whether it depends on load,
and **whether the fault is in the test or in the code under test**. It is in the
code, and it needs no load at all once the interleaving is named.

`WaitForPeerBarrier` told a fence from a disconnect by comparing the fence epoch
it captured at START against the epoch at wake-up: changed meant fenced,
unchanged with no ack meant the connection went away. Every caller of
`noteStreamConnLocked` bumps the epoch **under `writeMu`**, releases `writeMu`,
and only then calls `onStreamMoved`, which sweeps every pending waiter — all
three callers do this (`sync_conn_write.go`, `sync_bulk.go`,
`captureBarrierFenceForBulk`), and the split is deliberate so the sweep does not
run under `writeMu`.

So the sweep can land arbitrarily late. A barrier that starts in that gap — and
it is admissible precisely because an ACKed re-prime discharged the fence —
captures the ALREADY-BUMPED epoch. At wake-up it sees no epoch change, no ack,
and reports `session sync disconnected during barrier wait`, for a connection
that never went away. That is why the failing run logged
`released_barrier_waiters=1` immediately before the failure, and why it was
seq=2: the barrier AFTER the re-prime.

The misreport is not cosmetic: the caller's remedy for a fenced barrier is to
re-prime and retry, and its remedy for a disconnect is not.

## The fix

`barrierWaiters` now holds a `*barrierWaiter` carrying a `fenced` flag.
`onStreamMoved` sets it under `barrierWaitMu` before closing, and the woken
barrier reads it under the same mutex, so the reason cannot race the wake-up.
`handleDisconnect` deliberately does NOT set it — that one IS a disconnect. The
epoch comparison stays, because it still catches a move the waiter was
registered before.

## Evidence

- A new cell reproduces it DETERMINISTICALLY on unmodified master, with no load:
  bump the epoch as a write does, discharge the fence as an ACKed re-prime does,
  start a barrier, then run the deferred sweep. On master it fails with exactly
  `session sync disconnected during barrier wait seq=1`.
- Mutation: dropping the reported reason and inferring from the epoch alone (kept
  compilable, since a non-building mutant measures nothing) makes that cell FAIL;
  restoring the fix makes it pass.
- The #9508 suite the flake was reported against passes 20 consecutive runs.
