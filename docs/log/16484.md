# #16484 — NAT64 reload reseed selected the previous prefix by /96 bytes alone

- **Timestamp**: 2026-10-24
- **Context**: In the fresh-allocator arm of
  `Nat64State::from_snapshots_with_previous`, the #6765
  retained-address reseed took its source allocator from the FIRST
  previous prefix with equal prefix bytes, and
  `prev_prefix_is_deterministic` took the same first match. Since
  #15678 several zone- or routing-instance-scoped rule-sets can
  share one /96 (e.g. `64:ff9b::/96` per tenant) with disjoint
  pools. A pool edit on any rule-set after the first therefore
  reseeded from the wrong allocator: an empty retained-index map
  carried nothing, or a deterministic first rule-set suppressed the
  reseed outright. That rule-set's live sessions stayed valid, so
  the fresh allocator handed their `(X, P)` tuples to other clients
  of the same rule-set connecting to the same server — replies
  could then be delivered to the wrong host. The same bytes-only
  key also sat in `reuse_allocator`, so phase-1 (#6982) charging
  and the build-loop reuse could select a sibling's allocator when
  two same-/96 rule-sets shared prefix, pool, deterministic
  identity, and port range.
- **Fix**: select the previous prefix by rule identity in
  `userspace-dp/src/nat64/state.rs`. `Nat64Prefix` now carries the
  snapshot rule-set `name`; a new `Nat64ScopeKey` holds the
  normalized scope (zone / routing-instance unions with the
  singular folded in, plus the parsed source-prefix constraint,
  normalized exactly as the build loop installs it). A known name
  is authoritative (a renamed rule neither steals nor keeps live
  ownership under the other spelling); with no names on either
  side the legacy bytes + normalized-scope match applies and an
  ambiguous legacy match refuses to guess. All three reload
  lookups — `reuse_allocator`, `prev_prefix_is_deterministic`,
  and the #6765 reseed — go through the one
  `find_previous_prefix` selector. The installed prefix's scope
  fields are now taken from that normalized key so a later reload
  compares like with like. Packet-path matching
  (`match_ipv6_dest_scoped`, classification, revalidation) is
  unchanged.
- **File(s)**: `userspace-dp/src/nat64/state.rs`,
  `userspace-dp/src/nat64_tests.rs`, `docs/log/16484.md`,
  `debian/changelog`
- **Validation**: new `nat64_16484_*` cells in `nat64_tests.rs`:
  second-rule pool edit reseeds its own tenant (live tuple held,
  not reissued to a second client), first-rule control stays
  green, deterministic-first no longer suppresses a round-robin
  second rule's reseed, round-robin-first does not reseed a
  deterministic second rule, no-op reload reuses each tenant's
  own allocator, and nameless legacy scoped rules reseed by
  scope. Existing `nat64_4518_*`, deterministic (#15178),
  range (#15283), and scoped (#15678/#15932) cells stay green
  (see PR for exact counts).
- **Residual**: component level only, matching the finding's
  evidence (no wire observation). Rule-set names are assumed
  unique in a committed config (the Go gate's posture); duplicate
  names with different scopes fall back to the first name match.
