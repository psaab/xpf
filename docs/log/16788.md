# Issue #16788: community member regexes matched against the whole joined string (R3-A11-05)

## Why

Junos evaluates each `policy-options community` member regex against
each community on a route ("only one route community needs to match a
given member"), but xpf rendered a single member verbatim as an FRR
expanded list, which FRR matches against the whole space-joined,
numerically sorted community string. An anchored member such as
`^666:.*$` therefore matched only when the 666 community sorted
first: a peer could bypass a `from community FROM-666; then reject`
term by adding any lower-sorting community (`100:1 666:5`), and
accept/modify terms on anchored members under-matched.

## What

- `pkg/config/community_translate.go` (new): `TranslateCommunityMemberRegex`
  rewrites a Junos regex member into a per-community FRR pattern —
  strips one leading `^` and trailing `$`, wraps as `(^|[ ])(…)([ ]|$)`
  (pipe-free, so no rendered line carries the `| ` FRR's vty pipe hook
  refuses, R3-A11-04), and confines `.` outside bracket expressions to
  `[^ ]` so a match cannot span communities. Members that cannot be
  confined are rejected: interior `^`/`$`, a literal space, a bracket
  expression that can match a space (including negated classes that do
  not exclude it and ranges spanning it), a POSIX class other than
  `[:digit:]`, any backslash escape (`\s`, `\d`, `\w`, …), a `(?...)`
  construct, and the empty/`^$` member. `TranslateCommunityMemberCore`
  exposes the unwrapped core plus anchored-edge flags for sequencing;
  `RenderableCommunityMember` mirrors the #15007 as-path API.
- `pkg/config/community_member.go`: `ValidCommunityMember` now also
  requires regex members to be translatable, so the strict commit gate
  rejects unconfined members and the shared predicate keeps the render
  belt in agreement (one bad member condemns the whole definition).
- `pkg/frr/policy_render.go`: single regex members render their
  translation; multi-member expanded conjunctions sequence
  per-community factors (`communitySequencePattern16788`) whose token
  boundaries are structural — each later factor opens after one
  separator plus intervening tokens, so adjacent communities share
  their separator instead of each factor consuming it (the #16835
  adjacent-literal row, covered as a consequence; the shared-token row
  remains #16835's). Literal factors keep whole-token anchoring in the
  pipe-free spelling. The generated delete backing carries the same
  translation for regex members, since FRR matches backing entries
  against single community values.
- Docs: the #15008/#16788 community bullets in `pkg/frr/README.md`
  describe the per-community translation and the remaining caveat.
- Updated the pre-existing exact-render expectations that pinned the
  verbatim/pipe forms (`frr_test.go` MIXED patterns, the #8449 belt
  table, the #15008 conjunction assertions).

## Risk

Neighbours preserved: literal-only definitions stay on the standard
list; unanchored members keep substring-within-one-token semantics;
the #15008 conjunction bound, collision gate, and #10822 fail-closed
arms are unchanged. Members previously rendered verbatim that cannot
be confined (e.g. `65000:[^0-9]+`, `^((56) | (78)):(.*)$`) now fail
strict commit and are omitted on the tolerant path instead of
silently matching the wrong routes — the intended fail-closed change.
Residuals: the #16835 shared-token row (one community satisfying two
regex members) still under-matches in a conjunction; backreferences
interact with sequencing as before; no daemon-path (running bgpd)
oracle was run — the oracle is Go's POSIX ERE, the #8449 agreement
for FRR's `regcomp(REG_EXTENDED)`.
