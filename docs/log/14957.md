# Issue #14957 — wireguard: bind cross-family WireGuard decap to zone listener and reject mapped-v6 filter bypass (D26-01)

- **Issue:** Cross-family `wg_outer_zone_matches` short-circuit (report
  `D26-01`, 3-way MATERIAL in research run `tpzkKgAuZL`). A WireGuard
  endpoint bound to an IPv4 source (`endpoint.source = 172.16.80.8`, WAN)
  was selected for IPv6-wire datagrams whose destination was the
  IPv4-mapped form `::ffff:172.16.80.8`, on the destination's owner zone
  alone: `wg_endpoint_for_listen_port` treated any cross-family source as
  matching, and `wg_outer_zone_matches` skipped the source-zone lookup
  (substituting the ingress zone). When the mapped destination was locally
  owned in a *different* zone than the v4 listener (e.g. configured on a
  LAN interface), an attacker arriving in that zone (a) was exempted by
  `is_wg_underlay_frame` from the #10686 mapped-v6 ingress drop
- **Fix (userspace-dp/src/afxdp/wg/decap.rs only):**
  - `wg_outer_zone_matches`: reject a mapped/compatible IPv6 destination
    outright (`wg_dst_is_mapped_or_compat`, reusing
    `frame::ipv6_addr_is_v4_mapped_or_compat`); reject any SPECIFIC
    cross-family pair (native v6 dst vs v4 source or vice versa). A
    same-family destination must BE the configured source, and both
    destination-owner zone and source-owner zone must equal the ingress
    zone. The previous `source_zone = ingress_zone_id` cross-family
    substitution is deleted. An UNSPECIFIED source is the dual-stack
    wildcard listener (`[::]:port` serves v4 peers on the kernel socket,
    `bind_wg_socket`): it has no family-specific local address, so it is
    admitted only on the destination's owner zone equalling the ingress
    zone — which is exactly the #14957 binding, and cannot exempt the
    mapped-v6 drop because mapped destinations are rejected first.
  - `wg_endpoint_for_listen_port`: `source_matches` drops the
    `source.is_ipv4() != dst_ip.is_ipv4()` cross-family admission; a
    specific source must equal `dst_ip`, an unspecified source still
    scans and is zone-bound by `wg_outer_zone_matches`.
  - Why this preserves legitimate behaviour: a v4 peer's records arrive
    as native v4 frames (dst = v4 listener, admitted unchanged, control
    below), a v6 peer's as native v6 frames, and a dual-stack wildcard
    tunnel (unspecified source, the common config) is bound by the
    destination owner zone. NOT changed: socket-layer canonicalisation,
    inner mapped checks (post-decap gate still drops mapped inner
    identities), GRE, or any caller signature — all three consumers
    (`try_wg_decap_*`, `is_wg_underlay_frame`, `is_wg_listener_tuple`)
    funnel through the two fixed functions.
- **Regression (userspace-dp/src/afxdp/wg/decap_tests.rs):**
  - `cross_family_mapped_v6_wg_decap_rejected_14957`: v4 listener owned
    in WAN, `::ffff:172.16.80.8/128` configured on LAN. For a real AEAD
    record to the mapped destination: not WG underlay, not a listener
    tuple, no decap, no AEAD counters, no endpoint roam — on LAN and WAN
    ingress. Control: same record natively v4 in WAN still decaps.
  - `cross_family_v6_listener_mapped_dst_rejected_v4_control_14957`:
    v6-bound listener rejects a mapped destination; native v6 in-zone
    still decaps (control).
  - `cross_family_native_v6_binds_wildcard_not_specific_v4_14957`:
    native v6 destination decaps via the unspecified wildcard tunnel
    (ifindex 401), never the specific v4 listener (400) — pins both the
    specific cross-family rejection and the wildcard preservation.
  - Adjacent control: `mapped_ipv6_wg_underlay_candidate_..._10686`
    now configures its listener as the unspecified wildcard (its dst is
    native `2001:db8::1`, mapped only as peer source) and still passes.
