## Re-verified at origin/master

On gRPC for a non-superuser the gates run in this order:
1. permission bits;
2. `authorizeRPCCommand`, which evaluates the OPERATIONAL regexes and denies an unresolved method whenever the class carries any of them;
3. `authorizeRPCConfigMutation`, which evaluates `*-configuration` regexes, but `configMutationLineFor` maps only Set and Delete.

The consequences:
- **V069.** The documented `permissions all; deny-commands "request system zeroize"` class could configure at the console, where `dispatchConfig` runs only `checkConfigRegex`, but not over gRPC.
- **V068.** `UnenforceableDenySurfaces` and `unenforceableDenyPatterns` both return early without a DENY source, so an `allow-commands` pattern that permits nothing never warned.

## Design (the issue's suggested order)

1. **The configuration gate learns Load and Rollback.**
   - `load set` and `load merge` are adjudicated per written path. Hierarchical content is parsed with `config.NewParser` and rendered with `FormatSet`, so every leaf it writes meets `AuthorizeConfigMutation`.
   - `load override` and `rollback n>0` replace the whole candidate. The paths they delete cannot be adjudicated one by one, so a class that carries configuration regexes is refused them.
   - `rollback 0` returns to the committed configuration and stays available.
   - A class with no configuration regexes is untouched.
2. **Only then is the operational gate narrowed.** Config-mode methods return early after the one-shot pattern warning.
   - `configModeMethods9633` is bound by a test to `methodsWithoutCanonicalCommand`, so a method cannot join it without a reviewed reason.
   - Every other unresolved method (the routing-protocol status RPCs) stays denied.
3. **Allow-side advisory.** `UnenforceableAllowSurfaces` counts a command as permitted only when the ALLOW leaf decided it (`DecidedBy == LoginRegexAllow`). It feeds both the commit advisory and the gRPC one-shot warning.
