# Issue #13137 — preserve unit-0 and fabric-member lifelines

## Why

When a cluster lifeline was configured as `control-interface em0.0` or `fabric-interface ge-0/0/0.0`, the configured unit was marked lifeline but its bare parent remained explicitly non-lifeline. Unit 0 and the bare parent share one kernel netdev, so `BuildJunosHostDenyProjection` could install a `to-zone junos-host` deny on the control/fabric netdev. The same mismatch caused a false #11365 warning on device-map `em0`. In addition, `HostInboundLifelineSet` treated a fabric-options parent as lifeline but did not include its configured physical `FabricMembers`, so member traffic could still be denied.

## What

`HostInboundLifelineSet` now promotes the parent only for a configured canonical unit-0 control/fabric reference, and records physical `FabricMembers` as lifelines while retaining the fabric-options aggregate exemption. For parent lifelines, declared sibling units remain explicit non-lifelines so VLAN units with distinct kernel devices are not exempted. Non-zero-unit cluster references do not promote their physical parent. Regression coverage checks unit-0 and physical member matching, sibling-unit and non-zero-unit boundaries, absence of false #11365 warnings, and absence of deny ingress scope on the shared unit-0 lifeline netdev. No other validation or projection paths were changed; they all consume the shared lifeline set.
