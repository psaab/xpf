- **Issue**: #18682, security.
- **Cause**: `ipsecIdentitiesCollide` recognized ID_ANY and same-type `equals()` only, while strongSwan's lookup also matches leading-wildcard FQDN/RFC822 owners, intersecting host/subnet/range identities within an address family, and structurally matching DN encodings whose BER length octets differ. The renderer already consumes this predicate, so an unrecognized intersection could leave two PSK owners selectable by one peer identity.
- **Change**:
  - `ipsecIdentitiesCollide` now checks wildcard suffix intersection, address/subnet/range match-set overlap (including directed subnet-mask behavior), and DN wildcard/length-octet intersections. `ipsecLookupSelectsOwner` models the directed `lookup->matches(owner)` relation for the same classes; subnet/range decoding and matching primitives are shared so the paths stay aligned without treating a symmetric intersection as a directed lookup hit.
  - Config cells cover both gateway orders for wildcard, address/range, explicit subnet-mask, DN wildcard, and BER length-octet collisions; local-identity cells cover both gateway placements. Disjoint wildcard and subnet controls still compile cleanly. Renderer cells prove conflicting groups are skipped while an unrelated VPN remains, and both disjoint groups/secrets still render.
  - Updated the config schema and IPsec README collision/upgrade notes. The render belt continues to use the shared detector; no separate renderer collision rule was added.
- **Oracle evidence** (installed `oracle-m`, columns end with `equals` both ways then `matches` both ways): `64.0.0.0` matches both `ipv4net:#00000000a0ffffff` and `ipv4net:#4000000040ffffff` (19); `32.0.0.0` does not match the first. The explicit-mask owner pair is included in both gateway orders.
