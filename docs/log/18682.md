- **Issue**: #18682, security.
- **Cause**: `ipsecIdentitiesCollide` recognized ID_ANY and same-type `equals()` only, while strongSwan's lookup also matches leading-wildcard FQDN/RFC822 owners, intersecting host/subnet/range identities within an address family, and structurally matching DN encodings whose BER length octets differ. The renderer already consumes this predicate, so an unrecognized intersection could leave two PSK owners selectable by one peer identity.
- **Change**:
  - `ipsecIdentitiesCollide` now checks wildcard suffix-set intersections using strongSwan's full-owner-length guard and NUL-terminated suffix comparison, address/subnet/range match-set overlap (including directed subnet-mask behavior), and DN wildcard/length-octet intersections. `ipsecLookupSelectsOwner` models the directed `lookup->matches(owner)` relation for the same classes; subnet/range decoding and matching primitives are shared so the paths stay aligned without treating symmetric intersection as a directed lookup hit. A wildcard lookup must be at least as long as its owner; aligned raw suffixes stop comparing at a shared NUL.
  - Config cells cover both gateway orders for wildcard (including raw embedded-NUL FQDN owners), address/range, explicit subnet-mask, DN wildcard, and BER length-octet collisions; local-identity cells cover both gateway placements. Disjoint wildcard/subnet and too-short exact/bare-wildcard controls still compile cleanly. Renderer cells prove conflicting groups are skipped while an unrelated VPN remains, including a concrete NUL-bearing lookup that matches both raw wildcard owners; positive controls still render uniquely.
  - Updated the config schema and IPsec README collision/upgrade notes. The render belt continues to use the shared detector; no separate renderer collision rule was added.
