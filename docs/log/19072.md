# Issue #19072: the RSS hash key changes on every deploy (no reboot)

## Why

- **Timestamp**: 2026-11-10 PST
- **Action**: G1's #18780 gate found that the data VFs' RSS key differed
  between every two arms on the same boot. On tcp fw1 the post-deploy key
  was 8c:80, 2a:ff, f1:ed, 37:16, a5:a9, bc:67, 59:d1, e9:02, a8:87, with
  no reboot. Identical 5-tuples therefore land on different workers in A
  and B, and placement-sensitive cells differ by deploy, not by build.
  Those cells are H1 Group 8b (#19069), H1 per-stream zero intervals and
  H11 per-stream stalls. G1 pinned the key by hand
  (`/var/worktrees/wave1-logs/g18780.sh`, `g_rss`).

## The writer (found in code)

- **xpfd writes it.** `pkg/dataplane/compiler.go`:
  `tuneInterfaceBuffers` calls `configureRSSHashKey(name)`, which runs
  `ethtool -X <if> hkey <key>`. The key is `rssHashKeyForBoot()`, a
  CSPRNG key behind a package `sync.Once`: one key per xpfd PROCESS,
  shared by every interface. That is why both data VFs of a node always
  show the same key.
- `tuneInterfaceBuffers` runs from `mapZoneInterface` on every
  `CompileConfig`, with a fresh per-result cache. So every config commit
  re-applies the current process's key, and a hand-set key holds only
  until the next config commit or xpfd start.
- **Intended:** #11057 (commit 0ce15ecb5f, PR #11309) replaced a hardcoded
  key, which let an attacker precompute tuple-to-queue placement and aim a
  flood at one worker. Its commit message says "Generate a per-process
  CSPRNG RSS key". The function is named `...ForBoot`, but the key is per
  process, so every deploy and restart re-randomizes it.
- **Ruled out:**
  - the mlx5 driver: its own key comes from `netdev_rss_key_fill()`,
    which is one key per kernel boot;
  - the helper and AF_XDP attach: no RSS writes;
  - systemd-networkd: `.link` files have no RSS key setting;
  - xpfd's other ethtool writes (`-X weight/default`, `-C`, `-K`): they
    leave the key alone, because the kernel SRSSH path copies a key only
    when one is passed.
- **Lab confirmation:** approved by the coordinator, and waiting for a
  slot between gates. Predictions, written before running:
  1. an xpfd restart on the secondary gives both data VFs a NEW
     identical key;
  2. `networkctl reload` leaves it alone;
  3. VF link down/up leaves it alone;
  4. `ethtool -X <vf> default` leaves it alone;
  5. (not yet approved) a config commit puts the process key back over a
     pin.

## Risk

Lab tooling only. Production keeps its per-process random key; nothing
in xpfd changes. Pinning in the gate path makes A/B placement equal, but
it also stops gates from sampling placement variation. That is deliberate
for paired comparisons.

## Product fix: one RSS key per boot, not per xpfd process

- **Timestamp**: 2026-11-10 PST
- **Action**: the coordinator asked for the product to match its name
  (`rssHashKeyForBoot`), keeping #11057's security property if the
  per-process randomness was intentional.
- **Was per-process intended?** No. #11057's acceptance asks for an RSS
  key "randomized per box/boot". Its threat is a fleet-wide hardcoded key
  that lets a remote attacker precompute tuple-to-queue placement. Commit
  0ce15ecb5f's message says "per-process CSPRNG RSS key" and implements it
  with a `sync.Once`, but nothing in the issue, the PR or the code argues
  for rotating the key at each restart. A restart is not a designed
  rotation.
- **Choice:** keep the CSPRNG draw, but store it per boot instead of
  deriving it from `boot_id`.
  - The first xpfd process of a boot draws the key and writes
    `/run/xpf/rss-hash-key` (`v1 <boot_id> <hex key>`, mode 0600). Later
    processes in the same boot read it back.
  - `/run` is tmpfs, and a stored key naming another `boot_id` is
    ignored, so every boot gets a new key.
  - Why not a keyed hash of `boot_id`, as suggested: every local user can
    read `boot_id`, and it travels in journal metadata (`_BOOT_ID`). An
    unkeyed hash would be predictable, and a keyed one needs a long-lived
    secret at rest. A boot-scoped random key needs neither, and it keeps
    #11057's property unchanged: unpredictable, and different per box.
  - **Trust:** a stored file that is not a regular file owned by xpfd's
    user, or that has group or other permissions, is ignored and replaced,
    because a planted key is a known key.
  - **Fallbacks:** with no readable `boot_id`, or no writable `/run/xpf`,
    the process uses a fresh key of its own. That was the old behaviour,
    and it is never a fixed key.
  - The unit already keeps `/run/xpf` across stops
    (`RuntimeDirectoryPreserve=yes`, #16050). A factory reset wipes
    `/run/xpf`, so it draws a new key.
  - **Trade-off, accepted and documented:** placement that an attacker
    infers through a side channel now holds until the next reboot instead
    of the next xpfd restart.
