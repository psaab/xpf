# #15000 — NAT64 rule-set with undefined/omitted source-pool aborted every dataplane compile (A08-02)

## Defect

`compileNAT64` (`pkg/config/compiler_nat_source.go`) stored `rs.SourcePool`
verbatim with no existence check. No strict gate covered it: the only
`pkg/config` NAT64 consumers skipped a missing pool
(`validateNATHostMaskStrict` continued on `SourcePool == ""` / unknown
pool). The typed dataplane compile then hard-errored:

- `pkg/dataplane/compiler_nat.go:compileNAT64WithStaging` returned
  `NAT64 rule-set %q: source pool %q not found` for an empty or undefined
  pool.
- That function is a `#4960` pre-pass row
  (`compiler_validate_4960.go`), and `CompileConfig` runs
  `validateBeforeMutateWithResult` before Phase 2, so the error aborted
  **every** dataplane compile — a strict-clean, persisted config made
  every later apply fail, including unrelated tightening commits. At
  boot no snapshot was compiled.

## Fix

1. **Strict gate** (`pkg/config/compiler_validate_strict_nat.go`,
   `validateNAT64PrefixStrict`): a new first loop rejects a NAT64
   rule-set whose `source-pool` is empty/omitted or names an undefined
   (or nil) source pool, naming the rule-set and pool. On the lenient
   load / peer-sync path (`lenientNAT64Prefix`, #1960) the same check
   downgrades to a `cfg.Warnings` entry via the existing `emit`
   closure. The pool check runs before the prefix arm, so a rule-set
   with both defects reports the pool first. An empty-prefix rule-set
   is not exempt: `buildNAT64Snapshots` skips it, but the typed
   `compileNAT64` path runs regardless of prefix.
2. **Dataplane** (`pkg/dataplane/compiler_nat.go`,
   `compileNAT64WithStaging`): an unresolvable pool now
   `compileWarn`s (`NAT64 source pool not found, skipping rule-set`,
   with rule-set and source-pool) and `continue`s instead of returning
   an error. The rule-set is skipped for pool-ID purposes — it is not
   assigned an ID — while sibling rule-sets still compile and
   `validateBeforeMutate` returns nil. `buildNAT64Snapshots` already
   emits such a rule-set with an empty pool-address list, which the
   Rust helper fail-closes per packet (#2291), so no snapshot change
   was needed. The #14679 "no valid addresses" hard error for a
   *defined* but poisoned pool is unchanged.

Deliberately NOT changed: `compileNAT64` in `pkg/config` (verbatim
storage is correct — the gate, not the reader, owns rejection, matching
the prefix gate's design); the peer-effective registry (no NAT64 prefix
subject is registered there today either — the new check travels with
the existing prefix gate).

  GREEN after.

## Risk

Bounded to the cited mechanism. A NAT64 rule-set that previously
committed clean and then wedged every apply is now rejected at commit
with an actionable message; already-persisted such configs still boot
(lenient warning) and now apply with that one rule-set inert instead
of aborting the whole compile. Defined-pool configurations are
byte-identical.
