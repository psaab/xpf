# #14615 — RPM `thresholds successive-loss N;` one-line spelling silently compiled to default 3

## Issue
`services rpm probe <p> test <t> thresholds successive-loss N;` (one-line
hierarchical spelling) arrived as one node `Keys=[thresholds,successive-loss,N]`
with no Children. `compileRPM`'s `thresholds` arm iterated only
`prop.Children`, so the loop no-oped: `ThresholdSuccessive` stayed 0 and
`EffectiveSuccessiveLossThreshold()` substituted the default 3. An operator's
`successive-loss 1` became 3 (two extra test-intervals of blackhole before
ip-monitoring actuation, +120s at the default 60s test-interval) and
`successive-loss 10` likewise became 3. The inline spelling also bypassed the
>=1 validator: `successive-loss 0` committed clean. Only hierarchical text
(`load override`/`load merge`/boot config) was affected; flat `set` was
correct. Finding Y19-01, deep-review.

## Fix
- `pkg/config/compiler_services.go` (`compileRPM`, `thresholds` arm): read
  through `packedBody(prop, rpmThresholdsSchema14615())` instead of raw
  `prop.Children`. `packedBody` expands the packed tail
  `successive-loss N` into the same synthesized child the braced spelling
  produces, returns the node unchanged when there is no tail, and returns
  raw children on a nil/unmodelled schema — so the block spelling is
  unaffected and no shape is invented. The existing
  `parseRPMPositiveInt(..., "thresholds successive-loss", v)` then runs on
  both spellings, rejecting `0`/non-numeric values naming the leaf.
- `pkg/config/last_operator_schemas_8939.go`: new
  `rpmThresholdsSchema14615()` resolving
  `services rpm probe <p> test <t> thresholds` from `setSchema` via the
  existing `rpmProbeTestSchema8939()`, so compiler and validator share one
  grammar source and cannot drift.
- `pkg/config/schema_system.go`: `thresholds` schema node now sets
  `packedTail: true` (#6821 pairing). Because the compiler now reads the
  container's packed tail, the strict schema walker validates the same
  `packedBodyChildren` expansion at commit — an inline `successive-loss 0`
  is rejected by the typed-leaf validator (`ValidateIntegerMin(1)`) as well
  as by the compiler, on both the strict commit path and, via the compiler,
  the lenient load/sync path.

NOT changed: no other RPM leaf, no parser change, no `Format()` change.
Sibling packed-tail sites in the #14402–#14440 family are separate issues.
