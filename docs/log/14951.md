# #14951 — SessionSync peerIdentity never advances after installConn-classified restart (D14-04)

## Defect
`SessionSync.peerIdentity` is the authoritative process identity of the
current peer incarnation. Two classifiers retire a peer reboot:
`installConn` (supersession / raised boot epoch) and the BulkStart switch
(`classifyPrimeLocked` → `applyPeerIncarnationSwitchLocked`).

When the first reboot (A→B) was classified by `installConn`, the
post-eviction `installedPeerIdentityLocked(retired=A)` scan advanced
`peerIdentity` to B and B's pre-evidence sibling was preserved
(`staleConnPreserve`, re-stamped current). When B later primed, the
BulkStart switch captured `retiredIdentity = s.peerIdentity` — already
B — as the identity it was retiring. Eviction therefore treated B as
both the retired and the authoritative process: B's sibling was
preserved again and `peerIdentity` stayed at B. On B's own reboot (→C),
C's BulkStart switch retired B but `peerIdentity` still named B, so
B's dead sockets read as proven-newer than the retired identity and
were preserved forever instead of evicted as corpses.

## Fix
- `pkg/cluster/sync_conn.go` `classifyPrimeLocked`: before calling the
  switch, capture the pre-advance `peerIdentity` as the retired identity
  and advance `s.peerIdentity` to the priming connection's proven
  capabilities identity (`connPeerIdentityLocked`). The priming
  connection's BulkStart boot id just switched, so its capabilities
  identity (sent by the same sender on install, before the bulk) is the
  new authoritative process. When the priming connection announced
  nothing, `peerIdentity` is left unchanged and the switch falls back
  to the existing post-eviction scan.
- `applyPeerIncarnationSwitchLocked` gains a variadic
  `retiredOverride ...peerProcessIdentity`: `classifyPrimeLocked`
  passes the pre-advance value so eviction retires B while
  `peerIdentity` already names C. Direct callers (tests) keep the
  previous behaviour (retired = current `peerIdentity`). The narrower
  "clear peerIdentity when no successor is proven" variant was tried
  and reverted: it breaks the deliberately pinned
  `TestSameProcessSupersessionThenBulkStartSwitchEvictsCorpse_9818`
  retention (same-process supersession with an unannounced keep must
  retain the prior known identity for the later BulkStart eviction).
