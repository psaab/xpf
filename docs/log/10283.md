# #10283 bulk snapshot-to-BulkStart gap

## Finding verified at current master

`doBulkSync` reads `BulkSnapshotSource` before `bulkSyncWindow` writes `BulkStart`. The receiver records a session key in `bulkRecvV4`/`bulkRecvV6` only while `bulkInProgress` is true, and `BulkEnd` runs `reconcileStaleSessions` against those maps. Therefore an incremental that is written before `BulkStart` is installed on the standby but absent from the authoritative receive set and is deleted at `BulkEnd`.

The sender has two relevant write paths: `sendLoop` drains `sendCh`, while `bulkSyncWindow` writes BulkStart, snapshot records, and BulkEnd directly under `writeMu`. The issue is the ordering gap between the table-truth read and the first direct marker write.

## Fix direction

This uses the issue's hold-incrementals direction, not a receiver grace set. `doBulkSync` acquires `bulkSendMu` before `bulkStartMu`, then holds both while reading the table-truth source; this serializes overlapping authoritative bulks without parking `sendLoop` behind a later bulk. It holds `bulkStartMu` through the BulkStart write. `sendLoop` takes `bulkStartMu` for the actual queued-frame write, so an incremental cannot precede BulkStart. The start gate is released immediately after the marker write; `bulkSendMu` remains held until the authoritative window completes.

A `queuedFrameMu` watermark records accepted queued frames and resolved successful or abandoned writes. BulkStart takes an exact pre-marker sequence/failure cut without holding `queuedFrameMu` across network I/O. Before BulkEnd, the bulk waits for every frame in that cut to resolve; a failed/cancelled frame or timeout aborts the authoritative window rather than reconciling an incomplete set. Barrier frames use the same enqueue helper, so they participate in the cut. Existing send-channel order and install generations are preserved, including an open followed by a close during the gap.

## Production-source deadlock proof

There is one production assignment: `pkg/daemon/daemon_ha_comms_wiring.go:300`, `ss.BulkSnapshotSource = d.userspaceBulkSnapshot`.

The call chain is:

- `userspaceBulkSnapshot` (`pkg/daemon/daemon_ha_userspace_export.go:147-160`) validates session sync/config/exporter and calls `userspaceBulkSnapshotWithConfig`.
- `userspaceBulkSnapshotWithConfig` calls synchronous `ExportOwnerRGSessionsPaged` and then `walkUserspaceSessionDeltas(..., snapshotDeltaSink)` (`daemon_ha_userspace_export.go:113-134`).
- `snapshotDeltaSink` only updates maps and converts them to a `BulkSnapshot` (`daemon_ha_userspace_stream.go:855-908`); it never calls `QueueSession*`, `QueueDelete*`, or `queueUserspaceSessionDeltasComplete`.

The separate `exportUserspaceOwnerRGSessionsWithConfig` path calls `queueUserspaceSessionDeltasComplete`, but it is not wired to `BulkSnapshotSource`. All other assignments found were tests. Thus no production snapshot source synchronously waits on a `sendLoop` write while `bulkStartMu` is held. The existing 9508 test callback did exactly that, so its intra-source `waitForFrame` was removed; its post-BulkEnd wait remains.
