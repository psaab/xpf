# #9952 — REST never evaluated `deny-commands` / `allow-commands`

Work log for issue #9952. See `docs/log/README.md` for why this lives here and
not in the repository-root `_Log.md`.

- **Timestamp**: 2026-09-12
- **Action**: Added the operational command-regex gate to the REST surface, with
  a route -> canonical-command table, a declared no-command table, a census
  binding both to `server.go`'s registrations, and the `docs/system-login.md`
  correction in the same change.
- **The absence was a measurement, not a failed search**:
  `OperationalLoginRegexesFor` is the only resolver for these regexes and had
  exactly two non-test enforcement callers — `pkg/grpcapi/authz_command_gate_7172.go`
  and `pkg/cli/permissions_regex.go`. The same grep finding both other surfaces
  is what makes "zero in `pkg/api`" evidence rather than a miss.
- **One table, not two**: `systemActionVerbCommand` moved from `pkg/grpcapi` to
  `pkg/authz` as `SystemActionVerbCommand`, with gRPC reading it through a
  one-line alias. Copying it was the obvious move and is the one this repo keeps
  paying for — two tables that agree today, drift silently, and each looks right
  on its own. The gRPC completeness guard that pins the key set against the
  handler's own `switch req.Action` still runs unchanged against the shared table.
- **The mapping was validated, not asserted**: every value in `restRouteCommand`
  is resolved against `cmdtree.OperationalTree` and required to be the CANONICAL
  spelling, the same rule the gRPC table has been held to since #7172. A deny
  regex is matched against these strings, so an unresolvable entry is a gate
  comparing against a command no operator can run. Writing the table and running
  that check found one route I had missed entirely
  (`GET /api/v1/config/status`) — the census found it, not a re-read.
- **`GET /api/v1/config/status` is charged `show version`** because that is what
  gRPC charges `GetConfigModeStatus`. Matched deliberately rather than
  "improved": if it is the wrong command it is wrong identically on both
  surfaces, which is discoverable; a better answer on one surface only is a
  divergence nobody sees.
- **Fail-closed, and only for a class that asked for it**: a class with no
  operational regexes is unaffected and pays nothing. An unmapped route, an
  unknown `show-text` topic and an unmapped SystemAction verb all DENY — including
  the prefix forms (`cluster-failover:1:node0`, `userspace-*`) that the handler
  parses out of a packed string and that therefore cannot appear in any table.
  Treating "cannot resolve" as "no match, allow" is the bypass the table exists
  to close.
- **The config-mode carve-out is a regression guard, not a convenience**:
  charging a config-mode route an operational command would lock any class with
  an operational pattern out of configuration over REST, which is exactly the
  lockout #9633 fixed on gRPC. It has its own cell.
- **Validation**: census (every registered route in exactly one table, both
  directions, with an empty-sweep guard), resolver check, a cross-surface parity
  cell on the six shared-data routes, and six behavioural cells — denied on read
  / clear / system-action, the positive control that an unmatched command still
  works, the narrowness control that a class with no regexes is untouched, the
  config-mode carve-out, the prefix-form verb, and the unmapped route.
