# Issue #14181 — client-side DHCPv6 Relay-Reply dispatch and client identity binding

- **Timestamp**: 2026-10-16
  - **Action**: Bound DHCPv6 Relay-Reply forwarding to the recorded
    soliciting client. The pending table (`pending.go`) is now generic
    over a payload value; the v6 instantiation stores `pending6Entry`
    (fixed 16-byte client address + request type, `pending6.go`) recorded
    at Relay-Forw insert time in `runDHCPV6ClientLoop` (`relay6.go`).
    `processDHCPV6ServerPacket` now requires: outer PeerAddr equals the
    recorded client (mismatch counted as `RepliesDroppedNoRequest`),
    loopback PeerAddr rejected in `decapsulateRelayReplyV6`, and inner
    type is a legitimate server answer to the recorded request
    (Solicit->Advertise; Request/Renew/Rebind/Confirm/Decline/Release/
    Information-request->Reply; RECONFIGURE and other client-direction
    inners dropped as `RepliesDroppedInvalid`). Relay-Replies arriving
    on a client-facing socket (`runDHCPV6ClientLoop`) may select only
    that receiving interface's own dispatcher target via new
    `dispatchFromClientSocket`; cross-interface selection is dropped as
    `RepliesDroppedDispatcherLocal` (new synthetic-row stat in
    `relay.go`). Upstream shared-socket dispatch and per-interface
    server-loop dispatch are unchanged in routing. Entries survive
    snapshot/adopt across relay reconfiguration. README updated.
    Regression tests in `relay6_replybind_14181_test.go` (peer mismatch
    + correct-peer control, loopback peer, RECONFIGURE/wrong-answer
    inners, Request->Reply pair, cross-interface client-socket forgery
    + own-interface/upstream controls, adopt preservation). Legacy
    #10198 dispatcher fixtures that used a `::1` PeerAddr with a
    Solicit-typed inner (the exact forged shape) now use the recorded
    link-local client `fe80::99` with an Advertise inner; the
    rate-limit fixture's receiving relay is now its registered target
    (the own-interface shape the fix requires).

  base-attributed, not introduced here).

## Risk

- Behaviour delta: a Relay-Reply whose outer peer-address differs from
  the address that solicited (e.g. a server that rewrites peer-address,
  or a downstream-relay chain — already fail-closed as nested) is now
  dropped instead of delivered to the named peer. Legitimate direct
  clients and the link-local shared-socket return (peer = soliciting
  link-local client) are unaffected, pinned by controls in the new
  tests and the #10198/#10699 suites.
- NOT changed: nested Relay-Reply forwarding remains refused (#9553
  has no downstream trust knob); the pending key, source allow-list,
  and Interface-ID/LinkAddr dispatcher routing are unchanged. The
  transitional inner-type floor for zero-payload entries (only
  constructible via test fixtures that insert without a recorded
  request type) accepts Solicit/Advertise/Reply; production inserts
  always record the request type and get the strict per-request check,
  and RECONFIGURE is rejected at the floor for every caller.
- Actual kernel delivery to `[::1]:546` through a SO_BINDTODEVICE
  socket was not live-tested (source/fake-conn scope per the issue's
  decisive check); loopback peers are now rejected before any write,
  so the question is moot for this path.
