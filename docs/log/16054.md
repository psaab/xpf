# Issue #16054 — helper binary resolution trusts CWD-relative ./xpf-userspace-dp

## Why

`findBinary`'s implicit candidate list starts with `./xpf-userspace-dp` (then the build tree and argv[0]'s directory, then PATH) and admission checked only stat + exec-bit (the #12196 fix). A root `xpfd` hand-run without a configured binary leaf from a low-privilege-writable CWD therefore executed a planted `./xpf-userspace-dp` as root and trusted its uid-0 peer credentials. The shipped systemd path (CWD=/, absolute configured binary) was already safe; the surviving arm was the hand-run/lab workflow, capping severity at Low.

## What

Every helper binary a root daemon resolves — the CWD, build-tree, and argv[0]-relative candidates, `exec.LookPath` results, and an explicitly configured path — must now be root-owned and not group/world-writable. Implicit candidates failing trust are skipped with a loud `slog.Warn` and their reason is appended to the not-found error (the #12196 diagnostics shape); an untrusted explicit path is a hard `not trusted` error with no PATH fallback, matching the explicit-branch strictness for directories and non-executable files. A non-root daemon is exempt: it gains no privilege by executing its own helper, so the developer workflow of running a freshly built, user-owned helper from the build tree/CWD (including the #12196 executable-CWD-over-PATH preference) keeps working. Candidate order and the PATH fallback are otherwise unchanged. `helperProcessEuid` and `helperFileOwnerUID` seams let tests simulate a root daemon and a root-owned fixture; fixtures otherwise use real files with real ownership. Fold: `findBinary` now returns the absolute path of the exact file it validated (`filepath.Abs` on every return arm), so `exec.Command` runs the checked file — a configured bare name previously stat'ed the CWD file but would have been re-resolved through PATH at `Start` time (validated file != executed file). The #12196 CWD-preference cell now expects the absolute CWD path; a symptom-only relative return would fail it.

## Validation

- **RED**: with only the two `helperBinaryTrustReason` call sites removed (test seam retained so the package builds), the four root-arm cells fail exactly on the defect: the CWD plant is accepted, the user-owned PATH helper is returned, the group/world-writable CWD helper is accepted, and the untrusted explicit path is returned. The two control cells (non-root CWD preference, trusted explicit path) pass on both sides.
- **Fold RED (writability)**: the writability cell now presents its 0777 fixture as root-owned via the owner seam, so only the `&0o022` arm can refuse and the reason must name `group/world-writable` specifically. Deleting the `&0o022` check turns exactly that cell RED (root-owned writable helper accepted); the ownership cells stay GREEN.
- **Fold RED (bare name)**: with a CWD plant and a different PATH helper, `findBinary("xpf-userspace-dp")` must return the validated absolute CWD path; reverting the explicit arm to return the bare name turns that witness RED (`validated file != executed file`). The root arm refuses the bare name for the untrusted CWD file it stat'ed, never falling through to the PATH namesake.
- **GREEN**: `go test ./pkg/dataplane/userspace/ -run 'TestFindBinary.*(16054|12196)' -count=1 -v` — all 16054 cells pass and all #12196 cells pass unchanged (12196 fixtures run as the non-root test user, or as genuinely-root-owned fixtures under a root runner, so neither arm regresses).
- `go vet ./pkg/dataplane/userspace/` clean; `gofmt -l` clean on both touched files (other listed files are pre-existing on `origin/master`).

- Full package run shows only failures that reproduce identically on pristine `origin/master` (`TestCanonical*RefBind5878`, WireGuard 9587 cells, `TestZonedTrunk...6722`) — verified by running those cells in a clean master worktree; they are unrelated config-compiler drift, not this change.

## Risk / residual

The trust decision still happens on the pre-exec stat, so the TOCTOU window named in #12196 remains: an attacker who can write the directory containing a root-owned, non-writable helper could still swap it between check and exec; closing that requires `openat2`/`execveat`-style descriptor execution and is out of scope. Parent directories are not checked — a root-owned helper inside a user-writable directory can be replaced by rename; operators pinning an explicit binary should keep it in a root-owned directory (the packaged `/usr/local/sbin` layout does). No dataplane hot path is touched; the check runs once per helper spawn, so there is no per-packet performance impact and no hot-path test applies. No live cluster was mutated.
