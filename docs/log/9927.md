# 9927 — A directly zoned fabric member must not overwrite the fabric MTU

## The defect

`planPhysDesired` (`pkg/dataplane/compiler_iface_desired.go`) merged references by
resolved physical netdev for addresses and unit MTUs, but MTU ownership was still
checked per reference. In the strict shape from #9927, `fab0.0` and
`ge-0/0/0.0` both resolve to `ge-0-0-0`: the fabric reference is local-fabric
owned while the direct member reference is an ordinary interface reference. The
member's 1500 MTU therefore won over the fabric setup's 9000 MTU.

STEP-0 on the origin/master checkout (`7edd4aaa5`) reproduced the defect in both
sorted zone orders: 2 subtests failed, each reporting `planned mtu 1500 on
fabric-owned netdev ge-0-0-0`.

## The fix

`fabricOwnedNetdevs` performs one config-wide pre-pass keyed by resolved Linux
netdev name:

- a `LocalFabricMember` contributes the canonical physical member key, whose
  parent MTU is owned by the fabric IPVLAN setup;
- a fabric bond contributes its own key only when the authored name is already
  the raw Linux name passed to `routing/bond.go` and fits the kernel name limit;
- a slash-bearing authored bond name is not marked owned because bond setup
  passes that raw name to netlink, while interface resolution canonicalizes it.

Both interface-level and unit-level MTU contributions are suppressed whenever
the current reference resolves to one of those owned keys. Address union,
DHCP/RETH/fabric address ownership, unit ordering, and all non-fabric MTU rules
remain unchanged.
