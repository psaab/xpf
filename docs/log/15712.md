# Issue #15712: login class regex POSIX validation and duplicate-overwrite gate

- **Timestamp**: 2026-10-19
- **Problem**: `system login class` leaves `allow-commands` / `deny-commands` / `allow-configuration` / `deny-configuration` were stored verbatim (`lc.AllowCommands = nodeVal(prop)` etc. in `pkg/config/compiler_system.go`) with no commit-time POSIX-ERE validation — a non-POSIX pattern such as `(?:show|ping).*` committed clean and only failed closed per-command at enforcement time (`CompileLoginRegexes` in `pkg/config/login_regex.go`). The #8436 find-or-create merge folds duplicate `class <name>` blocks into one `LoginClass`, but each regex leaf assignment overwrote the previous value, so an earlier `deny-commands "request system zeroize"` silently vanished when a second block wrote `deny-commands "request system reboot"`. Spark's probe on the base partly refuted a broader overwrite claim (different leaves across blocks merge correctly); the defect is same-leaf overwrite plus missing validation.
- **Fix**: New gate `validateLoginClassRegexes15712` (`pkg/config/login_class_regex_15712.go`), wired last in `runTailGates` so established tail-gate diagnostics retain first-error priority. It reads the COMPILED classes (post-#8436 merge, post-group-expansion), so hierarchical, flat-set (`SetPath` merges same-path leaves into one node — a single effective value), packed/flat-run (`expandFlatRun`), and group-inherited spellings are judged identically. (1) POSIX: every present leaf's effective value must pass `regexp.CompilePOSIX`; strict rejects naming class, leaf, pattern and parse error. (2) Duplicate: `LoginClass.RegexValues15712` (new `json:"-" yaml:"-"` field, `pkg/config/types_system_login.go`) records every distinct authored value per leaf in author order from the single compiler assignment site (`recordLoginClassRegexValue15712`); >1 distinct value is a strict rejection naming both values. Identical repeats and cross-leaf merges across blocks remain accepted. Strict = `CompileConfig`/`CompileConfigForNode`; tolerant (`CompileConfigLenient`/`CompileConfigForNodeLenient`, new `lenientLoginClassRegex15712` opt) warns per defect and keeps the last-authored value — exactly what the overwrite already installed — so persisted configs still boot (#1960) while enforcement keeps failing closed on an invalid pattern. Registered in `peerEffectiveStrictSubjects` (`validateLoginClassRegexesStrictView`) so a peer-only `groups nodeN` regex defect is rejected at the origin commit with a specific message (also covered by #9619's whole-pipeline peer strict compile).
- **Group semantics note**: a group scalar beside an inline scalar is Junos scalar override (inline wins, group value never materializes — verified by probe: only the inline value reaches the compiled record), so there is no effective duplicate to judge in that shape; the group leg that is judged is a group-supplied leaf with no inline override, and (where expansion materializes both) two-group conflicts.
- **Regression check**: `go test ./pkg/config/ -run '15712|V42_04' -count=1` passes; neighbouring `LoginClass|TestDenyClass|TestEmptyAllow` tests pass; `go vet ./pkg/config/` clean. Full `pkg/config` suite exceeds the local 4-minute test timeout in `TestSlotEscapeCoverage` and shows two failures (`TestHB166_T5_...`, `TestSlotEscapeTable/wireguard_allowed-ips`) that reproduce identically on a pristine `origin/master` worktree — pre-existing, unrelated to this change.
- **Not changed**: enforcement precedence/matching (`login_regex.go`, #7172 tiers), #8436 merge itself, permissions mapping, empty-pattern presence semantics (`deny-commands ""` remains valid POSIX and denies everything), built-in class shadowing, and any other leaf's duplicate policy.
