# Issue #12088 — reconcile RPM probe pins after kernel cleanup

## Why

Linux can remove the per-test route from table 7000 when the pinned egress link is bounced or its last address is removed, while leaving the fwmark rule in place. An unchanged RPM config hash therefore skipped re-installation and could leave `SO_MARK` probes without their pinned path.

## What

`Manager.VerifyProbePins` reads back each configured fwmark rule and exact host-route shape without mutating kernel state. Route verification uses the family default metric (IPv4 0, IPv6 1024) and treats `DEAD|LINKDOWN` as carrier loss when `ignore_routes_with_linkdown=1`; pure DEAD and unresolved nexthops still fail. The daemon checks readback on unchanged-hash reconciles, relevant link/address notifications, and a 30-second fallback tick. A missing pin holds only while the egress is administratively up, preventing an unbacked mark from false-passing through the main table; with the egress down, probes run and `ENETUNREACH` advances RPM's loss threshold. Closed link/address subscriptions are resubscribed after backoff, then all pins are verified to resync the gap. Readback-only drift waits for the retry tick, while still-failing installer errors retain immediate hash-gated retry behavior.

## Risk / residual

The pin loop treats a closed link/address netlink channel (including receive gaps such as ENOBUFS) as recoverable: it backs off, resubscribes, and verifies all pins after the new subscription is active. The 30-second periodic readback remains the fallback while a subscription is unavailable. Kernel cleanup and repair were exercised only inside a private network namespace; no live cluster was mutated.
