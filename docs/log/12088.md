# Issue #12088 — reconcile RPM probe pins after kernel cleanup

## Why

Linux can remove the per-test route from table 7000 when the pinned egress link is bounced or its last address is removed, while leaving the fwmark rule in place. An unchanged RPM config hash therefore skipped re-installation and could leave `SO_MARK` probes without their pinned path.

## What

`Manager.VerifyProbePins` reads back each configured fwmark rule and exact host-route shape without mutating kernel state. The daemon checks readback on unchanged-hash reconciles, relevant link/address notifications, and a 30-second fallback tick. Missing or mismatched pins hold only affected tests with the existing `ErrProbeSetup` gate; readback-only drift waits for the retry tick, while still-failing installer errors retain the existing immediate hash-gated retry behavior. A route marked `RTNH_F_LINKDOWN` remains a healthy pin shape: carrier loss keeps the selected path installed, so the genuine probe loss must advance RPM's successive-loss threshold and drive ip-monitoring failover rather than freeze `LastStatus`. Higher-metric duplicate host routes do not override the required default-metric pin; equal-or-better competing routes fail closed.

## Validation

- **RED before** (STEP-0 base `1c384b9a47ff7d6e567fa50632faa75c3995ae87`): the baseline scoped daemon tests passed, but a private-netns kernel reproduction showed the fwmark rule survived both admin down/up and last-address removal while table 7000 became empty. The new unchanged-hash regression initially failed with `missing route was not held after unchanged-hash reconcile: failures=0` before the behavior was wired.
- **GREEN after**: `go test ./pkg/routing -run '^TestVerifyProbePins' -count=1 -v`, `go test ./pkg/daemon -run '^TestReconcileRPMDetectsMissingKernelPinWithoutHashChange12088$' -count=1 -v`, and `go test ./pkg/daemon -run '^TestProbePinKernelDriftReconcilesInPrivateNetns12088$' -count=1 -v` passed. The private-netns acceptance exercised both link bounce and last-address removal/re-add: each missing route was held without sending a probe, then restored on the retry tick.
- The first post-wiring netns run caught an immediate same-hash retry after event-detected drift. Installer failure provenance now distinguishes that path; the rerun confirmed the route stayed absent until the retry tick.
- `go test ./pkg/daemon ./pkg/routing ./pkg/rpm -count=1`: all three packages passed (`daemon` 181.720s, `routing` 1.910s, `rpm` 0.718s).
- `go build ./pkg/daemon ./pkg/routing ./pkg/rpm` passed. `gofmt -l` on all six changed Go files produced no output.
- Carrier-down failover regression `TestProbePinCarrierLossTriggersIPMonFailover12088`: PASS in a private netns. The kernel retained the host route with `RTNH_F_LINKDOWN`; readback accepted the pin, two real ICMP losses advanced RPM to `fail` with zero pin-install failures, and the ip-monitoring actuator received the preferred failover default route.
- After the LINKDOWN fix: `go test ./pkg/routing -count=1`, `go test ./pkg/daemon -run '12088|ProbePin|ReconcileRPM' -count=1`, and `go test ./pkg/rpm -count=1` all passed with a private `GOTMPDIR`.

## Risk / residual

The link/address subscriptions are opportunistic; failed subscriptions fall back to the periodic readback/retry. Kernel cleanup and repair were exercised only inside a private network namespace; no live cluster was mutated.
