# #17269 — Unify cross-worker sharded-lock maps

- **Timestamp**: 2026-11-07
- **Base**: `99cb6b34ec` (the starting `HEAD` for `fix/17269-sharded-map`; `pwd` confirmed `/var/worktrees/campaign-drive/wt-17269`).
- **Why**: The seven maps named by #17269 were hand-rolled with divergent storage, hashing and power-of-two checks. In particular, #15956's newest SNAT live-flow map had unpadded shards, no compile-time shard-count guard and unkeyed `FxHasher` placement; PMech separately maintained `NUM_SHARDS = 32` and `SHARD_MASK = 31` without a compile-time guard.
- **What**: Added cycle-free root module `userspace-dp/src/sharded.rs` and registered it in `main.rs`. Its `ShardedMap<K, V, N>` stores an inline `[PaddedShard<V>; N]`; the one `#[repr(align(128))]` `PaddedShard` definition isolates each shard, and constructors plus shared index helpers force `N >= 2 && N.is_power_of_two()` at compile time. Ordinary keys use the process-keyed `HotPathSeededState` shard index. Fragment maps keep their independently drawn keys and their existing key-fold/domain behavior through the shared keyed-shard helper. Consumers retain their own `Mutex`/`RwLock`, map/vector value, poison handling, admission gates and lock-order rules. Migrated all seven requested components and an additional eighth similar punt-seed directory found during the census.
- **Files**: `userspace-dp/src/main.rs`, `userspace-dp/src/sharded.rs`, `userspace-dp/src/nat/allocator/flows.rs`, `userspace-dp/src/session/pmech_directory.rs`, `userspace-dp/src/afxdp/bpf_map/tuple_gate.rs`, `userspace-dp/src/fragment_assoc/mod.rs`, `userspace-dp/src/fragment_overlap/mod.rs`, `userspace-dp/src/afxdp/sharded_neighbor.rs`, `userspace-dp/src/afxdp/sharded_neighbor_tests.rs`, `userspace-dp/src/afxdp/bpf_map/steering_owners.rs`, `userspace-dp/src/session/punt_seed_directory.rs`, `docs/log/17269.md`.

## Design and migration order

The shared module lives at the crate root because every target is a child of the `main.rs` crate root. It depends only on `hot_hash_seed` and `std`, so all consumers import it without cycles; no map had a layout restriction that blocked migration. `ShardedMap<K, V, N>` centralizes padded shard storage and compile-time shard-count enforcement while `V` preserves each consumer's existing lock/value type. The keyed digest helper lets both fragment maps preserve their independent seeds and domain separation while sharing the common module's guarded placement path.

Migration order (requested seven first, discovered eighth last):

1. PMech directory.
2. SNAT live-flow map.
3. Tuple gate.
4. Fragment-association map.
5. Fragment-overlap tracker.
6. Dynamic-neighbor and solicited-probe maps.
7. Steering row/holdings maps.
8. Additional punt-seed directory.

No lock-order change was introduced. SNAT per-flow paths still lock one shard; `entries()` still walks and locks shards ascending. Its storage changes from a `Vec` header plus a heap-allocated array of 16 unpadded mutexes to an inline `ShardedMap` array plus its 8-byte seed. Each padded cell is 128-byte-aligned and has a size rounded to a 128-byte multiple, increasing per-shard padding versus a 64-byte cell. The exact before/after aggregate byte delta was not measured. SNAT placement is now process-keyed instead of unkeyed `FxHasher`; the map is process-local. Tuple-gate placement likewise changes from fixed-seed `DefaultHasher` to the common process-keyed placement. No wire-visible or cross-node hash value is introduced.
