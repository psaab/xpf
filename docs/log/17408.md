# #17408: #16600 source-NAT pool family gate rejects valid v6-only and unscoped pools

- **Timestamp**: 2026-10-25
- **Action**: Scoped `validateSourceNATPoolFamilyStrict`
  (`pkg/config/compiler_validate_strict_nat.go`) to proven
  mismatches and adjudicated the two pre-existing scaffold tests.
  Diagnosis (measured, not assumed): the failing #5627/#5875
  fixtures and the #16600 defect fixture compile to IDENTICAL
  rule shapes — `match source-address 10.0.0.0/24` (narrow v4-only)
  plus a v6-only pool — so no gate-local distinction exists; the
  issue's "pool-mode AND v4-only AND no v4 member" predicate is
  exactly the broken shape. The pre-existing tests assert POOL
  grammar, with the source prefix as scaffold. Two-part fix:
  (1) the gate now fires only when the proven single-family source
  set contains at least one NARROW prefix (proper subset of its
  family; `natPrefixIsFamilyWildcard` recognises /0 and bare
  0.0.0.0/::, including tolerated /+0//000 spellings; single-family
  wildcard keywords count as narrow) — a whole-family /0 source is
  a deliberate catch-all, not a proven authoring error;
  (2) `snat5627Tree`/`snat5875Tree` scaffolds now use a dual-family
  source match (`[ 10.0.0.0/24 2001:db8:9::/64 ]`) with rationale
  recorded in both files, so their v6-only/unscoped-v6 pool cases
  exercise pool grammar as intended. The alternative (admitting
  narrow v4 + v6-only pool at the gate) was rejected: it would
  silently re-open the literal #16600 defect row.
