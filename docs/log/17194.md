# Issue #17194: WireGuard TUN-origin builder uses the tunnel resolution SSOT

`build_wg_tun_origin_entries` re-derived the outer FIB lookup, recursion guard and outer→logical `ForwardingResolution` mapping of `resolve_tunnel_outer` / `resolve_tunnel_forwarding_resolution`, and had already missed `transport_route_mtu: outer.route_mtu` (#11411, stamped `0`) and the `tunnel_endpoints_down` NoRoute arm (#11423, absent). The ~70-line TunOrigin `SyncedSessionEntry` literal and the 5 s / 1 s refresh windows were likewise hand-copied from `afxdp/tunnel.rs`.

In `forwarding/tunnel.rs`, `resolve_tunnel_outer` is split into `resolve_tunnel_outer_to(state, dyn, endpoint, destination, depth)` plus the existing wrapper, and `map_outer_onto_tunnel_logical(state, endpoint_id, logical_ifindex, destination, outer)` carries the down-tunnel arm and `transport_route_mtu`. `resolve_tunnel_forwarding_resolution` keeps its exact behaviour (down-check first, then outer, then mapping). The WG builder calls both with `peer_endpoint.ip()` at depth 0 and maps `None` to the existing `Err("wg_tun_origin_outer_recursion")`; `wg_tun_origin_outer_usable` is deleted. `tun_origin_session_entry(..)` and `tun_origin_refresh_after_ns(protocol)` in `afxdp/tunnel.rs` are now the single literal/window used by both the GRE and WG builders.

Acceptance: `grep -n 'ForwardingResolution {' userspace-dp/src/afxdp/coordinator/wg_control/tun_origin.rs` matches nothing (the production literal is gone; the file no longer constructs a resolution). `wg_tun_origin_outer_guard_table_10038` is rewritten onto `resolve_tunnel_outer_to` (usable dispositions resolve `Some`; a local-delivery peer returns `None` and the builder returns the recursion `Err`) and stays green. New cell `wg_tun_origin_down_peer_route_mtu_17194` builds a WG TUN-origin entry whose peer route carries `mtu 1400` and whose row has `link_up=false`, and asserts `disposition == NoRoute` (the shared down arm returns `no_route_resolution`, MTUs 0 — same shape the GRE twin asserts), with an up-tunnel control on the same route asserting `transport_route_mtu == 1400`; it is RED on the pre-fix mirror (forwardable disposition, `transport_route_mtu: 0`) and GREEN after.

Deliberate behavior delta (F2, no code change): a down WireGuard tunnel now publishes a `NoRoute` forward + synthesized reverse pair, where pre-fix it published a forwardable outer-mapped forward + reverse. Pre-fix, `build_wg_tun_origin_entries` had no `tunnel_endpoints_down` arm, so a peer on a down WG row (`link_up=false`) still stamped the healthy outer disposition (e.g. `ForwardCandidate`/`MissingNeighbor` on the tunnel logical, with `transport_route_mtu: 0`) and published that forwardable pair. Now the builder resolves the outer first (preserving its recursion-`Err` contract) and then calls `map_outer_onto_tunnel_logical` (`tun_origin.rs:207-214`), whose down arm (`forwarding/tunnel.rs:92-94`) returns `no_route_resolution` when the endpoint id is in `tunnel_endpoints_down`; `wg_tun_origin_down_peer_route_mtu_17194` pins `disposition == NoRoute` for the down row. This matches the GRE / #11423 contract (`resolve_tunnel_forwarding_resolution` withdraws a down tunnel to `NoRoute` rather than forwarding through a healthy underlay). The fail direction is safe: a `NoRoute` pair forwards nothing, whereas the pre-fix forwardable pair could admit traffic toward a tunnel whose link is down. Encap remains ungated — the builder still returns `Ok` (it does not fail), the pair is published, and encapsulation proceeds exactly as before; only the stamped disposition changes.
