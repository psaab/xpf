# #16006 — tolerant screen numerics zero syn-flood subfields and limit-session (A3-M3)

- **Timestamp**: 2026-10-23
- **Defect**: On the tolerant load / peer-sync compile, an explicitly-authored
  screen numeric that failed to parse fell behind `if ok` guards in
  `compileScreen`: syn-flood `alarm-threshold` / `source-threshold` /
  `destination-threshold` / `timeout` and both `limit-session` caps became
  0/disabled behind only the #3317 warning, while the aggregate syn-flood
  gate stayed armed at its 200 default. Strict commit already rejected every
  bad value; icmp/udp flood, ip-sweep, port-scan and syn-flood
  attack-threshold already kept their Junos defaults.
- **Fix**:
  - `pkg/config/compiler_security_screen.go`: a bad syn-flood subfield now
    keeps its Junos default on the tolerant path (alarm 512, source 4000,
    destination 4000, timeout 20 — the values the CLI detail view already
    renders as the Default column). The repair keys off the `BadNumeric`
    record, so an unset leaf stays 0/disabled (#15269: never claim an
    unconfigured cap is applied) and a valid sibling value is never
    overwritten.
  - `limit-session` has no Junos default, so `parseThresh` instead marks
    the profile `BadNumericUnresolved` (`pkg/config/types_security.go`,
    compile-only `json:"-"`). `pkg/dataplane/userspace/screens.go` treats
    a marked profile as unresolved: `buildScreenSnapshots` publishes no
    entry for referencing zones, `buildScreenMissingProfileRefs` routes
    them through the missing-profile set so the dataplane substitutes the
    conservative default (#7168), the inert set excludes them (the three
    states stay disjoint), and SYN-cookie key derivation ignores them.
  - Strict behaviour is unchanged (#3317 still rejects); the missing-profile
    wire set already exists.
- **Fold (PR #16349, Opus)**: an unresolved profile dropped its
  `alarm-without-drop` modifier — `buildScreenMissingProfileRefs` emitted
  the ref with the flag always false and Rust `alarm_without_drop`
  consulted only the inert map, so the substituted default hard-dropped a
  packet the operator asked to log-and-forward (the #9425 defect on the
  new arm). Now Go populates the flag from the defined-but-unresolved
  profile, the Rust missing map carries `UnresolvedProfileRef` (renamed
  from `InertProfileRef`), `build_screen_missing_profiles` forwards it,
  and `alarm_without_drop` falls back to the missing map after the inert
  one. A truly undefined profile still carries false and hard-drops.
- **Tests**: `screen_tolerant_numeric_16006_test.go` (bad syn-flood
  subfields keep defaults incl. `1o00`/negative/uint32-wrap spellings,
  strict still rejects, unset stays disabled, valid siblings survive,
  bad limit-session marks unresolved with no invented default),
  `screen_tolerant_numeric_16006_test.go` in `pkg/dataplane/userspace`
  (unresolved profile publishes nothing, lands only in missing set,
  inert control unaffected, audit flag preserved on the missing wire),
  Rust `unresolved_*_16006` / forwarding decode cells (flag survives,
  drop still trips, non-audit control hard-drops).
- **Validation**: focused Go + Rust suites in the PR body.
