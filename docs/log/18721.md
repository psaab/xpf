# #18721: IPsec host-input fence readback fails since #16841

- **Timestamp**: 2026-11-01
  - **Action**: Triage found `TestHostInputFenceLiveReadbackAndRestore9506` red on master 5927babf07 in `make test-daemon-kernel-lib` ("host overlay leading rule absent"). A path-restricted `git bisect` (`pkg/nftables pkg/daemon go.mod go.sum`) driven by that cell gave first bad `2fa9d69062` (#16841). The good endpoint `19eb3e436b` was a real PASS, checked with `-v`, not a skip.
  - **Severity**: availability and liveness, not an admission bypass. The regression failed CLOSED. `InstallHostInbound` had already loaded the table, so the kernel fence (the overlay DROPs) stayed enforced. The readback failure then returned before every follow-up step (`pkg/daemon/daemon_nft.go`):
    - the apply was marked stale (`noteHostInboundApplyFailed`);
    - the host-input fence conntrack revocation was skipped;
    - gap-fence and pre-activation-fence deletion were skipped;
    - the early-input barrier handoff was skipped.

    On the IPsec side, `ipsecOverlayAcked` was never stored (`ipsec_host_fence_reconcile_9506.go`), so the hold could never acknowledge, and permit and divert transitions stalled behind "install host-input fence before divert transition".
  - **Cause**: #16841 emits `ip6 hoplimit 0 fib daddr type { local, anycast } drop` as the first rule of the host-inbound input chain, ahead of the #9506 overlay. `VerifyHostInboundOverlay` stopped at the first non-marker rule. Production runs that readback after every host-inbound apply with an overlay (`pkg/daemon/daemon_nft.go:1270-1276`), so every IPsec-fenced install failed it.
  - **Decision**: which invariant is load-bearing.
    - The overlay's documented purpose (`HostInputFenceOverlay`) is "so established/related accepts cannot bypass a revoked master". That is a property of what may run BEFORE the fence (nothing that admits), not of the fence's position.
    - Nothing depends on the position. No code inserts, deletes or replaces overlay rules by handle or position: every install and every restore is a whole-table `replaceTable`, and the readback reads marker, sets and rules.
    - #16841 puts its DROP first for the same reason, so that no accept precedes it.
    - Two DROP-only rules commute in effect: a packet matching either is dropped in both orders. So the verifier was over-strict. The fix accepts a DROP-only prefix (`hostInputRuleIsDropOnly`: exactly one DROP verdict, no verdict-map lookup, no queue). Every other rule ahead of the overlay still fails the readback.
    - Moving the zero-hop DROP after the overlay would also have restored the readback. It was not chosen: it would leave a verifier that breaks the next time any fail-closed DROP is added to the head of the chain, which is the same defect waiting to recur.
  - **File(s)**: `pkg/nftables/netlink_installer.go`, `pkg/nftables/netlink_spec.go` (doc), `pkg/nftables/README.md`, `pkg/nftables/overlay_readback_prefix_18721_test.go`, `docs/log/18721.md`
- **Timestamp**: 2026-11-01 (review fold, PR #18723 seats AD + U)
  - **Action**: replaced the denylist with an allowlist, and made the readback see expressions the decoder drops.
    - Finding: the first `hostInputRuleIsDropOnly` was a denylist. U showed that an xt-compat NFQUEUE target + DROP, `dup`, and `tproxy` all passed it. AD noted that google/nftables v0.3.0 SKIPS every expression it has no type for (`expr/expr.go` `exprsFromBytes`: `continue // unsupported expression type`).
    - Verified with a netns probe: `GetRules` returned `[payload drop]` for `[payload byteorder drop]`, `[cmp drop]` for `[rt cmp drop]`, and `[cmp drop]` for `[socket cmp drop]`. So no predicate over `rule.Exprs` alone, allowlist or denylist, can see those kinds. Even the production zero-hop rule reads back without its `byteorder`.
  - **Fix**:
    - `hostInputRuleOnlyDrops` judges each rule two ways and requires both:
      - the kernel's own expression names, dumped per rule handle by the new `readRuleExprNames` (raw `NFT_MSG_GETRULE` over the same dial target as the nftables conn), each in the allowlist `meta payload cmp bitwise byteorder fib lookup counter immediate`;
      - the typed decode: the same kinds, a lookup with no destination register, and exactly one verdict, DROP.

      The two must agree on the expression count, not counting byteorder, which the decoder never yields. A kind the decoder dropped, or a rule that changed between the two reads, fails closed.
    - Overlay rules are now held to the same list plus the marker `objref`. Before, a marked DROP rule carrying a queue passed.

- **Risk**:
  - The verifier now admits a DROP-only head ahead of the overlay. A rule that can only DROP cannot admit a fenced master's packet, so the fail-closed property is unchanged.
  - The allowlist is deliberately narrow: a future head rule using another kind (for example `ct`) fails the readback until the list is extended in review.
  - The readback now does a second netlink dump per verify. That is one small chain, and it runs only when an overlay is set.
