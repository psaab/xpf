# #18721: IPsec host-input fence readback fails since #16841

- **Timestamp**: 2026-11-01
  - **Action**: Triage found `TestHostInputFenceLiveReadbackAndRestore9506` red on master 5927babf07 in `make test-daemon-kernel-lib` ("host overlay leading rule absent"). A path-restricted `git bisect` (`pkg/nftables pkg/daemon go.mod go.sum`) driven by that cell gave first bad `2fa9d69062` (#16841). The good endpoint `19eb3e436b` was a real PASS, checked with `-v`, not a skip.
  - **Cause**: #16841 emits `ip6 hoplimit 0 fib daddr type { local, anycast } drop` as the first rule of the host-inbound input chain, ahead of the #9506 overlay. `VerifyHostInboundOverlay` stopped at the first non-marker rule. Production runs that readback after every host-inbound apply with an overlay (`pkg/daemon/daemon_nft.go:1270-1276`), so every IPsec-fenced install failed it.
  - **Decision**: which invariant is load-bearing.
    - The overlay's documented purpose (`HostInputFenceOverlay`) is "so established/related accepts cannot bypass a revoked master". That is a property of what may run BEFORE the fence (nothing that admits), not of the fence's position.
    - Nothing depends on the position. No code inserts, deletes or replaces overlay rules by handle or position: every install and every restore is a whole-table `replaceTable`, and the readback reads marker, sets and rules.
    - #16841 puts its DROP first for the same reason, so that no accept precedes it.
    - Two DROP-only rules commute in effect: a packet matching either is dropped in both orders. So the verifier was over-strict. The fix accepts a DROP-only prefix (`hostInputRuleIsDropOnly`: exactly one DROP verdict, no verdict-map lookup, no queue). Every other rule ahead of the overlay still fails the readback.
    - Moving the zero-hop DROP after the overlay would also have restored the readback. It was not chosen: it would leave a verifier that breaks the next time any fail-closed DROP is added to the head of the chain, which is the same defect waiting to recur.

- **Timestamp**: 2026-11-01 (review fold 4: AD on 337b88d882)
  - **Action 1, backoff (code).**
    - Problem: the generation counts every commit in the namespace, xpfd's own included. That covers the IPsec divert, the transit barrier, the forward fence and the early-input barrier, some of which run outside `applySem`. With 3 back-to-back attempts and no pause, a short burst of xpf's own unrelated-table commits could use up every attempt and fail an operator's commit closed.
