## Why the structural claim was false

The header said `evaluate_policy_result_with_icmp` "takes `&PolicyState` and
RETURNS a counter handle (`policy_counter_idx`) for the caller to bump; it cannot
count, log or meter by itself." That is true of the HANDLE and false of the
EVALUATION:

- `policy.rs` `try_match_rule` calls `rule.hit_counter.add(packet_len)` on every
  match;
- the implicit-default path calls `state.default_counter.add(packet_len)`;
- `&PolicyState` does not prevent either, because the counters are **atomics
  behind shared references** — an immutable borrow is not the guarantee the claim
  rested on.

And passing `packet_len = 0` did not help. `HitCounter::add` is

```rust
fn add(&self, packet_len: u64) {
    self.packets.fetch_add(1, Ordering::Relaxed);
    if packet_len != 0 { self.bytes.fetch_add(packet_len, Ordering::Relaxed); }
}
```

— the zero-length gate covers **bytes only**; the packet increment is
unconditional. So the re-derivation, which passes 0, recorded a phantom hit with
bytes unchanged.

## Impact, and why a no-forwarding-effect defect was worth fixing

`show security policies hit-count` and the default-policy counter inflate by up to
one packet per live session per config generation. No forwarding effect. It is
worth fixing for two reasons, both recorded in the header: hit-count is exactly
what an operator watches to confirm a narrowing took effect, so the noise arrives
at the worst possible moment; and a stated structural guarantee that is not
structural invites the next side effect into this path.

## Remedy, and why `HitCounter::add` itself was NOT changed

Threading a `PolicyHitCount` (`Count` / `Never`), mirroring the filter engine's
`NonRoutingCountPolicy` (#2620/#7212) — including its reason for being an
exhaustive `match` rather than a bool: *"a policy added later must classify itself
on BOTH axes instead of silently inheriting whichever answer a negated comparison
happened to give it."*

Making `add` treat `packet_len == 0` as "do not count" would have been a one-line
change and was rejected: #6304's own test-accessor doc depends on the
zero-length-still-counts behaviour as a DISTINGUISHER (*"a call site that passed a
stripped or zero length would still advance `test_packet_count`"*), and `add` is
on every counting path in the crate — repo-wide blast radius to fix a Low-severity
accounting bug.

The existing nine callers of `evaluate_policy_result_l3_aware` are untouched: it
is now a wrapper delegating with `PolicyHitCount::Count`, and the new
`evaluate_policy_result_without_counting` is the re-derivation's entry point. The
threading is internal to one function body plus `try_match_rule`.

## The site the census found, and why it is `Count`

`evaluate_junos_host_policy_l3_aware` also walks `try_match_rule`, and it passes
`PolicyHitCount::Count` at all three of its sites. That is correct, not an
oversight, and its head now says so: it is the `to-zone junos-host`
(host-inbound) evaluation, and #3706 deliberately makes it the counting site for a
host-bound packet — the established-hit path SKIPS its own re-count for
`LocalDelivery` precisely because this re-eval already counted. Only #8356's
re-derivation is side-effect-free, and it does not come through there.

## The measurement that was WRONG, and what caught it

The first run of these cells produced this, and it is worth writing down because a
matrix built on it would have been confidently wrong:

| cell | branch (fix present) | mutant (fix absent) |
| --- | --- | --- |
| `the_re_derivation_records_no_hit_on_the_matched_rule_9385` | ok | **FAILED** |
| `the_re_derivation_records_no_hit_on_the_implicit_default_9385` | ok | **FAILED** |
| `the_ordinary_admission_path_does_record_a_hit_9385` — POSITIVE CONTROL | **FAILED** | **FAILED** |
| `the_ordinary_admission_path_does_record_a_default_hit_9385` — POSITIVE CONTROL | **FAILED** | **FAILED** |

**The two POSITIVE CONTROLS fired, on BASE code, before the fix was in play.** That
is the instrument saying the reading is wrong, not the code — the cheapest
correction available, and it is only worth anything if it is followed rather than
re-run.

**The wrong measurement, exactly.** Each control asserted `session_hit == 0` (the
packet was a session MISS) and then read a counter delta. `session_hit == 0` says
the packet missed; it does **not** say the miss reached the counting
`try_match_rule` walk. `policy_deny_snapshot` carries **no neighbours**, so a MISS
to `172.16.80.200` resolves the connected route out `reth0.80`, finds no
neighbour, lands on the **MissingNeighbor** arm, and never reaches the walk. The
delta was 0 because the fixture could not move that counter at all.

**Why it was invisible.** Every other cell in this file PRE-INSTALLS a decision
that already carries a `neighbor_mac` (`decision(WAN_IFINDEX)`), so none of them
has ever needed a neighbour in the ledger. The #9385 controls are the first cells
in the file to drive a session MISS through real admission.

**What it would have cost.** The DEFECT half was measuring correctly the whole time
— 0 on the branch, +1 on the mutant, a clean kill in both directions. The danger
was the other half: "the counter did not move" is satisfied both by *the fix works*
and by *this fixture cannot move that counter at all*, and only the control
distinguishes them. Written without controls — the obvious way — these cells would
have gone green on the branch and been recorded as a bound property that was in
fact unmeasured.

**THE FIRST REMEDY WAS ALSO WRONG, AND THE SAME INSTRUMENT CAUGHT IT.** The
obvious fix — add a neighbour for the driven destination to a local copy of the
snapshot — was applied, and the controls STILL failed, now on the newly added
instrument: `tx == 0` for the permit control and `policy_deny == 0` for the
default one. So a session MISS in that fixture reaches neither the forward path
nor the implicit-default deny exit; a neighbour alone is not what it is missing.
That attempt also tripped a SHARED RATCHET on its way past —
`cos_literal_guard_7689` went red because the exhaustive `NeighborSnapshot`
literal pushed the additive-wire population from 26 to 27 — which is a second
reason the attempt was wrong and a reminder that a fixture edit has blast radius
beyond its own cell.

**The remedy that works is to stop guessing and build on MEASURED ground.** The
controls now run on `inbound_dnat_snapshot`, which is PROVEN to admit and forward:
the shipped `tests_policy_inbound_nat` cells and the #9382 two-phase cells both
assert `tx == 1` on exactly that fixture and pass. The default-verdict control uses
the same fixture with a policy covering only the pre-translation VIP, the shape
`policy_inbound_dnat_denies_when_only_original_dst_permitted` already proves
reaches `policy_deny >= 1`.

**What the controls do and do NOT establish**, stated in the cells rather than
implied: they establish that the counter-reading instrument observes a bump when
the ordinary admission path runs — so a zero delta means *the re-derivation did
not count*, not *nothing in this harness can count*. They do NOT establish that on
the SAME rule in the SAME fixture, which a same-fixture control would. That gap is
the price of the fixture limitation and is recorded rather than papered over.

The shared `forwarding_with_lan_rule` was deliberately left untouched: it is used
by the #8356, #9381 and #9384 cells, and perturbing a fixture six other cells
depend on to fix a measurement in two is the wrong trade.

**And the instrument stays.** `tx == 1` / `policy_deny >= 1` are now permanent
assertions in the controls, so a control that ever again stops reaching the site
it controls for fails loudly instead of silently reading a zero.
