# #15198 — application `icmp-type` symbolic names (A04-01)

- **Timestamp**: 2026-10-19
- **Action**: Resolve Junos symbolic `icmp-type` names in the application
  path with the existing `icmpTypeNames`/`icmp6TypeNames` tables chosen by
  protocol, so a symbolic cell compiles to the same `ICMPType` as the
  numeric one. `icmp-code` stays numeric-only.
- **Files**: `pkg/config/filter_match_resolve.go`,
  `pkg/config/compiler_applications.go`, `pkg/config/schema_security.go`,
  `pkg/config/schema_validators.go`,
  `pkg/config/compiler_validate_strict_application.go`,
  `pkg/config/types_security.go`,
  `pkg/config/application_match_drops_9525.go`,
  `pkg/config/compiler_application_symbolic_icmp_15198_test.go`,
  `pkg/config/application_match_drops_9525_test.go`,
  `pkg/config/README.md`.

## Defect

Application `icmp-type` / `icmp-code` rejected Junos symbolic names
(e.g. `echo-request`) although the firewall-filter path resolves them
(#3205). The application schema carried `ValidateInteger(0,255)`
(`schema_security.go`) and the compiler parsed with `Atoi` only
(`parseICMPTypeCode` in `compiler_applications.go`), recording the name
on `UnknownICMP` so `validateApplicationSpecsStrict` rejected the commit
with `must be an integer in 0..255`. Fail-closed rejection of valid
Junos syntax — a migration blocker with no loss of enforcement.

For `icmp-code` the symbolic premise does not hold: Junos application
`icmp-code` is numeric (Range: 0 through 255, Juniper CLI reference) and
the filter path likewise fails closed on symbolic codes
(`resolveICMPCodeToken`). No code-name table was invented; symbolic
codes remain rejected on both paths.

## Fix

- `filter_match_resolve.go`: `resolveApplicationICMPType(tok, protocol)`
  selects `inet6` for ICMPv6 protocols
  (`icmpv6`/`icmp6`/`icmp-v6`/`junos-icmp6-all`/`junos-pingv6`/`58`) and
  `inet` otherwise, delegating to the shared `resolveICMPTypeToken` /
  `icmpTypeNames` / `icmp6TypeNames`; `resolveApplicationICMPCode`
  delegates to the numeric-only `resolveICMPCodeToken`.
- `compiler_applications.go`: `parseApplicationICMPType` /
  `parseApplicationICMPCode` replace `parseICMPTypeCode` (deleted, no
  remaining callers). Direct body: `icmp-type` tokens are stashed raw and
  resolved after the child loop once the final `protocol` is known (the
  leaf may precede `protocol`), with the existing value-aware duplicate
  tracking — `echo-request` then `8` on `icmp` is an idempotent alias
  restate, `echo-request` then `0` is a conflict. Inline term: tokens are
  stashed and resolved per generated application, so a multi-protocol
  term (`protocol icmp protocol icmpv6 icmp-type echo-request`) yields
  8 on the icmp application and 128 on the icmpv6 one. Unresolvable
  tokens (unknown name, wrong-family name, out-of-range) still land on
  `UnknownICMP`/`badICMP` and fail closed at strict commit.
- `schema_security.go` / `schema_validators.go`: the application
  `icmp-type` leaf now uses `ValidateICMPTypeValue` (numeric 0..255 or a
  name from either family table — `SchemaValidate` has no protocol
  context, so a wrong-family name passes the schema and is then caught
  by the compiler/strict gate for the actual protocol) and `icmp-code`
  uses `ValidateICMPCodeValue` (numeric only, same accept set as before).
  The leaf keeps `valueType: ValueInteger` so the typed-leaf walk still
  invokes the validator.
- Strict-gate and tolerant-path wording (`UnknownICMP` doc,
  `ApplicationMatchDrops`) now states the symbolic alternative instead of
  claiming every value must be an integer.

NOT changed: the firewall-filter path (already symbolic-aware, #3205),
the `icmp6-type`/`icmp6-code` unimplemented-leaf refusal (#9603),
predefined applications, and any dataplane matching — the compiler
still emits only numeric `ICMPType`/`ICMPCode`.

## Risk

- A name valid in only one family table (e.g. `neighbor-solicit`) is
  accepted by `SchemaValidate` regardless of protocol, then rejected by
  the strict spec gate when the application's protocol is the other
  family — the commit still fails closed, with the compiler's message.
  Unreferenced applications on the tolerant path keep the pre-existing
  warn-only behaviour for `UnknownICMP`.
