# #15991 — ASCII `0x…` PSK rendered as raw hex bytes

- **Timestamp**: 2026-10-22 (fold 2026-10-23)
- **Action**: an `ascii-text` PSK that literally reads `0x<hex digits>`
  (e.g. `pre-shared-key ascii-text 0x61626364`) must reach charon as
  its literal ASCII bytes. Two stacked defects: (1) the renderer in
  `pkg/ipsec/policy.go` discarded provenance — the gateway-group fold
  encoded each member PSK as a bare string (prefixing hex values with
  `0x`), the lone-value emission treated any `0x`-prefixed string as
  a hex key (`secret = 0x61626364` unquoted), and the fold collapsed
  an ASCII `0x<digits>` with a hexadecimal `<digits>` member on one
  gateway; (2) **quoting does not fix it** (Opus fold on PR #16318):
  xpf loads secrets as TEXT — `Manager` writes
  `/etc/swanctl/conf.d/xpf.conf` and runs `swanctl --load-all`
  (`manager.go`); there is no Go VICI client in the secret path.
  swanctl's `load_secret` (strongSwan 6.1.0
  `src/swanctl/commands/load_creds.c:698-718`, identical on master)
  takes `get_str("secrets.%s.secret")` — the settings lexer
  (`settings_lexer.l` `<str>` state) has already stripped the quotes
  and processed `\"`/`\\` escapes — then `strcasepfx(value, "0x")`
  → `chunk_from_hex`, `strcasepfx(value, "0s")` →
  `chunk_from_base64`, else literal, and sends the decoded bytes as
  the VICI `load-shared` `data` blob (`vici_add_key_value(req,
  "data", data.ptr, data.len)`). So `"0x61626364"` and `0x61626364`
  load identically as bytes `61 62 63 64`. The fix keeps
  `pskValue{value, hex}` provenance through the fold/dedupe and emits
  a loader-facing token (`swanctlSecretRendered`/`swanctlSecretToken`
  in `crypto.go`): hex-authored → `0x<hex>` (#15027 unchanged);
  ASCII colliding with the loader prefixes (`0x`/`0X`/`0s`/`0S`,
  `asciiValueCollidesWithSwanctlEncoding`) → base64-armored
  `0s<base64 of the literal bytes>` (e.g. `"0sMHg2MTYyNjM2NA=="`
  for `0x61626364`), which charon base64-decodes back to the exact
  authored string; any other ASCII value → itself, quoted as before.
  Grouped secrets keep the single quoted comma-joined string with
  per-element tokens. No compiler/schema/gate change: `PSKHex`
  already carried provenance to the renderer. Residual (documented,
  not fixed): the pre-existing grouped shape is still ONE secret
  value at load (the loader takes the whole joined string literally
  unless it starts with `0x`/`0s`, so grouped members were never
  separate charon credentials); per-element tokens preserve each
  member's authored token text and keep a colliding element from
  re-decoding the whole value, but splitting grouped members into
  separate `ike-<conn>-<n>` secret sections is a larger redesign
  out of scope here.
- **Files**: `pkg/ipsec/policy.go`, `pkg/ipsec/crypto.go`,
  `pkg/ipsec/policy_psk_ascii_hex_15991_test.go`,
  `pkg/ipsec/README.md`, `debian/changelog`, `docs/log/15991.md`.
- **Validation**: (a) render probe at base `30638bcad3` (temporary,
  removed): `PSK="0x61626364", PSKHex=false` rendered unquoted
  `secret = 0x61626364`, indistinguishable from the hex control.
  (b) **Live charon 6.1.0** (strongSwan 6.1.0, two-daemon netns lab
  reusing the `/var/tmp/a16/lab` harness shape, `unshare -Urnm`):
  R `secret = "0x61626364"` (quoted) vs I `secret = "abcd"` →
  IKE_SA + CHILD_SA ESTABLISHED (proves the quoted form hex-decodes
  — the first PR head was therefore still wrong at load); R
  `secret = "0sMHg2MTYyNjM2NA=="` (the new renderer output) vs I
  same → ESTABLISHED, vs I `"0x61626364"` (hex bytes) →
  `AUTH_FAILED`, vs I `"abcd"` → `AUTH_FAILED` (proves the armored
  form loads as the literal string and nothing else). System charon
  and netns state restored afterwards (conf.d empty, no SAs).
  (c) New `TestASCIIHexPrefixedPSK15991` (lone ascii-0x/0X/0s
  armored vs lone hex raw, policy-fallback armored, grouped
  ascii-0x+hex distinct `"0s…,0x…"`, grouped dedupe+plain, grouped
  plain unchanged, non-hex `0xzzzz` armored, predicate boundaries)
  and `TestASCIIHexPrefixedPSKEndToEnd15991` GREEN with the fix;
  RED with the pre-fold quoted render (token assertions). Existing
  `TestPSKHexadecimal*15027`/`TestGatewayGroup*15024` unchanged
  GREEN; full `go test ./pkg/ipsec/ -count=1` GREEN;
  `go vet`/`gofmt` clean.
- **Risk**: only ASCII values starting with `0x`/`0X`/`0s`/`0S`
  change render (deliberately): they now authenticate as the literal
  string and stop matching a peer that had compensated with the
  decoded bytes. Hex, non-colliding ASCII (including every existing
  fixture secret), grouped-plain, and malformed-hex skip renders are
  byte-identical. Base64 output has no comma/quote/backslash/control
  byte, so armoring cannot break the swanctl line.
