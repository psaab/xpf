# #17859 — extracted pending resign can overwrite a newer restored priority

- **Timestamp**: 2026-10-27
- **Action**: `applyPendingResign` cleared `resignPending` and copied the
  stashed 0 out under `resignMu`, then installed that local copy into
  `cfg.Priority` only after re-acquiring `mu`. A cluster-authoritative
  priority restore (`Manager.UpdateRGPriority`,
  `vrrpInstance.updateConfigHeld`) completing in that window writes the
  restored priority and discards the stash — but the pending flag is
  already false, so the discard is a no-op flag-clear and the extracted
  0 silently overwrites the restore (retro-review of #17616 found the
  interleave; nothing repaired `cfg.Priority` until the next posture
  reconcile). Fixed by making the apply two-phase with an epoch fence:
  `extractPendingResign` snapshots `{priority, resignEpoch}` and clears
  the flag under `resignMu`; `commitPendingResign` re-checks
  `resignEpoch` under `mu` and drops the extracted value when a discard
  landed in between. `discardPendingResignLocked` (renamed for the
  must-hold-`mu` contract, like `removeVIPsLocked`) bumps `resignEpoch`;
  `updateConfigHeld` now calls it INSIDE the `mu` critical section that
  writes the replacement priority, matching `UpdateRGPriority`, so `mu`
  ordering alone decides commit-vs-restore and the restored value
  always survives.
- **Why**: The run loop parks between the stash extraction and the
  `cfg.Priority` write whenever the restore lands in that gap — legacy
  VRRP-backed RETH failback (`ResignRG` → posture reconcile drives the
  RG back to Primary → `UpdateRGPriority(200)`) could end with the
  instance stuck at resignation priority 0 until the ~10s reconcile
  mismatch repaired it, exactly the #16821 harm the discard helper was
  meant to close.
- **What**: `pkg/vrrp/instance_resign.go` — `pendingResign` snapshot
  type, `extractPendingResign`/`commitPendingResign` phase split with
  the `resignEpoch` re-check, `discardPendingResign` →
  `discardPendingResignLocked` (+epoch bump). `pkg/vrrp/instance.go` —
  `resignEpoch` field; `updateConfigHeld` discard moved inside `mu`.
  `pkg/vrrp/manager.go` — caller renamed. `pkg/vrrp/README.md` — A25-06
  bullet extended with the two-phase fence. New
  `resign_extract_supersede_17859_test.go`: two subjects drive the real
  window deterministically (extract → restore → commit) via
  `UpdateRGPriority` and `updateConfig`; controls pin that an
  unsuperseded commit still installs 0 (#16821 contract), a
  pre-extraction restore leaves nothing to install, and a
  post-commit restore still wins by ordering. NOT changed: the pending
  window's `getPriority` behaviour (pre-resign advert priority until
  consumption) — the separate retro finding about `masterDownInterval`
  skew during the pending window is out of scope here.
- **File(s)**: `pkg/vrrp/instance.go`, `pkg/vrrp/instance_resign.go`,
  `pkg/vrrp/manager.go`, `pkg/vrrp/README.md`,

- **Risk**: The commit-vs-restore decision now serializes on `vi.mu`
  at both restore sites; a future restore path writing `cfg.Priority`
  must discard under the same `mu` hold (enforced by naming/review, no
  runtime lock-ownership assertion). The concurrent `beginResign`
  interleave is value-safe (the stash is always 0). The pending-window
  `masterDownInterval` skew residual from the same retro review
  remains open as a separate finding.
