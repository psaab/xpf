# #16576 — persistent flow-trace writer confined to /var/log/xpf-flow-trace

- **Timestamp**: 2026-10-24
- **Action**: The persistent `security flow traceoptions file <name>` writer
  (`logging.TraceWriter`) wrote directly under `/var/log`, unlike the #5038
  CLI `monitor security flow file` writer. A strict-clean `file auth.log`
  (or `syslog`, `wtmp`, `btmp`, `kern.log`) made root xpfd chmod the existing
  host log to 0600, append flow telemetry to it, and rotate/unlink its
  generations. Fixed by confining the persistent writer to the same
  dedicated namespace as the CLI writer:
  - `pkg/logging/trace.go`: `traceLogDir` is now
    `/var/log/xpf-flow-trace`; new `TraceLogDir()` accessor for show
    surfaces; new `ensureTraceLogDir()` creates the dir 0700 after an
    #8482-style `Lstat` check (symlink / non-directory / non-ENOENT Lstat
    error all fail closed), replacing the bare `MkdirAll(..., 0755)`;
    `NewTraceWriter` uses it. The basename-only sanitize, `O_NOFOLLOW`,
    regular-file check and 0600 enforcement are unchanged, so a host-log
    name now lands harmlessly inside the private dir and still traces and
    rotates there.
  - `pkg/factoryreset/wipe_firewall_logs_10300.go`: the configured-trace
    wipe leg now resolves the basename inside `wipeFlowTraceDir`
    (`/var/log/xpf-flow-trace`, already `RemoveAll`'d as a static leg)
    instead of `/var/log`, so a zeroize naming `auth.log` as its trace no
    longer deletes the host's `/var/log/auth.log*`. (The appliance-only
    wholesale `logfiles` seal leg still clears `/var/log` on appliance
    hosts by design; that is unchanged and out of this leg's scope.)
  - Show surfaces: `show security flow traceoptions` in both
    `pkg/cli/cli_show_flow.go` and `pkg/grpcapi/server_show_flow.go` now
    render `File: /var/log/xpf-flow-trace/<name>` via
    `logging.TraceLogDir()` instead of the bare basename.
  - `pkg/config/compiler_security_flow.go`: gate comments and the
    bare-name error text now name `/var/log/xpf-flow-trace` as the write
    location (acceptance unchanged: bare basenames including `auth.log`
    still commit; they land in the private dir).
  - Docs: `pkg/logging/README.md` trace bullet and `docs/log/10300.md`
    wipe scope updated to the confined location.

- **Validation**: New `TestTraceWriterConfined16576HostLogsUntouched` seeds
  a host-log tree (`syslog`/`auth.log`/`wtmp`/`btmp`/`kern.log` at 0640
  plus `.1`/`.2` generations) in a parent dir, drives 600 events at
  `size 10240 files 2` through `NewTraceWriter` for each name, and asserts
  every seeded file byte-identical at 0640 while a non-empty trace plus
  rotations exist only inside the 0700 confined dir — the exact
  acceptance rows from the issue probe. Also
  `TestTraceLogDirDefaultIsDedicated16576`,
  `TestTraceWriterRefusesSymlinkedDir16576` (#8482 parent check),
  `TestZeroizeTraceConfined16576HostLogSurvives` (wipe leg leaves host
  `auth.log`, erases confined dir), updated
  `TestPerformZeroizeWipeErasesFirewallLogs10300` trace fixtures to the
  confined dir, and confined-path assertions added to both
  `TestShowFlowTraceoptionsProto15679` surfaces. Targeted runs:
  `go test ./pkg/logging/ ./pkg/factoryreset/ -count=1` PASS;
  `go test ./pkg/cli/ ./pkg/grpcapi/ ./pkg/config/ ./pkg/daemon/ -run
  'Trace|Traceoptions|Zeroize' -count=1` PASS. RED-on-revert: restoring
  `traceLogDir = "/var/log"` makes the seeded host files get chmodded /
  appended / rotated, failing the byte-identical assertions; restoring the
  wipe leg's `/var/log` join fails the new zeroize survival test.
- **Risk**: Existing persistent traces at `/var/log/<name>` from older
  builds are no longer appended to or rotated (the writer starts fresh in
  the private dir) and are no longer named by the zeroize trace leg; they
  remain ordinary files under `/var/log` (still cleared by the appliance
  `logfiles` seal leg). Operators looking for the trace file must look in
  `/var/log/xpf-flow-trace/`; both show surfaces now print that path.
  No config syntax change: `file <name>` still commits as before.
