# #16417 — persistent-NAT batch peer cap skipped Generation==0 first contact

- **Timestamp**: 2026-10-24
- **Context**: #14963 (ca901fc93e) capped new distinct origins on the
  lease-batch import path at `maxPersistentNatGenerationPeers11486`
  (16) so the durable generation state file could never exceed the
  loader's peer limit — but the cap was guarded by
  `batch.Generation > 0`. The generation-0 first-contact arm below it
  still persists a new `RemoteGenerations[origin] = 0` key. An
  authenticated HA sync peer emitting gen-0 batches from 17+ distinct
  origin ids therefore wrote a state file that
  `loadPersistentNatLeaseGenerationLocked` rejects
  ("persistent-NAT lease generation state exceeds peer limit") on
  every restart, durably bricking persistent-NAT lease export/import
  until the file is removed by hand. Genuine senders start at
  Generation 1, so reach requires a forged/corrupt/misbehaving peer;
  there is no enforcement loss.
- **Fix**: in `ImportPersistentNatLeaseBatch`
  (`pkg/dataplane/userspace/manager_idle_leases_8121.go`), drop the
  `batch.Generation > 0` condition so the peer cap applies to every
  unseen origin, mirroring the forwarded-clear sibling
  (`ClearPersistentNATLeasesWithGeneration`, which caps every unseen
  origin regardless of generation). Gen-0 first contact keeps its
  no-clear-barrier semantics for origins within the cap; it is not
  uncapped. Age/LRU pruning was considered and not added: the cap now
  maintains the writer-side invariant `|RemoteGenerations| <= 16` on
  every arm, and pruning durable watermarks would weaken replay
  protection. NOT changed: the jump bound, stale/local-clear fence
  handling, the gen-0 no-barrier arm itself, the clear path, or the
  loader.
- **File(s)**: `pkg/dataplane/userspace/manager_idle_leases_8121.go`,
  `pkg/dataplane/userspace/persistent_nat_generation_14963_test.go`,
  `docs/log/16417.md`, `debian/changelog`
- **Validation**: new `TestPersistentNatBatchGen0PeerLimitEnforced16417`
  fills the table to the cap with 16 empty gen-0 batches (one-time
  fresh-state local barrier on the first import, then no helper
  traffic), refuses the 17th distinct gen-0 origin before and after
  restart, proves the restarted loader accepts the capped file
  (16 origins), and admits a known gen-0 peer's empty generation-1
  advance at the cap. FAIL-ON-REVERT verified in-lane: restoring
  `batch.Generation > 0` makes the 17th gen-0 batch accepted and the
  test fails; with the fix it passes. The test deliberately uses
  empty lease sets and a direct loader call because the leased-import
  and `ExportPersistentNatLeaseBatch` paths cross the helper
  protocol-status gate, whose fake-helper fixture is broken
  package-wide on current master (pre-existing: the 11486/14580/14963
  leased tests fail identically on unmodified origin/master with
  "status response omitted required status"; out of scope here, see
  below).
- **Residual**: the pre-existing fake-helper/status breakage leaves
  the leased gen->gen+1 helper-import leg of the sibling 14963 test
  (and the 11486/14580 leased tests) red on master; this change does
  not touch that fixture and its new test avoids the broken seam
  while still exercising the cap, the persistence, and the restart
  load. A state file already poisoned with 17+ gen-0 origins by a
  misbehaving peer before this fix still needs manual removal — the
  loader continues to fail closed rather than silently dropping
  durable watermarks.
