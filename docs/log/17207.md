# Issue #17207 — future-incompatible `ambiguous_import_visibilities` glob cycle

- **Issue:** Three future-incompatible `ambiguous_import_visibilities` warnings (rust-lang/rust#149145, "will become a hard error") at `src/afxdp/mod.rs:144,149,272` (plus a fourth test-only site at `:154`), produced by child modules that both `use super::*` and glob re-export their own children (`session_glue/mod.rs:76-77` vs `:1`; `types/mod.rs:22` vs `:1`). Nothing denied `future_incompatible`, so new sites kept being added.
- **STEP-0 (defect live on origin/master `c4e12aafc3`):** `cargo +1.98.1 check --release --message-format=json` in `userspace-dp/` emitted 6 ambiguous diagnostics (2 names at `:149`, 1 at `:144`, 3 at `:272`); `cargo check --tests` added a 7th at `:154` (`export_forward_sessions_for_owner_rgs`, test-only). Re-anchored from the issue's `0ce804221f` lines: 143→144, 148→149, 271→272.

## What

1. Imported the six names from their defining leaf modules in `afxdp/mod.rs`, per the issue's first fix direction:
   - `forward_export_candidates_for_owner_rgs` and (test-only) `export_forward_sessions_for_owner_rgs` from `session_glue::revalidation` (defined `pub(crate)` at `revalidation.rs:717,764`);
   - `SESSION_DELETE_REPLICA_DROP_REPAIRED` / `SESSION_DELETE_REPLICA_DROPPED` from `session_glue::worker_commands` (defined `pub(crate)` at `worker_commands.rs:1089,1115`);
   - `ForwardingDisposition` / `ForwardingResolution` / `NeighborEntry` from `self::types::forwarding`.
2. Made the leaf modules nameable at `pub(in crate::afxdp)` — no wider: `afxdp::session_glue` itself, `session_glue::{worker_commands, revalidation}`, and `types::forwarding`. No item visibility changed; the existing `pub(super)`/`pub(crate)` re-exports inside `session_glue/mod.rs` and `types/mod.rs` are untouched and still serve all other callers.
3. Added `#![deny(future_incompatible)]` at the crate root (`src/main.rs:1`), so any new future-incompatible site fails the build instead of warning.
4. Updated the BUMP PROCEDURE in `userspace-dp/rust-toolchain.toml` to require "0 future-incompatible warnings — enforced by `#![deny(future_incompatible)]` in src/main.rs".

Note on the 4th (test-only) site: the issue counted 3 release / 4 tests sites; the `--tests` run here reports the extra name at the same three `afxdp/mod.rs` lines plus `:154`, all fixed by the same leaf imports.

## Risk

Import-path-only change: the same items are re-exported at the same `pub(crate)` surface from `crate::afxdp`, so all existing callers (`crate::afxdp::SESSION_DELETE_REPLICA_DROPPED`, `crate::afxdp::ForwardingResolution`, resync tests, coordinator status accessors) resolve unchanged. Module visibilities widen only to `pub(in crate::afxdp)` (visible inside `afxdp`, not crate-wide or public). The new `#![deny(future_incompatible)]` will turn any *future* rustc future-incompatibility warning in this crate into a build error — that is the intended enforcement, and it is exactly what the toolchain BUMP PROCEDURE now documents.
