# #15790 (G33-01) — `StaticNatTable::from_snapshots` index overwrite + unindexed `snat` / `nat_local_match_possible` scans

- **Timestamp**: 2026-10-19
- **Defect**: `StaticNatTable::from_snapshots` (`userspace-dp/src/nat/static_nat.rs`) built the
  #15116 per-destination index with `table.dnat_by_dst.insert(*ip, indexed)` inside the loop over
  the `dnat` map. One external IP hosting several port keys — `(203.0.113.10, Some(80))` and
  `(203.0.113.10, Some(443))`, the ordinary multi-port static-NAT VIP — maps every key to the same
  index bucket, so each `insert` discarded the previous key's entries. Only the last-iterated key
  survived; the rest were installed in `dnat` (the main `match_dnat_*` path keys that map directly
  and was unaffected) but invisible to `dnat_port_entries_for`, backing
  `flowless_l4_translation_possible`, `flowless_l4_dnat_translation_possible`, and
  `flowless_non_tcp_udp_port_map_possible` — the probes that decide whether a flowless packet
  (non-first fragment, non-TCP/UDP protocol, ICMP error) could be DNAT'd. This is the sibling bug
  to #15534, which fixed the identical `insert`→entry-extend overwrite in
  `DnatTable::from_snapshots` (`destination.rs`); the fix was never ported to static NAT.
  Additionally the secondary acceptance item: the outbound leg of
  `flowless_l4_translation_possible` linearly scanned the whole `snat` map per packet, and
  `nat_local_match_possible` (#15118, the local-delivery claim probe) linearly scanned the whole
  `dnat` map per lookup — both `O(N)` in installed rule count, the #15116 amplification class.
- **Fix**: In `from_snapshots`, build `dnat_by_dst` with `.entry(*ip).or_default().extend(indexed)`
  (verbatim the #15534 sibling pattern), and build a new symmetric `snat_by_src: FxHashMap<IpAddr,
  Vec<(Option<u16>, usize)>>` index over the finished `snat` map. Re-route the two unindexed
  probes through the indexes: the outbound leg of `flowless_l4_translation_possible` now visits
  only the packet source's port-bearing `snat` entries, and `nat_local_match_possible` visits only
  the destination's indexed entries (identical port gate — `Some(p)` requires an L4 protocol and
  `p == dst_port`, `None` claims every port — and identical per-entry scope/source predicates;
  `any` is order-insensitive so results are unchanged for destinations whose rules all survived).
  Both indexes are rebuilt wholesale from the finished maps in the only constructor, so they
  cannot drift. The `blocks` (prefix) leg of `nat_local_match_possible` stays a linear scan:
  prefix rules are operator-bounded and cannot be keyed by exact IP (same posture as #15116's
  DNAT prefix slots). No behaviour change outside the cited probes; fail-closed outcomes are
  preserved exactly.
- **Regression**: New `nat::tests_static_multiport_index_15790` (three tests): a two-port
  same-external-IP fixture (`203.0.113.10:80`→`192.168.80.10`, `:443`→`192.168.43.10`) in both
  snapshot orders asserts both ports are reachable via `nat_local_match_possible` (configured
  ports claim, unconfigured `:22` and unrelated destinations do not), via the flowless and
  non-TCP/UDP port-map probes, and via the main DNAT path; a source-scoped variant gives each port
  a distinct `match source-address` so each port is identifiable through the indexed probes (own
  source claims own port, cross claims and unrelated sources claim nothing); and the indexed
  `snat` leg reports each internal source possible while an unknown source is not. RED on base
  (discarded port's probes return false), GREEN after the fix.
- **Risk**: Index memory is O(installed entries), built once per config snapshot; no per-packet
  allocation (probes only dereference indexed entries). Tables are constructed only via
  `from_snapshots`, so no stale-index path. Residual: the `blocks` prefix scan in
  `nat_local_match_possible` is still linear in configured block-rule count (bounded, unrelated
  to the host-rule amplification).
