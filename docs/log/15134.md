# #15134 — #14660 inert-action gate stops at the `then` keyword: unknown change-configuration children commit clean and are dropped (A91-02)

## Defect

The #14660 closed-world gate (`pkg/config/event_options_inert_14660.go`,
`validateEventOptionsInertAST` / `validateEventPolicyInert14660`)
validated `event-options` children, policy children, `events` values,
and `then` action keywords — but nothing descended into the
`change-configuration` node. `compileEventOptions`
(`pkg/config/compiler_services.go`) reads only
`FindChildren("commands")` under `change-configuration`, and
`schemaEventOptions` (`pkg/config/schema_system.go`) declares only
`commands` there, so every other child was silently dropped.

Measured on `origin/master` `5a5cd5d57a` (probe run in this lane, all
`CompileConfig err=<nil>`): `change-configuration { commit-options {
check; } commands "..."; }`, `user-name bob`, `retry 3`, and
`junk-thing foo` — hierarchical and flat-set spellings alike.

The verify-only row is the dangerous one: an operator-authored Junos
`commit-options { check; }` means "verify, do not activate". It
committed clean, was dropped, and `pkg/eventengine` then performed an
autonomous LIVE commit of the `commands` when the policy fired.

## Fix

Extend the existing #14660 walk one level, in the same file and with
the same strict/lenient doctrine — no new gate, no schema change:

- `pkg/config/event_options_inert_14660.go`:
  `eventChangeConfigChildTokens14660` reads the permitted
  `change-configuration` children from `schemaEventOptions`
  (`policy > then > change-configuration`, #9017 rule), falling back
  to `commands`. `validateEventPolicyInert14660` now, for each
  permitted `change-configuration` action, checks every child keyword
  via the new `changeConfigChildTokens14660` helper and rejects
  (strict) / warns (lenient) any other keyword, naming the policy,
  the token, the known set (`commands`), and `(#14660, #15134)`.
  `changeConfigChildTokens14660` mirrors `thenChildTokens14660` one
  level down and covers both AST shapes: bare `then` with braced or
  packed (`Keys[1]`) `change-configuration` children, and packed
  `then change-configuration ...` where the child keyword is the
  braced body's child or the `Keys[2]` tail. Only the child keyword
  is read — its value (e.g. `check` under `commit-options`) is never
  interpreted, matching how the compiler would have dropped it.
- NOT changed: `compileEventOptions` (already reads only `commands`;
  the gate now makes the drop loud instead of silent),
  `SchemaValidate`/`closedWorld`, the event engine, and the flat-set
  parser. `apply-groups*` / `apply-macro` meta keywords at the
  `change-configuration` level remain exempt, as at every other level
  of this gate.

  `TestCheckTextEventOptionsInert15134` — the four hierarchical rows
  plus a flat-set row rejected by `CheckText` (the commit-check

RED evidence: on unmodified `origin/master` the probe shapes above
all compiled with `err=<nil>` (recorded in the lane probe run);
after the fix the new strict cells reject and the lenient cells warn.

Suites: see PR Validation for totals.

## Risk

- Behaviour delta: configs carrying inert `change-configuration`
  children (including `commit-options { check; }`) now hard-reject
  at commit / commit-check instead of silently performing a live
  commit. Already-persisted configs still boot via the lenient
  warning path (#1960).
- A future `change-configuration` child declared in
  `schemaEventOptions` is permitted automatically; actually
  executing it would still require a `compileEventOptions` reader.
- Rust/dataplane: untouched.
