## Decision rule

Thread the arm whenever the existing immediate dispatcher already holds and
branches on a lenient flag; use outcome-neutral wording only when obtaining the
arm would cross a schema/validator boundary or otherwise add a new arm-plumbing
layer. Every producer in this issue meets the first condition, so all eight
builder functions use per-arm outcomes. Their existing dispatchers pass the
exact flag used for the return-versus-warning decision. The four direct
peer-effective NAT calls pass `false`, preserving strict wording there. No
schema boundary is crossed and no behavior or gate decision changes.

For each builder, the strict outcome is the literal `the commit is refused`.
The tolerant outcome retains the original commit-succeeds/runtime-consequence
clause. Diagnostic heads, offending values, remediation, warning envelopes, and
compiled output remain unchanged.

### Empty application-set: action and sibling facts

The original tolerant outcome — `the dataplane installs a never-match term so
the translation never fires` — was true only for a translating rule whose
application list produced zero terms. It was false for off exemptions, which
widen the broken application axis to match all, and for mixed translating
lists, which retain valid sibling terms (#12631/#13547).

`natMatchEmptyAppSetError` now receives:

```go
(natKind, ruleSet, ruleName, name string, off, anySiblingTerms, lenient bool)
```

`off` is the rule's `Then.Off`. `anySiblingTerms` is computed by the caller from
the actual application resolutions/expansions. SNAT's `addApp` emits a term for
each resolved application; DNAT's protocol-less translating suppression
(#12224) is accounted for rather than mistaking a resolved name for an emitted
term. Off takes priority over the sibling fact.

`validateNATMatchApplicationsStrict` now collects-then-reports within each
rule. It evaluates each reference at most once, records the first empty set,
and scans the remaining references to learn the sibling fact. An undefined
reference before the first empty set still returns immediately; one after an
empty set cannot displace that earlier error. Thus first-error ordering and
accept/reject behavior are preserved, with no repeated set expansion. The
empty-first mixed pins prove the scan does not stop at the diagnostic's first
producer.

The three tolerant outcomes are now:

- **Lone zero-term translating rule (original text retained):**
  `the rule commits but the dataplane installs a never-match term so the translation never fires`.
- **Off exemption:**
  `the rule commits but the off exemption's application axis widens to match all (over-exemption)`.
- **Mixed translating list with sibling terms:**
  `the rule commits but the empty reference contributes no terms; sibling application terms remain in the match union`.
  This deliberately pins the union fact rather than overclaiming that every
  possible sibling term must itself match a flow.

`TestNATMatchEmptyAppSetOutcome18971` now pins five config-level cases: the
original lone SNAT translation, mixed-empty-first SNAT off, lone DNAT off,
mixed-empty-first SNAT translation, and mixed-valid-first DNAT translation.
The mixed shapes reuse #13547's valid `junos-http` plus `EMPTYSET` fixture
shape; the empty-first rows make the required whole-rule scan observable.
Strict pins and the peer-effective strict pin remain unchanged.

### Undefined pool: NAT-kind outcome

The original fallthrough text is DNAT-specific. SNAT's `missing_pool` marker
becomes `SourceNatLookup::Unavailable`, which drops the packet without trying a
later rule or the no-NAT default. `validateNATPoolReferencesStrict` already had
`kind`; its tolerant outcome now splits on it:

- **SNAT:**
  `otherwise the rule commits but the dataplane marks the rule unusable (missing_pool) and drops matching traffic (fail closed; no later-rule or no-NAT fallthrough)`.
- **DNAT (original text retained):**
  `otherwise the rule commits but the dataplane fails the translation closed (the pool lookup misses, so the rule is dropped / marked unusable) and matching traffic is silently left untranslated, falling through to a later rule or the no-NAT default`.

`TestNATPoolReferenceOutcome18971` pins both tolerant kinds and both strict
refusals. The source-NAT peer-effective negative pin was updated to exclude the
new source-specific tolerant text. Related producer/dispatcher comments now
state the same SNAT-versus-DNAT mechanism.
