# Issue #12789 — key SYN-rate and sticky SNAT placement

## Root cause

The SYN-rate count-min sketch mixed public row constants and a per-process seed into `FxHasher`; because FxHasher's seed is additive, attacker-controlled address differences still produced predictable key-pair collision families. The address-persistent SNAT selector used a fixed public salt with FxHasher, making its source-IP-to-pool-slot mapping predictable offline as well.

## What changed

- Replaced both SYN-rate hash paths (IP and IP+destination-port) with `HotPathSeededState` SipHash, preserving each row's independent domain, per-process stability, fixed sketch capacity, and index mask.
- Replaced address-persistent SNAT pool-index hashing with the process-keyed SipHash builder. The per-source selection remains deterministic within a process; existing allocated sessions/leases are unaffected. A new allocation after process restart or on another HA node can select a different pool address, unlike the prior public fixed mapping.
- Added regression coverage for v6 s3 collision families under pinned seeds, seed-sensitive/stable mappings, pool bounds, and existing per-source stickiness / allocation selection.

## Validation

- Not run by this implementation worker. Main integration should run the complete `xpf-userspace-dp` test suite and targeted `screen::syn_rate` and `nat` tests, then report actual results here.

## Risk

SipHash costs more per source selection than FxHash. The address-persistent fallback mapping is now node-local and per-process; a failover's newly allocated source may choose another pool address. Existing active allocations are not moved by this selector change. Confirm this is acceptable against the HA/address-persistence contract during integration review.
