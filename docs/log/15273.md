# #15273 — configstore boot-migration / commit-confirmed recovery edges (C01-01)

- **Timestamp**: 2026-10-19
  - **Action**: defer the durable #10826 api-auth `active.json` rewrite while
    `confirm.json` is present but unreadable, so the retained #8566 record is
    not stale-dropped on the next boot; accept the migration staging record's
    exact OldHash→NewHash pair as a generation alias in confirm recovery.
  - **Files**: `pkg/configstore/store_persist.go`,
    `pkg/configstore/api_auth_migration_confirm_unreadable_15273_test.go`,
    `pkg/configstore/confirm_recovery_read_failure_8566_test.go`,
    `pkg/configstore/README.md`, `docs/log/15273.md`.

## Defect

Three coincident conditions: (1) upgrade from a pre-#10826 build carrying
plaintext api-auth in `active.json`, (2) a pending commit-confirmed window,
(3) `confirm.json` unreadable on the migration boot (transient read/decrypt
fault; the #8566 retain-and-report path).

On boot 1, `migrateActiveAPIAuthSecrets` swallowed the `ReadConfirm` error
(`rec = nil`), so no rebinding happened, yet it still rewrote `active.json`
to the hashed generation. Recovery in the same boot set
`confirmRecoveryReadFailed` and retained the file. On boot 2, once the fault
cleared, `ReadConfirm` returned the record binding the OLD hash, but both
`activeHash` and `rawActiveHash` were the migrated hash, so `matchesActive`
failed and `recoverPendingConfirmLocked` dropped the record via
`stale_confirm_recovery`. The unconfirmed config became permanent and the
degraded signal disappeared with the deleted file.

## Fix

- `migrateActiveAPIAuthSecrets` now reports `confirmReadFailed` (ReadConfirm
  error AND `confirm.json` present on disk; a stat error other than
  not-exist also counts as present, failing closed). In that case it keeps
  the hashed tree in memory only (`tree.Children = hashed.Children`, so the
  compiled config carries verifiers this boot) and returns
  `migrationDeferred=true` without writing `active.json`; the
  PreviousHash finalize write is likewise skipped.
- `Load` skips `convergeAPIAuthMigrationStaging` while deferred, so the
  staging record and the pre-migration rollback-manifest binding survive
  for the next boot instead of being rebound to the in-memory hash and
  deleted (which previously also made the following boot fail staging
  consistency once the rollback sidecar was rebound while disk stayed old).
- `recoverPendingConfirmLocked`'s `matchesActive` additionally accepts the
  staging record's exact `OldHash`→`NewHash` pair (either direction) — as
  defence-in-depth for a crash between a future durable rewrite and staging
  convergence. An unrelated generation still matches neither side and is
  stale-dropped (#5835).
- Rollback-slot hashing/staging still runs while deferred (those bytes must
  not stay plaintext and do not change the guarded generation).

Deliberate trade-off (named in the issue's fix direction): legacy plaintext
credentials remain in `active.json` (0600, already on disk pre-upgrade)
until a boot that can read the record; the alternative silently destroys
the rollback safety net. With no confirm file, or a readable record, the
migration is byte-identical to before.

## Verification

  base — boot 1 rewrites `active.json`, boot 2 logs
  `ignoring a stale pending commit-confirmed record on boot… #5835` and
  stale-drops the record, so the live-window cell fails
  `IsConfirmPending` and the expired cell reports
  `did not roll back to the confirm record PrevTree`. The cells exercise
  the exact mechanism: valid record bytes on disk, a transient
  `rbReadBoundedFile` fault scoped to `confirm.json` on boot 1, fault
  cleared on boot 2.
- **GREEN**: both cells pass with the fix (live window re-armed; expired
  window rolls back to the record's PrevTree and removes the record).
- **Controls**: `TestBootMigrationNoConfirmStillRewritesActive15273` (no
  confirm file → durable rewrite unchanged) and
  `TestBootMigrationReadableConfirmStillRebinds15273` (readable record →
  existing #10826 rebinding path) pass.
  `TestBootReadFailureWithLegacyAPIAuthIsNonfatal_8566_10826` was updated
  to the new contract: `active.json` keeps the pre-migration generation
  while the record is unreadable, in-memory verifiers still work, and the
  #8566 degraded signal is unchanged. A permanently-corrupt record simply
  re-defers each boot (Load still succeeds, degraded) — no worse than the
  pre-fix plaintext exposure, which also persisted until operator action.
- Main should run: `go test ./pkg/configstore/ -count=1` (full package).

## Risk

- A store whose `confirm.json` is permanently corrupt AND whose active
  carries legacy plaintext api-auth will keep plaintext in `active.json`
  across boots until the operator resolves the record (arm/confirm/plain
  commit clears the #8566 state). This is the issue-sanctioned deferral;
  the credentials were already plaintext on disk before the upgrade.
- In-memory-only hashing means a crash before the next boot re-runs the
  migration from the same pre-migration bytes — idempotent, since
  `HashAPIAuthSecrets` on already-hashed values is a no-op (boot 2 of the
  readable control proves convergence).
