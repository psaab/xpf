# Issue #14432 — Garbage `conflict-policy` takes the UNGUARDED delete branch in `sendRemoveForward`

## Why

`rfc2136Updater.sendRemoveForward` (`pkg/ddns/backend_rfc2136.go`) branched
on the conflict policy as: `replace-owned` → the DHCID-guarded delete
(value-dependent "DHCID matches OURS" prerequisite, A/AAAA + DHCID removed
together); **anything else → `sendRemove`, a plain exact-RR delete with no
ownership prerequisite at all**. `policyFromConfig` (`pkg/ddns/manager.go`)
only defaulted the empty string, so any typo that survived to the backend —
`skip-existng`, `none`, `skip_existing`, a case/padding variant — silently
took the unguarded branch on lease release and could delete a third party's
record (the #2648/#2660 boundary breach class, re-opened by a typo on the
delete side).

The strict commit path already rejects such values via the schema enum
(`conflict-policy` in `pkg/config/schema_system.go`), but the tolerant
load / peer-sync path (`CompileConfigLenient` / `Store.Load` /
`Store.SyncApply`, #1960 no-brick) downgrades that reject to a warning, and
direct programmatic callers bypass it entirely — with no runtime guard, the
garbage value was honoured end to end on the delete path.

Sibling #14429 (DR16-H8) is the same garbage value on the INSERT side
(`sendAdd`'s bare-Insert fallthrough). The two share the root — no runtime
validation of `conflictPolicy` — so this fix introduces the shared
`validConflictPolicy` SSOT; the regression cells stay distinct per claim
(this issue's fixture drives `DeleteLease`/`sendRemoveForward`, #14429's
drives the ADD). At the time of this fix #14429 was still in flight in its
own worktree with an identical `validConflictPolicy` helper and the same
constructor gate; whichever lands second will rebase onto a single copy.

## What

- `pkg/ddns/manager.go`: new `validConflictPolicy` SSOT (exactly
  `replace-owned` | `skip-existing` | `strict-fail`; empty is invalid
  there because `policyFromConfig` has already defaulted it).
- `pkg/ddns/backend_rfc2136.go`:
  - `newRFC2136Updater` refuses construction with a non-empty invalid
    policy (error names the value and the valid set). The manager's
    `resolveFamilyUpdater` already falls back to the no-op updater on a
    factory error, so no UPDATE is emitted and no ownership is recorded
    that cycle. Empty stays allowed for policy literals that leave it
    unset (Surface A sets `replace-owned` explicitly; `policyFromConfig`
    defaults an unset config value before construction).
  - `sendRemoveForward` defence-in-depth: an updater built outside the
    constructor (struct literal) with an invalid policy returns an error
    instead of taking the unguarded plain-delete branch. Valid
    `skip-existing` / `strict-fail` keep the plain exact-RR delete
    byte-for-byte; `replace-owned` keeps the DHCID-guarded delete
    (including the #2700 `keepDHCID` partial-teardown behaviour).
- Regression tests (`pkg/ddns/conflict_policy_delete_14432_test.go`):
  - `TestRFC2136GarbageConflictPolicyRefusesDelete14432` — garbage values
    (`skip-existng`, `none`, `skip_existing`, `replace`, `SKIP-EXISTING`,
    `" replace-owned "`) must refuse the DELETE (construction error naming
    the value, or a delete error) with no wire DELETE emitted, and a
    seeded third-party record must survive.
  - `TestRFC2136GarbageConflictPolicyRefusesDeleteDirectUpdater14432` —
    a directly-built updater with `bogus-policy` calling
    `sendRemoveForward` directly must error and leave the victim record.
  - `TestRFC2136ValidConflictPolicyDeletesUnchanged14432` — controls:
    `skip-existing`/`strict-fail` plain deletes remove the exact tuple;
    `replace-owned` guarded delete removes own A+DHCID and counted-skips
    a foreign DHCID owner's name; the empty default resolves to
    `replace-owned` and deletes via the guarded path.

## Validation

- RED (pre-fix, `origin/master` 59fa41531): both garbage-delete tests fail
  — `DeleteLease succeeded (unguarded plain delete)` for all six garbage
  spellings, and the direct-updater `sendRemoveForward` succeeds; the
  valid-policy controls pass.
- GREEN (post-fix): `go test ./pkg/ddns/ -run
  'TestRFC2136GarbageConflictPolicy|TestRFC2136ValidConflictPolicyDeletesUnchanged'
  -count=1` passes; full `go test ./pkg/ddns/... -count=1` passes;
  `go build ./...` and `go vet ./pkg/ddns/...` clean.

## Risk

Fail-closed direction only: a garbage policy now refuses to withdraw (and,
via the shared constructor gate, to publish) instead of deleting
unguarded — records may linger until the operator fixes the typo, which is
the safe side (a lingering record is visible; a deleted third-party record
is data loss). Valid policies, the empty default, Surface A
(`replace-owned` literal), and the #2700 shared-DHCID teardown are
unchanged, pinned by the control cells above and the existing
`TestPartialDualStackTeardownKeepsSharedDHCID` / replace-owned lifecycle
tests in the full suite.
