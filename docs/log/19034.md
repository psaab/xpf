- **Root cause.**
  - Each move runs a same-plan `apply_snapshot`, which goes through
    `refresh_runtime_snapshot_inner`.
  - That calls `bulk_replace_neighbors(&old_manager_keys, &[])`
    (`coordinator/snapshot_refresh.rs:388`). It removes every
    manager-owned neighbor from the dynamic map with nothing reinserted,
    which bumps the #3048/#5147 epoch of every shard that held one.
  - The new snapshot carries the same neighbors, and lookups read the
    static table first, so no resolution changed.
  - The packets still queued with the left view run in a #18560 held pass.
    Its first packet per flow sees a stale shard. The hit stage evicts the
    entry and the packet is dropped (a held pass cannot re-resolve).
  - The flow's remaining queue then finds no entry: whole-backlog loss, one
    iperf3 stream at a time.
- **Design (F1)**: a held pass re-checks its own flow when its shard is
  stale. The next hop must resolve to the cached MAC in the stamped view's
  static table AND in the live dynamic map; each entry is either absent or
  equal, and at least one must be present. Then the shard bump belonged to
  another neighbor, and the HA decision revalidation judges the entry as
  usual. A changed or vanished neighbor still evicts and drops. Ordinary
  passes are unchanged.
  Least-sure step: that "dynamic present" catches a genuine MAC change
  while the retained view's static table still names the old MAC. Pinned by
  `held_pass_drops_when_the_live_neighbor_mac_changed_19034`, and killed by
  a static-first mutant.
- **Not in this change (reported)**:
  - F2: stop the spurious bump at its source (bump only for manager keys
    whose resolution changes). This is the #3048 area.
  - AHEAD at FIB-only bumps.
  - NEWER in-batch reseeds.
  - The new WAN owner has no real default route in its helper FIB for
    1.7-5 s after a move.
