# #16592: gate targeted failover on the applied ACK

- **Timestamp**: 2026-10-25
- **Why**: A remotely requested owner demotion advertises secondary-hold
  before its fence verdict arrives. The requester used that heartbeat as
  permission to promote even before an applied ACK, or after reporting an
  ACK failure/timeout to the operator. The request-ACK error exits also
  omitted the #15164 abort marker and bound abort; the timeout returns
  discarded the request ID.
- **What**:
  - `electRG` holds a pending request on a secondary-hold heartbeat until
    the post-applied-ACK override is installed. The check precedes weight
    and dual-resign recovery, not just the transfer-out arm.
  - An aborted-request marker blocks all promotion arms. Merely skipping
    "Peer transfer out" still lets a higher-priority non-preempt requester
    promote through ordinary election on the same stale hold. An already
    primary requester yields; an existing manual hold remains intact.
    Existing marker expiry on non-hold heartbeats, reset, new acknowledged
    transfer, peer loss and RG removal is unchanged.
  - Both request paths abort on request-ACK errors with a nonzero reqID.
    `SendFailover` and `SendFailoverBatch` preserve that ID on timeout;
    batch ACK errors preserve it too. Local rejection/send failure still
    returns zero. No new wire format or timeout setting is introduced.
  - A failed owner fence invokes the existing reqID-bound owner abort
    callback before sending the failed ACK. The owner clears its hold and
    lease and re-elects; stale aborts cannot clear a newer request's lease.
  - Corrected the #5640/#6177/#6371 comments and the session-sync and
    cluster documentation to describe both the ACK gate and election gate.
