# #9813: a fabric overlay re-created outside an apply is left outside vrf-mgmt

- **Timestamp**: 2026-09-11 10:58 PDT
- **Action**: Triaged the issue read-only on master `8a0919262`, then prototyped the fix locally,
  waiting on the lead's confirmation of the pick and scope.
  - Confirmed: `ensureFabricIPVLAN` creates the IPVLAN with only a name, a parent and L2 mode. The #6791
    `reassertFabricIPVLANOnce` re-creates a missing overlay through `fabricEnsureFn`, and
    `missingFabricOverlays` never looks at `MasterIndex`. The management-VRF set is bound only by apply
    steps 0b and 2.7. Session sync binds its sockets to the VRF device (`pkg/cluster/sync_conn.go`).
  - Apply order: `applyFabricIPVLAN` runs before step 2.7, so an overlay created inline is bound by the
    re-bind. The deferred `OnXSKBound` callback can run after it, and so can the re-assert loop.
  - Open PR #9851 (`fix/9819-vrf-miss-terminator`) changes `pkg/routing` only; this change uses the
    existing `BindInterfaceToVRF` API and touches no `pkg/routing` file.

## Tenant half: routing-instance list members

- **Timestamp**: 2026-09-11 18:22 PDT
- **Action**: Implemented the second half of the issue, which closes it. The fabric/management half landed as
  PR #9863 (`Refs #9813`), and the lead directed that the tenant half be done in this lane on the same issue
  rather than filed as a successor.
  - `riMemberVRFReassertLoop` is an always-on 30 s owner of routing-instance interface-LIST member VRF
    membership. `reassertRIMemberVRFOnce` keeps the store read, the cheap gate and the #4001 applySem
    discipline; `rebindRIMembersOutsideTheirVRF` is the pure pass, which the cells drive with a config
    literal exactly as the #6805 cells drive the apply's bind loop.
  - It binds ONLY a member whose master is not its VRF. `BindInterfaceToVRF` logs at Info on every call, so
    re-running the apply's bind loop on every tick would log on every tick of a healthy node and re-drive
    netlink for nothing.
  - It leaves a tunnel with its own `routing-instance` stanza alone. That is the tunnel manager's claim
    (`reconcileVRFClaimLocked` case 1), recorded in `appliedRI` only from its own successful bind, so a
    daemon-side bind would move the master with the claim bookkeeping left behind. List members are step 0a's,
    per the #1884 case-2 veto.
  - Names resolve through `riMemberLinuxName` with `cfg.TunnelNameMap()`, exactly as step 0a resolves them,
    so the loop and the apply reason about one name set (the #6805 reason for sharing one implementation).
  - A member absent on this chassis is skipped silently, matching step 0a's best-effort treatment.
  - Cells: a member outside its VRF is re-bound; one already in it draws no bind; forwarding instances and
    absent members are skipped; a stanza tunnel is left alone (with a control that the fixture's tunnel is
    actually collected, or the skip would be vacuous); an AST pin that `Run` starts the loop; a source-order
    pin for the applySem discipline; and a kernel cell in a private netns covering the apply-left-unbound bind,
    an out-of-band nomaster, and a no-op second pass.
  - All 14 #9813 cells pass under `unshare -rn` with no skips; unprivileged, the two kernel cells skip.
