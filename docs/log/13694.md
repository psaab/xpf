# Issue #13694 — reject NPTv6 IIDs that adjust to all-zero

## Why

`translate_inbound_result` applied the inverse checksum adjustment only after
checking the incoming IID for all-zero. A nonzero external IID could therefore
be adjusted into the reserved all-zero IID and translated instead of refused.
The outbound function had the symmetric gap: a nonzero internal IID could
adjust into all-zero. Both violate the RFC 6296 §3.7 discard requirement.

## What

Keep the input all-zero checks, then check the transformed IID after applying
the adjustment in both directions. A refused translation still leaves the
caller address untouched because the rewrite is held in a local word array.
Regression tests cover the inbound and outbound adjustment-to-zero cases.

## Validation

- **RED:** With the two post-adjustment guards removed, the two new regressions
  both failed: they observed `Translated` instead of `Untranslatable`.
- **GREEN:** `cargo test --manifest-path userspace-dp/Cargo.toml
  'iid_adjusting_to_all_zero_is_untranslatable_13694' -- --nocapture` passed
  both new regressions.
- **Affected module:** `cargo test --manifest-path userspace-dp/Cargo.toml
  'nptv6::tests::' -- --test-threads=1` passed 45 tests.
- **Build caveat:** On the unmodified source, Cargo test fails before tests
  because `afxdp/session_glue/mod.rs` imports
  `promote::purge_translated_synced_hit` unconditionally although its definition
  is `#[cfg(test)]`-gated. For focused and module test execution only, the
  import was temporarily split under `#[cfg(test)]`, then restored; that
  unrelated workaround is not part of this change. The full-crate fmt check
  also reports pre-existing formatting drift across unrelated files; the
  changed test/source sections introduce no rustfmt diffs.

## Risk

An IID that was previously translated despite mapping to all-zero is now
refused, as required. All other address translation paths are unchanged.
