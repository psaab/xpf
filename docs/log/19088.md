## A finding of my own: the leader thread is wedged, not terminated

The mutant run first showed `TestReleaseKeepsAThreadItCannotRestoreLocked19088`
failing under G7, which does not touch Release. The thread it kept locked was
the thread-group leader (tid == pid). When a goroutine exits locked on the
main thread, the Go runtime wedges that thread instead of terminating it. The
leader therefore stayed in the private namespace, every later census saw it,
and `/proc/<pid>/ns/net` pointed there.

- The cells now run their goroutines off the leader (`offLeader19088`). A
  goroutine that finds itself on the leader keeps it locked while a fresh
  goroutine does the work.
- After the fix: 30 repetitions of the testguard cells passed.
- For production use this is still safe: a wedged leader is never reused.
  Release's doc says so, and `Run` reports the wedged thread, because a
  restore failed.
