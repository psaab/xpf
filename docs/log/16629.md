# RPM test scoped to a forwarding instance is rejected at commit (#16629)

- **Issue**: #16629 (R3-A49-01).
- **Cause**: The #2496 commit gate (`validateRPMRoutingInstanceStrict`)
  checked only that an RPM test's `routing-instance` exists. The runtime
  binds the probe socket to `vrf-<ri>` (`probeOpts` in `pkg/rpm/rpm.go`),
  and the daemon deliberately creates no VRF device for a forwarding
  instance (`daemon_apply_interfaces.go` skips VRF creation). A test
  scoped to a forwarding instance — the documented multi-WAN/FBF instance
  type — therefore committed clean, held `unknown` with zero probes sent
  forever, and any `services ip-monitoring` policy matched on it could
  never inject its preferred route. The #2496 regression test pinned that
  exact forwarding config as accepted.
- **Change**: `validateRPMRoutingInstanceStrict` in
  `pkg/config/compiler_services.go` now also rejects, on the strict path,
  a test whose routing-instance names a forwarding instance, with an
  error naming the instance and its forwarding type / missing VRF device
  and pointing at the fixes (use a `virtual-router`/`vrf` instance, or
  set `destination-interface`). The existing lenient flag downgrades it
  to a `rpm routing-instance` warning on load / peer-sync (#1960
  no-brick), so a persisted forwarding-scoped test still boots and holds
  state. A test that also sets `destination-interface` is accepted even
  with a forwarding routing-instance: `probeOpts` gives the egress-device
  pin precedence over the VRF fallback, so it never binds the nonexistent
  `vrf-<ri>`. Gate callsite (`compiler_uniformgates_routing_rib_rpm.go`)
  and the lenient-flag doc (`compiler_opts.go`) updated to match;
  `docs/multi-wan.md` now states the VRF-instance requirement and the
  two ways to probe a forwarding (FBF) uplink.
- **Regression coverage**: `pkg/config/compiler_rpm_routing_instance_2496_test.go`
  — `TestRPMRoutingInstanceForwardingStrictRejects16629` (forwarding cell
  rejected, error names the instance, `forwarding instance`, and
  `no VRF device`) and `TestRPMRoutingInstanceForwardingLenientWarns16629`
  (lenient path warns, naming the forwarding type). RED pre-fix is the
  job `bg_8774` run on this worktree before the gate change: both tests
  failed (`CompileConfig accepted ... want strict reject`; `warnings=[]`).
  `TestRPMRoutingInstanceConfiguredAccepted` now uses a `virtual-router`
  instance as the positive control (plus `vrf`, omitted-type, and
  forwarding+`destination-interface` cells) and the empty-instance cell is
  unchanged. `pkg/config/compiler_rpm_scoped_hostname_2493_test.go`
  fixtures that used a forwarding ISP-B as an incidental scope were moved
  to `virtual-router` so they keep exercising the #2614 scoped-hostname
  behaviour rather than the new gate. The `TestRPMConfig` fixture in
  `parser_ast_test.go`, which used a forwarding `att-vr` as incidental
  RPM routing-instance coverage, likewise moved to `virtual-router`.
- **Risk / residuals**: Strict commits that previously accepted a
  forwarding-scoped RPM test without `destination-interface` now fail —
  that is the intended operator-visible break; such probes never ran, so
  no working failover is lost, and the error names both fixes. The
  alternative runtime implementation (SO_MARK + fwmark rule into the
  forwarding instance's table) was not built: the issue's acceptance
  allows the commit rejection, and the reserved probe-pin band is keyed
  to next-hop pins, not instance tables. Runtime behaviour for a
  leniently loaded forwarding-scoped test is unchanged (holds state).
