# #15027 — Render `pre-shared-key hexadecimal` as raw bytes and reject unknown qualifiers (A16-04)

## Summary

`set security ike policy <p> pre-shared-key hexadecimal <hex>` committed
cleanly but the hex digits were stored and rendered as an ASCII secret
(`secret = "6162636431323334"`), so strongSwan derived the ASCII bytes
and could never authenticate against a peer holding the same Junos hex
key (whose key material is the hex-decoded bytes). Any qualifier word
was accepted the same way, and the block spelling
`pre-shared-key { hexadecimal ...; }` dropped the key entirely.

- Issue: psaab/xpf#15027 (A16-04, 3-way MATERIAL in
  `research-work.AdQvt1jMKw`). Base: current `origin/master` at lane
  creation.

## Defect (present at base)

`pkg/config/compiler_ipsec.go`, IKE-policy `pre-shared-key` case:
`if len(p.Keys) >= 3 { pol.PSK = Secret(p.Keys[2]) }` — Keys[1] (the
qualifier) was never read; the children arm only recognised
`ascii-text`, so a `hexadecimal` block child set nothing. The schema
(`pkg/config/schema_security.go`) declares `pre-shared-key args: 2`
with no qualifier typing. `pkg/ipsec/policy.go` always rendered
`secret = "<value>"`; strongSwan needs a `0x` prefix for hex bytes.
The VPN-level form (`security ipsec vpn ... pre-shared-key`, args:1)
took `nodeVal` verbatim, so a qualified VPN spelling collapsed the
qualifier into the stored secret.

Base probe (flat set form, since removed): `hexadecimal`,
`bogus`, and `ascii-text` all committed with `PSK="6162636431323334"`;
hex values `616` / `zz` / `0x6162` all committed verbatim; the block
hexadecimal form failed only via the unrelated #14139 empty-PSK gate
because the key had been dropped.

## Fix

- `pkg/config/types_security.go`: `IKEPolicy` and `IPsecVPN` gain
  `PSKHex bool` (the value in `PSK` is hex digits to render as raw
  bytes) and `PSKQualifierInvalidSpec string` (`json:"-"`, mirrors
  `DHGroupInvalidSpec` #9919) recording an unknown qualifier or a
  malformed hex value for the strict gate.
- `pkg/config/compiler_ipsec.go`: `classifyPSKQualifier` switches on
  the qualifier — `ascii-text` as today, `hexadecimal` validates
  even-length hex (`validHexPSK`) and sets `PSKHex`, anything else
  records the qualifier as the invalid spec. `pskQualifierValue`
  resolves the qualifier/value across the packed (Keys≥3), flat
  args:1-split (qualifier on Keys, value as child), and block
  (qualifier-named child) shapes. Both the IKE-policy and VPN-level
  cases use it; the bare VPN form (`pre-shared-key <key>`) is
  unchanged ASCII.
- `pkg/config/compiler_validate_strict_ipsec_psk_qualifier_15027.go`
  (new): `validateIPsecPSKQualifierStrict` hard-rejects an unknown
  qualifier or malformed hex at strict commit, wired in
  `runUniformGatesIPsecEvent` with the new `lenientIPsecPSKQualifier`
  opt (tolerant load / peer-sync warns and keeps the config). The
  malformed-hex error deliberately does not echo the key material.
- `pkg/ipsec/policy.go`: the effective secret (VPN PSK, then
  IKE-policy fallback) carries its `PSKHex` flag; a hex-flagged value
  renders unquoted as `secret = 0x<hex>`, ASCII keeps the quoted
  #2126-escaped render. A hex-flagged value that is not valid hex
  (directly constructed / peer-synced) is skipped by name like every
  other malformed-PSK class (`validHexPSKRender` in `crypto.go`), so
  it never renders as ASCII.

NOT changed: `$9$` handling (`normalizePSK` still applies first;
a `$9$` value is never hex-classified from config because the
compiler only sets `PSKHex` on the `hexadecimal` qualifier), the
AST redactor (already preserved the qualifier), and the schema
arity (args:2 / args:1 already describe the token counts; the
compiler + strict gate own qualifier validation so the tolerant
path can warn instead of failing to load).

## Regression (RED → GREEN)

  `6162636431323334` (the issue probe) compiles hex-flagged;
  `ascii-text` control stays ASCII; `bogus` refused at commit

  `CompileConfigLenient`; malformed hex (`616`, `zz11`, `0x6162`)
  refused without echoing the value; block hexadecimal carries the
  key; block bogus refused; VPN-level hexadecimal hex-flagged and

  ignored / key dropped).

  no orphan secret; the end-to-end cell drives the authored spelling
  through `CompileConfig` → `renderConfig`.

## Risk

- A config that (ab)used an unknown qualifier (e.g. `pre-shared-key
  foo <key>`) previously committed with `<key>` as the ASCII secret;
  it is now refused at commit and warned on load. That spelling was
  never Junos-legal, and the key it produced was almost certainly
  not what the operator intended.
- Hex-keyed tunnels change rendered bytes (deliberately): they now
  authenticate against hex peers and stop matching a peer that had
  compensated by configuring the ASCII digits.
