# #16498 — ScanCore kept growing per-source destination sets to 1024 after the verdict fired at 10

- **Timestamp**: 2026-10-24
- **Context**: `ScanCore::check`
  (`userspace-dp/src/screen/scan.rs`) fired detection at the fixed
  `SCAN_DETECT_COUNT` (10) distinct destinations, then kept inserting
  distinct destinations into a per-source `FxHashSet` up to
  `MAX_UNIQUE_PER_SOURCE` (1024). The window reset's `clear()` retained
  the bucket allocation and the least-suspicious eviction preserved the
  fullest sets, so a spoofed-source new-flow flood (session-miss hook,
  pre-policy) could pin ~144 MiB (ip-sweep) + ~24 MiB (port-scan) of heap
  per worker per screened zone (~1 GiB at 6 workers, both screens),
  ~100x what detection requires, and paid hashing for destinations
  11-1024 that carry no verdict information.
- **Fix**: the recorded destinations now live in an inline
  `[Option<T>; SCAN_DETECT_COUNT]` buffer inside `SrcEntry` (with a
  `count` and `insert_unique` / `distinct_count` / `is_empty` /
  `reset_entries` accessors) — no per-source heap allocation, nothing
  retained across a window reset. `MAX_UNIQUE_PER_SOURCE` now equals
  `SCAN_DETECT_COUNT` (compile-time guard updated), a distinct
  destination past the count is not stored, counts once on the existing
  `skipped_pressure` signal (mirroring the old over-1024 path), and the
  verdict — already true — is still evaluated, so no gate weakens.
  Eviction's least-suspicious ordering and cleanup's empty test now read
  `distinct_count()` / `is_empty()` (counts are `<= 10`, semantics
  unchanged). The scan.rs module doc and the session README now publish
  the per-worker, per-zone bound: saturated records are 200 B
  (ip-sweep `SrcEntry<IpAddr>`) / 64 B (port-scan `SrcEntry<u16>`),
  i.e. at most 4096 x (200 + 64) B ~= 1.03 MiB per worker per zone for
  both screens' per-source records, on top of the unchanged source-axis
  index overhead.
- **File(s)**: `userspace-dp/src/screen/scan.rs`,
  `userspace-dp/src/session/README.md`, `debian/changelog`,
  `docs/log/16498.md`
- **Validation**: new `single_source_fanout_capped_at_detect_count_16498`
  cell drives one source with 2000 distinct destinations in one window
  for both instantiations: detection fires exactly at the 10th, the
  recorded count caps at 10 (RED on the pre-fix 1024-entry heap set),
  recorded bytes stay inline, each post-count distinct destination
  counts once as pressure, and a repeat of a recorded destination does
  not. New `per_source_state_capped_at_detect_count_16498` asserts
  `MAX_UNIQUE_PER_SOURCE == SCAN_DETECT_COUNT`, the measured record
  sizes (200 B / 64 B), and that a saturated 4096-source zone holds
  exactly sources x one fixed-size record. The existing bound cells
  (`per_source_unique_entries_bounded`,
  `memory_caps_bound_state_under_wide_window`) were re-anchored to the
  new cap. Targeted tests: `cargo test --bins screen::scan` 34/34 green
  and the full `screen::` filter 370/370 green (includes the
  `screen/tests.rs` bounded-state cells).
- **Residual**: component level only, matching the finding's evidence;
  helper RSS/OOM on a real appliance was not demonstrated by the report
  and is not measured here — the fix removes the attacker-driven heap
  axis entirely rather than tuning its size.
