# Issue #12640 — compile every duplicate to-zone block

## Why

`compilePolicies` used `FindChild("to-zone")` for each source-zone node. The parser
preserves repeated hierarchical blocks as sibling AST nodes, so
`from-zone { A { to-zone { B { ... } } to-zone { C { ... } } } }` compiled only
A->B and silently discarded the second pair, including its deny policy.

## What

- Iterate all `FindChildren("to-zone")` siblings and append each destination
  pair in declaration order.
- Add `TestDuplicateToZoneBlocksBothCompile12640` and the order-swapped control.
  The cells assert both A->B permit and A->C deny pairs survive compilation.
- No schema or runtime behavior was changed.

## Validation

- RED before the fix: both regression tests compiled only one zone pair instead
  of two.
- GREEN after the fix: `go test ./pkg/config -run '^TestDuplicateToZoneBlocks' -count=1`
  passed.
- `go test ./pkg/config -count=1` failed on unrelated existing config-package
  failures: stale inventory census (`TestInventoryDropShapeMatchesTheLiveCensus8662`),
  API auth expiry expectations (`TestMultiLeafSelfRepeatIsRefused9027`,
  `TestLegitimatelyNamedObjectIsAccepted9029`, `TestElidedQuotedValueKeepsItsQuote8921`,
  `TestSystemConfigWebManagementEnhanced`, `TestSystemConfigSetSyntax`), a
  routing-instance control (`TestPackedRoutingInstanceSurvives8787`), and timed
  out after 10 minutes in `TestSlotEscapeSweep`. No failure referenced this
  change. The full-package run prevented the chained gofmt check; that check is
  run separately.

## Risk

Configurations with duplicate `to-zone` siblings now compile every authored
pair; previously only the first sibling was represented. Pair order remains the
source declaration order. No other policy behavior is changed.
