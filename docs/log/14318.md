# #14318 — Cross-zone FIB reroute leaves reverse companion ingress_zone stale

## Defect
`SessionTable::revalidate_forwarding_resolution` persisted only
`decision.resolution`/`forwarding_generation`/`owner_rg_id`. After a
permitted cross-zone reroute (lan→wan1 becomes lan→wan2) or egress
re-zoning, forward `metadata.egress_zone` and reverse companion
`metadata.ingress_zone` stayed at wan1. Replies arriving on wan2 hit
`session_hit_authority` as Foreign (`arrival != ingress_zone`) and
`foreign_hit_verdict` judged the reversed pair (wan2→lan), dropping
100% of replies under the normal lan→wan2 permit / wan2→lan deny
stateful policy (`foreign_authority_drops`).

## Fix
- `session/mod.rs`: new `revalidate_forwarding_resolution_with_egress_zone`
  (old fn delegates with `None`). When `Some(new_zone)`: forward entry
  `egress_zone = new_zone`, reverse companion `ingress_zone = new_zone`,
  moved legs' vintage checks cleared. Handles forward-hit, reverse-hit
  (inverted via NAT), degenerate self-reverse, missing companion.
  New `rebind_forward_egress_zone` for zone-only rebinds.
- `shared_ops/lookup.rs`: `DeferredForwardingRevalidation.new_egress_zone`.
- `session_glue/resolve.rs`: compute `new_egress_zone` (live egress zone
  for locally-forwarding routes, recorded zone for FabricRedirect, else
  None); persist via new API + sync snapshot metadata.
- `poll_descriptor/mod.rs`: same persist at descriptor site.
- `poll_descriptor/policy_revalidation.rs`: reverse NoLocalEntry and
  Stale permit arms persist with new zone; forward-hit Permit arm calls
  `rebind_forward_egress_zone` (#9384 re-zoning: stored egress ifindex
  now in a new zone, resolution otherwise unchanged).
- `foreign_hit_verdict` direction unchanged: lanes refuted that half;
  with zones fresh, legitimate replies are Owner and never reach it.

## Notes
Flow-cache/BPF-conntrack/shared-map zone restamp on reroute follows the
existing deferred-route pattern (session table is authority; cache
entries are generation-stamped and re-seeded on miss).
