# 10216 — Reconcile owner-planned MTU in the fabric actuator

## Boundary

#9985 moved MTU ownership into the resolved-Linux-netdev planner. It retained
configured MTU for unusable tunnel devices that routing will not create, while
preserving #9927's fabric-owner `pd.mtu == 0` behavior. The remaining gap was
in the actuator: configured fabric MTU values above the 9000 floor were ignored,
and an absent planner-owned device could be soft-skipped with no MTU diagnostic.

## Fix

- `ensureFabricIPVLAN` now receives the configured fabric MTU through the apply,
  deferred-XSK, VRF rebind, and reassert paths.
- The fabric target is `max(9000, configured MTU)`; parent and overlay links are
  reconciled to that target.
- Every reconciliation performs a fresh netlink readback. Set, lookup, and
  readback mismatches are returned as errors instead of warn-only success. The
  existing bounded apply retries and terminal `errors.Join` therefore reject a
  fabric whose configured MTU cannot converge.
- The planner records whether the merged physical desired state contains an
  authored MTU. An absent netdev with such a plan records an
  `MTUGradeLookupFailed` diagnostic naming the configured value and the missing
  netdev. The materialized Linux default (1500) remains silent, and
  fabric-owned local members remain silent because #9927 intentionally leaves
  their MTU to the fabric actuator.
- The target is applied in direction-aware order: an existing overlay is
  lowered before its parent on a configured-MTU decrease, while increases and
  new overlays reconcile the parent first because IPVLAN cannot exceed it.
- Lookup failures remain `MTUGradeLookupFailed` diagnostics even when netdev
  presence is unknown; their detail says lookup failed rather than claiming
  absence.

## RED then GREEN evidence

- Before the absent-owner call was added, the absent unusable-tunnel and
  explicit-MTU cells returned zero MTU records despite a successful soft skip.
- With `fabricMTU10216` temporarily reverted to the pre-fix hard-coded floor,
  `TestFabricConfiguredMTUAboveFloorIsAppliedAndVerified_10216` failed because
  the configured target was 9000 instead of 9500.
- A parent-first-only transition probe fails when lowering a 9500 parent with a
  9500 IPVLAN still attached; the direction-aware transition cell now passes
  with writes ordered `[fab0 ge-0-0-0]`.
- Restored implementation: all seven `10216` daemon tests passed, including
  configured-MTU apply wiring, terminal refusal propagation, exact above-floor
  write plus fresh readback, safe decrease ordering, write failure, readback
  mismatch, and floor lower bound.
- The six absent-owner dataplane cells passed, including reversed zone-order
  merged-plan selection, unknown-presence lookup detail, and the #9927
  fabric-owner silence control.
