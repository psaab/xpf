# 10290 — NPTv6 RFC 6296 word selection and discard rules

## Boundary

NPTv6 `/64` translation previously always adjusted IID word 4. RFC 6296 §3.5 says a translator MUST inspect words in bits 64..79, 80..95, 96..111, and 112..127, choosing the first that was not initially `0xFFFF`. Section 3.2 says to discard an unmapped internal `0xFFFF` subnet (the section does not use RFC 2119 MUST language). Section 3.7 explicitly says an all-zero IID MUST be dropped for longer-prefix mapping.

The RFC text was verified from the primary source: <https://www.rfc-editor.org/rfc/rfc6296.txt>, §3.2, §3.5, and §3.7. The reviewer evidence scopes the `/64` all-ones IID edge separately: no IID word is available for the required selection, and the reserved-anycast note supports reporting it as untranslatable rather than forwarding unchanged; this is not an RFC 2119 MUST.

## Fix

- `Nptv6State` selects the first non-`0xFFFF` IID word for `/64` in both directions. The selected index is derived before prefix rewrite, and inbound uses the same index because a translated adjustment word is never left at `0xFFFF`.
- `/64` all-zero and all-ones IIDs return `Nptv6Translation::Untranslatable`. A non-neutral `/48` internal subnet word of `0xFFFF` returns the same explicit outcome; the existing #3233 neutral-pair exception remains a pure prefix swap. The all-zero behavior is the RFC §3.7 MUST; the all-ones behavior is the scoped reviewer edge, and §3.2's subnet behavior is a discard direction rather than an RFC 2119 MUST.
- The production inbound pre-routing, outbound permit, and missing-neighbor seed paths treat `Untranslatable` as a terminal recycle/drop, not as a prefix miss that can route unchanged or fall through to static/interface SNAT. Fragment probes classify the outcome as NAT-relevant, and embedded-ICMP reverse lookup refuses a prohibited quote.
- The historical boolean helpers remain as compatibility wrappers for helper-only callers; packet paths use the result-bearing APIs so the drop distinction cannot be lost.
