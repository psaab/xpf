# #9522 capped learned-route NoRoute disposition

## Problem

#8355 declines the entire learned-route import above a time-derived cap. #9054
restored kernel slow-path delegation for `NoRoute` while that cap flag was set,
so a destination the kernel could route but the helper did not import could
transit without zone policy, session, NAT, or screen. That accepted tradeoff had
no owner. A v26 helper also interprets the same snapshot bytes differently from
the fail-closed behavior required here, so the old protocol pairing had to be
fenced.

## Change

- Remove the capped-import early return from the shared NoRoute adjudication
  entry point. Capped and uncapped NoRoute frames now take the same policy
  path; a deny is downgraded to `PolicyDenied` and never reaches the delegated
  slow-path outlet. A policy `Permit` remains the exact delegation predicate.
- Keep `learned_route_import_capped` as diagnostic state, with the cap-build
  counter and policy-denial counter named in the operator diagnostic and
  Prometheus descriptions.
- Pin below-cap, exact-cap, and above-cap route-import behavior. Exactly
  `maxLearnedRoutes()` imports whole; only `> maxLearnedRoutes()` fires the
  cap.
- Bump the snapshot protocol from 26 to 27 in Go and Rust. A v26 helper would
  still delegate a capped NoRoute frame, so exact version equality must refuse
  the mixed pairing.
- Update the routing and dataplane architecture descriptions and the #9522
  regression cells. Historical #9054 logs remain historical records.
