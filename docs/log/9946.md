# 9946 — a failed post-link-cycle `rxvlan off` re-disable left the apply reporting success

## Reachability, settled first

The issue filed at High *"with that conditional stated"*, and named the deciding
check as its first acceptance item: whether the 1 Hz reconcile re-runs
`ensureRxVlanOff`. If it did, the exposure window would shrink to ~1 s and this
would degrade to a hardening note.

**It does not.** Measured at `origin/master` before any code was written:

- `ensureRxVlanOff` (`pkg/dataplane/compiler.go`) has exactly **one** production
  caller — `pkg/dataplane/compiler_iface.go`, inside the per-phys compile setup.
  Nothing else in the tree calls it.
- The only other `ethtool -K … rxvlan off` sites are the compile-time one it
  wraps and the warn-only post-cycle re-disable this issue is about.
- `pkg/dataplane/userspace/process_linkcycle.go:159` is **not** a third site — it
  is a comment citing the ethtool call as a *timing term*.
- The daemon's tickers are per-subsystem (DDNS, IPsec rebind, RA, HA reconcile);
  none re-runs the config apply. `applyConfigLocked` is reached from the boot
  load, `commitAndApply`, `commitConfirmedAndApply` and the HA `SyncApply` — all
  **event-driven**, none periodic.

So after a failed re-disable the NIC keeps stripping tags until the next apply
EVENT: an operator commit, a reboot, or a peer's config sync. Unbounded in
operator time. Per the issue's own severity rule, **High stands**.

The `rxVlanOffCache` refutation recorded on the issue — "a later commit re-gates,
because the cache is a per-compile field on `CompileResult`" — is sound and was
confirmed; it just does not shorten the interval, because nothing schedules that
next apply.

## Why it matters

`#5268` established the hazard and made it an activation precondition: the XDP
dataplane derives 802.1Q identity **solely** from the in-frame tag, so a NIC
whose RX-VLAN offload strips the tag into `skb->vlan_tci` (which XDP cannot read)
makes every tagged frame parse as `vlan_id=0`. `resolve_ingress_logical_ifindex`
then falls back to the PHYSICAL parent ifindex, which maps to the parent's zone —
untrusted VLAN traffic classified into a trusted zone.

`programRethMAC`'s link down/up cycle **resets the member NIC's ethtool
features**, so the offload comes back on exactly where #5268 said it must not be.
The re-disable that follows was warn-only, so the commit reported success.

## The fix

Three pieces, in the order that matters.

**1. The decision is now shared, because there are two enforcement points.**
`ClassifyRxVlanOffload` (`pkg/dataplane/compiler_rxvlan_classify_9946.go`)
reduces an `ethtool -k` result to `Absent` / `Off` / `NeedsDisable`, and both
`ensureRxVlanOff` and the new post-cycle path use it. The parse is the part with
a defect history — pre-#5268 it was `strings.Contains(line, "off")`, which
matches the feature NAME `rx-vlan-offLOAD` and so read *every* line as "off",
meaning an active offload was never disabled. That reasoning now exists once.

**2. The query is not optional.** The old post-cycle code ran `ethtool -K` blind.
That cannot distinguish "the NIC refused" from "the NIC has no such feature": on
virtio `-K` fails *"not supported"*. Promoting the warning without querying first
would therefore have failed commits on every virtio VLAN parent — a NIC that is
incapable of stripping a tag. `ensureRxVlanOff` already documents this trap; the
post-cycle path now respects it.

**3. Scope matches the compile-time gate exactly, in both directions.**
`config.InterfaceHasVlanSubinterface` moved to `pkg/config` (beside
`DHCPLeaseIfName`, which exists for the same "so the two derivations can never
drift" reason) and is used by both `rxVlanOffloadActivationError` and
`reDisableRxVlanAfterLinkCycle`. Wider than the compile gate and every
plain-parent deploy starts failing commits over a setting that cannot misroute
anything there; narrower and the bypass stays open on the parents that have it.

### Two things the fix had to not break

- **It must not skip the rest of the tail.** An early return would have skipped
  the VLAN MAC propagation loop and reintroduced the #6980 stale-MAC blackhole —
  trading one silent misforwarding for another. The error joins the
  "fail-closed but complete" accumulator this file already uses: the tail keeps
  going and the operator still sees the commit fail.
- **It must not break #6871's lease invariant.** `docs/reth-mac.md` and this
  function's own header state that each renewal window holds **at most one**
  20s-ceiling external command. A query plus a disable is two, which would spend
  40s of a 60s TTL and leave the operator-unbounded per-VLAN-child netlink loop
  under 20s. `reDisableRxVlanAfterLinkCycle` renews between them, keeping the
  invariant true rather than making the constant bigger — the same move round 6
  made for the member tail. The renewal table in `docs/reth-mac.md` gains a row,
  its "three renewal points" becomes four, and its "the last two renewals are
  unconditional" is corrected, since the new one is the only conditional renewal.

## Evidence

`pkg/daemon/reth_rxvlan_postcycle_failclosed_9946_test.go`, driven through the
seams this area already has (`runCommandTimeout`, `rethParentLinkByName`,
`rethLinkLister`) — the same harness #6980 used for the sibling defect.

Reproduction first: on unmodified master, four cells fail.

| cell | on master | after |
|---|---|---|
| re-disable fails, RETH carries VLAN units | **returns nil** (the defect) | fails the apply, error names the member and wraps the cause |
| query lists no `rx-vlan-offload` (virtio) | **runs `-K` anyway** | no `-K`, no error |
| already `off` / `off [fixed]` | **runs `-K` anyway** | no `-K`, no error |
| query fails (state unknown) then disable fails | **returns nil** | fails the apply, and the disable is still attempted |
| re-disable fails, RETH has no VLAN units | tolerated | tolerated (unchanged) |
| re-disable succeeds | no error | no error (unchanged) |

The last two rows pass **before and after**. They are the cells that distinguish
this fix from "fail the apply whenever ethtool errors", which would satisfy every
other assertion above while redding plain-parent deploys. A deny-shaped assertion
with no positive case beside it cannot tell a working gate from a broken one.

### The sibling regression, which my own cells could not see

Running only `-run 9946` was green. Running the **whole** touched packages was
not: `TestRethMemberLinkTailRenewsTheLease_6871/ethtool_failed` failed with
`RenewLinkCycle calls = 2, want 1`. That cell is the one that caught the #6871
lease interaction, and a matrix filtered to this issue's own cells would have
missed it entirely.

It was updated rather than relaxed. The property it pins is not "the tail renews
once" — it is that **no renewal window holds more than one 20s-ceiling command**,
and before #9946 those were the same assertion because the tail ran exactly one
command. It now carries five rows, each naming the commands its branch runs and
expecting one renewal per command. Its old `ethtool_ok` row was also quietly
mis-describing itself after the change: with the seam returning `(nil, nil)` for
everything it classifies as "feature absent" and runs no `-K` at all, so the span
no longer contained the command the failure message named. The rows now choose
their branch explicitly through a stub that answers the query.

### Mutation matrix — 14 cells, 14 KILLED, 0 escaped, 0 void, 0 apply-failed

Run in a detached copy (`/var/tmp/wt-9946-mut`), baseline 0 failures, tree
verified clean after every cell. Cells cover: the verdict itself; the scope
predicate deleted and inverted; the accumulate-don't-skip property; both lease
renewals; the blind-probe regression; `Absent` and query-failure
misclassification; the historical `Contains(l, "off")` bug; `off [fixed]`
narrowed to an exact match; the scope predicate weakened to `>= 0`; and the
compile-time side losing its `Absent` arm.

Two instrument faults were found and fixed before the matrix measured anything:

- **`grep -cF` is unsound for a multi-line anchor.** It treats each line as a
  separate pattern and returns the number of lines matching any of them — a
  2-line anchor in a 1225-line file reported "1225 occurrences". Seven cells
  scored APPLY-FAILED on the first run, which at least fails safe; the same
  misread would equally have passed a genuinely 2-occurrence anchor as unique.
  Counting is now one Python pass over the whole file content.
- **Verifying a patch by the anchor's absence is wrong for an insertion.** The
  cell that wraps the rxvlan call in an early return still contains the anchor,
  so it self-reported "patch did not land". The check is now a file comparison.

And one reporting fault: kill sets were printed truncated to the first three
names, which cannot distinguish "every row failed" from "the two
alphabetically-first rows failed" — the two RED-on-revert claims written into the
#6871 cell differ in exactly the rows truncation hid. Re-measured with the full
set:

| revert | claimed | measured |
|---|---|---|
| delete the split renewal in `reDisableRxVlanAfterLinkCycle` | the two two-command rows fail, the three one-command rows stay green | exactly `cycle_reset_the_offload` + `ethtool_failed`; the other three green |
| delete the tail's final `d.renewLinkCycleLease()` | every row fails | all five rows fail |

Both hold as written. That asymmetry is also the argument for asserting a
*count* rather than `>= 1`: a `>= 1` cell would survive the first revert.
