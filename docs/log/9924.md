# 9924 — make AUTO wake/zero-copy requests explicit and record shared-pool inheritance

- **Timestamp**: 2026-09-17
- **Issue**: #9924
- **Base commit**: `95d3a02e5c805af96e1a51996b1dc7fb952e72d7`

## STEP-0: the rows were absent on master

At the branch base (`origin/master`), `userspace-dp/src/afxdp/bind.rs` had:

```rust
const AUTO_BIND_FLAGS: [u16; 1] = [0];
const SHARED_SECONDARY_BIND_FLAGS: [u16; 1] = [SocketConfig::XDP_BIND_SHARED_UMEM];
```

The existing bind matrix test therefore asserted that the shared-secondary row
requested neither `XDP_COPY`, `XDP_ZEROCOPY`, nor `XDP_BIND_NEED_WAKEUP`. The
master baseline ran the three relevant cells green (3 passed), confirming that
the test was pinning the missing request rather than an already-fixed tree.

## Kernel truth

This is a mixed contract, not one flag row that can be changed uniformly:

1. **AUTO/private sockets do not have an owner pool to inherit from.** The AUTO
   candidate now explicitly tries `XDP_ZEROCOPY | XDP_USE_NEED_WAKEUP`, then
   `XDP_COPY | XDP_USE_NEED_WAKEUP`. This preserves the previous zero-copy-first,
   copy-fallback outcome while making the wake request explicit.
2. **Shared secondaries must remain `XDP_SHARED_UMEM`-only.** In `xsk_bind`,
   Linux rejects `XDP_COPY`, `XDP_ZEROCOPY`, `XDP_USE_NEED_WAKEUP`, and
   `XDP_USE_SG` when `XDP_SHARED_UMEM` is present (`net/xdp/xsk.c`, the
   `"Cannot specify flags for shared sockets"` guard). This rule is present in
   Linux v5.15, v6.12, v6.18, v7.0, and current `master`.
3. The effective shared-secondary behavior is inherited from the owner pool.
   Same-queue secondaries reuse `umem_xs->pool`; cross-queue secondaries call
   `xp_assign_dev_shared` (`net/xdp/xsk_buff_pool.c`), which derives
   `XDP_ZEROCOPY` versus `XDP_COPY` from `umem->zc` and adds
   `XDP_USE_NEED_WAKEUP` when `umem_xs->pool->uses_need_wakeup` is set. The
   shipped-image contract is kernel >= 6.18 (`docs/deploy-quickstart.md`).

The code comment beside the rows cites these exact kernel functions and
versions. The matrix test now positively pins the owner's zero-copy + wake bits,
checks the secondary's effective inherited source, and separately checks that
the secondary request itself carries no kernel-forbidden mode/wake flags.

## Fix and fail-on-revert proof

`AUTO_BIND_FLAGS` is now:

```rust
[XSK_BIND_FLAGS_ZEROCOPY, XSK_BIND_FLAGS_COPY]
```

Both candidates include `XDP_BIND_NEED_WAKEUP`; the secondary remains:

```rust
[SocketConfig::XDP_BIND_SHARED_UMEM]
```

The fail-on-revert cell was exercised by restoring AUTO to `[0]`:

```text
left:  [0]
right: [12, 10]
exit: 101
```

After restoring the fix, the same cell passed (1 passed, 0 failed). This is a
real red/green flip on the affected source row, not a source-text assertion.
