# #15075: feeds — persist the feed content epoch under its own digest so it survives restart (A50-01)

## Summary

The persisted feed content epoch (#14395) did not protect across a restart.
`ShrinkHighWaterSnapshot` wrote the epoch prefix set in `Prefixes` with only
`Hash` — the count high-water hash — as its integrity key, and
`RestoreShrinkHighWater` had no separate epoch digest to validate the set
against. After any ordinary install that advanced the high-water (every
non-rebasing rotation: `newCount >= highWater` moves `highWaterHash` to the
rotated set, while the epoch moves only on bootstrap or acknowledgement), the
two hashes diverge. On restore the epoch set therefore could not be keyed to
the high-water hash: at the report base (`51d355c1d`, validated at
`27b8cba22d`) the restore kept the prefixes only if
`hashPrefixes(canon) == highWaterHash`, so a single ordinary rotation before
shutdown silently dropped the whole epoch on the next boot. The first
post-restart fetch then saw no epoch: the shrink/churn trips required a live
snapshot, and the `wasBootstrap || guardBypass` branch rebased the epoch to
the candidate unchecked — a feed provider (or whoever controls its content)
plus any daemon restart could replace an enforced deny/allow list wholesale,
with no refusal and no acknowledgement.

#14994 (merged in #15336) closed the no-snapshot guard leg and accepted the
restored set under a locally recomputed digest, but it never persisted that
digest: the durable record still carried no epoch key of its own, so the
restored set was unverifiable against anything except the high-water hash it
had already diverged from, and the acceptance criteria of this issue — a
separately persisted `EpochHash`, validated on restore — remained unmet.

## Fix (`pkg/feeds/feeds.go`)

- `ShrinkHighWater` gains `EpochHash string` (`epoch_hash,omitempty`): the
  `hashPrefixes` digest of `Prefixes`, persisted separately from `Hash`
  (the count high-water hash).
- `ShrinkHighWaterSnapshot` now emits `EpochHash` from the in-memory
  `epochHash` alongside `Prefixes`. Deleting this emit (or the epoch copy it
  serializes) makes the persisted record carry the rotated high-water set's
  key only, and the regression below goes red.
- `RestoreShrinkHighWater` accepts a canonical persisted epoch set only when
  its digest matches the persisted `EpochHash`. Records written before
  #15075 have no `EpochHash`: their set is accepted only when its digest
  equals `Hash` (the pre-rotation shape, where epoch == high-water). A
  non-canonical set, or a set whose digest matches neither key, is dropped
  fail-closed — the count epoch still restores and the content epoch
  re-bootstraps under the #14994 remembered-baseline guard.
- Bootstrap rebase unchanged in mechanism, now anchored: on a bootstrap with
  a restored epoch, `installSnapshot` already evaluates
  `contentChurnTripped(restoredEpoch, candidate)` (#14994) and refuses a
  churned candidate pending the exact-candidate acknowledgement; it does not
  rebase the epoch (`wasBootstrap && !hasRememberedBaseline` is required for
  a rebase). #15075 makes that evaluation reachable across an ordinary
  rotation + restart by keeping the epoch restorable.

Docs: `pkg/feeds/README.md` drastic-shrink section (persisted `epoch_hash`,
restore keyed on it rather than the high-water hash, fail-closed drop of a
mismatched set, bypass paragraph).

## Regression coverage

`pkg/feeds/feed_shrink_15075_test.go`:

- `TestNonRebasingRotationKeepsEpochAcrossRestart15075` — seed a 100-prefix
  epoch, install a 51%-retained equal-count rotation (installs, does not
  rebase). The persisted snapshot must still carry all 100 original epoch
  prefixes (not the rotated step-1 set), with `EpochHash` equal to the epoch
  digest and distinct from the diverged high-water `Hash`. After a cold
  restart, the identical epoch set installs (control), the 51% rotation
  installs, and a 2%-of-epoch candidate is refused against the restored
  epoch.
- `TestRestartBootstrapDisjointAgainstRestoredEpoch15075` — after the same
  non-rebasing rotation + restart, the first fetch bootstrapping a wholly
  disjoint equal-count set against the restored epoch is refused (0
  installed), the durable epoch is unchanged, and the candidate installs on
  exact acknowledgement (which rebases the epoch).
- `TestCorruptEpochHashDropsEpoch15075` — a record whose `EpochHash` does
  not match its prefix set restores no epoch prefixes (dropped fail-closed)
  while the count high-water still restores.

RED/mutant proof (each makes the tests above fail; restoring the fix makes
them pass):

- Snapshot stops emitting `EpochHash`: the two restart tests fail (the
  legacy fallback only accepts epoch == high-water, which the rotation
  diverged).
- Restore ignores `EpochHash` and accepts any canonical set: all three
  tests fail, including the corrupt-hash drop.
- Restore re-keys the epoch on the high-water hash (`digest == hash`, the
  A50-01 defect shape): all three tests fail — the rotated record's epoch
  is dropped across the restart.

Named controls kept green: identical-to-restored and above-floor cold
candidates install (#14994/#11755 suites), acknowledged churn installs and
rebases, true bootstrap (no remembered baseline) remains installable, and
the full `pkg/feeds` suite passes.

## Risk

Behavior change is scoped to restore of the durable shrink-history record:
an epoch set is now restored only when it verifies against its persisted
`epoch_hash` (or, for pre-#15075 records, against the count hash in the
epoch == high-water shape). A record whose epoch set fails verification
restores the count baseline only — the feed's first post-restart candidate
is then guarded by the count high-water (#14994) and the content epoch
re-bootstraps on the first install, exactly the pre-#14395/#14994 fallback.
No change to thresholds, the acknowledgement tuple, hold policy, true
bootstrap, or any non-feed path. Daemon persistence is additive JSON
(`epoch_hash,omitempty`), so older binaries ignore the new field and newer
binaries read older files.
