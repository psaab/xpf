# docs/log/12156.md — #12156 (preserve MAC-form links when the original name is unknown)

- **Timestamp**: 2026-10-10
- **Action**: Treat a MAC-form `Name=<current>` link without `OriginalName=` as an unknown kernel original at every target name; retain it on the same-name path, neutralize the resurrectable O.link + stale T.link on a target change (MAJOR-1), and continue a required rename.
- **Base**: `origin/master` merge-base `83b5c955335f16d8c7835f206b210ce3ae1a5fe5`
- **Files**: `pkg/daemon/linksetup.go`, `pkg/daemon/bootstrap.go`, `pkg/daemon/device_map.go`, `pkg/daemon/device_map_test.go`, `pkg/daemon/device_map_original_name_6678_test.go`, `pkg/daemon/linksetup_originalname_12156_test.go`, `pkg/daemon/README.md`, `docs/log/12156.md`

## Why

When a `.link` contains `Name=fxp0` and a MAC match but no `OriginalName=`, the old `recoverOriginalName("fxp0")` returned `fxp0` without distinguishing that existing logical-name assignment from the absence of any `.link`. The original fix retained this file only when the NIC already equalled its target. A PCI-order shift or reorder can leave the NIC wearing a MAC-assigned logical name that differs from its new target; treating `current != final` as proof of a kernel name then persists that logical name as `OriginalName=` and breaks the chain. The existing device-map path had the #6678 skip-write/continue-rename pattern; positional and bootstrap naming now use it for this case too.

## What

- `recoverOriginalName` now reports both a recorded original and the distinct case where a `10-xpf-*.link` has `Name=<current>` but no `OriginalName=`; it also reports whether that name-only link matches by `MACAddress=`.
- Positional and bootstrap recovery treat a name-only match as unknown regardless of the eventual target. On the same-name path the positional phase skips only the `.link` write (the retained file stays); on a target change it neutralizes the own O.link + stale T.link (MAJOR-1) while the required rename still runs. Phase 2 runs unknowns-first so the known owner always rewrites after every neutralize.
- Unknown-original logs are `Info` when a matching name-only `.link` exists on the same-name path, including the healthy MAC-form case; `Warn` when no usable persistence file exists; `ERROR` on the target-changing F1 path (no persistence exists for the target). Bootstrap no longer reports the healthy retained-MAC case as `ERROR`.
- Added a shifted logical-name regression proving the own O.link + stale T.link are neutralized while the NIC renames, a collision regression proving the unknown marker survives its temporary rename without writing a temp-name link, and a bootstrap first-rename positive control (`enp5s0` at index 0, empty link directory → `fxp0.link` with `OriginalName=enp5s0`).
- The verified-original control now starts with a non-canonical recorded chain and asserts it is rewritten canonically, so a skipped write cannot masquerade as a no-op rewrite. Follow-up #12550 tracks validating a retained MAC address against the NIC identity before keeping the file.

## Risk

If a name-only `.link` has no usable kernel original, positional naming retains it on the same-name path rather than inventing one; on a changed target the own O.link + stale T.link are neutralized (deleted) and the required rename still runs. Phase 2 runs unknowns-first, so every neutralize lands before the known owner's rewrite (no map-order race); for an unknown whose own temp rename failed, a failed owner write leaves no claim behind (fail-closed). Temp-OK shape excepted (#12557: phase-2 key xpf-tmp-N misses the O.link removal). Retained MAC-form files are not yet checked against the NIC's live/permanent MAC, so a stale file could still claim the wrong device; follow-up #12550 records that hardening. Verification uses isolated Go fixtures and mutant runs; no real udev boot or live-cluster mutation was performed.
