# Issue #14417 — group packed `prefix-list` definition dropped beside inline packed definition

## Why

At the `policy-options` level the `prefix-list` schema node is
`args: 1, children: nil` without `multi`
(`pkg/config/schema_routing.go`). A group packed definition
`prefix-list PL2 192.168.0.0/16;` beside an inline packed definition
`prefix-list PL1 10.0.0.0/8;` therefore failed the
`namedLeafPeer9859` admission gate (`children == nil`), fell back to
the legacy keyword peer `leafListPeer(*dst, "prefix-list")`, which
selects by `Keys[0]` alone and picks PL1. The leaf branch then took
the override path (`isLeafListSchema` is false without `multi`;
promote/same-instance fail on `children == nil`) and dropped PL2 —
a different named object, not the same statement. A routing-policy
`term t1 { from prefix-list PL2; then reject; }` then referenced an
undefined list, which FRR resolves to NULL/`RMAP_NOMATCH`, so `t1`
never matched and every route PL2 was written to reject fell through
to `term t2 { then accept; }` on a clean commit. The only
prefix-list reference gate is the firewall one (#2506); no gate
covers routing-policy `from prefix-list` references.

## What

- `pkg/config/ast_groups.go` (`mergeNodes` leaf branch): new adopt
  arm gated by `prefixListDefinitionInstanceDiffers14417`. When the
  inline peer exists but the group leaf names a different instance
  (`Keys[1]` differs), the group definition is adopted beside the
  peer (`*dst = append(*dst, s)`) instead of dropped. Both
  definitions then compile, and the compiler's #2641 loop unions
  same-name instances as before.
- `prefixListDefinitionInstanceDiffers14417` (same file) is scoped
  to the definition level: it requires the last ancestor-path
  segment to be `policy-options`, `Keys[0] == "prefix-list"` on both
  sides, at least the name token on both sides, and the resolved
  schema node to be the `children == nil`, non-`multi` definition
  node. The `from`-level `prefix-list` reference (`multi: true`
  under a term `from`) is therefore excluded and keeps its existing
  leaf-list union path; `as-path` definitions (DR15-H4/#14419) are
  untouched, as are container-vs-leaf and container-vs-container
  prefix-list merges and the firewall #2506 gate.
- Same-name group/inline packed prefix-lists keep exactly the
  current behaviour (group leaf dropped, inline wins), per the
  issue's exactness requirement; the compiler #2641 union for
  same-name instances is preserved by the adopt/merge path.
- New regression `pkg/config/dr15_h2_prefix_list_definition_test.go`:
  the decisive fixture (group PL2 + inline PL1, `t1` referencing PL2
  with `then reject`), the order-swapped fixture, the same-name
  control (inline wins, one map entry), an inline-only control, and
  a group-only control.

## Validation

- RED on `origin/master` (`e466f0854`):
  `go test ./pkg/config/ -run 'TestDR15H2' -count=1` failed
  `TestDR15H2GroupPackedPrefixListBesideInlinePacked` with
  `PL2 = [], want [192.168.0.0/16]` and the swapped fixture with
  `PL1 = []`; inline-only and group-only controls passed.
  Re-verified by stashing the fix: both decisive tests fail again.
- GREEN after the fix: all 5 `TestDR15H2*` tests pass.
- Targeted suites:
  `go test ./pkg/config/ -run 'TestDR15H2|TestApplyGroups|TestPrefixList|TestCompactLeafPrefixList|Test.*[Pp]refixList' -count=1`
  passed. The full `pkg/config` suite exceeded the 300s tool
  deadline in this lane and was not completed; the main agent
  should run it on the final head.

## Risk

The adopt arm fires only for a different-name packed prefix-list
definition directly under `policy-options`. Same-name behaviour,
braced definitions, `from`-level references, and every other
named-object leaf keep their existing merge semantics, so no
legitimate configuration changes meaning; the only delta is that a
previously dropped group definition now compiles and its
referencing reject term matches as authored.
