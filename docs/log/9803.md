# #9803 — `update_fabrics` plan drift skipped the next fabric rebind

## Issue

`SyncFabricState` sends fabric rows containing both live forwarding values and
binding-plan inputs. The helper refreshed its forwarding links and stored those
rows, but did not replan bindings. A later full `apply_snapshot` carrying the
same rows computed an equal plan key and took the same-plan path, leaving
bindings on the old parent ifindex or queue layout.

## STEP-0 reproduction

On `origin/master` (`ba885b0b1`), the new end-to-end server regression was run
before the fix:

```text
running 1 test
thread 'server::tests::update_fabrics_plan_change_forces_rebind_on_next_apply_9803'
panicked: bindings still on the old parent: [("ge-0-0-0", 101), ("ge-0-0-0", 101)]
test result: FAILED. 0 passed; 1 failed
```

## Fix

- Added a coordinator-scoped `fabric_plan_replan_required` marker.
- `update_fabrics` compares the retained and incoming plan halves
  (`parent_interface`, `parent_linux_name`, `parent_ifindex`, `rx_queues`, and
  `parent_unbindable`) and marks the next full apply when they differ. MAC,
  peer-address, and link-state-only refreshes remain partial updates.
- `apply_snapshot` excludes a dirty fabric plan from the same-plan fast path,
  forcing `replan_queues` and the binding rebind. The marker clears only after
  a successful full apply; planner or reconcile failures leave it set for the
  next valid retry.

## Regression guard

`server::tests::update_fabrics_plan_change_forces_rebind_on_next_apply_9803`
performs this sequence:

1. Apply a fabric bound to parent ifindex 101.
2. Send `update_fabrics` with the same fabric on ifindex 202.
3. Attempt a refused full apply with a wild ifindex and verify old bindings
   remain live.
4. Apply the valid 202 rows and verify all bindings are rebound to 202.

The test was RED before the fix and GREEN after it.
