# #18207: reinjection wire zone field is u16 in Go writer, u32 in both Rust readers

- **Timestamp**: 2026-10-27
- **Problem**: The Go submit writer in `pkg/nfqueue/reinject_socket.go`
  emitted the P-MECH tail zone field as `putU16(uint16(item.ZoneID))`,
  while both Rust readers in `userspace-dp/src/slowpath_reinject_9506.rs`
  (`decode_submit_batch` and `decode_submit_batch_into_pool`) read it as
  `u32`. Every following field was displaced 2 bytes, the strict decoder
  exhausted input before the deadline/clock suffix, and the connection
  handler broke the connection on decode error. Every Go-produced
  reinject frame was rejected; a Rust round-trip could not catch it
  because the Rust encoder and decoder were both u32.

## STEP-0: which side owns the contract (evidence from the #17623 diff)

PR #17623 (`config: widen zone ids to u32 (#16557)`, commit
`ec61dae88b`) widened zone ids from a 16-bit FNV name-hash fold to a
32-bit fold `[1, 4294967293]` because valid zone pairs collided at u16.
Its diff is decisive about intent for this wire:

- Rust readers widened deliberately: `SubmitFrame.zone_id: u16 -> u32`,
  `PooledSubmitFrame.zone_id: u16 -> u32`, both decoders
  `c.u16()? -> c.u32()?`, the Rust encoder `push_u16 -> push_u32`, and
  the tail doc comment updated `zone u16 -> zone u32`.
- Go internal types widened the same way: `AdjudicatedFrame.ZoneID`,
  `ZoneEvaluation.ZoneID` and friends went `uint16 -> uint32`
  (`pkg/nfqueue/pipeline.go`).
- The Go writer was only mechanically touched: `putU16(&out,
  item.ZoneID)` became `putU16(&out, uint16(item.ZoneID))` — the cast
  that kept it compiling after the type widened, but left the wire
  field at u16 and silently truncated any id above 65535.

So #17623 intended the readers (and the whole zone-id contract) to be
u32 and missed the writer: the writer owns the defect, not the readers.
Reverting the readers to u16 would re-truncate ids that #16557/#17623
widened precisely to stop colliding, and would disagree with every
other widened consumer. The fix therefore widens the Go writer to u32.

Secondary evidence in the same diff: neither side updated the tail
length constant. The tail is snapshot u64 + config u64 + FIB u32 +
zone + if_id u32 + inventory generation u64 + inventory FIB u32 +
policy SHA-256 (32) + deadline u64 + clock id u8, which is 79 bytes
with a u16 zone and 81 bytes with a u32 zone. Both
`SUBMIT_PMECH_TAIL_LEN` (Rust) and `reinjectSubmitPMechTailLen` (Go)
still said 79 after #17623. They are capacity/boundary constants only
(the decoders are cursor-driven and reject trailing/truncated input),
so the stale value did not itself reject frames, but it misstated the
contract both sides pin in tests; this change corrects both to 81,
plus the `IpsecInnerAdvisory` doc (72 of 81 bytes, not 70 of 79).

## Fix

- `pkg/nfqueue/reinject_socket.go`: `putU16(&out, uint16(item.ZoneID))`
  -> `putU32(&out, item.ZoneID)`; `reinjectSubmitPMechTailLen` 79 -> 81.
- `userspace-dp/src/slowpath_reinject_9506.rs`: `SUBMIT_PMECH_TAIL_LEN`
  79 -> 81 and its doc comment (the field layout was already u32).
- `userspace-dp/src/afxdp/ipsec_inner.rs`: advisory-tail doc 70/79 ->
  72/81 (comment only).

## Cross-language golden (#17131 / #9412 pattern)

`pkg/nfqueue/testdata/reinject_submit_frame_18207.hex` is the shared
140-byte submit frame. The fixture carries zone id `0x00010017`
(65559) — above the u16 range — so a truncating writer emits different
bytes, not merely a shorter frame.

- Go: `TestReinjectSubmitGoRustPinnedLayout9506` encodes the fixture
  frame with the real `encodeSubmitBatch` and byte-matches both its
  inline vector and the shared golden file, pinning the zone u32 at
  tail offset 20..24, length 140, and tail const 81.
- Rust: `submit_wire_matches_pinned_go_vector_and_both_decoders`
  byte-matches `encode_submit_batch` against the same vector, asserts
  equality with the golden file (regenerated only under
  `XPF_WRITE_GOLDEN_18207=1`, mirroring `XPF_WRITE_GOLDEN_9412`), and
  decodes the bytes through both `decode_submit_batch` and
  `decode_submit_batch_into_pool`, asserting zone `0x00010017` and
  every other field.
- Existing exact-bytes tests updated to the u32 layout:
  `TestEncodeSubmitBatchPMechTailTwoFrames9506` (Go tail offsets) and
  `codec_submit_roundtrip_and_exact_bytes` (Rust, `23u32`/`24u32`).

Pre-fix, the Go encoder produced a 138-byte frame whose zone bytes
were `0017` at tail offset 20..22; both Rust decoders read
`00000017`-displaced fields and failed on the missing deadline/clock
suffix. Post-fix all three pins agree on the same 140 bytes.

## Risk

This is a wire-breaking alignment: a Go daemon and Rust helper built
from different sides of this change cannot exchange submit frames
(the strict decoder rejects them, fail-closed, as it already did for
every frame before this fix). Deploy both together. No other wire
field changes; frozen u16 records elsewhere (#17623) are untouched.
