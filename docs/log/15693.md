# Issue #15693: DHCPv6-client req-option multi, Option 24 parse, enum validation (V37-03)

- **Timestamp**: 2026-10-19
- **Problem**: Under `interfaces <if> unit <n> family inet6 dhcpv6-client`:
  1. `req-option` was declared `args: 1` without `multi: true` and compiled with `nodeVal(prop)` (first value only), so bracketed `req-option [ dns-server domain-name ]`, block, flat packed-tail, and flat repeated spellings dropped every option after the first (`ReqOptions` is a `[]string`).
  2. `req-option domain-name` put DHCPv6 Option 24 (`OptionDomainSearchList`) in the ORO on the wire (`buildDHCPv6Modifiers` / `buildDHCPv6RenewModifiers`), but neither `parseV6ReplyChecked` nor the stateless Information-Request path ever read `Options.DomainSearchList()` — the reply payload was discarded and `Lease` had no field for it.
  3. `client-type`, `client-identifier duid-type`, and `req-option` were untyped, unvalidated leaves: `client-type bogus` committed (daemon treats `!= "stateless"` as stateful), and `duid-type vendor`/`duid-en` silently fell back to `duid-ll` in `normalizeDUIDType`.
- **Fix (schema)**: In `pkg/config/schema_interfaces.go`, `client-type` is now `ValueEnumOf` + `ValidateEnum(stateful, stateless, autoconfig)`, `duid-type` is `ValueEnumOf` + `ValidateEnum(duid-ll, duid-llt)`, and `req-option` is `multi: true` + `ValueEnumOf` + `ValidateEnum(dns-server, domain-name)`. `autoconfig` is admitted because Junos accepts it and the #12714 editor test already drives it; the runtime treats it as stateful (only `stateless` selects Information-Request), which is now an explicit validated choice, and the strict commit gate — not silent coercion — is what rejects typos (the tolerant lenient-load path keeps its existing downgrade-to-warning contract, so a stale `client-type statefull` config still boots stateful rather than blackholing; three daemon test fixtures that typo'd `statefull` for `stateful` were corrected to the valid spelling — they exercised only commits that must still succeed).
- **Fix (compiler)**: In `pkg/config/compiler_interfaces.go`, the `req-option` case now accumulates `firewallMatchValues(prop)` (the same multi-value reader as `client-ia-type`, #15063) instead of a single `nodeVal`.
- **Fix (dhcp)**: `Lease` gains `DomainSearch []string`; `domainSearchFromOptions` extracts Option 24 in both `parseV6ReplyChecked` and the stateless Information-Request path in `pkg/dhcp/dhcpv6.go`; `leaseContentChanged` (`pkg/dhcp/commit.go`) diffs `DomainSearch` so a rotated search list re-fires the debounced recompile/DNS reconcile.
- **Fix (daemon)**: `mergeDNSInputWithMgmtDNSRulesRefused` (`pkg/daemon/daemon_dns.go`) appends lease `DomainSearch` entries after static `system domain-search`, skipping routing-instance leases exactly as for DHCP nameservers, de-duplicating, and passing each untrusted upstream value through the same #4902 `ValidateDNSDomain` render belt as static domains before it can reach the resolv.conf `search` line.
- **Not changed**: DUID runtime fallback for already-persisted/invalid types (`normalizeDUIDType` → duid-ll) is untouched — the commit gate is the operator-facing fix; `client-type autoconfig` runtime semantics (stateful) are unchanged, only validated. DHCPv4 domain handling is out of scope (no `req-option` surface).
