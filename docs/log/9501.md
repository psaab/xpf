## Mechanism (origin/master `35e43ba8c`)

`renderDHCPDefaults` emitted `ip route|ipv6 route <dest> <gw> <iface> 200<vrf>` and interpolated `dr.Interface` with no belt. The static-route renderer, one function away, belts exactly that operand class: `if ifName != "" && !validFRRInterfaceOperand(ifName) { continue }`.

`dr.Interface` is a plain string from `config.DHCPLeaseIfName` → `config.LinuxIfName`, which only maps `/` to `-`. `ValidateInterfaceName` rejects whitespace at commit, so a bad name can only arrive through a tolerant `Store.Load`, HA `SyncApply` or a rollback recompile. That is the population the static belt exists for.

The #6795 cell recorded "no belt needed". Its reasoning was correct for the gateway and the destination, which come from `netip` String() and cannot contain whitespace. It was silent on the interface, the third operand on the same line, and its fixture passed `Interface: "fxp0"` without analysing it. It also promised a compile error "if either field is ever widened to a string", and that can never fire: `DHCPRoute.Gateway` is already `string` at the FRR boundary.

## Change

- **`dhcpRouteInterface(dr)` (new).** It returns the qualifier to render and whether to drop the route. Both renderer branches now do `if ifn, drop := dhcpRouteInterface(dr); drop {…} else if ifn != "" {…}`.
  - An empty or token-safe interface renders exactly as before.
  - A token-unsafe interface is never rendered.
  - With a ROUTABLE gateway, the route renders without the qualifier. That is the static belt's granularity: drop the operand, not the route.
  - With a LINK-LOCAL gateway, the route is dropped. It cannot resolve without an interface, and a line FRR refuses fails the whole managed reload.
  - Each case logs a Warn carrying the gateway and the interface's length, never the value.
- **The #6795 cell's comment** now covers all three operands and drops the false tripwire claim. Its fixture builds the gateway from a real `netip.Addr`.

The issue's separate, unresolved DHCPv4 0.0.0.0-gateway question is not addressed here, as the issue itself scopes it out.

No module docs describe the DHCP route render belt, so no docs change is needed beyond this log.
