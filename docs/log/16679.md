# #16679: BGP `multihop` Junos spellings rejected at commit

- **Timestamp**: 2026-10-25
- **Action**: Modelled BGP `multihop` (group and neighbor level, default
  instance and routing instances via the shared schema node) as the
  Junos presence container it is, instead of the xpf-only scalar
  `multihop <ttl>` leaf. `multihop` is now a typed leaf with `ttl` and
  `no-nexthop-change` modifiers (`pkg/config/schema_bgp_multihop_16679.go`):
  bare `multihop;` commits and resolves to the Junos default TTL 64,
  `multihop { ttl N; }` and flat-set `multihop ttl N` pin the TTL
  (1..255, same range as before), and the legacy `multihop <N>` form
  stays as an alias. All forms land in `BGPNeighbor.MultihopTTL` and
  render the existing FRR line `neighbor X ebgp-multihop <ttl>`
  (neighbor statement overrides the group default as before).
  `no-nexthop-change` is REFUSED BY NAME at strict commit in every
  spelling (packed, blocked, flat-set): FRR's rendered `ebgp-multihop`
  rewrites the received next hop, Junos' flag asks to retain it, and
  FRR has no per-neighbor equivalent, so honouring the TTL while
  dropping the flag would silently invert route propagation. The
  tolerant load/peer-sync paths boot with a specific `#16679` warning
  naming the dropped statement (`warnBGPMultihop16679`, wired in
  `compiler_prewalk.go`), and the refused statement renders no TTL.
  Malformed TTLs (0, 256, non-integer, `ttl` with no value) still
  refuse at commit. A policy NAMED `multihop` still compiles as a
  policy (#15137 fused-cut guard extended, not weakened).
- **File(s)**: `pkg/config/schema_bgp_multihop_16679.go` (new),
