# 16769 — the #9165 drop-metric reader missed the system-syslog clients

- **Timestamp**: 2026-10-25
  - **Action**: Append the `system syslog host` clients to the #9165
    drop-metric reader, labelled by sink, and keep the counters cumulative
    per destination across client rebuilds (#16769, R3-A47-02).
    `Daemon.syslogDropStats` previously returned only
    `EventReader.SyslogDropStats()` (security-log streams), so drops counted
    by the `slogHandler` clients installed by `applySystemSyslog` (UDP
    ECONNREFUSED, #16083 queue overflow — the collectors carrying
    authorization and commit records) had no metric or show reader and the
    family showed an all-clear for exactly those collectors. The daemon
    reader now appends `SyslogSlogHandler.SyslogDropStats()`; a new `sink`
    label ("system" vs "security") on
    `xpf_syslog_messages_dropped_total` keeps the same addr:port on both
    sinks as two series. Both client sets fold each retired client's final
    counters into a per-(sink, addr, protocol) accumulator before Close, so
    a commit that rebuilds the set no longer resets the exported counter to
    the fresh client's zero. Regression tests:
    `daemon_syslog_drops_9165_test.go` (system-host case via the real
    `applySystemSyslog` yields one sink=system row with Writes>0 and the
    stream control unchanged; system and security counters cumulative
    across rebuilds; nil-safety with only a slog handler) and
    `metrics_syslog_drops_9165_test.go` (sink label distinguishes the same
    collector on both sinks; existing keys updated for the new label).
