# #14150 MonitorInterface limiter slot released while Send parked — history

Issue: psaab/xpf#14150 (research-validated D6-09). Lane branch:
`fix/14150-campaign`, base `origin/master` 0db0fa57c.

## Defect (present at base)

`sendMonitorInterfaceFrame` (pkg/grpcapi/server_diag_monitor.go) runs
`stream.Send` in a worker that releases the limiter slot only if the
`timedOut` flag was set. The `<-timer.C` branch sets that flag and
transfers ownership (`transferred=true`, caller disarms its defer), but
the `case <-ctx.Done(): return ctx.Err(), false` branch did not. So
`MonitorInterface`'s defer (transferred=false) released the
`monitorInterfaceLimiter` slot immediately while the worker could remain
blocked in `Send`.

The context at that point is the reauth-wrapped stream context
(`authorizeStreamContinuously` / `reauthServerStream`,
pkg/grpcapi/authz_stream_reauth_9051.go): it is a derived
`context.WithCancel(ss.Context())` whose cancellation does NOT cancel
the underlying transport `Send` (the wrapper overrides `Context()`, not
the transport). A revocation-cancelled, slow-reading client could park
the worker indefinitely; repeated cycles admitted unbounded parked
senders beyond `maxConcurrentMonitorStreams` (64).

Twin: `sendMonitorPacketDropFrame` already transfers on BOTH its
ctx-done and timer branches (with boundary drain). MonitorInterface
was the asymmetric one.

Scope guard: a plain transport ctx cancel that promptly unblocks Send
is benign timing-wise (worker exits quickly); the defect needs the
derived/reauth cancel (or any ctx cancel) while Send stays parked on
flow control — exactly the decoupled shape the regression models.

## Fix

- `pkg/grpcapi/server_diag_monitor.go`: `sendMonitorInterfaceFrame`'s
  `<-ctx.Done()` branch now mirrors the PacketDrop twin — stores the
  transfer flag, drains `done` non-blockingly (if Send already
  completed, release here and return `(ctx.Err(), false)`; otherwise
  return `(ctx.Err(), true)` so the caller disarms its defer and the
  parked worker releases when Send returns). Renamed semantic in docs:
  `timedOut` flag now means "transferred" for both timer and ctx paths.
  Handler defer comment and function doc updated accordingly.
- No other call sites: the only callers are `MonitorInterface`'s loop
  and `forwardMonitorInterfaceFrames`, both already honour the
  `(error, bool)` transferred contract — they needed no change, which
  is the proof the fix is at the right layer. NOT changed:
  `sendMonitorPacketDropFrame` (already correct), `recvMonitorInterfaceFrame`
  (Recv proxy path; `conn.Close` unblocks it, no slot held by worker),
  limiter itself.

## Regression

New `ctxDecoupledBlockingStream14150`: `Context()` is a cancellable
handler context, `Send` parks on a separate transport-release channel
— cancelling ctx does NOT unblock Send (the production reauth shape).
Existing `blockingMonitorStream9891` keys Send off the same ctx, so a
premature release is invisible there.

`TestMonitorInterfaceCtxCancelTransfersSlot_14150` (two subtests):
- `sendFrame`: drives `sendMonitorInterfaceFrame` directly, cancels
  ctx while Send parked; asserts `xfer=true`, `InFlight==1` and probe
  Acquire fails while parked, then slot drains after transport release.
- `handler`: full `MonitorInterface` handler; same assertions at
  handler return.

RED on pristine base worktree (`/var/worktrees/wt-14150-base`, only
test file copied): both subtests fail —
`sendFrame: xfer = false ... InFlight=0 exits=0`;
`handler: InFlight at handler return = 0, want 1`.
GREEN with fix (also `TestSendBoundary*`,
`TestMonitorInterfaceSlowConsumerTimesOut_9891`,
`TestMonitorPacketDropSlowSend*` pass).

## Residuals

- Real-transport proof that a reauth cancel parks a flow-control-blocked
  Send indefinitely is by construction of the derived context + grpc-go
  semantics (documented in #9051 code); the fake faithfully models the
  decoupling. The existing real-H2 test
  (`TestMonitorInterfaceRealFlowControlUnblocksOnReturn_9891`) covers
  the timer-transfer path over bufconn.
- On ctx-transfer, the slot is held until the transport actually
  unblocks Send (client drains/disconnects or handler-return teardown
  at the gRPC layer). That is the intended bounded retention, identical
  to the timer-transfer and PacketDrop doctrines.
