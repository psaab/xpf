# #12882: hold-interval drop must not release a refused shrink

## Summary

`dropSnapshotToEmptyLocked` cleared the outstanding refused-shrink candidate
when an explicit `hold-interval` expired. The refusal had stamped `StaleSince`
(refusals run through `recordFailureLocked`), so a feed serving a drastic
100→1 shrink was dropped to empty after the hold elapsed; the next fetch of the
exact refused candidate arrived with `hasSnapshot == false`, skipped both
`hasSnapshot`-keyed guard predicates, and installed through the deliberate
bootstrap path with an audit warning only — a refused, unacknowledged
relaxation became enforced. The operator could not even acknowledge it: the
tuple was gone and `AcknowledgeFeedShrink` rejected with "no current refused
shrink".

The fix removes the laundering mechanism:

- `dropSnapshotToEmptyLocked` no longer calls `clearShrinkCandidate`. The
  refusal and its acknowledgeable tuple survive the drop of the baseline they
  were recorded against.
- `installSnapshot` pins the exact refused candidate after a drop: when there
  is no live snapshot but a refusal is outstanding and the fetch matches the
  remembered candidate hash and new count, the refusal block runs anchored on
  the stored tuple (baseline hash, old count) instead of the emptied installed
  state. An exact pending acknowledgement installs (`guardBypass`); otherwise
  the candidate is refused again with a dedicated error/log
  ("REFUSED after hold-interval drop — awaiting exact acknowledgement").
  Previous-good enforcement persists via the #9527 omitted-binding preflight.
- A DIFFERENT candidate after the drop is not pinned: it keeps the deliberate
  bootstrap doctrine (install, audited against the remembered epoch
  high-water) and its install clears the refusal, exactly as before.
- `AcknowledgeFeedShrink` applies its installed-baseline currency check only
  while a snapshot is installed: after a hold drop there is no installed hash
  to compare against, yet the surviving tuple still names the dropped baseline
  and any install clears the refusal, so a surviving tuple is never stale.

## Risk

Behavior change is scoped to feeds holding an outstanding refused shrink when
an explicit positive `hold-interval` expires: the exact refused candidate now
requires acknowledgement before it can install after the drop (previously it
installed with an audit warning). Ordinary fetch-failure drops, never-fetched
feeds, recreated feeds (no carried refusal — `carryForwardSnapshot` still
drops the candidate on producer replacement), and different-candidate
recoveries are unchanged. The ack RPC change only widens acceptance for the
post-drop state where no installed baseline exists.
