# #17221 — fabric IPVLAN addresses fail-closed (#17221)

- **Base**: `e9718daaf25683f925f102cd5fc80ff20ec2a082` (origin/master)
- **Branch**: `fix/17221-campaign`

## Why

`ensureFabricIPVLAN` applied three policies to three properties of one
device: MTU was fail-closed after #10216, LinkSetUp was checked, and the
fabric address — the address the overlay exists to carry for session sync,
with no other writer (networkd skips fabric overlay addresses at both
planner sites) — was warn-only on both the create and reuse branches. The
#6791 retry gate (`missingFabricOverlays`) only checked presence and
admin-up, so a failed address write left a successful commit, a healthy
30 s gate, and a session-sync transport with no source address until the
next commit happened to reconcile it.

STEP-0 re-check on current master `e9718daaf2`: defect live —
`daemon_ha_fabric.go` create branch `AddrReplace` warn-only (`:87-90`
pre-change), reuse branch `reconcileIPVLANAddrs` void with all errors
`Warn` (`:104-151` pre-change), create `Info` logging the configured (not
present) addresses, and `daemon_fabric_reassert.go:80-104` gate returning
nothing once the link was present and up.

## What

- `pkg/daemon/daemon_ha_fabric.go`:
  - New `fabricOverlayReady(link, addrs, wantMTU) error` — administratively
    up, at the desired MTU, and carrying every configured address — plus
    `fabricPresentAddrs` / `fabricOverlayMissingAddrs` helpers over a new
    `fabricAddrList17221` seam.
  - `ensureFabricIPVLAN` ends BOTH branches with `fabricOverlayReady` on a
    fresh lookup (`fabricLinkByName17221`). Create branch: an invalid
    configured address or a failed `AddrReplace` now returns an error
    instead of `Warn`+continue; the `created fabric IPVLAN` Info logs the
    addresses actually present. Reuse branch: a `reconcileIPVLANAddrs`
    error, a `LinkSetUp` error, or a not-ready fresh lookup returns.
  - `reconcileIPVLANAddrs` now returns `error`: invalid desired address,
    `AddrList` failure, failed `AddrReplace` of a desired address, or a
    desired address still missing after reconcile are errors; a stale
    address delete failure stays `Warn` (cleaned next reconcile, does not
    strand session sync).
  - Netlink seams as the existing `fabricLinkByName10216` /
    `fabricLinkSetMTU10216` pattern: `fabricLinkByName17221`,
    `fabricLinkAdd17221`, `fabricLinkSetUp17221`, `fabricAddrList17221`,
    `fabricAddrReplace17221`, `fabricAddrDel17221` (production values are
    the netlink ops).
- `pkg/daemon/daemon_fabric_reassert.go`: `missingFabricOverlays` computes
  the configured addresses first and treats an overlay as present only
  when `fabricOverlayAddrReady` passes (admin-up + every configured
  address present, via the same `fabricOverlayMissingAddrs` /
  `fabricAddrList17221` seam), so gate and actuator cannot disagree and
  the reuse branch heals the address in place. MTU stays the actuator's
  terminal check (see Risks).
- Tests in `pkg/daemon/fabric_ipvlan_failclosed_6791_test.go`:
  `TestFabricReassertGateFiresWhenAddressAbsent_17221` (new gate cell: fab0
  UP, configured address absent → reported missing),
  `TestFabricReassertGateIsQuietWhenOverlayIsUp_6791` updated to carry its
  configured address on the fake and stays quiet,
  `TestApplyFabricIPVLANAddrReplaceFailureReachesApplyTail_17221`
  (`AddrReplace` → `EACCES` through the real `ensureFabricIPVLAN` and
  `applyFabricIPVLAN` reaches the apply tail naming fab0), and
  `TestFabricOverlayReady_17221` (up/MTU/address each independently fail
  ready).
- `pkg/daemon/README.md`: the #6791 paragraph no longer cites
  "address failures are warn-only" as the safety argument; it states the
  #17221 fail-closed address policy and the address-checking gate.

## Risks

- Gate MTU divergence, deliberately scoped: the issue's "same address
  predicate" is honoured (shared `fabricOverlayMissingAddrs`); the gate
  does not also check MTU, so a link present, up, correctly addressed but
  at the wrong MTU is not re-driven by the 30 s loop (it is still
  fail-closed at apply time by `fabricOverlayReady`). Extending the gate
  to MTU was rejected here because every existing gate fake would need an
  MTU model and the configured-MTU-vs-floor mapping (`fabricMTU10216`)
  would need threading through the gate — a wider change than the
  address defect.
- The gate now performs one `AddrList` per configured `fab*` device per
  30 s tick (at most two), only for links already found present; absent
  links cost the same lookup as before.
- IPv6 link-local note (pre-existing, out of scope): `ensureFabricIPVLAN`
  never calls `LinkSetUp` before `AddrReplace`, and the reuse branch's
  stale-delete set difference can include the kernel's IPv6 link-local —
  both unchanged by this fix.
