# #16207 — extract danglingRefs helper in FRR term renderer

- **Timestamp**: 2026-10-24
- **Action**: Extracted exactly the small `danglingRefs` helper named
  by the issue. In `renderPolicyTermSequencesWithDefinitions`
  (`pkg/frr/policy_render.go`) the as-path (#9881), community
  (#10822) and prefix-list (#14136) fail-closed term rules each
  open-coded the same collection idiom: allocate a
  `map[string]bool` sized to the name slice, skip empty names, probe
  each distinct name once (`asPathListMissingAtRender` /
  `communityListMissingAtRender` / per-family
  `prefixListRefMissingAtRender` aggregation), then scan the map for
  any `true`. They now call
  `danglingRefs(names, missing) (map[string]bool, bool)`, placed beside
  the `*MissingAtRender` predicates it composes. The prefix-list site
  keeps building `prefixListDanglingFamilies` inside its probe
  closure, so each distinct name's `fromPrefixListRefs` expansion
  still happens exactly once and only for names the old loop reached.
  The helper allocates the one map each site already allocated and
  folds the old second any-scan into the collection loop — no new
  per-term map or pass beyond the sites it replaces. Out of scope per
  the issue and untouched: generated-name hash unification
  (`pkg/frr/naming.go` names are a stability contract, REJECTED) and
  the term pipeline shape (DEFERRED behind the golden corpus).
- **File(s)**: `pkg/frr/policy_render.go`,
  `pkg/frr/policy_danglingrefs_16207_test.go`, `debian/changelog`,
  `docs/log/16207.md`
- **Tests**: New `TestDanglingRefs16207*` cells pin the helper
  directly (distinct names probed exactly once, empty names skipped
  and never recorded, `any` iff any distinct name dangles, absent

  nil/empty/all-dangling edges). Existing #9881/#10822/#14136/#14700
  render tests exercise the helper end-to-end through all three

  update makes both the new unit cells and the pre-existing
  deny-all render tests red. Byte-for-byte check: a throwaway golden
