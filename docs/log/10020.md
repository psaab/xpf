# #10020 — name the SYN-flood alarm screen bit in both Go consumers

- **Issue**: #10020 — `SCREEN_SYN_FLOOD_ALARM = 1 << 20` was emitted by
  `userspace-dp/src/afxdp/event_emit.rs` but omitted from both Go screen-flag
  tables, so event records rendered `screen(0x100000)`.
- **Branch**: `fix/10020-screen-bit`
- **Worktree**: `/home/ps/git/pi-xpf/.claude/worktrees/10020-screen-bit`

## Why

The Rust emitter maps `"syn-flood-alarm"` to bit 20. The Go logging mirror and
`pkg/dataplane` table stopped at bit 19. Delivery was preserved, but the
log-only alarm's screen reason was lost at both Go consumers.

## What

- Added `screenSynFloodAlarm = 1 << 20` and `ScreenSynFloodAlarm = 1 << 20`.
- Added the shared human-readable name `SYN flood alarm` to both maps.
- Added `TestScreenSynFloodAlarmLockstepWithRust_10020`, which reads the Rust
  source, checks the actual bit and reason mapping, and asserts both Go maps and
  the logging renderer decode the bit by name. Removing either Go entry reds
  the test.

## Validation

### RED before the fix

The new contract test was run before adding the bit-20 entries:

```text
logging screenFlagNames[1<<20] = "", want "SYN flood alarm" (renders "screen(0x100000)")
dataplane.ScreenFlagNames[1<<20] = "", want "SYN flood alarm"
screenFlagName(1<<20) = "screen(0x100000)", want "SYN flood alarm"
len(screenFlagNames) = 20, want 21
len(dataplane.ScreenFlagNames) = 20, want 21
FAIL
```

This proves the pre-fix raw fallback on the logging surface and the missing
bit-20 entry on the dataplane surface.
