## Re-verified at origin/master 7c494b5ca

`exact_cos_flow_bucket` seeds from the queue seed, protocol and address family, then mixes in the source and destination IP and port. It never reads `routing_domain` (u32, #7160) or `discriminator` (`TunnelDiscriminator`, #7188), although both are part of `SessionKey` identity (`Hash`/`Eq` derives). So two sessions that differ only in those fields hash to the same bucket for EVERY seed.

## Design

- **Routing domain.** Mixed only when non-zero: tag 1, then the id as two 16-bit halves.
- **Discriminator.** Matched exhaustively with no `_` arm, as in `session/key.rs`, so a new class has to decide:
  - `None` is not mixed;
  - `Unkeyed` is tag 2;
  - `Keyed(k)` is tag 3, then k as halves;
  - `Pptp(h)` is tag 4, then h as halves;
  - `Unparseable` is tag 5.
  The tags keep `Keyed(1)` and `Pptp(1)` apart.
- **Why halves, and why small tags.** The first draft mixed `(tag << 32) | value` in one step, and `flow_fair_bucket_separates_tunnel_discriminators_9645` went red on it. `mix_cos_flow_bucket` only carries upward and the bucket keeps the low bits, so any difference above bit 15 never reaches the bucket: `Unkeyed` vs `Unparseable` and `Keyed(1)` vs `Pptp(1)` collided for every seed. The same would hold for two 32-bit ids that differ only in their upper half. The cells now include upper-half-only pairs (`0x0001_0000` vs `0x0002_0000` for both a routing domain and a GRE key).
- **Pre-existing and not changed.** The same carry-only property means that source IPv4 addresses differing only in their top octet are separated only by the few mixes that follow them. Changing that would move the default-instance mapping and needs the loss-cluster fairness re-validation the seed-0 pins demand.
- **Why only when non-default.** A default-instance flow with no discriminator keeps the exact pre-#9645 bucket, so the seed-0 pins (410/1284) and the loss-cluster 5201 fairness baseline stay valid without re-validation. The unchanged cell below proves it against a verbatim copy of the old function.
- **Severity (from the issue).** Fairness coupling only, not an isolation boundary. Forwarding, policy and session identity already keep the routing domain.
- **Out of scope.** Reverse-match keys zero `routing_domain` by design (#7160). A reply's CoS item keys off its own session key, which is already a different flow.
