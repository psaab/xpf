# #13093 - Keep userspace status readers responsive

- **Timestamp**: 2026-10-15
- **Action**: The status loop now releases `Manager.mu` while awaiting its helper status poll, then revalidates the helper process generation before reconciling the reply. Control-socket requests are serialized independently. `Status()`, `CachedStatus()`, and `ForwardingSupported()` read the atomically published status snapshot without contending with reconciliation.
- **Validation**: `TestStatusLoopDoesNotHoldManagerLockAcrossStatusRPC13093` failed on pristine master while the helper was blocked on its status reply, and passes after the change. `TestStatusReadAPIsDoNotWaitForManagerLock13093` and `TestStatusLoopWiresTheLivenessCount9651` pass. `go vet ./pkg/dataplane/userspace` and `git diff --check` pass. Full `go test ./pkg/dataplane/userspace -count=1` was run twice; it fails on AF_UNIX path-length errors from existing `t.TempDir()` fixtures, `TestCapFlagIsWiredEndToEnd9054`, and the snapshot-shape digest test. All three failure classes reproduced on pristine `origin/master`.
- **Risk**: `Status()` now returns the most recently polled status rather than issuing an extra control-socket RPC; status freshness is bounded by the 1 Hz poll. HA and forwarding fail-closed gates are unchanged.
