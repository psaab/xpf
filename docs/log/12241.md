# Issue #12241 — expire feed holds on wall-clock deadlines

## Why

A positive feed hold interval was checked only while recording another fetch failure. With a 300-second hold and a 3600-second fetch cadence, a feed could retain a stale snapshot until the next failed fetch, so the configured time-to-drop was not a real-time bound.

## What

The existing per-feed refresh worker now arms a wall-clock timer for a stale snapshot's hold deadline independently of its fetch ticker. At expiry it rechecks that the feed is still current and stale, then uses the existing drop-to-empty and publish transition outside the manager lock. Successful recovery and feed cancellation stop/re-arm the timer through the existing worker lifecycle; ordinary fetch and rejected-candidate failure behavior is unchanged.

## Validation

- **STEP-0 / RED before** (`a714c90d472a3c3d98a3799831cfef3ec311a61c`): the throwaway probe advanced a 300-second hold to 310 seconds after the first failure without recording another failure; `GetPrefixes` still returned the last-good snapshot and `holdDropped=false`. The permanent wall-clock regression failed on that base: snapshot remained installed with exactly one failed request despite a 300ms hold / 3600ms scaled fetch cadence.
- **GREEN after**: `go test ./pkg/feeds/ -run '^TestHoldExpiryUsesWallClock12241$' -count=1 -v` passed; the regression also passed with `-count=3` and `-race`. It observes the drop publication while confirming the server received only the initial failed fetch.
- `go build ./pkg/feeds/` passed.
- `go test ./pkg/feeds/ -count=1` passed.
- `gofmt -l pkg/feeds/feeds.go pkg/feeds/feed_hold_expiry_12241_test.go` produced no output.

## Risk / residual

No live cluster was exercised. The integration regression scales both intervals by 1/1000 to keep wall-clock test time bounded while preserving the issue's 300:3600 ratio. Expiry uses the existing worker and adds no goroutine; callback/rejection semantics remain those of the existing drop path.
