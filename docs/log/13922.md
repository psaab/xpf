# #13922 — Reject cross-family NAT endpoint pairs

- **Action**: Reject DNAT match/pool and static-NAT host endpoint family mismatches during compilation.
- **Base**: `origin/master` `ad0ded0df330f8f80ed3c357d4b90e1e726701a0`
- **Files**: `pkg/config/compiler_validate_strict_nat.go`, `pkg/config/compiler_nat_cross_family_13922_test.go`, family-compatible DNAT test fixtures, `docs/log/13922.md`

## Why

DNAT uses family-specific entries. A match and translated pool address from different families cannot be installed as one usable entry. Static NAT likewise requires a same-family host pair for an installed mapping.

## What

Strict and lenient regressions cover both mismatch paths: strict commit rejects the pair, while tolerant compilation retains its warn-and-compile behavior. Regressions also cover mixed-family destination-address lists and verify IPv4-mapped IPv6 remains classified as IPv6. Existing DNAT parser and pool tests now use matching-family fixtures so they continue testing their stated behavior without asserting cross-family compatibility.

## Validation

- RED on pristine master: cross-family DNAT and static-NAT host cases committed CLEAN; cross-family static-NAT block configuration was rejected only by a generic route diagnostic.
- GREEN: focused #13922 strict/lenient, mixed-list, mapped-address and affected DNAT fixture regressions passed, including after rebasing onto current master.
- Full `go test ./pkg/config` fails on both the fix branch and pristine issue-base SHA `ad0ded0df330f8f80ed3c357d4b90e1e726701a0` at `TestConfiguredIPv6Prefixes10856` with the same expected/actual mismatch (`2606:4700:1111::/64` vs. `2606:4700:2222::2/128`); this is pre-existing.

## Risk

Compilation now rejects cross-family translation pairs that cannot be represented by the family-specific dataplane entries. Same-family translation behavior is unchanged.
