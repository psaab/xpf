# LLDP Chassis ID TLV is each port's own MAC (#14618)

## Why

`Manager.sendFrame` called `BuildFrame(iface.HardwareAddr, iface.Name,
...)` with the per-session interface, and `BuildFrame` encoded that
same MAC as the Chassis ID TLV (subtype 4). `LLDPConfig` carried no
system identifier, so one xpf box advertised a different chassis on
every LLDP-enabled port. LLDP-MIB models `lldpLocChassisId` as a
scalar of the local system data while `lldpLocPortId` is per-port, so
neighbour/NMS topology views showed N unrelated systems instead of
one, breaking correlation on every multi-port deployment. No
forwarding or security impact (Low).

## What

- `pkg/lldp/lldp.go`: new `LLDPConfig.ChassisMAC`. `Apply` now
  resolves all configured interfaces first, computes ONE chassis via
  `resolveChassisMAC` (valid explicit MAC wins; otherwise the
  deterministic smallest usable MAC among the resolved interfaces,
  order-independent), and threads it through `txLoop`/`sendFrame`.
  The Ethernet source and Port ID remain per-port. `buildFrame`
  splits chassis from source; `BuildFrame` delegates unchanged (peer
  modelling) and `BuildFrameWithChassis` exposes the split. An empty
  chassis (no usable MAC anywhere) falls back to the port MAC,
  preserving the old single-port corner.
- `pkg/daemon/daemon_apply_tail.go`: `effectiveLLDPConfig` populates
  `ChassisMAC` from `systemChassisMAC()` — fxp0, then em0, via the
  `chassisMACLookup` seam; nil delegates to the pkg/lldp fallback.
  The management MAC is the stable box identity: it does not change
  when the LLDP interface set changes, so the #2372 diff-guard stays
  quiet (verified deterministic in the daemon test).
- `pkg/lldp/README.md`: documents the one-chassis invariant.

NOT changed: Port ID / Port Description still carry the kernel
interface name (secondary cosmetic point in the issue; separate
consideration), the wire codec, neighbour parsing/keys, or any
RETH-MAC handling.

## Validation

- RED: `go test ./pkg/lldp/ -run TestChassisID -count=1` on the
  pre-fix tree fails to build (`unknown field ChassisMAC`,
  `undefined: resolveChassisMAC`); behaviourally the Manager test
  asserts byte-identical chassis across `02:..:01`/`02:..:02` ports,
  which the per-port derivation cannot satisfy.
- GREEN targeted: `go test ./pkg/lldp/ -run TestChassisID -count=1 -v`
  passes (also under `-race`); `go test ./pkg/daemon/ -run
  TestEffectiveLLDPConfigChassis14618 -count=1 -v` passes; all
  daemon LLDP reconcile tests pass.
- GREEN affected: `go test ./pkg/lldp/... -count=1` passes;
  `go vet ./pkg/lldp/ ./pkg/daemon/`, `gofmt`, `git diff --check`
  clean. The full `pkg/daemon` suite exceeded the harness timeout
  on both this branch and a pristine `origin/master` worktree
  (environment-bound, not attributed to this change); the LLDP
  subset above is the affected surface.

## Risk

Chassis ID values neighbours already learned change once on upgrade
(per-port MAC -> system MAC); neighbour tables re-learn within one
TTL. If the LLDP interface set changes and no management MAC exists,
the fallback chassis can change with the set — documented, and the
daemon path (fxp0/em0) avoids it on real hardware. No lab deployment
was run; topology effect is covered by the Manager-level frame test.
