# Issue #16636: burst ip-monitoring probes on first apply after process start

- **Timestamp**: 2026-10-25
  - **Action**: The ip-monitoring overlay is in-memory engine state, so a restarted xpfd rendered FRR and the helper snapshot with an empty overlay on its first apply, withdrawing the distance-1 preferred route for a dead uplink; probes restarted at normal cadence (the #11414 burst only fired on HA transitions), so the route returned only after (successive-loss-1) x test-interval (~120s at defaults). Fixed by bursting every ip-monitoring-referenced probe runnable in the effective RPM set on the first hash-gated `reconcileRPM` of a process (`Daemon.rpmFirstReconcileDone` latch + `ipMonReferencedProbeNames`), reusing `ApplyWithProbeBurst` so pin-install results publish before the burst loops start. Later config changes keep normal cadence; HA-takeover bursts unchanged. Added daemon-level RED/GREEN test (dead tcp-ping target, 60s interval, threshold 3: FAIL + `TakeoverBurst` within 2s on first apply, unreferenced probe not burst, second changed reconcile not re-burst) plus selector unit test.
