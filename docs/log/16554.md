# #16554: Reserved `zone-local/<zone>/<name>` key usable as a policy, NAT, or address-set-member token

- **Timestamp**: 2026-10-24
- **Problem**: `resolveZoneLocalAddressBooks` mints synthetic global keys
  `zone-local/trust/web` for zone-local entries and rewrites a policy token
  only when it resolves in the policy's own from/to zone book. An operator
  could spell the synthetic key directly in an untrust->dmz policy (or a
  global policy, NAT/NAT64 address-name, static-NAT `prefix-name`, or
  address-set member): the token was not rewritten, the post-fold global
  book contained it, and the #2008/definedness gates accepted it, so the
  strict commit armed trust's zone-local object on a rule whose zones never
  defined it. Display surfaces stripped the prefix and showed `web`, a name
  absent from the rule's zones, and a later edit of trust's book silently
  changed the other zonePair's rule. Measured at base `04cf7a6bd2`: policy
  (cross-zone), global, SNAT, DNAT, set-member, and NAT64 rows all committed
  clean.
- **Fix**: New pristine-tree gate `validateReservedZoneLocalRefTokensStrict`
  (`compiler_validate_strict_zonelocal_ref_16554.go`), dispatched in
  `runEarlyStrictAndFolds` immediately after the #3061 entry-name gate and
  before `resolveZoneLocalAddressBooks`, so every token it sees is authored
  and compiler-minted keys are never rejected. It rejects any token
  beginning with `zone-local/` on: zone-pair and global policy
  source/destination addresses, source/destination NAT
  `source-address-name`/`destination-address-name`, NAT64
  `source-address-name`, static-NAT `then static-nat prefix-name`, and
  address-set `address`/`address-set` members in the global, named, and
  zone-local books. Strict commit hard-rejects naming the surface and token
  (#16554). The tolerant path (`lenientReservedZoneLocalRefs`, #1960
  no-brick) warns and poisons via `poisonReservedZoneLocalRefs16554`:
  referencing policies (including through a set closure) get
  `LenientContentDropped`, NAT rules get `LenientMatchDropped`, and each
  token is quarantined in the global book's `CollidingNames` — which the
  policy, NAT, NAT64, and static prefix-name resolvers already refuse — so
  a leniently-loaded cross-zone binding never enforces the other zone's
  object. The own-zone authored-name control (`web` in a trust policy)
  still commits and rewrites to `zone-local/trust/web`.
