# Issue #15098 — RouteEntry.reject stored but never read by route selection (A65-01)

- **Issue:** psaab/xpf#15098 (deep-review A65-01, research-validated
  MATERIAL 3-way). Lane branch: `fix/15098-campaign` off
  `origin/master` `f524416374`.
- **Scope:** `userspace-dp/src/afxdp/forwarding/fib.rs` route selection
  only, plus regression tests. No other consumer changes — the
  `RejectRoute` disposition, its poll arm
  (`poll_descriptor/mod.rs`), reply builder (`reject_reply.rs`),
  exception/counter handling (`disposition.rs`), and session-delta /
  wire spellings already existed (#13949/#14021/#14237/#14319); only
  the FIB producer was missing.

## Defect (present at base)

`forwarding_build/fib.rs:715,782` store `reject: route.reject` into
`RouteEntryV4/V6`, but nothing in route selection read it:

1. `select_v4_route` / `select_v6_route` (`forwarding/fib.rs`) treated
   only `route.discard` as the terminal row. A reject row with no
   next-hop fell through to next-hop selection with an empty member
   list, so the `Static` arm hit `ifindex <= 0` →
   `no_route_resolution` — every reject route was counted as
   `no_route` and lost its dataplane ICMP unreachable.
2. A reject row carrying a next-hop (stale or Go-emitted member) was
   selected as an ordinary gateway row and **forwarded** — traffic
   the operator asked to reject.
3. A next-table leak whose target-table LPM is a reject route
   resolved `NoRoute` inside the target; the leak walk (#14319)
   treats a recursive `NoRoute` as a miss, so it fell through to the
   source table / less-specific route and **forwarded** — where
   kernel/FRR semantics reject.

This is the residual of `3743c24ffd`, whose message claims a FIB
change its diff does not contain.

## What

- `select_v4_route` / `select_v6_route`: `discard || reject` is the
  terminal row, under the identical #13950 drivable-fallback
  preference gate (an earlier drivable gateway at the same prefix
  still wins; an empty/invalid fallback does not suppress the
  terminal row; a reject row never reaches next-hop selection).
- `lookup_forwarding_resolution_v4_inner` / `_v6_inner` `Static` arm:
  `discard || reject` returns the zero-egress terminal resolution,
  with disposition `RejectRoute` when `reject` is set and
  `DiscardRoute` otherwise (reject wins if both flags are set — the
  Go producer never sets both, `pkg/dataplane/userspace/routes.go`
  keeps them distinct, and reject is the strictly more informative
  terminal).
- Leak walk unchanged: it already returns any non-`NoRoute`
  disposition immediately, so a target-LPM `RejectRoute` is now
  terminal rather than a miss. `table_has_v*_route` unchanged: a
  reject entry has no next-hops, so `route_entry_usable_*` already
  admitted it to the leak precheck.
- NOT changed: discard semantics, preference/ECMP selection for
  ordinary routes, connected-route precedence, tunnel handling,
  counters (`RejectRoute` already bumps `discard_route` via
  `disposition.rs`), caching, or the reply path.

## Tests

FIB (`forwarding/tests_lpm_parity_9522.rs`, snapshot-built through
the production `build_forwarding_state`):

- `reject_only_route_rejects_v4_v6_15098` — reject-only rows resolve
  `RejectRoute` (egress 0) in v4 and v6. Pre-fix: `NoRoute`.
- `reject_with_next_hop_still_rejects_v4_v6_15098` — reject rows
  carrying a live gateway still reject. Pre-fix: `ForwardCandidate`
  (forwarded).
- `leak_into_reject_target_rejects_v4_v6_15098` — next-table leak
  whose target LPM is a reject route surfaces `RejectRoute`.
  Pre-fix: leak miss → fall-through.
- `reject_controls_discard_and_preference_15098` — controls: discard
  stays `DiscardRoute`; a preferred drivable gateway is not shadowed
  by a less-preferred reject row (both families).

Poll level (`poll_descriptor/reject_reply_tests.rs`):

- `reject_snapshot_resolves_and_enqueues_icmp_unreachable_15098` —
  a reject snapshot built via `build_forwarding_state` resolves
  through the production FIB to `RejectRoute`, and feeding that
  disposition through the poll arm seam
  (`handle_route_reject_disposition`) enqueues exactly one ICMPv4
  destination-unreachable (`[3, 1]`). Pre-fix the FIB leg returns
  `NoRoute` and the assertion fails before any reply.

## RED -> GREEN proof

- **RED (fix reverted, tests present):** `cargo test --bin
  xpf-userspace-dp 15098` — 4 failed, 1 passed. The reject-only,
  reject+next-hop, and leak cells panicked on the `RejectRoute`
  assertions (`NoRoute` / forwarded dispositions on base), and the
  poll-level cell panicked at its FIB disposition assertion
  (`reject_reply_tests.rs:3763`, `NoRoute` instead of `RejectRoute`).
  The discard/preference control cell passed on base, as designed.
- **GREEN (with fix):** all 5 `15098` tests pass; the neighbouring
  `afxdp::forwarding::` + `afxdp::poll_descriptor::reject_reply`
  suites pass (408 passed, 0 failed), covering the #13950
  discard-preference, leak, and prior reject-reply regressions.

## Risk

- Behaviour delta is confined to destinations whose winning route
  carries `reject: true` — previously mis-counted as `no_route` or
  forwarded. Legitimate forwarding, discard (silent), and
  preference/ECMP behaviour for ordinary rows are untouched; the
  terminal-row gate is the existing discard gate widened by one
  flag read, no new allocation or scan on the hot path.
- `RejectRoute` flows through the pre-existing generated-reject
  suppression, output-classification, TX-budget, and per-zone
  rate-limit gates, so the newly produced replies inherit the same
  fail-closed suppression as policy/filter rejects.
