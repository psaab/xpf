  - **Action**: Fresh worktree `/var/worktrees/fix-18636`, branch
    `fix/18636-stale-config`, from origin/master `38d23b920b`. Read the
    issue (no comments). The refusal is `configEpochStale`
    (`pkg/cluster/sync_conn_gen.go`, authority branch): it refuses a
    reverse-tagged peer install when `epoch & configEpochGenMask <
    s.configGenCounter.Load()`. The peer stamps its applied generation
    (`stampConfigEpoch`, non-authority branch, when applied ==
    lastRecv and applied > the tenure floor). `configGenCounter` is the
    RESERVATION counter (`ReserveConfigGen` → `nextConfigGen` →
    `Add(1)`, seeded from MonotonicNanos). It is not the newest generation
    actually written: that is `recordLastSentConfigGen`, called just
    before `writeMsg` in `queueConfigOnConn` and
    `writeConfigWithPeerSnapshotGuard`.

  - **Action**: Found the leak. `reconcileConfigSyncToPeer`
    (`pkg/daemon/daemon_ha_sync.go`) calls
    `activeConfigSnapshotAndReserveForPeer(ss, gen)`, which consumes a wire
    generation, BEFORE its "already pushed for epoch/generation" no-op
    check. `configSyncReconcileLoop` ticks every 30 s. So within 30 s of
    any push, the counter passes the generation the peer applied, and
    every reverse-tagged peer install is refused until the next real push
    (a reconnect or a config change). #18610/#18612's
    `rejectedAsAuthorityConfigGen` feeds only ConfigStale readiness, and
    `configEpochStale` never reads it.
