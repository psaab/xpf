# Issue #16131 — userspace-dp: intern route tables inside ForwardingState only with dual-carry cell

- **Issue:** The per-address local-delivery attributions in `ForwardingState`
  (`local_tables_v[46]`, `interface_nat_tables_v[46]`, nested
  `interface_nat_v[46]`) key owning route tables by canonical table NAME
  (`FastSet<String>` / `FastMap<String, i32>`), so the packet path hashes the
  name string on every local-delivery probe. The proposal: intern those tables
  onto the numeric `RouteIdentity{domain, table}` (already published per
  generation in `route_table_identities`).
- **Dissent preserved (Codex, UNSOUND as a performance cutover):** resolving
  `table: &str` → ID costs a second hash probe before the membership test, so
  a pure interned replacement is strictly more probes than today's single
  string-set lookup. The accepted narrowed form is therefore dual-carry only.
- **What shipped:** Dual-carry interning inside `ForwardingState` only.
  - New interned twins `local_table_ids_v[46]`,
    `interface_nat_table_ids_v[46]` (`FastSet<RouteIdentity>`) and
    `interface_nat_ids_v[46]` (`FastMap<RouteIdentity, i32>`), plus a
    diagnostic `route_table_interning_complete` flag.
  - `forwarding_build::intern::intern_route_tables` derives the twins once
    per build, immediately after `route_table_identities` is assigned and
    after every string-form writer (interfaces, late-stage NAT append), from
    the authoritative string forms and the published identities. Identity is
    never synthesized: a name with no published row is omitted and flips
    `route_table_interning_complete` false; when the identity map itself is
    incomplete (legacy posture) the twins stay empty.
  - The string sets/maps remain the ONLY form any lookup reads — no packet
    code reads the twins, so the packet-path probe count is unchanged by
    construction (the Codex objection's condition). NAT zone interning is
    excluded (separate W3 allocator-API proposal; #6600 load-bearing).
  - **Dual-carry agreement cell** `route_table_dual_carry_agrees` proves both
    carries agree: forward (every carried name's published identity is
    interned for that address), reverse (every interned identity/ifindex is
    backed by a carried name of the SAME address — no phantoms), and
    cardinality. `intern_route_tables` asserts the cell before the state can
    publish; a disagreement panics in the build so the reconcile preflight
    keeps the previous live state (fail closed).
- **Acceptance mapping:** dual-carry agreement cell ✓ (hand-built states,
  corruption cells, and a real two-VRF `build_forwarding_state` build);
  packet-path probe count not increased ✓ (no lookup reads the twins —
  greppable); iperf witness row — NOT RUN (lab-gated; no throughput claim is
  made by this issue, and no packet code changed, so no live witness can
  distinguish this change).
