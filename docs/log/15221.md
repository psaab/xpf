# #15221 (A36-03): failed gap-fence delete after a successful real install reported Current with no fence standing

- **Timestamp**: 2026-10-19
  - **Action**: Tracked a failed `xpf_hostinbound_gap` delete after a successful real install the same way as the pre-activation fence delete — retain the gap-fence spec and OR the retention into `GapFenceActive` at every post-install store — so the applied-state probe no longer claims `Current` with `GapFenceActive=false` while the gap fence still drops. Added RED/GREEN regression plus healed-delete and clean-install controls.
  - **File(s)**: `pkg/daemon/daemon_nft.go` (`applyHostInboundFilterWithOverlay`), `pkg/daemon/host_inbound_applied_7181.go` (`HostInboundAppliedState.GapFenceActive` doc), `pkg/daemon/host_inbound_gap_delete_15221_test.go` (new), `docs/log/15221.md` (this file)

## Mechanism (origin/master `64c99bc8ee`)

- `applyHostInboundFilterWithOverlay`, after `InstallHostInbound` succeeded: the `DeleteTable(xpf_hostinbound_gap)` error was only a `slog.Warn` and `hostInboundGapFenceSpec` was cleared only on success — but no state recorded the failure. The sibling pre-activation delete right below set `preActivationFenceRetained = true` on error.
- The success tail then called `noteHostInboundApplySucceeded()` (which clears `GapFenceActive`) and stored only `preActivationFenceRetained`, so a lingering gap table was invisible: the probe reported `Current()` with `GapFenceActive=false` while `xpf_hostinbound_gap` still dropped admitted services to the fenced address. It fails closed (over-denial), so this is an operator-visible lie, not a fail-open; it healed only on the next successful apply's delete.
- Two further consequences of the same swallow: the retained `hostInboundGapFenceSpec` was dropped from the probe's truth (though kept in the field only on success — on failure the spec pointer was left as-is but unreported), and the `setEarlyInputHandoffDone`-failure tail stored `GapFenceActive=false` unconditionally, re-hiding even a retained pre-activation fence.

## Change

- Introduced `gapFenceRetained` beside `preActivationFenceRetained`: set on gap-delete error (spec retained), cleared with the spec on success.
- All three post-install `hostInboundGapFenceActive` stores (barrier-handoff-error tail, success tail, handoff-marker-error tail) now store `gapFenceRetained || preActivationFenceRetained`. The marker-error tail previously hardcoded `false`.
- The apply still succeeds when only the delete fails: the real table covers the desired set, so failing the commit would misreport enforcement; the truth is carried by `GapFenceActive=true` (the issue's acceptance permits either shape). The next successful real install retries the idempotent delete and clears the marker.
- Widened the `GapFenceActive` doc to name all three standing-fence cases (gap fence, pre-activation fence, failed-delete retention).

NOT changed: the delete itself (still attempted unconditionally after every successful real install), the gap/pre-activation install paths, the teardown path (which already fails closed on delete errors), `Current()` semantics, or any neighbouring fence lifecycle.

## Risk

- A box whose gap delete persistently fails now reports `GapFenceActive=true` indefinitely instead of silently claiming a single-table state; that is the intended truthful direction and remains fail-closed (the lingering fence only over-denies addresses the real table now covers). No traffic behaviour changes: the kernel tables installed/deleted are identical to before; only the reported state and the retained spec on delete failure change.
