# #14574 — `vlan-id` without `vlan-tagging` commits clean; two writers disagree

## Defect

A unit `vlan-id N` (N > 0) without `vlan-tagging` or
`flexible-vlan-tagging` on the parent committed clean with no warning.
The two writers then disagreed about the same address:

- `buildInterfaceNetworkdModels` (`pkg/dataplane/compiler_iface.go`)
  branches on `VlanTagging`; without it, all units' addresses are
  collected onto the untagged parent.
- `resolveInterfaceRef` returns `unit.VlanID` with no tagging test, and
  the zone path calls `ensureVLANSubInterface` when `vlanID > 0`,
  creating the tagged sub-interface `<parent>.N`.

So the host answered on both wires and the dataplane held a duplicate
connected prefix; nothing was reported. (Probe at filing: untagged
`strict OK warnings=[] zone-path phys=ge-0-0-1 vlan=100` +
`networkd name=ge-0-0-1 addrs=[10.0.1.1/24] vlanParent=false`; tagged
control put the address only on `ge-0-0-1.100`.)

## Fix

New strict gate `validateVlanIDTaggingAST`
(`pkg/config/compiler_interfaces_vlan_tagging.go`), doctrinally a sibling
of the #5879 QinQ and #6178 vlan-map gates:

- Runs PRE-expansion in both compile entrypoints
  (`compileConfigWithOpts`, `compileConfigForNodeWithOpts`), expanding
  the candidate once per cluster node (node0 AND node1) so the verdict
  is HA-symmetric: a vlan-id staged under a peer-only group, or tagging
  supplied only in a peer view, is judged on the aggregate view. Falls
  back to the raw tree when neither node expansion succeeds (mirrors
  #6178).
- Semantic, not string-based: only a positive tag fires — `vlan-id N`
  or `vlan-tags outer N` with N in 1..4094 (canonical digits). The new
  `vlan-tags outer` arm covers the spelling whose outer half the
  compiled writers do honour when tagging is on; without this arm the
  same two-writer disagreement would survive under that spelling.
- `vlan-id 0` / `vlan-tags outer 0` (the untagged sentinel), units with
  no tag, and malformed values (owned by the schema/numeric gates) stay
  legal.
- Declared dotted bases (`p.0`, #8994/#9821) are out of scope: their
  units' devices derive from the dotted base itself, and the #9821
  dotted-sibling MTU shapes depend on that derivation.

- Strict: hard error naming interface, unit, and both writers'
  divergent devices. Lenient (`lenientVlanIDTagging`, set only in
  `lenientCompileOpts`): warning, compiled shape unchanged (#1960
  no-brick).

Fixture migration: `TestNonCollidingVlanSubInterfaceStillCompiles7795`
now carries `vlan-tagging` on both parents — without it the shape is
this defect, not a legitimate non-colliding control. Its sibling
`TestVlanIDSubInterfaceCollidesWithAuthoredName7795` still fails
strict compile (now via #14574, whose message names the authored
device `ge-0-0-0.100` that test asserts).

NOT changed: the dataplane writers themselves. On the lenient path both
writers keep their historical behaviour (the warning is the diagnostic);
making them agree there would silently move addresses for
already-persisted configs. Junos parity ("vlan-id only on tagged
interfaces") is supporting only — the load-bearing contract is the
in-tree writer inconsistency, per the issue.

## Risk

Strict commits that previously (silently, wrongly) accepted
untagged `vlan-id` now fail with a remedy message; operators add
`vlan-tagging`. Lenient loads are unaffected apart from the warning.
