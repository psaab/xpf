## Review fold (PR #18538)

- **Timestamp**: 2026-10-30 (fold)
  - **Action**: Finding 1 verified at the cited line and folded. The
    ct-slice fabric swap (`run_ct_slice`,
    `afxdp/worker/loop_body/ct_slice.rs`) clones the published forwarding
    state, replaces `fabrics` with the coordinator's live fabric set and
    adopts the copy, keeping the published `publish_epoch`. That is a
    worker-visible state whose contents differ from the published snapshot
    under the same identity, so the round-2 risk statement ("
    `publish_runtime_view` is the only production constructor of a
    worker-visible forwarding `Arc`") was wrong. Fix: the swap restamps its
    copy with `ForwardingState::restamp_local_derivation`, a process-wide
    counter with the high bit set (`LOCAL_DERIVATION_EPOCH_BIT`), a range the
    coordinator's count from 1 never reaches. Not epoch 0: 0 disables both
    memos until the next coordinator publish; a fresh epoch costs one
    re-resolution per flow, the same as a publish. The swap is the only
    worker-local derivation of a forwarding state (searched: every other
    worker adoption is `refresh_runtime_view` taking the published `Arc`).
    Severity as read: neither memoised function reads `fabrics` today
    (`connected_owner_rg_for_target_in_table` reads the connected-owner
    index; the learn derivations read the on-link, owned-IP and VLAN-alias
    tables), so the kept epoch was a hazard for any later memo over
    fabric-dependent state rather than a wrong answer observed now. Cost:
    the swap runs only while the coordinator's published fabric set and
    a non-empty `ha.fabrics` differ, which the coordinator leaves open only
    between its `ha.fabrics.store` and `publish_runtime_view` (fabric
    refresh stores first, the reconcile apply publishes first); in that window the
    worker re-adopts the published `Arc` each tick and re-derives, so the
    memos re-resolve each tick there and nowhere else.
