# #12167 — fail closed on backward-clock confirm recovery

- **Issue**: #12167 — standalone commit-confirmed recovery could re-arm an unbounded timer after a backward wall-clock step.
- **Original base**: `a714c90d472a3c3d98a3799831cfef3ec311a61c`
  (stack base `b6f0d9f5888f1c6af971a56fb57564133762c5fd`, containing #12154 and #12155).
- **Branch**: `fix/12167-clock-skew`
- **Worktree**: `/var/worktrees/12167-clock-skew`

## Why

`recoverPendingConfirmLocked` computed the recovered timer as `Deadline - current wall time`. If reboot recovery ran with the clock before the persisted `ArmedAt`, standalone nodes had no cluster skew alarm to force rollback; a 10-minute window with the wall clock 30 days behind re-armed for 720h10m. `time.AfterFunc` uses a monotonic timer, so a later wall-clock correction would not shorten it. Elapsed downtime is unknowable in this state, so trusting the shifted deadline could leave the unconfirmed config active far beyond its original window.

## What

- Treat a current wall clock before a non-zero persisted `ArmedAt` as conclusive backward-step evidence and use the existing fail-closed boot rollback path, including durable config/record resolution and a specific warning/journal reason.
- Bound any recovered `AfterFunc` delay to the lesser of `Deadline - now` and the duration represented by `Deadline - ArmedAt`; cap records without `ArmedAt` to `MaxCommitConfirmedMinutes`.
- Preserve normal remaining-time re-arm and the existing active daemon clock-skew alarm behavior. Document the policy and its inability to reconstruct downtime.
- Preserve #12155's first-window teardown-marker behavior on the stacked branch; add a first-commit backward-clock recovery test that asserts its durable teardown debt remains.

## Risk / residual

A reboot with a wall clock before `ArmedAt` now immediately reverts the pending commit-confirmed change; this can be earlier than the intended timeout when boot time is untrusted, but avoids extending an unconfirmed configuration by unknowable downtime. Legacy records without `ArmedAt` cannot recover their exact original duration; their recovered timer is bounded by the API's 65,535-minute maximum. No monotonic deadline is persisted across reboot.
