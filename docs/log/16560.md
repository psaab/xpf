# #16560: per-set 256 expanded-rule cap removed — contiguous policy ID allocation

- **Timestamp**: 2026-10-24
- **Action**: Strict commit capped each zone pair and the whole global
  rulebase at 256 expanded rules because runtime policy IDs were
  `policySetID*256 + ruleIndex`. Removed the per-set cap everywhere:
  runtime PolicyIDs are now contiguous per-set ranges (each set starts at
  the cumulative expanded offset of earlier non-quarantined sets) via the
  `walkPolicyRuleSlots` SSOT, mirrored by the legacy `compilePolicies`.
  All slice-index counter handles now go through the single
  `userspace.PolicyCounterID` helper (CLI/gRPC/REST/metrics/bulk resolver);
  the runtime-ID namespace and the counter-handle namespace stay distinct
  as before. Legacy eBPF `policy_rules` is indexed by the contiguous
  RuleID (map capacity 4096*256 » 65536 total cap) and a single legacy
  set is bounded by the u16 `NumRules` field (65535). Remaining limits,
  enforced at both commit and apply: total expanded rules 65536 and 4096
  policy sets (documented in `docs/config-schema.md`). Quarantine
  accounting mirrors the walker in the strict validator.

- **Validation**: 257/1000-in-one-pair and 257-global probes commit
  (config), build snapshots with unique contiguous IDs (userspace), and
  compile in the legacy compiler; ID stability across an unrelated edit
  in a later set is pinned (earlier sets unchanged, later sets shift by
  the inserted span — the documented positional contract swept by daemon
  invalidation). Targeted suites green — see PR body for counts.
- **Residual**: Rolling upgrade — a pre-#16560 peer stamps sessions with
  block-layout IDs while this node stamps contiguous IDs; policy *names*
  in RT_FLOW resolve via the admitting node's own PolicyNames generation,
  and counters are name-keyed, so the skew is attribution-only and heals
  on upgrade completion. Sessions admitted under the old layout keep
  their frozen IDs until re-evaluation/invalidation.
