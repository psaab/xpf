# Issue #16669: wake LLDP RX goroutine via ppoll+eventfd so Stop/re-Apply cannot hang on a silent link

- **Timestamp**: 2026-10-25
  - **Action**: LLDP `Stop()`/re-`Apply` could not wake the RX goroutine parked in `unix.Recvfrom` on the AF_PACKET socket: `shutdown()` returns ENOTCONN on the connectionless socket and `close()` does not wake an in-flight Recvfrom on Linux, so teardown blocked until a frame arrived (forever on a silent link, the norm for `interface all` members), holding `lifecycleMu` — and in the daemon `applySem` inside `applyConfigLocked` — wedging every later commit/rollback/HA apply, with shutdown then taking the `TimeoutStopSec=20` SIGKILL path; the freed fd number could also be reused under the parked reader. The #2035 socketpair test could not see it because `shutdown` does wake a connection-oriented SEQPACKET reader. Fixed by making recv cancellable: each `ifSession` now owns a non-blocking CLOEXEC wake eventfd, `recv` waits in `unix.Ppoll` on `{rxFD, wakeFD}` and only calls `Recvfrom` once the RX fd is readable (frame wins if both are ready; the level-triggered wake is not lost), `stopLocked` is reordered to cancel → `signalStop` (one 8-byte eventfd write per session) → `wg.Wait()` → `close()` (signal → wait → close, so no recv is ever in flight on a closed/reused fd and no `shutdown()` is issued), and `rxLoop` re-checks `ctx` after every successful recv so a frame racing Stop is neither learned nor looped on. The socketpair-only seam was replaced: injected sessions carry a real wake eventfd through the production ppoll path, and the silent-vs-chatty acceptance cell uses real AF_PACKET sessions on a veth pair in a private netns.
