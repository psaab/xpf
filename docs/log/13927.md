# 13927 — Fence new static addresses before activation

## Boundary

Issue #13927 identifies a day-2 apply window: dataplane publication makes a
newly configured static address locally deliverable, networkd activates the
address in the apply core, and the host-inbound nft table is only rendered in
the tail. Until that final render, a listener can receive traffic under the
prior table, which has no destination rule for the new address.

## Change

Before any link-affecting apply step, render the incoming config's host-inbound
views from the same config-backed interface snapshot used by the normal ruleset
and compare its deny destinations against the retained table's recorded
coverage. Install an additive host-inbound gap table for uncovered destinations
before the dataplane/networkd sequence. The temporary fence denies host services
uniformly (while preserving only mandatory protocol handling and lifeline-shared
ingress); the normal full host-inbound render retires it after the address
policy is ready. A gap-install failure aborts the apply before address
activation. Configured static unit addresses are present in the snapshot before
networkd brings them up, so this covers the static-address sibling to DHCP
day-2 backstops.
