# #16830: stale-owner refusal triggers unfenced compensating rollbacks (R3-F11-01)

- **Timestamp**: 2026-10-25
- **Action**: #15539 fenced every direct host-auth write, but a superseded
  closeout owner's *compensating* actions still ran unfenced and undid the
  newer authority's work. Three arms fixed:
  - Key/password/shell markers: `ownershipClaim.rollback()`
    (`pkg/daemon/login_password.go`) called the raw
    `removeProvenanceMarker`. A stale owner parked between its fenced
    claim (marker absent → `preExisting=false`) and its fenced
    `authorized_keys` write resumed after a newer authority had written
    K2 under the now-pre-existing marker; the write refused stale and
    the rollback then unlinked the marker, so the next marker-gated
    empty-key revocation left K2 installed while the commit succeeded.
    `rollback()` now routes through `removeProvenanceMarkerFenced14969`
    (single fix point — every caller: key, password, account, shell
    and root claims — inherits the fence; the fenced removal reports the
    stale error and the existing best-effort warning logs it).
  - PAM faillock: `applySSHConfig`'s deferred
    `restoreSSHPAMFaillockOnRollback` wrote through the raw
    `sshdPAMWriteFile = fsatomic.WriteFileAtomic`
    (`pkg/daemon/ssh_faillock_11492.go`), stripping/restoring over the
    faillock a newer authority had just installed.
    `sshdPAMWriteFile` is now `guardedWriteFileAtomic14969`,
    `restoreSSHPAMFaillockOnRollback` seam-checks at entry (covers the
    strip leg, which only reaches the write at its end), and the
    deferred caller in `applySSHConfig` skips stale /
    completed-superseded triggers instead of joining a spurious
    rollback failure. The sshd drop-in `revertDropIn` already went
    through the fenced `sshdWriteFile`/`sshdRemoveFile` and is
    unchanged.
  - Exec seam: `runWithHostAuthExec15539`
    (`pkg/daemon/exec_timeout.go`) discarded a completed child's
    result for the stale sentinel, so `reconcileUserPassword` rolled
    back the password/account claims for a chpasswd that may have
    landed. It now distinguishes a watcher-killed child
    (`ctx.Err() != nil` → plain `errHostAuthStaleOwner14969`, nothing
    completed) from a child that ran to completion before
    supersession was observed: the latter returns its real
    output/error marked with the new
    `errHostAuthExecCompletedSuperseded16830`, which deliberately does
    NOT wrap the stale sentinel, so claim rollback abstains while the
    supersession stays fail-visible.

- **Residual**: The completed-but-superseded exec classification keys
  on the watcher not yet having cancelled `ctx` at the post-check; a
  child that exits naturally in the same instant the watcher cancels
  can still classify as killed (plain stale, rollback proceeds) — the
  fail-safe direction for a mutation whose landing is unproven, and
  the same 1ms race window #15539 accepted. In this non-root sandbox
  the newer authority's durable key write itself EPERMs on
  `WithOwner` chown (pre-existing #15539 control caveat), so the
  end-to-end cell asserts marker survival + marker-gated revocation
  rather than K2 bytes; on a root-capable box the write lands under
  the same marker. No full selftest run (per lane instructions).
