# Issue #12835 — research D2-13: packed apply-meta in zone members

## Confirmed behavior and correction

`zoneInterfaceKeysBeforeBody` previously split a member's Keys only at
`host-inbound-traffic`. Meta tokens (`apply-macro`, `apply-groups`, and
`apply-groups-except`) and their arguments in a packed member's own Keys were
therefore returned as interface names. Child-node meta statements were already
skipped by `zoneInterfaceMembers`. The splitter now terminates at apply-meta
keywords too, suppressing their arguments and macro children. The packed-tail
walk also stops at own-Key apply-meta only before a body keyword; after one, meta is an ordinary tail token (B1 fold) and skips apply-meta child subtrees, so
opaque macro payload is not read as interface content.

Parser-level regression runs `SchemaValidate`, strict `CompileConfig`, and
lenient `CompileConfigLenient` on a valid in-Keys apply-macro form. Its payload
contains a host-inbound-looking non-member token; only the actual interface may
survive as zone membership. Unit cases cover all three meta keywords and the
adjacent host-inbound body boundary.

## Resolving-run gate claim: not included in this PR

`compileZones` expands security-zone resolving runs, while the two strict
zone-interface gates inspect direct children. I investigated adding the same
expansion to both gates, but did not retain it: a fixture whose expansion split
`host-inbound-traffic` into a sibling lost the packed-tail signal, so naive
expansion could suppress the ambiguity the packed-tail gate is meant to reject.
The non-empty synthetic fixture did produce a gate error, but I did not establish
a reachable full-pipeline miss on a valid strict or tolerant config. The issue's
scalar-schema refutation also notes that packed `screen` and `description` tails
are rejected by strict schema validation. Therefore this PR ships only the
demonstrated apply-meta correction; the resolving-run gate hypothesis remains
unvalidated and is not treated as fixed here.
