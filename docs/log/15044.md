# #15044 — positional naming re-indexes over a live non-PCI fxp0 holder on upgrade (A33-01)

- **Severity / consensus**: Medium, bounded population (positional-mode
  box with a USB NIC that sorted ahead of the PCI NICs at its xHCI BDF);
  MATERIAL 3-way in validator research `research-work.AdQvt1jMKw`. A
  pure software upgrade plus reboot rebinds mgmt/zone names to
  different cables.
- **Mechanism**: #14595 (`extractPCIAddr`, `pkg/daemon/linksetup.go`)
  stopped returning a USB NIC's xHCI controller BDF as its PCI address,
  so `enumeratePCINICs` now skips the USB NIC entirely (empty BDF). On a
  box where a pre-#14595 build had named that USB NIC `fxp0`, the first
  post-upgrade `renamePositional` saw only the PCI NICs, assigned `fxp0`
  to the first of them, and phase 2 ran `writeLinkFile(fxp0, <PCI kernel
  name>)` — rewriting `10-xpf-fxp0.link` — before the rename `EEXIST`ed
  against the still-live USB `fxp0` (warn-only at
  `daemon_run_naming.go`'s boot caller). The next boot's udev then bound
  `fxp0` (management, zones, addresses) onto the PCI cable, and the USB
  NIC fell back to its kernel name.
- **Fix** (`pkg/daemon/linksetup.go`): `enumerateAndRenameInterfaces`
  now scans the live interface list (`liveInterfaceNamesFn`, sysfs in
  production) via `livePositionalHolders` before assigning any index.
  A live netdev wearing a positional name (`fxp0`, cluster `em0`,
  `ge-{0,7}-0-N`) that is not among the enumerated PCI NICs refuses the
  whole positional pass loudly (error on the existing #5842 naming
  channel, so the one-shot config-arrival retry marker is preserved)
  before any `.link` write, rename, or reload. A scan failure likewise
  refuses — re-indexing blind is the fail-open being removed. The
  operator resolves the refusal with a `chassis device-map` (the USB
  NIC is bindable there by permanent MAC, #4884) or by removing the
  stale positional name. No `.link` is rewritten and the next-boot
  mapping is unchanged.
- **NOT changed**: `extractPCIAddr` / the #14595 non-PCI skip (correct —
  a USB NIC has no PCI positional identity), `renamePositional` itself
  (its collision discipline is sound once the enumeration is complete),
  and device-map mode (already identity-based and unaffected).
- **Residual**: a pre-#14595 box whose USB NIC held a positional name
  now boots with positional naming refused (PCI NICs keep kernel names,
  management stays on the USB `fxp0` where the config expects it) until
  the operator configures a device-map. That loud, reachable state is
  the intended fail-closed outcome; silently keeping the name working
  would require positional naming to adopt non-PCI NICs, which #14595
  deliberately removed.
- **RED evidence**: (a) the new tests reference the new seam, so they
  fail to build on pristine master; (b) behavioral probe of the exact
  mechanism on master code (PCI-only enumeration `enp5s0`, live USB
  `fxp0`, pre-upgrade `10-xpf-fxp0.link` with `OriginalName=enx…`):
  `renamePositional` rewrote the file to `OriginalName=enp5s0` while
  live `fxp0` stayed on the USB NIC — the rewrite-before-EEXIST that
  rebinds the next boot.
- **GREEN evidence**: `TestPositionalUpgradeUSBHolderRefused15044`
  (refusal names `fxp0`/`#15044`, zero renames, `fxp0.link` bytes
  unchanged, no new `.link`), `TestPositionalHolderScanFailureRefused15044`
  (scan error refuses), `TestPositionalNoHolderControl15044` (USB at
  kernel name: normal pass persists and renames exactly as before),
  `TestLivePositionalHolders15044` (enumerated/cluster/syntax pins).
  Adjacent suites (`TestRenamePositional*`, `TestBreakNameCollisions*`,
  `TestEnumerateAndRenameInterfaces*`, `TestPositionalNaming*`,
  `TestConfigArrivalNaming*`, `TestDeviceMap*`) pass; `go vet` clean.
