# 7007 — the link-cycle lease released at the FIRST repair, not the last

## Premise check first

Verified at `origin/master` (`44a335624`) before writing code. **PREMISE HOLDS**,
every behavioural claim, with one immaterial erratum: the two cited line numbers
have drifted uniformly by +30 (step 2.6b2's release is `:371`, not `:341`; the
loop ends `:347`, not `:317`). Both were byte-exact at `656b6b9cc`, the revision
the issue was written against.

Two additions the check turned up that the issue does not mention:

- The `renameJoin` hook is a **third** acquire site with no release partner at
  all (`renameRethMember` never notifies, and the renamed member then hits
  `programRethMAC`'s `bytes.Equal` early return, leaving the gate clear). The
  deferred-abandon ERROR is therefore already reachable on a non-bug path —
  which **strengthens** the "don't refcount" argument rather than weakening it.
- The mixed path issues **two** `NotifyLinkCycle`s, not one; the second is a
  release-when-not-held. The count that matters for the bug is *when protection
  ends*, not how many calls occur.

## The defect, measured

Acquire is per MEMBER (inside the loop); release was per REPAIR (one per aborted
member's rollback, plus at most one for the whole apply at step 2.6b2, outside
the loop and gated on `needLinkCycleRecovery`). The binder's trace at the
pre-fix revision:

```
acquire  renew  renew  prepare-failed  notify(release)
         renew(NO-OP: lease already released) x3  notify(release)  abandon
```

Three renewals against a zeroed word, because `RenewLinkCycle` refuses the `0`
sentinel. While the lease is down the 1 Hz status tick's **whole body** resumes,
ctrl stops being pinned at 0 (`ctrlMustStayDisabledLocked`),
`set_forwarding_state` stops being deferred, and three operator verbs stop being
refused — against a helper that is still half repaired.

## Why not a refcount — kept, because it is still the obvious wrong answer

Acquires and releases do not pair. Two members both cycling is **two acquires and
one release**, so a refcount would sit at 1 on the most ordinary multi-member
commit, strand the lease to the deferred abandon, and make that backstop's
"leaving with a RETH link-cycle lease still held" ERROR routine noise. That is
worse than the gap it closes.

## The fix: separate REPAIR from RELEASE

The two acts were fused in `NotifyLinkCycle`, and the fusion is the bug. An
aborted member genuinely must rebind — its own workers are joined, its ctrl is
off, nothing else will undo that — but it has no business ending the *apply's*
lease to do it.

- The in-loop rollback calls the new `NotifyLinkCycleKeepingLease`: identical
  rebind, and it **renews** the lease rather than releasing it, so the repair's
  own duration cannot be what expires it.
- Release moves outside the loop, in two arms that together make it
  unconditional in effect:
  - step 2.6b2's `NotifyLinkCycle`, when some member actually cycled;
  - an explicit end-of-apply `AbandonLinkCycle`, gated on
    `rethRollbackKeptLease`, for the apply where **every** member aborts — which
    reaches no `NotifyLinkCycle` at all and would otherwise strand the lease,
    arriving at the refcount's failure mode by another route. `AbandonLinkCycle`
    rather than a second rebind, because the rollbacks already rebound: what is
    owed there is the release, not another NIC-settle second on a path where the
    commit is failing anyway.

The gate stays scoped to `rethRollbackKeptLease` rather than "release whatever is
held", so the deferred abandon keeps its teeth for the rename-join hook.

## The failed-rollback-rebind residual, re-decided

The old ordering made it moot by accident — the lease was already gone before the
rebind could fail. Under a last-repair release it is a real question, and the
answer is that the lease is **still released**, by the end-of-apply arm. That is
deliberate and it is the same trade `docs/reth-mac.md` already argues for the
single-member case: on a path where this node's forwarding is down, a stranded
lease would add a frozen reconcile loop to an outage in progress. What changes is
that protection now covers the whole apply *including* the failed-rebind window.

## Three project gates fired, and all three were right

| gate | what it pins | why it fired |
|---|---|---|
| `TestLinkCycleLeaseHasExactlyOneAcquisitionSite_6871` | an allowlist keyed on the ENCLOSING FUNCTION NAME of every `PrepareLinkCycle` | splitting the join helper into a renamed inner function MOVED the sole production acquisition site |
| `TestEveryControllerAdapterMethodIsBound_6871` | every adapter forwarder has a binding-table row with a driver | the new `NotifyLinkCycleKeepingLease` had none |
| `TestDaemonPassesRethBeforeCycleHook_5103` | `programRethMemberMAC` has exactly ONE call site, and its result is assigned straight back into the apply's accumulators | routing the loop through a renamed inner function left the real one with zero call sites; then the third return value changed the assignment shape |

Two of the three fired because of a RENAME, which is the point: a rename is how
an acquisition site or a fold silently escapes its guard. Both renames were
collapsed into widened signatures, leaving the guarded names — and therefore the
gates' containment proofs — untouched.

## The fixture had to be built, and its first two versions were wrong

Three existing pieces each blocked reuse: `rethCallsiteConfig` is deliberately
one member; `newRecordingRethOps` returns a single shared fake link that ignores
the interface name, with one global `liveFail`; and
`abortRecoveryLinkController` models the lease as a bool only `AbandonLinkCycle`
clears, so it cannot observe "still held".

**Order independence is load-bearing.** The apply iterates `rethToPhys`, a Go
map, so member order is randomised per run. The error is injected by CALL order
rather than by member identity, and the assertions are counts and invariants
rather than sequences — which is what stops the binder being a 50/50 flake.

Two defects in my own test work, both caught by the mutation matrix rather than
by review:

**1. The assertion could not distinguish leak from release.** The abort-only test
asserted "the apply finished with the lease released". The deferred
`abandonLinkCycleLease` clears the word on *every* exit, so that is true whether
the apply released it or leaked it — cell R2 passed against a build with the
end-of-apply release deleted. The discriminator is what the deferred backstop
**found**: if it still found a held lease, the apply leaked one and that backstop
logs its ERROR.

**2. The fake modelled the wrong acquire point.** It released the lease when
`PrepareLinkCycle` errored, on my guess that a failed prepare arms nothing.
Production does the opposite and says so — the acquire precedes the fallible work
because "the window that needs covering opens at the ctrl disable, not at the
successful join" — and `TestPrepareLinkCycleHoldsTheLeaseWhenTheJoinFails_6871`
pins it. Because the abort-only fixture fails *both* members' prepares, the wrong
model left it holding no lease at all: nothing to leak, and R2 passed again. The
fixture was certifying an arm it never reached.

Both are the same shape — a fixture that cannot produce the state it asserts
about — and both were invisible until a mutation asked it to.

## Validation

- `go build ./...`, `go vet ./...` clean.
- `go test ./... -count=1` rc=0, with the FAIL count taken from the whole log.
  (An earlier claim on this branch came from a run piped through `head -20`,
  which truncated the FAIL line away and read `head`'s exit code. That is how a
  real breakage on the sibling #6988 branch survived one extra commit.)
- Mutation cells R1-R3 above.
- **Cluster smoke RUN** on the loss userspace cluster under the shared lock:
  `make cluster-deploy` (both nodes sha256-verified against the local build) +
  `./test/incus/apply-cos-config.sh loss:xpf-userspace-fw0` + `make test-failover`
  -> **16 passed, 1 failed**.

  Every HA assertion passed, and they are the set this change could disturb:
  crash failover (sysrq reboot of the primary), rejoin as secondary with no
  auto-preempt, manual failover back, session sync (20 sessions synced within
  5s), and IPv4 + IPv6 transit before and after each transition.

  The one failure is **#7847**, the known fixture collision, not a regression:
  `test-failover.sh` runs iperf3 on the DEFAULT port 5201 and
  `cos-iperf-config.set` — which the deploy protocol requires re-applying — maps
  5201 to forwarding-class `iperf-100m`. Same box, same minute, same build:

  | port | class | throughput | retransmits |
  |---|---|---|---|
  | 5201 | `iperf-100m` | 92.3 Mbit/s | 1684 |
  | 5211 | `iperf-uncapped` | **22.2 Gbit/s** | **0** |

  22.2 Gbit/s at zero retransmits is a healthy dataplane on this branch, in the
  band the engineering-style validation table expects. An `IPERF_PORT=5211`
  override does not help because the script does not read one — which is
  precisely what #7847 asks for.

  **What the smoke does NOT cover, stated because the issue says so.** On this
  cluster the mlx5 VFs accept the live MAC set, so `programRethMAC` returns at
  its `liveSetErr == nil` early return and `beforeCycle` never runs — no lease is
  ever taken. The smoke therefore proves the change did not break the HA path; it
  does not exercise the lease at all. The multi-member ordering is bound by the
  unit binder instead, which is why that binder had to be built rather than
  deferred to the cluster.
