## Divergence found while building the fixture (fixed, not just pinned)

Writing the mode-2 duplicate-pool row from the dataplane's current code
showed the Go mirror had diverged a fourth time: `expandPoolV4` deliberately
did **not** dedupe mode-2 pools, on the claim that NAT64 `parse_pool_v4`
"pushes each parsed host verbatim (no seen-set)". That was true of the
function but false of its caller: `parse_nat64_rule`
(`userspace-dp/src/nat64/state.rs`, #14624 in `8ed8cf0733`) threads a
first-occurrence seen-set through `parse_pool_v4`, so a duplicated NAT64
pool member has exactly one allocator position and `host_count` is computed
from the deduped length. Go kept both positions, so for a pool such as
`[198.51.100.1, 198.51.100.1/32, 198.51.100.2]` the Go forward/reverse
answers (and the pool-bounded capacity) named a different subscriber than
the dataplane enforces — the same lawful-intercept wrong-subscriber class
as #14623. Fix: `expandPoolV4` now dedupes first-occurrence in both modes;
`TestDeterministicNAT64PoolExpansionDoesNotDedupe14623` is flipped/renamed
to `TestDeterministicNAT64PoolExpansionDedupes14624`, and the fixture's
`v6-14624-duplicate-pool-deduped` vector pins it on both sides.

## Risk

- Behaviour change only for deterministic NAT64 (mode-2) pools carrying a
  duplicated external address: those pools were answered with a shifted
  index space before, i.e. the wrong subscriber; every other pool's
  expansion is byte-identical (the seen-set only drops exact repeats).
- Mode-1, port-range, and arithmetic paths are untouched except comments.
- The fixture is additive: no wire format, snapshot, or protocol change.
