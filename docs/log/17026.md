# #17026 — redistribute chain composer clone of the BGP chain composer (R4-Q42-03)

- **Timestamp**: 2026-10-28
- **Action**: Single-sourced the two chain composers. The #15156
  redistribute composer (`renderRedistComposedMapVariant16864`) was a
  renamed clone of the #5277 BGP composer
  (`renderComposedRouteMapWithDefault`) with its own hand-summed
  overflow predicate (`total += config.RouteMapSequenceCount(...)`)
  in place of the shared SSOT `config.ComposedChainSequenceCount`.
  Both render loops and both overflow arithmetics now live in one
  implementation, `composeChainRouteMap` in the new
  `pkg/frr/route_map_chain.go`: adapters prepare ordered
  `[]namedPolicy` members plus a `chainTail` {fallbackAction,
  carvedBGPOnly, leadingTagDeny} and delegate. The BGP adapter passes
  the authored statements (byte-identical former call); the
  redistribute adapter passes its per-source, per-variant filtered
  statements, so the belt counts exactly what will render — the SSOT
  truncates at the first terminating filtered member and saturates,
  where the hand sum did neither reliably (non-saturating addition
  could also wrap a saturating member count). The OR-composed
  pre-check in `renderRedistOrComposedMap16868` hand-summed the same
  way and now uses the same SSOT over its filtered members. No strict
  commit gate was added for redistribute chains: the rendered count
  depends on per-source/per-variant filtering the config-side gate
  cannot reproduce without duplicating the renderer, so redistribute
  chains remain render-belt-only — recorded in `pkg/frr/README.md`
  (the belt renders the bounded quarantine deny on the tolerant
  path). Acceptance greps: `RouteMapSequenceCount(po, f)` no longer
  appears in `pkg/frr/redistribute.go`, and `defaultVerb` now lives
  in exactly one non-test file (`pkg/frr/route_map_chain.go`).
  STEP-0 note: on current master the plain terminating shape from
  the report already renders 4,001 sequences (the #16868 fix had
  hand-copied the truncation into the clone's count loop after the
  report's verification revision), verified by direct-construction
  and strict-gate probes before editing; the live defect removed is
  the duplicated algorithm and its divergent-by-construction
  arithmetic, including the separate re-derivation of filtered
  statements for counting vs rendering.

- **Risk**: Byte-identity was the design constraint: the shared
  composer preserves both former render loops' sequence allocation,
  default handling, next-policy retargeting, carved tail, and the
  cluster leading tag deny; the #15156/#16868/#5277 suites and the
  16125 goldens passing unchanged is the evidence. Residual risk is
  in shapes no existing cell renders (e.g. duplicate member names,
  variant-filtered next-policy terms) — spot-checked by hand during
  development with identical old/new output. The redistribute belt
  now counts filtered statements through the SSOT, which can differ
  from the old hand sum only where the two already disagreed with
  the render loop; the direction is fail-closed (quarantine deny)
  and matches what actually renders.
- **Fold (PR #18306 review)**: The carved reserve walk is now
  single-sourced in `pkg/config`: `composeChainRouteMap` calls
  `config.CarvedComposedExtraSequencesForStatements16869` over the
  statement map it renders, and
  `CarvedComposedExtraSequences16869` delegates to the same walk over
  `po.PolicyStatements` — the former `pkg/frr` mirror
  (`carvedComposedReserveFor16869`) and the dead
  `carvedComposedReserve16869` wrapper are deleted, so a future
  config-walk change cannot silently diverge the BGP render belt
  from the strict gate (an under-reserve of 1 at the 65535 boundary
  would reopen #5701 poisoning). Quarantine byte delta, claim
  accuracy only: on the redistribute path an oversized chain's
  quarantine deny previously ended with a trailing double `!`
  separator (the old clone returned
  `renderQuarantineDenyRouteMap(name) + "!\n"` and its caller
  appended another `"!\n"`); the shared composer returns the deny
  without the trailing separator and the caller appends exactly
  one, so the emitted bytes carry a single `!`. This is
  behavior-preserving — `!` lines are FRR config separators with
  no semantics — and no other rendered byte changed.
