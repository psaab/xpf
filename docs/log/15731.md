# #15731 — master unit suites red: pkg/config x3 + pkg/cluster 9752 golden

Smoke-matrix on origin/master (7d95e004cb / be68c567ec) found four failing
tests. Each was triaged as real regression vs stale fixture/golden; the
dispositions differ per test, which is why this is not a blanket regen.

## 1. `TestZoneInterfacePackedApplyMacroOwnKeysCompiles12835/strict` — REAL REGRESSION (code fix)

Fixture (unchanged, correct):

```
security { zones { security-zone Z { interfaces {
  ge-0/0/0.0 apply-macro M { host-inbound-traffic ge-0/0/9.0; } } } } }
```

An `apply-macro` on a zone-interface member's own Keys owns its braced
payload (#12835): `ge-0/0/9.0` is opaque macro data, not a member and not
host-inbound content. `zoneInterfaceMembers` and
`zoneInterfaceMemberPackedTail` already honour that (`zoneInterfaceKeysBeforeBody`
stops at apply-meta), but the per-interface host-inbound reader in
`compileZones` did not: the parser attaches the macro body as the member
node's `Children`, so `FindChildren("host-inbound-traffic")` found the
macro's `host-inbound-traffic ge-0/0/9.0` line, `parseHostInboundNode`
recorded `ge-0/0/9.0` as an unknown child, and the strict gate
(#14352, `validateHostInboundUnknownChildrenStrict`) hard-rejected with
`interfaces "ge-0/0/0.0" host-inbound-traffic has unknown child keyword
"ge-0/0/9.0"`. Lenient compiled but minted a phantom deny-all
`InterfaceHostInbound["ge-0/0/0.0"]` override from macro data.

Fix (`pkg/config/compiler_security_zones.go`): skip the HIB read for a
member node entirely when apply-meta stops its own Keys
(`zoneInterfaceHasApplyMeta` distinguishes apply-meta from a body-keyword
stop, so the ordinary packed-body path is untouched). This mirrors the
existing member/packed-tail readers — no new convention. Verified RED on
revert (strict fails with the exact message above) and GREEN with the fix;
`TestZoneInterfaceMetaAfterBodyTailStillRejects12835` (meta *after* a body
keyword must not void the packed-tail signal) still passes, as do the
`TestPerInterfaceHostInbound*` / `TestHostInbound*` suites.

## 2. `TestStreamSourceInterfacePrecedence_6875` (3 subtests) — STALE FIXTURE

The fixture authored `reth1 unit 100` with no `vlan-tagging`/`vlan-id`.
That is exactly the defect #15034 (PR #15383) now strict-rejects: a
non-zero untagged unit on an untagged parent resolves to a `reth1.100`
device nothing creates, while its addresses fold onto the untagged
parent. The gate is correct; the fixture predates it. Migrate the fixture
to the gate's own tagged control shape (`set interfaces reth1
vlan-tagging` + `unit 100 vlan-id 100`, as in
`TestUntaggedUnitControlsAccepted15034`). The address
(`10.9.9.9/24 primary`) and the precedence assertions are unchanged.

## 3. `TestSchemaValidate_Interfaces_AcceptedValuesCompileAsWritten` — STALE FIXTURE

Same class, older gate: the fixture authored `ge-0-0-2 unit 50 vlan-id 50`
without `vlan-tagging`, which #14574 (PR #14787) strict-rejects (writers
disagree, duplicate connected prefix on both wires). The test's purpose is
"accepted values compile verbatim", so the fixture must use an accepted
shape: added `set interfaces ge-0-0-2 vlan-tagging`. The
`Units[50].VlanID == 50` verbatim assertion is unchanged.

## 5. `TestInstallTableProducerToResendEndToEnd9752` — STALE GOLDENS (regen, justified)

#15176 added `SessionValue.NatScopeIfindex`/`NatScopeFold` (and #13965
earlier added `PptpCallIDs`); Go's `encoding/json` marshals new struct
fields unconditionally, so the installed pair now carries
`NatScopeIfindex:0, NatScopeFold:0, PptpCallIDs:0` that
`pkg/dataplane/userspace/testdata/installed_val_9752.json` lacks. All
three are zero — no scope was recorded for this fixture session and no
PPTP association exists — so no behaviour changed; only the JSON shape
grew. Regenerated via the test's own deliberate-regen env
(`XPF_WRITE_INSTALLED_VAL_9752=1`).

The upstream link has the identical drift and was red on master too
(not in the issue's list, same root cause): `pkg/daemon`
`TestProducerDeltaConvertsToSyncedValue9752` vs `synced_val_9752.json`,
regenerated via `XPF_WRITE_SYNCED_VAL_9752=1`. Field-level diff of both
goldens is exactly the three added zero fields; the session key and every
other value are byte-identical.

Downstream consumer verified unchanged: `pkg/dataplane/userspace`
`TestInstalledValBuildsTheImportRequest9752` still passes and
`synced_request_9752.json` needs no regen — the builder reads
`NatScopeFold` (0) and resolves no `nat_scope_ifindex`, so the request
JSON is unchanged. The Rust chain links consume only
`pbr_delta_9752.json` / `synced_request_9752.json`, neither of which
changed.
