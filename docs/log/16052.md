# Issue #16052 — reinject Go client never verifies the helper peer; squatter gets decrypted payloads and lying success

## Why

The Go reinject client dialed both helper unix sockets (submit and complete) with a bare `net.DialTimeout` and never checked `SO_PEERCRED`. A squatter listening on the socket path in a non-default (operator-selected, writable/sticky) socket dir received ANNOUNCE plus decrypted IPsec-inner payloads, and could return spoofed completions that the client reported as success while every packet was actually dropped (all completion paths are `VerdictDrop` — blackhole with lying success, no fail-open forwarding). The default root-owned `/run/xpf` disallows squatting, so the precondition is a non-default socket dir plus a local squatter, capping severity at Medium. The #9171 census verified the Rust helper side, never the Go client's peer; #15950's server-side change does not fix this.

## What

`SocketReinjectSubmitter.dial` — the single choke point for both the submit and complete streams — now verifies the peer via `SO_PEERCRED` immediately after connect, before any byte (ANNOUNCE, decrypted payload, or completion poll) is written, and closes/refuses the connection on failure. The trust decision mirrors `verifyUnixPeerIsPrivileged`/`peerCredTrustError` in `pkg/dataplane/userspace/socket_trust_9003.go`: only root (uid 0) or this process's own euid is accepted, which in production is root == root; the euid arm lets a non-root test binary drive the real path against a socket it binds itself. The decision is split from the syscall shell (`reinjectPeerTrustError16052` vs `readReinjectPeerCred16052`) so the hostile foreign-uid case is reachable from a test, and the shell never substitutes a zero `unix.Ucred` for a failed read — a zeroed credential has `Uid 0`, so swallowing the error would fail open. Refusals wrap the sentinel `errUntrustedReinjectPeer16052`. A `peerVerify` seam on the submitter lets tests present a foreign credential on a real socket; the `GetsockoptUcred` seam lets a test force a credential-read failure.

## Validation

- **RED (compile)**: `reinject_peercred_16052_test.go` alone fails to build — `reinjectPeerTrustError16052`, `verifyReinjectPeer16052`, `errUntrustedReinjectPeer16052`, and `reinjectGetsockoptUcred16052` are undefined.
- **Decisive regression**: `TestReinjectSquatterSeesZeroBytes16052` stands up squatter listeners on both socket paths in a `/tmp`-style temp dir and drives ANNOUNCE, a decrypted-payload SUBMIT, and a completion drain through a client whose peer decision is foreign: every arm is refused with the sentinel, each squatter records exactly zero bytes on hangup, and no refused connection is retained. Removing the verify call in `dial` (bare-dial mutant) turns exactly this cell RED — the announce is accepted by the squatter — while the decision/read-failure cells stay GREEN.
- **Fail-closed shell**: `TestReinjectPeerCredReadFailureFailsClosed16052` covers a non-AF_UNIX connection and a forced `SO_PEERCRED` read failure; both refuse with the sentinel rather than falling through as uid 0.
- **No brick**: `TestReinjectTrustedPeerAccepted16052` proves a same-uid helper is accepted, the ANNOUNCE frame flows, and the real peer credential reads back as this process's euid. The pre-existing 9506/13234/14678 reinject socket suites exercise the same-uid path unchanged.
- `go vet ./pkg/nfqueue/` clean; `gofmt` clean on both touched Go files.

## Risk / residual

Peer verification runs once per lazy dial (submit/complete connect or reconnect), never per packet, so there is no dataplane hot-path cost. The check is race-free for the connection it is applied to (kernel-resolved `SO_PEERCRED`), unlike any path/mode check. It does not authenticate beyond uid: a root-compromised peer is still trusted, which matches the existing control/session/event socket posture (#9003/#9171). No live cluster was mutated.
