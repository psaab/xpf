# #14155 — becomeMaster GARP race: concurrent updateVIPs suppresses initial failover GARP

## Why

`becomeMaster` (`pkg/vrrp/instance_transition.go`) bumped `garpEpoch`
0→1 under `vipMu`, unlocked **without populating `pendingGARPVIPs`**,
then launched `go vi.sendGARP(false)` asynchronously. A concurrent
`updateVIPs` adding V3 acquired `vipMu` first, bumped the epoch 1→2,
saw an empty pending set in `pendingGARPForSetLocked`, and announced
only `[V3]`; its `reserveGARPBurstLocked` stored `lastGARPEpoch=2`.
When the deferred failover sender finally ran, it re-read
`garpEpoch==2 == lastGARPEpoch` and was epoch-deduped — V1/V2 never
received a failover GARP/NA, so neighbours kept stale ARP/NDP pointing
at the old master until cache expiry. Pure adds were safe in isolation
(pending verified empty implies the sender had already reserved, so
the bounded added-only scope was intended); the defect is that the
pre-reservation window left no pending record at all.

## What

- `pkg/vrrp/instance_transition.go`: on the success arm only, under the
  already-held `vipMu` and after the epoch bump, record the actuated
  set (`res.applied`, canonical kernel truth including EEXIST) via
  `addPendingGARPVIPsLocked`. Unconditional of `suppressGARP`: a
  suppressed tenure later unsuppressed while MASTER is then entitled
  to announce the full set. Fail-closed rollback arm untouched.
- `pkg/vrrp/instance_garp.go`: the full-set `sendGARP` path now uses a
  pending-aware gate (`reserveGARPBurstGateLocked`) and a `pendingOnly`
  reserved mode: a non-forced full-set sender whose epoch was already
  reserved by a bounded (added-only) membership announcement is admitted
  when pending VIPs remain — subject to the existing 500 ms time
  dampener — and then emits only the still-pending entries, clearing
  each on its synchronous first frame. `sendGARPFor` (bounded membership
  announcements) keeps strict epoch dedup via the original gate.
- NOT changed: advert-before-GARP ordering, 500 ms dampener semantics,
  strict/tolerant (suppress) doctrine, `updateVIPs` announcement scope,
  `reconcileVIP`/`reaffirmMaster`/unsuppress senders. No test input is
  special-cased; the fix is the general pending record at promotion.
- Regression: `pkg/vrrp/become_master_garp_race_14155_test.go` —
  `TestBecomeMasterGARPDeferredSenderSurvivesVIPAdd_14155` models the
  parked deferred sender deterministically (suppress only the async
  launch, run `updateVIPs(+V3)`, then invoke `sendGARP(false)`
  synchronously as the parked goroutine would; `sendGARP` re-reads the
  epoch at `vipMu` acquisition, so this is the same state/path) and
  asserts exactly one burst per VIP (V1, V2, V3) and an empty pending
  set; `TestBecomeMasterSuppressedThenUnsuppressAnnouncesAll_14155` is
  the control that the unsuppress full-set sender still announces every
  VIP exactly once. The deferred sender is modelled synchronously
  because `becomeMaster` launches it with no scheduling seam; asserting
  through the real async goroutine would be scheduling-dependent.

  — `GARP bursts for 10.0.141.1 = 0, want exactly 1 (all bursts: map[10.0.141.3:1])`
  (only the added VIP announced; V1/V2 suppressed). The unsuppress
  control passed pre-fix, as expected.
- RED-ON-REVERT, production-only: stashing only the two production
  files (test kept) reproduces the same failure; reverting only
  `instance_transition.go` (keeping `instance_garp.go`) reproduces it
  too, confirming the load-bearing hunk is the becomeMaster pending
  record; reverting only `instance_garp.go` still passes, confirming
  the pre-existing pending carry-forward in `updateVIPs` then covers
  the interleaving, and the new gate/mode is a second-chance drainer
  rather than the primary mechanism.
- GREEN with fix: the 14155 tests, the #12201 becomeMaster launch pins,
  dampener/forced/reaffirm/reconcile/unsuppress/VIP-membership suites

## Risk

A suppressed becomeMaster now leaves its VIPs pending; that state is
carried only into MASTER announcements bounded by current membership
(`pendingGARPForSetLocked` prunes non-members, `removeVIPsLocked`
paths and demotion fences unchanged), so a BACKUP never announces.
Periodic non-forced full-set senders that find an already-reserved
epoch with pending VIPs may emit the retained VIPs once (subject to
the dampener) — that is the intended failover announcement, bounded
to one synchronous first frame per pending VIP. No behaviour change
when no membership update interleaves the promotion window.
