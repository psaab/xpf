# #15129 — ipsec: partial load tears down changed immediately survivor without re-initiation (A90-03)

- **Timestamp**: 2026-10-19
- **Action**: In the #14589 partial-load branch of `ApplyGeneration`, keep the
  `changed` result of `promoteConnNames`, capture `terminated` from
  `terminateRemovedConns`, and call `reinitiateChangedConnections` with the
  candidate config — mirroring the full-load path — joining any initiation
  error with the partial and terminate-debt errors.
- **File(s)**:
  - `pkg/ipsec/manager.go` (`ApplyGeneration` partial branch; doc comment)
  - `pkg/ipsec/partial_reinitiate_15129_test.go` (new; 4 cells)
  - `pkg/ipsec/README.md` (partial-load paragraph)

## Mechanism (verified at base 08489f99aa)

`ApplyGeneration` success path (manager.go:323-330 pre-fix): `removed, changed :=
promoteConnNames(...)`, `terminated, failed := terminateRemovedConns(removed)`,
then `reinitiateChangedConnections(ipsecCfg, changed, terminated)` — the #14140
re-initiation that brings a changed `establish-tunnels immediately` tunnel back
after its stale SA is terminated (`start_action = start` in policy.go fires only
on load; once the SA is terminated there is no trap and nothing re-dials).

Partial branch (manager.go:306-314 pre-fix): `removed, _ =
m.promoteConnNames(pae.names, pae.hashes)` — `changed` discarded —
`terminateRemovedConns(removed)` (changed names are in `removed` via
promoteConnNames:865-868), then `return` before any re-initiation.
`promoteConnNames` also clears `pendingChanged` (pre-fix :888-889), so the
survivor's NEW hash is promoted with no debt retained: a later commit that
fixes the refused VPN sees no hash change for the survivor and never
re-initiates it either. One commit that both rotates a survivor's PSK and
adds a VPN charon refuses therefore leaves the always-on tunnel down
permanently (until HA RG transition, daemon_ha.go, or manual intervention).
The #14589 test `TestPartialLoadChangedSurvivorKeepsNewSecret14589` asserted
only the adopted hash, not initiation.

## Fix

- Partial branch now mirrors the success path's teardown+reinitiation
  sequence: `removed, changed`, `terminated, failed`, `recordTerminateDebt`,
  then `reinitiateChangedConnections(ipsecCfg, changed, terminated)` —
  guarded to the non-clear branch with a non-nil candidate config. The
  candidate config is the correct argument: it carries the survivor VPN
  with its new settings (the recovered subset on disk is that same VPN);
  `reinitiateChangedConnections` internally applies the #14140 intent gate
  (`vpnEagerlyInitiates`: immediately + non-responder-only only), so
  on-traffic/responder-only survivors are terminated but not eagerly dialed,
  exactly as on a full load. Deleted names are never in the candidate
  config's VPN iteration for initiation (and are not in `changed`).
- The clear partial path is unchanged: it promotes the empty/prior set,
  `changed` cannot name a loaded candidate VPN, and the explicit
  `!pae.clear && ipsecCfg != nil` guard keeps it from initiating.
- `Loaded` still does not fire on a partial load; the partial error is
  still returned (now joined with terminate-debt and any re-initiation
  error, matching the success path's fail-closed error contract #6542/#10878).
- NOT changed: `promoteConnNames`, `terminateRemovedConns`,
  `recordTerminateDebt`, `reinitiateChangedConnections`, recovery
  (`recoverPartialLoad14589`), and the full-load path.

## Risk

- Operator-visible delta: a partial load that changes an immediately
  survivor now issues `swanctl --initiate --child <name>` for it (previously
  the tunnel silently stayed down). A failed initiation now also surfaces
  in the returned error alongside the partial error.
- No other behaviour change: non-eager modes, unchanged survivors, deleted
  connections, the clear path, and full loads are pinned unchanged by the
  control cells.
