# #9692 — test-ha-crash kills established iperf3 streams unobserved

- **Timestamp**: 2026-09-11
- **Action**: Measure established-stream survival and recovery across the takeover in test-ha-crash phases 1 (hard stop) and 2 (daemon stop), before the phase kills its client
- **File(s)**: `test/incus/test-ha-crash.sh`

## Re-verified at origin/master 80db775c4

- **Phase 1** (`incus stop --force fw0`) and **phase 2** (`systemctl stop xpfd`) each start `iperf3 -P4 -t120`, then assert only three things: the takeover, a NEW TCP connection and a ping.
- They then `pkill -9 iperf3`, and phase 1's comment says "sessions are dead — fw0 hard-crashed".
- No cell measures established-flow survival or recovery, which is the pass criterion `docs/engineering-style.md` gives this mandated gate ("0 / very low packet loss across failover/failback").
- The client also ran on the default port 5201, which `cos-iperf-config.set` shapes to 100 Mb/s.

## Change

- **`established_streams_recovered <phase>`.** Called after each phase's ping cell and before its client is killed. It waits `RECOVERY_WAIT` (10 s), then requires two things:
  - iperf3 is still running;
  - the most recent `[SUM]` interval is at or above `RECOVERY_MIN_GBPS` (0.5), parsed by the shared `iperf_sum_rate_gbps`.

  A stalled `0.00 bits/sec` interval does not parse as K/M/G bits and FAILs.
- **Port.** The client is pinned to the unshaped port 5211 (`IPERF_PORT`), so the recovery rate is not measured against a 100 Mb/s class.
- **Comments.** Phase 1's "sessions are dead" comment is gone: synced sessions are expected to survive a hard stop, and the cell now checks it. The header lists the new check in both phases.

## Validation

- `bash -n` is clean. `shellcheck -S warning` reports nothing. `make harness-census` is OK.
- The lib parses a real `[SUM]` interval line (`23.4 Gbits/sec` → 23.4000). A `0.00 bits/sec` line is unparseable, so the cell fails.
- **Calibration:** see below.
