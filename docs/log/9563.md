# #9563: the #8356 re-derivation revoked host-bound sessions on their first ACK

## Re-read at `origin/master` `b81c3613a`

The issue has no comments, so its body is the spec. The defect is still live at this commit.
`revalidate_zone_policy_on_session_hit` (`userspace-dp/src/afxdp/poll_descriptor/policy_revalidation.rs`)
declines three cases: a reverse hit, a protocol whose ICMP verdict depends on type, and a fresh or
absent revalidation target. It does not decline `LocalDelivery`.
`zone_policy_deny_on_session_hit` still takes `to_id` from `decision.resolution.egress_ifindex`.

Commits that touched these paths after the issue was filed: #9517, #9519 and #9529 (this lane)
and the HA close-class change. None adds a host-bound decline. #9519 routes an OWNER hit (arrival
zone equals the entry's ingress zone) to this re-derivation, and routes a foreign hit to
`foreign_hit_verdict`, which already forwards `LocalDelivery`. The issue's SSH-to-self fixture is an
owner hit, so it still reaches the defect.

## Mechanism

Every local-delivery resolution sets `egress_ifindex` to the local interface: `forwarding/fib.rs`,
`forwarding/nat.rs` and `forwarding/local_delivery.rs`. For a lan host's SSH to `10.0.61.1`, the
re-derivation therefore asks `lan -> lan`, a transit pair that host-inbound admission never
consulted. Install stamps policy generation `0`, which is never live (#8356 by design), so the FIRST
hit always re-derives. No rule matches, the default policy denies, and the owner's own first ACK
revokes the session.

## Census of cells that depend on the old behaviour

No existing cell asserts a revocation on a host-bound hit. Two cells assert zero revocations on
host-bound-shaped sessions, `a_fabric_punted_packet_keeps_the_entrys_ingress_zone_9384` and
`an_established_dnat_to_self_session_meets_a_junos_host_deny_on_the_translated_address_9529`, and
the fix keeps both at zero.

Three comments in this lane's #9519 and #9529 cells described working around this defect: separate
tables, no owner ACK, and a wan -> lan permit. They are rewritten to say it was the pre-#9563
behaviour. The fixtures stay as they are, so those cells do not start depending on the decline.

## Fix

- `revalidate_zone_policy_on_session_hit` returns `None` for a `LocalDelivery` decision, before the
  `policy_revalidation_target` lookup, so host-bound hits pay nothing for it.
- Host-bound authority is the host-inbound gate plus `to-zone junos-host` policy, and the
  established-hit path already re-evaluates both on every host-bound packet
  (`host_inbound_gated_lo0_action`, `junos_host_local_policy`). No revalidation question is lost.
- Docs: the module header of `policy_revalidation.rs`, `userspace-dp/src/session/README.md` (the
  zone-policy revalidation stamp) and `userspace-dp/README.md` (the hit-path re-derivation bullet).
  `session_glue/README.md` says the re-derivation declines every reverse packet; that stays true
  and is unchanged.

## An instrument fault in the first validation run, found before landing

The first `make test` on `a4239af0d` exited 2 with 12 Rust failures, all transit-revocation cells
(`tests_policy_revocation_8356`, plus one #9519 owner cell). That is not a regression from this
change. It was a fault in the validation chain:

- The chain exported `CARGO_TARGET_DIR=/var/tmp/x9563/userspace-dp/target` for its base-RED build
  and never unset it. The mutation matrix it then launched in `/var/tmp/x9563m` inherited it, so
  the matrix and `make test` built into ONE target directory at the same time.
- Cargo names the bin's test binary without the worktree path (`xpf_userspace_dp-e754dfd0775802aa`
  in both), so the matrix's M2 build overwrote the binary that `make test` then ran.
- Evidence: `make test`, M1 and M2 all report running
  `/var/tmp/x9563/userspace-dp/target/release/deps/xpf_userspace_dp-e754dfd0775802aa`. The 12 tests
  `make test` failed are exactly the 12 that M2 fails, with none extra on either side. The head-cell
  run on the same commit, before the matrix started, passed all 65 filtered cells, including every
  `tests_policy_revocation_8356` cell.

Both `make test` and the matrix were re-run in isolation, each with its own target directory. The
mechanics were also changed so this cannot recur silently: every matrix script unsets
`CARGO_TARGET_DIR`, and the scorer marks a run VOID when cargo reports a test binary outside that
run's own worktree.

Before pushing, the landing script intersects the `origin/master` delta since `81efb7aad` with this change's files by name, and refuses on any overlap. When master has moved past `81efb7aad`, it also merges `origin/master` into this commit in a throwaway worktree. The merged tree must pass `go build ./...`, `go vet ./...` (judged against master's own diagnostics) and `cargo check --tests --benches` in `userspace-dp`. Both checks repeat if master moves again before the merge, and the merge is pinned to the checked head commit. The script also refuses if a file the mutants edit differs from the matrix head `a4239af0d` or was changed on master. A guard that scans the whole tree (a census, a line count, a golden file) is out of reach of both checks. A full `make test` on master after merges covers that class.
