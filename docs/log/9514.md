## Timestamp: 2026-09-10 — the contradiction, and why it had to be measured

- #9514 claims the old decision's reverse-NAT steering holder is stranded by a
  same-key HA replacement, and then refuses row reclamation "permanently".
- A validated external report, `gpt-unknown-review-session-enforcement-forwarding-correctness-001.md`
  line 1014, records the opposite: "FIXED: synchronized same-key NAT
  replacement cleanup releases prior steering holders".
- `git log f3e7b9683..origin/master -- userspace-dp/src/afxdp/ha/session_import.rs userspace-dp/src/afxdp/checksum.rs`
  is EMPTY (and `f3e7b9683`, the report's base, is an ancestor of the issue's
  `098294d28`). So both claims describe byte-identical code, and a code change
  cannot reconcile them. One of them is wrong.

## Timestamp: 2026-09-10 08:37–08:44 — measurement at `5fafce23f`, before any fix

Three cells through the production `Coordinator::upsert_synced_session` /
`delete_synced_session`, with a `dnat_table_fd` of `-1` so the delete path
reaches `DNAT_DELETE_ATTEMPTS` (bumped just before the syscall).

**The fixture moves the steering row.** A holder row is keyed on
`(protocol, SNAT source address, SNAT source port)` only. So A and B differ in
`rewrite_src_port`, and the cell asserts
`dnat_steering_key(K, A) != dnat_steering_key(K, B)` as a precondition. A
same-row replacement re-acquires the holder a release would drop, so it cannot
tell the claims apart. Rows use 203.0.113.95, ports 49514–49519, which no other
cell uses; the registry is process-global (#8291).

```
A->B:     a_after_replace=1 b_after_replace=1 deletes_on_delete=1 a_after_delete=1 b_after_delete=0 later_row_a_deletes=0 a_final=1
A->A:     after_refresh=1 deletes=1 after_delete=0
recovery: stranded=1 recovery_deletes=1 after_recovery=0 later_row_a_deletes=1
```

- **#9514's mechanism reproduces.** The row-A hold survives the replacement
  and the delete, because the delete names only the stored decision B. A later
  session on row A then has its map delete REFUSED.
- **The report's FIXED verdict is refuted for this code.** A likely source, NOT
  verified: the #6979 F3 cells (`synced_replace_*_6979_f3`) release the OLD
  decision on a synced replacement, but what they release is the NAT pool PORT
  RESERVATION on the worker path, not `DNAT_STEERING_HOLDERS`.
- **"Permanently" is too strong, and measured separately.** A stranded
  `(K, A)` hold IS released in-process when the same key K comes back with
  decision A and is deleted; row A is then reclaimed by a later session. The
  accurate claim: never released unless that exact `(key, old decision)` pair
  recurs and is deleted, or the process restarts, and nothing makes either happen.
- **A→A passes either way.** It cannot settle this, which is the coordinator's
  point about identical-decision fixtures.
- **Limitation (the issue states it too):** `cargo test` cannot create BPF maps.
  The kernel row is not observed; the accounting and the pre-syscall delete
  counter are. The refusal lives in the accounting, before that syscall.

The measurement was posted on #9514 (issuecomment-5621430540).

## Timestamp: 2026-09-10 — the fix

- **File**: `userspace-dp/src/afxdp/ha/session_import.rs`, inside
  `upsert_synced_session`'s forward-entry publish block. After publishing the
  new decision's row: if `previous_entry`'s steering row differs from the new
  one, call `delete_dnat_table_entry(&dnat_fds, &previous.key, previous.decision.nat)`.
- **Through the holder accounting, never a raw map delete.** The row is shared
  (#6745), so this drops only this key's hold and deletes the row only when that
  was the last one.
- **Gated on the row changing.** A same-row refresh re-acquires the hold
  idempotently. Releasing it would drop a LIVE session's hold and delete its row,
  blackholing its return traffic. The A→A control pins this.
- **No new plumbing.** `previous_entry` was already in scope and was consulted
  only for the owner-RG prewarm refresh.
- **Docs in the same change.**
  - `checksum.rs` `DNAT_STEERING_HOLDERS` states the contract: a replacement
    must release what it replaces, and a same-row refresh must not.
  - The publish comment in `session_import.rs` now names both releases.
  - No README describes the holder lifecycle, so none needed changing.
