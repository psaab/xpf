# #14694 — malformed SSH key / negative UID bypassed shell demotion and password revocation

## Defect

In `pkg/daemon/daemon_hostauth_apply.go`, `applySystemLogin` did
`fail(err); continue` on `validateAuthorizedSSHKeys` failure (:250) and a
silent `continue` (no `fail`) on `user.UID < 0` (:258), both before the
shell-demotion block (`usermod -s`, :301-318) and
`reconcileUserPassword` (:325). `applyRootAuth` returned at :1353 before
its `reconcileUserPassword` (:1361). `reconcileAbsentLoginUsers`
(`login_password.go:598-606`) marks the user desired by name only, so the
skipped user was never deprovisioned either.

For the malformed-key arm on the strict-commit path the failure is
visible (`fail` joins the apply error), but on the tolerant / peer-sync /
rollback apply path the demoting config is already live, so the bypass
leaves the old shell/shadow/keys in force. The negative-UID arm was
genuinely silent on every path: the compiler keeps authored invalid UIDs
negative on the tolerant path (`pkg/config/compiler_system.go`, #11826),
`applySystemLogin` returned nil, and the OS shell, shadow hash and
authorized_keys were untouched — a config↔host credential desync.

## Fix

`applySystemLogin`: record the key/UID failure with `fail` (negative UID
now surfaces an error instead of silently skipping), set
`provisionBlocked`, and suppress only account creation (`useradd` when
`id` reports absence) and both SSH-key branches (install and
emptied-list revoke). The existing-account shell demotion and
`reconcileUserPassword` (apply or D2 lock) still run. A nonexistent
account is never created, preserving #5005/#11826 fail-closed creation.

`applyRootAuth`: record the malformed-key failure with `fail`, still run
`reconcileUserPassword` for root, and suppress only the key install /
emptied-list revoke when keys are invalid. Prior xpf-managed keys stay
untouched — the bad key is never installed and its presence is not
treated as an emptied list.

Updated expectations that encoded the old skip: #11826's UID test now
requires the surfaced error (still no `useradd`/`usermod` mutation for a
nonexistent account), and #10725's system-login cells now allow the
`id`/`usermod` demotion commands while still forbidding `useradd` and
any key file/marker mutation. Root #10725 cells are unchanged (their
password fixture already fails hash validation before any command).

## Tests

- RED (pre-fix / fix reverted): `TestApplySystemLoginMalformedKeyStillDemotesAndLocks14694`
  fails with "alice kept /bin/bash: usermod demotion was skipped";
  `TestApplySystemLoginNegativeUIDStillDemotesAndLocks14694` fails with
  "applySystemLogin silently accepted negative UID";
  `TestApplyRootAuthMalformedKeyStillLocksPassword14694` fails with
  "chpasswd was not invoked to lock root despite malformed key".
- GREEN (post-fix): all three pass — existing account's shell is demoted
  to the CLI shell, `chpasswd` locks the shadow (`alice:!` / `root:!`,
  shadow readback locked), the error surfaces, prior authorized_keys are
  byte-identical, and the malformed key is never written.
- Control: `TestApplySystemLoginMalformedKeyNewUserNotCreated14694`
  passes pre- and post-fix (no `useradd` for a refused new user).
- Suites: targeted cells above pass; broader host-auth/login/root
  pattern run passes except `TestReconcileDHCPRelayWiresIfNameResolver9406`,
  an unrelated DHCP-relay fixture failure (vlan-tagging compile error in
  its own fixture, untouched by this change — no login/host-auth code in
  its path). `go vet ./pkg/daemon/` clean.

## Risk

Strict-commit behavior for malformed keys is unchanged in outcome (the
commit still fails; shell/password now also converge for an existing
account before the failure is reported, which is the revocation-safe
direction). Negative-UID applies now return an error where they
previously returned nil — intended: the config↔host desync is now
visible to the commit/closeout path instead of silent.
