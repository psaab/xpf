# Issue #13955 — lo0 IPv4 `is-fragment` cannot match at input

## Why

The lo0 nftables mirror evaluates packets in an `inet` input-hook chain at
priority 0. IPv4 defragmentation runs earlier at prerouting, so the input hook
sees the reassembled datagram with fragment offset zero and MF clear. The
rendered `ip frag-off & 0x1fff != 0` predicate therefore cannot match the
fragmented datagram the operator intended to filter. This was a silent semantic
mismatch on the kernel-primary host-bound path.

## What

The input-hook placement cannot inspect IPv4 fragments after the kernel has
reassembled them. Moving the rule to prerouting is not a safe local change:
that hook sees forwarded traffic too, before input routing, and has different
verdict/action semantics. The implementation therefore fails closed instead
of claiming support: a V4 lo0 `is-fragment` term refuses the whole candidate
netlink table, and the text renderer emits a constant nft-invalid sentinel so
an atomic nft load retains the prior generation. The existing daemon apply
failure/fence path remains responsible for fail-closed runtime handling.

IPv6 is unchanged: its fragment extension header is available at input and its
`exthdr frag exists` rule remains supported. Ordinary IPv4 lo0 filters are
unchanged.

## Risk

An IPv4 lo0 filter containing `is-fragment` can no longer install a new
kernel-mirror generation; on a cold boot the existing fail-closed fence path
applies, and on an already-enforced node the prior generation is retained. This
is intentionally safer than silently installing a rule that never matches.
The feature remains unsupported for IPv4 lo0 until a broader pre-defrag design
preserves host-only scope, filter ordering, and action semantics.
