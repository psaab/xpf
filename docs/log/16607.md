# #16607: Two source-NAT rule-sets with identical from/to context commit clean and the later one is shadowed

- **Timestamp**: 2026-10-25
- **Action**: Added strict-commit gate `validateSourceNATDuplicateContextAST`
  (`pkg/config/dup_nat_ruleset_names.go`) rejecting two differently-named
  source-NAT rule-sets whose normalised `(from, to)` contexts are equal.
  Normalisation reuses `collectNATScopes` (the compiler's own reader, with
  the `{zone, ""}` match-any default for absent clauses) and renders each
  side as a sorted set of `kind value` tokens, so bracket lists compare
  order-insensitively (`[ trust dmz ]` equals repeated `from zone` clauses),
  duplicate spellings collapse, and a single authored rule-set carrying a
  list (#3096 Cartesian expansion) is one instance and never self-collides.
  Same-named pairs stay owned by the #6454 gate (which runs first strictly);
  empty names are skipped for the same reason. The diagnostic names both
  rule-sets and the shared context and states the shadowing consequence
  (a later `source-nat off` exemption unreachable behind an earlier
  catch-all). Wired in `compiler.go` beside the #6454 gate with a new
  `lenientSourceNATDuplicateContext` opt (tolerant load/peer-sync warns and
  keeps the historical concatenated behaviour, #1960), and added as the
  fourth scanner in `dupNameScannersExpanded` so a duplicate-context pair
  authored entirely inside an applied group is caught on the expanded view
  (the #6455 mechanism, both cluster nodes). NOT changed: destination/static/
  nat64 contexts (the Junos citation and the acceptance probe are
  source-only), the dataplane snapshot ordering (#4161 tier sort), and the
  overlapping-but-not-equal case (distinct specificity still first-matches
  legitimately).

- **Validation**: Targeted suites pass except
  `TestNAT5144MappedV6VsGenuineV4Accepted`, which the new master
  gate #17408 (pool family scoping, landed during this lane)
  rejects for an unrelated family reason — pre-existing on the
  rebased base, not this gate. New tests cover the acceptance probe
  (catch-all + exemption), bracket-set equality, unscoped==unscoped,
  distinct from/to/kind and single-list acceptance, lenient
  warn-and-boot with both rule-sets surviving, and group-authored
  rejection. Full `pkg/config` comparison against a pristine
  origin/master worktree showed only base-attributed failures after
  the #5144 fixture rescope and the shipped-config merge.
- **Residual**: Overlapping but non-equal contexts (e.g. `[ trust dmz ]`
  vs `trust`) still first-match in definition order within a tier — that is
  the deliberate #4161 semantics and Junos permits distinct contexts.
  Destination-NAT duplicate `from` contexts are not gated here; if Junos
  parity is wanted there it needs its own probe/issue.
