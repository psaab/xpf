# #7342 — enforce security flow tcp-session initial/closing/time-wait timeouts

- **Timestamp**: 2026-08-30 (`fix/7342-tcp-session-timeouts`)
- **Action**: split the TCP close state into CLOSING and TIME_WAIT, carried the
  three `security flow tcp-session` timeout leaves on one additive wire bump,
  and flipped the #6539 enforcement table.

## Why the split had to come first

`session_timeout_ns` split a TCP close only into RST and not-RST, so
`closing-timeout` and `time-wait-timeout` had ONE window between them. Mapping
either onto it was a guess and mapping both was impossible, which is why #6539
could only record that neither was enforced. `initial-timeout` alone would have
been a small additive field — it maps 1:1 onto `tcp_opening_ns` — but doing the
three together is one protocol change, one cluster smoke and one release note
instead of two of each.

## The discriminator, and the one that looked right and was not

A FIN per DIRECTION. Forward and reverse are independent entries, so each knows
whether its own direction FINed; `propagate_tcp_state_to_companion` mirrors that
as the companion's peer-side FIN. One FIN is CLOSING, two is TIME_WAIT, a RST
short-circuits both.

`SessionEntry.observed_tcp_flags` looks like the same thing already exists and it
does not: `account_packet` OR-folds BOTH directions' flags onto the forward entry
deliberately (#2749, so NetFlow's `tcpControlBits` reports the whole flow), so
`observed_tcp_flags & TCP_FIN` is true after ONE fin. A TIME_WAIT detector built
on it would have put every half-closed session straight into TIME_WAIT, and every
single-FIN test would still have passed.

## Compatibility

Both new windows default to the one every post-FIN close already used, and `0` on
the wire means unset, and the three fields are `omitempty` / `serde(default)`. So
an operator who sets neither leaf, a Go binary that predates the change, and a
helper that predates it all produce byte-identical reaping. Each of those three is
pinned by its own cell.

## Upgrade posture — the advisory inversion

Scope item 4 of the issue was an explicit decision and it went to the maintainer
with four options costed. The ruling was option 1: invert the #6539 advisory
rather than delete it.

Before #7342 these leaves were accepted-only and #6539 had been saying so at
commit — so the population carrying a configured value is exactly the operators
who set one AFTER being told it did nothing. For them the upgrade activates a
value they had no reason to keep realistic, and `initial-timeout` is the sharp
one: a large value turns the half-open window from a fixed 20s bound into a
session-table pin.

Rejected, with reasons, so they are not re-litigated:

* a release note alone — the surface an operator checks is the commit they are
  about to run, not a note read last month. Saying nothing there is #6539's own
  failure mode pointed the other way.
* a magnitude-keyed warning — the threshold has no derivation behind anyone, and
  a warning whose bound cannot be defended gets tuned out, which costs the
  warnings that matter.
* narrowing the schema bound — rejects configs that commit cleanly today, a hard
  upgrade regression, and it violates the repo's no-schema-only-caps rule.

The advisory states two bounds an operator cannot check from the config alone
and which are what make activation defensible: an unset leaf is unaffected (`0`
means "keep the dataplane default" on this wire), and a zone with
`screen ... syn-flood timeout` is already bounded by that override regardless of
`initial-timeout`. The half-open clause is CONDITIONAL on `initial-timeout`
actually being set — an unconditional one would put an exposure in front of an
operator who did not configure the knob that causes it.

It was temporary and the temporariness was tracked rather than intended:
automatic retirement would need a release-version predicate, a mechanism with
its own failure modes for a message costing one commit-time line; "keep until
someone deletes it" rots into permanent noise unless the deletion has an
object. Same shape as the UNSURFACED queue and the dead-entry-rejecting
accepted list.

**#8129 deleted the advisory** (2026-10): its deferral was "one release past
the boundary", v0.9.3 shipped 2026-03, and master is far past it. The selection
machinery (`unenforcedTCPSessionTimeoutsIn`) and
`TestTCPSessionTimeoutTableCoversSchema_6539` STAY, per this issue's acceptance —
they are what stops a fifth timeout leaf from rendering unannotated. See
docs/log/8129.md.

## Live validation, loss userspace cluster

`make cluster-deploy` + `make test-failover`: 17 passed, 0 failed, iperf3
22.8 Gbit/s. The wire bump and the helper binary both move, so the smoke is owed.

The feature measurement took three attempts, and the two failures are recorded
because each produced a plausible-looking number that meant nothing:

1. Counting sessions by destination prefix — there is background traffic to the
   iperf3 target, so the counts moved by 1 against a base of 11. A decrease of
   one is not a measurement of a window.
2. Forcing a source port with an explicit `bind()`, which failed (address in
   use) and exited before connecting. Every arm reported the flow absent at
   `t+1s`, which reads exactly like a fast reap. A VOID run, scored as a result.
3. Closing with `close()` on a socket carrying unread data, which sends RST, not
   FIN. RST takes the 2s abort window and is deliberately NOT operator-
   configurable, so BOTH arms died at +8s and the comparison proved nothing.

The measurement that discriminates drives a genuine half-close —
`shutdown(SHUT_WR)`, socket held open, a FIN in ONE direction, which is exactly
Junos CLOSING — and runs BOTH arms:

| arm | v4 | v6 |
|---|---|---|
| `closing-timeout` UNSET (the pre-#7342 fixed 30s window) | alive at +8s | alive at +8s |
| `closing-timeout 3` | gone at +8s | gone at +8s |

Four cells, two arms, both families: the leaf governs the post-FIN window, and
with it unset the pre-#7342 behaviour is preserved. A single arm could not show
either half.

The CLI also rendered all four leaves with no accepted-only annotation after the
commit, which is the #6539 surface retirement working end to end.

## The advisory, live

Record of the #7342-era behaviour as validated then; #8129 has since deleted the
advisory (see docs/log/8129.md).

Re-deployed at head and driven through real commits. The first attempt at this
check reported the OLD #6539 accepted-only text — the cluster was still running
the pre-change `xpfd`, and a `make build` alone does not deploy it. Reading the
text rather than only its presence is what caught that; "an advisory fired" would
have recorded as confirmation.

After `make cluster-deploy`:

| commit | advisory |
|---|---|
| `closing-timeout 15` alone | "closing-timeout is now ENFORCED (#7342)", half-open clause ABSENT |

The conditional clause is the part a single-arm check could not see: it appears
only when `initial-timeout` is among the leaves set.
