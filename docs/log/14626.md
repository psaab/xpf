## Why

Junos places `persistent-nat` under `… rule … then source-nat pool <name>`
(and `… interface`). xpf modeled it only per-pool
(`security nat source pool P persistent-nat`). `recordSourceNATUnknownThen`
returned on `pool <name>` and skipped the tail, the schema kept the tail
open-world (`closedWorldOpaque`, #4313/#10078), and the pool parser — the
only writer of `PersistentNAT` — never saw it. A migrated config therefore
committed clean under strict `CheckText` with `persistent_nat=false` and no
warning: persistent NAT (STUN/VoIP/P2P inbound reuse of the mapping,
endpoint-independent mapping) was silently lost, and an empty persistent-NAT
table looked like "no traffic yet". The schema comment falsely claimed "The
compiler consumes that tail". The interface spelling already rejected
(#10294 unknown-then gate), proving the gate could reject the shape.

Reproduced on base (`df69dc1cf`): the new snapshot test failed with
`PersistentNAT = false, want true (rule-level tail was inert, #14626)`
while the pool-level control passed.

## What

- New `scanRulePersistentTail14626` extracts the tail from every AST shape
  (fully-compact `then` Keys, packed `source-nat` Keys, flat-set pool
  children, hierarchical `source-nat { pool …; persistent-nat { … } }` and
  `pool { P; persistent-nat { … } }`) into `NATRule.rulePersistentNAT`
  (unexported, per-rule — the shared pool is never mutated, so a rule tail
  cannot leak onto a sibling rule). Authored field sentinels (`Timeout=-1`,
  `PermitSet`) distinguish "absent" from authored.
- `EffectivePersistentNAT` layers the tail over the referenced pool's own
  config (unauthored sub-fields inherit the pool's). Malformed/conflicting
  tails never override the pool.
- Strict gate `validateSourceNATRulePersistentNATStrict14626` (wired in
  `runUniformGates` beside the pool-reference gate) rejects: malformed
  permit/timeout/unknown sub-keyword, a tail on `interface`/`off`, a tail
  disagreeing with the pool, two rules on one pool disagreeing, and a tail
  on a deterministic pool. Tolerant load warns (#1960) and falls back.
- `recordSourceNATUnknownThen` now stops at the modeled tail instead of
  calling it an open-world exemption; unknown siblings still record (#10294).
- Consumers switched to the rule-effective value: userspace snapshot
  (`nat_source.go`), legacy `compileNAT` persistent-table registration,
  `UsesPersistentSourceNATPool` (helper protocol floor), and
  `natshow` source-rule detail.
- Schema: `persistent-nat { permit, inactivity-timeout }` modeled under the
  rule-then `pool` leaf (typed enum 1..86400 validators, so `SchemaValidate`
  rejects `permit bogus` / timeout 99999 on hierarchical spellings); packed
  flat spellings are owned by the compiler gate because the tail collapses
  onto Keys past the pool name. False "compiler consumes that tail" /
  open-world comments corrected in `schema_security.go`, `types_security.go`,
  `compiler_nat_then_occurrences_7013.go`, `7033`, `compact_normalize_8662.go`,
  and `docs/config-schema.md` (the "NOT flipped … follow-up" paragraph now
  records the tail as modeled).
- NOT changed: pool-level parsing/semantics (control row byte-identical),
  the #7033/#7013 action-cardinality scans (they still stop at
  `persistent-nat`), DNAT/static tails, and the wire format (existing
  `persistent_nat*` snapshot fields carry the effective values).

## Risk

- A previously-committable rule tail that disagrees with its pool (or with a
  sibling rule on the same pool) now fails strict commit; such configs
  still load tolerantly with a warning and keep the pool's persistence.
  `persistent-nat permit off` (previously inert-accepted) now rejects as an
  invalid permit value.
- Two rules sharing one pool with DIFFERENT valid tails cannot both be
  honored by the per-pool Rust lease keying, so strict commit forces the
  operator to state persistence once on the pool — deliberate, not a silent
  first-wins.
