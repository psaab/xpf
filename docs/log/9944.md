# DHCP renewal reply binding (#9944)

## Why

DHCP renewal exchanges accepted replies by message type alone. A reply from an unrelated server, a reply for another transaction or client, or a reply received while the lease belonged to another interface could therefore affect the renewal path. Lease-binding server identity was also omitted from the content-change decision. A valid granting-server DHCPNAK must revoke the lease immediately, while a wrong-server NAK must remain ignored.

## What

- `pkg/dhcp/renew.go:19,29,55` adds explicit DHCPv4 and DHCPv6 acceptance predicates. They require the request transaction identity and client identity, the response type, a server identity, and the stored granting server. REBINDING does not relax the server binding; an off-server ACK or NAK is ignored.
- `pkg/dhcp/dhcpv4.go:29,158,224` validates lease/interface ownership before opening the interface-bound client, preserves the granting-server NAK sentinel, and routes a valid NAK through `abandonLeaseAfterNAK` to deconfigure and return to INIT.
- `pkg/dhcp/dhcpv6.go:287` performs the equivalent interface ownership validation and uses the DUID-bound matcher.
- `pkg/dhcp/lease.go:51` and `pkg/dhcp/commit.go:102` compare v6 server DUID and v4 server-identifier changes as lease content.
- `pkg/dhcp/dhcp.go:129,155` exposes atomic per-family server-identity
  rejection counters through `RenewalBindingStats()`, so ignored off-server
  replies are observable rather than silently discarded.
- `pkg/dhcp/renew_binding_9944_test.go:36,107,152` covers v4/v6 transaction, client, server, missing-identity, REBINDING, and cross-interface rejection cells. `pkg/dhcp/renew_test.go:291,372` and `pkg/dhcp/dhcp_lease_expiry_4874_test.go:83` cover immediate granting-server NAK revocation and timeout retention. `pkg/dhcp/commit_test.go:144,157` covers server-identity content changes.
- `pkg/dhcp/README.md:151,404` documents the reply ownership, NAK, lease retention, and recompile coupling rules.
