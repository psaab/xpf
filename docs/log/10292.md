# 10292 — Honour host-inbound `except` modifiers

## Boundary

Junos host-inbound `system-services` and `protocols` leaves can express an
exclusion as either a value-tail modifier (`ssh except`) or a nested modifier
(`ssh { except; }`). Flat `set` trees can also represent the positive value and
its modifier as sibling nodes. Before this fix, the nested form dropped
`except`, while the flat forms reached strict validation as an unknown token.

## Fix

- `parseHostInboundNode` now walks the complete value subtree while preserving
  each value-node boundary, aggregates same-key leaves before applying
  modifiers, and uses one path for hierarchical and flat AST shapes.
- A nested or inline `except` is recognized only inside its operand's own AST
  node; a standalone `except` sibling remains visible to strict validation.
- Known exclusions are applied to explicit values and to the corresponding
  `all` expansion for both services and protocols.
- Unknown exclusion operands remain in the positive stream so the existing
  strict/lenient host-inbound token validator still reports them instead of
  silently accepting a typo.
- Compiler-local exclusion provenance survives duplicate
  `host-inbound-traffic` blocks, so a restrictive sibling cannot be erased by
  positive-list union. Public `HostInboundTraffic` admission slices remain the
  existing runtime representation; physical/unit effective-view merging stays
  positive-list-only.

  failed: nested service/protocol forms compiled as `[all ssh]`/`[all ospf]`,
