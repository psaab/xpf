- **Timestamp**: 2026-09-11 ~12:50 UTC
  - **Action**: Chose option 1, dropping the zone set from the base.
    - **Why the zones separated nothing.** The helper's SYN-cookie machinery is global, and the domain label plus the cluster identity already separate the key. Keeping the zones only made the key a function of the screen configuration, with two consequences:
      - two nodes that screen different zones disagree on every key;
      - a commit that adds or removes a screened zone invalidates every cookie minted before it, even on one node.
    - **Why option 2 falls short.** A commit warning would address neither consequence.
    - **Upgrade cost.** The issue's mixed old/new-pair cost is small here: #9173's derivation (merge `5f28e89ac`) is in no tag (`git tag --contains` is empty), so no released build carries the zone-bearing base.

  - **Action**: Codex round 1 on `08d97b739` returned MERGE NO with three findings. All three are addressed:
    - **HIGH, "the zones separate nothing" was false.**
      - Cookies and validated-client entries were bound only to the 16-bit StableZoneID, and that fold collides (`z174`/`z214`). The quarantine keeps colliding zones apart within one config, but not across node-specific configs or a commit that swaps one colliding zone for the other.

        - the cookie MAC;
        - the per-epoch secret;
        - the validated-cache key (including the test-only `debug_set_index`).
      - The screen callers compute the tag from the zone name they already hold, and their now-unused `zone_id` parameters are renamed `_zone_id`.
      - **New cells:**

      - Six existing test sites that mint or check a cookie directly and then go through the production path now pass `syn_cookie_zone_tag("trust")`.

- **Timestamp**: 2026-09-11 ~14:15 UTC
  - **Action**: Codex round 2 on `2c8560395` returned MERGE NO with four MED and two LOW findings. Each was checked against the code.
    - **MED, the tag was hashed per SYN, on the flood path.** `contains_valid` and the mint both hashed the zone name on every initial SYN in a cookie zone.
    - **MED, a public 64-bit tag.** Its collision resistance is about 32 bits under a birthday search, so two zone names sharing a tag could be found offline.
      - **Fix for both.** The tag is now the first 128 bits of SHA-256 over a domain label, the name's length and the name (`SynCookieZoneTag`, `[u64; 2]`).
        - It is computed once, in `ZoneScreenState::from_profile`, and read from the zone's state on every path, so the packet path hashes nothing.
        - The MAC, the per-epoch secret and the validated-cache key absorb both halves.
      - **Vectors.** `syn_cookie_zone_tag_matches_its_known_answers_9740` now carries vectors from Python's hashlib.
    - **MED, a removed and re-created zone inherited its whitelist.**
      - **Cause.** A new zone's generation was a per-zone bump from 0, so every incarnation got generation 1, and the validated cache outlives a removed zone for up to one epoch.
      - **Scope.** The same was true with the 16-bit zone id, so this predates #9740. It is small and in code this change edits, so it is fixed here.
      - **Fix.** Generations now come from one counter for the whole screen state (`next_syn_cookie_profile_gen`).
      - **Cell.** `syn_cookie_a_removed_and_recreated_zone_does_not_inherit_its_whitelist_9740`.
    - **MED, the mixed-version description was false.**
      - **Why.** A helper from before #9740 absorbs the 16-bit zone id, so it and this helper refuse each other's cookies from the first one, not from a period boundary. Every helper that ignores the ring predates #9740, so the boundary-only case never occurs between real builds.
      - **Docs.** `docs/syn-cookie-flood-protection.md` and `pkg/cluster/README.md` now say so. The #9173 mixed-version cell's comment says which pairing it models.
      - **Cell.** `syn_cookie_mint_binds_the_zone_tag_twice_and_refuses_a_pre_9740_cookie_9740` rebuilds a pre-#9740 cookie from its documented parts and shows this helper refuses it.
    - **LOW, no cell bound either zone binding on its own.**
      - **The gap.** The MAC and the per-epoch secret each absorb the zone, so dropping one left every behavioural cell green.
      - **Fix.** The same new cell requires `mint_isn` to equal the ISN rebuilt from its documented parts, for three zones and three MSS classes. That fails if either binding moves.
      - **Not covered.** Dropping the tag from the cache's `key_hash`. It changes only which set a key lands in, not which entry matches.
    - **LOW, stale "zone_id" descriptions.** These now name the zone tag:
      - the whitelist key in the doc, in two places;
      - the `syncookie.rs` module doc;
      - the `check_packet_with_zone_id` doc.
