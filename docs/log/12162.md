# Issue #12162 — disarm watchdog after failed kernel arm

## Why

`armCandidate` armed the hardware watchdog before persisting ARMING, setting and verifying BootNext, recording the promotion binary, and persisting ARMED. Every later failure returned without `DisarmWatchdog`; the existing BootNext cleanup helper only cleared the firmware one-shot. `Arm` likewise returned a failed `Reboot()` without disarming the watchdog.

## What

Every post-watchdog arm failure now disarms the watchdog. Failures after `SetBootNext` also retain the existing BootNext cleanup. A failed watchdog disarm is included in the returned error without masking the original arm or reboot cause. A successful arm leaves the watchdog armed for the candidate trial.

## Validation

- **STEP-0 base:** `1c384b9a47ff7d6e567fa50632faa75c3995ae87` (`origin/master`).
- **RED before:** the focused #12162 tests failed on all six `armCandidate` post-acquisition failures and on failed `Reboot()`: the fake observed zero `DisarmWatchdog` calls and the watchdog remained armed. The cleanup-failure case also lacked a reported watchdog-disarm error.
- **GREEN after:** the focused #12162 tests passed, covering ARMING persistence failure, `SetBootNext` failure, BootNext readback error and mismatch, promote-binary recording failure, ARMED persistence failure, failed `Reboot()`, watchdog-disarm failure reporting, and the successful-arm control.
- `go test ./pkg/upgrade/... -count=1` passed for `pkg/upgrade` and all its subpackages.
- `go build ./...` passed.
- `gofmt -l` on the three changed Go files produced no output.

## Risk / residual

Tests use the non-live fake `KernelSystem`; they verify that each error path calls disarm and that cleanup errors remain visible, but do not model Linux watchdog-driver magic-close/nowayout semantics, hardware state, or reset timing. No live watchdog device or cluster was exercised.

## Review fold 77b615779 — classify landed journal writes (F1–F6)

The failed-`Reboot` path treated every ARMING backstep write error as
pre-rename. A post-rename directory-sync error leaves ARMING visible on disk,
but the old path kept BootNext and the watchdog, so the reset boot skipped the
promotion gate. On the BootNext-clear failure path, a failed ARMED restore
also left an ARMING journal under an armed watchdog; strict partial-watchdog
cleanup could additionally report exit 2 even when disarm itself had failed.

### What

- Classify `*fsatomic.PostRenameSyncError` through the journal `%w` wrapper at
  both the ARMING backstep and ARMED restore. A landed ARMING backstep continues
  through BootNext clear and watchdog disarm; a landed ARMED restore remains
  ARMED in memory and in operator reporting.
- In the triple-fault path, attempt watchdog disarm after the failed ARMED
  restore, retain and report a disarm error, and state when the still-armed
  watchdog will force the queued-candidate reset.
- Report automatic watchdog resets only when watchdog arming succeeded.
  Strict partial-acquisition cleanup failures return an infrastructure error
  (exit 1), not the LANE-2 sentinel (exit 2).
- Clear the arm-record sidecar whenever a failed-Reboot unwind leaves the
  journal ARMING, including failed ARMED restore, preventing a pre-retry
  binary cut from leaving a stale gate record.
  Remove the unused BootNext-cleared return from `disarmAfterArmFailure` and
  put errors last in the remaining tuple-return helpers.

### Validation

### Risk / residual

The matrix's `armedPersistPost` case remains a separate pre-existing defect
tracked as #12549: the ARMED rename is visible while the arm failure unwind
clears BootNext and disarms, leaving a false-ARMED journal. It is deliberately
not changed here. D2 remains best-effort: an `ArmWatchdog` error may still
partially acquire hardware state, but the runner does not promise an automatic
watchdog reset without a successful arm result. Tests use the fake
`KernelSystem`; they do not model physical watchdog-driver magic-close,
nowayout, or reset timing.
