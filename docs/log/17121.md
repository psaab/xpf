# #17121 — single-source LoginClassPermission rendering in String()

- **Timestamp**: 2026-10-27
- **Issue**: #17121 (R4-Q47-07)
- **Base**: `origin/master 06217b5108`

## Defect (STEP-0, verified at base)

`LoginClassPermission` had two diverged renderers and no `String()`:

- `pkg/authz/authz.go:176-193` `PermissionName`: `PermAll -> "all"`, default -> `"permission(%d)"` (used in the `Authorize` denial at `:169` and at log/denial call sites in pkg/api and pkg/grpcapi).
- `pkg/config/compiler_system.go:1957-1975` `loginClassPermName`: `PermAll -> "super-user"`, default -> `"unknown"` (used in the commit advisory at `compiler_system.go:2012` and in `describePerms` at `compiler_login_deny.go:114`).

So a custom class whose tokens fold to PermAll was described at commit as holding `{super-user}` and later denied for lacking "the all permission" — two words for one enum value on two operator surfaces, with no test binding the tables. Defect live at base, not already fixed.

## Fix

- Added `func (p LoginClassPermission) String() string` in `pkg/config/types_system_login.go` — the one rendering table, using the Junos permission vocabulary: view/clear/control/configure/maintenance/all, with out-of-range values rendering `permission(<n>)` so a corrupt value stays diagnosable. `PermAll` is `"all"` (the permission token), not `"super-user"` (a predefined class name).
- Deleted `loginClassPermName` from `pkg/config/compiler_system.go`; the advisory now appends `p.String()`.
- `authz.PermissionName` now delegates to `p.String()` (signature and all call sites unchanged); its private switch is deleted.
- Deleted `describePerms` from `pkg/config/compiler_login_deny.go`: it was dead code (zero callers tree-wide — only its own definition) whose sole purpose was rendering through `loginClassPermName`; with the helper gone it had no caller and no reason to survive. Its now-unused `sort`/`strings` imports went with it.
- NOT changed: `mapJunosPermissions` (the parser/fold in the same file — it maps tokens TO permissions, the inverse direction, and is explicitly allowed by the acceptance grep), the built-in `LoginClassPermissions` table, any authorization decision, or any wording outside the permission rendering (e.g. the #16080 advisory still says "super-user (all)" where it names both the class and the permission).

## Risk

Low. Display-only: no authorization decision, permission mapping, or class resolution changes. Operator-visible change is deliberately the point — PermAll classes now read `{all}` (was `{super-user}`) in the commit advisory and in folded-class warnings, matching the denial vocabulary that already said "all"; unknown values in advisories now read `permission(<n>)` instead of `unknown`. Residual: the #16080 advisory tail still pairs "super-user (all)" (class name + permission word) — that is intentional dual naming, not the single-value divergence this issue removes. Note pkg/api and pkg/grpcapi consume `authz.PermissionName` unchanged and inherit the unified word automatically.
