# #17256 — share NAT64 name validation with NAT

- **Timestamp**: 2026-11-06
- **Branch**: `fix/17256-nat64-exists`
- **Base**: `199750132a` (`fix: key placeholder offsets per pool (#17257)`)

## Why

`validateNAT64ScopeStrict` had its own address-book existence check instead of
using the NAT name-reference path. The direct dynamic-address feed false reject
was already fixed by #16550 on this base and is pinned by
`TestNAT64SourceAddressNameFeedBindingAdmitted16550`. The live residual was a
defined-but-unresolvable name: an empty/prefix-less address-book closure passed
NAT64 commit while source NAT rejected the same shape via
`policyMatchAddressBookResolves` (#3425). The runtime retains an unparseable
fallback for the empty closure, so the NAT64 scope never matches.

## What

- Added `natAddressNameReference` as the single NAT name decision: it handles
  the direct `AddressBindings` carve-out, address-book definition, and shared
  recursive resolution. Both `validateNATSourceAddressNameReferencesStrict`
  and the NAT64 name arm call it.
- The shared resolver now returns whether a failure is solely a cold/failed
  `dns-name`. NAT64 preserves the established #15930/#16595 DNS-only runtime
  dependency without excusing a mixed closure that also contains an empty or
  dangling static member. `policyMatchAddressBookResolves` remains the policy
  API and delegates to the same resolver.
- NAT64 still applies its separate #16550 IPv6-family check after common name
  resolution. Errors for unresolved names retain the `security nat nat64
  rule-set <name>` context.
- **Disposition for the defined-but-empty case**: strict commit refuses it,
  matching the SNAT predicate's hard reject. The shared resolver returns an
  error because the name produces no usable address; the snapshot's fallback
  is never-match, so accepting it would silently ship an inert scope.
- Updated `TestNAT64SrcShadowNestedEmptySetPoison16873` to exercise the shadow
  and owner analysis directly on the typed config. Strict compilation now
  correctly rejects that empty nested closure before the downstream analysis.

### Shared-predicate call graph

`runUniformGatesNAT` → `validateNATSourceAddressNameReferencesStrict` →
`nameError` → `natAddressNameReference` → `policyMatchAddressBookResolution`.
The NAT64 tail gate → `validateNAT64ScopeStrict` →
`natAddressNameReference` → that same `policyMatchAddressBookResolution`.
The policy validator's existing `policyMatchAddressBookResolves` wrapper also
uses the same recursive engine. NAT64's additional `nat64NameClosureNoIPv6`
check remains only the NAT64-specific family rule.

## Risk

Strict commit now rejects a defined NAT64 source name that resolves to no usable
address, consistent with the source NAT gate; tolerant loading still warns. The
direct feed carve-out, DNS-only transient behavior, IPv4-only rejection, and
mixed IPv4/IPv6 admission are retained. No dataplane, wire, or runtime resolver
behavior changed.
