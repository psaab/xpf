- **Date**: 2026-10-13
- **Issue**: #12503
- **Why**: TUN-origin reverse sessions resolved in the tunnel routing-instance table but carried no installing-table identity. A peer/shared-session materialization received an invalid forwarding-generation stamp, so the first descriptor pass treated it as stale. The generic refresh then interpreted the reverse's `(0,0)` identity as the default table and changed a VRF `LocalDelivery` into `NoRoute`.
- **What**: Both GRE and WireGuard TUN-origin builders now stamp the synthesized reverse with the validated install-table `(domain, check)` derived from its tunnel instance table. Default-instance reverse entries remain `(0,0)`. The generic stale-generation resolver now revalidates these entries in their table without special-case packet-path logic or per-packet allocation. Updated the TUN-origin reverse-revalidation comment and pinned the VRF/default stamp contracts in the existing GRE/WireGuard product tests.
- **RED-before**: `gre_tun_origin_vrf_reverse_resolves_local_10038` and `wg_tun_origin_domain_vrf_hit_delivers_10038` both failed on the pre-fix worktree at their final LocalDelivery assertions after recording a session hit.

- **Risk**: The table identity is attached only to TUN-origin reverse decisions built against a named tunnel instance. Default-instance behavior is unchanged; ordinary/non-TUN reverse construction and revalidation are unchanged.
