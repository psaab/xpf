# #19164: embedded-ICMP errors return by a stale stored reverse resolution

Lane F2. Found by the #19145 design round's R-read. The coordinator approved
fixing it in the ICMP return path itself (the only shape covering both cases).

- **Timestamp:** 2026-11-16T15:53:00Z
  - **Action:** fixed it, branched on master b725d9542e, with the repro
    (485ce2f08d on `repro/icmp-return-stale-reverse`) cherry-picked.
    - **`embedded_icmp_return_resolution`** (`icmp_embed/return_resolution.rs`)
      looks the matched reverse up FRESH (`fresh_reverse_resolution`) with
      the reply path's own lookup variant:
      - cache-free when the stored resolution's forwarding generation is
        stale;
      - the synced-session variant for a peer-synced reverse;
      - the cached variant otherwise.
    - **When that fresh lookup cannot forward** (NoRoute, MissingNeighbor),
      the STORED resolution is kept, the pre-#19164 behaviour, so a PTB is
      never dropped where it used to be sent.
    - **HA is left to the poll arm.** The arm already finalizes every matched
      resolution (`finalize_embedded_icmp_resolution_parts`: the HA snapshot,
      the fabric redirect, the #16053 owner-RG promotion).
    - **A design change from the first draft.** The first draft threaded HA
      state into `NatMatchCtx` and ran the reply's whole
      `reresolve_stored_session` pipeline inside the matcher. That applied HA
      twice and pre-empted the arm's HA-inactive accounting. It broke
      `poll_descriptor_co_moved_pmtud_admitted_as_related_16053` and
      `poll_descriptor_unowned_claimed_zone_pmtud_denied_16053`, and with the
      cache-free-only lookup also
      `icmpv6_te_prefers_reverse_session_resolution_for_client_return_path`.
      All three pass unchanged under the final design.
    - **Residuals:**
      - the #9951 leak-revocation arm is not mirrored;
      - a stored FabricRedirect whose fresh lookup finds no neighbor yet (just
        after a takeover) keeps the redirect until the neighbor is learned.
    - **`handle_upsert_synced` is untouched.**
    - **Cells** (`icmp_embed/stale_reverse_return_tests.rs`), each driving the
      arm's real sequence (the return resolution, then
      `finalize_embedded_icmp_resolution_parts`) against the reply pipeline:
      - (a) after an RG activation;
      - (b) a FIB change, with the forwarding generation advanced;
      - (c) the negative control, with the peer owning the client RG;
      - (d) the cannot-forward fallback;
      - an ignored cost bench.

- **Timestamp:** 2026-11-16T19:32:40Z
  - **Action:** the three existing tests whose fixtures changed, and why the
    TEST was wrong in each case and not the fold (the coordinator's check).
    - **The mechanism.** The poll pass stamps the forwarding generation before
      any descriptor (#11373, `set_forwarding_revalidation_gen_with_neighbor`).
      A reverse the harness installed beforehand is therefore STALE, and the
      reply re-resolves it cache-free by the FIB. The other two tests call the
      matcher directly with a never-stamped table, and are served by the
      #11315 cached path, which needs the stored MAC to be the live neighbor.
    - **`poll_descriptor_co_moved_pmtud_admitted_as_related_16053`:**
      - it pins that a co-moved PMTUD error whose delivery egresses the
        locally active LAN is promoted and admitted RELATED;
      - its client had no neighbor anywhere, which is impossible for a live
        session, since the forward packet came from that client;
      - the change adds the client's neighbor on the LAN (24). Its assertions
        and the property are unchanged.
    - **`icmpv6_te_prefers_reverse_session_resolution_for_client_return_path`:**
      - it pins that the reverse session's resolution is preferred for the
        client return path (#219, NPTv6);
      - its `ForwardingState::default()` had no neighbor for the stored next
        hop;
      - the change adds the client's live neighbor on egress 24. The
        assertions are unchanged.
    - **`poll_descriptor_unowned_claimed_zone_pmtud_denied_16053`:**
      - **What it pins:** the unowned half of #16053. A co-moved PMTUD error
        arrives over the fabric with an Ambiguous stamp, and its delivery
        egresses an interface whose RG (3) is NOT forwarding-active here. The
        withheld claimed zone must stay unpromoted, RELATED never fires, the
        PTB is not forwarded, and the refusal is counted HA-inactive.
      - **Why the old client address was an impossible shape.** The client
        10.0.61.102 sits on `reth1.0`'s subnet (10.0.61.0/24, RG2, active),
        while the stored delivery named `reth3.0` (10.0.62.0/24, RG3).
        - Under a current stamp that stored value cannot arise: it would have
          been resolved by the same FIB, which places the client on egress 24.
        - Under the harness's stale stamp, a reply re-resolves to egress 24.
        - So "delivery egresses an inactive RG" held only because the old ICMP
          path used the stored value verbatim, which is this issue's bug.
      - **The change** moves the client onto `reth3.0`'s subnet
        (10.0.62.102), where the FIB and the stored delivery agree. Its four
        assertions are unchanged, and it pins the same property: the PTB is
        still denied for the unowned claimed zone, with HA-inactive counted
        once.
      - **The ORIGINAL fixture, measured on fold 1 and on master** (a probe
        on the throwaway branch `probe/19164-orig-16053`, tcp:xpf-testrunner3,

    - **The shape.** As above, but `reth3.0` is marked peer-owned, so its

      |---|---|---|

      | FabricRedirect | forwards 1 | forwards 1 |

    - **So fold 1 flipped a #16053 verdict on a valid shape:** a local
      reverse whose client RG has moved to the peer, before demote rewrites
      it.
    - **The reply path on the identical shape**
      (`probe_unowned_peer_owned_reply_path_19164`, master code) takes the
      WAN answer in two places:
      - a stale local reverse, on either arrival;
      - a stored FabricRedirect arriving over the fabric link
        (`rehome_skipped`).

      This is a pre-existing reply-path defect, filed as #19171 with the full
      table.
    - **Fold 2, the connected-owner guard**
      (`return_resolution.rs` `contradicts_connected_owner`). The fresh
      answer is NOT adopted when all of these hold:
      - it is a local candidate (FC or MissingNeighbor on a non-fabric
        egress);
      - the client has a known connected owner
        (`connected_owner_rg_for_target_in_table`, the HA-independent ledger,
        which still names a withheld peer-owned prefix);
      - its egress is not the client's connected interface.

      There the stored resolution is kept (master's value), and finalization
      judges it with HA once.
      - It is the HA-free core of the reply's own verdict: #15958b's
        connected-interface equality, and #16524's re-home for an unknown
        owner.
      - It covers every stored shape and every arrival, which closes both
        #19171 holes for ICMP.
      - It replaces fold 1's retain plumbing (`StoredRedirectReturn`, the match
        field, `retain_stored_fabric_redirect`). With the guard, that plumbing
        added nothing: every case it decided, the guard plus finalization
        decides the same.
    - **New cells**, in `tests_embedded_poll_filter.rs` from the probe shapes:
      - `poll_descriptor_unowned_peer_owned_stale_local_reverse_pmtud_denied_19164`
        asserts master's DENY;
      - `poll_descriptor_unowned_peer_owned_stored_redirect_pmtud_not_out_the_wan_19164`
        asserts one forward, as master, and not by the WAN egress.
    - **New mutant:** M4 removes the guard.
    - **New residual:** a more-specific route that overrides a connected
      client's prefix after install is not followed by the error, which keeps
      master's stored value. A reply follows it.
