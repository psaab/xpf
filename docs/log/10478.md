# Issue #10478 — S5 capture witness surfaces and harness reader

## Scope and Phase-1 approval

Phase 1 approved a witness-first implementation for H1/H2/H3 diagnosis. Phase 2a is intentionally limited to witness surfaces, the harness reader, and unit cells; it does not change H-branch forwarding behavior, run a live cluster, or claim packet delivery without a product-owned downstream witness.

The design approval carried three binding directives:

1. The Go API must expose its authenticated actor counters and the Rust helper must expose an additive `s5_reinject` status block. The surfaces join on `run_id`, `generation`, and `permit_epoch`; Go must not proxy the Rust block into one synthetic status surface.
2. `delivered` is valid only when a product-owned witness observes the path downstream of the Rust TUN write. When no such witness exists, the surfaces publish `delivered_available=0` with an explicit residual and never alias `completed_written` or `Written` to delivery.
3. Phase 2a consists only of witness, harness, and unit work. Green rows remain VOID until the Phase-2b attestation and workload evidence.

The design was approved in the Phase-1 issue discussion before implementation. No live-cluster access was used for this PR.

## Ownership boundary

Go does not proxy the Rust block into a single status surface. Go owns the capture actor and its receive/adjudication counters; Rust owns q0 authority, terminal outcomes, and bounded provenance. Keeping these surfaces separate prevents a control-plane proxy from erasing ownership and residual uncertainty, while the authenticated `run_id`/`generation`/`permit_epoch` tuple makes the two observations joinable without converting an unavailable downstream witness into a success claim.

## Phase 2c delivered witness

Phase 2c adds the q0 delivered witness without changing the transit-gate verdict. The inet forward fence renders a named `CounterObj` and `Objref` only on the exact q0 conjunction `iifname=xpf-usp1`, `mark=0x58465001`, and `mask=0xffffffff`, immediately before the final `accept`. The counter is strictly non-terminating and verdict-neutral; the bridge fence has no witness object. `ReadTransitFenceCounter` requires the named object and the exact armed q0 rule/Objref, so an absent, detached, disarmed, malformed, or unreadable fence is unavailable rather than a zero delivery count.

The armed-fence installer preserves its one-second reassertion cadence. Replacement is skipped only when all four gates hold: (1) the desired spec is the q0 witness spec, (2) the prior install succeeded, (3) the cached spec is exactly equal to the desired spec, and (4) canonical live readback proves the same inet/bridge tables, `forward` chain policy, ordered rules, sets, named counter object, and q0 Objref. Mutable packet/byte counters and kernel handles are excluded from that equality. Any read error, malformed or unequal shape, missing counter, policy drift, or non-witness/unarmed spec takes the existing replacement path. Thus an identical periodic tick preserves the kernel counter, while uncertainty remains fail-closed and heals the fence. The Go pipeline baselines the counter exactly at `Start`; absent/read-error/negative-delta/reset conditions latch delivery unavailable for the actor run and never lazily rebaseline. The q0 rule is a deliberate superset witness (shared `MissingNeighbor` traffic can also match), so its delta is authoritative only for a quiesced S5 window; a TUN userspace write is kernel RX, not a TX-side scrape.
