# #14980 — grpcapi: bound Ping and Traceroute stream sends so diag limiter slots cannot be pinned indefinitely (D35-01)

- **Timestamp**: 2026-10-18
- **Mechanism**: `Server.Ping`/`Server.Traceroute` (`pkg/grpcapi/server_diag_ping.go`) passed `func(line) error { return stream.Send(...) }` inline to `streamDiagCmd`. grpc-go `Send` has no deadline: a client that fills its 64 KiB stream window and stops draining parks `Send`. That parks the scanner goroutine inside `streamDiagCmd`, so `c.Wait()` never returns, the handler goroutine never returns, and its `defer release()` never fires. The exec timeout does not help (the waiter is stuck downstream of the child, and the parent stream ctx stays live while the connection is open), and the #9051 reauth wrapper cancels only the wrapper `Context()`, not the transport `Send` (see `authz_stream_reauth_9051.go:122-145` note). Four such clients permanently exhaust the process-wide `diagcmd.DefaultLimiter` (`MaxConcurrentDiagnostics = 4`), shared with the REST ping/traceroute surface — every later diagnostic on both surfaces returns `ResourceExhausted` until restart. Validated MATERIAL 3-way (Codex/Opus/Spark, run `tpzkKgAuZL`, claim `D35-01`).
- **Action**: Added `sendDiagFrame` + package-var `diagStreamSendTimeout` (30 s, matching the MonitorInterface/MonitorPacketDrop slow-reader budget) in `server_diag_ping.go`, generalising the proven `sendMonitorInterfaceFrame` pattern (#9891) to the diag response types via a send closure. Each line's `Send` runs in a worker; the handler path selects over completion, stream-ctx cancellation, and the per-write timer. On sever the handler returns `DeadlineExceeded` (or the ctx error) promptly — which also unblocks `streamDiagCmd`'s scan loop so it kills the child — and the `diagLimiter` slot *transfers* to the Send worker, which releases it when `Send` finally unblocks (handler return drives grpc-go `WriteStatus` → stream-ctx cancel → flow-control quota release, so the worker exits promptly; retained H2 transport state is separately bounded by `MaxConcurrentStreams`/windows). The handler's `defer release()` is disarmed on the transferred path (`Limiter.release` is idempotent, but releasing while the worker is parked would admit a fifth diagnostic beyond the cap — the #14150 premature-release hole). Timeout ownership is terminal: a Send completing in the timer boundary window still severs, never continues slotless. Ping and Traceroute only; `streamDiagCmd`, the REST surface (no gRPC `Send`), and all neighbouring behaviour unchanged.
- **Validation**: New `pkg/grpcapi/diag_send_bound_14980_test.go` (6 tests): blocked-`Send` Ping and Traceroute sever with `DeadlineExceeded` in ~150 ms (compressed timeout), slot held while the worker is parked (second RPC `ResourceExhausted`), slot freed and budget reusable after unblock; four stuck clients at the production cap of 4 all sever and the budget fully reclaims; ctx-cancel sever transfers rather than frees; boundary-completing Send still severs without leaking/double-freeing; healthy instant-drain control returns the line, nil error, slot released normally. RED on unmodified master (handlers hang in `Send`, watchdog fires, slot pinned), GREEN post-fix. Existing `TestDiagConcurrencyLimitGRPC*`, `TestStreamDiagCmd*`, `TestMonitor*` suites stay green; `go vet`/`gofmt` clean.
- **Risk**: Fail-closed only — a slow-but-legitimate reader is cut per write after 30 s of *zero* drain progress, never on elapsed stream lifetime (ping emits ~1 line/s, well inside the window). DELIBERATELY NOT CHANGED: retained H2 transport bytes after sever are bounded by connection/stream limits as documented for #9891, not by the limiter; no change to the REST SSE path, which already has `sseWriteDeadline`.
