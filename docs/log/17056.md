## Why

Peer-heartbeat-timeout suppression was split across the pkg/cluster boundary: the daemon held the policy (`shouldSuppressPeerHeartbeatTimeout`), the 5s cap and the `hbSuppressStart` stamp, while heartbeat admission (the reset event) ran inside `cluster.Manager.handlePeerHeartbeat` under `Manager.mu`, joined by three hooks (`SetPeerTimeoutGuard`, `SetPeerHeartbeatRecoveredFunc`, `SetPeerNeverSeenSyncFreshFunc`). That split caused #12165 (stamp never re-armed on recovery, second gap inherited an expired cap) and forced an unlock/guard/relock recheck in `handlePeerTimeout` to repair late guard stamps.

## Risk

Timing is unchanged (2s recency, 5s cap, CLOCK_MONOTONIC). Suppression state no longer survives a sync-source republish (publish resets the stamp), nor a per-connection reconnect on the same source (the `OnPeerReconnected` binding resets it at each cold-prime/announce dispatch — restoring the pre-move per-connect reset; a reconnect that neither cold-primes nor announces, e.g. a routine single-fabric flap with the cold-prime obligation discharged, does not reset, matching the pre-move dispatch which was likewise gated on `shouldColdPrime`). A timeout concurrent with heartbeat admission now serialises on `m.mu` instead of racing an unlocked guard — the #12165 late-stamp interleaving is unrepresentable rather than repaired. `peerHeartbeatFreshLocked` is consulted before suppression (previously only after the guard); a fresh heartbeat aborts either way, so no outcome changes. The reconnect reset is dispatched with `go` like `OnPeerConnected`, so a timeout running in the dispatch gap still sees the old stamp — the same async edge the pre-move daemon reset had.
