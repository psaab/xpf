# #15705 — compileIPMonitoring appended PreferredRoutes without destination dedup across repeated policy blocks

## Claim

`compileIPMonitoring` (`pkg/config/compiler_services.go`) rebuilt a fresh
per-policy route map for every same-name `policy <name>` block and appended
the result to the existing policy's `PreferredRoutes` without
deduplicating by destination. Two failure modes followed:

- **Split refinement fails commit.** Block 1 carries `next-hop`, block 2
  carries only `preferred-metric` for the same destination (the Junos
  split-block spelling). The compiler minted a second, metric-only route
  with an empty next-hop, and `validateIPMonitoringStrict` rejected it
  (`next-hop "" is not a valid IP address or DHCP interface unit`).
- **Next-hop override loses.** Block 2 restates the next-hop for a
  destination already present from block 1. Both entries reached
  `pkg/ipmon`'s `computeOverlayLocked`, where the duplicate competed for
  the same `(routing-instance, canonical prefix)` key; on a metric tie
  the first-appended entry won, so the operator's override never
  actuated.

Flat-set input never showed this: `SetPath` folds the two blocks into one
node before compilation, and `compilePreferredRoutes` already merged
repeated lines inside one block. Only hierarchical duplicates (config
files, `load merge`, `load override`) hit it.

## Fix

In `compileIPMonitoring`, seed `routes`/`order` from
`existing.PreferredRoutes` — keyed by `RoutingInstance + "|" +
staticRouteMergeKey(Destination)` (the existing family-preserving masked
prefix identity) — before compiling the new block, and assign the merged
slice back instead of appending. `compilePreferredRoutes` now keys its
map by the same canonical destination, so a block that spells a route
`0.0.0.1/0` is refined (not duplicated) by a later block spelling
`0.0.0.0/0`; the stored `Destination` keeps its first spelling. Attributes
merge per-field, last writer wins — exactly what the merged single block
compiles to. Distinct destinations, and the same destination in distinct
routing instances, stay distinct entries; the first spelling wins for a
legacy duplicate already sitting in `existing.PreferredRoutes`.

## Census note

The fix direction named removing `"services ip-monitoring policy"` and
`"services ip-monitoring policy xpfname then preferred-route
routing-instance"` from `dupConservationSkipped8436`. Measured after the
fix, both sites are still skipped by the generic census — but for
fixture-synthesis reasons unrelated to this defect: `policy` uses
`hold-down`/`match` statements that strict validation rejects without a
real rpm probe sibling (no `contextFor` preamble reaches it), and
`routing-instance` is container-only (no synthesizable scalar leaf
pair). Deleting the skip rows would fail the pinned census as stale
entries while the census still cannot probe either site, so the entries
stay; the dedicated regression tests above are the probe for this
mechanism, mirroring the #15006 disposition.

## Risk

Strict commits that previously (silently) kept duplicate routes — or
failed on split refinements — now compile the union with last-writer
attribute merging, the Junos/flat-set semantics. A config relying on the
first entry winning over an explicit later override changes meaning,
deliberately: that shadowing was the defect. No new rejection is
introduced; tolerant (lenient) loads merge identically, so no new
no-brick exposure.
