# Issue #15741 — post_transform_wg_inner_mtu_is_per_peer_underlay fails on master (0 vs 1425)

## Diagnosis

Reproduced on clean `origin/master` 439a10a241 (the issue cites
8871e79a9d; same failure):

```
post_transform_wg_inner_mtu_is_per_peer_underlay
  left: 0, right: 1425   (icmp_ptb_tests.rs peer-A assertion)
stderr: wireguard peer public key is degenerate (all-zero,
        repeated-byte, or small-order); dropping this tunnel row (#14373)
```

Root cause is NOT the suspected #14118 change
(`wg_selected_peer_outer_with_dynamic`). The suspect is innocent:
`post_transform_wg_inner_mtu_charges_selected_peer_family_14118` and
`wg_segmentation_sizes_to_selected_v6_peer_not_endpoint_v4_row_14118`
both pass on master, and the per-peer selection logic itself is
unchanged and correct.

The actual culprit is #14373 (19cbeffc20, landed after #14118):
`hydrate_wg_identity` now drops a whole WG tunnel row fail-closed when
any peer public key (or the local private key) is degenerate —
all-zero, repeated-byte, or small-order. The test fixtures for this
test still used repeated-pattern placeholder keys:

- `wg_two_peer_asymmetric_snapshot` (icmp_ptb_tests.rs): peer A
  `"0a0a0a0a"×8`, peer B `"0b0b0b0b"×8` — both repeated-byte.
- Shared fixture `wg_outer_mtu_snapshot` (test_fixtures.rs) that the
  asymmetric snapshot extends: local privkey `"deadbeef"×8`, peer
  `"abadcafe"×8`; the two-peer DNAT variant adds `"beadfeed"×8`.
- `wg_live_endpoint_survives_one_peer_edit_rebuild_14640`
  (forwarding_build/tests.rs): peer keys `"1010..."` / `"2020..."`
  (repeated-byte) — same root cause, failed identically.

With every peer key degenerate, hydrate dropped the tunnel row, so
`forwarding.tunnel_endpoints` had no endpoint for id 1 and
`tunnel_inner_mtu` returned 0 (its documented missing-endpoint
fail-closed) — hence left 0 vs right 1425. The other PTB WG tests
that passed did so because they either do not depend on the dropped
peers' AllowedIPs selection the same way or were flipped/constructed
to tolerate it; the per-peer test is the one that exercises two
distinct peers, so it is the one that went red. #15132's commit
message already noted this class ("stale repeated-byte fixtures vs
#14373 — base-attributed"), but the fixture migration in #14373
covered the Go fixtures and the forwarding_build wg_snapshot helper,
not these Rust fixtures.

The production code is correct: a real config with a degenerate peer
key SHOULD drop the row (that is the #14373 security fix), and a
missing endpoint SHOULD yield PTB inner MTU 0. This is a test-fixture
bug, not a code bug.

## Fix (test-only)

Replace the degenerate placeholder keys with fixed non-degenerate
64-hex keys, preserving every property the tests rely on:

- `test_fixtures.rs::wg_outer_mtu_snapshot`: new local privkey and
  peer-A pubkey; `wg_two_peer_dnat_snapshot`: new peer-B pubkey.
  Same key-for-key mapping for all ~90 consumers of the shared
  fixture.
- `icmp_ptb_tests.rs::wg_two_peer_asymmetric_snapshot`: new peer A/B
  pubkeys; peer A still sorts first (`0a1b...` < `f9e8...`), so the
  documented "first-peer revert path resolves to peer A" property is
  preserved.
- `forwarding_build/tests.rs::wg_live_endpoint_survives_one_peer_edit_rebuild_14640`:
  new peer A/B pubkeys (same root cause, same failure mode).

No assertion, expected MTU, or production code changed. The
fail-on-revert strength is unchanged: reverting the per-peer
selection to first-peer still returns peer A's 1500 underlay for
peer B and fails the peer-B assertion; the keys are inputs, not
expectations.

keys still drop fail-closed per #14373. The shared-fixture key swap
is value-only — consumers assert on MTUs/endpoints/peer selection,
not on key bytes (verified by the wg/icmp_ptb suites above).
