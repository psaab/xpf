# Issue #15783 — `staticHopActive` drops non-RETH / IPv6 statics when RG0 (or the VRF's RETH RG) is secondary, and misses RETH `vrrp-group virtual-address` subnets

## Claim

G23-01 — `frrHADemotionState.staticHopActive` (#15734) drops non-RETH
interface-qualified and IPv6 static routes when RG0 (or the VRF's RETH RG)
is secondary, and misses IPv4 static routes in RETH `vrrp-group
virtual-address` subnets.

## Mechanism

`staticHopActive` (`pkg/daemon/daemon_frr_rg_shutdown_11415.go`) decided
interface-qualified hops through the shared `inactiveInterface` helper.
That helper is protocol-oriented: when the named interface matches no
configured RETH RG it falls through to the routing-instance groups and
then to `!globalActive` (RG0). That is correct for BGP/IGP participation
(a non-RETH peering has no data-RETH address and must follow cluster
control ownership), but it violates the static-route contract stated at
the site — "not RETH-attributable → active" — because a node-local
connected interface (plain `ge-*`/`xe-*`/`lo0`) exists on both nodes
regardless of RG0. With RG0 secondary (a state every #15734 fixture
avoided — they always set RG0 primary), a static qualified with such an
interface, or an IPv6 static whose next-hop interface is inferred onto
one (`inferIPv6StaticNextHopInterfaces` → `xe-…`), was dropped from the
FRR managed section; per-instance statics were dropped likewise via the
instance-groups arm when the VRF's RETH RG was secondary.

Independently, the address-only attribution walk enumerated only
`unit.Addresses` prefixes of RETH interfaces. A next-hop reachable only
through a RETH `vrrp-group virtual-address` subnet (the VIP subnet exists
on the owner via VRRP, not as a configured host address) matched nothing,
so the route was kept ("no RETH prefix claims it") on the demoted node —
zebra then marked it inactive there and could select the cluster
blackhole default, while the owner-side behaviour the filter exists to
produce was not symmetric.

## Fix (only this mechanism)

In `daemon_frr_rg_shutdown_11415.go`:

- `staticHopActive` no longer calls `inactiveInterface`. A new
  static-specific `staticInactiveInterface` demotes an interface-named
  hop **iff** the interface is attributable to a configured RETH RG
  (base/unit refs, canonicalised through the existing
  `haInterfaceRefsMatch`) that is not locally active. Unmatched
  interfaces are node-local and never inactive for statics, regardless of
  RG0/`globalActive` or routing-instance groups. `inactiveInterface` and
  every dynamic-protocol filter (BGP/OSPF/OSPFv3/RIP/IS-IS) are untouched,
  so protocol demotion on RG0 loss still occurs.
- The address attribution walk (`unitAddressOrVRRPContains` /
  `prefixContainsAddr`) now scans, per RETH unit, both `unit.Addresses`
  and every `VRRPGroups[*].VirtualAddresses` prefix (mirroring how
  `globalBGPNeighborGroups` already scans both), in deterministic RG
  order. Bare VIP literals count as host prefixes; no prefix length is
  inherited from sibling addresses. A hop claimed only by an inactive
  RG's RETH prefix is demoted; an active owner anywhere in the overlap
  keeps it.
- A fallback scan attributes a hop contained in a **non-RETH** connected
  prefix (configured or virtual addresses of a plain interface) to that
  node-local interface, keeping the route even if an inactive RETH
  prefix also covers it, because the zebra connected route for the plain
  interface exists on this node.

Deliberately not done: no prefix-length inheritance for bare VIPs
(inventing a subnet), no reordering of RETH-vs-local resolution beyond
the node-local override above, no changes to `inferIPv6…`, protocol
filters, or the render.

## Regression

`pkg/daemon/frr_static_ha_15783_test.go::TestFRRStaticsNonRETHAndVRRP15783`
(drives `assembleFRRConfig`, the production wiring):

- RG0 **and** RG1 secondary: non-RETH interface-qualified v4
  (`xe-0/0/0.0`), interface-qualified v6 (`xe-0/0/1.0`), and address-only /
  v6-inferred v6 in the non-RETH `xe-0/0/1` prefix are all retained;
  the tenant VRF's node-local qualified static is retained despite its
  RETH RG (RG1) being secondary.
- Same state: the IPv4 static whose next-hop lies only in reth0's
  `vrrp-group virtual-address 192.0.2.1/24` subnet is dropped, as are the
  genuinely RG1-owned controls (configured-prefix v4, qualified v4,
  prefix v6).
- RG1 promoted with RG0 still secondary: the VRRP-subnet and RG-owned
  statics return; node-local statics remain.

RED on pre-fix code: with `staticHopActive` restored to
`inactiveInterface`, cells 1–2 drop; without the VirtualAddresses scan,
cell 3 is kept. Neighbour suites (#15734 ownership, #11415 demotion incl.
its RG0-secondary protocol assertions) remain green — protocol behaviour
is unchanged by construction.

## Residual

The node-local override resolves an overlap (same prefix on an inactive
RETH and a plain interface) in favour of keeping the route; zebra still
arbitrates the actually-installed connected routes, so a genuinely
ambiguous operator config renders on both nodes rather than neither.
Live-cluster proof (RG0-secondary split with WAN/LAN statics) still
belongs to the #12495/#13058 gate on the converged build.
