# #9556: the #6637 neigh-monitor gates read a joined thread as a leak

## Re-read at `origin/master` `e695094e3`

The issue has no comments, so its body is the spec. At this commit both #6637 gates in
`userspace-dp/src/afxdp/coordinator/tests.rs` still take their starting count with one instant
sample, `let before = neigh_monitor_thread_count();`, and assert `before == 0`:

- `coordinator_bringup_does_not_leak_a_neigh_monitor_thread_6637`, the gate the issue saw fail;
- `stopped_coordinator_guard_joins_the_neigh_monitor_on_drop_6637`, its sibling.

Their `during` and `after` reads already poll through `await_neigh_monitor_count` (5 s bound).
The helper's own comment records why an instant read is racy at thread START: the child applies
its name after the thread exists.

## Mechanism, measured

The only spawner is `start_post_readiness_neighbor_services` (reconcile bringup).
`stop_and_join_monitor` signals and then JOINS the monitor, and tests reach it through the
`StoppedCoordinator` guard or an explicit `stop()`. `Coordinator` has no `Drop`. A spawner that
never stopped would hold the count at 1 for the rest of the binary and fail the gate in every
serial run. The issue saw it fail in one run of three, which rules that out.

The question was whether a joined thread can still be counted. A standalone probe (`rustc -O`,
outside the crate) spawned a thread named `neigh-monitor`, joined it, and read
`/proc/self/task/*/comm` once:

| load | joins | still listed after `join()` | mean linger | max linger |
| --- | --- | --- | --- | --- |
| machine as-is (load 9.1) | 5000 | 43 | 2.8 ms | 14.3 ms |
| one busy loop per core (load 15.3) | 5000 | 394 | 6.5 ms | 34.5 ms |

`join()` returns once the exiting thread wakes its joiner. The kernel removes the task from
`/proc/self/task` after that, and under load the gap lasts tens of milliseconds. That is longer
than the two quick tests that ran between the guarded spawner and the gate. So the issue's three
open questions resolve like this:

- **Which earlier test spawned it:** any guarded spawner that ran shortly before the gate. In the
  failing run that is `committed_reconcile_prunes_rule_counters_for_removed_rules_7010`, which
  takes the serial lock, reconciles, and is stopped by its guard.
- **Leak or un-joined stop:** neither. The thread was joined, and only its `/proc` entry had not
  gone yet. The #6637 doc claim that every spawner stops and joins its monitor stands.
- **Rate:** per join, 0.9% at load 9 and 7.9% under full load. The gate-level rate is measured
  below.

## Census

Every read of the count in the crate: `neigh_monitor_thread_count()` is sampled instantly in
exactly those two preconditions. Every other read goes through `await_neigh_monitor_count`. No
other `/proc/self/task` counter exists in `userspace-dp`.

## Fix

- Both preconditions now use `await_neigh_monitor_count(0)`. A joined thread leaves inside the
  bound. A real leak, or a spawner that skipped the serial lock, is still listed when the 5 s
  wait ends, and still fails, with a message that now says the thread outlived the wait.
- The `await_neigh_monitor_count` doc and the serial-lock doc in `neighbor_manager.rs` record the
  exit-side race next to the start-side race they already described.

## Load-pair control: measured, and why it does not bind the fix

The pair ran in fresh processes, 200 times per set: `committed_reconcile_prunes_rule_counters_for_removed_rules_7010`
(a guarded monitor spawner), then the #6637 gate, `--exact`, `--test-threads=1`. The binaries were
base (`e695094e3`), a call-site revert (the named gate back to an instant sample) and head (both
gates wait). The spawner-then-gate order held in all 200 runs of every set.

| binary | no added load | one busy loop per core |
| --- | --- | --- |
| base | 1 of 200 gate failures (`before=1`) | 0 of 200 |
| call-site revert | 1 of 200 gate failures (`before=1`) | 0 of 200 |
| head | 0 of 200 | 0 of 200 |

The two failures are the issue's exact symptom in a serial pair, so the mechanism reaches the
gate. But 1 in 200 against 0 in 200 does not separate base from head, and busy loops did not raise
the rate: they slow the next test's start-up as much as the exiting thread's reap. This control is
recorded, and it is not what binds the fix. The two deterministic control cells below are.

## Deterministic control cells

The fix has to be observable at each gate's call site, and a timing race cannot do that reliably.
Two cells in `coordinator/tests.rs` create the window on purpose:

- `coordinator_bringup_does_not_leak_a_neigh_monitor_thread_0_lingering_monitor_control_9556`
- `stopped_coordinator_guard_joins_the_neigh_monitor_on_drop_0_lingering_monitor_control_9556`

libtest runs tests in name order under `--test-threads=1`, which is how `make test` and every
matrix run execute. Each control's name sorts immediately before its gate, which a check in the
edit script verified against the file's full test list. The control takes the serial lock and
starts a stand-in thread named `neigh-monitor`. It waits until the stand-in is counted in
`/proc/self/task`, then releases the lock while the stand-in is still listed. The stand-in exits
about a second later, well inside the gate's 5 s bound.

A gate that waits for zero passes. A gate that samples instantly reads `before=1` and fails. A
thread that never exits is still listed when the wait ends, so a real leak is still caught.

Measured on `4ca7ac6e0` (`origin/master` `81efb7aad` plus this change), serial, in execution order:

| cell | result |
| --- | --- |
| `coordinator_bringup_does_not_leak_a_neigh_monitor_thread_0_lingering_monitor_control_9556` | ok |
| `coordinator_bringup_does_not_leak_a_neigh_monitor_thread_6637` | ok |
| `stopped_coordinator_guard_joins_the_neigh_monitor_on_drop_0_lingering_monitor_control_9556` | ok |
| `stopped_coordinator_guard_joins_the_neigh_monitor_on_drop_6637` | ok |

The four cells took 3.07 s, most of it each gate waiting out its stand-in.

## Validation

- **`make test`, both legs, on `4ca7ac6e0`** (`origin/master` `81efb7aad` plus this commit): exit 0. Go: 77 packages `ok`, no `FAIL`. Rust: 5,813 passed, 0 failed, across all 11 test binaries, including both #6637 neigh-monitor gates and their two #9556 control cells. No disk-exhaustion lines.
- **Landed via merge commit; master delta since tested base shared no files with this change.** There was no rebase after the green run. Before pushing, the landing script intersects the `origin/master` delta since `81efb7aad` with this change's files by name, and refuses on any overlap. When master has moved past `81efb7aad`, it also merges `origin/master` into this commit in a throwaway worktree. The merged tree must pass `go build ./...`, `go vet ./...` (judged against master's own diagnostics) and `cargo check --tests --benches` in `userspace-dp`. Both checks repeat if master moves again before the merge, and the merge is pinned to the checked head commit. The script also refuses if a file the mutants edit differs from the matrix head `4ca7ac6e0` or was changed on master. A guard that scans the whole tree (a census, a line count, a golden file) is out of reach of both checks. A full `make test` on master after merges covers that class.
