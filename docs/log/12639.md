# Issue #12639 — back off rejected hold-drop retries

## Why

After an explicit hold interval expires, the feed manager publishes an empty
snapshot. A whole-snapshot refusal (for example retain-mode omission combined
with a policy that cannot compile without its binding) leaves the empty state
as publication debt. Each later failed fetch previously reran `onUpdate`, which
runs the daemon's full `applyConfigLocked` pipeline, and emitted another warning
although the desired empty state had not changed. At short update intervals,
this repeated full apply and log noise throughout the outage.

## What

Hold-drop refusal retries now use a per-feed exponential schedule: first retry
after five seconds, doubling to a one-hour cap. Failed fetches before the
scheduled time record the fetch error but do not call `onUpdate`. A scheduled
retry remains eligible until accepted; acceptance records the empty published
hash and clears the retry state. A successful fetch publishes changed content
immediately even while a retry is backed off and clears the retry state on
install. Ordinary rejected non-drop feed publications retain their existing
next-refresh retry behavior. README explains the distinction.

Regression cells cover an unchanged fetch inside the backoff, scheduled retry,
doubling/cap, changed-content recovery/reset, and independent retry state for
two feeds. The existing #12240 hold-drop convergence cell now advances its
injected clock through the retry deadline before expecting a retry.

## Risk / residual

Publication debt remains visible while refused. The desired hold-dropped state
is not changed or falsely marked published; only repeated full-apply retries
are rate-limited. The one-hour cap bounds recovery delay even for persistent
outages, while new content bypasses it.
