## Mechanism

`delete security ipsec vpn X` (or a PSK/proposal change) + commit → `applyIPsecTracked` → `ApplyGeneration` → successful `--load-all` → `promoteConnNames` reports X removed/changed → `terminateRemovedConns` → `terminateIKE` → charon sends an INFORMATIONAL DELETE, the peer stays silent → swanctl blocks until the 15 s `swanctlTimeout` kills it → `recordTerminateDebt` → the commit returns a teardown-debt error. Each such connection in one commit adds ~15 s under applySem, sequentially. charon holds the SA in DELETING with CHILD_SA + kernel XFRM states installed until retransmits exhaust (~165 s at defaults). Factory reset inherits it: `clearIPsecForReset` aborts on the `Clear` error. All `terminateIKE` callers (success, partial-apply, and Clear arms in manager.go) ride the single helper, so one site fixes every commit/Clear consumer including the `--list-sas`-failed unconditional fallback.

## Fix

- `terminateIKE`: append `--force`. The connection is no longer authorized, so no ack is needed — the exact reasoning the package already documents for the HA primitive (`TerminateConnection`, ike.go #15194: "a graceful delete can stall or never be acked … waiting would leave the stale SA in charon").
- `InitiateConnection`: append `--timeout 5`. Per strongSwan docs, `--timeout <s>` is the "timeout in seconds before detaching": swanctl hands the request to charon and detaches; charon keeps negotiating with its own retransmits. This bounds the commit re-initiate path and the HA failover initiate path against an unresponsive peer without the 15 s kill. NOT changed: the error wrap text (still names the connection; callers match on the error, not the argv).

## Scope decisions (siblings census in pkg/ipsec)

`--terminate` census at current master (re-verified, lines drifted from the issue's d1ea69f9aa snapshot): manager.go terminateIKE (fixed), ike.go:1008 TerminateConnection (already --force, HA demotion), ike.go:895 TerminateAllSAs (operator clear).

- **TerminateAllSAs: deliberately NOT forced.** It backs operator `clear ipsec sa` (CLI + gRPC ipsec-sa-clear). That is an operator action against a still-authorized configuration, not a de-authorization; #15279 deliberately made it attempt every SA and report each failure to the operator, so a graceful stall there is bounded (15 s), reported, and does not ride a commit under applySem. `TestTerminateAllStaysGraceful16851` pins this so a future "force everything" sweep must make the scope call explicitly (the source report's H46-03 sibling is this same operator-clear consumer). If an operator-clear stall is ever filed, it is a separate issue.
- **InitiateConnection `--timeout`: included** (the issue's "consider"). Both consumers are stall-sensitive (commit re-initiate under applySem; HA failover per-SA initiate) and neither consumes the negotiation outcome — both only need the request accepted by charon. Detaching cannot lose the tunnel: charon owns the negotiation after the handoff.

## Operator-visible delta

Removing a VPN or rotating its PSK with an unresponsive peer now commits immediately (was: ~15 s stall per connection + teardown-debt error + up to ~165 s of lingering tunnel). Factory reset no longer aborts on such a peer. Operator `clear ipsec sa` behavior is unchanged.
