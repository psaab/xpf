# #17125 — FinalizePeerTransferOut[Batch] half-cleared the transfer-out override pair (R4-Q35-04)

## Defect

`FinalizePeerTransferOut` and `FinalizePeerTransferOutBatch`
(`pkg/cluster/failover.go`) deleted only `peerTransferOutOverride`,
leaving the reqID-matched `peerTransferOutPrevious` snapshot behind and
bypassing `clearPeerTransferOutOverrideLocked`, the helper that deleted
both halves. `ResetFailover`'s #14979 comment cited both Finalize paths
(and the #8435 RG-removal purge) as keeping the pair "in lockstep" — true
for `notePeerTransferCommitted[Batch]` and the purge, false for Finalize
from the commit that added the comment.

The stale snapshot is inert today: every reader of
`peerTransferOutPrevious` is gated on the override being present
(`restorePeerTransferOutOverrideLocked` checks the reqID first;
`heartbeat_manager.go`'s #15211 snapshot only consulted it alongside an
armed override). It is a misleading-invariant defect, not a live
behaviour bug — but the #15211 restore already snapshotted `previous`
independently, so a future reader keyed on the snapshot alone would
inherit a stale peer view, and two maps that must change together with
bypass sites are the shape that produced the #8435 purge gap.

## Fix

Collapse the pair into one map so a half-clear cannot be represented:

- `Manager.peerTransferOutOverride map[int]uint64` and
  `Manager.peerTransferOutPrevious map[int]peerGroupSnapshot` are
  replaced by `Manager.transferOverrides map[int]transferOverride`,
  where `transferOverride{reqID uint64; previous peerGroupSnapshot}`
  (new type beside `peerGroupSnapshot` in `manager.go`).
- `applyPeerTransferOutOverrideLocked` writes the single entry;
  `clearPeerTransferOutOverrideLocked` is now its only delete;
  `restorePeerTransferOutOverrideLocked` reads reqID + snapshot from
  the one entry (behaviour identical: a missing snapshot was already
  indistinguishable from `present:false`).
- `FinalizePeerTransferOut[Batch]` route through
  `clearPeerTransferOutOverrideLocked` instead of a bare delete.
- The #8435 RG-removal purge in `group_state.go` routes through the
  same helper; the separate `peerTransferOutPrevious` delete 31 lines
  below it is gone.
- The #15211 peer-loss snapshot/restore in `heartbeat_manager.go`
  carries one `transferOverride` value instead of
  `overrideReqID/hasOverride/previous/hasPrevious`; its restore writes
  the single entry back.
- `election.go`'s acknowledged-override check reads the new map.
- `ResetFailover`'s #14979 comment corrected: it now states the helper
  drops the whole entry rather than claiming a pairing the Finalize
  paths did not keep.
- Existing tests referencing the old fields updated to the single map
  (`cluster_test.go`, `failover_commit_rollback_6527_test.go`,
  `fence_abort_restore_15211_test.go`,
  `reset_failover_transfer_14979_test.go`,
  `rg_incarnation_purge_8435_test.go`,
  `transfer_override_peer_loss_6656_test.go`); the #8435
  reflection guard now enumerates `transferOverrides` and still passes,
  since the purge goes through the helper. Historical mentions in
  `pkg/cluster/README.md` updated to the new name (issue-history and
  archived reviews left as historical record).

Acceptance from the issue: `peerTransferOutPrevious` no longer exists;
`grep -n 'delete(m.peerTransferOutOverride' pkg/cluster/*.go | grep -v
_test` is empty (both old names are gone from production code entirely);
the probe passes.

## Risk

Pure representation change under `m.mu`; no wire, election, or timing
behaviour changes. The one semantic subtlety: previously an override
could theoretically exist without a snapshot entry; `apply` always
wrote both, so the collapsed entry's zero `previous` is exactly the old
"no snapshot" case and restore treats it identically.
