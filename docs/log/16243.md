## Issue-target TCP rig remains lab-bound (2026-11-02)

- `ssh tcp` shows both `xpf-tcp-fw0` and `xpf-tcp-fw1` RUNNING, with
  `systemctl is-active xpfd` → `active` on each. This is the cluster named
  in the issue's measurement origin.
- Both nodes run ring-entries 16384 and have `Bound bindings: 30/30`,
  `Hugepage-backed bindings: 0/30`, and
  `UMEM fallback bytes: 5033164800` in
  `cli -c "show chassis cluster data-plane statistics"`.
- On both, `/proc/sys/vm/nr_hugepages = 0` and `/proc/meminfo` reports
  `HugePages_Total: 0`. Neither has
  `/etc/sysctl.d/99-xpf-hugepages.conf`; `/etc/sysctl.d/` contains only
  `99-bpf.conf`, `README.sysctl`, and `99-xpf-neighbor.conf`. This is
  provisioning on the running lab image, not a missing mmap/status code path.
- Each VM has ~16 GiB `MemTotal` (~8 GiB `MemAvailable`). The documented
  sizing formula requires 80 × 30 = 2400 pages (4.69 GiB) per VM at
  ring-entries 16384. Provision with an explicitly sized TCP rig image
  (`bake.py --hugepages 2400`) or an operator sysctl copy, then apply/restart
  and verify again. The ordinary 90-page default is intentionally only for
  ring-entries 1024.
- No changes were made on the shared TCP rig: the live TCP cluster is being
  used by a concurrent baseline lane. Post-provisioning bindings and the
  throughput spot-check therefore remain pending lab work; this report does
  not close those acceptance items.
