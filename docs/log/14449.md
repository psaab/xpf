# #14449 — Duplicate policy `scheduler-name`: wide window wins over narrow (DR20-H3)

## Defect
`compilePolicy` (`pkg/config/compiler_security_policy.go`) read the policy
scheduler binding with `policyLeaves.FindChild("scheduler-name")` — the
FIRST sibling wins. A policy authored

```text
scheduler-name wide;    # daily 00:00-23:59
scheduler-name narrow;  # daily 09:00-17:00
```

compiled `SchedulerName == "wide"` silently on strict and lenient paths.
No gate counted `scheduler-name` occurrences, and the reference-existence
gate (`validatePolicySchedulerReferencesStrict`) checked only the compiled
(first) name, which resolves vacuously because scheduler definitions
themselves merge (#5825) so both names exist. The runtime evaluator gates
the policy on the installed scheduler
(`pkg/dataplane/userspace/policies_lower.go`), so the permit policy
enforced 00:00-23:59 although the operator's last-authored value selected
09:00-17:00 — traffic admitted outside hours (fail-open). The reverse
ordering was fail-closed, but the strict path committed either ordering
silently.

RED on pristine `origin/master` (`874903e13`): strict compile succeeds
with `SchedulerName == "wide"`, no warning; lenient likewise installs
`wide` with no warning and no poison.

## Fix
- `pkg/config/compiler_security_policy.go`: collect every
  `scheduler-name` value in author order via `FindChildren` on the same
  `expandResolvingRun9792` expanded leaves; `SchedulerName` is now the
  LAST value and the ordered list is kept on the new unexported
  `Policy.schedulerNames` field (`pkg/config/types_security.go`, same
  doctrine as `terminalActions`).
- `pkg/config/compiler_policy_scheduler_name_14449.go` (new):
  `validateDuplicatePolicySchedulerName14449` rejects a policy whose
  collected values are not all identical, naming scope, policy, and both
  scheduler names; `poisonConflictingSchedulerPermits14449` marks a
  conflicting tolerant-path PERMIT policy `LenientContentDropped` so the
  userspace snapshot is refused (previous-good / fresh-boot default-deny)
  rather than enforcing a potentially wider window. Deny/reject keep
  last-wins unpoisoned — refusing a deny would itself fail open.
- `pkg/config/compiler_uniformgates_policy.go`: gate wired after the
  duplicate-policy-name gate in `runUniformGatesPolicy` (covers both
  `CompileConfig` and `CompileConfigForNode`); strict returns the error,
  lenient warns + poisons via the new
  `lenientDuplicatePolicySchedulerName14449` opt
  (`pkg/config/compiler_opts.go`, set in `lenientCompileOpts`).

Identical repeats (`narrow; narrow;`) stay legal, like identical terminal
actions (#3850). Scheduler definitions / merging (#5825) and the
reference-existence gate are unchanged — the compiled (now last-wins)
name is still checked there.

NOT changed: policy `description` duplicates (separate MEDIUM companion,
out of scope per the DR20-H3 spec); the shared `validateDuplicateSingletonScalarAST`
helper named in the spec does not exist in-tree (its DR20-H1/H2 siblings
are unlanded), so the gate follows the established typed pattern
(`validatePolicyTerminalActionStrict` #3043 / `validateDuplicatePolicyNamesStrict`
#3473) instead of inventing a parallel AST walker.

## Tests
`pkg/config/compiler_policy_scheduler_name_14449_test.go`:
- `TestDuplicatePolicySchedulerNameStrictReject14449`: zone-pair and
  global policies, both orders — strict rejects naming `scheduler-name`,
  both names, the policy, and `#14449`.
- `TestDuplicatePolicySchedulerNameLenient14449`: lenient warns + installs
  last-wins; conflicting permit (zone-pair/global, both orders) is
  poisoned; conflicting deny is not poisoned.
- `TestSingleAndIdenticalSchedulerNameUnchanged14449`: single value,
  identical repeat, and no-scheduler controls unchanged on strict and
  lenient, with no `#14449` warning and no poison.
- `TestDuplicatePolicySchedulerNameFoldedStatements14449`: two folded
  `policy p1` statements (load-merge shape) warn + poison with last-wins
  on the tolerant path.

A repeated flat `set ... scheduler-name` line can never author a
duplicate (`SetPath` replaces the single-value leaf — idempotent Junos
set semantics, verified by AST dump), so the duplicate spellings are
hierarchical text and load-merge; both are covered.
