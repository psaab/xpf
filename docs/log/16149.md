# #16149 — config: strict-3 token-walk kernel, CompleteSetPathWithValues deferred (W2.3 R2)

- **Timestamp**: 2026-10-24
- **Issue**: W2.3 / config-schema R2. The three strict consumed/identity
  walks in `pkg/config/schema_complete.go` (`CompleteSetPath:38`,
  `ResolveConsumedSetPathTokens:276`, `editIdentityConsumed:422`,
  `editIdentityStarts:486`) independently re-derived
  exact/unique-prefix/wildcard/compound-key logic, so completion and
  edit-identity walks could drift on prefix/compound semantics.
  Validated severity: Low (maintenance). No real defect claimed.
- **Change**:
  - `pkg/config/schema_complete.go`: one shared kernel
    `walkStrictConsumedTokens(tokens, strictWalkRules)` producing
    `[]strictConsumedStep{node, keyword, subKeyword, start, end}` plus
    outcome/ok. Descent mechanics are shared: exact/unique-prefix
    keyword lookup, wildcard fallback, 1+args span, compoundKey
    sub-token descent (unique-prefix resolved), multi-with-no-children
    staying at the current level.
  - `ResolveConsumedSetPathTokens` = kernel with
    `requireUniquePrefix: true` (ambiguous/unknown consumed tokens
    fail, as before); its projection now prefix-expands a compoundKey
    sub-token (the pre-kernel walk appended it verbatim — see
    Divergence note).
  - `editIdentityConsumed` / `editIdentityStarts` = kernel in tolerant
    mode: ambiguous/unknown tokens merely stop segmentation.
  - `CompleteSetPathWithValues` and `CompleteSetPath` are UNTOUCHED
    (they handle partial terminal keywords and early value
    suggestions; non-strict). The tolerant completion path (#1960) is
    unchanged. No mode-flag adapter was forced over the fourth walk.
  - Deleted: the three duplicated walk bodies (~180 lines of
    re-derived prefix/compound logic). `PopEditPathIdentity`,
    `TruncateEditPathIdentities`, `PopEditPathAfterTruncate` keep
    their exact behavior (they consume `editIdentityStarts` /
    `editIdentityConsumed`).

- **Strict-walk divergence table** (published; also pinned as executable
  assertions in `TestStrictWalkAgreement16149` /
  `TestStrictWalkDivergence16149`):

  | Row | Input class | ResolveConsumed (strict) | editIdentityStarts/Consumed (tolerant) | Shared kernel behavior |
  |-----|-------------|--------------------------|----------------------------------------|------------------------|
  | S1 exact chain | fully spelled keywords | expands, ok | steps [0 1 2…], consumed=len | identical steps |
  | S2 unique prefix | `secu na sou` | `security nat source`, ok | same steps | identical steps |
  | S3 exact compound | `family inet` | ok | family = ONE identity | identical steps |
  | S4 compound unique prefix | `family in` under a single-child family (chassis ip-monitoring), or `family inet6` | expands sub-token (FIXED, see below) | same steps | identical steps |
  | S5 wildcard fallback | `interfaces lo0` | verbatim token, ok | same steps | identical steps |
  | S6 args span | `security-zone trust description hello` | ok | desc starts at 4 | identical steps |
  | S7 multi leaf | `match source-address X destination-address Y` | ok | both leaves are identities at the match level | identical steps (stays at level) |
  | S8 truncated final | `security zones security-zone` | partial path, ok=true | truncated step recorded | identical steps |
  | S9 truncated compound | `… unit 0 family` | partial path, ok=true | family step recorded | identical steps |

  D1/D3 are the ONLY deliberate divergences: `requireUniquePrefix`.
  Everything else is one kernel.

  **Behavior fix found while merging (not previously asserted by any
  test)**: the pre-kernel `ResolveConsumedSetPathTokens` appended a
  uniquely-prefix-matched compoundKey sub-token VERBATIM (e.g.
  `family in` under a single-child family came back as `in`, not
  `inet`), while the keyword arm expanded it. The kernel expands both,
  matching `editIdentityStarts` segmentation and the function's stated
  contract ("expands uniquely matching keyword prefixes"). No existing
  test pinned the verbatim behavior; the new agreement test now pins
  expansion (row S4).
