## Why

The `TestFilterValuelessFromControls9875` control row's named range carried
`match-start layer-3; byte-offset 4;` but no match-value. Since `ece34d264f`
(#16849) the strict gate hard-rejects a value-less flexible-match-range on a
discard/reject term — exactly the control row's action — so the cell's
"control must commit" assertion failed at master. The row was exercising the
#15943/#16849 value gate instead of the #8480/#9875 valueless-leaf boundary it
exists to bound: the control's job is to prove a properly-valued
flexible-match-range records no `ValuelessFrom` marker, not to re-test the
value gate that owns refusal.

## What

- Give the control range `match-value 0x11`, keeping `match-start layer-3`,
  `byte-offset 4`, and the `discard` action. No explicit match-mask or
  bit-length: finalisation substitutes the defaults (`compiler_firewall.go`
  finalisation block; bit-length 32, full-field mask only when `!MaskSet`),
  and `FlexMatchValid` accepts any u32 at width 32 — the same strict-clean
  shape as the #5823 flat-set single-range control.
- Pin the rationale in the cell's doc comment: a value-less control row would
  test the #15943/#16849 value gate, not this boundary.
- No assertion weakened or changed: the control must still commit strictly,
  compile leniently, and record an empty `ValuelessFrom`; the value-less
  refusal half stays owned by `TestFilterValuelessFromRecordedLenient9875`
  and `TestFilterFromMarkerGateEquivalence9875`.
