# 10297 — Fail closed when the active DB disappears

## Boundary

Issue #10297 was read in full, including its comments, before implementation. It
remains open and has no comments that withdraw, narrow, contradict, or mark the
request shipped.

The failure is a missing `.configdb/active.json` being interpreted as a never-
booted store. On a previously committed box, stale day-0 `xpf.conf` can then be
imported and committed over surviving rollback history. The acceptance boundary
is to inspect rollback evidence before deciding that an absent active DB is a
fresh install; an absent DB with history must fail closed or require explicit
re-initialization.

## Evidence checked at current master

- `Store.Load` reads `active.json` through `ReadActiveMeta`; the absent-tree
  branch previously returned success with `everCommitted == false`.
- Commit persistence retains numbered text rollback slots, DB rollback slots,
  and a pending commit-confirmed record. Those markers survive independently of
  the active tree and prove that the store has previously persisted state.
- The daemon bring-up path falls back to the text file only when there is no
  active configuration and no fail-closed load error. The same path computes
  bootstrap/normal takeover and clears the managed FRR section for a fail-closed
  boot.
- `master.key` alone is not a prior-commit marker: an encrypted first write can
  create it before the first active write succeeds.

## Change

`Store.Load` now checks recovery markers before treating an absent active DB as
fresh. Text rollback slots, `.configdb/rollback.*.json`, and
`.configdb/confirm.json` return `ErrConfigAbsentWithHistory`, restore committed
state, and reload surviving history. An absent active DB with no markers remains
an ordinary first boot; a key-only `.configdb` remains fresh.

The daemon classifies the sentinel separately, skips stale text import, keeps
rollback history available, forces the lifeline-safe bootstrap class, and passes
the combined fail-closed flag through FRR setup so the managed forwarding
section is cleared just as for the existing compile-failure guard.
