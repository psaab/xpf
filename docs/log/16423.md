# #16423 DHCPv6 REBIND replacement-by-omission — engineering history

Issue: psaab/xpf#16423 (`#14997 REBIND gate keys on teardown content
only: a non-granting REBIND Reply that omits the held IA_NA address
and offers a different live one is accepted, and the held WAN address
is removed in one packet`). Finding ID: R3-F04-05, validated
MATERIAL (codex/smr/wonder). Lane branch: `fix/16423-campaign`, base
`origin/master` 80283e103e.

## Defect (present at base)

`v6ReplyTearsDownHeldBinding` (`pkg/dhcp/renew.go`) returned true only
for a non-Success status or a valid-lifetime-0 element in a requested
IA. A non-granting REBIND responder could therefore omit the held
IAADDR `2606:4700::50` entirely, offer only a different live IAADDR
(`2606:4700::bad`), pass the #14997 gate as a "pure extension", and
have `parseV6ReplyChecked` select the foreign address and store the
attacker DUID. The run loop then ran `commitLease`, whose
`prev.Address != lease.Address` arm removed the held WAN address and
applied the attacker's — one packet, no teardown element on the wire.
RFC 8415 §18.2.10.1 requires the client to leave unchanged any lease
recorded in the IA but not included in the server's IA, and to add
only new leases; omission-plus-replacement is neither.

## Fix

In `pkg/dhcp`, matcher-layer, fail-closed, extending the #14997 gate:

- `renew.go`: `v6ReplyTearsDownHeldBinding` gains replacement arms.
  For each requested IA_NA, the held addresses are read from the
  request echo (which `buildV6RenewMessage` derives from the held
  lease); a matched Reply IA that offers a live address but keeps none
  of the held ones is teardown. For each requested IA_PD, a matched
  Reply IA that offers a live prefix but keeps none of the held
  prefixes (masked-prefix identity, as `reconcileDelegatedPDs` keys
  it) is teardown. Helpers `v6HeldIANAAddrs` / `v6ReplyKeepsHeldAddr`
  and `v6HeldIAPDPrefixes` / `v6ReplyKeepsAnyHeldPrefix` implement the
  comparison; hint-only IA_PD echoes (unspecified prefix, #15069) carry
  no held element. Rejections reuse `DHCPv6TeardownRejects`.
- `dhcp.go`: `RenewalBindingStats` doc now names the #16423
  replacement class alongside #14997 teardown.
- `pkg/dhcp/README.md`: new bullet recording the
  replacement-by-omission class and the silence/extension boundary.

Not changed: `parseV6ReplyChecked`, `selectIANAAddress`,
`extractDelegatedPrefixes`, `reconcileDelegatedPDs`, `commitLease`,
the run loop, request builders, or any DHCPv4 path. The granting
server may still replace the address (re-acquisition-equivalent,
#1777); a partner that keeps the held element and adds another, or
that is silent on an IA (#15071 carry-forward / #1844
retain-on-silence), is still accepted. Known limit (recorded on the
issue, deliberate #14600 behaviour, not this defect): any accepted
non-granting Reply — including a pure extension — becomes the next
RENEW binding, so an attacker who wins the T2 race with a genuine
extension can tear down on the following RENEW; closing that would
require revisiting #14600 itself.

## Residuals

- The gate compares decoded options against the request echo, so a
  future change to `buildV6RenewMessage`'s echo discipline (or a new
  held-element container) must keep the echo faithful; the matcher
  comment names this contract.
- No wire capture or kernel run: the matcher/parse layer is executed
  by the tests and the `commitLease` removal is the pre-existing
  #14998 source path, unchanged.
