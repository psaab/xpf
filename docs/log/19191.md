`tcp:xpf-testrunner3` (fallback). Logs:

## The mechanism being removed

- On a split-RG / active-active node that does not own the flow's egress RG,
  `handle_upsert_synced` (`afxdp/session_glue/commands/upsert_synced.rs`)
  stores the raw local `ForwardCandidate` unenforced (#326: the row is ready
  at activation).
- The first slow-path packet of a cached redirected flow re-resolves (the
  import's stamp is unvalidated), HA-enforces it to `HAInactive`, converts it
  to the zone-encoded `FabricRedirect`, and persists that into the row with
  a validated forwarding stamp (#12265 Owner-persist,
  `apply_deferred_forwarding_revalidation`).
- Every primary-liveness re-import (Go `pkg/cluster/sync.go`,
  `primaryLivenessScanIntervalSeconds`, bounded to [1 s, 10 s]) writes the raw
  candidate back. Under #19173's rule the decision differs, so the install
  mints a new epoch and every cached redirected flow is refused once per
  interval (option B: ~N/L slow-path packets/s per node; master 0).

## The carry condition

`ha_resolution_carry_applies` (`userspace-dp/src/session/install.rs`), called
by `SessionTable::upsert_synced_import`. An import may keep the replaced
row's resolution AND its forwarding stamp only when ALL of these hold:

1. **A judgment was stated, about this import.** `handle_upsert_synced`
   passes a `LocalHaRederivation { from, to }` and `from` equals the
   import's resolution field for field (egress, TX ifindex, next hop,
   neighbor and source MACs, VLAN, MTUs). The handler states it only when it
   stored the raw local lookup itself, unenforced, because the owner RG is
   not forwarding-active here (`!is_active`), not the #326 peer-candidate
   fallback; any other caller (`upsert_synced_with_origin_and_leak`, the
   shared-hit materialize, `UpsertLocal`, the session-level wrappers) passes
   none, and reverse rows never get one.
2. **HA class.** `from` is a pre-HA local candidate (`ForwardCandidate` or
   `MissingNeighbor`) and `to` is a `FabricRedirect`. Only a redirect is ever
   kept, so the carry can never keep a LOCAL forward. `HAInactive` /
   `ClusterTerminalHAInactive` are not carried: no cache entry is ever
   seeded from them (`ForwardingDisposition::is_cacheable`), so carrying
   them would change what an import writes for no benefit.
3. **This node's own, current HA judgment.** `to` is what the stored-session
   pipeline (`reresolve_stored_session`, the function the packet path and
   RefreshOwnerRGS/DemoteOwnerRGS all call) derives from `from` for an
   ordinary direct arrival under the HA snapshot the import command ran with
   (`direct_arrival_rederivation`, `afxdp/session_glue/resolution.rs`), and
   `to` equals the row's resolution field for field (fabric egress and TX
   ifindex, peer fabric MAC, zone-encoded source MAC, VLAN, MTUs).
4. **The row's resolution is a validated derivation of the current
   generation.** The table's revalidation generation is valid and the row's
   stamp equals it. Only three writers stamp a valid generation, all this
   node's own derivation: the slow-path persist
   (`revalidate_forwarding_resolution_with_egress_zone`), the HA transition
   refresh (`refresh_in_place`) and the local install. A default (never
   validated) stamp, or one from an older config/FIB/neighbor generation,
   never carries a resolution difference. This is the fix for the
   prototype's bug, which read a default stamp as fresh.
5. **Everything else equal.** The install substitutes the row's resolution
   and stamp into the replacing row, then runs #19173's
   `replacement_keeps_incarnation` unchanged: same incarnation identity,
   the whole decision (so NAT and the installing-table stamp must be EQUAL),
   every metadata field (owner RG, zones, fabric ingress, policy, ...),
   SNAT provenance, origin, leak stamp, adoption mark, TCP close class and
   handshake stage. If it fails, the install puts the import's own
   resolution and a default stamp back and mints, exactly as without the
   carry.

**Egress, next hop, installing table.** NAT and the installing-table stamp
are decision fields outside the resolution and must be equal (term 5). The
import's raw egress and next hop are NOT compared with the row: on current
master the stored `FabricRedirect` names the fabric parent (egress 4), the
peer's fabric MAC and VLAN 0, not the WAN unit, so a literal egress compare
can never hold. They are pinned instead by terms 1, 3 and 4: the judgment is
derived from exactly the import's resolution, and under the same generation
the import's raw lookup and the one the persisted redirect came from are the
same lookup of the same flow, NAT and installing table. Under #19171 Stage A
(a split node's re-resolution names the same egress and only the disposition
changes) the rule needs no change: term 3 compares against whatever the
pipeline derives.

**Forwarding stamp.** The kept row keeps its stamp with its resolution: the
pair says "derived under generation G", and term 4 requires G to be the
current one. So no kept row ever carries a default stamp, and the
alternative ("keep the resolution, reset the stamp to never-validated") is
not needed. A kept stamp goes stale exactly as an unreplaced row's does:
the next config/FIB/neighbor generation makes the slow path re-resolve and
re-persist, and the same generation change has already fenced every cache
entry seeded under G (cell `a_generation_change_revalidates_the_kept_row_19191`).
The other local revalidation stamps (filter, policy, SNAT, app-id) are still
reset by the import, as #19173's identical carry does.

## HA-safety trace

Line numbers are at this branch's tip. The question: can keeping the local
HA-derived resolution ever keep forwarding locally a flow this node no
longer owns, or keep redirecting a flow this node now owns?

1. **Never a local forward.** Term 2: only a `FabricRedirect` is kept
   (`ha_resolution_carry_applies`, `session/install.rs`). A carried row can
   never hold a `ForwardCandidate` the import did not write.
2. **Never a redirect the import's own HA snapshot disagrees with.** The
   handler computes the owner RG from the raw local resolution and
   `allow_replace_local` from the HA snapshot it runs with
   (`upsert_synced.rs:139-141`; `synced_entry_allows_local_replace`,
   `session_glue/resolution.rs:431`). On a node where that RG is
   forwarding-active (`is_active`), it HA-enforces and states NO judgment
   (`upsert_synced.rs:190`), so the import installs the enforced local
   candidate and mints: an import that lands after an activation is visible
   to the worker replaces a carried redirect with the local candidate (cell
   `import_after_activation_installs_the_local_candidate_19191`). On the
   inactive path the judgment is derived under the same snapshot
   (`direct_arrival_rederivation` -> `reresolve_stored_session`,
   `session_glue/resolution.rs:735`, whose HA enforcement is at `:796`) and
   must reproduce the row exactly (term 3).
3. **The worker sees an HA change in the order the coordinator publishes it.**
   `update_ha_state` bumps the demoted and activated RGs' epochs (and the
   node-level slot 0 on an activation) BEFORE it publishes the new runtime
   (`afxdp/ha/state.rs:63-79`, store at `:81`), then pushes DemoteOwnerRGS
   (`:114`) or RefreshOwnerRGS (`:249`) behind any import already queued.
   The worker loads the HA snapshot once per loop pass, before it drains
   its command queue (`worker/loop_body/mod.rs:1072`). So an import drained
   in a pass that loaded the pre-transition snapshot can still carry the
   redirect; the transition command for that worker is queued behind it, and
   the cache fences read the epoch atomics live (point 4). That window is
   not new: the carried row is byte-for-byte the row the slow path's
   Owner-persist writes on the first packet after any import (terms 3 and 4
   require it), which is the steady state of every cached redirected flow
   under option (B), and on master after any slow-path pass. (Observation,
   not changed here and independent of the carry: a RefreshOwnerRGS pushed
   between a pass's snapshot load and its drain is applied in that pass with
   the pre-transition snapshot; the per-packet re-judgement in points 4 and 6
   is what keeps forwarding right for such a row. Read from the code, not
   reproduced in a cell.)
4. **The cache entry is fenced on every HA change for its flow.** The epoch
   compare at lookup (`afxdp/flow_cache.rs:1785`), the live lease
   (`:1813`), and the per-hit decision validator, whose redirect arm
   re-judges a cached `FabricRedirect` against the slow path's re-home result
   (`FabricRedirectDestinationNowLocal`, `forwarding/ha.rs:669-685`) and
   whose `EnforceChanged` arm (`:695`) re-runs enforcement. None of them
   reads the row's stamp, so a kept stamp cannot keep an entry alive across
   an HA change (cells `activation_*_19191`, `demote_*_19191`).
5. **The transition paths rewrite carried rows.** RefreshOwnerRGS collects
   EVERY peer-synced row, not only the activated RG's
   (`commands/refresh_owner_rgs.rs:156`), re-resolves it through the same
   pipeline with the Command arm (`:174`) and writes forwarding outcomes
   with a fresh stamp (`refresh_for_ha_transition`, `session/mod.rs:7014`).
   A stored `FabricRedirect` takes the #15958b/#16524 rehome-or-retain
   branch (`resolution.rs:823-838`). DemoteOwnerRGS does the same for the
   demoted RG's rows (`commands/demote_owner_rgs.rs:85`, `:111`). Both
   rewrite in place, so they never depend on the import.
6. **The slow path re-judges HA on every pass, whatever the stamp.** A hit
   on a row with a fresh stamp looks up through the synced variant
   (`session_glue/resolve.rs:738`; `cached_session_resolution` refuses a
   stored redirect, `resolution.rs:139`) and every hit re-resolves through
   `reresolve_stored_session` (`resolve.rs:758`) with packet-time HA
   enforcement. A stale stamp (`resolve.rs:684`) re-looks-up cache-free and
   re-persists.

**Verdict: safe.** The carry keeps only a redirect, only when the import's
own HA snapshot still derives exactly that redirect, and only a redirect this
node itself derived under the current generation; every HA transition
fences the cache entry and rewrites the row without the import. No unsafe
case found, so no carry exclusion beyond the five terms was needed.

**Difference from master that this carries forward from (B).** On master a
cache-served redirected flow's row holds the import's `ForwardCandidate`
(the cache kept hitting, so nothing re-persisted after an import). With (A),
and under (B) after the first post-import packet, it holds the persisted
`FabricRedirect`. At an activation a stored redirect takes the
rehome-or-retain branch instead of the else-arm: the flow re-homes when the
destination's connected owner is active here and the fresh route reaches
its connected interface (or the destination has no connected owner), and
keeps the redirect only on the #15958b transient-FIB-lag shape (owner active,
fresh route not reaching the connected interface). That is the designed
behaviour for every stored redirect, it is (B)'s steady state already, and
cell `activation_before_refresh_rehomes_a_carried_redirect_19191` pins the
re-home on the measured shape.

## The five #19173 cells the (A) prototype redded

The prototype (#19173 fold lane `c3-19173-proto`, not committed) carried any
resolution-only difference when the row's forwarding stamp read "fresh", and
read a DEFAULT stamp as fresh because the session-level tables run with no
published generation (`forwarding_resolution_is_stale` is false whenever the
table's generation is invalid). Each of the five cells re-imports a row with
a CHANGED resolution (another egress, `ForwardCandidate` -> `ForwardCandidate`,
or `ForwardCandidate` -> `FabricRedirect`) on such a table and requires a new
incarnation. All five pin a real property: a resolution change that is not
this node's own, current, validated HA judgment is a new incarnation. So the
implementation was adjusted, not the cells: each stays green UNCHANGED here.

| Cell (`session/`) | What it pins | Why it stays green under #19191 |
|---|---|---|
| `cache_incarnation_19173_tests::replaced_record_is_refused_before_any_write_19173` | a changed (egress+1) re-import is a new incarnation and its old seed is refused before any write | no judgment is stated (`upsert_synced` wrapper), the row's stamp is default and the table's generation invalid (terms 1 and 4) |
| `cache_incarnation_19173_tests::every_new_incarnation_moves_the_install_epoch_19173` | same-id changed re-import, new id, local install, delete+install all mint | same: no judgment, no validated stamp |
| `cache_incarnation_19173_tests::seed_accessor_resolves_like_the_probe_19173` | a changed re-import of the canonical row refuses the wire tuple's hit | same |
| `cache_incarnation_19173_tests::reverse_translated_alias_resolves_like_the_probe_19173` | a changed re-import of the reverse row refuses the alias hit | same; reverse rows never get a judgment |
| `reimport_carry_19173_tests::any_forwarding_input_change_mints_a_new_epoch_19173` | each of 41 single-input changes mints, the 9 resolution-field rows included | same; and its non-resolution rows are replayed WITH a judgment and a validated redirect in `any_non_resolution_change_mints_under_the_carry_19191` |

The new negative table (`every_other_resolution_difference_mints_and_installs_the_import_19191`)
pins the prototype's exact failure shape explicitly: a redirect row whose
stamp was never validated, one from an older generation, and a table that
never published a generation all mint, with the judgment stated (MR5 reds
them).
