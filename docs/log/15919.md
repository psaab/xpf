# Issue #15919 — connectedRowPeerOwned nil-provider boot window

- **Timestamp**: 2026-10-20
- **Action**: Fix F4 (GLM retro review): nil RG provider no longer suppresses a clustered primary's own connected prefixes; provider wired at dataplane construction; clustered Compile gated until wiring lands; transitions logged.
- **File(s)**: pkg/dataplane/userspace/routes.go, routes_connected.go, protocol.go, manager.go, manager_compile.go, pkg/daemon/daemon_run_bringup.go, pkg/dataplane/userspace/routes_connected_rg_15742_test.go, pkg/dataplane/userspace/routes_connected_nil_provider_15919_test.go, docs/log/15919.md

## Diagnosis (verified at HEAD 0592fffd00)

- `connectedRowPeerOwned` (routes.go) returned `true` (peer-owned) for
  `provider == nil` on clustered RG>0 rows.
- The provider was wired only inside `applyDataplaneAndHACore`
  (daemon_apply_dataplane.go:204-208). Snapshot builds running before
  that point — boot applies, link-refresh (manager_link_refresh.go)
  and overlay publishes (manager_overlay.go) racing the first wiring —
  suppressed the node's OWN prefixes. On the true primary this turned
  local transit into terminal → punt/drop until wiring plus an
  ownership edge or commit republished. Nothing logged the window.
- The boot order actually guaranteed the first full apply was wired
  (provider wiring precedes `ApplyConfig` inside the same function),
  so the exposure was the racing/early partial publishes and any
  future unwired build, not the first apply itself. The fix closes
  the class, not just the observed ordering.

## Fix

- Predicate: nil provider => not peer-owned (fail open until wired).
  A wired provider returning unknown still fails closed; the #15742
  unknown-RG test now pins only that case.
- Daemon: `setupDataplaneAndInitialConfig` wires
  `cluster.LocalGroupPrimary` into the manager right after dataplane
  construction (cluster manager exists from `initManagers`), before
  the first apply. Apply-time wiring in `applyDataplaneAndHACore`
  stays as the refresh/clear.
- Manager: `rgProviderWired` latch + `RGProviderWiredFor(cfg)`.
  Standalone configs never require wiring; nil Manager never blocks.
  `Compile` refuses clustered builds while unwired (apply retains
  prior state) instead of publishing guessed rows. The predicate
  fail-open is the backstop for direct builder calls (tests, partial
  rebuild helpers) that bypass Compile.

## Fold (#15924 review, Codex P2)

- The Compile-only gate left partial publishers open: after
  `SetRGPrimaryProvider(nil)`, `PublishRouteOverlaySnapshot` and
  `RefreshInterfaceRowsForLink` cloned the retained clustered
  snapshot, rebuilt with the nil (fail-open) provider, and sent a
  peer-owned RG prefix unmarked (reproduced with the fake-helper
  overlay fixture, generation-8 send).
- Fix: the single `apply_snapshot` send site
  (`requestApplySnapshotPreparedLocked`, pinned by
  `TestApplySnapshotHasOneSendSite9520`) refuses clustered sends
  while unwired via the m.mu-held `rgProviderWiredForLocked` variant;
  `errRGProviderNotWired` is shared with Compile and classified as a
  known-unsent failure, so no generation burns and no retry debt is
  adopted. This covers overlay, link-refresh, scheduler,
  capture-authority, and worker-arm publishers with one check.
- `TestUnwiredPublishersRefuseClearedProvider15919` drives real
  Compile + overlay + link-refresh with the provider cleared
  (0 sends, outcome state untouched) and a rewired positive control.

NOT changed: Rust side (it only consumes the Go-set
`ConnectedRGPeerOwned` flag; no protocol bump — wire shape identical),
the wired-unknown fail-closed direction, RG<=0 / standalone handling.
