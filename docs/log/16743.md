# #16743: ISSU drain weight-0 pin (ForceSecondary) undone by next recalcWeight, leaving zero owners under preempt

- **Timestamp**: 2026-10-25
- **Action**: `ForceSecondary` (the ISSU drain) pinned `Weight=0` only as a
  value in the derived `Weight` field. `recalcWeight` recomputes that field
  from monitor debt unconditionally, and the daemon apply tail feeds every
  interface monitor through `SetMonitorWeight` -> `recalcWeight` on every
  commit / peer config sync — so one no-change feed restored weight 255 on
  the drained node. Its heartbeat then advertised 255 at the higher
  priority, the peer preempt-yielded (`Preempt: lower priority`), and the
  drained node's `ManualFailover` arm returned NoChange (peer not resigned,
  not in hold, not commit-pinned), leaving no owner for the RG until the
  drained node restarted or was reset. Fix: make the pin a state fact.
  `RedundancyGroupState.forcedSecondary` is set by `ForceSecondary`
  alongside `ManualFailover`; while set, `recalcWeight`,
  `debtDerivedWeightLocked`, and `reconcileMonitorDebtsLocked` keep
  `Weight=0`. The flag is cleared wherever `ManualFailover` is deliberately
  cleared: `ResetFailover` (hence `ResetAllFailover`), peer loss in
  `handlePeerTimeout` (the #15211 fence-abort snapshot/restore carries and
  restores the flag), the electRG dual-resign and transfer-out-lease
  restores, a peer-transfer request consuming the hold
  (`manualFailoverHoldSnapshot` now carries the flag and restores the
  pinned weight on abort, preserving #10004/#10245), 
  `FinalizePeerTransferOut`/`FinalizePeerTransferOutBatch`, and
  `AbortRemoteTransferOut`. Plain `ManualFailover` does not set the flag —
  it preserves monitor-derived weight. New tests in
  `force_secondary_pin_16743_test.go` drive two real managers through real
  heartbeats: after the drain, one no-change `SetMonitorWeight` feed keeps
  weight 0 (local + wire) and owners stays 1 in both the preempt and
  non-preempt rows; monitor fail/recover + config re-apply also keep the
  pin; `ResetFailover` and peer loss clear the pin and restore the real
  weight; plain `ManualFailover` never sets the pin.
- **File(s)**: `pkg/cluster/manager.go`, `pkg/cluster/failover.go`,
  `pkg/cluster/election.go`, `pkg/cluster/heartbeat_manager.go`,
  `pkg/cluster/force_secondary_pin_16743_test.go` (new),
  `pkg/cluster/README.md`, `docs/log/16743.md` (this file).
- **Validation**: RED-on-revert verified firsthand: disabling the
  `forcedSecondary` check in `recalcWeight` makes
  `TestForceSecondaryPinSurvivesMonitorFeed16743` fail in both rows with
  `node0 weight=255, want pinned 0`. With the fix, the new tests plus the
  #10004/#10245/#9640 hold/restore and ForceSecondary suites pass
  (`go test ./pkg/cluster/ -run 'TestForceSecondaryPin|TestManualFailoverDoesNotPin|TestRequestPeerFailover|TestForceSecondary|TestManualFailoverAtPeerTimeout|TestPeerLossWithManualFailover|TestResetFailover|TestResetAllFailover' -count=1`).
- **Residual**: None known. Mixed-version peers are unaffected: no wire
  format change — the drained node simply keeps advertising weight 0,
  which old peers already honour. A stacked `ManualFailover` after
  `ForceSecondary` inherits the pin (weight stays 0 in SecondaryHold)
  until a deliberate clear, matching the #10245 stacked-hold contract.
