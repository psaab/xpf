# 15015 — Emit `ip ospf bfd` / `isis bfd` enable line before the BFD profile binding on OSPFv2 and IS-IS interfaces (A12-03)

## Summary

An OSPFv2 or IS-IS interface configured with
`bfd-liveness-detection minimum-interval` and/or `multiplier` rendered
ONLY a profile binding — ` ip ospf bfd profile xpf-<i>-<m>` or
` isis bfd profile xpf-<i>-<m>` — with no bare enable line. In the
deployed FRR (stable/10.6) neither profile line enables BFD monitoring
by itself, so the commit and `frr-reload` reported success, `show
configuration` looked correct, yet no BFD session ever ran and
convergence silently fell back to the OSPF dead interval / IS-IS hold
time.

Primary-source verification against FRR frr-10.6.0 (and master, same
shape):

- OSPFv2, `ospfd/ospf_bfd.c`: the `ip ospf bfd profile BFDPROF` DEFUN
  checks `if (!params->bfd_config)` and returns CMD_WARNING with
  "ip ospf bfd has not been set" — `bfd_config` is allocated only by
  `ip ospf bfd` (`ospf_interface_enable_bfd`). FRR's own
  `ospf_bfd_write_config` prints ` ip ospf bfd` first and
  ` ip ospf bfd profile %s` second.
- IS-IS, `isisd/isis_cli.c` + `isis_nb_config.c`: `isis bfd profile`
  enqueues only the `bfd-monitoring/profile` leaf;
  `lib_interface_isis_bfd_monitoring_profile_modify` sets
  `circuit->bfd_config.profile` and never touches `enabled`. The
  `enabled` leaf is set solely by `isis bfd`, and
  `isisd/isis_bfd.c:bfd_handle_adj_up` returns early when
  `circuit->bfd_config.enabled` is false. FRR's
  `cli_show_ip_isis_bfd_monitoring` prints ` isis bfd` before the
  profile line.
- FRR docs (bfd.rst) state the OSPFv2 profile command "Only takes
  effect if `ip ospf bfd` command is also present."

NOT changed (verified self-enabling single commands, no bare-enable
leg exists):

- OSPFv3: `ipv6 ospf6 bfd [profile BFDPROF]` is one DEFUN in
  `ospf6d/ospf6_bfd.c` that sets `oi->bfd_config.enabled = true` and
  stores the profile in the same handler.
- BGP: `neighbor X bfd profile BFDPROF` is documented in bfd.rst as
  "Same as command `neighbor X bfd`, but applies the BFD profile".
- The bare-BFD branch (no interval/multiplier) already emitted exactly
  the enable line; byte-identical after this change.

## Fix

`pkg/frr/protocols_render.go` only, in `generateProtocolsWithQNH11447`:

- OSPFv2 interface loop (was :371-379): in the profile branch, emit
  ` ip ospf bfd\n` immediately before
  ` ip ospf bfd profile %s\n`.
- IS-IS interface loop (was :1388-1396): in the profile branch, emit
  ` isis bfd\n` immediately before ` isis bfd profile %s\n`, still
  inside the interface block before `exit` (#2942 ordering preserved).

No other render path, profile naming/dedup (`bfdProfileName`,
`bfdSection.addProfile`), or config/compiler surface changes.

## Risk

Rendered `frr.conf` for profile-carrying OSPFv2/IS-IS interfaces gains
one line per interface; FRR's own `write memory` output has exactly
this two-line shape, so a subsequent config write-back/diff sees the
canonical form. Lab acceptance per the issue (BFD session visible in
`show ip ospf interface` / IS-IS running-config on the loss cluster)
remains an operator-side verify; the render contract is pinned by the
regression test. Because frr-reload previously warned-and-continued on
the OSPFv2 profile line, existing deployments gain working BFD on the
next reload with no config change required.
