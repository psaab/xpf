# #15051 — Junos `$9$` routing authentication keys are not decoded; the obfuscated blob commits strict-clean and is installed as the live key

- **Timestamp**: 2026-10-18
- **Action**: move the Junos `$9$` decoder into pkg/config and apply it at compile to every Junos-reversible routing secret leaf (BGP, OSPF including MD5 keys, IS-IS global/interface, RIP; global and per-routing-instance), refusing a malformed `$9$` at strict commit.
- **File(s)**: listed under Change.

## Defect

`pkg/ipsec/crypto.go` `normalizePSK` was the only caller of
`decodeJunosSecret`, and its only caller was the IKE PSK render in
`pkg/ipsec/policy.go` (#157, IKE only). No routing or VRRP site decoded
`$9$`: `pkg/frr/auth_token_9050.go` `authTokenOrOmit` checked only
whitespace, and `pkg/frr/protocols_render.go` rendered
`AuthPassword.Reveal()` / `AuthKey.Reveal()` verbatim. A config
migrated from Junos `show configuration` display output therefore
committed strict-clean with the `$9$...` blob as the live TCP-MD5/MD5
key, and authenticated BGP/OSPF/IS-IS/RIP adjacencies to the real peer
(whose key is the plaintext) never formed.

Known-answer probe (the IKE vector, `pkg/ipsec`
`TestGenerateConfig_JunosObfuscatedPSK`):
`$9$SpRrMLYgaZDirexdwgUDzFn9uO1RhlKW` decodes to `QZ1agnL21L`.

## Change

- `pkg/config/junos9_15051.go` (new): the `$9$` decoder (adapted from
  the MIT-licensed jcrypt tables, license pointer retained) plus
  `DecodeJunos9Secret` (exported) and `decodeJunos9AtCompile`, which
  walks BGP `AuthPassword`, OSPF `AuthKey` + `AuthMD5Keys[].Key`,
  IS-IS global/interface `AuthKey`, and RIP `AuthKey` in the global
  protocols block and every routing instance, decoding in place on
  the compiled `*Config`. A malformed `$9$` returns an error naming
  the leaf (never the value); on the tolerant paths it keeps the blob
  and returns a warning instead.
- `pkg/config/compiler_uniformgates_log_feed_routing.go`:
  `decodeJunos9AtCompile` runs FIRST in
  `runUniformGatesLogFeedRouting`, before the #9105/#14399/#14398/
  #15013 auth gates and before any renderer, so every later gate
  (e.g. the RIP 16-char length gate) and every consumer sees
  plaintext.
- `pkg/config/compiler_opts.go`: `lenientJunos9Secret15051` (set only
  by `lenientCompileOpts`) downgrades the malformed refusal to a
  warning on tolerant load/peer-sync so a persisted config still
  boots (#1960); commit/commit-check stay strict.
- `pkg/ipsec/crypto.go`: the duplicated decoder is deleted;
  `normalizePSK` now delegates to `config.DecodeJunos9Secret`, so IKE
  keeps its exact prior behaviour through the single shared decoder.
- Cells: `pkg/config/junos9_routing_15051_test.go` (valid `$9$`
  decodes at every global site and in a routing instance,
  `$9$garbage` refused at strict commit at every site with the leaf
  named and the secret never echoed, lenient keeps the blob + warns,
  plaintext controls byte-identical, decoder known-answer),
  `pkg/frr/junos9_render_15051_test.go` (full parse → strict compile →
  `generateProtocols` renders `neighbor 10.0.0.1 password
  QZ1agnL21L` with no `$9$` residue; `$9$garbage` refused before
  render), `pkg/configstore/junos9_checktext_15051_test.go`
  (`CheckText` refuses `$9$garbage`, accepts the valid probe and
  compiles it decoded).
- `pkg/config/README.md`, `pkg/ipsec/README.md`: decoder location and
  contract updated.

## Scope notes (VRRP / LDP)

The fix direction names VRRP and LDP. At this base neither carries a
decodable site, and the log records why rather than widening scope:

- **VRRP**: `validateVRRPAuthenticationAST` (#4288/#5834) already
  refuses any VRRP `authentication-type`/`authentication-key` at
  strict commit and DROPS the auth-carrying group on tolerant load,
  because the dataplane is RFC 5798 VRRPv3, which removed
  authentication. A `$9$` VRRP key therefore cannot be installed as a
  live key on either path — the surviving leg of A20-01 does not
  exist for VRRP. Adding a decode walk for a field that is stripped
  before compilation would be dead code.
- **LDP**: there is no LDP stanza, `LDPConfig` type, or LDP
  authentication-key leaf anywhere in the typed config (grep-verified
  at the fix base); LDP appears only as a predefined application /
  host-inbound token. There is no leaf to decode. If an LDP auth leaf
  is added it must join the `decodeJunos9AtCompile` walk (noted in
  the file header).

  not red for a fixture reason. (The decoder known-answer cell is
  lane-only: `DecodeJunos9Secret` does not exist on master.)
- GREEN: see the PR body for the exercised suites at the final head.

## Risk

- A config that today commits a malformed `$9$...` routing key will
  now be refused at commit/commit-check until the key is re-entered
  as plaintext or a valid `$9$` value. That is the intended
  fail-closed change: such a key never authenticated. On the tolerant
  load/peer-sync paths it still boots with a warning and the blob
  kept, so no persisted config bricks.
- Valid `$9$` routing keys now install the decoded plaintext — the
  Junos-correct key — which changes the live key for migrated configs
  from the (wrong) blob to the intended secret; adjacencies that
  could never form can now form. Plaintext (non-`$9$`) keys are
  byte-identical, pinned by the control cells.
- IKE PSK rendering is unchanged: `normalizePSK` delegates to the
  moved decoder, and the existing IKE `$9$` golden
  (`TestGenerateConfig_JunosObfuscatedPSK`) plus the malformed-PSK
  skip cells stay green.
