# #17145 — pkg/vrrp open-codes the track-demoted effective priority and Master_Down_Interval (R4-Q36-02)

- **Timestamp**: 2026-10-27
- **Issue**: #17145 (R4-Q36-02)
- **Base**: `origin/master be463f60e7`

## Defect (STEP-0, verified at base)

Live on `be463f60e7`. In non-test `pkg/vrrp`, `grep -cF '> 254 {'` counted 12
sites (the issue's 11 at its older base plus `skewTimeLocked`, added since by
#16771) and `grep -F '(256-'` counted 8 code sites. The RFC 5798
effective-priority rule (0/255 pass through; minus `TrackPriorityCost` while
tracked-down; clamp [1,254]) was re-typed in `effectivePriorityLocked`,
`armMasterDownTimer`, `armMasterDownSafetyTimer`, `shouldPreemptObservedMaster`,
`preemptingLiveLowerMaster`, `heldMasterIsStale`, `armPreemptHold`,
`observedMasterStaleLocked`, `skewTimeLocked`, the `getPriority` pending-resign
branch and `prioritySnapshot`; `3*advert + (256-p)*advert/256` was re-typed at
the matching Master_Down_Interval sites. Two preempt copies spelled the owner
sentinel as the literal `255`. Only the `prioritySnapshot` copy was pinned
(`TestGetPriority_TrackMatrix`), so a drift in any other copy survived the
suite — the exact "one formula, many gates" shape banned by
docs/engineering-style.md first principle 3.

## Fix

- `pkg/vrrp/instance_timing.go`: pure `effectivePriority(prio, cost, trackDown,
  trackIface)`, `skewFor(advert, effPrio)`, `masterDownFor(advert, effPrio)`,
  and lock-held `(vi) masterDownLocked()`. `masterDownInterval` and
  `skewTimeLocked` now delegate to them; the lock discipline is unchanged
  (#6230 — no RLock is ever taken under the write lock; the #15927
  single-hold snapshot → Reset → note invariant in the arm functions is
  preserved, with `Reset` now fed by `masterDownLocked()` inside the same hold).
- `pkg/vrrp/instance.go`: `effectivePriorityLocked`, `armMasterDownTimer` and
  `armMasterDownSafetyTimer` (still `max(3×masterDown, 500ms)`) delegate.
- `pkg/vrrp/instance_preempt.go`: `shouldPreemptObservedMaster`,
  `preemptingLiveLowerMaster` and `heldMasterIsStale` compute from their
  RLock-snapshot locals via the pure functions (owner sentinel now
  `addressOwnerPriority`); `armPreemptHold`'s watchdog arm uses
  `masterDownLocked()`.
- `pkg/vrrp/instance_rx.go`: `observedMasterStaleLocked` compares against
  `masterDownLocked()`.
- `pkg/vrrp/track.go`: the `getPriority` pending-resign branch and
  `prioritySnapshot` delegate to `effectivePriority`; `prioritySnapshot`'s
  `trackDown` return keeps its exact prior meaning (active demotion branch:
  non-0/255 priority, link down, track interface set), so status/event
  consumers are unchanged. `clampConfigPriority` is untouched — it is a
  distinct config-domain clamp, the one other legitimate `> 254` site.
- New `pkg/vrrp/priority_formula_17145_test.go`: `TestEffectivePriority_17145_Matrix`,
  `TestMasterDownFor_17145_ExactValues`, `TestFormulaAgreement_17145` (every
  former copy site — advert path, pending-resign branch, snapshot, locked
  helpers, staleness checks, preempt comparisons — agrees on one demoted
  fixture) and `TestArmTimersUseMasterDownFor_17145` (the three timer arms
  fire on the shared horizon, safety floor included).

## Risk

Low. Pure refactor: every rewritten site computes bit-identical values to
its former copy (verified site-by-site, including the 0/255 pass-throughs,
the [1,254] clamp, learned-vs-local advert selection and the safety timer's
3×/500 ms wrapper), and lock ordering/hold scope is unchanged. No wire,
config or operator-visible behaviour changes. Residual: `masterDownInterval`
still snapshots the learned interval under a short RLock and then calls the
RLock-taking `getPriority()`, exactly as before; #16771/#16768 can now land
their new lock-held sites on `masterDownLocked`/`skewFor` instead of adding
copies.
