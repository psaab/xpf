# Issue #19062: a stall in the LAST move's window was scored "never recovered"

## Why

- **Timestamp**: 2026-11-09 PST
- **Action**: In the #18780 gate (tcp, `SOAK_MOVES=40 SOAK_SLEEP=2
  SOAK_FROM=0`), move 40, the last, FAILed: "v4 stream(s) [11] stalled in
  this window and never recovered".
  - The same stream stalled on every move to node0 and recovered after
    2.3-6.1 s (COST).
  - On move 40 the soak stopped iperf3 1 s after the last window, 5.8 s
    after the issue. The stream had been stalled 4.97 s by then.
  - `traffic_for_window` scored every stall still open at the end of the
    data (`to_end`) as died, so the harness's own stop became a product FAIL.

## What

- **File(s)**: `test/incus/rg_move_soak.py`, `test/incus/rg_move_soak_test.py`,
  `docs/ha-rg-move-correctness.md`
- **Tail**: after the last move, the traffic keeps running for
  `SOAK_MAX_COST_STALL_MS` + `FINAL_TAIL_MARGIN_S` (2 s), not 1 s, before
  `stop_traffic`. A stall that began in the last window can show it
  recovered.
- **Split of a stall still open at the end of the data**:
  - one longer than the COST cap is `died` (FAIL, "never recovered");
  - one no longer than the cap is `cut_streams`: recovery was not
    observable, so the move is VOID with that reason and every other reason
    listed as unscored evidence, the same handling as an uncovered window
    (#19054). With the tail in place this happens only when the traffic
    ended early.
- **Cells** (`FinalMoveTail19062`):
  - G1's shape (`LastMoveLateStall`): a 4.5 s stall from 1.5 s after the
    last CLI, at sleep 2, is a COST, not a FAIL;
  - a stall cut by a traffic run that ends 1.7 s after the last window
    (`SOAK_TRAFFIC_S=8`) is VOID ("recovery was not observable"), with the
    window covered;
  - a stall that never ends still FAILs "never recovered".

## Validation

See the commit message (runner RED/GREEN and mutants).

## Risk

Harness only. Every run now ends with `SOAK_MAX_COST_STALL_MS` + 2 s (12 s
by default) of extra traffic, which used to be 1 s. A stall cut short is
VOID, never FAIL.

## Fold: Codex review at 79155094ef (finding 4 and the general rule)

- **Timestamp**: 2026-11-09 PST
- **Finding 4 (P1)**: a short cut stall on stream 7 made the move VOID even
  though stream 5 had a proven 19 s stall, which is past the cap and a
  FAIL. `cut_streams` and uncovered windows returned VOID before any FAIL
  evidence was looked at.
- **General rule (coordinator)**: VOID means "cannot judge", and it never
  overrides evidence that proves a FAIL.
- **Fix** (`move_verdict`):
  - FAIL > VOID > COST > PASS. Every VOID reason (an uncovered window, a cut
    stall, a VOID UDP probe, an untargeted fallback) is listed as "VOID
    evidence" beside a FAIL, and makes the move VOID only when there is no
    FAIL evidence.
  - So that every FAIL reason is evidence about traffic that was really
    sent, the absence-of-traffic checks (no ping replies in the tail, a low
    tail rate, an open ping gap) run only for a family whose generators
    covered the window. The traffic-follow counters run only when every
    family did.
- **Cells** (`VoidNeverOverridesFail19062`):
  - Codex's mixed died/cut reproduction FAILs;
  - a property cell checks every pairing of eight FAIL evidences with five
    VOID reasons, and each one FAILs;
  - follow counters that did not move are VOID without traffic and FAIL
    with it;
  - VOID reasons alone stay VOID.
