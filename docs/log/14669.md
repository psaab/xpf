# #14669 — handle_upsert_synced derives HA ownership from the peer stamp, trusts peer-cached resolutions, and leaks cross-pool reservations

## Defect

`handle_upsert_synced` (`userspace-dp/src/afxdp/session_glue/commands/upsert_synced.rs`)
computed `allow_replace_local` / `is_active` from `entry.metadata.owner_rg_id`
— the SENDER's stamp — before re-resolving, then called the cached
`lookup_forwarding_resolution_for_session`, and gated the replaced
reservation's release on `!new_entry_reserves` only:

1. Split-RG ordering: peer owner 0 with any locally active RG makes
   `synced_entry_allows_local_replace` false, so a standby-RG resolution
   is HA-enforced to `HAInactive` and the entry keeps the peer's foreign
   resolution/owner 0. Conversely a stale standby stamp (RG1) whose local
   route lands on active RG2 keeps `allow_replace_local=true` and
   `upsert_synced_with_origin` clobbers a live locally-owned session.
2. Cached trust: the cached lookup serves a peer `LocalDelivery` verbatim
   (foreign `local_ifindex`, resolution.rs fast path) and reuses the
   peer's ForwardCandidate as neighbor fallback on local NoRoute /
   MissingNeighbor — delivering transit into the wrong node's host stack.
3. Reservation leak: `reserve_flow`'s stale-tuple eviction only retires
   the incumbent in the allocator the NEW reservation lands in, so a
   Pool A -> Pool B (zone-pair change), Pool -> static, or SNAT/NAT64
   domain change strands the old holder bit forever.

## Fix

Forward entries now re-resolve with
`lookup_forwarding_resolution_for_session_without_cache`, stamp
`owner_rg_for_resolution` locally first, and only then compute
`allow_replace_local` / `is_active` and apply
`enforce_ha_resolution_snapshot` — mirroring
`collect_refresh_owner_rgs_items`. One deliberate exception: on the
standby arm (`!is_active`) a local NoRoute/MissingNeighbor may still
fall back to the peer candidate, but only through
`cached_session_resolution`, which revalidates egress/neighbor against
THIS node's live state and rejects a peer `LocalDelivery` outright
(it requires `ForwardCandidate`) — preserving #326 activation
readiness without trusting the foreign ifindex/MAC verbatim. The
previous reservation is released when the new entry does not reserve,
or when the previous `(nat, is_reverse, ingress_zone, egress_zone)`
differs from the new entry's; the release sweep is keyed on the exact
previous translated tuple and no-ops elsewhere, and same-tuple
refreshes (unchanged target) never release, preserving the holder bit.

NOT changed: the coordinator pre-publish guard in
`ha/session_import.rs` (`synced_entry_allows_local_replace` on the peer
stamp before reservation/shared publish) has the same stale-stamp shape
but is a separate surface with its own #9678 rationale; left for a
follow-up rather than folded in here.

## Tests

New `session_glue/upsert_synced_14669_tests.rs` (5 cells):
split-RG owner-0 stores local ForwardCandidate + RG1 stamp; stale
standby stamp does not clobber an active local session; peer
LocalDelivery (foreign ifindex 99) is not trusted; Pool A -> Pool B
replacement releases Pool A and reserves Pool B; same-tuple refresh
control keeps one reservation.

  kept): 4 of 5 cells fail — owner-0 stamps 0 not 1; stale standby
  stamp clobbers the active local session; peer LocalDelivery retains
  foreign ifindex 99; cross-pool replacement strands Pool A. The
  same-tuple control passes, as designed.
- GREEN (fix applied): all 5 `upsert_synced_14669` cells pass.
- `cargo test --bins -- session_glue`: 337 passed, 3 failed,
