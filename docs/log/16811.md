# Issue #16811 — deferred kernel prune is forgotten after the journal clear (R3-A56-03)

- **Timestamp**: 2026-10-25
  - **Action**: Persisted the prune deferred while the candidate is the
    running kernel (#14165) so it is collected exactly once on a later
    boot instead of leaking the candidate on disk forever. Previously
    `revert` → `restoreKnownGood` correctly deferred the destructive
    prune when `running == CandidateVersion` (or uname was unreadable),
    but `revert` then transitioned the journal to REVERTED and cleared
    it (`kernel_run.go`), so the next boot took `Promote`'s ordinary-boot
    early return and the candidate's packages, `/lib/modules/<candidate>`
    and `/boot/*-<candidate>` stayed installed, held, and on disk
    permanently. The fix adds a prune-owed sidecar
    (`kernel-prune-owed`, beside the journal, mirroring the
    arm/refusal sidecars): `restoreKnownGood` writes
    `{slot, candidate, known-good}` BEFORE any terminal journal clear on
    both deferral branches; `Promote`'s ordinary-boot branch settles it
    via `settlePruneOwed` (running-kernel re-checked here and again
    inside the real `PruneInactiveSlot`; still-running or unreadable
    leaves the record for a later boot, a failed prune keeps it for
    retry, only success clears it). A same-boot exit that reaches
    `restoreKnownGood` already off the candidate prunes in place as
    before and clears a same-candidate record so it never double-fires.
    Re-arming the same version supersedes its record in `Arm` (fatal on
    an unreadable record, mirroring the stale-marker clear); a promote
    discharges a same-version leftover via
    `settlePruneOwedAfterPromote` so it can never be refused forever.
    A different version's record is never pruned from the arm or promote
    paths (that would rewrite a slot selector to a stale known-good) —
    the next ordinary boot settles it. The record is deliberately NOT
    cleared by `clearKernelJournal`: its lifetime must outlive the
    journal's, and the transient ARMED-without-record gate state a
    promote's post-clear settle can create matches the documented
    backup/cleanup desync and refuses safely (exit-3 reboot to
    known-good), never promoting unverified.
