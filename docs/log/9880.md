- **Timestamp**: 2026-09-15
- **Issue**: #9880
- **Base commit**: `4eedd01d7` (`origin/master`, lane base)

## Re-verification at the base commit

STEP-0, live through `config.SchemaValidate` (strict) with a lenient
control, all on base:

```
prefer block+packed                      STRICT-ACCEPT            (control)
server 1.1.1.1 { key 5; }                STRICT-REJECT  unknown modifier "5"     LENIENT Key=5
server 1.1.1.1 key 5;                    STRICT-REJECT  unknown modifier "5"     LENIENT Key=5
version 4 / routing-instance foo         STRICT-REJECT  (both spellings)        LENIENT ok
threshold 400 { action accept; }         STRICT-REJECT  unknown modifier "accept"  LENIENT act="accept"
threshold 400 action accept;             STRICT-REJECT  unknown modifier "accept"  LENIENT act="accept"
server 1.1.1.1 { bogus 5; }              STRICT-REJECT  unknown modifier "bogus"
```

Two reject sites, both presence-only: the block spelling dies in
`validateModifierChild` (`pkg/config/schema_walk.go`, `len(node.Keys) > 1`
unconditionally rejects, never consulting the modifier schema); the packed
spelling dies in the `validateTypedLeaf` tail loop (every trailing token
must be a bare child keyword). Dumping the normalized tree shows
`normalizeCompactForValidation` does not split these shapes, so both sites
are reachable. Flat-set (`set ... key 5`) files the modifier as a child
via the #7132 `valueList` absorber, so the operator commit path dies at
the first site. `store.go:compileTreeStrict` runs the gate before compile,
so the reject is terminal.

In-package census of typed leaves (`valueType != ValueAny`) with children:
only `system ntp server`, `system ntp threshold`, and the CoS
`transmit-rate`/`buffer-size` leaves — which take the `tailValidator` path
(checked first in `walkSchemaNode`) and are untouched by this fix. Blast
radius is exactly the five NTP modifiers.

## Remedy

1. `validateModifierChild`: consume the modifier's declared `args` as
   value tokens, each run through the modifier's own `checkValue`
   (validator/treeValidator). Fewer → `modifier %q requires a value`;
   more → `unknown modifier` on the first excess token (same message
   family, still naming the leaf). `args == 0` keeps byte-identical
   behavior.
2. `validateTypedLeaf` tail loop + modifier-only branch: the same
   consume-and-validate while walking packed `Keys`, so both spellings
   accept and reject identically. A lone valued modifier (`server key;`)
   is a missing value, not a sibling-rule accept (the compiler drops it).
3. Schema (`schema_system.go`): `key`/`version` get
   `validator: ValidateIntegerMin(1)` — declared `ValueInteger` but
   validator-less, so `key notanint` would otherwise commit and Atoi-drop
   to the unset sentinel, the #6940 shape (consumers gate on `> 0`, cf.
   `renderChronySources`). `action` gets `valueType: ValueEnumOf` +
   `ValidateEnum([accept, reject])`, the repo's own contract
   (`types_system.go`; `renderChronyThreshold` ignores anything else).
   `routing-instance` stays arity-only: any single token is a plausible
   instance name and the compiler reads it verbatim. Every added validator
   carries a `valueType` per the #8852/#9206 inert-validator ratchets.

Deliberate boundary: a value-as-block spelling (`key { 5; }`) stays
rejected. Junos valued leaves take the value on the statement; the
block-value exception (#6774) is an explicit per-leaf opt-in no modifier
takes, and the server-modifier readers take values off Keys only.

Observed but out of scope (behavior preserved, verified): bracketed
`server [ a b ]` and nested-block `server { a; b; }` are also
strict-rejected today — a different mechanism (value-list, not
valued-modifier).

## Review fold: modifier-headed multi-token statements

Parent review (GPT NEEDS-MAJOR) found the round-1 tail loop admitted
address-less statements: `server prefer key 5` passed `prefer` as the
value (a valid hostname) and consumed `key 5` as a modifier, while the
compiler reads every token as a modifier with no address and yields zero
servers (`ntpServerValues`: modifiers table first, attach only to a
preceding server on the same node). Measured on round-1 code:
strict ACCEPT with `servers=[]`, and the block spelling
(`server prefer { key 5; }`) still rejected — a spelling divergence on
top of the admitted-but-empty hole. The all-presence run
(`server prefer prefer`) was the same hole pre-existing.

Remedy: `validateTypedLeaf` now disambiguates the head token once — a
head that names a known modifier means the statement carries NO value
on this node (the compiler's modifier-first grammar, already embodied
by `siblingSuppliesTypedValue`'s skip-modifiers rule). Lone
presence-only keeps the historical sibling rule byte-identical; lone
valued keeps `modifier %q requires a value`; multi-token
modifier-headed fails as `missing value` — with NO sibling rescue,
measured: the address-less node's modifiers are dropped even beside a
supplying sibling, so rescue would be a silent drop wearing an accept.
Flat-set never produced this shape (the absorber descends on modifier
keywords, rejecting via the lone-modifier branch); now pinned as a guard.

Deliberately unchanged adjacent: lone `server prefer;` beside a sibling
still takes the historical sibling-rule accept while the compiler drops
the prefer — pre-existing single-token semantics, not this finding; noted
for a possible follow-up filing, not widened here.

New cells: `Test9880_ModifierHeadedMultitokenRejected` (packed shapes +
with-sibling + threshold head + flat guards, all naming the leaf),
`Test9880_StrictCommitRejectsAddresslessModifiers` (commit pipeline,
both spellings), and the accept cell now asserts the SERVER LIST
(`NTPServers == [1.1.1.1]`) before the modifier fields. Full suites
re-run on the folded tree: `pkg/config` ok (184s), `pkg/configstore` ok
(33s); named cells 5x green.
