## Step-1 findings (code, file:line at 602f946af5)

### Why the standby's kernel default is the Null0
1. In cluster mode FRR always renders `ip route 0.0.0.0/0 Null0 tag 2500 250`
   and `ipv6 route ::/0 Null0 tag 2500 250`
   (`pkg/frr/config_render.go:976-983`, rationale at `:963-975`).
2. The RG-ownership filter `frrHADemotionState.filterStaticRoutes` (#15734)
   drops every static hop whose egress is a RETH of an RG this node does not
   own (`pkg/daemon/daemon_frr_rg_shutdown_11415.go:353-412`, the hop test at
   `:441`). It runs at render time from `d.cluster.IsLocalPrimary(rg)`
   (`:19-46`) and is applied to the global and per-instance statics in the
   FRR assembly (`pkg/daemon/daemon_ipmon.go:236-237,290-291`).
3. On the standby, then, zebra's only default is the Null0 (AD 250 → kernel
   metric 20). The learned-route import marks it `ClusterTerminal` by the shape
   (default prefix, static protocol, priority 20)
   (`pkg/routing/fibimport.go:107,185-196,361-363`). It reaches the helper as a
   discard `cluster_terminal` row (pref 200 in the dumps).

### Why the replacement waits for an FRR re-render
4. On promotion, the RETH statics come back only through a re-render:
   `scheduleFRRHAReconcile` (callers `pkg/daemon/daemon_ha.go:967,1092,1946`)
   → a 250 ms debounce (`pkg/daemon/daemon_frr_ha_coalesce.go:30`)
   → render under applySem → `applyFRRConfigIfCurrent`, i.e. frr-reload.py,
   300-600 ms per run (`pkg/daemon/daemon_frr_rg_shutdown_11415.go:843-899`).
   Zebra then installs the static, the kernel default changes, the learned
   import re-runs, and a routes-only publish removes the discard row.
5. Measured in lane G's dumps (RG1 moves, run-diag2): the discard row appears
   0.10-0.50 s after demotion and disappears 1.41-4.82 s after promotion.

### The helper does NOT select the discard row on either node
6. Both nodes' helper FIBs carry the CONFIG static default (pref 5,
   `172.16.50.1` / `2001:559:8585:50::1` via ifindex 12) the whole time.
   #18517 deliberately keeps it in the helper on a split node so it HA-demotes
   and crosses the fabric (`pkg/dataplane/userspace/routes.go:387-397`).
7. The Rust FIB sorts same-prefix rows by ascending preference
   (`userspace-dp/src/afxdp/forwarding_build/fib.rs:1060-1080`).
   `select_v4_route` skips a discard/reject row whenever an earlier row has a
   drivable next hop (ifindex > 0), live neighbor or not
   (`userspace-dp/src/afxdp/forwarding/fib.rs:2658-2674`). The pref-200
   terminal is therefore shadowed by the pref-5 static.
8. An unresolved gateway is a MissingNeighbor. That path buffers one packet
   per hop and fires an ICMP probe; it never hands transit to the kernel FIB
   (`userspace-dp/src/afxdp/poll_descriptor/mod.rs:13325-13335`).
9. Prediction, to be measured (acceptance 1): helper-forwarded ROUTED transit
   through the new owner is not blackholed by this window. The window still
   applies to the KERNEL default on the new owner: host-originated traffic in
   the default instance (RPM/ip-monitoring probes enabled at the edge, syslog/
   flow export, IKE, multihop BGP) meets the Null0 for 1.4-4.8 s.

### Where the discard does bite (not this cluster's config)
10. With a DYNAMIC default (BGP/OSPF on a RETH), the standby has no config
    static. Its peering is filtered by RG (#11415, `filterProtocols`,
    `daemon_frr_rg_shutdown_11415.go:47-90`), so the only helper default is the
    terminal. On the new owner the terminal demotes to DiscardRoute when no
    peer-owned egress can be attributed
    (`userspace-dp/src/afxdp/forwarding/ha.rs:204-220`), so routed traffic drops
    until the protocol reconverges. That is the routed blackhole #19050
    describes, with a window bounded by protocol convergence, not by
    frr-reload. Not measured.

### Why the discard exists (safety)
- It is a terminal, not "no route": the lookup returns BLACKHOLE/terminal
  instead of NoRoute, so a node that does not own the WAN fabric-redirects new
  connections to the owner (`config_render.go:963-969`; #15742 ClusterTerminal,
  `fib.rs:1386-1411`, stamp `:1406-1411`).
- AD 250 keeps it below every real default (static 5, DHCP 200).
- It is tagged 2500 and denied first in every generated redistribute map, so
  it is never exported (#15158, `config_render.go:924-961`).
- The #15734 static filter keeps the standby's kernel from carrying a live
  default via a RETH it does not own. That matters for interface-qualified
  hops: IPv6 statics get an inferred egress interface
  (`pkg/frr/manager.go:502-507`; `inferIPv6StaticNextHopInterfaces`,
  `pkg/daemon/daemon_run_routehelpers.go:126`).

## D1 repeat for the move-1 transit outlier: classification written BEFORE the run

- **Timestamp**: 2026-11-10 PST (committed before any repeat move ran)
  - **Action**: Pre-registered how to classify the 220 ms r4 gap on D1 move 1
    (udp, 2026-11-09).
  - **File(s)**: `docs/log/19050.md`

**Design.** A fresh D1 deb from the rebased head goes onto udp. Two
back-to-back 20-move RG1 soaks follow, with no deploy between them:
- soak A starts right after the deploy;
- soak B starts right after A, so it is the same build and no first move after
  a deploy is involved.

**Threshold.** An r4 gap of 150 ms or more counts as *elevated*. In 40 master
moves on udp the maximum was 61 ms, and on loss it was 79 ms. Elsewhere in the
D1 run, the largest gap after move 1 was 51 ms.

**Verdicts, decided in advance:**
- **First-move-after-deploy effect:** A is elevated on move 1, or at most on
  moves 1-2 (the first acquisition by each node after the deploy). A's moves
  3-20 and all of B are not elevated.
- **D1 effect:** some elevated move sits at another position, meaning any of
  A's moves 3-20 or any move of B. Master showed none in 40 moves, so even one
  such move counts against D1.
- **Not reproduced:** nothing in A or B is elevated. The verdict is a one-off
  that is not attributable. Two D1 runs plus this one do not establish a rate,
  so this would be recorded as such, not as "cleared".
- **The connected v4 gap is the discriminator for the path.** An elevated r4
  whose move also has an elevated connected gap is a move-wide event, not a
  routed-path one.

## v6 window design proposal (research only, 2026-11-10)

- **Timestamp**: 2026-11-10 PST
  - **Action**: Posted the IPv6 design proposal on #19050
    (issuecomment-6762229997). No code was changed.
    - **Why v6 is outside D1:** v6 static next hops are interface-qualified by
      `inferIPv6StaticNextHopInterfaces` (5ea19c756c, #575). In April 2026 a
      bare global v6 hop did not install even on the loss owner. An
      interface-qualified hop is active whenever the member is up, so it
      stays filtered on the standby.
    - **Options weighed:**
      - A: an address-only gated v6 hop on the standby (extends D1);
      - B: a link-local next hop (rejected; it is interface-scoped);
      - C: a daemon-side fast-path install (two writers; removal must hook
        every demotion path);
      - D: a BFD-tracked static (not general);
      - E: protodown of the standby member (high blast radius).
    - **Recommendation:** A, staged as its own issue:
      1. re-test #575 with a bare hop on the owner first;
      2. add a covering-route census guard. Zebra resolves unqualified hops
         recursively through any non-default covering route. This latent
         risk is shared with v4 D1 and needs review and lab verification;
      3. measure v6 host-originated lag with a new `host6` probe.

## A-vs-B re-assessment and the B spike (udp, 2026-11-10 08:57-09:02Z)

- **Timestamp**: 2026-11-10 PST
  - **Action**: Researched whether A can meet the bar: a pre-rendered static
    must never resolve through anything but the RETH's own connected prefix,
    including covers learned at runtime.
    - FRR 10.5.1 has no static-level "connected only" switch.
      - `static.rst` has only the `onlink` option, which is the opposite.
      - `zebra.rst` has only `ip nht resolve-via-default`, which is on in the
        traditional profile.
    - zebra does have `filter-nht`, a per-VRF, per-client-protocol NHT
      route-map, defined in `frr-zebra.yang` on a udp node and in the `zebra`
      binary. `zebra_rnh.c` applies it to the RESOLVING route (`rnh->state`).
      It can therefore require connected resolution even for covers learned
      at runtime.
    - It cannot be scoped to the gated statics: it does not see the gateway or
      the client route. So it must also deny resolution via `0/0`, which costs
      every static that resolves only through the default.
    - How staticd treats a filtered update is unverified.
    - It does not close v6.
    - Not recommended.
  - **File(s)**: `docs/log/19050.md`
