# #8274 — WireGuard type-4 decap into the AF_XDP worker

- **Timestamp**: 2026-09-04
- **Action**: STEP 2 of the #7167 adjudication's Option A — teach the XDP shim
  to steer WireGuard handshake/cookie records (types 1, 2, 3) to the kernel and
  leave transport-data records (type 4) to userspace. Deliberately inert on its
  own; step 3 is the worker decap stage that adjudicates what this stops handing
  away.
- **File(s)**: `userspace-xdp/src/wg_classify.rs` (new),
  `userspace-xdp/src/lib.rs`,
  `userspace-dp/src/afxdp/frame/tests_shim_wg_classify_8274.rs` (new),

## Premise check at `origin/master` (`5973e8fd9`)

Both halves confirmed by reading the code, not the issue.

**The decap really is outside the worker.**
`coordinator/wg_control/dispatch.rs`'s `WG_TYPE_DATA` arm calls
`engine.try_decap(...)` and, on success,
`crate::slowpath::write_packet_nonblocking(tun.as_raw_fd(), &decap_buf[..outcome.len])`.
Between those two statements there is an RFC 6040 ECN combine and nothing else:
no zone lookup, no session create, no route/PBR/filter/NAT evaluation, no zone
counter, no policy-deny event, no worker submission.

**The plaintext really is unadjudicated.** The kernel routes what lands on the
TUN, and xpf installs only `hook input` nftables chains while holding
`ip_forward` at 1 for as long as the dataplane is armed.

**And the shim really does not look at the message type.**
`wg_steer_to_kernel` was `wg_port != 0 && protocol == UDP && flow_dst_port ==
wg_port && is_local_destination(pkt)`.

## What landed

`wg_classify.rs` — a `core`-only module holding the two decisions that matter
(only type 4 is claimed; `is_local_destination` remains mandatory) — which the
shim calls and a host test `#[path]`-includes and EXECUTES. That shape is
copied from `ipv6_ext_walk.rs` + `tests_shim_ext_parity.rs`, whose own comment
records why: five successive source-text MODELS of a shim property each leaked
to a more ordinary edit, the worst of them accepting the deletion of a security
property.

## Two things the verifier forced, both of which I got wrong first

Recorded because both cost a regenerate cycle and neither is guessable.

1. **The type byte cannot be read at the steer site.** Reading at
   `pkt.payload_offset` inside `wg_steer_to_kernel` was rejected:
   `invalid access to packet, off=0 size=1, R8(id=5227,off=0,r=0)`. That offset
   reaches the call site through a `ParsedPacket` field, so its `var_off` spans
   the whole `u16` range. It was rejected identically with a hand-rolled deref
   and with the shim's own `read_bytes`, so it is the OFFSET and not the read;
   the documented narrowing mask did not fix it either, and a mask small enough
   to help would have been a correctness hazard of its own (a WireGuard payload
   offset is 42/62, or 46/66 with a VLAN, and deeper with IPv6 extension
   headers — a mask can wrap a large offset onto a small one and read the wrong
   byte, which for this classifier means possibly reading a 4 out of a
   handshake record). The byte is captured in `parse_l4`'s UDP arm instead, at
   the same freshly-validated `l4_offset` the mandatory 8-byte header read
   already uses; a 9-byte read there is a shape the verifier accepts.

2. **`ParsedPacket` may not grow.** Carrying the byte as a `u16` was rejected
   at `invalid access to packet, off=0 size=1, R4(id=343,off=0,r=0)` — and the
   full verifier trace showed the failing load was **not the new read at all**:
   it was a 1-byte load dominated by a FOUR-byte check, in `frame1`, with the
   offset reloaded from the stack. Widening the struct had pushed an unrelated
   packet read out of line into a BPF subprogram where the range was lost. A
   `bool` lands in the struct's existing padding and the object verifies.

   This is the one that would not have been found by reasoning. Four rounds of
   guessing produced four rejections; reading the full verifier log (dumped
   with `LogLevelInstruction`, since the gate only prints a tail) produced the
   answer in one.

## Inertness — the claim the issue says must be measured, not assumed

For exactly the packet set the WireGuard arm matched, a type-4 record now falls
through to the session-miss path and is matched by the SAME
`is_local_destination` predicate a few arms down, returning the SAME
`cpumap_or_pass(ctrl)`.

- `native_gre` cannot divert it: that gate requires `protocol == PROTO_GRE`,
  and a WireGuard record is UDP.
- `should_fallback_early` and the ICMPv6 NDP arm both end at the kernel too.
- `USERSPACE_SESSION_ACTION_PASS_TO_KERNEL` returns the same
  `cpumap_or_pass(ctrl)`.

So the ONE divergent outcome is `USERSPACE_SESSION_ACTION_REDIRECT`, and nothing
installs a session on the outer 5-tuple: the outer UDP header is synthesized at
frame-build time by `wg_encap_frame` under the INNER flow's session, and the
inbound direction still reaches the kernel without the worker adjudicating it.
The live `wg-interop.sh` smoke is what measures the conclusion.

## What a host test cannot bind here

The cells execute the classification module. **Nothing a host test can express
binds the shim's CALL SITE**: if `wg_steer_to_kernel` stopped calling
`wg_classify`, every cell above would stay green. The shim is `no_std` for
`bpfel-unknown-none` and cannot be executed here, and emitting a fact about the
constant into `XPF_SHIM_FACTS` would be a claim written into inert code rather
than a binding on the wiring. The live-NIC smoke is the only thing that binds
it, which is exactly why the adjudication says step 2 owes one.

## Direction of the change

Step 2 changes no packet's destination (see Inertness). The SECURITY posture
change belongs to step 3, and its direction is stated there rather than
claimed here: today an authenticated peer's inner plaintext is forwarded by the
kernel with no zone adjudication, so step 3 makes traffic that flows today
subject to policy for the first time — which means it can start being DENIED.
That is a deliberate tightening of a path that is currently open, and it is why
the two steps are separate PRs.

# Step 3 as BUILT — worker-side type-4 decap

Step 2 built the shim classifier and left it deliberately inert. Step 3 is the
change that moves packets, and it is two edits that MUST land together: the
worker gains a decap stage, and the shim stops handing type-4 records to the
kernel. Landing only the first leaves the stage unreachable; landing only the
second breaks every WireGuard tunnel.

## Direction, restated at the point it becomes true

**This is a tightening, and it can deny traffic that flows today.** Before it,
an authenticated peer's inner plaintext was written to the `wgN` TUN and routed
by the kernel: no zone lookup, no session, no policy, no counter. A peer's
`allowed-ips` is a cryptographic check on the inner SOURCE address only — no
destination, no zone pair, no application, no direction — so it was not a
security policy, and it was the only thing in the path.

**What an operator sees on the first packet after the change.** WireGuard inner
traffic that flowed yesterday is denied unless a policy admits it from the
tunnel's zone. This is not a corner case: an operator with no `sfmix ->` policy
loses all transit over the tunnel at once. That is the intended posture and it
is the reason the change is worth stating in a release note rather than only a
changelog line.

`poll_loop_denies_wg_inner_plaintext_with_no_permitting_policy_8274` is that
sentence as a test: same record, same fixture, policy removed, no session.

## The residual, narrowed by Half A (#10527)

The control thread's `write_packet_nonblocking(wgN)` in
`coordinator/wg_control/dispatch.rs` remains the local-delivery seam: it writes
decrypted host-inbound plaintext to the TUN with no zone policy, so the kernel's
input chains receive it. Half A now applies the kernel-path disposition to
EVERY ingress before that write. A steered-port record whose inner destination
is transit is dropped and counted on both shim-covered and shim-uncovered
ingress; only traffic addressed to the firewall reaches the TUN
(`rx_degraded_transit_drops`, #10527).

The local handoff was deliberately NOT removed:

- Host-inbound over the tunnel (SSH to the firewall across WireGuard) reaches
  the local stack through that TUN write. GRE's equivalent has a dedicated
  `local_tunnel_deliveries` seam; WireGuard has none, and building one is a
  separate Half-B change with its own failure modes.
- The shim-uncovered ingress remains the only kernel-path route for that
  host-inbound traffic on deployments where the shim is not attached. Removing
  the write would blackhole management over the tunnel, while retaining it for
  local delivery does not reopen authenticated transit forwarding.

So Half A closes the transit bypass on the path this issue measured and keeps
the host-inbound behavior needed by the residual path. A full worker-adjudicated
WG local-delivery seam is a separate Half-B follow-up, not part of #10527.

## Test discipline — what each mutation killed

Every guard was mutation-tested. The table is the record:

| Mutation | Cell that died |
|---|---|
| `logical_ifindex: endpoint.logical_ifindex` → `meta.ingress_ifindex` (adjudicate under the UNDERLAY) | `worker_decap_presents_inner_under_the_tunnel_zone_8274` **and** `poll_loop_adjudicates_..._8274` |
| `config_generation: meta.config_generation` → `0` (fabricate, defeating attachment fencing) | `worker_decap_presents_inner_under_the_tunnel_zone_8274` |
| drop the `first() == WG_TYPE_DATA` gate (claim every message type) | `worker_decap_declines_a_handshake_record_8274` |
| report the wrong roam port | `worker_decap_presents_inner_under_the_tunnel_zone_8274` |
| **WIRING**: poll loop never adopts the decapped frame | `poll_loop_adjudicates_...` **and** `poll_loop_denies_...` |
| **WIRING**: adopt the frame but not the rebound meta | `poll_loop_adjudicates_...` |

Two of those need explaining, because both were escapes first.

**The type gate escaped.** Deleting it left all four direct-call cells green.
The handshake cell built its fixture by flipping byte 0 of a real type-4 record,
and `try_decap` ALSO refuses that record — its own header parse fails. So the
cell asserted the right outcome for the wrong reason and could not see its
subject deleted. The fix is not a better fixture: any record that decaps is
type-4 by construction, so no input distinguishes the two refusals by outcome.
It is bound by SIDE EFFECT instead — the stage's own gate must decline without
touching any decap counter, and `try_decap` cannot refuse anything silently.

**The wiring escaped.** All four direct-call cells stayed green with the poll
loop's adoption replaced by `if false`. That is the failure mode this board has
paid for twice, so the wiring got its own pair of cells driven through the real
`poll_binding_process_descriptor` body via `txn_run_descriptor`.

Building those two cells surfaced a third thing worth recording: the deny cell
was GREEN while its permit sibling was RED, because the descriptor was being
dropped on `try_parse_metadata`'s magic check before any stage ran. "No session
installed" is what a correct deny looks like AND what a packet that never
arrived looks like. It now carries a non-vacuity control (`dbg.policy_deny >=
1`) so it cannot pass by never reaching policy again.
