# Issue #16555: fence neighbor MACs at the snapshot-build boundary

- **Timestamp**: 2026-10-24
  - **Action**: Applied the #13951 accept rule at every neighbor ingestion edge. `fenced_neighbor_mac` (forwarding_build/fib.rs) is now the single rule — a differing MAC is accepted only when the row is NUD_PERMANENT or the monitor's dynamic entry already carries the same MAC, otherwise the previous generation's MAC (static, else dynamic) is retained — shared by the mirror verb (`Coordinator::apply_manager_neighbors_with_permanent`), the forwarding build (`populate_neighbors`, now taking `previous` + the live dynamic map), and the stored-snapshot rewrite. The production builds (same-plan refresh, full reconcile) thread `Coordinator.neighbors.dynamic` into the build; discarded validation builds keep `None` (no prior evidence). `server/handlers/neighbors.rs` now stores the fenced `accepted` set (read back from the live forwarding table via `Coordinator::fenced_neighbor_snapshots`), not the raw request rows, in `guard.snapshot.neighbors`; `server/handlers/snapshot.rs` fences the stored candidate on every successful apply leg (same-plan needs-reconcile, same-plan refresh, full/deferred) via `Coordinator::fence_snapshot_neighbors` and clears the content digest when a row changes, so a rebind/arm rebuild from the stored snapshot can never install a laundered MAC. Regression cells: `snapshot_refresh_cannot_launder_refused_neighbor_mac_16555` (va71 subject: spoofed STALE refresh keeps G, genuine re-push not refused, dynamic-confirmed convergence, permanent exception), `reconcile_build_cannot_launder_refused_neighbor_mac_16555` (full-reconcile twin), `update_neighbors_stores_fenced_mac_not_refused_raw_16555`, and `apply_snapshot_stores_fenced_neighbor_mac_16555`; `manager_neighbor_mirror_cannot_replace_live_mac_without_confirmation_13951` stays green.
