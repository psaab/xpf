## Re-verified at origin/master 931ea3a65

Both producers (`root_exact_demand_queue_mask`, `exact_backlog_queue_mask`) still
folded `queue_idx < 64 ? bit : u64::MAX`, and both consumers still counted
`queue_idx >= 64` unconditionally when the mask was non-zero. The published
slot was one `AtomicU64`. Queue ids are `u8` (`types/cos.rs`), and the strict
gate enforces the forwarding-class <-> queue bijection, so a committed
interface has at most 256 queues.

## Design choice

Two options were weighed:
- **Key by exact-queue ORDINAL** (as the #1732 waterfill honored set does). It
  keeps one `u64`, but it still degrades past 64 exact queues. It also depends
  on `exact_queues_by_rate_ascending`, which a dozen hand-built test runtimes
  leave empty, so every one of those fixtures would silently change meaning.
- **Widen the index-keyed mask to 256 bits** (chosen). Every u8 queue id has
  its own bit, so no committed config reaches the overflow policy. Existing
  cells keep their meaning (bit i = queue index i). The slot grows from 3 to 6
  `AtomicU64`s, still inside its 64-byte alignment (const-asserted).

Past 256 (only via a tolerated config that breaks the bijection) there is one
documented overflow policy in `with_queue`/`counts`: saturate and over-reserve.
`builders.rs` warns on that count.

Torn reads: the four words are stored and loaded one at a time, so a reader
racing a publish can mix words from two publishes. Each word was really
published, so a single pass can add or drop a queue until the next publish.

## Acceptance line "a commit of a >64-queue CoS interface warns or rejects"

Not implemented as a commit warning, deliberately. That line was written for
the fix direction that kept a `u64` with a >= 64 policy. With a 256-bit mask a
65..256-queue interface is tracked exactly, so a commit warning about it would
describe a limitation that no longer exists. The only remaining overflow is
unreachable from a strict commit, and the runtime builder warns on it.
