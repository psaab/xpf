# #16832: #15667 preflight rejects every CA:TRUE leaf, including the stock OpenSSL 3 self-signed certificate

- **Timestamp**: 2026-10-25
- **Action**: The #15667 preflight (`managementTLSCertificatePreflightError`)
  rejected any leaf with `IsCA=true`. The stock OpenSSL 3
  `openssl req -x509 -nodes -newkey ec -pkeyopt ec_paramgen_curve:P-256
  -subj /CN=fw -addext subjectAltName=DNS:fw` command emits
  `basicConstraints=critical,CA:TRUE`, so an upgrade took a working custom
  management HTTPS certificate offline (no HTTPS leg, selector refuses
  handshakes) until the operator reissued with `CA:FALSE`. RFC 5280 does
  not forbid `CA:TRUE` on a self-signed certificate used as its own trust
  anchor, and Go/curl accept it when pinned; before `a88e050183` the file
  had no `IsCA` check and these certificates were served. Fixed by
  downgrading only the verified single-entry self-signed case to a logged
  diagnostic:
  - `pkg/api/tls_certificate_10827.go`: new
    `managementTLSCertificateIsSelfSignedCALeaf(chain)` — true only for a
    1-entry chain whose leaf `IsCA`, `RawSubject == RawIssuer`, and whose
    signature verifies via `leaf.CheckSignature` under its own key
    (`CheckSignatureFrom` is not used there because it also enforces
    parent constraints). Preflight now rejects `IsCA` only when that
    predicate is false; all other preflight rules (validity windows for
    every entry, leaf ServerAuth EKU, non-leaf CA/CertSign, adjacent
    signature links, final-entry self-signature, signing-only leaf
    KeyUsage) are unchanged. A CA:TRUE leaf issued by an intermediate
    (multi-entry chain, the existing #15667 "CA leaf" cell) and a
    single-entry CA leaf whose self-signature does not verify are still
    rejected with the original message (fail-closed; a corrupt
    self-signature also fails the final-entry `0->0` check).
  - `pkg/api/tls_certificate_10827.go`: install paths log the diagnostic
    once per install — `managementTLSCertificateCALeafDiagnostic` via
    `slog.Warn` at custom load
    (`loadManagementTLSCertificateWithGen`) and at custom monitor
    refresh (`refreshCustomManagementTLSCertificate`, after the
    unchanged-fingerprint early return so an unchanged pair does not
    re-warn hourly). Per-handshake revalidation
    (`managementTLSGetCertificateFromSlot`), the generated-pair paths and
    `generateSelfSignedCertAtWithStatusMulti` reuse the same predicate
    through preflight, so a self-signed CA:TRUE leaf handshakes and a
    generated durable pair of that shape is reused, not re-minted; no
    warning is emitted per handshake.
- **File(s)**: `pkg/api/tls_certificate_10827.go`,
  `pkg/api/tls_certificate_15667_test.go` (comment pinning the existing
  "CA leaf" cell as the intermediate-issued control),
  `pkg/api/tls_certificate_16832_test.go` (new),
  `debian/changelog`, `docs/log/16832.md`.
- **Validation**: targeted Go tests in `pkg/api`:
  `TestPreflightSelfSignedCALeaf16832` (synthetic self-signed CA:TRUE
  passes; CA:FALSE control passes and is not classified CA),
  `TestPreflightNonSelfSignedCALeafRejected16832` (intermediate-issued
  CA leaf and corrupt-self-signature single CA leaf still rejected),
  `TestCustomSelfSignedCALeafLoads16832` (`NewServer` installs the leg,
  warning logged, selector serves, real pinned TLS handshake with
  `ServerName=fw`), `TestCustomOpensslCALeafLoads16832` (certificate
  actually produced by the issue's `openssl req -x509` command on
  OpenSSL 3.6.4 loads; skips when openssl is absent or does not emit
  CA:TRUE), plus unchanged `TestPreflight15667`,
  `TestCustomChainRejectedAtLoad15667`, `TestCustomValidChainSANLog15667`,
  `TestMonitorRecoversAfterFix15667`. RED check: with preflight
  temporarily restored to reject every `IsCA` leaf, the three
  self-signed load/preflight tests fail with the original
  "leaf certificate is a CA certificate" error while the rejection
  controls still pass; restored, all pass.
- **Residual**: Browser-specific treatment of CA:TRUE leaves was not
  tested (per the source probe limits); management clients pin the
  certificate, matching the pre-#15667 behaviour. The single-entry
  exemption requires a cryptographically verified self-signature, so a
  mislabelled or tampered certificate remains fail-closed.
