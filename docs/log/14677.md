# #14677 — stop_workers (PrepareLinkCycle) must not wipe the state rebind replays

## Scope and verified mechanism

On `origin/master` before the fix (`09c6b9ed` filing anchor, re-verified
at the lane's rebase base):

- `userspace-dp/src/server/handlers/stop_workers.rs::handle` — the
  `stop_workers` verb Go's `PrepareLinkCycle` sends before a RETH MAC
  link DOWN/UP cycle (`pkg/daemon/daemon_apply_dataplane.go`) — called
  `guard.afxdp.stop()`.
- `Coordinator::stop()` is `stop_inner(true)`
  (`userspace-dp/src/afxdp/coordinator/mod.rs`). With
  `clear_synced_state=true`, `stop_inner` locks and clears
  `sessions.nat`, `sessions.forward_wire`, and — via
  `SharedSessionOwnerRgIndexes::clear(&sessions.synced)` — the primary
  HA-synced session map itself. Unconditionally, it also defaults
  `self.forwarding` and `self.validation`.
- The following `rebind` (`NotifyLinkCycle`) is documented in
  `server/handlers/rebind.rs` to rely on exactly that state:
  `tear_down` (coordinator/reconcile/teardown.rs) captures
  `tunnel_owners` from `coord.forwarding.tunnel_endpoints` and
  `snapshot_was_installed` from `coord.validation` **before** its own
  `stop_inner(false)`, and bring-up replays the live synced map and
  builds the new forwarding with `previous = Some(&coord.forwarding)`
  for PortAllocator reuse (persistent-NAT leases). After the old
  `stop_workers`, all three baselines were already empty/defaulted:
  synced sessions un-replayable, persistent-NAT allocator instances
  discarded, tunnel-owner remap purge blind. The old `rebind.rs`
  comment asserted the link-cycle path was "unaffected" because Go
  sends a separate `stop_workers` first — that separate call was
  precisely the wipe.

Consumers checked: `stop()` / `stop_with_event_stream()` remain the
terminal stops (disarm in `server/helpers/status.rs`, shutdown verb,
process exit in `server/lifecycle.rs`) and keep `stop_inner(true)`.
`stop_workers` has exactly one production caller path (Go
`PrepareLinkCycle`); its documented contract is "stop workers, rebind
recreates them", so preserving coordinator state there cannot leak
into a terminal teardown — the next `rebind` reconcile's own
`tear_down` still runs `stop_inner(false)` and a later disarm still
runs `stop()`.

## Fix

- New `Coordinator::stop_for_link_cycle()`: takes `forwarding` /
  `validation` out, runs `stop_inner(false)` (workers joined, synced
  state preserved), restores both, republishes the runtime view, and
  records `ReconcileStage::Stopped`. Holder retirement inside
  `stop_inner` runs against the live forwarding's allocators before
  the take/restore completes — the `PortAllocator`s are `Arc`-shared,
  so worker-held bits are freed on the same allocator instances the
  preserved forwarding (and the rebuild via `previous`) reuses; no
  leak, no double-free. The event stream is untouched (same as
  `stop()`).
- `stop_workers::handle` now calls `stop_for_link_cycle()`.
- `rebind.rs` comment corrected: the link-cycle leg is covered by the
  new stop, not "unaffected".

Scope cut: the reconcile/bring-up path, `tear_down`, and the terminal
stops are unchanged — they already implement the preservation
contract; only the `stop_workers` leg violated it.

## Regression cells (`userspace-dp/src/server/tests.rs`)

- `stop_workers_preserves_synced_sessions_for_rebind` — drives the
  exact Go verb sequence `sync_session` upsert → `stop_workers` →
  `rebind` and asserts the synced map survives both legs.
  RED-on-revert: restoring `guard.afxdp.stop()` in `stop_workers`
  empties the map at the post-`stop_workers` assertion.
- `stop_workers_preserves_forwarding_and_validation_baselines` —
  seeds (via `Coordinator::seed_link_cycle_baselines_for_test_14677`)
  one tunnel endpoint, one persistent pool source-NAT rule with a
  `PortAllocator`, and `snapshot_installed=true`; asserts all three
  survive `stop_workers`. RED-on-revert with the old `stop()`.
- `full_stop_still_wipes_synced_sessions_control_14677` — control:
  terminal `stop()` still wipes the synced map, proving the
  preservation is link-cycle-only and did not leak into `stop()`.

The forwarding-publish census pin
(`forwarding_publish_population_is_pinned_7015`) count for
`coordinator/mod.rs` moves 1 → 2: the link-cycle restore is a second
teardown-side `publish_runtime_view`, not an apply publish.

## Risk

- A `stop_workers` that is never followed by `rebind` (aborted cycle)
  now leaves synced sessions and forwarding resident until the next
  reconcile/disarm. That is the pre-existing behaviour of every
  `stop_inner(false)` reconcile teardown, and Go's abort path
  (`NotifyLinkCycle` rollback, #5103/#6871) does send the rebind.
- No wire, Go, or BPF changes.
