# 10288 — Close the delete-drop / queued DeleteSynced NAT strand

## Boundary

A peer-synced session can be removed by the delete-drop sweep after a
`DeleteSynced` was accepted by the worker queue but before that command was
drained. The sweep previously released only steering rows. The later command
then found no session-table entry and released steering rows only again. The
worker's NAT holder bit, `live_by_flow` record, and pool port consequently
survived for the allocator lifetime.

The refused-queue path from #8576 is different: the deleting worker already
releases the refused worker's NAT holder on its behalf. The fix therefore must
be idempotent and must not over-release a worker that will still process a
queued command.

## Fix

- Keep the existing #9560 steering release before deleting the session-table
  entry.
- Add a NAT-aware `DeleteDropSweep::step_with_nat` path for the worker loop.
  It reads the candidate's exact decision and metadata, then calls the existing
  holder-aware source-NAT and NAT64 release helpers with this worker id before
  deleting the entry.
- Keep the existing steering-only wrapper for origin/steering behavioural
  cells that intentionally have no forwarding state. Production uses the
  NAT-aware path.
- The existing #6211 holder-mask release discipline makes the operation
  idempotent: a refused delete whose bit was already cleared is a no-op, while
  the queued-delete race clears the still-present bit. A late queued
  `DeleteSynced` finds no entry, records its key for #6457 flow-cache
  invalidation, and cannot double-free the allocation.

## RED then GREEN evidence

The issue cell enqueues `DeleteSynced` through the real bounded worker queue,
asserts that it remains queued, sweeps the stale table entry, drains the queue
through `apply_worker_commands`, and finally reserves the freed one-port pool
with a distinct flow key.

- RED with the sweep call temporarily routed through the pre-fix
  steering-only `step`: `cargo test --bin xpf-userspace-dp
  delete_drop_sweep_releases_nat_before_a_still_queued_delete_synced_10288
  -- --nocapture` failed at the holder-strand assertion (`0 passed; 1
  failed`; artifact `38924`).
- GREEN with the production `step_with_nat` call restored: the same command
  passed (`1 passed; 0 failed`; artifact `38928`).
- The clean #9560 steering sweep cells remained green in the full session-glue
  module run.
