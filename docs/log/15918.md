# #15918 — fab1 link-local fallback marks fabric ready while helper needs configured peer address

## Defect (retro-review codex finding 1 + opus O-F2)

`refreshFabricFwd`/`refreshFabricFwd1` (pkg/daemon) accept a sole (or
identity-matched) parent IPv6 link-local neighbour when the configured
fabric peer IPv4 address has no address-matched neighbour, program the
retired BPF `fabric_fwd` map, and latch `fabricPopulated`/`fabric1Populated`.
`reconcileRGState` treats either flag as fabric takeover readiness.

The live userspace redirect never consumed that MAC:
`buildFabricPeerMAC` (pkg/dataplane/userspace/fabric.go) only looked up the
configured peer IP on overlay/parent, so with `10.99.14.2` unresolved and
only `fe80::b` present it published `FabricSnapshot.PeerMAC=""`. Rust
(`resolve_fabric_links_from_snapshots` / `populate_fabrics`) then skipped
the fabric as `UnresolvedPeerMac` and installed no `FabricLink`. A
fab0-down/fab1-link-local-only node could therefore pass takeover while
its cross-node redirect could not be built. Additionally
`refreshFabricFwd1` never called `SyncFabricState` on success (fab0 did),
and `Manager.TakeoverReady` never attested an installable fabric.

## Fix

- Single authoritative selector: moved the identity-constrained
  link-local selection into `dpuserspace.SelectFabricPeerLinkLocalMAC`;
  the daemon's `selectFabricPeerLinkLocalMAC` is now a delegate. Rules
  unchanged (#6554): known identity wins, sole distinct MAC accepted,
  ambiguous/lone-decoy refused, self/multicast/unusable excluded,
  deduped by MAC.
- Live resolver: `buildFabricPeerMAC` now falls back, after the
  address-matched overlay→parent lookup, to that selector on the parent
  IPv6 table (skipped when the peer is itself link-local). It takes the
  parent local MAC and the daemon-registered identity constraint.
- Identity plumbing: daemon `rememberFabricPeerMAC` registers the
  address-matched MAC via `RegisterFabricPeerMACConstraint` (keyed by
  peer address); peer replacement in `populateFabricFwd{,1}` clears it.
  `buildFabricSnapshotsFrom` passes both into the resolver, so full
  snapshot builds and `SyncFabricState` agree.
- fab1 sync: `refreshFabricFwd1` now calls `SyncFabricState` on success,
  mirroring fab0.
- Readiness: `Manager.takeoverReadyLocked` (cluster HA, fabrics
  configured) now requires at least one fabric row with non-empty
  `PeerMAC` + parent ifindex, and refuses while `partialFabrics`
  (update_fabrics outcome unknown) is outstanding. Blockers map to
  `fabric_peer_unresolved` / `fabric_not_converged`. Non-cluster and
  no-fabric nodes are unaffected; one installable fabric suffices
  (fab0-down/fab1-up stays ready when fab1 truly resolved).

NOT changed: Rust — it already installs any non-empty `peer_mac` and
retains a prior link on unresolved refresh; the defect was Go never
supplying the MAC, so no wire/`ProtocolVersion` change was needed.
NOT changed: daemon populated-flag semantics — they remain the BPF-map
signal; the helper-installability gate is the additional consumer proof.

## Review fold (#15923, Codex+Opus NEEDS-FIX; GLM READY/minor)

- Canonical registry keys: registration used `peerIP.String()`
  (canonical) while builder lookup/clear used raw config text, so a
  non-canonical IPv6 peer spelling (e.g. expanded `2001:0db8:...:0002`)
  missed the known-peer constraint and a sole decoy link-local
  neighbour could be accepted as the redirect MAC. All three paths
  now go through `fabricPeerKey` (netip.ParseAddr + String; verbatim
  for unparseable text); clears prune the entry so peer replacement
  cannot leave a stale identity. Regression:
  `TestFabricPeerConstraintNonCanonicalIPv6_15918` (register canonical
  ↔ lookup expanded and vice-versa, decoy refused / known resolves
  end-to-end, clear-by-either-spelling prunes). Verified RED when
  `fabricPeerKey` is made identity, GREEN canonicalized.
- Takeover predicate strengthened to the Go-checkable half of Rust
  `build_fabric_link_or_skip` (parseable peer address, valid local +
  peer MACs, positive parent ifindex; Rust's interface-row local-MAC
  fallback only adds installs, so this stays conservative) and the
  gate now applies when the applied config names a fabric even if the
  builder emitted zero rows (missing interface stanza is only a
  config warning). New cases: missing/malformed MACs, unparseable
  peer, configured-with-zero-rows blocked, no-fabric stays ready.
- Re-review fold (#15923r): `fabricPeerKey` now `Unmap()`s before
  `String()`. The daemon registers via `net.IP.String()`, which
  renders IPv4-mapped `::ffff:10.99.14.2` dotted, while netip
  retained the mapped form — that spelling lost the constraint the
  same way. All spellings (expanded, compressed, mapped, dotted)
  now collapse to one key. Regression:
  `TestFabricPeerConstraintMappedIPv6_15918` (mapped↔dotted both
  directions, decoy refused / known resolves, clear prunes).
  Verified RED without `Unmap`, GREEN with it.

## Residuals

- End-to-end lab proof (cold helper, fab0 down, fab1 link-local-only,
  real redirect both directions) still requires the loss-cluster smoke
  gate; unit tests prove the Go→helper snapshot contract, not wire TX.
- A previously resolved Rust link retained across an unresolved refresh
  can keep an older fabric working while Go reports unresolved — the
  takeover gate is conservative in that window (may block a takeover
  that would have worked via the retained link).
