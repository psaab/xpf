# #18599 — size timeout-tick liveness probe windows from live heartbeat timing

Timestamp: 2026-11-07.

## Why

The manager heartbeat fields are desired configuration, while a running receiver may still use the values it snapshotted before a configuration commit. The timeout-tick liveness-probe window was derived from the desired values, so a desired threshold of 2 and a live threshold of 5 produced a 50 ms window instead of the live 350 ms window. That could declare a live peer lost one interval after the probe.

## What

- `livenessProbeAnswerWindowLocked` now derives the window through `liveHeartbeatTimingLocked`, preserving the 50 ms minimum and its desired-value fallback when no receiver is running.
- Added `TestProbeWindowUsesLiveHeartbeatTiming18599` for divergent configured and live timing.
- Added phase-sensitive `TestPrearmedLivenessProbeKeepsFloor18599`; the pre-armed path retains its 50 ms floor when only 250 ms remain before heartbeat timeout.
- Added `TestSendInstallHeartbeatWriteFailureDisconnects18599` to prove an install-heartbeat write failure closes and removes the connection.

Restoring each behavior made its cell pass.

## Risk

The only production behavior change is sizing the timeout-tick probe window from the running receiver. The accessor retains the desired-timing fallback when no receiver exists; the 50 ms floor for pre-armed probes and the timeout-tick window's minimum are unchanged.
