# 10261 — Preserve established flows across rolling daemon cuts

## Diagnosis

The rolling driver used the `in-service-upgrade` system action to call
`cluster.Manager.ForceSecondary`. That path changed every configured redundancy
group to weight zero without invoking the manager's pre-manual-failover hook.
The daemon wires that hook to the userspace session-sync peer barrier, so the
rolling drain could hand ownership to a peer before its queued session deltas
had been processed. This explains the established-flow asymmetry in the issue:
flows whose state arrived continued while flows still queued at the cut stayed
at the TCP congestion floor, without requiring a reset or daemon death.

The existing generic userspace reconciliation prep remains best effort during
startup. The explicit manual/ISSU hook now fails closed when session sync is
absent or disconnected, and the manager retries retryable barrier errors before
committing any RG demotion.

## Changes

- `ForceSecondary` snapshots and reserves all active RGs, runs the pre-failover
  hook for each one before demotion, validates peer liveness and RG incarnation
  after the unlocked barrier wait, and commits all weight-zero state only after
  every barrier succeeds. Concurrent reset, remove/re-add, enable/disable, or
  failover ownership changes abort without a trailing demotion.
- Explicit userspace demotion requires a connected session-sync object; automatic
  readiness preparation retains its existing fail-open startup behavior.
- The `in-service-upgrade` gRPC action deadline scales with the maximum
  representable active-RG count, covering each bounded 60-second barrier,
  admission retry slack, and the observed 10-second handoff wait.
- Session-sync now publishes a separate, non-timeout-released inbound bulk-prime
  bit. The daemon clears it for a cold sync epoch and sets it only after inbound
  bulk completion; cluster information renders `Bulk sync primed: yes|no`.
- Rolling rejoin first waits for peer liveness, sync transport establishment,
  and inbound bulk priming while the local ForceSecondary hold remains active;
  only then does it reset election state and require per-RG eligibility before
  the driver can advance to the peer. This prevents a restarted daemon from
  promoting while its session table is still incomplete.
