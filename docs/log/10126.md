# #10126 — connectivity lock-idleness owner-epoch probe

Worktree `fix/10126-lockprobe`, based on `origin/master`.

- **Timestamp**: 2026-09-18
- **Context**: Read the full open #10126 body and all comments (the issue has no comments). The residual is the F-158 polling hole: a destructive lock cell can acquire and release entirely between the connectivity START and END probes, leaving both endpoint flock checks idle.
- **Mechanism**: `with-cluster.sh` now publishes one unique acquisition token to a persistent epoch sidecar (`/tmp/xpf-cluster-state/epoch`) while its lock is held. The production state directory is non-sticky and mode `0777`; publishers stat first and chmod only when needed, then verify the final mode, so a non-owner cooperating user does not fail on an unnecessary chmod and failed normalization refuses the lock cell with rc 73. Atomic `mv -T` publication refuses a directory sidecar path. Cooperating users can replace a mode-`0666` sidecar; publication also refuses on any setup/write/mode failure. The sidecar is deliberately separate from the lock inode: legacy connectivity probes that open the lock with `>` can truncate the lock file but cannot erase the epoch witness. The first lock open is non-clobbering and read-only, which also avoids `protected_regular=2` failures for an existing cross-user lock inode.
- **Probe**: The remote-cluster connectivity gate records owner identity (PID, acquisition timestamp, user) and epoch at START before its non-blocking read-only flock check. At END it checks edge contention first, then reads identity followed by epoch as the final observation and compares both; any change voids with rc 77. Absent epoch state is a valid pre-first-cell empty snapshot, but a read failure for a present witness now voids at either START or END instead of collapsing to empty==empty. Blocking flock remains out of scope because read-only gates must not hold the shared-cluster lock. Raw one-command flock holders do not publish epochs and remain covered when they overlap an endpoint; this is documented as the residual polling class.
- **Tests**: Extended `cluster-cell-selftest.sh` with a literal pre-#10126 RED probe, repaired GREEN whole-window proof, a legacy `9>` non-erasure proof, END-edge contention, no-lock clean window, selective-cat unreadable-epoch START/END proof, mode-`0666` atomic replacement, pre-`0777` shared-directory no-chmod proof, invalid-parent and directory-sidecar refusals, and deterministic chmod-publication failure refusal proving the destructive body does not run. Private lock, owner, and epoch paths are used throughout. `with-cluster-selftest.sh` also uses a private sidecar.

## Red → green evidence

- **RED on pre-fix probe**: the literal pre-#10126 polling helper returned rc 0 after a fixture completed a full `with-cluster.sh` acquire+release between START and END; the lock was idle at both probes.
- **GREEN after fix**: the same hermetic whole-window cell returned rc 77 with `owner epoch/identity changed`, proving the sidecar token changed even though the lock was idle at END; selective read failure at either endpoint also returned rc 77.
- **Legacy compatibility**: the pre-fix `9>` endpoint probe changed the lock inode but left the sidecar byte-for-byte unchanged.
- **Edge and clean controls**: a holder present at END returned rc 77; a remote no-lock START→END window returned rc 0; bare/local FW0 stayed probe-free.
