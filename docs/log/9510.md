# #9510 — frr: redistribute source outside the enclosing router's address family

- **Timestamp**: 2026-09-10
  - **Action**: Verified the defect and the fix direction against FRR stable/10.6
    source (lib/route_types.txt, lib/route_types.pl, ospfd/ospf_vty.c,
    ospf6d/ospf6_asbr.c, ripd/rip_cli.c, bgpd/bgp_vty.c, isisd/isis_cli.c,
    isisd/isis_redist.c, vtysh/vtysh.c, vtysh/vtysh_config.c, vtysh/vtysh_main.c).
    Two corrections to the issue body:
    - The negative control "`ospf6` under `bgp` still renders" is inverted. A
      bare-token BGP export is written directly under `router bgp` (BGP_NODE),
      and bgp_vty.c installs only the IPv4 redistribute grammar there
      (`FRR_IP_REDIST_STR_BGPD`, the *_ipv4_hidden commands). The IPv6 grammar
      is installed only in BGP_IPV6_NODE. So BGP's use-site family is IPv4.
    - The reload fallback's outcome is a hard failure, not ErrFRRReloadDegraded.
      `vtysh -f` continues past a rejected line (`vtysh_config_from_file` only
      breaks the switch) and returns the remembered error, and main() calls
      exit(ret) without `--noerror`. So VtyshLoad returns an error, and
      reloadLocked returns `vtysh reload: ...`. noteReloadOutcomeLocked marks it
      degraded and arms a retry either way, and every retry fails the same way.
      Additions still reach FRR; removals do not.
