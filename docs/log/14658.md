# Issue #14658 — `fragment_nat64_ipv6_frame` floors MTU to 1280, emitting oversized fragments on sub-1280 underlays

## Why

`fragment_nat64_ipv6_frame` (`userspace-dp/src/afxdp/frame/mod.rs`)
early-returned when `total_len <= mtu`, then floored the caller's MTU
with `let mtu = mtu.max(1280);`. For a DF-clear IPv4 reply translated
to IPv6 whose egress MTU is below 1280 — concretely a NAT64+tunnel
inner MTU: `nat64_v6_egress_mtu` (tx/dispatch) composes
`post_transform_inner_mtu`, which for NAT64-through-WireGuard returns
`wg_inner_mtu(selected-peer outer)` (e.g. outer 1280 over IPv6 =
1280-80-15 = 1185) and for GRE `native_gre_inner_mtu` (transport-24),
each `+20` for the v4->v6 header delta, so sub-1280 budgets are
reachable on ordinary tunnels — a 1240-byte translated packet was
emitted as one 1248-byte "atomic" fragment (larger than the input,
48 B over the 1200 egress MTU), and larger packets fragmented at
1280. Downstream `wg_encap_frame_with_commit`'s exact outer-MTU
guard (and GRE's outer-length guard) then dropped the frame with no
PTB: silent blackhole. The IPv6-minimum-MTU comment confused a link
floor hosts must accept with the configured egress MTU the caller
already computed; sibling #5159 (`tcp_segmentation.rs`) explicitly
forbids this floor for tunnel underlays.

The non-8-octet leg of the source finding is not reproduced: the loop
already rounds `max_data` down to a multiple of 8 and only the final
chunk may be non-multiple-of-8, so no fix was needed there (kept as
regression coverage via exact reassembly assertions).

## What

- `userspace-dp/src/afxdp/frame/mod.rs` —
  `fragment_nat64_ipv6_frame`: removed `mtu.max(1280)`; fragment at
  the actual caller MTU. Added a fail-closed `max_data == 0` guard
  (MTU <= 48 cannot carry base+fragment header plus an 8-byte-aligned
  data chunk) mirroring `fragment_nat64_ipv4_frame`'s
  `max_payload == 0 -> None`, without which removing the floor would
  spin forever on zero-length chunks.
- `userspace-dp/src/afxdp/frame/tests_nat_rewrite.rs` — new tests
  `nat64_v4_reply_fragments_at_sub1280_ipv6_egress_mtu_14658` and
  `nat64_v4_reply_too_small_ipv6_egress_mtu_fails_closed_14658`
  through the real `build_nat64_forwarded_frames` builder.

NOT changed: `nat64_v6_egress_mtu` / `post_transform_inner_mtu` —
their composed tunnel budgets are correct and are the reachability
proof; the floor inside the fragmenter was the sole defect. The
`mtu == 0` (unknown) early return still forwards whole.
