# DHCP REBINDING accepts replies from any server (#14600)

## Why

`v4RenewMatcher`/`v6RenewMatcher` discarded their `rebind` parameter
(`_ bool`) and required the granting server's identity in both RENEWING
and REBINDING. RFC 2131 §4.3.2 defines REBINDING for multi-server sites
and RFC 8415 §18.2.5 sends Rebind to any available server with no Server
Identifier, so in a failover pair the partner's ACK/Reply was rejected,
T2 was defeated, and the client fell through to full re-acquisition with
possible address/PD churn.

## What

- `pkg/dhcp/renew.go`: name the `rebind` parameter in both matchers. In
  rebind mode require only a present, valid server identity (v4 option
  54 convertible to IPv4; v6 server DUID non-nil) while keeping the
  transaction, chaddr (v4) / client-DUID (v6), interface, and message-type
  checks. In renew mode keep the exact granting-server check. Accepted
  replies already store the answering server via `leaseFromACKv4`
  (`Lease.serverID`) and `parseV6ReplyChecked` (`Lease.v6ServerDUID`), so
  the partner becomes the binding for the next RENEW; verified by test.
  A partner NAK in REBINDING is therefore also honored (revocation by any
  server that legitimately took over the binding).
- `pkg/dhcp/dhcpv4.go`, `pkg/dhcp/dhcp.go`: update NAK and
  `RenewalBindingStats` comments to the renew-only binding; sentinel text
  `granting server sent NAK` -> `server sent NAK`.
- `pkg/dhcp/README.md:182-206,491-494`: rewrite the #9944 documented
  choice that contradicted the RFCs and the README's own RFC-correct
  claim.
- Tests: new `pkg/dhcp/renew_rebind_14600_test.go`
  (`TestRebindAcceptsAnyServer14600`) plus updated REBINDING cells and
  rejection-counter expectations in `renew_binding_9944_test.go`.

NOT changed: RENEWING/RENEW granting-server binding, request builders,
destinations, acquisition matchers, or the counters' meaning for renew.

## Validation

- RED on current master: `go test ./pkg/dhcp/ -run
  TestRebindAcceptsAnyServer14600 -count=1 -v` failed with v4 partner
  ACK/NAK rejected, v6 partner Reply rejected, and counter mismatches.
- RED-on-revert: stashing only `renew.go` made both the new test and the
  updated 9944 matcher tests fail on the rebind cells.
- GREEN targeted: `TestRebindAcceptsAnyServer14600`,
  `TestV4RenewMatcherBindsServerAndInterface9944`,
  `TestV6RenewMatcherBindsDUIDAndInterface9944` pass; wrong-xid,
  wrong-client, and missing-server rebind replies are still rejected,
  renew-mode partner replies are still rejected, and the partner's
  server-id/DUID is stored on the parsed lease.
- GREEN affected suite: `go test ./pkg/dhcp/... -count=1` passed,
  `go vet ./pkg/dhcp/` and `git diff --check` passed.

## Risk

REBINDING now trusts any server that passes xid/chaddr/DUID checks on
the interface-bound socket — that is the RFC-defined T2 semantic and is
bounded by those identity checks plus the requirement of a present
server identity. No lab failover-pair capture was run; the predicate and
storage are unit-covered.
