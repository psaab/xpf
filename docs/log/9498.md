## Timestamp: 2026-09-10 09:30 — the smallest commit-accepted config that wraps

The coordinator's ask: establish the smallest config that a commit accepts and
that reaches the wrap. Derived first, then measured.

**Derivation.** With `block-size 1` and the default 1024–65535 range,
`blocksPerIP = 64512`, and `2^32 = 64512 × 66576 + 16384`. So pool index 66576
at block ≥ 16384 makes `uint32(ipIdx)*uint32(bpi) + blockIdx` wrap to subscriber
index 0. Index 0 is below `hostCount` even for a /32 subscriber. Index 66575 at
its largest block reaches 4,294,950,911, which does not wrap.

**Measured.** Every row goes through `configstore.CheckText` (the real strict
commit gate), and the lookup runs on the config that gate returned.

| pool | CheckText | reverse at pool index 66576, port 17408 |
|---|---|---|
| `/16 + /21` (67,584 addrs, 2 statements) | ACCEPTED | **100.64.0.0** (real block 10.0.0.0:1024): misattribution |
| `/16 + /22 + /28 + /32` (66,577 addrs) | ACCEPTED | **100.64.0.0**: misattribution |
| control `/16 + /22 + /28` (66,576 addrs) | ACCEPTED | fail-closed (no index reaches 66576) |

In the same run, index 66575 at its largest block failed closed. Smallest by
address count: **66,577**. Smallest by statement count: **2**. That is about a
third of the issue's 196,608-address witness. Posted on the issue
(issuecomment-5622040246).

## Timestamp: 2026-09-10 — the fix

- **`pkg/nat/deterministic.go` `lookupReverseInPool`**: compute
  `uint64(ipIdx)*uint64(blocksPerIP) + uint64(blockIdx)` and fail closed when it
  is `>= hostCount`. A product past 2^32 is necessarily ≥ `hostCount` (at most
  2^32 − 1), so this fails closed exactly where the Rust
  `reverse_deterministic_v4` `checked_mul` / `checked_add` return `None`.
- **ModeV6 (NAPT64) `hostCount`**: `len(poolV4) × bpi` is computed in 64 bits,
  and past `MaxUint32` Go returns `ErrCodeNotDeterministic`. That mirrors the Rust
  `build_deterministic_v6`, which `checked_mul`s and DOWNGRADES the pool to
  round-robin on overflow. Before this, Go wrapped to a small wrong capacity and
  kept answering as if the pool were deterministic.
- **`pkg/config/compiler_nat_source.go` capacity gate**: counts EXPANDED pool
  hosts, through the existing `sourceNATPoolMemberHostCount` that the #5877
  aggregate gate uses, and now includes the singular `pool.Address`. The
  arithmetic saturates.

### A premise in the issue body, corrected rather than repeated

The body says the statement-counting gate is "*why* the witness config is
admitted at all". That points the wrong way. Counting statements makes the gate
STRICTER (a CIDR counts once), not looser, and the minimal witness passes even at
1 statement × 64,512 ≥ a /32's 1 subscriber. The gate fix is therefore a SEPARATE
over-refusal: a pool whose CIDR statements really have the capacity was
rejected. It is included because the issue's fix direction names it. The wrap is
fixed by the arithmetic, not by the gate.
