# #18174 — correct the IPv6 RETH first-hop expectation in connectivity MTR

## Triage

The watch log initially ended with lock-contended entries at `80bf938afd`
(1793190935, 1793191835), but has since appended two non-VOID summaries:
`1793192879` at `85ee385d1e` and `1793193907` at `668ab4cdc4`. Both report
fw1-to-fw0 fabric, LAN-to-internet IPv6, and all three MTR cells failing; the
MTR summaries still expect the routed VIP as hop 1. These latest recorded
masters confirm that the VIP expectation mismatch persisted before PR #18343
and #18360 merge. The summaries do not report Group10 TTL=1 or Group11 MTR
status, so neither is classified from their omission. The `80bf938afd` entries
remain VOID because another lane held the shared-cluster lock.

Earlier sample `001c5507c5` (1793183223) reports Group10 TTL=1 without
Time-Exceeded output. In the same connectivity window Group12 controlled pings
pass, `fw0 -> internet (1.1.1.1)` fails, and the end probe reports lock
contention (1793183223-1793184261). This coupled failure does not justify
weakening the existing TTL contract to accept an empty reply. Prior #18174
triage records TTL=1 passing at `142af8fe258b` with Time-Exceeded evidence from
`169.254.2.1` / a fe80 link-local source; TTL status on the newest masters is
unconfirmed.

PR #18343 corrects the IPv4 RETH MTR checks to use the observed IPv4
link-local first hop and require the requested destination as the final
0%-loss hop. It is still open and this branch is stacked on its head. The
remaining IPv6 VIP mismatch is a separate instance of the same harness
expectation defect, but the public IPv6 target itself does not respond in the
captured report. No source-side evidence establishes that the upstream target
is dead rather than that the IPv6 path is broken, so this change does not
relabel or mask that independent reachability failure.

## What

- Added `check_mtr_linklocal6` mirroring the IPv4 first-hop-and-final-target
  contract: the first hop must be an IPv6 link-local source (`fe80::/10`), and
  the requested destination must be a later final hop with `0.0%` loss.
- Changed only the cluster public IPv6 MTR call to use that validator. The
  old IPv6 VIP check incorrectly treated the routed gateway address as the
  hop-limit-expired source.
- Extended `connectivity-mtr-selftest.sh` to extract both production
  validators and test captured and synthetic IPv6 cases.
- TTL=1 checks, forwarding code, IPv4 MTR, fabric/WAN gateway checks, and the
  IPv6 ping/iperf cells are unchanged. TTL=1 has prior passing evidence.
  The newest non-VOID summaries omit TTL=1, so current TTL state remains
  unconfirmed. Fabric/WAN-gateway and
  Group11 IPv4 MTR follow the open #18212 host-ICMP / VLAN50 gateway
  investigation. Internet IPv6 reachability remains an independent open
  failure; without WAN-side egress/return evidence it is not classified as an
  external target failure.

## Root causes

1. `poll_descriptor/embedded_icmp.rs` `related_admit`: the untranslated arm
   used the #10684 path-error set (v4 3/11/12, v6 1-4) but the NAT'd arm used
   `outer_is_pmtud_error` (v4 3/4, v6 2/0 only, #10666). Every NAT'd Time
   Exceeded / Destination Unreachable therefore went to
   `enforce_queued_embedded_icmp_policy`, which evaluates the reverse
   `wan -> lan` pair -> default deny. The #9948 cell
   `poll_descriptor_embedded_icmp_reversal_zone_policy_denies_9948` pinned
   exactly this (a right-zone NAT'd TE asserted denied).
2. `forwarding_build/interfaces.rs` shared-ifindex egress merge:
   `existing.primary_v4.or(Some(p))` (first-row-wins). The RETH base row's
   per-row pick is its link-local FALLBACK (169.254.2.1), which shadowed the
   unit row's 10.0.61.1; `build_local_icmp_error_v4` sources the TE from
   `egress.primary_v4`. v6 was right only because the base row happened to
   carry no v6 address in this snapshot (the #18168 diag captured a fe80 hop
   1 when it did).

3. (found by the split-RG end-to-end cell, not live) `icmp_embed/nat_match_v4.rs`
   / `nat_match_v6.rs` forward-NAT arm at the FABRIC peer: the WAN-RG node's
   embedded arm FabricRedirects an ALREADY-REVERSED frame (outer dst =
   client, quote pre-NAT). At the LAN-RG owner the quote matches the forward
   session through its canonical reply alias, and the #14665 gate expected
   the outer destination to be `rewrite_src` (the SNAT address) -> NoMatch ->
   flowless -> HAInactive (resolution toward the inactive WAN RG). Every
   split-RG SNAT error (traceroute and PMTUD) was lost at the peer. Debug
   probe: direct `try_embedded_icmp_nat_match_from_frame` on the peer state
   with `FABRIC_INGRESS_FLAG` returned `NoMatch`.

## Fix

- `embedded_icmp.rs`: one type set (`outer_is_related_path_error`) for
  untranslated matches and for NAT'd FORWARD quotes, same direction-derived
  zone check. A NAT'd REPLY quote (new `EmbeddedIcmpMatch::quoted_is_reply`,
  set by both matchers) keeps PMTUD-only so the outbound-SNAT policy cells
  (#13649, and #13772's re-NAT'd fabric hand-off where `outbound_snat` is
  false at the peer) are unchanged. A first cut keyed the exception on
  `outbound_snat` and #13772 went RED at the peer — that is why the
  direction, not the NAT shape, is the key. NAT64 unchanged (PMTUD only).
- `nat_match_v4.rs` / `nat_match_v6.rs`: at FABRIC ingress, a forward-NAT
  quote whose source equals the forward key's pre-NAT source expects that
  source as the outer destination.
- `interfaces.rs`: `merge_undesignated_primary` — a non-link-local pick
  replaces a link-local incumbent; otherwise first row wins; designated
  primaries unchanged.
- `test-connectivity.sh`: `check_mtr_reth_vip` replaces the
  `check_mtr_linklocal4/6` validators that #18343/#18360 had fitted to the
  defect: hop 1 must be the RETH LAN VIP, hop 2 must be resolved when the
  target is further, target final at 0%. v6 MTR target moved to
  `2001:4860:4860::8888`.
