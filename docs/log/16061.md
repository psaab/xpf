# #16061 — ifindex_to_config_name last-write mis-scopes from-interface NAT (SI-4-name)

## Why

`populate_interfaces` inserted every snapshot row's name into the single
`ifindex_to_config_name[ifindex]` slot. Distinct logical units can collapse
onto one netdev ifindex — an interface-level tunnel maps every unit onto the
tunnel device (`TunnelNameMap`), and unit 0 collapses onto its base — so the
last row walked named the device. `nat_scope_ctx_for_flow` and
`prerouting_ingress_scope` read that one name for `from interface` /
`to interface` NAT matching, so a rule scoped to one sibling unit matched
traffic the dataplane can only attribute to the shared ifindex, and which
sibling won depended on snapshot row order.

## What

- `userspace-dp/src/afxdp/forwarding_build/interfaces.rs`: track the config
  name claimed by logical-unit rows per ifindex. The ifindex keeps a name
  only while its unit rows agree on one; distinct unit names contest it and
  the entry is withdrawn (absent reads as `""`, so interface-scoped NAT
  fails closed — no match — in both row orders). Base rows are device
  aliases, not traffic identities, and never contest, so the ordinary
  base + unit-0 pair keeps the unit's name byte-identically, duplicate rows
  naming the same unit agree, and a lone base row keeps its own name.
- The #10313 parent fallback (`entry(parent).or_insert(base)`) is skipped
  when the parent slot is itself config-name contested, so a collapsed unit
  cannot resurrect even its base name (`wg0`) onto the contested ifindex.
- One operator warning per contested ifindex per build naming every unit
  that claimed it, mirroring the #7509 zone-contest observability rule.
- Regressions: `config_name_16061_tests` (contested name withdrawn in both
  orders, NAT scope reads `""`, agreeing/alias controls) and
  `snat_from_interface_never_matches_a_sibling_on_a_shared_ifindex_16061`
## Validation

- RED (pre-fix, by construction): the unconditional insert named the
  last-walked sibling; the new contested-name assertions fail on that code,
  and the SNAT end-to-end cell initially caught the #10313 parent fallback
  resurrecting `wg0` on the contested ifindex, which the parent guard now
  closes.
- GREEN: `cargo test --bin xpf-userspace-dp 16061` — 4 passed.
- GREEN: `cargo test --bin xpf-userspace-dp forwarding_build::` — 317
  passed, 1 ignored.
- Full `cargo test --bin xpf-userspace-dp`: 9012 passed, 63 failed,
  10 ignored. The 63 failures are pre-existing on pristine
  `origin/master` (9011 passed equivalent): a captured pristine failure
  list contains every one of the 63 (plus one flaky
  `screen::tests::syn_flood_dest_threshold_trips_under_aggregate` that
  passed in the changed run), so this change introduces no new failure.

## Risk

Limited to forwarding-state construction (`populate_interfaces`); no
packet-path or hot-path change (the NAT match itself is untouched — it
already treats `""` as no-match for an interface-scoped rule). Deployments
whose units share an ifindex AND rely on per-unit `from/to interface` NAT
scoping will see those rules stop matching (fail-closed, with the new
warning line naming the units); zone- or routing-instance-scoped rules on
the same traffic are unaffected. Perf impact: none on the packet path; one
extra BTreeMap probe per interface row at snapshot build.
