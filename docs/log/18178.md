# #18178 — Serialize/isolate concurrent `make deb`; repair trailerless changelog

- **Timestamp**: 2026-10-27
- **Why**: Sibling worktrees share one parent dir. `dpkg-buildpackage`
  wrote `../xpf_<ver>_*.deb`, `../xpf-appliance_<ver>_*.deb`,
  `../xpf_<ver>_*.changes`, and `../xpf_<ver>_*.buildinfo` there, and the
  `deb` recipe's EXIT trap deleted `../xpf_$(DEB_VERSION)_*`. Two lanes at
  the same commit count (or same HEAD) therefore shared one filename
  namespace: one lane's cleanup deleted the other's just-built `.deb`
  before its `dpkg-genbuildinfo` could `fstat` it
  (`cannot fstat file ../xpf-appliance_..._amd64.deb`). Separately,
  `debian/changelog` had 83 `xpf (0.0.0)` entries but only 2 trailers;
  `dpkg-parsechangelog --all` emitted 161 warnings and parsed exactly one
  entry.

## What

- **Private per-invocation stage (preferred isolation, no lock).**
  `Makefile` `deb` now creates
  `$(CURDIR)/.deb-stage-<version>-<pid>` (guarded to stay under
  `$(CURDIR)/.deb-stage-*`, git-ignored) and routes every artifact there:
  `XPF_DEB_STAGE=<stage>` for `debian/rules`
  (`dh_builddeb --destdir=$(XPF_DEB_STAGE)`, default `..` preserved for
  direct `debian/rules` use), plus
  `--buildinfo-file=<stage>/xpf_<ver>_amd64.buildinfo`,
  `--changes-file=<stage>/xpf_<ver>_amd64.changes`, and
  `--buildinfo-option=-u<stage>` / `--changes-option=-u<stage>` so
  `dpkg-genbuildinfo`/`dpkg-genchanges` resolve the `.deb` files in the
  stage, not the parent. The `cp` into `dist-deb/` reads only from the
  stage, so the `dist-deb/xpf_<ver>_amd64.deb` +
  `xpf-appliance_<ver>_amd64.deb` contract is byte-identical. The cleanup
  trap now restores the changelog version and `rm -rf`s **only** the
  stage this invocation created (prefix-guarded); it never touches
  `../xpf_*`. A private-stage micro-package proof (real
  `dpkg-buildpackage` with the same flags) emitted both debs,
  `.buildinfo`, and `.changes` into the private dir and nothing into the
  parent. The hermetic fake in
  `scripts/image/test_bake_dirty_detection_12158.py` now honours
  `XPF_DEB_STAGE` the same way.
- **Changelog collapse (smaller safe change).** The file is a
  version-token carrier — only line 1's `(0.0.0)` is consumed — so
  instead of fabricating 81 per-entry trailers/dates, history is
  collapsed to the single maintained first entry (lines 1–65, trailer
  `Mon, 26 Oct 2026`). Line 1
  `xpf (0.0.0) unstable; urgency=medium` is byte-identical to
  `origin/master` (verified with `cmp`). Removed: 4054 lines /
  82 trailerless entries that dpkg tooling folded invisibly into the
  first entry anyway.
- **Guard.** `scripts/check-changelog-18178.sh` fails on any
  `dpkg-parsechangelog --all` non-zero exit, any stderr warning, or zero
  parsed entries. Wired as `make deb-changelog-check`, a prerequisite of
  `make deb`, and via `make deb-changelog-check` for CI/operators (the
  workflow-file edit was not included: the pushing token lacks the
  `workflow` scope, so `.github/workflows/test.yml` is unchanged here). Verified: passes the repaired file
  (1 entry, zero warnings) and rejects a trailerless two-entry fixture.

## Validation

- `dpkg-parsechangelog -l debian/changelog --all`: exit 0, zero
  warnings, 1 `Version:` (was: 161 warning lines, 1 parsed entry of 83).
- `sh scripts/check-changelog-18178.sh debian/changelog`: PASS;
  trailerless fixture: FAIL with the expected warnings.
- `make deb-changelog-check`: PASS. `make -n deb` shows the private
  stage, `XPF_DEB_STAGE`, and all four dpkg output flags.
- `python3 -m unittest scripts.image.test_bake_dirty_detection_12158`:
  11 tests OK — the real `make deb` recipe (with a fake
  `dpkg-buildpackage` honouring `XPF_DEB_STAGE`) still lands both debs
  in `dist-deb/` and the changelog fixture copies the new guard script.
- Single-flight real `make deb` (in this worktree, clear window checked
  with `pgrep -af 'make deb'` first): both debs landed in `dist-deb/`
  (`xpf` + `xpf-appliance`, `0.0.24765+gc79486406ec1`, amd64), the stage
  was removed, the shared parent stayed clean, and changelog line 1 was
  restored to `xpf (0.0.0)`.
- Concurrent-pair proof: two worktrees at the same HEAD
  (`c79486406e`, same version `0.0.24765+gc79486406ec1`) under the same
  parent `/var/worktrees/campaign-pub/`, launched 5 s apart, overlapped
  (two distinct `.deb-stage-…-2384130` / `-2385528` dirs coexisted; one
  lane briefly waited on cargo's own build-dir lock, which is unrelated
  to dpkg output). Both succeeded, each with both debs in its own
  `dist-deb/` at the correct Package/Version; zero `cannot fstat` in
  either log; no `*.deb`/`*.changes`/`*.buildinfo` ever appeared in the
  shared parent; both stages were removed; neither lane deleted the
  other's artifacts.

## Risk

- Direct `dpkg-buildpackage` / `debian/rules` invocation without
  `XPF_DEB_STAGE` keeps the historical parent-dir (`.`) behaviour
  (`XPF_DEB_STAGE ?= ..`), so foreign builds are unchanged; only the
  `make deb` path is isolated. The `.deb` bytes are produced by the same
  `dh_builddeb` invocation, only `--destdir` differs, so package content
  is unchanged. No lock is taken, so concurrent builds are not
  serialized — each owns its stage; the only shared writes left are the
  pre-existing per-worktree build tree (`debian/xpf/`, binaries), which
  sibling worktrees already isolate.
