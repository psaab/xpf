## Why

`can_admit_after_closing_tcp_pair_for_syn` (session/lookup.rs) computed
`len - reclaimed + needed <= max_sessions`, ignoring
`reserved_session_slots`, while `can_admit` and the raw install check
(`len + reserved >= max`) both charge outstanding IPsec install-plan
reservations (2 slots per `reserve_ipsec_install`). Witness: max=10,
len=8, reserved=2, one local closing TCP half, needed=2 — the reuse
preflight admitted (8-1+2=9), the packet path evicted the closing pair,
and the replacement forward/reverse install then failed against slots
already promised to the IPsec plan (9+2=11 needed in truth), dropping an
admitted SYN and needlessly destroying the closing incarnation.

## What

Add `reserved_session_slots` to the closing-pair preflight so it matches
`can_admit` semantics exactly: `len - reclaimed + reserved + needed <=
max_sessions`. One-line arithmetic fix in
`userspace-dp/src/session/lookup.rs`; all four call sites in
`poll_descriptor/mod.rs` inherit it (they still fall through to
`can_admit_new_syn` pressure-shedding on refusal, unchanged). No other
code path changes; the `pair`-absent fallback already delegates to
`can_admit`.

Regression: `session/closing_pair_reserved_slots_14126_tests.rs` builds a
one-sided closing TCP entry (pair installed, FIN-closed, reverse half
deleted), reserves two IPsec slots via the real
`reserve_ipsec_install`, fills to len=8 at max=10, and asserts the reuse
preflight refuses `needed=2`, does not evict the closing row, and admits
again after `cancel_ipsec_install` (positive control proving the refusal
is reservation-caused, not tuple-caused).

## Risk

Strictly more conservative admission for closing-pair SYN reuse when an
IPsec reservation is outstanding: the SYN takes the existing
pressure-shed/refusal path instead of evicting-then-failing. No behavior
change when `reserved_session_slots == 0`.
