# #18624 — key punt-seed first use on the shard reservation

## Root cause

`HashMap::capacity()` is not a first-use marker: deletions can leave tombstones
that exhaust insertion capacity while the table is still allocated. A drained
shard can therefore have `rows.len() == 0` and `rows.capacity() == 0` after its
first reservation. Using that capacity value as the reservation guard makes the
next publish reserve the table again, growing it beyond its one-time bound.
`Shard::row_cap` already records whether the shard has been initialized.

## Fix

- `reserve_on_first_publish` now checks `shard.row_cap == 0` before reserving
  `rows`; the existing `row_cap` calculation and live-row limit are unchanged.
- Added `tombstoned_empty_shard_does_not_rereserve_18624` to the existing
  `punt_seed_directory_18562_tests.rs` module. Its `cfg(test)`-only seam fills a
  same-bucket collision cluster to the map's growth threshold, removes every
  row, and asserts the empty/exhausted-capacity premise (`len == 0`,
  `capacity() == 0`). The next publish must stay within the table's original
  reservation. No production seam was added.
- Updated the existing `session/mod.rs` test-module comment; the test remains
  wired through its existing module path.
