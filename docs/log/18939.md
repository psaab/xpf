# #18939: rate-limited SessionSync fabric dial-failure log

- **Timestamp**: 2026-11-03
- **Action**: `fabricConnectLoop` (pkg/cluster/sync_conn.go) silently discarded
  dial errors (bare `continue` at the old :1497-1499), so a peer that could
  never be dialed retried invisibly every second — exactly what hid the
  #18038 testguard lo-down rot behind a "never connected" deadline in #18933.
  The dial-failure path now emits a rate-limited `slog.Warn`
  (`cluster sync: dial to peer failed`, attrs `addr`, `fabric`, `err`,
  `suppressed_since_last`) with NO control-flow change: same 1s retry
  cadence, same error-swallow semantics.
  - **Idiom reused**: `heartbeatRejectWarnLimiter`
    (pkg/cluster/heartbeat_reject_warn.go) — injectable monotonic clock seam
    (`fabricDialWarnNowNanos = MonotonicNanos`), 30s interval matching
    `heartbeatRejectWarnInterval`, `admit()` returning `(emit, suppressed)`
    so the bound never conceals the volume. One deliberate divergence,
    documented on the type: no mutex, because the limiter is loop-local state
    owned by exactly ONE `fabricConnectLoop` goroutine (one per fabric,
    started once per session incarnation), and a fresh incarnation's first
    dial failure is news again by design. Extension over the heartbeat
    shape: a CHANGED error string emits at once (an error that changes every
    second describes a genuinely changing network; volume stays bounded by
    the one-attempt-per-second loop).
  - **File(s)**: `pkg/cluster/sync_conn_dial_warn_18939.go` (limiter),
    `pkg/cluster/sync_conn.go` (wiring: `var dialWarn fabricDialWarnLimiter`
    before the loop; `admit`-gated `slog.Warn` inside the dial-error arm),
    `pkg/cluster/sync_conn_dial_warn_18939_test.go` (cells),
    `docs/log/18939.md`.
- **Validation**: all via `./scripts/testguard-run.sh` (GOCACHE=
  /var/worktrees/.cache/go-build, GOTMPDIR=/wtgt; never overridden).
  - RED (limiter + tests present, wiring absent — bare `continue` at base):
    `go test ./pkg/cluster/ -run 'TestFabricDial' -count=1 -v` →
    `TestFabricDialFailureWarnIsRateLimitedOnTheRealPath_18939` FAIL in
    12.00s with "timed out waiting for 1 dial-failure warnings; got 0" —
    the exact #18939 silence, reproduced under the lo-down testguard netns.
  - GREEN (wiring applied): same command → both cells PASS (binder 4.01s).
    The binder drives the REAL `fabricConnectLoop` dial path (the #6669
    doctrine: a limiter that works but is not wired changes nothing about
    log volume): (a) first failure logs with addr/fabric/err and
    `suppressed_since_last=0`; (b) ≥3 further real retries inside one pinned
    30s window keep the count at exactly 1; (c) stepping the clock seam past
    the interval emits again with a positive suppressed count. The closed
    loopback port makes the test lo-state agnostic (ECONNREFUSED when lo
    routes, ENETUNREACH when it does not — both dial failures; the error's
    presence is asserted, never its text). No netlink mutation: no census
    registration needed.
  - `TestFabricDialWarnLimiterEmitsOnChangeAndInterval_18939` pins
    change/interval semantics directly (first emit 0-suppressed → two
    suppressed repeats → changed error emits at once reporting both →
    interval step re-emits reporting the in-window repeat), because a fixed
    peer address cannot produce an error change on the real path.
  - `-count=3` on the new cells: all PASS ×3 (6/6). Neighbour
    `TestSyncHandshakeTimeoutIsShort` (source-scan constant pin):
    PASS ×3.
  - Pre-existing, NOT this change (reproduced at base 5e65228f29 under the
    same runner, the #18038 lo-down class the #18933/#18935 docs predicted
    would redden other real-loopback fixtures): `TestAcceptLoopHandshakeDoesNotBlockOthers`,
    `TestSendWriteTimeoutTeardownReachesStalledPeer18521`,
    `TestPeerResetWhileReceiveLoopStalledTearsDown18521`,
    `TestStaleDisconnectClosesItsOwnSocket18521`,
    `TestReceiveLoopExitNamesItsReason18521` each fail instantly at their
    own fixture dial (`dial tcp 127.0.0.1:NNN: connect: network is
    unreachable`), and `TestConnectDialerIsTheNoiseInitiator7163` hangs in
    `ln.Accept()` — no route to loopback, so the dial can never complete,
    at base and at this head alike. Each needs its own #18935-style
    lo-restore cell + census registration; out of scope for #18939 (this
    change adds no netlink and touched no dial timing).
  - Live demonstration (side effect of the 7163 base-hang reproduction at
    this head): that hung session's log held exactly two warns 30s apart —
    `suppressed_since_last=0` then `suppressed_since_last=29` — the loop's
    once-per-second retries made visible, which is verbatim the #18939
    symptom ("retries every 1s invisibly") now self-evident in one line.
- **Risk**: Log-only observability change; no dial timing, retry, or teardown
  behaviour touched. Worst-case volume is one line per dial attempt when the
  error TEXT genuinely changes every attempt (bounded by the loop's 1s
  cadence); an unchanged outage is bounded to one line per 30s. The warn
  fires from the per-fabric dial goroutine only, via the shared slog
  default. Residual: `peerAddr` hostname-resolution failures inside
  `DialContext` surface through this same line (resolution errors are dial
  errors); the accept-side handshake-failure log (sync_admission.go) is
  untouched and already unconditional by design.
