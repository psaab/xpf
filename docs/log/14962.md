# #14962 — NAT64 pool-unusable reason propagation + NAT64 interface-SNAT overlap quarantine (D27-01)

## Defect

Two fail-open legs around NAT64 source pools, both anchored at
`pkg/dataplane/userspace/nat64.go:66-118`,
`pkg/dataplane/userspace/nat_iface_pool_overlap.go:296-365`, and
`userspace-dp/src/nat64.rs:908-925` on base `27b8cba22d` (re-anchored on
current master; the mechanism is unchanged):

1. **`buildNAT64Snapshots` omits `SourceNATPoolUnusableReason`.** The SNAT
   builder has stamped `PoolUnusable`/`PoolUnusableReason` from
   `config.SourceNATPoolUnusableReason` since #6812 (missing / empty /
   invalid member / zone-scoped / bad port range). The NAT64 builder never
   consulted it: it copied the referenced pool's raw members onto the wire
   unmarked. In Rust, an unparseable member made
   `Nat64State::from_snapshots_with_previous` SKIP the whole rule
   (`continue 'rules`, #3888 all-or-nothing) — so a destination inside the
   NAT64 prefix matched no prefix, classified `NoPrefixMatch`, and was
   ROUTED as ordinary IPv6 (the synthetic `64:ff9b::a.b.c.d` destination
   leaked upstream untranslated). A parseable-but-unusable pool (bad port
   range, etc.) minted normally from a pool the control plane had already
   declared unusable.
2. **`reportInterfaceSNATPoolOverlaps` never quarantines `snap.NAT64`.**
   The detector has iterated `snap.NAT64` since #14367 and logs NAT64
   findings, but the quarantine loop only stamped `snap.SourceNAT`. A
   NAT64 pool colliding with an interface-SNAT egress address was warned
   about and then translated anyway, so the NAT64 allocator and the
   interface allocator could mint the same `(address, port)` — the exact
   collision #7717 quarantines pool SNAT for. The stale #14367 test even
   asserted this ("no PoolUnusable transport on NAT64 snapshot").

## Fix

- `NAT64RuleSnapshot` (Go `protocol_nat.go` + Rust `protocol/nat.rs`)
  gains `pool_unusable` / `pool_unusable_reason`, the same wire vocabulary
  as the SNAT snapshot. Protocol version bumped 50 -> 51 on both sides
  (`ProtocolVersion` / `CONFIG_SNAPSHOT_PROTOCOL_VERSION`): a v50 helper
  ignoring the fields would mint from an unusable pool, which is the
  defect, so exact-equality versioning fences the pairing rather than
  degrading silently (the #9874 LenientMatchDropped precedent).
  `protocol_wire_v1.json` regenerated.
- `buildNAT64Snapshots`: a configured `SourcePool` that is missing stamps
  `missing_pool`; otherwise the pool verdict comes from the shared SSOT
  `config.SourceNATPoolUnusableReason`. Members are now resolved via
  `config.SourceNATPoolMembers` (same "what is in this pool" answer as
  SNAT). Deterministic mode-2 fields are only derived for a usable pool
  (a pool Rust will never mint from has no deterministic mapping). A rule
  with NO source-pool configured stays the legitimate unmarked empty-pool
  state, byte-identical to before.
- `reportInterfaceSNATPoolOverlaps`: NAT64 findings now stamp
  `snap.NAT64[i].PoolUnusable` + `poolUnusableReasonIfaceOverlap`,
  preserving an existing definition reason exactly like the SNAT arm.
- Rust `Nat64State::from_snapshots_with_previous`: `snap.pool_unusable`
  installs the prefix with an EMPTY pool (the #6982 over-budget posture)
  — logged once with its reason, no allocator bitmap materialised, no
  deterministic mapping, and `nat64_rule_identity` returns `None` so
  phase 1 neither reuses nor charges it. Prefix traffic therefore
  classifies `MatchUnavailable` (drop + counter) instead of
  `NoPrefixMatch` (route as IPv6). The reason is carried onto
  `Nat64Prefix.pool_unusable_reason` so the three empty-pool states
  (no-pool-by-config, unusable-by-verdict, refused-by-budget) stay
  distinguishable at consumption, mirroring `over_budget`.
  NOT changed: NAT64 has no allocator drain — pre-quarantine NAT64
  sessions re-derive through the peer-overlap machinery as before; this
  change only stops NEW mints, which is fail-closed and strands nothing
  that was not already collision-exposed.

## Risk

- Wire change rides the v51 bump; mixed binaries refuse snapshots
  (previous-good image keeps forwarding) rather than silently ignoring
  the marker. Rolling upgrade therefore needs daemon+helper together,
  as with every version bump in this codebase.
- A NAT64 ruleset whose pool is newly marked unusable will DROP its
  prefix traffic instead of translating/routing it. That is the intended
  fail-closed delta; on a strict commit such pools were already rejected,
  so this only changes tolerated (lenient-load / peer-sync) configs.
