# #14711 — Reserve the API-key budget for dual-header authentication

## Defect and change

REST requests containing both `Authorization` and `X-API-Key` previously
reserved only the Authorization-derived identity. The credential checker could
then evaluate the fallback key without consulting or charging its per-source
API-key bucket. A valid key behind a bad Authorization header bypassed an active
API-key lockout; rotating Basic usernames gave failed keys the larger source
budget instead of the five-failure key-pair budget.

Both static and dynamic middleware use the shared throttled check. It now
atomically reserves the API-key pair alongside the claimed identity, global
Basic identity where applicable, and source. Capacity accounting and eviction
protection include the additional bucket, as do active-lockout and in-flight
admission checks. Completion releases all reservations exactly once, charges
both failed pairs but the source only once, and clears only verified identities.
An unevaluated fallback preserves its existing failures.

Credential precedence and successful fallback with unlocked budgets are
unchanged. A dual-header request is refused before either verifier if either
pair is locked or occupied, even when the other credential could succeed.
Bearer-only identity namespaces and per-key verifier implementations are not
changed. Double verification on an admitted dual-header failure remains allowed,
but it can no longer escape the fallback key's admission/failure budget.
