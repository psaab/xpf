# #14678 — DrainReinjectCompletions destroys in-flight completions on idle timeout; per-flow FIFO unbounded (D8-02)

## Defect
Three arms, one root: the completion stream had no ownership protocol.

1. **Close-on-idle (Go).** `SocketReinjectSubmitter.DrainReinjectCompletions`
   (`pkg/nfqueue/reinject_socket.go`) set a 5ms read deadline and, on *any*
   `isTimeout` — including a zero-byte idle expiry — closed `s.complete`
   and returned `(nil, nil)`. Verified on base: two consecutive idle
   drains both left `s.complete == nil`.
2. **Commit-on-buffer-write (Rust).** `serve_complete_conn_with_target`
   (`userspace-dp/src/server/reinject_9506.rs`) ran
   `peek_ready → write_all → ack_ready`; `ack_ready` is the destructive
   purge. A completion written into the socket buffer after Go's
   deadline expired but before Go's `Close()` executed was therefore
   acked/purged in Rust and destroyed unread in Go. The Go
   `pendingReinject` then expired in `Poll` (`pipeline.go`) as
   `uncertain("ack timeout")` → fail-closed quarantine/drop of a frame
   Rust had actually written.
3. **Mid-frame timeout misreported.** A timeout after partially
   consuming a frame took the same silent `nil, nil` path, so `Poll`
   never called `failPending("completion drain error")`.
4. **Unbounded per-flow FIFO.** `enqueueFlowLocked` appended
   unconditionally and always returned `nil`, despite `consumeFrames`
   expecting drop-returns. Behind a pending head, `p.flows[key].frames`
   grew without bound (only the 16384 handoff and try-or-drop `Enqueue`
   were capped).

## Fix
Go (`pkg/nfqueue/reinject_socket.go`):
- The completion reader is now buffered (`completeBuf` on the
  submitter). A drain first tries to complete a frame from the buffer,
  then reads with the 5ms deadline into the buffer. A **zero-byte**
  timeout returns `(nil, nil)` and **keeps the connection**; a timeout
  with a partial frame buffered closes the stream and returns an
  **error**, so `Poll` fails pending work closed. `readReinjectMessage`
  is still used on the submit stream (unchanged).
- After a full frame is buffered locally, Go writes a one-byte
  application acknowledgement (`reinjectCompleteAck = 0xAC`).

Rust (`userspace-dp/src/server/reinject_9506.rs`):
- `serve_complete_conn_with_target` now sets a 100ms read timeout and,
  after `write_all`, waits for the `REINJECT_COMPLETE_ACK` (0xAC) byte
  before calling `ack_ready`. On ack timeout/EOF/wrong byte it
  `release_ready`s the batch (redelivered whole on the next
  connection) and breaks. The pre-existing MSG_PEEK probe is kept but
  now only tolerates a queued ack byte; a stale ack with nothing
  reserved is consumed and ignored.

Per-flow cap (`pkg/nfqueue/pipeline.go`):
- New `CapturePipelineConfig.MaxFlowFrames` (zero → `defaultMaxFlowFrames`
  = 512, negative rejected). `CapturePipeline.maxFlowFrames` bounds
  `flow.frames` including the head; `enqueueFlowLocked` returns the
  excess frame for the existing terminal-DROP path in `consumeFrames`
  and counts `PipelineStats.FlowQueueDrops`. The cap also applies to
  directly-constructed pipelines (test literals) via the in-function
  default. 512 ≫ BatchCap 64 adjudicated per ack window, so legitimate
  bursts are unaffected while worst-case retention is 512 frames/flow.

NOT changed: the submit-stream protocol, `decodeCompletions`, the
`pendingCompletions` overflow buffer (#13234), `Poll`'s fail-closed
semantics, Rust `peek_ready`/`ack_ready`/`release_ready` core logic.

## Tests
New `pkg/nfqueue/reinject_flowcap_14678_test.go`:
- `TestDrainReinjectCompletionsPreservesConnOnZeroByteTimeout` (named
  in the issue): two idle drains keep the connection; a completion
  written afterwards is delivered on it.
- `TestDrainReinjectCompletionsPartialFrameTimeoutIsError`: partial
  header + stall → drain error + stream closed.
- `TestDrainReinjectCompletionsPartialRecovery14678`: next drain
  re-dials and delivers.
- `TestEnqueueFlowLockedCapsPerFlowFrames14678`: fills the FIFO to the
  512 cap behind a pending head; the excess frame is returned for DROP
  and `FlowQueueDrops == 1`.

Updated (asserted the old defective contract):
- `TestReinjectSocketCompletionTimeoutResetsPartialFrame9506`: partial
  timeout is now a drain error (stream still closed).
- Rust `complete_conn_streams_completions` and
  `complete_conn_delivers_after_idle_13715` now send the ack byte.
- New Rust `complete_conn_releases_unacked_batch_on_disconnect_14678`:
  an unacked batch survives reader disconnect (`ready_len == 1`), is
  redelivered to a second reader, and is purged only after its ack.

## Remaining validation
- No lab validation: the race is socket-local and exercised by the
  Go socketpair-style cells plus the Rust loopback cells above. A loss
  cluster run would confirm end-to-end but is not required; the wire
  change is confined to the Go↔Rust completion stream, both sides of
  which ship together.
- Mixed-version skew note: an old Go reader never acks, so a new Rust
  helper releases and redelivers each batch on reconnect (never
  purges) — fail-safe, not fail-open. A new Go reader against an old
  Rust helper sends one ack byte per frame; the old helper's probe
  treats client bytes as a protocol violation and drops the
  connection, after which completions redeliver on the next accept —
  degraded but lossless. Both sides deploy together in practice.
