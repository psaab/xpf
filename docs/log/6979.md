## The finding's own attribution is wrong, and measuring is what showed it

F6 says a MATCH-ONLY rule edit "strands a reservation in an allocator that can
no longer match the flow, while the rule that now owns it is free to reissue the
tuple". Three probes at master, single-address pools and a one-port range:

| probe | construction | master |
|---|---|---|
| P1 | pools `a` and `b` both `[203.0.113.1]`, then a match-only edit moves the flow from r1 to r2 | flow 2 gets the IDENTICAL `203.0.113.1:20000` flow 1 still holds |
| P2 | the same two pools, NO edit at all | the same duplicate |
| P3 | ONE pool, the same match-only edit | `AllocatorExhausted` — no defect |

P3 is the one that mattered. The key's ignorance of match criteria and zone
scope is harmless by itself: a match-only edit changes none of `(pool name,
addresses, range)`, so the allocator is reused by `Arc` and its live reservation
keeps refusing the tuple. **F6's own fix suggestion — add match criteria to the
key — would have fixed nothing and broken that carryover**, which is the
stranding `drain_allocator_key` (#7717) was added to prevent. P2 says the edit
is not load-bearing either. What is left is the real defect: two distinct
allocator keys can cover one pool address, so that address carries two
independent occupancy bitmaps and neither can see the other's reservations.

Worth writing down as a shape: an issue that names a MECHANISM ("a match-only
edit") may be right about the OUTCOME and wrong about the cause, and the
single-variable control (P3) is what separates them. Without it the obvious fix
looks correct and is a regression.

## A quarantine was built first, and 16 merged tests said no

The first implementation was the #7717 shape: quarantine the later of two pools
sharing an address, retain its allocator so live flows drain, gate the
survivor's mint while the peer drains. It passed all eight of its own cells and
**red 16 merged tests** — #6211, #6812, #6751 fail-on-revert guards among them.

That was not fixture noise. `overlapping_pool_rules_6211` builds two rules with
overlapping pool addresses in SEPARATE allocators *on purpose*, because that is
the state #6211's pass-1 narrowing exists to resolve; #6876's release sweep
frees from every allocator for the same reason. Overlapping pools are a shape
this dataplane deliberately RESOLVES, not one it refuses — so a fix that fails
one of them closed inverts two merged designs to close one duplicate. The
quarantine was discarded.

## What shipped

Minting narrows; retention is untouched.

- `wire_overlap_peers` records, per rule at apply, the peer pool allocators
  covering the same addresses and the index each shared address has in that
  peer. Static relation, resolved once; occupancy read at mint.
- `reject_peer_owned_identity` rolls back and fails a PAT allocation that lands
  on an identity a peer already owns (`PoolPeerAddressOverlap`).
- The check runs AFTER the allocation. Check-then-mint has a window where two
  workers on two peer allocators both see the tuple free; mint-then-check means
  at least one sees the other and rolls back. Worst case a refused flow, never a
  published duplicate, and no cross-allocator lock.
- **A hostile pass over my own claim found the hole in it.** The two workers
  store to DIFFERENT bitmaps and then load the other's — the store-buffer litmus
  test — and the bitmap's existing `fetch_or(AcqRel)` / `load(Acquire)` pair
  does NOT forbid both observing the peer free and both publishing. The
  "mint-then-check has no window" sentence was therefore too strong as written
  (it is true on x86-64, where the `lock`-prefixed `fetch_or` is a full barrier,
  and that is not a property to lean on silently). A `SeqCst` fence between the
  store and the load on both sides is the standard fix; it sits after the
  empty-peer early-out, so no config a strict commit accepts executes it. It
  cannot be bound by a test, and the doc comment says so rather than implying a
  cell covers it.
- Peer identity is the ALLOCATOR INSTANCE (`Arc::ptr_eq`), not the key: two
  rules naming one pool share an allocator and are one domain. Comparing keys
  would make a rule check its own just-set bit and refuse EVERY mint on a shared
  pool — invisible in every cell that uses one rule per pool, which is why
  `two_rules_naming_one_pool_are_not_peers_6979` exists.
- `SourceNatPoolAllocatorKey` is byte-identical, so no allocator's carryover
  moves. That is the entire upgrade story, and it is this short because the key
  was not touched.

## What this does NOT cover — corrected after round 1

The first version of this entry called the address-only path "the residual",
which understated the scope. Codex's round-1 review found three separate ROUTES
to the same duplicate that this change does not close, and one cost defect:

- **address-only** (`port no-translation`, port-less protocols) mints an
  `address_only_owners` reverse-identity token and claims NO occupancy bit, so
  it is invisible to this query in both directions;
- **the HA synced reserve** (`source/synced.rs`) calls `reserve_flow` on one
  allocator directly and never reaches the check, so an imported flow can take a
  tuple a LOCAL flow already owns in a peer pool — no concurrency needed;
- **NAT64** prefixes are their own allocators and are not indexed at all.

All three are tracked in #8115 with the constraint each carries, rather than
folded into this change.

Fixed in round 2, both raised by the same review:

- the index was built per RULE with a directed rule-peer map per pair, which is
  NOT bounded by #6812 (1024 rules over one `/16` pool built 67,108,864 owner
  entries on a strict-VALID config). It is now built per DISTINCT ALLOCATOR and
  stores only the SHARED addresses, which is the budgeted quantity;
- the peer index used `.position()`, recording only an address's FIRST position.
  `expand_pool_address` does not deduplicate and each position gets its own
  bitmap, so a peer holding the tuple at its second position reported free. Every
  position is recorded now. The first cell written for this was VACUOUS — the
  `.position()` mutation escaped it because the fixture left the peer holding the
  tuple at BOTH positions; it now releases the first flow so position 0 is
  genuinely free.

Pinned rather than fixed: the deterministic-v4 refusal costs the colliding
subscriber its whole block rather than one port
(`a_deterministic_collision_refuses_the_subscriber_6979`).

## Round 2 self-check found the same cost defect one loop later

Codex's finding 4 was the per-rule peer index. Rebuilding it per DISTINCT
ALLOCATOR fixed the counting and owner passes — and left the `touches` pass,
which decides WHICH rules get the index, scanning every rule's full address
vector. That is the same unbounded quantity: 1024 rules over two overlapping
`/16` pools is 67,108,864 hash lookups where it should be 131,072. The address
scan now runs once per distinct allocator and the per-rule step is a pointer
compare against the (at most `max_pools`) allocators that touch a shared
address.

Worth recording because of how it survived: the fix for a finding was applied to
the two loops the finding NAMED, and the third loop with the same shape was not
re-derived. A cost bound is a property of every pass over the same collection,
not of the passes the reviewer happened to cite.
