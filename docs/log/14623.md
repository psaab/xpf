# #14623 — Go deterministic-NAT lookup does not dedupe the pool

## Defect

Rust `expand_pool_address` (`userspace-dp/src/nat/source/expand.rs:137-185`),
via the seen-sets threaded by its production caller
(`userspace-dp/src/nat/source/mod.rs:1828-1852`, #10700), keeps only the
first occurrence of each pool address. Go `expandPoolV4`
(`pkg/nat/deterministic.go`) appended every expanded address verbatim, so
on a tolerated overlapping pool (strict commit rejects it, but pre-#5144
lenient `Store.Load` / mixed-version `SyncApply` can carry it) every pool
index after a duplicate shifted by one.

Witness: pool `[203.0.113.1/32, 203.0.113.0/30]`

- Rust deduped: `[203.0.113.1, 203.0.113.0, 203.0.113.2, 203.0.113.3]`
- Go pre-fix: `[203.0.113.1, 203.0.113.0, 203.0.113.1, 203.0.113.2, 203.0.113.3]`

The forward lookup therefore named a different external address than the
dataplane translates to, and the reverse lookup named a different
subscriber (or not-found / ambiguous) — the #5794 invariant-8 forensic /
lawful-intercept failure, with no error.

## Fix

`expandPoolV4` now applies the same first-occurrence seen-set for mode 1
only: a `map[uint32]struct{}` keyed on the host-order address value, so a
bare host, its `/32` form, and a CIDR-enumerated host all collide, and
`pool.Address` prepend duplicates collapse too. Mode 2 is deliberately
NOT deduped: it mirrors Rust NAT64 `parse_pool_v4`
(`userspace-dp/src/nat64.rs:468-476`), which pushes each parsed host
verbatim (no seen-set), and the NAT64 deterministic `host_count` is
derived from that verbatim pool length — deduping there would diverge
from the NAT64 dataplane.

Consequential update: `TestReverseRejectsDuplicatePoolAddress`
(`pkg/nat/deterministic_test.go`) pinned the pre-#10700 behaviour — a
duplicated address occupying two pool positions and reverse answering
`ambiguous-pool`. Under the dataplane's deduped pool that pool has one
position, so the test now pins first-occurrence semantics: forward past
the deduped capacity is out-of-range and reverse resolves unambiguously
to the first-position subscriber. The `ErrCodeAmbiguousPool` branch in
`lookupReverseInPool` is retained (still reachable across distinct pools
via `LookupReverse`'s multi-pool path, and defensive within a pool).

NOT changed: the Rust dataplane (already correct), the strict commit
gate (already rejects overlapping pools), and the #9498 uint32-wrap
guard (different mechanism).
