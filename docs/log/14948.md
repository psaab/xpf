# #14948 — Enforce reinject completion origin and duplicate-early contract regardless of ledger state (D8-01)

## Issue

`CapturePipeline.resolveCompletion` gated its origin check on
`pending.ledger != nil`:

```go
originMismatch := pending.ledger != nil &&
    (completion.Family != family ||
        completion.Hook != hook ||
        completion.OwnedIfindex != pending.frame.origin.OwnedIfindex)
```

For an ordinary (non-D11) FORWARD pending row (`ledger == nil`) a
completion whose family, hook, or owned ifindex disagreed with the
pending frame's capture origin was therefore *not* an identity
mismatch: a `written` completion with matching lease epochs and
byte count was counted as clean `Written`/`Reinjected` even though
the reinjection owner claimed a different origin than the packet was
captured on. The pre-existing test
`TestD11CompletionOriginMismatchIsUncertainWhileV1Accepts10484`
encoded exactly this fail-open exception in its second ("V1") leg.

Separately, `resolveCompletion` latched `pending.duplicateEarly = true`
when a second early completion arrived before admission resolved, and
`D11AttestationLedger.MarkDuplicate` marked the ledger row
Duplicate/FAIL so it could never finalize cleanly. But the pipeline
half of that contract was inert: nothing outside the admission-pending
branch ever read `duplicateEarly`, so when admission succeeded and
`applyAdmission` replayed the retained early completion through
`resolveCompletion`, a duplicate-delivered `written` outcome was
counted as clean `Written`/`Reinjected` (and as `V1PermitSuppressed`
for `would_permit`), contradicting the ledger's FAIL disposition.

Scope narrowing (binding, from the issue): completion-contract /
bookkeeping defect only. Packet misrouting is NOT established and is
not claimed; the origin leg is an accounting/attestation fail-open
(a written reinjection is *asserted* for a packet whose origin was
not verified), not proof that bytes reached the wrong interface.
The issue's "Races Poll Against Cancel/CancelForD11Drain" title
phrase was not narrowed into a surviving leg by the synthesis (the
surviving leg is the origin/duplicate-early contract), and no data
race was reproduced in this lane: `resolveCompletion`, `Poll`,
`Cancel`, and `CancelForD11Drain` already serialize pending-map
access under `p.mu` (+ `submitGate`/`drainMu` for cancel fencing).
No behaviour change is made there; see Residuals.

## Fix

- `pkg/nfqueue/pipeline.go` (`resolveCompletion`):
  - Drop the `pending.ledger != nil &&` gate. `originMismatch` is now
    computed unconditionally from `d11OriginWire(pending.frame.origin)`
    vs the completion's `Family`/`Hook`/`OwnedIfindex`, for D11 and
    ordinary rows alike, and feeds the existing `identityMismatch` →
    `ambiguous` → uncertain/drop path (including the
    `completion lease or origin mismatch` reason and the D11
    `RecordCompletion(..., "Uncertain")` when a ledger *is* present).
  - Honour `pending.duplicateEarly`: it now forces `ambiguous` (so the
    resolution counts `Uncertain`, invokes the uncertain callback,
    terminal-DROPs the head, and retires the pending flow) and excludes
    the outcome from the `wouldPermit` fast path. Ledger rows already
    preserve their FAIL terminal state via
    `RecordCompletion`'s duplicate guard.
- `pkg/nfqueue/pipeline_attest_10484.go` (`applyAdmission`): comment
  only — documents that a replayed early completion carrying latched
  `duplicateEarly` state is resolved as ambiguous by
  `resolveCompletion`. No logic change was needed there because the
  flag lives on the pending row and survives the replay.
- `pkg/nfqueue/pipeline_attest_10484_test.go`:
  - `TestD11CompletionOriginMismatchIsUncertainWhileV1Accepts10484`
    renamed to `TestD11CompletionOriginMismatchIsUncertain10484` and
    extended: family/hook/ifindex mismatches are each exercised on
    both the ledger (D11) leg and the ordinary (ledger==nil) leg, all
    expecting `Uncertain` only, plus a matching-origin ordinary
    positive control expecting clean `Written`/`Reinjected`. The old
    ordinary-leg "accepts mismatch" expectation is deleted as the
    encode-the-bug leg of the contract change.
  - `TestDuplicateEarlyCompletionDoesNotCountAsWritten14948`: two
    early `written` completions latch `duplicateEarly`; admitted replay
    must yield `Uncertain` only (no `Written`/`Reinjected`), one
    uncertain callback, Duplicate+FAIL ledger row that refuses
    `FinalizeIfTerminal`, and DROP verdicts for head + retired
    follower. A single-early positive control still resolves to clean
    `Written`/`Reinjected` and finalizes.
  - `TestDuplicateEarlyOrdinaryCompletionDoesNotCountAsWritten14948`:
    the same duplicate contract on the ledger==nil ordinary arm.

NOT changed: `submitEligible`, `submitAdmitted`, `attestSubmit`,
`deadlineFailedState`, `admissionFailedState`, the rejected-admission
(`!admission.Admitted`) branch of `applyAdmission` (it already counts
an accompanying early completion as `Uncertain` and records it as
such), `Poll` timeout handling, `Cancel`, and `CancelForD11Drain`.
No wire format, ledger record shape, or stats field changes.

## Residuals

- The issue title's Poll-vs-Cancel race phrase: no race was
  reproduced or fixed; current locking already serializes the pending
  map. If the validator's full report (not available in this lane —
  the synthesis file was not present under `/var/worktrees`) intended
  a specific interleaving beyond the origin/duplicate legs, that leg
  remains unaddressed and should be refiled with its exact
  interleaving rather than inferred here.
- Origin validation uses `d11OriginWire`, which maps any non-`inet`
  family to wire family 2 and any non-`forward` hook to wire hook 2.
  Ordinary pending rows are only minted for
  `family == inet && hook == forward` frames in `submitEligible`
  (other hooks/families are dropped before minting), so the fallthrough
  mapping cannot mask a distinct legal origin on reachable rows.
