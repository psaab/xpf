## Why

Issue #14192 (D10-01): a bare chassis-cluster control/fabric lifeline base (`control-interface ge-0/0/0`, no unit) exempted every numeric suffix of that physical interface. `HostInboundLifelineSet` recorded only declared interface base keys (value `false` for ordinary interfaces) and set the bare lifeline base to `true`; declared units were never registered as keys. `HostInboundLifelineInterface` therefore missed the exact lookup for a declared transit VLAN unit (`ge-0/0/0.100`) and its numeric-suffix fallback returned the parent's `true`. That exemption propagated to `junosHostNonLifelineRefs` and `junosHostZoneNetdevCoverageMap` (fine deny-program refs and coarse ingress-netdev projection), and to the userspace host-inbound path which delegates to the same matcher (`zones_host_inbound.go` lifeline skip), so a zone-assigned VLAN unit with its own kernel netdev (`ge-0-0-0.100`) could be exempted from the intended `to-zone junos-host` default-deny. Conditional exposure only — a host listener on such a unit still had to be reached — but the deny scope was silently dropped.

## What

`pkg/config/lifeline.go`:

- The fixed `fxp0` lifeline now also registers `fxp0.0` explicitly. Before, `fxp0.0` matched only through the numeric-suffix fallback against the bare `fxp0` key; once declared units of a declared `fxp0` interface are registered `false`, that fallback would have returned the registered unit's `false` for its own lifeline. The explicit key keeps the management unit exempt.
- Register every declared unit of every declared interface as an explicit `false` key (`<base>.<unit>`) before the cluster walk, so the matcher resolves the exact key and never falls back to a lifeline parent for a declared unit. Unit 0 is registered `false` here and re-marked `true` only when it is itself the designated lifeline (`set[name]=true` plus `set[name+".0"]=true` in the cluster and fabric-aggregate walks, or `markBaseLifeline` for a `.0`-spelled / fabric-member role). A role name spelled at a declared unit (`control-interface hb.1`, `fabric-interface ge-0/0/0.100` where that dotted name is a declared interface) is re-marked `true` in the same registration loop, since it designates that unit, not a new interface.
- Non-zero-unit role bindings (`fabric-interface ge-0/0/0.100` against a declared bare parent) no longer promote the bare parent: the `SplitInterfaceUnitRef` walk forces the declared base back to `false`. The pre-existing naive `strings.Cut` guard for undeclared-parent spellings (`hb.1`-style dotted names) is kept.
- `markBaseLifeline` (unit-0-spelled roles and fabric members) keeps the `unit == 0` rule for untagged units but forces VLAN-tagged (`VlanID != 0`) units to `false`, so a tagged unit on a fabric-member parent no longer inherits the exemption. Its distinct netdev (`<parent>.<vlan>`) is the reason the bare-parent rule does not apply.
- Matcher (`HostInboundLifelineInterface`): in the fallback, an undeclared unit-0 spelling of a lifeline prefix (`set[prefix]==true`) is decided decisively `true` even when a declared sibling was registered `false` (`ge-0/0/0.0`, `hb.1.0`, `ge-0/0/0.100.0`). When the stripped prefix verdict is `false` (a dotted declared sibling under a lifeline parent, `hb` under `hb.1.0`), the registered verdict governs, preserving #12848.

NOT changed:

- Undeclared numeric spellings (pinned by #13137 `ge-0/0/0.1`/`ge-0/0/2.1` and #12848 `hb.2`/`fxp0.2`/`fxp0.100`) still inherit the parent verdict. Registering "declared+1..N" ranges or walling off the fallback there would have broken those pinned cases and the `fxp0` default lifeline (`fxp0.1` exempt today; verified not a failing control on master).
- Userspace `zones_host_inbound.go` and the coverage/dup/dhcp consumers: they already delegate to the config matcher, so the set fix reaches them without a second convention.

## Validation

New regression `TestLifelineBareParentDeclaredVLANUnit14192` (`pkg/config/lifeline_bare_transit_vlan_14192_test.go`): parsed Junos-style config with `control-interface ge-0/0/0` (bare), declared `unit 100 vlan-id 100` plus `unit 0` on `ge-0/0/0`, zone `untrust` assigning `ge-0/0/0.100` and standalone transit parent control `ge-0/0/1.0`, `untrust -> junos-host deny-all`.

- RED on pristine `origin/master` `4adefde7a`: `HostInboundLifelineInterface("ge-0/0/0.100") = true` (and `.0100`), `junosHostNonLifelineRefs = [ge-0/0/1.0]` (unit dropped), and `BuildJunosHostDenyProjection` ingress netdevs `[ge-0-0-1]` only — `ge-0-0-0.100` deny scope missing.
- GREEN with fix: bare parent/`ge-0/0/0.0` stay lifelines; declared `ge-0/0/0.100` is ordinary; standalone `ge-0/0/1[.0|.100]` stay ordinary; the projection keeps `ge-0-0-0.100` in ingress netdevs. The parent netdev `ge-0-0-0` also remains as a conservative parent-superset candidate for the VLAN unit (pinned coverage doctrine #12839) — that is the unit-100 deny widened to its carrier, not a lifeline deny on unit 0.

Targeted suites: `Lifeline*` (3682/5250/11068, dotted 12848, unit0 13137, 14192), `TestHostInboundLifelineInterface`, `TestJunosHostExempt13134*` (incl. `fxp0.50` ordinary), `TestLifelineIsNotWithheld7490`, dup-host-local-address, contested-trunk advisory all pass. Userspace: all `TestHostInbound*` pass except one known regression below. Full `pkg/config` suite exceeds the 300s tool budget in this environment (timed out with no output, not a failure signal); the lifeline/host-inbound subsets above are the affected surface.

Known regression (documented, not hidden): `TestHostInboundLifelineIngressNetdevsDoesNotAddUnitParent12848` (userspace) now fails — `hb.1` with `Units{7}` and `ControlInterface=hb.1` yields `ingress=[fxp0]`, missing `hb.1.7`. Root cause: the config set now registers the declared unit `hb.1.7` as `false`, and the userspace helper resolves lifeline netdevs only via declared-unit spellings (`hb.1.7`), never via #12848's ".0-strip" — so a dotted lifeline whose only declared unit is non-zero loses its exception netdev. This is a userspace-helper coverage gap exposed by making the set truthful; the helper would need to also probe the lifeline base's unit-0 view. It does not affect the #14192 deny-scope fix (config projection is correct), and the unit is now correctly deny-scoped rather than exempt — fail-closed direction. Follow-up should teach `HostInboundLifelineIngressNetdevs` to consider the stripped lifeline base.

Decisive check named in #14192 (userspace admitted host-inbound decision on the unit): covered by delegation for the config projection — the userspace path calls the identical `HostInboundLifelineSet`/`HostInboundLifelineInterface`; the exception-netdev gap above is the one place the userspace walk diverges (it enumerates declared units rather than asking the matcher per row).

## Risk

Behavior delta is narrow: only declared non-zero/VLAN-tagged units of a bare lifeline parent, and bare parents of non-zero-unit role bindings, lose an exemption they should never have had (fail-closed: host-inbound deny now applies). Unit-0 and undeclared-unit inheritances pinned by #13137/#12848 are unchanged. Residual: a deployment that deliberately relied on exempting a declared VLAN unit via a bare parent lifeline name will now see that unit deny-scoped — that reliance was the defect.
