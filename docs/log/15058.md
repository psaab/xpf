# #15058 — static RA and PD RA target resolving to one netdev merge instead of clobbering

## Why

A static RA authored as `ge-0/0/1.0` and a DHCPv6-PD
`update-router-advertisement interface ge-0/0/1` name the same kernel
netdev (`ge-0-0-1`; unit 0 collapses onto the parent). `buildRAConfigs`
keyed its merge map by the raw authored string, so the PD prefix created a
second RA config instead of merging into the static one. The final
`ResolveKernelIfName` pass then produced two configs both named
`ge-0-0-1`, and `ra.Manager.Apply` built its desired map last-wins,
silently dropping the static config — its M/O flags, RDNSS servers and
static PIOs disappeared from the LAN whenever a PD lease was present, on a
config that committed clean with no warning.

## What

- `pkg/daemon/daemon_ra.go` (`buildRAConfigs`): key `raByIface` by
  `cfg.ResolveKernelIfName(...)` for both the static entries and the PD
  merge lookup, so differently-spelled references to one netdev merge
  into one config carrying the static options plus the delegated prefix.
  Two distinct static entries resolving to the same device keep the first
  and log a warning (a config-file duplicate the compiler's find-or-create
  normally prevents; never silently last-wins). Nil static entries are
  skipped instead of dereferenced by the clone.
- `pkg/ra/ra.go` (`Manager.Apply`): refuse a config slice containing two
  entries for the same interface with an error, before locking or touching
  any sender state — fail closed, live senders keep their last good
  config. This makes the residual duplicate the daemon merge could
  historically produce (or any future caller bug) loud instead of a
  silent option loss.

NOT changed: the compiler still accepts the mixed spellings (they are
legitimate Junos); merging at the daemon seam against the canonical
resolver covers the unit-0 collapse, RETH members and VLAN units
uniformly. `DelegatedPrefixesForRA` and the PD lifetime decay are
untouched.

## Validation

- RED on `origin/master` (`3b1f906880`):
  `go test ./pkg/daemon/ -run TestBuildRAConfigs15058StaticDotZeroMergesPD`
  failed with `buildRAConfigs returned 2 RA configs, want 1 merged config
  for ge-0-0-1`; `go test ./pkg/ra/ -run TestApply15058RejectsDuplicateInterface`
  failed with `Apply accepted two configs for interface "lo"; the first
  would be silently dropped (last-wins)`.
- GREEN after the fix: both tests above pass, including both spelling
  directions (static `.0` + PD bare, static bare + PD `.0`), asserting one
  `ge-0-0-1` config with M/O flags, RDNSS and both prefixes. Control:
  `TestBuildRAConfigs15058DistinctInterfacesStaySeparate` (PD on
  `ge-0/0/2` stays a separate config) passes before and after.
- Neighbouring suites: `go test ./pkg/daemon/ -run 'TestBuildRAConfigs|TestClusterRAConfigSets|TestDesiredClusterRA|RA'`
  and the full `go test ./pkg/ra/` pass.

## Risk

Behavior change only where two RA configs previously collided on one
resolved device: they now merge (daemon) or error (direct `Apply`
callers — the daemon is the only production caller and now never produces
duplicates). A duplicate `Apply` error leaves existing senders running
their previous config rather than withdrawing them. Two static stanzas
authored with different spellings for one device keep the first stanza's
options and warn; previously the PD-created (later) entry won and static
options were lost.
