- **`test-dhcp-lease-failover`**: row `53bb851d8b2a2549`, verdict VOID, from the preflight `LAB PREREQUISITE MISSING: dhcp-lease-synchronization is not enabled`. The committed lab config carries neither the knob nor a `dhcp-local-server`.

## Persistent-NAT fixture fix

The pool is now DISCOVERED instead of assumed:
- `reachable_source_pool` reads `show configuration | display set` and returns the first committed source pool whose /32 is proxy-ARPed on an interface unit whose subnet contains `TARGET`.
- `resolve_pool` then REUSES that pool (`pool-snat-pool` here), adding only `persistent-nat` for the run.
- The restore removes only that `persistent-nat` stanza and puts rule `snat` back on `source-nat interface`, so the cluster's own pool survives.
- Setting `POOL_ADDR` keeps the old dedicated-pool mode.
- If no reachable pool exists the harness dies before committing anything, instead of measuring a path that cannot answer.

Checked against the captured live config (`show configuration | display set`, 310 lines):
- `TARGET=172.16.80.200` gives `pool-snat-pool 172.16.80.7`;
- `TARGET=172.16.100.200` gives nothing;
- `TARGET=172.16.50.200` gives nothing.

`bash -n` is clean and `make harness-census` is OK. `shellcheck -S warning` reports one SC2034 (`CONFIG_APPLIED` unused), which origin/master's copy of the file reports identically.

## DHCP lease gate: self-provisioned fixture, and ordering that can fail

The first run was VOID because the lab config carries no lease-sync knob. The harness could not have produced a verdict on this cluster, and the issue's fix direction for V-07 was still open on three points: cell (c), the Kea load anchor for (a), and a client that does not disturb the shared LAN host. Changes to `test/incus/dhcp-lease-failover.sh`:

- **Fixture.**
  - If the knob is absent, the run commits it on the RG0 primary together with `dhcp-local-server group g9729` on `reth1.0`, subnet 10.0.61.0/24, range .150-.199. Success is gated on the CLI's `commit complete` marker (#6440), not the exit status.
  - An EXIT trap removes both on each node. The trap is armed before the attempt, so a commit that fails half-way is still rolled back.
  - A lab config that already has the knob is left untouched. `DHCP_PROVISION=0` restores the old refusal.
- **Clients.**
  - Each client runs in its own network namespace, on a macvlan over the LAN host's `DHCP_CLIENT_IFACE`.
  - A dhclient script only adds or removes the leased IPv4 address. The shared LAN host's own 10.0.61.102, its routes and its resolv.conf are never touched.
  - The trap deletes the namespaces.
- **(a)** is anchored on a POSITIVE event: `DHCPSRV_MEMFILE_LEASE_FILE_LOAD` in `kea-dhcp4-server`'s journal on the promoted node since the standby's clock reading taken just before the reboot, polled for up to `REBOOT_WAIT`. Only after that load is seen is "no load error since the failover" asserted. With no load event the cell FAILs and names Kea's `ActiveEnterTimestamp`, instead of passing on an empty journal window.
- **(c) is implemented and runs BEFORE (b).** Client B DISCOVERs on the promoted node and must get an address, and not client A's. The order is the point. If client A re-requested first, its own request would occupy the address whether or not the lease had synced, and (c) could never fail.
- **(b) is judged on the exchange, not only the address.**
  - Client A is stopped without release, then restarted on its lease file.
  - The run must show `DHCPREQUEST for <addr>` and `DHCPACK of <addr>`, with no `DHCPNAK` and no `DHCPDISCOVER`.
  - The same address alone would be weak, because an allocator can hand a returning client the first free address again.
- **Header:** says what is automated. v6 stays opt-in with `DHCP_V6=1`, and IA_PD is not claimed.

`bash -n` and `shellcheck -S warning` are clean. The embedded dhclient script passes `sh -n`, and `make harness-census` is OK. The live verdict comes from the lab run below.

The gate is reporting a product defect, not a fixture defect. A further counter-diff cell (below) locates where the replies stop, before anything is filed.

## Third DHCP run: the fixture broke the lab's own DHCP, and a product gap

- **Row `run 3`** (VOID): the namespaces worked with `nsenter`, but client A's DISCOVER went unanswered.
- **Cause, from `kea-dhcp4-server` on the RG0 primary:**
  - `DHCP4_PARSER_FAIL ... subnet with the prefix of '10.0.61.0/24' already exists`, then `DHCP4_INIT_FAIL`; Kea exited.
  - The lab config ALREADY has `dhcp-local-server group lan-pool` serving 10.0.61.0/24. The first VOID's preflight checked only the lease-sync knob, and my alternation `| match "a|b|c"` query returned nothing (the CLI's `match` does not take alternation), so I wrongly concluded the lab had no server. The fixture's second group for the same subnet committed clean, and Kea then refused the whole config.
- **Product gap, filed as #9785:** two `dhcp-local-server` groups with the same subnet commit clean and stop all DHCP on the node.
- **Side effect:** removing the group rewrote a valid Kea config, but nothing restarted the failed unit, so the lab's LAN DHCP stayed down on the primary until it was restarted by hand in a lock cell (below).
- **Harness fix:** `provision_dhcp` reads `show configuration system services dhcp-local-server`.
  - When a group with a subnet already exists, it commits ONLY `set chassis cluster dhcp-lease-synchronization`, and the clients lease from the lab's own pool.
  - The `g9729` group is added only when no group exists.
  - The restore removes exactly what was added (`PROVISIONED_KNOB`, `PROVISIONED_GROUP`).
  - `bash -n`, `shellcheck -S warning` and `harness-census` are clean.

## Fourth DHCP run: a verdict, and one premature check

Before the gate, the cell restored the lab's LAN DHCP. The earlier fixture had left `kea-dhcp4-server` failed on the primary; by then #9651's deploy had restarted it, and the cell confirmed it `active` with `DHCP4_STARTED`. Only the lease-sync knob was provisioned, and the lab's own `lan-pool` served the clients.

**Result: 8 passed, 1 failed.**
- the v4 pre-seed header on the standby is byte-exact;
- promotion was observed;
- (a): Kea on the promoted node logged a memfile load after the failover, with no load errors;
- (c): client B got 10.0.61.101, not client A's in-use 10.0.61.100;
- (b): client A kept 10.0.61.100 through REQUEST/ACK, with no NAK and no DISCOVER.

**The failed check** was that the leased address is in the standby pre-seed memfile, read by a fixed `sleep 3` after the lease. That wait is shorter than the push path can guarantee. The push is change-polled every 2s, runs in a guarded goroutine that reads Kea's lease set, and crosses session sync; a full re-push comes every 30s.

The later cells show the lease had synced: client B was refused A's address BEFORE client A re-requested it, so the promoted node already held the lease at promotion. So this is the harness's timing, not a lost lease. Step 2 now polls for the address for up to `LEASE_SYNC_WAIT` (30s), and reports how long the push took.
