# 9246 / 11366 — bracketed to-zone lists silently lose policy coverage

## Legacy ungrouped shape (#9246)

The original `#9246` regression used `ParseSetCommand` and produced this
four-key residue:

    [security]
      [policies]
        [from-zone trust to-zone untrust]     <- the 4-key context
          [dmz policy p1 then permit]          <- the rule is absorbed as key tokens

The compiler builds `trust->untrust`, but `FindChildren("policy")` matches
nothing because the only child is named `dmz`. The authored rule is absorbed
and exists nowhere.

## Production grouped shape (#11366)

Operator `set` commands use `ParseSetCommandGrouped` and
`SetPathQuotedGrouped`. The same input preserves the full list on the context:

    [from-zone trust to-zone untrust dmz]     <- extra zone token retained
      [policy p1 ...]                          <- the rule remains a child

The compiler still reads only `Keys[1]` and `Keys[3]`, so it builds
`trust->untrust` with the policy while silently ignoring `dmz`. Hierarchical
text preserves the extra token on the context too, affecting hierarchical
override loading and peer sync. The old `#9246` test did not exercise these
production shapes.

Before #12039, `from-zone` lists collapsed the other way:
`[from-zone trust dmz to-zone]` with the real destination and policy in a
child. `Keys[3]` became the literal `"to-zone"`, so strict compilation rejected
it as an undefined zone. That diagnostic blamed the wrong thing; tolerant
loads only warned, leaving the dropped deny able to fall through to a global
permit. The #12039 fix and its placeholder exclusion are described below.

## Why reject rather than expand

Junos accepts no bracketed list on `from-zone`/`to-zone`; a policy context is
ONE zone pair. Expanding would invent a semantics the platform does not have,
and would owe an answer to a question this is not the change to decide: what a
single policy NAME means once it exists in several contexts. Rejecting is
smaller, matches the platform, and restores the operator's ability to see the
problem.

## Where the check lives, and why not in the strict validator

The compiler records both malformed AST forms before it discards the
unrecognized structure: the legacy residue child and extra context keys after
the one permitted zone pair. The latter is detected by key shape even when
`KeysBracketed` provenance is absent; provenance makes the diagnostic more
specific for an authored bracket list. A single-zone bracket and an ordinary
one-zone pair remain valid.

`SecurityConfig.MalformedZonePairs` carries the diagnostic to the shared
strict/tolerant gate. Candidate `CommitCheck` and `Commit` reject. Tolerant
loads still skip the malformed zone-pair context rather than inventing an
expansion, but now append a synthetic global policy flagged
`LenientContentDropped`. The existing userspace lowering emits the
`__unsupported__` application sentinel, so the helper rejects the WHOLE policy
snapshot (previous-good retained; fresh-boot default-deny) instead of allowing
the listed pairs to fall through to a global/default permit (#12039). The
tolerant warning explicitly says the malformed context is not enforced.

## Two false positives, found by running the suite rather than reasoning

The first detector flagged "any child of a hierarchical pair that is not
`policy`". That is wrong twice over, and neither case was visible from the
mechanism:

  - `inactive: policy p1 ...` is a SUPPORTED Junos spelling (#2008 H1). The
    marker is a statement PREFIX, so the node's first key is `inactive:` and
    `policy` follows -- byte-identical to the absorbed shape. Refusing it
    rejected a spelling the product accepts, and the repo's own
    TestInactive_UpgradeEquivalence caught it.
  - the #2419 census synthesises placeholder paths like
    `from-zone xpfarg xpfarg xpfarg policy ...`, which are not configs.

So the test narrowed to the ABSORBED-RULE signature: a child whose first key is
not `policy` and is not the parser's `inactiveMarker`, but which carries
`policy` LATER in the same key list. Both conditions together are what separate
absorbed tokens from every legitimate child.

Adding a struct field also perturbed the #4406 goldens with
`"MalformedZonePairs": null` on every case. It is a compile-time DIAGNOSTIC, not
semantic content, so it carries `json:"-"` -- otherwise it would shift every
fixture and every ConfigFingerprint comparison the elision censuses run, for a
field that is nil in every valid config.

## Scope: from-zone lists are now recorded, with the #2419 placeholder excluded

`from-zone [ trust dmz ] to-zone untrust` collapses the other way:
`Keys=["from-zone","trust","dmz","to-zone"]`, with the two source-zone values
bracketed and the real destination/policy absorbed into a child. Before #12039,
the detector only recognized `Keys[2]=="to-zone"`, so tolerant compilation did
not record this malformed context. The pair builder read `Keys[1]` and
`Keys[3]`, creating a phantom `trust->to-zone` pair with zero policies. The
undefined-zone warning then claimed the helper would refuse the whole snapshot,
but no rule for the empty pair reached the helper; a global permit could still
win.

The detector now recognizes the shifted `to-zone` key at `Keys[3]` or later and
records the malformed source shape. The existing tolerant gate carries that
record into its synthetic-global `LenientContentDropped` poison, so the
unsupported sentinel rejects the whole userspace snapshot; no second poison
mechanism or guessed zone-pair expansion was added. The #2419 census's
synthetic `from-zone xpfarg xpfarg xpfarg` placeholder is explicitly excluded.
Single-source bracket and ordinary zone-pair controls remain valid.
`TestMalformedFromListZonePairIsRecorded12039`,
`TestMalformedFromListZonePairRefusesSnapshot12039`, and
`TestMalformedFromListZonePairLeavesNoPhantomPair12039` were RED before this
change; `TestMalformedFromListDetectorExemptsCensusPlaceholders12039` is the
placeholder control.

## Mutation matrix, including the call site

    remove the gate from uniformgates (WIRING)   -> 2 cells red, "committed clean"
    neuter the detector, call site intact        -> 3 cells red, "committed clean"
    drop the inactive: exemption                 -> TestInactive_UpgradeEquivalence reds
    record the defect but do NOT skip the build  -> SURVIVED at first

The last one is the useful entry. Recording without skipping is invisible to
every strict-path cell, because the gate refuses either way — but on the
TOLERANT path it leaves a phantom `trust->untrust` context carrying zero
policies, which an operator would see in `show security policies` next to a
warning about the rule they actually wrote.
`TestMalformedPairLeavesNoPhantomContext9246` was added for it, and the mutant
now reds with "phantom context trust->untrust".

## Controls

The `#9246` controls assert that an ordinary pair still carries its policy and
that separate per-zone statements still produce two contexts. The `#11366`
cells build the real grouped-set tree, assert strict rejection and tolerant
quarantine, remove provenance to prove shape-based detection, and cover
hierarchical text. Store-level cells exercise `SetFromInput`, `LoadSet`, flat
and hierarchical `LoadOverride`, and tolerant peer `SyncApply`.
