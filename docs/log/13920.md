# Issue #13920 — preserve port 0 in application port ranges

- **Issue:** An application source-port or destination-port range `0-N` was
  rewritten to `1-N`, so a deny missed TCP/UDP traffic whose real port was 0.
- **Base:** `ad0ded0df`.
- **Branch:** `fix/13920-campaign`.
- **Worktree:** `/var/worktrees/campaign-zero/wt-13920`.
- **Source:** Opus review H02-01; issue acceptance requires a fail-on-master
  regression and source/destination parity.

## Change

The application canonicalizer now preserves 0 range endpoints, and the
application port validator, userspace representability gate, Rust policy range
parser, and host-inbound deny-port parser accept an explicit zero-floor range.
A bare single port 0 remains invalid. The app-ID catalog continues to reserve
`(0,0)` for an omitted port constraint, so explicit `0-0` remains
unrepresentable in that catalog; the policy-term representation keeps `0-0`
distinct from an empty constraint. NAT port allocation and translation ranges
are unchanged.

Regressions cover referenced source-port and destination-port apps, inline
terms, explicit `0-0`, source/destination catalog bounds, Rust runtime deny
matching for TCP and UDP with L4 present, Rust range parsing, and Go capability
checks agreeing with Rust.

## Risk and residual

The app-ID catalog wire uses `(0,0)` as the no-constraint sentinel, so an
explicit `0-0` constraint cannot be represented for app-identification labels;
policy evaluation itself has a distinct non-empty range representation. The
Go simulator's query format encodes an omitted port as zero and has no
`l4_present` bit, so zero-valued query ports remain fail-closed there; the
literal-zero packet assertion belongs in the Rust dataplane test, where L4
presence is explicit.
