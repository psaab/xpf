# Issue #14313 — AppCatalog::lookup_directional l4_present guard

- **Issue:** psaab/xpf#14313 (deep-review D1-02, zone-policy-100). Lane
  branch: `fix/14313-campaign` off `origin/master`
  `5b122dda5ebb23aec9c283ef7cbddca0874b9338`. Worktree:
  `/var/worktrees/wt-14313`; base RED worktree:
  `/var/worktrees/wt-14313-base` (detached at the same SHA, never stashed).
- **Scope:** AppID labelling integrity only. `AppCatalog` never admits or
  denies traffic — enforcement goes through `CompiledApplications::matches`,
  which already carries the #3291 `l4_present` guard. Severity is the
  narrowed Low/Medium (wrong application name in session display /
  RT_FLOW / policy-deny / filter-log / conntrack telemetry), not High.

## Defect (present at base)

`CompiledApplications::matches` (`policy.rs:1300-1343`, #3291) takes
`l4_present: bool` and refuses port terms when `!l4_present`.
`AppCatalog::lookup_directional` (`policy.rs:1594-1669`) had no such
parameter: its `in_range(0, N, 0)` is true, so a flowless non-first
TCP/UDP fragment — synthetic tuple `(src_port, dst_port) = (0, 0)` —
matched a `0..=N` port-constrained catalog entry (#13920 shape, e.g.
FaceTime `0-41640`, `port_constrained = true` at `policy.rs:1524-1535`)
in the port tier and beat any protocol-only entry. The same applied to
`exact_dst` (always port-constrained). Callers resolving AppID from a
flow key made no fragment distinction.

## What

- `AppCatalog::lookup_directional` gains `l4_present: bool`. When
  `!l4_present` it skips `bucket.exact_dst` and every
  `port_constrained` scan entry; only `proto_only_scan_hit`
  (`!port_constrained`) may resolve — mirroring #3291. No test-input
  special-casing; the guard keys on L4 presence, not port values, so a
  real port 0 with L4 present still matches `0..=N` (#13920 preserved).
- `lookup_forward` / `lookup_admitted` are flow-backed wrappers and pass
  `l4_present = true` (byte-identical for every session/conntrack caller:
  `poll_descriptor/mod.rs` install sites, `session_delta.rs`,
  `policy_revalidation.rs` restamps).
- Cold-path resolvers in `event_emit.rs` gain `resolve_flow_app_id_l4` /
  `resolve_policy_deny_app_id_l4`; the existing names delegate with
  `true`, so every flow-backed deny/filter-log/PBR/forward-request caller
  is unchanged.
- Flowless sites that previously resolved through the unguarded lookup
  now pass their known L4 presence:
  - `flowless_verdict.rs` (flowless LocalDelivery): host-inbound and
    junos-host deny emits via new `emit_host_inbound_deny_l4` /
    `emit_junos_host_deny_l4` with `extra.l4_present` (false for a
    non-first fragment); its lo0 filter-log AppID now resolves via
    `apply_lo0_filter_action` with `extra.l4_present`.
  - Input-filter logs: `CachedInputFilterLog` carries `l4_present`
    (populated from `extra.l4_present` at all four construction sites in
    `poll_descriptor/filter.rs`); `emit_input_filter_log_match` and the
    Stage-11 pending log resolve with it. Cached-output logs keep `true`
    (established flows only, real ports in the descriptor key).
  - Already-correct flowless denies are unchanged and now documented as
    such: transit ForwardCandidate (`mod.rs:7677`), MissingNeighbor
    (`mod.rs:9654`), NoRoute (`mod.rs:9056`, `ports` is `None` when
    flowless → app_id 0), and embedded-ICMP (`embedded_icmp.rs:547`) all
    pass app_id 0 outright.
- `event_stream/README.md` records the #14313 L4-aware lookup contract
  next to the #3321 directional one.
- Regression `app_catalog_flowless_fragment_skips_zero_floor_port_range_14313`
  in `policy_tests.rs`: catalog with TCP `0..=41640` (id 5) + protocol-only
  TCP (id 3); asserts flowless `(0,0)` forward and reverse resolve 3 (not
  5), flowless with only the `0..=N` entry resolves 0, flowless exact-port
  entry is skipped, and L4-present real port 0 / 41640 still resolve 5.
  All pre-existing `lookup_directional` test callers pass `true`.

## Risk

Labelling-only: no policy verdict, forwarding, or session-install path
changes. The only behavioural delta is that a flowless packet's AppID
label can now fall back to a protocol-only application (or UNKNOWN)
instead of a spurious `0..=N` port application — fail-closed for
telemetry. Flow-backed resolution is byte-identical (`l4_present = true`
everywhere a real tuple exists). Residual: Go's AppID-disabled fallback
(`resolveTupleFallback`) has no `l4_present` bit (noted in #13920's log);
it is a simulator/display path with no fragment caller and is out of
scope here.
