# #17862 — Arm record written before the BootNext mutation

- **Timestamp**: 2026-10-27
- **Action**: Salvaged in place by the parent after the engineer lane died
  on a GLM quota error (lane had completed the Go reorder + RED capture;
  the parent completed the shell half and the final green run).
- **Defect**: A crash after SetBootNext but before the promotion record
  was written left an ARMING journal with a queued one-shot and no arm
  record; the boot script folded that to not-armed and exited with a
  quiet "nothing to promote" while a candidate could boot unverified.
- **Fix**:
  - `pkg/upgrade/kernel_run.go`: `armCandidate` durably writes the arm
    record (`recordPromoteBinary`) after recording ARMING and before
    `SetBootNext`, so the record exists before any NVRAM mutation; the
    positive BootNext readback still gates the ARMED transition.
  - `scripts/image/xpf-kernel-promote`: `journal_state` reports
    `arming-unrecorded` for an ARMING journal with no record; that state
    takes a loud branch — durable `unrecorded-arming` refusal record
    plus a WARNING naming both files — instead of the quiet fold.
- **Validation**:
  - `go test ./pkg/upgrade/ -run '17862|16796|16809' -count=1` PASS
    (new `kernel_arm_record_before_bootnext_17862_test.go` pins the
    record-before-BootNext order).
  - `python3 scripts/image/test_kernel_promote_explicit_path.py` — 76
    tests OK, including the two renamed #17862 recordless-ARMING cells
    (durable record `journal_state=arming-unrecorded`, busybox parity).
- **Risk**: pre-#17862 arms (record written after readback) that crash
  in the old window now warn loudly on the candidate boot instead of
  exiting quietly; the gate still does not run without a designated
  binary, and the next plain reboot falls back to the known-good slot.
