# Issue #15112: Reinject submit/complete accept loops survive accept errors (A73-01)

- **Timestamp**: 2026-10-19
- **Action**: `spawn_reinject_socket_servers` in
  `userspace-dp/src/server/reinject_9506.rs` spawned the #9506 submit and
  complete accept threads with a hand-rolled match: `WouldBlock` slept 1 ms
  and every other accept error did `Err(_) => break`. The thread then
  returned and the `UnixListener` moved into its closure was dropped, so
  the socket path went deaf permanently. An idle EMFILE — descriptor or
  memory pressure with an empty backlog, where the kernel reserves the
  result descriptor before looking at the backlog — therefore killed both
  loops; every IPsec FORWARD flow using the #9506 adjudicated re-entry
  black-holed behind a healthy control socket until a helper restart that
  nothing triggers. `#9172` had converted only the control and session
  loops in `lifecycle.rs` to `accept_step`; these two loops were the
  residual its predicate did not cover.
- **Action**: both reinject loops now decide through
  `lifecycle::accept_step` with `retry_unclassified = true`, exactly as
  the session loop does: `WouldBlock` keeps the previous 1 ms poll
  interval, EMFILE/ENFILE/ENOBUFS/ENOMEM retry on the shared
  50 ms-doubling-to-1 s `AcceptBackoff` with one onset and one recovery
  journal line, and any unclassified error logs and retries instead of
  exiting (the `AcceptStep::Fail` arm, unreachable with
  `retry_unclassified = true`, sleeps at the backoff ceiling rather than
  spinning, mirroring the session loop). The peer-credential check and
  the inline, globally-serialized serving of each accepted connection
  are unchanged. Each accepted connection is additionally served under
  `catch_unwind` (the issue's optional serving wrap): a handler panic
  drops that one connection with a journal line and the accept loop
  continues, instead of unwinding the thread and dropping the listener.
  No change to `lifecycle.rs` (`accept_step`/`AcceptBackoff` are reused
  as-is), to the Go side (`pkg/nfqueue` already redials per reconnect),
  or to any neighbouring behaviour.

## RED -> GREEN proof

- **RED**: on `origin/master` (`699145ac4e`) with only the new tests
  added, `cargo test 15112 -- --test-threads=1` failed all three cells:
  both idle-EMFILE cells (which lower the soft `RLIMIT_NOFILE` to just
  above the open-fd count, then drain the remaining slots with
  `/dev/null` duplicates so the idle listeners' `accept()` returns
  EMFILE) found their accept thread had exited on the first EMFILE —
  the post-pressure connection was refused / never served — and the
  textual-wiring cell found zero `accept_step` calls in
  `spawn_reinject_socket_servers`.
- **GREEN**: after the fix the same command passes all three cells
  (3 passed, 8644 filtered, 6.5 s). The two behavioural cells induce
  the idle EMFILE as above, release the pressure, and then prove the
  real spawned loops still serve: the submit cell's ANNOUNCE applies
  permit epoch 4242 to the fallback core, and the complete cell
  receives the queued completion and acks it. The wiring cell pins
  both `accept()` results through `accept_step` with
  `retry_unclassified = true`, in the same shape as the #9172
  lifecycle cell. Adjacent controls: the full `reinject_9506` module
  (93 passed) and the #9172 `lifecycle` accept-step cells stay green.
  The full `--bins` suite on the fixed tree reports 8585 passed /
  54 failed; the failures were reproduced on clean `origin/master`
  worktrees or traced to concurrent campaign merges landing on
  `origin/master` after this lane branched (wire-fixture and
  shim-tally drift), i.e. none is attributable to this change, which
  touches only the two reinject accept loops.
