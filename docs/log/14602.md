# #14602 — dual-stack DHCP client never gets both A and AAAA under replace-owned

## Defect

Under the default `replace-owned` policy, a dual-stack DHCP client
never publishes both its A and its AAAA. The only identity producers
are `identity4` (`cid:`/`mac:`, `pkg/dhcpserver/ddns_leases.go`) and
`identity6` (`duid:<duid>/<iaid>`); `dhcidRR` digests the raw prefixed
identity string, so the two families of one host always produce
different RFC 4701 DHCIDs. Whichever family publishes first owns the
name under its own DHCID; the sibling's RFC 4703 Attempt B
(DHCID-matches-ours) can never match, so it is refused with
`errDDNSConflictRefused` every cycle (owned=1, SkippedConflict rises,
err=nil) and half the host's forward DNS silently never appears. The
winner depends on Go map iteration order in Pass 2.

The #2700 fixture (`spine_fixes_test.go:dualStackLease`) passed one
identical identity string (`cid:01:02:03`) for both families — a
shape `identity6` cannot produce — so the existing test exercised a
condition that never occurs in production and gave false assurance.

## Fix

`sendAddOwned` (`pkg/ddns/backend_rfc2136.go`) now takes a sibling
branch when the manager threads `SiblingFamilyOwned` (stamped by
`upsertLocked` from `crossTypeSiblingOwned`, the #14604 store scan —
same canonical FQDN, opposite family, no ClientID equality required).
The branch adds this family's forward RR + its OWN per-family DHCID
under a per-type `RRsetNotUsed` prerequisite and leaves the sibling's
records untouched. Each family's delete already replays its own
publishing identity, so teardown removes only its own A/AAAA + its
own DHCID; the identical-identity case still shares one DHCID and the
`dhcidSharedWithOther`/`KeepForwardDHCID` keep-alive is unchanged.

Coordination with #14604 (merged first, `164f51d63`): #14604 changed
skip-existing/strict-fail to a name-level `NameNotUsed` guard with
exactly this sibling bypass for the cross-family publish. This change
extends the same manager-store sibling proof to the default
replace-owned policy, which #14604 did not cover (its sibling branch
only existed on the skip/strict path). No #14604 test was weakened.

Guards preserved: a name with no manager-owned sibling keeps every
name-level/DHCID guard unchanged; the sibling branch itself refuses
(YX/NX) when its own type already exists at the name, so a foreign
same-type RRset is never adopted and no phantom ownership is recorded.
