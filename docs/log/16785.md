# Issue #16785: zoned DHCP/DHCPv6 unit with no routable address (incl. PD-only DHCPv6 WAN) keeps the #10751 early input barrier (policy DROP) up indefinitely while commits succeed and host-inbound reports Current (R3-A36-03)

## Why

At boot, `xpf-input-closed.service` installs `xpf_input_barrier`. The
first apply installed the real `xpf_hostinbound` successfully, then the
handoff re-sample found a zoned WAN with DHCP/DHCPv6 intent and no
global address and retained the barrier with only a WARN: the commit
returned OK and `HostInboundApplied().Current()` was true. For a
successful PD-only DHCPv6 WAN (`dhcpv6-client client-ia-type ia-pd`,
the common ISP shape) no WAN address ever arrives — the lease installs
no kernel address (`pkg/dhcp/commit.go` gates on `lease.Address`),
and the delegated prefix is consumed only for downstream RA — so
every later commit and every xpfd restart repeated the retention and
the prio-12 policy-DROP chain stayed in place indefinitely, dropping
every new host-bound connection on every non-lifeline data interface
(in-band SSH/ping, BGP/IKE/OSPF responders, DHCPv6 server, DNS/NTP)
while lifelines stayed admitted. The same strand hit any zoned
never-leasing unit (unplugged backup WAN, ISP that never answers).
There was no age or attempt bound on the hold, and nothing surfaced
"barrier retained" to the operator.

## What

- `pkg/config/types_interfaces.go`: `DHCPv6ClientConfig.DHCPv6ExpectsAddress()`
  / `InterfaceUnit.UnitDHCPv6ExpectsAddress()` — the single source for
  "this DHCPv6 client can install a routable address on its own unit".
  PD-only (`ia-pd` without `ia-na`) and stateless clients return false;
  bare `dhcpv6;`, no explicit IA types (runtime defaults to IA_NA),
  `ia-na`, and `ia-na`+`ia-pd` return true.
- `pkg/dataplane/userspace/zones_observability.go`: the per-interface
  pending predicate and the zone-level DHCP-intent map now count only
  address-expecting DHCPv6 intent. A PD-only/stateless unit beside only
  its automatic link-local is no longer pending (its installed
  link-local deny already covers everything reachable). Exported
  `AddresslessEnforcing{Interfaces,Zones}FromSnapshots` for callers
  already holding a snapshot.
- `pkg/dataplane/userspace/zones_host_inbound.go`: the v6 interface
  backstop (zoned, unzoned-pending, and unzoned-VRF builders) is
  scoped to address-expecting clients. Without this a PD-only unit's
  `#11577` backstop (`iifname <dev> fib daddr type local drop`, no
  destination scoping, no dhcpv6 admit for it) would blanket-drop its
  link-local host traffic forever after handoff.
- `pkg/daemon/input_barrier_gate_10751.go`: bounded pre-handoff hold.
  `earlyInputPendingHandoffBound` (5m from the FIRST retention;
  repeated applies cannot extend it) plus per-daemon retention state
  (`earlyInputHandoffPendingSince`/detail, wall-clock seam for tests)
  and `hostInboundPendingDetail` rendering the holding scopes.
- `pkg/daemon/daemon_nft.go`: all three handoff sites (real install,
  fenced fallback, no-enforcement teardown) record the retention with
  `barrier_retained`/`pending`/`handoff_bound_expired` log fields and,
  once the bound expires, hand off anyway — the #11577 per-interface
  backstop installed with the render plus the lease-triggered
  re-apply cover the pending unit (the post-handoff steady state the
  design already accepts). Successful handoff clears the hold.
- `pkg/daemon/host_inbound_gap_retry_11497.go`: the always-on 30s
  retry loop also re-drives an apply when a pending hold has expired,
  so the bound fires without a commit or a lease.
- Surfacing: `HostInboundAppliedState.BarrierRetained` +
  `BarrierPendingDetail` (daemon), mirrored through
  `grpcapi.HostInboundApplied`, `api.HostInboundAppliedSnapshot`, and
  `api.HostInboundAppliedInfo` (`barrier_retained` /
  `barrier_pending_detail` JSON); `show security zones` renders a
  "Host-inbound barrier: RETAINED (…; pending: …)" line. Retention no
  longer reads as plain Current with no trace.
- `docs/host-inbound-service-matrix.md`: PD-only/stateless non-pending
  rule, the 5-minute bound, and the retained surfacing documented.

Neighbours preserved: within the bound the barrier is retained exactly
as before (`TestEarlyInputPendingIntentAllBranches10751` green — a
lease landing within the bound still hands off only after re-render);
PD-only unzoned behaviour unchanged (already non-pending); the #11577
backstop for address-expecting clients (ia-na, mixed, bare) unchanged.

## Risk

Fail-open direction is bounded and deliberate: after 5 minutes a
still-pending unit's NEW addresses are covered only by the #11577
per-interface backstop until the lease-triggered re-apply renders
destination rules — the same window already accepted post-handoff.
Within the bound nothing changes. A PD-only unit loses a v6 backstop
that only ever dropped its own link-local host traffic; its
destination-scoped link-local deny remains. Lab check not executed:
on a node with a zoned `dhcpv6-client client-ia-type ia-pd` WAN,
reboot, confirm `nft list table inet xpf_input_barrier` is absent
after the first apply and ssh/ping to a LAN-zone address that permits
them succeeds.
