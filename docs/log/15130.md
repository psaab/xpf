## Why

`validateVRFOverlap` source 2 iterated every `FiltersInet`/`FiltersInet6`
filter and counted its `then routing-instance` terms: `sawPBRRoutingInstance`
plus the steered prefixes. No attachment check existed (only the #13098
dead-term `srcNone || dstNone` skip). The PBR rule builder has installed
steering only for interface-unit INPUT attachments since #3430, so a dormant
filter manufactured the #7924 strict refusal **and** the #7991 tolerant
admission for steering that never happens.

Concrete victim: `docs/ha-cluster-userspace.conf:132` binds `sfmix-pbr` on
`reth1.0`; `test/incus/fbf-two-upstream-config.set:42-43` rebinds `reth1.0`
input to `fbf-steer`/`fbf-steer6`, leaving `sfmix-pbr` unattached. Its term
steers `10.255.192.40/30` into `sfmix`, whose member `gr-0/0/0.0` carries
`10.255.192.42/30` — so the documented base + FBF overlay
(`make test-fbf-steering`) could not commit.

Severity: a false commit refusal (workaround: delete the dormant term) and a
dead on-wire FBF smoke; no enforcement loss. The fix direction is
fail-closed-preserving: attached steering still refuses exactly as before.

## What

- `validateVRFOverlap`: build an attachment census from the compiled
  `FilterInputV4`/`FilterInputV6` bindings over all interface units, and
  process only census-listed filters in source 2 (per family). This is the
  same compiled state the builder's `collectAttachedInputFilters`
  (`pkg/routing/rules.go`) walks, so the detector and the builder now agree
  on which filters steer. Dormant and output-only filters set neither
  `sawPBRRoutingInstance` nor steered prefixes.
- Attachment shapes that therefore count, unchanged: direct `filter input`
  bindings; apply-groups / `groups ${node}` attachments (plain bindings on
  the compiled config — pinned by `TestVRFOverlapGroupAttachedPBRCounts_15130`);
  #11321/#11589 FBF-member clones (bound under their clone name before the
  tail gate runs, so they are census-listed; on the strict path such shapes
  are refused earlier by the #11321 gate anyway). lo0-unit input attachments
  count, as the builder walks them too (it drops their kernel rules loudly;
  the userspace override still steers).
- Re-pointed pre-existing fixtures whose filters were unattached and only
  ever intended "a live PBR term exists": each now attaches its filter as an
  input filter on a scratch default-instance interface (assertions
  unchanged). The direct-`validateVRFOverlap` budget/primary-claim fixtures
  attach via `FilterInputV4` on synthetic units. The bare-member fixture
  attaches on a non-member interface (attaching on the RI-B member itself
  trips the unrelated #11321 strict gate).
- NOT changed: source 1 (native membership), the pairing rules, the
  warning/error text, the lenient downgrade, `TolerantVRFOverlapAdmissions`
  plumbing, and the builder. No behaviour change for any attached filter.

## Risk

- A config that today commits *because* its only steering filter is dormant
  and overlaps natively will now commit with the plain warning instead of
  being refused — that is the fix, not a regression: no traffic was ever
  steered by that filter.
- The census reads compiled bindings at tail-gate time; any future pass
  that rebinds input filters after `runTailGates` would need the same
  post-quarantine-style refresh the detector already does for RI membership
  (#13098). None exists today.
