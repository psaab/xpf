# #15154 (B14-01): reseed queue_vtime on vacate re-entry, not only at construction

## Defect

The #4254 frontier reseed ran only at `FlowFairState` construction
(`promote_cos_queue_flow_fair` in `userspace-dp/src/afxdp/cos/admission.rs`).
A worker whose last bucket drained vacated its V_min slot
(`account_cos_queue_flow_dequeue` in `queue_ops/accounting.rs`, #941 A) but
kept its frozen `queue_vtime`. On re-entry the new bucket re-anchored at
`max(tail, queue_vtime)` with that stale value, and the worker's first
post-settle publish (`publish_committed_queue_vtime` in
`queue_ops/v_min.rs`) broadcast it. On a shared_exact (multi-worker exact)
queue that stale-low value becomes the cross-worker V_min, so busy peers
that kept serving fail the V_min gate (`cos_queue_v_min_continue`), burn
the hard-cap, and arm suspension — ordinary idle/return traffic inverts
the fairness brake.

## Fix

In `account_cos_queue_flow_enqueue` (`queue_ops/accounting.rs`), before
the bucket anchor is computed: if this is the first enqueue into an empty
shared_exact queue (`active_flow_buckets == 0`) whose own slot is
`NOT_PARTICIPATING`, set
`ff.queue_vtime = max(ff.queue_vtime, floor.peer_frontier_vtime(worker_id))`
when a participating peer frontier exists. The frontier is captured
before the `flow_fair_state` borrow (peer Acquire loads, own slot
excluded, same helper as the construction reseed). Max semantics keep an
ahead re-entrant ahead and leave the value unchanged when no peer
participates. Nothing is published on enqueue — the slot stays
`NOT_PARTICIPATING` until the first post-settle publish (#940), which now
broadcasts the reseeded value. A genuine laggard never takes this path
(its slot is participating, and `peer_frontier_vtime` excludes self), so
`vmin_r7_seeded_rejoiner_still_defers_to_genuine_laggard` is unaffected.

NOT changed: the construction reseed, the vacate, publish-on-commit only,
the V_min gate/thresholds, and non-shared queues (no `vtime_floor`, and
the explicit `shared_exact()` + own-slot checks gate the reseed).

## Regression

New cells in `queue_ops/v_min_tests/vacate.rs`:

- `v42_b14_vacate_reentry_traps_survivor` — a vacated worker 1 with frozen
  `queue_vtime = 42_424` re-enters while worker 0 participates at
  ~100 GiB. Asserts the reseed to the frontier on the first enqueue, no
  first-enqueue publish, the post-settle publish broadcasting the
  frontier, and the survivor's V_min gate continuing with zero throttles.
  RED on `origin/master` (queue_vtime stays 42_424), GREEN after the fix.
- `v42_b14_vacate_reentry_max_and_no_peer_controls` — an ahead re-entrant
  keeps its higher vtime (max, not pulled down); re-entry with no
  participating peer keeps the frozen value.

Neighbour controls (named in the issue) stay green:
`vmin_r7_seeded_rejoiner_still_defers_to_genuine_laggard`,
`vmin_r7_rejoiner_*`, `vmin_vacate_*`,
`vmin_publish_after_settle_keeps_vacated_slot_empty`,
`vmin_no_first_enqueue_publish`.

## Risk

Only the first enqueue into an empty shared_exact queue by a
non-participating worker can move `queue_vtime`, and only upward to a
real participating peer's committed frontier — the same value the
construction reseed would have used. Cold start / sole worker (no
participating peer) is byte-identical to before. No publish timing,
gate, or threshold changes.
