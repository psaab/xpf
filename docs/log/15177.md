# #15177 — deterministic CGNAT capacity gate counted other-family pool members

- **Issue**: #15177 (C05-01)
- **Branch**: `fix/15177-campaign`
- **Base**: `51e002a3c7` (worktree branched from origin/master at lane start)

## Defect

`validateSourceNATDeterministicStrict` summed `sourceNATPoolMemberHostCount`
over every pool member with no family filter. A v6 `/112` contributed 65536
hosts (saturating), so a pool with one usable IPv4 address (63 blocks at
block-size 1024) plus a v6 member committed clean for a `/20` IPv4 subscriber
(4096). Rust builds `deterministic_v4` only from `pool_addresses_v4`, so
subscribers past the first 63 got `AllocatorExhausted` at runtime. The same
all-family count fed `deterministicPoolBlockCapacity` in `pkg/api`.

## Fix

- `pkg/config/nat_pool_capacity.go`: `SourceNATPoolDeterministicV4AddressCount`
  — mode 1: textual-v4 unique-expanded union (colon-bearing members, including
  IPv4-mapped, are v6 per `expand_pool_address`); mode 2 (IPv6 subscriber /
  NAT64): only bare or `/32` v4 hosts, once per member, matching
  `parse_pool_v4` (no dedupe, no prefix expansion).
- `pkg/config/compiler_validate_strict_nat.go`: the deterministic gate uses
  that count for both subscriber families.
- `pkg/api/metrics_nat.go`: `deterministicPoolBlockCapacity` uses the same
  count (and the fixed NAT64 range for mode-2 block math), keeping the
  `SourceNATPoolReportableAddresses` unusable check.
- `docs/deterministic-nat-cgnat.md`: capacity description updated.

## Tests

- `pkg/config/deterministic_capacity_family_15177_test.go`: +v6 `/112` and
  +v4-mapped cells reject with `insufficient capacity (63 blocks)`, v4 `/25`

- `pkg/api/metrics_det_pool_family_15177_test.go`: mixed pool = 63 blocks;

- Existing #9498 deterministic capacity tests stay green.
