# Issue #14407 — Same VIP claimed by two independent VRRP elections on one interface

Two `vrrp-group`s on one interface unit carrying the same VIP (or an explicit
group whose VIP equals a RETH unit address) committed cleanly. Each group is
an independent election — the manager keys instances by (interface, VRID,
family), never by VIP, and each master independently installs its VIPs. With
per-group, per-node track divergence (node A's `ge-0/0/1` down, node B's
`ge-0/0/2` down), group 1 elects B while group 2 elects A: both nodes
becomeMaster for the same VIP, both install it, both emit GARP/NA —
dual-master duplicate-IP, ARP flapping, split/blackholed traffic.

## Change

- `pkg/config/compiler_validate_strict_vrrp_vipcrossgroup.go` (new):
  `validateVRRPVIPCrossGroupStrict` builds a canonical host-IP →
  group-identity map per resolved kernel interface + family across (a) all
  explicit `vrrp-group`s on a unit and (b) RETH-derived instances (unit
  addresses, VRID 100+RG) when RETH VRRP synthesis is active. A second
  distinct VRID claiming the same VIP hard-rejects naming the VIP and both
  groups. Canonicalization reuses `vrrpVIPHostIP` (bare and CIDR spellings
  collide). Same-VRID claims are not two elections and are left to the
  manager's duplicate-identity guards. RETH scope mirrors
  `CollectRethInstances` (VLAN-tagged = per-unit sub-interface, untagged =
  combined base instance; skipped under `no-reth-vrrp` /
  `private-rg-election`).
- `pkg/config/compiler_uniformgates_cluster_zone.go`: dispatch the gate;
  `pkg/config/compiler_opts.go`: `lenientVRRPVIPCrossGroup` downgrades it to
  a warning on tolerant load / peer-sync paths (#1960 no-brick), enabled in
  the lenient opts set.
- `pkg/vrrp/manager.go`: runtime backstop in `UpdateInstances`. A canonical
  VIP → first-claimant map (interface + per-VIP family + host identity)
  refuses/skips the second distinct claimant via the existing
  `rejectedDesired` pattern (retains any running instance for that key,
  records the refusal in `unbuiltDesired`), so a leniently-loaded duplicate
  seats only one election. First claimant in desired order wins.
- `pkg/config/README.md`: documented the gate alongside the #6779/#11482
  VRRP VIP gates.

NOT changed: same VIP on different units/interfaces stays legal; different
VIPs on one unit stay legal; within-group dedupe (`dedupeVRRPVIPs` /
`dedupeVIPs`) unchanged; RETH synthesis-off means the explicit-vs-RETH arm
is inapplicable.

## Regression

- `TestVRRPCrossGroupSameVIPFailsCommit`: the issue fixture (group 1
  tracking `ge-0/0/1`, group 2 tracking `ge-0/0/2`, same VIP
  `10.0.0.100/24`) fails commit naming the VIP and both groups.
- `TestVRRPCrossGroupSameVIPAliasSpellingFailsCommit`: bare vs CIDR
  spellings of the same host collide.
- `TestVRRPCrossGroupDifferentInterfacesCommits`: same VIP on two different
  interfaces and on two different units still commits.
- `TestVRRPCrossGroupDifferentVIPsCommits`: two groups with different VIPs
  on one unit still commit.
- `TestVRRPCrossGroupLenientWarns`: lenient compile succeeds and warns
  naming the VIP.
- `TestVRRPCrossGroupExplicitVsRethFailsCommit`: explicit-vs-RETH overlap
  rejected when synthesis is active; not rejected under private RG election.
- `TestUpdateInstances_RefusesSecondVIPClaimant14407`: `UpdateInstances`
  refuses the second claimant, keeps the first, records the refusal.
- `TestUpdateInstances_DifferentVIPsBothSeated14407` /
  `TestUpdateInstances_SameVIPDifferentInterfacesBothSeated14407`: runtime
  controls seat both elections.

## Risk

- Operators with two groups sharing one VIP on a unit (previously silently
  accepted) must give each group a distinct VIP or merge the groups; strict
  commit now rejects, lenient load warns and seats only the first election.
