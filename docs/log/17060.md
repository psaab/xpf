## Fix

- `clearFabricSlots` (`daemon_ha_fabric.go`): zeroes both slots (iface,
  overlay, peer IP/MAC, populated), probe and failure-log rate limits,
  queued-probe flags, and drops each old peer's helper identity constraint
  (`RegisterFabricPeerMACConstraint(peer, nil)`, deduplicated when both
  slots share a peer). Constraints are the only post-lock work; the MAC
  hint state itself is cleared under `fabricMu`.
- `stopClusterComms` calls it under `clusterCommsMu`, alongside the
  channel nilling and AFTER cancel + `clusterCommsWG.Wait()`. It is
  deliberately not earlier: a populate loop still perched between its
  pre-probe ctx check and its config store at cancel time may re-store
  between cancel and clear — the clear must be the last writer.
- Fold (Rev18312Opus B1–B3, head `aa4cad5268`): the populate loops are
  now tracked on a dedicated `fabricPopulateWG` — `Add(1)` on the
  launcher's stack in `startFabricForwardingLoops` before each `go`
  statement, `Done` deferred in each loop — and `stopClusterComms`
  joins it (`fabricPopulateWG.Wait()`, outside `clusterCommsMu`, after
  the constructor join) BEFORE `clearFabricSlots`, so an in-flight
  `refreshFabricPeer` cannot latch `fabric{,1}Populated` after the
  clear (B1) and a not-yet-scheduled loop cannot store its config
  after it (B2; the loops also re-check `ctx.Err()` under `fabricMu`
  before storing). `clearFabricSlots` bumps `fabricEpoch` under
  `fabricMu`, and `rememberFabricPeerMAC` re-checks that epoch (and
  the current peer) under `fabricMu` before publishing a non-nil
  constraint, so a pre-clear reader cannot re-arm the constraint the
  clear dropped (B3). `monitorFabricState` is deliberately untracked:
  it only pokes channels and never writes slot state. The false
  "drained by that same cancel / cannot resurrect" comments were
  corrected. `refreshFabricPeer` also skips `SyncFabricState` when
  its epoch ctx is already cancelled after the latch.
- `RefreshFabricFwd` is now `queueFabricProbe()` + the existing
  non-blocking `triggerFabricRefresh()` poke. The per-slot 2s
  rate-limited probe is queued (`fabricProbePending{,1}`) and executed
  by the epoch-owned populate loop on wake, with the epoch ctx, before
  its refresh — so the probe-then-refresh order, probe target
  (`overlayOrParent`), rate limit, and coalescing are preserved, but
  nothing runs on `context.Background()` or outside an epoch. With
  comms stopped the channels are nil and the poke is a no-op.
- The three `go d.RefreshFabricFwd()` sites call it directly (it never
  blocks, so fire-and-forget goroutines are now pure waste).

Failover behaviour preserved: populate loops, the 30s safety-net
ticker, `monitorFabricState`/`triggerFabricRefresh`, readiness gating,
retain-on-neighbour-miss, identity recording, fab1 handling, and the
#7072 `activeClusterTransport` non-clear are all untouched.

## Risk

- Fail-closed direction: a fabric event arriving while comms are
  mid-restart now no-ops instead of refreshing stale state; the new
  epoch's populate loop does its immediate fast-retry pass, so no
  refresh is lost beyond the restart window that already cancelled
  the loops.
- A probe queued just before a stop is dropped with the slot (flags
  cleared); the next epoch re-probes on its own schedule.
- Fold risk: `stopClusterComms` now also waits for populate loops to
  observe cancellation. A loop parked in a blocking resolver/netlink
  call delays teardown until that call returns (same class as the
  existing constructor join); the loops' fast-retry path checks
  `ctx.Err()` before every probe, so the wait is bounded by one
  in-flight refresh.
