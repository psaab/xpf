# 9411 — `forwarding-options dhcp-relay dhcpv6` committed clean and was discarded (or worse)

- **Timestamp**: 2026-09-10
- **Issue**: #9411
- **Base commit**: `3b24fe26e`; rebased before push

## Channels

The issue asked that the channel be named, because "commits clean" is a different
statement on each. Every pre-fix row below was measured on all four:
`config.SchemaValidate`, `config.CompileConfig`, `config.CompileConfigLenient`,
`configstore.CheckText`.

## The issue body's premise was too mild

Filed as "commits clean and is **discarded** entirely". Measured at the pristine
base, that holds for the braced, bare-leaf and flat-set spellings, but not for the
elided one:

```
dhcp-relay { dhcpv6 { … } }                              ACCEPT x4   0 server-groups, 0 groups
dhcp-relay dhcpv6 { group g6 { … } }                     ACCEPT x4   v4-groups=[g6]
dhcp-relay dhcpv6 { g6 }  THEN  dhcp-relay { isp; g1 }   ACCEPT x4   server-groups=0 v4-groups=[g6]
dhcp-relay { isp; g1 }    THEN  dhcp-relay dhcpv6 { g6 } ACCEPT x4   1 server-group, v4-groups=[g1]
CONTROL v4 relay                                         ACCEPT x4   1 server-group, 1 group
CONTROL dhcp-relay { xpfbogus { … } }                    ACCEPT x4   0, 0
```

The elided spelling puts `dhcpv6` on the relay node's own Keys, so `group g6` is a
direct child of a node named `dhcp-relay`, and `compileForwardingOptions` took
`FindChild("dhcp-relay")`. A DHCPv6 relay group was installed **as a DHCPv4 relay**
on the interface the operator named for DHCPv6, and when that block came first the
operator's **real DHCPv4 relay was never compiled**. That is operator-reachable:
`configstore.CheckText` accepted all of it.

This was found by my own test, not by reading. The first draft of the gate claimed
the tolerant downgrade was safe "because the stanza already compiles to nothing",
and the refusal cell's tolerant-path relay count came back `0 / 1` instead of
`0 / 0`. The test was right; the claim — and the compiler — were wrong.

## AST shapes, measured before writing the gate

```
dhcp-relay { dhcpv6 { … } }              child node,  Keys=["dhcpv6"]
dhcp-relay { dhcpv6; }                   child leaf,  Keys=["dhcpv6"]
set … dhcp-relay dhcpv6 group …          child leaf,  Keys=["dhcpv6","group",…]
dhcp-relay dhcpv6 { … }                  the relay node's OWN Keys[1]
forwarding-options dhcp-relay dhcpv6 …;  forwarding-options' OWN Keys[1:3]
```

**Those are PARSER shapes. The gate sees four of them**, and that was found by the
mutation matrix, not predicted from reading: removing the forwarding-options-Keys
clause SURVIVED every end-to-end cell, while removing the relay-node Keys[1] check
also reddened the fully-elided row. The brace-elision normalizer folds that spelling
into the relay-node shape before `runPreWalkGates`. The clause is kept (the
normalizer is under active change, #8690 / #8876) and made exercisable by
`TestDHCPRelayDHCPv6GateSeesTheRawElidedShape9411`, which drives the gate on the
raw parser tree.

## Remedy

1. `validateDHCPRelayDHCPv6AST` — compiler pre-walk gate (beside #9017 / #9323),
   strict refuse, tolerant warn (`opts.lenientDHCPRelayDHCPv6`, #1960). On the AST
   because the stanza compiles to nothing.
2. `dhcpRelayV4Node9411` — `compileForwardingOptions` reads the first `dhcp-relay`
   node that is not the dhcpv6 spelling, which is what makes the tolerant downgrade
   inert rather than a warning in front of a mis-compile.

**Position, not membership.** A DHCPv4 relay `group` or `server-group` NAMED
`dhcpv6` must still commit; a token search anywhere would refuse it.

## Reach, measured after the gate existed

- injected via `apply-groups` → refused (pre-walk runs on the expanded tree)
- `inactive: dhcpv6` → accepted (pruned before the gate; inert by design)
