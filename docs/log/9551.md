# #9551 — refuse a negated close keyword on the commit path and the PR-body path

## 2026-09-10 — Action: re-verified the defect and the enforcement points at base
- **File(s)**: none (reading)
- The issue's last word is its body; there are no comments. It asks for three
  things: a predicate over GitHub's real grammar with the source cited, a
  refusal in negated or scoping context, and the safe spellings named at the
  point of refusal. It must run on BOTH the commit path and the PR-body path.
- GitHub's documented grammar (docs.github.com, "Linking a pull request to an
  issue using a keyword"):
  - nine keywords, used as `KEYWORD #N` or `KEYWORD OWNER/REPO#N`;
  - a colon and uppercase are allowed;
  - each issue needs its own full syntax;
  - keywords are honoured in the body of a PR targeting the default branch, and
    in a commit message once it is merged there.
- Shapes measured in-repo (`docs/engineering-style.md`): emphasis inside the
  phrase does not break it, and a heading plus a blank line plus `#N` still
  closes.
- Where it can run. There is no CI directory, and `core.hooksPath` points at the
  shared primary clone's hooks dir, which contains only samples. The repo is
  PUBLIC and Actions are ENABLED; master is NOT branch-protected.
  - A `pull_request` workflow is the one place that sees both incident shapes
    (a PR body, and a commit message inside a PR) without anyone installing
    anything.
  - A red check does not block `gh pr merge` while master is unprotected.
    Requiring it is a repository setting, not something this change can make.

## Human step: workflow wiring (needs workflow scope)
Post this exact file as `.github/workflows/close-keyword-lint.yml` after the
repository owner grants the required scope:

```yaml
# close-keyword-lint.yml (#9551): refuse a NEGATED GitHub close keyword on every
# pull request, at a point nobody can forget.
#
# GitHub's close-keyword parser does not read negation: a PR body or commit
# message saying an issue stays open closes it at merge when a close verb
# stands in front of the number. It wrongly closed #9016 (via a PR-body scope
# heading) and #9412 (via a commit message) on one day.
#
# Both legs live in scripts/close_keyword_lint_ci.sh -- the PR body and every
# commit message in the PR's base..head range -- which this job calls with the
# body passed through `env`, never interpolated into a command line, so a PR
# body cannot inject shell. The selftest and the campaign landing pipeline
# call the same script, so there is exactly one grammar, not three.
#
# `edited` is load-bearing in the trigger list: without it a PR body edited
# after opening -- the #9016 shape -- would never re-run this check.
# `fetch-depth: 0` is load-bearing too: the commit-message leg needs the full
# base..head range.
name: close-keyword-lint

on:
  pull_request:
    types: [opened, edited, synchronize, reopened]

jobs:
  lint:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Refuse a negated close keyword
        env:
          PR_BODY: ${{ github.event.pull_request.body }}
          PR_NUMBER: ${{ github.event.pull_request.number }}
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
        run: bash scripts/close_keyword_lint_ci.sh
```

- The owner must post the file with a token carrying `workflow` scope. Until
  then, `make selftest` is the enforced merge gate for commit messages and
  the commit-msg hook remains available for local commits; no PR-body CI
  claim is made.
