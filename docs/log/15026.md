# 15026 — IPsec `proposal-set standard` carries group-2 PFS (g2-esp-*)

## Summary

The predefined IPsec proposal-set `standard` expanded to ESP members
with no Diffie-Hellman group (`dhGroup 0`), rendering bare
`esp_proposals = 3des-sha1,aes128-sha1`. Junos defines `standard` as
the group-2 PFS set (g2-esp-3des / g2-esp-aes128). The tunnel
established initially, but a Junos peer's PFS child-SA rekey — which
proposes the DH group — was refused `NO_PROPOSAL_CHOSEN` until hard
expiry, and the configured set silently lacked the PFS its shorthand
promises.

`basic` and `compatible` are correctly no-PFS and are unchanged; the
IKE (Phase-1) `standard` set already carried DH group 2 and is
unchanged. A policy-level `perfect-forward-secrecy keys <group>` still
overrides the proposal group at render (`buildESPProposal` prefers
`pfsGroup > 0`), so operators who pinned a different PFS group keep
exactly that behaviour.

## Fix

`pkg/config/compiler_ipsec_proposalset.go` only:

- `espProposalSets["standard"]` members now carry `dhGroup 2`
  (`3des-cbc`/`hmac-sha1-96` and `aes-128-cbc`/`hmac-sha1-96`), so
  `buildESPProposal` renders `3des-sha1-modp1024` /
  `aes128-sha1-modp1024`.
- The table comment now records that `standard` is the group-2 PFS
  set and that `basic`/`compatible` carry no PFS (the previous comment
  claimed all legacy sets carry no PFS).

No renderer, schema, or other proposal-set changes.

## Risk

Only configs using `security ipsec policy <p> proposal-set standard`
change rendered output: their child SAs gain the group-2 PFS term
Junos peers already expect. Interop with a non-PFS peer that strictly
rejects a DH-bearing ESP proposal could in principle change, but that
is the Junos-defined meaning of `standard`; operators wanting no PFS
use `basic`/`compatible` or explicit proposals, all unchanged. Lab
acceptance (run7.sh rekeys against the PFS peer) remains an
operator-side verify; the render contract is pinned by the regression
tests above.
