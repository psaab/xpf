# Issue #14603 — TSIG-signed RFC 2136 UPDATE accepted an unsigned response

- **Timestamp**: 2026-10-16
  - **Action**: Closed the residual #4483 forged-rcode gap for
    TSIG-configured deployments (`Y13-03`). `exchange()` in
    `pkg/ddns/backend_rfc2136.go` signed the UPDATE when a TSIG key was
    configured but accepted ANY reply miekg returned without error —
    and miekg/dns v1.1.72 only verifies a MAC when the reply happens to
    carry a TSIG RR (`client.go` ReadMsg: verify `if IsTsig()!=nil`,
    no else), so a forged UNSIGNED reply's rcode set the verdict: a
    forged NOERROR recorded a phantom publish/delete as settled, a
    forged YXDOMAIN/YXRRSET counted a phantom conflict and suppressed
    publishing, and a forged NOTAUTH on the PTR could be counted as a
    permanent skip. Docs (`pkg/ddns/README.md`, `docs/config-schema.md`)
    promised the opposite ("fully closed by configuring tsig-key").
    `exchange()` now validates every response through the new
    `validateTSIGResponse` when `tsigKeyName != ""`, on BOTH the UDP
    leg and the TCP truncation-retry leg: the reply MUST carry a TSIG
    RR whose key name and algorithm match the configured values
    (canonical, case-insensitive); an unsigned, wrong-key, or
    wrong-algorithm reply is a transport error that never reaches the
    rcode verdict, so no ownership is recorded/dropped and no conflict
    or PTR-skip is counted. A signed reply with a bad MAC already
    failed inside miekg and still does. A truncated TSIG exchange via
    a non-`*dns.Client` exchanger (which cannot retry over TCP) now
    fails closed instead of returning an unverifiable verdict. The
    no-TSIG posture is unchanged (warned, #4483). The false doc claim
    is corrected in `pkg/ddns/README.md` and `docs/config-schema.md`,
    and the two commit-time warning comments in
    `pkg/config/compiler_validate_warn_ddns.go` now state the real
    mechanism. Regression tests in `backend_rfc2136_test.go` extend
    the in-process miekg fake with forgery controls (unsigned reply,
    wrong key/algorithm/secret, TCP-only unsigned) and drive the real
    `*dns.Client` over UDP/TCP loopback: unsigned replies of every
    rcode (NOERROR/YXDOMAIN/YXRRSET/NXRRSET/NOTAUTH/REFUSED/SERVFAIL)
    to both UpsertLease and DeleteLease error as transport errors with
    zero conflict counts; wrong-key/wrong-algorithm/wrong-secret
    replies error without leaking a secret; the signed same-key
    control succeeds and a signed REFUSED still surfaces as its rcode
    verdict. `TestExchangeTSIGValidation` pins the validator's
    case-insensitive key/algorithm pins and the truncated-stub fail-
    closed branch directly.
  - **File(s)**: pkg/ddns/backend_rfc2136.go,
    pkg/ddns/backend_rfc2136_test.go, pkg/ddns/README.md,
    docs/config-schema.md, pkg/config/compiler_validate_warn_ddns.go,
    docs/log/14603.md

## Risk

- Behaviour delta: a TSIG-configured deployment whose authoritative
  server (or middlebox) strips TSIG from UPDATE responses will now
  see transport errors and retry instead of accepting verdicts — that
  is the intended fail-closed posture; such a server was never
  actually authenticating replies. Properly TSIG-signing servers
  (BIND, Knot, the in-process miekg fake) are unaffected.
- RED-evidence caveat: `TestExchangeTSIGValidation` calls the new
  validator, so with the production file reverted the test package
  does not compile; the RED run therefore temporarily excluded that
  one unit test (restored verbatim for GREEN). The decisive wire
  tests compile and fail on base without that exclusion.
- Note: during the RED check a careless `git stash pop` in this
  worktree briefly pulled in a foreign stash's `pkg/config` changes;
  they were identified by `git status` and fully restored to HEAD
  before any further work — the final diff touches only the files
  listed above (verified by `git -C <worktree> status --short`).
- NOT changed: the no-TSIG warned posture (#4483), the DHCID
  ownership guards, PTR-skip classification for AUTHENTICATED
  replies, and any other DDNS backend (dyndns2/cloudflare/etc. do not
  use `exchange`).
