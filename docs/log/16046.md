# #16046 — fsatomic preserve lifts 0644 wholesale; frr.conf secrets stay world-readable

## Defect

`fsatomic.WithPreserveExisting` lifted the existing file mode wholesale
(`mode = fi.Mode().Perm()`), replacing the caller-requested perm. The FRR
writer requests 0640 for `frr.conf` (which carries BGP TCP-MD5 / OSPF /
IS-IS keys, #4484) but always passes `WithPreserveExisting`, so a legacy
0644 `frr.conf` stayed 0644 after every managed apply and routing keys
remained world-readable to any local account. Preserving owner/group is
legitimate (operator ownership must not be overridden); widening mode
past the caller perm is not.

## Service identity (established for the fold)

Debian `frr` package: `/usr/lib/frr/frrcommon.sh` sets
`FRR_USER=frr`, `FRR_GROUP=frr`, `FRR_VTY_GROUP=frrvty`,
`FRR_CONFIG_MODE=0640`; the `frr` account is `uid=978(frr)
gid=978(frr) groups=978(frr),979(frrvty)` and daemons drop to
`frr:frr` (xpfd/`vtysh`/`frr-reload.py` run as root). Stock
`/etc/frr/frr.conf` is `root:root 0644`. Fresh xpf writes land
`root:frr 0640`; preserved-existing files historically kept the
operator group — commonly `root` — so a bare cap `0644 & 0640 = 0640
root:root` would deny the frr reader (Codex fold, valid).

## Fix

In `pkg/fsatomic` `writeFile`, cap the preserved mode at the caller's
perm: `mode = fi.Mode().Perm() & perm`. Preserve can keep a stricter
mode (0600 under a 0640 request stays 0600) but never installs a mode
wider than the caller asked for (0644 & 0640 = 0640). Ownership
preservation is unchanged in fsatomic. `WithPreserveExisting` is called
in production only by `pkg/frr`'s `atomicWriteFile`, so the tightening
is scoped to `frr.conf` writes on the normal apply and zeroize-strip
paths.

In `pkg/frr`, tightening stays service-readable:

- `atomicWriteOwnerOpt(path, perm)`: on an existing wider-than-perm
  file whose group is not the frr gid, when the frr group resolves
  (root), return `WithOwner(existing-uid, frr-gid)` — migrate only the
  group, keep the operator uid — so the capped 0640 file is
  group-readable by the service.
- `preserveFloorPerm`: when the frr group cannot be resolved
  (non-root / FRR absent), pass the existing mode as perm so
  `existing & perm` is unchanged — floor at 0644 until a root apply can
  migrate and tighten safely, rather than stranding FRR.

Docs (`fsatomic.go`, READMEs, `docs/engineering-style.md`, FRR manager
comments) updated to state the capped-mode + migration contract.

## Validation

- `TestPreserveExistingNeverWidensBeyondCallerPerm` (fsatomic): seeded
  0644/0600/0640/0777 rows under narrower perms; wider rows capped,
  stricter kept. RED on revert (0644 and 0777 rows fail).
- `TestFRRConfLegacy0644TightenedTo0640` (frr): seed 0644 with the
  service group as preserved group → lands 0640. RED on revert.
- `TestFRRConfRootRoot0644MigratesToServiceGroup` (frr, fold cell,
  root-only): legacy 0644 with a non-service group → 0640 with gid
  migrated to the injected frr gid, uid preserved, service-readable
  predicate true; with the group unresolvable → floored at 0644 and
  still service-readable. Run under `sudo go test` (non-root runs skip
  the chown cell; decision logic is covered non-root by
  `TestAtomicWriteOwnerOptDecision`, extended with wide/migration and
  wide/absent arms).
- Existing `TestPreserveExistingMode`, `TestFRRConfPreservesOperatorMode`
  (0600 kept), fresh-create 0640, and owner-opt decision tests still pass.

## Risk

Only caller is `frr.conf`. Tightening 0644→0640 now either keeps a
service group, migrates the group to `frr` (uid preserved), or does not
tighten yet (floor) — never lands a 0640 file the `frr:frr` daemons
cannot read. An operator who deliberately chose a mode wider than
0640 loses the extra bits on the next root apply — intended, since the
managed section carries secrets the operator did not author. Group
migration changes group ownership of an existing operator file only
in the tightening case (wider than 0640, non-service group); uid and
stricter files are untouched.
