# #16046 — fsatomic preserve lifts 0644 wholesale; frr.conf secrets stay world-readable

## Defect

`fsatomic.WithPreserveExisting` lifted the existing file mode wholesale
(`mode = fi.Mode().Perm()`), replacing the caller-requested perm. The FRR
writer requests 0640 for `frr.conf` (which carries BGP TCP-MD5 / OSPF /
IS-IS keys, #4484) but always passes `WithPreserveExisting`, so a legacy
0644 `frr.conf` stayed 0644 after every managed apply and routing keys
remained world-readable to any local account. Preserving owner/group is
legitimate (operator ownership must not be overridden); widening mode
past the caller perm is not.

## Service identity (established for the fold)

Debian `frr` package: `/usr/lib/frr/frrcommon.sh` sets
`FRR_USER=frr`, `FRR_GROUP=frr`, `FRR_VTY_GROUP=frrvty`,
`FRR_CONFIG_MODE=0640`; the `frr` account is `uid=978(frr)
gid=978(frr) groups=978(frr),979(frrvty)` and daemons drop to
`frr:frr` (xpfd/`vtysh`/`frr-reload.py` run as root). Stock
`/etc/frr/frr.conf` is `root:root 0644`. Fresh xpf writes land
`root:frr 0640`; preserved-existing files historically kept the
operator group — commonly `root` — so a bare cap `0644 & 0640 = 0640
root:root` would deny the frr reader (Codex fold, valid).

## Fix

In `pkg/fsatomic` `writeFile`, cap the preserved mode at the caller's
perm: `mode = fi.Mode().Perm() & perm`. Preserve can keep a stricter
mode (0600 under a 0640 request stays 0600) but never installs a mode
wider than the caller asked for (0644 & 0640 = 0640). Ownership
preservation is unchanged in fsatomic. `WithPreserveExisting` is called
in production only by `pkg/frr`'s `atomicWriteFile`, so the tightening
is scoped to `frr.conf` writes on the normal apply and zeroize-strip
paths.

In `pkg/frr`, one decision function — `planFRRWrite` (one `os.Stat` +
one `resolveFRRGroup` per write, carried in a single plan; fold-2
claim 4) — guarantees every SUCCESSFUL write is (a) ⊆ 0640 bitwise and
(b) keeps the reader the service principal had via owner/group/other,
or fails before publication with the old inode untouched:

- Fresh: exactly 0640 (clarifying fold-2 claim 1: fresh writes never
  used the floor; they always passed 0640 explicitly).
- Existing ⊆ 0640: pure preserve.
- Wider + group resolved: cap; migrate only the group to the frr gid
  (uid preserved) when needed; grant group-read when the cap lost it
  (e.g. `0604` other-read-only → `0640`, fold-2 claim 3; result still
  ⊆ 0640).
- Wider + group unresolvable or not installable by this process:
  ERROR, old inode untouched (fold-2 claims 1+2: the fold-1 floor
  published new secrets world-readable; deleted).

`pkg/frr`/`pkg/daemon`/`pkg/grpcapi` test binaries default the resolver
to the process egid (`TestMain` / `SetFRRGroupResolverForTest`) so
seeded-0644 fixtures tighten by pure preserve without root.

Docs (`fsatomic.go`, READMEs, `docs/engineering-style.md`, FRR manager
comments) updated to state the capped-mode + single-decision contract.

## Validation

- `TestPreserveExistingNeverWidensBeyondCallerPerm` (fsatomic): seeded
  0644/0600/0640/0777 rows under narrower perms; wider rows capped,
  stricter kept. RED on revert (0644 and 0777 rows fail).
- `TestFRRConfLegacy0644TightenedTo0640` (frr): seed 0644 with the
  service group as preserved group → lands 0640. RED on revert.
- `TestFRRConfRootRoot0644MigratesToServiceGroup` (root-only): 0644 →
  0640 gid=frr uid preserved; unresolved → error + old inode untouched.
- `TestFRRWritePlanDecision`: the full single-plan table incl. exactly
  one resolver call per plan and fail-closed foreign-gid rows.
- `TestFRRConfOtherReadOnlyKeepsServiceReader`: 0604 → 0640 readable.
- `TestFRRConfResolverFlipConsistent`: both resolver-flip directions
  via `writeManagedSection` (one lookup; success-first migrates,
  failure-first fails closed). The reviewer's three hostile scratch
  tests were also run against this head: world-only + success-first
  PASS; reverse-flip "fails" only its implicit success assumption
  (write now correctly errors, old inode kept).
- `TestStripManagedSectionMode16046`: zeroize resolved/unresolved/
  marker-less rows.
- Full `pkg/frr` suite: failure set identical to parent head (4
  pre-existing vtysh-dependent BGP tests); fsatomic canary failures
  pre-existing on `origin/master`.

## Risk

Only caller is `frr.conf` (apply + zeroize strip). A wider operator
file now tightens safely, migrates its group, gains group-read, or the
write fails closed — an unresolved-group host sees apply errors (old
config retained, reload not advanced) rather than insecure or
unreadable publication; this is the deliberate availability cost of
the secrecy invariant, and on a packaged appliance (root, `frr`
package installed) resolution succeeds. Group migration touches group
ownership only in the tightening case; uid and stricter files are
untouched.
