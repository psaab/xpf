# #18635 — Count lost HA event-stream session deltas

## Why

The HA session-sync idle predicate compared sent/received create counters, pending deltas, and the RPC-fallback `Session delta dropped` counter. It could not see a non-bulk session delta that failed the helper's lossless event-stream enqueue, so the wait could report idle after losing session state.

## What

- Added per-kind Open/Close/Update loss counters to `EventStreamShared` and `EventStreamStats`. The common lossless session-delta enqueue boundary increments them on failure, excluding bulk-resync and `CommandExport` deltas. This includes the worker flush and direct lossless producers without counting a flush failure twice; the existing generic dropped-frame counter and out-of-sync latch remain separate.
- Tunnel-remap purge counts the unattempted Close suffix after its first failed enqueue, without double-counting that failed delta; the same bulk/CommandExport filter applies.
- Projected the counters through Rust `ProcessStatus`, its JSON wire fixture, the Go status adapter, and a distinct overview line: `Event stream HA session delta lost: <total> (open=<n> close=<n> update=<n>)`. The line is present even when the optional `EventStream` block is absent, but only when all three counters were present in helper JSON.
- Go tracks each additive counter as an optional `*uint64`: a current helper serializes zero explicitly; an older helper omits the keys, and formatting omits the loss line so shell idle evidence is VOID. This key-presence compatibility requires no protocol-version bump.
- Stamped deltas from the actual `snapshot_all_sessions_export` FullResync producer as bulk at creation; `SessionDelta::from_shared` defaults are incremental, so the counter's existing bulk filter alone would otherwise misclassify peer-connect export loss. A producer-level failed-enqueue test asserts counters remain `(0,0,0)`.
- Extended `ha_session_sync_idle_sample` with the source event-stream-lost total baseline. It fails closed on missing/malformed evidence, treats counter rewind as re-baselining, and rejects any increase. Both wait loops require distinct manager-published helper status sequence values for their stable samples and one further publication for final confirmation, preventing cached CLI reads from proving idle.
- Added loss and status-freshness mutant/control cells to `ha-assurance-selftest.sh`, updated its legacy/current status fixtures, and documented the presence and freshness behavior in `docs/userspace-ha-validation.md`.

## Design decisions

The loss counter is incremented at `push_delta_lossless_within_seq`, rather than only in `flush_session_deltas`: tunnel-purge and other direct lossless producers can also lose non-bulk session deltas, and counting at the common failure boundary covers them. The helper filters bulk-resync and `CommandExport`; the flush's bulk generic-drop accounting remains independent. The AllSessionsExport producer stamps full-resync deltas `bulk_resync=true` because `from_shared` defaults are not provenance. The Go presence-aware fields avoid a status protocol bump: old helper keys are absent, not zero, and do not produce the formatted loss line. The manager's status publication sequence is a separate Go-owned freshness fence; it increments only when a helper response is recorded.

## Risk

The helper loss counters are additive/defaulted and require no status protocol-version bump: an older helper that omits them yields VOID, not a false zero. The Go manager stamps a separate publication sequence; the wait requires one extra fresh publication after the stable streak, adding at least one status-poll interval and failing closed if the cache stops updating. Counters count failed lossless enqueue attempts, not RT_FLOW producer drops or silently coalesced/skipped deltas. The existing counter-based idle predicate retains its already documented in-flight/background-create blind spots.
