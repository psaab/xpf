# #18635 — Count lost HA event-stream session deltas

## Why

The HA session-sync idle predicate compared sent/received create counters, pending deltas, and the RPC-fallback `Session delta dropped` counter. It could not see a non-bulk session delta that failed the helper's lossless event-stream enqueue, so the wait could report idle after losing session state.

## What

- Added per-kind Open/Close/Update loss counters to `EventStreamShared` and `EventStreamStats`. The common lossless session-delta enqueue boundary increments them on failure, excluding bulk-resync and `CommandExport` deltas. This includes the worker flush and direct lossless producers without counting a flush failure twice; the existing generic dropped-frame counter and out-of-sync latch remain separate.
- Tunnel-remap purge counts the unattempted Close suffix after its first failed enqueue, without double-counting that failed delta; the same bulk/CommandExport filter applies.
- Projected the counters and helper measurement sequence through Rust `ProcessStatus`, its JSON wire fixture, the Go status adapter, and status output. `Event stream HA session delta lost: <total> (open=<n> close=<n> update=<n>)` appears only when all three counter keys are present; `Helper status measurement sequence: <n>` appears only when the helper supplied its projection epoch.
- Go tracks each event-stream loss counter and the helper measurement sequence as optional `*uint64`: a current helper serializes zero/its sequence explicitly, and the normal status formatter omits the loss line when any counter key is absent. The separate loss-since probe requires all three counter keys plus valid helper identity/stamp; an older helper's unsupported request, absent result, or missing fields makes the shell idle verdict VOID. No status protocol-version bump is required.
- Stamped deltas from the actual `snapshot_all_sessions_export` FullResync producer as bulk at creation; `SessionDelta::from_shared` defaults are incremental, so the counter's existing bulk filter alone would otherwise misclassify peer-connect export loss. A producer-level failed-enqueue test asserts counters remain `(0,0,0)`.
- Replaced cached event-loss sampling with a helper-evaluated since-baseline probe. The wait-start token binds helper PID, start time, measurement sequence, and all three loss counters; both wait loops ask the source helper for a fresh loss-since answer on each sample and again after the paired stable window. `ha_session_sync_idle_sample` rejects any positive helper answer, and a missing/malformed answer or identity/stamp/counter rewind is VOID, never a silent event-loss rebaseline. Both loops also require fresh source AND target helper measurement sequences for every counted sample and final confirmation; Go's manager publication sequence is bookkeeping only.
- The Rust `status` handler projects status and evaluates `lost_since` against the supplied token while answering the dedicated control request. Go's manager probe sends a new direct control-socket request with status-cache publication suppressed, so stale status responses and all cache-only publishers (including `ClearFilterCounters`, `manager_compile`, policy/filter counter publishers, and maps-sync publication) cannot answer the gate. The Go status loop's additional second status read remains a publication safeguard, but the idle gate trusts only the helper's direct since-answer. Added tests for helper identity/rewind rejection, ordinary projections 41/42 held in cache, and a confirmation request held before the helper answer while loss lands; the fresh 43 answer reports `lost_since=1`. Both shell loops have positive-since/final-confirmation failure paths.

## Design decisions

The loss counters are incremented at the common `push_delta_lossless_within_seq` failure boundary, rather than only in `flush_session_deltas`: tunnel-purge and other direct lossless producers can also lose non-bulk session deltas, and counting there covers them without double-counting flush failures. The helper filters bulk-resync and `CommandExport`; the flush's generic bulk-drop accounting remains independent. `AllSessionsExport` explicitly stamps its full-resync deltas `bulk_resync=true` because `SessionDelta::from_shared` defaults to incremental. Go's optional counter and helper-measurement fields distinguish unknown from zero without a status protocol-version bump.

Shape B was chosen for the idle gate: the baseline is an opaque token containing PID, `StartedAt`, helper measurement stamp, and the three monotonic per-kind counters; the helper computes the counter differences inside the request-answer path, with checked arithmetic. The loss-since query uses a new direct helper round trip and never reads/publishes through the Go status cache. The final query is issued after the stable wait window, so the proof is as fresh as that confirmation round trip itself; loss after the helper answers is outside that proof. A PID/start-time mismatch, stamp rewind, or counter rewind is invalid evidence and VOIDs the wait rather than silently establishing a new baseline. Since the gate trusts only this direct helper answer, cache-only publishers such as `ClearFilterCounters`, `manager_compile`, `policycounters`, `filtercounters_clear`, and `maps_sync` are irrelevant to loss proof. Shell helper measurement stamps are compared as decimal strings (normalized length then C-locale lexical order), not Bash signed arithmetic.

The fixture-completeness check caught a branch-red Go-only `helper_status_observation_sequence` key and a missing Rust `helper_status_measurement_sequence` in `protocol_wire_v1.json`; the former is explicitly allowlisted as Go manager bookkeeping, and the latter was regenerated from the Rust specimen. The gRPC current-helper fixture supplies explicit loss pointers and measurement/observation sequences, preserving the distinct loss line. The Rust census scanner currently skips some fields whose declaration follows a `pub` comment; this is a follow-up observation for Main to file, not fixed here.

## Risk

The helper loss counters and measurement sequence are additive and require no status protocol-version bump: new Go with an old helper sees absent counters/epoch and the idle predicate is VOID; old Go ignores the new fields and has neither loss nor helper-freshness gating, so mixed-version operation does not provide this assurance. `HelperStatusObservationSequence` is manager cache/publication bookkeeping only. For helpers reporting any loss key, each Go status poll performs one additional full status round trip and publishes only the second response, requiring its helper measurement sequence to advance; a failed/partial/non-advancing refresh or PID change publishes no stale status, at the cost of one extra status RPC per poll. Both wait loops require fresh source AND target helper measurements for stable samples and final confirmation, so stale target received/pending/drained values or cache-only Go publications cannot certify idle. Counters count failed lossless enqueue attempts, not RT_FLOW producer drops or silently coalesced/skipped deltas. The existing counter-based idle predicate retains its already documented in-flight/background-create blind spots.
