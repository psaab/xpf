# #18635 — Count lost HA event-stream session deltas

## Why

The HA session-sync idle predicate compared sent/received create counters, pending deltas, and the RPC-fallback `Session delta dropped` counter. It could not see a non-bulk session delta that failed the helper's lossless event-stream enqueue, so the wait could report idle after losing session state.

## What

- Added per-kind Open/Close/Update loss counters to `EventStreamShared` and `EventStreamStats`. The common lossless session-delta enqueue boundary increments them on failure, excluding bulk-resync and `CommandExport` deltas. This includes the worker flush and direct lossless producers without counting a flush failure twice; the existing generic dropped-frame counter and out-of-sync latch remain separate.
- Tunnel-remap purge counts the unattempted Close suffix after its first failed enqueue, without double-counting that failed delta; the same bulk/CommandExport filter applies.
- Projected the counters through Rust `ProcessStatus`, its JSON wire fixture, the Go status adapter, and a distinct overview line: `Event stream HA session delta lost: <total> (open=<n> close=<n> update=<n>)`. The line is present even when the optional `EventStream` block is absent, but only when all three counters were present in helper JSON.
- Go tracks each additive counter as an optional `*uint64`: a current helper serializes zero explicitly; an older helper omits the keys, and formatting omits the loss line so shell idle evidence is VOID. This key-presence compatibility requires no protocol-version bump.
- Stamped deltas from the actual `snapshot_all_sessions_export` FullResync producer as bulk at creation; `SessionDelta::from_shared` defaults are incremental, so the counter's existing bulk filter alone would otherwise misclassify peer-connect export loss. A producer-level failed-enqueue test asserts counters remain `(0,0,0)`.
- Extended `ha_session_sync_idle_sample` with the source event-stream-lost total baseline. It fails closed on missing/malformed evidence, treats counter rewind as re-baselining, and rejects any increase. Both wait loops now require fresh source AND target helper-status observation sequences for every counted sample and final confirmation. When a helper advertises the loss counters, Go reads status a second time after the initial RPC response and publishes only that second status; refresh errors/missing counters fail closed, preventing a pre-loss Rust projection from acquiring a fresh Go publication sequence.
- Added loss, held-projection/second-read, target-stale/source-fresh, and two-endpoint status-freshness control/mutant cells to `ha-assurance-selftest.sh`, updated its legacy/current status fixtures, and documented presence, compatibility, and paired freshness behavior in `docs/userspace-ha-validation.md`. Go status-loop tests pin the held projected-zero → increment → second-read-one → publication order and fail closed on a failed confirmation read.

## Design decisions

The loss counter is incremented at `push_delta_lossless_within_seq`, rather than only in `flush_session_deltas`: tunnel-purge and other direct lossless producers can also lose non-bulk session deltas, and counting at the common failure boundary covers them. The helper filters bulk-resync and `CommandExport`; the flush's bulk generic-drop accounting remains independent. The AllSessionsExport producer stamps full-resync deltas `bulk_resync=true` because `from_shared` defaults are not provenance. The Go presence-aware fields avoid a status protocol bump: old helper keys are absent, not zero, and do not produce the formatted loss line. The manager's status publication sequence is a Go-owned cache/publication counter, not a measurement epoch. Therefore, when the first response advertises any loss counter key, statusLoop performs another helper status read after the first response returns and publishes that second full status; missing counters, a failed read, or a helper PID change fail closed instead of publishing the pre-captured status. New Go with old helper: all counters remain absent and the idle predicate is VOID. Old Go with new helper: unknown JSON keys are ignored and the old wait has no loss-counter gate, so mixed-version operation does not provide the new assurance. Per-node source and target sequence checks prevent stale received/pending/drained target data as well as stale source loss/sent data from satisfying the wait.

## Risk

The helper loss counters are additive/defaulted and require no status protocol-version bump: a current helper reports zero explicitly; new Go with an old helper sees absent keys and the idle predicate is VOID, while old Go ignores the new keys and retains no loss gate (mixed-version operation does not provide the new assurance). The manager-owned observation sequence is a cache/publication counter, not a helper measurement epoch. For helpers reporting any loss key, each Go status poll performs one additional full status round trip and publishes only that second response; a failed/partial refresh or PID change publishes no stale status, at the cost of one extra status RPC per poll. Both wait loops require fresh source AND target sequences for the stable samples and the final confirmation, so stale target received/pending/drained values cannot certify idle. Counters count failed lossless enqueue attempts, not RT_FLOW producer drops or silently coalesced/skipped deltas. The existing counter-based idle predicate retains its already documented in-flight/background-create blind spots.
