# #15008 Multi-member community renders as ANY instead of ALL (A11-02) — engineering history

Issue: psaab/xpf#15008 (`frr: fix — policy-options community X members
[ a b ] renders one bgp community-list ... permit line per member, so
from community X… (A11-02)`). Source claim `A11-02`
(claude-opus-5-5-review), validator run `research-work.AdQvt1jMKw`,
consensus MATERIAL (3-way). Lane branch: `fix/15008-campaign`, base
`origin/master` 0ab128349b.

## Defect (present at base)

`generatePolicyOptionsWithRefNodes14380` (`pkg/frr/policy_render.go`)
emitted one `bgp community-list <kind> <name> permit <member>` line per
member of a `policy-options community` definition. Junos semantics
(Junos routing-policy community evaluation docs): "The evaluation of
all members must be successful for the named community evaluation to
be successful" — a route must carry a community matching EVERY member.
FRR semantics (bgpd `community_list_match`, `bgpd/bgp_clist.c` stable
10.6): entries are walked in order and the FIRST permit entry whose
community set is contained in the route decides — so any ONE member
matched the whole list. Every multi-member `from community X` was
widened from ALL to ANY: an accept term over-accepts on import, a
reject term over-rejects, and non-terminal actions hit the wrong routes.

## Fix

In `pkg/frr/policy_render.go`, the public community name now renders as
ONE permit entry whose value is the conjunction:

- **All-literal (`standard`)**: all members space-joined on one line
  (`bgp community-list standard X permit 65000:100 65000:200`). FRR
  parses the value with `community_str2com` into a set and
  `community_match` requires every value in the entry to be present in
  the route — exact AND. Member order is preserved (FRR sorts the set,
  so matching is order-independent). Single-member output is
  byte-identical to before; duplicate members collapse (to the
  single-member render when all equal).
- **Any-regex (`expanded`)**: one entry whose pattern is a conjunction
  of positive lookaheads over the joined, numerically sorted community
  string FRR matches expanded entries against (`community_str`).
  A literal member is first anchored to a whole token
  `(^| )member( |$)`, so `65000:100` cannot match by substring inside
  `65000:1000` or split across a boundary (`1:2` inside the adjacent
  tokens `65000:1 2:3`), then wrapped as `(?=.*factor)`; a regex member
  is wrapped directly, preserving the documented unanchored single-regex
  semantics (#2643). Factors are joined with `.*` and the pattern ends
  with `.*` so FRR's unanchored `regexec` has a consuming match.
  Caveats (documented in code + README): members with backreferences or
  an embedded `(?=` can interact with the wrapping, and author-written
  `^`/`$` keep whole-string meaning, which can be stricter than Junos's
  per-value evaluation for anchored multi-member regexes.

`then community delete <name>` cannot reuse the AND entry: FRR's
`community_list_match_delete` strips a route value only when ONE permit
entry matches that single value, so an AND entry would strip nothing.
Delete therefore targets a generated per-member backing
(`<frrName>-xpf-del-<64-bit digest of the raw name>`,
`communityDeleteListName`) whose entries are the separate per-member
permit lines; the backing is emitted for every rendered multi-member
definition so definition and reference cannot drift. Single-member,
empty, and unrenderable definitions keep the historical delete target.

`communityListCollision` (new, wired into `Manager.ApplyFull` beside
`routeFilterACLNameCollision`) fails the apply closed when rendered
lists would fuse in FRR's flat community-list namespace: two operator
names normalizing to one FRR name, an operator name forging a generated
backing, or two backings colliding. The `#8449` unrenderable belt and
`communityListMissingAtRender` now share `communityListKind` /
`communityListRenderable` / `dedupStrings` with the emitter so they
cannot drift.

Existing tests updated for the changed render shape (same behaviour
assertions, new spelling): `TestGeneratePolicyOptionsCommunityListAndMetricType`
and `TestGeneratePolicyOptionsCommunityExpandedVsStandard` in
`pkg/frr/frr_test.go` (the latter's standard-line shape check now
accepts the joined multi-value AND line). Docs: this file plus a
`pkg/frr/README.md` bullet. No pkg/config change: member validity gates
are unchanged.

NOT changed: `invert-match` (never modelled in xpf — no compiler
support exists to invert), resolved `then community add/set`
literals (#12069 path; they are values, not list membership), and the
tolerant-path dangling delete for unrenderable definitions (stays as
before, out of scope).

## Risk

- Behaviour delta is the fix itself: multi-member `from community`
  terms now match strictly fewer routes (ALL instead of ANY); a route
  previously accepted on one member alone will now fall through.
  Operators relying on the widened behaviour see the Junos-correct
  outcome. Single-member configs are byte-identical.
- Render delta: new `<name>-xpf-del-<digest>` community-lists appear in
  frr.conf for multi-member definitions, and delete clauses for those
  names point at the backing (operator-visible in `show` output).
  A collision with an operator name fails the apply closed instead of
  silently merging lists.
- Residual: the anchored-regex-member caveat above (whole-string `^`/`$`
  in a multi-member regex definition can be stricter than Junos
  per-value matching). Bounded to multi-member definitions containing
  anchored regex members; single regex members are unchanged.
