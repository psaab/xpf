# Key fairness flow throughput by counter owner, not wire tuple (#13091)

- **Issue**: #13091 (research finding D8-04, deep-review source report
  `gemini-4-argon-high-review-performance-cos-fairness-100e100m-and-code-quality-modularity-001.md`,
  three-way research-validated). Go telemetry path:
  `pkg/dataplane/userspace/fairness_throughput.go`.
- **Cause**: `Coordinator::flow_worker_map`
  (`userspace-dp/src/afxdp/coordinator/status.rs`) concatenates the
  per-binding flow-cache snapshots without deduplicating
  `(egress_ifindex, cos_queue_id, forward_wire_key)`, so the same wire
  tuple is reported by several bindings (RSS re-steer, multi-queue
  ingress, hairpin) as independent `ObservedBytes` counters. But
  `FairnessThroughputWindow.Update` keyed `fairnessFlowThroughputKey` on
  `(queue, tuple)` only — omitting the row's `Slot`/`WorkerID` — so the
  duplicate rows overwrote `w.prev[key]` in place within a single
  Update. With static counters `a >= prev` then `b < prev`, the smaller
  row re-derived a bogus counter-reset delta every scrape: a completely
  idle flow pair fabricated `min(a,b) + |a-b|` phantom bytes per scrape
  forever (1_000/scrape for 1_000/500 counters), polluting
  `ObservedBytes`, `ObservedBPS`, per-worker `bytesByWorker`, and the
  `EqualFlowEstimate` model behind the fairness Prometheus gauges.
- **Change**: `fairnessFlowThroughputKey` gains `worker` + `slot`
  fields, and `Update` builds the key from `row.WorkerID`/`row.Slot`.
  The key now identifies one `ObservedBytes` counter (the owning
  binding's flow-cache entry), not one wire tuple, so each row's delta
  is measured against its own prior scrape value. Semantics otherwise
  unchanged: per-flow attribution follows the counter (matching
  `cos_active_flow_counts`, which also counts a tuple per binding), the
  counter-reset branch still covers genuine counter resets (eviction +
  reseed), and the truncation fail-closed reset
  (`FlowWorkerMapTruncated` → `resetWindowState`) is untouched.
- **Regression coverage**
  (`pkg/dataplane/userspace/fairness_throughput_test.go`):
  `TestFairnessThroughputWindowDuplicateTupleAcrossBindingsAddsNoPhantomBytes`
  — two bindings (Slot 0/Worker 0, Slot 1/Worker 1) report the same
  `(EgressIfindex, CoSQueueID, ForwardWireKey)` with counters 1_000 and
  500. Two completely static scrapes must produce no summary (zero
  packet progress ⇒ zero added bytes), then real progress (2_000 and
  1_500) must add exactly 2_000 bytes across 2 flows — each counter's
  own delta once, no reset-branch inflation.
- **GREEN evidence**: With the fix, the new test passes;
  `go test ./pkg/dataplane/userspace/ -count=1` is 2355 passed with the
  single failure `TestSnapshotShapeIsPinnedToProtocolVersion8892`, which
  fails identically on pristine origin/master (base-attributed,
  unrelated: config-snapshot wire-shape digest).
  `pkg/dataplane/userspace/format` and `pkg/api` are ok. `go vet` clean
  on the touched package. (Two `snapshot_catchup_incarnation_8597`
  failures seen under a long `GOTMPDIR` are unix-socket path-length
  artifacts; both pass with a default temp dir.)
- **Blast radius / risk**: Telemetry-only — no scheduler or dataplane
  path reads the window; the sole consumer is the fairness metrics
  collector (`pkg/api/metrics_userspace_fairness.go`), which sees
  corrected (smaller) byte/BPS gauges for multi-binding duplicate
  tuples. A tuple served by N bindings now counts as N flows in
  `FlowCount`/CoV, consistent with `CoSActiveFlowCounts` (also
  per-binding). Residual (out of scope, no evidence it occurs): two
  distinct sessions inside ONE binding mapping to the same forward wire
  key would still share a key (NAT pools with overlapping ranges);
  `flow_worker_map_snapshot` rows are unique per cache entry otherwise.
