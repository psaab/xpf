# #13135 — keep host-deny zone ownership on the owning ingress device

- **Source**: deep-review finding D2-03, validated by three-way adversarial research.
- **Files**: `pkg/config/junos_host_deny.go`,
  `pkg/config/junos_host_vrf_trunk_13135_test.go`.

## Why

A non-VRF tagged VLAN unit could claim the physical base merely because its
unit-0 sibling was enslaved to a VRF. Coverage then treated the tagged zone as
a second owner of the VRF master and withdrew the legitimate zone's
`to-zone junos-host` deny program. Non-zero tunnel units could similarly claim
a distinct base device.

## What

Only allow a unit ref to claim the base when its own resolved Linux ingress
name is the base device. Do not use a VRF-enslaved physical parent as a
conservative candidate for another tagged unit. Added regression coverage for
the mixed VRF/unit-0 plus tagged-VLAN case, including preserved deny
representability, and for a distinct non-zero tunnel unit.

## Validation

- RED on pristine `origin/master`: the D2-03 VRF trunk regression failed with
  `base must belong to unit-0 owner trust, got "dmz"`.
- Focused regressions:
  `go test ./pkg/config -run 'TestJunosHost(TaggedUnitDoesNotStealVRFBase|TunnelUnitDoesNotClaimBase)13135' -count=1`: GREEN.
- Full package test: `go test ./pkg/config -count=1 -timeout 30m`: GREEN
  (`874.687s`).
- Repository build: `go build ./...`: GREEN.

## Risk

Base ownership is intentionally more conservative for distinct unit devices;
explicit bare-interface ownership and same-device unit-0 ownership remain
unchanged.
