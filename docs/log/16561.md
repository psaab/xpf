# Issue #16561: wire-owner roster off above 16,384 distinct wire keys (R3-A71-03)

## Why

#15106 added the per-wire-key owner roster (`wire_owners` in
`SharedNatAmbiguityIndex`) so NAT'd forward removal resolves survivors
in O(1) instead of scanning `shared_sessions` under its mutex. But the
roster shared the alias index's 16,384 bound and latched
`wire_saturated`: `observe_wire_owner` set the latch from the alias
`saturated()` arm or when `wire_owners` reached `MAX_KEYS`, and only
`clear()` (via a full stop) reset it. So at 16,384+ live NAT'd forwards
with DISTINCT wire keys — the exact 100k-row regime #15106 targeted —
and forever after one such excursion, every NAT'd removal fell back to
the O(table) scan under the global mutex (research probe: 21.5us fresh
vs 19.8ms after one 16,385-session excursion at 100k rows). The
`shared_wire_ambiguity_saturated` gauge read `saturated()` only, so it
reported 0 while the fallback persisted. The #15106 cost probe pinned
`rewrite_src_port 50_000` for every row (one wire key), so it never
exercised the defect.

## What

- `types/mod.rs`: the `wire_saturated: bool` latch is deleted. The
  roster is decoupled from the alias cap: new `MAX_WIRE_KEYS`
  (16 x 131,072, the shared-session ceiling order) bounds DISTINCT
  wire keys, and `wire_saturated()` is a live function of
  `wire_owners.len() >= wire_key_cap()` — removals recover trust with
  no latch, reseed or restart (#15104 rule for the same struct).
  `observe_wire_owner` no longer consults alias saturation; it refuses
  only a NEW wire key at the live roster ceiling. New
  `wire_roster_trusted_for_removal()` keys removal-path trust to the
  roster's own live state, so a saturated alias index no longer forces
  the O(table) fallback (the alias bound still governs uniqueness
  proofs via `wire_owners_trusted`/`is_unique_for` — no fail-open
  change). A `#[cfg(test)] WIRE_KEY_CAP_OVERRIDE` seam lets cells
  exercise the live ceiling without 2M sessions.
- `shared_ops/store.rs` + new `shared_ops/counters.rs`:
  `remove_shared_session_if` trusts the roster via
  `wire_roster_trusted_for_removal`; every legacy fallback scan bumps
  the new `SHARED_WIRE_FALLBACK_SCANS` counter.
- Gauge/counter end to end: `Coordinator::shared_wire_ambiguity_saturated`
  now reads live `saturated() || wire_saturated()`;
  `shared_wire_fallback_scans_total` -> Rust `ProcessStatus` (additive,
  `default`) -> Go `ProcessStatus` -> Prometheus
  `xpf_userspace_shared_wire_fallback_scans_total`.
  `protocol_wire_v1.json` regenerated (also picks up pre-existing
  drift: `flow_cache_evictions_by_arm`, `fwd/rev_packets`,
  `session_gc_expired`, `snat_revoked_sessions_total` key ordering).
- Tests: `wire_roster_stays_trusted_above_alias_bound_16561` (16,385
  live distinct-wire-key SNAT forwards through the real
  publish/remove path; roster records all, removal uses O(1) path,
  fallback counter does not move) and
  `wire_roster_live_ceiling_fails_closed_and_recovers_16561` (seam cap
  4: at-ceiling fails closed, drops below recover, later removal stays
  O(1)). The #15106 release probe now uses distinct translated ports
  (`1024 + index % 60_000`) so its 100k leg has distinct wire keys.

NOT changed: alias 16,384 bound and its fail-closed uniqueness
semantics, roster survivor verdicts (0/1/2+), the legacy scan as
fallback for unrecorded keys (still reseeds, still fail-closed).

## Risk

- Roster memory grows with distinct live wire keys up to the session
  ceiling instead of 16,384: bounded by live forwards (one key per
  NAT'd forward, SmallVec inline 2), same order as `shared_sessions`
  itself. `clear()` still resets it.
- At the (unreachable-in-practice) roster ceiling the roster fails
  closed exactly as before, but now recovers on removal and is
  counted/gauged.
- Lab verify still outstanding: appliance throughput under >16k
  concurrent NAT'd forwards (component ratio only, per issue).
