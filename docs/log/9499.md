## Member 1: overflow as an executed oracle

`make test-rust` ran tests only with `--release`, where `overflow-checks` is off, so a wrap failed a test only if the test asserted the exact wrapped value.

### Measurements (worktree `fix/9499-rust-overflow-miri-gates`, based on `fbc51cc02`)

  - A first attempt with `RUSTFLAGS="-C overflow-checks=on"` failed to link with `duplicate symbol: crc32`. `RUSTFLAGS` replaces `userspace-dp/.cargo/config.toml`'s `rustflags` and so drops its `--allow-multiple-definition` link argument. Use the profile variable, not `RUSTFLAGS`.
- **Debug-profile filtered leg** (`cargo test --bins --tests -- --test-threads=1 frame nat session checksum`): build 213 s cold, run 65 s, 2489 passed, 0 failed.

### The planted mutant

No deterministic test drove a sequence-number `wrapping_add` across `u32::MAX`; only a proptest strategy weights toward it. The new cell `reject_rst_v4_for_syn_at_seq_max_wraps_ack_to_zero_9499` sends a SYN with `seq = u32::MAX` into `build_reject_rst_frame` and asserts the RST `ack` wraps to 0.

The mutant is `parsed.seq.wrapping_add(seg_len)` changed to `parsed.seq + seg_len` in `afxdp/frame/tcp.rs`:

| run | result |
|---|---|
| A: `--release`, original | cell ok |
| B: `--release`, mutant | cell **ok**, because the unchecked `+` wraps to the same value |
| C: `--release` with overflow checks, mutant | cell **FAILED**, `attempt to add with overflow` |
| E: `--release` with overflow checks, original | cell ok |
| debug filtered leg, mutant | cell **FAILED**, `attempt to add with overflow` (2484 passed, 1 failed, 90 s incremental) |

The file was restored after each run and verified equal to HEAD.

### Choice of leg

A second `--release` build with overflow checks costs a full optimised compile on every fresh worktree. The debug-profile leg gives the same oracle for the named modules (the issue's first remedy option), with debug assertions on as well, for about 4.5 minutes cold. It is filtered to `frame nat session checksum` and carries a comment to widen the filter rather than drop the leg.

### Why a registry and not `cargo miri test` over the crate

Measured, not assumed (probe worktree at `16df7c8c7`):

| filter | result |
|---|---|
| `afxdp::types::cos::` | **12 passed, 0 failed**, 76 s, no unsupported operations |
| `afxdp::frame::` | **stopped after 1021 s** — 94 frame tests passed, then `unsupported operation: open not available when isolation is enabled` from a test that reads a file |
| `checksum::` | **no result line** under `-Zmiri-disable-isolation` — UNJUDGED, neither clean nor broken |

So Miri over this crate is neither fast nor uniformly clean. The honest shape is
a named subset with a floor per module, plus a census that makes every module
OUTSIDE the subset say so in writing.

### The scoring is the gate, not the exit status

`cargo miri test -- <filter>` that matches NOTHING prints
`0 passed; … N filtered out` and **exits 0**. A leg that trusted the exit status
would report a clean run over a filter that matched nothing — which is the same
defect class #9499 is about. `scripts/miri-leg.sh` therefore judges the LOG, and
five distinct states are FAILURES rather than skips: no `test result:` line,
`0 passed`, a count below the registered floor, any `failed > 0`, and an
`unsupported operation` line (Miri refusing to execute is a VOID measurement,
and a VOID that scores clean is a coverage claim nobody made).

Isolation stays ON. A module needing `-Zmiri-disable-isolation` is reading files
in its tests, which makes it both a poor UB oracle and a slow one; it belongs in
`MIRI.unregistered` with that reason, not in the registry behind a weakened flag.

### What makes the subset unable to shrink in silence

A registry alone does not fix the finding, because a registry can shrink:
deleting its last line makes `make test-miri` **quieter**, not louder.
`scripts/miri-census.sh` is what inverts that. Every file under `userspace-dp`
that mentions Miri — a `cfg(not(miri))` exclusion or a prose claim — must be
either covered by a registered module or declared in `MIRI.unregistered` with a
one-line reason, so deleting a registry line reports every claim that line was
covering as undeclared and exits 1.

The census found one claim on its first run that a hand grep had missed: it is
case-insensitive, and `userspace-dp/src/xsk_ffi_tests.rs` writes `Miri`. That
file is the one that already had it right — it states that Miri **cannot** drive
it (the libxdp bridge is `extern "C"` FFI) and names the pins that stand in. It
is declared, not corrected.

### The four claims that were false about the world

Each of these described the tests' SHAPE accurately and asserted a run that did
not happen, which is the substance of #9499 — a reader takes them as a
protection that exists:

- `frame/mod.rs`: "the deterministic example tests keep miri coverage of the same fns"
- `frame/README.md` (twice): the same sentence, plus the `prop_tests/` table row
- `frame/prop_tests/inspect.rs`: "These also run under miri (no proptest loop)"
- `frame/tests_ttl_descriptor_dscp.rs`: "miri-coverable twin"

All four now name #9499 and state that no leg runs `afxdp::frame::`, with the
measured reason. `coverable` is kept where it was accurate and marked as *not*
`covered`.

### Self-test: both halves fail invisibly, so each defence is a mutation

A census whose claim matcher breaks reports a CLEAN BOARD; a leg whose scorer
breaks reports a clean run. `test/incus/miri-census-selftest.sh` asserts each
defence twice — an unmutated sandbox that must PASS, and a mutation that must
flip it — and a mutation that does not flip is an ESCAPE that fails the target.

Census cells (each against a sandbox repo built from scratch, never the real
worktree — a self-test that edits the tree it checks cannot tell its own mutant
from the author's uncommitted work):

| mutation | must report |
|---|---|
| registry line DELETED (**the issue's own bar**) | UNCOVERED and undeclared |
| registry EMPTIED | registers NO modules |
| registered module resolves to no file | resolves to no file |
| registry floor of `0` | not positive |
| registry entry with no reason | has no reason |
| declared path that IS covered (re-hiding) | IS covered by a registered module |
| declared path not in the tree | does not exist in the tree |
| NEW file mentioning Miri, undeclared | UNCOVERED and undeclared |
| declaration dropped for an existing claim | UNCOVERED and undeclared |
| positive control declared instead of covered | POSITIVE CONTROL |
| claim matcher broken (discovers nothing) | ZERO files |

Leg cells drive the REAL `scripts/miri-leg.sh` over a stub `cargo` replaying
fixture logs, so the parser under test is the shipped one rather than a second
copy of the same idea. Every fixture **exits 0**, which is what makes them the
interesting cases: healthy → pass; no result line → FAIL; `0 passed` → FAIL;
below floor → FAIL; `failed > 0` → FAIL; `unsupported operation` → FAIL.

Two real defects in my own census were found by these cells before landing, not
after: an empty registry produced a PHANTOM entry (the heredoc yields one blank
line, so the loop scored a floor of `''`), and the reason field was read with
`cut -d' ' -f3-`, which on a two-space column gap returns the FLOOR as the
reason — so a reason-less entry escaped its own check. Both are field-based now.

### The leg's first real run failed, and the failure was in the leg

Running `make test-miri` for the first time reported:

```
miri leg: afxdp::types::cos:: (floor 12)
  FAIL: afxdp::types::cos:::: 0 passed -- the filter matched nothing and Miri exited 0
```

The module was fine. **The scorer was wrong.** `--bins` runs each binary target
in turn, so the log carries one `test result:` line per binary:

```
Running unittests src/bin/fairness-eval.rs
test result: ok. 0 passed; 0 failed; … 63 filtered out; finished in 0.37s
Running unittests src/main.rs
test result: ok. 12 passed; 0 failed; … 5698 filtered out; finished in 46.28s
```

`grep -m1 '^test result:'` read `fairness-eval`'s line — a binary the filter was
never aimed at — and scored a clean 12-test run as "the filter matched nothing".

The same `-m1` is wrong in the **opposite** direction too, which is the half
that would have shipped silently: a FAILURE in a later binary sits behind an
earlier clean line and never reaches the verdict. One read of one line, two
opposite wrong answers.

Both faces are now pinned by multi-binary fixture cells, and the scorer sums
`passed` and `failed` across every result line. The self-test's fixtures were
all single-binary, so **no cell could see this** — it took running the leg for
real. That is the standing lesson about fixtures that are valid and carry no
signal, arriving in this change's own harness.
