# Issue #13498 — emit each VRF-overlap metric label set once

## Why

`TolerantVRFOverlapAdmissions` preserves distinct overlap findings by prefix
claim so warnings retain their origin information. A logical overlap can be
found more than once when one routing instance carries the same prefix both
natively and through PBR. The metric projects those findings onto
`(instance_a, instance_b, prefix)`, so they became duplicate samples with
identical Prometheus labels and pedantic Gather failed.

## What

- `collectVRFOverlapPBRAdmitted` now deduplicates findings by the metric's
  complete label tuple before emitting samples.
- The config detector and its warning/admission findings remain unchanged;
  no warning detail or detector counts are discarded.
- Audited `pkg/api` for other `xpf_vrf_overlap_*` metric families: this is the
  sole family/collector, with one descriptor and one Collect call site.

## Validation

- RED on pristine `origin/master` (`802eda508`):
  `go test ./pkg/api -run TestVRFOverlapAdmittedEmittedWhenDataplaneUnloaded_7991 -count=1`
  failed at pedantic Gather with duplicate `xpf_vrf_overlap_pbr_admitted`
  samples carrying the same `instance_a`, `instance_b`, and `prefix` labels.
- The target test passed after the fix, then failed again when the collector
  deduplication was reverted, with the same duplicate-label Gather error; it
  passed after restoring the fix.
- `go test ./pkg/api -run 'TestVRFOverlap' -count=1` passed.
- Full `go test ./pkg/api -count=1` passed (`ok ... 160.786s`).
- `gofmt -l pkg/api/metrics_counters.go` produced no output;
  `git diff --check` passed.

## Risk

Duplicate detector findings are now represented by one gauge sample, as
required by Prometheus label-set uniqueness. The underlying warning/admission
findings remain intact. No dataplane behavior changes.
