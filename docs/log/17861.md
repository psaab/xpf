# #17861: background kernel-truth drift loop cleared apply-owned maps and fence state without applySem — stale observation could wipe a freshly applied generation

- **Timestamp**: 2026-10-27
  - **Action**: `recheckHostKernelTruth15264` now acquires `applySem` (via `applyCancelCtx`) for its whole observe+clear pass — from before the first kernel read (`TableDropsInput` / `TableEnforcing`) until after the last retention clear — so the background 30s drift loop can no longer clear apply-owned state concurrently with, or interleaved inside, an apply's publication. Previously the loop wrote `hostInboundEnforced`, `hostInboundCoveredAddrs`, `hostInboundDHCPRetainedAddrs`, `hostInboundGapFenceSpec`, `hostInboundPreActivationFence`, `hostInboundGapFenceActive`, and `lo0Enforced` with no lock, although `daemon.go` documents applySem ownership for all of them and every other reader/writer (`applyHostInboundFilter`, the #5790 teardown, `applyLo0Filter`) holds applySem. A probe that had observed a flushed table could be preempted between its reads and its clears while a concurrent apply installed and published a fresh real generation; the resumed stale observation then wiped the fresh generation's retention state, so the NEXT failed apply replaced the valid retained table and its service accepts with the cold-boot deny-only fence and lost the retained gap/pre-activation fence bookkeeping. Deterministic RED/GREEN regression added (parks the recheck between kernel reads and clears, publishes a fresh generation under applySem, asserts the fresh retention state survives).
  - **File(s)**: `pkg/daemon/host_kernel_truth_15264.go` (recheck acquires applySem for the whole pass; file + function + loop comments), `pkg/daemon/daemon.go` (`hostInboundEnforced` contract comment: the recheck clears under applySem), `pkg/daemon/daemon_run.go` (loop idle-cost comment), `pkg/daemon/host_kernel_truth_15264_test.go` (new `TestKernelTruthDriftClearSparesConcurrentFreshApply17861`; the five test daemons now initialize `applySem`), `docs/log/17861.md` (this file).

## Mechanism (issue evidence, verified at head 61aa231da6)

- `host_kernel_truth_15264.go` (pre-fix): drift arm ran `noteHostInboundApplyFailed(now)`, `hostInboundEnforced.Store(false)`, `hostInboundCoveredAddrs = nil`, `hostInboundDHCPRetainedAddrs = nil`, and — when the gap table was also proven gone — `hostInboundGapFenceActive.Store(false)`, `hostInboundGapFenceSpec = nil`, `hostInboundPreActivationFence = nil`; the lo0 arm cleared `lo0Enforced` / `lo0LastFailed`. All invoked from `hostKernelTruthLoop15264` (started in `daemon_run.go` beside the other reassert loops) with no `applySem`.
- Interleaving: drift probe reads `TableDropsInput=false`/`TableEnforcing=false` (flushed kernel) → probe goroutine pauses → `applyHostInboundFilter` succeeds under applySem and publishes a fresh real generation (`daemon_nft.go`: `hostInboundEnforced.Store(true)`, fresh covered/DHCP sets, gap-fence marker/spec, pre-activation fence) → stale probe resumes and nils/clears the FRESH state. Unsynchronized plain-map/pointer writes race the apply's writes; the atomic latches lose their publication. A subsequent FAILED apply then sees `hostInboundEnforced=false` and installs the cold-boot deny-only fence over a valid retained table (service accepts lost) with the gap/pre-activation specs gone — an avoidable outage plus lost fence bookkeeping, self-healing only at the next successful apply.
- Fix shape: one critical section. Under applySem an apply either completes before the kernel reads (the probe then observes the FRESH table and stays Current) or runs after the clears (its publication supersedes the drift clear). A cancelled acquire means the daemon is stopping (applyCancelCtx is the daemon-stop context); the tick is skipped and the shutdown drain owns the semaphore.

## Consumers re-checked

- `hostKernelTruthLoop15264`: sole production caller; the loop holds nothing else, so no lock-order inversion; a probe-length (two netlink reads) hold every 30s max is the only added applySem contention.
- Shutdown drain (`daemon_run_shutdown.go` TryAcquire/Acquire): a recheck holding applySem is bounded by the probe; its acquire aborts on the daemon-stop context.
- Existing #15264/#16823 cells: unchanged semantics — armed-gate behavior, probe choice, warn de-dupe/re-arm, gap-table partial-flush retention all preserved (the semaphore only serializes them).
- `beginBackgroundApply` fencing/bootstrap gates do not apply: the recheck drives no apply, it only synchronizes state access, so it acquires applySem directly like the other non-apply critical sections (fabric/mgmt/rxvlan reasserts, conntrack flush).

## Risk

- The drift recheck now briefly queues behind (or is queued behind by) applies — at most one probe per 30s tick; no behavioral change to what the recheck observes, only to WHEN relative to applies.
- A drift episode concurrent with an apply is now resolved in the apply's favor when the apply lands after the probe started (probe observes fresh tables → stays Current): drift that is superseded within the same tick window is not reported — correct, the kernel is holding a real generation again.
