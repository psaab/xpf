# #17812: failed VRF rebind must retain scope fingerprint

- **Timestamp**: 2026-10-28
- **Action**: `SetBindDevices` publishes the desired scopes before rebind, but `syncCurFromLiveLocked` previously copied that desired snapshot into the management fingerprint whenever any listener was serving. A same-address A-to-B rebind failure therefore left the old A-scoped listener in place while recording B as converged, suppressing later retries. The reconciler now advances the scope fingerprint only after every HTTP/HTTPS plane driven by that scope change succeeds; failed scope rebinds retain the prior fingerprint as retry debt. Address/TLS state still resynchronizes from live legs after partial reconciles. The API server also has one `legDevices` map shared by both planes: pruning after either plane's reconcile retains records for every installed HTTP and HTTPS leg. A new regression combines scope A-to-B with HTTPS certificate-plan failure after bind: the B socket is closed, the old A leg and scope remain, and the next reconcile must bind B again.
- **File(s)**: `pkg/daemon/management.go`, `pkg/daemon/webmgmt_vrf_bind_16709_test.go`, `pkg/daemon/README.md`, `pkg/api/listener.go`, `pkg/api/listener_vrf_16709.go`, `pkg/api/listener_vrf_16709_test.go`, `pkg/api/server.go`, `pkg/api/tls_certificate_10827.go`, `pkg/api/tls_deadbind_cert_reload_7041_test.go`, `pkg/api/README.md`, `docs/log/17812.md`.

- **Risk**: A failed scope rebind retains the old scope fingerprint until a later reconcile succeeds. Scope pruning now keeps both installed planes' records, so a retry does not force an unchanged sibling leg into a colliding bind.
