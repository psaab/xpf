# #14324 — Pre-MAC SYN-cookie ACK sketch starves legitimate clients

## Defect
`#13952` placed `syn_cookie_ack_attempt_limited` (16/s per
`(src_ip, dst_ip, dst_port)`, 1024-column count-min sketch) **before**
`ring.validates()` in `ScreenState::validate_syn_cookie_ack_on_session_miss`,
charging valid and invalid ACKs before SipHash MAC verification. This
reintroduced the starvation `#13700` had removed by moving the zone-wide
budgets after the MAC: 16 spoofed ACKs/s with a victim's source IP starve
that client's legitimate cookie ACK during a flood, and legitimate clients
behind one NAT/CGNAT IP to one service share 16 new connections/s per
worker.

## Fix
Validate first, charge only failures (`userspace-dp/src/screen/mod.rs`):
`ring.validates()` now runs before any per-key charge. A valid cookie
returns `Validated` and inserts into the validated-client cache without
touching the sketch. Only on a failed MAC does the code charge
`ZoneScreenState::syn_cookie_ack_attempt_limited`:

- Active arm: per-key limited OR zone-wide active budget spent →
  `ActiveBudgetExceeded` (fail-closed drop preserved); otherwise `Invalid`.
- Standby arm: charges the per-key sketch (shared across role changes, so
  a brute-forcing key's history survives failover) plus the standby
  zone-wide budget, still fail-open `NotApplicable`.

The sketch, its 16/s production rate (256/s in tests), allocation, and
reconcile lifecycle are unchanged — only the charging point moves.
`SYN_COOKIE_FAILED_ATTEMPT_RATE_LIMIT_PER_SEC` now names failed attempts;
comments in `zone.rs`/`syn_rate.rs`/`syncookie.rs` updated to post-MAC.

Accepted tradeoff (from the issue's fix direction): SipHash validation
cost (~15ns) is now paid for every plausible-epoch session-miss ACK before
any per-key refusal. This is bounded by the existing post-MAC zone-wide
active (65536/s) and standby (4096/s) budgets' verdicts, and a single
SipHash-2-4 over 40 bytes is comparable to the sketch hash itself. The
per-key sketch no longer bounds candidate MAC checks pre-validation; it
bounds *failed* attempts per key, which is what throttles a flooding key's
verdict to `ActiveBudgetExceeded`. A brute-forcer can still attempt MACs
at line rate (as between #13700 and #13952), but can never starve a valid
cookie or throttle NATed legitimate clients, and a guessed MAC was always
required to be exact — the sketch never added MAC strength.

## Regression
New tests in `userspace-dp/src/screen/tests.rs` (test build raises the
per-key limit to 256/s, so counts exceed that; production limit is 16/s):

- `syn_cookie_spoofed_failures_do_not_starve_valid_ack_14324` — 300 spoofed
  invalid ACKs from `src_ip`, then 1 valid cookie ACK from the same
  `src_ip` must be `Validated`. RED on base (see below).
- `syn_cookie_nat_valid_acks_not_throttled_14324` — 300 valid cookie ACKs
  from different source ports behind one NAT `src_ip` to the same
  `(dst, dport)` at one instant must all be `Validated`. RED on base at
  the 257th ACK.
- `syn_cookie_active_failed_attempt_bound_preserves_valid_ack_14324` and
  `syn_cookie_standby_failed_attempt_bound_preserves_valid_ack_14324` —
  rewritten #13952 regressions: after the failed budget is spent, further
  invalid ACKs report `ActiveBudgetExceeded` (active) / `NotApplicable`
  (standby), but the correct MAC for the same key now validates instead
  of being blocked; unrelated keys validate in both arms.

RED evidence (base worktree at `db3cdaebb`, only the two new tests added):
both failed with `left: ActiveBudgetExceeded, right: Validated`
(spoofed test at the valid ACK; NAT test at source port 40256).

GREEN: `cargo test --bin xpf-userspace-dp -- syn_cookie_` — 122 passed;
`cargo test --bin xpf-userspace-dp -- screen::` — 340 passed.

## Risk
Valid-cookie path is unchanged in cost and verdict; invalid-ACK floods now
pay one SipHash per plausible-epoch ACK before refusal (see tradeoff
above). Sketch collisions still fail closed for *invalid* ACKs only.
Standby remains fail-open. No wire, config, or verdict-enum changes.
