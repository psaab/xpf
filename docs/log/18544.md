# #18544: deb deploy never reconciled a stale /etc xpfd.service shadow

- **Timestamp**: 2026-10-30
  - **Action**: Measured the defect with read-only `incus exec` queries
    (`systemctl show`, `ls -l`, `readlink`, `dpkg-query`); nothing on any
    cluster was changed. All six HA nodes report
    `FragmentPath=/etc/systemd/system/xpfd.service`. loss fw0/fw1 and tcp
    fw0/fw1 run `KillMode=control-group`, and udp fw0/fw1 run `mixed`.
    Every installed deb descends from 9d16341ce9 (#18213), and its packaged
    `/usr/lib/systemd/system/xpfd.service` carries `KillMode=mixed`. The
    `/etc` copy shadows it. The loss fw0 copy (980 B, Oct 16) also lacks the
    #16050 `RuntimeDirectory*`/`UMask` hardening and the packaged
    `ExecStartPre` verify-dataplane gate. On five of the six nodes the
    wants link points at the `/etc` copy. Filed #18544 with this table.
  - **File(s)**: none (issue only).

- **Timestamp**: 2026-10-30
  - **Action**: Chose REMOVE over RE-SYNC. A production install has no `/etc`
    copy, so after removal the unit shipped in the deployed deb governs.
    Re-syncing from the worktree would pair one tree's unit with binaries
    from a possibly different, `XPF_DEPLOY_DEB_PATH`-pinned, deb. No
    existing assertion breaks. The raw path's
    `deploy_verify_running_xpfd` (base-unit ExecStart) runs only on the raw
    path, and that path re-pushes the `/etc` copy. On the deb path, ExecStart
    comes from the #1917 `10-xpf-version.conf` drop-in, which applies whatever
    the fragment, and pkg/upgrade never reads `FragmentPath`.
    Added `deploy_reconcile_unit_shadow` to `test/incus/deploy-lib.sh`. It
    removes only a regular file and leaves a mask symlink alone (the
    xpf-deploy.py #7559 hold). It refuses when no packaged unit exists, then
    daemon-reloads (also when the file is gone but systemd still has it
    loaded). It asserts that the LOADED `FragmentPath` is neither empty nor
    the shadow, and re-points a wants link that targets the shadow. It never
    starts, stops or restarts xpfd. `deploy_vm_deb` calls it after
    `deploy_install_deb` and before `xpfd upgrade --rolling`, so the cut's
    stop already uses the packaged KillMode.
  - **File(s)**: `test/incus/deploy-lib.sh`, `test/incus/cluster-setup.sh`.

- **Timestamp**: 2026-10-30
  - **Action**: Folded the round-1 review of PR #18546 at 441e3a240c
    (harness-B MINOR, harness-A CLEAN; LOW findings only). I checked each
    cited line before folding.
    - **The post-removal check was negative only** (harness-A and harness-B
      LOW). It accepted any fragment that was non-empty and not `/etc`, so
      a `/run/systemd/system` or `/usr/local/lib` unit (which `/etc` used to
      outrank), or a runtime mask, passed as "packaged". The check is now
      positive: `LoadState=loaded`, and `FragmentPath` must be the unit's
      file under `deploy_packaged_unit_dirs`. The `/etc` copy is now PARKED
      in `/run/xpf-deploy-unit-shadow/` instead of deleted, so a failed
      check puts it back and reloads, and the deploy dies with the node as
      it was.
    - **A symlink at the /etc path returned 0 unchecked** (harness-A LOW).
      A `/dev/null` link (the #7559 mask) is still left alone, by design. Any
      other link is an alias this deploy did not write: it is still not
      removed, but it now goes through the positive check, which fails an
      alias that systemd does not resolve to the packaged file.
    - **The sibling barrier units had the same shadow** (harness-B LOW). This
      is confirmed read-only: every node loads
      `xpf-{transit,input}-closed.service` from `/etc`, and loss fw0's copies
      (Oct 16) differ from the packaged ones. On udp, all five barrier install
      links (`sysinit.target.wants`, `systemd-networkd.service.requires`,
      `xpfd.service.requires`) target the `/etc` copies. I generalized the
      function to `deploy_reconcile_unit_shadow <rinst> <unit>`, and the new
      wrapper `deploy_reconcile_unit_shadows` covers all three units. The
      link re-point now scans every `/etc/systemd/system/*/<unit>` link, so
      the WantedBy=/RequiredBy= links stay present (enabled, RequiredBy=
      intact) and target the packaged file. Nothing restarts the barriers;
      the new versions apply at the next boot.
    - **NIT, a false rationale.** I had claimed that re-syncing "keeps dropping
      the packaged ExecStartPre". In fact the #1917 drop-in resets and
      re-adds ExecStartPre whatever the fragment is
      (`pkg/upgrade/flip.go:351-352`). The claim is dropped here and in the PR
      body.
    - **NIT, the wiring pin was not anchored at the end**, so a backgrounded
      `... &` call survived. It is now anchored with `[[:space:]]*$`.
