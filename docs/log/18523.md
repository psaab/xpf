# #18523: HA smoke false verdicts

- **Timestamp**: 2026-10-29 18:40 UTC
- **Action**:
  - `test-active-active.sh` accepts `secondary` or `secondary-hold` for
    the old RG1 owner and requires node1 to read `primary`. That is the
    `ha_rg_owner_verdict` rule from #18503. Before, a committed transfer
    was recorded as "RG1 did not move" (VOID) on loss and tcp.
  - `test-ha-crash.sh` starts instances through `start_instance`, which
    records the `incus start` error as a FAIL naming the cause. Before,
    the error was discarded and a VM that could not start at all (tcp:
    SR-IOV VF pool exhausted) read as "xpfd did not restart within 90s".
- **File(s)**: `test/incus/test-active-active.sh`,
  `test/incus/test-ha-crash.sh`, `docs/log/18523.md`
- **Validation**: `bash -n` on both scripts. The new RG-move predicate was
  checked against five status shapes: secondary-hold/primary and
  secondary/primary pass; primary/secondary, hold/hold and hold/primary
  fail. Live: the loss and tcp `test-active-active` runs that recorded
  VOID on `secondary-hold` (2026-10-29) are the motivating cases.
- **Risk**: the active-active check is now stricter in one way (node1 must
  read primary), so a half-moved RG that it used to pass on node0 alone now
  FAILs. That is intended. No docs change: `docs/testing-procedures.md`
  describes these targets at a level these fixes do not change.
- **Timestamp**: 2026-10-29 19:00 UTC
- **Action**: `restore_fw0_primary` in `test-ha-crash.sh` and
  `test-restart-connectivity.sh` moves one RG at a time and polls each
  (5 s per request). It re-requests until `RESTORE_FW0_WAIT` (default
  60 s), and the FAIL names the last refusal. Before, three blind requests
  with refusals swallowed (`|| true`) were followed by one fixed
  `sleep 5`, shorter than one admission window plus a post-restart bulk
  (~50 sessions/s, #18521). Verdicts stay honest: a node that cannot be
  restored still FAILs, with the reason.
- **File(s)**: `test/incus/test-ha-crash.sh`,
  `test/incus/test-restart-connectivity.sh`, `docs/log/18523.md`
- **Validation**: `bash -n` on both.
- **Risk**: a slow restore now takes up to 60 s per helper call instead of
  failing at 5 s, which lengthens a failing run.
- **Timestamp**: 2026-10-29 19:35 UTC
- **Action**: `test-ha-crash.sh` sources `failover-clock-lib.sh` and resyncs
  both nodes' clocks from one host reading after each VM restart (phase 1
  and every phase-3 cycle), as `test-failover` and `test-double-failover`
  already do (#11872). Loss fw0 came back 2m42s behind fw1 after the
  force-stop. The skew breaks the fabric gRPC auth window; session sync is
  monotonic-clocked and unaffected.
- **File(s)**: `test/incus/test-ha-crash.sh`, `docs/log/18523.md`
- **Validation**: `bash -n`.
- **Risk**: none beyond the existing helper's (it sets both guests' wall
  clocks).
