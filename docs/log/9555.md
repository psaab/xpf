a silent dead rule-set when the pools are disjoint. Posted on the issue

My issue comment proposed a STRICT duplicate-prefix reject. Before writing it I

- **Their stated premise is wrong:** "resolve to ONE runtime allocator".
- **Their verdict is right:** the second rule-set never mints, so it cannot
  collide.

So a strict reject would overturn a considered decision in order to refuse a
harmless dead rule-set. I also confirmed that warnings reach the operator: the
tail gate appends `validateNAT64PrefixStrict`'s warnings to `cfg.Warnings` in
BOTH modes, and the CLI prints `compiled.Warnings` at commit and check
(`pkg/cli/cli_config.go`).

**Remedy, revised:** align Go's owner model with the dataplane's selection rule,
and make the dead rule-set LOUD rather than rejected.
1. `nat64ShadowedRuleSets` maps each rule-set to the earlier one that shadows it.
2. The #5144 NAT64 owner loop skips shadowed rule-sets, because they never mint.
3. `validateNAT64PrefixStrict` warns, in both modes, that a shadowed rule-set is
   UNREACHABLE, naming the rule-set that shadows it.

The three #5144 cells stay green. Only their rationale comments were corrected,
not their assertions.

## Two traps the helper is built around

- **Config order, not name order.** `compileNAT64` appends rule-sets in
  `namedInstances` (AST) order, and `buildNAT64Snapshots` emits that slice; Rust
  keeps it. The #5144 owner loop sorts by NAME. Choosing "earlier" by name could
  make the rule-set the dataplane never uses the owner, and drop the reachable one
  from the owner set: an UNDER-refusal of a real collision.
- **Conservative on "built".** Rust skips a rule whose prefix address does not
  parse, and skips the WHOLE rule when any pool member fails `parse_pool_v4`
  (#3888). `isNAT64PoolHostAddress` mirrors that parse exactly. A rule-set that
  would be skipped shadows NOTHING, so a later one stays an owner: over-refusal,
  never under-refusal. A missing or empty pool IS built (an empty allocator that
  fails closed), so it still shadows.
