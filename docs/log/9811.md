# #9811 — a caller-less auto-rollback apply had no retry owner and no degraded signal

Work log for issue #9811. See `docs/log/README.md` for why this lives here and
not in the repository-root `_Log.md`.

- **Timestamp**: 2026-09-12
- **Action**: Gave the commit-confirmed auto-rollback apply a retry owner
  (`configApplyDebt` + `configApplyReassertLoop`, `pkg/daemon`) and a durable
  degraded signal (`ConfigApplyDebtFn` -> `/health` 503, `pkg/api`).
- **Why it is a divergence and not a stale rule**: `executeConfirmedRollback`
  promotes the STORE to the rollback target C1 first, then applies. Under the
  #5679 contract a failed full apply keeps the OLD compiled policy live, so the
  node goes on ENFORCING the abandoned C2 while the store, `show configuration`,
  the peer resync and `/health` all report C1. The commit path self-heals
  because the operator sees the error and re-commits; this is a timer callback
  with no caller to report to.
- **Mechanism chosen**: the pattern this repo already settled on for "a failure
  has no retry owner" — `proxyARPReassertLoop` (#4001),
  `fabricIPVLANReassertLoop` (#6791), `serviceReloadDebtReassertLoop` (#6800),
  `routingReconcileReassertLoop` (#9693). Not a new shape; the fourth instance
  of an existing one.
- **The decision inside it that is load-bearing**: the retry re-reads the ACTIVE
  config rather than replaying the config whose apply failed. Replaying is the
  obvious implementation and it is wrong in the silent direction — a commit
  landing between the failure and the next tick would be UNDONE by the retry
  owner. Re-reading is also what discharges the debt after an unrelated
  successful commit, which would otherwise pin a converged node at 503 forever.
  Both halves have their own cell.
- **Why 503 and not a non-fatal field**: `rollback_history_degraded` is
  explicitly non-fatal, with the reasoning that a perfectly forwarding firewall
  must not be pulled from rotation over a degraded recovery aid. That reasoning
  does not transfer: here the node forwards something it does NOT report, which
  is `config_persist_degraded`'s class ("a restart would load a stale config").
  An orchestrator steering traffic at a node whose policy is not the policy it
  published is acting on a false premise. It is transient by construction — the
  retry owner converges it.
- **Scope deliberately not widened**: every caller-less apply (boot load, DHCP
  lease callback, feed refresh, config poll) has the same shape, and #9693
  already owns the routing tail for all of them. On those paths the store has
  not advanced, so the reported configuration is still the enforced one. Stated
  in the code rather than left implicit.
- **Not bundled**: `RoutingReconcileDebt()` (#9693) still has no non-test
  caller, so routing debt remains invisible on `/health`. That is a real gap of
  the same family but it changes rotation behaviour for an existing mechanism,
  so it is not folded in here.
- **Validation**: 7 cells — 4 in `pkg/daemon` (latch + retry + converge, the

  cell), 3 in `pkg/api` (503 while owed, 200 once converged with the historical
  count still visible, and the #5031 redaction with the signal surviving it).
