# #16058 — Kea lease-sync client bare-dials the pathname with no peer verification

## Why

The Kea lease-sync client dialed Kea's control socket by pathname
(`lease_sync.go` `defaultKeaDialer`: a bare `DialContext(ctx, "unix",
socketPath)`) with no `SO_PEERCRED` verification of the server. A
wrong/squatted server on that path was trusted as Kea: returned leases
are sanitized, but sanitization cannot authenticate the wrong server,
so fabricated lease data could be fed into HA lease sync (and
lease-add/update commands would be delivered to the squatter on the
seed path). Legit peer is `_kea`; the likely actor needs `_kea`
compromise or bad `/run/kea` perms (HA-only) — hence Low. The
permissions arm is DUP A10-06 and out of scope; only the
peer-verification arm is fixed here. Fix shape per the issue: verify
`SO_PEERCRED` (expected `_kea` uid) on connect in the lease-sync dial,
mirroring the reinject fix (#16052).

## What

- `pkg/dhcpserver/lease_sync.go`: `defaultKeaDialer` — the single
  production dial choke point for every Kea control-socket exchange
  (`lease{4,6}-get-all`, `lease{4,6}-add`/`-update`, `dhcp-disable`,
  display reads) — now verifies the peer via `SO_PEERCRED` immediately
  after connect, before any command byte is written, and closes/refuses
  on failure (`errUntrustedKeaPeer`). Trusted uids: the resolved Kea
  runtime user (`_kea`/`kea` via the #2450 lookup), root, or this
  daemon's own euid — the reinject #16052 / helper #9003 posture. The
  decision (`keaPeerTrustErrorAs`) is split from the syscall shell
  (`readKeaPeerUID`, `keaGetsockoptUcred` seam) so the hostile
  foreign-uid arm is reachable from an unprivileged test. A failed
  credential read never substitutes a zero Ucred (Uid 0 = root =
  trusted, the #9003 fail-open).
- `waitControlSocket` re-verifies for custom dialers, so a connectable
  squatter is never reported Kea-ready to the post-start seed.
- NOT changed: the `keaSocketDialer` test seam's contract — custom
  dialers are test doubles whose in-process peers this process's uid
  admits (the suite relies on `net.Pipe`, which cannot present
  credentials); the production no-seam path is the verified one. The
  memfile fallback, sanitization, and all callers are untouched. No
  new Manager field: the dialer holds no Manager, so the expected uid
  resolves through the same user names uncached (once per dial, never
  a packet path).

## Risk

Peer verification runs on every dial, and the seed path dials once
per command (`keaControl` per `lease{4,6}-add`, plus one more for a
conflict `lease{4,6}-update`), so verification IS per command — and
therefore per lease on the takeover seed: one `getsockopt` against a
fresh connection for each lease seeded. It is never per packet. That
cost sits on the async takeover seed, not on DHCP serving or any
dataplane path. The check is race-free for the
connection it is applied to (kernel-resolved `SO_PEERCRED`), unlike
any path/mode check. A refused peer degrades lease reads to the
existing memfile fallback and fails seeds open exactly as a down
socket does today, so a mis-resolved Kea uid cannot wedge serving. It
does not authenticate beyond uid: a root- or `_kea`-compromised peer
is still trusted, matching the #9003/#16052 posture. No live cluster
was mutated.
