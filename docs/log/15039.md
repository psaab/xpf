# #15039 — Bare session deletes scanned the full scoped generation map

## Defect
`#14358` made every bare (non-scoped) session delete cover each domain's
scoped generation entry for its tuple, implemented as a full scan of the
scoped map (`scopedKeysForTuple`): sender `takeDeleteGenV4/V6` scanned
`genSentScoped*` under `bulkSnapshotGenMu` + `genSentMu`, and receiver
`deleteGenGuardV4/V6` scanned `recvGenScoped*` up to twice under
`recvGenMu`, inside `applyMu`. Bare deletes are the production close path
(`capFlagScopedPolicyDelete` is unadvertised), and the receiver map is
pinned near its cap by tombstones, so each bare delete cost
O(held scoped entries) at both ends, serializing the standby's delete
apply rate and the sender's stamping.

Measured pre-fix on the campaign host (benchmark below, pristine
`origin/master`): sender bare delete 62us at 1k held scoped entries,
874us at 10k, 7.55ms at 50k.

## Fix
Index the scoped entries by bare tuple instead of scanning:

- `scopedTupleIndex[K, SK]` (`pkg/cluster/sync_conn_gen.go`): side map
  bareTuple -> set of scoped keys. It holds no generations — the scoped
  map stays authoritative for every ordering decision; the index only
  names which scoped keys exist per tuple. Sets are pruned as soon as
  they empty.
- One index per scoped map on `SessionSync`
  (`genSentScopedByTupleV4/V6`, `recvGenScopedByTupleV4/V6`, in
  `pkg/cluster/sync.go`), guarded by the same mutex as its map.
- Maintained at every scoped mutation, through index-aware helpers so no
  call site can update one structure without the other:
  `putScopedGenBounded` (sender stamps in `stampInstallGenV4/V6`),
  `putScopedGenEvictingTombstones` (`pkg/cluster/sync_gen_tombstones_9719.go`;
  also de-indexes the oldest tombstone evicted at cap, via a new
  `genTombstoneOrder.frontKey`), and `deleteScopedGen` (bare/scoped
  takes, gen-0 evictions, cross-space tombstoning in the guards).
- Bare paths now iterate `index.keys(tuple)` — a snapshot copy, since
  callers tombstone/delete while iterating — instead of
  `scopedKeysForTuple`, which is deleted.
- `resetRecvSessionGen`: preserve=true rebuilds the receiver indexes
  from exactly the retained tombstone entries; preserve=false clears
  them with the maps.
- An absent index set is exactly the pre-existing "tuple has no scoped
  entries" no-op, and every guard still reads generations from the
  scoped map, so a (never expected) index/map disagreement cannot invent
  ordering — it can only miss a reclaim/tombstone the scan would have
  made. The lifecycle test asserts index/map agreement after cap
  eviction, reclaim, namespace reset, gen-0 delete, bare close, scoped
  take, and both v6 twins.

No wire, capability, or generation-semantics change; install guards and
all neighbouring memo families are untouched.

## Tests (`pkg/cluster/sync_scoped_index_15039_test.go`)

- `TestBareDeleteCostFlatWithHeldScopedEntries15039`: 50k unrelated
  scoped entries held at both ends; 200 bare deletes must average
  < 2ms each at sender and receiver.
- `TestScopedTupleIndexTracksLifecycle15039`: index/map consistency
  after every scoped lifecycle transition (see above).
- `BenchmarkBareDeleteScopedIndex15039` (report-only): held=1k/10k/50k.

Existing `#14358` / `#10512` suites are the control cases (unchanged):
`TestNormalCloseReclaimsScopedGen14358`,
`TestScopedDeleteCrossTombstonesBare14358`, and the `*10512` tests.

## RED/GREEN
- RED on pristine `origin/master` `192c7455ba` (timing test transplanted
  alone; the lifecycle test uses post-fix fields and does not compile
  pre-fix): `sender bare delete = 6.90ms at 50000 held scoped entries,
  want < 2ms`. Benchmark pre-fix: 61.8us / 874us / 7.55ms at
  1k / 10k / 50k held.

  at 1k / 10k / 50k held (within-noise flat). `-race` on the scoped
  suites passes. Full `./pkg/cluster/` suite (149s): sole failure
  `TestInstallTableProducerToResendEndToEnd9752`, documented in
