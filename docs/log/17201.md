# Issue #17201 — R4-Q51-03: Mutex-poison policy is chosen per call site

- **Issue:** At least 31 `.expect` lock acquisitions, 48 `if let Ok(..) = x.lock()` acquisitions and at least 6 `.lock().map(..).unwrap_or_default()` acquisitions remained in production, against `docs/engineering-style.md:1536-1567`. Inside `afxdp/bpf_map/`, `steering_owners` recovered from poison (#9560) while the process-global `TupleGate` (#10512) `.expect`ed at 16 sites on the worker install, GC-teardown, HA-import and BPF-publish paths — one poisoned shard became a panic on every later install/teardown/import hashing to it, with nested `.expect`s cascading poison from an entry to its whole shard.
- **STEP-0 (defect live on origin/master `eb4571c7ef` at branch creation, merged forward to `e9718daaf2`):** `grep 'expect("tuple gate'` on `origin/master:userspace-dp/src/afxdp/bpf_map/tuple_gate.rs` returned 16 sites (15 lock + 1 Condvar `wait_timeout`). A refined production census on the merged tree (test files and `#[cfg(test)]` items excluded, multi-line chains included) found: 49 `if let Ok`/`let Ok else` lock acquisitions, 33 `.lock().expect` (16 tuple-gate, 5+5 flood/zone counter stores incl. test-only fns, 1 policy store, 3 allow-listed `server/lifecycle.rs`, 1 documented neighbor-warmer, 8 `#[cfg(test)]`-only HA hooks), and 14 `.lock().map(..).unwrap_or_default()` chains (plus comment-only historical citations). No `sync_util` module existed. Pre-existing unrelated breakage on the starting master (`shared_umem_tests.rs:247` `json!` vs `UserspaceSnapshot`) was fixed upstream before the merge-forward and is not part of this change.

## What

1. **Crate-level helper (`userspace-dp/src/sync_util.rs`, new):** `lock_tolerant`, `read_tolerant`, `write_tolerant`, `wait_timeout_tolerant`, plus `_counted` variants taking `Option<&AtomicU64>` bumped only on the poisoned arm (no journald line per acquisition). Each is the named inline `unwrap_or_else(PoisonError::into_inner)` idiom; the uncontended fast path is the same single CAS as `lock()`. Subsystem helpers with their own counter/log/quarantine (`worker_queue::lock_recover`, `shared_ops::lock_shared_recover`, `lock_ha_recover`, `lock_server_state_recover`) are **not** folded — the module doc states why borrowing them would make operator messages and counters lie.
2. **Private copies folded:** `wg/handshake_session.rs:87` `lock_recover` now checks `is_poisoned()`, stamps its WG counter + journald line + `clear_poison`, then delegates to `lock_tolerant`; `wg_uncovered_forward.rs:134` `lock_recover` delegates to `lock_tolerant_counted` with its queue counter. `server/helpers/guards.rs` `lock_server_state_recover` is retained (annotated #17201) because recovery must also set `quarantined_after_panic` on the recovered guard — folding it would drop the quarantine.
3. **TupleGate converted (16 sites):** all shard/entry/admission locks use `lock_tolerant_counted(..., Some(&TUPLE_GATE_POISON_RECOVERIES))` and the admission `wait_timeout` uses `wait_timeout_tolerant_counted`. Nested shard→entry acquisitions now recover without panicking under the shard lock. Shard-order discipline in `try_acquire_installs` and the `ACQUIRE_BUDGET` deadline are unchanged. New counter `TUPLE_GATE_POISON_RECOVERIES` (bump-only-on-poison, per the HPC note).
4. **Counter stores converted:** `flood_counters.rs` (4 production sites) and `zone_counters.rs` (4) and `policy.rs` `rule_hit_counter` (1) `.expect` → `lock_tolerant` (their `#[cfg(test)]` helpers keep `.expect`, stripped by the scan).
5. **All other production `if let Ok` / `let Ok else` / `map().unwrap_or_default()` / `map().unwrap_or(0)` / `.unwrap()` lock sites converted** to `lock_tolerant`/`read_tolerant`/`write_tolerant` with recovered-state semantics (never skip, never empty): `binding_state/{mod,snapshot}.rs`, `coordinator/{mod,status,snapshot_refresh,tunnel_supervision}.rs`, `coordinator/reconcile/bringup.rs`, `disposition.rs`, `tunnel.rs`, `wg/{endpoint_resolver,cookie,engine,handshake_session}.rs`, `nat/mod.rs`, `policy.rs`, `slowpath.rs` (incl. the limiter `match lock { Err(_) => false }` fail-closed site — now recovered, so a poisoned limiter admits per its recovered state instead of refusing every frame), `state_writer.rs`, `session/lookup.rs` (`let Ok else continue` → recovered guard). Documented exclusions kept and counted by the scan: 3 `server/lifecycle.rs` fail-fast sites, 2 neighbor-warmer sites (`neighbor.rs` module doc designs the panic/skip as the operator-visible failure), 3 `ipsec_inner_queue.rs` sites owned by R4-Q10-01.
6. **Source-scan test (`userspace-dp/src/sync_util_scan_tests.rs`, new, `#[cfg(test)]`):** walks every `.rs` under `src/`, obtains production text via the shared #17152 blankers (`blank_comments_and_strings` + `blank_cfg_test_modules` + `is_fixture`), squashes whitespace (multi-line chains included), and fails on any banned shape beyond the counted allowances above (lifecycle 3 expect; neighbor 1 hard + 1 expect; ipsec 3 hard). It fails when a new banned shape is added, including in a newly added file.

## Risk

Behaviour changes only on the poisoned arm, which previously panicked, silently skipped, substituted empty state, or (slowpath limiter) refused every frame. Recovered state is the committed prefix — well-formed for these small state flips (the gate/counter/status sections have no panic site except the removed nested `.expect`s themselves). The one semantic widening to note: `slowpath` adjudicated-limiter acquisition and `session/lookup` shared-establishment now proceed on recovered state instead of failing closed per call; both guard diagnostic/admission state whose recovered value is the last committed state, per the style rule's test. Hot paths: `lock_tolerant` on an unpoisoned lock is the identical CAS; no allocation, no logging, no counter bump on the fast path (counted variants bump only after a poisoned `Err`). Residual: `ha/session_domain.rs` `#[cfg(test)]` hook locks keep `.expect` (test-only, scan-stripped); Go code is untouched.
