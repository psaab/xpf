# #18515 — synced sessions carry truncated u16 zone IDs; every established flow dies on failover

- **Timestamp**: 2026-10-29
- **Action**: Diagnosed the H5 "established streams never resume after
  takeover" thread of #18503 on the tcp cluster with a port-filtered
  diagnostic helper build (not committed). On the new owner every hit on a
  peer-synced session was `AUTHORITY-FOREIGN` with stored zones `9721`/`23882`
  against live zones `382805497`/`262430026` — the low 16 bits of the full
  `StableZoneID`s. Reply packets were then judged as their own wan->lan flow
  and default-denied (`policy_id=4294967295`).
- **Root cause**: `fillSessionSyncValue` sent `uint32(u16)` as the zone ID
  (commented "widened losslessly") and resolved the name by exact u32 match,
  which finds no zone above 65535. The helper prefers a nonzero ID.
- **Fix**: `resolveTruncatedZone` recovers the full ID and name by low-16
  match against the published zones; ambiguous low bits import an ID no zone
  carries (round 3); no published zones keeps the old pass-through.
- **File(s)**: `pkg/dataplane/userspace/manager_sessionsync_request.go`,

  `pkg/dataplane/userspace/session_sync_zone_truncation_18515_test.go`,
  `docs/session-sync-architecture.md`, `docs/log/18515.md`
- **Validation**: unit cells for the resolver (lan/wan recovery, ambiguous
  low bits, no match, no published zones) and for
  both request families (full IDs, names, and the zone-derived owner RG);
  both reverted-fix mutants fail. `pkg/dataplane/userspace` package: the
  failing set is identical to master's pre-existing reds;
  `TestDesiredForwardingStateResumesAfterLinkCycle_6871` is red on master
  in isolation (5/5) and intermittent here (3/5), so it is not attributable
  to this change. Cluster validation recorded on the PR.
- **Round 2 (review folds)**: resolve against `m.lastSnapshot.Zones` (the
  post-quarantine set the helper enforces, read under the held `m.mu`)
  instead of the pre-quarantine compile table; drop the test hook so the
  production read is exercised; one-shot warning for an ambiguous value;
  cells for the zero/unrecoverable and ambiguity cases (the three mutants
  that survived round 1 now fail); stale `zoneNameByID` references fixed.
  This is the residual of #17863 item C, which closed on items A/B.
- **Timestamp**: 2026-10-29 18:20 UTC
- **Action**: Round 3 (review folds). An ambiguous value no longer resolves to
  zone 0. An arrival on an interface in no zone has arrival zone 0 and
  `session_hit_authority` would judge it the session's owner, skipping the
  #6682 unzoned-transit deny. It now resolves to `unattributedZoneID`: same
  low 16 bits, no published zone, outside the reserved band (0xFFFFFFFE is
  junos-host). Every hit is foreign, and a re-export truncates to the same
  wire value. The warn cell now includes a uniquely-matching zone, so the
  "warn on any match" mutant fails. Documented the receiver-only ambiguity
  residual (sender-only zones), fixed stale doc lines (`zoneid.go`, the
  architecture doc's compile-result reference, the warn-once wording).

- **Risk**: the match consults only the receiver's zones. A sender-only zone
  sharing low 16 bits with a local zone is attributed to the local zone
  (about 1/65536 per such pair). Widening the u16 wire fields is the only
  complete fix. Sessions in ambiguous zones are foreign after failover until
  one zone is renamed (warned once per value).
