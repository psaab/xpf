# #14592 VPN with no establish-tunnels never initiated — engineering history

Issue: psaab/xpf#14592 (finding Y09-05, deep-review, validated-by:research).
Lane branch: `fix/14592-campaign`, base `origin/master` c4848b1ae
(rebased onto abb8a06c6 before push; #14729's fix for the
TestCompactBlockEquivalenceInventory2419 panic had landed there).

## Defect (present at base)

`pkg/ipsec/policy.go` rendered a child `start_action` only for the two
explicit modes:

- `immediately` → `start_action = start`
- `on-traffic` → `start_action = trap`
- `""` (statement absent) → nothing

`pkg/config/compiler_ipsec.go` stores the leaf verbatim with no
defaulting, and charon's own default `start_action` is none. Junos
contradicts the render: "If this configuration is not specified, IKE is
activated only when data traffic flows" — on-traffic is the default
behavior. Two xpf peers at the Junos default therefore never initiated:
no SA, no error, green commit — a silent fail-closed availability
failure. The in-tree `pkg/ipsec/README.md` #4301 text ("silently degraded
to on-traffic") and the #14140 text ("the first matching packet
re-establishes") already asserted the on-traffic default the render
dropped.

Scope guard: `responder-only` *mode* (`""` is distinct) and a
responder-only *gateway* (`gw.ResponderOnly`, `remote_addrs = %any`,
#11688) must still emit nothing — there is no fixed peer for a trap to
dial.

## Fix

- `pkg/ipsec/policy.go`: the child switch is now
  `case "on-traffic", "":` → `start_action = trap`, still inside the
  existing `gw == nil || !gw.ResponderOnly` guard. No compiler
  defaulting: the compiled value stays verbatim (hand-built configs and
  tolerant loads carry `""` too), and every consumer of `""` — render,
  `vpnEagerlyInitiates`, DPD derivation — already treats non-`immediately`
  as non-eager, so no other behavior moves. Deliberate scope cut: no
  change to `compiler_ipsec.go`, `vpnEagerlyInitiates`, or `deriveDPD`;
  an unset (trap) VPN is deliberately not eagerly reinitiated after a
  config change (#14140), exactly as explicit on-traffic is not.
