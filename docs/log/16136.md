# #16136 — ShowText/SystemAction metadata registry split from handlers

- **Timestamp**: 2026-10-21
- **Action**: Split the topic/verb metadata of the two request-multiplexed
  RPCs (ShowText by topic, SystemAction by verb) into a new metadata-only
  registry package, `pkg/optopic`. Each `optopic.Entry` carries the key
  (exact, or a `:`-suffixed prefix rule), the coarse authz price
  (`config.LoginClassPermission`), the canonical argument-free command,
  and the cluster-fabric admission bit. Typed `*Server` handlers stay in
  `pkg/grpcapi` — the registry holds no handler values of any shape (no
  `func(any, …)`), and `pkg/optopic` depends only on `pkg/config`'s
  permission enum, never on `pkg/grpcapi`.
  - Derived, not re-typed: `pkg/grpcapi`'s `showTextViewTopics` /
    `showTextElevatedTopics` / `systemActionPermissions` (now named views
    over the registry), `pkg/cmdtree`'s `showTextTopicCommand` (+ reverse
    command→topic lookup), `pkg/authz`'s `SystemActionVerbCommand`, and
    `pkg/grpcapi`'s `fabricAllowedShowTextTopics` are all built once from
    `optopic` entries. Every existing consumer (principal gate, deny-
    commands gate, REST gate, remote CLI topic resolution) reads the same
    derived values as before.
  - Closed a real census hole the scrape exposed: `applications:` was
    dispatched (the `applications:<name>` filtered render, #15207) but
    had no price and no canonical command — the two pre-existing
    completeness guards were red on master for exactly this key. It is
    now registered at `PermView` / `show security applications`.
  - Prefix-priced SystemAction families (cluster-failover grammar,
    `userspace-*` control forms) are registered as PermMaint prefix
    metadata in `optopic`; the D11 attestation arm stays PermAll. The
    failover family's fabric admission remains the parsed node-targeted
    subset via `pkg/clusterfailover` — it has no fixed spelling and is
    enumerated separately in the census.
  - Equivalence cycle (decisive check): new
    `pkg/grpcapi/authz_registry_census_16136_test.go` keeps an
    independent, differently-filtered source scrape after the flip — the
    AST case/`==`/`HasPrefix` extraction over the handler files plus the
    #6532 regexp scrape (which must agree with each other first), the
    `switch req.Action` case walk plus the handler's `HasPrefix` arms,
    and the failover grammar — and asserts registry ≡ scrape in both
    directions, separately for exact topics, prefix topics, exact verbs,
    prefix families, priced+commanded resolution, fabric admission, and
    unknown-content strictness. A behavioural arm drives every registered
    topic through the real `ShowText` dispatcher. The registry is never
    its own oracle: no expected set is derived from `pkg/optopic`.
  - Explicitly NOT done: no blanket "no new ShowText topics" freeze (the
    issue records it as unsound — `ShowText` is a declared v1 generic
    service); dispatch itself is untouched (ordered prefix arms + switch
    in `server_show.go`, switch + default-branch forms in
    `server_diag_system_action.go`), so operator output is byte-identical.
- **Validation**:
  - `go test ./pkg/optopic/ -count=1` — PASS.
  - `go test ./pkg/cmdtree/ -run 'ShowTextTopic|8058' -count=1` — PASS
    (the one full-package cmdtree failure,
    `TestCompleteRepeatedAndOtherOptionMaps15720`, is identical on the
    pristine `ba55ef764a` base).
  - `go test ./pkg/grpcapi/ -run '16136|5278|7172|8597|9022' -count=1` —
    all 16136 census arms and every pre-existing 5278/7172/8597/9022
    guard PASS (including the previously-red `applications:` cells). Two
    principal-identity cells (`TestPeerIdentityIsResolvedOnce…_5278`,
    `TestANewConnectionGetsAFreshIdentity_5278`) fail identically on the
    pristine base — pre-existing, unrelated to this change.
  - Mutation proofs (temporary, reverted): dropping the `chassis`
    registry entry, repricing `test-policy:` to view, fabric-admitting
    `route-all`, adding an unregistered `zzbogus-16136` handler case, and
    adding an unregistered `zzbogus-verb-16136` handler verb each red the
    census.
- **Risk**: Registry lookups happen on the unary authz path (ShowText /
  SystemAction admission), not on a dataplane/hot path; the lookup is an
  exact map hit plus a short longest-prefix scan over pre-sorted rules,
  replacing the identical pre-existing scan — no new per-request
  allocation of consequence (entry slices are copied only by the
  `Entries()` census accessors, not by lookups). Fail-closed directions
  are unchanged: unknown topic → `PermAll` + `InvalidArgument` at
  dispatch, unknown verb → `PermMaint`, fabric admission stays exactly
  `chassis-forwarding` + `clear-persistent-nat` + targeted failover.
