# Issue #15048 — VRRP track-interface bypassed the SSOT resolver and committed undeclared (A25-01)

- **Timestamp**: 2026-10-18
- **Action**: `CollectInstances` resolved the instance interface through the
  SSOT `cfg.ResolveKernelIfName` (#5083) but `TrackInterface` through the
  slash-to-dash-only `config.LinuxIfName`, and no commit gate checked that
  the tracked name denotes a configured interface or unit. A track ref of
  `ge-0/0/1.0` stored `ge-0-0-1.0`, a VLAN unit stored its base device, a
  reth stored `reth1`, and `ge-0/0/9` stored a name for a device that does
  not exist — every one resolving to no (or the wrong) netdev, so
  `seedTrackState` held the group at priority-minus-cost for the life of
  the config and link events, matched by exact kernel name, never arrived.
  Fixed on both halves of the cited mechanism:
  - `pkg/vrrp/vrrp.go`: `TrackInterface` now goes through
    `resolveTrackInterface` → `cfg.ResolveKernelIfName` (empty stays
    empty), the same SSOT as the instance interface. Bare and unit-0
    spellings resolve exactly as before; VLAN-unit and reth spellings now
    yield the real device (`ge-0-0-1.100`, the reth's physical member).
  - `pkg/config/compiler_validate_strict_vrrp_trackref.go` (new):
    `validateVRRPTrackInterfaceRefStrict` rejects, at commit /
    commit-check, a track-interface that `unresolvedInterfaceRef` (the
    shared #9405/#9406 declared-reference check, over the both-spellings
    declared index) reports as naming no configured interface, no
    configured unit, or an unparseable unit. Wired in
    `compiler_uniformgates_cluster_zone.go` after the cross-group VIP
    gate; `lenientVRRPTrackRef` (`compiler_opts.go`, set in
    `lenientCompileOpts`) downgrades it to a warning on the tolerant
    load / peer-sync paths (#1960 no-brick).
  - NOT changed: RETH instances (they never carry track config), the
    duplicate/cost track shape gates, and any resolution behaviour
    outside `CollectInstances`' track field.
  - Fixtures that tracked a never-declared `ge-0/0/1` now declare it (and
    `ge-0/0/2`/`ge-0/0/3` where a second tracked name is used):
    `pkg/config/vrrp_track_test.go`,
    `pkg/config/dual_ast_differential_test.go`,
    `pkg/config/vrrp_misplaced_auth_14403_test.go`,
    `pkg/config/vrrp_track_secret_5195_test.go` (declarations only; no
    assertion changed).

  unit-zero (`ge-0-0-1.0`), VLAN-unit, reth and reth-unit cells;
  `TestVRRPTrackInterfaceRefStrict15048` committed `ge-0/0/9`,
  `ge-0/0/1.7` and `ge-0/0/1.foo` clean and the lenient cells warned about
  nothing. GREEN after the fix: both new tests pass, the declared
  controls (bare, unit-0, VLAN unit, reth, dash spelling) commit, and
  `go test ./pkg/vrrp/ -count=1` plus the VRRP/track config test set pass.
  `TestInstanceNameBlindPopulationIsRatcheted9091` fails identically on
  clean `origin/master` (base-attributed, unrelated arming drift).
- **Risk**: Configs in the field that track an undeclared interface —
  previously committed silently and held demoted — now fail strict
  commit and must name a configured interface/unit; tolerant loads still
  boot with a warning. No wire or snapshot change (the tracked name was
  and remains a `pkg/vrrp`-internal string).
