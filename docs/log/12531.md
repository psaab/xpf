# #12531 — restore per-QNH RIP metrics via offset-lists

- **Action**: deliver the configured qualified-next-hop metric to RIP
  with ripd-native `offset-list` lines in the integrated `router rip`
  stanza, superseding the #12071 RIP limitation.

## Why

#12071 kept the shared QNH route-map metric-free and installed the
metric only in ospfd, because on FRR 10.7.1 `vtysh -d ripd -f` exits 0
without applying anything and integrated `vtysh -f` broadcasts the
metric action to other daemons. This lane re-probed the transport on
the locally installed FRR 10.7.1 (isolated netns, zebra/mgmtd/staticd/
ospfd/ripd) and found a stronger blocker plus a working alternative:

- `vtysh -d ripd -f` overlay: ripd still has no route-map (silent no-op).
- `vtysh -d mgmtd -f` overlay: the `set metric` action lands in ripd
  *and* creates match-less copies in zebra/ospfd — not ripd-confined.
- Route-map `set metric` present in ripd (RIPMET map, integrated base):
  readback shows metric 7, yet `show ip rip` stays at metric 1 and the
  RIPv2 wire (tcpdump decode of the route entry) carries metric 1.
  ripd simply ignores the route-map metric for redistributed statics.
- `offset-list <acl> out 6 <iface>` in `router rip`: the RIP database
  stays at 1 (expected — offsets apply on egress), but the RIPv2 wire
  carries metric 7 for the ACL-matched prefix and metric 1 for the
  unmatched prefix. The offset-list is ripd-native configuration that
  lives only inside `router rip`, so no non-RIP daemon can apply it.

The issue's premise ("when FRR provides a transport that confines
configuration to ripd") is therefore met by a different mechanism than
the anticipated daemon-scoped route-map load: the offset-list *is* the
daemon-confined installation, and unlike the route-map action it
actually takes effect in RIP.

## What

- `pkg/frr/qnh_metric_11447.go`: `ripQNHMetricACLName12531` (hashed
  `xpf-qnh-rip-*` name per scope+destination),
  `ripQNHMetricOffset12531` (offset = metric-1, clamped to wire metric
  16; metric 0 unrepresentable), `ripQNHMetricRoutes12531` (IPv4 only,
  lowest metric wins per destination), `renderRIPQNHMetricACLs12531`
  (ACL definitions gated on a bare-static RIP export in that scope),
  `renderRIPQNHMetricOffsets12531`. The stale ripd warning in
  `qnhMetricDaemonOverlays11447` is removed; OSPF overlay unchanged.
- `pkg/frr/protocols_render_rip.go`: emits the offset lines inside
  `router rip` after the redistribute chain.
- `pkg/frr/policy_render.go` + `pkg/frr/manager.go`: thread the
  FullConfig so ACL definitions render beside the QNH prefix-lists.
- Scope cuts (deliberate): policy-exported RIP keeps authored policy
  metric semantics (no offset); interface-qualified QNH routes key on
  destination only (offset-lists cannot express a next-hop/interface
  discriminator — the lowest metric per destination wins); metric 0
  renders no offset (RIP wire metrics start at 1).

## Risk

- The offset key is destination-only: two QNH backups for one prefix
  with different next-hops collapse to the lowest metric in RIP (OSPF
  still discriminates per next-hop). Documented in README.
- RIP metrics clamp at 16 (unreachable); a QNH metric above 16 marks
  the route unreachable in RIP rather than wrapping.
- The RIP database (`show ip rip`) still displays metric 1 by design;
  operators must read the wire/peer view for the advertised metric.
