# #12168 — rebind cluster comms when management VRF membership converges

- **Issue**: #12168 — HA heartbeat sockets can remain unbound after a failed boot publishes management-VRF membership later.
- **Branch**: `fix/12168-vrf-retry`
- **Worktree**: `/var/worktrees/12168-vrf-retry`
- **Base**: `1c384b9a47ff7d6e567fa50632faa75c3995ae87`

## Why

Cluster comms can start before the management-VRF interface set is published. The heartbeat retry loop previously captured the VRF device once, and step 20 compared only configured endpoints, so a later successful apply could leave the original unbound heartbeat active even after the control interface was enslaved to `vrf-mgmt`.

## What

- Resolve the heartbeat VRF membership on each retry attempt rather than freezing it before the retry loop.
- Include the selected session/heartbeat socket VRF binding in `clusterTransportKey`; step 20 now restarts comms when membership convergence changes the binding. Its candidate-key resolution is quiet, avoiding a warning on every apply.
- Add regression coverage for the key transition, apply-tail restart, and a failed-boot-to-converged kernel-VRF path. The kernel acceptance test verifies the replacement heartbeat is bound to `vrf-mgmt`; a cluster test independently inspects `SO_BINDTODEVICE` on a real heartbeat socket.
- Keep test side effects isolated: DNS reconciliation uses a temporary reconciler, and the kernel test uses temporary user/network/mount namespaces with `/var/lib/xpf` bound to a temp directory. Its cleanup joins the keyed epoch worker before unmounting.
