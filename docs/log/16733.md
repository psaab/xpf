# #16733 — managed faillock `even_deny_root` locks root out of console

- **Timestamp**: 2026-10-25
  - **Action**: The #14973 managed `pam_faillock.so` lines in
    `/etc/pam.d/common-auth` carried `even_deny_root`, and the
    per-user faillock tally is shared across every PAM service that
    includes `common-auth` (`sshd`, `login`, `su`, `sudo`, …). sshd
    runs PAM even for root attempts it will itself reject
    (`PermitRootLogin != yes`) with a substituted fake password, so
    five failed root passwords from any network peer locked root out
    of the local console (`login`) and `su -` for 300 s, repeatably —
    the Junos CVE-2017-10604 pattern, against the documented console
    lifeline. Fix: each managed faillock line (preauth/authfail/
    authsucc) is now preceded inside its managed block by
    `auth [success=1 default=ignore] pam_succeed_if.so service in sshd
    quiet_success quiet_fail`, so for every non-sshd service the
    guard skips exactly the one following faillock line (tally is
    neither consulted nor written, and a console success no longer
    clears the sshd tally via authsucc), while for sshd the guard
    returns PAM_IGNORE and the faillock line runs unchanged —
    `even_deny_root`, deny=5/fail_interval=600/unlock_time=300 and
    the #14973 sshd-side root lockout are preserved. The pre-#16733
    unguarded bodies and the pre-#14973 legacy bodies are recognised
    as known-good variants in `stripPAMFaillockBlock`, so hosts
    carrying either upgrade in place and remain strippable on
    rollback; tampered bodies or guard lines are still refused.
    NOT changed: tally remains in `common-auth` (no new host file in
    `/etc/pam.d/sshd`, so no new rollback surface), counters and
    thresholds, the appliance skip, the custom-stack refusal, or the
    #15229 advisory-failure posture.
  - **File(s)**: `pkg/daemon/ssh_faillock_11492.go`,
    `pkg/daemon/ssh_faillock_16733_test.go` (new),
    `pkg/daemon/testdata/faillock_pamtest_16733.c` (new PAM harness),
    `pkg/daemon/ssh_faillock_11492_test.go` (guard count pin),
    `pkg/daemon/ssh_faillock_14973_test.go` (legacy-upgrade wording),
    `docs/config-schema.md`, `docs/log/16733.md`
  - **Validation**: new cells in `ssh_faillock_16733_test.go`:
    `TestRenderSSHPAMFaillockGuardedToSSHD16733` (guarded shape,
    [success=1] jump target, idempotence/reversibility),
    `TestRenderSSHPAMFaillockUpgradesUnguardedRules16733`
    (unguarded→guarded byte-identical upgrade, strip, tamper
    refusal), and `TestPAMFaillockSSHDOnlyScoping16733`, which
    renders the production stack and executes it with the host's
    real libpam modules plus a stub `pam_unix.so` verifier and a
    per-test tally dir: five sshd root failures leave sshd refusing
    root (correct password included) while console (`login`) root
    login with the correct password succeeds, a console success does
    not clear the sshd tally, and a non-root user's sshd lockout
    still works. The identical sequence over the reconstructed
    pre-fix unguarded stack is the in-cell RED control: console root
    login is denied there. Existing #11492/#14973/#15229/#16421
    faillock suites stay green (full faillock set in the commit
    body). `go vet ./pkg/daemon/` clean, gofmt clean.
  - **Risk**: Hosts already carrying the unguarded block are
    rewritten once on the next SSH apply (same upgrade machinery as
    #14973/#16421; rollback restores the exact prior bytes). A
    service literally named `sshd` other than OpenSSH would share
    the tally — that is the stock Debian service name the fix
    targets. The executed PAM cell skips when gcc, libpam.so.0, or
    the host PAM modules are unavailable; the render cells always
    run.
