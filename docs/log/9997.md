# Issue #9997 — WireGuard cross-unit duplicate peer pubkeys

## Finding

Issue #9997 reported that duplicate WireGuard peer public-key validation was
scoped to one tunnel / one compiled unit. Under an interface-level WireGuard
tunnel, each unit inherits the interface peer slice and appends its own peers.
Two units could therefore author the same additional pubkey with different
AllowedIPs, pass strict commit, and then reach `mergeWireguardUnitPeers`, whose
first-wins pubkey dedup silently dropped the later unit's routing intent.

The emitter comment claiming that the merge cannot conflict was consequently
too broad: the per-tunnel validator only established that property within one
unit. The comment now states the per-unit strict scope, the separate merged-view
gate, and the defensive first-wins behavior retained for tolerant loads.

## Fix

`pkg/config/compiler_validate_wireguard.go` now runs a merged-view gate for
each interface-level WireGuard tunnel after the existing per-tunnel and identity
gates. It walks units in deterministic numeric order, removes the interface
peer keys that are intentionally inherited by every unit, and tracks the
unit-owned keys that feed the one emitted endpoint. A key authored by two
different units is rejected before emission, with both canonical unit refs
(for example, `wg0.1` and `wg0.2`) in the diagnostic. Unit-only WireGuard
interfaces remain per-endpoint and retain their existing behavior.

The tolerant path downgrades the merged conflict to a warning naming the
pubkey and both units, then preserves the existing first-wins emitter behavior:
because units are merged in ascending numeric order, the lowest-numbered unit's
copy survives. This lets an already-persisted config load without a boot
blackout while making the dropped routing intent visible.

`pkg/config/compiler_validate_wireguard_9997_test.go` adds three issue-specific
fail-on-revert cells:

- cross-unit duplicate pubkey: strict rejection names both units;
- single-tunnel duplicate behavior and valid per-unit / cross-interface
  controls remain unchanged;
- tolerant loading warns with both units and still installs the duplicate key
  once through the defensive first-wins merge.
