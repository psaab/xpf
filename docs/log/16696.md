# #16696: legacy-mode `handleClusterEvent` never ran the RG service edges

- **Timestamp**: 2026-10-25
- **Action**: In legacy non-strict mode (`no-private-rg-election`,
  rg-state desired = `clusterPri || allVrrpMaster`), either the cluster
  input or the VRRP input can be the one that flips desired, but only the
  `watchVRRPEvents` and reconcile `tr.Changed` arms ran
  `applyRethServicesForRG` / `clearRethServicesForRG`. When the cluster
  event flipped desired — VRRP-BACKUP-first demotion of a preempt
  failback, or cluster-first promotion — the service edge was lost
  permanently, because every later input reports `Changed=false`: the old
  owner kept its Kea RG groups and skipped the #15194 RG-anchored SA
  terminate; a cluster-first new owner never applied Kea or the data-RG
  IPsec re-initiate. Fixed both ways the issue's acceptance allows:
  (1) `handleClusterEvent` now drives the edge from its own transition
  via `driveRethServicesEdge` on both the primary and demotion branches
  (direct-VIP mode excluded — it owns services inside
  `reconcileDirectVIPOwnership`); (2) a level-triggered converger in
  `reconcileRGState` compares `snapshotRethMasterState` against the
  last-applied service ownership (`rethServicesApplied`, advanced at the
  tail of apply/clear) every pass and re-drives a lost edge exactly once
  — which also repairs edges swallowed by discarded hold-mirror
  transitions (the R3-A34-03 class, owned by #16692). Idempotence when
  both inputs arrive: the second reports `Changed=false` and the
  converger sees desired == applied, so no double-apply/clear.
- **File(s)**: `pkg/daemon/daemon_ha.go` (helpers
  `markRethServicesApplied`/`rethServicesAppliedFor`/`driveRethServicesEdge`/
  `convergeRethServices`, two `handleClusterEvent` call sites, reconcile
  converger arm, marker writes in apply/clear),
  `pkg/daemon/daemon.go` (`rethServicesApplied` field + `New` init),
  `pkg/daemon/reth_services_cluster_edge_16696_test.go` (new),
  `docs/log/16696.md`.
- **Validation**: `go vet ./pkg/daemon/` clean. New tests use the
  proxy-ARP nudge (sent unconditionally by both apply and clear, by no
  other code in these handlers) as the service-edge observable:
  cluster-first and VRRP-first promotion rows, VRRP-first and
  cluster-first demotion rows, and converger promotion/demotion rows
  each assert the edge ran exactly once across the full input sequence.
  RED-on-revert: removing the `handleClusterEvent` call sites fails the
  cluster-edge rows; removing the converger arm fails the converger
  rows; removing the marker writes fails the idempotence assertions.
- **Residual**: The demotion converger row drives the discarded edge via
  a direct `SetCluster(false)` on the state machine rather than a live
  hold-mirror refresh, because reconcile re-derives the kernel-upgrade
  hold from the (unarmed) cluster manager; the promotion converger row
  uses the real `SetSyncHold` release shape. #16692's own producer
  (VRRP-path mirror refresh) remains its owner's fix; this converger
  repairs its service-edge symptom as a side effect.
