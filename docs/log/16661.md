# A commit confirmed that removes or renames a feed can now roll back (#16661)

- **Issue**: #16661 (R3-A32-01).
- **Cause**: C1 binds `dyn1` to feed `malware`; `commit confirmed` of C2
  removes or renames the feed. The arm gate passes (C1's feed is live), then
  C2's apply runs `reconcileFeeds(C2)` and cancels the `malware` producer
  with its snapshot discarded. At fire time
  `confirmRollbackTargetHandledAtFire` refuses C1 feed-only
  (`SnapshotForBindings` omits `dyn1`), deferral runs 24 × 5 s waiting for a
  producer only the rollback's own apply would restart, then
  `PromoteRollback` + `enterBootstrapMode` retire takeover files, clear the
  FRR managed section, detach the dataplane, and resign every RG.
- **Change**: `pkg/daemon/confirm_rollback_preflight_9615.go`.
  `rollbackTargetFeedProducersAbsent` reports whether any feed named by the
  target's bindings has no running producer (`feeds.Manager.AllFeeds`).
  Before classifying a feed-only refusal, the fire path reconciles the feed
  producers FOR THE TARGET (`reconcileFeeds(target)` — the same step a
  normal target apply runs at `daemon_apply_dataplane.go`) and restarts the
  bounded deferral (`delete(d.confirmFeedDeferrals, gen)`), so the async
  fetch converges through `onUpdate` / the next deferred fire and the
  normal rollback then applies C1. Bootstrap is never reached for a
  feed-only refusal whose producer was absent. A producer that exists but
  has not fetched yet (late feed, #9615) or exists and never installs
  (server down) keeps the existing semantics: bounded deferral, then the
  #9615 safe state. No-manager / half-built daemon (#6739:
  `reconcileFeeds` early-returns, classifier returns false) keeps the
  pre-fix deferral→cap→bootstrap behaviour. DNS-only (#16612), statically
  refused, and healthy targets are unchanged; the arm-time #6707 gate is
  untouched.
- **Regression coverage**: `pkg/daemon/confirm_rollback_feed_producer_16661_test.go`
  — real `feeds.Manager` against an httptest TLS feed server; the apply
  body runs only the real `reconcileFeeds` (the production step the defect
  rests on). Defect arm (C2 removes the feed) and rename arm (C2 renames
  `malware`→`malware2`) both apply `c1-feed-target` with `bootstrap=false`;
  the classifier pins absent vs present-but-unfetched vs no-manager; the
  feed-still-down control (producer restarted, server dead) still takes
  the bounded safe state without applying and without deferring forever.
  Before the fix the defect arms end in bootstrap after the cap with C1
  never applied (probe behaviour, R3-A32-01).
- **Risk / residuals**: While the target's producers run during the
  deferral, `onUpdate` applies the still-active C2 with the target's feed
  overlay — C2 binds no removed feed, so this is snapshot-idempotent, and
  the bounded deferral guarantees the window resolves (apply or safe
  state) within 24 × 5 s of the producer restart. No end-to-end lab run;
  bootstrap teardown remains demonstrated in-process only, as in the
  source probe.
