# #12615 — superseded STOPPED cut must not adopt an unverified target

- **Timestamp**: 2026-10-13 (`fix/12615-campaign-pub`)
  - **Action**: recover a STOPPED cut whose FLIP 6a changed `current` before a newer staged version starts a fresh cut.
  - **File(s)**: `pkg/upgrade/cutover.go`, `pkg/upgrade/cutover_12615_test.go`, `pkg/upgrade/stopped_recovery_restart_5846_test.go`, `docs/in-place-upgrade.md`, `docs/log/12615.md`

## Red before

`TestCut_SupersededStoppedAfter6a_RollsBackToKnownGood_12615` went RED before the fix. It seeded a known-good 1.0.0 runtime, a STOPPED journal for 2.0.0 with `current` already repointed to 2.0.0 but systemd still loaded on 1.0.0, and a newly published 3.0.0. With 3.0.0 health forced to fail, the old code recorded 2.0.0 as its `PreviousVersion` and rolled back to that unverified version instead of 1.0.0.

A manual mutant disabling the STOPPED/current recovery check also went RED: `current after failed 3.0.0 cut = "2.0.0"`, expected known-good `1.0.0`.

When a superseded STOPPED journal has `current` at its target, recovery
validates the journaled previous runtime, stops the unit, and flips back to
that known-good version before restarting the unit and beginning the fresh cut.
It deliberately does not restore the stale DB snapshot, so commits made by a
restarted old daemon after STOP are preserved. If a crash interrupts that
restore after `current` changes but before `daemon-reload`, the next run checks
both the loaded `ExecStart` and running executable, then re-flips/reloads the
known-good version before starting. Unexpected `current` values, an
unrestorable previous runtime, or lifecycle errors fail closed and retain the
journal. Updated the state-machine documentation to describe both recovery
steps.

## Risk

Recovery now performs an explicit stop + flip to the journaled previous version only when a superseded STOPPED cut has already repointed `current` to its unverified target. Errors stop the fresh cut and preserve recovery evidence; the prior runtime's DB is not rolled back, protecting any post-STOP commits.

### Fold risk

Stale STOPPED recovery now execs `PreviousVersion`'s `--capability-check`
probe. If the probe fails or the live envelope is malformed, recovery now
refuses and waits for the operator instead of restarting the daemon. A
post-stop refusal leaves the unit down; the postinst safety net may then
restart whatever `ExecStart` is still loaded. A refusal does not undo an
earlier attempt's partial restore (R6), so a reboot before the operator
resolves it would start `PreviousVersion` on the migrated DB.
