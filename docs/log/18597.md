# #18597 — a config commit must not bounce em0 (the cluster control link)

- **Branch:** `fix/18597-em0-bounce` (worktree `/var/worktrees/fix-18597`,
  from origin/master `9370dd0f93`)

## Root cause (measured, not inferred)

Two networkd behaviours combined, then the daemon repaired them every commit.

1. `.network` rows for vrf-mgmt members rendered `VRF=vrf-mgmt`. vrf-mgmt is a
   daemon-created netlink VRF, not a networkd `.netdev`, so networkd logs
   `vrf-mgmt NetDev could not be found, ignoring assignment` on every load and
   treats the link as having NO master. A reconfigure therefore sets
   `IFLA_MASTER=0`; the kernel VRF driver cycles a link on every enslave and
   release, and its addresses go with it.
2. `Apply` reconfigured EVERY managed interface whenever ANY generated file
   changed. `set interfaces fxp0 description X` changes only
   `10-xpf-fxp0.link` (`Description=`), yet em0 was reconfigured.
3. The step-2.7 rebind moved em0 back (a second cycle) and
   `RestartHeartbeat` ran unconditionally after it, rebuilding the heartbeat
   sockets while the address was mid-move.

## Fix

- `pkg/networkd`: a row with `VRFName` renders `KeepMaster=yes` instead of
  `VRF=` (unless it names a networkd-owned Bond=/Bridge= master). `Apply`
  reconfigures only the interfaces whose files changed in this call plus
  owed names; a pass that inherits an earlier call's obligation still
  reconfigures all.
- `pkg/routing`: `VRFMasterMoveSeq(name)` counts the IFLA_MASTER changes the
  manager actually made.
- `pkg/daemon`: `restartHeartbeatIfControlLinkMoved` restarts the heartbeat
  only when the control link's count moved (or, post-networkd, a restart is
  owed), and runs right after the step-0b bind, after the step-2.7 rebind,
  and after `mgmtVRFReassertLoop` moves a drifted control link back (before,
  that loop rebound em0 and never restarted the heartbeat).

## Review fold: config-derived LocalAddress (seats AH and AG on 835a2b4e88)

Both seats found the same BLOCKING regression in the renumber fold: the key's
`LocalAddress` was resolved from the LIVE interface, and step 20 compares the
whole key on every apply. A direct-cabled control link loses carrier when the
peer reboots, networkd drops em0's static address, and the survivor's next
apply (an operator commit, or an fxp0 DHCP renewal re-entering applyConfig)
saw `""` and tore comms down: generation 1 -> 3, heartbeat left stopped,
reassert churn every 30 s until the address returned. AG found a second edge:
two IPv4 addresses on em0 can be listed in a different kernel order between
the heartbeat's, the sync's and step 20's lookups.

Fix (AG's shape): `LocalAddress` is derived from CONFIG — the control unit's
static addresses paired with `peer-address` by the same `selectClusterBindAddr`
rule — so it depends only on config and a renumber is a config change. `""`
(no static address) is unknown on either side (`sameClusterTransport`). A bind
on an address config does not give the unit marks `BindingChanged`; membership,
not equality, so a kernel reorder of two configured addresses is not a change.

Cells: transient absence (AH/AG probe: no restart, same generation, heartbeat
still on 127.0.0.1; the combined revert reproduces AH's 1 -> 3), kernel reorder
of two configured addresses, config renumber still restarts and settles,
off-config bind marks the epoch, boot edge, peer-family pairing. Mutants killed:
kernel-derived key, helper removed, equality instead of membership, key
ignoring the address, no-static config marking, off-config bind never marking.

Also (AG MINOR): the failed-link query reads the SETUP column of `networkctl
list --no-legend --no-pager` instead of `--json=short`, which carries every
link's routes (about 350 B per route; hundreds of MB with a full BGP table, and
possibly over the varlink message cap, which would have made every commit a
silent full pass). 536 B against 32.9 KB on tcp fw0. Parse errors still fall
back to the full pass; parser mutants killed.
