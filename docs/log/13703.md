# #13703 — publish scheduler receipt before version

## Why

`SchedulerHeartbeatLease::apply` exposed a nonzero version with the prior
receipt timestamp because the successful version CAS came first. A worker
could then see an expired lease during a heartbeat update and fail-close a
scheduled permit.

## What

- Store `received_at_ns` before release-publishing `version`; a reader that
  acquires the published version also observes the preceding receipt stamp.
- Preserve rejection of version zero and rollback. `ServerState` serializes
  control requests, so publication does not need a competing-writer CAS loop.
- Add a concurrent version/receipt invariant regression test.
- Not changed: other scheduler-policy paths; all use this lease object and
  share the same publication method.

## Validation

The targeted regression command was attempted on base `1aea24f7b` with the
new test before the fix and again after it:

```sh
CARGO_TARGET_DIR=/var/worktrees/.cache/cargo-13703 \
  cargo test --manifest-path userspace-dp/Cargo.toml \
  scheduler_lease_never_publishes_version_before_receipt_stamp_13703 \
  -- --exact --nocapture
```

Both attempts were blocked during test-binary compilation by an unrelated
master error: `afxdp/session_glue/mod.rs:59` imports
`promote::purge_translated_synced_hit`, but its definition in
`promote.rs:412` is `#[cfg(test)]`-gated. The test did not execute, so no RED or
GREEN result is claimed. The same compile also reports pre-existing warnings.

## Risk

No new timestamp/version atomic aggregate is introduced. The writer remains
serialized by the `ServerState` contract. The regression test's runtime
execution remains unverified until the unrelated test-build error is fixed.
