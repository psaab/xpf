# 10285 — fragmented-transit overlap completion reclaim

## Issue grounding

`gh issue view 10285` was read in full on the assigned branch. The issue was open with zero comments, so there was no withdrawal, shipped note, or comment narrowing the implementation. Its evidence pins the comparison to `c96e0b24dbdb0c62e963608f3dbf9f228a3d051c` and the research evidence to `8f7563c8a42486f8fac57091b625118cdf6c19f4`.

The current master code confirmed the material claims:

- `OverlapTracker` has 16 shards of 64 entries (`1024` total), with a 30-second idle TTL and 60-second absolute lifetime. Before this fix, the only reclaim path was TTL/absolute expiry; no successful-datagram completion path removed an entry.
- A full shard fails closed and increments `FRAG_OVERLAP_SHARD_FULL_DROPPED`. The pure pre-policy check intentionally does not reserve a slot; the post-commit check is the authoritative full-shard admission gate.
- The shard hash deliberately omits protocol and routing domain, while full key equality includes `routing_domain`. Thus same-shard contention can be cross-domain availability contention, but identical tuples in isolated VRFs do not false-overlap. This preserves the issue's availability direction without reopening cross-VRF poisoning.
- The old post-commit gate ran after forward/session/zone accounting, so a shard-full drop could be counted as a forward candidate. The gate now runs before those accounting sites.
- The cap arithmetic is `1024 / 30 = 34.13` new datagrams/s under the idle TTL. A same-family translated post-key can plant a second entry, giving approximately `17.07` datagrams/s for that case.

## Change

- IPv4 MF and IPv6 M are carried from `overlap_parse` into the tracker. A terminal fragment is completion-eligible only when its declared payload is fully present on the wire; truncated terminal fragments remain incomplete.
- Entries remember the terminal end. Completion requires the coalesced ranges to start at offset zero, contain no gap, and end exactly at the terminal end. Tail-first and gap-before-last arrival are therefore safe.
- A completed record returns a revision-bearing completion snapshot plus a
  linear admission token. Reclaim is deferred until all pre/post-translation
  admissions reach accepted TX/slow-path delivery; only an explicit commit
  consumes those tokens and releases the entry. Failed build, rewrite, queue,
  output-filter, and teardown paths retain the ranges until TTL/absolute expiry.
- Shard-full remains fail-closed and is observable through `FRAG_OVERLAP_SHARD_FULL_DROPPED`; shard-full drops are no longer forward-accounted.

## Follow-up: transactional admission ownership

The review follow-up converted completion-only release into a linear admission
reservation carried by `PendingForwardRequest`, `TxRequest`, and
`PreparedTxRequest`. A reservation is committed only after the TX descriptor is
accepted; every queue eviction, builder failure, rewrite refusal, output-filter
drop, and teardown path drops the reservation and permanently keeps the
datagram ranges as overlap protection until the normal TTL/absolute sweep.
Pre- and post-translation reservations carry a stable entry incarnation, so an
old token cannot reclaim a remove/reinserted key. IPsec passthrough now performs
the late overlap reservation before reinjection and commits only when slow-path
delivery returns accepted.
