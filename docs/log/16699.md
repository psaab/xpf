# #16699 - route-based VPN capture limit not enforced at commit

- **Timestamp**: 2026-10-25
- **Action**: The IPsec capture generation is bounded to 32 distinct route-based VPN capture tunnels (`ipsecCaptureMaxTunnels`, four NFQUEUE provenance classes each), but no commit-time limit existed. A 33rd distinct `bind-interface` committed cleanly, `stageIpsecCapture` discarded the bound error (`staged, _ = quarantineWith(QUEUE_OPEN, errIpsecQueueExhausted)`) and returned a `QuarantineAll(QUEUE_OPEN)` runtime with a nil error, and `commitIpsecCaptureStage` installed it — every apply dropped all non-loopback, non-lifeline kernel INPUT/FORWARD while reporting success (residual of #15068). Fix, mirroring #10638: (1) `pkg/config` exports `MaxRouteBasedVPNCaptureTunnels = 32` and the #2933 AST gate (`validateSecureTunnelBindInterfaceAST`) now counts DISTINCT non-zero XFRM if_ids and hard-rejects above the limit on the strict commit/commit-check path naming the limit, while the lenient load/peer-sync path warns and still boots (#1960); VPNs sharing one bind-interface count once. (2) `pkg/daemon` aliases `ipsecCaptureMaxTunnels` to the config constant so commit-time and runtime cannot drift, and every QUEUE_OPEN `quarantineWith` site in `stageIpsecCapture` (per-generation bound, queue alloc, queue open, reinject submitter) now RETURNS its wrapped error — the staged quarantine runtime is still installed fail-closed by `commitIpsecCaptureStage`, but `captureStageErr` joins the apply error so an over-cap fails the commit visibly. Unknown-reason quarantines keep their nil return (out of the QUEUE_OPEN scope). NOT changed: the 32-tunnel capacity itself (raising it is a separate allocator/queue-number decision), and the plan-level quarantines (IFIDUnderivable/LinkLookup/OwnerContested), which the strict compiler already rejects or which are runtime link states.
- **File(s)**: `pkg/config/compiler_ipsec_bindiface.go`, `pkg/config/compiler_ipsec_bindiface_limit_16699_test.go` (new), `pkg/daemon/ipsec_queue_lifecycle.go`, `pkg/daemon/ipsec_capture_wiring_9506.go`, `pkg/daemon/ipsec_capture_queue_capacity_15068_test.go`, `pkg/config/README.md`, `docs/log/16699.md`
- **Validation**: Targeted tests (see PR): config strict 33-reject / 32-control / lenient-warn / distinct-counting, daemon 33-tunnel QUEUE_OPEN stage now requires a non-nil limit-naming error wrapping `errIpsecQueueExhausted` while 31->32 and rezone-32 controls still stage clean. RED evidence recorded in the PR (reverting the compiler arm accepts 33; reverting the stage error return yields a nil stage error).
- **Risk**: A persisted or peer-synced config already over 32 distinct tunnels still boots leniently but its applies now fail visibly with the QUEUE_OPEN stage error while the quarantine guard stays installed (fail-closed, management lifelines preserved) until VPNs are removed via fxp0/console — strictly better than the prior silent false-success, but operators on such a config will see apply failures where they previously saw success. No per-packet cost; commit/apply-path only.
