# #18966 — shimverify attestation mktemp honors the pre-sudo TMPDIR

- **Timestamp**: 2026-11-03
- **Action**: Capture the gate-attestation directory before the sudo hop and pass it to `mktemp -p` explicitly in both of `run_verifier`'s arms, so the attestation lands under the caller's TMPDIR instead of sudo-scrubbed `/tmp`.
- **File(s)**: `pkg/dataplane/build-userspace-xdp.sh`, `pkg/dataplane/userspace_xdp_attestation_tmpdir_18966_test.go`, `docs/log/18966.md`

## Why

`run_verifier`'s non-root arm ran `sudo -n mktemp -t shimverify-attestation.XXXXXX`. sudo scrubs TMPDIR from the environment, so `mktemp -t` resolved the template against `/tmp` no matter what the caller exported — the Makefile pins `TMPDIR ?= /var/worktrees/.cache/tmpdir` (#14833) precisely so build scratch never lands on `/tmp`. On a workstation whose `/tmp` tmpfs is full (this one: `df` shows 32G/32G, 0 available all session), the attestation was created there and shimverify's verdict write failed with ENOSPC, so `make generate-userspace-xdp` died at the verifier gate — parent-reproduced on 2026-11-03 during PR #18965's verification, blocking its mandatory manifest regeneration. The root arm relied on the same implicit `-t` TMPDIR lookup instead of a directory the recipe captured. Consumption is unchanged: `shimverify <candidate> --gate-verdict <path>` writes the verdict (`cmd/shimverify/main.go:130`), the recipe installs it as `pkg/dataplane/userspace_xdp_gate_verdict.json` (read by `TestCommittedVerdictCarriesProvenance15218` and the release retention workflow), and the EXIT trap removes the temp file by absolute path (root `rm -f` / `sudo -n rm -f`) — all path-agnostic, so moving the location changes no consumer.

## What

- Capture `ATTESTATION_TMPDIR="${TMPDIR:-/tmp}"` in the parent script before the verifier hop — the same explicit-across-sudo threading the `XPF_SHIM_*` provenance vars use, except the directory travels as mktemp argv (`-p`), not env, so sudo's scrubber cannot touch it. The `/tmp` default preserves the old `mktemp -t` semantics when the caller exports no TMPDIR.
- Both arms create the attestation with `mktemp -p "${ATTESTATION_TMPDIR}" shimverify-attestation.XXXXXX` (root arm direct, sudo arm under `sudo -n`). Gate semantics, verdict format, exit-code arms, install, and cleanup are untouched.
- Layered regression coverage in `userspace_xdp_attestation_tmpdir_18966_test.go`: a comment-stripped structural pin (both arms' attestation mktemp must reference `ATTESTATION_TMPDIR`, must not use the ` -t ` shape, capture must precede them, sudo arm must carry `-p` argv) and a behavioral probe driving the real recipe through `run_verifier` with stand-in cargo/go (#17729 fixture shape) whose stub shimverify records the `--gate-verdict` path it received, requires the file to exist inside the caller-set TMPDIR at invocation time, and requires the EXIT trap to leave that TMPDIR empty. Under this repo's testguard (private net+mount ns, uid mapped to 0) the probe exercises the root arm; on a genuinely non-root host with passwordless sudo it exercises the sudo arm. The pre-fix `-t` shape happens to honor TMPDIR in the unscrubbed root arm, so red/green discrimination for the scrubbed sudo arm is carried by the structural pin — stated in the test's doc comment.

## Risk

Low. The attestation location is the only change; every consumer is path-agnostic. `mktemp -p DIR` is supported by GNU coreutils and BusyBox (probed on this host). With TMPDIR unset the behavior matches the old `/tmp` default exactly. The sudo arm's root-owned attestation now sits in a caller-owned directory; the existing `sudo -n rm -f` cleanup (exercised in the proof runs) removes it, and `chmod 0644` before the verifier keeps the parent-side `install` readable. The structural pin intentionally matches the recipe's code shape; a future relocation of the capture must keep threading a pre-hop directory into both arms or the pin fails loudly.
