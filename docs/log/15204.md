# #15204 — config: name-server multi-value leaf validator/compiler mismatch (A13-03)

- **Timestamp**: 2026-10-19
- **Action**: Validate every key of each `system name-server` and
  `system domain-search` block-list child at strict commit, matching
  the `firewallMatchValues` compiler reader, instead of checking only
  the first key per child.

## Mechanism

`validateMultiValueLeaf` (`pkg/config/schema_walk.go`) defaults to
validating `c.Keys[:1]` per hierarchical block-list child. The compiler
for `system name-server` and `system domain-search`
(`pkg/config/compiler_system.go`, via `firewallMatchValues` in
`compiler_firewall.go`) consumes *every* child key. Neither leaf set
`allChildKeysAreValues`, so:

```text
system { name-server { 1.1.1.1 source-address 10.0.0.2; } }
system { name-server { 1.1.1.1 routing-instance foo; } }
```

committed clean (only `1.1.1.1` was validated), compiled to
`NameServers=[1.1.1.1 source-address 10.0.0.2]` /
`[1.1.1.1 routing-instance foo]`, and the daemon render belt
(`pkg/daemon/daemon_dns.go`) silently skipped the non-IP tokens while
keeping `10.0.0.2` as an extra resolver the operator never intended
as one — and any routing-instance/source-address scoping was lost
with no diagnostic. The flat spelling (`name-server 1.1.1.1
routing-instance foo;`) was already refused, because the flat tail
goes through the per-token check; only the block spelling escaped.

## Fix

- `pkg/config/schema_system.go`: set `allChildKeysAreValues: true` on
  `name-server` and on `domain-search` (the other `system` leaf read
  via `firewallMatchValues`). The walker now validates the identical
  token stream the compiler consumes, so a modifier keyword/value
  packed onto a block child is refused strictly (`invalid value
  "source-address"`, `invalid value "routing-instance"`, ...).
- NOT changed: compiler, walker default, or daemon render belt. The
  legitimate block/bracket/single shapes are token-for-token the same
  values the validators already accept, so no legitimate config changes
  behaviour; the tolerant load/peer-sync path still only *warns* via
  the existing daemon belt, which now-unvalidated persisted values
  continue to hit.

## Risk

An operator config that today smuggles a Junos `name-server`
modifier (`source-address`, `routing-instance`) in block form will
now be refused at commit instead of silently miscompiled. That is
the intended fail-closed direction; the modifier was never honoured
(the routing instance was dropped and the source address became a
resolver), so no working configuration loses function.
