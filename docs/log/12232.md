# #12232 — refuse zone-local fold collisions with literal synthetic-prefix entries

- **Issue**: #12232 — tolerant compilation could rewrite a trust-zone policy reference to `zone-local/trust/A` while preserving an operator-authored global `address zone-local/trust/A`, silently resolving the policy to the global twin instead of the zone-local definition.
- **Branch**: `fix/12232-zone-fold`
- **Worktree**: `/var/worktrees/12232-zone-fold`
- **Base**: `a714c90d472a3c3d98a3799831cfef3ec311a61c`

## Why

The zone-local fold intentionally does not overwrite a pre-existing qualified global key. But it also rewrote zone-local policy tokens to that same key and did not mark the key ambiguous, so tolerant loads could silently bind the policy to an operator-authored global entry.

## What

- Marked each qualified address or address-set key in `AddressBook.CollidingNames` when the fold's no-clobber branch preserves an existing global entry.
- Updated the early-strict comment to describe the tolerant-path policy-refusal behavior.
- Added compiler regressions for address and address-set collisions plus an ordinary-fold no-false-collision control.
- Added a userspace policy-snapshot regression proving a trust policy with the literal twin is lowered to the unsupported-address sentinel instead of a global book ID.
