# #15006 — duplicate hierarchical CoS classifier / rewrite-rule blocks overwrite each other (A09-03)

## Defect

`compileClassOfService` (`pkg/config/compiler_class_of_service.go`) built a
fresh typed object for every named instance in six loops and assigned it to
the typed map, discarding any same-named object an earlier hierarchical
block had produced:

- `classifiers dscp` → `cos.DSCPClassifiers[name]`
- `classifiers ieee-802.1` → `cos.IEEE8021Classifiers[name]`
- `classifiers inet-precedence` → `cos.INetPrecedenceClassifierDefs[name]`
  (plus an unconditional duplicate append to `INetPrecedenceClassifiers`)
- `rewrite-rules inet-precedence` → `cos.INetPrecedenceRewriteRuleDefs[name]`
  (plus duplicate `INetPrecedenceRewriteRules` append)
- `rewrite-rules exp` → `cos.EXPRewriteRuleDefs[name]`
  (plus duplicate `EXPRewriteRules` append)
- `rewrite-rules dscp` → `cos.DSCPRewriteRules[name]`
- `rewrite-rules ieee-802.1` → `cos.IEEE8021RewriteRules[name]`

`compileSections` dispatches every top-level `class-of-service` root to the
same compiler in author order, and one root can carry two `classifiers` /
`rewrite-rules` containers, so a second block naming an existing classifier
or rewrite rule silently lost the first block's BA classification or rewrite
code points — no diagnostic. Reachable through a hierarchical config file,
`load merge`, or `load override`; the flat-set spelling merged, which is
the conservation property the #8436 census exists for. This is a QoS loss,
not a security one.

Schedulers, scheduler-maps, traffic-control-profiles, and interfaces under
the same compiler already used find-or-create (#8436); these loops did not.
The #8436 census still cannot synthesize a fixture for these containers, so
they remain listed in `dupConservationSkipped8436` — the dedicated
regression below is the probe, and the skip entries stay truthful.

## Fix

Find-or-create at the compiler layer, the same rule the neighbouring
containers use:

- Each of the six map loops now looks up `cos.<Map>[inst.name]` first and
  only allocates when absent, so entries from every same-named block
  accumulate on one object. The existing `len(Entries) > 0` assignment
  guard is preserved, so a later block that contributes no entries cannot
  erase an earlier one.
- The three name slices (`INetPrecedenceClassifiers`,
  `INetPrecedenceRewriteRules`, `EXPRewriteRules`) append only when the
  name is absent (`slices.Contains`), so a merged duplicate keeps one
  entry for definedness scans and advisories.

Compiler-layer find-or-create was chosen over adding rows to
`mergeDuplicateBlocks9023` (the issue's other direction) because the
compiler must merge anyway across multiple `class-of-service` roots, and
the sibling containers in the same function already set that precedent; a
tree fold would need a separate `class-of-service`/`classifiers`/
`rewrite-rules` site family plus a second mechanism for the cross-root
case. NOT changed: `forwarding-classes` (its bijection gate already
rejects conflicting duplicates), the census skip inventory (still
unprobeable by the generic fixture), and validation/advisory consumers.

## Regression (`pkg/config/cos_classifier_rewrite_dup_15006_test.go`)

Fourteen tests, one merge cell + one different-names control per affected
family, plus the DSCP cross-root/merged equality cell and an
empty-second-block control:

- Merge cells assert duplicate == merged (two entries survive) for DSCP,
  IEEE-802.1, and inet-precedence classifiers and DSCP, IEEE-802.1,
  inet-precedence, and EXP rewrite rules; the inet/exp cells also assert
  the name slices contain the name exactly once.
- Controls assert two different names stay two distinct entries — a merge
  keyed on anything broader than the authored name would pass the merge
  cells while collapsing distinct objects.
- `TestCoSEmptySecondClassifierBlockPreservesFirst15006` pins that an
  empty later block does not erase an earlier one.

RED on current master: all seven merge cells fail with "has 1 entries,
want 2 — first block overwritten". GREEN after the fix.

## Risk

Strict commits that previously (silently) kept only the last block now
compile the union — the Junos/flat-set semantics. A config that relied on
the overwrite to shadow an earlier block changes meaning, deliberately:
that shadowing was the defect. No new rejection is introduced; malformed
code points still reject/warn exactly as before on the strict/tolerant
paths.
