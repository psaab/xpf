## Design

- **Timestamp**: 2026-09-10
- **Action**: Read the #9075 adjudication first (GEMINI-050-072: publishing
  `ConnectionName` breaks multi-selector child SAs). Chose the issue's
  preference 1 — fix the LOOKUP, not the wire. `ActiveConnectionNames` keeps
  publishing CHILD names (what `swanctl --initiate --child` needs); the
  receiver's `lookupIPsecVPNByConnName` gains a step that inverts the

  match stays first, so every name that resolved before resolves identically.
  A child name two VPNs both render is declined (RG0 default kept).
- **Wire**: unchanged, so no mixed-version cell is owed.

## Stopgap: the failed-reload regression window (Refs #9511, Refs #9641)

- **Timestamp**: 2026-09-11
- **Finding**: the Codex plan review of #9641 (finding 4), verified. The landed #9511
  (583cb8cbe) is worse than master in one window:
  1. `applyConfig` writes the new swanctl file before `reload()` and does not restore it
     on failure.
  2. `strongswan.service` (`ExecStartPost`/`ExecReload` `swanctl --load-all`,
     `Restart=on-abnormal`) loads that file on charon's own next start or reload.
  3. `ipsecLoadedCfg` still names the previous generation, so attribution targets a
     generation charon no longer runs.
  4. Master's promoted-config answer is the generation charon loaded.
  - Preconditions: a failed xpfd reload, then a charon restart or reload outside xpfd,
    then a per-RG failover, all before the next successful xpfd apply.
  - Posted on #9511 (comment 5628064710) and on #9641 (comment 5628064854).
- **Decision (lead)**: option B. A small stopgap PR, with no new issue.
- **Action**: `ipsec.Manager.ApplyWithHooks` with `ApplyHooks{Written, Loaded}`.
  `Written` fires once the on-disk config changes (a write, or a removal on the clear
  path) and before the reload; it does not fire on a render or write failure.
  `ApplyNotifyLoaded` becomes a wrapper. `applyIPsecTracked` clears `ipsecLoadedCfg` on
  `Written` and records it on `Loaded`. So in the failed-reload window attribution falls
  back to the promoted config, which is master's answer. A render or write failure keeps
  the record (disk and charon unchanged). #9511's steady-state child-SA-to-VPN mapping is
  kept.
  - **File(s)**: `pkg/ipsec/manager.go`, `pkg/daemon/ipsec_sa_rg_9139.go`,
    `pkg/ipsec/apply_hooks_window_9511_test.go`, `pkg/daemon/ipsec_sa_rg_9511_test.go`,
    `pkg/ipsec/README.md`, `pkg/cluster/README.md`

    - `Written` fires before `--load-all` with the file already on disk, and only
      `Written` fires on a failed reload;
    - no hook fires on a render failure or a write failure;
    - the clear path fires `Written` before the reload with the file already removed;
    - a success fires `Written` then `Loaded`.
