# #12959 — fence WG admits include IngressDeny addresses

- **Timestamp**: 2026-10-14 (`fix/12959-campaign-pub`)

## Why

#12846 taught the steady-state renderers that a lifeline-shared address on an
empty-admit zone lives in `IngressDenyV4` / `IngressDenyV6`, and included those
withheld values in the WireGuard owner-zone and destination mapping. The fence
surfaces kept their own `V4Addrs` / `V6Addrs`-only copy of that mapping
(`emitHostInboundFenceWGAdmits` / `emitHostInboundGapFenceWGAdmits` and the
netlink mirrors), so fence windows could diverge from the steady-state
verdict: an IngressDeny-only endpoint had no scoped fence accept, and the gap
fence's owner map ignored the withheld claims — a cross-zone-shared value was
treated as uniquely owned by its `V4Addrs` zone and admitted on that zone's
ingress even though steady state (#12846) judges it ambiguous and denies it.

## What

- The cold-boot/lo0 fence (`emitHostInboundFenceWGAdmits`) and the coverage-gap
  fence (`emitHostInboundGapFenceWGAdmits`) now reuse the steady-state
  `hostInboundWireGuardZoneAddresses` mapping instead of a private owner map,
  so `IngressDenyV4/V6` participate in ownership and ambiguity exactly as in
  the real chain. The gap variant narrows that mapping to its uncovered
  destination set as before.
- The netlink renderers (`emitHostInboundFenceWGAdmitsNetlink`,
  `emitHostInboundGapFenceWGAdmitsNetlink`) mirror the same structure; the
  private `emitFenceWGIngressAcceptNetlink` / `uniqueFenceWGAddresses` owner
  copies are deleted, leaving the steady-state mapping as the single source of
  truth on both render paths.
- Regressions: v4/v6 cold-boot + lo0 scoped admits for an IngressDeny-only
  endpoint, no-listener fail-close, same-zone gap admit ahead of the bare
  uncovered drop, cross-zone ambiguity fail-close (text + netlink), and a
  fence self-check in the T1 parity gate.

## Validation

- **Base / RED**: before the fix, `go test ./pkg/daemon/ -run
  'TestWireGuardIngressDeny(FenceAdmits|FenceNoListenerStaysFailClosed|GapFenceSameZoneAdmit|GapFenceAmbiguityStaysFailClosed)12959'
  -count=1` failed (no fence accept named the withheld address; the gap fence
  emitted the bogus unique-owner accept `iifname "ge-0-0-1" ip daddr 192.0.2.1
  udp dport 51820 accept` for the cross-zone-shared value), and `go test
  ./pkg/nftables/ -run 'TestFenceWGIngressDenyAdmittedNetlink12959|TestFenceWGIngressDenyGapNetlink12959'
  -count=1` failed the same way in the netlink plan.
- **Focused GREEN**: both commands passed after the change.
- **Fence/WG slice**: `go test ./pkg/daemon/ -run
  'Fence|FenceWG|WireGuard|IngressDeny|Gap' -count=1` passed, including the
  #11076/#11572/#5644/#6476/#12846 invariants.
- **Full packages**: `go test ./pkg/nftables/... -count=1` (0.289s) and
  `go test ./pkg/daemon/... -count=1` (`pkg/daemon` 390.562s) passed.
- **Text/netlink parity**: `go test ./pkg/daemon/ -run '^TestNftNetlinkParity$'
  -count=1 -v` passed under a real private-netns nft (10.8s), including the
  cold_boot_fence / lo0_cold_boot_fence / gap_fence cases carrying the
  IngressDeny view and the new fence self-check.
- **Vet**: `go vet ./pkg/daemon ./pkg/nftables` passed; `gofmt -l` clean.

## Risk

No global port exception: fence admits still require a unique owner zone (now
judged over both address lists) and its own ingress; zones without a listener
gain nothing. The previously bogus gap accept for a cross-zone-shared
IngressDeny value is removed (fail-closed, matching steady state). Fence
payloads may reorder WG accepts (zone-major instead of view-major); the T1
parity gate pins text/netlink equality.
