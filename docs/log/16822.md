# Issue #16822: deterministic NAT gauges hard-code the NAT64 1024-65535 window for IPv6 subscribers (R3-F08-05)

## Why

`deterministicPoolBlockCapacity` in `pkg/api/metrics_nat.go` overrode the
pool's port range with the fixed `65535-1024+1` window whenever the
subscriber CIDR was IPv6 (mode 2 / NAT64). That was correct before
#15283, which made mode 2 honour the pool's own `port range` (default
1024-65535) in `pkg/nat` (`poolParams` mode 2 via `poolPortRangeV4`),
the NAT64 wire builder (`deterministicNAT64V6Fields`), and the Rust
allocator. The Prometheus collector was the missed consumer of that
change: for a pool with `port range 2000 to 3000`, block-size 100 and
an IPv6 host, the allocator/wire compute 10 blocks per pool address
while `xpf_nat_pool_deterministic_info{host_count}`,
`xpf_nat_deterministic_pool_blocks_total`, and
`xpf_nat_deterministic_pool_blocks_allocated` reported 645 — a 64.5x
overstatement. Capacity alerts on allocated/total therefore never fire
at the real exhaustion point for range-limited NAT64 pools. Allocation
and enforcement were unaffected.

## What

- `pkg/api/metrics_nat.go` (`deterministicPoolBlockCapacity`): drop the
  mode-2 special case. The port range now comes from
  `config.SourceNATPoolPortRange` (the SSOT: pool's own `port range`,
  default 1024-65535, invalid spec fails closed) for both modes, so
  `portRange` already defaults correctly. The stale comment claiming
  mode 2 uses a fixed NAT64 range is replaced with the #15283/#16822
  rationale. `deterministicSubscriberCapacity` delegates to this
  function for IPv6, so `host_count` is fixed by the same change. The
  `SourceNATPoolReportableAddresses` unusable check above already
  returns 0 for refused/invalid-range pools, so the resolver's `!ok`
  branch is a defensive guard; a `port no-translation` + deterministic
  pool (mutually exclusive, rejected at strict commit) now reports 0
  instead of a fabricated capacity, matching `pkg/nat`'s refusal.
- `pkg/api/metrics_det_pool_range_16822_test.go` (new): pins the probe
  SUBJECT (2000-3000, block 100, IPv6 /32 => 10 for both gauges; 2
  counted hosts => 20), the default-range CONTROL (645, unchanged),
  and block-size > configured range => 0.
- `docs/deterministic-nat-cgnat.md`: the Prometheus `blocks_total`
  definition now states the port-range is the pool's own range (else
  1024-65535) for mode 2 as well since #15283.

## Validation

- RED (pre-fix, from issue probe): SUBJECT reported 645/645 against
  pkg/nat's 10.
- GREEN: `go test ./pkg/api/ -run
  'TestDeterministicPoolBlockCapacityMode2PoolPortRange16822|TestDeterministicPoolBlockCapacityFamily15177|TestDeterministicSubscriberCapacity|TestDeterministicPoolBlock'
  -count=1` — new #16822 test, the shipped #15177 mode-2 cell (default
  range, 64), the #4692 IPv6 capacity test, and the #4752 block-math
  suite all pass. RED-on-revert verified by mutation: forcing the
  64512 window in the capacity multiplication turns the new test RED.
- `go vet ./pkg/api/` and `gofmt` clean on touched files.

## Risk

Only the three deterministic Prometheus samples change, and only for
IPv6-subscriber pools with a non-default `port range` (they decrease
to the true allocator capacity). Default-range mode-2 pools and all
IPv4-subscriber pools are byte-identical. No dataplane, wire, or
allocation behaviour changes; no fail-open change (invalid ranges and
oversized blocks still report 0).
