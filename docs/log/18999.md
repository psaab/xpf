# #18999: fabric mutation replay cache rejects legitimate repeated failover RPCs

## STEP-0 design decision (before code)

### Finding and surface census

The issue evidence is the H11 wave-gate 2 TCP soak at base `d8305e128f`: 11/40 repeated failover calls failed with `mutating request token was already used`, targeting node1, while measured node skew was 0.01s. The failure is the intended single-use behavior colliding with identical method+request-digest+window tokens for distinct CLI invocations every ~5 seconds; it is not a clock-skew failure.

`pkg/grpcapi/fabric_auth.go` deterministically hashes the complete unary protobuf request, HMAC-binds that digest and the full gRPC method into a 30-second-window token, accepts the current and adjacent token windows, then consumes a mutating token in a process-local high-water-window replay cache. The cache's monotone expiry, capacity fail-closed behavior, and stale-window rejection across clock rollback are security invariants and will remain unchanged. The fabric mutation census (`fabricMutationReplayProtected`, `fabricAllowedUnaryMethods`, and `isFabricSafeSystemAction`) identifies the admitted mutations: `ClearSessions`; and `SystemAction` for node-targeted redundancy-group failover, node-targeted data failover, and `clear-persistent-nat`. Other SystemAction verbs are not fabric-admitted. Both CLI peer RPCs (`pkg/cli/peer.go`, used for forwarded failover/NAT clear, and `pkg/cli/cli_clear.go`, for peer session clear) and daemon peer RPCs (`pkg/grpcapi/server_diag.go`, `proxyPeerSystemAction`/`proxyPeerSystemActionWithPersistentNatGeneration` in `server_diag_system_action.go`) install the shared `FabricAuthUnaryClientInterceptor`; changing that common call path covers all mutating fabric RPC invocations without touching local loopback actions.

Neither mutating protobuf request has an existing nonce/request-id. `ClearSessionsRequest` uses fields 1–10 and `SystemActionRequest` uses fields 1–10. The protobuf regeneration command is `PATH=$PATH:$HOME/go/bin make proto`; stubs live in `pkg/grpcapi/xpfv1/`.

### Decision

Choose **(b) + (a)**: add an optional `bytes fabric_nonce = 11` to both mutating request messages, generate a fresh 256-bit nonce from `crypto/rand` in the shared unary client interceptor for each invocation of a fabric-protected mutation, and place the nonce on a cloned request (never mutate the caller's request). Continue hashing the complete canonical protobuf request into the existing HMAC, so the nonce is authenticated together with every argument and method. On the receiving server, consume a SHA-256 hash of a non-empty authenticated nonce as the mutation-cache identity; when absent/empty, retain the current HMAC-token identity. A repeated nonce is therefore rejected even if a key holder attempts to re-sign changed arguments, while a new invocation of the same operation gets a separate cache claim. Nonce material is not stored in logs or the cache. No nonce field is added to reads or streams.

The CLI nonce-only alternative (b without server nonce identity) would give distinct HMAC tokens but would leave the replay-cache contract implicitly coupled to all other serialized request fields. Explicit nonce identity documents and enforces invocation identity. Changing soak cadence (c) only masks the issue, fails to support legitimate immediate retries/commands, and leaves the product API behavior defective. The 30-second authentication windows and replay-cache retention rules are not widened or shortened; replay of an identical request+nonce+token remains single-use.

### Rolling-upgrade behavior (both directions)

- **Old CLI → new server:** old callers send no nonce. They keep the existing method+request+window token and cache identity; the first mutation is admitted and a byte-identical in-window repeat is rejected exactly as before. This is fail-closed with respect to duplicate execution, but the H11 repeated-identical-command limitation remains until the caller is upgraded.
- **New CLI → old server:** the added field is protobuf-wire-compatible and unknown fields are retained by the Go protobuf runtime. Thus the old server's deterministic request marshal still includes the nonce bytes that the new CLI signed, and the old token-keyed replay cache sees a distinct authenticated token for each fresh nonce. An old runtime or non-Go implementation that discards unknown fields would reject the new request's token (fail-safe, unavailable rather than silently accepting it); it cannot strip/change the nonce while preserving the HMAC. This compatibility relies on the Go protobuf unknown-field-preservation behavior and will be pinned with a wire round-trip regression test.

## Change record

### Why

The H11 soak legitimately invokes the same failover command repeatedly inside the token window; the digest-only invocation identity mistakes a new command for a captured replay.

### What

Added `fabric_nonce = 11` to both `ClearSessionsRequest` and `SystemActionRequest`. The shared unary client interceptor adds a fresh 32-byte `crypto/rand` nonce to a clone for every fabric-protected mutation, then HMAC-binds the full method and deterministic request digest. After authentication, the server uses SHA-256(nonce) as replay identity; an absent/empty nonce keeps the original HMAC-token identity. This covers ClearSessions, both node-targeted failover forms, and persistent-NAT clear; cache window, expiry, capacity, and rollback behavior are unchanged.

### Risk / gaps

The change preserves legacy no-nonce behavior and does not claim that the historical H11 result is reversed. No live H11 cluster soak was run. Full affected-package suites are not green on this workstation, but their exact failures are identical at the unchanged `master` base and the target head. New-client/old-server compatibility relies on Go protobuf unknown-field preservation; implementations that discard the nonce fail closed by rejecting the HMAC, as described above.
