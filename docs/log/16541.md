# #16541: A group leaf-list member is spliced into the FIRST of several same-key inline statements: inline BGP export written as two `set` lines `a`, `b` plus group `c` compiles and renders as the chain `[a c b]`

- **Timestamp**: 2026-10-24
- **Action**: Fixed the apply-groups leaf-list union in
  `pkg/config/ast_groups.go` so it deduplicates over ALL same-key inline
  siblings and appends new group members to the LAST sibling, instead of
  unioning into the first sibling `leafListPeer` returns. Repeated
  flat-set statements (`set protocols bgp group ext export a` then
  `... export b`) stay separate sibling leaves, so the old union spliced
  group member `c` into the `a` node and the compiler concatenated
  `[a c b]`; a group member equal to a later inline member (`b`) was
  likewise duplicated as `[a b b]` because `seen` was computed from the
  first node alone. Added `leafListPeers16541` (every same-key sibling,
  in order), `lastLeafListPeer16541` (the append target), and
  `mergeLeafListIntoSiblings16541`, which for a single peer is exactly
  `mergeLeafListInto` and otherwise seeds `seen` from every sibling,
  appends only new members to the last sibling (preserving its collapsed
  or block shape), records a spanning duplicate's #9862 ownership on the
  sibling that carries it, keeps per-sibling `leafMemberGroups9862`
  aligned for later `apply-groups-except` filtering, and carries the
  #9627 bare self-repeat onto the last sibling so the #9027 gate still
  sees it. All leaf-list union call sites route through it: the group
  leaf branch, the block-shape leaf-list branch, and the groupReplace
  port block branch (eligibility is still decided on the originally
  selected peer exactly as before; only where appended members land
  changes). `leafListPeer` itself is untouched — override and peer
  detection keep their first-match semantics. Added
  `pkg/config/group_leaflist_sibling_order_16541_test.go`:
  `TestVA03ExportOrder` (the acceptance test named by the issue) gives
  `[a b c]` for the two-`set`-line, bracket, block, and hierarchical
  sibling spellings, `[a b]` with no duplication when the group member
  equals the later inline member, `[a b]` with no group, and the
  symmetric import `[a b c]`; `TestGroupLeafListSiblingUnionNameServer16541`
  proves the fix lives in the shared union (`[1.1.1.1 2.2.2.2 9.9.9.9]`,
  not the spliced `[1.1.1.1 9.9.9.9 2.2.2.2]`); and the direct
  `TestMergeLeafListIntoSiblings*16541` cases pin the mixed
  collapsed+block sibling shape, dedup, per-sibling provenance
  alignment, and self-repeat carriage. Added
  `pkg/frr/bgp_group_leaflist_order_16541_test.go`
  (`TestVA03ExportOrderRenderedChain16541`) driving the full
  ParseSetCommand + SetPath + CompileConfig + render path: the neighbor
  references the composed route-map `a-b-c-xpf-chain`
  (`config.ReservedChainSuffix`) and the spliced `a-c-b-xpf-chain`
  never appears. The FRR renderer itself needed no change — it already
  preserves the compiler's order (#5277). Residual: the pre-existing
  `TestGroupCanonicalWireGuardPeerKeepsKeywordOverride9859` failure
  (degenerate WireGuard test key rejected at compile) fails identically
  on an unmodified origin/master worktree and is untouched by this
  change.
