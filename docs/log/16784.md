# Issue #16784: deny-configuration prices only the path a mutation names (R3-A53-02)

## Why

`AuthorizeConfigMutation` adjudicated exactly the string(s) a verb
names: one path for `delete`/`deactivate`/`activate`, the two endpoint
strings for `copy`/`rename`. Those executors act on the whole subtree
rooted at the named path, so `delete security` destroyed a descendant
covered by `deny-configuration "^security policies policy guard"` and
every gate returned nil. The commit gate
(`AuthorizeExpandedCandidate`) had the mirror hole in two ways: it
skipped group-free trees entirely (`ExpandedMutationLines` returns
nil), and it priced only candidate − active lines, so a REMOVED line
never reached a regex — including removal of an `apply-groups` linker
whose group supplied the denied leaf (folded R3-F04-01). The product
contract already treats deletion of denied paths as governed:
`load override` / `rollback n` are refused to regex classes because
"the paths they delete cannot be adjudicated one by one"
(docs/system-login.md), and #15995 applied the same principle on the
read side.

## What

- `pkg/config/authz_config_mutation_9154.go`:
  `AuthorizeConfigMutationOnCandidate` runs the unchanged per-line
  gate, then for subtree verbs (delete/deactivate/activate/copy/
  rename) enumerates the pre-mutation candidate subtree as `set`
  lines (via `FormatPathSet`, the #15995 rendering) plus its
  group-expanded lines at/below the root, adjudicating each
  descendant. Any denied (or allowlist-uncovered) descendant refuses
  the mutation. Copy/rename price only the source subtree — a
  destination that already exists is refused by the executor, so it
  is not priced as overwritten. No-regex and empty classes price
  nothing extra; a nil candidate keeps the legacy verdict.
- `pkg/config/authz_config_groups_14981.go`:
  `AuthorizeExpandedCandidate` now also prices the active − candidate
  removal difference for EVERY tree (`authorizeRemovedLines16784`):
  both trees are rendered as literal ∪ group-expanded set-line sets,
  removed non-definition lines are adjudicated (credential-touching
  removals for surcharge-only classes go through the #16080 fence).
  Unchanged lines — including the class's own deny-configuration
  definition — are never removal-priced.
- Surfaces: CLI (`checkConfigRegex`), gRPC
  (`authorizeRPCConfigMutation`) and REST
  (`authorizeRESTConfigMutation`) pass their pre-mutation
  `CandidateTree()` into the new gate; without a store they keep the
  per-line gate and the commit gate remains the backstop.
- `docs/system-login.md`: new subsection documenting subtree pricing
  and symmetric commit-removal pricing.
- Tests: `pkg/config/authz_config_subtree_16784_test.go` — premise +
  controls, the five defect verbs under both deny and allow
  spellings, absent-descendant/allowed-subtree/nil-candidate/
  unrestricted controls, edit-path resolution, and commit removal
## Validation

  — the subtree gate did not exist; a base probe through the old
  per-line gate showed the defect directly
  (`delete security => nil`, `deactivate security => nil`,
  `rename security to sec2 => nil` under the guard deny).
- GREEN: `go test ./pkg/config/ -run '16784'` passes (7 tests);

  pass in pkg/config, pkg/configstore 16611 gate tests pass, and

## Risk

Neighbours preserved: `set`/`insert`/`annotate` keep single-path
pricing; pre-existing candidate content a class could not have
authored alone is never re-priced (only removals and the mutated
subtree are); already-active lines stay exempt at commit. A class
that staged a denied removal through a path with no candidate held
at the per-line surface is still caught at commit by the new
active − candidate pricing. Residual: `load override`/`rollback`
whole-candidate refusals are unchanged (already refused to regex
classes); Junos parity for ancestor deletes under deny regexes
remains unverified upstream — the fix follows the product's own
documented contract.
