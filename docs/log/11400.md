# Issue 11400 — reject conflicting OSPF interface area assignments

- **Timestamp**: 2026-10-01
- **Action**: Added a strict compile gate for a resolved interface assigned to
  distinct areas within an OSPFv2 or OSPFv3 process, including routing
  instances. Tolerant loads warn and preserve the typed config; FRR rendering
  keeps the first area's interface settings/activation, drops later conflicting
  interface blocks, and warns. Integer and dotted-quad spellings of the same
  area ID are treated as equivalent.
- **File(s)**: `pkg/config/compiler_validate_strict_ospf_interface_area_11400.go`,
  `pkg/config/compiler_uniformgates.go`, `pkg/config/compiler_opts.go`,
  `pkg/config/ospf_interface_area_reuse_11400_test.go`,
  `pkg/frr/protocols_render.go`,
  `pkg/frr/ospf_interface_area_reuse_11400_test.go`, `docs/log/11400.md`
- **Validation**: Before the fix, strict OSPFv2/OSPFv3 compile accepted the
  duplicate interface without warnings, and direct rendering emitted two
  interface blocks with the later area activation. After the fix, strict
  rejection, lenient warning, first-area render/dedup, and equivalent-area
  controls passed with `go test ./pkg/config ./pkg/frr -run
  '^(TestOSPFAreaInterfaceReuse|TestOSPFInterfaceAreaReuse)' -count=5`; a
  throwaway `Manager.ApplyFull` smoke also confirmed first-area-only output and
  a warning. A pre-rebase full `go test ./pkg/config ./pkg/frr` run failed
  unrelated #11312/#10826 cases, timed out in the bcrypt-heavy schema spelling
  gate, and had FRR environment failures (daemon permission and symlink mode).
