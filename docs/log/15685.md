## Why

`compileDynamicAddress` records an `address-name` even when its `profile`
carries no `feed-name`, producing an `AddressBinding` with zero `FeedNames`.
The strict cross-reference gate `validateDynamicAddressFeedReferencesStrict`
(#3300) only iterated *present* feed names, so the orphan binding committed
clean with no error or warning. No feed fetch can ever populate such a
binding, so `feeds.Manager.SnapshotForBindings` omits it forever; at
userspace lowering a declared binding absent from the feed overlay is
unrepresentable (the declared-binding guard in `policies_lower.go` runs
before the static-book lookup), so a referencing policy lowers to
`__unsupported_address__` and the Rust preflight rejects the *whole*
snapshot publication permanently (previous-good retained, or fresh-boot
default-deny). The same ordering means the orphan — and equally a valid
feed-backed binding — shadows any same-named static `address` /
`address-set`: while the feed is unready the static entry never enforces,
and once the feed is ready the name enforces the union of feed prefixes and
the static entry. Neither is the single meaning either stanza declares.
Junos requires `profile feed-name` at commit check and forbids the
name ambiguity.

## What

- `pkg/config/compiler_validate_strict_observability.go`:
  `validateDynamicAddressFeedReferencesStrict` now returns an error for any
  binding with `len(ab.FeedNames) == 0`, naming the binding and the missing
  `profile feed-name`, before the existing per-feed typo check. The sorted
  name walk keeps the first reported binding deterministic. On the tolerant
  load / peer-sync path the existing `lenientDynamicAddressFeedRef`
  downgrade turns it into a warning (#1960 no-brick; the runtime stays
  fail-closed for the name).
- `pkg/config/compiler_validate_strict_addrbook.go`: new
  `validateDynamicAddressStaticCollisionStrict` rejects any
  `address-name` binding whose name matches a static `address` or
  `address-set` in the global book or any zone-local book (sorted binding
  and zone walks for a deterministic first error).
- `pkg/config/compiler_earlystrict.go`: wires the collision gate on the
  PRISTINE books, immediately after the #5676 address/address-set collision
  gate and before `resolveZoneLocalAddressBooks` folds zone-local entries
  into synthetic `zone-local/<zone>/<name>` keys. Pristine placement is
  load-bearing: bindings are keyed by authored name and the userspace
  lookup unqualifies zone-local tokens back to that name
  (`dynamicAddressLookupName`), so a zone-local static entry really does
  collide with a global binding even though the post-fold keys differ.
  Strict commits hard-reject; tolerant loads warn via
  `lenientDynamicAddressFeedRef`.
- `pkg/config/dynamic_address_no_profile_15685_test.go`: strict rejects for
  a bare `address-name`, a `fail-mode`-only profile, orphan-over-static,
  feed-backed-over-static-address, feed-backed-over-static-address-set, and
  zone-local collisions; a lenient cell proving both new diagnostics
  downgrade to warnings while the binding is retained; a valid
  distinct-names control; and direct-validator determinism (lexicographically
  first orphan reported).
- `pkg/config/README.md`: documents both gates in the address-book section.

NOT changed: the compiler's binding recording, the feeds manager, and all
userspace lowering. A leniently loaded orphan/colliding name keeps the
existing fail-closed lowering (`__unsupported_address__` → whole-snapshot
reject); the fix only stops *new* strict commits from creating the state
silently.

## Risk

Configs that previously committed with a feed-less `address-name`, or with
an `address-name` shadowing a static entry, now fail strict commit and must
be renamed or given a `profile feed-name` — that is the intended Junos
parity. Already-persisted configs still load on the tolerant path with
warnings and keep the previous fail-closed runtime behaviour, so an upgrade
cannot brick a running firewall (#1960). No dataplane, wire-format, or
schema change.
