# Issue #12159 — demote a crash-looping userspace helper

## Why

The shim deliberately stays attached and drops transit when its helper dies, but the daemon treated `armed && attachedXDPLinks > 0` as readiness. That left the host transit gate open and the incumbent RG at weight 255 while traffic was blackholed. A helper restart in progress must close transit immediately; a persistent crash loop must also resign the incumbent so it cannot hold a blackholed RG.

## What

- The userspace manager and legacy adapter expose a synchronized helper-supervisor snapshot and a wake-only observer. The daemon registers the observer with the published dataplane and re-reads state on each wake/tick.
- Transit opens only with kernel/XDP readiness and a running helper. One fast restart closes the gate but does not flap the incumbent. Once restart backoff reaches its cap, a dedicated reserved monitor applies full election debt (weight 0); successful recovery clears that debt. Kernel-arm debt remains independent.
- All production gate-opening paths, including rxvlan audit reassertion, use the helper predicate. The helper-loop monitor is preserved across unrelated monitor reconciliation. The dataplane docs describe the fail-closed and election behavior.
- Regression fixtures cover both preempt settings, a fast restart, persistent crash-loop demotion, and recovery; supervisor tests cover running, single-crash, failed readiness at the cap, and observer delivery.
