# Stale secondary sync peer after fabric restart (#13542)

- **Issue**: #13542 — dual-to-single fabric restart retained `syncPeerAddr1`,
  while session-sync wiring and peer-address readers accessed both address
  fields without synchronization.
- **Cause**: `wireSessionSyncTransportRefs` only assigned the secondary address
  when fab1 was active, so a rebind to single-fabric left the previous fab1
  address published. Concurrent gRPC and CLI peer lookups raced rebinding.
- **Change** (`pkg/daemon/daemon_ha_comms_wiring.go`,
  `pkg/daemon/daemon_run_servers.go`, `pkg/daemon/daemon_run.go`): publish and
  clear both addresses under `fabricMu`; take a consistent locked snapshot for
  both gRPC and CLI peer-address readers. Explicitly suppress secondary-IP
  fallback after single-fabric wiring, so an already-discovered stale fab1 IP
  cannot bypass clearing the configured secondary address. Added
  `sync_peer_addr_13542_test.go` for dual-to-single stale-address removal
  (including a populated fallback IP) and concurrent rebind/snapshot race
  detection.
- **RED evidence** (pristine master `d7fe769aa`):
  `go test ./pkg/daemon -run '^TestSyncPeerAddrsDualToSingleClearsSecondary_13542$' -count=1`
  failed because `syncPeerAddr1` remained `10.99.1.2` after the single-fabric
  wiring call. A throwaway pristine-tree `-race` probe also failed with races
  between the wiring writes and simultaneous peer-address reads.
- **GREEN evidence**: targeted race regression plus `go vet ./pkg/daemon` and
  targeted gofmt check passed. Full `go test ./pkg/daemon -count=1` passed
  (472.802s; short `GOTMPDIR` avoids unrelated Unix-socket path-length
  failures). Full package `-race` timed out after 10 minutes in
  `TestPersistentConfigSyncNACKPreservesDistinctHistory12163`, outside this
  change; the targeted race regression passed.
- **Risk**: peer-address snapshots use the existing fabric read lock, limited
  to reading the two configured addresses/fallback IPs.
