# #16783 — DeleteRescueConfig unlinked a later successful rescue save

- **Timestamp**: 2026-10-25
  - **Action**: `DeleteRescueConfig` claimed its rescue generation
    under `s.mu` and bumped `rescueAppliedGen` under `rescueMu`, then
    released `rescueMu` before its durable unlink (`rbRemove` +
    `rbSyncDir`). A `SaveRescueConfig` started after the delete claims
    a later generation, so in that window it took `rescueMu`, wrote
    rescue.conf durably, set `rescueAppliedGen` and reported success —
    after which the delete's unlink removed the newer save's file,
    leaving no rescue.conf for a later `rollback rescue` (the reverse
    ordering of the race #14722 fixed). Fix: the delete now holds
    `rescueMu` across the generation bump, the unlink and the dir
    fsync, so a later save either completes before the delete's
    critical section (and is legitimately removed by it) or writes
    only after the delete has finished (and legitimately recreates
    rescue.conf). No-deadlock property of #14722 is preserved: a save
    held at `rescueWriteBarrier` has not yet taken `rescueMu`, so the
    delete still supersedes it promptly; the delete now merely waits
    for a save already inside its critical section, the same
    serialization saves already have among themselves. NOT changed:
    generation claiming, the supersede checks, the durable
    unlink+dir-fsync discipline (#5197), or any caller.
  - **File(s)**: `pkg/configstore/store_persist.go`,
    `pkg/configstore/store.go` (rescueMu contract comment),
    `pkg/configstore/rescue_delete_race_14722_test.go` (new
    `TestDeleteRescueConfigDoesNotUnlinkLaterSave_16783`),
    `docs/log/16783.md`
  - **Validation**: new test pauses the delete inside the `rbRemove`
    seam (generation claimed/applied, unlink not yet landed) while a
    later save runs, then asserts rescue.conf exists with the later
    save's content. RED pre-fix (fix temporarily reverted):
    `rescue.conf missing after later save reported success: ... no
    such file or directory`. GREEN post-fix together with
    `TestDeleteRescueConfigDoesNotResurrectInFlightSave_14722`,
    `TestSaveRescueConfigNewestWins_14722`,
    `TestDeleteRescueConfigDirSynced` and
    `TestDeleteRescueConfigAbsentNoDirSync` (5 passed), and the three
    race tests pass under `-race`. `go vet ./pkg/configstore/` clean,
    gofmt clean.
  - **Risk**: A delete now waits for an in-flight save already inside
    its `rescueMu` critical section to finish its durable write
    (bounded by one fsync'd file write) instead of unlinking
    concurrently; operator-visible only as a marginally slower
    `rescue delete` racing a `rescue save`. No other behavior delta.
