# #12249 — tolerated defined zone `any` widens zone-pair policies

- **Timestamp**: 2026-10-08 (`fix/12249-zone-any`)
- **Action**: fail closed when tolerant loading retains a definition named `any` but quarantine omits that zone from the dataplane snapshot.

## Red before

On the clean STEP-0 base `a714c90d4`, a temporary regression probe compiled a pre-#3055-shaped persisted config through `CompileConfigLenient` with zone `any` and a `from-zone any to-zone untrust` permit. The tolerant config retained the `any` definition, while `buildSnapshot` published only `trust`/`untrust` and still emitted `any->untrust/p1` with no application poison. `PolicyContentRejectionReasons` returned `[]`. The targeted probe failed after logging these facts, reproducing the wildcard widening.

## Change

- Added a shared `any` token and defined-zone predicate. Strict validation continues to reject the reserved zone definition; ordinary `any` policy wildcards with no such definition remain valid.
- Policy lowering detects the legacy defined-`any` shape and poisons zone-pair policies naming it with the existing `__unsupported__` application sentinel. A build-time marker lets the rejection mirror report the reserved-zone cause rather than an unrepresentable application. `junos-global` poison retains precedence.
- The snapshot quarantine path reapplies the same poison defensively after collision scrubbing. Global policies and their `any` match scopes are not affected.
- Updated the defined-reserved-zone quarantine regression and added tolerant-boot tests for from-, to-, and both-any zone-pair policies, the helper wire poison/rejection reason, a healthy sibling, and the no-defined-zone wildcard control. Updated `pkg/config/README.md` and this issue record.
