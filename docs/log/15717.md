# #15717 — collectSchemaRefs unapplied-group login-class poisoning and missing post-compile `system login user <name> class <class>` gate

## Defect

V44-04 from the deep-review synthesis (all three blind lanes MATERIAL).
Three legs, all reproduced in-lane on `origin/master` (959eeee6c5)
before the fix:

1. **Case B (direct compile)**: `CompileConfig` on
   `set system login user bob class totally-undefined-class` returned
   `err=nil`. `CompileConfig` never runs `SchemaValidate`, and no
   post-compile validator checked `cfg.System.Login.Users[*].Class`.
2. **Case A (unapplied-group poisoning)**: a class `ops-admin` defined
   only inside `groups { staged-rbac { ... } }` with no `apply-groups`
   satisfied `validateLoginClassRef` at schema-validate time, because
   configstore passes the pre-expansion tree as `defsSource` and
   `collectSchemaRefs` collects definitions from group bodies, applied
   or not (the deliberate #1319 PR 3 permissive union). After
   `ExpandGroups` discarded the unapplied group, the compiled config
   carried user `alice` with `Classes=[]` — accepted clean.
3. **Case C (sibling miss)**: `collectSchemaRefs` used singular
   `group.FindChild("system")` / `group.FindChild("class-of-service")`,
   so a login class (or forwarding class) defined in a *second* sibling
   `system` / `class-of-service` block of a group was never collected
   (`refs.loginClasses` empty for the report's Case C shape).

Impact calibration (per the lanes' refutation): at runtime
`ResolveClassPermissions(cfg, unknown)` returns `ok=false` and every
authorization check denies, so this is **not** a privilege gain. It is
a silently-accepted config whose user can never log in usefully — a
lockout discovered only at the next login — plus a misleading commit.
Junos rejects the shape at commit (`class '<c>' is not defined`
against the *effective*, post-`apply-groups` configuration).

## Deliberate non-change

The permissive schema-refs union itself is **kept**. It exists so a
definition living only in the peer node's un-applied group (e.g.
`groups node1 { ... }` in a `"${node}"` cluster config) keeps
satisfying shared-section references when validating on node0
(#1319 PR 3). The report's Fix Direction 2 proposed collecting
top-level references "from the expanded tree while only using
defsSource when validating unexpanded group bodies"; implementing
that would re-break the peer-node case the union protects, and the
post-compile gate below already makes the poisoning unreachable: the
schema gate may pass, but compilation validates against the effective
config. Fixing collectSchemaRefs' *sibling* miss (leg 3) is separate
and safe — it only widens collection within a body already being
scanned.

## Fix

- `validateLoginUserClassReferencesStrict`
  (`pkg/config/compiler_validate_strict.go`): post-compile gate —
  every login user with a non-empty `Class` must satisfy
  `_, ok := ResolveClassPermissions(cfg, u.Class)`; first offender
  rejected naming user and class. Wired dead-last in `runUniformGates`
  (`pkg/config/compiler_uniformgates.go`) so it cannot steal an
  established first-error slot (invariant #6), with the
  `lenientLoginUserClassRef` downgrade flag
  (`pkg/config/compiler_opts.go`, enabled in `lenientCompileOpts()`)
  turning it into a warning on the tolerant boot/peer-sync path
  (#1960 no-brick: the runtime already denies the unknown class, so
  tolerant behaviour is unchanged).
- `collectSchemaRefs` (`pkg/config/schema_walk.go`): both collectors
  now iterate `FindChildren` — every sibling `system` (login classes)
  and every sibling `class-of-service` (forwarding classes) — at top
  level (via a synthetic root parent) and inside each group body.

## Tests

`pkg/config/login_class_gate_15717_test.go`, six groups, all verified
RED on pristine `origin/master` (test file alone) and GREEN after:

- `TestLoginUserUndefinedClassRejectedStrict15717` — Case B.
- `TestLoginUserUnappliedGroupClassRejectedStrict15717` — Case A,
  through full `CompileConfig` (parse → expand → compile → gate).
- `TestLoginUserUndefinedClassLenientWarns15717` /
  `TestLoginUserUnappliedGroupClassLenientWarns15717` — tolerant path
  warns naming the class and retains the user stanza.
- `TestLoginUserValidClassesAccepted15717` — positive controls:
  built-in class, top-level custom class, custom class inherited from
  an *applied* group, and a classless user all still compile strict.
- `TestCollectSchemaRefsSecondSystemBlock15717` /
  `TestCollectSchemaRefsSecondCoSBlock15717` — Case C legs.

## Residual

- Boot/peer-sync of an already-persisted config carrying this defect
  still succeeds (with a warning) by design (#1960); the operator
  must fix the class at the next strict commit.
- `SchemaValidate` called directly on an unexpanded tree still
  accepts a reference satisfied only by an unapplied group — that is
  the tree gate's documented permissive contract; the commit path is
  closed by the post-compile gate, which is where the effective
  config exists.
