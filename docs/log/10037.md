# 10037 — OSPFv3 area activation uses the FRR 10.6 interface grammar

## Summary

`pkg/frr/protocols_render.go` previously emitted OSPFv3 area membership as
` interface <name> area <id>` under `router ospf6`. FRR removed that command
before 10.6 (it was `DEFUN_HIDDEN` in 9.1 and is absent at frr-10.6.0 and
stable/10.6 head `2ab78e9`), so the deployed daemon accepted the surrounding
configuration but never activated OSPFv3 on the interfaces.

FRR stable-10.6 documents the live command under INTERFACE_NODE:

`ipv6 ospf6 area <A.B.C.D|(0-4294967295)>`

The renderer now emits an `interface <name>` block for every configured
OSPFv3 area interface and places the validated area activation inside it. The
existing passive, cost, adjacency-timer, priority, and BFD lines remain in the
same interface block. Invalid area IDs still omit only the activation line
through the existing #9820 belt. OSPFv2 remains on its existing `ip ospf area`
form.

## Version policy

The tree has no FRR-version selector in its renderer, and its deployed target
is the single stable/10.6 line. The removed router-level form therefore has no
supported target to retain behind a version gate; the renderer uses the current
INTERFACE_NODE grammar directly.

## Regression cells

`pkg/frr/ospf6_area_render_10037_test.go` pins:

- the FRR 10.6 `interface` + `ipv6 ospf6 area` block and absence of the removed
  router-level form;
- independent interfaces in different areas, each retaining its own area;
- invalid-area omission while preserving other interface settings; and
- an OSPFv2 control asserting the existing `interface` + `ip ospf area` output.

The existing OSPFv3, area-belt, and interface-name tests were migrated from the
removed output form to the FRR 10.6 grammar.
