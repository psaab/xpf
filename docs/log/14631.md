# Issue #14631 — `from is-fragment` matches IPv4 first fragments (MF=1, offset 0)

## Why

Junos SRX defines `is-fragment` as `fragment-offset 0 except`: only trailing
fragments (offset != 0) match. xpf's firewall-filter term bit was the
any-fragment predicate (IPv4 MF set OR offset != 0; IPv6 Fragment header
present), so a first fragment — which carries the L4 header — matched an
`is-fragment accept` term and bypassed following port terms at the stateless
layer. The MX any-fragment reading is platform-specific and not xpf's SRX
target.

## What

- `term_match_extra_from_frame` (the single builder for every filter/CoS
  evaluation path) now sets `TermMatchExtra::is_fragment` via the new
  `is_term_fragment` predicate, which is exactly `is_non_first_fragment`
  (fragment offset != 0, both families). First and atomic fragments carry
  `is_fragment: false` with `l4_present: true`, so they face port/tcp-flags
  terms; trailing fragments keep matching `is-fragment`.
- Internal any-fragment consumers are unchanged: `is_any_fragment` /
  `ipv4_is_any_fragment` / `ipv6_is_any_fragment` still back TCP
  segmentation, NAT64, embedded-ICMP, and checksum guards.
- The BPF/XDP filter path and the lo0 nftables mirrors already implement
  trailing-only semantics (`ip frag-off & 0x1fff != 0`; IPv6 `exthdr frag
  exists` is presence-only at the kernel hook, and IPv4 lo0 is refused after
  #13955), so no change was needed there. `first-fragment` remains
  unimplemented as a config term (pre-existing; Junos operators combine it
  with `is-fragment` in separate terms).
- Docs/comments corrected: `userspace-dp/src/filter/README.md`,
  `docs/feature-gaps.md`, the snapshot field comments in Rust and Go, and
  the two stale test assertions that pinned any-fragment term behaviour
  (a first-fragment builder test and a meta-flavor parity test now assert
  the trailing-only bit; an IPv6 declared-fragment test now uses a trailing
  fragment).

## Validation

- RED on base: `is_fragment_term_14631_first_fragment_faces_port_term_trailing_matches`
  failed with `left: Accept, right: Discard` for an IPv4 MF=1/offset-0
  TCP/22 packet through `frags{is-fragment accept}; no-ssh{tcp 22 discard}`.
- GREEN after fix: same test passes (plain and first-fragment TCP/22 →
  Discard; trailing v4/v6 fragments → Accept via `frags`; v6 first fragment
  → Discard), plus corrected builder/parity tests.
- Pre-existing failures, reproduced on pristine base and unrelated:
  `local_origin_tunnel_ipv6_nonfirst_fragment_transmits_without_session_14119`
  (`unsupported_local_origin_packet`) and
  `stage11_local_ike_passthrough_honors_ingress_input_filter_13637` both fail
  identically without this change.

## Risk

Filters that (against Junos SRX semantics) relied on `is-fragment` catching
first fragments now let first fragments fall through to subsequent terms —
the intended SRX behaviour. Trailing-fragment handling is unchanged.
