# #18324 — userspace-xdp verifier headroom recovery: measured floor, STOP at ~25%

## Verdict

**STOP per assignment gate.** No behavior-preserving change measured
≥25% headroom, let alone the ≥30% target (≤700,000 processed insns).

#16009 remains blocked on headroom; its WIP widening must not be

## Method

Every figure below is a genuine pinned build measured through
`cmd/shimverify` (the recipe's verify-then-install gate), scratch-only,
restored after each run. Two classes:

- **Neutralization stubs** (behavior-breaking, measurement only):
  early-return the named subsystem and read the delta. These bound
  what a perfect, free version of that subsystem could save.
- **Behavior-preserving, but insufficient:** `#[inline(never)]`
  outlines, session-miss extraction, and per-CPU-scratch laundering.
- **Exploratory only:** merged degraded/healthy parse and a two-program
  `bpf_tail_call` split; neither prototype meets the zero-behavior
  acceptance as implemented here.

## Exploratory tail-call split

A scratch prototype split at the binding-ready point into
`xdp_userspace_prog` (first half: ctrl/L2/ingress/parse/tagged/LAND/binding)
and `xdp_userspace_tail` (re-parsed, then ran ingress/parse/tagged/LAND
again before WG/early/session/GRE/redirect dispatch; the binding slot was
handed over through per-CPU scratch). The verifier measured entry
535,844 (46.42% headroom) and tail 288,747 separately. This is evidence
that separate XDP programs can reduce per-program verifier accounting,
not evidence of behavior preservation: the prototype repeats trace and
LAND work, and its branch counters can differ.

`bpf_tail_call` had to sit in the `#[xdp]` wrapper itself — in the
`#[inline(never)]` dispatcher it rejected with `tail_call is not
allowed in subprogs without BTF` — so the dispatcher returned a
sentinel for the wrapper to tail-call on.

The prototype is not landable as-is. `TestUserspaceXDPShimSourceMatchesRetainedObjectAllowlist`
currently rejects `ProgramArray`, `.tail_call(`, and `bpf_tail_call`
tokens and its source/object allowlists admit the existing single XDP
program and maps. A valid implementation may update those gates, but
must also wire the loader to populate the program array; currently it
loads only `xdp_userspace_prog`, so an unpopulated tail call falls
through to DROP. It additionally needs twin/degraded/kernel-pass cells
that execute the split composition and prove the extra dispatch work
preserves verdicts, counters, and ordering. Those changes were not
implemented or validated in this headroom lane.

This prototype therefore does **not** count as a zero-behavior
headroom result and is not the requested change.

## Measured floor

- **Best valid result:** 772,430 insns / 22.76% (outline
  `drop_degraded_transit`). It is 3.2 percentage points better than
  baseline but remains below the requested ~25% stop threshold.
- **Not valid under zero behavior change:** the parse merge measured
  750,993 / 24.90%, but moves branch-stat increments into degraded
  mode; this changes observable counters and cannot be called a
  behavior-preserving recovery.
- **30% (≤700k) remains unreached.** Parse/dispatch outlines were
  neutral, worse, stack-rejected (496/512 already used) or
  pointer-tracking-rejected. Laundering the protocol through scratch
  made the count hit 1,000,001, unlike the #8249 fragment flag,
  because this value remains relevant across downstream dispatch.

## What would actually unlock #16009

1. A correctly composed program split behind a tail call, with loader
   population and host-side twin/degraded/kernel-pass coverage proving
   identical verdicts, counters, and order. The exploratory counts
   above are per-program measurements only, not acceptance evidence.
2. Or investigate BTF-enabled subprogram calls/toolchain changes with
   their own provenance and packet-range verification.
3. Not: more `#[inline(never)]` shuffling or scratch laundering of
   `ParsedPacket` fields. Re-inlining `parse_l4` regressed by 298,714
   at #8249 and the reverse is rejected.
