# Issue #15081 — forwarded cluster-failover proxy 5s deadline (A43-02)

- **Issue:** `proxyPeerSystemAction` applied a flat 5s deadline to forwarded
  `cluster-failover ... node <peer>` and data failover, so the operator got a
  bare `DeadlineExceeded` although the peer completed the ownership move.
  Console twin: `pkg/cli/peer.go:155`.
- **Context read:** Read the complete issue body via `issue://15081`. No
  comments were present (`gh issue view 15081 --comments` returned no
  output). No scope withdrawal, narrowing, shipped notice, or contradiction.

## Mechanism (verified at base ac543c5b9e)

- `pkg/grpcapi/server_diag_system_action.go:38` (pre-fix) wrapped every
  forwarded `SystemAction` in `context.WithTimeout(ctx, 5*time.Second)`.
  `executeClusterFailover` forwarded `KindDataFailover` and
  `KindRGFailoverNode` through it and returned `st.Err()` verbatim.
- The peer side runs `s.cluster.RequestPeerFailover(op.RG)` /
  `RequestPeerFailoverBatch` with no ctx. That sequence is: failover-ACK
  round-trip (`failoverAckTimeout` = 20s, `pkg/cluster/sync.go`), local
  commit-ready settle (`localFailoverCommitTimeout`, 3s default in
  `pkg/daemon`), and failover-commit round-trip (another 20s ACK cap). The
  daemon already sizes the owner-side transfer-out lease as
  `2*localFailoverCommitTimeout + 20s` for the same worst-case post-ACK
  commit latency (`daemon_ha_comms_wiring.go`).
- `pkg/daemon/daemon_ha_userspace_readiness.go:186-187` notes bulk session
  sync can delay the barrier write/ack "by 30+ seconds" — alone far beyond
  5s. So a legitimate planned failover routinely exceeded the proxy
  deadline; the peer completed the transfer while the operator was told it
  failed, inviting a needless retry/escalation during maintenance.
- `pkg/cli/peer.go` `requestPeerSystemActionWithPersistentNatGeneration`
  applied the identical 5s deadline on the CLI forwarding path.

## Fix

- `pkg/clusterfailover/deadline.go` (new, side-effect-free like the rest of
  the grammar package): `FailoverAckTimeout` (20s mirror of
  `pkg/cluster`'s `failoverAckTimeout`, pinned by a parity test in
  `pkg/cluster` since `pkg/cluster` imports `clusterfailover`),
  `DefaultCommitSettle` (3s), and `ProxyFailoverTimeout = 2*Ack + 2*Settle
  = 46s` — mirroring the daemon's `2*settle + 20s` lease sizing with room
  for both ACK/commit round-trips. Plus `IsFailoverActionString`, which
  reuses `ParseAction`+`Targeted()` so malformed family members never get
  the long budget (they are rejected before any proxy dial).
- `pkg/grpcapi/server_diag_system_action.go`: `proxyPeerTimeout` returns
  the cluster budget only for validated targeted failovers; every other
  forwarded action keeps 5s. New `proxyClusterFailover` wraps the two
  failover proxy sites: on a deadline outcome (`context.DeadlineExceeded`
  or `codes.DeadlineExceeded`) it reconciles against ownership instead of
  relaying the bare error.
- `pkg/cluster/group_state.go`: `PeerPrimaryRGs()` returns the peer's
  primary data RGs (ascending, RG0 excluded) plus peer liveness, so the
  reconciliation can distinguish unreachable (no verdict) from
  reachable-but-not-primary.
- Reconciliation (`failoverProxyTimeoutOutcome` / CLI
  `failoverProxyTimeoutMessage`): peer primary for the RG (or for every
  data RG) → "transfer committed … proxy response timed out after the
  peer committed"; otherwise → "outcome unknown … verify ownership
  before retrying" (naming the peer's current primary set for data
  failover, or peer-unreachable). Invariant: a deadline outcome on this
  path never surfaces as a bare `DeadlineExceeded`.
- `pkg/cli/peer.go`: same sizing (`peerSystemActionTimeout`) and the same
  reconciliation on both the `peerSystemActionFn` seam and the real dial
  path.

NOT changed: the 5s budget for non-failover forwards (e.g.
clear-persistent-nat), the peer-side `RequestPeerFailover` execution, the
fabric allowlist, and any timeout inside `pkg/cluster` — the defect was
the proxy deadline and the verbatim relay, not the failover itself.

## Risk

- A genuinely hung peer now holds the operator's failover command for up
  to 46s instead of 5s before the outcome-unknown report. That is the
  deliberate trade the issue directs (size from the cluster budget): the
  peer's own sequence can legitimately take that long, and the previous
  5s answer was a false failure report.
- The reconciliation oracle is heartbeat-advertised cluster state
  (`peerGroups` / local groups). In the test seam no heartbeat has run,
  so tests inject it via `SetPeerGroupStateForTesting` (the existing
  hook for exactly this). If no heartbeat state exists at timeout, the
  report is outcome-unknown with a peer-unreachable note — never a
  claimed success.
