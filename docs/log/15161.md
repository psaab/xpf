# Issue #15161: owner-RG export accumulator caps a complete window at 17 pages

## Why

`ExportOwnerRGSessionsPaged` charged every retained delta the
1863-byte worst-case JSON size (`ownerRGExportEstimatedDeltaBytes`)
against the 256 MiB retained-slice bound
(`ownerRGExportMaxAccumulatorBytes`). `256 MiB / (8192 * 1863) = 17`
pages, so a complete window was refused after ~139k-144k deltas
regardless of the real decoded size. An owner holding more forward
sessions than that (the issue's six-worker case is 6 x 65536) could
never cold-prime or FullResync: every attempt failed closed with
`ErrOwnerRGExportIncomplete`, reviving the #9344 harm at a higher
threshold. The structural bound was never the limiter — the helper
asserts `16 workers * DEFAULT_MAX_SESSIONS * 2 / 8192 = 512` data
pages, and the fake deltas in the paging tests decode to ~540 bytes
each (520-byte struct plus short strings), not 1863.

## What

- `pkg/dataplane/userspace/owner_rg_export_paging_9344.go`:
  `ownerRGExportActualDeltaBytes` charges actual decoded retention —
  `unsafe.Sizeof(SessionDeltaInfo)` (which already includes the
  `[16]byte`/`[6]byte` `json:"-"` legs) plus the length of every heap
  string field. The collector sums that per page and still fails
  closed at the unchanged 256 MiB bound, so genuinely wide deltas
  (full-width IPv6 literals on every string field) are still refused
  rather than retained without bound. `maxOwnerRGExportDataPages`
  (512) remains the structural cap, and the 513-page unterminated
  probe and dropped-delta paths are untouched.
- `ownerRGExportEstimatedDeltaBytes` now documents its remaining role:
  sizing ONE page against `MaxControlResponseBytes`. It is no longer
  charged per retained delta. `maxOwnerRGExportAccumulatorPages`
  stays as the nameable 17-page history, no longer a collector budget.

NOT changed: the paging protocol, page size, structural page bound,
terminal probe, incarnation/sequence/dropped-delta validation, the
daemon snapshot API (still one complete slice), or any Rust code.
Streaming pages into the sink would require changing that API and
every fake that implements it; the actual-bytes charge meets the
acceptance (48 pages complete, byte bound still fail-closed) without
that blast radius.

## Validation

- RED on base (`ada5f856da`, detached `/var/worktrees/base-15161-check`
  with only the mechanism cell copied in):
  `TestOwnerRGExportCompletesSixWorkerWindow15161` fails with
  "export accumulator exceeds 268435456-byte bound after 18 requests".
- GREEN in this lane: the same cell passes (48 pages, 393216 deltas);
  `TestOwnerRGExportRejectsActualAccumulatorBudget15161` derives the
  pages needed to exceed 256 MiB from the measured actual cost and
  still gets `ErrOwnerRGExportIncomplete` with no partial window;
  the 513-page unterminated and terminal-probe cells, dropped-delta,
  v1-refusal, restart, oversized-page, and lock-release cells all pass.
- Pre-existing base failure, not this change:
  `TestOwnerRGExportPageFitsTheResponseCap9344` fails identically on
  unmodified `ada5f856da` (reflected worst case drifted 1863 -> 1900
  as the wire schema grew). Left untouched; it sizes one page, not
  retention, after this fix.

## Risk

- Maximum-width deltas charge their actual size (~1105 B: 520 B
  struct + 15 string fields at up to ~39 B), below the old flat
  1863 B charge, so the byte bound trips at ~29 full pages of the
  widest possible deltas instead of 17 — still fail-closed, still
  256 MiB of measured struct+string bytes plus slice growth slack,
  the same order the old bound intended. Narrow deltas (the common
  case) charge ~540 B and complete up to the 512-page structural cap.
- Lab verify still outstanding: cold prime / FullResync on the loss
  cluster with an owner holding >144k forward sessions.
