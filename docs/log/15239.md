# #15239 — single-RG failover reset cleared the node-global kernel-upgrade hold (A56-01)

## Defect

`Manager.ResetFailover(rgID)` (`pkg/cluster/failover.go`) dropped the
node-global `kernelUpgradeHold` inline, for any single RG:

```go
if m.kernelUpgradeHold {
    m.kernelUpgradeHold = false
    ...
}
```

The hold is node-scoped: a kernel-upgrade candidate boot must stay
SECONDARY on every RG until the promotion gate verifies the dataplane
(promotion marker == running kernel). The inline clear treated every
per-RG reset as a node rejoin. So on a candidate-trialling node (journal
ARMED, candidate running, marker not yet written), an operator running
`request chassis cluster failover reset redundancy-group 1` — or the
equivalent gRPC `cluster-failover-reset:1` action — cleared the hold for
the whole node. The reset's `recalcWeight` election (and every later
election, heartbeat, `LocalPriorities`, and VRRP mirror, all gated on the
same flag) then let the unverified candidate claim primary on every RG
before `xpf-kernel-promote` verified it — the exact blackhole the hold
exists to prevent. Nothing re-asserted the hold: the daemon's 5s
`reconcileKernelUpgradeHold` only releases on the marker and never
re-arms, so the clear was permanent for the boot.

The comment on the clear named a manual `request ... reset` as an
intended rejoin. That conflated two different verbs: a per-RG operator
reset (one RG, no promotion check) and the orchestrator rejoin
(`xpfd upgrade kernel rejoin` / `RejoinAndConfirm`, which resets every
configured RG after bulk sync). Only the latter is a verified node
rejoin.

## Fix

- `ResetFailover` no longer touches `kernelUpgradeHold`. Its per-RG work
  is unchanged: `ManualFailover`/role-pin clear, transfer-commit state
  clear (#14979), remote lease clear, `failoverGen` bump, and
  `recalcWeight`. While the hold is set, the election inside
  `recalcWeight` (`electRG`/`electSingleNode`) keeps every RG secondary,
  so the reset is safe but not a promotion. A log line names why the node
  stays held.
- `ResetAllFailover` (`pkg/cluster/kernel_selfrecover.go`) now clears the
  hold explicitly via `ClearKernelUpgradeHold()` before the per-RG
  resets, synchronously. This is the sole synchronous reset producer:
  the orchestrator rejoin and kernel self-recovery. Clearing first, in
  deterministic RG order, preserves the r2 Codex HIGH never-both-down
  property — the node is election-eligible the instant rejoin returns —
  at the all-RG scope where it belongs, instead of on the first arbitrary
  RG a reset happened to name.
- The orchestrator transport follows: `grpcCluster.ResetFailover`
  previously enumerated every configured RG and issued
  `cluster-failover-reset:<rg>` per RG — i.e. it depended on the per-RG
  clear this fix removes. It now issues the single node-local
  `cluster-rejoin` SystemAction (`Manager.ResetAllFailover`), priced
  `PermMaint`, mapped in `SystemActionVerbCommand`, and denied on the
  fabric listener like the other local-only lifecycle verbs. The per-RG
  readback (`LocalRejoinComplete`, #5044/#5138) is unchanged and still
  fails closed if any configured RG stays drained.
- The promotion-marker reconcile (`ClearKernelUpgradeHold` from the
  daemon) and the reboot-to-known-good path are unchanged. A
  reverted/failed roll still keeps the hold fail-safe.
- Stale comments updated: `TestResetFailover_ClearsKernelUpgradeHold`
  now drives `ResetAllFailover`; `ClearKernelUpgradeHold`,
  `kernelUpgradeHold` field, daemon reconcile, and `pkg/cluster/README.md`
  no longer describe a per-RG clear.

The acceptance probe in the issue — held=true and no RG primary after
`ResetFailover(1)` with an unpromoted candidate, and the orchestrator
rejoin still clearing synchronously — is pinned at both the manager
layer (`ResetAllFailover`) and the wire layer (`cluster-rejoin`).

## Risk

Bounded to the hold-release scope. An operator who previously relied on
a single-RG reset to force-release a stuck kernel-upgrade hold must now
use the node rejoin (`xpfd upgrade kernel rejoin`, which resets every
RG) or wait for the promotion-marker reconcile; the per-RG reset still
performs all of its per-RG work. This is deliberate: a per-RG verb must
not assert node-level verification it never performed.
