## Members

1. `DUP-CMP08` (MATERIAL): `instance-type` accepts any value. The schema leaf
   (`schema_routing.go:994`) has no validator; the compiler stores the raw
   token (`compiler_routing.go:575`); every consumer tests the literal
   `"forwarding"`. A typo (`forwardng`), an unimplemented Junos type
   (`no-forwarding`, `l2vpn`, `vpls`), or garbage (`bogus`) commits clean and
   is silently treated as a VRF — the harmful direction: `forwarding` is what
   makes the daemon SKIP VRF creation, so losing the value creates a VRF the
   operator asked NOT to have.
2. `SYN-CMP-04` (COHORT): `vrf-target`, `vrf-table-label`,
   `route-distinguisher` are deliberately accepted and inert (#9323) but draw
   no warning, unlike inert per-instance protocols (#9374). Consequence is an
   unmet VPN route-exchange expectation, not lost isolation.

## Omitted-type decision (per the issue's "decide and document")

Omitted `instance-type` stays accepted and silent, with VRF semantics: every
consumer already treats non-`"forwarding"` as a VRF, existing tests compile
typeless instances, and warning would churn those paths for zero operator
gain. Junos types xpf does not implement (`no-forwarding`, `l2vpn`, `vpls`,
...) are rejected at strict commit (unknown non-empty value) and warned on
the tolerant path — they are indistinguishable from typos at the value
domain, and silently VRF-ing them is exactly the defect.
