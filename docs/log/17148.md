## STEP-0: defect live on current origin/master?

Partly superseded, partly live. The issue was filed against `0ce804221f`, where production strict was four hand-copied `compileOpts{lenientFlexMatchValueMissing: true}` literals and the measured divergence was: production strict accepted a value-less flexible-match-range, the zero value rejected it.

At `be463f60e7` the *field* half is already fixed by #16849 (`ece34d264f`), which this issue explicitly excluded from its scope: `lenientFlexMatchValueMissing` no longer exists, `grep lenientFlexMatchValueMissing pkg/config` is empty, the four strict entries spell `compileOpts{}`, and an executed probe (`TestProbe17148Divergence`, since deleted) reported NO DIVERGENCE between `CompileConfig` and `compileTree(compileOpts{})` on both the discard (both hard-reject, #16849) and accept (both accepted with the `no match-value` warning) arms.

What remains live at `be463f60e7`, and is exactly what this issue owns (the missing constructor, not the #16849 security semantics):

- No `strictCompileOpts()` exists (`grep strictCompileOpts` = only the #8690 test helper name `compileStrict8690`).
- Production strict is still spelled as bare literals: `compiler.go:139` and `:950` (`compileOpts{}`), `currentClusterOpts` (`var opts compileOpts`), and `compiler_services.go:2052` (`compileForwardingOptions` → `compileOpts{}`). Acceptance grep `compileOpts{` in non-test sources lists those plus the two exempt side compiles (`tunnelid.go:226`, `compiler_validate_strict_reth_lag.go:213`, both `compileInterfaces(..., compileOpts{lenientNonNumericUnit: true})` best-effort unions).
- `compileStrict8690`, documented as "the STRICT commit path — the one that runs the commit gates", built `compileOpts{skipCompactNormalize: ...}` from the zero value, as did 41 single-line `compileTree/compileExpanded(..., compileOpts{...})` test calls (recounted at base: 41).
- The `compiler_uniformgates_filter.go` gate comment still described the pre-#16849 strict shape ("hard-reject a term whose byte-offset/... could not be parsed") without the value-less discard/reject hard-reject. `lenientFlexMatch`'s godoc, which the issue reported split by the inserted field, is intact again at `compiler_opts.go:1311-1322` (the #16849 deletion restored it); verified, no change needed there.

So the next always-on strict fold would again have to be hand-edited into each literal and would again be silently absent from every zero-value test compile. That is the defect fixed here.

## Fix

- `pkg/config/compiler_opts.go`: new `strictCompileOpts()` beside `lenientCompileOpts()` — the single source of truth for strict mode. It returns the zero value today (no `lenient*`/`sanitize*` downgrade enabled), with a doc recording that any future non-zero strict field lands there once, under a non-`lenient*` name if it is not tolerant-only (per #16166).
- `pkg/config/compiler.go`: `CompileConfig`, `CompileConfigForNode`, and `currentClusterOpts` (hence both `WithCurrentClusterPrimary` entries) route through `strictCompileOpts()`.
- `pkg/config/compiler_services.go`: the test-seam wrapper `compileForwardingOptions` routes through `strictCompileOpts()` (production dispatch already passes caller opts via `compileForwardingOptionsWithOpts`).
- Part (b) of the issue's fix direction (replace the always-true flag with unconditional code) was already landed by #16849 and is not repeated: `validateFilterFlexMatchStrictOpts(cfg, opts.lenientFlexMatch)` is mode-dependent again (strict rejects value-less discard/reject; accept/next-term warn), so the flag correctly stays under its `lenient*` name as a tolerant-only downgrade.
- (c) Test helpers: `compileStrict8690`/`compileSeam8690` and every `compileTree`/`compileExpanded` call site in tests that spelled strict as a `compileOpts{...}` literal now start from `strictCompileOpts()` (or `lenientCompileOpts()` where the site already did) and apply seam overrides (`skipCompactNormalize`, the single-flag fabric-stamp probe) to the returned value. 28 test files migrated; sub-helper probes that take an opts value as data (NAT registry accessors, advisory appenders) are untouched — they are not compile-entry spellings.
- (d) Docs: corrected the flex gate comment in `compiler_uniformgates_filter.go` to the #16849 semantics; `flexMatchValueMissingWarning`'s doc at `compiler_validate_strict_filter.go:2442-2447` already states the current strict/tolerant split, no change needed; fixed the stale `compileOpts{} zero value` label in `compiler_ipsec_lifetime_9008_test.go`.

## Risk

Low. No behavioural change: strict was already the zero value after #16849, so every routed entry compiles identically (golden output byte-identical, flex cells unchanged). The only production-code change is spelling — four literals become calls to a constructor returning the same value. Residual: the AST census flags only direct `compileTree`/`compileExpanded` literal arguments in tests; a test that builds a bare `compileOpts{...}` into a variable first and passes the variable would evade arm 3 (arm 1/2 still catch any resulting production divergence only if the variable feeds a production entry, which it cannot). Future non-zero strict fields must be added to `strictCompileOpts()` — enforced for production by arm 3 and for the value by arms 1–2.
