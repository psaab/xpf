# Issue #12623: Quarantine zones with any unknown child

## Defect and decision

The #11575 tolerant-load heuristic tried to identify whether an unknown
security-zone child resembled an enforcement keyword. Its edit-distance and
prefix bounds missed distant spellings including `addr-set`, `adr-book`,
`addrset`, and distant variants of screen, host-inbound, TCP-RST, and interface
membership. On `Store.SyncApply`, the compiler then retained the zone's
interface binding even though the unknown child had been dropped. A policy
reference could consequently fall back to a same-named global address set
while the zone appeared healthy.

Per the owner decision recorded in #12623, the tolerant path now unbinds on
ANY unknown zone child (option (b) from #12218). This intentionally reverses
the #11575 behavior pinned by `TestUnknownNonEnforcementZoneChildWarnsWithoutUnbinding11575`:
unknown `description-typo` content now warns and quarantines the zone too. The
strict compile path continues rejecting unknown zone children; known children
and the tolerant-load/no-brick behavior remain unchanged.

## Change

`recordUnknownSecurityZoneChild11575` now records and quarantines any unknown
child in one decision, without guessing whether its spelling is close enough
to a known enforcement name. Removed the now-dead distance, substring, and
prefix heuristic helpers. The existing post-pass clears membership and screen
claims after all repeated zone blocks, and the dataplane diagnostic now says
that an unknown child caused exclusion.

Regression coverage includes every distant spelling enumerated in #12623 at
`CompileConfigLenient`, the `addr-set` / `adr-book` / `addrset` SyncApply
reproducers, and strict-path rejection. Existing valid zone-local address-book
coverage remains the positive control. Tests also pin warning and quarantine
behavior for an unrelated unknown description and packed unknown child.
