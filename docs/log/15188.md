# Issue #15188 — helper-internal republishes re-ship single-use policy_session_rebinds (C08-02)

- **Issue:** After a full snapshot apply with `policy-rematch extensive`
  (a policy/zone rename commit), the coordinator's retained
  `ForwardingState` kept that apply's single-use `policy_session_rebinds`
  and `policy_rename_ancestry`. Every later helper-internal republish —
  a neighbor push (`Coordinator::apply_manager_neighbors_with_permanent`,
  `coordinator/mod.rs`) or an HA fabric refresh
  (`Coordinator::refresh_fabric_links`, `coordinator/snapshot_refresh.rs`) —
  clones `self.forwarding` through `publish_runtime_view`, so workers took
  their rotation branch on the fresh Arc and re-ran
  `rebind_policy_sessions_from_snapshot` over the full record list:
  two `restamp_bpf_conntrack_policy` calls plus shared-table restamps per
  record, on every worker, on every rotation, with no generation check,
  until the next Go partial/full publish happened to clear them. The Go
  single-use strip (#10509/#11530/#12073,
  `stripSingleUseCommitMetadata`) does not cover this helper-internal path.
- **What:**
  - `Coordinator::clear_single_use_policy_metadata` (new,
    `coordinator/mod.rs`): clears the retained
    `policy_session_rebinds`/`policy_rename_ancestry`. The just-published
    Arc keeps its copy, so the full apply still ships the metadata once.
  - Called immediately after the `publish_runtime_view()` in both
    full-apply sites: `refresh_runtime_snapshot_inner`
    (`coordinator/snapshot_refresh.rs`) and
    `reconcile/snapshot::apply_snapshot`
    (`coordinator/reconcile/snapshot.rs`). The choke point itself
    deliberately does not strip (documented there): it cannot distinguish
    a full apply from a helper republish.
  - Worker-side backstop (`worker/loop_body/mod.rs`):
    `last_rebind_generation` (seeded from the startup forwarding's
    generation) tracks the config generation whose rebinds this worker
    already consumed; a rotation whose forwarding carries rebinds for an
    already-consumed generation passes an empty record slice. A record is
    therefore applied exactly once per generation even if a republish
    still carries it. Neighbouring rotation behaviour (first-policy
    rematch, zone purges, CoS/screen updates) is unchanged.
  - Field docs on `ForwardingState::policy_rename_ancestry` /
    `policy_session_rebinds` (`types/forwarding.rs`) record the
    single-use contract.

## RED -> GREEN proof

- **RED (fix reverted, tests kept):** all 4 new cells fail —
  `neighbor_push_after_full_apply_ships_no_rebinds_15188` (retained
  forwarding still carries the metadata), `fabric_refresh_…_15188`
  (fabric refresh ships `rebinds=1`, want 0),
  `later_full_apply_still_ships_fresh_rebinds_15188` (retained state not
  stripped), and the worker cell
  `rebind_record_applied_exactly_once_per_generation_15188` (same-generation
  republish re-applies the record: zones move `(3,2)/(2,3) -> (1,2)/(2,1)`).
- **GREEN:** the same 4 cells pass. The coordinator cells drive real
  `refresh_runtime_snapshot_disarmed` full applies, then the real neighbor
  push / `refresh_fabric_links` republishes, and assert the published view
  ships `rebinds=0`/`ancestry=0` while the neighbor/fabric payload itself
  still lands. The later-full-apply control proves stripping is per-apply,
  not a latch. The worker cell drives the real `worker_loop`: gen-8 full
  apply rebinds the pair to `dmz->wan/p-new`, a same-generation republish
  carrying a zone-rewritten record must not move the pair, and the gen-9
  fresh record is consumed normally.
- **Build note:** unmodified `origin/master` (26ce364426) does not compile
  its test target: `afxdp/mirror/mod_tests.rs:1032` constructs
  `MirrorConfigSnapshot` without the `ingress_vlan_id`/`unit_scoped`
  fields added by #15113/#15114 (pre-existing, unrelated). Test runs above

## Risk

- Coordinator change is two `Vec::clear()` calls on already-committed
  state after the worker-visible store; the published Arc is untouched,
  so workers still consume the apply's rename exactly once. Worker change
  adds one `u64` compare on the cold rotation branch only; the per-packet
  path is untouched. No wire/config change.
