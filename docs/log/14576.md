# #14576 — `security flow tcp-mss <kind>` packed tail silently dropped (Y03-01)

## Defect

`selectMSSToken` (`pkg/config/compiler_interfaces.go`) returns only the
compiler-selected MSS token for a tcp-mss kind node (the `mss` child's
value, or flat `Keys[1]`, or `Keys[2]` after the flat `mss` keyword); no
caller inspected anything past it, and the kinds are `closedWorldOpaque`
so `SchemaValidate` never sees the tail either. Any extra tokens packed
into the same kind node committed clean and were silently dropped while
`show configuration` still displayed them.

Measured at `origin/master` `a615690ed` (probe via `CompileConfig`,
flat-set AST via `ParseSetCommand`+`SetPath`, hierarchical via parser):

- `set security flow tcp-mss gre-out mss 1300 all-tcp mss 1350` → ok,
  `TCPMSSGreOut=1300 TCPMSSAllTCP=0` — the second kind is lost; when the
  lost kind is `all-tcp` the PMTU clamp the operator configured is not
  applied.
- `security { flow { tcp-mss { gre-out mss 1300 all-tcp mss 1350; } } }`
  → same loss (strict `CheckText` text of this shape is in fact refused
  earlier by the #8437 sibling-statement gate; the flat-set spelling
  nests instead and was fully silent).
- `set security flow tcp-mss all-tcp mss 1350 bogus 7` → ok, all=1350.
- `set security flow tcp-mss all-tcp 1350 9999` → ok, all=1350.
- Controls behaved: two-`set`-line form compiles both (1350/1300);
  `all-tcp msss 1350` and `mss 99999` refuse.

Junos rejects these spellings, so the acceptable outcomes are "compile
every kind named" or "reject". This fix rejects (no synthetic multi-kind
splitting — Junos has no such statement).

## Fix

Token accounting in the existing commit-time gate, the single source of
truth shared by compiler and validator:

- `pkg/config/compiler_interfaces.go`: `selectMSSValueEnd` computes the
  selected token plus the end-exclusive index just past the consumed
  value grammar, mirroring `selectMSSToken` branch-for-branch including
  the #1979 mixed-shape precedence and the #8824/#8838 branches.
  `mssLeftoverTokens` returns every token packed past that point:
  on the kind node itself (packed hierarchical), inside the selected
  `mss` child (`all-tcp { mss 1350 bogus 7; }`), on the flat-set value
  carrier child (`all-tcp > [1350 9999]`, `gre-out > [mss 1300 all-tcp
  ...]`), past an unparseable-child fallback, and on never-read sibling
  children (extra child after a braced `mss`, repeated `mss`). Tokens
  the #1979/#8838 precedence deliberately discards (flat token beside a
  parseable child; unusable child beside a flat token) are consumed by
  that precedence and are NOT leftover, so the mixed shapes keep
  compiling to the flat value.
- `pkg/config/compiler_security_flow.go`: `checkTCPMSSKindTail` (new,
  called by `checkTCPMSSKind` before the range gate and by the
  `ipsec-vpn` branch before its rejection, so a tail cannot hide behind
  it) — strict: hard error
  `invalid tcp-mss value: unexpected token(s) ... after the selected MSS
  value ...`; lenient (boot/peer-sync): warning with
  `(ignored: token(s) not compiled — ...)`, compiler keeps only the
  selected (first) value. `validateTCPMSSRanges` already runs on the
  group-expanded tree, so apply-groups shapes are covered; the fully
  packed `tcp-mss > [kind ...]` leaf is reached via the existing
  `tcpMSSOptionNodes` synthetic node.

NOT changed: `parseMSSValue`/`selectMSSToken` selection semantics,
`compileFlow` (gate runs before it on both strict and lenient paths),
schema opacity, dataplane. No new split/compile-both semantics.
