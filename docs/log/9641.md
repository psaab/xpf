## Codex hostile plan review, round 1: PLAN NO, 5 findings

- **Timestamp**: 2026-09-11
- **Action**: dispositions (the plan is revised after the lead's answer on the regression
  handling below).
  - **P1 Critical: name-set equality is not generation identity. ACCEPTED.** RG moves,
    policy changes and sanitised collisions can keep one flat set, and a flat set also
    erases connection -> child structure. The revised match compares a structural
    fingerprint per connection: children plus `local_addrs`/`remote_addrs` (see
    local_addrs derivation above). A render-identical ambiguity is not guessed:
    re-initiation proceeds only when every matching candidate attributes the name to the
    same RG, and skips otherwise. Codex's persisted-marker alternative is recorded but not
    adopted; the agreement rule resolves ambiguity without new durable state.
  - **P2 High: render-error handling was wrong. ACCEPTED.** A hard render error aborts the
    WHOLE production render, so charon never loaded any of that generation. A candidate
    whose whole render fails is disqualified; only renderer-skipped VPNs are excluded
    within a candidate. `LoadableSANames`' per-VPN rule must change accordingly.
    Candidates must not call `PrepareConfig` (DNS/DHCP/kernel state is neither historical
    nor cheap); `--list-conns` reports loaded config, not SAs, so IKE-only state is
    irrelevant.
  - **P3 High: wrong rollback source, arbitrary depth. ACCEPTED.** `DB.ReadRollback`
    slots have no production callers. The canonical history is `Store.history`
    (`Store.ListHistory()`, a goroutine-safe most-recent-first snapshot of uncompiled
    `*config.ConfigTree`), persisted as `xpf.conf.N` by `saveRollbackFiles`. `SyncApply`
    pushes the previous active into it (`pkg/configstore/store.go:830`), so peer-synced
    generations are included. Candidates are the promoted config plus ALL retained
    history, not K=5, precompiled outside the failover path.
  - **P4 High: cache lifetime unsound. ACCEPTED, and it exposes a regression in landed
    #9511.** Verified mechanism:
    1. `applyConfig` writes the new file with `fsatomic.WriteFileAtomic` BEFORE
       `reload()` and does not restore it on failure (`pkg/ipsec/manager.go`).
    2. `strongswan.service` on loss fw0 has `ExecStartPost=/usr/sbin/swanctl --load-all
       --noprompt`, `ExecReload=... --load-all` and `Restart=on-abnormal`, so a charon
       restart or reload loads that new file.
    3. `ipsecLoadedCfg` still names the old generation, because `ApplyNotifyLoaded`
       fires only on xpfd's own successful reload.
    4. Master's promoted-config answer is the generation charon now runs.
    So head is worse than master after a failed xpfd reload followed by a charon restart
    or reload outside xpfd. Reported to the lead with options: fold the fix into #9641,
    or a stopgap that clears `ipsecLoadedCfg` in that window. The revised design queries
    charon on EVERY re-initiation pass and never caches charon's answer (only compiled
    candidates).
  - **P5 Medium: error policy. ACCEPTED.** Charon unreachable keeps today's fallback,
    UNCACHED and re-asked on the next pass. An unknown mismatch uses rule (b), tightened:
    initiate only names whose RG attribution agrees across all known candidates, skip
    otherwise. Falling back to the promoted config there would recreate the wrong-RG
    defect.

  - **P5**: agreement among known candidates cannot establish an UNKNOWN generation's RG.

    wrong-RG initiation, and conflicting retained candidates can suppress an initiation
    master would perform.

    evictions, publish rebuilt snapshots atomically). A multi-RG takeover repeats full
    dumps, and an unreachable query can add about 15s.

  assume it's right"), revision 2's inference model is not iterated blind. Proposed to
  the lead instead: a render-time GENERATION MARKER that charon reports back, making
  identity something READ rather than inferred. Render an inert marker connection whose

  never initiated); `swanctl --list-conns` then names exactly the generation charon

## Codex short plan check, round 3 (revision 3, marker): PLAN NO on atomicity

- **Timestamp**: 2026-09-11
- **Verdicts**:
  1. INERTNESS: an unreferenced pool cannot be drawn from, negotiated against, or make
     charon initiate or respond, because only a pool a connection references supplies
     virtual addresses. It cannot appear in connection or SA paths, since those enumerate
     connections and SAs, not pools. **Inert.**
  2. **ATOMICITY: NO.** `swanctl --load-all` runs separate loaders (authorities, pools,
     connections, secrets), not a transaction. The 6.0.5 capture shows pools loading
     before connections. After a failure or an interruption, connections and pools can
     belong to DIFFERENT generations.
  3. FALLBACKS: every listed fallback is master's answer. Exception: a stale but KNOWN
     marker left by a partial load skips the fallback and can be worse than master.
  4. DIGEST SOURCE: sound, provided the active-config identity check and the
     `ActiveDigest()` read stay under applySem; a non-active config gets "unknown".
- **Disposition: ACCEPTED, refinement proposed.**
  - Keep the marker for IDENTITY, and VALIDATE the claimed generation against what
    charon actually loaded: the per-connection fingerprint (children + `local_addrs` +
    `remote_addrs`, from `--list-conns --raw`, whose parser already exists) must equal
    the claimed generation's whole render (`LoadableSANames` rules: skips excluded, a
    render error disqualifies).
  - On a mismatch, or when the candidate's `local_addrs` cannot be reproduced without
    `PrepareConfig`'s kernel lookup or DNS hint, fall back to master's answer. There is
    NO wildcard.
  - A partial load, with pools at one generation and connections at another, then
    fails validation and falls back.
  - Residual: a render-IDENTICAL RG move (explicit local-address unchanged) combined
    with a pools-only partial failure. The loaded connections are then byte-identical
    across the two generations. Documented, not solved.
- **Action**: confirmed xpf's own reload command. `Manager.reload()` runs
  `swanctl --load-all` (`pkg/ipsec/manager.go`), so a marker pool in the same file is
  loaded by xpf's reload as well as by strongswan.service. No explicit pool load needed.
- **Action**: plan revision 3b. The marker is identity only, and validation against
  `--list-conns --raw` is required:
  - fingerprint equality between the loaded connections and the claimed generation's
    whole render (children + local/remote addrs);
  - local addrs resolved config-only (explicit addresses, else the configured interface
    unit address);
  - an unvalidatable candidate or a mismatch falls back to master's answer, with no
    wildcard.
  - Residual: a render-identical RG move plus a pools-only partial load.
  - **File(s)**: `docs/pr/9641-ipsec-startup-loaded-generation/plan.md`
