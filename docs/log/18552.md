## Production reachability (severity)

**Verdict: reachable only under named conditions.** The generation check is
not one of them: it does not stop a later send.

- **Generations climb on every send.**
  - The sender stamps every install from one global counter
    (`pkg/cluster/sync_conn_gen.go:650-651` `nextInstallGen`, applied at
    :940-941 for each send).
  - Its own comment (:810-815) says a re-send of a live key "intentionally
    bumps the generation".
  - The receiver forwards that stamp to the helper unchanged
    (`pkg/dataplane/userspace/manager_sessionsync_request.go:386` / :444).
  - Both receive-side guards refuse only a STRICTLY older generation:
    `installGenGuardV4` (`sync_conn_gen.go:1824-1830`) and the helper's
    `session_import.rs:1501-1510`.
  - So any later send from the same peer process passes, and a legacy
    generation-0 peer bypasses the check entirely. The triage fixture's
    generation 0 was not what let the race through.
- **Conditions:**
  1. This node is the newly active owner of the RG. A worker promotes the
     peer row on its first owner hit (`resolve.rs:837` arms the promotion).
     Since #18540 the new owner activates before it drains the old owner's
     backlog, so late imports arrive in exactly this phase
     (`docs/ha-failover-status.md`, the "Note for that gate").
  2. A peer import of the same 5-tuple overlaps the promotion. Either it runs
     between the flip and the shared publish, or its lease body spans them:
     it re-read the peer row at :1475 and publishes after the promotion did.
  3. The T1 leg and the reverse-companion legs also need the late row to name
     a DIFFERENT translation. A later send for the same 5-tuple with a
     different translation is a new incarnation on the peer: the 5-tuple was
     reused and the peer's allocator picked another port. This node must
     still hold the predecessor row, because the predecessor's delete has not
     been applied here. Two ways that happens:
     - a delete and the successor's install reordered across the two fabric
       receive loops (a newer install supersedes; the older delete is then
       refused as stale);
     - a predecessor that expired on the peer while sync was down.

     Fixed-source-port UDP (DNS, NTP, IKE) reuses tuples this way routinely.
- **A same-incarnation resend, the common backlog case, carries the same
  translation.** `reserve_flow` takes its idempotent return (:6327), and the
  reverse companion has the same key. Only the shared-origin overwrite leg
  remains.
- **The fixture models condition 3:**
  - the stored row has generation 7, the late row generation 9;
  - the two rows have different RT_FLOW session ids;
  - T1 = 40002, T2 = 40001;
  - T1 is seeded through the production import and the worker drain.

## Design notes and residuals

- **Permit keys.** The permit covers `key` and
  `reverse_session_key(key, decision.nat)`, the same pair the new-flow install
  takes. Every import lease of the forward key also covers `key`, so the two
  always exclude each other. A promotion that started from a reverse-companion
  hit covers that companion and its forward.
- **Hot path.**
  - The permit is taken once per promotion: the first owner hit after
    activation. After that the row is `SharedPromote` and is no longer
    promotable.
  - `try_acquire_installs` allocates (the keys `Vec`, the permits `Vec`, an
    admission `Arc`, possibly a gate-entry `Arc` and a shard insert that a
    refusal rolls back), as it does for every new flow. Review cycle 1 (r24
    P3-1) put a non-allocating `install_claim_would_refuse` pre-check in
    front of it, so a refused hit costs lock operations only.
  - A refused attempt repeats only on a RESOLVED hit, and only while a lease,
    a sibling's permit, a publisher or a clear fence holds the tuple. Before
    review cycle 1 this line said "on each hit", which was false: a refused
    packet seeded the flow cache, and cache hits never promote. The refused
    packet is now kept out of the cache (`promotion_deferred`, fold F1).
  - The flip-failed case does not repeat per packet:
    `apply_deferred_shared_materialization` cancels the deferred promotion when
    materialization fails (`resolve.rs:395-397`).
  - The permit never blocks. The import's side may wait up to its existing
    100 ms `ACQUIRE_BUDGET`, off the packet path.
- **No refusal counter.** A refusal is a deferral and retries on the next
  resolved hit (the refused packet does not seed the flow cache).
  It joins the existing silent no-op of a flip that did not apply. A new
  static counter would be read by nothing: it is not exported in the status
  protocol, and a cell cannot reference it without compiling at master.
  Surfacing promotion deferrals is a follow-up candidate, not part of this
  fix.
- **Gated helpers on the promote leg.**
  - The only gated helper was the origin RMW.
  - `publish_session_map_entry_for_session` passes `ct: None`, so it publishes
    no conntrack row (`bpf_map/mod.rs:2079-2140`).
  - `publish_shared_session` and `replicate_session_upsert` take no tuple gate.
- **Side effect.** A peer synced DELETE also takes the tuple lease
  (`session_import.rs:2441`), so it now serializes against promotion the same
  way. Pinned in review cycle 1 by `in_window_peer_delete_is_refused_*_18552`.
- **Departure from the brief (master-red tree).** The brief said the tree
  should hold only the test file and its registration. Cells (a) and (b)
  need the promote hook, and (b) also needs `adopt_tuple_gate_for_test`, so
  the tree holds those two seams as well. Both are `#[cfg(test)]`-only, and
  the tree has no non-test code change; `git diff --stat` there shows the
  same four seam files plus the new test.
- **Review cycle 1 residuals.**
  - **Codex P1-4 / r24 P2-1(a), pending (fold 2).** A reply-first promotion
    flips and publishes only the reverse row, so the forward row the #9678
    and #9714 gates read can stay `SyncImport`. The lead is choosing the
    design. Fold 1 does not change reverse-promotion semantics, and its
    pieces are direction-agnostic: `synced_row_incarnation` judges exactly
    the row under the key it is given, so fold 2 can call it for the forward
    row of a reverse-hit promotion. The "closed" wording in
    `docs/session-sync-architecture.md` and the permit-keys note above are
    left for fold 2 to narrow, as instructed.
  - **r23 P3-3, pre-existing, not fixed.** The coordinator demote
    (`shared_ops/owner_rg.rs` `demote_shared_owner_rgs`, ~:3-62) rewrites
    shared rows to `SyncImport` without the tuple gate, and a promotion's
    Owner verdict is computed before its permit. A promotion that straddles a
    demote can publish `SharedPromote` after the demote's rewrite. The queued
    `DemoteOwnerRGS` fixes the worker row, and a peer import heals the shared
    row while the RG is inactive. Interaction with F2: if that stale
    `SharedPromote` survives to reactivation, this worker's row reads
    `SharedLocal` and is not promoted until a peer import or the transient
    purge heals shared. Shared still records local ownership, so #9678 and
    #9714 hold, and `SharedLocal` does not suppress the cache seed, so it
    costs no per-packet slow path.
  - **A promotable worker row with no shared row and nothing queued** would
    now never promote (before, the promotion re-created shared). The paths I
    read do not leave one in a steady state: imports publish shared before
    the fan-out, new flows publish at install, and demotes rewrite shared in
    place. I did not audit every shared-removal site (`session_delta.rs`
    closes, GC teardown, purges) for whether each also removes every
    sibling's promotable replica; a site that does not would strand that
    replica unpromoted. Such a row still forwards, and `SharedAbsent` does
    not suppress the cache seed, so the cost is a lost promotion, not a
    per-packet slow path. The fixtures that built this shape are the 21
    updated above.
  - **The importer's synthesized reverse still uses the pre-lease HA view**
    for its resolution (pre-existing). Its key does not depend on HA state,
    and a stored resolution is re-resolved on its next hit.
  - **No behavioural killer for the pre-check.** Disabling
    `install_claim_would_refuse` changes only allocation, which no cell can
    observe; `try_acquire_installs` still refuses. Its unit cell pins the
    predicate (every holder class, and no entry inserted).
  - **Live gate.** This fold touches session sync and the promote path, so
    CLAUDE.md requires `make test-failover`. The brief forbids touching the
    lab clusters from this lane; the lead owns the cluster gates.
