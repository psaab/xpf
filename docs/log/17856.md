# #17856 — a deny alternative matching the command core disables the pipe-only guard

- **Timestamp**: 2026-10-27
  - **Action**: Reproduced RED on origin/master (61aa231da6). A scratch
    probe against `CompiledLoginRegexes.EvaluateFormsWithPipe` (the
    evaluator the CLI gate calls at `pkg/cli/command_regex_leaf_16158.go:230-234`)
    showed `allow ^show` / `deny ^sh|display set` over
    `show configuration | display set` ALLOWED with the core-measured
    reason "allow matched a longer extent than deny (4 > 2 characters)":
    on the full form the deny's `display set` alternative wins 11 > 4
    through pipe text only, but because the sibling `^sh` alternative
    matches the core (2, losing to 4 there), #16780's `pipeOnlyDeny`
    first clause (`longestMatchLen(c.deny, core) < 0`, whole-pattern)
    was false, `denyingCoreTier` stayed false (the core is allowed), and
    the #14686/#16780 pipe-boundary save at login_regex.go:430 re-allowed
    the command. 7 new config cells and 7 new CLI cells (combined and
    split pipe suffix, subtree spelling, `\| match` verb, grouped
    sibling, anchored full-spelling pipe deny, exception-allow core)
    all ALLOWED pre-fix; every control cell passed pre-fix.
  - **Fix**: `pkg/config/login_regex.go` — `pipeOnlyDeny` now judges the
    deny PER ALTERNATIVE: only the alternatives realizing the deny's
    winning extent on the full piped form decide whether the denial is
    pipe text (a non-winning sibling's core touch is already priced into
    the core verdict, which is allowed; a winning alternative that also
    covers core text keeps the denial core-explained and the
    deny-with-exceptions saves available). Alternatives come from a new
    `denyAlternatives` helper reusing the #9340 splitter
    (`denyPatternAlternatives9340`, same POSIX dialect
    CompileLoginRegexes compiles in, union-exact); a pattern that cannot
    be split degrades to the whole pattern as its single alternative —
    the pre-#17856 whole-pattern reading.
