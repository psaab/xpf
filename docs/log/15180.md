# #15180 — ipsec: renderedSectionEntry locates a connection by an unanchored substring (C02-01)

- **Timestamp**: 2026-10-19
- **Action**: In `renderedSectionEntry` (`pkg/ipsec/policy.go`), anchored
  the connection-header search to a line start at exactly two spaces:
  the marker `"  <name> {\n"` is now matched only at offset 0 of the
  section or immediately after a `"\n"`. The close-marker search and
  the returned slice are unchanged.
- **File(s)**: `pkg/ipsec/policy.go`,
  `pkg/ipsec/rendered_section_anchor_15180_test.go` (new),
  `pkg/ipsec/README.md`, `docs/log/15180.md`

## Mechanism (verified at base b9ed3334e9)

`renderedSectionEntry` pre-fix did `strings.Index(section, "  "+name+" {\n")`.
Every rendered connection contains nested four-space blocks
`    local {`, `    remote {`, `    children {`. Each contains the
two-space marker as a substring at its third character, so for a VPN
named `local`, `remote` or `children` the search matched the nested
header inside whichever earlier-sorting connection came first, and
the returned slice ran from that nested header to that connection's
top-level close. Consequences, both directions:

- The keyword VPN hashed the earlier VPN's `remote {auth}` +
  `children {<child>}` tail plus its own `ike-<name>` secret. Rotating
  the keyword VPN's own PSK still changed its hash (the secret is keyed
  correctly), which masked the defect for the PSK arm — but every
  connection-block field of the keyword VPN (selectors, proposals,
  local-address, lifetimes, start/DPD, if_id) was absent from its
  fingerprint, so the #10878 teardown was lost for those changes: the
  established SA kept forwarding under the superseded config.
- Editing the earlier VPN's nested block (its auth, its child
  selectors) changed the keyword VPN's fingerprint, tearing the
  keyword VPN's SA down spuriously.

A first hash-level test that only rotated PSKs therefore passed
pre-fix; the pinning evidence is the section-entry test, whose pre-fix
failure shows the returned entry verbatim:

```text
entry for remote lacks its own remote_addrs:
"  remote {\n      auth = psk\n    }\n    children {\n      aaa {\n ..."
```

i.e. the slice starting at `aaa`'s nested `remote {`, not at the
top-level `  remote {` connection (peer 10.0.2.20).

Sorted order note: connection names render sorted, so an
earlier-sorting VPN (here `aaa`) always precedes `children`/`local`/
`remote`. The secret lookup `ike-<name>` has no nested occurrence and
was already correct; it now shares the anchored lookup.

## Fix

- `renderedSectionEntry`: accept the marker only at section start
  (`strings.HasPrefix`) or after a newline
  (`strings.Index(section, "\n"+marker)`). A four-space nested header
  can never satisfy either: the characters before its name are spaces,
  not a line-start two-space indent. Not found still returns
  `("", false)`, so a genuinely missing connection still errors in
  `renderedConnectionHashes` (fail-closed, unchanged).
- NOT changed: the close scan (`"\n  }\n"`), hash composition
  (connection + NUL + secret), `renderedConnectionHashes` section
  splitting, the renderer, `connNamesInConfigText14589`, teardown /
  re-initiation. Existing fingerprints for non-keyword names are
  byte-identical (the anchored match finds the same top-level header
  the unanchored search found first for them); a keyword-named VPN's
  fingerprint changes once at upgrade to its own block's hash, which
  may cause a single teardown/re-initiate of that VPN on the first
  apply after upgrade — the safe direction.

rotating `remote`'s PSK terminates `remote` and not `aaa`; rotating
only `aaa` does not terminate `remote`.

## Risk

One-time fingerprint change (and possible single teardown) for
VPNs/connections literally named `local`, `remote` or `children` on
first apply after upgrade, as their hash becomes their own block's.
No other name's fingerprint changes. The anchor relies on the
renderer's invariant that top-level headers are exactly two-space
indented at a line start — the same invariant the close scan and
`connNamesInConfigText14589` already assume.
