# Issue #13195: purge reinjection state at owner lifecycle boundaries

## Why

A disconnected submit client left its queued, write-started, and terminal-but-unacked entries in `ReinjectCore`; a daemon `run_id` restart cleared provenance and tombstones but retained `entries`, `flow_order`, `reserved`, and `ready_count`. Those old records consumed the bounded live-entry budget, could block flow-ordered completion delivery, and collided with request IDs reused by the restarted daemon.

## What

The submit server assigns each accepted stream a unique connection ID, purging its records from a prior target core when publication changes and from its current core on disconnect. Admissions, queued writes, write resolution, cancellation rollback, and asynchronous D11 verdicts preserve/check the owner ID. A changed accepted `run_id` purges all prior-run entries and flow queues, then clears tombstones created by that purge so the new run can reuse IDs. Removed unused announce-ACK, baseline-reset, orphan-sweep, shutdown-query, and socket-parent helpers.

## Risk

The submit connection ID is internal to userspace-dp and does not change the socket protocol. On disconnect, owned pending/terminal records are discarded and counted as purged; after a run restart, old records are discarded and the fresh run may reuse request IDs. No completion from an old connection/run is exposed to a new owner.
