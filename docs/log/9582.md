## 2026-09-10 — Action: design, from reading the code (not from memory of #9412)

- **What a replica is.**
  - `synced_replica_entry` clones the publisher's `SyncedSessionEntry`, INCLUDING
    `session_id`, and retags only the origin.
  - `worker_replica_origin()` keeps promotable peer imports (`SyncImport`,
    `SharedMaterialize`) as `SyncImport`, and maps every other origin to
    `WorkerLocalImport`.
  - So `WorkerLocalImport` means exactly "a replica of a session THIS node owns".
- **Where replica ids diverge.** `upsert_synced_with_origin` adopts a non-zero wire
  id and mints one (`alloc_session_id`) for 0. Census of non-test
  `SyncedSessionEntry` literals carrying `session_id: 0`:

  | Site | What it is | In scope? |
  |---|---|---|
  | `poll_descriptor/mod.rs` ~3098 | ForwardFlow local shared publish | **yes**: replicas mint their own id |
  | `poll_descriptor/mod.rs` ~6054 | MissingNeighborSeed local shared publish | **yes** |
  | `session_glue/promote.rs` ~122 | SharedPromote republish | **yes** |
  | `forwarding/local_delivery.rs` ~121 | feeds only the BPF session-map publish (`publish_session_map_entry_for_session`); never shared or replicated | no, not a replica source |
  | `poll_descriptor/mod.rs` ~3560, `shared_ops.rs` ~1029/~1134 | reverse companions | no: 0 by the #6666 design, and a reverse RST resolves to the FORWARD entry's id |
  | `tunnel.rs` ~627 | `build_local_origin_tunnel_tx_request`, not a shared session publish | no |
  | `ha/session_import.rs` ~955 | `test_install_local_forward_session`, a test helper | no |

- **The #9412 interaction** (asked for by the coordinator).
  - The BPF conntrack mirror row is written only on the four `poll_descriptor`
    INSTALL paths, each stamping `sessions.session_id_for(&flow.forward_key)`.
    The replica install path passes `ct: None`. So today every mirror row carries
    the INSTALLER's id, and #9412's memo, keyed (tuple, SessionID), is consistent
    for installer announcements.
  - Letting replicas announce WITHOUT sharing the id would break that. The Go memo
    DELETES its record when a different id arrives (the reused-tuple rule). The
    next sweep row, carrying the installer's id, would then mismatch and resend
    class 0, undoing both the replica's announcement and #9412's fix for that
    session. The peer would also adopt the replica's id, flipping #5212
    correlation.
  - Sharing the installer's id is therefore required, not cosmetic.
- **The guard, stateless.**
  - `alloc_session_id` returns `session_id_worker_hi | counter`, where
    `session_id_worker_hi = (node_bit << 15 | worker_id) << 48`.
  - A `WorkerLocalImport` replica announces only if its forward entry's id is
    non-zero and its high 16 bits differ from this table's own namespace, i.e. it
    was CARRIED from the installer.
  - A replica holding a locally minted id stays silent: from a site not covered,
    or a legacy publish. It never feeds the memo a foreign id.
- **Bounds this change keeps, stated before any code.**
  - Several workers may announce the same class for one session: the installer
    sees the client FIN, a replica sees the server FIN. The Go memo is monotone
    per (tuple, id), and the peer import is idempotent. Volume is at most 3 per
    worker that actually carries the flow's packets, not 3 per session.
  - TIME_WAIT needs both FIN bits on ONE worker's entry. With the two directions
    on different RSS queues, each worker sees one FIN and announces CLOSING. That
    shares TIME_WAIT's 30 s default window. A configured, different TIME_WAIT
    window stays on CLOSING's.
  - A replica announcing a LOWER class than the installer already sent (RST, then
    a server FIN) is raised back by the #9412 memo for the same id. Without the
    memo (a daemon restart), the peer holds the longer window, never an early reap.
