# #18746: #16841's zero-hop DROP breaks nftables readback predicates

- **Timestamp**: 2026-11-01 (fix 1 of 3: #12128 uncertain-ACK recovery)
  - **Action**: `tableMatchesPlan` now compares each rule through
    `ruleMatchesPlan`. That function judges the decoder-dropped planned
    kinds (`decoderDroppedExprNames`: byteorder, dup, tproxy, socket, rt)
    against the kernel's expression names from `readRuleExprNames`. It
    works position by position, so a dropped expression missing from the
    kernel is a mismatch. The decodable remainder is compared byte for byte,
    as before.
  - **Cause**: 2fa9d69062 (#16841) added `expr.Byteorder` to the zero-hop
    rule at the head of all five `replaceTable` tables (host-inbound, the
    cold-boot fence, the lo0 cold-boot fence, gap/pre-activation, lo0).
    google/nftables v0.3.0 drops byteorder on decode, so the `len(want) !=
    len(got)` check failed on rule 0 every time. A committed-but-unACKed
    flush was then reported as failed.

- **Timestamp**: 2026-11-01 (fix 2 of 3: TableDropsInput and TableEnforcing, one shared matcher)
  - **Action**: `isZeroHopLimitLocalDropRule` (new `zerohop_rule_18746.go`)
    recognises only the EXACT #16841 rule:
    - the kernel names are `meta cmp payload cmp fib byteorder lookup immediate`;
    - the typed decode is byte-equal to the builder's own pieces;
    - the lookup is a plain anonymous-set lookup;
    - the verdict is DROP;
    - the set holds exactly `{RTN_LOCAL, RTN_ANYCAST}`.

    The builder now shares those pieces with the matcher
    (`hopLimitZeroExprs`, `fibDaddrAddrType`, `fibAddrTypeHton`,
    `fibLocalOrAnycastElements`), so the two cannot drift.
    `inputRulesBeyondZeroHop` drops only that rule, and `TableEnforcing` and
    `TableDropsInput` count what remains. Misreading a real DROP as zero-hop
    would read as drift and trigger a reinstall, which is the fail-safe
    direction, so the matcher is exact rather than broad.

    host-inbound drift only when `TableDropsInput` AND `TableEnforcing` are
    both false. The lo0 arm, and the handoff re-verify at
    `input_barrier_gate_10751.go`, use `TableEnforcing` alone. Fixing
    `TableDropsInput` by itself would have left the drift path unable to
    fire.

- **Timestamp**: 2026-11-01 (review fold: AG on c6cde9d858, boot-handoff availability and the sentinel error)
  - **AG 1, the boot handoff can refuse on any nft commit.** c6cde9d858 bracketed `TableEnforcing`/`TableDropsInput` by the nf_tables generation. The handoff re-verify in `removeEarlyInputBarrierAtHandoff` reads `TableEnforcing` after the barrier comes down. So one commit landing during that read made it unreadable, and the handoff refused and reinstalled the guard. At boot nothing re-drove it: the doc said "the next apply retries", but no owner guaranteed a next apply. The box stayed closed until a commit or a lease.
    - **Bounded re-read.** On `ErrGenerationChanged` only, the re-verify re-reads at once, up to `xnft.GenerationChangeRereads` (3) more times (`xnft.RereadOnGenerationChange`). A real read error is not re-read. The #18721 no-retry rule does not apply here. It bounds the overlay readback, which runs inside `reconcileIpsecHostInputFence`'s short `applySem` hold that HA transfer pre-activation waits on. The handoff runs inside an apply, whose hold already lasts seconds. The helper's doc says not to use it for the overlay.
    - **Named retry owner.** Every refusal on the first-handoff path now owes a retry (`earlyInputHandoffRetryOwed18746`, set by `noteEarlyInputHandoffRefused18746` with one Warn per episode). The owner is the existing 30 s `reassertHostInboundGapOnce` loop. Its `barrierOwed` condition, added for the #16785 pending bound, now also holds while that debt is owed. `setEarlyInputHandoffDone` discharges it with one Info. The refusal does not nudge the loop: a refusal caused by steady churn would otherwise become back-to-back full applies.
    - **`xpfd input-barrier ensure`.** The same regression was there. Both of its probes fall through to the global install on an error. So one commit during a probe (the live daemon's own apply) would install global DROP into a live daemon, or replace a standing lifeline guard with the global form. Those are the two outcomes `runInputBarrierEnsure` exists to prevent. Both probes now re-read the same way. A probe that stays unreadable still falls through, fail-closed as documented.
  - **AG 2, sentinel error.** `readAtStableNftGeneration` no longer logs. It returns `*GenerationChangedError{CommitsObserved, Before, After}`, which matches `errors.Is(err, ErrGenerationChanged)` through `%w` wrapping. Each caller labels and levels it:

    - kernel truth logs Debug and Warns after 3 passes in a row (`noteKernelTruthUnreadable18746`). Before, every unreadable kernel-truth pass also emitted a Warn labelled "host overlay readback", which was wrong.
    - the handoff and `ensure` re-read, as above.
