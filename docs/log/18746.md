# #18746: #16841's zero-hop DROP breaks nftables readback predicates

- **Timestamp**: 2026-11-01 (fix 1 of 3: #12128 uncertain-ACK recovery)
  - **Action**: `tableMatchesPlan` now compares each rule through
    `ruleMatchesPlan`. That function judges the decoder-dropped planned
    kinds (`decoderDroppedExprNames`: byteorder, dup, tproxy, socket, rt)
    against the kernel's expression names from `readRuleExprNames`. It
    works position by position, so a dropped expression missing from the
    kernel is a mismatch. The decodable remainder is compared byte for byte,
    as before.
  - **Cause**: 2fa9d69062 (#16841) added `expr.Byteorder` to the zero-hop
    rule at the head of all five `replaceTable` tables (host-inbound, the
    cold-boot fence, the lo0 cold-boot fence, gap/pre-activation, lo0).
    google/nftables v0.3.0 drops byteorder on decode, so the `len(want) !=
    len(got)` check failed on rule 0 every time. A committed-but-unACKed
    flush was then reported as failed.
  - **File(s)**: `pkg/nftables/netlink_transport.go`,
    `pkg/nftables/zerohop_uncertain_ack_18746_test.go`,
    `pkg/nftables/README.md`, `docs/log/18746.md`
  - **Validation**:
    - `TestLargeReplaceRecoversUncertainAck12128` (netns) PASSes. It was RED
      on master since 2fa9d69062: PASS at 0f7903b4c8, FAIL at 2fa9d69062
      (#18745 triage).
    - `TestUncertainAckReadbackMatchesTheZeroHopRule18746` PASSes:
      - The real zero-hop plan rule matches its readback.
      - The pre-fix typed-only compare does not match, as the fixture
        asserts.
      - Fail-closed cases are refused: the kernel lacks the byteorder;
        another kind sits where the byteorder is; a dropped kind sits at a
        decodable position; an extra kernel expression; the byteorder at
        another position; a different typed verdict.
    - Mutants, 4/4 killed:
      - MR1, no name check at the dropped position: hermetic.
      - MR2, old typed-only compare: killed only by the live netns cell,
        `TestLargeReplace...`. That cell is not forced today; the leg in
        #18745 forces it.
      - MR3, a dropped kind allowed at a decodable position: hermetic.
      - MR4, no length check: hermetic.
  - **Risk**: the readback makes one more netlink dump per chain, and it
    only runs after a Flush error. A mismatch keeps the old fail-closed
    behaviour: the Flush error is returned.
