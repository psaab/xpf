# #18212 — map fabric-parent traffic into its overlay domain

- **Timestamp:** 2026-11-02
- **Branch:** `fix/18212-campaign`
- **Issue:** Fabric/control host pings fail on all clusters despite the fabric peer address being configured on the fab* overlay.
- **File(s):** `pkg/dataplane/userspace/maps_sync.go`,
  `pkg/dataplane/userspace/fabric_ingress_domain_18212_test.go`,
  `debian/changelog`

## Why

AF_XDP receives fabric packets on the physical fabric parent, while the
local peer address belongs to its fab* IPVLAN overlay. The snapshot already
included the parent in `userspace_ingress_ifaces`, but
`buildUserspaceIngressDomainEntries` emitted domains only for ordinary
`InterfaceSnapshot.Ifindex` rows. A fabric parent without such a row therefore
had no `(parent-ifindex, untagged)` domain key; `ingress_domain_for` returned
the unresolved-domain sentinel, so the shim's local-destination lookup could
not match the overlay's peer address and host ICMP did not reach the kernel.

## Action

- Added an untagged ingress-domain entry for each admitted fabric parent,
  derived from the unique routing domain of the corresponding overlay ifindex.
  The existing `put` conflict rule still poisons contradictory claims to the
  fail-closed sentinel; an overlay with no unique domain remains unmapped.
- Added a fixture-controlled regression cell that builds the compiled cluster
  snapshot with stubbed link/address, XFRM, link-state, route-rule, DSCP-selector,
  and fabric-neighbour readers. It proves the parent domain matches the local
  overlay address domain and keeps ordinary LAN ingress mapped from its own row.
  The sysfs queue-count observation is not used by the domain mapping.
