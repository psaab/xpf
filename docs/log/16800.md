# Issue #16800: RR export-policy set clauses discarded on reflected routes (`bgp route-reflector allow-outbound-policy` never rendered)

## Why

On an xpf route reflector, export-policy `set` clauses were silently
discarded by bgpd on reflected (IBGP→IBGP) advertisements. The #5115
lowering renders Junos `then next-hop self` as the per-term route-map
clauses `set ip next-hop peer-address` / `set ipv6 next-hop
peer-address`, and local-preference/community/metric/origin/as-path
sets likewise live in the outbound route-map; but FRR evaluates an
outbound route-map for a reflected advertisement on a dummy attribute
copy unless `bgp route-reflector allow-outbound-policy` is set, so
every `set` clause was dropped for exactly the routes the #2977 fix
claims to rewrite. RR clients received the original next-hop and
attributes despite `next-hop self` / `local-preference` / `community`
in the export policy — and clients without an IGP path to that
next-hop blackholed the traffic (the #2977 failure returning through
the RR). The rendered config showed `bgp cluster-id`,
`route-reflector-client` and `route-map <export> out`, so the loss was
invisible to the operator. `grep -rn allow-outbound pkg/frr` found no
hit on master.

## What

- `pkg/frr/protocols_render_bgp.go` (`renderBGP16125`): after the
  cluster-id block, emit ` bgp route-reflector allow-outbound-policy`
  once at router level when the stanza actually renders a
  route-reflector-client. The knob is a router-global bgpd toggle with
  no per-neighbor/AF form, so this single emission — shared by the
  default instance and every VRF stanza, since all go through
  `renderBGP16125` — makes outbound set clauses effective on reflected
  routes in every stanza. This is the issue's primary acceptance shape
  ("every `router bgp` stanza that has a `route-reflector-client`
  neighbor"), chosen over the narrower "only when an export chain has
  modifying terms" variant: it does not depend on resolving effective
  chains (own/global/composed/narrowed-alias/emptied-deny/
  default-export) per stanza, covers terms added later, and leaves
  accept/reject filtering (already effective) unchanged.
- `pkg/frr/bgp_cross_field_14585.go`:
  `bgpRRAllowsOutboundPolicy16800` reports whether the
  already-excluded `validNeighbors` set contains a neighbor whose
  `route-reflector-client` line the #14585 belt will render — same
  predicate as `renderBGPRouteReflectorClient14585` (flag set and
  effective-iBGP by router AS / per-neighbor local-as, #15663), so a
  stanza whose only would-be clients are omitted as eBGP, disabled,
  or remote-as-0 renders no knob and stays byte-identical.
- Corrected the now-conditional guarantee in comments
  (`policy_render.go`, `protocols_render_bgp.go`) and
  `pkg/frr/README.md`: reflected-route rewriting holds when the stanza
  renders the knob, which it now does for every RR stanza.
- Tests: `pkg/frr/bgp_rr_allow_outbound_policy_16800_test.go` (8
  tests) pin: exactly one router-level line after cluster-id for an
  RR client with a modifying export (next-hop self + local-pref 777 +
  community add, with the route-map clauses themselves asserted
  present); byte-identical non-RR stanzas (plain iBGP, eBGP, no
  neighbors); the line with accept-only / import-only / global-chain /
  no policy; own, global and composed (≥2) modifying chains still
  resolving; one line for two clients across families; no line when
  the only clients are eBGP-omitted (incl. local-as override),
  disabled, or remote-as-0; and per-VRF independence through
  `buildManagedSection` (RR VRF gains it, non-RR VRF and default
  instance do not).

## Risk

Only stanzas that render a `route-reflector-client` gain one line;
every other stanza is byte-identical, so non-RR configs see no reload
churn and no behavior change. On RR stanzas the change is the intended
semantic fix: outbound route-map `set` clauses (and any re-advertised
attribute modifications) now take effect on reflected routes exactly
as Junos applies export policy to reflected advertisements. No
fail-open change: accept/reject filtering already worked without the
knob and is untouched. Residual: FRR behavior is asserted from the
documented dummy-attribute semantics and the render contract; a live
bgpd adj-RIB-out probe (client A → RR → client B showing NH self and
LP 777 for 10.9/16) remains an operator/lab validation, not covered
by the render tests.
