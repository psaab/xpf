# #18662: bound ct-slice shared-evidence work

## Change

The worker-side shared-evidence pass retains a cursor and processes at most
2,048 worker-table rows per ct-slice. The pending-row completion-evidence batch
takes one map-lock pair per worker chunk and processes up to 2,048 candidates
in that hold. Stage/count lookup uses a maintained
`entry.key -> forward-wire map keys` index, then direct derived-key reads. Each
stage/count dual-map lock hold visits at most 128 rows/candidates; the full
traversal charges at most 16,384 lookup-plus-fold operations per
`run_ct_slice` invocation. It retains alias cursors and completed row folds
across paced slices, releases all three locks before folding, and emits no
partial result to the delta consumer. Alias matches still check the stored
`entry.key`, preserving exact scan matching where map and entry keys differ.
The index is updated with forward-wire publication, removal, displacement,
and alias-restamp insertion, and is cleared with its maps. Removed alias slots
remain tombstones while the canonical row is live, so releasing locks between
chunks cannot shift an unvisited alias behind the cursor; restamps revive the
same map key in its stable slot and canonical removal prunes an empty bucket.

Each pending output slot retains the live forward row's `(session_id,
NatDecision)` identity captured with its fold. Before queueing an Update, the
worker compares both values with the current row; delete-and-reinstall of the
same key therefore cannot apply an old fold to a new incarnation. The next
worker-evidence cycle evaluates the replacement from its own shared row.

Freshness contract: a worker row or alias published/revived after its cursor
slot has passed is deferred until the next worker-evidence cycle that queries
that canonical key; it is not lost because cursors restart from the beginning
on the next cycle/call. Cross-bucket displacement between chunks may mix
per-key snapshots: the processed owner can retain pre-move evidence while the
later owner sees its post-move row. This is accepted because each row is
matched by its own `entry.key`, so evidence cannot transfer across owners, and
stage/counts are max-only (never summed or cleared). The old owner can receive
only evidence its row held before displacement, which the prior single-hold
scan could also observe; the next cycle converges to the new owner.

The two-slot `SmallVec<[SharedEntryKeySlot; 2]>` keeps common aliases inline.
Publication and completion-restamp insertion branches perform an alias-index
map insert once per flow event (not per packet); the production-restamp
regression checks same-key restoration without a third key or spill.
Established packet hits use `get_mut` on the existing slot and do not run index
maintenance or allocate.

Output-slot folds stay outside map locks and are charged to the separate
16,384-operation invocation budget. Query pairs are not deduplicated: the
collision and 65,536-duplicate cells prove all output slots are folded without
allowing fan-out to make one invocation unbounded.

An indexed alias read is smaller and more exact for stage/count than a bounded
cursor scan of both whole tables: it follows only requested keys and wire
aliases whose stored `entry.key` matches them, releasing all three locks at a
fixed row/work budget. A full-table cursor would repeat whole-map work on every
nonempty batch and require maintaining cross-chunk matching semantics despite
concurrent map updates.

## Risk

- Stable tombstones remain until their canonical session is removed, so index
  storage tracks distinct wire-map keys seen during each live session (not
  only currently live aliases). Releasing locks between chunks also means
  results across different keys can span concurrent publishes/removes rather
  than one whole-table snapshot; each candidate is checked against its current
  stored `entry.key`.

- An alias bucket stays inline through two distinct map keys; a genuinely new
  third key can spill its `SmallVec` on that flow-event update. The ordinary
  completion path reuses its published key and cannot create that spill.

- The positive node-served evidence batch uses a `SmallVec` scratch with 16
  inline candidate slots; larger worker chunks can spill it, but the candidate
  count is bounded by `CT_EVIDENCE_CHUNK` and is not per-packet work.

- The retained traversal and emission path own per-pass output/request/identity
  vectors and a fixed 128-fold scratch array; this state is allocated once per
  ct-slice pass, not per packet. High alias fan-out can defer complete output
  emission across multiple cadence ticks. Expiry currently uses the slab-only
  worker-row cadence baseline, so pathological alias fan-out can extend the
  actual stage/count completion interval beyond that retention estimate.
