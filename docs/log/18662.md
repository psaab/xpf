# #18662: bound ct-slice shared-evidence work

## Change

The worker-side shared-evidence pass retains a cursor and processes at most
2,048 worker-table rows per ct-slice. Stage/count lookup uses a maintained
`entry.key -> forward-wire map keys` index and visits at most 128 lookup
candidates/rows during any hold of the shared-session, forward-wire, and
index mutexes. The pass releases all three locks between chunks. Alias matches
still check the stored row's `entry.key`, preserving the old scan's exact
matching behavior where the map key differs from the entry key.

The index is updated with forward-wire publication, removal, displacement,
and alias-restamp insertion; it is cleared with its maps and empty buckets are
pruned after the canonical session is removed. Empty buckets stay reserved
while the canonical row is live so restoring its displaced alias does not
allocate a new index entry. `SmallVec<[SessionKey; 2]>` keeps the common alias
bucket inline; the regression fixture asserts that restoring an alias does
not spill it to the heap. No allocation was added to packet processing; the
bounded work is maintenance on the ct-slice cadence.

An indexed alias read is smaller and more exact for stage/count than a bounded
cursor scan of both whole tables: it follows only the requested keys and the
wire aliases whose stored `entry.key` matches them, while still releasing
both map locks at a fixed row/candidate budget. A full-table cursor would
repeat whole-map work on every nonempty batch and require maintaining a
cross-chunk scan's matching semantics despite concurrent map updates.

## Risk

- The alias directory adds storage proportional to forward-wire aliases.
  Releasing locks between chunks means results across different keys can
  span concurrent publishes/removes rather than one whole-table snapshot;
  each candidate is still checked against its current stored `entry.key`.
