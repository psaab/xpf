# #18662: bound ct-slice shared-evidence work

## Change

The worker-side shared-evidence pass retains a cursor and processes at most
2,048 worker-table rows per ct-slice. Pending-row shared-map evidence is
batched under one map-lock pair per worker chunk. Stage/count lookup uses a
maintained `entry.key -> forward-wire map keys` index and fetches at most 128
rows per map-lock hold; lookup candidates and every output-slot fold iteration
share the same 128-work chunk budget. The pass releases all three locks before
folding and between lookup chunks. Alias matches still check the stored row's
`entry.key`, preserving exact scan matching where map and entry keys differ.

The index is updated with forward-wire publication, removal, displacement,
and alias-restamp insertion, and is cleared with its maps. Removed alias slots
remain tombstones while the canonical row is live, so releasing locks between
chunks cannot shift an unvisited alias behind the cursor; restamps revive the
same map key in its stable slot and canonical removal prunes an empty bucket.
Freshness contract: a worker row or alias published/revived after its cursor
slot has passed is deferred until the next worker-evidence cycle that queries
that canonical key; it is not lost because cursors restart from the beginning
on the next cycle/call. Cross-bucket displacement between chunks may mix
per-key snapshots: the processed owner can retain pre-move evidence while the
later owner sees its post-move row. This is accepted because each row is
matched by its own `entry.key`, so evidence cannot transfer across owners, and
stage/counts are max-only (never summed or cleared). The old owner can receive
only evidence its row held before displacement, which the prior single-hold
scan could also observe; the next cycle converges to the new owner.

The two-slot `SmallVec<[SharedEntryKeySlot; 2]>` keeps common aliases inline.
Publication inserts the flow's alias slot once per flow event, not on every
packet; the completion transition carries NAT from its installed `SessionTable`
entry and updates/revives that same slot. The production-restamp regression
checks same-key restoration without bucket growth or spill; established packet
hits do not perform this index maintenance or add per-packet allocation.

Output-slot folds stay outside the map locks, but their iterations are charged
to the same 128-work chunk and resume in later chunks. Query pairs are not
deduplicated: the collision and 65,536-duplicate cells prove that all output
slots are folded without allowing fan-out to make one chunk unbounded.

An indexed alias read is smaller and more exact for stage/count than a bounded
cursor scan of both whole tables: it follows only the requested keys and the
wire aliases whose stored `entry.key` matches them, while releasing all three
locks at a fixed row/work budget. A full-table cursor would repeat whole-map
work on every nonempty batch and require maintaining a cross-chunk scan's
matching semantics despite concurrent map updates.

## Validation

- Focused Rust cells: stage/count group **15 passed**; worker ct-slice group
  **5 passed**.
- Fail-on-revert mutants: removing the per-chunk slot-fold cap made the
  65,536-duplicate bound assertion fail; restoring it made the focused cell
  pass. The stage/count lock-budget mutant (`usize::MAX`) failed the 64k
  rows-per-hold assertion. The worker-budget mutant (6,145) failed the
  2,048-row first-slice cursor assertion (`0` observed versus `2,048` expected).
- Full Rust binary suite: **10,286 passed, 27 failed, 20 ignored**. The failure
  names match the pre-recorded master baseline exactly (10,274 passed, 27
  failed, 20 ignored); no new failing names, and 12 additional tests pass.
- The contender-wait/RX-stall experiment is pre-registered as the parent's
  post-land TCP lock-cell gate and was intentionally not run in this worktree.
  The guarded reachability probe could not reach the TCP Incus remote
  (`172.16.100.102:8443`: network unreachable); the parent will use the
  repository-supported deploy path and burst-only harness for that gate.
  No deployment or traffic measurement was attempted here.

## Risk

- Stable tombstones remain until their canonical session is removed, so index
  storage tracks distinct wire-map keys seen during each live session (not
  only currently live aliases). Releasing locks between chunks also means
  results across different keys can span concurrent publishes/removes rather
  than one whole-table snapshot; each candidate is checked against its current
  stored `entry.key`.

- An alias bucket stays inline through two distinct map keys; a genuinely new
  third key can spill its `SmallVec` on that flow-event update. The ordinary
  completion path reuses its published key and cannot create that spill.
- Pending evidence uses a `SmallVec` scratch that can spill above 16 candidates;
  it is bounded by the 2,048-row ct-slice chunk and is not per-packet work.
