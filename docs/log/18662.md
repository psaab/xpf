# #18662: bound ct-slice shared-evidence work

## Change

The worker-side shared-evidence pass retains a cursor and processes at most
2,048 worker-table rows per ct-slice. Stage/count lookup uses a maintained
`entry.key -> forward-wire map keys` index and visits at most 128 lookup
candidates/rows during any hold of the shared-session, forward-wire, and
index mutexes. The pass releases all three locks between chunks. Alias matches
still check the stored row's `entry.key`, preserving the old scan's exact
matching behavior where the map key differs from the entry key.

The index is updated with forward-wire publication, removal, displacement,
and alias-restamp insertion, and is cleared with its maps. Removed alias slots
remain tombstones while the canonical row is live, so releasing locks between
chunks cannot shift an unvisited alias behind the cursor; restamps revive the
same map key in its stable slot and canonical removal prunes an empty bucket.
The two-slot `SmallVec<[SharedEntryKeySlot; 2]>` keeps common aliases inline,
and regression fixtures assert stable cursor slots and no heap spill on alias
restoration. No allocation was added to packet processing; the bounded work
is maintenance on the ct-slice cadence.

An indexed alias read is smaller and more exact for stage/count than a bounded
cursor scan of both whole tables: it follows only the requested keys and the
wire aliases whose stored `entry.key` matches them, while still releasing
both map locks at a fixed row/candidate budget. A full-table cursor would
repeat whole-map work on every nonempty batch and require maintaining a
cross-chunk scan's matching semantics despite concurrent map updates.

  **3 passed**.

  failed the 64k rows-per-hold assertion. Setting the worker budget to 6,145
  failed the 2,048-row first-slice cursor assertion (`0` observed versus
  `2,048` expected).

  No build, deployment, or traffic measurement was attempted here.

## Risk

- Stable tombstones remain until their canonical session is removed, so index
  storage tracks distinct wire-map keys seen during each live session (not
  only currently live aliases). Releasing locks between chunks also means
  results across different keys can span concurrent publishes/removes rather
  than one whole-table snapshot; each candidate is checked against its current
  stored `entry.key`.
