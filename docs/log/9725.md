# Issue 9725: kernel transit gate

## Problem

The boot path could set IPv4/IPv6 kernel transit forwarding before the first XDP
program was attached. A successful dataplane Start was treated as sufficient
proof, even though Start can return before attachment converges and links can
disappear without a writer callback. That transient state made the host a
plain kernel router before policy existed.

## Reproduction and design

The required STEP-0 reproduction ran on pristine `origin/master` before the
change using a removed throwaway test named `TestStep0WindowOpenAtStart9725`.
It passed with IPv4 and IPv6 forwarding set to `1`, barrier action `remove`,
and `armed=true` between Start and the first ApplyConfig. The committed
`TestTransitGateStaysClosedUntilXDPAttach9725` now asserts the corrected
window: forwarding `0`, barrier `install`, and arm state true before a live
link is proven.

The gate now opens only when both conditions are true:

1. the dataplane has successfully started; and
2. a fresh `link.Info().XDP().Ifindex` census reports at least one live XDP
   link.

A one-second kernel-truth tick is the correctness mechanism while xpfd remains
alive. Link-map writers send a coalesced, wake-only callback to reduce
latency; the callback carries no count and the daemon always recounts. Missing
writers, device unregister, driver reset, and external cleanup are therefore
covered by the next tick. Link-info errors, zero ifindexes, missing capability,
and negative counts fail closed.

The tick is a daemon goroutine and does not survive xpfd SIGKILL, OOM, panic, or
host failure. In those cases forwarding sysctls and the barrier can persist at
their last state until restart/startup cleanup; this is an explicit residual.
Likewise, regular detach closes the kernel link before its wake is processed,
so closure is eventual within the one-second tick window rather than a
pre-detach synchronous guarantee.

Boot and bootstrap-exit host posture remains available without opening transit.
The apply tail and deferred MAC reapply reassert the same gate predicate.
Rollback closes transit before tearing down the dataplane. Standalone cleanup
installs and verifies the barrier and both forwarding sysctls before destroying
pinned XDP state; verification failure leaves the pins for the next daemon
start.

Writer-side enumeration was deliberately not used as correctness: helper-process
exit, driver reset, and external cleanup can remove the last kernel link while
xpfd remains alive, without any writer event. Those live-daemon cases are
covered by the next tick; xpfd death itself remains the persistence residual
above, handled by startup/standalone cleanup on the next invocation.

## Validation

change:

- `go test -count=1 -run 'TestAttached|TestTransitGate|...' ./pkg/dataplane ./pkg/daemon`

  — all four changed packages compiled.

  — passed.

  — the #9725 daemon entries are no longer reported; the canary reports only
  the parent-verified clean-master baseline `pkg/networkd/networkd.go:717`
  writer drift, filed separately by the parent.
