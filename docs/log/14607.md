# Issue #14607 — chunk persistent-NAT idle-lease batches below the sync frame cap

- **Issue:** An unchunked persistent-NAT idle-lease batch over 16 MiB was
  written as one session-sync frame; the receiver's `hdr.Length > 16 MiB`
  check returns from `receiveLoop`, whose deferred `handleDisconnect`
  closes the HA session-sync connection on every 30 s push. Roughly
  215k–250k idle persistent mappings (below the 262,144 per-pool cap)
  suffice. An export failure in the same loop was logged only at Debug.
- **What:**
  - `pkg/cluster/sync.go`: shared named `maxSyncPayload = 16 MiB`
    constant; `sync_conn_read.go` and the handshake reader in
    `sync_auth.go` now use it, and the oversize-receiver arm counts
    `stats.Errors`.
  - `pkg/cluster/sync_persistent_nat_lease_8121.go`:
    `encodePersistentNatLeaseBatchFrames` /
    `...FramesCounted` encode one origin/generation batch as one or more
    complete batch payloads within
    `persistentNatLeaseFrameBudget = maxSyncPayload - 64` (envelope +
    count + full-set trailer accounted). Records stay whole; a record
    that cannot fit any frame, or fails to encode, is dropped and counted
    via `MalformedRecordsDropped`. `QueuePersistentNatLeaseBatch` writes
    chunks in order under `writeMu`, each with its own increasing
    full-set sequence and the same origin/generation, and refuses
    (defense in depth) any frame that would exceed `maxSyncPayload`.
    Receiver semantics are unchanged and need no change: records are
    additive within one generation and advancing the generation clears
    before import, so chunk 1 carries the clear barrier and later chunks
    add to it. Empty batches still emit exactly one barrier frame.
  - `pkg/daemon/daemon_persistent_nat_lease_sync_8121.go`: export
    failures are counted (`PersistentNatLeaseExportFailures()`) and
    logged at Warn rate-limited to once per minute via the existing
    `warnThrottle`, replacing the Debug-only log.
  - NOT changed: the Rust helper export (single control-socket response;
    the transport that capped at 16 MiB is the cluster sync frame, now
    chunked), the receiver's additive/generation import semantics, wire
    version, or message type 41.

## RED -> GREEN proof

- **RED (base mechanism):** On unmodified master code the decisive
  acceptance population cannot be delivered: the new chunk tests failed
  to build/run against base sender symbols, and the pre-fix sender emits
  exactly one frame for the whole batch (single `writeMsg` in
  `QueuePersistentNatLeaseBatch`, no byte budget), which the receiver
  cap rejects connection-fatally (issue probes: 260k remote-less leases
  = 20.3 MB → `payload too large, delivered=false
  connected_after=false`).
- **GREEN (cluster chunking):**
  `go test ./pkg/cluster -run 'TestPersistentNatLeaseChunk|TestPersistentNatLeaseSingle' -count=1`
  passed. Cells: 262,144 remote-less leases, 1300×1024 IPv6-remotes
  leases, and 300,000 remote-less leases each produce >1 frame, every
  frame ≤ `maxSyncPayload`, and a receiver fed all frames in order
  delivers every lease under the same origin/generation; the chunk
  encoder bound cell decodes every lease across frames and yields
  exactly one frame for an empty batch; an unencodable oversize lease
  emits no over-cap frame and is counted.
- **GREEN (daemon):**
  `go test ./pkg/daemon -run TestPersistentNatLeaseExportFailureCountedAndWarned14607 -count=1 -v`
  passed: first failure Warns and counts, second inside a minute counts
  without re-warning, third after the interval Warns again.
- **Existing lease suites:** `go test ./pkg/cluster -run
  'TestPersistentNatLease|TestQueueStampsFullSetSeq' -count=1` passed.

## Risks / residuals

- Mixed-version: a new sender's chunk frames are ordinary type-41
  batches to an old receiver — each chunk is additive at the same
  generation, so an old peer imports the union (its generation-clear
  fires on the first chunk only if it implements #11486 semantics; a
  pre-#11486 peer ignores type 41 entirely, as before). No wire bump.
- A single lease record larger than the frame budget is dropped and
  counted rather than tearing down sync; with the 1024-remote cap a
  record is ~20 KiB, so this is unreachable for legal leases.
- The Rust helper `export_idle_leases` response itself is not paged;
  acceptance was framed on the cluster transport, and the helper
  response is a local control-socket JSON reply, not the 16 MiB-capped
  HA frame. Real-helper serde sizing near 10 remotes/lease remains as
  in the issue's remaining-validation note.
