# #17215 — Rollback slot error travels inside one capture; REST compare no longer answers 200 "" for a missing slot / no candidate

- **Issue**: #17215 (R4-Q52-01)
- **Timestamp**: 2026-10-27
- **STEP-0 (defect live on origin/master 9bfb2516fd)**: the getters
  `RollbackCompareSnapshot` / `RollbackSnapshot` still returned the slot
  error as a trailing positional value at 12 production call sites
  (REST 2, gRPC 3, CLI 7), plus `RollbackSnapshotErr` second-lock
  re-derivations in the REST and gRPC show-rollback handlers. A
  hermetic probe through the real REST listener (open-view classed
  principal vs uid 0, one history slot, no
  candidate) measured: classed `compare?rollback=1` → `200 ""` while
  uid 0 → `400 not in configuration mode` (the live wrong arm);
  classed `compare?rollback=40` already → 400 via the #17967 gate
  slot-error return; positive control (candidate open, slot 1) renders
  the identical diff for both principals.
- **Action**: added `configstore.RollbackCapture{Cfg, Slot, Other,
  NodeID, Gen, Err}` with `CaptureRollback(n, activeBaseline)` and
  `CaptureRollbackSlot(n)` under the same single store lock as the old
  getters; deleted `RollbackCompareSnapshot`, `RollbackSnapshot` and
  `RollbackSnapshotErr`. All 12 gate sites now consume the capture:
  pricing still treats a nil Slot as "renders nothing" (unchanged),
  each surface's snapshot struct (`restConfigReadSnapshots`,
  `configReadSnapshots`, CLI `setRenderSnapshots16613(cap)`) stores
  the captured `Err`, and handlers surface it before rendering — REST
  compare also answers `400 not in configuration mode` for a resolved
  slot with no candidate (`NoCandidate`), matching the ungated store
  helper; gRPC ShowCompare surfaces the captured history error
  verbatim instead of synthesizing `rollback slot %d not found`.
  No second live-store read was added on any gated arm; the
  #15994/#15995 single-lock price/render pairing is preserved.
