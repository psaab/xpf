## The defect

```rust
if to_id == 0 || from_id == 0 { return None; }
```

`0` is what a **deliberately unzoned interface** resolves to. After an operator
removes an interface from its security zone — a supported, committable action —
NEW flows correctly fall to the default policy while EXISTING ones decline
revalidation and keep forwarding indefinitely.

## The justifying comment was wrong in every clause after the first — measured

It said `ifindex_unambiguous_zone_id` is filled by `populate_egress` "only for
interfaces with a resolvable link-layer address", so a MAC-less IPsec `xfrmi` is
absent from it. At this base:

- the map is filled by **`populate_interfaces`** (`forwarding_build/interfaces.rs`,
  the `egress_zone_claim` loop); `populate_egress` only READS it;
- the fill is not conditioned on a link-layer address in any way — it reads
  `iface.egress_zone` corroborated by `iface.zone`, both pure config;
- #6722 is the change that made a correctly-zoned xfrmi resolve to its REAL zone,
  so the comment restated the **pre-#6722 bug** as current behaviour.

## The measurement that changed the fix's shape

Two comments in the tree contradicted each other about whether this arm can see an
unresolved egress. The ARM said "the established-hit arm never sees an unresolved
decision, because the poll path re-resolves it"; the CELL
(`an_unresolvable_egress_declines_rather_than_denying_8356`) said "198.51.100.77 …
has no route, so the egress genuinely does not resolve". An instrumented probe
through the same helper the poll path uses settled it:

```
PROBE egress_zone_id(MACLESS_IFINDEX=77) = 0
PROBE ifindex_unambiguous_zone_id keys   = [(24, 1), (12, 2)]
PROBE ifindex_to_zone_id keys            = [(11, 2), (77, 2), (12, 2), (24, 1)]
PROBE re-resolve 198.51.100.77: disposition=ForwardCandidate egress_ifindex=77
                                -> egress_zone_id=0
PROBE unzoned-ingress: ifindex_to_zone_id[24] = None
```

**The ARM was right.** The egress resolves fine, to `st0.0` (77) — the fixture adds
a `198.51.100.0/24` route through it. What is zero is the ZONE, because the fixture
leaves `egress_zone` at `""`. `ifindex_to_zone_id[77]` is `Some(wan)` while
`egress_zone_id(77)` is 0: that is the split, and the MAC has nothing to do with it.

So the shipped cell was never testing what it said. It is renamed, re-explained and
INVERTED rather than deleted, because the `(zone: "wan", egress_zone: "")` state it
exercises is real — it is what a contested ifindex produces under `stampEgressZones`
rule 1 / #7509.

## The fix is NOT "revoke on zero"

Zero has a fourth cause that must keep declining: **no egress ifindex at all** — a
flow with no route, or a peer-synced import for an INACTIVE redundancy group, which
`upsert_synced` deliberately leaves at `NoRoute`/0. Revoking there tears down the
whole standby population at the moment of promotion.

The two are separable today with no new state: `egress_ifindex == 0` is exactly the
lookup failure; a non-zero ifindex whose zone is 0 is exactly the unzoned case. The
ingress half splits the same way on `arrival_logical == 0`, with fabric ingress
keeping the entry's zone (#9384) so its lookup failure is `metadata.ingress_zone == 0`.

**And past that arm, a zero zone is simply EVALUATED rather than given a bespoke
"revoke" branch.** `evaluate_policy_result_*` (#3110) refuses to match any zone-pair
or `junos-global` rule against the 0 sentinel and falls through to the default
action — precisely the verdict a NEW flow on that interface gets. That is why this
is automatically right under both postures: `default-policy deny` revokes,
`permit-all` keeps, and in each case the established flow is treated exactly as a
new one would be. #9513's own severity analysis says the same thing from the other
direction.

## A rationale of MY OWN is retracted, and only the half that was wrong

#9384 landed `an_ingress_moved_to_no_zone_declines_rather_than_revoking_9384` as an
explicit CHANGE DETECTOR whose doc said "a future change to it is deliberate and
visible". #9513 is that change and the cell is what made it visible.

Its rationale claimed closing the residual "would mean distinguishing 'this
interface is deliberately unzoned' from 'the ledger has no row yet', **which the
snapshot does not currently express**". That half is **wrong**: the snapshot does
not need to express it, because the poll path already carries the distinction as
`arrival_logical == 0` versus a resolved ifindex with zone 0. The other half — that
revoking on a genuine lookup failure is a mass-teardown risk — was right and is now
carried by two dedicated controls.
