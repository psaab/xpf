# Issue #12195 — persist accepted neighbor replaces in the snapshot

## Why

An accepted `update_neighbors` replace updated coordinator forwarding and cleared `content_digest`, but left `guard.snapshot.neighbors` unchanged and did not request a state-file write. The next ordinary persistence event therefore serialized the stale apply-time neighbor set.

## What

Authoritative neighbor replaces compare their accepted set with the stored snapshot. A changed set is folded into `snapshot.neighbors`, clears the digest, and requests persistence; an unchanged, family-consistent set retains its digest and does not rewrite the state file. An applied family-mismatched row is excluded from the stored set and clears a non-empty digest because it changes the live manager table. A fenced replace changes neither. Rows whose parsed IP contradicts their non-empty declared family are excluded from the stored set, so later arm/rebind reconciles keep a buildable snapshot (#3771 M11). `NeighborSnapshot` derives `PartialEq` for set comparison. Additive updates retain their existing behavior because they do not represent a complete replacement set.

## Risk / residual

The stored snapshot is the input to later arm/rebind reconciles, so family-mismatched rows are excluded from that snapshot. An applied mismatch still clears a non-empty digest to prevent a stale same-generation full-apply retry while live manager state has changed. This filter does not change the manager-neighbor table's acceptance behavior. Folding and persistence apply only to authoritative `neighbor_replace` updates; additive updates cannot safely replace the stored set and retain their prior digest-invalidation behavior. No live cluster or hardware was mutated.
