# Issue #12195 — persist accepted neighbor replaces in the snapshot

## Why

An accepted `update_neighbors` replace updated coordinator forwarding and cleared `content_digest`, but left `guard.snapshot.neighbors` unchanged and did not request a state-file write. The next ordinary persistence event therefore serialized the stale apply-time neighbor set.

## What

Authoritative neighbor replaces now compare their accepted set with the stored snapshot. A changed set is folded into `snapshot.neighbors`, clears the digest, and requests persistence; an unchanged set does not rewrite the state file. `NeighborSnapshot` derives `PartialEq` for this set comparison. Additive updates retain their existing behavior because they do not represent a complete replacement set.

## Risk / residual

Snapshot folding and persistence apply to authoritative `neighbor_replace` updates only; additive updates cannot safely replace the stored set and retain their previous digest-invalidation behavior. No live cluster or hardware was mutated.
