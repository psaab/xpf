# #18672: owner-active MissingNeighbor still launders a stored fabric redirect onto WAN

## Fix

- **Timestamp**: 2026-11-01
- **Action**: `rehome_or_retain_fabric_redirect_inner`
  (`session_glue/resolution.rs`) now gives a `MissingNeighbor` the
  `ForwardCandidate` keep tests in the owner-active branch:
  - unknown owner on a non-fabric local egress: keep (#16524 mirror);
  - egress equals the destination's connected interface: keep.

  Otherwise it falls through and retains the stored redirect, as the
  transient-FIB-lag `ForwardCandidate` does. The #18659 gate
  (`missing_neighbor_toward_peer_owner`) became `missing_neighbor_retained`.
  It no longer requires a not-active owner, because the owner-active keep
  cases have already returned. Fabric and zero egress are still verbatim.
- **Cells**:
  - `rehome_or_retain_owner_active_missing_neighbor_18672`. This is seat W's
    #18660 repro: WAN ForwardCandidate and WAN MissingNeighbor, both with
    owner Active(2), now both retain. Its controls cover the
    connected-egress keep, an unknown owner, a fabric egress and a zero
    egress.
  - `rehome_or_retain_missing_neighbor_table_18659` dropped its
    owner-active row, which this cell now owns.
- **Design note**: like the existing `ForwardCandidate` rule, this sends a
  reply whose owner is locally active over the fabric while the FIB lags.
  The trade is deliberate (#15958b): a transient fabric hop rather than
  laundering the reply onto the WAN egress. It ends when the LAN connected
  row is republished and the next FIB bump makes the row stale.
