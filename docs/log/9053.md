# 9053 — eight cost bounds: two doc defects fixed, and the measurement is BLOCKED (not skipped)

## The instruction that shaped this

> Be careful about what "measure" buys here; a benchmark that measures the wrong
> thing is the #4800-class trap. If some of the eight cannot be measured
> cheaply, say which and why rather than measuring the easy ones and reporting
> on all eight.

That turned out to be the whole issue. The measurement is not merely undone —
it is **blocked**, for three specific reasons none of which is the harness's
wiring, and the harness could only ever have spoken to three of the seven sites
anyway.

## Item 2 first: the two doc defects, because they mislead the reader who would do item 1

**Defect A — a comment wrong twice** (`userspace-dp/src/afxdp/README.md`). It
said the owner-RG bucket walk "runs once per authoritative removal (never per
refresh) **on the control thread**" and that the bucket count "is not enforced
today". Both halves verified false at head:

- `remove_shared_session`, the walk's caller, is invoked from
  `session_delta.rs:520` and `:530` — **twice per Close delta, on WORKER
  threads**. A comment asserting a threading property that is false is how the
  next reader concludes a lock is uncontended and stops measuring it.
- **#8486 enforces the bound at the filing** (`owner_rg_filings_declined_total`,
  `owner_rg_bound_8486_tests.rs`).

What survives — once per authoritative removal, never per refresh, allocates
nothing — is kept.

**Defect B — a shipped signal a review called missing.** The proposed
"O(1)-per-worker bulk-invalidation signal" is `SESSION_DELETE_DROP_EPOCH`
(#8586), shipped, and deliberately keyed on refused DELETES rather than queue
depth because depth-keyed pressure "would fire continuously through normal
traffic and reconcile nothing". `replicate_session_delete_repairing`
(#8114/#8576) already runs the refused worker's NAT teardown on its behalf —
0 repaired-drops across 30,786 refusals.

There was no repo text calling it missing, so the defect is DISCOVERABILITY:
the mechanism exists only in source, which is how a reviewer reached the
opposite conclusion. Fixed where that reader actually looks — a named section
in `docs/userspace-newflow-ceiling.md`, the document a cost review reaches
first.

## Item 1: attempted, and blocked — each blocker verified at source

Off-cluster everything passes: analyzer unit tests OK, `newflow-gen` 13/13,
harness `--dry-run` resolves every host, target and analyzer. The blockers are
all in the SHARED cluster's committed state.

1. **The client cannot source from the prefix the pool rule matches.** Committed
   rule `pool-snat` matches `source-address 10.0.61.240/28`; the LAN host is
   `10.0.61.102`, outside it, so its traffic takes the sibling interface-mode
   rule and the pool sees ZERO allocations — the harness's first named refusal.
   `newflow-gen` has no client source-address option: `--bind` (main.rs :79/:341)
   is the SINK's, and the client calls `TcpStream::connect_timeout` (:296) with
   no local bind. **Read at source, not inferred from `--help`** — an absence
   claim from a help text is a claim about the help text.
2. **The pool holds 1000 ports** (`172.16.80.7/32`, `range 30000 to 30999`)
   against a documented 5000–80000 flows/sec sweep — roughly two orders of
   magnitude short. The harness names port exhaustion as a refusal ("a capacity
   ceiling, not a lock ceiling"), so this would refuse cells rather than corrupt
   a number. That is the failure mode to want, and it is why no figure is quoted.
3. **The default WAN target is not an instance on this cluster.**
   `172.16.80.200` answers from the wire (fw0 pings it) but is not an incus
   instance on `loss:`, so the sink cannot be started on it. Surmountable —
   `loss:xpf-mouse-target` holds `172.16.80.201` on the same VLAN-80 subnet and
   `TARGET_IP` is overridable.

Blockers 1 and 2 both need a change to the shared cluster's committed
configuration — a wider pool and a rule matching the generator's source — which
affects every other lane's smokes. **That is a decision for whoever owns the
cluster, not something a measurement run should do to itself.** Reported to
team-lead rather than done unilaterally.

**2026-10-15 update:** the generator limitation in blocker 1 was fixed by
#13727: client mode now supports `--src-bind <IP>`, and the ceiling harness
passes `SRC_BIND=<IP>`. The historical source-code evidence above describes
the implementation at the time of the 2026-09-06 attempt; it is not a current
limitation. This does not resolve the pool-capacity or operator-baseline
blockers, and no measurement was run as part of #13727.

## What the harness could attribute even unblocked — 3 of 7

Recorded because the cohort lists seven sites and a run reported against all
seven would be the #4800-class trap the harness's own header warns about.

**Attributed:** the NAT allocator `live` mutex (the pool path is the driven
path), `replicate_session_upsert`, `publish_shared_session`.

**Not attributed:** `publish_live_session_entry` (no per-syscall counter);
`remove_shared_session` (a CLOSE-path site, and the sweep drives opens);
`snapshot`+`replay` (a reconcile/bring-up path the sweep never enters);
source-NAT `matches` O(R) (one rule-set of 2 rules; R is not varied); bulk HA
import (no peer bulk transfer during the sweep).

So an unblocked run answers *which of three synchronization sites saturates
first* — exactly what #2852 Phase-2 is gated on — and nothing about the other
five.
