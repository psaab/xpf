# #18567 — failover pool probe collides with its own Phase 1b iperf3

- **Timestamp**: 2026-10-30
- **Action**: Diagnosed the `test-failover` cell "a pool-mode TCP flow did not
  complete after the role change", which failed on every loss run (master
  integ8, integ9, integ10 and the #18563 gate) with "iperf3: error - the
  server is busy running a test".
  - Phase 1b (`test-failover.sh:1509`) keeps a pool-mode client on
    `POOL_PORT` (5210) for the whole run, and the post-failback probe
    (`:1819`) reused that port.
  - The busy reply crossed the firewall on the probe's TCP control
    connection, so the cell scored a working data path as the #8341 defect.
  - Control: a plain `iperf3 -c 172.16.80.200 -p 5210 -t 1` from the loss LAN
    host outside the test completed `iperf Done.`.
- **Action**: The fix.
  - The post probe gets `POOL_POST_PORT` (default 5209).
  - `failover_pool_probe_verdict` in `failover-client-lib.sh` scores the
    probe log: `pass`, `busy` (VOID with the collision as its reason), or
    `fail`.
  - Five hermetic cells in `failover-client-selftest.sh`: four verdict
    shapes, plus a static check that the probe port differs from Phase 1b's.
  - Mutants, all killed (26/27):
    - M1: probe back on `POOL_PORT`.
    - M2: busy scored as fail.
    - M3: busy scored as pass.
- **File(s)**: test/incus/test-failover.sh, test/incus/failover-client-lib.sh,
  test/incus/failover-client-selftest.sh, docs/log/18567.md
