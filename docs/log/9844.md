# 9844 — TestIPsecSASyncHotEnableStartsAndStops8967 raced the exiting publisher

- **Timestamp**: 2026-09-12T07:05Z
- **Action**: made the cells read the publisher's cancel handle under `loopMu`.
- **File(s)**: `pkg/daemon/ipsec_sa_hotenable_8967_test.go`, `docs/log/9844.md`.

## The defect

The cells read `d.ipsecSASync.loopCancel` directly, with no lock. Every
production writer takes `loopMu` — `ensureIPsecSASyncLoop`,
`stopIPsecSASyncLoop` and `clearIPsecSALoopIfCurrent` — and the last of those
runs on the PUBLISHER's own goroutine as it exits. So the synchronisation was
correct on the writing side and absent on the reading side, and
`go test -race ./pkg/daemon` went red intermittently in any lane, on a file none
of them had touched.

The handle is only ever compared against nil, so reading it under the lock
changes nothing any cell asserts. It just stops the read racing the write.

## Evidence

A positive control first, because a flake fix with no reproduction cannot be
told from luck:

- unmodified master `9b2133e1e`, 200 runs of the hot-enable cell under `-race`:
  **1 DATA RACE**, write at `daemon_ipsec_sa_sync_loop.go:172`
  (`clearIPsecSALoopIfCurrent`) against the cell's unlocked read — the exact
  signature the issue reports;
- unmodified master again, 1000 runs: **1 DATA RACE**. It reproduced in both
  campaigns, so the control is real rather than a one-off;
- with the fix, the same cell: **0 races in 1000 runs**, and the sibling cell
  **0 in 200**.

Reverting the accessor to a direct field read IS the mutation for this change,
and the control above is that mutant: it races, the fix does not.

## Docs

No module doc changed: this alters no production behaviour and adds no contract.
The reasoning lives beside the accessor, where the next person to read an
unlocked field access will find it.
