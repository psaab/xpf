# #16802 — PBR window-exhaustion accounting over-counts a multi-attached filter

## What was wrong

`accountPBRWindowExhausted` (residual of the #15271 B21-02 fix) identified
the triggering attachment by filter NAME and resumed accounting at the
first attachment of that name. Attachments are sorted (filter, iif), so
when one filter attached on several interfaces exhausted the 500-rule
PBR window at its last attachment, every earlier attachment of that
filter after the first — including attachments whose rules were
installed, and the trigger itself — was counted again as degraded. Only
the operator-visible `xpf_pbr_degraded_terms` count and the degraded
error list were wrong (duplicate, indistinguishable lines); the
installed kernel rule set was always correct.

## Fix

- `pkg/routing/rules.go` `BuildPBRRules`: the build loop now tracks the
  attachment index and passes `atts[attIdx+1:]` — exactly the
  attachments after the triggering (filter, iif) attachment — to
  `accountPBRWindowExhausted`, so accounting resumes strictly at the
  NEXT attachment as its contract states.
- `accountPBRWindowExhausted`: the `skipFilter` name-matching predicate
  is removed; the function accounts every attachment it is given. The
  other-family arm passes its full attachment list unchanged.

Acceptance probe: one filter with a 250-dst term on ge-0/0/0..2 fills
the window with the first two attachments — degraded=1 (only ge-0/0/2
lost its steer), matching the three-distinct-filters twin control
(previously degraded=3 with three identical error lines).

## Regression

`pkg/routing/rules_16802_test.go` (FAIL pre-fix, PASS after):
- `TestBuildPBRRulesWindowExhaustedMultiAttach16802` — the acceptance
  probe above plus its twin control (both degraded=1, 500 rules).
- `TestBuildPBRRulesWindowExhaustedMultiAttachLaterStillCounted16802` —
  four attachments of the same filter: degraded=2 (trigger + genuinely
  lost fourth), pinning resume-after-trigger rather than skip-whole-name
  (pre-fix degraded=4).
