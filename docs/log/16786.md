# Issue #16786: `insert` adjudicates only the moved element, never the reference (R3-A53-03)

## Why

`configMutationPaths` (`pkg/config/authz_config_mutation_9154.go`)
adjudicated an `insert <element> before|after <ref>` line on the moved
element alone and discarded the reference, on the rationale that "the
ref is a SIBLING identifier that is not itself mutated … so a deny
covering the element covers it". That holds only for a deny on the
common parent. Security policies are first-match within a zone pair
(and the compiler preserves AST order), so a restricted class could
move a permitted permit policy ahead of a protected deny policy named
only by the reference — anchored (`^security policies p1$`) or plain
deny alike — while `show` still listed the deny and the commit gate's
additions-only, order-blind set-line comparison saw an unchanged
multiset. The reorder was invisible to every gate.

## What

- `pkg/config/authz_config_mutation_9154.go`: the `insert` arm of
  `configMutationPaths` now also adjudicates the resolved reference
  path, built exactly as the executors build it — `insertRefPath`
  over the edit-path-resolved element (`InsertRefPath` semantics: ref
  tokens replace the element's trailing identifier under the same
  parent) — returning both endpoints like `copy`/`rename`. Because
  `AuthorizeConfigMutation` already refuses on the first denied path
  and prices every returned path through the #16080 credential
  fences, one change prices the on-box CLI, gRPC and REST surfaces,
  which all share that decision. A ref longer than the resolved
  element (refused by every executor) contributes no reference path;
  the element verdict stands. Malformed inserts keep the existing
  whole-remainder fallback.
- `docs/system-login.md`: new "`insert` is adjudicated on both
  endpoints (#16786)" subsection beside the #16598 flat-set note.
- Tests: `pkg/config/authz_config_insert_ref_16786_test.go` — plain
  and anchored deny spellings × before/after × full and short
  (`before p1`) ref spellings, an edit-path-resolved short ref, the
  element-denied cells (unchanged #9938 behaviour), and positive
  controls: both-endpoints-allowed inserts under both deny spellings,
  an allow-list class with both endpoints in scope, an allow-list
  refusal when only the reference is out of scope, and a no-regex
  class unaffected.

## Validation

- GREEN: `go test ./pkg/config/ -run '…16786|9938|14147|9154'`
  passes; the broader authz-pattern run
  (`Authorize|Insert|CopyRename|Expanded|Credential|14981|16080|
  16598|15167|14716|15082|9939|9892`) passes except
  `TestPackedTailCredentialValuePosition16108`, which fails
  identically on pristine `origin/master` (3c1e8e5734) — an OSPF MD5
  key-length compile rejection (#16628) unrelated to this change,
  base-attributed. `go vet ./pkg/config/` clean; `gofmt -l` empty
  on the changed Go files.

## Risk

Deliberate behaviour delta: an insert whose reference is denied (or
outside the class's allow) is now refused even though the reference
statement itself is not edited — its position in a first-match list
is part of its configuration. Both-endpoints-allowed inserts are
unchanged; unrestricted classes are unaffected. Adjacent cohort issue
#16784 (ancestor delete/deactivate/rename descendant pricing and the
expanded-gate removal leg) is untouched and remains open; this fix is
the per-line insert leg only. No commit-gate change was needed: the
refused insert never lands, so the order-blind candidate comparison
never sees it.
