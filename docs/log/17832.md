# Issue #17832: SNMP replies pinned into the xpf-usp0 reinjection TUN by echoed ingress ifindex

- Timestamp: 2026-10-27T00:40:00Z
- Action: fix + fail-on-revert RED regression + focused suite green
- File(s): pkg/snmp/pktinfo_linux.go, pkg/snmp/agent.go, pkg/snmp/pktinfo_other.go, pkg/snmp/README.md, pkg/snmp/agent_usp_tun_17832_linux_test.go (new), pkg/snmp/agent_inband_16781_linux_test.go

## Why

PR #17600 (#16781) made the SNMP agent echo the received `IP_PKTINFO`/
`IPV6_PKTINFO` ifindex into every reply's control message. For a request the
kernel received through the userspace dataplane's write-only reinjection TUN
(AF_XDP slow path LocalDelivery → `xpf-usp0`), that ifindex is the TUN, not
the real return path: pinning reply egress to `xpf-usp0` strands the reply in
a device nothing reads for egress, so the manager never receives an answer
while `SNMP write error` may not even fire (the send can appear successful
into the TUN). This hits the default listener even without a management VRF —
any in-band poll delivered by userspace forwarding to a data-interface
address.

## What

- `pkg/snmp/pktinfo_linux.go`: `pktinfo.oob` now takes `pinEgress`; when
  false the reply cmsg pins only the source (`Spec_dst`/`Addr`), leaving the
  egress ifindex 0 so the kernel routes the reply normally. New
  `isUserspaceReinjectTUN` resolves the request's ingress ifindex to a name
  and reports whether it is `xpf-usp0`/`xpf-usp1`. A vanished device
  reports false, so the reply stays pinned to the stale received ifindex
  (fail-closed toward the #16781 VRF behaviour), not unpinned.
- `pkg/snmp/agent.go`: `serveOne` computes
  `pinEgress := !isUserspaceReinjectTUN(ingress.ifindex)` at the write
  site, only for an admitted request that produced a reply, so shed
  datagrams never pay the link-dump lookup (review fold).
  Design note from the live regression run: simply never pinning egress is
  WRONG — a VRF-domain sendmsg route lookup needs the explicit oif to reach
  the VRF's routing table; without it the #16781 management leg fails
  `sendmsg: network is unreachable` (reproduced both on the vrf-mgmt-bound
  socket and for a VRF-domain datagram served by the main-table listener
  under `udp_l3mdev_accept`, which is why the socket-split variant was
  abandoned in favor of the per-request TUN-name rule). Every non-TUN ingress
  keeps the exact #17600 pinning bytes.
- `pkg/snmp/pktinfo_other.go`: non-Linux stubs updated (`oob(pinEgress)`,
  `isUserspaceReinjectTUN`); the package still does not cross-build on
  non-Linux (`unix.SO_BINDTODEVICE` in `socket_vrf.go`, pre-existing).
- `pkg/snmp/README.md`: `SetVRFDevice` contract wording updated to the
  per-request egress rule.
- Tests: new class-N netns cell
  `TestSNMPUserspaceTUNPollAnswered17832` (`agent_usp_tun_17832_linux_test.go`)
  reproduces the production shape end-to-end — a real TUN created under its
  production name `xpf-usp0`, a crafted SNMP GET injected into it (kernel
  ingress = TUN, dst = 198.51.100.1 on trust0), a manager reachable only via
  trust0; three polls must be answered from 198.51.100.1. It self-re-execs
  like the #16781 cell, asserts netns isolation on the locked fixture thread
  (host-isolation directive 2026-10-26), relaxes rp_filter only inside the
  private netns, and skips honestly without CAP_NET_ADMIN.
  `TestPktinfoParseOOB16781` extended: reply oob for the TUN arm (pinEgress
  false) must carry ifindex 0 + the polled source, and the pinned arm (true)
  must echo ifindex + source for v4 and v6.

## Risk

- Neighbours: #11427 (management reply source/path + trap routing via
  vrf-mgmt) and #16781 (dual listener, in-band + management legs) are green
  in the netns cell; non-TUN ingress produces byte-identical cmsgs to
  merged master, so no behaviour change off the TUN path.
- Per-reply cost: `isUserspaceReinjectTUN` does one netlink `RTM_GETLINK`
  (`net.InterfaceByIndex`) per answered request — bounded by the SNMP serve
  budget (#9917) and dwarfed by the per-PDU `LinkList` the ifTable path
  already does; it is live-resolved (no ifindex cache to go stale across
  userspace-dp restarts).
- If a future dataplane renames or adds reinjection TUNs, the name list in
  `pktinfo_linux.go` must follow; a missed name restores the #17832 strand
  for that device only (fail-open direction: replies still sent, pinned to
  the TUN), never a misrouted reply on a real interface.
- #17800 (IPv6 in-band leg verification and the former ifindex-only oob
  fallback) remains open; this change removes the ifindex-only fallback
  structurally (oob with no captured destination returns nil) but does not
  add the v6 live-wire cell that issue asks for.
