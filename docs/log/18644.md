# #18644 — No generation reservation for config-sync no-op ticks

## Why

The 30-second config-sync reconcile path reserved a wire generation before checking whether the current `(peer connection epoch, config hash)` had already been pushed. Every no-op tick therefore advanced `SessionSync.configGenCounter` past the newest generation actually sent to the peer, undermining the sent-generation threshold added by #18636.

## What

The reconciler now checks and claims the `(epoch, hash)` marker before reserving. Claiming first also makes concurrent reconciles share one reservation. If the active snapshot or peer authorization changes, or the connection/claim is no longer current, the claim is cleared; queue failures and post-queue failures retain their existing retry behavior. A daemon regression cell installs a satisfied marker, drives ten production reconcile ticks through a real `SessionSync`, and asserts the counter is unchanged. The cluster test seam exposes the counter read-only for that assertion. Updated the session-sync architecture and cluster README to describe the corrected reservation ordering.

## Risk

Only a claimed push attempt consumes a generation; an attempted queue that later fails can still consume one, as before. The marker is cleared on the existing failure/revalidation paths so a later reconcile can retry. No wire format or peer protocol behavior changes.
