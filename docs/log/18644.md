# #18644 — No generation reservation for config-sync no-op ticks

## Why

The 30-second config-sync reconcile path reserved a wire generation before checking whether the current `(peer connection epoch, config hash)` had already been pushed. Every no-op tick therefore advanced `SessionSync.configGenCounter` past the newest generation actually sent to the peer, undermining the sent-generation threshold added by #18636.

## What

The reconciler checks and claims the `(epoch, hash)` marker before reserving, so an already-satisfied tick does not consume a wire generation and concurrent reconciles share one reservation. If the active snapshot or peer authorization changes, it clears only its still-owned claim; a superseding push remains intact. The counter regression cell installs a satisfied marker, drives ten production reconcile ticks through a real `SessionSync`, and asserts the counter is unchanged. The cluster test seam exposes the counter read-only for that assertion. Updated the session-sync architecture and cluster README to describe the corrected reservation ordering.

The first fold review found a same-text race: a reconcile could reserve G1, then
a commit could successfully push G2 with the same hash, after which the
reconcile's hash-only check allowed G1 to overwrite G2's pushed marker. The
marker now carries a unique, nonwrapping claim token alongside epoch, hash, and
wire generation. Operator-push publication gets a fresh token too. Reconcile
post-reservation checks and failure clears require the exact token, so equal
pre-reservation tuples cannot alias after a NACK or retry. The claim sequence
is protected by `configSyncMu`; exhaustion fails closed instead of wrapping.

The barrier-controlled regression pauses G1 after reservation, pushes G2
through the production operator path, invokes NACK invalidation, then starts
and pauses G3. Releasing G1 must neither queue G1 nor clear G3's claim; G3 must
then queue and retain the marker, and overdue-ACK recovery must resend the same
text at G3.

## Risk

Only a claimed push attempt consumes a generation; an attempted queue that later fails can still consume one, as before. The marker is cleared on the existing failure/revalidation paths so a later reconcile can retry. No wire format or peer protocol behavior changes. The pre-existing NACK invalidator remains unconditional: a stale NACK may clear a newer marker and cause an extra retry (fail-closed); invalidation clears the active claim token but does not rewind the monotonic sequence, so any replacement claim is distinct.
