# #18644 — No generation reservation for config-sync no-op ticks

## Why

The 30-second config-sync reconcile path reserved a wire generation before checking whether the current `(peer connection epoch, config hash)` had already been pushed. Every no-op tick therefore advanced `SessionSync.configGenCounter` past the newest generation actually sent to the peer, undermining the sent-generation threshold added by #18636.

## What

The reconciler checks and claims the `(epoch, hash)` marker before reserving, so an already-satisfied tick does not consume a wire generation and concurrent reconciles share one reservation. If the active snapshot or peer authorization changes, it clears only its still-owned claim; a superseding push remains intact. The counter regression cell installs a satisfied marker, drives ten production reconcile ticks through a real `SessionSync`, and asserts the counter is unchanged. The cluster test seam exposes the counter read-only for that assertion. Updated the session-sync architecture and cluster README to describe the corrected reservation ordering.

The fold review found a same-text race: a reconcile could reserve G1, then a
commit could successfully push G2 with the same hash, after which the
reconcile's hash-only check still allowed G1 to overwrite the pushed-generation
marker. The marker now carries the claimed wire generation, and config writes
serialize their final generation check, queue, and marker publication. Failed
reconcile attempts clear only the exact `(epoch, hash, wire generation)` claim;
they cannot erase a newer same-text push.

A barrier-controlled regression cell pauses reconciliation after G1 reservation,
completes the production operator-push path for the same text at G2, and then
releases G1. It requires only G2 to be queued and recorded, and verifies overdue
ACK recovery resends the same text at G2.
