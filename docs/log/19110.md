# #19110 — the restart's XDP attach races the kernel's release of the dead process's links

- **Timestamp**: 2026-11-13
  - **Action**: Filed the issue from lane T's #19093 lab on loss. After an
    xpfd SIGKILL, the restarted daemon sometimes fails its dataplane arm
    or arms the mlx5 VFs in generic mode. 9 of 30 SIGKILL restarts were
    affected, on both master and the #19093 build.
  - **File(s)**: none (issue text and journals under
    `/var/worktrees/lane-t-19093-lab/out/`)
- **Timestamp**: 2026-11-14
  - **Action**: Design note posted on the issue, pinned to master
    05b4645749 and to kernel v6.19 source.
    - **Mechanism:** the first apply's pin sweep unlinks the dead
      process's link pins (`shim_pins.go:55-79`). Unlinking only
      `schedule_work`s the release, which takes rtnl. The native attach
      about 1 ms later can overtake it:
      - mlx5 returns EBUSY;
      - the loader reads that as "native unavailable" and falls back to
        generic. Generic then fails with EEXIST (the arm fails) or
        succeeds (the VF ends up in skb mode).
    - **Corroboration:** the first native attach took 584–692 ms in 21
      clean SIGKILL restarts, against 202–232 ms after 3 graceful
      restarts.
    - **Recovery:** the #9811 retry converges with no peer, but the
      #7191 latch never re-arms the node (filed as #19118). With a live
      peer the retry wedges on the policy-authority fence (filed as
      #19111).
    - **Proposed scope:** F1, synchronous `BPF_LINK_DETACH` of stale pins
      in the sweep; F2, an occupied device (EBUSY/EEXIST) is retried
      within a bound and never falls back to generic.

- **Timestamp**: 2026-11-14
  - **Action**: Design v2 posted on the issue
    (issuecomment-6885105013), folding Codex's DESIGN-NEEDS-CHANGES.
    - **Ordering:** each interface is reclaimed immediately before its
      own attach, with a gap budget of 1 s per mlx5 interface.
    - **F1 contract:** reclaim never aborts the apply by itself. Load
      failures are classified by errno (ENOENT; not-a-link; EACCES off
      bpffs; unknown). Close always runs. A nil Detach proves the release
      ran, not that the hardware recovered.
    - **F2:** native is retried within one deadline and every result is
      reclassified. EBUSY/EEXIST mean "refused", not "occupant proven",
      because tcp-data-split, memory providers and upper devices also
      return them. The retry is the probe. Diagnostics run only at
      give-up, on a 250 ms netlink socket, and keep the original errno
      ("occupant unknown" if nothing is found).
    - **Budget:** one 5 s budget shared by the whole attach pass.
    - **Cells:** added C1a–g, C2b, C3b–d and P3.
    - **F4:** transferred to its own issue, with a proposed acceptance
      edit; to be filed on agreement.
  - **Cell edit:** C5 now asserts its attempt sequence (2 native, then
    generic), so master's single native attempt makes it RED.

## Lab pre-registration (written before any lab run)

Recorded 2026-11-15, before the lab slot.
- **Where:** loss, default lock tuple. Each phase runs in its own
  with-cluster cell with a lane-t owner string, and the measured cells
  also take the shared measure lock.
- **Driver:** `/var/worktrees/lane-t-19110-lab`. Its deploy cell is G5's
  frozen deploy cell verbatim, minus the RSS pin (see the lab's
  `FROZEN.txt`).
- **Builds:**
  - head: the fix, built at the SHA that lands after the review folds
    (`build.sh`);
  - master control: 05b4645749, deb 0.0.30507 (`stage.sh`; sha
    `71866f38…`, attested).
- **Order:**
  1. master control: deploy, kill;
  2. head: deploy, f1, kill, lone, o2, smokes;
  3. restore: master 0.0.30507, CoS re-apply gated on its success line,
     and post-CoS F1, all in the same lock cell.

**Kill loop.**
- **Shape:** SIGKILL the SECONDARY's xpfd while the peer owns RG0-2:
  12 runs with node1 as the victim, then RG0-2 move to node1, then 12
  runs with node0 as the victim. That is 24 runs per arm, 48 in all.
- **Per run:**
  - the victim's takeover-ready time;
  - the kernel-truth XDP mode of its data VFs;
  - from its journal: arm failure, native-unavailable lines, reclaim
    outcomes and `detach_ms`, refusal retries, `ErrXDPOccupied`, and
    daemon start → compiled → attach-pass end → XSK liveness.
- **Pass criterion (head):** **0 of 24** runs with an arm failure, a
  data VF in generic in the kernel, or `ErrXDPOccupied`. Master
  measured 9 of 30 on 2026-11-13 (p≈0.3). If the fix did nothing, a
  0/24 head would have probability 0.7^24 ≈ 2·10⁻⁴.
- **Master control prediction:** some runs affected. At p≈0.3 the
  expectation is about 7 of 24. 0 of 24 on master would void the
  comparison: the race would not have been exercised in this session.
- **Gap bound:** reclaim plus attach ≤ **1 s** per mlx5 data VF, on
  every head run with a stale pin. Measured from the detach start
  (reclaim line time minus `detach_ms`) to that VF's "attached XDP
  program" line.
- **Reclaim outcomes (head):** all `detached`. Any fallback outcome is
  reported by name.
- **Startup timeline:**
  - daemon start → attach-pass end, compared head vs master;
  - prediction: head is no slower by more than ~0.5 s, since a
    synchronous detach replaces master's wait behind the deferred
    release;
  - takeover-ready is reported per run, but it includes the cold-boot
    gates, so it is not the attach comparison.

**Lone owner (head, 4 runs under traffic).**
- **Prediction:** ping forwarding resumes at about 34–35 s, matching
  the #19093 lab's cold-boot promotion, with 0 arm failures and 0 VF
  generic.
- **TCP flows:** existing iperf3 flows may not resume on either build,
  so they are not judged.

**O2 (head): a deliberate native refusal.**
- **Trigger:** on node1's WAN data VF, enable `large-receive-offload`
  or `rx-gro-hw`, whichever ethtool reports changeable; VOID if
  neither. Then gracefully restart node1's xpfd.
- **Predictions:**
  - native refused with EINVAL (`mlx5e_xdp_allowed`), and the VF ends
    GENERIC in the kernel;
  - with the peer alive, the F4 guard holds node1 not takeover-ready
    with the "attached in generic XDP mode" reason, logs one ERROR,
    and sets the metric `xdp_generic_data_member` = 1;
  - after node0's xpfd is stopped, the lone node1 promotes with no F4
    block, and the metric is still 1.
- **Measured, with NO prediction:** does generic plus copy-mode AF_XDP
  forward through a native-capable mlx5 VF, and at what rate? Either
  answer is a finding. "Forwards nothing" would argue that F4's
  lone-owner branch should do more than log.
- **Restore:** feature off, graceful restart, kernel shows native,
  metric 0.

**Smokes (head):** `test-failover`, `test-ha-crash` and
`test-restart-connectivity` all pass.

**O1:** whenever a run shows an attach error, the cell captures
