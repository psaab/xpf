# #9852: close bridged transit before networkd

- **Timestamp**: 2026-09-17 UTC
- **Action**: Proved the networkd-to-xpfd bridge window on the starting master, added an early fail-closed transit-barrier command and unit, staged it in baked images, Debian installs, and both Incus harnesses, and added fail-on-revert plus netlink-parity coverage.
- **Base**: The initial STEP-0 probe ran on `origin/master` at `1c9b202fbcfe7dd5c607729bc4127db8d03360ed`. The branch was rebased after master advanced, before publication.

## STEP-0: unbarriered window on master

The existing bridge lifecycle and daemon ordering prove the vulnerable interval:

1. `pkg/networkd/networkd.go:412-420` recognizes bridge `.netdev` definitions, `:496-499` writes them, and `:852-857` emits `Kind=bridge`.
2. `pkg/daemon/daemon_apply_dataplane.go:290-317` applies those networkd definitions. On boot, this is performed by networkd before the daemon's bring-up.
3. `test/incus/xpfd.service:3-9` has `After=network-online.target frr.service`; therefore xpfd starts after networkd has reached the network-online milestone.
4. `pkg/daemon/daemon_run_bringup.go:586-595` only closes transit from xpfd bring-up (`closeTransitUntilAttached`). There was no early unit and no `xpf-transit-closed.service` on the starting master.
5. `pkg/nftables/transit_barrier.go:61-75` on the historical starting-master ref (base `1c9b202fbcfe7dd5c607729bc4127db8d03360ed`) installs the nftables barrier only when that daemon path runs. `scripts/image/bake.py:98-104` sets forwarding sysctls, but `ip_forward` does not govern bridge frames, so those sysctls cannot cover this interval.

Thus a recreated bridge could forward between its ports after networkd and before xpfd's first barrier install. The proof is static because starting a real networkd boot transaction would alter the host; the referenced ordering and absence of an early unit are direct source evidence.

## Fix

The existing `pkg/nftables.NewNetlinkInstaller().InstallTransitBarrier()` is reused without a second nftables implementation:

- `cmd/xpfd/main.go:44-48,102-120,184-189` recognizes and dispatches `xpfd transit-barrier close` before daemon/config/lock paths.
- `cmd/xpfd/transit_barrier_9852.go:1-94` accepts exactly `close`, installs the inet and bridge forward-hook DROP, and returns exit status 1 with the kernel error for usage, inet, or real bridge failures. If the inet leg succeeds but the kernel reports the bridge family as unsupported (`ENOENT`, `EOPNOTSUPP`, or `EAFNOSUPPORT`), it returns success with an explicit degraded-coverage warning. It reads no config, takes no lock, writes no sysctl, and touches no filesystem path.
- `scripts/image/xpf-transit-closed.service:19-40` runs the command after `nftables.service`, before `network-pre.target`, `systemd-networkd.service`, `frr.service`, and `xpfd.service`. `RequiredBy=systemd-networkd.service` makes the dependency fail closed; the unprefixed `ExecStart` does not swallow an install error. The barrier remains forward-only, leaving INPUT/OUTPUT management and loopback traffic unaffected on the normal success path. The unit deliberately does not own the #9725 forwarding sysctls.
- `scripts/image/bake.py:581-590` copies and enables the unit in baked images after apt installs the package. `debian/rules:67-71,157-161,174-178` stages the unit in the package and invokes `dh_installsystemd --no-start --no-stop-on-upgrade`, so a package upgrade does not start/drop the barrier on an already armed live daemon; the next boot enables it. `debian/.gitignore:12` ignores the generated staging copy.
- `test/incus/setup.sh:665-676` and `test/incus/cluster-setup.sh:912-923` stage, reload, enable, and start the unit before raw `xpfd` in standalone and cluster VMs.
- `cmd/xpfd/README.md:45-63` documents the recognized subcommands and the new early-boot command.

The daemon's existing bring-up re-install remains the same shared installer and is idempotent; the existing #9725 gate removes both families only after its live-XDP readiness condition opens.

`pkg/nftables/transit_barrier.go:15-74,122-141` tags only the bridge-family
unsupported error classes already treated as an absent family by
`tableExistsInFamily` (`ENOENT`, `EOPNOTSUPP`, `EAFNOSUPPORT`). The command
accepts that sentinel only when it is the sole joined error, preserving fatal
status for inet failures, real bridge failures, and mixed failures.

## Remaining lab boundary and recovery

A real reboot/networkd sequencing run was not completed in this checkout. I
launched the disposable `xpf-9852-recovery` VM from the cached
`xpf-appliance-1921` image, but the image booted without an Incus VM agent and
without a network device (the console reached the kernel, `incus exec` returned
`VM agent isn't currently running`, and `incus info` showed only loopback).
The disposable VM was deleted afterward. Consequently there is no real
forced-failure reboot or management-reachability observation to claim.

The recovery procedure for a real disposable VM is an **emergency bypass**;
it intentionally removes the dependency that prevents networkd from starting.
Keep the serial console available throughout and isolate every transit/data
NIC before allowing networkd to configure anything:

1. Use the serial console (not in-band SSH) after the required barrier fails.
2. Run `systemctl disable xpf-transit-closed.service`. This removes both its
   `sysinit.target.wants` enablement and the
   `systemd-networkd.service.requires` link created by `RequiredBy=`.
3. Run `systemctl mask xpf-transit-closed.service`, then
   `systemctl daemon-reload` and `systemctl reset-failed
   xpf-transit-closed.service`.
4. Before starting networkd, physically disconnect every transit/data NIC. If
   physical disconnection is unavailable, move or mask each matching persisted
   transit `.network`/`.netdev` definition out of `/etc/systemd/network` into
   a root-only recovery directory, run `systemctl daemon-reload`, and verify
   the data definitions are absent. Do **not** rely on `ip link set ... down`:
   networkd can re-enable those persisted links. Only the management path may
   be restored. Starting networkd with a transit NIC or bridge definition
   active is an intentional policy-free bridge forwarding bypass, not a
   no-brick result. Start `systemd-networkd.service` from the console and
   observe `systemctl is-active systemd-networkd.service`, `networkctl list`,
   and the management address/ping.
5. After fixing the underlying nftables/xpfd problem, run
   `systemctl unmask xpf-transit-closed.service`,
   `systemctl enable xpf-transit-closed.service`, and start it. Do not treat
   exit status 0 alone as safe: bridge-unsupported is a deliberate degraded
   success. Before restoring definitions or reconnecting data NICs, require
   the journal to contain `transit barrier installed (inet + bridge forward
   DROP)` and require `nft list table bridge xpf_transit_barrier` (and the
   inet equivalent) to succeed. A degraded warning or failed bridge listing
   means data stays isolated and the emergency bypass is not complete.
   If definitions were moved, restore every `.network`/`.netdev` file from the
   root-only recovery directory to `/etc/systemd/network`, run
   `systemctl daemon-reload` and `networkctl reload`, then reconnect the data
   NICs. Verify the restored links/configuration and management reachability.
   Confirm the next reboot runs the barrier before networkd and that the #9725
   gate later removes both tables.

The disable/mask mechanics were dry-run against a temporary systemd root. The
run created the `systemd-networkd.service.requires/xpf-transit-closed.service`
symlink, `systemctl --root=<root> disable` removed it, and
`systemctl --root=<root> mask` created the `/etc/systemd/system` symlink to
`/dev/null` (all commands exited 0). The Incus/HA lab must still verify the
boot transition with the built package or raw binary: inspect
`journalctl -b -u xpf-transit-closed.service`, confirm
`systemctl show xpf-transit-closed.service` is active before
`systemd-networkd.service`, and run `nft list table inet xpf_transit_barrier`
plus `nft list table bridge xpf_transit_barrier` before xpfd starts. With the
barrier active, bridge-port transit must be blocked while management and
loopback pings continue; after xpfd attaches XDP and opens the #9725 gate,
confirm both barrier tables are removed and permitted transit resumes. Also
exercise a forced `xpfd transit-barrier close` failure in a disposable VM:
networkd must remain stopped, then the console recovery above must restore the
management address and reachability after the dependency is disabled.
