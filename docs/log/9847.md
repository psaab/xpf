# 9847 — every compile removes the XDP link pins; restart detaches the shim

## The defect

`CompileUserspaceShim` called `removeUserspaceShimXDPLinkPins()` on every
compile, before the attach (`pkg/dataplane/loader.go`). That deleted every
`xdp_*` link pin so the attach would be fresh rather than pinned-link reuse.

`AttachXDP` then returned "XDP already attached" for any ifindex already in
`m.xdpLinks`, and both attach loops (`attachUserspaceShimXDP`, legacy
`Compile`) swallow that error. A link attached by an earlier compile was
therefore never pinned again.

`Manager.Close` closes every XDP link handle, and its comment says hitless
restart keeps the pinned state. But a bpf_link survives only while a handle
or a pin holds it (cilium `link.Link.Close`: "The link will be broken unless
it has been successfully pinned"). Once a second compile had removed the
pins, closing the last handle detached XDP from every interface.

Consequence: on a stop or restart after at least two compiles — including a
hitless restart — the shim leaves every interface when the process exits,
and kernel transit forwards with no program until the next attach. The same
held when the initial `Pin` failed after a successful attach (WARN-only).

Correction to `docs/log/7079.md`: it claimed the pin removal "is
self-healing" because "the next SUCCESSFUL apply re-pins". That holds only
for the fresh-attach path. For a registered link the attach short-circuits
before `Pin`, so nothing re-pinned — this issue. The fix below makes the
7079 claim true again.

## The fix (shape)

Three links, each pinned by its own cells in `xdp_link_pin_9847_test.go`:

1. **Scoped sweep.** `removeUserspaceShimXDPLinkPins` is now a method that
   snapshots the registry and removes only pins for ifindexes with NO live
   link (`removeUserspaceShimXDPLinkPinsExcept`). A registered link never
   takes the pinned-reuse path the sweep exists to prevent (it returns
   before `LoadPinnedLink`), so keeping its pin changes nothing about the
   mlx5 fresh-attach rationale.
2. **Re-pin on "already attached".** `AttachXDP`'s short-circuit now calls
   `ensureXDPLinkPinned`: stat the pin, `Pin` only if missing. Heals the
   initial-Pin-failure case on the next compile. Same error string either
   way; callers are untouched. The helper is library-aware: cilium caches
   the pin path on the handle (`RawLink.pinnedPath`), so a `Pin` to the same
   path is a nil no-op — it `Unpin`s first to forget the cached path, then
   `Pin`s, then stats the file as the verdict (a nil `Pin` with no file is
   returned as an error, not logged as success).
3. **Repair before release, then degraded report.** `Close` re-pins missing
   pins BEFORE closing the handles (after the last handle closes there is
   nothing left to pin), closes every handle either way, then returns an
   error naming the registered ifindexes still without pins
   (`unpinnedXDPLinks`). The hitless-shutdown path claims preservation only
   on success and logs the degraded close otherwise. The naming is
   deliberately "degraded report", not "fail closed": nothing here can keep
   an unpinned link attached past process exit — the enforcement is the
   best-effort repair plus a loud residual, not a barrier.

## Considered and rejected

- **Memory-tracked pin flags** (`xdpPinned[ifindex]`): loses to a pin file
  deleted out from under the process, and adds flag-sync points in
  Attach/Detach/Teardown. Filesystem existence is ground truth in every
  realistic flow.
- **Failing the compile when Pin fails**: the issue asks for a loud residual
  on shutdown, not aborted commits over a hitless-ness precondition. A pin
  failure still attaches (forwarding works) and now heals on the next
  compile.
- **TC symmetry**: none. The per-compile TC sweep only ever sees
  legacy-daemon leftovers — the shim path attaches XDP-only
  (`attachUserspaceShimXDP`), and the legacy path never sweeps. Verified,
  not assumed: the TC/XDP attach loops live in legacy `(m *Manager) Compile`
  (`compiler.go`), not in shared `CompileConfig`.

## Deferred: shutdown-path transit barrier

The review asked whether a degraded shutdown should also close kernel transit
(sysctls) so the expose window does not forward. Explicitly DEFERRED as its
own issue, not this fix: the scoped sweep makes an in-process unpinned link
nearly unreachable (pins of live links are never removed; a missing one is
repaired at every compile AND at close), so the residual this barrier would
cover is a double-failure (repair fails at shutdown after never succeeding
in-process). A transit barrier is shutdown-path dataplane surgery with its
own blast radius and cells; folding it here would hold the restart-detach
fix hostage to a second design.
