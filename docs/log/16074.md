# #16074 — api-auth shadowed-class neutralisation misses api-auth users/keys (#15987 R1)

Split from #15987 (claim R1). Evidence at `c1b86e871b`:
`pkg/config/compiler_system_login_gates.go:673-704`.

## Mechanism

The #14387 shadowed login-class neutralisation
(`neutraliseShadowedLoginAssignments14387`, tolerant load / peer-sync
only) rewrote compiled `system login user` assignments naming a built-in
shadowed by a custom class definition to `unauthorized`. It did not
cover `system services web-management api-auth`:

- `APIAuthUser.Class` / `APIAuthKey.Class` are stamped at compile time
  from the per-credential `class` leaf or the inherited
  `APIAuthConfig.DefaultClass` (`compiler_system.go` api-auth reader).
- The daemon (`daemon_run_servers.go`) wires those classes (falling back
  to `DefaultClass`) into the REST auth middleware, which resolves them
  through the same built-in-first `ResolveClassPermissions` table.
- Legacy `api-key` tokens carry no class and inherit `DefaultClass` at
  wiring time.

So under `class super-user { permissions view; }`, an api-auth user/key
on `super-user` (explicitly or via `api-auth class super-user`) kept the
built-in PermAll on tolerant load while the authored narrowing never
applied — the exact #14387 defect, one consumer over. Strict commit is
unaffected: the shadowing definition is rejected there.

## Fix

Extend `neutraliseShadowedLoginAssignments14387` (same tolerant-only
call site, gated on `lenientLoginClassShadowsBuiltin`):

- `APIAuthConfig.DefaultClass` naming a shadowed built-in is rewritten
  to `unauthorized` (this is what neutralises legacy `api-key` tokens).
- Every `APIAuthUser` / `APIAuthKey` whose effective class (explicit, or
  the authored default when empty) names a shadowed built-in is
  rewritten to `unauthorized`. The authored default is captured before
  rewriting so an already-rewritten default cannot mask an explicit
  shadowed assignment, and no credential is double-warned.
- One warning per neutralised site, tagged #16074, in the #14387 wording
  shape. Unshadowed classes, the shadowing definition itself, and
  built-in-first precedence are unchanged.
