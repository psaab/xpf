# #9495: an IPsec VPN name breaks out of its swanctl section header

- **Timestamp**: 2026-09-11T04:05Z-04:30Z
- **Action**: measurement against the pinned strongSwan on loss:xpf-userspace-fw0, under the
  cluster lock.
  - Harness:
    - Each candidate is rendered by master's own `ipsec.Manager.Apply`, via a throwaway
      generator in a detached master worktree.
    - It is pushed ALONE into fw0's `/etc/swanctl/conf.d`, which was empty at start; the cell
      refuses otherwise.
    - It is loaded with `swanctl --load-all --noprompt` and read back with
      `swanctl --list-conns --raw`. Nothing is initiated.
    - conf.d was restored clean after every round.
    - swanctl 6.0.5; `swanctl --stats` lists the `updown` plugin as loaded.
  - Negative control: a truncated file returns exit 0 with "syntax error ... invalid config
    file". So `swanctl --load-all`'s exit status is NOT a load verdict. The cells score the
    parser's message and what list-conns reports.
  - Round 1 is VOID: it measured 1 of 32 candidates. `incus exec` in the manifest loop
    swallowed the manifest on stdin (the #9683 class). Later rounds read it on fd 3.
  - Round 2, 32 single-VPN candidates:
    - Whole file unparsable (parser error, nothing loads): `evil } # {`, `x # y`, `a=b`,
      `a,b`, `a b`, `a"b`, `a.b`.
    - Refused without a parser message: `a%b` (exit 255); `vpn` + U+00E9 and
      `vpn` + U+202E + `x` (exit 22).
    - Loaded under a DIFFERENT name: `a:b` loads as connection `a`, because `:` is section
      inheritance. The name swanctl reports is then not the configured name.
    - Structure injected: `x { children { p { updown = /bin/true } } } y` loads TWO
      connections, `x` and `y`. The same holds with the value quoted.
    - Loaded verbatim: `plain`, and `a'b a/b a@b a+b a~b a!b a$b a&b a*b a(b) a[b] a;b a<b>
      a?b a^b a|b`, a backslash and a backtick.
  - Round 3, 12 candidates. Some render TWO VPNs into one file.
    - **Whole file versus one tunnel.**
      - `plain` beside `evil } # {`, beside `a.b` or beside `a%b` loads NOTHING, so `plain`
        is lost too. One hostile name takes down every tunnel in the file.
      - Beside `vpn` + U+00E9, `plain` still loads (exit 22); only that tunnel is lost.
      - Beside `a:b`, both load, as `a` and `plain`.
    - **A key written inside a VPN name reaches charon.**
      - `x { children { p { mode = transport } } } y` lists child `p` with mode=TRANSPORT.
      - The control, `mode = tunnel`, lists TUNNEL.
      - A hand-written positive control with `mode = transport` lists TRANSPORT, so the
        detector is sound.
    - **`updown`.**
      - Neither `--list-conns --raw` nor `--load-conns --raw` shows an updown key, even for
        the hand-written positive control. Both detectors are blind to it.
      - That an injected `updown` is applied is INFERRED from the `mode` differential (same
        child section, same parser path, plugin loaded), not observed. Observing it needs a
        CHILD_SA to come up.
    - **Dotted traffic-selector name.**
      - VPN `sel` with selector `t.s` renders child `sel-t.s`. That is a parse error, and
        nothing loads, including beside `plain`.
      - The control, selector `ts`, loads child `sel-ts`.
      - `ipsecname.ChildBase` keeps `.`, so a dotted selector name is a whole-file outage.
        Whether commit admits one is checked in the implementation.
- **Action**: conclusions for the naming contract.
  - Not availability-only. A VPN name can inject swanctl structure and settings that charon
    applies, including (inferred above) an `updown` script the loaded plugin runs as root on
    CHILD_SA events. That turns `security ipsec` configuration rights into root command
    execution.
  - Availability: one name can take down every tunnel in the file, not only its own.
  - `.` is unsafe in every section name, connection or child. `:` silently renames.
    Non-ASCII fails to load.
