# #14342 — Container-Form security policies from-zone Silently Drops Additional Bracketed from-zone and to-zone Names

## Defect
- `compilePolicies` (`pkg/config/compiler_security_policy.go`) container branch built zone pairs from single scalars — `fzSub.Name()`, `tzNode.Keys[1]`, `tzSub.Name()` — without checking extra keys. `malformedZonePairShape9246` guarded only the inline `len(child.Keys) >= 4` branch.
- Container-form bracketed lists therefore compiled strict-clean with only the first pair and no `MalformedZonePairs` record: `from-zone { [ trust dmz ] { to-zone untrust { … deny … } } }` kept only `trust->untrust`; `from-zone { trust { to-zone [ untrust dmz ] { … } } }` and `from-zone { trust { to-zone { [ untrust dmz ] { … } } } }` kept only `trust->untrust`. The dropped pairs fell through to broader/global/default policy; neither the strict uniform gate (`compiler_uniformgates_policy.go`) nor the tolerant poison saw them.

## Fix
- `pkg/config/compiler_security_policy.go`: new `containerBracketedZoneList14342(fzSub, tzNode)` checked for every container pair before construction. It records a diagnostic in `sec.MalformedZonePairs` (and skips the pair) when `len(fzSub.Keys) > 1`, `len(tzNode.Keys) > 2`, a child of a keyless `to-zone` has `len(tzSub.Keys) > 1`, or a keyed `to-zone` on a keyed from-zone context carries folded extra destinations (`to-zone <zone>` children / policy-bearing grandchildren from key peeling). Diagnostics name the bracketed list (`[ trust dmz ]` / `[ untrust dmz ]`), matching the #9246 remediation wording. Existing uniform gate then rejects strict and poisons tolerant (synthetic global carrier). Single-member brackets and plain/keyed container spellings remain valid. NOT changed: inline-form handling (already covered by `malformedZonePairShape9246`), list expansion (Junos has no bracketed zone-list semantics; reject/poison is the doctrine).
