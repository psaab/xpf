# Issue #15155 — Userspace snapshot sorts unit addresses lexicographically and carries no primary flag (B15-02)

## Why

The Go snapshot builder sorts a unit's addresses by family, then by the
address **string** (`buildConfiguredAddressSnapshots`,
`mergeInterfaceAddressSnapshots`, `buildInterfaceAddressSnapshots` in
`pkg/dataplane/userspace/interfaces.go`), and
`InterfaceAddressSnapshot` carried family/address/scope only. Nothing
read the configured `PrimaryAddress` into the userspace snapshot.
Rust `pick_interface_v4/v6` (`forwarding_build/interfaces.rs`) and Go
`pickInterfaceSnapshotV4/V6` (`maps_sync.go`) both return the first
non-link-local entry in that order, so on any multi-address egress unit,
`primary_v4/v6` — and therefore every `source-nat interface` flow, the
Go local-address tables, and the Rust RST candidates — used whichever
address sorted first lexicographically (e.g. `10.0.0.10/24` over the
designated `10.0.0.9/24`), not the address the operator marked
`primary`. When that address is a transfer net or an RFC1918 secondary,
every interface-SNAT flow leaves with a source the operator did not
choose.

## What

- `pkg/dataplane/userspace/protocol.go`: `InterfaceAddressSnapshot`
  gains `Primary bool` (`json:"primary,omitempty"`). `ProtocolVersion`
  53 -> 54.
- `pkg/dataplane/userspace/interfaces.go`:
  `buildConfiguredAddressSnapshots(addrs, primaryCIDR)` marks the one
  row whose canonical CIDR matches the unit's `PrimaryAddress` (a
  primary naming no configured row marks nothing — the #13549
  stale-metadata shape must not manufacture one), and
  `mergeInterfaceAddressSnapshots` overlays the marker onto the live
  row the kernel also reports, next to the existing scope overlay.
  The caller passes `unit.PrimaryAddress`.
- `pkg/dataplane/userspace/maps_sync.go` and
  `userspace-dp/src/afxdp/forwarding_build/interfaces.rs`: both pick
  pairs scan the full family — a marked primary wins wherever it
  appears in the order; otherwise the first non-link-local address,
  otherwise the first address of the family (the pre-existing
  order-based rule, bit-for-bit for an unmarked snapshot).
- `userspace-dp/src/protocol/snapshot.rs` + `control.rs`: `primary`
  field (`serde(default)`, no `skip_serializing_if` so the false
  default pins the key in `protocol_wire_v1.json`, mirroring `scope`)
  and `CONFIG_SNAPSHOT_PROTOCOL_VERSION` 53 -> 54. Exhaustive
  `InterfaceAddressSnapshot` literals in test files gained
  `..Default::default()`.
- `pkg/dataplane/userspace/snapshot_shape_version_8892_test.go`:
  shape pin 52 -> 54 (v53's mirror fields and v54's `primary` both
  move the digest; see the file's own ledger).
- `docs/feature-gaps.md`: the two Primary/Preferred rows now record
  that userspace `primary_v4/v6` (interface SNAT and every other
  consumer) honours the designation, and that no-designation keeps the
  previous first-non-link-local order (Junos would use the numerically
  lowest address; xpf has never promised that order — see Residual).

NOT changed: the sort itself (compile determinism, #1434), the
`preferred` flag (Junos source selection for device-originated traffic
prefers `preferred`; no cited consumer reads it and the issue scopes
the primary leg only), and the config model — `PrimaryAddress` is a
single slot the compiler fills from inet first (#15078), so a unit can
designate one address across both families, exactly as syslog source
already resolves it.

## Risk

Mixed-version pairing is fenced by the exact-equality protocol gate
(v54): a v53 helper refuses the snapshot rather than silently SNATing
from the lexicographic address. Units with no `primary` designation
behave byte-identically to before. Residual: with no designation Junos
prefers the numerically lowest address per family while xpf keeps
first-non-link-local in builder order (lexicographic-configured,
kernel order live) — pre-existing, out of the cited mechanism, and
noted in `docs/feature-gaps.md`; operators who care can designate
`primary` explicitly.
