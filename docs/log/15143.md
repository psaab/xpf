# Pre-#1896 v1 journal lines kept cleartext api-auth credentials after #10826 (#15143)

## Why

Pre-#1896 v1 audit-journal lines embedded the FULL compiled
`*config.Config` per commit in `before`/`after`
(`pkg/configstore/journal/journal.go` History note; deleted v1 writer
at `pkg/configstore/journal.go:21-27` pre-#1896). The compiled config
carries `System.Services.WebManagement.APIAuth` — the REST api-auth
user password and API keys — which before #10826 were plain strings
(`pkg/config/types_system.go` `APIAuthUser`/`APIKeys`, no json tags).
#1896 made v2 entries compact metadata-only and #5188 tightened the
file to 0600, but both deliberately kept legacy segments intact
("rotates to .1 intact … no migration pass"), and the #10826
salted-hash migration rewrote active/rollback/rescue/archive copies
with no journal arm. So an upgraded box still carried
superuser-equivalent cleartext in `.config.journal[.N]` (root-owned
0600, retained up to `DefaultMaxSegmentBytes=1MiB` ×
`DefaultMaxSegments=2` plus the current segment) until rotation aged
it out — exposure via root, a disk image, a backup, or a support copy.

## What

- `pkg/configstore/journal/journal.go`: one-time legacy-payload scrub
  on first use, alongside the #5188 permission repair
  (`migrateLegacyLocked`, called from `migratePermsLocked` on first
  `Log`/`Tail`, with its own `j.scrubbed` guard so it retries even
  after the perms pass has completed). Every owned segment
  (current + `.1`..`.N`) that textually carries a top-level
  `"before":`/`"after":` key is rebuilt from its parseable entries —
  re-marshaling drops `before`/`after` and any other unknown field —
  and installed atomically at 0600 via
  `fsatomic.WriteFileDurable` (temp+rename + dir fsync), preserving
  timestamp/action/detail/config_hash/principal so
  `show system commit` still renders. A segment that cannot be read
  or rewritten safely is removed rather than left secret-bearing
  (oversized-with-payload past the 16 MiB scrub cap, or
  payload-bearing with no parseable entries); an oversized segment
  WITHOUT a payload marker (head probe) is left untouched so the
  #9898 `Tail(0)` full-scan refusal still fires loudly. Clean v2
  segments are never rewritten (no mtime/content change). Symlinked
  or non-regular segments are skipped (the read/append paths refuse
  them loudly). Failures latch `LegacyScrubDegraded` and retry on
  next use, mirroring #9898 F-113; appends/reads continue.
  Freshly-scrubbed entries keep `Schema=0` in the triggering `Tail`
  view (`scrubNormalized`/`renormScrubbedSchema`: legacy lines never
  carry `config_hash`, native v2 lines rewritten alongside keep
  theirs and stay distinguishable).
- `pkg/configstore/journal.ScrubLegacyPayloads()` (exported,
  mutex-guarded) + `Store.Load` calls it at all three #10826 arms
  (absent-active-with-history, fresh, and main after
  `purgeAPIAuthArchives`) in `store_persist.go`, so the journal arm
  lands with the same Load migration that hash-rewrites the other
  copies — the issue's "during the #10826 Load migration" direction.
  `Store.JournalLegacyScrubDegraded()` polls the state like
  `JournalPermsDegraded`.
- Updated the now-false contract statements: package header,
  `TestLegacyFatFileRotatesOnFirstAppend` (was "rotated intact"),
  and the README audit-journal section. NOT changed: rotation,
  retention sizes, tail-scan bounds (#9898), permission repair
  (#5188), principal handling (#10301), rollback files (canonical
  full-config history), or any config/compiler behaviour. Boot still
  never reads journal history; Load only invokes the scrub.

## Risk

Scrubbed legacy entries lose only their `before`/`after` payloads
(read by nobody; rollback slots remain canonical). A payload-bearing
segment with no parseable entries, or oversized-with-payload, is
deleted — its commit metadata is lost loudly (warn + degraded flag)
instead of its credentials staying on disk; that is the fail-closed
choice the issue prescribes ("purge segments that contain v1
payloads" as the alternative arm). A payload buried past the 64 KiB
head probe in an oversized segment is the documented residual:
rotation ages it out and the #9898 full-scan cap refuses it loudly
meanwhile. Operators must still rotate credentials that may have
been copied off-box before the upgrade (backups/support bundles are
out of reach of any on-box scrub).
