# #9908 — bound valid-MAC2 WireGuard handshake admissions

## Scope and verified mechanism

Issue #9908 concerns the userspace WireGuard responder's valid-MAC2 path. At
`43e7038a1` (the origin/master revision used for the RED run),
`userspace-dp/src/afxdp/wg/engine.rs:673-677` returned `Process` for every
under-load initiation whose MAC1 and MAC2 verified. The control dispatcher
calls the responder inline at
`userspace-dp/src/afxdp/coordinator/wg_control/dispatch.rs:81-115`.
`userspace-dp/src/afxdp/wg/handshake_session.rs:584-595` performs the Noise
responder read (including DH) and only then
`:611-626` applies the per-peer TAI64N high-water/replay check. The existing
#4332 per-source bucket at `wg/cookie.rs:436-479` gates cookie replies only;
it does not gate valid-MAC2 admissions.

The expensive path is therefore reachable by a non-spoofed source that has
legitimately obtained a cookie and replays the same valid-MAC2 initiation.
The source is keyed by IP for the new admission bucket, matching the existing
#4332 source scope. UDP-port changes cannot evade the per-source bound.

## STEP-0: RED measurement on origin/master

The new real-key responder harness replays one valid-MAC2 initiation from one
source at a frozen control-thread clock. It dispatches every `Process` arm
through `consume_initiation_create_response`, so `dh_paid` is the number of
responder Noise reads/DH operations reached. The pre-fix run was:

```text
9908 flood: N=100 admitted=100 dh_paid=100 dropped=0 responses=1 replayed=99 mac2_ok=100 elapsed_ms=228
```

This is the RED result: all 100 replays reached Noise and paid the responder
DH before 99 TAI64N replay drops. The same run completed 31 other engine tests;
the new flood assertion failed (`31 passed, 1 failed`).

## Fix and decision

A pre-Noise replay cache was not selected because it would only suppress exact
byte replays; a source can rotate MAC1/ephemeral/timestamp while retaining a
valid cookie. The implementation instead adds a control-thread per-source
handshake-admission token bucket in `CookieChecker`, independent from the
#4332 cookie-reply bucket:

- 20 valid-MAC2 handshake admissions per second, with a 5-admission burst;
- frozen/backwards monotonic-clock behavior follows the existing bucket
  discipline (`saturating_sub`, high-water `last_ns`);
- the handshake source table is GC-reclaimed with the existing source table
  and hard-capped at 2048 entries; an over-cap new source fails closed;
- exhaustion returns `InitiationAction::Drop` before the responder Noise read
  and increments `hs_rx_under_load_admission_drops`;
- MAC1/MAC2 verification, cookie construction/verification, and TAI64N replay
  semantics are otherwise unchanged;
- the counter is carried through the Rust status wire, Go status mirror, and
  the existing Prometheus handshake-drop family as
  `reason=under_load_admission`.

The rate/burst intentionally match the existing 20/s, burst-5 source reply
bucket. A legitimate source therefore has room for a fresh handshake and
quick retransmit while the source flood has a small, deterministic expensive
prefix.

## GREEN and fail-on-revert cells

The three engine cells in
`userspace-dp/src/afxdp/wg/engine_tests.rs` use real Snow keypairs and pin:

1. a one-source valid-MAC2 replay flood is bounded and counted;
2. a fresh initiation from a different source completes while source A is
   flooding;
3. a same-source fresh retransmit is admitted, while an identical-byte
   redelivery still reaches and preserves the TAI64N replay rejection.

The GREEN flood measurement is:

```text
9908 flood: N=100 admitted=5 dh_paid=5 dropped=95 responses=1 replayed=4 mac2_ok=5 elapsed_ms=23
```

The three cells passed (`3 passed, 0 failed`). The cookie unit cell
`handshake_source_bucket_burst_and_table_cap` also passed (`1 passed, 0
failed`), pinning the burst/refill and 2048-entry map cap.

## Residuals / gaps

The bound is per source IP. A distributed flood that rotates source IPs can
consume one bounded burst per active source; the 2048-entry fail-closed table
bounds state growth, but this change does not claim to provide an aggregate
multi-source Noise budget. MAC2 BLAKE2 verification remains intentionally
before the admission decision; the protected resource is the responder Noise
read/DH and subsequent session work identified by #9908.
