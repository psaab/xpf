# #17052: consolidate failover announcement engines

- **Timestamp**: 2026-10-28
- **Action**: Failover announcement ran on two mode-selected engines —
  `pkg/vrrp` `sendGARPReservedMode` (VIP-only, per-instance epoch dedup /
  500 ms dampener / `vipMu` + `markGARPAnnouncedLocked` bookkeeping) and
  daemon `directSendGARPs` (VIP + router-LL NA + pool GARP/NA) — with the
  #5695 clamp duplicated in both. Fixes landed in one engine only in both
  directions (#2377→#3922, #2867→#2898), and the router-LL NA (#15684)
  and IPv6 pool NA (#12172) existed only in direct mode, so legacy VRRP
  mode never sent them. Consolidated onto one shared engine while
  preserving each mode's semantics/timing:
  - `pkg/cluster/announce.go` (new): `AnnounceTarget{Iface, IP,
    Kind(VIP|RouterLL|PoolV4|PoolV6), Burst, ProbeIP}`,
    `AnnounceTargets(cfg, rgID, probeDerive)` (VIPs via the #17140
    single walk `Config.RethVIPsForRG`, router LL via the #17049
    placement `Config.RouterLinkLocalPlacements`, pool via the #17086
    SSOT `Config.RefRG`), `NonVIPAnnounceTargets`,
    `PoolAnnounceTargets`, `AnnounceTargetsFromVIPMap`, and
    `SendAnnounceTargets(targets, stillValid, sender)` which holds the
    frame sequence (VIP v4 GARP burst + gateway probe — probe fires
    even on GARP error, as both engines did, and never counts as
    announced; VIP v6/router-LL NA burst; pool single-frame with the
    #8405 64-attempted bound and mid-sweep `stillValid` fence) and the
    single announce-path `ClampGratuitousARPCount` call
    (`AnnounceBurstCount`/`EffectiveAnnounceBurstCount`).
    `GatewayProbeTarget` stays in `pkg/vrrp` (no import cycle) and is
    passed in as `probeDerive`. Package placement is `pkg/cluster` per
    the issue's fix direction; the leaf-package placement proposed by
    the still-open sibling #17325 is its own later move.
  - `pkg/daemon/daemon_ha_vip.go`: `directSendGARPs` is now a wrapper —
    #2898 fence (`directBurstStillValid`) + per-RG clamp warn-once,
    then `SendAnnounceTargets(AnnounceTargets(...))` through the
    existing `direct*Fn` seams. New `sendVRRPModeNonVIPAnnounce` sends
    the non-VIP half in legacy mode, gated on `rgState.IsActive()`.
    `announceProxyARPPoolAddresses` delegates to
    `PoolAnnounceTargets`+sender (kept for the #8405/#12172 tests);
    pool-truncation warn-once split into `poolTruncWarned` so a clamp
    warning no longer suppresses the distinct truncation warning.
  - `pkg/daemon/daemon_ha.go`: VRRP MASTER arm
    (`tr.Changed && tr.Active`) now calls
    `sendVRRPModeNonVIPAnnounce(rgID)` after `addStableRethLinkLocal`,
    before `applyRethServicesForRG` — ordering preserved, announce
    added where none existed.
  - `pkg/vrrp/instance_garp.go`: `reserveGARPBurstGateLocked` takes
    its count from `cluster.EffectiveAnnounceBurstCount` (per-instance
    warn-once kept); `sendGARPReservedMode` builds one VIP
    `AnnounceTarget` per VIP and sends it via `SendAnnounceTargets`
    under `vipMu`, so epoch dedup, dampener, #14155 pending tracking
    and the mid-burst ownership fence are unchanged. NOT changed: the
    VRRP bookkeeping stays in `pkg/vrrp` (per the issue's adversarial
    analysis, only the target set + frame sequence needed sharing);
    the redundant `added` GARP in `reconcileProxyARP` is kept — it
    fires on config-commit adds, a different trigger than failover
    ownership, so folding it in would change commit-path timing.
  - Fold (Rev18310Opus B1/M1/M2/M3): the non-VIP announce is now
    level-triggered. `convergeLegacyNonVIPAnnounce` +
    `legacyNonVIPAnnouncePending` (daemon_ha_vip.go) claim each
    activation generation exactly once; the cluster-primary arm, the
    VRRP MASTER arm and the reconcile converger arm all funnel
    through it, fixing the cluster-first ordering on the default
    userspace (non-strict) dataplane where SetCluster consumes the
    edge and ForceRGMaster then reports Changed=false. Chosen over a
    cluster-arm-only call because it also covers sync-hold-release /
    dropped edges (the #16696 pattern) for the same cost. M1: #17158
    nil-predicate up-front refusal restored in
    `announceProxyARPPoolAddresses`. M2: the parity cell now drives
    the real handlers (handleClusterEvent cluster-first, then
    handleVRRPEvent) and the real VRRP leg
    (CollectRethInstances -> sendGARPReservedMode via
    pkg/vrrp/test_seams.go) and asserts per-target sequence without
    sorting (set equality only across the two producers). M3:
    AnnounceResult.ProbeSucceeded restores the probe-success Info
    independent of the GARP result, pinned by
    TestProbeSuccessInfoOnGARPFailure17052.
  - Fold round 2 (Rev18310bOpus B1/B2): the first fold keyed the
    exactly-once claim to rg-state `epoch`, which reconcileLocked
    increments on EVERY input — so the 2s reconcile pass re-sent the
    full non-VIP burst forever. The claim is now keyed to a REAL
    activation generation: `rgStateMachine.activationSeq` increments
    only on inactive->active transitions, `CurrentActivation` reads
    (active, generation) atomically in one lock hold, and the
    converger claims exactly the generation it observed. The marker
    is cleared explicitly on the deactivation arms: cluster demotion
    clears only when the resulting desired state is inactive (a demotion
    with VRRP still MASTER preserves the same-generation claim), while
    VRRP BACKUP and reconcile deactivation clear on their inactive
    paths; never as a pending-check side effect. `legacyNonVIPAnnouncePending`
    remains a pure read. Lifecycle is pinned by
    `TestNonVIPAnnounceLifecycle17052` (activate -> claim -> reconcile
    ticks NO re-send -> inactive -> cleared -> reactivate exactly one
    re-send) and `TestNonVIPAnnounceProducerRace17052` (cluster/VRRP/
    reconcile producers racing one generation send exactly one burst).
  - `pkg/daemon/announce_parity_17052_test.go` (new): mode-parity test
    asserting the (iface, IP, kind) set announced on activation is
    identical in direct mode and legacy VRRP mode (VIP leg by the
    shared walk, non-VIP leg captured through the seams). RED with the
    legacy leg disabled (missing router-ll + pool-v4/v6), GREEN with
    the fix.
  - Fold round 3: cluster demotion no longer clears the non-VIP claim
    unconditionally. It clears only when `tr.Active` is false; if VRRP
    remains MASTER, the RG stays active at the same generation and the
    claim must survive so reconciliation cannot re-send it. All
    deactivation clears are keyed through the transition's activation
    generation, so a late old-generation cleanup cannot erase a new
    claim. Pinned by `TestNonVIPAnnounceClusterDemotionWhileVRRPMaster17052`:
    MASTER -> active cluster demotion -> no re-send -> BACKUP -> MASTER
    reactivation -> exactly one burst; the cell also pins delayed cleanup
    preserving the newer claim.
    Previously `AnnounceResult.FirstErr` was ignored: total non-VIP send
    failure left the generation claimed forever. Chosen semantics: when
    `Sent == 0` and `FirstErr != nil`, release only that generation's claim
    so the next producer/reconcile pass retries; partial success remains
    claimed (at-most-once for already delivered targets), avoiding duplicate
    frames. Pinned by `TestNonVIPAnnounceRetriesAfterTotalFailure17052`.
    The pre-existing direct-mode dual-active-win re-announce
    (`DualActiveWin -> scheduleDirectAnnounce`) is intentionally unchanged
    and out of scope for this PR.

  - Fold round 4 (B1/B2): claim admission is monotonic under
    `nonVIPAnnounceMu`: an existing claim at or beyond the observed
    activation generation rejects a stale claimant, and map membership
    distinguishes an absent claim from stored generation zero. The
    sender carries its exact claimed generation and validates that the
    RG remains active at that generation and that the generation remains
    claimed before sending and at the existing follow-up/pool gates.
    This generation-aware predicate was chosen over holding
    `nonVIPAnnounceMu` across frame I/O: it retains a short claim lock
    and lets deactivation cleanup/pending checks proceed without waiting
    on sends. Deterministic cells
    `TestNonVIPAnnounceMonotonicClaims17052` and
    `TestNonVIPAnnounceDelayedGenerationSend17052` cover a stale claim
    after a newer claim and a delayed stale sender after
    deactivate/reactivate, respectively.

- **Risk**: legacy-mode failovers now emit router-LL NAs + pool
  GARPs/NAs that were previously absent (the intended fix; bounded by
  the same clamp + 64-address cap + ownership fence). Direct-mode
  frame order changed from map iteration to sorted-iface order
  (deterministic; no semantic dependency on the old random order).
  Log wording on per-target failures now comes from the shared sender
  (`announce: ... failed`) instead of the two engines' prefixes.
  Round-3 risk: partial target failures remain at-most-once, so a target
  that failed alongside another successful target is not retried until a
  later activation; retrying the whole set could duplicate delivered
  frames. The direct-mode dual-active-win re-announce remains pre-existing
  and out of scope.
