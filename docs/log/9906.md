# #9906 + #9907 — IPsec proposal safety cohort

- **Timestamp**: 2026-09-17T01:57:49-07:00
- **Scope**: #9906 (algorithm values reaching unquoted swanctl proposal lists) and #9907 (non-AEAD ESP proposals without integrity), fixed together because both defects are in the IKE/ESP proposal builders and share the same strict/tolerant/render pipeline.

## Baseline RED proof

Before the implementation, on the clean `origin/master` commit `cad1eeab0`, a temporary regression harness exercised both paths:

- `#`, `{`, `}`, and `=` embedded in each of the four algorithm leaves (IKE encryption, IKE authentication, ESP encryption, and ESP authentication) survived compilation and reached the generated unquoted `proposals`/`esp_proposals` values.
- An ESP proposal with `aes-256-cbc` and no `authentication-algorithm` compiled and rendered a bare `aes256` proposal, silently omitting integrity.

The temporary harness was removed after the RED run. The permanent cells below retain the same malformed inputs and fail if either behavior returns.

## Decision and implementation

- `config.IsSafeIPsecAlgorithmValue` is an allowlist shared by commit validation and the renderer: ASCII letters, digits, `-`, and `_`; an empty value is allowed only as an omitted leaf. Strict validation walks every IKE and ESP proposal and reports the proposal, field, and authored value.
- A non-AH ESP proposal whose effective encryption is not GCM must carry `authentication-algorithm`. Strict compilation rejects the proposal with an integrity diagnostic. GCM is AEAD and may omit a separate integrity token.
- The tolerant load/peer-sync path downgrades the strict error to a warning. The renderer independently skips an unsafe or incomplete proposal, while preserving any safe sibling in a multi-proposal list; if none remain, the affected VPN is omitted rather than emitting an empty or fabricated proposal.
- The render-side check also covers direct, legacy proposal fallbacks, and preserves the existing DH-group fail-closed sentinel.

## Ratchets and fixture updates

- `TestCompactNormalizeScopePreservesCompiledResult8690` initially exposed one consequence of the new #9907 gate: compact normalization dropped an authored authentication leaf, so the pass-disabled spelling was rejected while the repaired pass-enabled spelling was accepted. This is a benign normalizer repair, not a gate disarm; the census map records the evidence and the focused 8690 test is green.
- Four pre-existing positive config fixtures used non-AEAD ESP proposals without an integrity leaf. They now specify `hmac-sha-256-128` so they remain valid positive fixtures under #9907: the multi-value flat/hierarchical and dangling-reference cases, the duplicate-block merge case, and the lifetime-kilobytes advisory case. The malformed no-integrity form remains covered by the dedicated strict/tolerant/render tests above.
- The #6469 expectation change is intentional: control-byte replacement cannot make a newline-bearing algorithm safe inside an unquoted proposal list. The renderer now skips that persisted VPN; this is the belt required by #9906, not an over-escape of legitimate proposal lists.
