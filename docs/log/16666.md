# Issue #16666: NAT64 PTB→Frag-Needed MTU ignores quoted Fragment Header

- **Timestamp**: 2026-10-25
  - **Action**: The PTB arm of `translate_icmpv6_message_to_icmpv4`
    (`userspace-dp/src/nat64/icmp.rs`) advertised `PTB_MTU - 20`
    unconditionally. RFC 7915 §5.2 requires the MTU adjustment to take
    "into account whether or not the packet in error includes a
    Fragment Header": a translated IPv6 fragment carries the 8-byte
    Fragment Header and is `v4_len + 28`, so quoting one must subtract
    28. Advertising `mtu - 20` for a first-fragment quote left the
    relayed Next-Hop MTU 8 bytes too large (e.g. 1380 for a 1400
    bottleneck); every DF-clear retry at that MTU still exceeded the
    IPv6 bottleneck, eliciting another PTB — a non-converging PMTUD
    black hole for large DF-clear UDP through NAT64 to IPv6 clients
    behind a reduced-MTU hop. Fix: `EmbeddedV6ToV4Layout` now carries
    `has_fragment_header` (from the `ipv6_fragment_header` walk the
    layout already performed), and the PTB arm inspects the embedded
    quote via that shared layout, subtracting the new
    `NAT64_FRAGMENT_HEADER_LEN` (8, `nat64/translate.rs`) in addition
    to `NAT64_HEADER_DELTA` (20) when a Fragment Header is present.
    A quote that fails the layout aborts the whole error translation
    in `write_icmpv4_error_with_embedded` anyway, so the -20 fallback
    on layout failure cannot emit a wrong MTU. The reverse
    Frag-Needed→PTB arm (§4.2) was audited: the packet in error there
    is the outer IPv4 packet, whose MF/offset are not visible in the
    ICMP message, and the outer translators drop fragmented ICMP
    before that arm (#2562), so its plain +20 is correct for every
    reachable input (documented in place; the quote's own fragment
    state is handled by `translate_embedded_v4_to_v6` emitting the
    quote's Fragment Header).
  - **File(s)**: `userspace-dp/src/nat64/icmp.rs`,
    `userspace-dp/src/nat64/translate.rs`,
    `userspace-dp/src/nat64_tests.rs`, `debian/changelog`,
    `docs/log/16666.md`
  - **Validation**: New tests in `nat64_tests.rs`:
    `nat64_v6_to_v4_ptb_fragment_quote_uses_delta28_16666`
    (first-fragment quote, PTB 1400 → Frag-Needed 1372, embedded MF
    and checksums verified), `..._atomic_fragment_quote_...`
    (RFC 6946 atomic quote → 1372), and
    `nat64_v6_to_v4_ptb_unfragmented_quote_keeps_delta20_16666`
    (control 1400 → 1380). RED evidence: with the delta forced back
    to 20, the two fragment tests fail (1380 != 1372) while the
    control passes. The pre-existing 1500 → 1480 cell
    (`nat64_v6_to_v4_packet_too_big_becomes_frag_needed_with_mtu`)
    stays green. Full `nat64::` test module run — see PR for counts.
  - **Residual**: None known. The optional RFC minimum-MTU
    refinement mentioned in the issue (applying the IPv4/IPv6
    next-hop minimums) was not adopted: the existing clamp
    (68..=65535) is unchanged and out of the defect's scope.
