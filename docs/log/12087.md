# #12087 — resolve secure-tunnel RI members by the authored netdev

- **Issue**: #12087 — routing-instance member `st<N>.0` is collapsed to `st<N>` although the XFRM interface is created using the authored `bind-interface` name.
- **Branch**: `fix/12087-st0-unit`
- **Worktree**: `/var/worktrees/12087-st0-unit`
- **Base**: `1c384b9a47ff7d6e567fa50632faa75c3995ae87`

## Why

`LogicalUnitDeviceKey` intentionally collapses logical unit zero onto its base. For an IPsec bind authored as `st0.0`, however, the xfrmi reconciler creates `st0.0`; deriving the RI member from the unit reference alone instead returns `st0`. The bind failure is WARN-only, so the configuration apply can continue without putting the xfrmi into its intended VRF. Stale-member cleanup also resolves its desired-device set through the same member resolver.

## What

- `routingInstanceMemberLinuxName` now asks `SecureTunnelUnitNetdev` for a secure-tunnel unit's owned Linux netdev before the tunnel-name and logical-unit fallbacks. The resolver remains the single source of truth for authored-bind spelling and collision behavior.
- Added table coverage for `bind-interface` values `st0.0`, `st0`, `st0.1`, and `st1.0`, plus an unbound fallback control. Updated the shared resolver caller inventory to include the RI member resolver.
- Added an isolated netns acceptance cell that creates the real xfrmi and VRF, applies RI list binding once, checks `MasterIndex`, and verifies stale-member cleanup does not queue `st0.0` for unbind.
