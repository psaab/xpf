# #12087 — resolve secure-tunnel RI members by the authored netdev

- **Issue**: #12087 — routing-instance member `st<N>.0` is collapsed to `st<N>` although the XFRM interface is created using the authored `bind-interface` name.
- **Branch**: `fix/12087-campaign-pub`
- **Worktree**: `/var/worktrees/campaign-pub/wt-12087`
- **Base**: `83b5c955335f16d8c7835f206b210ce3ae1a5fe5`

## Why

`LogicalUnitDeviceKey` intentionally collapses logical unit zero onto its base. For an IPsec bind authored as `st0.0`, however, the xfrmi reconciler creates `st0.0`; resolving an explicit RI unit from the reference alone therefore returns `st0`. The initial #12087 fix covered explicit unit members, but declared bare members expand through a separate fanout helper and still resolved the generated `st0.0` key as `st0`. That split identity bypassed the #11060 cross-instance ownership gate and left bare-only membership outside the intended VRF. The bind failure is WARN-only, and stale-member cleanup consumes the same member resolver.

## What

- Explicit and generated secure-tunnel unit keys use `SecureTunnelUnitNetdev` before the tunnel-name and logical-unit fallbacks. The resolver remains the single source of truth for authored-bind spelling and collision behavior; bare-primary identity and ordinary/tunnel fallbacks remain intact.
- Added strict and tolerant #11060 coverage for bare `st0` versus explicit `st0.0`, including the generated key's preserved `st0` primary and distinct-unit/tunnel-fallback controls. Retained the authored-bind table coverage for `st0.0`, `st0`, `st0.1`, and `st1.0`.
- The isolated netns acceptance cell now binds both a bare-member fanout xfrmi and an explicit unit xfrmi, checks real kernel `MasterIndex`, and verifies stale-member cleanup does not queue either for unbind.
