# #16804 — networkd foreign-rule cleanup deleted xpf ip rules

- **Timestamp**: 2026-10-25
  - **Action**: systemd-networkd kept its default
    `ManageForeignRoutingPolicyRules=yes` and xpf never overrode it, so
    networkd deleted every xpf ip rule on each `networkctl reconfigure`
    (which xpf itself runs on any commit that changes a networkd file)
    and on every networkd restart. Only the #9819 VRF miss terminator
    was re-asserted; the mgmt-DNS 2500–2503 steering pairs are installed
    before the networkd activation, so the tail DNS reconcile dropped
    the management DHCP name-servers from resolv.conf, and after a
    restart the next-table, rib-group and PBR bands had no owner until
    the next commit (with the userspace FIB mirror losing them on its
    next republish). Three coordinated fixes:
    (1) ship `/etc/systemd/networkd.conf.d/xpf.conf` with
    `[Network] ManageForeignRoutingPolicyRules=no` — the repo file
    `etc/systemd/networkd.conf.d/xpf.conf` is the single source: the
    image bake copies it into `/etc/systemd/networkd.conf.d/` and the
    .deb stages the same bytes under
    `/usr/lib/systemd/networkd.conf.d/` (package-owned, not a conffile;
    effective at the next networkd start, so installing it never
    disturbs a running foreign host).
    (2) commit path: the existing post-FRR `applyMgmtDNSRules` re-run
    (#16782) already lands after the networkd activation inside
    `applyDataplaneAndHACore`; it is now documented and pinned as the
    #16804 post-activation re-assert, so MGMT-DNS-RULES-INSTALL follows
    NETWORKD-RECONFIGURE and the tail readiness gate sees live rules.
    (3) restart arm: the #9693 30 s routing owner now detects a flush
    between commits — the always-on terminator re-assert is paired with
    a RuleList readback canary (`terminatorFlushed16804`): a desired but
    missing pref-2000 terminator escalates the tick to re-run the
    policy bands, the route-leak snapshot republish and the mgmt-DNS
    reconcile, latching any failure as ordinary routing debt. A healthy
    tick writes nothing beyond the existing terminator check.
    NOT changed: rule priorities/shapes, the #16782 FRR-static refusal,
    readiness/publication semantics, fail-closed behaviour.
  - **File(s)**: `etc/systemd/networkd.conf.d/xpf.conf` (new),
    `debian/rules`, `scripts/image/bake.py`,
    `pkg/daemon/daemon_apply.go`,
    `pkg/daemon/routing_reconcile_debt_9693.go`,

  - **Validation**: new Go cells (RED-verified by reverting each arm:
    disabling the flush escalation fails both tick cells; deleting the
    post-FRR reconcile fails the dynamic order cell with events
    `[MGMT-DNS-RULES-INSTALL NETWORKD-RECONFIGURE]`)
    `TestApplyOrderMgmtDNSAfterNetworkdFlushDynamic16804` (dynamic
    event order through real applyConfigLocked),
    `TestMgmtDNSReconcileRunsAfterNetworkdActivation16804` (source-order
    pin), `TestRoutingTickRestoresAllRuleBandsAfterFlush16804` (simulated
    restart flush restored without a commit, no debt on success),
    `TestRoutingTickNoFlushIsQuiet16804` (healthy tick rewrites
    nothing), `TestRoutingTickFlushRestoreFailureLatchesDebt16804`,
    `TestTerminatorFlushedProbe16804`; existing #10421/#9693/#16782
    cells stay green in the same run. New Python cells
    `test_networkd_dropin_16804.py` (source content, bake copy-in, deb
    staging) pass 3/3; the neighbouring bake cells (transit sysctls,
    hugepages/deb-payload) stay green. The live netns probe could not
    be re-executed in this sandbox: networkd 262 starts and stays alive
    but never leaves the udev-pending state without a host udev
    database (links never get a Network File assigned even with a
    synthetic udevd), so reconfigure never reaches the rule-cleanup
    path; the executed default/fix arms from the validated source
    report (networkd 262 netns: default after-reconfigure=0,
    after-restart=0; fix arm 5/5 survive) stand as the kernel-level
    evidence, and the Go cells above pin the in-daemon ordering and
    the no-commit restart healing on this branch.
  - **Risk**: On hosts that already merge networkd.conf drop-ins, the
    new file only disables foreign-rule cleanup — networkd stops
    deleting rules it did not install, which is exactly xpf's ownership
    model; an operator can override with a lexically later drop-in.
    The tick escalation adds a full band re-assert only on ticks where
    the terminator readback shows a flush (or debt is already owed);
    the reconciles are the same idempotent clear+re-add the commit
    path runs.
