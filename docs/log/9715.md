# #9715: cross-loop session-sync apply can apply an older operation over a newer one

- **Timestamp**: 2026-09-11T09:40Z
- **Action**: worktree `/var/tmp/wt-9715-sync-apply-serialize` on origin/master 1a7f8f7cc, branch
  `fix/9715-session-sync-per-key-apply`.
- **Action**: research, at 1a7f8f7cc.
  - Every installed fabric connection runs its own `receiveLoop`
    (`sync_conn_read.go` `receiveLoop` → `handleMessage`).
  - The install arms call `installClusterSyncedV4/V6`. Within that call:
    - the guard (`installGenGuard*`) and the record (`recordInstalledGen*`) each take `recvGenMu`
      on their own;
    - the dataplane `PutClusterSynced*` runs between them, holding no lock.
  - The delete arms call `deleteClusterSyncedV4/V6`. `deleteGenGuard*` checks and tombstones under
    `recvGenMu`, then `DeleteWithCompanions*` runs after the unlock.
  - The #2198 F3 note justified this by a single-threaded apply over one active stream. That holds
    per loop only. While the stream moves between fabrics, two loops can apply the same key.
  - `resetRecvGen` (accepted `BulkStart`) clears the maps under `recvGenMu` alone. So an install on
    the other loop that passed its guard before the reset could record its pre-reboot generation
    after it.
  - Re-entrancy checks for a lock held across the apply:
    - The dataplane delete path (`DeleteKnownV4` → `DeleteBatchKnownV4`) calls back into nothing.
    - `OnForwardSessionInstalled` only starts a goroutine (`scheduleStandbyNeighborRefresh`).
    - The only existing write hooks (#6368) call `beginConfigApply`, whose `configGenMu` is a leaf.
- **Action**: design decision. ONE `applyMu`, not per-key stripes.
  - It is uncontended in steady state, because one loop applies at a time.
  - It serializes only while two loops apply at once.
  - It also covers the reverse-companion row a forward install writes, which a per-key lock keyed
    on the forward key would not.
  - Lock order: `applyMu` → `recvGenMu`.
  - Rejected: fencing frames from a non-active connection. A frame read on the old connection
    before the move is legitimate, and what orders the old loop's in-flight frames against the
    new loop's is exactly what is missing.
- **Action**: change.
  - `applyMu` on `SessionSync`, with its contract and lock order documented at the field.
  - Held across `installClusterSyncedV4/V6` (guard → write → record or rollback) and across
    `deleteClusterSyncedV4/V6` (guard → dataplane delete).
  - Held around the `resetRecvGen` map reset.
  - The F3 note is rewritten to state the corrected invariant.
  - The #6368 rollback comment no longer cites F3 as refusing a lock. `applyMu` orders the receive
    loops against each other, not against `configApplyLoop`.
  - The `pkg/cluster/README.md` generation-guard paragraph is corrected the same way.
  - `mockSweepDP` gains `onDeleteV4/onDeleteV6`, which park inside the dataplane delete as
    `onSetV4/V6` do inside the write.
  - **File(s)**: `pkg/cluster/sync.go`, `pkg/cluster/sync_conn_gen.go`, `pkg/cluster/README.md`,
    `pkg/cluster/sync_test.go`, `docs/log/9715.md`
