# 14712 — Non-GET safe methods (HEAD) bypassed command-regex route resolution

`readPermissionFor` (#9134) canonicalizes any safe non-GET method to the
`GET` table entry, so `HEAD /api/v1/status` passes the coarse `PermView`
gate and reaches `authorizeRESTRead` → `authorizeRESTCommand`. There the
route was keyed on the raw `r.Method` (`authz_command_regex_9952.go`:
`route := r.Method + " " + r.URL.Path`), so `"HEAD /api/v1/status"`
missed every GET-keyed table — `restRouteCommand`, `restRoutesNoCommand`,
and the `restRequestCommand9952` request-decoded switch — and hit the
fail-closed `!mapped` denial. Every regex-restricted (non-superuser,
`OperationalLoginRegexesFor` ok) class therefore got 403 on 100% of HEAD
reads while GET succeeded. This is a fail-closed availability/correctness
defect (health probes, SDK HEAD checks), not an authorization bypass:
HEAD got *less* access than GET.

Scope note: only HEAD is reachable this way. Go's `ServeMux` aliases
HEAD to GET patterns; `OPTIONS`/`TRACE` have no GET pattern and never
reach a GET handler (the coarse gate's `/api/v1` fail-closed arm or the
mux 405 stops them first). The packet's "safe methods × endpoints"
framing collapses to HEAD.

Fix (`pkg/api/authz_command_regex_9952.go`): `authorizeRESTCommand` now
keys the tables on `canonicalRESTRoute14712(r.Method, r.URL.Path)`, which
returns the GET spelling for any safe method and the raw method
otherwise — the same `isSafeHTTPMethod` predicate `readPermissionFor`
uses, so HEAD follows the GET verdict exactly, including deny cases,
the six declared-no-command reads (#14146), and the request-decoded
routes (`show-text` topic, `system/info` type). Non-safe methods (the
POST mutation family) keep their raw key, so no mutation route is
aliased; `restActionVerb9952` is POST-only and unchanged. The coarse
gate (`readPermissionFor`), the mutation gate, and the route tables are
untouched.

Regression (`pkg/api/authz_command_regex_14712_test.go`, RED on
origin/master ca1baec1e9): `TestHeadFollowsGetCommandVerdict14712`
fails pre-fix with HEAD refused by the generic `!mapped` message while
GET is allowed under `allow-commands "^show version$"`, and with the
HEAD refusal not charging `"show version"` under a deny;
`TestHeadRequestDecodedFollowsGet14712` fails pre-fix with HEAD
`show-text?topic=version` and `system/info?type=uptime` refused under
their allow-lists; `TestHeadThroughReadMiddleware14712` fails pre-fix
with HEAD `/api/v1/status` and HEAD `show-text?topic=version` returning
403 through the real `readAuthz` middleware under
`allow-commands "^show "` while GET serves. All pass post-fix.
`TestHeadNoCommandRoutesFollowGet14712` pins the deny direction on the
six no-command routes, the no-regex narrowness control, and the
superuser exemption under HEAD.

Validation: `go test ./pkg/api/ -run '14712'` RED pre-fix (3 tests
failing as above), GREEN post-fix. Neighbor suites
(`9952|14146|9134|13249|11678|12582|9051|9903|6660|5561`) pass.
Full `pkg/api` suite: only pre-existing failures
(`TestFirewallValidationHarnessDocGuard`,
`TestEmitUserspaceDynamicBufferMetrics`, and the five `6960`
session-interface cells), all reproduced identically on
`origin/master` 8fa985618f and unrelated to this change.

Risk: operator-visible delta — a regex-restricted login class can now
read via HEAD exactly what it can read via GET (and is denied via HEAD
exactly what it is denied via GET, now with the resolved command named
in the denial instead of the generic unmapped-route message). Classes
without operational regexes and superusers are unchanged. No route,
permission, or config surface changes.
