# #12513 — retain term-line values for the other policy actions

- **Timestamp**: 2026-10-10; review fold 2026-10-12
- **Action**: Hand the term-line `then` spelling of the six remaining value-carrying actions to their operand readers, and validate those operands at strict commit the way the schema validates the braced spelling.
- **Base**: `origin/master` `442fd0dd0` (originally `f9cb48ed8`)
- **Files**: `pkg/config/compiler_routing.go`, `pkg/config/policy_then_operands_12513.go`, `pkg/config/compiler_validate_strict_routing.go`, `pkg/config/types_routing.go`, `pkg/config/compiler_opts.go`, `pkg/frr/policy_render.go`, `pkg/frr/render_validate.go`, `pkg/frr/README.md`, `docs/config-schema.md`, the two `policy_termline_values_12513_test.go` files, this log
- **Parent**: #12070

## Why

The #12070 inline-loop fix dispatched only `then next-hop` and
`then as-path-prepend` to their operand readers. For `community`,
`load-balance`, `local-preference`, `metric`, `metric-type`, and `origin`,
the term-line spelling `term t then <action> <value>;` still took the generic
`then` branch: `term.Action` got the keyword and the value was dropped, so the
term rendered permit/fall-through with no `set` clause (#8933 shape).

Only the term-line spelling misrouted. Compact `term t { then <action>
<value>; }` is normalized to the braced form (`compact_normalize_8662.go`) and
already compiled correctly, and `then accept <action> <value>` tails already
reached the operand readers. Those packed tails (term-line, and compact or
term-line `then accept ...`) bypass the schema walk, so out-of-range values
such as `then accept metric 4294967296` committed and rendered FRR lines that
fail the reload. The first #12513 commit made the term-line spelling reach the
same unvalidated readers.

## What

- **Dispatch**: the six actions (`policyTermThenValueActions12513`) now go to
  their operand cases. If the operand position is empty, or holds a word the
  inline parser's main switch interprets (`accept`, `reject`, `next`, `from`,
  `then`, another action, or `protocol` / `prefix-list` / `route-filter` /
  `as-path`), the dispatch skips only the action keyword. That word keeps the
  meaning it had before #12513, and the operand is recorded for the strict
  gate. Without this, the first #12513 commit read `then origin reject` as
  origin `reject`: strict commit accepted it and the term rendered
  `permit 10 / on-match next` instead of `deny 10`. `then origin protocol
  static accept` also lost its match.
- **Readers**: a missing operand, a non-integer local-preference / metric /
  metric-type, and metric-type 0 are recorded in compiler-only
  `invalidThenOperand12513` state. `then community add|delete|set` and the bare
  replace form read a whole bracketed list (#2902), stopping before a list
  member the main switch interprets; that member is recorded. This also fixes
  the compact `then accept community add [ a b ]` spelling, which kept only
  `a` before #12513.
- **Strict gate**: `validatePolicyThenOperandsStrict` calls
  `validatePolicyThenValueOperands12513`. It rejects the recorded operand,
  then applies the term `then` schema validators (looked up from the schema,
  not copied) to the compiled fields: local-preference and metric
  0..4294967295 when present, metric-type 1..2 when set, origin
  `igp | egp | incomplete`. Errors name the policy, term, leaf, and value.
  The existing `lenientPolicyThenOperands` option downgrades these errors to
  warnings on tolerant load and peer-sync.
- **Renderer**: `set local-preference` and `set metric` are omitted with
  `slog.Warn` outside 0..4294967295 (`validRouteMapU32`). A larger value fails
  the reload, and a negative one would read as FRR's relative `-N` form.
  metric-type (1/2 only) and origin (#4919) already had render guards.
- The stale community comment that said the inline path is "not reached for
  `then community`" is replaced.

## Risk

- **Strict commit now rejects** compact and term-line tails with an
  out-of-range, non-integer, missing, or keyword operand (`then metric
  4294967296`, `then accept local-preference -1`, `then origin bogus`, `then
  local-preference accept`, `then metric-type 0`, `then community add [ 65001:1
  reject ]`). It also rejects term-line `then community add|set <undefined
  name>`, which committed before because the value was dropped; it now meets
  the #12069 gate. A persisted config with one of these blocks its next commit
  until it is fixed. Tolerant boot and peer-sync only warn.
- **Tolerant boot and peer-sync render differently**: term-line values now
  become active FRR clauses, and community lists render every member. An
  out-of-range local-preference or metric from any spelling is omitted with a
  warning. Before, FRR either failed the reload or applied a relative change.
- **deny → permit for `next policy` terms**: a term-line value action combined
  with `then next policy` (for example `then local-preference 200 next
  policy`) used to be rejected at commit and render `deny 10` on tolerant
  paths, because the keyword in `Action` conflicted with `next policy`. It now
  commits and renders `permit 10 / set ... / on-match goto`, the same as the
  braced spelling. With a missing or invalid operand, strict commit still
  rejects it, but a tolerant load renders permit/goto with a warning.
- Mixed-version HA peers render these inputs differently until both nodes run
  this build.
- **Unchanged**: unknown words such as `then foo` are #12517. A keyword
  operand after a leading `accept`/`reject` is still consumed as the value,
  as before, so that spelling's tolerant meaning does not change; strict
  commit now rejects it. load-balance values are still unvalidated, because
  the schema has no enum for them. In the term-line operand position, a
  community *named* like a policy keyword fails strict commit; the braced
  spelling still accepts it.
- No live FRR reload or cluster mutation was performed.
