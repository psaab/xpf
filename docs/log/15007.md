# #15007 — Junos AS-path regex semantics not translated to FRR (A11-01)

## Defect

`policy-options as-path <name> <regex>` text was rendered verbatim into
`bgp as-path access-list <name> permit <regex>` (`pkg/frr/policy_render.go`).
FRR evaluates that as an **unanchored POSIX character regex** over the
space-separated AS-path string; Junos matches **whole AS numbers** under an
implicit `^...$` anchor, where `.` is one AS number and `()` is the null
(empty, locally originated) path. Every Junos pattern therefore matched a
different set in FRR:

- `()` — the canonical anti-transit export accept (only my own routes) —
  matches **every** path in FRR: a strict-commit-clean provider-to-provider
  route leak (accept `()`, reject else, advertises BGP-learned routes to
  another eBGP peer).
- `65000` matches substrings (`165000`, `650001`, `1 65000 2`), not the
  single-AS path.
- `.* 65000 .*`, `65000 .*`, groups, `{m,n}`, `[...]` sets and `-` ranges
  are all interpreted at character level, not AS-token level.

`ValidASPathRegex` (POSIX-compile only) could not see any of this.

## Fix

- `TranslateJunosASPathRegex` (`pkg/config/aspath_junos_translate.go`):
  parses the Junos grammar — AS numbers 1..4294967295, `.` (one AS),
  `[...]` AS sets/ranges incl. `[^...]` complement, `(...)` groups,
  `* + ? {m} {m,} {m,n}`, `|`, `-`/en-dash ranges, implicit `^...$` with
  optional explicit anchors, `()` = null path — and emits an anchored FRR
  POSIX ERE over whole AS tokens (`[0-9]+`). Repetition repeats
  `" <term>"`, never digits (`1234+` = repeated AS 1234); separators are
  folded into nullable elements so optional terms leave no stray space;
  ranges become value-exact digit patterns (brute-force-oracle tested).
  Anything outside the grammar (character classes inside an AS number
  such as `65[0-9]+`/`[0-9]+`, escapes, empty alternatives, descending
  or invalid intervals, out-of-range/leading-zero ASNs, stray `^`/`$`)
  is rejected with a diagnostic.
- Renderer (`pkg/frr/policy_render.go`): emits only the translated
  pattern; untranslatable definitions are omitted and
  `asPathListMissingAtRender` keys on the same translation, so reject
  terms render deny-all and other terms skip the dangling branch (the
  existing fail-closed belt, now covering the #15007 omission set).
- Strict gate (`validatePolicyASPathRegexStrict`): rejects
  untranslatable patterns at commit with a Junos-syntax diagnostic
  (suggesting e.g. `65000-65999` for `65[0-9]+`); tolerant load still
  warns and boots (#1960). `ValidASPathRegex` is retained as the legacy
  POSIX predicate for its remaining premise/dialect callers.
- Neighbouring fixtures whose text only had FRR-dialect meaning
  (`65[0-9]+`, `^65000 [0-9]+$`, bare `0-9 +`, `"x"`) were re-spelled to
  Junos equivalents (`[65000-65999]`, `[123-125]`, valid ASNs) or moved
  to the lenient path where their subject is lexing/provenance rather
  than commit acceptance. No behaviour change outside as-path regexes.

## Regression

- `pkg/config/aspath_translate_15007_test.go` — translation table
  evaluated against Junos semantics with the POSIX engine as oracle,
  reject table, numeric-range brute-force oracle (1..70000 + extremes),
  strict-commit gate accept/reject + tolerant-boot warning.
- `pkg/frr/policy_aspath_translate_15007_test.go` — exact rendered lines
  for every divergence row, `()` matches only the empty path, rendered
  semantics table, omission of untranslatables, the canonical
  anti-transit policy end-to-end through `CompileConfig` + render, and
  reject-term deny-all over an untranslatable list.
- Pre-fix, the renderer emitted the verbatim patterns, so the exact-line
  and semantics cells fail on master (e.g. `()` matching `65000 65001`).

## Validation

- Targeted config/frr/configstore suites run at PR time (see PR body).

## Risk

Operators who (unknowingly) relied on FRR character-regex behaviour of
as-path patterns — e.g. `65[0-9]+` to mean ASes 65000-65999 — must now
write the Junos form (`[65000-65999]`); strict commit names the fix.
Stored configs with such patterns still boot (warning) and their lists
are omitted at render with terms failing closed, rather than matching
the wrong routes silently.
