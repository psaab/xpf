# 13931 — Size the userspace steering map for session capacity

## Boundary

H06-01 found that the shim's 262,144-row `userspace_sessions` map could fill
before the session tables did. A forward interface-SNAT session can publish
four distinct steering rows; a failed publish is counted but leaves
interface-SNAT ICMP replies and WireGuard-port SNAT replies without their
userspace reverse-NAT steering. The relevant bound is workers × 131,072
sessions per worker × four rows, not the number of logical sessions alone.

## Change

The shim now declares 8,388,608 rows (`16 × 131,072 × 4`) with
`BPF_F_NO_PREALLOC`: capacity covers the 16-worker binding-planner ceiling and
the worst-case four rows per session without preallocating a value pool. Go
pins the same expected capacity, checks it and the map flags during shim
preflight, and tests both the embedded ELF map ABI and the capacity formula.
The generated shim object and manifest are refreshed. Existing pins with the
old map ABI remain subject to the targeted stale-pin refusal/recovery path.

## Capacity note

`BPF_F_NO_PREALLOC` avoids reserving map elements for unused rows, but the
kernel still allocates hash-bucket storage from `max_entries`. The map was not
filled to its limit in a lab; the alternative acceptance is the capacity
formula bound and the embedded-object ABI regression.
