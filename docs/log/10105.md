# Issue #10105: fabric zone-stamp authentication decision

- **Date**: 2026-09-18
- **Decision**: document-and-constrain; do not change the fabric stamp wire format
- **Disposition**: shared-segment active/active fabric is unsupported; the fabric data link must be a private two-peer L2 domain or operator-provided MACsec
- **Implementation**: `docs/fabric-cross-chassis-fwd.md`, `docs/config-schema.md`, and the strict compiler advisory in `pkg/config/compiler_fabric_stamp_10105.go`

## Evidence reviewed

- `gh issue view 10105`: the stamp residual is the #9901/F-073 item; issue comments: none.
- `gh issue view 9901`: the `routing_table`/`ingress_routing_domain` SSOT work is not a wire change and leaves the stamp authenticator learnable.
- `userspace-dp/src/afxdp/forwarding/fabric.rs:241-360`: V1a destination-MAC and V1b RG-binding gates, plus the accepted shared-segment clone residual.
- `userspace-dp/src/afxdp/forwarding/fabric.rs:537-555`: the sender encodes only `02:bf:72:fe:<hi>:<lo>`; the u16 zone id is the public stable name hash.
- `userspace-dp/src/afxdp/frame/inspect.rs:2219-2274` and `afxdp/poll_stages.rs:530-552`: receive-side parsing and validation occur at stage 9 on every packet that enters the fabric path.
- `docs/fabric-cross-chassis-fwd.md` #6458 section: the receiver cannot distinguish a byte-identical forged punt from a legitimate punt in live split-RG mode.
- `pkg/config/zoneid.go:41-49`: `StableZoneID` is a deterministic public FNV-1a fold of the zone name.
- `docs/ha-cluster-userspace-wiring.yaml`: the reference data fabric is `bpu-fab0` and heartbeat is a separate `bpu-hb0`; the supported shape is a private two-peer bridge.
- `pkg/config/compiler_uniformgates_cluster_zone.go:469-523`: `authentication-key` is already a strict commit gate, with `additional-authentication-key` overlap for rotation; this authenticates control channels but does not authenticate the fabric data stamp.
- `docs/vsrx-gaps.md`: product MACsec is not implemented, so MACsec is currently an operator switching/NIC facility rather than an xpf feature.

## Threat model

Production L2-adjacency inventory is not observable from this repository. The
known reference topology is direct-attached or a dedicated two-peer bridge;
the attacker below is a possible deployment placement, not a claim that the
repository measured a shared production VLAN.

The relevant possible attacker is any third speaker on the fabric L2 domain:
compromised hypervisor/host, co-tenant on a shared switch, or misprovisioned
VLAN member. The normal direct-attached/private-bridge deployment has no such
speaker. The residual is reachable only when that attacker is L2-adjacent, a
split-RG active/active placement (or asymmetric failover window) is live, and
the attacker sends a unicast frame to the receiver's fabric MAC. Single-primary
steady state is already closed by V1b/V2, but private L2 remains the required
support boundary and defense in depth.

The stamp has no secret: magic is fixed and `StableZoneID` can be computed
offline. V1a/V1b/V2 remove broadcast sprays, local-RG claims, and wrong-owner
claims, but an attacker can copy the exact remote-RG zone and destination shape
of a currently legitimate punt. No receiver-only predicate can reject that
copy without rejecting the legitimate packet too.

## Options

### Shared-secret MAC — deferred, not selected

The cluster already has an operator-distributed control-link PSK, so key
provisioning is not fundamentally absent: the same secret keys heartbeat HMAC,
fabric gRPC auth and session-sync auth, with a rotation overlap. But an
integrity tag needs a new encapsulation/trailer; the current source MAC has no
spare bytes. An inserted authenticated envelope/header would shift L3 offsets
through the XDP shim and `verified_l3_or_stamp`; an appended tag avoids that
offset shift but changes frame length, MTU/MSS and padding parsing. Either form
is a full wire revision. A useful MAC must bind more than the zone id
(otherwise the attacker can replay a valid zone tag onto another packet),
requiring the inner immutable tuple and additional L3/L4 parsing.

A future MAC design, if shared-segment active/active becomes a supported
requirement, should use a domain-separated control-link PSK and MAC
`(protocol-version, direction, zone-id, immutable inner tuple)`, verify only at
session-miss decisions, and roll through dual-parse/dual-accept plus key
rotation. Existing untagged and V1 stamp frames must not be accepted after the
operator arms the new mode.

The tuple MAC above stops zone-byte cut-and-paste but does **not** stop an
attacker replaying an exact authenticated first packet. If the future feature
claims replay resistance, it must add a sender epoch plus a per-flow/packet
sequence or nonce and a receiver replay window. That creates real dataplane
cost: ordered packets can arrive on different workers, so replay state must
be sharded with bounded cross-worker coordination (or the check must run only
on session-miss state); failover must transfer the epoch/high-water state or
accept a replay window after promotion; and reboot requires a fresh epoch
handshake or durable counter. A miss-only tuple MAC can explicitly accept
ordinary L2 replay as outside its goal, but it must say so; it cannot be
described as complete anti-replay authentication.

### Asymmetric signatures — rejected

Signature verification is materially slower than the existing fixed-MAC
comparison and hash lookups. A reproducible single-thread baseline was run on
2026-09-18 with `/tmp/stampauth_sigbench.go`, Go 1.26.4 stdlib
`crypto/ed25519`/`crypto/hmac`, Intel Xeon D-2146NT @ 2.30 GHz (one worker):
1,000,000 Ed25519 verifications took 88.07 s = 88,066.9 ns/verify, or
88.07 CPU cores at 1 Mpps and 0.8807 cores at 10 k miss/s. The sender-side
Ed25519 signing loop took 36.55 s = 36,552.4 ns/sign, or 36.55 CPU cores at
1 Mpps. A same-message HMAC-SHA256 compute+compare baseline took 3.44 s =
3,439.1 ns/verify, or 3.44 cores at 1 Mpps. This is a Go baseline, not a Rust
dataplane benchmark, but it bounds both sender and receiver costs with a
reproducible implementation/library result. Running signatures for every
packet at stage 9 is therefore infeasible on the measured baseline; moving
verification to session-miss sites reduces the 10 k miss/s case to about one
core, but signing remains a per-redirect sender cost (0.3655 cores at 10 k
redirects/s) and an L2 spammer can still turn verification into a CPU-DoS.
Fail-closed overload would drop legitimate punts.
Signature deployment lacks authenticated peer-public-key provisioning/rotation
and private-key storage lifecycle in this cluster; mTLS/PKI is one possible
heavier mechanism, not a prerequisite of signatures. Both HA peers are equally
trusted stamp issuers in different RG placements, so non-repudiation provides
no useful security property.
The signature-bearing wire trailer and mixed-version negotiation would still be
required.

Signatures have the same replay property: a valid signature proves who minted
the bytes, not that this exact packet is fresh. A signature design that closes
replay therefore also needs an epoch/sequence/nonce and receiver replay
window, with the same worker reordering, failover state transfer and reboot
handshake costs as the MAC design, plus public-key provisioning. A signature
without that state only closes unauthorized stamp cloning, not exact-packet
replay; the selected constrain decision intentionally claims neither.

### Document-and-constrain — selected

This is the smallest correct change for the current supported topology. It
preserves the load-bearing split-RG stamp and its existing fast fixed-cost
validation, while making the only trust-boundary assumption explicit: no
untrusted L2 speaker may share the fabric data domain. It also avoids adding a
second key lifecycle and avoids making the high-rate receive path cryptographic.

## Mixed-version behavior

| Option | Old sender → new receiver | New sender → old receiver | Arming / downgrade consequence |
| --- | --- | --- | --- |
| Document-and-constrain (selected) | Existing stamp is parsed byte-for-byte with V1a/V1b/V2; the new node emits only a strict compile warning. | Existing stamp is unchanged, so the old receiver accepts it exactly as before. | No capability bit, arming state, or wire downgrade exists; the warning is local operator state and cannot split a cluster. |
| Shared-secret MAC (future, not authorized) | Before arming, a new receiver must dual-parse the legacy stamp and therefore retains the clone residual. After arming, rejecting the legacy form would drop legitimate old senders and break split-RG punts. A replay epoch/window also cannot be synchronized with an old sender. | An armed sender MUST use a distinct non-legacy marker/envelope rather than `02:bf:72:fe:<zone>`, so a pre-MAC receiver cannot mistake the frame for an authenticated legacy stamp; its existing parser yields no override/default-deny (or drops). Legitimate stamped new-flow punts therefore break until both peers upgrade. | Rollout requires both nodes to advertise/accept the MAC version, then an explicit arm; rotation requires old+new key dual-accept plus replay epoch/window state. Arming with an old peer is fail-closed for the punt path, not silently accepted. |
| Asymmetric signatures (future, rejected) | Before arming, a new receiver must accept unsigned legacy stamps and retains the clone residual; after arming, old unsigned senders downgrade/drop and legitimate split-RG punts break. A replay window cannot run against a peer that sends no epoch/sequence. | An armed sender MUST use a distinct non-legacy marker/envelope rather than `02:bf:72:fe:<zone>`, so a pre-signature receiver cannot mistake it for an authenticated legacy stamp; its existing parser yields no override/default-deny (or drops). The new sender cannot rely on its signed zone until both peers upgrade. | Rollout requires public-key provisioning, capability negotiation and explicit arm; replay epoch/sequence state must also be negotiated and transferred across failover/reboot. A mixed-version receiver cannot treat an unsigned legacy stamp as authenticated. There is no downgrade that preserves both security and legitimate split-RG traffic. |

The selected path therefore has the only safe mixed-version behavior for the
currently supported topology: old and new nodes interoperate without changing
the wire, while the new strict compiler makes the unsupported shared-L2
assumption visible before deployment.

## Guardrail

`fabricStampSharedSegmentAdvisories10105` emits one strict-path warning whenever
`fabric-interface` or `fabric1-interface` compiles non-empty. It tells the
operator that the data link MUST be direct-attached, a dedicated two-peer
VLAN/bridge, or MACsec, and that shared switching with live RG split is
unsupported. It is not emitted on tolerant boot/peer-sync paths, and it is not
a hard reject because software cannot inspect the cable plant without
rejecting supported direct links. Tests cover the positive signal, no-fabric
negative control and tolerant-path suppression.

## Reproduction recipe for the performance evidence

The measurement above is preserved by this exact source and command (the
benchmark is intentionally outside the product tree; it uses only the Go
standard library and a deterministic key/message):

```sh
cat >/tmp/stampauth_sigbench.go <<'EOF'
package main

import (
	"crypto/ed25519"
	"crypto/hmac"
	"crypto/sha256"
	"fmt"
	"runtime"
	"time"
)

func main() {
	seed := make([]byte, ed25519.SeedSize)
	for i := range seed {
		seed[i] = byte(i + 1)
	}
	priv := ed25519.NewKeyFromSeed(seed)
	pub := priv.Public().(ed25519.PublicKey)
	msg := []byte("xpf fabric stamp benchmark: version=1 zone=50675 proto=6 src=198.51.100.7:443 dst=203.0.113.8:8443")
	sig := ed25519.Sign(priv, msg)
	macKey := []byte("benchmark control-link key 32 bytes")
	mac := hmac.New(sha256.New, macKey)
	_, _ = mac.Write(msg)
	expectedMAC := mac.Sum(nil)
	const n = 1_000_000

	var edOK uint64
	runtime.GC()
	start := time.Now()
	for range n {
		if ed25519.Verify(pub, msg, sig) {
			edOK++
		}
	}
	edElapsed := time.Since(start)

	var signedBytes uint64
	runtime.GC()
	start = time.Now()
	for range n {
		signedBytes += uint64(len(ed25519.Sign(priv, msg)))
	}
	signElapsed := time.Since(start)

	var macOK uint64
	runtime.GC()
	start = time.Now()
	for range n {
		h := hmac.New(sha256.New, macKey)
		_, _ = h.Write(msg)
		got := h.Sum(nil)
		if hmac.Equal(got, expectedMAC) {
			macOK++
		}
	}
	macElapsed := time.Since(start)

	fmt.Printf("go=%s goos=%s goarch=%s n=%d ed25519_ok=%d ed25519_total=%s ed25519_ns=%d ed25519_ns_per_verify=%.1f ed25519_cores_at_1Mpps=%.2f ed25519_cores_at_10k_miss=%.4f ed25519_signed_bytes=%d ed25519_sign_total=%s ed25519_sign_ns=%d ed25519_sign_ns_per_packet=%.1f ed25519_sign_cores_at_1Mpps=%.2f hmac_ok=%d hmac_total=%s hmac_ns=%d hmac_ns_per_verify=%.1f hmac_cores_at_1Mpps=%.2f\n",
		runtime.Version(), runtime.GOOS, runtime.GOARCH, n, edOK, edElapsed, edElapsed.Nanoseconds(), float64(edElapsed.Nanoseconds())/n, float64(edElapsed.Nanoseconds())/1e9, float64(edElapsed.Nanoseconds())*1e4/n/1e9, signedBytes, signElapsed, signElapsed.Nanoseconds(), float64(signElapsed.Nanoseconds())/n, float64(signElapsed.Nanoseconds())/1e9, macOK, macElapsed, macElapsed.Nanoseconds(), float64(macElapsed.Nanoseconds())/n, float64(macElapsed.Nanoseconds())/1e9)
}
EOF
go run /tmp/stampauth_sigbench.go
```

The HMAC loop includes stdlib `hmac.New`/`Sum` allocation work, so its 3.44
core/Mpps number is a conservative baseline rather than a claim about a
future optimized Rust implementation. The Ed25519 signing loop likewise
includes the stdlib signature allocation and measures sender work; both
Ed25519 numbers are decision bounds, not dataplane throughput claims.
