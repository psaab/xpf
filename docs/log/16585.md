# #16585: Cloudflare tag gains a per-install component

- **Timestamp**: 2026-10-24
- **Action**: The Cloudflare record-comment tag was a hash of the zone
  endpoint only (`xpf-managed:prov/<endpoint-fingerprint>`), so two
  independent xpf installs publishing into the SAME zone — same zone,
  same API base, same token, the production shape — derived identical
  tags and one install's withdraw deleted the other's record (#16086
  fold finding 1, left open for exactly this shape). The tag is now
  `xpf-managed:inst/<hash>` where the hash covers a durable per-install
  `install-id` plus the endpoint fingerprint. The id is a new
  `system services dynamic-dns provider <n> install-id` leaf (32
  lowercase hex, schema-validated): carried in committed config, so an
  HA pair sharing the config shares the id (one logical writer), while
  independent installs mint different ids. When the leaf is unset the
  SurfaceAManager mints one per process and caches it per provider
  (`providerWithInstallID`, threaded through both the publish and
  withdraw backend builds); operators pin it via the leaf for
  durability across restarts. Rows stamped with this endpoint's
  pre-#16585 zone-hash tag are read as legacy — withdrawn only through
  the logged value-scoped fallback, never adopted or PATCHed — and any
  other endpoint's or install's tag stays foreign. The #16086 test
  fixture that hid the defect (other instance on `other.example.net`)
  now uses the same zone with a different install-id.
