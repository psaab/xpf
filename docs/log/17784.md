# #17784: preserve undeclared-RG0 IPsec re-initiation on data-RG edges

- **Timestamp**: 2026-10-28
- **Action**: The data-edge fallback is admitted only when one current
  cluster-config snapshot has no RG0 and exactly one data RG, the edge ID
  equals that sole data RG, and the peer's live heartbeat has no RG0 entry.
  `PeerGroupPrimary(0)` is the peer signal: an entry means the
  live peer declares RG0 (including secondary); a primary entry also
  identifies peer ownership. The accessor does not treat retained group
  history as current after heartbeat liveness expires. Local undeclared-RG0
  ownership remains decided by `ownsIPsecConn`. The RG0 edge cannot admit an
  undeclared RG0 candidate, and a stale edge for a removed data RG cannot
  admit the fallback. Declared RG0 stays on its RG0 edge, multi-data-RG
  configurations cannot fan the name across a takeover wave, and spanning
  names remain excluded. A peer-fenced name is retained as owed; the existing
  30-second IPsec sync loop schedules one coalesced retry goroutine after
  heartbeat pruning or liveness expiry, so retry commands do not block the
  publisher. Per-name claims prevent a retry from duplicating a late edge;
  successful-attempt suppression is scoped to the data-RG ownership epoch, so
  a later takeover still runs the #15194 duplicate belt. Comments and the
  collision warning state that multi-RG names rely on strongSwan trap/traffic
  or manual re-initiation. Coverage includes RG1-only, declared-RG0, peer-state,
  stale-edge, apply-lag, multi-RG, retry, and new-ownership-epoch cells.
