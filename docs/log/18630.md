## Why

#18616 makes the standby refuse a synced change to its own control-link
address. The primary's local commit could still promote the peer's new address
and report success, leaving the standby on its old text and nacking every
re-push. The runtime heartbeat already has the authoritative address it dials;
peer-effective validation in the config registry cannot see that running
endpoint.

## What

`commitWithGenBinding` now passes the bound candidate generation to its
preflight callback and retries when a preflight reports a candidate-generation
conflict. The new gate in `cluster_topology_preflight.go` samples the candidate
tree and generation together with `Store.CandidateGateSample`, verifies the
sample matches the bound generation, compiles that tree for the peer node with
`config.CompileConfigForNodeLenient`, and checks the peer view's networkd-
rendered control-unit addresses via `controlLinkStaticAddrs18606` against
`Manager.HeartbeatPeerAddr()`.

A missing running heartbeat endpoint is an abstention. A peer view that no
longer carries the running endpoint is rejected before promotion with the
BOTH-nodes / offline xpfd restart procedure. The gate is wired only in
`commitAndApply` and `commitConfirmedAndApply`; peer-synced apply is unchanged.

refused-commit cell fail (`got <nil>`, exit 1); restoring it made the targeted
`18630|18606` suite pass again. A separate generation-binding cell mutates the
candidate and returns `ErrCandidateGenerationConflict`; the callback is rerun
against the new generation and the new candidate is promoted.
