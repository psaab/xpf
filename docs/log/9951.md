# Issue 9951 — revoke removed inter-VRF leak cache entries

## Why

A cached session could keep serving a forwarding candidate after the inter-VRF route leak that admitted it was removed. WAN failover next-hop pinning remains intentional; leak removal is a tenancy revocation scoped to the exact leak.

## What changed

- Added stable per-leak incarnations retained across config rebuilds and refreshed on remove/re-add.
- Built per-family incarnation-to-prefix liveness indexes once per forwarding snapshot, avoiding a full source-table leak scan on each stamped hit.
- Carried provenance through local/shared session entries independently of the PBR installing-table stamp.
- Recomputed zero-token peer imports locally in both materialization and `UpsertSynced`; preserved nonzero published tokens through sibling fan-out and demotion/rematerialization.
- Applied revocation checks before both ordinary and peer-synced cached lookup arms, including shared rematerialization.
- Stamped forward, reverse, and missing-neighbor installs; reverse synthesis publishes the same stamp.
- Added a zero-token-only `UpsertSynced` recompute gate so nonzero sibling and bring-up replicas retain revocation evidence.
- Failed closed when a removed leak is re-added with a fresh incarnation, preventing ABA resurrection.
- Gated tunnel cached fallback with the same revocation-aware path.
- Restored the two existing `#6979 F3` / zone-pair comments unchanged.
- Documented the scope decision in `docs/multi-wan.md`.

The first provenance implementation compared a second mutable neighbor/ECMP resolution with the original decision. It was corrected before the final green run: provenance now comes from the immutable, precedence-ordered leak-rule walk, with local-delivery ownership checked before leak scanning.
