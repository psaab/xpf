# Issue #12508 — interface filter/sampling editor follows compiler

## Contract and change

Issue #12093 made the inet/inet6 interface compiler read every `filter`
sibling in authored order. Repeated filter leaves therefore resolve to the
last value. Interface-family `sampling` siblings are unioned. Before this fix,
`SetPath`, `DeletePath`, and deactivate/activate descended into or changed only
the first matching sibling, so editing a repeated configuration could leave the
compiled binding unchanged or leave a later binding active.

The editor behavior is now scoped to the `filter` and `sampling` schema nodes
under interface-family `inet` and `inet6` in `pkg/config/ast_edit.go`:

- `set` edits the sibling that supplies the binding. Outside `groups` that is
  the last active matching sibling; if it is a compact leaf, set appends a
  compiler-visible container after it. With no active sibling, set edits the
  last eligible inactive statement (a braced block, or a compact single
  statement braced in place) instead of creating an active copy, so
  deactivate, set, then activate ends at the new value. Apply-groups expansion
  keeps the first group sibling, so under `groups` set edits the first active
  braced or compact single-statement sibling, bracing a compact one in place;
  with no active sibling it edits the first eligible inactive statement.
- Bare `delete` removes all matching siblings. A targeted filter direction or
  sampling direction removes matching bindings from every sibling and compact
  leaf. If the targeted value exists only in a later sibling, its deletion can
  expose an earlier sibling's value; bare delete removes every copy. Missing
  deletes still wrap `config.ErrPathNotFound`. These deletes run the packed
  statement (#8992) and bracket-group (#9799) refusals before clearing
  siblings; every other delete still removes an exactly-elided statement
  before those refusals, as it did before this change.
- Bare `deactivate`/`activate` toggles every matching sibling; targeted
  operations toggle the matching binding in every sibling. A targeted miss now
  reports `path not found: no node matching "filter input"` where it reported
  `path not found: container "filter" does not exist` (likewise for
  `sampling`); a bare miss still reports `no node matching "filter"`. These
  toggle errors still do not wrap `config.ErrPathNotFound`.

This does not change the compiler, schemas, filter value validation, or the
forwarding-options sampling schema. Set targeting, the delete order, and the
all-sibling delete and toggle are scoped to the interface-family `inet` and
`inet6` filter and sampling schema nodes, including their `groups` copies.

## Regression coverage

`pkg/config/interface_filter_editor_12508_test.go` covers four filter shapes
for both `inet` and `inet6`: hierarchical repeats, compact repeats,
compact-then-block, and block-then-compact. It verifies last-value set behavior
and filter/sampling bare and targeted delete/deactivate operations. A
value-naming filter delete also pins the Junos-visible behavior that deleting
later value `B` can expose earlier sibling value `A`. A deactivate, set
`input C`, activate sequence over the four shapes, on `ge-0/0/0` and `lo0` in
both families, must stay off after the set and end at `C`; for lo0 it also
requires `System.Lo0FilterInputV4/V6` to match. Group-body tests pin set,
delete, deactivate, and that sequence for the four shapes plus an inactive
sibling ahead of the first active block. Other cases cover set-into-inactive
filter and sampling statements, including compact leaves; targeted filter
activate; refusal of packed filter/sampling deletes without mutation; and the
scoped delete order: deleting `system host-name` beside a packed `host-name
fw2 domain-name x.example` statement, or `security-zone zgb` beside a
`security-zone [ zga zgb ]` group, still removes the exactly-elided statement.

The lo0 regression starts with repeated inet and inet6 filter blocks, deletes
the binding container, verifies the compiled lo0 binding is empty, then sets
`input C`. It asserts the AST has exactly one filter sibling and the compiled
`System.Lo0FilterInputV4/V6` is `C`.

## lo0 upgrade path

This is an active control-plane path, not merely a config display concern:
`compileInterfaces` iterates interface children without a lo0 exclusion
(`pkg/config/compiler_interfaces.go:67-82`); `resolveDerivedConfig` hoists
unit-0 lo0 filter inputs into `System.Lo0FilterInputV4/V6`
(`pkg/config/compiler_derivations.go:103-107`); and `applyLo0Filter` consumes
those fields (`pkg/daemon/daemon_nft.go:144-157`). The userspace filter
compiler maps an empty lo0 filter name to `Ok(None)`
(`userspace-dp/src/filter/compiler.rs:447-453`). The regressions prove the
editor's delete-then-set consolidation and the deactivate/set/activate
sequence reach the values used by those runtime paths. No live-cluster or
packet-path validation was performed.

## Risk and residuals

- `activate` toggles every matching sibling, so it also revives a sibling
  that was deliberately left inactive. On `filter { input A; } inactive:
  filter { input OLD; }`, `activate ... filter` makes `OLD` effective where
  base kept `A`, and a deactivate/activate round trip moves from `A` to no
  filter to `OLD`. On lo0, `OLD` then reaches `System.Lo0FilterInputV4/V6`.
- Bracing a compact first group sibling also makes the statement it carried
  compile. Compact `sampling input;` is otherwise not compiled, so
  `set groups ... sampling output` against it turns on input and output
  sampling.
- A bare `filter;` or packed first group sibling still shadows group edits,
  as at base: neither can be braced in place, so set edits the next braced or
  compact sibling. Commit refuses a packed filter binding (#10293); packed
  and compact `sampling` spellings are not compiled.
- Outside `groups`, set on a compact last sibling appends a block instead of
  converting the leaf, so a later targeted delete of the new value exposes
  the old one again.
- Repeated `family inet` blocks keep the same editor/compiler mismatch one
  level up; #12661 tracks it.
