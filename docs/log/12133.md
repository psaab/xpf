# Issue #12133 — retry refused PPTP installs

## Why

A successful local PPTP Call-Reply install broadcast to peer workers, but the drain discarded the broadcast result and had no retry record. A full peer queue therefore missed the install and resolved the call's GRE packets as unassociated for the association lifetime, losing the per-call discriminator (forwarded/counting continues; this is not a drop).

## What

`broadcast_pptp_install` now returns both its accepted count and the identities of refusing queues. The control inbox tracks those unsent recipients and retries the install on its periodic drain, without incrementing the local learned count again. A complete later broadcast supersedes pending retries. CDN and control-channel teardown cancel older pending installs so replay cannot resurrect a torn-down association.

- **GREEN after**: the end-to-end regression applies the retried command and verifies both GRE directions resolve to the same handle on the previously missed worker. The full `pptp_broadcast_tests_7699` module passed (5 tests), the focused end-to-end retry test passed, and the broader PPTP filter passed (68 tests).
- The adjacent CDN retry regression passed (1 test).

## Risk / residual

No live cluster was exercised. If a peer queue remains full, that worker stays unassociated while periodic retries are refused; retries stop when the queue accepts the install or a matching CDN/control-channel close cancels it. The existing worker-command queue-drop counter records refused attempts.
