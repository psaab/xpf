# #15662 — `match application-excluded` omitted from policy match schemas and unsupported-leaf gate

- **Timestamp**: 2026-10-19
- **Action**: register `application-excluded` in the two policy `match`
  schemas in `schema_security.go` (zone-pair and global) and in
  `unsupportedPolicyMatchLeaves`, so standalone and collapsed occurrences
  are rejected on strict commit and poisoned on tolerant load.
- **Files**: `pkg/config/schema_security.go`,
  `pkg/config/compiler_policy_match.go`,
  `pkg/config/compiler_policy_match_application_excluded_15662_test.go`,
  `pkg/config/schema_spelling_gate_coverage_7484_test.go`,
  `pkg/config/testdata/spelling_gate_members_7484.txt`,
  `pkg/config/README.md`, `docs/log/15662.md`.

## Red before

New tests in `compiler_policy_match_application_excluded_15662_test.go`
failed on `origin/master` (d316277cb4): flat-set/bracketed collapsed forms
(`application junos-http application-excluded`) were misdiagnosed under
#3144 as an undefined application named `application-excluded`, the
collapsed tolerant case compiled with `LenientContentDropped=false`, and
`SchemaValidate` rejected the standalone leaf as
`unknown configuration keyword "application-excluded"` under the
closed-world subtree. Hierarchical standalone forms were already rejected
under #3113 as a direct child, but flat collapsed forms escaped that taxomony.

## Change

- `schema_security.go`: add `"application-excluded": {desc: "Negate
  application match", children: nil}` to both policy `match` schemas
  (zone-pair `from-zone … policy` and `global policy`), so `SetPath`
  recognizes it as a sibling boundary and stops `application`'s
  `multi: true` value consumption, and `SchemaValidate` recognizes it.
  The issue text says "all 3 policy match schemas"; only two policy
  `match` schemas exist in this file (the other `match` blocks are NAT
  rule matches, which have no application-excluded leaf) — verified by
  grep for `"match":` / `source-address-excluded` in `pkg/config`.
- `compiler_policy_match.go`: add `"application-excluded"` to
  `unsupportedPolicyMatchLeaves`. The shared
  `policyUnsupportedMatchLeafFindings` walk then flags it both as a direct
  child and as a token collapsed onto a supported leaf's tail (#3142
  path): strict rejects under #3113 naming `application-excluded`,
  tolerant warns and `compilePolicy` poisons via the existing #5575
  `LenientContentDropped` check (no compiler change needed — `compilePolicy`
  has no `application-excluded` case and must not gain one; the leaf stays
  unenforced and therefore rejected/poisoned, never silently inverted).

## Risk

Bounded to the cited mechanism. Persisted configs carrying
`application-excluded` now warn and have that policy poisoned (snapshot
refused, previous-good retained) instead of silently compiling the
negation as a positive application match; strict commits now fail with
the correct #3113 taxonomy instead of a misleading #3144. Full
enforcement of application exclusion (typed field + dataplane negation)
remains a separate feature, consistent with the #3113 interim contract.
