# 9872 — Fabric interface with configured members but no local member gets its interface MTU planned by the wrong owner

## The defect

`planPhysDesired` (`pkg/dataplane/compiler_iface_desired.go:117`) excluded a
fabric interface from the #9761 tagged-parent MTU plan by testing
`LocalFabricMember == ""` alone. That field is derived
(`pkg/config/compiler_derivations.go:129-141`): it is set only when a chassis
cluster is configured AND a member's slot maps to this node's NodeID. The
configured membership (`FabricMembers`, from `fabric-options
member-interfaces` at `pkg/config/compiler_interfaces.go:185`) can therefore
be non-empty while `LocalFabricMember` stays empty — no cluster stanza, or
members whose slots map to the other node. The exception did not fire and the
planner wrote the interface-level `mtu` onto `fab0` itself.

Measured on base `c576960c4` (compiled strict configs):

- shape (a), no cluster stanza, members `ge-0/0/0 ge-0/0/1`:
  `plan[fab0].mtu = 1400`;
- shape (b), node-1 box, members `ge-1/0/0 ge-2/0/0` (slots 1,2 map to node
  0): `plan[fab0].mtu = 1400`.

One framing correction to the issue: in these shapes fab0's MTU is owned by
the **bond** setup, not the IPVLAN setup. The IPVLAN setup skips interfaces
without a local member (`pkg/daemon/daemon_apply_interfaces.go:54`), while
`ApplyBonds` runs for every ifc with `len(FabricMembers) > 0`
(`daemon_apply_interfaces.go:428-437`) and `routing/bond.go:134` creates the
bond (named fab0, MTU in its signature) exactly when members exist and none
is local. `daemonOwned[fab0]` is likewise set on configured membership alone
(`pkg/dataplane/compiler_iface.go:1607-1609`). The planner entry is a genuine
dual write — with the bond.

The issue's verbatim example (node 0 + slots 1,2) does NOT reproduce:
`SlotToNodeID` (`pkg/config/types.go:119-124`) falls through to 0 for every
non-7 slot, so those members derive local on a node-0 box. Pinned by
`TestFabricMembersDeriveLocalOnNode0_9872`.

## The fix

Planner only, one condition: the :117 exception now also requires
`len(ifCfg.FabricMembers) == 0`, so it follows configured membership. The
reference still resolves to fab0 itself (the bond) — see below.

Parent-review fold (GPT NEEDS-MAJOR, sustained): the planner skip alone
loses convergence on retained bonds across a normal transition. A zoned
untagged unit-0 MTU override (1300) is written onto fab0 by the dataplane
while the unit exists (`compiler_iface_desired.go:155-162`); when the unit
is removed, leaving tagged fab0.10, the bond signature is unchanged (it
carries no units, `bond.go:50-64`) so Apply takes the KEEP path — which
brought the bond up without checking MTU. With the planner now silent too,
fab0 would sit at 1300 forever (networkd stamps MTU only at creation:
.netdev at `networkd.go:761-762`, .link at `:816-817`). The handoff is
completed bond-side: `reconcileBondMTU` (`bond.go`) converges a KEPT or
ADOPTED bond's live MTU to the interface level, compare-then-write (zero
churn when converged), no-op at MTU 0, hard #4823 error on set failure
with the bond left tracked so the next reconcile retries. Within-commit
order stays deterministic: bonds reconcile (1400) before the dataplane
apply, so a live unit override still ends at its value (1300) while the
unit exists.

## Considered and rejected

- **Resolving bond-mode fab0 refs to `FabricMembers[0]`** (the issue's
  resolver half): unsafe, not implemented. In these shapes fab0 IS the bond
  device, so `fab0.10 -> fab0` is the correct resolution — the daemon agrees
  (`resolveFabricParent` falls back to fabName in legacy mode,
  `daemon_ha_fabric.go:176-185`; `ResolveFab` returns input unchanged without
  a local member, `types.go:186-188`). Resolving to the first member would
  misparent the VLAN child onto a bond slave (`mapZoneInterface`:
  `resolveInterfaceRef` at `compiler_iface.go:705` feeds
  `ensureVLANSubInterfaceFn` at `:726` -- traffic arrives on the master, so
  the zone would go silently dead), point BPF/zone-map/SNAT-egress
  (`compiler_nat.go:392-394`) at a slave that carries no addresses, and move
  the wrong MTU write from the bond to the slave rather than removing it. A
  comment at the resolver branch (`compiler_iface.go:116-120`) locks the
  bond-mode identity, and the new cells assert `fab0.10 -> fab0` while the
  planner skips. Brief posted to the issue; parent rules at review.
- **Touching the untagged path** (`compiler_iface_desired.go:134-140`):
  out of scope; the issue scopes to the #9761 tagged exception.
- **st\<N\> rows in the generated table**: noted gap, not in the required
  direction; secure-tunnel resolution has its own exception semantics.
