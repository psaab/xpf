## Fix

Callers-level, not inside `clearPendingConfirmLocked` — the helper's
`cleared` bit is the "a window was pending" contract `ConfirmCommit`
(error) and `ConfirmPendingOnDemotion` (bool) report, and an erroring
caller supersedes nothing. A helper-level fix would flip both with no
window pending.

1. `CommitWithDescription` (`store_commit.go`): after the
   `clearPendingConfirmLocked` block, when it did not fire and the flag is
   set, `resolveConfirmRemovalLocked("plain_commit_supersede")` — success
   clears the flag (record durably gone, `DeleteConfirm` tolerates an
   already-absent file), failure retains removal debt + degraded health
   and converges via the retry loop. Gated on `!cleared` so the
   timer-armed + flag-set combo (failed arm after a corrupt boot) does not
   double-drive a removal the first call already attempted.
2. `SyncApply` (`store.go`): captures `syncSupersededLostWindow` alongside
   the timer cancel and folds it into the existing #5473 ordering — defer
   via `confirmResolvePendingPersist` while the sync write is not durable,
   `resolveConfirmRemovalLocked("config_sync_remove")` once it is.
   `commitConfirmedLocked` already drains the deferred flag before arming,
   so a later arm cannot have its fresh record deleted by the deferral.
3. `persistRetryLoop` removal-heal branch (`store_persist.go`): a healed
   removal also clears the flag. Sound by the single-file argument — every
   ARM `WriteConfirm` success clears the flag (the #8565 tombstone write
   does not, but it is a no-op in the flag-set state where the record reads
   nil), so a still-set flag at heal time can only describe this same
   file — and required: the loop's debt set does not include the flag, so
   without this a healed removal exits the loop with the flag latched and
   /health stuck at 503.

Also updated: one accuracy sentence in the #8566 bullet of
`pkg/configstore/README.md` (#9887 extends the removal leg to plain

## Parent-review fold (GPT NEEDS-MAJOR + SPARK NEEDS-MINOR)

GPT BLOCKING — supersession could delete a genuinely NEWER live record: a
successful re-arm clears read-failure/arm flags but leaves removal debt
outstanding, and `confirmRemovalSupersededLocked` reports "not superseded"
on ANY read error — so a transient `ReadConfirm` failure in the retry loop
re-drove `DeleteConfirm` on the newer window's live record while its timer
REMAINED ARMED (#4577). Unreadable is not proof of not-a-fresh-arm. Fix:
the loop's removal re-drive now skips while `s.confirmTimer != nil`,
consulting in-memory liveness instead of readability alone; the debt clears
via supersession on a readable tick or via window resolution (bounded by
window expiry). All synchronous `resolveConfirmRemovalLocked` callers were
audited to run timer-dead (clearPending cancels first; SyncApply cancels
first; rollback nils first; deferred finalizes can only be pending with no
newer arm since `commitConfirmedLocked` drains before arming), so the loop
was the lone async deleter and the only site gated. Cell:
`TestRemovalRetryNeverDeletesLiveRecordOnTransientReadError_9887` (debt
predates a newer arm; transient reads race fast ticks; zero remove
attempts, live record byte-identical, debt supersede-clears on heal;
RED-verified with the gate disabled: 1 remove attempt deleting R2).
Required a new `rbReadBoundedFile` seam (`DB.ReadConfirm` only; other
`ReadBoundedFile` callers untouched) plus `restoreRollbackSeams` coverage.

SPARK-F1 — the "every production WriteConfirm success clears the flag"
comment was FALSE (tombstone writes do not clear). Safe as reasoned above,
but the comment now says "every ARM WriteConfirm success", here and in
`store_persist.go`. Also clarified the `ConfirmRecoveryReadFailed` doc: a
superseding plain commit/sync performs the clearing removal.

SPARK-F2 — pending+flag+defer drove TWO resolves in one op (direct
supersede + deferred finalize, two journals). Single-drained:
`clearConfirmResolutionPendingLocked` now reports did-work;
`CommitWithDescription` skips its direct supersede when the finalize above
already drained the same single file, and `SyncApply` consumes a stale
defer when its direct resolve ran (failure debt already owns convergence).
Cell: `TestSupersedeAndDeferSingleDrain_9887` (failing-unlink sync phase
and commit phase each attempt exactly 1 removal).
