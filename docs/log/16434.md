# #16434 — session-sync frame-auth boundary cells (exact replay, header/type MAC)

## Defect (assurance gap; production code correct at HEAD)

`authConn.verifyFrame` (`pkg/cluster/sync_auth.go`) enforces the
strictly-increasing per-connection sequence (`seq <= recvSeq` replay guard)
and MACs `header||payload||seq` (sealFrame MACs `frame||seq`,
frame = header||payload). The only frame-auth cell,
`TestSyncFrameSealVerifyRoundTripAndReplay`, replayed a strictly older
frame (seq 1 after watermark 2) and tampered only the payload. Two mutants
therefore passed the whole `pkg/cluster` suite green:

- MUT-R: `seq <= recvSeq` → `seq < recvSeq` — an exact replay of the latest
  frame (seq == watermark) verifies, so an on-path party on the
  MAC'd-not-encrypted sync link could re-inject the latest authenticated
  frame indefinitely.
- MUT-H: remove the 12-byte header from both seal and verify MACs — the
  header's type byte (byte 4) can be rewritten (e.g. SessionV4 install →
  DeleteV4) without failing the HMAC, since `handleMessage` dispatches on
  `hdr.Type` and a changed type byte has no framing side effect.

## Fix (test-only)

`pkg/cluster/sync_auth_test.go`:

- `splitSealedFrame16434` helper (splits a sealed frame the way
  receiveLoop does; the existing inline closure in the round-trip test
  delegates to it).
- `TestSyncFrameSealVerifyRoundTripAndReplay` extended: exact-replay
  assertion (re-presenting frame2 at watermark 2 must return
  `errSyncFrameReplay`) and a `header_tamper` subtest (type-byte
  install→delete XOR, magic byte, length byte each fail
  `errSyncFrameAuth` on fresh receivers, plus the explicit
  SessionV4→DeleteV4 swap and an untampered control).
- `TestSyncFrameExactReplayLatest16434` (new named cell): frames 1,2
  verify in order, watermark asserted at seq 2, exact replay of frame2
  returns `errSyncFrameReplay` and leaves the watermark unmoved. This is
  the cell that turns MUT-R red.
- `TestSyncFrameHeaderTamper16434` (new named cell): sealed SessionV4
  frame verifies untampered (control), type byte rewritten to DeleteV4
  and every other header byte flipped each return `errSyncFrameAuth` on
  fresh receivers. This is the cell that turns MUT-H red.

Fresh receivers are used for the header cells so the replay watermark
(check runs after the MAC in verifyFrame) cannot mask a MAC failure;
under the mutants the cells fail with `err == nil` exactly as the
issue's probe did.

No production code changes.

## Validation

- Targeted, HEAD: `go test ./pkg/cluster/ -run
  'TestSyncFrameSealVerifyRoundTripAndReplay|TestSyncFrameExactReplayLatest16434|TestSyncFrameHeaderTamper16434'
  -count=1 -v` — 3/3 PASS (plus the `header_tamper` subtest).
  Neighbours: `go test ./pkg/cluster/ -run 'TestSyncFrame|TestSyncAuth|TestNoise' -count=1` — pass.
- MUT-R (`seq <=` → `seq <` in verifyFrame): both exact-replay cells fail
  with `err=<nil>` ("exact replay of the latest frame (seq == watermark)
  accepted"); the header cell stays green. Production file restored and
  cmp-checked after.
- MUT-H in the issue's exact form (12-byte header omitted from both MACs,
  payload retained — seal MACs `out[syncHeaderSize:n+8]`, verify drops
  `mac.Write(header)`): `TestSyncFrameHeaderTamper16434` fails with
  "frame with rewritten message type verified: err=<nil>" and the
  round-trip `header_tamper` subtest fails on the type-byte row, while the
  payload-tamper cell stays green (proving header-specificity). A stronger
  variant dropping header+payload from both MACs also turns the header
  cells red (and, incidentally, the old payload cell). Production file
  restored and cmp-checked after each mutant.
- `gofmt` / `go vet ./pkg/cluster/` clean.

## Risk

Test-only change; no production behaviour changes. The new cells pin
existing correct behaviour, so a future seal/verify refactor that drops
the header from the MAC or relaxes the replay comparison now turns a
named cell red instead of passing silently.
