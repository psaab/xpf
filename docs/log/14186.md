# #14186 — Pre-auth SNMP `snmpServeBudget` pending-reservation starves admitted managers (D9-05)

## Verdict: NOT REAL at origin/master (7d6ac3b2b) — no production fix; regression pin added

Claim: pre-auth `allow()` pending enrollment lets many spoofed sources set
`pendingSources` so high that admitted managers are shed whenever
`globalTokens < pendingSources+1`, starving them (allegedly at ~64 pendings,
implying a ~64-token global burst).

## Why it does not hold (source, `pkg/snmp/serve_budget_9917.go`)

- Constants are `snmpServeGlobalBurst=4000`, `snmpServeGlobalRate=2000/s`,
  per-source burst 200 / rate 100 — not 64. Lockout of an admitted source
  after a refill requires `pendingSources+1 > globalTokens`, i.e.
  `pendingSources >= 4000` at the burst cap.
- `pendingSources` increments only (a) for a not-admitted, not-already-pending
  distinct source arriving while `globalTokens < 1`, and (b) for an admitted
  `everExpensive` non-expensive source arriving while `globalTokens < 1`.
  Both require a bucket in `perSource`, which is capped at
  `snmpServeMaxSources=1024` (past the cap a newcomer displaces a random
  incumbent, decrementing `pendingSources` if the victim was pending). Hence
  `pendingSources <= len(perSource) <= 1024 < 4000` invariantly; no path
  (including admitted→pending re-enrollment, displacement, or the
  `pendingSeen`-refresh in `allow`) creates a pending count without a tracked
  bucket, and every increment is paired with `bkt.pending=true` on a tracked
  bucket while every decrement/expiry/displacement mirrors it.
- Pending expires after 1s quiet (`expireExpensiveLocked`,
  `snmpServeExpensiveIdle`), swept at most once/sec; after a 2s refill the
  bucket caps at 4000 and the sweep clears stale pendings.
- The scarce gate sheds an admitted non-pending source only while
  `globalTokens < pendingSources+1`; with `pendingSources <= 1023` (plus M's
  bucket = 1024 tracked) a full refill always admits M. Under continuous
  flood the global 2000/s backstop binds everyone equally — that is the
  intended #9917 aggregate limit, not a pending-reservation starvation
  specific to admitted managers. `allow()` is indeed pre-auth at
  `agent.go:957` (before BER/community/USM in `handlePacketFrom`), but that
  only establishes the attacker can enroll pendings, not that they can lock
  out admitted sources.

## Decisive check (executed, separate base worktree at origin/master)

Fake-clock probe mirroring the issue's decisive regression check, plus
variants, run against unmodified `origin/master`:

- admit cheap M, drain global bucket, enroll 64 / 1023 / 1024 spoofed
  pendings (table fills at 1024 tracked, `pendingSources=1023`), refill 2s to
  burst: **M admitted in every variant** (`globalTokens` 4000 → 3999, stale
  pendings swept to 0), and a pending newcomer is also admitted.
- expensive-M variant (M `everExpensive`): same result.
- sustained-refresh probe (1023 pendings retrying every 500ms for 20 rounds,
  attacker refreshing `pendingSeen`): pendings are progressively admitted and
  cleared (714 admitted in round 0); M admitted in 19/20 rounds (round 0
  sheds only because the refill had not yet exceeded `pendingSources+1`,
  i.e. genuine global scarcity). No starvation.

The issue's own decisive check therefore passes on current master: it
refutes, rather than confirms, the defect. (The truncated tail of the issue
body itself concedes `pendingSources` can exceed 4000 only via
admitted→pending churn, which the bucket-count invariant above bounds by
1024.)

## Change in this PR

No production change — there is no defect mechanism to remove, and altering
the reservation would risk the #10113 onboarding guarantee
(`TestServeBudgetFairShareSplitsGlobalHalf10113`,
`TestServeBudgetFairSharePendingExpiry10113`). Added
`pkg/snmp/serve_budget_14186_test.go`:
`TestServeBudgetPendingReservationNoStarve14186` pins the decisive scenario
(full-table 1023 pendings + refill) and asserts the
`pendingSources+1 <= snmpServeGlobalBurst` bound, so a future change to the
global burst, table size, or pending accounting that makes the claimed
lockout reachable fails loudly. The test passes on unmodified master by
design (it is a refutation pin, not a RED→GREEN fix test).
