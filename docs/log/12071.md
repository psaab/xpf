# #12071 — keep QNH metric actions daemon-scoped

- **Timestamp**: 2026-10-09 (stacked on #12067 / `faaa1adc8`)
- **Action**: keep shared QNH route-maps metric-free; install a verified
  metric overlay only in `ospfd`; reconcile legacy metric actions after a
  successful load; do not install a RIP overlay on FRR 10.7.

## Why

Shared FRR route-map definitions are copied to multiple daemons. If a daemon
discards a QNH destination or next-hop match but retains `set metric`, it can
apply a backup cost to routes the complete QNH predicate did not select.
Experiments on FRR 10.7.1 found that `vtysh -d ripd -f` exits successfully but
does not apply the RIP overlay, while integrated `vtysh -f` broadcasts metric
actions into other daemons. The available scoping primitives and call /
on-match indirection did not confine the action. The safe contract is therefore
OSPF support with an explicit RIP limitation.

## What

- The integrated config contains the shared QNH destination/next-hop matches
  and `on-match next`, but no generated QNH `set metric`. After reload, only
  `ospfd` receives a daemon-scoped metric overlay. Exact route-map readback
  verifies its configured metric.
- RIP receives no overlay, scrub, or readback; its redistribution uses the
  default metric. Commit warns when QNH metric configuration would export to
  RIP. Restoring RIP backup-cost export when a safe transport exists is tracked
  by [#12531](https://github.com/psaab/xpf/issues/12531).
- **F1 — legacy cleanup:** old generated metric-bearing QNH sequences, including
  IPv6 sequences, are identified by route-map and sequence. After a successful
  reload, the manager removes the metric from still-configured sequences and
  removes stale sequences, then verifies all reachable daemon copies. Legacy
  broadcast sequences are cleared even if OSPFD still targets the same
  sequence.
- **F2 — reload ordering:** cleanup is post-load only. A failed primary load
  does not trigger a pre-clear; FRR's load path is not transactional, so a
  failed load may still have partial FRR-side effects. A successful additive
  fallback or retry is followed by reconciliation before OSPFD overlay
  installation.
- **F-C — route-map-recipient census:** readback checks the 17 FRR daemons
  that can hold route-map copies (`zebra`, `mgmtd`, `staticd`, `ospfd`,
  `ospf6d`, `ripd`, `isisd`, `bgpd`, `ripngd`, `eigrpd`, `fabricd`, `pimd`,
  `pim6d`, `babeld`, `pbrd`, `vrrpd`, and `bfdd`) — not a literal inventory
  of every FRR 10.7 daemon (`ldpd`, `nhrpd`, `sharpd`, `pathd`, `watchfrr`
  exist but are not VTYSH_RMAP route-map recipients). Only explicit `failed
  to connect to any daemons` errors are skipped; other readback failures
  remain hard errors.
- Authored policy `then metric` actions remain in the integrated configuration;
  they are not copied into QNH overlays or cleanup identities and can still
  override the QNH metric. Overlays are memory-only and are replayed after
  Apply, so a restart starts with the metric-free integrated config.

## Risk / residual

RIP backup-cost export from QNH metrics is unavailable on FRR 10.7 and uses
the default RIP metric until a safe per-daemon transport exists (#12531).
OSPF remains supported. FRR loads are not transactional; the manager does not
pre-clear before a hard failure, but FRR itself may have partially applied a
failed load. Overlay state is memory-only and returns to the metric-free
integrated config on daemon restart until the next Apply.
