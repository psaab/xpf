# Issue #15160 — chunk DHCP lease full-sets below the sync frame cap (B03-01)

- **Issue:** `queueDHCPLeaseSnapshot` wrote the entire Kea lease set as one
  session-sync frame with no size check. A set over `maxSyncPayload`
  (16 MiB — roughly 165k ordinary v4 leases; `pkg/dhcpserver` has no
  lease-count cap and the Kea read bound is 64 MiB) makes the receiver's
  `hdr.Length > maxSyncPayload` arm return from `receiveLoop`, tearing
  down the HA connection that also carries sessions, IPsec SAs and
  config, and the forced re-push on reconnect repeats the cycle forever.
  DHCP lease protection for takeover silently stops. Residual of
  #14607/Y15-01, whose fix (9e58892fba) chunked only the persistent-NAT
  encoder.
- **What:**
  - `pkg/cluster/sync.go`: two additive message types
    `syncMsgDHCPLeaseV4Chunk = 45` / `syncMsgDHCPLeaseV6Chunk = 46` (44 is
    `syncMsgAuthConfirm`; no wire-version bump — a pre-#15160 peer ignores
    the unknown types, per the #14607 precedent).
    `queueDHCPLeaseSnapshot` keeps the exact legacy single-frame shape
    when the encoded set (authority trailer + full-set trailer included)
    fits the cap; over cap it draws a chunk generation, splits the lease
    records via `encodeDHCPLeaseChunkFrames`, stamps each chunk with its
    own increasing full-set seq under `writeMu`, and refuses
    (defense-in-depth) any frame that would exceed `maxSyncPayload`.
  - `pkg/cluster/sync_dhcp_chunk_15160.go` (new): chunk envelope
    `{generation u64, index u32, total u32, totalLeases u32}` + standard
    count-prefixed lease body; budget
    `dhcpChunkFrameBudget = maxSyncPayload - header - seq trailer - 4096`
    (authority-trailer allowance); per-family receiver assembly state
    keyed by `(incarnation, generation)` — inconsistent totals or a
    duplicate index invalidate the generation, and the table is bounded.
    A lease whose single record fits no frame is dropped and counted via
    `MalformedRecordsDropped`, never emitted over-cap.
  - `pkg/cluster/sync_conn_read.go`: new chunk arms admit chunks in seq
    order through the existing per-family `fullSetSeqGuard`, reuse the
    legacy arms' decode + semantic/identity filters, and commit the
    concatenated set atomically (held-set store + high-water advance +
    callback under `dhcpApplyMu`) only when the last chunk lands; the
    #10170 authority trailer rides the last chunk and is validated before
    commit. An unclosed generation never commits (the #7175 posture); a
    committed legacy set discards pending assemblies. The legacy DHCP,
    session, IPsec and persistent-NAT paths are unchanged.
  - `pkg/cluster/sync_capabilities_6650_test.go`: chunk types added to
    the live message census (the #7163 completeness scan requires it).
  - NOT changed: `writeMsg`/receive cap, the legacy wire shape for
    in-cap sets, wire/HA protocol versions, the daemon push loop, or Kea
    lease handling.

## Risk

- A mixed-version pair loses only over-cap lease pushes (old receiver
  ignores the unknown chunk types) instead of losing the whole sync
  connection; in-cap sets are byte-identical to before. No lab verify is
  required for the wire change itself; a live two-node over-cap lease
  population remains an operator-scale check.
