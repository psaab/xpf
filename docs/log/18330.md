# #18330 — Factory-reset commit guard dereferenced nil configstore before rejecting

- **Timestamp**: 2026-10-28T08:56:09Z
- **Action**: Kept the factory-reset rejection ahead of the #16719 rollback-discard generation sample in both plain and commit-confirmed apply paths. Retained the post-`applySem` reset check and the pre-`applySem` discard sample.
- **File(s)**: `pkg/daemon/daemon_apply_commit.go`, `pkg/daemon/factory_reset_5281_test.go`, `docs/log/18330.md`
- **Validation**: See below.
- **Risk**: See below.

## Root cause and fixture disposition

On pristine `origin/master` (`416e0288d0c4dc5a121e190234c9832477ee8fd4`), the named cell reproduced the reported panic:

```text
go test ./pkg/daemon/ -run TestFactoryResetGatesAndEntersResetGeneration -count=1
```

It failed at `pkg/daemon/daemon_apply_commit.go:262` while `commitAndApply` called `d.store.RollbackDiscardGen()`, which dereferenced the nil receiver at `pkg/configstore/commit_authority.go:268`.

The test fixture is intentional, not a test defect: it creates a bare `Daemon` with an `applySem` and no `store`, successfully runs a factory reset, then asserts that config writers in the terminal reset generation return `errDaemonResetting` before touching persistent state. `factoryReset` itself explicitly supports nil-store test daemons. The #16719 token sample was newly placed before the existing under-semaphore #5281 reset guard, so it bypassed that expected rejection and panicked. The test assertion and fixture were not weakened or replaced.

## Change

Both `commitAndApply` and `commitConfirmedAndApply` now check the lock-free terminal reset flag before calling `RollbackDiscardGen`. Their existing under-`applySem` checks remain to catch a reset that begins after the early check. The rollback-discard token remains sampled before acquiring `applySem`, and `commitWithGenBinding` still checks `PromotionStale` before examining or promoting a candidate; the #16719 fence for real stores is unchanged.

The existing `TestFactoryResetGatesAndEntersResetGeneration` assertions already pin the expected `errDaemonResetting` from both commit paths. Its comment now explains why the bare daemon is intentional and why reset rejection must precede the token sample.

## Validation

- RED on pristine base: `go test ./pkg/daemon/ -run TestFactoryResetGatesAndEntersResetGeneration -count=1` — reproduced nil-pointer panic in `RollbackDiscardGen` from `commitAndApply`.
- GREEN: `go test ./pkg/daemon/ -run TestFactoryReset -count=1` — `ok github.com/psaab/xpf/pkg/daemon 2.852s` (includes the named regression cell and the related factory-reset tests).

## Risk

The early check reads only the existing atomic reset flag and does not move or weaken the rollback-discard sample or its promotion-time stale check. A commit racing a reset still reaches the existing under-semaphore guard; a call made in the terminal reset generation returns before the store access. Store-backed commit behavior outside reset is unchanged.
