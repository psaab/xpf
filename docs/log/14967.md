# Issue #14967 — Address-book duplicate, group precedence, and trailing-token handling fail explicit (D30-01)

## Why

A Junos address names exactly one prefix, but the compiler folded every
definition of a name into a single `Address` with an order-dependent
winner and no diagnostic:

- Repeated `address A <p1>; address A <p2>;` definitions (same block,
  repeated `global` containers, two braced containers, or two bare
  children in one container) compiled to the LAST prefix; the first was
  silently dropped.
- Zone-local duplicates folded the same way into the qualified global
  entry.
- `apply-groups` precedence (#14424) covered single-group-vs-inline, but
  two groups defining `A` with distinct prefixes resolved
  first-group-wins, an inline container carrying two bare prefixes kept
  the last beside a group value, and a trailing token riding a DROPPED
  group definition (or a dropped group prefix in a leaf group beside a
  clean inline container) vanished without reaching the #3332
  trailing-token gate.
- On the tolerant path the surviving prefix was fully enforceable:
  `Address.UsableValue()` ignored trailing-token taint, and the #3149
  strict mirror (`policyMatchAddressBookResolves`) read raw `Value`, so
  commit and runtime resolvers could disagree.

Measured on `origin/master b8f1ff7ac9` with a probe harness (strict
`CompileConfig` / lenient `CompileConfigForNodeLenient`): every duplicate
shape above committed cleanly to one surviving prefix; group-trailing
cells committed cleanly; lenient policy resolution accepted the tainted
entry.

## What

- `pkg/config/compiler_security_addressbook.go`: `setAddressPrefix14967`
  records every distinct prefix in authoring order (identical repeats
  collapse); `mergeAddressNode` routes every prefix slot (leaf,
  packed-description, description-child, bare child) through it and
  records extra keys on a bare prefix child as trailing tokens. The
  zone-local fold now carries `TrailingTokens` and `DuplicatePrefixes`
  into the qualified global entry (previously only `Value` /
  `Description` / `UnimplementedForms`).
- `pkg/config/types_security.go`: new `Address.DuplicatePrefixes`
  compiler metadata (`json:"-"`); `UsableValue()` returns `""` for
  duplicate- and trailing-token-tainted entries as well as
  unimplemented-form ones.
- `pkg/config/compiler_validate_strict_addrbook.go`:
  `validateAddressBookDuplicatePrefixStrict` rejects a duplicate entry
  at commit, naming entry, book, and prefixes.
- `pkg/config/compiler_earlystrict.go` + `compiler_opts.go`: the gate
  runs on the pristine books before the zone-local fold; tolerant
  load / peer-sync downgrades to a warning
  (`lenientAddressBookDuplicatePrefix`, #1960 no-brick).
- `pkg/config/group_merge_address_book_14424.go` +
  `pkg/config/ast_groups.go`: the #14424 merge records distinct
  group-vs-inline / group-vs-group prefixes, repeated bare prefixes on
  either side, and trailing tokens on either side through an inert
  `__xpf_duplicate_address_14967__` marker child consumed by
  `mergeAddressNode`; a second group container with a same-name peer is
  routed through the same conflict recording instead of adopting beside
  the first group's entry.
- `pkg/config/compiler_validate_strict_policy.go`:
  `policyMatchAddressBookResolves` reads `UsableValue()`, aligning the
  #3149 mirror with the runtime resolver.
- Regression `pkg/config/address_book_duplicate_prefix_14967_test.go`:
  nine strict-reject cells (global/zone-local/group shapes + dropped
  trailing), tolerant boot + warning + usable-refusal per cell, policy /
  address-set fail-closed on the tolerant path, and green controls
  (identical repeat, prefix/description split in both orders, disjoint
  group description union, group/inline prefix agreement).
  `pkg/dataplane/userspace/address_duplicate_tolerant_14967_test.go`
  additionally pins the tolerant snapshot path: neither authored prefix
  is published and the referencing deny carries the
  `__unsupported_address__` sentinel, with a clean-entry control.
- `TestDuplicateNameStillLastWins7524` updated: the pre-#14967 last-wins
  control is superseded by explicit rejection (identical repeats still
  collapse, covered by the new controls).
- `pkg/config/README.md`: new “An address takes exactly one prefix”
  section beside the #9524 entry.

Scope cuts: `address-set` union semantics unchanged (sets legitimately
union members). Flat-set handling measured: re-`set` with a distinct
prefix produces two leaf nodes and now rejects as a duplicate;
re-`set` with the identical prefix collapses and commits. No
wire/persisted format change (`DuplicatePrefixes` is `json:"-`
metadata; the group marker never leaves the expanded tree).

## Validation

- RED on base `b8f1ff7ac9` (probe, pre-fix): all duplicate shapes
  committed to a surviving prefix (e.g. global same-block
  `A="10.0.0.2/32"`, two groups `A="10.3.0.1/32"`, dropped-trailing
  group cells clean); lenient `policyMatchAddressBookResolves` accepted.
- GREEN after the fix (same probe): strict rejects with
  `has duplicate prefixes "10.0.0.1/32, 10.0.0.2/32"` (zone-local named
  against the clean zone); dropped-trailing cells reject; tolerant path
  boots with the duplicate/trailing warning and `UsableValue()==""`;
  controls (identical repeat, description splits, disjoint union) stay
  clean and usable.
- New regression + neighbours (`TestAddressBookDuplicate*`,
  `TestDuplicateNameStillLastWins*`, `TestRepeatedAddressBook*`,
  `TestAddressBookSameName*`, `TestSchema3332*`) and the full
  `pkg/config` suite: see PR.

## Risk

- Behaviour delta (intended): a config that today commits with two
  distinct prefixes for one address name, or with a group definition
  losing silently to an inline one, now fails commit with a naming
  diagnostic; already-persisted such configs still boot on the tolerant
  path but the entry resolves to no usable address (policies referencing
  it fail closed via the existing `__unsupported_address__` path).
  Identical repeats and disjoint prefix/description merges are
  unchanged.
- Residual: a group-vs-inline pair whose prefixes AGREE but where the
  group side alone carries trailing tokens beside a same-prefix inline
  container is recorded (marker exemplar) and rejected as trailing —
  deliberate fail-explicit, matching the #3332 strict posture for a
  directly authored trailing token.
