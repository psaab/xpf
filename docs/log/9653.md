# #9653: bound the ClockSync peer clock and apply the offset per connection

Branch `fix/9653-clocksync-offset-bound`, from origin/master `125e23931`.

- **Timestamp**: 07:03
- **Action**: Read the issue and the code. `syncMsgClockSync` stores `monotonicSeconds() - peerMono` in `SessionSync.peerClockOffset` with no check. The two install arms (`syncMsgSessionV4`/`V6`) rebase `Created`/`LastSeen` through `rebaseTimestamp`, which clamps a negative result to 0. The offset is global and in seconds. The only other readers are `clockSynced` (set here, cleared on a full disconnect, read nowhere else).
- **File(s)**: none

- **Timestamp**: 07:08
- **Action**: Design, in three parts.
  - **What a bound can do.** It can only refuse readings no running peer can send: 0 (a daemon is not running in the first second of its boot) and anything above a century. A false reading inside the window has the same effect as `2^63-1` (a decade of claimed uptime still clamps every stamp to 0). So the bound meets the acceptance but does not protect the real peer's sessions by itself.
  - **What does protect them.** The offset belongs to the connection that carried it. Each `authConn` keeps the offset its own ClockSync set, and each install rebases with its carrying connection's offset. One frame on any connection then no longer rewrites the sessions another connection carries.
  - **Not done.** I am not refusing ClockSync on an unauthenticated connection when a key is configured, which the issue lists as a "consider". During a key rollout the peer's connection stays unauthenticated until the in-place upgrade, and ClockSync is sent once per connection. So the offset would stay unset, and synced sessions would age by the uptime difference between the nodes. `strict-session-auth` already controls the unauthenticated reach.
