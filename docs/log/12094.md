# Issue #12094 — include enforced wildcard zone-pair stanzas in filtered policy views

## Why

Filtered `show security policies` views compared configured zone-pair names to the requested pair by exact string equality. That hid `any -> zone`, `zone -> any`, and `any -> any` stanzas even though the runtime evaluates them for the selected pair before globals. This made the displayed hit counts and policy inventory incomplete.

## What

Added `NewZonePairPolicyFilter` and `ZonePairPolicyAppliesToFilterPair` as the shared prepared selector and applicability predicate, plus the exact/single-wildcard/both-wildcard tier classifier. The gRPC hit-count/detail, local hit-count/detail/brief/standard, and remote filtered views include applicable wildcard stanzas in runtime order with stable counter IDs and detail Index values.
Transit wildcard expansion is limited to defined, non-quarantined concrete zone filters. Explicit literal `any` filters use literal zone-name matching: no expansion, with authored literal stanzas shown. The host-bound view excludes transit `to-zone any` and `any -> any`, retaining exact host pairs and the runtime `any -> junos-host` exception for unknown ingress. Quarantined filters retain exact authored pairs without expanding transit wildcard tiers.
Global selection remains governed by the scoped-global predicate and appears after zone-pair tiers. The unscoped-global host-view mismatch and remote brief filter omission are tracked in follow-ups #12523 and #12524. The CLI reference documents the filtered-view behavior.
