# Issue #15060 — RG interface sets hold only base RETH names

## Why

The HA interface sets behind two mechanisms held only base RETH names:

- `haRoutingRequirementsForRG` (#11377 readiness gate) built its set from
  `addHAInterfaceName(ifc.Name)` — `reth0`, `ge-0-0-2`, never any unit.
- `newFRRHADemotionState` (#11415 FRR filter) built `rethInterfaces[rg]`
  the same way from `RethRGOwners()` base names.

A VLAN-tagged unit ref `reth0.80` resolves to `ge-0-0-2.80` (member plus
unit `vlan-id`), which matched neither set. In the #11415 filter,
`inactiveInterface` then fell through to `!globalActive` (RG0): after a
data-RG-only failover with RG0 left on the peer, the new RG owner withdrew
OSPF/OSPFv3/RIP/IS-IS from every VLAN-tagged unit of that RG (and kept
them when it should not, in the inverse split). In the #11377 gate the
unit was invisible, so no routing requirement was ever generated for it.

## What

- `pkg/daemon/daemon_ha_routing_readiness.go`: new
  `addHAInterfaceUnitNames` registers every authored unit ref
  (`name.<unit>`) of an RG interface in the same set as the base name,
  including each unit's canonical resolution (`reth0.80` → `ge-0-0-2.80`
  for `vlan-id 80`). `haRoutingRequirementsForRG` calls it per interface.
- `pkg/daemon/daemon_frr_rg_shutdown_11415.go`: `newFRRHADemotionState`
  expands each owner's units into `rethInterfaces[rg]` the same way, so
  `inactiveInterface("reth0.80", …)` is decided by the owning RG, not RG0.

Nothing else changed: BGP neighbour attribution already walks unit
addresses (`bgpNeighborsForRG` / `globalBGPNeighborGroups`), unit-0 refs
resolved through the base-name forms already, and non-RETH interfaces are
untouched.

## Validation

- RED on `origin/master` (f9d6d28ba4) with only the new test file present:
  `TestVLANUnitFollowsOwningRGNotRG015060` failed — RG1 secondary / RG0
  primary kept `reth0.80` in OSPF, OSPFv3, RIP and IS-IS, and
  `inactiveInterface(reth0.80)` returned false; the inverse split
  (RG1 primary / RG0 secondary) wrongly marked it inactive.
  `TestHARoutingRequirementsIncludeVLANUnit15060` failed — RG1
  requirements contained only `ge-0-0-2` (from `reth0.0`), no OSPFv3/RIP/
  IS-IS requirement and no `ge-0-0-2.80` netdev.
- GREEN after the fix: both new tests pass; the strict probe keeps
  `reth0.80` if and only if RG1 is active, independent of RG0.
- Neighbouring controls green:
  `TestDemotedPrimaryWithdrawsDynamicRouting11415`,
  `TestDemotedPrimaryWithdrawsRoutingInstancePeer11415`,
  `TestClusterDemotionReconcilesFRR11415`,
  `TestHARoutingRequirementsAreScopedToRGAndInstanceTable`
  (unit-0 and BGP behaviour unchanged).

## Risk

Bounded to the two RG-set builders. Interfaces with no units, non-RETH
interfaces, and BGP local-address attribution are unaffected. The unit
expansion trusts the authored unit set of the owning interface, which is
the same structure `ResolveKernelIfName` resolves against.
