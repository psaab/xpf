# Answer the UDP probe echo from the receiving address (#19022)

- **Issue**: #19022. Loss H1 Group 1c (the #18679 UDP continuity probe)
  was VOID on every run. On loss, the Group 1b raw session-miss floor
  failed in both arms after the target was reprovisioned.
- **Cause**: `test/incus/mouse-target-echo.py` bound its UDP socket to
  0.0.0.0 and replied with a plain `sendto()`, so the kernel chose the
  route's preferred source. `loss:xpf-mouse-target` holds .201 (primary)
  and .202 (`IPERF_TARGET4`), so a probe to .202 was answered from .201.
  Target capture (parent, 22:34 UTC):
  `172.16.80.8.36216 > 172.16.80.202.6201` then
  `172.16.80.201.6201 > 172.16.80.8.36216`. That reply matched no
  firewall session. The probe's connected socket would have discarded it
  anyway. Each such reply was one `Session misses` on the RG owner.
  tcp/udp were spared, but NOT because they hold one address. udp
  also holds DHCP 172.16.80.130, and all three hold several global v6
  addresses. They were spared because their target address IS the
  connected route's source (`172.16.80.0/24 ... src 172.16.80.210` /
  `src .211`). On loss that source is .201 while harnesses target .202
  (`ip route get 172.16.80.8` -> `src 172.16.80.201`). The 79feab294c
  log and the first issue comment said "one address each"; R12 F4
  corrected it.
- **Second defect, same script**: on tcp/udp, `mouse-target-setup.sh up`
  installed `mouse-iperf3@5200-5211`, although socket-activated
  `iperf3@52xx.socket` units already serve those ports. All 12 units
  crash-looped and were disabled and reset by hand (issue comments,
  19:56 and 21:35 UTC).
