# #15005 — policer / three-color-policer same-name collision (A09-01)

## Why

A name defined as both `firewall policer P` and
`firewall three-color-policer P` committed cleanly. The two definitions
live in separate compiled maps (`Firewall.Policers` /
`Firewall.ThreeColorPolicers`) but share one operator-visible namespace:
`buildPolicerSnapshots` / `buildThreeColorPolicerSnapshots`
(`pkg/dataplane/userspace/filters.go`) ship both under the bare name `P`,
and the userspace filter compiler loads three-color templates first
(`load_three_color_policer_templates`, then
`lower_single_rate_policer_templates` skips a single-rate policer whose
name already exists, `userspace-dp/src/filter/compiler.rs`). A filter
term's `then policer P` therefore silently enforced the three-color
meter instead of the single-rate rate limit the operator authored — the
configured limit was replaced with no diagnostic. xpf has no
`then three-color-policer` spelling that could disambiguate the
reference.

## What

- New `validateFirewallPolicerNameCollisionStrict` in
  `pkg/config/compiler_validate_strict_filter.go`: rejects (sorted,
  deterministic first error) any name present in both policer maps,
  naming both definitions (`firewall policer P` and
  `firewall three-color-policer P`) and the silent three-color
  precedence consequence.
- Wired in `runUniformGatesFirewallNAT2`
  (`pkg/config/compiler_uniformgates_firewall_nat2.go`) immediately after
  the `then policer` reference gate, on the fully-compiled `*Config` so
  both maps are populated regardless of authoring order.
- New `opts.lenientPolicerNameCollision` (`pkg/config/compiler_opts.go`,
  set by `lenientCompileOpts`): tolerant load / peer-sync downgrades the
  reject to a `cfg.Warnings` entry (#1960 no-brick). Both definitions
  survive on that path and the dataplane keeps its pre-gate three-color
  precedence — now visible instead of silent. Strict commit /
  commit-check stays hard-reject.
- Regression: `pkg/config/policer_name_collision_15005_test.go` —
  flat-set and hierarchical strict rejects, lenient warning + both
  definitions retained, and controls (single-rate only, three-color
  only, distinct names in the two namespaces all commit cleanly).
- NOT changed: the Rust precedence itself, the eBPF policer-ID leg, or
  either snapshot builder. The collision is now unrepresentable on the
  strict path that feeds them, and the tolerant path deliberately
  preserves prior dataplane behaviour.

## RED -> GREEN proof

- RED on `origin/master` (11e114643b): `go test ./pkg/config/ -run
  'TestPolicerNameCollision15005' -count=1` failed — strict flat-set and
  hierarchical compiles accepted the collision and the lenient compile
  recorded no warning (`warnings = []`); the three control tests passed.
- GREEN after the fix: the same focused run passes, together with the
  adjacent policer gates (`TestPolicerRef*`, three-color policer tests).

## Validation

- `go test ./pkg/config/ -run 'TestPolicerNameCollision15005|TestPolicerRef|TestThreeColorPolicer' -count=1` — ok.
- `go test ./pkg/config/ -run 'Policer|ThreeColor|8445|9882|14443' -count=1` — ok; `go vet ./pkg/config/` clean.
- `go test ./pkg/configstore/ -run 'Policer' -count=1` — only
  `TestPolicerThenNonLeafTail_9882` fails, identically on pristine
  `origin/master` (pre-existing, unrelated to this change).
- Full `go test ./pkg/config/ -count=1 -timeout 25m` exceeded the 25m
  timeout in the long spelling-differential gates on this loaded host
  (no 15005-related failure observed before the timeout); the focused
  and adjacent policer suites above are the exercised evidence.

## Risk

- A Junos-migrated config that deliberately reused one name across both
  namespaces now fails commit until one definition is renamed — that is
  the intended behaviour change, since its `then policer` references
  were silently enforcing the three-color meter. Lenient load / HA
  peer-sync of an already-committed such config still boots with a
  warning, so no deployed node is bricked by upgrade.
