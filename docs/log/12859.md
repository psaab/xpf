# Issue #12859 — first-policy ICMP ancestry rematch

Status: implemented and validated; focused regression module and binary build pass. Full package suite has one unrelated performance-threshold failure; details below.

## Scope and source

- Tracking issue: https://github.com/psaab/xpf/issues/12859 (research D5-03, Medium).
- Worktree: `/home/ps/git/pi-xpf/wt-12859`, branch `fix/12859-icmp-rematch-first-policy`, base `70b55328a1ac2937139b982d83f39df01d23a717`.
- The rematch is a commit-time, frame-independent ancestry check. Its session key has no ICMP type/code, so `packet_icmp = None` cannot establish equivalence with packet-scoped ICMP evaluation.

## Change and evidence

- In `userspace-dp/src/afxdp/worker/loop_body/mod.rs`, the first-policy rematch now declines *only after* the ancestry descriptor, source-zone legs, destination-zone legs, and destination rule are validated when the new policy has any ICMP type-constrained term (permit or deny). This avoids treating an unknowable type-specific decision as a broad-permit rebind or an unjustified purge. Missing/ambiguous/invalid ancestry still follows the existing fail-closed purge path.
- For other traffic, the rematch calls `evaluate_policy_result_without_counting_at` and passes the worker's captured `now_ns`, instead of sampling scheduler time in the convenience wrapper.
- Regressions in `first_policy_purge_rotation_9526_tests.rs` cover type-constrained permit retention without rebind, a type-constrained DENY followed by an unconstrained ICMP permit (no blind rebind), unconstrained ICMP permit rebind, and purge when ancestry is absent despite type-constrained rules.
- The deny-then-permit fixture uses `junos-icmp-all` as its broad successor, so type-blind evaluation with `packet_icmp = None` skips the type-constrained DENY and can actually match the successor. With the decline disabled, the mutant test failed because the pair rebound to `lan->wan/p-icmp-all` instead of remaining bound to `lan->wan/p-first`.

The failing test and `session_glue` source compare unchanged to base SHA `70b55328a1ac2937139b982d83f39df01d23a717`; the changed implementation is in the worker-loop rematch. The test was not rerun on base, so this runtime result alone does not establish whether the timing threshold also fails there.
- `cargo build --bin xpf-userspace-dp`: passed with existing warnings.
- `cargo fmt --check` does not pass repository-wide: rustfmt reports numerous existing diffs across unrelated files. Changed-file rustfmt inspection likewise encounters pre-existing formatting drift in surrounding portions of the test module and let-chain parser errors when run without the crate's edition; no formatting change was applied to unrelated code. ## Risk and boundaries

The rematch remains deliberately conservative where a type-specific ICMP verdict cannot be reconstructed. Packet-scoped session-hit policy enforcement still receives the actual ICMP type/code. The decline does not make invalid/missing ancestry retain a session, and non-ICMP/unconstrained rematches continue through the existing policy evaluator.
