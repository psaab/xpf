# Issue #17264 — publish the daemon gRPC server atomically

- **Issue:** #17264 — the fabric-listener startup poll races the daemon's gRPC-server publication and silently expires after 30 seconds.
- **Branch:** `fix/17264-grpc-publish`
- **Worktree:** `/var/worktrees/campaign-drive/wt-17264`
- **Base:** `bb7ec6adff`
- **Timestamp:** 2026-11-06

## Why

`startGRPCServer` published `d.grpcSrv` through a plain pointer while the HA comms goroutine polled it without synchronization. The poll also ignored the comms context and stopped after 30 seconds, so it could both race and miss a delayed server publication.

## What

- Replace the plain server reference with `atomic.Pointer[grpcapi.Server]` and a lazily initialized ready channel. Publication stores the server before closing readiness once; nil publication is a no-op. Readers use one atomic load per call.
- Replace the fixed sleep poll with `awaitGRPCSrv(commsCtx)`, retaining the IPv6-safe `net.JoinHostPort` logic, dual-fabric child goroutine and per-attempt VRF resolver.
- Migrate existing production and test accesses. Remove the stale #12168 comment that claimed the poller race remained.
- Add race, wake-on-publication, cancellation, nil-publication and delayed-publication listener cells. The listener cells run in the testguard network namespace and bring loopback up before binding/dialing.

## Risk

The listener waiter remains parked until its comms context is cancelled if the gRPC server is never published; the epoch owns that context and no constructor wait group joins the listener goroutine. The ready channel is lazily created for zero-value `Daemon` fixtures, and closing it follows the atomic store.
