## Timeout and census proof

The timeout diagnostic captured the subject session at the witness, before the idle wait, and after the 15-second idle wait. The observed sequence was `Timeout: 20` on the initial witness display, then `Timeout: 10` both before and after the idle wait. The subject helper log contained only:

```
CONNECTED host=172.16.80.201 port=55121
```

The completed raw-wire capture observed `exp_leaked=0`: the expired tuple was dropped. The CLI census still reported the subject row after the idle wait because expiration is packet-triggered/lazy on this path. The pre-fix gate sampled that census before sending the raw probes and treated the retained row as `stale_present=1`, even though the raw probe itself was the expiry trigger and the wire evidence proved no stale forwarding.

## Hermetic RED → GREEN

Before the fix, the same evidence fed directly into the verdict function produced a false RED:

```
WIRE_GATE wire_conntrack_lifecycle FAIL reason=-- created=1 witnessed=1 evicted=0 stale_present=1 exp_offered=1000 exp_leaked=0 fresh_offered=1000 fresh_leaked=0 syn_offered=1500 syn_observed=1500 ctrl_sess=1 lifecycle_bad=1 cksum_bad=0
```

The fixed gate derives `stale_present` only after the capture/probes complete and uses completed expired-tuple wire leakage as the stale-forwarding evidence. A retained CLI census alone is not sufficient because the census is lazily refreshed. The equivalent hermetic verdict is now GREEN:

```
WIRE_GATE wire_conntrack_lifecycle PASS reason=-- created=1 witnessed=1 evicted=1 stale_present=0 exp_offered=1000 exp_leaked=0 fresh_offered=1000 fresh_leaked=0 syn_offered=1500 syn_observed=1500 ctrl_sess=1 lifecycle_bad=0 cksum_bad=0
```

The gate selftest covers both sides of the rule: a dropped expired tuple is not stale even if the census would retain an idle row, while an expired-tuple leak remains stale.
