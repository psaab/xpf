# #15145 — preserve incumbents when a synced re-decision is refused caller-side

- **Timestamp**: 2026-10-19
- **Action**: Ask peer/static ownership before reserving a synced
  re-decision, and restore the incumbent when the post-reserve recheck
  refuses anyway.
- **File(s)**: `userspace-dp/src/nat/source/synced.rs`,
  `userspace-dp/src/nat/allocator.rs`, `userspace-dp/src/nat64.rs`,
  `userspace-dp/src/nat/tests_pool_overlap_8115.rs`,
  `userspace-dp/src/afxdp/tests_nat64_overlap_8115.rs`.

## Caller-side residual of #13691

#13691 ordered every refusal *inside* `PortAllocator` before the
stale-incumbent teardown, so an in-allocator refusal (occupied bit, lease
mismatch, capacity) leaves the flow's incumbent reservation intact. The
peer/static ownership refusal (#8115 R2 / #14368, and #9021 on the NAT64
twin) lived one layer up, in `reserve_synced_on_first_pool_owner` and
`reserve_synced_nat64_port_unless_peer_owns`, and ran *after* the reserve:

1. `reserve_flow_maybe_persistent` / `reserve_address_only_maybe_persistent`
   (or the NAT64 reserve) evicts the same flow's incumbent — freeing its
   port bit or address-only token and completing its persistent lease —
   and installs the replacement tuple.
2. Only then does the caller ask `peer_owns_wire_identity` /
   `static_owns_wire_identity`; on refusal it calls `rollback_flow`, which
   removes only the *replacement*.

The still-live flow was left with no reservation at all, reopening
#13691's duplicate-identity/reissue hazard on an HA standby: the incumbent
tuple could be re-issued to a new local flow while the synced session
still forwards on it. Reachable only where strict commit is bypassed
(lenient load / SyncApply) with a cross-pool or static overlap — the same
population #8115/#14368 already bound.

`session_import.rs` returns `RejectedReserve` on this refusal with no
snapshot restore, so the allocator/caller ordering is the only place the
incumbent can survive.

## Fix

- **Pre-reserve ownership check** (the fix direction's first half): both
  synced SNAT arms and the synced NAT64 helper now evaluate the same
  peer/static predicates against the wire-named tuple *before* calling
  the reserve, under the same PASS-1 (`stop_at_first_owner`) gate as the
  existing post-reserve check. A pre-check refusal returns
  `Refused`/`false` without touching the allocator, so the incumbent is
  never evicted. PASS 2 is unchanged, preserving the #6979 F1
  fall-through contract.
- **Post-reserve recheck + incumbent restore** (the second half): the
  existing post-reserve checks stay for races (a peer mint landing
  between the pre-check and the reserve). On that path the SNAT arms now
  also restore the incumbent: `SourceNatReservationSnapshot` captures the
  complete incumbent allocation (record, addr_index, mode flags) under
  the same live guard that evicts it, and the new
  `SourceNatReservationSnapshot::restore_displaced` re-installs it after
  `rollback_flow` removes the replacement. Restore is conservative: it
  refuses (leaving current state untouched) when the flow's slot was
  retaken, when the incumbent's plain-PAT bit was re-claimed, when the
  record no longer names the replacement, or when the persistent-lease
  shape is not the completed shape the replacement left. For a lease that
  is still present it restores the exact lease record and holder mask.
  The NAT64 twin's snapshot is a bare holder mask (pre-existing plumbing),
  so its recheck helpers keep their rollback behaviour and the
  coordinator's strict-mirror rollback remains the NAT64 restore path;
  the deterministic pre-check closes the eviction for every synced NAT64
  re-decision whose contended state is visible at reserve time.

## Neighbouring behaviour preserved

- PASS 2 (`stop_at_first_owner == false`) never pre-checks and never
  restores: byte-identical fall-through, bound by the existing
  `pass2_still_falls_through_a_refusing_owner_6979_f1` cell.
- Admissible re-decisions still replace the incumbent (new positive
  controls on both the SNAT and NAT64 arms).
- The #8115/#9021/#14368 refusal outcomes, counters, and
  `RejectedReserve` mapping are unchanged — only the incumbent's survival
  changes.
