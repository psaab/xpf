# #12136 — propagate adopted-VRF `LinkSetUp` failure

- **Issue:** #12136 — adopt path swallowed `LinkSetUp` failure and could report a green apply with a down VRF.
- **Branch:** `fix/12136-vrf-linkup`
- **Worktree:** `/var/worktrees/12136-vrf-linkup`
- **Base:** `1c384b9a47ff7d6e567fa50632faa75c3995ae87`

## Why

When reconcile found an existing `vrf-*` device with the desired table, it attempted `LinkSetUp` but only logged failures at Debug level, then adopted and tracked the VRF while returning no reconcile error. This differed from `createLinkedVRF`, which returns the same bring-up failure. Callers could therefore treat the managed VRF as ready after an otherwise green apply.

## What

- The existing-VRF adopt path now logs a failed `LinkSetUp` at Warn and records `set VRF <name> up: <cause>` as the reconcile error, matching the create path's error context.
- The VRF remains tracked after the failure, preserving ownership so a later reconcile retries `LinkSetUp` without deleting or recreating the existing device.
- Added #12136 regressions for an already-present, correct-table, admin-down VRF: failed `Reconcile` with retained managed state, followed by successful in-place retry when `LinkSetUp` recovers.

## Risk / remaining acceptance

A failed bring-up leaves the VRF tracked by design; the returned reconcile error fails the apply, and the next reconcile retries the link-up. No live cluster was mutated. The regression uses the routing package's injected netlink fake rather than a real kernel VRF.
