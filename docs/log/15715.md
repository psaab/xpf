# Issue #15715: OSPF multi-key MD5 rollover authentication bypass

- **Timestamp**: 2026-10-19
- **Problem**: Two strict gates validated OSPF MD5 rollover incompletely.
  `validateFRRAuthValuesStrict` checked only the scalar `iface.AuthKey`,
  which `compileProtocols` overwrites with the last `keyPresent` md5 entry,
  so `md5 1 key "bad secret"` + `md5 2 key "goodsecret"` compiled clean and
  the FRR renderer silently dropped key 1 (breaking rollover adjacency);
  with the bad/empty key last, both keys were dropped and the whole
  interface block was omitted after a clean commit.
  `validateOSPFAuthKeyPresenceStrict` accepted a rollover when ANY entry
  was non-empty, so `md5 1 key "goodsecret"` + keyless `md5 2` (or an
  empty-string entry) compiled clean and was silently dropped at render.
- **Fix (FRR auth values)**: In `validateFRRAuthValuesStrict`
  (`pkg/config/compiler_validate_strict_routing.go`), check every
  `iface.AuthMD5Keys` entry by key-id
  (`protocols ospf area <id> interface <name> md5 <key-id> key`) before the
  scalar `AuthKey` check, which remains for simple/legacy configurations.
  Per-key-first ordering names the offending key-id even when it is also
  the legacy `AuthKey`.
- **Fix (presence)**: In `validateOSPFAuthKeyPresenceStrict`
  (`pkg/config/compiler_validate_strict_ospf_auth_key_14397.go`), when
  `len(AuthMD5Keys) > 0` require EVERY entry to have
  `Key.Reveal() != ""`, naming the first empty key-id; the legacy
  single-key view (empty `AuthMD5Keys`, non-empty `AuthKey`) still passes.
  Strict rejects; lenient (#1960) warns naming interface + key-id and the
  renderer belt (#14388/#14397, unchanged) omits the interface. This
  narrows the #14397 "at-least-one-non-empty-key" rule — documented in the
  gate header and the #14397 test header.
- **Fix (compiler coalesce)**: `compileProtocols`
  (`pkg/config/compiler_protocols.go`) now coalesces same-key-ID md5
  fragments instead of appending a duplicate entry: an inline
  `authentication md5 1;` packed leaf beside a group
  `authentication { md5 1 { key ...; } }` container (#14414) is the same
  key-id restated in two fragments, so whichever side is empty is filled
  from the keyed side (either compile order). A DISTINCT keyless key-id
  still appends and is rejected by the presence gate. This mirrors
  `OSPFInterfaceUnion12186.mergeMD5Key12186`, which already fills an empty
  same-ID entry.
- **Regression check**: `go test ./pkg/config/ -run
  '15715|14414|14397|TestFRRAuthValueWhitespaceRejected|TestOSPFAuthKeyPresence'`
  and `go test ./pkg/frr/ -run '14414|14388|14397|8443|OSPF|Auth'` pass;
  all `OSPF` tests in `pkg/config` pass. The pre-existing
  `TestFRRAuthValueWhitespaceRejected/ospf-key-with-space-rejected`
  assertion now expects the per-key field name `md5 1 key`, and the #14397
  empty+valid rollover control became an all-valid rollover control.
- **Not changed**: The FRR renderer belt, key-ID range gate (#11794),
  simple-password handling, and tolerant-load booting (#1960: warnings,
  never hard errors) are unchanged. Directly constructed configs with a
  mixed `AuthMD5Keys` (one empty entry) now strict-reject where #14397
  previously accepted; the renderer still renders the non-empty keys for
  tolerant/direct consumers.
