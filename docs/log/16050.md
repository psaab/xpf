# /run/xpf 0755 + flock files 0644 let a local user block upgrades (#16050)

- **Issue**: #16050 (split from #15986, claim F2).
- **Cause**: `/run/xpf` was created 0755 (`pkg/upgrade/lock`,
  `pkg/daemon` singleton, input-barrier markers, `debian/xpf.preinst`)
  and the flock files were created 0644 (upgrade lock, HA epoch lock
  `ha-boot-epoch.lock`, `kernel-roll.lock`). On Linux an exclusive
  `flock(LOCK_EX)` succeeds on a readable `O_RDONLY` fd, so any local
  unprivileged user who could traverse the directory and read the lock
  file could exclusively flock it and block all upgrades (and epoch
  persists / kernel-roll lease consumption) indefinitely — no write
  permission needed. Creation mode alone could not fix it: shell
  first-creators (`xpf.preinst` `mkdir -p`+`flock(1)`, `xpf-deploy.py`
  `flock(1)`) create these files under the caller's umask.
- **Change**:
  - Go: parent dir created 0750 + chmod-asserted on every acquire and
    lock files created 0600 + chmod-asserted before the flock, at every
    site — `pkg/upgrade/lock` (upgrade.lock), `pkg/daemon` singleton
    (xpfd.lock dir+file, file chmod moved before the flock in the GLM
    fold), input-barrier markers (dir), `pkg/cluster` epoch lock,
    `pkg/upgrade` kernel-roll.lock. A chmod failure refuses/declines
    rather than proceeding on a world-flockable lock.
  - Shell: `debian/xpf.preinst` `mkdir -p /run/xpf && chmod 0750`, chmod
    0600 a pre-existing lock, and the gate `flock` runs under `umask 077`.
  - Orchestrator: `scripts/deploy/xpf-deploy.py` lease acquire/renew/clear
    now `chmod 0750 /var/lib/xpf`, chmod 0600 a pre-existing
    `kernel-roll.lock`, and run `flock`/lease writes under `umask 077`
    (was `umask 022`) — chained with `&&` so a chmod failure aborts
    before flock (fail closed, like the Go paths).
  - Unit: `test/incus/xpfd.service` (the unit `debian/rules` stages)
    gains `RuntimeDirectory=xpf`, `RuntimeDirectoryMode=0750`,
    `RuntimeDirectoryPreserve=yes`, `UMask=0027`. Preserve is required:
    systemd otherwise removes `/run/xpf` at unit stop while the upgrade
    runner holds an open flock on `upgrade.lock` across stopping xpfd,
    unlinking the locked inode and letting a second process flock a
    new inode (split mutex mid-cutover). Preserve keeps only the
    directory/path; lock *state* is inherently per-boot (`/run` is
    tmpfs, recreated empty at boot), so nothing meaningful survives
    a reboot.
  - Docs: mode invariant recorded in `docs/in-place-upgrade.md`.
- **Regression coverage**:
  - `pkg/upgrade/lock`: `TestAcquireTightensPermissiveModes16050`
    (pre-existing 0755/0644 tightened on acquire; fresh create under
    umask 0 lands 0750/0600) and
    `TestUnprivilegedCannotFlockUpgradeLock16050` (as root, a
    `nobody` `setpriv flock -n` probe must fail; non-root runs assert
    the 0600 bits instead, never vacuous).
  - `pkg/daemon`: `TestDaemonLockTightensPermissiveModes16050`,
    `TestUnitRuntimeDirectoryHardened16050` (parses the shipped unit).
  - `pkg/cluster`: `TestEpochLockFileTightened16050`.
  - `pkg/upgrade`: `TestKernelRollLockTightened16050`.
  - Shell harnesses: `test/debian/preinst-besteffort-test.sh` sed
    redirects updated for the new chmod lines; preinst/postinst/
    preinst-migrate/preinst-safe-segment harnesses all pass; the
    redirected real preinst lands the dir 0750 and the lock 0600.
  - Deploy: `test_xpf_deploy_lease_ttl` + `test_xpf_deploy_lease_renew_fence`
    (34 tests) pass; the generated acquire script was executed against a
    temp root and lands dir 0750, lock 0600, lease 0600.
    `test_xpf_deploy_lease_chmod_16050` executes the real generated
    acquire/renew/clear scripts with a failing `chmod` shim and asserts
    no flock is reached and no lease is written/rewritten/deleted.
- **RED evidence**: Decisive syscall check (root, this host, temp root):
  pre-fix shape (0755 dir + 0644 lock) —
  `setpriv --reuid=nobody flock -n upgrade.lock true` **succeeded**
  (vulnerability reproduced); post-fix (0750/0600) — the same probe
  **fails** (`flock: cannot open lock file: Permission denied`, exit 66),
  and `cat` as nobody is denied. The root probe cell carries the same
  shape as a control: loosened back to 0755/0644 (flock released) the
  nobody probe succeeds; restored to 0750/0600 and re-acquired it
  fails — so a green cell cannot be a probe that never could flock.
- **GREEN evidence**: `go test ./pkg/upgrade/lock/ ./pkg/cluster/`
  (16050 cells), `go test ./pkg/daemon/ -run 16050`,
  `go test ./pkg/upgrade/ -run TestKernelRollLockTightened16050` pass;
  root run of `TestUnprivilegedCannotFlockUpgradeLock16050` passes
  (real nobody probe, control + blocked arms); `go vet` on the touched
  packages is clean.
- **Blast radius / risk**: All lock holders are root (xpfd, maintainer
  scripts, the deploy orchestrator over ssh/incus exec), so 0750/0600
  removes no legitimate access; the dataplane helper runs as root and
  keeps traversing `/run/xpf`. (Root's chmod succeeds regardless of
  who owns a pre-existing `/run/xpf`, so a non-root-owned dir is
  tightened in place, not refused — owner-adoption *refusal* is the
  separate #9003 helper-socket guard, not these locks.) No
  dataplane/hot-path code is touched; the chmods are one syscall per
  lock acquire.
