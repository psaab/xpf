- **Timestamp**: 2026-10-19
  - **Action**: Every SSH PAM faillock failure is now advisory in `applySSHConfig` (#15229, A45-02). Previously only errors wrapping `errSSHPAMFaillockUnsupported` were logged and skipped; any other faillock error — in particular a locally tuned managed block in `/etc/pam.d/common-auth` (`deny=` edited, so the body no longer matches a known-good variant) — hard-returned before the sshd drop-in was built, so every later SSH policy apply, including a `PermitRootLogin no` revocation or drop-in removal on stanza clear, failed on non-appliance hosts until the block was hand-restored. The faillock leg now logs every failure (the unsupported-baseline message is unchanged; other failures log that the lockout was not applied and the drop-in apply is continuing) and proceeds to the drop-in write/removal. The tuned block itself remains refused by the render path and byte-untouched — xpf never rewrites administrator-modified PAM state, it just no longer lets that state veto sshd policy.
  - **Validation**: New cells in `pkg/daemon/ssh_faillock_15229_test.go` seed a stock stack carrying tuned managed blocks (`deny=99`) on a non-appliance host: the `PermitRootLogin no` apply returns nil, writes the revocation into the drop-in, reloads sshd, logs the faillock problem, and leaves `common-auth` byte-identical; the stanza-clear apply removes the existing drop-in and reloads. Both fail on pre-fix master with `apply SSH cross-connection password lockout: managed PAM faillock block ... was modified` and pass after the fix. Adjacent controls stay green: #11492 stock install / idempotence / custom-stack / appliance-skip cells and #14973 rollback-strip + success-keep cells. See PR for full suite results.
  - **Risk**: On non-appliance hosts with a broken or tuned PAM stack, SSH applies now succeed without the cross-connection lockout and report that only in the daemon log (WARN) — the previous behaviour coupled an unrelated sshd-policy revocation to that failure, which is the worse failure mode; the lockout gap itself is unchanged from what the hard-fail already left in place, and a subsequent apply retries the PAM leg. `faillockInstalled` stays false on failure, so the #14973 rollback strip remains a no-op for pre-existing admin/tuned faillock. Appliance hosts are unaffected (PAM leg skipped). No wire/config-schema change.
