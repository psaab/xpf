# Issue #19054: H11 soak's traffic budget ran out; uncovered moves scored FAIL

## Why

- **Timestamp**: 2026-11-09 PST
- **Action**: In the wave-1 gate (loss, master 602f946af5), `SOAK_MOVES=200
  SOAK_SLEEP=5` ended 182 PASS, 18 FAIL. All 18 FAILs were moves 183-200.
  - iperf3 and ping had exited. The run length was estimated as moves x
    (sleep + converge + 4 s) + 60 s = 2,860 s, while the moves took about
    16 s each on average, rising from about 11 s to 38 s near the end.
  - The windows the traffic did not cover were scored FAIL ("did not cover
    the move window", "traffic did not follow").

## What

- **File(s)**: `test/incus/rg_move_soak.py`, `test/incus/rg-move-soak.sh`,
  `test/incus/rg_move_soak_test.py`, `docs/ha-rg-move-correctness.md`
- **Run length**: the generators run until the soak stops them (it always
  does, after the last window). Their `-t`/`-w` cap is now 120 s per RG
  move + 600 s (`TRAFFIC_S_PER_MOVE_CAP`, `TRAFFIC_S_SLACK`), and
  `SOAK_TRAFFIC_S` overrides it. `info.traffic_s` records the value used.
- **Uncovered window = VOID**: `move_verdict` scores a move whose window
  ping or iperf3 did not cover as VOID, never PASS, COST or FAIL.
  - The reason names the cause, recorded per family by `finish()` as
    `uncovered_cause`: the traffic run's planned end came first
    (`traffic_end_lan`), or a generator stopped early (with iperf3's error
    text).
  - Every other reason is kept as "unscored evidence: ...".
- **Fake**: `FakeCluster`'s generators now stop after their own `-t`/`-w`
  seconds, as the real ones do. `run_fake` accepts `traffic_s`.
- **Cells**, `TrafficCoverage19054`:
  - `test_no_uncovered_move_is_scored`: a 12 s traffic run under 3 moves;
    every uncovered move is VOID with the cause, and there are no FAILs;
  - `test_moves_slower_than_the_old_estimate_stay_covered`: 6 moves of
    about 26 s each (`SlowCliCluster`), which the old run length cannot
    cover; all are covered and the run exits 0.
- **Changed existing cell**: `MoveVerdict.test_traffic_generator_death_fails`
  asserted that an uncovered window FAILs, which is the defect #19054
  removes. It is now `test_traffic_generator_death_is_void_never_pass`: the
  same two inputs (iperf3 or ping not covering) must be VOID, with the
  "did not cover" reason, and never PASS.
- **Not fixed here**: why moves slow down over a long run. #19054's
  comment points at per-move work that scales with the run. That is
  outside this change, which makes the soak correct however long the moves
  take.

## Validation

See the commit message (runner RED/GREEN and mutants).

## Risk

Harness only. A long run's tail moves are now covered, and are scored,
where before they were FAILed. If the generators die, the moves they leave
uncovered are VOID, which makes the run exit 2, so a run is never a false
PASS. A dead controller leaves iperf3 running on the LAN host for up to the
cap. That risk already existed with the old 2,860 s figure for 200 moves.

- **Measured first** on udp:xpf-testrunner: iperf3 3.22's `start` event
  carries `timestamp.timesecs` and `timemillisecs` (its connect time).
  `--timestamps` does not stamp `--json-stream` lines. On SIGINT, iperf3
  3.22 writes a final partial interval, then the error `interrupt - the
  client has terminated by signal Interrupt(2)`, then `end`. A background

  not started as one.

    the start timestamp (`timemillisecs`, else `timesecs`), and

    median is gone. The anchor is the connect time, at or before the test
    start, so every interval time is a lower bound. An iperf3 without a
    start timestamp voids the run at the traffic preflight.
  - Who ended a generator, from what is recorded (`generator_end()`):
    - iperf3: an `end` event without an error is its `-t`. SIGINT's exact
      text (`IPERF_SIGINT_ERROR`, in both its 3.22 and older forms) is
      the harness. Any other error, including the server's "interrupt",
      is a death. Output that stops with neither is a death.
    - ping: a recorded stop that found its pid running, or a line at or
      past the planned end (ping's `-w` runs 60 s past iperf3's).
  - `generator_stop_script()`: the soak's stop and the watchdog both
    record the LAN time and which generator pids answer `kill -0`, then
    SIGINT. The soak's stop prints `STOPPED <time> <running>...`
    (`parse_stop_record()`). The watchdog's marker is `<time> <age>
    <run token> <running>...`. `WATCHDOG_GUARD_S` is gone.
  - `parse_watchdog_marker()` also requires this run's random token
    (`Soak.run_token`, handed to the watchdog at its start).
  - `family_traffic()` always charges a self-stopped generator to exactly
    one move: the first window it did not cover, or the LAST move if it
    covered them all ("stopped by itself in the final tail"). A stall
    that iperf3's own death cut short never recovered (FAIL). Only a
    harness-ended stall is VOID.
  - `finish()` words a later window from the charged move's ACTUAL
    verdict ("which scored VOID" for a precondition VOID).
  - The fake: each generator's output, its start stamp and its `-t`/`-w`

## D1 correction: a reader clock step (after 1911a37fb5)

- **Timestamp**: 2026-11-10 PST
- **Finding** (Codex, at 1911a37fb5): D2 is FIXED; D1 is PARTIAL. The
  epoch's upper bound, min(arrival - interval end), assumes the LAN
  reader's wall clock never steps back. After a 0.2 s backward step, one
  late arrival gave 100.402 against a true 100.600. The 10.1 s stall then
  fell out of [105,125), and the move PASSed again.
- **Disposition** (orchestrator, on #19054): one more commit on the batch
  branch, limited to D1, failing closed. The bound is not re-derived.
- **Fix**:
  - The reader stamps `<wall>@<mono before>:<mono after>`.
  - `iperf_reader_step()` checks that every line's wall - monotonic offset
    interval, widened by the 1 µs printing resolution, shares a point. If
    one does not, the clock stepped. A stamp with no monotonic time
    cannot be checked.
  - Either way, every window of that family gets "reader clock stepped;
    timing not certifiable" as VOID evidence. That is never PASS, and FAIL

## Re-plan design note: one clock (after 0f1d3f2461)

- **Timestamp**: 2026-11-10 PST
- **Context**: at 0f1d3f2461, Codex F1 (a false PASS: a wall step hidden inside a read bracket) and R16 F1 (a false-VOID storm from rounding) came in opposite directions, so the orchestrator re-planned the batch under the escalation rule. This is a plan, not code. It asks Codex and R16 for DESIGN-READY before any implementation. The branch stays at 0f1d3f2461, unlanded, and #19085 is paused locally.

#### 1. Root cause

Every round failed at a seam between clocks:
- Windows are controller monotonic, mapped to the LAN wall clock by one preflight offset.
- ping's `-D` stamps are LAN wall time.
- iperf3's interval times are its LAN-wall connect stamp plus its own elapsed offsets.
- Reader arrivals are LAN wall time, with a monotonic bracket bolted on.
- Stops and the watchdog are LAN wall time.

Every fix either moved the seam (connect stamp, then arrival minimum, then step detector) or added a tolerance at it. This plan removes the seams instead: every instant that reaches a traffic verdict is read from ONE clock, the LAN host's `CLOCK_MONOTONIC`, as integer nanoseconds. No wall clock remains in the verdict path.

#### 2. The one clock

All stamps come from the LAN host: the reader, the probe, the stop, the watchdog, the window boundaries and the iperf3 launch stamp. They are `time.monotonic_ns()` integers from python3, or the probe's own `clock_gettime(CLOCK_MONOTONIC)`. All of these run in the same LAN container, so they share one clock. Incus uses no time namespace by default; the preflight checks for one (section 9).

`CLOCK_MONOTONIC` never steps. NTP slews it at the same rate as the wall clock, and iperf3's interval clock is the same `CLOCK_MONOTONIC` (to be verified, section 9). So durations agree, and steps of either sign do not exist in this clock.

The controller's own monotonic clock keeps measuring only controller-side durations: the sleep cadence, the converge bound, landing and the CLI time. Those are never compared with LAN evidence. The `lan_time()` mapping and the preflight LAN offset leave the verdict path; offsets are still measured and reported for skew diagnosis.

#### 3. Window boundaries, recorded on the LAN clock

- Just before each move's CLI is sent, after the UDP pre-move reads, the controller runs one exec on the LAN host. It returns `monotonic_ns`, and that value is boundary `b_k`.
- Window k is `[b_k, b_{k+1})`. The last window ends at a stamp taken when its watch window ends, as today.
- **Causality, not a tolerance:** `b_k` is read on the LAN host before that exec returns. The CLI is sent only after the exec returns. So `b_k` precedes every effect of move k, on the LAN clock, however long the round trip is. Evidence caused by move k can never land in window k-1.
- **A slow controller-to-LAN round trip:**
  - Window k then starts earlier than CLI k, by up to that round trip. Late effects of move k-1 that fall in the gap are charged to move k.
  - That is today's behaviour too: today's window starts before the UDP pre-move reads, seconds before the CLI. It is a precision cost, not a soundness one.
  - The soak records each boundary exec's controller-side round trip in `result.json`, so a slow one is visible.
- **A boundary exec that fails or times out:** the adjacent windows have no certified boundary, so both are VOID ("window boundary not recorded on the LAN clock"). This fails closed.

#### 4. iperf3: generator time in the one clock

- **Launch stamp `L`:** the launch shell runs `python3 -c 'print("LAUNCH", time.monotonic_ns())'` immediately before `exec iperf3`. iperf3 starts after that, so its test-start epoch `E >= L`.
- **Arrival stamps `A_i`:** the reader stamps each line `<monotonic_ns> <json>`. Integer nanoseconds, no wall clock, no float.
- **Upper bound `U`:** an interval cannot be read before it ends, so `A_i >= E + e_i` for its end offset `e_i`. Then `U = min_i(A_i - e_i) + ε_e`. Here `ε_e` covers only iperf3's microsecond truncation of `e_i`, plus double rounding. It is a fixed, provable 2 µs, not a timing tolerance. The interval timestamps iperf3 uses have microsecond resolution and are truncated, so `e_true - e_printed < 1 µs`.
- **The epoch interval:** `E ∈ [L, U]`, entirely in the one clock. If `U < L`, the logs contradict each other, and that family is VOID ("iperf3 timing inconsistent"). That cannot happen if the premises hold; the check exists so that a broken premise fails closed.
- **Coverage uses the lower bound:** the stream covers window k only if `L + e_last >= b_{k+1}`.
- **Attribution is conservative over the interval:** a stall that starts at offset `s` truly starts in `[L + s, U + s]`. It is charged to every window that range intersects. That keeps D1's rule; only the coordinates change. The COST-to-FAIL over-attribution is kept as accepted, documented behaviour. `U - L` is now about the exec, connect and parameter-exchange time, tens of milliseconds, so over-attribution only touches stalls that start that close to a boundary.
- **How iperf3 ended** is read from its own events (unchanged): `end` with no error is its `-t`; the exact SIGINT text is the harness; any other error is a death. Its death is charged to the first window it does not provably cover, or to the last move if it covered them all.

#### 5. ping: a monotonic-native probe replaces `ping -D -O`

- **Recommended: `icmp_probe.py`.** It is stdlib python3, run as root by `incus exec`. It sends ICMP or ICMPv6 echo on a `SOCK_DGRAM` ping socket, falling back to `SOCK_RAW` as root, every 10 ms. Every log line carries `clock_gettime(CLOCK_MONOTONIC)` nanoseconds taken by the probe itself:
  - `S <seq> <ns>` for each send. This is the liveness line: the probe was running at `ns`.
  - `R <seq> <recv_ns> <rtt_ns>` for each reply.
  - `END deadline|sigint <ns>` when it exits.
- **What each check reads:**
  - Gaps, lost replies, the open gap, tail replies and the final tail are computed on reply receive times.
  - Liveness is the last `S` or `R` line.
  - How the probe ended is its `END` line, or a recorded stop that found it running.
- **Identity:** the launch records the PID and start time, as now.
- **Rejected alternative, reader-stamped `ping` lines:** an arrival stamp only bounds a line's print time from above. If the reader was late on the reply before an outage and on time for the reply after it, the measured gap is SHORTER than the true one, which is a false PASS. Read brackets bound that only to the line cadence, and only with a reader that never batches.
- **Rejected alternative, `-D` stamps converted through a measured wall-to-monotonic offset:** that puts the wall clock back in the path, the F1 class.
- **What this changes:** ping's `-w` and `-O`, `_PING`, `ping_last_seen()` and the R1 mutant go away. The probe has its own deadline, `duration + 60 s`, which it reports itself in its `END` line.

#### 6. Stops, the watchdog and the planned end

- **The soak's stop** prints `STOPPED <monotonic_ns> <alive...>`. The identity check, SIGINT and alive list are unchanged.
- **The watchdog marker** is `<monotonic_ns> <age> <token> <alive...>`. Its start and read stamps are also LAN monotonic, so the range check is in the one clock.
- **The planned end** is no longer an instant. iperf3's `end` event and the probe's `END deadline` report it.
- **The final tail** for #19085 is `[b_last_end, STOPPED_ns)`.

#### 7. What is removed

- Wall time everywhere in the verdict path: `lan_time()` for windows, `traffic_end_lan`, ping's `-D` stamps, and iperf3's `timestamp` as the anchor. iperf3's `timestamp` is kept as a diagnostic only.

- `PING_DEADLINE_EXTRA_S` as a cross-generator margin. The probe's own deadline replaces it.

#### 1. Notation

- Every LAN stamp is an integer nanosecond reading of the LAN container's `CLOCK_MONOTONIC` (`time.monotonic_ns()` in python3, which R16 confirmed is `clock_gettime(CLOCK_MONOTONIC)` on 3.13.5 and 3.14.4).
- `δ = 1000 ns` (section 2.2).
- Budgets are converted once to integer ns (section 6).
- "Certainly in X" means: in X for every value the evidence admits. "Possibly in X" means: in X for at least one.

#### 2. iperf3

**2.1 What the 3.20 source guarantees (Codex F5, non-monotonic offsets).** Read from esnet/iperf tag 3.20; R16 verified the LAN binaries are 3.20-2 and that `iperf_time.c` is byte-identical to 3.22.
- `iperf_time_now()` is `clock_gettime(CLOCK_MONOTONIC)`, stored as seconds plus `tv_nsec / 1000` (truncated), `iperf_time.c:39-55`.
- `iperf_init_test()` reads the clock ONCE and stores that one value in every stream's `start_time` (`iperf_api.c:2236-2242`). The only other writer, `iperf_reset_stats()` (`:3622`), runs only from `client_omit_timer_proc()` (`iperf_client_api.c:261`), and the soak never passes `-O`. So all streams of one process share one epoch `E`.
- `iperf_stats_callback()` reads the clock once PER STREAM for each interval's end, and each stream's next interval starts at its own previous end (`iperf_api.c:3656-3664`). Per-stream offsets in `streams[j].start/end` are relative to the shared epoch (`:4639-4642`).
- The `sum` span is the FIRST stream's span (`:3936-3947`). v1's source (`parse_iperf_stream`, rg_move_soak.py:673-680) gives every stream the sum's span. That is the defect Codex F5 names, and it is removed.
- JSON numbers are `cJSON_CreateNumber(double)` (`iperf_util.c:408`), printed with `%1.15g`, or `%1.17g` when the 15-digit form does not round-trip within `max·DBL_EPSILON` (`cjson.c:549-589`).

**Build gate.** These facts hold for the audited build only. When it launches iperf3, the harness records `iperf3 --version` and the sha256 of the `libiperf.so.0` mapped by the running process (from `/proc/<pid>/maps`). The audited set is the two LAN builds R16 pulled: Debian 3.20-2 on loss (`abe22eca…`) and Ubuntu 3.20-2 on tcp (`c45c485a…`). udp is admitted only if its sha256 equals tcp's (section 8). Any other build makes that family's iperf timing VOID ("iperf3 build not audited for its interval clock"). A new build is admitted by repeating the audit in section 8, never by editing the list alone.

**2.2 Offsets as exact integers (Codex F6).**
- For each offset `v`, `us = round(v × 10^6)`. The parser requires `|v × 10^6 − us| ≤ 10^-3`, otherwise "offset off the microsecond grid": the family's timing is VOID.
- Then `ns = us × 1000`.
- This recovery is exact. iperf3's value is an integer number of µs. cJSON's round trip is within `|v|·DBL_EPSILON`, and Python's float parse is correctly rounded. Together that is under 0.5 µs for every `v < 10^6 s`. An offset of `10^6 s` or more is VOID ("unsupported duration").

**2.3 The truncation error is two-sided (Codex F6).**
- Each printed offset is `x_p = trunc(T_x) − trunc(T_0)`. Here `T` is a full-ns `CLOCK_MONOTONIC` reading, and `trunc` removes `r ∈ [0, 1000)` ns.
- So `x_true = T_x − T_0 = x_p + r_x − r_0 ∈ (x_p − δ, x_p + δ)`.
- Codex is right that this error is two-sided. Every use of an offset below is therefore widened by δ in the conservative direction for that use, on start and end offsets alike.

**2.4 Per-stream layout (Codex F5).** Each stream is scored on its own `streams[j].start/end`. The sum span is used only for the aggregate check, where it is the first stream's span by construction. Any of the following makes the family's iperf timing VOID ("unsupported interval layout"):
- a stream set in any interval that differs from the `start` event's connected sockets;
- a stream whose first start is not 0, whose start is not its previous end (integer µs), or whose end is not after its start;
- an `omitted` interval.
A stream missing from one interval but present before it is still a dead or low stream, as today.

**2.5 The epoch interval.**
- `E` is iperf3's full-ns reading in `iperf_init_test()`.
- `L` is the `LAUNCH` stamp, taken immediately before `exec iperf3`, so `L < E`.
- Each interval line is read after iperf3 wrote it, and iperf3 wrote it after every per-stream end reading in it. So `A ≥ T_e = E + e_true > E + e_p − δ`, which gives `E < A − e_p + δ`.
- `U = min over every stream entry of every interval of (A − e_p) + δ`. This is a strict upper bound.
- A missing `LAUNCH` line VOIDs the family (R16 D5). So does `U < L` (a broken premise), and so does a family with no interval.
- `U − L` is recorded per family in `result.json` (R16 D4).
- The admissible epochs are `E ∈ [L, U]`. Every true instant `E + x_true` lies in `[L + x_p − δ, U + x_p + δ]`.

**2.6 Coverage and attribution (Codex F2).**
- **End coverage:** a stream covers a window's end `t1` iff `L + e_last − δ ≥ t1`.
- **Start coverage (new):** iperf3 was running at the window's start `t0` iff `U + δ ≤ t0`, since its first interval starts at offset 0. Otherwise the window's beginning was not observed, and the iperf checks for that window are VOID.
- **Stalls:** a stall run with offsets `[s, e]` (its own stream's spans) occupies at most `[L + s − δ, U + e + δ]`. It is charged to EVERY window that range meets. That includes a stall that began in warmup and is open at `b_1`, and a stall open across any `b_k`. A stall that straddles a boundary is charged to both moves: documented over-attribution, the same class as v1's accepted COST-to-FAIL.

**2.7 Durations (Codex F7).**
- A stall's duration is `d = e − s` in integer ns, with true value in `(d − 2δ, d + 2δ)`.
- It is certainly over a budget if `d − 2δ > budget_ns`, and certainly within it if `d + 2δ ≤ budget_ns`. Between those it is VOID ("within 2 µs of the budget").
- This applies to the per-stream budget, the COST cap and the all-stream outage.

**2.8 Positive evidence in the tail (Codex F3, R16 D4).**
- "Traffic followed" is judged at the worst admissible placement, not at `L`.
- For each candidate epoch `E'` in `[L, U]`, take the intervals certainly inside `[tail0, t1)` under `E'`. Certainly inside means `E' + s_p − δ ≥ tail0` and `E' + e_p + δ ≤ t1`. Compute their mean aggregate rate.
- The inside set changes only at breakpoints `tail0 − s_p + δ` and `t1 − e_p − δ`, so the candidates are those breakpoints that fall inside `[L, U]`, `L` and `U`, and one integer-ns point strictly between each pair of consecutive candidates. An open segment can hold fewer intervals than either of its ends.
- **PASS:** every candidate has at least one interval inside, and its mean is at least `low_bps`.
- **FAIL:** the mean is below `low_bps` at every candidate, so every admissible placement fails.
- Otherwise VOID ("tail not certifiable at U − L = … ms").
- **Why VOID rather than R16's empty-tail-to-FAIL:** FAIL claims a product defect. A healthy run whose `U − L` is wider than the tail would FAIL with no defect present. R16's cell (a blackhole in move k's tail, move k+1 restoring) still never PASSes: it FAILs when the restore takes longer than `U − L`, and is VOID otherwise.
- **Codex's F3 scenario:** with `E' = 101`, the tail holds the true low intervals, so not PASS. With `E' = 100`, it holds healthy ones, so not FAIL. Result: VOID.

**2.9 Death (R16 D4).**
- A generator that stopped by itself went silent somewhere in `[L + e_last − δ, U + e_last + I + δ]`, where `I = 100 ms` is the report interval.
- It FAILs every window that range meets. Later windows are VOID ("after"), as today.
- How iperf3 ended is unchanged: an `end` event, the exact SIGINT text, or an error.

#### 3. The ICMP probe

**3.1 Why a probe, and v1's rejection narrowed (Codex).** Reader brackets are not unsound in principle. They are rejected here for one specific reason: a gap needs a LOWER bound on each reply's arrival, in the one clock. `ping` prints no send time in that clock, and the moment it prints is not a lower bound on anything. The probe supplies both bounds itself.

**3.2 Socket (R16 D1).**
- Raw only: `SOCK_RAW` with `IPPROTO_ICMP` or `IPPROTO_ICMPV6`, as root in the LAN container. The probe never opens a ping (DGRAM) socket.
- The reason: all three LAN hosts have `ping_group_range = 65534 65534`, so DGRAM is EACCES for root there (R16's measurement). One path runs in production, and that path is the one tested.
- The header records `socket=raw`. A log whose header says anything else VOIDs the family.

**3.3 Probe contract (R16 D1, D3).**
- **Wire:**
  - v4: type 8, code 0, checksum computed by the probe. v6: type 128; the kernel fills the checksum on raw ICMPv6 sockets, as R16 observed.
  - Ident: 16 random bits per run.
  - Wire seq = `lseq & 0xffff`, where `lseq` is a 64-bit logical sequence number.
  - 56-byte payload: the 128-bit run token, then `lseq` (u64), then the send stamp `s` (u64), then 24 zero bytes.
  - `ICMP_FILTER` / `ICMP6_FILTER` may pass only echo replies, as defence in depth. The verdict does not rely on them.
- **A reply counts only if ALL of these hold:**
  - type 0 or 129, code 0 (the IPv4 header, `IHL × 4` bytes, is stripped first);
  - source address equals the target;
  - ident equals the run ident;
  - payload is 56 bytes and its token equals the run token;
  - its `lseq` has an `S` line in this log, wire seq equals `lseq & 0xffff`, and the payload `s` equals that `S` line's stamp;
  - it is the first valid reply for that `lseq`.
- **Lines that do not count as replies:** duplicates are logged `D <lseq> <r>`. Everything else is counted in a once-per-second `C <ns> foreign=… dup=… own_request=…` line, including the probe's own looped-back requests, inbound echo requests and other pingers' traffic.
- **Send:** `s = monotonic_ns()` is read immediately BEFORE `sendto`, then `S <lseq> <s>` is logged. An `OSError` logs `X <lseq> <s> <errno>`, and the probe continues. The cadence is 10 ms. A send due earlier than it ran also logs `M <lseq> <due> <s>` (a diagnostic); the probe never bunches sends to catch up.
- **Receive:** after `select` reports the socket readable, the probe drains `recvfrom(MSG_DONTWAIT)` until EAGAIN. For each datagram, `r = monotonic_ns()` is read immediately AFTER `recvfrom` returns. A valid reply logs `R <lseq> <s> <r>`. A receive error other than EAGAIN logs `X - <ns> <errno>`, and the probe continues.
- **End:** the probe's own deadline logs `END deadline <ns>`; SIGINT logs `END sigint <ns>`; SIGTERM logs `END sigterm <ns>`. Any other exception logs `END error <ns> <repr>` and exits 1.
- **Output:** `python3 -u`, and every line is written with `flush=True` to a LAN-local file (`icmp.log`). The controller fetches the file after the stop. The probe's loop therefore never blocks on the `incus exec` stream (Codex's output backpressure). Stamps are fields of the line, so line order and write delay do not matter; the parser orders by stamp.
- **Liveness:** the last `S`, `X` or `R` stamp.
- **Optional:** `chrt -f` may be used to keep VOIDs rare. Soundness does not depend on it.

**3.4 Gaps (Codex F1, F2).**
- **Each reply's arrival is bracketed:** `s < a ≤ r`.
  - The reply cannot exist before its request left, and `s` is read before `sendto`.
  - It was dequeued before `r` was read.
  - This holds for the wire arrival and for the socket enqueue alike, whatever the receive backlog, NAPI or softirq delay, or probe scheduling. Delay only widens the bracket.
  - An EAGAIN-based floor would bound only the enqueue time, not the wire arrival, so it is not used.
- **Chain:** a sequence of replies whose brackets are ordered: `r_j ≤ s_{j+1}`. Their arrivals are then ordered too. Every true reply-to-reply gap inside `[a_first, a_last]` is at most the largest link `r_{j+1} − s_j`; other replies only split gaps. The chain is built greedily: from the current member, the next member is the valid reply with `s ≥` the current `r` that has the smallest `r`. Any chain gives a sound bound, so a suboptimal choice can only cost a VOID, never create a PASS. At a 10 ms cadence with sub-millisecond brackets, the chain is simply every reply in order.
- **PASS for window `[t0, t1)` needs a chain that:**
  - starts with `r ≤ t0`, so a gap that began before `t0`, in warmup or the previous window, is inside the chain (F2);
  - ends with `s ≥ t1`;
  - has every link `≤ budget_ns`.
- **FAIL needs a certain outage:** an interval `(x, y)` that meets the window and contains no reply bracket, with `y − x > budget_ns`, while the probe kept sending: its `S`/`X` stamps in `(x, y)` have no hole over `H = 100 ms`, and the first and last lie within `H` of `x` and of `y`. The same rule, run up to the probe's last stamp, is the open gap of a blackhole with no closing reply.
- **Otherwise VOID** ("ICMP gap not certifiable: link ≤ … ms, certain gap ≥ … ms, worst read delay … ms").
- **A probe pause** (no sends) can never PASS: its link exceeds the budget. It can never FAIL either: it has a send hole.
- **Codex's F1 history:**
  - The brackets are `[0.979, 0.980]`, `[0.989, 1.190]`, then `[2.099, 2.100]`.
  - The last link is `2.100 − 0.989 = 1.111 s`, over budget, so not PASS.
  - The reply-free interval `(1.190, 2.099)` is 0.909 s, within budget, so not FAIL.
  - Result: VOID. With the 0.989 reply read promptly, the free interval is about 1.10 s, and the result is FAIL.
- **Straddling gaps:** a gap that straddles `b_k` is judged in both windows (documented over-attribution).

**3.5 Tail replies (Codex F3).**
- **PASS** needs a reply certainly inside `[tail0, t1)`: `s ≥ tail0` and `r < t1`.
- **FAIL** needs no reply bracket meeting the tail while the probe kept sending through it (the same `H` rule).
- Otherwise VOID.

**3.6 How the probe ended.**
- `END sigint`, `END sigterm`, `END deadline`, or found running at the soak's stop: the harness. Windows it did not cover are VOID.
- `END error`: an instrument fault whose cause is known. Uncovered windows are VOID, and FAIL evidence elsewhere is kept.
- No `END`, and not running at the stop: stopped by itself, cause unknown. That FAILs the first uncovered window, as today (fail closed).

#### 4. Window boundaries

**4.1 Where `b_k` is taken (R16 D5, Codex cell 9).**
- `b_k` is stamped on the LAN host by the last LAN exec before move k's FIRST CLI.
- When the first RG's UDP pre-move read ran, that exec is its baseline read, and it becomes `cat <log>; python3 -c <stamp>`, with the stamp as its LAST statement. This saves the 150–250 ms exec R16 measured.
- Otherwise a dedicated exec takes the stamp.
- In a multi-RG move, the later RGs' UDP pre-reads and CLIs fall inside window k. There is still one `MoveRecord` per move.

**4.2 The stamp.**
- The stamp line is `BOUNDARY <nonce> <m1> <boot> <m2> <timens>`, and `b_k = m2`.
- The nonce is 128 random bits per attempt.
- These are all failed attempts: a missing line, another nonce, a malformed line, `m1 > m2`, a non-zero exit, or a timeout.
- Causality is as in v1: `b_k` is read before the exec returns, and the CLI is sent after that. Codex judged this sound.

**4.3 Failure (Codex).**
- **Retry:** up to two fresh dedicated attempts, all before the CLI. A successful retry is `b_k`, and the preceding window simply extends to it. A failed attempt's late output is discarded by nonce.
- **Never** controller time, never interpolation.
- **Interior failure after the retries:** the CLI still runs, because the move sequence is the operator's. Windows k−1 and k are judged as one merged span `[b_{k−1}, b_{k+1})`:
  - neither move can PASS;
  - certain FAIL evidence in the merged span FAILs both moves, because it cannot be split;
  - each move's non-traffic evidence (ownership, dual-active, follow counters) stays its own.
- **First boundary failed:** move 1 has no start, so it is VOID unless its own evidence FAILs.
- **Final stamp failed:** the last move is VOID unless its own evidence FAILs.
- **`b_{k+1} ≤ b_k`:** both windows are VOID ("LAN clock not monotonic across execs").
- Each boundary's controller-side round trip is recorded (diagnostic).

#### 5. Observation continuity

**5.1 Contract (Codex F4).** The preflight enforces two conditions and VOIDs the run if either fails:
- The LAN host is an Incus container. The setup script launches it as one (`cluster-setup.sh:562`, no `--vm`), and the preflight checks the instance type.

Under this contract, only a kernel suspend stops the LAN `CLOCK_MONOTONIC`. A container pause is a cgroup freeze, which stops tasks, not clocks:
- the probe shows a send hole, so its windows are VOID;
- a frozen iperf3 sender reads as a stall, which can FAIL;
- neither can PASS.

**5.2 Suspend witness (Codex F4).**
- Every LAN stamp source records `(m1, boot, m2)`, with `boot` from `CLOCK_BOOTTIME`. The sources are `LAUNCH`, every `BOUNDARY`, the probe's header and `END`, `STOPPED` and the watchdog marker.
- The offset `boot − mono` therefore lies in `[boot − m2, boot − m1]`.
- The kernel changes that offset only by adding slept time on resume. In `kernel/time/timekeeping.c` (v6.18), `offs_boot` is written only by `tk_update_sleep_time()`, called only from `__timekeeping_inject_sleeptime()`, which rejects a negative delta. So it never decreases.
- If a later witness's lower bound exceeds an earlier one's upper bound, the kernel slept between them. Every window between those two witnesses is VOID, FAIL evidence is kept, and the slept time is reported.
- **The contract's limit, written down:** a hypervisor that hides itself and pauses the host is invisible to every LAN observer.
- **A controller-side elapsed comparison was considered and rejected as a certificate:** its resolution is the sum of two exec round trips, about 0.3–0.5 s from R16's measurements, too coarse for a 1 s budget. It is kept as a diagnostic only.

**5.3 Clock context (Codex, R16 D5).**
- Every stamp source records `readlink /proc/self/ns/time` and `/proc/self/timens_offsets` (or `absent` when the kernel has no time namespaces), from inside its own exec.
- A mismatch between any two sources, or a value that cannot be read for any reason other than ENOENT, VOIDs the run.
- Nonzero offsets are recorded, not rejected: a constant offset shared by every source cancels.

#### 1. Sampling validity (C-N4)

- Every per-stream interval has its own duration `d = e − s`, in integer ns from exact µs.
- A window cannot PASS on its iperf3 evidence if any interval of any stream that meets it, at its outer placement `[L + s − δ, U + e + δ]`, has `d > P + B`.
- Here `P = 100 ms` is the requested `-i 0.1`, and `B = 50 ms`. The window is VOID unless other certain evidence FAILs it.
- The first interval is held to the same bound. The last, short interval at `-t` is not a concern, because the rule bounds only long intervals.
- **Why 50 ms (measured):** I read 84 real H11 json-stream logs from `/var/worktrees/wave1-logs/*/soak`, both families, from loss, tcp and udp gates. They hold 1,659,652 interior per-stream intervals:

  | p50 | p99 | p99.9 | p99.99 | max |
  |---|---|---|---|---|
  | 100.000 ms | 100.990 ms | 102.169 ms | 104.216 ms | 107.401 ms |

  - None exceeds 110 ms.
  - The first interval's maximum is 100.497 ms.
  - The spread of end times across streams within one event was p50 12 µs, p99 391 µs, max 4.836 ms.
  - So `P + 50 ms` voids no interval seen in any real run.
- **The resolution this certifies, written down:**
  - An outage hides at most the two partial intervals at its ends, so a measured low run understates the true outage by at most `2(P + B) = 300 ms`.
  - The stall and outage budgets therefore certify "no outage longer than budget + 300 ms".
  - This is the same class as H10's documented 200–300 ms alignment window. The docs state it.
- **Codex's case:** the stats thread is delayed 3 s, and a 2.2 s blackhole is averaged into one interval. That interval has `d = 3 s > 150 ms`, so the windows it meets cannot PASS: VOID.

#### 2. The tail check becomes a byte count (C-N2, C-N3, R-N4, R16 (a))

The tail check asks whether traffic flowed in `[tail0, t1)`. The metric is now

`rate = bytes in the tail / (t1 − tail0)`,

summed over every stream's intervals, each interval placed on its own span. No `sum` field is used.

- **Bytes are counted inside their own span.**
  - A write is counted when `send()` returns (`iperf_tcp.c:110`).
  - In `iperf_stats_callback`, the per-stream count is read (`iperf_api.c:3651`) before that stream's end stamp (`:3663`). It is reset (`:3749`) after that stamp, in the same pass.
  - So an interval's bytes were counted within `[s, e]`. Bytes counted between the read and the reset are lost, which only undercounts.
  - Undercounting errs low, which is safe for PASS. For FAIL, every interval that meets the tail is counted in full (below), so the loss cannot manufacture a FAIL either.
  - The quantity is still iperf3's own sender-side count, as since v1. v3 changes where it is placed in time, not what it counts.
- **Monotone in membership, so correlations are irrelevant.**
  - Let `C` be the intervals certainly inside the tail: `L + s − δ ≥ tail0` and `U + e + δ ≤ t1`.
  - Let `M` be the intervals that possibly meet it: `L + s − δ < t1` and `U + e + δ > tail0`.
  - Every admissible history puts `C`'s bytes inside the tail, and nothing outside `M` can contribute.
  - So the true rate lies in `[Σ_C b / T, Σ_M b / T]` for every joint placement of epoch and endpoint residues, whatever their correlations.
  - Removing an interval can never raise this metric, so the mean-over-intervals defect cannot recur.
- **Verdict:**
  - PASS needs `Σ_C b / T ≥ low_bps`.
  - FAIL needs `Σ_M b / T < low_bps`.
  - Otherwise VOID, with the reason carrying both bounds and `U − L` (R16 (a)).
  - There is no empty-mean shortcut: an empty `C` gives 0, which cannot PASS, and FAIL is judged on `M` alone. The `or 0.0` at rg_move_soak.py:1112 goes (R-N4).
- **Codex's N2 example:** eight certain intervals at 1.1 Mbit/s and one uncertain zero give `Σ_C b / T = 0.88 Mbit/s`, so not PASS.
- **Codex's N3 example:** the later stream's interval `[10.051, 11.151]` is not in `C`, so it is not PASS. It also fails section 1.
- The ICMP tail check (v2 §3.5) is existential: one reply certainly inside. That is monotone already.

#### 3. Aggregate outage and stream identity (C-N3, C-N7, R-N5)

- **Aggregate outage.**
  - The facts already word it as "every stream under `low_bps`". It is now computed as exactly that: the overlap of every stream's low run, each run on its own spans.
  - All streams share one epoch, so the overlap length is computed in offset space and `E` cancels. Its uncertainty is the `±2δ` of section 2.7 in v2.
  - Certain overlap uses inner bounds (the latest start and earliest end). Possible overlap uses outer bounds.
  - Attribution to windows uses `[L + ·, U + ·]` as in v2.
- **Stream identity and precedence:**
  1. **Prior certain FAIL survives.** A layout violation at interval event `n` makes the family's iperf3 timing unusable from `n` on. Every bound is recomputed from the valid prefix `[0, n)`. `U` from fewer events is larger, so looser, and still sound. FAIL evidence certified on that prefix stands. Windows the prefix does not cover are VOID unless they FAIL.
  2. **Present, then gone: a dead stream.**
     - A stream in the `start` event's connected set that reported before and is absent from an event counts as low, as today, and FAILs once over the COST cap.
     - With no span of its own, it is placed on that event's other streams' spans: the run's certain end is the minimum end over the present streams, and its possible end is the maximum.
     - A stream that reappears afterwards is a layout violation from that event on (rule 1).
  3. **Absent from the start: layout VOID.** That means a connected socket missing from the first interval, or a socket id never announced in `start`.

#### 4. Death time from an observed exit (C-N6, R-N6 on `I`)

- Generators are no longer `exec`'d. The launch shell runs the generator as a child, `gen & pid=$!`, and records `pid` and its start tick for the stop's identity check, as `pid_record_command` does today. It then waits for it, `wait "$pid"`, and logs `EXIT <rc> <m1> <boot> <m2>`.
  - For iperf3 the line goes through the same pipe and is stamped by the reader.
  - For the probe it is appended to `icmp.log`.
- **Death range:** from the generator's last liveness evidence to its `EXIT` stamp.
  - For iperf3, the last liveness evidence is `L + e_last − δ`; for the probe, its last `S`, `X` or `R` stamp.
  - With no `EXIT` line (the wrapper itself died), the range runs to the first later observation that the generator was gone: `STOPPED`'s alive list, or the watchdog marker. Failing both, it runs to the end of the run. The range is recorded in `result.json`.
- **Charge:**
  - **FAIL** every window the death range meets. Over-attribution is documented: an unresolved range can charge more than one move, and the run FAILs either way.
  - **VOID "after"** for windows wholly after the range.
  - **Covered** for windows wholly before the range.
  - The requested period `I` no longer appears anywhere.
- How the generator ended (`end`, the SIGINT text, `END sigint`, `END error`) is classified exactly as in v2.

#### 5. Probe receive contract (C-N5, R-N1, R-N6)

- **IPv4 (checked by the probe).** On Linux the kernel does not check the ICMP checksum for a raw IPv4 socket:
  - `ip_rcv_core` validates only the IP header checksum (`net/ipv4/ip_input.c:515-516`, v6.18);
  - fragments are reassembled before local delivery (`:255-256`);
  - `raw_local_deliver` hands the datagram to raw sockets ahead of the ICMP handler (`:193`);
  - `raw_rcv` / `raw_rcv_skb` queue it with no ICMP checksum check (`net/ipv4/raw.c:296-325`).

  So the probe requires all of the following:
  - version 4, `IHL ≥ 5`, `IHL × 4 ≤` the datagram length;
  - total length equal to the bytes received;
  - protocol 1;
  - not a fragment (MF = 0, offset = 0);
  - an ICMP length of exactly 64 (8 bytes of header plus the 56-byte payload);
  - the IP header's source equal to the target;
  - the ones'-complement sum over the ICMP message equal to `0xffff`.

  A failure is counted in the `C` line as `bad_csum` or `bad_frame` and never accepted. IP options (`IHL > 5`) are parsed, not rejected.
- **IPv6 (checked by the kernel, with citations).** For an `IPPROTO_ICMPV6` raw socket:
  - `rawv6_init_sk` sets `checksum = 1, offset = 2` (`net/ipv6/raw.c:1180-1182`);
  - `IPV6_CHECKSUM` at the `IPPROTO_IPV6` level cannot turn it off for ICMPv6 (`:998`);
  - `rawv6_rcv_skb` drops a datagram whose checksum fails before queueing it, and counts it as a socket drop (`:362-366`);
  - `rawv6_recvmsg` verifies it again on copy (`:461-470`, `csum_copy_err` at `:500`).

  The probe still requires type 129, code 0, an ICMPv6 length of 64, and source equal to the target.
- **One rule replaces "unsent lseq" and "stamp equals S" (R-N1):** the payload's `(lseq, s)` must equal an `S` line's `(lseq, s)`. Its mutant drops that combined rule, so it can be killed.
- **Addresses (R-N6):** they are compared as `ipaddress` objects, never as strings.
- **Local drops (R-N6):**
  - The probe sets `SO_RXQ_OVFL` (40) and reads its cumulative drop count from `recvmsg` ancillary data, logging it in the `C` line.
  - A drop counter that rose inside a candidate FAIL interval (v2 §3.4) makes that interval uncertain, so VOID, not FAIL. It never affects PASS.
  - On IPv6 the same counter includes checksum drops, so a corruption storm on v6 VOIDs where v4 would FAIL. Both are fail-closed, and the asymmetry is documented.

#### 7. Suspend witness: accepted limit, arithmetic corrected (C-N1)

- **Detection.** The kernel's `boot − mono` offset never decreases (v2 §5.2). A suspend is detected iff, for some witness `j`, its lower bound exceeds the smallest upper bound of any earlier witness. That catches a cumulative increase spread over several windows, which an adjacent-pair check misses.
- **The undetected amount is bounded.**
  - A cumulative suspend between witnesses `i` and `j` that goes undetected is less than `w_i + w_j`, where `w = m2 − m1` is a witness's own width. So the bound is the sum of two widths, not one width.
  - `result.json` records `w_max` and the bound `2·w_max`.
  - R16 measured read gaps of 2.8–6.8 µs on the LAN hosts, so the bound is on the order of 15 µs.
- **The limit, per the orchestrator.** A bare-metal LAN host suspending mid-gate is outside the lab envelope, so an undetected suspend below that bound is an accepted limit, documented with its size.
  - Carrying the bound into every PASS comparison would close it at negligible cost. It is left out because the limit is accepted.
- **Coverage.** Witnesses come from `LAUNCH`, every `BOUNDARY`, the probe's header and `END`, every `EXIT` (section 4), `STOPPED` and the watchdog marker. `STOPPED` is taken after the final tail, so the run is covered through its end.

#### 1. Sender accounting can credit bytes the network never carried (Codex 1 + R-N7: one defect, two mechanisms)

**The mechanisms, accepted.**
- **Late accounting (Codex):** each stream thread calls `Nwrite` and only afterwards increments `bytes_sent_this_interval` (`iperf_tcp.c:103`, then `:109-110`). Codex found the same separation in both cached LAN binaries (tcp `0x1c297` against `0x1c270`; loss `0x20f9d` against `0x20f7c`). A thread descheduled between the two credits a write that completed before an outage to a later interval.
- **Refill (R16):** a stream thread delayed across the start of an outage resumes into a send buffer with free space. It writes, and counts, up to that free space although nothing is delivered.

**Why the bound is per stream.**
- Late accounting holds at most one write per stream, because the thread increments before its next write: at most one `-l` block.
- A refill writes at most the free send buffer. iperf3 is not run with `-w`, so `SO_SNDBUF` is unset, autotuning keeps `sk_sndbuf ≤ tcp_wmem[2]`, and unacked data keeps its space until ACKs return, which in an outage they do not.
- So every maximal period with no TCP progress can carry at most `A = tcp_wmem[2] + blksize` unverifiable counted bytes per stream.

**The allowance.**
- At preflight the soak reads `tcp_wmem` on the LAN host (`/proc/sys/net/ipv4/tcp_wmem`, which also governs IPv6 TCP). A value that cannot be read gives VOID. R16 measured 4 MiB on all three hosts.
- `blksize` comes from iperf3's own `start` event (`test_start.blksize`, the configured `-l`; 128 KiB here).
- `A`, both of its inputs and `n_streams` are recorded in `result.json`.
- An iperf3 command line carrying `-w` or `--window` gives a preflight VOID, because the `tcp_wmem` bound would no longer hold.
- The allowance is never hard-coded.

**Applied on the PASS side only.** It is subtracted from every positive certificate, so a FAIL never needs it.
- **Tail (v3 §2).**
  - PASS needs `8·(Σ_C b − n_streams·A)·10^9 ≥ low_bps·T_ns`, in integers.
  - FAIL keeps `Σ_M b`, plus section 2's discrepancy.
  - R16's run over the 84 logs: 0 of 3,870 tails flip. The minimum v4 tail was 2172.6 Mbit/s against an 8-stream allowance of about 278 Mbit; the minimum v6 tail was 299.9 against about 70.
- **"Not low" for the all-stream outage, and per-stream stalls (v3 §3).**
  - A stream window `W` (whole intervals on that stream's own spans) is **possibly an outage** when `Σ_W b ≤ low_bps·dur(W) + A`.
  - Equivalently, an interval or window counts as "not low" for a PASS only after `A` is subtracted.
  - **Per stream:** the longest possible-outage window comes from prefix sums `P_j` of `(b_i − low_bps·d_i)`. For each end `j`, the earliest start `i` with `P_i ≥ P_j − A` is found by binary search over the running maximum of `P`. That is O(n log n), and it is exact for "longest window with sum ≤ A".
  - **Aggregate:** for each stream, take the union of its maximal possible-outage windows. Intersect those unions across streams. The longest contiguous segment is the possible all-stream outage.
  - This over-approximates the true common windows, so it is conservative for PASS, and it is used only for PASS.
  - Certain outages stay v3's certain-low runs, and their overlap, with section 2's discrepancy.
- **Verdict per budget:**

  | Check | Certain | Possible only | Neither |
  |---|---|---|---|
  | all-stream outage > 1000 ms | FAIL | VOID | PASS |
  | a stream > COST cap 10 s (did not recover) | FAIL | VOID | — |
  | more than one stream > 2000 ms | FAIL | VOID | — |
  | one stream > 2000 ms (the COST line, per R16) | COST | COST | PASS |

  R16 measured the cost on the 84 logs: 0 aggregate-outage flips, 0 cap flips, and 5 of 420 per-stream series moved across the 2 s line, so those become COST.

**v3 §1's resolution sentence, restated.**
- Bound what a sender can count without delivery at `A` per stream per no-progress period.
- Then a window that PASSes has no TCP outage longer than its budget plus `2·(P + B) = 300 ms`. The 300 ms is the two partial intervals at the outage's ends, made exact in section 5.
- An outage during which a stream counts more than `A` is outside the certificate. That needs a sender writing more than its own send buffer with no ACKs returning.
- The docs state the bound and its byte premise together.

**Cells (the fake gains a sender-accounting delay, independent of the statistics-thread delay of v3 §1):**

  - With the allowance it is VOID.

#### 2. Increments discarded between the read and the reset (Codex 2)

`iperf_stats_callback` reads the interval counter (`iperf_api.c:3651`) and resets it (`:3749`) without a lock. A write accounted between the two appears in no interval, so `Σ_M b` is not an upper bound.

**The lossless total.**
- The same increment site also adds to the cumulative `bytes_sent` (`iperf_tcp.c:109`), which is never reset (we do not use `-O`).
- Sender-side results are not overwritten by the exchanged peer results: on a local sender (`if (sp->sender)`, `iperf_api.c:2847`) the peer's count goes to `bytes_received`, and only the `else` branch (`:2879-2881`), the local receiver's, writes `bytes_sent`.
- The cumulative total is printed as `end.streams[].sender.bytes` (`:4144`, `:4193`).
- iperf3 also prints `end` after the soak's SIGINT: `iperf_got_sigend` runs the reporter for the client (`:5069-5078`).

**Reconciliation.** Per stream, `D_s = end.sender.bytes − Σ_i b_i`, where `D_s ≥ 0` (anything else is a layout VOID).
- **FAIL-side upper bounds add `D_s`, wherever it may have fallen.**
  - Tail FAIL needs `8·(Σ_M b + Σ_s D_s)·10^9 < low_bps·T_ns`.
  - An interval counts as certain-low only if `b_i + D_s < low_bps·d_i`, so the certain stall and outage runs use that test.
- **When `D_s` cannot be bounded** (no `end` record: the generator died, or the log was cut off), a FAIL that rests only on counters becomes VOID unless ICMP or UDP evidence certifies the same window independently. "Counters only" means the tail, the all-stream outage and the stall FAILs. A death FAIL (v3 §4) is not counter evidence and stands.
- **Bytes to bits.** Every comparison of a byte sum with `low_bps` is `8·bytes·10^9` against `low_bps·duration_ns`, in integers. `bits_per_second` from the JSON is never used for verdicts.
- **Cell: read-to-reset delay.** In the tail, the statistics thread reads 0, is delayed 40 ms (so the interval stays ≤ 150 ms), and the sender accounts a large burst that is then reset. Every interval meeting the tail shows 0 bytes. `end.sender.bytes` exceeds the interval sum. Expected: not FAIL (VOID), with no ICMP failure.
- **Control.** No discard: `D = 0` and a FAIL.
- **Its twin.** The same, with no `end` record and healthy ICMP: VOID.
- **Mutants:** dropping `D` from the bound; ignoring a missing `end`.

#### 3. Local receive drops (Codex 3, replaces v3 §5's drop rule)

**Observation.** The probe reads its own socket's drop count from `/proc/net/raw` or `/proc/net/raw6`, matching its socket inode (`os.fstat(sock.fileno()).st_ino`).
- Both files print `sk_drops_read()` per socket: `net/ipv4/raw.c:1033-1049`, and `raw6_seq_show` through `__ip6_dgram_sock_seq_show` (`net/ipv6/datagram.c:1048-1071`), v6.18.
- The read is bracketed by monotonic stamps and logged as `C <c1> <c2> drops=<n> …` once per second and at `END`.
- This replaces the `SO_RXQ_OVFL` ancillary snapshot. That snapshot arrives only with a later delivered packet, so a corruption-only suffix would never report its own count.
- IPv6 checksum drops are counted there too (`net/ipv6/raw.c:362-366`).

**Attribution.**
- Drops that possibly fall in a free interval `(x, y)`: `k ≤ D(first reading with c1 ≥ y) − D(last reading with c2 ≤ x)`.
- With no reading after `y`, the `END` reading is used. With no `END` reading, `k` is unbounded.
- A count that decreases (a wrap, or an inode mismatch) also makes `k` unbounded.

**The FAIL rule.**
- **A gap FAIL stands** if no placement of `k` hypothetical arrivals inside `(x, y)` brings every sub-gap within budget: `y − x > (k + 1)·budget_ns`. One drop cannot rescue a 10 s gap.
- Otherwise, or with `k` unbounded, that gap is VOID.
- **The ICMP-tail FAIL** ("no reply in the tail") stands only if `k = 0` for the tail, because one reply would pass it.
- Independent FAIL evidence is always kept. Drops never affect PASS.

**Cells:**
- a 10 s free interval with one possible drop: FAIL;
- a 1.5 s free interval with one possible drop: VOID;
- a tail with one possible drop: VOID;
- no reading after the gap and no `END`: VOID;
- v6, in the runner netns: a bad-checksum reply is never delivered, and the `/proc/net/raw6` count rises (no later packet is needed).

**Mutant:** the blanket "any drop gives VOID" rule, killed by the 10 s cell.

#### 7. The RTT VOID region and the delayed-previous-read twin (Codex 9)

- **The qualified statement.** For adjacent brackets around a gap, the certain free interval is `s_next − r_prev`. Against the true arrivals it loses BOTH `(r_prev − a_prev)`, the previous reply's read delay, and `(a_next − s_next)`, the next reply's RTT.
- So a true gap `G` is VOID rather than FAIL when `budget < G ≤ budget + (r_prev − a_prev) + (a_next − s_next)`.
- R16's measured RTT (max 191 ms) covers only the second term. Receive scheduling can enlarge the first.
- **New cell, the delayed-previous-read twin of the 1.3 s FAIL cell.** The same 1.3 s outage, with the previous reply read 200 ms late and the next RTT 200 ms, leaves a certain free interval of 0.9 s: VOID.
- **Existing cell.** The prompt-read 1.3 s cell stays FAIL.

#### 8. SIGINT under dash (R-N8)

R16 measured this on tcp:xpf-testrunner2. `/bin/sh` is dash, and with job control off, `gen &` children start with SIGINT ignored. CPython installs its `KeyboardInterrupt` handler only when the disposition is SIG_DFL, so v3 §4's launch would leave a `KeyboardInterrupt` probe deaf to the soak's stop and to the watchdog. iperf3 is unaffected, because it installs its own handler.

- **The probe** installs `signal.signal(SIGINT, …)` and `signal.signal(SIGTERM, …)` at start, which override an inherited SIG_IGN. Each logs `END sigint` or `END sigterm` and exits 0.
- **Cell, on a runner under dash.** It launches the real probe exactly as the soak does (`sh -c 'python3 -u icmp_probe.py … & pid=$!; …; wait "$pid"'`), confirms SIGINT arrived ignored in `/proc/<pid>/status`, sends SIGINT, and asserts `END sigint`, a zero exit, and an `EXIT 0` stamp.
- **iperf3 control.** The same launch of iperf3 stops with its own SIGINT text.
- **Mutant.** A probe relying on `except KeyboardInterrupt` fails the cell.

#### 9. A LAN-local file for the iperf3 reader (R-N9)

- iperf3's main thread runs the statistics timer (`iperf_client_api.c:741`) and writes the JSON with `--forceflush` (`:208`). A reader streaming over `incus exec` could back-pressure through the 64 KiB pipe into that thread. That would stretch intervals, and VOID windows, because of a slow controller.
- So the stamping reader writes, line-flushed, to a LAN-local file beside `icmp.log`, and the controller fetches it after the stop. `LAUNCH` and `EXIT` still pass through the reader.
- **Cell.** A consumer that stalls for 2 s does not lengthen any interval.
- **Mutant.** A reader piping to a stalled consumer produces an interval over `P + B`, so the cell kills it.
