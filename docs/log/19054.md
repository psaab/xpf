# Issue #19054: H11 soak's traffic budget ran out; uncovered moves scored FAIL

## Why

- **Timestamp**: 2026-11-09 PST
- **Action**: In the wave-1 gate (loss, master 602f946af5), `SOAK_MOVES=200
  SOAK_SLEEP=5` ended 182 PASS, 18 FAIL. All 18 FAILs were moves 183-200.
  - iperf3 and ping had exited. The run length was estimated as moves x
    (sleep + converge + 4 s) + 60 s = 2,860 s, while the moves took about
    16 s each on average, rising from about 11 s to 38 s near the end.
  - The windows the traffic did not cover were scored FAIL ("did not cover
    the move window", "traffic did not follow").

## What

- **File(s)**: `test/incus/rg_move_soak.py`, `test/incus/rg-move-soak.sh`,
  `test/incus/rg_move_soak_test.py`, `docs/ha-rg-move-correctness.md`
- **Run length**: the generators run until the soak stops them (it always
  does, after the last window). Their `-t`/`-w` cap is now 120 s per RG
  move + 600 s (`TRAFFIC_S_PER_MOVE_CAP`, `TRAFFIC_S_SLACK`), and
  `SOAK_TRAFFIC_S` overrides it. `info.traffic_s` records the value used.
- **Uncovered window = VOID**: `move_verdict` scores a move whose window
  ping or iperf3 did not cover as VOID, never PASS, COST or FAIL.
  - The reason names the cause, recorded per family by `finish()` as
    `uncovered_cause`: the traffic run's planned end came first
    (`traffic_end_lan`), or a generator stopped early (with iperf3's error
    text).
  - Every other reason is kept as "unscored evidence: ...".
- **Fake**: `FakeCluster`'s generators now stop after their own `-t`/`-w`
  seconds, as the real ones do. `run_fake` accepts `traffic_s`.
- **Cells**, `TrafficCoverage19054`:
  - `test_no_uncovered_move_is_scored`: a 12 s traffic run under 3 moves;
    every uncovered move is VOID with the cause, and there are no FAILs;
  - `test_moves_slower_than_the_old_estimate_stay_covered`: 6 moves of
    about 26 s each (`SlowCliCluster`), which the old run length cannot
    cover; all are covered and the run exits 0.
- **Changed existing cell**: `MoveVerdict.test_traffic_generator_death_fails`
  asserted that an uncovered window FAILs, which is the defect #19054
  removes. It is now `test_traffic_generator_death_is_void_never_pass`: the
  same two inputs (iperf3 or ping not covering) must be VOID, with the
  "did not cover" reason, and never PASS.
- **Not fixed here**: why moves slow down over a long run. #19054's
  comment points at per-move work that scales with the run. That is
  outside this change, which makes the soak correct however long the moves
  take.

## Validation

See the commit message (runner RED/GREEN and mutants).

## Risk

Harness only. A long run's tail moves are now covered, and are scored,
where before they were FAILed. If the generators die, the moves they leave
uncovered are VOID, which makes the run exit 2, so a run is never a false
PASS. A dead controller leaves iperf3 running on the LAN host for up to the
cap. That risk already existed with the old 2,860 s figure for 200 moves.
