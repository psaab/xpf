# #14639 — WireGuard under-load admission: key IPv6 on /64, evict LRU at cap

## Scope and verified mechanism

At base `042b46dd27` (branch point; since drifted, see Validation),
`userspace-dp/src/afxdp/wg/cookie.rs`:

- `SOURCE_TABLE_MAX = 2048` with a doc claiming overflow "evicts the
  least-recently-refilled bucket" — true of the cookie-reply table,
  false of the handshake table.
- `source_handshake_allowed(src_ip: IpAddr)` keyed `handshake_buckets`
  on the full `IpAddr` (full IPv6 /128), returned `false` for a new
  source at the cap, and GC reclaimed only entries idle ≥ 1 s.
- `source_reply_allowed` had the same full-address keying (with LRU
  eviction already present).
- The under-load trigger is 25 type-1/s per tunnel counting junk too,
  so an unauthenticated attacker who knows the tunnel public key and
  has IPv6 reach to the listen port — one SLAAC /64 suffices — can
  refresh 2048 distinct /128s within the 1 s GC window and keep the
  handshake table permanently full. Every legitimate peer in another
  /64 then fails `source_handshake_allowed`, loses rekey, and existing
  sessions die at REJECT_AFTER_TIME (180 s). This diverges from the
  Linux reference ratelimiter, which keys IPv6 on /64 ("Only use 64
  bits, so as to ratelimit the whole /64", `ratelimiter.c`), and from
  the module's own documented eviction behaviour.

Consumers: the sole production callers are in
`userspace-dp/src/afxdp/wg/engine.rs` `classify_initiation` —
`source_handshake_allowed(from.ip(), now_ns)` after MAC1+MAC2 verify
(valid-MAC2 → Noise admission) and `source_reply_allowed(from.ip(),
now_ns)` before building a cookie reply. Both pass `from.ip()`, so
keying inside `CookieChecker` covers every consumer; no signature
change was needed. Cookie MAC binding (`endpoint_cookie_bytes`,
IP+port) is untouched — aggregation applies only to the rate-limit
tables, not to cookie issuance/verification.

## Fix and decision

In `userspace-dp/src/afxdp/wg/cookie.rs`:

- New `source_bucket_key(IpAddr) -> IpAddr`: IPv6 → /64 (host bits
  zeroed); v4-mapped v6 → canonical v4 first (mirroring
  `endpoint_cookie_bytes`/`canonicalize_endpoint`); IPv4 → /32.
  Applied at the top of both `source_reply_allowed` and
  `source_handshake_allowed`, so one /64 shares one reply budget and
  one handshake budget, and the 2048-entry cap now bounds distinct
  /64s / v4 hosts instead of /128s.
- New `evict_lru_if_full` helper (least-recently-refilled by
  `last_ns`, the same discipline the reply table already used):
  `source_handshake_allowed` now evicts instead of returning `false`
  for a new key at the cap; `source_reply_allowed` uses the same
  helper. The memory bound is unchanged (never more than
  `SOURCE_TABLE_MAX` entries per table).
- Corrected the false `SOURCE_TABLE_MAX` doc and the
  `source_handshake_allowed` doc; module doc gained a #14639 note.
- `source_contains_for_test` canonicalises its argument through
  `source_bucket_key` so test lookups match stored keys.

Deliberate scope cuts / trade-offs:

- Hosts inside one /64 now share one budget (reference behaviour);
  hosts in different /64s and every distinct v4 host keep independent
  budgets. A legitimate peer behind the same /64 as an attacker can
  still be starved by that attacker — unavoidable under /64
  aggregation and identical to the Linux reference.
- Eviction churn: an attacker cycling ≥2048 distinct /64s can evict a
  legitimate bucket, but the evicted peer's next initiation simply
  creates a fresh full bucket (and may evict the attacker's LRU
  entry in turn) — admission is never permanently denied, and table
  memory stays bounded. This strictly dominates fail-closed refusal.
- NOT changed: cookie MAC binding (still full IP+port), MAC2
  verification, under-load trigger, GC interval, rates/bursts,
  counters, and the engine call sites.

Tests updated/added in `cookie_tests.rs`:

- `handshake_source_bucket_burst_and_table_cap` (#9908 pin): fill now
  uses distinct /64 keys; the over-cap assertion is inverted from
  refusal to LRU admission with the table still at the cap.
- `handshake_slash64_flood_does_not_lock_out_other_prefix_14639`:
  one /64 refreshing 2048 /128s (both gates) → a peer in another /64
  is admitted by both gates; positive control: after a GC interval
  the same peer is still admitted.
- `handshake_slash64_shares_one_budget_14639`: rotating /128s inside
  one /64 draw exactly `SOURCE_HANDSHAKE_BURST` (and, reply side,
  `SOURCE_REPLY_BURST`) admissions; a different /64 is unaffected.
- `handshake_v4_mapped_shares_v4_budget_14639`: exhausting the v4
  bucket also exhausts its `::ffff:` mapped form.
