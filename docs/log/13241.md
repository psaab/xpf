# api: avoid duplicate request credential verification (#13241)

## Why

`principalFrom` checked the listener credential before resolving the principal, then the off-box credential path checked it again to gate locality enumeration, checked it again after enumeration, and repeated the live check on pass two. For bcrypt-backed Basic credentials and API keys this repeated expensive hash verification for one mutation request.

## What

- Added requestIdentity-scoped successful credential memoization.
- Reuse requires unchanged Authorization/X-API-Key headers and semantic equality across every AuthConfig map, not snapshot pointer equality. Expiry timestamps compare by instant. This preserves reuse for unrelated snapshot republishes while ensuring credential rotation, revocation, class or expiry-policy changes force verification against live policy.
- Memo entries use the matched credential's own expiry, so an unrelated expired user or key does not disable reuse. Failed checks are not cached; published AuthConfig maps are referenced without deep-copy allocation.
- Added a per-request credential-resolver test seam and regression coverage for same-policy reuse, semantic policy changes, memo expiry, and expired credentials.
- Existing auth policy checks and locality revalidation remain on both adjudication passes; the memo only avoids repeating verification when credentials and policy are unchanged.

## Risk

A successful credential result is reused only inside the current request and only while the presented headers, semantic policy, and expiry remain current. No process-global cache or verifier instrumentation is introduced.
