# Issue #17174 — R4-Q16-03: dead `RulePrefixBudgetExceeded` variant and stale "pure code-motion" header in `policy_snapshot_error.rs`

- **Issue:** `SnapshotIntegrityError::RulePrefixBudgetExceeded` was
  never constructed anywhere in the crate, but its doc comment and
  `Display` arm described present-tense behaviour — that an
  over-budget policy-rule literal address side rejects the whole
  snapshot. #15091 deliberately did NOT implement that: rule literal
  sides keep the infallible `PrefixSet::from_prefixes` /
  `from_v3_literals` factories, whose over-budget posture is
  fail-closed `MatchNone` (the side matches nothing), and only
  feed-backed address-book rows hard-reject via
  `AddressBookPrefixBudgetExceeded`. A reader of the rejection enum
  therefore got a false picture of fail-closed coverage for rule
  literals. Separately, the file header still claimed the file was a
  verbatim "Pure code-motion: no behavior change" relocation out of
  the policy parser, although the type is now the crate-wide
  snapshot-rejection type (raised by the policy parser and by the
  forwarding / CoS / NAT / interface / route / tunnel snapshot
  builders, and re-exported as `crate::policy::SnapshotIntegrityError`).

- **STEP-0 re-check on current `origin/master` (47a93d76fd):**
  defect live. `grep -rn RulePrefixBudgetExceeded userspace-dp/src`
  finds only the variant definition
  (`policy_snapshot_error.rs:1025`) and its `Display` arm
  (`:1046`) — no construction site. The header at `:1-7` still
  reads "Pure code-motion: no behavior change". The surviving
  sibling variant `AddressBookPrefixBudgetExceeded` is constructed
  in `policy.rs` (book-build loop, `try_from_v3_literals` map_err)
  and pinned by `test_book_prefix_budget_exceeded_rejected_15091`.

- **What:** Deleted the `RulePrefixBudgetExceeded` variant and its
  `Display` arm (the fix direction's first option; constructing it
  would have reversed #15091's recorded decision to keep rule
  literals on the infallible `MatchNone` factories, a behaviour
  change this dead-code/docs issue does not call for). Extended
  the doc on the surviving `AddressBookPrefixBudgetExceeded`
  variant to state explicitly that only address-book rows
  hard-reject on the merged-range budget, that rule literals are
  NOT rejected there (infallible factories, over-budget →
  fail-closed `MatchNone`), and that there is deliberately no
  rule-literal counterpart variant — so the enum no longer implies
  rejection coverage that does not exist. Rewrote the file header
  to describe the file as it is now: the crate-wide
  snapshot-rejection type (#1606), raised by the policy-snapshot
  parser and the forwarding/CoS/NAT/interface/route/tunnel
  builders, whole-snapshot fail-closed, defined in the sibling
  file to keep `policy.rs` under the LOC threshold and
  re-exported via `crate::policy`. No "Pure code-motion" claim
  remains. Historical `docs/log/15091.md` is left untouched (it
  already records the variant as merely "reserved", which was
  accurate at the time).

- **Acceptance:**
  - `grep -rn RulePrefixBudgetExceeded userspace-dp/src` returns
    no matches; the header no longer says "Pure code-motion".
  - `cargo check` on the crate emits no `never constructed`
    warning for `policy_snapshot_error.rs` (see Tests).

## Risk

Dead-code + documentation only: no construction site existed, so
no runtime behaviour, wire format, or fail-closed posture changes.
The one risk was an exhaustive `match` on the enum breaking when
the variant was removed — the only match over the variant was its
own `Display` arm, removed in the same change, and `cargo check`
confirms the crate still compiles. Rule-literal over-budget
handling is intentionally unchanged (`MatchNone`, #15091); whether
`MatchNone` on a deny rule is the right long-term posture is the
separate unsettled policy question noted in the issue and is out
of scope here.
