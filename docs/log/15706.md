# Issue #15706: compileSNMP two-level containers and trap-group merge

- **Timestamp**: 2026-10-19
- **Problem**: `compileSNMP` in `pkg/config/compiler_system.go` peeled only the first child of two-level containers (`len(child.Keys) < 2` → `child.Children[0].Children`), so `client-list { <L> { ... } }` compiled to an empty `ClientLists` map (referencing communities then rejected as unresolved / quarantined), and the 2nd+ children of `community { <c> { ... } }`, `trap-group { <g> { ... } }`, and `v3 usm local-engine user { <u> { ... } }` were silently dropped. Trap-group handling also created a fresh `SNMPTrapGroup` per block and validated zero targets per block, so a same-name pair split across blocks (first block carrying only `version`) wrongly rejected instead of merging (the #9023 AST fold masked this for tree-compiled configs, but direct `compileSNMP` callers saw it).
- **Fix (compiler)**: Use `namedInstances` to peel two-level containers for `client-list` (pre-pass), `community`, `trap-group`, and `v3 ... user` (in `compileSNMPv3`), synthesizing the named node shape (`Keys[1] == <name>`) where the downstream reader expects it. In `case "trap-group"`, look up or create `snmp.TrapGroups[tgName]`, accumulate `Targets`/`Categories` across same-name blocks, expand flat runs via `expandFlatRun(packedBodyChildren(inst.node, schemaForPath("snmp", "trap-group")))`, update `Version` only when `nodeVal(prop) != ""`, and defer category-vocabulary + zero-target validation to a sorted post-loop pass over the merged groups. Added `sortedTrapGroupNames15706` for deterministic validation order.
- **Fix (strict gate)**: `pkg/config/compiler_validate_strict_snmpv3_level_9155.go` — recognize a nameless two-level `user { <name> { ... } }` container as starting user bodies (`isTwoLevelUserContainer15706`): `checkSNMPv3BracedKeywordsDepth14411` validates each instance as a user body instead of rejecting its protocols as "outside any user" (#14411), and `checkSNMPv3UserKeywords9155` expands the container into per-instance checks so unknown-protocol rejection still fires inside two-level users.
- **Regression check**: `go test ./pkg/config/ -run '15706|SNMP|TrapGroup|9416|5472|2990|15256|15124' -count=1` passes; full `pkg/config` suite run for comparison against the pre-existing failure baseline at this head.
- **Not changed**: Conflicting scalar children keep last-wins semantics; `#9023` duplicate-block tree fold and its diagnostics are untouched (compiler-level merge is the safety net for direct callers); unknown trap-group statements still reject strict / warn lenient per block.

## RED -> GREEN proof

- **RED** (fix stashed, tests present): `go test ./pkg/config/ -run '15706' -count=1` failed — two-level `client-list` unresolved-reference rejection, two-level community/trap-group kept only the first instance (`map[c1:...]`, `map[g1:...]`), two-level v3 user rejected by the #14411 gate, and same-name trap-group rejected with `no targets configured` on the first (version-only) block.
- **GREEN**: Same command passes after the fix; two-level instances compile with their prefixes/targets/users, same-name trap-groups merge targets/categories with version preserved from any block, and a genuinely target-less merged group still rejects strict.
