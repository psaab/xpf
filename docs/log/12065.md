# #12065 — protocol-specific redistribute maps

- **Timestamp**: 2026-10-07 (`fix/12065-redist-maps`)
- **Action**: render a distinct, filtered FRR route-map per policy/source protocol; remove the daemon-unsupported `match source-protocol` from redistribute maps and the QNH-integrated static map.

## Red before

Added `TestRedistributePolicyMapsAreProtocolSpecific12065` before the implementation and ran it against the base. It failed as expected: `TO-OSPF` attached one shared map to both `redistribute static` and `redistribute connected`; the map contained both source-specific terms and emitted `match source-protocol` clauses. The test also requires each generated map to contain only its protocol's term and no source-protocol match.

## Change

- `resolveRedistribute`, `resolveISISRedistribute`, and the BGP IPv6 resolver now attach `<policy>-<protocol>-xpf-redist` maps. Terms are filtered by normalized source protocol, global terms are retained, and `FromProtocols` is cleared before rendering.
- Policy generation emits those filtered maps and quarantines an oversized filtered expansion under its own bounded deny map. A render-side collision guard refuses generated names that normalize to an operator policy name; the commit-time reserved-suffix gate and its warning/docs now describe protocol-specific names.
- QNH metric maps use the static-only policy subset and rely on `redistribute static` to select the source rather than rendering a source-protocol match. A regression covers the QNH metric and authored metric order, omission of a connected-only term, and absence of that match clause.
- Existing render expectations for OSPF/RIP/IS-IS and quarantine reporting now use protocol-specific names. The cross-context BGP/OSPF regression still checks that BGP uses the base map while redistribution uses the deny-default protocol map.
