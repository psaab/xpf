# Production coalescers compiled in test builds (#14656)

- **Issue**: #14656 (deep-review finding Y37-01).
- **Cause**: `userspace-dp/src/policy.rs` put
  `POLICY_HIT_FLUSH_PACKETS`, the thread-local pending record,
  `record_policy_hit_counter`, and `flush_recorded_policy_hit_counters`
  under `#[cfg(not(test))]`, with a `cfg(test)` write-through twin
  (`counter.add`). `userspace-dp/src/filter/mod.rs` had the same shape for
  `FILTER_COUNTER_FLUSH_PACKETS`, `record_filter_counter`, and
  `flush_recorded_filter_counters` (test twin: `counter.record`). Both
  `cargo test` legs in the Makefile therefore never compiled or exercised
  the shipped buffering, counter-switch, generation-discard, or
  64-packet threshold-flush bodies. The issue's mutant (both production
  bodies replaced by `let _ = (counter, packet_bytes);`) survived
  `hit_count` (13 passed), `counted` (41 passed), and `established_hit`
  (3 passed), while neutering the test twins was killed — the suite
  asserted on a body that does not ship, so a recurrence of #3073/#3448
  would ship green. `policy.rs` also claimed the #3448 generation-discard
  was "unit-tested directly" while the record side was compiled out.
- **Change**:
  - `policy.rs`: factored the coalescer into `PolicyHitCoalescer`
    (pending record + `flush_packets`), compiled in every build, with
    `record()` (same-counter + same-generation continuation, otherwise
    flush/discard-then-recapture, threshold flush at 64) and `flush()`
    delegating to the existing generation-guarded
    `flush_pending_policy_hit_record`. The thread-local
    `POLICY_HIT_COALESCER` wrapper and the public
    `record_policy_hit_counter` / `flush_recorded_policy_hit_counters`
    are now single non-cfg-gated definitions used by both builds.
  - `filter/mod.rs`: same factoring into `FilterCounterCoalescer`
    (no generation guard — filter term counters have no in-place clear),
    thread-local `FILTER_COUNTER_COALESCER`, single
    `record_filter_counter` / `flush_recorded_filter_counters`.
  - Test sites that read shared counters after recording now flush the
    thread-local coalescers first (the production per-RX-batch flush in
    `worker/loop_body` already did this; unit tests must do it
    explicitly now that test builds coalesce exactly like production).
    Helpers `g9528_packets`, `rule_hits`, `lo0_term_packets`, and
    `accepting_analyzer_counter_packets` flush before reading.
- **Regression coverage**:
  - `policy_tests.rs`: `coalescer_buffers_until_flush_and_switch_14656`
    (10 buffered, switch flushes, flush lands 1), 
    `coalescer_threshold_flushes_at_64_14656` (63 buffered, 64th flushes),
    `coalescer_record_10_clear_record_5_flush_reads_5_14656` (the issue's
    decisive cell: record 10, clear, record 5, flush reads exactly 5),
    `thread_local_wrapper_buffers_until_flush_14656`.
  - `filter/tests.rs`: `filter_coalescer_buffers_until_flush_and_switch_14656`,
    `filter_coalescer_threshold_flushes_at_64_14656`,
    `filter_thread_local_wrapper_buffers_until_flush_14656`.
  - The 58 pre-existing tests that asserted on write-through counters
    (filter counted walks, CoS TX-selection, flow-cache replay, GRE/WG
    decap, NAT64, mirror, session-hit authority, etc.) now flush before
    asserting and pass against the shipped coalescer.
- **RED evidence**: Mutant M (both `PolicyHitCoalescer::record` and
  `FilterCounterCoalescer::record` replaced by
  `let _ = (counter, packet_bytes); return;`): 
  `14656|hit_count|counted` filter went from 64 passed to 46 passed /
  16 failed, including all seven new `_14656` cells'
  record-side assertions (`coalescer_buffers_until_flush_and_switch_14656`,
  `coalescer_record_10_clear_record_5_flush_reads_5_14656`,
  `coalescer_threshold_flushes_at_64_14656`,
  `thread_local_wrapper_buffers_until_flush_14656`, and the filter twins).
  On current master before the fix the same mutant survived
  (13/41/3 passed, per the issue probe).
- **GREEN evidence**: After restoring the production bodies,
  `14656|hit_count|counted|established_hit` reports 64 passed / 0 failed;
  the 60 targeted pre-existing + new cells report 60 passed / 0 failed
  (`--test-threads=1`, debug profile,
  `CARGO_TARGET_DIR=/var/worktrees/.cache/cargo-14656`).
  A full `--bin xpf-userspace-dp --test-threads=1` run on an earlier head
  showed 55 failures that are also present on clean `origin/master`
  (54 base failures: BPF shim names, coordinator reconcile, runtime-view,
  session-delta golden, etc.) plus timing-sensitive cells; the only
  new-vs-base failures were the coalescer cells fixed above. Note:
  clean master currently does not compile its test binary
  (`ha_tests.rs` calls `publish_row` with the pre-#14650 arity) — that
  pre-existing break was worked around locally for the runs above and
  reverted; it is not part of this change.
- **Blast radius / risk**: Production behaviour is unchanged by
  construction — the factored `record()` bodies are the former
  `cfg(not(test))` bodies verbatim, and the thread-local wrappers keep
  the same per-worker coalescing and per-RX-batch flush cadence.
  Test builds now buffer up to 64 packets before counters become
  visible, so any future test that records and reads without flushing
  will read a stale zero — the flush-before-read pattern is documented
  at each patched site with a `#14656` comment. No wire, Go, or
  snapshot-format change.
