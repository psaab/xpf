# Issue #15213 — VRRP diagnostics/visibility cohort (A25-03, A25-04, A25-06)

## Why

- **A25-03:** a #14404-held RETH candidate that hears no peer retries
  `becomeMaster` on every master-down horizon and logged "refusing
  MASTER" at INFO each time — ~8 lines/s/instance of journal flood
  (legacy RETH-VRRP mode; no forwarding effect).
- **A25-04:** `Status()` and every surface reusing it printed the
  configured `cfg.Priority`; the advertised (tracked) priority and the
  track state were never exported, so a track-demoted MASTER displayed
  100 while advertising 50 — a diagnostic lie hiding A25-01-class
  misbehaviour.
- **A25-06:** `ResignRG` wrote `cfg.Priority=0` before the run loop
  consumed `resignCh`; if the advert timer won the select, a MASTER
  still holding its VIPs advertised priority 0 and the peer took the
  1ms takeover path — a probabilistic two-owner window during planned
  failover.

## What

- `instance_transition.go`: the kernel-hold refusal logs INFO once per
  hold episode (`kernelHoldRefusalLogged`, cleared by
  `setKernelUpgradeHold(false)`), Debug thereafter.
- `track.go`: `prioritySnapshot()` is the single source for
  configured/effective/trackDown (getPriority delegates, with the
  pending-resign carve-out); `manager.go` `Status()` prints the
  effective priority plus `, track down`, and `InstanceStates()` /
  `emitEvent()` populate new `VRRPEvent.EffectivePriority` /
  `TrackDown` fields.
- `manager.go` `ResignRG` + `instance_resign.go`: priority 0 is
  stashed as a pending resignation (`beginResign`) instead of
  overwriting `cfg.Priority`; `becomeBackup` applies it
  (`applyPendingResign`) after the VIP removal, and
  `masterDownInterval` uses the stashed 0 while pending so the
  resigning instance cannot re-elect itself. The #6177 barrier test's
  synchronous-priority-0 control was updated to the pending marker
  (the barrier semantics themselves are unchanged).
- NOT changed: the priority-0 burst after `becomeBackup` (still the
  peer takeover signal), the #6177 ResignBarrier, peer RX handling,
  config priority clamping (#8597), or any CLI table beyond the
  manager Status text.

## Validation

- RED on `origin/master` (2511cb3228): the new
  `diagnostics_15213_test.go` failed behaviourally — 5 INFO refusals
  in one episode (want 1), `Status` printed `priority=100` with no
  track marker while advertising 50, and `getPriority()` returned 0
  immediately after `ResignRG` (want 200 until becomeBackup). The
  `InstanceStates` field assertions additionally fail to compile
  pre-fix (fields absent).
- GREEN after the fix: `go test ./pkg/vrrp -run 15213 -count=1`
  passes all four cells (including the track-up control).
- Full `go test ./pkg/vrrp -count=1`: only failure is
  `TestRethOwnershipCollectorsUseTheSharedPredicate/RethVIPsForRG`,
  which fails identically on the pristine base (verified via stash) —
  base-attributed, untouched here.
- `go vet ./pkg/vrrp` clean; `gofmt -l` empty on changed files.
  Targeted race run (`-race`, 15213/6177/Status/GetPriority/Prio0
  cells) passes. `pkg/cli` has pre-existing failures
  (e.g. `TestShowSecurityZonesDetailBaseMemberNoRegression5325`,
  `TestMultiPipeDispatchFullChainOrder14714`) that fail identically
  on the pristine base — base-attributed, unrelated (no vrrp surface
  touched there beyond additive `VRRPEvent` fields).

## Risk

Operator-visible deltas only in diagnostics: the hold-refusal INFO
now appears once per hold episode (Debug repeats remain available),
and `Status()` shows the effective priority (identical to the
configured value whenever tracking is not demoting). The resign
change delays only the *routine-advert* visibility of priority 0 by
one run-loop hop; the explicit post-becomeBackup priority-0 burst and
the ResignBarrier ordering are unchanged.
