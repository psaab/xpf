# #16582: config apply during a GRE peer outage re-ups the keepalive-down tunnel

- **Timestamp**: 2026-10-24
- **Action**: The dataplane zone compile (`mapZoneInterface`) LinkSetUp'd
  every zoned netdev after `ApplyTunnels` had honoured the keepalive
  runner's `skipUp`, and the runner's only down edge was gated on
  `state.Up`, so any commit (or HA secondary config-sync apply) during
  a peer outage re-upped the dead GRE tunnel for the rest of the
  outage — connected/static/IGP routes and userspace FIB ECMP
  selection restored while keepalive status still read down. Both
  fix options from the issue are implemented. (1) Held-down
  predicate: `tunnelManager.TunnelHeldDown` / `Manager.TunnelHeldDown`
  (runner present, `Up==false`, `Failures>=MaxRetries`) is registered
  by the daemon as `dataplane.SetTunnelHeldDownResolver` (the
  `SetProtectedInterfaceResolver` injection shape; pkg/dataplane does
  not import pkg/routing) and consulted by Linux netdev name in
  `mapZoneInterface` before `LinkSetUp`; a held-down tunnel is left
  down as an intentionally-down surface (same XDP-skip disposition as
  `disable`, so arm-coverage does not report it uncovered). The zone
  loop's admin writes move behind `zoneLinkSetUpSeam` /
  `zoneLinkSetDownSeam` so the guard is bindable in tests (the #8122
  lesson). (2) Runner robustness: `keepaliveTick` now arms `wantDown`
  at `Failures>=MaxRetries` regardless of `state.Up`, suppresses it
  only when the link is observed admin DOWN, and re-downs an
  externally re-upped link on the next dead tick; a re-down does not
  re-fire the liveness-change callback. The generation guard, the
  commit-after-success `Up` commit, and the exactly-one-down steady
  state are unchanged.
