# #15240: postinst — preserve foreign content at the managed sbin names (A57-04)

## Summary

On first install (`configure` with empty `$2`), `debian/xpf.postinst`
ran `ln -sfnT "$STAGED/$b" "$SBIN/$b"` for each of the four managed
binaries (`xpfd cli xpf-userspace-dp xpf-day0-config`, postinst:198-201
at the report base). `ln -sfnT` replaces whatever already sits at
`/usr/local/sbin/<bin>` — including an operator's pre-existing regular
file in the admin-owned `/usr/local/sbin`. The postinst then handed the
names to `xpfd seed-runtime`, whose sbin repoint
(`pkg/upgrade/runtime/seed.go` step 4) likewise replaced any existing
entry through `versions/current`. Package removal
(`debian/xpf.postrm`, `link_is_owned`/`remove_owned_sbin_links`) deletes
links pointing at staged or `versions/current`, so the overwritten
original was permanently lost on remove. Severity Low (admin-file loss
on foreign hosts; root runs apt, no security boundary crossed);
consensus MATERIAL in the validator research run.

## Fix

- `debian/xpf.postinst`: new `establish_sbin_link` helper, used by the
  first-install pre-seed loop. For each managed name:
  - absent → create the staged link exactly as before;
  - symlink already pointing at `$STAGED/<bin>` (our own prior attempt,
    e.g. a postinst retry) → re-created idempotently;
  - any other symlink → left exactly as found, with a
    `preserving existing symlink` warning on stderr;
  - non-symlink (regular file or directory) → moved aside to
    `<path>.xpf-saved` with a `preserving existing` warning, then the
    staged link is created. If `<path>.xpf-saved` already exists the
    helper returns non-zero and `set -e` aborts the install rather than
    overwrite either file.
  The seed-failure fallback loop is unchanged in behaviour; foreign
  content has already been moved aside or left untouched by then, so it
  only re-creates links the helper established.
- `pkg/upgrade/runtime/seed.go` (Seed step 4): a sbin entry that already
  exists and is not a symlink to our staged path or through
  `versions/current` is preserved (logged, skipped); absent names and
  our own links are seeded exactly as before. Without this, the Go seed
  would immediately re-clobber the names the shell guard preserved.
- `docs/in-place-upgrade.md` §A and `debian/changelog` record the
  preserved-foreign-content behaviour.

`debian/xpf.preinst` (`install|abort-upgrade` no-op) is NOT changed: it
runs before unpack, when no link has been created yet; the destructive
operation is the postinst's first-install link creation and the seed
repoint. Upgrade paths are untouched — they already only recover
completely absent links and never repoint existing/dangling ones
(#2000).

Operator-visible consequence of preserving a foreign symlink: that
managed name keeps resolving to the operator's target (e.g. a foreign
`/usr/local/sbin/xpfd` means the packaged daemon is not the one at that
name until the operator moves it aside). This is the correct trade-off:
silently destroying admin-owned wiring is the defect; the warning makes
the preserved state loud.

## Regression / RED-GREEN evidence

- Shell (`test/debian/postinst-test.sh`, real postinst with paths
  rewritten to a temp root, run under both `sh` and `dash`):
  - `first_install_preserves_foreign_regular_file` — regular file at
    `cli` survives at `cli.xpf-saved` byte-identical with the warning
    printed; the managed link is still created. **RED on the original
    postinst** (`FAIL: foreign cli was not preserved as a regular file
    at cli.xpf-saved`), GREEN after the fix.
  - `first_install_preserves_foreign_symlink` — foreign symlink at
    `xpfd` keeps its target; no `.xpf-saved` appears; warning printed.
    (The seed stub in this cell mirrors the fixed Go seed's skip.)
  - `first_install_preserves_foreign_directory` — a real directory at
    `xpfd` is moved aside whole, contents intact.
  - `first_install_refuses_when_saved_name_taken` — with both `cli` and
    `cli.xpf-saved` present the postinst exits non-zero and both files
    survive byte-identical.
  - Controls: `first_install_recreates_own_staged_symlink` (our own
    staged symlink is adopted through `versions/current`, no
    `.xpf-saved`) and
    `first_install_seed_failure_no_foreign_still_falls_back` (fallback
    still direct-to-staged, no preservation warning) stay green, as do
    all pre-existing scenarios (`ALL POSTINST SCENARIOS PASSED`).
- Go (`pkg/upgrade/runtime/seed_test.go`):
  `TestSeed_PreservesForeignSbinEntries_15240` — a foreign symlink and a
  regular file at managed names survive `Seed` byte-identical while
  uncontested names seed normally. **RED with `seed.go` reverted**
  (foreign symlink repointed through `versions/current`), GREEN after.
  `TestSeed_RepointsOwnStagedSbinLink_15240` is the own-link control.

## Risk

First-install path only. Upgrades, the verified cut, clustering gates,
and removal semantics are unchanged (postrm already only removed owned
links). A foreign regular file no longer blocks daemon launch: it is
preserved at `<path>.xpf-saved` and the managed link is created. A
foreign symlink at a managed name now keeps that name on the operator's
target (warned) instead of silently adopting it — operators who
pre-wired those names intentionally keep their wiring; operators who
left a stale link there see the warning and can move it aside.
