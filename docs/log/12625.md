# #12625 — refuse colliding static-NAT prefix names

- **Timestamp**: 2026-10-13 (`fix/12625-campaign-pub`)

## Why

`resolveStaticNATThenPrefixName` selected a direct address or expanded a singleton address-set without consulting `AddressBook.CollidingNames`. On tolerant compilation a static-NAT `prefix-name` could therefore pick the address winner from an ambiguous name and set `rule.Then`, bypassing the existing #4290 empty-target warning.

## What

Static-NAT prefix-name resolution now refuses a colliding target, every colliding set name traversed during singleton expansion, and a colliding expanded member. Valid non-colliding addresses and singleton sets retain their prior resolution. Added direct resolver coverage for colliding direct names, set names, expanded members, nested sets and cross-kind members, plus non-colliding controls. End-to-end lenient compilation tests assert `Then==""` and the #4290 warning for direct and singleton-member collisions. Updated the #12502 cross-kind precedence control: its previously expected address winner is now refused and emits the warning.

## Validation

- **RED before fix**: `go test ./pkg/config -run '^TestStaticNATPrefixName(CollidingNames|CollisionLenient)12625$' -count=1` failed for direct address, set, expanded member, nested-set collisions, and both lenient end-to-end cases: each unexpectedly resolved to `10.0.0.5/32`.
- **GREEN after fix**: the focused collision tests passed on the final change. `go vet ./pkg/config` and `go build ./...` passed.
- `go test ./pkg/config -count=1` did not pass: unrelated inventory/live-census, API-auth expiry, packed routing-instance, and slot-escape coverage tests failed, then `TestSchemaSpellingDifferentialGate` hit the package's 10-minute timeout. The issue-specific collision tests and the updated `TestCrossKindAddressFirstOnNameCollision12502` passed independently.

## Risk / residual

No issue-specific residual is known. No live-cluster validation was performed.
