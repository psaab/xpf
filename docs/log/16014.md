# Issue #16014 — sessions: same-domain reverse-NAT ambiguity first-wins instead of ambiguous-drop (A2-C6)

- **Issue:** Both ordinary reverse-NAT matchers (`find_forward_nat_match_inner`, `find_forward_nat_match_expiry`) and the quote matcher treated a second candidate as ambiguous ONLY if it lived in a different routing domain (#14374/#14375 cross-domain rules). Same-domain DNAT twins (different VIPs, same backend, same client tuple) share one post-NAT reverse tuple, so both pass and the first won — a reply was rewritten with the wrong VIP source.
- **Fix:** Extend the any-distinct rule (#14375 shape) to all three matchers: a second passing candidate with a different forward key or NAT decision is ambiguous in ANY domain, bumping the existing `NAT_REVERSE_AMBIGUOUS_TOTAL` (`xpf_userspace_nat_reverse_ambiguous_total`, already plumbed by #14374). Expiry matcher returns the new `ForwardNatExpiryProbe::Ambiguous` (distinct from `Absent`/`IdleCrossed`); inner matcher returns tri-state `ForwardNatMatchLookup` (`Unique`/`NoMatch`/`Ambiguous`) behind the unchanged `Option` wrappers; quote `Ambiguous` now bumps the counter too.
- **Fold (PR #16351):** `lookup_forward_nat_across_scopes_inner` treats local `Ambiguous` as terminal in both its expiry and no-timestamp legs — never falling through to the shared fallback (previously an ambiguous local `None`/`Absent` for a nonzero domain could be rescued by a shared candidate, minting a reverse session from the wrong scope). Regression: `ambiguous_local_reverse_lookup_blocks_shared_fallback_16014` (both legs + single-candidate control). Counter assertions are delta-based (`after - before == 1`), never absolute.
- **Tests:** `same_domain_dnat_twins_are_ambiguous_16014` (all matchers + quote, delta counters, single + cross-domain demux controls); `shared_egress_overlapping_tenants_are_ambiguous_14374` updated to expect `Ambiguous`; `nat_reverse_1n_collision_preserves_displaced_return_path` now asserts the ambiguous drop while both twins live (survivor resolves after one closes).
