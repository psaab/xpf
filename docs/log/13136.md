# #13136: Resolve management VRF ingress scopes

The D2-04 source finding (deep-review run `review-work.iw8lxdGtK5`) identified
three mismatches in host-inbound VRF projection: management-class interfaces
were marked enslaved but had no `vrf-mgmt` master mapping, declared management
VLAN units were omitted from DHCP VRF backstops, and `#11060`-quarantined
tunnel devices could still acquire a guessed host-inbound master.

`junosHostVRFMasterNetdevs` now maps management interfaces and each configured
unit to `vrf-mgmt`, clears ownership guesses for quarantined RI member devices,
and skips quarantined explicit tunnel claims. Management-class bindings are
applied after RI conflict evidence because the daemon's management binding is
unconditional. `HostInboundDHCPVRFEnslavedNetdevs` now uses the shared Linux
netdev resolver for management base interfaces and units.

Regression coverage checks `em0`/`em0.100` master and DHCP mappings, the
`vrf-mgmt` ingress scope for a host-inbound deny, and a quarantined tunnel claim.
The regression tests fail on pristine master: projection emits `em0` and
`em0.100` directly with no VRF scope, DHCP coverage omits `em0.100`, and the
quarantined tunnel retains `vrf-blue` ownership.
