# #14972 — reap single-path IPv6 and backup-router mgmt statics on delete and rollback

- **Timestamp**: 2026-10-18
- **Issue**: Single-path IPv6 static routes and the IPv6 `backup-router` in `vrf-mgmt` (table 999) were never reaped on deletion, priority (preference) change, rollback, or reset. They were stamped `RTPROT_STATIC` + the xpf realm (`mgmtStaticRouteRealm`, `RTA_FLOW`), but Linux stores no `RTA_FLOW` for IPv6, so they read back with realm 0, `mgmtStaticRouteOwned` never claimed them, and the stale route kept forwarding after the config that created it was gone (report `D31-04`, severity High, 3-way MATERIAL in `tpzkKgAuZL`).
- **Base**: `origin/master` `28a08b27f1`.

## Fix

Reuse the marker that already survives both families instead of inventing a second one: every management static the reconcile installs — single-path statics from `mgmtStaticRoutesDesired` and the backup-router from `mgmtBackupRouterRoute` — now carries `config.ManagementVRFMultipathStaticProtocol` (0x58, the #12539 ECMP marker) as its `rtm_protocol`. A single-path route additionally keeps the realm, so:

- `mgmtStaticRouteOwned` is unchanged and now matches every route the current build installs, in both families: protocol 0x58, or legacy `RTPROT_STATIC` + realm.
- IPv4 single-path routes installed by earlier builds (`RTPROT_STATIC` + realm) are still recognized and reaped; they are replaced in place by the new stamp on the next reconcile (same destination/priority slot, no delete issued for the overwritten copy).
- Operator `RTPROT_STATIC` routes without the realm are never claimed in either family; the protocol also scopes the kernel delete match, so a stale xpf delete against an operator route at the same slot returns `ESRCH` (tolerated) instead of removing it.
- ECMP routes are byte-identical to #12539 (protocol 0x58, no realm). No new protocol number, no wire/config changes. `rtProtoName` already renders 0x58 as `static`, and `mgmtVRFRouteInventory` already counts it as operator authority for DHCP precedence.
- Bounded pre-existing gap (unchanged): an IPv6 single-path route installed by an earlier build reads back as plain `RTPROT_STATIC` realm 0, indistinguishable from an operator route, and still cannot be reaped safely. IPv4 legacy routes have the realm and are reaped.

Files: `pkg/config/routinginstance_reserved_name_9622.go` (marker contract), `pkg/daemon/mgmtvrf_static_routes.go` (desired + backup-router stamps, ownership comment), `pkg/daemon/daemon_flow.go`, `pkg/daemon/README.md`, `docs/critical-patterns.md`, `pkg/config/compiler_system.go` (comments only).

## Risk

- IPv4 single-path and backup-router routes change `rtm_protocol` 4 -> 88 (realm unchanged): `ip route` shows `proto 88`, xpf `show route` still shows `static`. systemd-networkd foreign-route handling for a non-`RTPROT_STATIC` protocol is the same bound already accepted for ECMP in #12539; the post-networkd management reconcile reinstalls dropped table-999 routes.
- Tables other than 999 are untouched; table 999 is excluded from the FIB importer, so the protocol change cannot leak into the dataplane FIB.
