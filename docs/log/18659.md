# #18659: RG activation refresh moves peer-owned reverse rows onto an unresolved WAN gateway

## Diagnosis (found while root-causing the #18598 re-gate regression)

- **Timestamp**: 2026-11-01 01:30-03:35 UTC
- **Action**: Ran test-failover on loss on master and #18598 builds, with a
  1.7 kHz `userspace_ctrl` sampler on node0 (`r-18598-ctrlsample.py`). Two
  diag builds followed, both rate-limited `eprintln`, local commits, never
  pushed:
  - deny sites with their call location and the local and shared session row
    (0.0.27200);
  - every write that stamps a reverse 5210/5211 row
    (`revalidate_forwarding_resolution_with_egress_zone`,
    `refresh_in_place`), on PR (0.0.27600) and on master 3f5daa77a7
    (0.0.27610).

  Artefacts: `/var/worktrees/.cache/fwd-goal/r-18598/failover-*`.
- **Finding**:
  - Every "RG1 Group 4" deny is the same packet shape: a WAN reply to an
    established SNAT flow, on the node that just took RG1 back while RG2 (LAN)
    stays on the peer.
  - The local reverse row reads
    `MissingNeighbor/eg12/nh 172.16.50.1 SyncImport rev=true gen17/4`, i.e. the
    WAN default gateway, unresolved, stamped with the current generation. The
    reply takes the MissingNeighbor arm (`poll_descriptor/mod.rs`); the #1913
    gate there judges wan->wan and the reply is default-denied.
  - The rewriter is the RG-activation HA refresh,
    `refresh_for_ha_transition@refresh_owner_rgs.rs:81`, writing
    `old=(FabricRedirect, eg4) new=MissingNeighbor/eg12`. It does this for
    every worker's copy, on master as well as on the PR.
  - Copies are stamped with each worker's own revalidation generation:
    - PR: 0/0/0 x366, 11/3/x x185, current x105;
    - master: 0/0/0 x116, 11/3/x x418, current x85.

    The roughly 1-in-6 current copies do not re-resolve. Those deny.
- **Cause**: `rehome_or_retain_fabric_redirect_inner` returned every candidate
  that was not `ForwardCandidate` unchanged. The #15958b retain-redirect guard
  never saw `MissingNeighbor`, the answer the split FIB gives for the peer's
  LAN while the WAN gateway's neighbor is still unlearned.
  `reverse_hit_departed_destination_redirect` had the same gap.

## Fix

- **Action**:
  - `session_glue/resolution.rs`: keep the fabric redirect for a
    `MissingNeighbor` candidate on a local, non-fabric egress when the
    destination's connected owner RG is known and NOT forwarding-active
    locally.
  - `session_glue/resolve.rs`: `reverse_hit_departed_destination_redirect`
    also converts `MissingNeighbor`.
  - New cells in `afxdp/tests_fabric_zone_stamp.rs`:
    - `split_rg_unresolved_gateway_fixture_shape_18659` checks the fixture
      reaches the live shape.
    - `split_rg_refresh_keeps_fabric_redirect_unresolved_gateway_18659` covers
      the production refresh collector, v4 and v6.
    - `rehome_or_retain_missing_neighbor_table_18659` checks that a locally
      active owner, an unknown owner, a fabric egress and a zero egress are
      never redirected.
    - `reverse_departed_destination_converts_missing_neighbor_18659` holds the
      conversion to the same terms as `ForwardCandidate`.
    - `split_rg_laundered_reverse_row_wan_reply_fabric_tx_18659` drives the
      packet path: a laundered, current-stamped row must fabric-TX the WAN
      reply with `policy_deny == 0`.
  - Docs: `docs/fabric-cross-chassis-fwd.md` (#18659 section) and
    `userspace-dp/src/afxdp/session_glue/README.md`.
- **File(s)**: userspace-dp/src/afxdp/session_glue/resolution.rs,
  userspace-dp/src/afxdp/session_glue/resolve.rs,
  userspace-dp/src/afxdp/tests_fabric_zone_stamp.rs,
  docs/fabric-cross-chassis-fwd.md,
  userspace-dp/src/afxdp/session_glue/README.md, docs/log/18659.md
- **Security notes**:
  - Neither path ever redirects a locally active owner or an unknown owner.
    Both are pinned in the two table cells.
  - The #1913 gate is unchanged. It still judges every `MissingNeighbor` that
    reaches it. Only an established reverse row whose reply destination the
    peer owns no longer reaches it, which matches how a `ForwardCandidate`
    reverse row already converted.
