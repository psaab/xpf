## Verdict: (b) NOT SAFE at HEAD — concrete failure, file:line cited

An established-flow move is unsafe at HEAD without an ownership-transfer
protocol. Concrete case: exact rules are installed for **both directions** of
flow F (or F is a one-way UDP flow), so future packets land on W_new and no
packet refreshes W_old's local entry. W_old's GC can then emit Close, remove
shared state, and broadcast `DeleteSynced` to W_new. The 70 s #9488
forward-only TCP run demonstrates the forwarding win, but reverse ACK traffic
can keep W_old alive through the companion gate; that run does not by itself
exercise this expiry interleaving.

The three MAJOR hazards from #1748's plan review (stale-owner GC cascade,
never-cleanup owner semantics, zero-owner race) were code-verified at the
stated HEAD, the fixing protocol (#1749) never landed, and every gate that
produces the primary failure is still present:

- `git grep -n -e 'RebalancedOut' -e 'RebalancedOwner' -e 'flow_rebalance' -- userspace-dp/src pkg`: **empty** — no ownership-transfer protocol exists at HEAD.
- `git grep -n -e 'ethtool_rxnfc' -e 'ntuple' -e 'flow_spec_from_key' -- userspace-dp/src userspace-xdp/src`: **empty** — no steering-rule code exists at HEAD.
- `git grep -n -e 'select_move' -e 'count_balanc' -- userspace-dp/src`: **empty** — no selection/move code exists at HEAD.

#1765's forbidden-verdict therefore **stands**, on narrowed grounds: the
forwarding path is safe for a moved flow (premise re-verified fresh below,
and #9488 reproduces the forwarding win), but the session lifecycle can kill
the flow or leave stale state during recovery. "It would not help anyway" is
dead (#9488); "it kills the flow at GC" replaces it.

Per-queue UMEM ownership is **not** the forbidding mechanism for a ntuple
re-pin (no hazard found; each candidate examined below). It forbids
cross-queue `XDP_REDIRECT` (Wall A, still holds) — a different mechanism
(packet redirect) from ntuple re-pin (future-packet steering).

## Failure mechanism 1 (primary): stale-owner GC cascade kills the moved flow

Setup. Flow F is established on worker W_old (queue q_old): W_old holds a
local `ForwardFlow` entry, the shared session is published, and every sibling
— including W_new — holds a `WorkerLocalImport` replica (`replicate_session_upsert`,
`userspace-dp/src/afxdp/session_glue/mod.rs:1492-1543`, fanned from both the
forward install at `poll_descriptor/mod.rs:3462-3465` and the reverse install
at `poll_descriptor/mod.rs:3821-3824`, to the sibling set built as
all-workers-except-self at `coordinator/reconcile/bringup.rs:694-699`).

Interleaving (no protocol at HEAD, so nothing below is gated):

1. **t1 — rules land.** Exact rules steer **both directions** of F to W_new
   (or F is a one-way UDP flow, so there is no reverse packet). W_new hits
   its local `WorkerLocalImport` replica, the per-RG gate admits it
   (`enforce_session_ha_resolution`, `session_glue/mod.rs:2469-2491`, keyed
   on the egress RG via `forwarding/ha.rs:16-41` with no worker input), and
   W_new forwards. Each hit refreshes **only W_new's** local `last_seen_ns`
   (`session/lookup.rs:189`, on the worker-local `&mut SessionTable`).
   W_old's copy receives no refresh and goes stale. This is a concrete
   lifecycle interleaving; the forward-only TCP run in #9488 is not this case.
2. **t2 — W_old GCs.** `expire_stale_entries_ha`
   (`session/expire.rs:121-411`) removes W_old's idle `ForwardFlow` entry and
   emits a Close delta: the gate at `expire.rs:364-368`
   (`!is_reverse && !is_peer_synced() && !transient && !tun`) **passes** for a
   locally-owned forward entry. The companion keep-alive at
   `expire.rs:316-341` cannot save this case because both directions moved
   (or the one-way flow has no companion traffic).
3. **t3 — Close tears down shared state and broadcasts.** W_old's
   `flush_session_deltas` (`afxdp/session_delta.rs:632-733`) deletes the live
   BPF entries (`:646-652`), the dnat alias (`:661`), **both shared sessions**
   (`remove_shared_session`, `:671` and `:699`), both coordinator row claims
   (`:683`, `:707`), and fans `DeleteSynced` for forward **and** reverse keys
   to every sibling (`replicate_session_delete_repairing`, `:712` and `:724`).
4. **t4 — W_new's replica is deleted mid-flow.** W_new drains the
   `DeleteSynced` in `handle_delete_synced`
   (`session_glue/commands/delete_synced.rs:20-140`). The #9048 refusal
   (`:86-93`) fires only for `!is_peer_synced()` origins; W_new's
   `WorkerLocalImport` **is** peer-synced (`session/entry.rs:468-473`), so the
   refusal is inert and W_new runs `sessions.delete` (`:94`), drops its NAT
   holder bit (`:103-126`), deletes the BPF alias (`:127-132`), and
   invalidates its flow-cache slot (`:95` → #6457 path).
5. **t5 — next packet re-misses.** F's next packet on W_new finds no local
   entry and no shared entry: a cold-path reinstall as a **new** session
   mid-flow (policy re-evaluation, fresh NAT allocation, new Open delta), or
   a drop. The established flow is torn down and re-missed; no TCP sequence
   window claim is needed to establish the disruption.

A 70 s forward-only TCP push never reaches this both-direction/one-way t2
case, which is exactly why #9488 shows the move forwarding and says nothing
about lifecycle safety (#9778 scope note).

## Failure mechanism 2 (secondary): stale-replica window, not permanent leak

W_new's `WorkerLocalImport` replica cannot become the cleanup owner:

- It cannot promote: `maybe_promote_synced_session`
  (`session_glue/promote.rs:71-90`) no-ops unless
  `is_promotable_synced()`, which matches only
  `SyncImport | SharedMaterialize` (`session/entry.rs:475-477`) — never
  `WorkerLocalImport`. Pinned by
  `maybe_promote_synced_session_skips_worker_local_import`
  (`session_glue/tests.rs:588`).
- Its GC emits no Close: the `expire.rs:364-368` gate excludes every
  `is_peer_synced()` origin. Its reap (`worker/loop_body/mod.rs:1884-1939`)
  releases only its own NAT holder bit, its BPF alias, and its flow-cache
  slot.

The earlier #1748 “never-cleanup leak” wording is too strong for this HEAD:
when a `DeleteSynced` is refused by a full queue,
`replicate_session_delete_repairing` bumps the target worker's out-of-band
delete epoch and repairs that worker's NAT holder
(`session_glue/mod.rs:1768-1787`); the bounded `DeleteDropSweep::step` then
removes peer-synced entries whose shared authority is gone and releases their
steering rows (`session_glue/delete_drop_sweep.rs:72-118`). This is eventual
recovery, not a permanent leak, and it does not make the handoff safe: the
old owner's Close can still remove shared authority before the destination's
delete/sweep is applied, leaving a stale/orphaned local copy during the
un-ordered window. The primary GC cascade above remains a concrete flow
disruption.

## Failure mechanism 3 (structural): zero-owner race across the move

There is no cross-worker ordering primitive at HEAD:

- Command queues are independent per-worker `VecDeque<WorkerCommand>`:
  `apply_worker_commands` drains a per-worker
  `Arc<Mutex<VecDeque<WorkerCommand>>>`
  (`session_glue/mod.rs:1011-1073`), while the peer set is built as
  all workers except self (`coordinator/reconcile/bringup.rs:694-699`).
  They are drained as a bounded 256-command prefix per tick
  (`worker_queue::WORKER_COMMAND_DRAIN_BUDGET`, `worker_queue.rs:540-560`),
  refusing (never evicting) past 4096 (`worker_queue.rs:521-538`,
  preserving per-queue `UpsertSynced`→`DeleteSynced` order only).
- W_old's shared removal is synchronous inside its own Close drain
  (`session_delta.rs:671-707`); the sibling deletes that follow are async
  queue traffic. Between the two, W_new forwards an orphan with no shared
  backing, and a MISS-install for the same 5-tuple on any third worker races
  W_new's still-live replica with no barrier between them.

#1749's applied-command barriers (promote→ack→demote→ack→rule) were the
designed answer; they do not exist at HEAD (empty grep above).

## Sibling-replica premise: re-verified FRESH at HEAD (holds)

The 2026-06 reading is confirmed current, at new line numbers:

- Fan-out to every sibling on install, forward and reverse:
  `poll_descriptor/mod.rs:3462-3465` + `:3821-3824` →
  `replicate_session_upsert` (`session_glue/mod.rs:1492-1543`) →

  `bringup.rs:694-699`. Local entries re-tag to `WorkerLocalImport` via

  `entry.rs:479-490`).
- Forwarding-ready on receipt: `handle_upsert_synced`
  (`commands/upsert_synced.rs:50-231`) re-resolves with local egress
  (`:85-112`), upserts, reserves NAT/NAT64 holder bits (`:181-221`), and
  publishes the kernel session-map entry (`:222-230`).
- Backstops: reactive `materialize_shared_session_hit`
  (`session_glue/mod.rs:2118-2152`) reinstalls a missing replica off the
  shared map on first hit.
- Forwarding gated per RG, never per worker: `enforce_ha_resolution_snapshot`
  (`forwarding/ha.rs:66-79`) and `enforce_session_ha_resolution`
  (`session_glue/mod.rs:2469-2491`) take forwarding + HA state + resolution —
  no worker identity — and the resolve path (`session_glue/mod.rs:2242-2276`)
  applies them identically on any worker.

## Per-queue UMEM: no concrete hazard for a ntuple re-pin

Each candidate from the issue scope was traced and cleared:

- **Frames sitting in the old queue's rings when the rule lands.** They stay
  in the old queue's UMEM and drain on the old worker's own loop: RX recycle
  pushes the ingress offset to the **same** binding's fill queue
  (`recycle_ingress_frame`, `tx/dispatch/mod.rs:121-129` → `drain_pending_fill`
  per binding, `tx/rings.rs:175-178`). A steering rule changes where **future**
  packets DMA, never where existing frames live. Nothing migrates, nothing
  needs a cross-queue free.
- **TX completions on the old UMEM.** They complete to the **same** binding's
  free pool (`reap_tx_completions` → `recycle_completed_tx_offset`,
  `tx/rings.rs:82-153` + `:340-382`, with invalid/duplicate completions
  dropped and counted, never recycled). The only cross-binding recycle
  (`shared_recycles`) is distributed within the **same worker's** binding
  slice (`apply_shared_recycles_to_bindings`,
  `tx/dispatch/shared_recycle.rs:274-302`). No worker ever frees another
  worker's frame: `WorkerUmem` is `Rc`, single-owner
  (`umem/mod.rs:45-48`), held per `BindingWorker` per queue
  (`worker/mod.rs:120-136`).
- **A worker acting on a session it no longer owns.** Real, but it is the
  session-table hazard of mechanisms 1–3, not a UMEM hazard: frames are never
  accessed via session ownership. No frame-lifetime interleaving exists
  because no frame changes hands.
- **What per-queue UMEM ownership actually forbids** is cross-queue
  `XDP_REDIRECT` under zero-copy: `xsk_rcv_check()` requires
  `queue_id == rxq->queue_index` (`userspace-xdp/src/binding_index.rs:4-9`;
  Wall A). That kills packet-redirect rebalancing (#899), not ntuple re-pin.
  Even under the narrow mlx5 shared-UMEM prototype (`bind.rs:531-534`), the
  re-pin moves no socket binding and no frame.

The #9488 retransmit burst (2681/2851/4770 in t14–16, ≤3 elsewhere, no stream
under 100 Mb/s, iperf exit 0) is consistent with a transient reorder window
while 13 rules go in over ~3 s — not with frame corruption, which would not
heal into 6.7–13.9% steady-state CoV.

## R2/R4/R5/R6 answers (all open, none has code at HEAD)

- **R2 reverse direction: UNSUPPORTED / unanswered in the shipped tree.** The
  #9488 recipe installs forward-direction rules only
  (`src-ip <client> dst-ip <server> src-port <p> dst-port 5210`), so
  server→client traffic keeps its swapped tuple and stays RSS-placed. Reverse
  ACK traffic can companion-keepalive W_old (`expire.rs:316-341`), so the
  forward-only TCP run is not itself the GC-failure interleaving. Moving both
  halves (or using a one-way flow) costs 2 rules/flow, halving the effective
  1024-rule cap to ~512 flows. No reverse-rule code exists at HEAD; a safe
  future protocol must coordinate both directions or explicitly handle the
  split ownership, and neither exists here.
- **R4 HA peer rule mirroring: OPEN.** Rules are node-local NIC state; no
  mirroring, export, or peer-install code exists at HEAD (empty ntuple grep).
  After a failover the peer has no rules, so moved flows revert to RSS
  placement there while session sync carries no placement information.
  `make test-failover` with rules installed is untested and unhandled.
- **R5 1024-rule cap + churn/hysteresis: CAP STANDS, POLICY ABSENT.** The 1024
  cap (`MLX5E_ETHTOOL_FLOW_SPEC_NUM`) and ~1 ms firmware cost per rule are
  #1649's live-NIC findings, unchanged by this issue. The bulk-move cost is
  now measured twice (R1: 7601/run; #9488: 2681/2851/4770 in the install
  window). No hysteresis, cooldown, or incremental-move code exists at HEAD.
- **R6 selection policy: OPEN.** #1748's byte-rate-aware selection is blocked
  on the unreliable `observed_bytes` signal (#1750); #1751's count-balancing
  redesign never landed (draft branches only). The only demonstrated policy
  is manual round-robin to `[2,2,2,2,2,2]` (R1, #9488).

## Follow-up spec (precise; NOT implemented — docs verdict only)

To make the move safe, enforce the single-cleanup-owner invariant —
**exactly one worker holds a Close-emitting origin per 5-tuple at every
instant across the move** — at these sites:

1. `session/expire.rs:364-368` Close gate + `session/entry.rs:468-477`
   origin taxonomy: the demoted old copy must not emit Close or delete shared
   state (the `RebalancedOut` suppression set of #1749 v7: Close delta,
   shared-map + conntrack delete, `DeleteSynced` broadcast, SNAT release, HA
   demote/refresh/export, terminal/purge paths).
2. `session_glue/promote.rs:71-90` + `session/entry.rs:475-477`: the promoted
   new copy must become the single Close-emitting owner (`RebalancedOwner`).
3. Rule transitions must ride applied-command barriers
   (install = promote→ack→demote→ack→rule; rollback/live-teardown reversed;
   structured `{seq,key,origin,result}` acks) across the per-worker queues of
   `types/runtime.rs:536-607` — the barrier transport does not exist at HEAD.
4. Acceptance: move an established flow, idle past GC on the old queue, flow
   survives with no re-miss; exactly one Close fires at true flow end;
   `make test-failover` clean with rules installed; R2/R4/R5/R6 closed
   alongside (reverse rules, peer mirroring, cap/hysteresis, selection).

#1749's closed-draft design (v7, 6 plan-review rounds + 3 code-review rounds
per the #1748 thread) is the reference shape — not landed, so cited as prior
art, not as enforcement.
