# Issue #13717 — stage scheduler latch with desired state

- **Issue:** #13717 — `UpdatePolicyScheduleStateWithLatch` and `PublishRouteOverlaySnapshotWithLatch` updated the desired scheduler map without updating its paired `failClosed` disposition.
- **Branch:** `fix/13717-campaign`
- **Worktree:** `/var/worktrees/campaign-zero/wt-13717`

## Change

Both latch-aware setters now stage `policySchedulerDesiredFailClosed` under the same manager lock as the desired scheduler map and set bit. The overlay path only stages the latch when `schedulerState != nil`; a route-only publish with no scheduler state preserves the previously staged map/latch pair. The regression test checks both activation and clearing directions for each setter on the helper-down/no-snapshot early-return paths, as well as nil-state preservation for route-only publish.

## Validation

- Regression added: `pkg/dataplane/userspace/manager_sched_latch_desired_13717_test.go` (`TestWithLatchSettersStageFailClosedForSubsequentCompile13717`).
- Tests, race tests, vet, and build were not run in this worker environment; tool policy forbids test/build verification commands. The regression is expected to fail before the change because both setters omit the latch assignment and pass after it; this expectation is source-derived, not an observed RED/GREEN result.

## Risk

The change only synchronizes the already-paired desired scheduler inputs. Applied/show scheduler state and publish/commit behavior are unchanged.
