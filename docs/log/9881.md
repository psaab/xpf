# #9881 leading-bracket as-path regex — engineering history

Issue: psaab/xpf#9881 (config: unquoted leading-bracket as-path regex lexed
as list sugar, silently compiles to valid-but-different POSIX — `[0-9]+`
becomes `0-9 +`). Lane branch: `fix/9881-aspath-bracket`, base
`origin/master` 2456a1fcb.

## STEP-0 (defect PRESENT at base)

Throwaway probe `TestStep0LeadingBracketRepro9881` (removed after use):

- `NewLexer("[0-9]+")` → `0-9` (`InBracket=true`), `+` (`InBracket=false`).
- `ASPathRegexFromTokens(["0-9","+"])` → `"0-9 +"`; `ValidASPathRegex` → nil.
- `ParseSetCommandQuoted` + `SetPathQuoted` + `CompileConfig`:

Mechanism file:line proof (base): `pkg/config/lexer.go:148`

## Design (MEDIUM tier; brief + adjudication on the issue)

The lexer bit (`tokInBracket`) and the AST slot (`Node.KeysBracketed`)
already exist and the hierarchical parser records them; the gap is the
operator `set` path, which parses with `ParseSetCommandQuoted` (discards
grouping) and sets with `SetPathQuoted` (nil grouping). Only
`applyEditLine` (load-merge/replay) used the grouped pair.

1. **Plumb**: `Store.SetFromInputAs` parses with `ParseSetCommandGrouped`
   and sets with new `SetAsQuotedGrouped`; `DeleteFromInputAs` likewise
   with new `DeleteAsGrouped` (set/delete symmetry). All-false grouping
   is a proven no-op, so behavior changes only for lines with literal
   unquoted brackets.
2. **Provenance hygiene** (stale-true vectors that would false-refuse):
   dup re-issue re-stamps both masks (`refreshDupKeysProvenance`, all 5
   arms); `CopyPath`/both `RenamePath` arms clear `KeysBracketed`;
   `removeMultiLeafMembers` rebuilds the mask in lockstep; whole-group
   delete allowed in `elidedPackedRunCarrying` (node-mask-aware, whole
   node only — member paths keep the #9799 refusal).
3. **Flag**: `ASPathDef.RegexUnquotedBracket`, set from the exact winning
   span (instance tail if non-empty, else last non-empty body entry) when
   any of its keys is bracketed-but-unquoted.
4. **Gate**: strict branch checked BEFORE validity (the mangled form loads
   fine, so the #6686 message would lie), with a quote-or-unbracket
   diagnostic that never reconstructs the authored spelling. Lenient
   downgrade automatic at the existing call site.
5. **Belt**: FRR renderer omits flagged defs (referencing terms resolve
   to NO MATCH — fail-closed for accept terms, no worse for reject).

Adjudication: hostile H1 (narrow to split-group) REJECTED — single-token
`[0-9]` is the same miscompile and the contract demands refusal; all other
review findings adopted. Reviews + full rationale on the issue.

## Parent-review fold (post-PR #10085)

Parent: GPT NEEDS-MAJOR + SPARK READY. All four findings folded:

1. HIGH — FRR omission disabled effective reject terms: the belt omitted
   flagged lists while term rendering still emitted `match as-path` refs
   to them (dangling = NO MATCH), so reject terms fell through to a later
   accept or the BGP permit default. Fixed with a fail-closed term rule
   in `renderPolicyTermSequences`: reject term + any dangling ref
   (undefined, invalid, or flagged — one `asPathListMissingAtRender`
   predicate) renders a single bare deny-all; accept/non-terminating
   terms skip the dangling OR-branch in the dispatch. Six policy-level
   cells drive full reject-then-accept route-maps (all red-proven against
   the pre-fix renderer); the false "no worse than the miscompiled
   pattern" belt comment corrected; the #4482 fixture now defines its
   evil list (no-dangling doctrine, #9493).
2. MEDIUM — copy/rename cleared structural grouping: split by role in
   `rekeyBracketProvenance` (containers retain, leaves clear, same-path
   rename retains). Wide-container copy/rename pinned through rendering,
   replay, deletion, and compile; same-path rename pinned as still
   refusing (no `rename X to X` laundering). All three red pre-fix.
3. MEDIUM — tokenless brackets vanished pre-token (`[]0-9]+`, trailing
   `[]`, stray `]`): lexer records per-gap delimiter loss (empty pair
   closed in-gap, stray closer), marks the following token, and persists
   the gap for span-end taint of the last key (`LastGapLoss`, Peek
   leaks it deliberately). Balanced non-empty lists never mark.
   Lexer-level pins + strict-verdict cells on both authoring paths, all
   behaviorally red-proven pre-fix.
4. LOW — this log now qualifies the group-expansion and
   non-terminating-modification residuals explicitly instead of claiming
   blanket coverage.

Full gates + 5x re-run after the fold; updated table on PR #10085.

## Residuals

1. `LoadMergeAs`-hierarchical replays via `FormatSet`, which drops ALL leaf
   bracket provenance (`nodeKeyBracketMask` nils every leaf) — probe-proven:
   candidate renders `0-9 +`, strict commits clean, on exactly that path.
   Filed pre-merge as #10084. Needs a lossless internal replay renderer or
   direct tree merge; own review cycle.
2. Group-expanded as-path values fail OPEN (miss, = today's behavior): the
   group leaf-list union appends inherited values without extending the
   bracket mask, so a bracket bit authored inside `groups` does not reach
   the compiled definition and the gate cannot fire. Deliberately left:
   extending the merge struct with bracket evidence is speculative
   generality for an unobserved shape (groups + as-path + unquoted
   brackets), and the miss direction preserves today's verdicts rather
   than risking false refusals. Revisit if ever observed in the wild.
3. Lenient-path non-terminating MODIFYING terms (community set, prepend,
   ...) over a dangling as-path match skip the modification — the
   pre-existing dangling outcome, made explicit by the term rule.
   Match-all application would be unsound (restrictive and permissive
   actions need opposite defaults). Same class as the #6686 belt.

Every other authoring path (interactive set/delete, hierarchical parse,
flat load-merge/set, load override, SyncApply direct parse, JSON
persist/rollback) is covered and pinned.
