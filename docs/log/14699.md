# #14699 — resolvePBRDirection ignores `except` prefix-lists with match-any / positive scopes

## Defect

`resolvePBRDirection` (`pkg/routing/rules.go`) resolved a firewall-filter
term direction carrying an `except` prefix-list as follows:

- The pure-except refusal (non-empty except → degraded error, no rule)
  required `len(positive) == 0 && !hasPositiveRef && !unconstrainedSeen`.
- `normalizePBRAddr` maps `0.0.0.0/0`, `::/0`, and `any` to
  `unconstrainedSeen=true`, and a positive prefix-list expanding to
  `0.0.0.0/0` does the same. Any specific positive (literal or
  prefix-list) sets `positive`/`hasPositiveRef`.
- Every such combined shape therefore fell into the "POSITIVE-WINS —
  ignore the except" warn branch and returned the positive set, or
  `[]string{""}` (match-all) when the only positive was match-any.

Dropping an exclusion always widens `(P \ E)` to `P`; the in-code
"never widen the steer" rationale was inverted for a negation. The
affected strict-valid shape is the #4338-blessed Junos lockdown idiom
`source-address 0.0.0.0/0; source-prefix-list X except; then
routing-instance …`: the kernel FBF mirror installed a match-all
`ip rule` steering the very prefixes (typically management/RFC1918)
Junos says to exclude, with only a Warn log. The userspace filter path
lowers the same term correctly (`ResolveFilterPrefixListAddrs`), so
only kernel-forwarded / slow-path / local traffic was over-steered.
When the term carried another selector (DSCP, opposite direction, L4),
the mirror emitted a real steered rule; with no other selector the
generic unconstrained-term guard in `buildPBRFromFilter` happened to
drop it, but with the wrong degraded reason.

## Fix

In `resolvePBRDirection`, whenever a direction carries an `except`
reference the outcome now depends only on the resolved except size:

- **Non-empty except → degraded error, term dropped** (fail-closed
  under-steer to the main table), regardless of an accompanying
  match-any token, specific positive literal, positive prefix-list
  (including one expanding to `0.0.0.0/0`), or resolved-empty positive
  ref. An `ip rule` has no negated `from`/`to`, so `(P \ E)` cannot be
  represented; the error text is unchanged from the former pure-except
  branch.
- **Defined-empty except → carves nothing out**: the direction reduces
  to its positive set (deduplicated), or to match-all `[""]` when the
  sole scope is the except, a match-any literal, or a resolved-empty
  positive ref. This preserves the Junos "not in {} = match all"
  semantics and the prior specific-positive + empty-except behavior
  (positive set kept, now without the misleading positive-wins warn).
- Unresolved `except` handling (#11451) is unchanged and still checked
  first; the no-except path (match-any → `[""]`, empty positive →
  skip, otherwise the positive set) is byte-identical.

The now-unused `hasPositiveRef` variable is removed. The userspace
resolver (`ResolveFilterPrefixListAddrs`) is intentionally NOT changed:
its boolean-inversion matcher can represent sole-except, and its
specific-positive + except positive-wins fallback is a separate,
already-documented tolerant-path behavior outside this issue's scope.

`pkg/routing/README.md` kernel-FBF support matrix updated to list the
#4338 match-any + `except` idiom and any positive + `except` mix among
the fail-closed non-empty-except shapes.

## Regression

New `pkg/routing/rules_14699_test.go`:

- `TestResolvePBRDirectionMatchAnyPlusExceptFailsClosed` — the decisive
  fixture named by the issue, exercised through `BuildPBRRules` (the
  production entry): 8 cells (v4 `0.0.0.0/0`+except, v6 `::/0`+except,
  `any` destination+except, positive prefix-list expanding to
  `0.0.0.0/0`+except, specific literal+except, positive
  prefix-list+except, resolved-empty positive ref+non-empty except,
  and `0.0.0.0/0`+except with no other selector). Each asserts 0 rules
  AND a degraded error naming the unrepresentable `except`. DSCP `ef`
  on the first seven cells isolates the except mechanism from the
  generic unconstrained-term guard; the eighth cell pins the degraded
  cause by error substring.
- `TestResolvePBRDirectionExceptControls14699` — controls that must
  stay green: match-any + defined-empty except stays one unconstrained
  rule; specific positive + defined-empty except keeps exactly the
  positive set; pure non-empty except still drops; specific positive
  without except is untouched.

## Validation

- RED (fix reverted, tests kept): all 8 decisive cells FAIL — seven
  emit a steered rule (`Src:""` match-all or the positive CIDR) with no
  degraded error after the positive-wins warn; the no-other-selector
  cell records only the generic "unconstrained routing-instance"
  degraded message. All 4 controls PASS on base (behavior preserved).
- GREEN (fix applied): both new tests PASS; pre-existing
  `TestBuildPBRRules` (incl. M2 empty/non-empty except cells),
  `TestBuildPBRRulesUnresolvedExceptDropsTerm11451`, and
  `TestBuildPBRRulesDefinedEmptyExceptKeepsMatchAll11451` PASS.
- Full package: `go test -count=1 ./pkg/routing/` PASS; `go build ./...`
  PASS; `gofmt -l pkg/routing/` clean.

## Risk

- Terms that previously over-steered now under-steer on the kernel
  mirror only (traffic falls back to the main table) and surface a
  degraded build error; the userspace fast path already enforced the
  exclusion and is unchanged. This is the intended fail-closed
  direction.
- Specific-positive + defined-empty except no longer emits the
  positive-wins Warn (there is nothing being ignored); rule output is
  unchanged.
- No change to the strict commit gate: specific-positive + except
  remains commit-rejected (#3359); match-any + except remains accepted
  (#4338) and now fails closed only in the kernel mirror, matching the
  README's documented support matrix.
