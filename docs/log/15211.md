# #15211 — HA fence-path residuals (A22-01, A22-02)

- **Base**: `dcc31bea75` (origin/master at branch start)
- **Branch**: `fix/15211-campaign`

## Why

- **A22-01**: `handlePeerTimeout` clears `ManualFailover` (+weight via
  `manualFailoverRestoreWeightLocked`), the peer transfer-out override
  (+snapshot, #6656) and aborted-request markers (#15164) *before* the
  `disable-rg-confirmed` fence wait. When `awaitPeerFenceLocked` aborts
  the takeover (#14158: a heartbeat arrived during the wait and the fence
  did not confirm), nothing restored them. The peer is alive and never
  fenced, yet the operator's transfer-out is silently gone; the
  heartbeat's peer-aware election has already run against the cleared
  hold, so under preempt this node can promote/move the RG contrary to
  the operator intent (observed in RED: preempt promoted local to
  primary; non-preempt left it secondary without the hold).
- **A22-02**: `handlePeerNeverSeen` ran `electSingleNode()` with no
  `markFenceUnconfirmedLocked` under every fencing policy, so the
  cold-boot never-seen takeover never rendered
  `Peer-loss takeover: DEGRADED` (#10701), unlike every peer-loss path.

## What

- `pkg/cluster/heartbeat_manager.go` (`handlePeerTimeout`): under
  `disable-rg-confirmed`, snapshot per-RG operator intent
  (ManualFailover/at/state/weight, override reqID, previous snapshot,
  aborted reqID — including entries keyed by RGs no longer in
  `m.groups`) before the clears. Only on fence abort, restore them,
  re-apply the override to the peer view rebuilt by the intervening
  heartbeat (secondary-hold + override markers, as
  `applyPeerTransferOutOverrideLocked` does), and re-run the peer-aware
  election so ownership reconverges under the restored holds. Takeovers
  that proceed (confirmed or fail-open) keep the clears unchanged.
- `handlePeerNeverSeen`: mark the takeover
  `peer never seen; no fence possible` before `electSingleNode()`.
  Sync-fresh suppression returns before the mark (no takeover).
- Regression: `pkg/cluster/fence_abort_restore_15211_test.go` —
  abort-restore for both preempt values (state/weight/at/override/
  snapshot/aborted/peer-view), confirmed and fail-open-no-heartbeat
  controls (clears preserved), never-seen degraded under all three
  policies, sync-fresh no-mark control.
- `pkg/cluster/README.md`: peer-fence section documents both residuals.

## Validation

- RED on base: `TestFenceAbortRestoresOperatorIntent15211` failed for
  both preempt values (manual hold/weight/state/override/snapshot/
  aborted all lost); `TestNeverSeenTakeoverMarkedDegraded15211` failed
  for all three policies. Controls passed on base.
- GREEN after fix: same tests pass; adjacent suites
  (`9640|14158|10701|6656|7147|NeverSeen|ColdBoot`) pass;
  `go vet ./pkg/cluster/` clean.
- Full `go test ./pkg/cluster/ -count=1`: one pre-existing failure
  `TestInstallTableProducerToResendEndToEnd9752`, reproduced identically
  on the clean base tree (unrelated golden drift), not caused by this
  change.

## Risk

- Restore is abort-only and confirmed-policy-only; the ordinary
  peer-loss takeover, `disable-rg`, and unconfigured paths are
  byte-identical in behaviour. The re-run election after restore is the
  same peer-aware election a subsequent heartbeat would run; worst case
  it reconverges to the peer's reported ownership, which is the correct
  outcome for a live, never-fenced peer. Never-seen marking is
  status-only (no election/gate change) and clears on the first real
  heartbeat via the existing `clearFenceUnconfirmedLocked` path.
