# #16860 — Former RETH member keeps the virtual MAC; swap duplicates the MAC and recovery can hijack a configured standalone port

- **Issue**: R3-B05-01. A former RETH member kept the RETH virtual MAC for the
  rest of the boot. After a member swap two local ports shared one MAC; when
  the replacement member name was absent (or later disappeared), the
  missing-member recovery renamed the operator's configured standalone port
  into the RETH member slot while the commit reported success.
- **Change**:
  - Step 2.6 (`applyDataplaneAndHACore`) records the previous apply's local
    RETH member set (`Daemon.lastRethMembers`, under `applySem`) and, before
    programming current members, restores each former member's `PermHWAddr`
    via `restoreFormerRethMemberMAC` — the same `programRethMAC`
    worker-join/link-cycle discipline, VLAN-child propagation included. This
    covers member swaps and RETH deletion alike. A post-join restore failure
    is classified `errRethPrepareLinkCycle` and fails the commit; the
    acquisition site is registered in the #6871 allowlist with a
    goroutine-containment proof.
  - Missing-member recovery (`renameRethMember` in the daemon,
    `findRethMemberByMAC` in the dataplane compiler) now excludes every
    configured interface name (`Config.ConfiguredLinuxNames`), not only
    current RETH members. A configured standalone port can no longer be
    claimed; the missing member then surfaces as an ordinary absent-link
    warning instead of a silent rename under a green commit.
  - `TestDaemonPassesRethBeforeCycleHook_5103` now expects the two legitimate
    `programRethMAC` call sites (wrapper + restore).

## Residuals

- The former-member record is in-memory: a daemon restart between the swap
  commit and any later apply loses it, but a restart also reverts every port
  to its permanent MAC at boot, so the stale-virtual-MAC window cannot
  survive the restart that would lose the record.
- The compiler cell binds `findRethMemberByMAC` + `ConfiguredLinuxNames`;
  the full compiler path (`NoDataplane` in the daemon probe) is exercised
  through the daemon sequential-apply cells, not a live NIC/eswitch.
