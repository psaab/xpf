# #15214 — RA retry-owner coverage gaps (A26-03)

- **Timestamp**: 2026-10-19
- **Action**: make wanted-but-not-started RA interfaces and repeated
  ENODEV/ENXIO send failures visible to the #6793 dead-sender retry owner,
  and report them as non-active in `Status`.
- **Files**: `pkg/ra/ra.go`, `pkg/ra/sender.go`,
  `pkg/ra/wanted_not_started_15214_test.go`, `pkg/ra/README.md`,
  `docs/log/15214.md`.

## Red before

New tests in `wanted_not_started_15214_test.go` failed on `origin/master`
(9597a48d75): `HasDeadSenders()` was false after an `Apply` whose netdev
was absent at `startLocked` (no sender is inserted, so the #6793 map walk
saw nothing and the standalone 30s retry owner never fired), and false
after five consecutive ENODEV `sendRA` failures (the sender stayed
reported `active` while sending nothing). The healthy-sender control
passed before and after.

## Change

- `Manager.wantedNotStarted` records a desired interface whose
  `startLocked` failed before insertion (missing netdev or start error).
  `HasDeadSenders()`/`DeadSenderInterfaces()` include it; `Status()`
  reports it as `State: "failed"`. It is pruned when the interface leaves
  the desired set, cleared on a successful start, and cleared by
  `Apply` empty / `Withdraw` / `WithdrawInterfaces` /
  `ClearInterfacesWithoutGoodbye` / `WithdrawOnce` (claimed) / `Clear`,
  so it can never drive the retry loop for a removed config.
- `sender.sendRA` counts consecutive ENODEV/ENXIO write failures (any
  success resets the count); at three it sets `sendDead`, which `dead()`
  reports, so the existing #2865 rebuild path restarts the sender instead
  of leaving it `active`. Other write errors stay transient. `Status()`
  reports any `dead()` sender as `failed`, not `active`.

No daemon change was needed: both retry owners (cluster digest bypass and
the standalone `raDeadSenderReassertLoop`) already gate on
`HasDeadSenders()` and rebuild through `Apply`.

## Risk

Bounded to the cited mechanism. A permanently missing netdev now drives
the existing 30s standalone re-assert (and the 2s cluster digest bypass)
until it appears or its config is removed — the intended retry, at the
pre-existing cadence and logging. Send-failure death requires three
consecutive device-gone errors, so a single link flap cannot restart a
healthy sender. `Status` gains a `failed` state value; consumers matching
only `active`/`draining` (cluster silent-stop) treat it as not-active,
which is correct for a sender that emits nothing.
