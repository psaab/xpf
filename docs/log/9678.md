## Re-verified at origin/master 557e38f12

- `upsert_synced_session` calls `reserve_synced_translation` for every peer-synced forward entry with a registered worker. Before it, the only refusals are a standalone reverse, a stale generation (both non-zero) and capacity.
- The BPF publish further down IS gated on `synced_entry_allows_local_replace`.
- The worker's `upsert_synced_with_origin` refuses when the existing entry is `!origin.is_peer_synced()` and `!allow_replace_local`.
- `reserve_flow` retires a `live_by_flow` incumbent with a different translated tuple before any of its own refusals.

## Design

**Guard.** Before the reservation, the coordinator applies the worker's exact predicate:
- the shared `synced` map holds a local-origin entry for the key; and
- `!synced_entry_allows_local_replace(ha_state, entry.metadata.owner_rg_id, now_secs)`.

Both inputs match the worker's: the worker computes `allow_replace_local` from the incoming owner RG before re-resolution.

**Returns `Applied`, before the reservation, the shared publish and the fan-out.**
- **Why stop the publish too.** Skipping only the reservation would still publish the peer's decision into the shared maps. That is the #6600 shape: a shared entry naming a port this node does not hold, which `materialize_shared_session_hit` on another worker would forward on.
- **Why `Applied`.** It matches the observable outcome before the fix: the worker refused silently while the import reported `Applied`. A new refusal token would reach the Go control plane as a peer error during a dual-primary window.

**Recovery.** Once the RG is no longer locally active, the next sync imports normally.

**Residual.** The guard reads local ownership from the shared map, which the poll path publishes for local sessions. A worker-local session absent from the shared map is still refused by the worker, but its allocator record is not protected by this guard.
