# 9945 — validated SYN-cookie clients still charge victim-side SYN-flood accounting

- **Base**: `origin/master` `a2ba528d04fbbd2af31c4bdacd298874c8790460`
- **Action**: route SYN-cookie-validated initial SYNs through the zone SYN-flood gate so the per-destination cap and aggregate accounting still run, while preserving the validated fast-path verdict and skipping only the source-scoped limiter.
- **Files**: `userspace-dp/src/screen/mod.rs`, `userspace-dp/src/screen/zone.rs`, `userspace-dp/src/screen/tests.rs`.

## Reachability, settled before implementation

The issue's cited sites are present on the base:

- `screen/mod.rs` computes `syn_cookie_validated` from the source-scoped
  `(src_ip, dst_ip, dst_port)` cache and previously set `syn_cookie_bypassed`
  without calling `zstate.syn_flood_gate`.
- `screen/zone.rs`'s gate first increments the aggregate `RateCounter`, then
  charges the per-destination sketch, then handles aggregate attack/alarm
  classification and the per-source sketch.
- The validated cache TTL is one `SynCookieCodec::EPOCH_SECS` cookie epoch: the
  regression pins that value to **64 seconds**. Its configured shape is 4096
  entries in four-way sets, as documented in `syncookie.rs`.

## STEP-0 RED on unmodified master

The new fail-on-revert cells were added before the implementation and run on the
clean base. The matching `syn_cookie_validated_` filter produced **13 cells: 3
failed, 10 passed**:

- validated traffic over the per-destination threshold returned
  `SynCookieBypass` instead of `Drop("syn-flood")`, and the destination-drop
  counter stayed zero;
- a validated burst did not make the following unvalidated SYN cross the
  aggregate attack threshold into a cookie challenge;
- a validated burst crossing the aggregate alarm threshold emitted no alarm;
- the per-source skip control passed, showing that the source-scoped exception
  is independently observable.

This is the reported bypass, not a synthetic direct call to the gate: each
validated entry is installed by minting a real cookie and driving
`validate_syn_cookie_ack_on_session_miss`.

## Fix

`check_packet_with_zone_id_opts` now calls `syn_flood_gate` for both ordinary and
validated initial SYNs. A `validated_client` flag makes the distinction explicit:

1. `syn_counter.increment_and_classify` always charges attack/alarm aggregate
   accounting before any verdict branch.
2. The per-destination sketch always charges and remains authoritative; a trip
   returns the existing `Drop("syn-flood")` verdict and bumps
   `syn_flood_dst_drops`, including for a validated client.
3. A validated client does not mint a second challenge when aggregate attack is
   already over; the caller retains `SynCookieBypass`, preserving the
   cookie-validation fast path after charging the aggregate.
4. The per-source sketch is the deliberate exception: validated clients skip it
   because the completed cookie round trip proved source liveness. Unvalidated
   traffic still takes the existing per-source path.
5. A validated over-attack packet returns before extending
   `syn_cookie_active_until_secs`, so a sustained validated burst cannot keep the
   cookie-active window alive indefinitely. An existing deadline is unchanged.

## Regression evidence

The four #9945 cells are:

- `syn_cookie_validated_charges_per_dest_cap_9945`: validated burst trips the
  victim cap and includes an unvalidated positive control in the same run;
- `syn_cookie_validated_charges_aggregate_attack_9945`: validated aggregate
  charges force a later unvalidated challenge and assert the active deadline is
  not extended;
- `syn_cookie_validated_charges_aggregate_alarm_9945`: validated aggregate alarm
  crossing raises the event, honors the one-per-second cadence, and raises again
  in the next second;
- `syn_cookie_validated_still_skips_per_source_9945`: validated source remains
  admitted while an unvalidated SYN from that source to another destination
  still trips the source cap.

After the implementation, the same filter was **13 passed, 0 failed**. The full
screen unit-test namespace (`screen::`) was **305 passed, 0 failed** across 13
suites (6107 filtered). No non-screen behavior was changed or included in this
lane; broader project validation remains the parent lane's gate.
