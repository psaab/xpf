# #17123 — Four hand-copied Unix-socket accept loops collapse into one

- **Timestamp**: 2026-10-27
- **STEP-0 (defect live on current origin/master `16db8c584e`)**:
  `grep -rn 'accept_step(' userspace-dp/src --include=*.rs | grep -v test`
  gave 4 production hits — `lifecycle.rs:784` (session), `lifecycle.rs:842`
  (control), `reinject_9506.rs:376` (submit), `reinject_9506.rs:426`
  (complete) — each with its own ~40-line hand-written loop around
  `accept_step`, and the reinject pair used a bare
  `std::panic::catch_unwind` (reinject_9506.rs:395, :450) that rendered no
  payload, counted no panic and capped no log, while control/session went
  through `serve_one_catch_unwind` (guards.rs:105) which does all three.
  Defect confirmed live; implemented the named fix.
- **What**:
  - Added `userspace-dp/src/server/accept_loop.rs` with
    `run_accept_loop(listener, AcceptLoopSpec { name, poll,
    retry_unclassified, peer_label }, running, on_panic, serve)` as the
    only accept-loop body, and `PanicPolicy::{QuarantineAndStop { sock_name,
    &Arc<Mutex<ServerState>> }, DropConnection}` selecting the panic arm.
    The loop implements once: `accept_step` decision + journal line
    (#9172), `reject_unprivileged_peer` before dispatch (#9003), and
    panic containment (#9900 F-094). The control loop's `Fail` remains
    process-fatal (`return Err`); session/reinject `Fail` (unreachable
    with `retry_unclassified: true`) logs and sleeps `AcceptBackoff::MAX`.
  - Migrated all four loops: session (10 ms poll, retry) and control
    (50 ms, fail) in `lifecycle.rs`, reinject submit/complete (1 ms,
    retry, `DropConnection`) in `reinject_9506.rs`. Ordering/poll/labels
    preserved verbatim per socket, including the reinject peer labels
    (`"reinject submit"` vs accept name `"reinject submit socket"`).
  - `helpers/guards.rs`: extracted the single `catch_unwind(` call in
    `server/` into `serve_catch_unwind` returning a three-way
    `ServeOutcome { Ok, HandlerErr, Panic(rendered) }` so a handler `Err`
    is never mistaken for a panic payload. `serve_one_catch_unwind`
    (quarantine arm) and the new `serve_connection_panic_counted`
    (drop-connection arm) both build on it and share
    `server_panic_payload_message`. Added sibling counter
    `REINJECT_HANDLER_PANICS` (not folded into `SERVER_HANDLER_PANICS`,
    which means "quarantined and shutting down" — a reinject panic does
    neither). The accept loop prints the reinject panic line (payload
    rendered) only while the counter is within the first 10.
  - Updated the two textual-wiring cells to bind the new shape:
    `both_accept_loops_are_wired_through_accept_step_9172` (lifecycle.rs
    carries no `accept()`/`accept_step(`, accept_loop.rs holds the only
    production `accept_step(` fed by `accept()`, run() wires session
    retry=true / control retry=false) and
    `reinject_accept_loops_are_wired_through_accept_step_15112`
    (spawn carries no `accept()`/`accept_step(`, wires both sockets via
    `run_accept_loop` with `retry_unclassified: true`). All other
    #9172/#15112 cells unchanged.
  - Updated `server/README.md` Gotchas entry to name the single loop.
