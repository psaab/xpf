# Issue #14667 — Hardcoded `session_id: 0` in reverse-companion synthesis defeats `DeletePolicyBatch` revocation

- **Issue:** psaab/xpf#14667 (deep-review D4-04, validated MATERIAL by two
  independent re-review passes).
- **Lane branch:** `fix/14667-campaign` off `origin/master`.
- **Files:** `userspace-dp/src/session/mod.rs`,
  `userspace-dp/src/afxdp/shared_ops/reverse_synth.rs`,
  `userspace-dp/src/afxdp/ha/session_import.rs`,
  `userspace-dp/src/afxdp/worker/synced_entry.rs`,
  `userspace-dp/src/session/README.md`,
  `userspace-dp/src/afxdp/session_glue/tests.rs`.

## Defect (present at base)

Both reverse-companion synthesis sites published `session_id: 0`:

1. `install_reverse_session_from_forward_match`
   (`shared_ops/reverse_synth.rs`) installed the companion on the
   synthesizing worker (which minted a worker-namespaced id), then
   published and replicated a `SyncedSessionEntry` with
   `session_id: 0`.
2. `synthesized_synced_reverse_entry_in_table` (same file), used by the
   HA-import fan-out, takeover prewarm, reconcile replay and TUN-origin
   builders, likewise stamped `session_id: 0`.

`upsert_synced_with_origin` (`session/install.rs`) mints a fresh
worker-namespaced id when the wire id is 0, so every sibling worker held
a DIFFERENT id for the same reverse companion.
`ListSessionsByPolicy` captures the listing worker's companion id and
`DeletePolicyBatch` identity-checks it on every worker
(`session_glue/commands/delete_synced.rs`): on W-1 workers the check
missed, the companion survived as `partial`, and the coordinator
probe/repair republished its conntrack mirror. Single-worker tests
cannot see this.

## Change

- Site 1 (live reply): the published/replicated entry now carries
  `sessions.session_id_for(reverse_key)` — the id the synthesizing
  worker just minted — so siblings adopt it verbatim.
- Site 2 (coordinator synthesis): there is no minting worker, so the
  companion id is DERIVED deterministically from the forward entry's
  stable id by the new `synthesized_companion_session_id`
  (`session/mod.rs`): reserved namespace `0xFFFE << 48` (one below the
  Go control plane's `0xFFFF`, #6198; disjoint from every worker
  namespace, whose only `0xFFFF` value is the refused control-plane
  reservation) plus the forward id's low 48 bits (0 corrected to 1).
  Every worker, either node, and any re-derivation (prewarm, replay,
  restart) yields the SAME companion id for the same forward. A forward
  with no stable id (0) derives 0 and keeps the legacy per-worker
  fallback in `upsert_synced_with_origin`.
- The stale-companion retirement guard in
  `delete_synced_reverse_companion` (`ha/session_import.rs`), which
  identity-checks the companion it retires on a same-key NAT
  replacement, now expects that same derived id instead of the legacy
  0 incarnation.
- Docs: `SyncedSessionEntry.session_id` field doc and
  `session/README.md` companion bullet record the #14667 exception to
  the "synthesized companions leave this 0" rule.

NOT changed: the `DeletePolicyBatch` worker delete path itself (its
identity check is the correct fail-closed guard), the forward
session's id handling, and any other `session_id: 0` publish
(local-origin entries whose Open delta carries the real id straight
off the live entry).

## Evidence

- New regression
  `synthesized_reverse_companion_converges_session_id_across_workers_14667`
  (`afxdp/session_glue/tests.rs`) drives BOTH sites through the exact
  chain: synthesize → replicate to a second worker (namespaces 0 and 1)
  → capture the companion id from worker 0 → identity-conditional
  policy remove (`handle_remove_policy_item`, as `DeletePolicyBatch`
  dispatches it) on both workers → both companions removed, cleanly
  (no partial/refused). It also asserts the shared authority carries
  the synthesizer's id (site 1) and that the derived companion id is
  non-zero and distinct from the forward's (site 2).
  - RED (pre-fix tree, same test): failed at the site-1 shared-authority
    assertion — shared companion `session_id` was 0 while worker 0 held
    its minted id (`left: 0, right: 2`).
  - GREEN (this lane): 1 passed.
- Neighbors: `cargo test --release --bin xpf-userspace-dp --
  synthesized_synced_reverse_entry session_id policy_remove` — 26
  passed, 0 failed.
- Full release suite (`--bins --tests`, single-threaded): 8416
  passed, 54 failed, 8 ignored. The 54 fail in isolation too and are
  unrelated to this change (wire-fixture drift, shim/coordinator
  environment cells, WG/GRE tunnel cells — none touch
  reverse-companion identity), except one cell this fix DID break and
  then repaired:
  `ha_same_key_replace_changing_nat_retires_old_reverse_companion_13710`
  failed because the stale-companion retirement guard
  (`delete_synced_reverse_companion`) still expected the legacy
  `session_id: 0` incarnation. It now derives the expected companion
  id from the owner forward (`synthesized_companion_session_id`), and
  the cell passes again. One full-run-only flake
  (`screen::tests::icmp_flood_secondary_zone_ceiling_still_fires`)
  passes in isolation and is unrelated.

## Risk

Bounded to the identity stamped on synthesized companions. The derived
namespace cannot collide with a worker-minted id (disjoint high bits)
or with the Go control-plane reservation (`0xFFFF` vs `0xFFFE`).
Companion ids are correlation/delete-identity stamps, never lookup
keys, so adopting a derived id cannot affect forwarding. Legacy
zero-id forwards keep the pre-#14667 per-worker fallback. Lab
verification on a multi-worker loss cluster was not performed; the
2-worker fixture exercises the exact synthesis→replication→delete
mechanism in-process.
