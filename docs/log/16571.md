# #16571: valueless packed screen sub-thresholds commit strict-clean

- **Timestamp**: 2026-10-24
- **Action**: The four screen families (`icmp`/`tcp`/`ip`/`udp` under
  `screen ids-option`) are `closedWorldOpaque`, so the #8597
  valueless-leaf gate in the schema walk never reached a packed tail:
  `tcp syn-flood attack-threshold 300 source-threshold;`,
  `icmp flood threshold;`, `tcp port-scan threshold;` (and the flat
  multi-leaf `set` spelling) committed strict-clean while the braced
  spelling was rejected — the sub-cap was dropped, or the Junos default
  substituted, with no error and no warning. Fixed at the compiler
  record (the issue's distinct-missing-value direction):
  `compileScreen` now records every authored-but-valueless numeric
  leaf on the new `ScreenProfile.MissingValue` — flood/scan/sweep
  `threshold` sub-leaves, syn-flood
  `alarm/attack/source/destination-threshold` + `timeout`, and the
  `limit-session` caps — and `validateScreenMissingValueStrict`
  refuses them at strict commit with the #8597 message; the tolerant
  load / peer-sync path downgrades to a warning
  (`lenientScreenMissingValue`) and keeps the default/disabled value.
  A `threshold` sub-leaf counts as authored only when the sub-leaf
  node itself is present, so bare `flood;` / `port-scan;` /
  `ip-sweep;` (no `threshold` keyword) still arm the #3230 Junos
  default, and unset syn-flood subfields / limit-session caps stay
  disabled (#15269). This deliberately amends the compile-level
  contract `TestScreenValuelessLimitSession15944` pinned: strict now
  rejects, tolerant keeps 0 with a `MissingValue` record (never a
  `BadNumeric`).
