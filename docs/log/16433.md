# #16433 — `vlan-tags outer N <anything>` committed as single-tag VlanID=N

## Defect

`vlanTagsHasToken` compared tokens exactly (`k == token`), so the Junos
inner spellings `inner-list`, `inner-range` and `inner-vlan-id-range`
carried no `inner` token and the #5879 QinQ gate counted
`vlan-tags outer 100 inner-range 1-200` as an outer single S-tag. The
#15035 reader then took the first value after `outer` and ignored every
remaining token, so the unit compiled `VlanID=100, InnerVlanID=0` on a
green commit in both AST shapes. Arbitrary tails (`outer 100 bogus 7`)
were likewise accepted. Single-tagged VID-100 frames were admitted into
a zone the operator had scoped to double-tagged traffic, and the
configured QinQ traffic was not served.

Probe on base: `outer 100 inner-range 1-200`, `outer 100 inner-list
[ 10 20 ]`, `outer 100 inner-vlan-id-range 1-200` and `outer 100 bogus 7`
each ACCEPTED with VlanID=100 in flat and hierarchical shapes; controls
`outer 100` ACCEPTED as VlanID=100 and `outer 100 inner 200` REJECTED
#5879.

## Fix

Close the `vlan-tags` statement's world in the existing QinQ gate — no
new gate, opt, or schema leaf:

- `pkg/config/compiler_interfaces_qinq.go`: new `vlanTagsIsInner`
  (exact `inner` or any `inner-*` token, packed Keys or hierarchical
  child heads) and `vlanTagsIsOuterOnly` (exactly `outer <one value>`
  and nothing else: packed Keys, `vlan-tags { outer 100; }`, or
  `vlan-tags { outer { 100; } }`; value validity stays with the #15035
  reader so TPID-prefixed values keep their #15035 message).
  `unitVLANStack` now classifies each `vlan-tags` node as inner
  (existing #5879 QinQ text), outer-only, or invalid (new
  `qinqUnitStack.invalid`); `qinqFinding.message` prefers the QinQ text
  when a unit carries both, else renders the #16433 text naming the
  statement and the `outer <vid>` / `vlan-id` remedy. Findings trigger
  on inner OR invalid, merged across duplicate-unit views.
- `pkg/config/compiler_interfaces.go`: the #15035 reader skips every
  `vlan-tags` node that is not outer-only (was: skipped only exact
  `inner`), so on the tolerant path a defective node's outer value
  never silently applies as a single tag. Strict commits never reach
  the reader for these shapes — the gate rejects first.
- `pkg/config/compiler_opts.go`: `lenientQinQVLANStack` comment widened
  to the `inner-*` / closed-world scope (no new opt; both defect
  classes downgrade through the existing #1960 warning).

NOT changed: the schema (`vlan-tags` stays intentionally unadvertised),
the #14574 tagging gate (its positive-VID predicate is scoped to the
tagging question; the QinQ gate now owns the tail), and the dataplane.

## Tests

- `pkg/config/vlan_tags_closed_world_16433_test.go`:
  `TestVlanTagsInnerSpellingsRejected16433` (inner-range, inner-list
  bracketed and bare, inner-vlan-id-range, inner-bogus, bogus tail,
  extra value, inner keyword — flat + hierarchical packed, plus block
  children, split statements, standalone malformed, `outer 0 bogus`),
  `TestVlanTagsOuterOnlyStillCompiles16433` (flat/hier/block/one-deeper
  compile VlanID=100, `outer 0` untagged, TPID keeps #15035),
  `TestVlanTagsClosedWorldLenient16433` (lenient warns #5879/#16433,
  defective node never applies, valid sibling still applies).
- `pkg/configstore/vlan_tags_closed_world_16433_test.go`:
  `TestCheckTextVlanTagsClosedWorld16433` — the acceptance surface:
  four probe spellings plus bogus rejected by CheckText in both
  shapes, `vlan-tags outer 100;` still compiles VlanID=100.
- Mutation proofs: reverting inner detection to exact `inner` fails
  the inner-* rows (they fall to the #16433 text); restoring the
  any-`outer` classification fails the bogus/extra-value rows;
  restoring the old reader skip fails the lenient never-applies pin.
  `renderVLANStmt` now folds grandchildren too, so a one-deeper
  finding renders its value.

## Risk

Strict commits that previously (silently, wrongly) accepted an
`inner-*` spelling or any trailing `vlan-tags` token now fail with a
remedy message. `vlan-tags outer <vid>` configs are unchanged. Lenient
loads keep booting (#1960): the finding becomes a warning and the
defective statement is not applied, so a persisted stacked-VLAN unit
loads untagged rather than as the single tag it never was.
