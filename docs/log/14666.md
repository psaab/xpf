# 14666 — Local-hit shared_identity blindness, conditional queue-full NAT release, companion stranding/clobber

- **Timestamp**: 2026-10-17
- **Action**: fix three legs of D4-03 in the userspace dataplane
  session-glue delete/purge paths.
- **File(s)**: `userspace-dp/src/afxdp/session_glue/resolve.rs`,
  `promote.rs`, `worker_commands.rs`, `commands/delete_synced.rs`,
  `types/runtime.rs`, `session_delta.rs`, `ha/session_import.rs`,
  `session_glue/tests.rs` (+ pattern updates in `ha_tests.rs`,
  `pbr_install_table_9752_tests.rs`).

## The defect

All three sites present on `origin/master` at filing (`09c6b9ed`):

1. **Local-hit purge blindness.** `resolve.rs` derived
   `shared_identity` solely from `hit.shared_entry`, which is `None`
   on a worker-local hit — the normal case after
   `UpsertSynced`/`DemoteOwnerRG` materialized the row into the local
   table. `purge_translated_synced_hit_with_context` therefore took
   the `Absent` branch: never removed the shared entry, never
   replicated the conditional delete to siblings. Sibling state and
   shared authority leaked for exactly the peer-synced translated
   population.
2. **Queue-full conditional repair.** When a sibling queue refused
   `DeleteSyncedConditional`, `replicate_session_delete_conditional`
   called `release_source_nat_allocation_for_worker` /
   `release_nat64_allocation_for_worker` unconditionally for the
   target worker. The allocator is keyed by `(flow, translated)` with
   no incarnation, so a live replacement on that worker sharing the
   tuple could have its port freed under it.
3. **Companion conflation.** `handle_delete_synced_with_guard`
   recursed into the companion with `expected_id = 0`
   (unconditional): `session_id_for == 0` (absent, already converged)
   and `== other_id` (replaced incarnation) were treated alike, so a
   companion replaced during queue delay was clobbered with its
   forward; producers captured no companion identity at all.

## Fix

1. `resolve.rs`: for a peer-synced local hit with a nonzero local
   `session_id`, read the shared entry under the same key and adopt
   `(session_id, generation)` only when the shared entry's
   `session_id` matches the local row's adopted id. The purge's
   existing under-lock `(session_id, generation)` predicate remains
   authoritative — a replacement published in the window declines
   and survives (control cell pins this).
2. `worker_commands.rs`: conditional replicate performs **no**
   on-behalf NAT/NAT64 repair on queue-full. It still bumps
   `SESSION_DELETE_DROP_EPOCH` so the sibling's delete-drop sweep
   reconciles against shared authority. `repaired` stays 0 for
   conditional drops (operator counter delta is the documented
   signal). The unconditional `replicate_session_delete_repairing`
   is unchanged (control cell pins it still frees the port).
3. `DeleteSyncedConditional` gains `companion_expected_id`, captured
   at the same moment as `expected_id`: shared reverse entry id at
   the stale-close producer (`session_delta.rs`) and at the
   coordinator fan-out (`session_import.rs`, read before fan-out;
   0 when no shared reverse row remains — worker then preserves a
   replaced companion, bounded leak healable by sweep/age-out).
   The worker guard deletes the companion only when live id is 0
   (converged), expected is 0 (legacy uncaptured), or live ==
   expected; a different live id is preserved. Policy-batch path
   already validated identity, so it passes its captured id through.

## Scope notes

NOT changed: unconditional delete repair, policy-batch companion
validation logic, shared removal predicate, NAT allocator holder
semantics. No wire-format change (WorkerCommand is in-process only).
Residual: conditional queue-full drops no longer repair the NAT bit
inline; the stranded stale bit is reclaimed by the sibling's
delete-drop sweep / holder retirement, never by freeing a possibly
live replacement port — the safe direction per
`PortAllocator::drop_holder_locked`.
