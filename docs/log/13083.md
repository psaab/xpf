# Issue #13083 — index expanded NAT address pools

- **Issue:** #13083 — D6-04 pool-vector membership scans caused per-packet
  linear scans and a quadratic NAT64 drain check over pools of up to 65,536
  addresses.
- **Branch:** `fix/13083-campaign-pub`
- **Worktree:** `/var/worktrees/campaign-pub/wt-13083`

## Why

Source-NAT validation and translated-address matching used `Vec::contains`
for expanded address pools, and synced reservations used `Vec::position` to
recover allocator slots. A /16 therefore required up to 65,536 comparisons on
these paths. More severely, NAT64 minting scanned every NAT64 pool address and
called draining-pool membership scans for each one, reaching 4,294,967,296
address comparisons for two disjoint /16 pools. This could stall an AF_XDP
worker during configuration drain and drop co-queued traffic.

## What

- Added source-NAT and NAT64 address-to-position indexes, keeping the ordered
  vectors authoritative for allocator selection. The maps are shared with
  `Arc` across worker-state clones; insertion keeps the first occurrence so
  slot lookup retains `Vec::position` semantics.
- Routed source-NAT membership/revalidation and synced reservation lookups
  through these indexes, and replaced NAT64 synced `position` scans.
- Precomputed the NAT64-prefix-to-draining-allocator overlap relation during
  forwarding build. The packet path now checks only live counts on the small
  list of actually overlapping draining allocators; drain state remains
  dynamic, and disjoint pools do not quarantine NAT64 minting.
- Added /16 index-position and disjoint /16 NAT64 drain regressions. Existing
  same-address drain tests continue to pin fail-closed behavior for both NAT64
  allocation modes.
