# #16492 — a #15273-deferred api-auth migration strands `.configdb/api-auth-migration.json`, so the next plain commit or HA config sync makes the following boot fatal

- **Timestamp**: 2026-10-24
- **Context**: On the upgrade boot crossing the #10826 api-auth migration
  with legacy cleartext REST api-auth configured and `confirm.json`
  present but unreadable, #15273 defers the durable active rewrite: the
  hashed tree lives in memory, `active.json` keeps the pre-migration
  generation, and the staging record (`OldHash=H1` → `NewHash=H2`) plus
  the pre-migration rollback-sidecar binding stay on disk. `Load`
  returns OK with `ConfirmRecoveryReadFailed` set (/health 503). The
  documented remedy — a superseding plain commit — or a routine HA
  `SyncApply` then writes a new generation H3 and rebinds the sidecar
  to H3, but no promotion path retired staging. The next boot's
  `apiAuthMigrationStagingConsistent` gate saw sidecar H3 matching
  neither staged side and returned `ErrConfigDBUnreadable`, so xpfd
  refused to start on every later boot until an operator deleted a file
  no message named (the daemon fatal pointed at the healthy
  `active.json`). Under persistent `confirm.json` corruption the
  deferral repeats every boot, so the only exit always tripped it.
- **Fix**: a durable promotion whose rollback sidecar binds the new
  on-disk active generation exactly (same hash and file identity) while
  naming neither staged hash supersedes the staged transition
  (`apiAuthMigrationStagingSuperseded` in
  `pkg/configstore/rollback_metadata.go`). Every promotion that rebinds
  or shifts the sidecar now retires staging via
  `retireSupersededAPIAuthMigrationStaging`: plain commit and
  commit-confirmed (after `saveRollbackFiles`), `SyncApply` (after its
  shifted save; deferred with the save on a pre-rename write failure),
  `PromoteRollback` and boot-recovery rollback (after
  `rebindRollbackMetadataLocked`), and the persist-retry heal (after its
  rebind or deferred-ladder save). `Load` re-checks supersession before
  both staging-consistency gates (present-active and absent-active
  arms), so a retirement lost to a crash or a failed delete self-heals
  on the next boot instead of bricking it. The check stays exact: any
  sidecar/disk disagreement (tampered `active.json` against a stale
  sidecar, missing or empty sidecar, malformed staging) is not
  supersession and stays fail-closed, and the fatal error now names the
  staging file (`staged api-auth migration in
  .configdb/api-auth-migration.json ...`). The committed tree a
  promotion writes already carries hashed api-auth verifiers (the
  deferred boot's in-memory tree is hashed; `SyncApply` hashes before
  persisting), and boot2's ordinary migration hashes anything left, so
  api-auth is hashed on disk after the recovery boot. NOT changed: the
  staged Old/New alias admission, per-slot staging checks, and the
  #15273 deferral itself — with no intervening promotion, staging and
  the pre-migration binding survive untouched.
- **File(s)**: `pkg/configstore/rollback_metadata.go`,
  `pkg/configstore/store_persist.go`, `pkg/configstore/store_commit.go`,
  `pkg/configstore/store.go`,
  `pkg/configstore/api_auth_migration_superseded_16492_test.go` (new),
  `pkg/configstore/README.md`, `docs/log/16492.md`,
  `debian/changelog`
- **Validation**: new `*_16492` cells — arm A (deferred boot → plain
  `Commit` → boot2 clean, staging retired, api-auth hashed on disk),
  arm SyncApply (same via HA sync), control B (no promotion: boot2
  still defers, staging and pre-migration active survive), control C
  (readable confirm: boot1 converges, confirm + boot2 clean), and a
  negative control (direct `active.json` tamper against a stale sidecar
  stays `ErrConfigDBUnreadable`, now naming the staging file, staging
  preserved). Arms A/SyncApply and the negative control's message
  assertion are RED on base (staging stranded / fatal boot / unnamed
  file); the full `pkg/configstore` suite and the neighboring
  #10826/#15273/#9887/#8566 migration tests stay green (see PR for
  exact counts).
- **Residual**: component level only, matching the finding's evidence —
  the daemon's `loadFatalUnreadable` classification of the wrapped
  error is unchanged and covered statically (the error still wraps
  `ErrConfigDBUnreadable`). A promotion whose sidecar write itself
  degrades (`rollbackPersistDegraded`) leaves staging in place
  deliberately: the next boot's Load-side supersession check retires it
  once the sidecar actually binds the disk generation, and until then
  the fail-closed gate is the correct posture for an unverified ladder.
