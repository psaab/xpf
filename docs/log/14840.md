# Release the reverse/policy-batch Coordinator steering claims on delete (#14840)

- **Issue**: #14840 (gemini-hostile D6-02, revalidation 002).
- **Cause**: An HA import publishes two steering entries as the
  Coordinator: the forward under `owner=entry.key` and the synthesized
  reverse under `owner=reverse.key`
  (`publish_synced_entry_or_note_unpublished(&reverse.key, ..)` in
  `userspace-dp/src/afxdp/ha/session_import.rs`). The forward's live row
  set also claims `row(reverse)` under `owner=entry.key`, so the reverse
  row carries two Coordinator claims. Pre-fix,
  `delete_synced_session_gen_marked` issued exactly one steering delete,
  keyed on the removed forward entry, releasing only the
  `owner=entry.key` claims. `row(reverse)` therefore stayed claimed by
  Coordinator under `owner=reverse.key` (`OwnerRemoval::Remaining`):
  the BPF row was never deleted and every later aliased teardown
  skipped it, for the life of the process. Policy-batch limb:
  `execute_deferred_redirects` executed each collected intent only
  under `SteeringHolder::Worker(intent.worker_id)`, and
  `remove_shared_policy_item` removed the shared-map rows with no
  steering delete and no `delete_dnat_table_entry` at all — so a
  batch-removed synced session kept both Coordinator claims and its
  DNAT steering hold.
- **Change**:
  - `delete_synced_session_gen_marked` retains the removed reverse
    incarnation from the reverse shared removal and, alongside the
    forward steering delete, deletes the reverse entry under
    `owner=reverse.key` (only when the reverse removal landed or was
    already absent; a declined reverse removal keeps its claim).
  - `remove_shared_policy_item` captures the removed forward/companion
    incarnations and, on an authoritative removal, releases the
    Coordinator steering claims for both (plus the already-absent
    companion's claim when converged, and nothing for a preserved
    partial companion) and releases the forward's DNAT hold via
    `delete_dnat_table_entry` — the same teardown the synced delete
    performs, under the caller's batch lease.
  - `execute_deferred_redirects` additionally executes each intent
    under `SteeringHolder::Coordinator`; releasing a non-existent
    coordinator claim is a no-op, so purely local worker sessions are
    unaffected.
  - NOT changed: worker-holder execution (still per collecting
    worker), DNAT holder accounting (forward-only, as at publish),
    and the `forward_only` path (no reverse derivation, as before).
- **Regression coverage** (`userspace-dp/src/afxdp/ha_tests.rs`):
  - `synced_delete_releases_coordinator_claim_on_reverse_row_14840` —
    real `upsert_synced_session` + `delete_synced_session`; asserts
    `steering_owners.owner_count(session_map_row(reverse))` is 2 after
    import (both owners) and 0 after delete (the decisive check named
    by the issue).
  - `policy_shared_remove_releases_coordinator_and_dnat_14840` —
    drives `remove_shared_policy_item` on a matched forward+reverse;
    asserts both Coordinator claims and `dnat_steering_holder_count`
    go to 0.
  - `policy_deferred_redirects_release_coordinator_claim_14840` —
    pre-claims one row for Worker(1) and Coordinator, executes the
    intent, asserts `owner_count == 0`.
  - `policy_batch_uncovered_intent_fails_loud_then_quiesces_shared_10512`
    assertion narrowed: the shared quiesce now legitimately records
    BPF deletes for the batch's own tuples, so the cover-failure
    property is asserted as "no write names the uncovered intent key".
- **RED evidence**: With the two production files reverted
  (`git checkout -- session_import.rs session_domain.rs`, tests kept),
  all three new cells fail: reverse claim `left: 1, right: 0` after
  synced delete; forward claim `left: 1, right: 0` after policy remove;
  coordinator claim survives deferred execution. Command:
  `cargo test --manifest-path userspace-dp/Cargo.toml --bin
  xpf-userspace-dp 14840 -- --test-threads=1` (0 passed, 3 failed).
- **GREEN evidence**: With the fix restored, the same command reports
  3 passed. Full `afxdp::ha::` suite: 200 passed, 3 failed —
  `policy_batch_uncovered_intent_...` (fixed above, see Regression
  coverage), plus two base-attributed failures reproduced on the
  unmodified base: `strict_mirror_refusal_replays_imported_lease_and_
  holder_mask_11476_10789_f4` (fails on base) and
  `merge_owner_rg_candidate_keys_scales_linearly_not_quadratically`
  (timing-sensitive; passes standalone on base). Test environment:
  `CARGO_TARGET_DIR=/var/worktrees/.cache/cargo-14840`. No live
  dataplane probe was run.
- **Blast radius / risk**: Deletes now release strictly more claims
  than before, only for incarnations actually removed under the
  removal lock / batch lease. The one behavior delta beyond the fix:
  in a policy batch whose worker intent is uncovered, the abort-path
  shared quiesce now also deletes the batch tuples' steering rows
  (previously left claimed) — convergent with the shared removal it
  accompanies. Rows another owner still holds remain protected by
  the registry's last-owner rule.
