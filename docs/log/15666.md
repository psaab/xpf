# #15666 — `policy-rematch extensive` fingerprint tore down sessions on non-verdict edits

## Defect

`PolicyResolvedFingerprints` (`pkg/dataplane/userspace/policies_resolved_fingerprint.go`)
hashed `json.Marshal(PolicyRuleSnapshot)` after zeroing only `PolicyID`.
The snapshot serializes non-verdict fields — `LogSessionInit` /
`LogSessionClose` (`then log`), `SchedulerName`, and `Inactive` (always
`true` for a named scheduler because fingerprints are built with
`activeState = nil`) — and match collections in authored slice order
(`Applications`, `ApplicationTerms`, literals, expanded addresses,
`MatchFromZones` / `MatchToZones`).

Under `policy-rematch extensive`, the daemon's third invalidation arm
(`policyReferencedObjectChanged`, `pkg/daemon/daemon_policy_invalidate.go`)
ORs this fingerprint comparison with the two correct gates
(`policyMatchOrActionChanged` — set-compare, ignores log/scheduler name;
`policySchedulerBecameInactive` — live active→inactive only). Any
fingerprint delta therefore marked the policy changed and cleared its
live sessions: toggling `then log`, binding/swapping a currently-active
`scheduler-name`, or reordering match-list elements all tore down
established sessions that Junos would keep.

Verified pre-fix by probe (RED): log toggle, scheduler bind,
application reorder, source-literal reorder, and scoped-global zone
reorder each changed the fingerprint; an application redefinition
correctly changed it (control).

## Fix

- Added `canonicalResolvedRule` in `policies_resolved_fingerprint.go`:
  the fingerprint now hashes a normalized copy of each resolved rule —
  `PolicyID` / `RuleID` zeroed (identity/positional), `LogSessionInit` /
  `LogSessionClose` / `SchedulerName` / `Inactive` zeroed (non-verdict;
  scheduler verdict transitions remain owned by
  `policySchedulerBecameInactive` against live scheduler state), and
  every set-valued match collection canonicalized to sorted,
  duplicate-free form (`SourceAddresses`, `DestinationAddresses`,
  `SourceBookIDs`, `DestinationBookIDs`, `SourceLiterals`,
  `DestinationLiterals`, `Applications`, `MatchFromZones`,
  `MatchToZones`). `MatchFromZone` / `MatchToZone` are re-derived via
  `config.ScopeSingular` from the canonical sets. `ApplicationTerms`
  are sorted by JSON encoding with duplicates removed: term order only
  picks which overlapping term stamps the per-application inactivity
  timeout, never the verdict or the matched flow set.
- Both fingerprint entry points share the canonicalization:
  `PolicyResolvedFingerprints` (extensive rematch) and
  `PolicyResolvedIdentityStrippedFingerprints` (rename ancestry now also
  strips identity on top of the canonical form, so a rename combined
  with a log toggle or match reorder keeps continuity).
- NOT changed: the wire snapshot itself (`buildOneRuleSnapshot` /
  publish path still ship log flags, scheduler name, and config-order
  terms — the dataplane needs them), the daemon's three-arm gate, and
  quarantine scrub ordering (canonicalization runs after
  `policySnapshotAfterZoneQuarantine`, so #14330 behavior is preserved).

## Validation

- New `pkg/dataplane/userspace/resolved_fingerprint_nonverdict_15666_test.go`:
  log/scheduler-bind/scheduler-swap/application-reorder/address-reorder
  all fingerprint-equal (plus identity-stripped equality); controls prove
  application redefinition, membership narrowing, action change, and
  address-set value change still move the fingerprint; scoped-global
  zone reorder equal / membership change differs; 5× determinism.
- New `pkg/daemon/daemon_policy_rematch_nonverdict_15666_test.go`:
  `changedPolicyRuntimeIDs` clears nothing for the non-verdict cases
  (acceptance criterion 1 at the gate) and clears exactly `web` for an
  application redefinition (criterion 2).
- Existing suites: userspace fingerprint/quarantine/feed/address-book
  tests and daemon rematch/scheduler/rename tests — see PR.

## Risk

- Fingerprint values change for every policy (canonical form), but they
  are computed fresh on both sides of every commit diff; no persisted
  fingerprint exists to skew against.
- Residual: reordering overlapping application terms with different
  inactivity timeouts no longer re-evaluates sessions. The verdict and
  matched set are unchanged; only the stamped idle timeout of a future
  re-match would differ, which is outside the rematch contract.
