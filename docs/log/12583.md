# #12583 — backup-router route replaced on every management-VRF reconcile

- **Timestamp**: 2026-10-13 (PR #12699 review fold the same day)
- **Action**: The system backup-router route takes its gateway's management
  output link the same way as an interface-less static next-hop, and the
  reconcile keeps exact route identities. A gateway that resolves to no
  management link keeps LinkIndex 0, so the route is replaced, and the kernel
  re-checks the gateway, on every reconcile.
- **Base**: `origin/master` `3c84d334e`
- **Files**: `pkg/daemon/mgmtvrf_static_routes.go`,
  `pkg/daemon/mgmtvrf_backup_linkindex_12583_test.go`,
  `pkg/daemon/mgmtvrf_backup_linkindex_kernel_12583_test.go`,
  `pkg/daemon/README.md`, `docs/log/12583.md`

## Why

`mgmtBackupRouterRoute` builds the backup-router route without an output link.
The kernel lists a gateway route with the output link it chose, so the desired
key (`…|0|<gw>`) never matched the listed key (`…|9|<gw>`), and every
management reconcile replaced the unchanged route again. Reconciles run on
every commit, every management DHCP lease change and every management-route
debt retry.

On this base the symptom is that one redundant `RouteReplace` per reconcile;
the route stays installed. The present/absent flap the issue describes
(replace, then delete) predates #12539, whose overwritten-slot guard keeps the
cleanup pass from deleting a slot that the same pass replaced. The RED run
below shows `deleted=[]`.

The first version of this PR let a desired LinkIndex of 0 match a listed route
on any link. Review showed that this removed the only re-check of the
backup-router. Real-kernel probes (private netns, VRF on table 999) found:

- a route that the kernel first installed through a non-management link stayed
  there after the management link was connected;
- a route stayed on the old link after the gateway's subnet moved to another
  management link;
- a route whose gateway became unreachable was kept, and the apply returned
  success. That breaks the #5867 fail-closed rule (`daemon_apply.go`).

## What

- `mgmtStaticImplicitLinkIndex` now holds the interface-less next-hop
  resolution that statics already used: the live table-999 connected route
  that contains the gateway or, for IPv6, the management link that
  `inferIPv6StaticNextHopInterfaces` assigns from the configured prefixes. The
  static next-hop path and the backup-router both call it.
- The backup-router's IPv6 gateway is passed to
  `inferIPv6StaticNextHopInterfaces` as an extra next-hop, so it gets the same
  inference as a static next-hop with that address.
- A resolved gateway gives the desired backup-router that link. The listed
  route then has the same key, so an unchanged reconcile replaces nothing, and
  a gateway that moves to another management link moves the route in place.
- An unresolved gateway keeps LinkIndex 0. That key matches no listed route, so
  the route is replaced on every reconcile and the kernel validates the gateway
  each time. When the gateway is unreachable the replace fails: the apply
  returns the error (commit error and management-route debt), and the cleanup
  pass deletes the stale route because the failed replace did not overwrite its
  slot.
- Presence and cleanup matching stay exact on every key field, LinkIndex
  included. The wildcard matcher is gone.

Kernel behaviour this relies on (7.2.8, private netns, VRF on table 999):

- A gateway route added without an output link is listed with the link the
  kernel chose (`default via 192.0.2.1 dev fxp0`; IPv6 the same).
- IPv6 connected routes are listed with universe scope (`scope global`), so
  `mgmtStaticConnectedLinkIndex`, which requires link scope, never matches
  them. On a real kernel an IPv6 gateway resolves only through the inference.
- With no output link and no table-999 connected route for the gateway, the
  kernel falls back to a full lookup and can install the table-999 route
  through a main-table link that is not a management link.
- An unreachable gateway fails the replace: IPv4 `Nexthop has invalid gateway`
  (ENETUNREACH), IPv6 `No route to host`. An IPv6 link-local gateway without an
  output link fails with `Egress device not specified`.

## Risk

- An unresolved gateway behaves as on master: one replace per reconcile. The
  first install can still go through a non-management link until the
  management link is connected; the next reconcile then moves the route.
- IPv6 resolution comes from configured prefixes, as for static next-hops. A
  gateway in a prefix learned only at runtime (SLAAC, DHCPv6) stays
  unresolved and is replaced on every reconcile, as before. With a configured
  prefix, the route is no longer re-checked on every reconcile, the same as an
  IPv6 static next-hop.
- An IPv6 link-local backup-router gateway now installs when the inference
  assigns it a management link, which happens when the only configured IPv6
  interface outside routing instances is a management interface. The kernel
  used to refuse it on every reconcile for lack of an output link.
