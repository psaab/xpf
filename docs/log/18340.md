## Why

The named `tunnel_wg_nodf_oversize_emits_ptb_with_inner_mtu_10705` cell advertised the computed value 1340 while pinning 1325. The 15-byte subtraction belonged to the pre-#16499 worst-case padding model; #16499 caps WireGuard padding at the derived inner budget. The production WG MTU calculation already matched that model, so changing it would introduce an incorrect extra subtraction.

## Change

- Corrected the #10705 PTB cell's pin from 1325 to 1340 and documented the full overhead derivation in its fixture comment.
- Corrected the adjacent `post_transform_inner_mtu_wireguard_is_pad_aware` comment, which described subtracting 15 bytes while its assertion and implementation used the capped-pad result.
- Updated the generated-reply classifier fixture's described WG inner MTU from 1325 to 1340; it remains a classification-only fixture.
- No production computation or packet behavior changed.

## Derivation

The shared PTB fixture sets the egress MTU to 1400. GRE gets that outer-MTU input through `tunnel_outer_mtu` (the tx ifindex 22 misses, then egress ifindex 80 hits). The WG endpoint in this fixture has no peers, so `wg_selected_peer_outer_with_dynamic` uses its no-peer fallback to `decision.resolution.egress_ifindex` 80's egress MTU, also 1400; a peer-backed WG path resolves the selected peer's physical underlay instead. This fixture therefore pins the overhead conversion using the same numeric outer MTU without claiming to exercise peer/underlay resolution.

The complete WireGuard outer overhead is IPv4 (20) + UDP (8) + WG data header (16) + Poly1305 tag (16) = 60 bytes. Therefore the largest inner IP packet budget is 1400 − 60 = 1340 bytes; no inner-IP header is subtracted because the PTB advertises the maximum size of the whole inner IP packet.

The encap's #16499 `padded_len_capped` caps §5.4.6 padding at that budget: `pad_to_16(1340)` is 1344, which exceeds the 1340-byte budget, so an inner packet of 1340 bytes is padded only to the cap, 1340. Its outer size is exactly 60 + 1340 = 1400 bytes. Thus the advertised inner MTU is 1340, not 1325. The latter incorrectly subtracts an additional worst-case 15-byte pad that this capped-padding path does not require. (The separate TCP-MSS calculation still conservatively subtracts up to 15 bytes for segment sizing.)

## Follow-up: jumbo outer MTU qualification

The exact-outer-MTU result applies to an unclamped outer-derived inner budget only when it is within the WG engine's 4096-byte ceiling. For an IPv4 outer MTU of 9000, the outer-derived budget is 8940, but the advertised inner MTU clamps to 4096; that inner packet encapps to 4156, not 9000. Qualified the PTB, coordinator budget, engine, padding-helper, and interoperability comments with this distinction; the standard-MTU test comment now states its rows are below the ceiling. No code or packet behavior changed.
