# #15663 — `BGPNeighborIsIBGP14585` ignored per-group/per-neighbor `local-as`

## Why

`BGPNeighborIsIBGP14585` (`pkg/config/bgp_cross_field_14585.go`) classified
a neighbor as iBGP only when `peer-as == router AS`. A neighbor (or its
group) configured with `local-as 65001`, `peer-as 65001` under router AS
65000 is iBGP in FRR (the session presents AS 65001, and bgpd decides
internal/external against that effective local AS, cf.
`bgpNeighborBFDMultihop14587` in `pkg/frr/protocols_render.go`), but the
helper called it eBGP. Both consumers inverted:

- the strict commit gate `validateBGPCrossFieldStrict` false-rejected a
  valid `route-reflector-client` (`peer-as 65001 != local-as 65000`) and
  false-accepted `remove-private` on that iBGP peer, with a diagnostic
  naming the router AS as the local AS;
- the FRR render belt (`pkg/frr/bgp_cross_field_14585.go`, same helper)
  omitted the valid RRC line and emitted the FRR-refused
  `remove-private-AS all` line for a leniently-loaded config (#1960),
  failing/misconfiguring every later frr-reload.

The mirror case also inverted: `peer-as == router AS` with a differing
`local-as` override is eBGP, but was classified iBGP (RRC false-accepted
at commit / rendered; remove-private false-rejected / omitted).

## What

- Added `BGPNeighborEffectiveLocalAS15663(routerAS, n)` in
  `pkg/config/bgp_cross_field_14585.go`: `n.LocalAS` when set, else the
  router AS. No group parameter is needed — the compiler stamps a
  group's `local-as` onto each neighbor's `LocalAS` at create time
  (`pkg/config/compiler_protocols.go`, group two-pass), matching the
  precedence in `bgpNeighborBFDMultihop14587` and the issue direction
  (neighbor > group > router, with group already folded in).
- `BGPNeighborIsIBGP14585` now compares `PeerAS` to the effective local
  AS; `PeerAS == 0` and an effective AS of 0 remain never-iBGP.
- `validateBGPCrossFieldStrict` diagnostics now cite the effective
  local AS (`peer-as %d !=/== local-as <effective>`).
- FRR render belt keeps delegating to the shared helper (no signature
  change) and now logs the effective `local_as` alongside `router_as`
  on both omission warnings, so the belt reason is auditable.
- NOT changed: the `local-as == router AS` rejection itself (still
  compares `n.LocalAS` to `bgp.LocalAS` — FRR refuses that spelling
  regardless of classification), the BFD multihop helper (already
  effective-AS correct), or any other consumer.

## Validation

- New unit + strict-compile regression
  `TestBGPCrossField15663EffectiveLocalAS`
  (`pkg/config/bgp_cross_field_14585_test.go`): helper table (router-AS
  iBGP/eBGP, local-as iBGP, local-as overriding a router-AS match,
  peer-as 0, router-AS 0, nil), effective-AS resolution, strict
  acceptance of group/neighbor local-as iBGP RRC fixtures
  (65001/65001 vs router 65000, incl. routing-instance scope), strict
  rejection of true eBGP under local-as for RRC and of local-as iBGP
  for remove-private with diagnostics naming `local-as 65001`.
- New render regression `TestRenderCrossField15663LocalASEffective`
  (`pkg/frr/bgp_cross_field_14585_test.go`): local-as iBGP renders RRC
  and omits remove-private; true eBGP under local-as omits RRC and
  renders `remove-private-AS all`; router-AS peer under a differing
  local-as override is treated as eBGP both ways.
- RED evidence: with only the helper body reverted (new symbol kept so
  the tests compile), both new tests fail on the classification cells
  and fixtures above (valid local-as iBGP RRC rejected with
  `peer-as 65001 != local-as 65000`, local-as iBGP remove-private
  accepted, FRR emitting the refused RRC line); GREEN after the fix.
- `go vet ./pkg/config/ ./pkg/frr/` clean; `gofmt` clean.
- Full `go test ./pkg/config/ ./pkg/frr/ -count=1`: every failure is
  pre-existing on `origin/master` (fail-name set identical to a clean
  master checkout apart from two slot-escape tests present only on the
  newer master; the 4 `pkg/frr` failures reproduce on master too).

## Risk

- Behavior delta is confined to neighbors with a non-zero `LocalAS`
  (per-neighbor or group-inherited) whose `PeerAS` classification flips;
  neighbors without `local-as` are byte-identical to before.
- A config previously (wrongly) accepted with `remove-private` on a
  local-as iBGP peer will now be rejected at strict commit and omitted
  (with warning) at render — that is the FRR-correct outcome; lenient
  load still boots (#1960).
