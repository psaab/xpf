# #13667 — defer WireGuard send-state mutation until send admission

- **Issue**: #13667 — prevent premature WireGuard send timers, counters, and failed-encryption nonce consumption.
- **Branch**: `fix/13667-neighbor-parity`
- **Worktree**: `/var/worktrees/campaign-zero/wt-13667`

## Why

WireGuard `try_encap` mutated T6/T7/T8 state and packet/byte counters while only constructing ciphertext. Its callers can still fail to send or admit the resulting frame, leaving timers and accounting to claim transmission that never happened. The nonce was also advanced before AEAD success, so an encryption failure consumed a nonce despite producing no ciphertext.

## What

- Serialize per-session transmit nonce use and advance the counter only after AEAD encryption succeeds.
- Return send metadata from encapsulation without changing peer send timers or packet/byte counters; callers commit that metadata only after successful socket send or TX-queue admission.
- Carry the commit token through normal, NAT64, copy-path TCP-segment, and deferred-neighbor replay frame construction; commit only after the respective send/queue-admission operation succeeds.
- Keep the direct WireGuard control/keepalive send paths consistent with the data path.
- Add a regression covering failed encryption, deferred timers/counters, and the successful-send commit; update existing tests that model successful transmission.

## Risk

WireGuard nonces are consumed once ciphertext is successfully produced, even if later submission fails, because reusing a nonce would be unsafe. The data path commits timers/counters once the TX pipeline accepts the frame into its queue; it does not wait for hardware TX completion. The deferred-neighbor replay path follows the same commit boundary.
