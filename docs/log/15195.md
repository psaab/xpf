## Mechanism (verified at base 565ded80fb)

A01-05: `parseStatements` incremented `p.nodes` once per statement
(`parser.go:359-365` at base); `parseKeys` (`:622-650`) appended keys
without bound. Probe `a k k k … ;` with `maxParseNodes+5000` keys parsed
with zero errors on base.

A01-06: `matchNodeKeys` (`ast.go:878-899` at base) returns 1 when only
`Keys[0]` matches (both when later keys differ and when the node has more
keys than the remaining path). `findNodeWithParent` and `childrenAtPath`
preferred the longest consumed match but fell back to that 1-key hit, so
`RenamePath([firewall filter term T2], …)` descended into `[filter F1]`
and renamed `term T2`; `RenamePath([interfaces ge-0/0/0 unit], …)` returned
the `[unit 0]` node and renamed it into `[ge-0/0/0 RENAMED]`.
`Store.RenameAsPlantClass` (`store_command.go:319-329`) records ancestry
on any `RenamePath` success, so the phantom rename entered lineage (strict
commit still refused the corrupted candidate — fail-closed downstream,
but the candidate itself was silently corrupted).

## Fix

- A01-05: keys now charge against the same `maxParseNodes` budget.
  `parseKeys` checks `p.nodes+len(keys) >= maxParseNodes` before each
  append and latches the existing budget diagnostic; `parseStatements`
  adds `len(node.Keys)` to `p.nodes` per built node so moderate parses
  count exactly. A key-dense statement therefore reports the budget
  ParseError and its slices never grow past the budget.
- A01-06: mutating resolution requires full identity. `matchNodeKeysFull`
  returns `len(n.Keys)` only when the node's whole key list equals the
  path segment, else 0; `findNodeWithParent` (rename/copy/insert source,
  element, reference) and `childrenAtPath` (rename/copy destination
  parent) use it. A missing source now returns "source not found" before
  any mutation, so `Store.Rename` records no lineage. Existing callers
  that legitimately resolved multi-key nodes by their full path
  (#3982 non-first siblings, #5822 copy parents, as-path leaves) resolve
  identically — full matches were always preferred and remain the only
  matches. `findNode`/`navigateToNode` have no non-test callers and keep
  the lenient walk, as does display-only `navigatePath`.
