- **Defect** (repro-confirmed RED at base): the VLAN branch writes the
  child's unit MTU before the per-phys setup writes the parent's planned
  MTU later in the same call. Linux refuses a child MTU above the
  parent's CURRENT MTU, so a commit raising both logs one warning, raises
  the parent, reports success, and leaves the child at its old MTU until
  the next commit. Related gap from the issue: no MTU write recorded a
  #4960 host mutation.
- **Fix** (per the issue's Fix direction): `applyVLANSubInterfaceMTU9757`
  returns a `vlanMTUPending9845` token (same link object + same MTU) iff
  the seam returned an error; `mapZoneInterface` retries that same write
  once, right after the parent's per-phys MTU write, iff the token is
  non-nil AND the parent write succeeded. Honest predicate (review
  precision caveat): ANY child-write error + ANY successful differing
  parent write — not specifically stale-parent/increase; the kernel
  decides admission, nothing models the cap, the macsec `VLAN_HLEN` bite,
  or async propagation. Parent write unmoved (stays after the #5268
  RX-VLAN gate); initial child write stays inline and ungated (no veto
  on failed parent read, no deferral past the call, no re-resolve).
  #4960 marks on all three success arms (`set interface MTU`, `set VLAN
  sub-interface MTU` ×2). `compiler_iface.go` at 1995 LOC (floor 2000);
  the contradicted next-commit-convergence passage in the dataplane
  README rewritten.
