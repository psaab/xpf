# #14636 — filter forwarding-class keys egress DSCP rewrite over BA class

With an ingress BA classifier plus an input-filter `then forwarding-class`,
the packet queued as the filter's class but its DSCP was re-marked with the
BA class's code-point (regression from #13968, whose class-first rewrite key
re-derived the class from DSCP/PCP only and never received the resolved
filter class). On the fresh, cached-seed, cached-flowless, fresh-flowless
and cache-hit paths the BA class therefore won the rewrite even though the
filter class won the queue: MF-selected voice was bleached to the BA class's
marking (or EF-marked bulk promoted), so upstream treatment followed the
host's marking instead of the operator's filter.

## Fix

- `CoSState` now retains the global forwarding-class → queue-id map built
  at snapshot time (`forwarding_build/cos.rs`), so a filter-selected class
  name resolves to the same global queue id the `dscp_rewrite_by_fc_lp`
  matrix is keyed by.
- New `resolve_cos_priority_class_lp_rewrite` in `tx/cos_classify_ba.rs`
  resolves the rewrite in the order filter class → BA class → clamped
  queue, at the packet's ingress-classified loss priority.
- `resolve_cos_ba_class_rewrite` takes the resolved filter class and is
  threaded at all four callsites (cached flowless, cached seed, fresh
  flowless, fresh flow); the fresh flowless arm now resolves its rewrite
  after the ingress filter walk instead of before it (the early result was
  discarded by the later one).
- `CachedTxSelectionDescriptor` stores the filter class's global queue id
  (`filter_class_queue_id`); the cached-seed `cos_lp_reclassify` arm now
  also fires when only the filter class (not the pinned queue) has a
  class-keyed rewrite entry, and `reclassify_cached_cos_lp_rewrite` takes
  the stored id so cache hits key the same entry. This also covers a
  filter class with no materialized egress queue: it rewrites by its own
  class entry instead of the clamped queue's.
- NOT changed: drain-time per-queue uniform rewrite (`cos_queue_dscp_rewrite`)
  and the #13968 BA-only paths — a per-packet class rewrite is already set
  on the request, and the queue-uniform fallback only fills `None`.

## Validation

- New regression test
  `filter_forwarding_class_keys_egress_rewrite_over_ba_class_14636`
  (fresh / cached-seed / cache-hit all `Some(46)` for a DSCP-10 packet
  BA-classified `bulk-data` but filter-pinned to `voice`; controls:
  no-filter/no-BA unchanged, BA-only unchanged, unmaterialized filter
  class rewrites by its own entry on all three paths).
  RED evidence: with the resolver's priority temporarily swapped
  (BA class before filter class) the test fails at the fresh assertion
  with `left: Some(17), right: Some(46)` — exactly the reported defect.
  Restored, it passes.
- `#13968` control `egress_dscp_rewrite_unmaterialized_fc_does_not_bleach_and_no_unmaterialized_guard`
  still passes unchanged.
- Suites: `cos_classify` / `forwarding_build` / `flow_cache_hit` filter
  run: 461 passed, 2 failed — both failures
  (`wg_live_endpoint_survives_one_peer_edit_rebuild_14640`,
  `gre_decap_flow_cache_hit_ttl_expiry_reads_inner_ttl_5615`) reproduce
  identically on pristine `origin/master` `51d355c1d8`, so neither is
  attributable to this change.
- Full `--bins` suite: 8398 passed, 50 failed, 8 ignored. The 50 failures
  are the pre-existing environment/baseline set (coordinator reconcile,
  GRE/WG TTL, session-delta JSON, runtime-view and similar — none in the
  CoS classification paths touched here; the two CoS-adjacent candidates
  from the filtered run were base-attributed as above).

## Risk

Behavior changes only for packets whose filter-selected class differs
from their BA class — precisely the mis-marked cohort; BA-only and
filter-only configs resolve the same entries as before (filter class
absent → BA class → queue, identical to the #13968 order). No wire-format
change; the retained map is compiled at snapshot build from the existing
forwarding-class table.
