# #15206 — DHCP-server group naming an undeclared unit: strict gate with lenient twin (A17-03)

- **Timestamp**: 2026-10-19
- **Action**: refuse a DHCP-server group interface ref that names no configured interface or unit at strict commit, warn on the tolerant path, correct the #9407 advisory to the whole-family consequence, and drop phantom devices at the Kea render belt.
- **File(s)**: listed under Change.

## Defect

`system services dhcp-local-server group <g> interface <ref>` (and the
DHCPv6 twin) names the segment Kea serves. #9407 taught the daemon to
resolve the ref through `Config.ResolveKernelIfName`, whose honest
fallback for a ref naming no configured interface or unit returns the
ref verbatim. The daemon therefore rendered a phantom device
(`reth1.7`, `ge-0-0-9.0`) into Kea's `interfaces-config` — and into the
per-subnet selector of a single-interface group — while the only
commit-time signal was the #9407 advisory saying "the segment gets no
leases".

That understates the blast radius: Kea validates the rendered file as
one unit and refuses to load it for the unknown interface, so every
pool of the family stops serving — the same whole-family outage
#9785 / #14601 / #15028 gate against through other leaves. The strict
path accepted a config Kea refuses, and the advisory misdescribed the
consequence as one segment.

## Design notes

- **Strict gate with lenient twin, not wording-only.** The issue's
  primary fix direction; the wording-only fallback would leave the
  strict path accepting a config Kea refuses. The advisory stays
  because alarm surfaces recompute `ValidateConfig` from the active
  config rather than reading `cfg.Warnings`.
- **No guessing.** The gate reuses `unresolvedInterfaceRef` verbatim,
  so a legitimately dotted DECLARED interface name (#8994), a VLAN
  unit, a reth, and both spellings stay legal, and the verdict is
  structural — independent of node-local reth member resolution, so
  commit-check agrees on both HA nodes.
- **Render belt keys on the active config, not netlink.** A device is
  usable IFF some declared interface resolves to it through the same
  `ResolveKernelIfName` the daemon used; tunnel/IRB/VLAN/fab/lo/st
  devices therefore survive, and the belt cannot drift from the
  resolver.
- **Known approximation (unchanged from today):** the #6696
  `RealValuesStillCommitClean` fixture (`ge-0/0/1.0 ge-0-0-2 reth0.80
  fxp0 ge-0/0/3` with no interfaces stanza) still commits via the
  wildcard/lifeline exemptions in its own group; a phantom ref sharing
  a group with an exempt ref is not separately refused. Tightening
  that would require per-ref exemption accounting the issue does not
  ask for.

## Risk

Configs that today commit clean with an undeclared DHCP-server group
interface ref now fail commit naming the ref; such a ref never served
leases and (per the claim) stopped the whole family at Kea load time.
Tolerant loads still boot with a warning, and the render belt keeps
the healthy pools of a leniently-loaded family serving.
