## STEP-0: mechanism verified on unmodified master

- `pkg/dataplane/userspace/process_status.go` `statusLoop`: every
  non-nil poll error fell into one `else` branch that logged
  `status poll failed` and fed the error to
  `noteStatusPollResultLocked` / `killWedgedHelperLocked`.
- `pkg/dataplane/userspace/helper_liveness_9651.go`
  `noteStatusPollResultLocked`: only `nil` and `errHelperRejected`
  reset the count; every other error — including a JSON decode
  failure on bytes the helper DID answer — incremented
  `liveness.failures`. At 30 failures spanning >=30s (plus the 10s
  RG grace) it returned true, and `killWedgedHelperLocked` SIGKILLed
  the helper. So a wire-width drift (Rust u32 zone ID vs Go uint16,
  #18207-class) that made every status answer undecodable killed a
  healthy, answering helper once a minute — matching the issue's
  fw0 evidence (1324 identical decode errors/hour, each <1s before
  a `killed` helper exit).

## Fix

Decode-failure is now a distinct, typed class end-to-end:

- `process_control.go`: new `errStatusDecode` sentinel +
  `statusDecodeError` (verbatim decoder message as `Error()`,
  classification via `Is`, cause via `Unwrap` — the
  `helperRejectedError` convention).
  `requestDetailedAtSocket` tags ONLY `req.Type == "status"`, and
  only past two earlier arms that stay silence:
  - response-cap truncation (`responseCapError`, handled in
    `statusLoop` below), and
  - bare `EOF`/`ErrUnexpectedEOF` — the helper closed with NO
    response (#1961 shape). No bytes were answered, so it stays
    untagged and wedge-countable.
  All other verbs return the bare decoder error exactly as before.
- `socket_trust_9003.go`: `responseCapError` now also wraps a new
  `errResponseCap` sentinel (message unchanged, `isResponseCapError`
  helper). Previously the cap arm returned before any tagging, so a
  status answer truncated by OUR cap would still have counted as
  silence; `statusLoop` now re-tags that one case as decode for
  `status` only.
- `process_status.go` `statusLoop`:
  - a `validateRequiredStatusReply` failure (answered status object
    Go cannot use — absent/partial) is re-minted as
    `statusDecodeError`;
  - a new `else if errors.Is(err, errStatusDecode)` branch logs
    `status poll decode failed; helper answered but its status
    could not be decoded (#18293)`, records the poll, and never
    kills.
- `helper_liveness_9651.go` `noteStatusPollResultLocked`: an
  `errStatusDecode` poll increments `liveness.decodeErrors` and the
  process-lifetime `statusPollDecodeErrors` atomic, returns false,
  and — unlike success/refusal — neither advances nor resets an
  in-progress silence streak (it is neither silence nor a usable
  answer; the streak is left exactly as it was). Genuine silence
  (dial/write/deadline/EOF, any other error) is unchanged: 30
  failures + 30s span + RG grace -> kill, supervisor restarts.
- Metric: `StatusPollDecodeErrors()` (userspace) exported through
  the existing silent-skips collector as
  `xpf_status_poll_decode_errors_total`
  (`pkg/api/metrics.go`, `metrics_descriptors_global.go`,
  `metrics_descriptor_table.go`,
  `metrics_dataplane_silent_skips_9019.go`), always emitted
  including at zero, in the `BindingWedgeGiveups` shape.

## Risk

- Fail direction: a helper that answers garbage forever is now
  never wedge-killed. That is the intended trade — it is provably
  alive (accept loop + handler running), and the decode counter +
  Warn give the operator the signal the kill used to mask. A
  genuinely silent helper is unaffected and still killed on the
  original schedule (pinned by cells above).
- `controlRequestHook` test paths do not mint the class (they
  bypass the decoder, as before); a hook returning a bare decoder
  error is treated as silence, same as master. Only the production
  socket path mints it.
- Session-socket and boot-probe decoders are untouched; their
  errors already map to their own unreachable classes.
- No wire, config, or Rust change; no new allocation on the poll
  path beyond the error value on failure.
