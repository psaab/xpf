# #15103 — OverlapTracker refuses a third zone at the shard cap (A74-02)

- **Base**: `fde73e9b28` (origin/master at branch start)
- **Branch**: `fix/15103-campaign`

## Why

`OverlapTracker::check_and_record_fragment_detailed` reclaims completed
anchors only at the candidate's own 32-entry `(routing_domain,
ingress_zone)` reserve, and only over that zone's entries. At the fixed
64-entry shard cap it returned `ShardFull` with no reclaim at all. Two
zones holding 32 completed anchors each therefore starved every third
zone in the same routing domain and shard: all new fragmented datagrams
for zone C dropped fail-closed for the anchors' TTL, even though
completed anchors are the explicitly reclaimable class. Reachable by
#14321's own attacker shape (4 untrusted senders) plus any moderately
busy second zone.

## What

- `userspace-dp/src/fragment_overlap/mod.rs`, shard-cap branch only:
  when `shard.len() >= OVERLAP_CAP_PER_SHARD` and the candidate's zone
  is below its own reserve (guaranteed by the ordering — the own-zone
  check above either reclaimed, refused, or left it below 32), reclaim
  the globally oldest COMPLETED anchor (`overlap_entry_complete`:
  `pending == 0`, not failed, ranges cover the terminal end) of any
  zone in the candidate's routing domain before refusing. Incomplete
  anchors are never reclaimed; with none reclaimable the refusal is
  unchanged (same `FRAG_OVERLAP_SHARD_FULL_DROPPED` + `ShardFull`).
- New observability counter `FRAG_OVERLAP_CROSS_ZONE_RECLAIMED`
  (global atomic alongside its siblings; issue wording "Add a
  FragAssoc refusal counter" — the refusal already had both the global
  and binding-local counters, so the new reclaim event is the counter
  added; see deviation note in PR body). The issue's alternative
  (per-active-zone reserve division) was not taken: it shrinks every
  zone's reserve as zones join, changes admitted behaviour for the
  two-zone case, and contradicts #14321's fixed 32-entry reserve.
- Module docs (fairness + failure-direction bullets) updated at the
  mechanism; the early poll-descriptor/post-commit callers
  (`poll_descriptor/mod.rs` pre-check and TX record sites) need no
  change — they already drop on `ShardFull` and forward on admission,
  so the fix is entirely inside the tracker.
- NOT changed: sender quota (8/shard), per-zone reserve (32), shard
  cap (64), TTLs, range geometry, shard hashing, `FragAssoc` (the
  A74-02 mechanism is OverlapTracker-only; FragAssoc has no completed
  anchor class and its shard-full refusal stays as-is).

Security trade, explicit: an evicted completed anchor loses overlap
protection for the remainder of its reassembly window — the identical
trade #14321 already accepts at the per-zone cap, now extended across
zones in one domain. The alternative shipped before (third-zone
blackhole) is the worse failure.

## Validation

- RED (base `fde73e9b28` + test only):
  `third_zone_admitted_by_cross_zone_completed_reclaim_15103` FAILED
  with `zone-C victim must be admitted by cross-zone completed reclaim,
  reason=Some(ShardFull)` — the exact claimed mechanism (zones A/B =
  32 completed anchors each in one shard, zone C refused).
- GREEN (with fix): same test passes; asserts zone A stays capped via
  its own-zone reclaim, zone C admitted, `t.len()` stays 64, no
  `SHARD_FULL` bump, exactly one `CROSS_ZONE_RECLAIMED` bump, and a
  shard of incomplete anchors still refuses zone C fail-closed.
- Controls: `cargo test --bins fragment_overlap` — 44 passed;
  `cargo test --bins 9950` — 28 passed (includes
  `shard_full_drops_without_evicting_live_9950`,
  `cross_zone_domain_fill_cannot_starve_other_zone_14321`,
  `completed_entries_hold_shard_capacity_until_expiry_10285`,
  `completed_anchors_preserve_routing_domain_reserve_14009`).
- `rustfmt --check` on the file was already dirty on base (58 hunks
  pre-existing under the local rustfmt); the change introduces no new
  fmt hunks beyond the file's baseline drift — new code follows the
  file's existing formatting.

## Risk

Residual: under sustained churn of completed datagrams across many
zones in one shard, anchors rotate faster than their 30s TTL; the
`FRAG_OVERLAP_CROSS_ZONE_RECLAIMED` rate makes this visible. No
behaviour change when a shard is below 64 or the candidate's zone is
at its own reserve.
