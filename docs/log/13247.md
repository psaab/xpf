# #13247 — make NAT views deterministic and preserve combined NAT flags

## Why

Three NAT session-count paths rebuilt `zoneByID` by iterating `ApplyResult.ZoneIDs` directly. When a quarantined zone and its surviving collision owner shared a stable ID, the later map entry could be the quarantined name, so a live session was attributed to the wrong zone and the survivor's NAT count was reported as zero. REST/gRPC NAT pool and template views also ranged over maps directly, making output order unstable. Peer session briefs assigned the DNAT flag after the SNAT flag, so a session containing both was rendered as `D` rather than `B`.

## What

- REST `natPoolStatsHandler`, gRPC `GetNATDestination` and `GetNATPoolStats` now use `config.SurvivorZoneNames` for collision-safe zone attribution.
- REST/gRPC named source pool lists and all six CLI source/destination NAT pool loops use existing sorted-key helpers. CLI flow-monitoring template output and gRPC flow-monitoring show text now sort template names as well.
- Peer session brief NAT classification now handles SNAT+DNAT as `B`, matching local session briefs.
- Added an API regression with multiple synthetic stable-ID colliders (to make the old randomized overwrite readily reproducible) and a CLI peer-flag unit test.
