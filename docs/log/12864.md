# #12864 — suppress reject replies on tunnel decap

- **Timestamp**: 2026-10-13 (`fix/12864-campaign-pub`)

## Why

GRE and WireGuard decap synthesize an Ethernet header around the inner L3 packet with twelve zero MAC bytes. The shared `enqueue_reject_reply` path previously treated it like a native frame: TCP `then reject` reflected those zero MACs into a reset, while UDP/filter rejects reflected them into an ICMP error, then queued the unencapsulated response on the physical ingress binding. That can send unusable reply bytes to the underlay instead of returning an error through the tunnel.

## What

- Add `TUNNEL_DECAP_INGRESS_FLAG` separately from the GRE MSS clamp bit and set it on GRE decap, authenticated WireGuard decap, and injected WireGuard plaintext.
- In the shared policy/filter/session-miss reject choke, treat that provenance as unreplyable before building a reply or charging reply budget/rate-limit tokens. The triggering packet still drops as before; IPsec's bare-L3 path is unchanged.
- Cover TCP RST and UDP ICMP suppression, preserve normal native TCP reject behavior, and pin GRE/WireGuard producer metadata.

## Risk

Tunnel-decapsulated packets denied with `then reject` are now silent drops rather than emitting an unencapsulated, zero-MAC response on the underlay. No physical GRE/WireGuard TX capture was performed; regression coverage proves the shared choke emits no `TxRequest`, and producer tests verify tunnel provenance reaches that choke.
