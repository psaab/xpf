# #14979 — ResetFailover left transfer-commit grace, hold, and override state armed (D34-04)

## Defect

`Manager.ResetFailover` (`pkg/cluster/failover.go`) cleared only
`ManualFailover`, `transferCommitRolePinned`, `ManualFailoverAt`, the
kernel-upgrade hold, and the remote transfer-out lease (#6301). It left
three pieces of transfer-commit authority armed for the reset RG:

- `peerTransferOutOverride` (+ its `peerTransferOutPrevious` snapshot) —
  no expiry; `applyTransferCommitOverridesOnPeerStateLocked` re-forces
  the peer to `SecondaryHold` on every heartbeat, so `electRG` takes its
  "Peer transfer out" arm and self-elects primary regardless of what the
  peer reports (#6527/#6656 class).
- `peerTransferCommitGraceUntil` — same peer-state rewrite until the
  (~10s floor) window expires.
- `localTransferOutHoldUntil` — keeps a committed secondary parked via
  `electRG`, and is cluster-wide in effect:
  `suppressPeerTimeoutForTransferCommitLocked` scans the whole map, so
  one RG's leftover hold suppresses peer-loss detection for every RG.

Consequences on the surviving leg: an operator reset (the explicit
"this transfer is over, normal election resumes" action — including the
preempt-reclaim path pinned by #10776) did not actually end the
transfer. If the peer reclaimed primary, the requester kept rewriting
its heartbeats to `SecondaryHold` and stayed primary alongside it
(dual-primary, duplicate VIP/MAC). A stale hold also silenced
`handlePeerTimeout` cluster-wide until it expired.

## Fix

`ResetFailover` now clears, for the reset RG only, the full transfer
state — mirroring the pairing used by `notePeerTransferCommitted`,
`FinalizePeerTransferOut`, and the RG-removal purge (#8435):

- `clearPeerTransferOutOverrideLocked(rgID)` (override + snapshot; a
  later abort restore for a pre-reset reqID then no-ops),
- `delete(peerTransferCommitGraceUntil, rgID)`,
- `delete(localTransferOutHoldUntil, rgID)`.

Other RGs' armed state is untouched, and all pre-existing reset
behaviour (manual-failover clear, kernel hold, lease, failoverGen bump,
weight recalc/election) is unchanged. Clearing happens before
`recalcWeight`, so the reset's own election already sees the cleared
state. `ResetAllFailover` inherits the fix via `ResetFailover`.

## Tests

`pkg/cluster/reset_failover_transfer_14979_test.go`:

- `TestResetFailoverClearsTransferCommitState14979` — all four map
  entries for the reset RG are gone; a second RG's armed state survives
  (per-RG, not a wipe). RED on master (entries survive), GREEN after.
- `TestResetFailoverStopsForcingReclaimedPeerSecondaryHold14979` — after
  commit + reset, a peer heartbeat advertising primary is honoured and
  the local node yields instead of staying dual-primary. RED on master
  (heartbeat rewritten to `SecondaryHold`), GREEN after.
- `TestResetFailoverStopsPeerTimeoutSuppression14979` — peer-timeout
  suppression ends once every RG's hold is reset; a still-armed second
  RG keeps suppressing as the control. RED on master, GREEN after.

RED/GREEN verified by reverting only the `ResetFailover` additions:
all three tests fail on the revert, pass with the fix.

Adjacent controls staying green: `TestResetFailover`,
`TestResetFailoverClearsRemoteTransferOutLease`,
`TestRequestedPreemptTransferPinsCommittedRoleUntilReset10776`,
`TestHandlePeerTimeoutSuppressedDuringRecentTransferCommitGrace`,
`TestNotePeerTransferCommittedPreservesPeerTransferOutDuringGrace`,
`TestResetFailover_ClearsKernelUpgradeHold`.

Full `go test ./pkg/cluster/` has one unrelated failure,
`TestInstallTableProducerToResendEndToEnd9752`, which also fails on
pristine `origin/master` without this change (pre-existing).

## Risk

Bounded to the reset path: a reset issued inside a genuinely in-flight
transfer for that same RG now also drops that transfer's grace/hold,
which is the operator's stated intent (reset wins, #5246). Live
transfers on other RGs are unaffected.
