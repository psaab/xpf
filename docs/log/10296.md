# 10296 — Reject empty rollback slots and durably persist all slots

## Boundary

A zero-length text rollback slot was parsed as a valid empty configuration. An
operator could run `rollback N`, then commit, and replace the active
configuration with that empty tree. The canonical text rollback writer also
used the non-fsync atomic writer for slots 2..N, so a power cut could expose a
partial or zero-length higher slot.

The issue body and comments were read in full before implementation. The issue
is open, has no comments withdrawing or narrowing it, and its acceptance calls
for zero-length/whitespace-only slots to be rejected as tombstones plus a
rollback-to-empty confirmation cell.

## Fix

- `loadRollbackHistory` now tombstones a slot whose bytes are empty or
  whitespace-only before parsing. It also tombstones parser-successful empty
  trees (including comment-only input), preserving the slot's position and
  emitting a diagnostic rather than loading an empty healthy target.
- `saveRollbackFiles` now routes every canonical text rollback slot, including
  tombstone markers and slots 2..N, through `fsatomic.WriteFileDurable`; the
  trailing directory sync remains the batch barrier for the shuffle and stale
  unlinks.
- The configstore README now describes the all-slot durability contract.
