# #16799: rib-group return rows ran before the source VRF table in the AF_XDP FIB

- **Timestamp**: 2026-10-25
  - **Action**: The helper treated every rib-group RETURN row (kernel
    priority 1001–1999, after the l3mdev VRF lookup at 1000) as a stage-1
    leak that runs before the source VRF table's own longest-prefix match.
    If tenant A had a default route or any route covering a co-leaking
    tenant B's prefix, the AF_XDP path forwarded A's traffic into B,
    while the kernel and Junos use A's own route.
    Fix (Rust FIB only; no wire or Go change): `LeakRuleV4`/`LeakRuleV6`
    gain a `post_table` flag, set in `forwarding_build` when the mirrored
    `RouteSnapshot.rule_priority` is in (1000, 2000) — exactly Go's
    `IsRibGroupReturnRulePriority`, including the legacy flat 1500. The
    stage-1 leak walk skips deferred rows; after the source table's own
    LPM (and the #16614 Junos next-table competition, which is part of
    that LPM) a deferred row is tried only on a genuine source miss —
    the LPM produced `NoRoute` and the source table owns nothing for the
    destination (no usable ordinary route, connected prefix, or
    per-table local/NAT/anycast ownership; discard/reject count as
    owned, so the source's terminal answer stands). A deferred target
    miss falls through to the next deferred row and then to the original
    `NoRoute`, never fabricating a result. `leak_incarnation_for_resolution`
    likewise does not stamp a deferred return for a destination the
    source table owns. The 30000-band leaks into `inet.0` keep stage-1
    precedence (they follow main's table rule in the kernel too), and
    priorities 1000/2000 are not return priorities and are unchanged.

  - **Validation**: New `tests_return_order_16799` (9 tests) drives the
    production `build_forwarding_state` + lookup with the va38 fixture
    shape (`tenant-a.inet.0` row `10.20.0.0/24 -> tenant-b.inet.0 @1225`,
    B egress ifindex 21, A WAN ifindex 20): control (source miss) -> 21;
    A default -> 20; A more-specific /25 -> 20; A discard -> DiscardRoute;
    band edges 1000/2000/30001 keep stage-1 while 1500/1999 defer; a
    30000-band leak in `inet.0` still beats main's default; the v6 twin
    (`@1449`) agrees; a deferred target miss stays `NoRoute`; and the
    incarnation stamper returns `None` when the source owns the
    destination but stamps on a source miss. With `post_table`
    temporarily forced false the source-route cells fail (egress 21,
    the pre-fix divergence), proving RED. Existing leak suites pass:
    `tests_leak_overlap_9955` (16) and `tests_leak_precheck_14319`.
    No Go behavior changes (comment only).
  - **Risk**: Only tables carrying a (1000, 2000) leak row pay one
    extra source-ownership scan on the lookup path; no allocation. A
    config next-table route in a VRF table (Junos hand-off) still wins
    over a deferred return by construction, matching Junos table
    semantics; the kernel RPDB expresses no such ordering (config
    next-table installs no kernel rule for VRF tables), which is
    pre-existing #16614 behavior, not changed here. Sessions stamped
    with a deferred return's incarnation while the source owned the
    destination cannot be produced anymore; already-established
    sessions re-resolve fail-closed as before.
