## Remedy

`collectPolicyZoneRejections` joins the same slice the content sentinels use, so
`pkg/policymatch`'s existing single gate inherits the arm with no call-site
change. It reads the ZONE SNAPSHOT rather than `cfg.Security.Zones`, and that is
the load-bearing design decision: the helper resolves against a map that DROPS a
zone with id 0, an empty name, or a reserved-range id, so a config-side predicate
would answer "resolvable" for a zone the helper cannot resolve — the simulator
agreeing with the compiler while disagreeing with the dataplane, which is the
SHAPE of this defect rather than its fix.

## Three existing cells went red, and each was a prior decision speaking

All three were found by running the consumers, not by the targeted run.

### 1. `TestSharedMatcherGlobalScopeRegressionMatrix` — the row that made the doc false

This matrix is cited in `docs/userspace-dataplane-architecture.md` as the
cross-language SSOT whose halves "assert the same matrix case-for-case … so the
operator's test output can never permit/deny differently than the wire", with one
named exception for a typo'd scope.

Its Go row asserted `wantDefault: true, wantAction: PolicyPermit` — fall through
to a default PERMIT. The Rust half has asserted the opposite since #3402, and
`policy_tests.rs unknown_zone_pair_fails_closed` states exactly why: *"under
`default-policy permit-all` a stale `deny` became an ALLOW (fail-OPEN) … Rejecting
the snapshot keeps the previous good state."*

**So the Go half of the SSOT matrix was pinning, on the operator-facing `show`
surface, the fail-open the dataplane had already been fixed not to have.** That is
a stronger statement than the issue makes, and it is what the "deliberate
divergence" sentence was papering over. Re-anchored, not deleted: the row's
subject — an undefined scope must not match and must not yield a fabricated
verdict — is unchanged; only the FORM of "no verdict" moved.

### 2. `TestWildcardZoneAndScopedGlobalPrecedence/undefined_global_scope_fails_closed`

Same shape, and its NAME was wrong too: falling through to a default `permit-all`
is failing OPEN. Re-anchored with the reason.

### 3. `TestNoZonesDefinedNoTransitMatch` (#3355) — and its fail-on-revert was HOLLOWED

Its fixture has an empty `Security.Zones` map AND a policy naming `trust`/`untrust`,
so it is simultaneously an unknown-query-zone case and an unresolvable-policy-zone
case. The new arm fires on the second, and the content gate returns BEFORE any zone
check — so the cell's stated fail-on-revert ("restoring the
`len(cfg.Security.Zones) == 0` leniency in `zoneKnown` makes this query match")
could no longer fire.

**Measured, not assumed**, and the first measurement was VOID: with the fix in
place the cell was ALREADY red, so scoring the `zoneKnown` mutation against it
told me only that "something else fired". Re-anchoring first, then re-scoring, is
what made the verdict readable.

`TestNoZonesDefinedNoTransitMatchZoneGate` now carries #3355's property on a
fixture the new gate does NOT intercept: the policy's zones are DEFINED (so the
snapshot resolves and the content gate stays silent — asserted as a positive
control) and only the QUERY names an unknown zone. Re-scored on a green baseline,
mutating `zoneKnown` to return true unconditionally reds it, so the guard is
rebuilt rather than reworded.

## The doc paragraph is DELETED, not reworded

A paragraph describing a divergence that no longer exists is not a wording bug.
Rewording it would leave a reader believing the divergence is still there in some
form. Both halves of its excuse were false — *"fails closed to the default"* is
failing open and was true only for a SINGLE-element scope (`globalScopeSetMatches`
`continue`s past an undefined element, so a multi-element scope keeps matching its
siblings and returns a concrete verdict), and *"a typo can never commit"* ignores
the tolerant path — and after this change the two halves agree with no exception.
The replacement records what was wrong, why, and what now holds.
