# 12173 — qualify HA failover timing by mode and event

- **Date**: 2026-10-07
- **Why**: `CLAUDE.md:470` and `pkg/cluster/README.md:3675` described ~60ms with default 30ms VRRP advertisements as general failover timing, although the compiler default is private-RG election without RETH VRRP. They also gave an unmeasured ~130ms failback figure.
- **What**:
  - The compiler sets `PrivateRGElection = true` by default and `no-private-rg-election` opts out (`pkg/config/compiler_system.go:3133-3137`). The VRRP mode table identifies `no-private-rg-election` without `no-reth-vrrp` as VRRP-backed and private-RG election as the direct/default mode (`pkg/vrrp/README.md:915-923`).
  - Steady-state heartbeat staleness is `threshold × interval` (`pkg/cluster/heartbeat.go:1916-1960`): runtime defaults are 100ms and 5 (`pkg/cluster/heartbeat.go:61-65`), while the deployed lab config is 200ms and 5 (`docs/ha-cluster-userspace.conf:71-72`). Startup/restart grace can defer peer-loss handling (`pkg/cluster/heartbeat.go:1938-1953`). Interface/IP monitors poll every second (`pkg/cluster/monitor.go:383-398`) and require three consecutive failures (`pkg/cluster/monitor.go:28-32`).
  - In legacy VRRP-backed mode, RETH advertisement defaults to 30ms (`pkg/vrrp/vrrp.go:155-166`). The master-down timer is `3 × advertised interval + priority skew` (`pkg/vrrp/instance_timing.go:112-128`); with 30ms and priorities 1–255, that timer falls between 90ms and 120ms. It is a detection timer, not an end-to-end forwarding-restoration measurement.
  - For planned VRRP shutdown, the resigning instance emits three priority-0 advertisements (`pkg/vrrp/instance.go:803-806`); the backup arms a 1ms timer (`pkg/vrrp/instance_rx.go:155-173`), and the run-loop test asserts takeover under 50ms (`pkg/vrrp/instance_prio0_run_test.go:145-149`). Private-RG manual failover is an explicit peer-transfer path (`pkg/cluster/failover.go:447-450`) with explicit transfer-out/resignation state (`pkg/cluster/election.go:1021-1042`); no end-to-end latency is asserted.
  - Removed the unsupported ~130ms failback claim; no source-derived bound or measured end-to-end timing record was found for it.
- **Validation**:
  - RED-before: on the clean `1c384b9a4` base, the two docs contained the unqualified ~60ms/30ms-VRRP and planned ~1ms claims; the passages were captured before edits.
  - GREEN-after: searched `CLAUDE.md` and `pkg/cluster/README.md` for `~60 ms`, `60ms.*failover`, `~130 ms`, `130ms.*failover`, `~97 ms`, and unqualified default-30ms-VRRP wording; no stale markers remain. Replacements cite source lines above.
  - `make docs-check` — `check-upgrade-docs: upgrade/install docs are clean`.
  - Scope check: documentation-only; no code or test files changed.
- **Risk**: the documented values are configuration thresholds, monitor polling requirements, or a VRRP timer formula—not end-to-end failover SLAs. Startup/restart grace, monitor polling phase, and forwarding recovery can affect observed restoration time; planned private-RG transfer has no asserted numeric bound.
