# Issue #13557: Bound SNMPv3 tooBig fallbacks

## Why

GET and GETNEXT returned an unchecked `errTooBig` response when the original
response exceeded the effective manager limit. GETBULK did the same when no
varbind prefix fit. Because SNMPv3 echoes the request contextName without a
length bound, the fallback itself could exceed the manager's advertised
`msgMaxSize` (including the 484-byte floor) and emit an oversized datagram.

## What

Added a shared v3 fallback builder that encodes the complete `errTooBig`
response and drops it when it exceeds the effective limit. Routed GET/GETNEXT,
GETBULK, and SET fallback paths through it. Added an authenticated regression
for oversized contextName across GET, GETNEXT, GETBULK, and SET control.

## Validation

- RED on pristine issue branch (`5fba34bd2`):
  `go test ./pkg/snmp -run '^TestV3OversizedFallbackDropped$' -count=1` failed
  for GET, GETNEXT, and GETBULK; each emitted 1168 bytes against 484 bytes.
- GREEN: focused regressions `go test ./pkg/snmp -run
  '^(TestV3OversizedFallbackDropped|TestV3Set_OversizedFallbackDropped|TestV3Set_OversizedReturnsTooBig)$' -count=1`.
- `go vet ./pkg/snmp` and `go build ./...`: passed.
- Full `go test ./pkg/snmp -count=1`: failed in
  `TestServePerSourceBudget9917` (control source received 3/5 responses before
  timeout); suite run ended with that test failure.

## Risk

Requests with an excessively long contextName whose `errTooBig` response
cannot fit are now silently dropped; emitting the oversized fallback was not
usable by managers with the advertised receive limit.
