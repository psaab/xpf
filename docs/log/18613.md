# #18613 — warn when the fab1 local address drifts from the running sync epoch

## Why

(#18597 records this drift class as not covered by the PR 18601 key;
this issue is that citation's follow-up.)


Dual-fabric `SessionSync` captures fab1's local bind address in its constructor.
That address is not part of `clusterTransportKey`, by design, so a fab1
renumber can leave the live session using its old secondary address without
rebuilding comms. This loses secondary-fabric redundancy while primary sync
continues.

## Change

- Record the constructor's normalized fab1 local host under `fabricMu`, keyed
  to the current cluster-comms generation. Publish only while that generation
  is current; clear it with the epoch-owned fabric state.
- Before the healthy return in `reassertMgmtVRFOnce`, resolve fab1 only when
  the current epoch has a dual `SessionSync` and a recorded local host. Resolve
  outside locks, then re-check generation, pointer, and host before warning.
  A differing non-empty address warns once per epoch without setting transport
  debt, restarting comms, or replacing `SessionSync`. Empty resolution does not
  consume the mismatch-warning allowance.
- Add `TestFab1LocalAddressMismatchWarnsOncePerEpoch18613`, which covers
  equivalent IPv6 spellings, repeated reasserts, `SessionSync` pointer identity,
  and a fresh warning allowance in a successor epoch.
- Add `TestFab1MismatchSkipsResolveWithoutDualEpochHost18613` to pin zero
  resolution for ineligible epochs and no mismatch warning for an empty result.
- Extend the late-fab1-upgrade constructor cell to check that the host and
  generation are published from the actual `startClusterComms` construction.

## Risk

The change is diagnostic only. It deliberately leaves the current epoch's
`SessionSync` pointer and transport lifecycle untouched; an ordinary config
change remains responsible for a comms restart.

Parent note (race-cell honesty, 2026-11-07): the race cell proves the
stale result does not warn and spends no allowance in the swap
shape, but parent re-derivation shows it does NOT discriminate the
recheck arms: the resolver hook samples eligibility at warn-entry,
so the swap lands before the resolve it was meant to race, and both
recheck mutants (gen/pointer, fabric) stay green with the cell. The
recheck's correctness rests on GLM/Kimi source verification (gen
strictly increases at stop/start; host+latch rechecked under lock
order) — recorded here rather than claimed as cell-proven.
