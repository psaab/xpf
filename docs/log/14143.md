# Issue #14143 — embedded command admission with edit cursor

## Why

`authorizeConfigMutationDepth9939` (`pkg/config/authz_config_mutation_9154.go`)
resolved the CLI `edit` cursor into the outer paths it adjudicated via
`configMutationPaths`, but passed only the raw typed `parts` to
`authorizeEmbeddedChangeConfig9939`. `embeddedChangeConfigCommands9939`
(`pkg/config/authz_event_change_config_9939.go:42`) scans for an adjacent
`change-configuration commands` token pair, so a payload planted from inside
the stanza carried no such token in the typed line:

- cursor `event-options policy p then change-configuration` +
  `set commands "set system root-authentication …"` — the ancestors live
  only in the cursor; the payload passed planting-time validation despite
  the outer path being authorized (decisive check from the issue,
  reproduced: `AuthorizeConfigMutation(..., editPath=[... change-configuration],
  'set commands "set system …"')` returned nil on origin/master).
- The same gap applied to `delete commands …` from the same cursor and to
  any cursor depth that supplied the `change-configuration` half of the pair.

Fire-time revalidation (`eventengine.validatePlantClass`, stamped plant
class) remained as the only gate — defence-in-depth loss, exactly as the
research gate narrowed it (planting-time #9939 bypass; execution still
bounded by the fire-time check).

Rename/copy variant, characterized rather than fabricated (per the issue's
own refutation note): a rename/copy line carries no payload text — the
embedded commands already exist in the candidate under the source subtree.
Both endpoints are adjudicated as resolved paths by `configMutationPaths`
(#9938 F-029), the moved subtree is re-stamped to the mover's class by
`StampChangedEventPlantClasses`, and every command is re-adjudicated
against that class at fire time. There is no payload text on the line to
scan, and inventing one from endpoint words (`... commands to ...`) would
adjudicate a command the engine never runs.

## What

- `authorizeEmbeddedChangeConfig9939` now takes `editPath` and locates the
  payload on the RESOLVED path: cursor + typed path without the verb (the
  same resolution `configMutationPaths` and the store apply — keeping the
  verb would interleave it between the cursor's `change-configuration` and
  the typed `commands` and the adjacent-pair scan would walk past the
  payload). Quoted provenance is padded with `false` for cursor elements,
  which are never quoted.
- copy/rename return early from the payload scan: their resolved endpoints
  are the payload's location, not its text (documented at the site).
- No other surface changes: gRPC/REST/load/fire-time callers pass `nil`
  editPath (their lines are already resolved) and are byte-identical in
  behaviour; the recursion bound and its fail-closed direction are
  unchanged (existing direct-call test updated for the new parameter).

Regression tests (`pkg/config/authz_event_change_config_14143_test.go`):
- `TestEditCursorRelativePayloadIsAdjudicated14143` — quoted/unquoted
  payloads from cursors at `change-configuration`, `then`, and `policy`
  depth, plus a `delete`-verb plant; positive controls (allowed payload,
  non-payload relative set) still pass.
- `TestEditCursorPayloadDeniedSystem14143` — the issue's decisive check
  verbatim (allowed `event-options` / denied `^system`).
- `TestRenameCopyIntoChangeConfigurationHasNoPayloadText14143` — rename
  into `change-configuration` with no denied endpoint is allowed (no
  fabricated payload), rename/copy touching a denied endpoint is refused.

## Validation

- New tests on the fix: PASS. On a separate pristine origin/master worktree
  (test file copied over, production code untouched): the three
  cursor-at-`change-configuration` cells and the decisive `^system` cell
  FAIL (`planted a payload targeting it from edit cursor [...]`,
  `was ALLOWED for a class denied ^system`); cursor-at-`then`/`policy`
  cells pass on base too because the typed line itself carries the pair —
  they pin that the fix does not double-adjudicate or break that depth.
  The rename/copy cell passes on both, as designed (it characterizes
  existing endpoint + fire-time behaviour, not the defect).
- Existing neighbours pass: `TestAPlantedPayloadIsAdjudicatedAgainstThePlanter9939`,
  `TestAnAllowedPayloadStillPlants9939`, `TestAnUnanchoredDenyCatchesThePlantIncidentally9939`,
  `TestAClassWithNoRegexesCanPlantAnything9939`,
  `TestThePayloadBoundaryMatchesTheCompilersOwnRule9939`,
  `TestTheRecursionBoundRefusesRatherThanWavesThrough9939`,
  `TestAuthorizeConfigMutation*`.
- `go vet ./pkg/config/` clean; changed files gofmt-clean (four pre-existing
  unformatted files in the package untouched).

## Risk

- Fail-closed direction preserved: the scan can only find MORE payloads
  (those the store will actually write under the cursor); allowed payloads
  from inside the stanza still plant (positive controls). Tolerant/strict
  doctrines untouched — this is the planting-time authorization gate only.
- One allocation per gated line when a cursor is present (resolved slice);
  the nil-cursor surfaces (gRPC/REST/load/fire-time) allocate nothing new.
- Residual: payloads planted by `load` remain adjudicated per rendered
  mutation line with nil cursor (`AuthorizeConfigLoad`), which is correct
  because loaded lines are already fully resolved; hierarchical load
  content that plants a payload is rendered to flat `set …` lines before
  this gate sees them.
