# Issue #16869 — carved single-policy BGP export: `then next policy` escape landed on the policy's own default

- **Issue:** #16869 (R3-B08-01), a #15157 regression. A single-policy BGP
  export with an explicit policy default (`then reject` / `then accept`)
  and a `then next policy` term sent the escape to the policy's own
  default instead of the Junos BGP default export, once any peer in the
  instance originates (#14586). With a reject default, BGP routes the
  operator explicitly handed to the default policy were withdrawn from
  the peer (fail-closed advertisement outage); the trigger was remote —
  adding an origination export to a different neighbour flipped this
  peer's verdict.
- **Mechanism (re-verified at e3b6281a76):**
  `renderRouteMapForPolicyExport15157` passed the explicit default as
  both trailing and fallback action into
  `renderRouteMapForPolicyWithFallback`; the carved branch fired only
  for `DefaultAction == ""`, and the non-carved tail emitted the plain
  fallback at `seq+10`, which the `on-match goto` escape targeted.
  So `EXP { term transit { from { protocol bgp; community TRANSIT; }
  then next policy; } then reject; }` rendered in an originating
  instance as `permit 10 ... on-match goto 30`, `deny 20`, `deny 30` —
  the TRANSIT route jumped to 30 and was denied. The composed renderer
  (`renderComposedRouteMapWithDefault`) already lands the last member's
  escape on the carved pair; the single-policy path did not.
- **What:** In `renderRouteMapForPolicyWithFallback`, when the map is a
  carved export (`carvedBGPOnly`), the policy has an explicit default,
  and a valid `next policy` term exists, emit the carved pair
  (`permit <seq+10> match source-protocol bgp`, `deny <seq+20>`) after
  the plain explicit-default tail at `<seq>` and target the escape
  (`on-match goto`) at the carved permit. Without a next-policy term
  nothing can reach past the terminating default, so no pair is
  emitted and the render is byte-identical to before (preserving the
  #15157 explicit-default control). The non-carved path and the
  no-default carved tail are unchanged.
- **Sequence accounting (review Findings 1/R1, Astra R1/R2):** The
  carved pair renders one sequence beyond the old budget: pre-fix
  usage was terms + explicit default + one fallback (highest
  `10*(count+1)`), post-fix it is terms + default + pair, so a policy
  admitted at the old count `MaxRouteMapSequences` (6552) would have
  rendered a carved deny at 65540 > 65535 and poisoned the whole
  frr-reload (#5701 class). Accounting now, per carved path:
  - *Single explicit-default (this issue):* `config.RouteMapSequenceCount`
    counts **2** (not 1) for an explicit-default policy with a valid
    `next policy` term (+1 bypassable default, +1 second carved
    sequence; the first occupies the reserved fallback slot).
    `pkg/config` cannot see the carve, so this is conservative for
    every such policy. Strict gate and render belt share it.
  - *Community-chain expansion (#16835, Astra R1):* an orphan term
    over a k-member expanded chain emits `2k` slots + body but was
    counted as 1 per alternative, so 1310 such terms admitted and
    rendered the carved deny at 65540. `RouteMapSequenceCount` now
    adds the mirror of pkg/frr's
    `communityExtraTermSeqWeight16835` (re-derived in pkg/config
    from the shared `ValidCommunityMember`/`CommunityMemberIsRegex`
    predicates; cross-pinned against the frr weight in tests). This
    fixes the undercount for ALL uses of such terms, carved or not.
  - *No-default single + composed carved tails (Opus R1):* these
    render pair (+fallback) beyond the one reserved fallback, but
    the carve is visible only in pkg/frr. The config count is
    deliberately NOT inflated for them (that flipped ~20 exact-count
    suites); instead the frr render belts add the exact reserve
    where the carved flag is known
    (`carvedSingleExtraSeqs16869`: +1 pair-only / +2 pair+fallback;
    in `pkg/frr/carved_seq_reserve_16869.go`, added at the belts
    with saturating arithmetic (`beltTotal16869`) so a count
    saturated to `math.MaxUint64` cannot wrap past the guard.
    Belt-refusal renders the quarantine deny. The strict composed
    gate keeps the non-carved formula — see Residuals.
- **Tests:** `pkg/frr/bgp_default_export_nextpolicy_16869_test.go`
  (12 tests, incl. saturation). The five semantic arms and the dual-use pin drive the
  full `buildManagedSection` path (EXP exported to neighbour A,
  LOCAL static export on neighbour B flips origination); the four
  boundary tests render real expansions (defined prefix-lists /
  defined communities) through `buildManagedSection` or the carved
  composed renderer and assert exact header counts and max
  sequences:
  - Arm A reject-default + origination: escape `goto 30` lands on
    `permit 30 match source-protocol bgp` + `deny 40`, after
    `deny 20`; no plain `deny 30`.
  - Arm D accept-default + origination: escape lands on the carved
    pair after the plain `permit 20`.
  - Arm B control (no origination): plain `permit 30` fallback, no
    carved pair.
  - Arm C control (no default + origination): pre-existing #15157
    carved tail unchanged (`goto 20` → carved permit, plain fallback
    at 40).
  - Control (explicit default, no next-policy term): no carved pair,
    plain deny tail, no goto.
  - Dual-use pin (Finding 2): EXP exported to A and imported by C
    renders the one shared carved map for both attachments (accepted
    fail-closed import-side tradeoff, mirroring the composed
    renderer's shared-name note); import-only EXP in an originating
    instance keeps the plain fallback.
  - Boundaries, all with DEFINED references so the counted expansion
    actually renders: explicit-default at ceiling renders 6553
    headers / max 65530 for both defaults, one over quarantines;
    1310 community-chain orphans count 6553 and quarantine (1309
    control admitted, 6549 headers, max ≤ 65535); composed E=0
    carved chain at belt-total 6552 renders max 65530, one over
    quarantines; no-default single at belt-total 6552 renders max
    65530, one over quarantines.
  The #11780 count expectations in `pkg/config`
  (`TestNextPolicySequenceCountsIncludeSkippedDefaults11780`) move
  from 2/3 to 3/4 for the explicit-default allowance.

## Residuals

- No live bgpd/lab run in this lane, and none for the new sequence
  layout (explicit default at `<seq>`, carved pair at
  `<seq+10>/<seq+20>`, `goto <seq+10>`): that layout is asserted at
  render level only here. The reporter/vb08 bgpd 10.7.1 executions
  covered the defect render and a Junos-correct control render, not
  this exact layout.
- Accepted tradeoff (Finding 2): a dual-use policy (carved export +
  import under the same name) serves its import attachment with the
  carved escape too — fail-closed for import, never fail-open for
  export. Pinned by test; inherited from the #15157 one-map-per-name
  design.
- Strict-gate nuance: the strict composed-chain gate
  (`validateBGPComposedChainSequenceBoundStrict`) and the strict
  per-policy gate use the config formula, which does not reserve
  the frr-only carved tail extras (no-default single / composed).
  A boundary carved chain can therefore pass strict commit and be
  quarantine-denied at render (fail-closed, routes withdrawn, no
  poisoned reload) rather than rejected at commit. The config
  formula cannot see origination, and inflating it for all chains
  broke the exact-count contract of the non-carved suites.
- The QNH metric map renderer (`qnh_metric_11447.go`) and redistribute
  maps are non-carved (`carvedBGPOnly=false` / fail-closed fallback)
  and intentionally keep the plain fallback escape.
