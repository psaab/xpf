# #16844 — userspace fabric takeover term ignores peer liveness (R3-F14-02)

- **Timestamp**: 2026-10-25
  - **Action**: #15918's `takeoverReadyLocked` fabric-installability clause (`PeerMAC != ""` + installable row, plus `partialFabrics` debt) had no peer-liveness input. On a cold boot with the peer confirmed absent (`peerEverSeen=false`, no neighbour to resolve, `PeerMAC=""`), it alone held every userspace data RG secondary until the #7161 degraded fallback promoted it DEGRADED after `DefaultDegradedPromoteTimeout` (2m) — defeating the daemon's `fabricReady` exemption ("only relevant when peer is alive", `daemon_ha.go`) and the `election.go` cold-boot premise that fabric readiness is forced true when the peer is down. Fix (option one from the issue): thread peer liveness into the userspace readiness query. `Manager.TakeoverReadyForPeer(peerAlive)` applies the whole fabric clause only while the peer is alive; `Manager.TakeoverReady()` is now the peer-alive form so metrics (`HATakeoverReadiness`) and every caller that cannot prove the peer down stay fail-closed (#15918 protection unchanged peer-alive). `LegacyDataPlaneAdapter.TakeoverReadyForPeer` forwards it; the daemon passes `cluster.PeerAlive()` (nil cluster = alive, fail-closed) through `checkUserspaceTakeoverReadinessFor`/`takeoverReadinessForRG`, preferring the peer-aware interface and falling back to plain `TakeoverReady()` for legacy backends. All other takeover terms (helper, arming, XSK, mirror, inventory, snapshot, event-stream) are local and unchanged peer-down. Updated the `electSingleNode` premise comment and appended a follow-up to `docs/log/15918.md`.
