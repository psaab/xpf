# Issue #16564: reverse-NAT alias published while the NAT ambiguity index is saturated is never recorded (R3-A71-04)

## Why

`SharedNatAmbiguityIndex::remember`
(`userspace-dp/src/afxdp/types/mod.rs`) returned early while saturated,
dropping the alias record for any session published inside a saturation
excursion. `owners` still recorded the claim and the shared NAT map
still took the alias, but `aliases` never got the record, and the only
code that installs one (`reset_to_owner`) is reached from a wire
co-owner removal. So after removals dropped the live population below
16,384 and the index "recovered" (#15104 contract), those long-lived
sessions stayed unresolvable for their whole lifetime through every
ambiguity-gated shared lookup — shared reverse-NAT match,
quoted-tuple embedded-ICMP reversal, reverse-flow prevalidation, shared
wire match (`is_unique_for` requires `Some(Some(owner))`). The exact-key
shared lookup was unaffected, and no counter distinguished the stranded
sessions. The #15104 regression only exercised a pre-saturation session.

Sibling defect found while tracing the wire index recovery path (same
class): `observe_wire_owner` set the `wire_saturated` latch when the
alias population was saturated, and nothing cleared it. That half was
fixed separately by #16561 (merged while this lane was in flight —
roster decoupled from the alias bound, trust computed from the live
population); this change was rebased onto it and carries no wire-latch
code of its own.

## What

- `types/mod.rs`: the index gains a bounded FIFO of unrecorded
  `(alias, owner)` claims (`unrecorded` + `unrecorded_set` membership
  mirror, hard-capped at `MAX_KEYS` = 16,384; claims past the cap shed
  and keep failing closed as before). `remember` queues owner claims
  refused while saturated (`None` marks name no owner and are not
  queued); `track_owner` queues saturated canonical claims the same
  way; `reset_to_owner` queues instead of silently discarding a
  survivor named while saturated. `forget_owner` dequeues the departed
  claim, re-queues a still-live sole owner whose alias was never
  recorded, then drains the queue via `backfill_unrecorded`: each
  candidate is revalidated against the live `owners` multiset (dead
  claims discarded), multi-owner aliases drain as ambiguous (`None`),
  and draining stops at the bound — the live population never exceeds
  `MAX_KEYS`. `observe` dequeues a claim it manages to record.
  `forget`/`clear` purge queued claims.
- No publish/remove signature changes, no new scans, no new locks,
  no changes to `shared_ops/store.rs`.

NOT changed: the 16,384 bound, fail-closed lookup semantics
(`is_unique_for`/`unique_owner`/`contains` unchanged), #14383 wire
survivor re-resolution, #15106 roster logic. No fail-open weakening:
a backfilled alias resolves unique only when the live owner multiset
holds exactly that one owner, which is the same proof a
never-saturated publish produces.

## Validation

- New regression cells in
  `session_glue/newflow_contention_tests.rs`, all driving the real
  `publish_shared_session`/`remove_shared_session` over the real
  16,384 bound: `shared_nat_ambiguity_saturation_era_alias_backfills_16564`
  (pre-saturation control / saturation-era subject / post-recovery
  twin, plus the real `shared_forward_nat_candidate_is_unique` proof),
  `shared_nat_ambiguity_saturation_era_collisions_stay_ambiguous_16564`
  (two owners colliding during saturation stay ambiguous, survivor
  restores on twin removal),
  `shared_nat_ambiguity_saturation_era_then_removed_never_backfills_16564`
  (subject removed before recovery is never resurrected),
  `shared_nat_ambiguity_saturation_partial_recovery_stays_bounded_16564`
  (FIFO order, bound never exceeded, remainder drains later).
- Existing #15104 cells re-run green (10/10 with the #16561 wire cells):
  `shared_nat_ambiguity_recovers_after_lifetime_churn_15104`,
  `shared_nat_ambiguity_live_bound_fails_closed_and_recovers_15104`,
  `shared_nat_ambiguity_survivor_controls_15104`. One #15104 cell was
  updated: it expected a single removal to clear saturation, which only
  held because tail aliases were silently dropped; it now removes until
  the population is actually below the bound and probes a survivor.
- RED evidence: on origin/master shimmed only with a stub
  `unrecorded_len`, the subject cell fails (`subject claim must be
  queued`); with the fix's enqueue calls neutered (same compile shape)
  both the subject cell and the exact-population cell fail at the same
  assertion. With the fix restored, all 10 targeted cells pass.
- Rebased onto #16561 (wire roster decoupled from the alias bound)
  mid-flight; the wire-latch half of the original plan was dropped as
  already-fixed there, verified by its two cells passing alongside.
- Full `cargo test --bins` suite run for the userspace-dp crate.

## Risk

- Memory: the queue is bounded by 16,384 `(SessionKey, SessionKey)`
  pairs plus its membership set — the same order as the alias map it
  mirrors, and only non-empty after a saturation excursion.
- Backfill runs under the index mutex on the removal path; it is
  bounded by the number of freed slots plus stale-claim discards, and
  the common (never-saturated) path is one `is_empty` check.
- Residual: claims shed past the 16,384 queue cap (more distinct
  aliases published during one excursion than the alias bound itself)
  keep the pre-fix fail-closed behavior; packet-level loss through the
  gated fallbacks was STATIC in the source research and remains
  lab-unverified — live saturation/recovery on the loss cluster under
  >16k concurrent shared NAT flows is still outstanding.
