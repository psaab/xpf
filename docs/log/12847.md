# #12847 — retain flood-screen fallback for ambiguous zone ingress

- **Timestamp**: 2026-10-13 (`research/12847-d3-13`)

## Why

`HostInboundScreenFloodRules` coalesced all views in a zone into one per-family rule. It merged every address and every unambiguous ingress scope, but both nft renderers selected the direct/VRF ingress match whenever any such scope existed. For a second view whose ingress was ambiguous, the combined rule therefore omitted the address fallback that was its only kernel flood screen. This was limited to the kernel host flood-screen backstop; the userspace screen can still cover traffic that is steered there.

## What

- Preserve the single zone/family/protocol meter budget and direct/VRF ingress rules.
- Collect fallback destinations only from views with no usable direct or VRF ingress. If the zone has no ingress scopes, retain the existing all-address fallback; otherwise, keep the fallback destination list disjoint from direct/VRF view addresses.
- Emit the residual destination-scoped match alongside direct and/or VRF matches in both netlink and nft text output.
- Add regressions for mixed direct + address fallback, VRF + address fallback, address-only shape, netlink rule emission, and text rule emission.

## Validation

- **Base / RED before fix**: the dedicated netlink RED probe found no per-source flood-meter rule carrying ambiguous destination `192.0.2.2`; the fallback appeared only in unrelated host-inbound service rules. The text-emitter RED test emitted only direct `iifname` rules, with no `ip daddr 192.0.2.2` match. Both failed with production source stashed. The VRF variant also confirmed the missing fallback in the normalized-rule projection.
- **Focused GREEN**: `go test ./pkg/nftables -run 'TestHostInboundScreenFlood' -count=1` passed (`ok .../pkg/nftables 0.020s`); `go test ./pkg/daemon -run 'TestHostInboundScreenFlood' -count=1` passed (`ok .../pkg/daemon 0.648s`). The netlink regression specifically requires a dynamic flood meter on the ambiguous IPv4 destination; the daemon regression pins both direct and address-scoped rule texts.
- **Package checks**: `go test ./pkg/nftables -count=1` passed (`ok .../pkg/nftables 0.570s`); `go test ./pkg/daemon -count=1` passed (`ok .../pkg/daemon 473.646s`); `go vet ./pkg/nftables ./pkg/daemon` passed (no diagnostics). After adding the stricter VRF dynamic-meter assertion, `go test ./pkg/nftables -run 'TestHostInboundScreenFloodRulesVRFPlusAddressFallback12847' -count=1` also passed (`ok .../pkg/nftables 0.007s`).

## Risk

This adds a destination match only for the residual addresses attached to views without a direct or VRF ingress scope. Existing per-zone threshold aggregation, alarm/drop behavior, reply/original placement, direct device rules, VRF slave scopes, and pure address-only zones retain their prior behavior. No live nftables packet/counter probe was performed; this change is covered by normalized rule and renderer-shape tests.
