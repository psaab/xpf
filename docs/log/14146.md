# 14146 — REST deny-commands skipped on six operational routes + system/info variants

REST enforced `deny-commands`/`allow-commands` through a route-to-command
table (#9952), but the declared-no-command arm of `authorizeRESTCommand`
returned `nil` (allow) for every route listed in `restRoutesNoCommand`
that was not request-decoded. Six operational reads sat in that table —
`GET /api/v1/statistics/interfaces`, `statistics/zones`,
`security/vrrp`, `routing/ospf`, `system/buffers`,
`services/flow-exporters` — each with a reason recording why no
argument-free canonical command exists. The reason was treated as an
exemption: a login class with `deny-commands ".*"` (PermView still
granted by the coarse bits) read all six over REST, while gRPC denies
the same shape (`authorizeRPCCommand`: an RPC with no canonical command
denies for a restricted class). Separately, `GET /api/v1/system/info`
was charged the flat `"show version"` for every `type`, while the
handler serves `type=uptime|memory` and gRPC charges those as
`show system uptime` / `show system memory` — so
`deny-commands "^show system memory$"` never fired over REST.

Fix (`pkg/api/authz_command_regex_9952.go`): the declared arm now denies
for a restricted class unless the route is in the new exhaustive
`restNoCommandExempt14146` set — `/health`, `/metrics`, and the
config-mode family, the only declared routes governed by a different
authorization decision (unauthenticated / #4162 metrics rule /
`*-configuration` pair, #9633). `GET /api/v1/system/info` moved from the
static table to the request-decoded family: `restSystemInfoCommands14146`
maps `uptime`/`memory` to the exact strings gRPC charges for
`GetSystemInfo`; unknown or missing types resolve to no command and
deny. Both new command strings join `allRESTCanonicalCommands9952`, so
the #11678 commit-time advisory knows `^show system memory$` can fire
on REST. Deliberately NOT charged: the six keep no invented command
strings (several candidate spellings do not resolve as argument-free
paths in `cmdtree.OperationalTree`, and a gate comparing against a
string no operator can type cannot be permitted by any allow either —
denial is the honest answer). Config-mode routes, `/health`, `/metrics`,
unrestricted classes, and superusers are unchanged.

Regression (`pkg/api/authz_command_regex_14146_test.go`, RED on
origin/master 0db0fa57c with the table-guard cells stripped so the
behavioral cells compile there): `TestSixNoCommandRoutesDenyForRestrictedClass14146`
fails pre-fix with all six ALLOWED under `deny-commands ".*"`;
`TestSystemInfoChargesPerTypeCommand14146` fails pre-fix with
`?type=memory` ALLOWED under `^show system memory$`;
`TestRestrictedClassControls14146` fails pre-fix with all six plus both
system/info types ALLOWED under `allow-commands "^show version$"`;
`TestReadMiddlewareDeniesSixAndSystemInfo14146` fails pre-fix with the
six returning 200 through the real `readAuthz` middleware.
`TestNoCommandExemptSetIsExactlyTheOtherFamily14146` pins the exempt
set in both directions and restates the #9633 config-mode guard against
the new mechanism; `TestSystemInfoCommandsResolve14146` holds the
per-type strings to the canonical argument-free rule.

Validation: `go test ./pkg/api/ -run '14146'` — 6 passed.
`go test ./pkg/api/ -run '9952|12582|11678|13249|...'` — existing
#9952 census/behavior/wiring cells, #9633 config-mode guard, and the
no-regex narrowness control all pass unchanged. Full `pkg/api` suite
run before push (see PR).

Risk: operator-visible delta — a login class with any operational
regex leaf can no longer read the six no-twin endpoints over REST at
all (403), matching gRPC's fail-closed posture for unmapped RPCs;
classes without operational regexes are unaffected. The six remain
reachable via `show-text` topics / CLI where a real command exists.
