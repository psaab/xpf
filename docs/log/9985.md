# 9985 — Resolve MTU ownership per resolved netdev

## The boundary after #9927

The STEP-0 probe ran on `origin/master` at `6d3775e11`, after #9927's
fabric-owner pre-pass had landed. That probe showed the boundary rather than
reproducing the original fabric-member overwrite:

- local-fabric `fab0.10` with `mtu 9500` produced no planner row;
- local-fabric `fab0.0` with `mtu 9500` produced `plan[ge-0-0-0].mtu = 0`;
- the tagged and untagged fabric references therefore already agreed on the
  resolved member, with #9927's `pd.mtu == 0` semantics intact;
- the STEP-0 tunnel scratch shape had no source/destination endpoints. Its
  tagged-arm yield therefore measured the planner asymmetry, not a successful
  routing owner; the untagged arm still planned `1300` on the resolved tunnel
  name;
- an ordinary interface with its MTU statement absent produced a desired row
  whose `mtu` remained `0`.

The tunnel scratch result exposed the remaining planner ownership arm, while
the missing ordinary target exposed the deletion no-op. The separate fabric
9000 floor and write-failure propagation are actuator concerns in
`pkg/daemon`/`pkg/routing`; this lane deliberately does not change those
components.

The current-master #9927 fabric controls remain the required boundary: they
already prove that the original fabric-member overwrite is fixed and must not
be reopened as a RED case.

## The fix

`mtuOwnedNetdevs` extends #9927's resolved-Linux-netdev pre-pass:

- existing fabric ownership remains supplied by `fabricOwnedNetdevs`, with no
  change to the #9927 fabric semantics;
- every configured interface/unit tunnel is collected by its actual assigned
  Linux device name, even when unzoned, so an ordinary alias cannot contest an
  owner that the zone walk never visits;
- only tunnels accepted by `config.TunnelHasUsableEndpoints` are owners. An
  unusable tunnel is not created by the routing owner, so the planner retains
  the configured target rather than classifying the uncreated device as owned;
- an interface-level tunnel name cannot claim a different per-unit tunnel
  device;
- both tagged and untagged MTU contributions consult this one ownership map;
- an unowned netdev with no configured MTU gets the explicit Linux default
  `1500`, so deleting an interface MTU supplies a planner reset target.

The unusable-tunnel case is ownership classification only: the dataplane
actuator may still soft-skip the absent netdev. Reconcile-or-reject and owner
write-failure propagation therefore remain follow-up work outside this lane.

Fabric-owner controls remain byte-identical: local fabric and canonical fabric
bond plans still have `pd.mtu == 0`, while the ownerless slash-bond control and
ordinary lowest-unit precedence still plan as before.

## Coverage

- `TestMTUOwnershipIsPerResolvedNetdev_9985`: one valid interface-level tunnel
  is referenced through tagged and untagged units in both reference orders;
  both references yield against one owner decision.
- `TestUntaggedTunnelReferenceDoesNotPlanMTU_9985`: a valid untagged per-unit
  tunnel owner suppresses the old unit-MTU write.
- `TestTunneledRethPlansMemberMTU_9985`: a tunneled reth whose zone ref
  resolves to its physical member still plans the member-side MTU; the reth
  TUN owner does not claim that member.
- `TestUnzonedTunnelOwnerSuppressesAliasReference_9985`: an unzoned tunnel
  still owns its configured netdev against a canonicalizing ordinary alias.
- `TestInterfaceTunnelDoesNotClaimPerUnitDevice_9985`: a valid base tunnel
  does not falsely own an unusable per-unit child device.
- `TestUnusableTunnelDoesNotOwnMTU_9985`: missing tunnel destination is a
  negative ownership classification control and retains the configured unit
  MTU; it is not proof of successful reconciliation on an absent device.
- `TestDeletedInterfaceMTUPlansExplicitLinuxDefault_9985` and
  `TestTaggedOnlyInterfaceWithoutAnInterfaceMTUPlansLinuxDefault_9761`: absent
  interface MTU materializes `1500`.
- Existing #9927 fabric-owner, bond-owner, slash-bond, zone-order, and tagged
  reference-shape controls remain in the affected suite.

The revert probes were RED and then GREEN:

- omitting the global tunnel pre-pass made the valid mixed-reference tunnel
  tests fail (`1400`/`1300` were planned);
- restoring the zone-keyed ownership pre-pass made the tunneled-reth member
  control fail (`mtu` became `0` instead of `1400`);
- accepting every tunnel without `TunnelHasUsableEndpoints` made the unusable
  tunnel control fail (`mtu` became `0`);
- replacing the default with `0` made the deleted-MTU control fail.
