# Issue #13208: Drain XFRM dump responses after interleaved events

## Finding

Deep-review finding D2-01 (High, source:deep-review; run
`review-work.tSdtKLhsvV`) identified that `full_dump` returned immediately
when a multicast XFRM event (`nlmsg_seq == 0`) appeared during a GETSA dump,
or when the kernel marked a reply with `NLM_F_DUMP_INTR`. Because the monitor
retries on the same socket with a new sequence, unread response datagrams from
the aborted dump remained queued. Each retry could then consume an older
sequence and fail again, leaving the IPsec SA store stale and dropping
userspace ESP-in-UDP traffic.

## Change

`full_dump` now consumes each datagram through a sequence-aware parser. It
skips stale sequence replies, marks multicast notifications and interrupted
dump replies invalid, and continues draining until the current dump's
terminal message. Invalid or interrupted snapshots are not published; the
monitor retries only after the old dump response has been consumed. Tests
cover interleaved multicast invalidation, `NLM_F_DUMP_INTR` invalidation, and
stale reply recovery.

## Risk

current snapshot and retry. This preserves the existing fail-closed store
behavior and avoids publishing a possibly inconsistent SA set. The Rust test
