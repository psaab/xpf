# #14997 DHCPv6 REBIND Reply teardown validation — engineering history

Issue: psaab/xpf#14997 (`dhcp: validate DHCPv6 renew and rebind replies
before tearing down leases and delegations (D40-03)`). Source claim
`D40-03` (gemini-4-argon), validator run `tpzkKgAuZL`, consensus
MATERIAL (3-way). Lane branch: `fix/14997-campaign`, base
`origin/master` 89626a2bb0.

## Defect (present at base)

`v6RenewMatcher` (`pkg/dhcp/renew.go`) accepted a REBIND Reply from any
server on transaction-ID + client-DUID + present server DUID alone
(the #14600 RFC 8415 SS18.2.5 any-server arm), and the run loop trusted
its contents to tear down state:

- IA_PD `NoPrefixAvail` set `pdRefused`, and the run loop's refusal arm
  (`pkg/dhcp/dhcpv6.go`, acquire/renew/rebind) replaced the reconciled
  set with `nil, true` — every held delegation cleared in one packet.
- IA_NA with all valid-lifetime 0 returned `errV6AddrInvalidated`, and
  the renew/rebind loop deconfigured the held WAN address and
  re-acquired (#5927 path).
- An IAPREFIX with valid-lifetime 0 entered `withdrawnPDs` and
  `reconcileDelegatedPDs` removed that held prefix.
- A non-Success status at message level failed the exchange; at IA
  level (`NoBinding`/`NoAddrsAvail`/`NoPrefixAvail`) it fed the same
  teardown arms above.

The answering server never granted those bindings and, per RFC 8415
SS18.2.10/SS21, a Reply from a different server must not replace the
binding during Renew/Rebind processing at all; SS18.2.5's any-server
Rebind is only meaningful for servers that actually hold the binding.
The transaction ID and client DUID are learnable by any on-link host
(the client's RENEW/REBIND and the servers' Replies are observable),
and the REBIND is multicast, so one spoofed packet at T2 tore down the
WAN lease and the whole IA_PD delegation.

Scope narrowing (binding from the filing): REBIND focus; the
negative-status parser sub-leg was refuted in synthesis and is not
touched — `parseV6ReplyChecked` still treats a granting server's
`NoPrefixAvail` as a refusal (#14598) and a granting valid-lifetime 0
as an explicit invalidation (#5927). DHCPv4 is out of scope: a partner
NAK in REBINDING is the #14600-documented RFC 2131 SS4.3.2 behaviour and
v4 has no delegated-prefix set.

## Fix

In `pkg/dhcp`, matcher-layer, fail-closed:

- `renew.go`: `v6RenewMatcher` gains a REBIND content gate. After the
  existing transaction/client/server-presence checks, a REBIND Reply
  whose server DUID differs from the committed granting DUID is
  rejected when `v6ReplyTearsDownHeldBinding` reports teardown
  content: a non-Success status at message level or on a requested IA,
  an IAADDR with valid-lifetime 0 in a requested IA_NA, or an
  IAPREFIX with valid-lifetime 0 in a requested IA_PD (IAID discipline
  mirrors `v6ReplyMatches`, #10858 — only requested IAs count). Pure
  extensions pass, so the #14600 failover partner still extends the
  binding and becomes the next RENEW server. RENEW is unchanged (the
  granting-server binding already rejects partner teardown at the
  identity gate).
- `dhcp.go`: `RenewalBindingStats` gains `DHCPv6TeardownRejects`,
  backed by `Manager.renewV6TeardownRejects`, so the new rejection
  class is observable like the #9944 server-identity rejects.
- `pkg/dhcp/README.md`: the renewal-binding bullets now record the
  REBIND extension/teardown split and the v4 non-twin rationale.

Not changed: `parseV6ReplyChecked`, `extractDelegatedPrefixes`,
`reconcileDelegatedPDs`, the run loop's commit/refusal/invalidation
arms, acquisition/stateless matchers, request builders, destinations,
or any DHCPv4 path. A granting server's teardown (RENEW or REBIND) is
byte-for-byte the pre-fix behaviour.

Behaviour delta (deliberate, the issue's ask): a non-granting server
can no longer revoke the lease/delegation at T2; it can still extend
them. If the granting server has failed over and the partner genuinely
holds no binding, its `NoBinding` Reply is now ignored and the client
keeps the binding until the partner grants an extension or the lease
expires into a fresh Solicit — the RFC 8415 SS18.2.10 posture.

## Residuals

- The gate inspects the same decoded options the parser consumes, so
  there is no wire/parser divergence; a future teardown class added to
  the parser (a new status-driven clear) must be mirrored in
  `v6ReplyTearsDownHeldBinding` — the matcher comment names the three
  current classes.
- No lab failover-pair capture: the gate is at the unit-testable
  matcher seam, and the run loop is unchanged once a Reply is accepted.
