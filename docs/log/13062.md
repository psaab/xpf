# Honor #1229 v7 cap-aware selection and the #917 V_min brake in `build_cos_batch_from_queue` (#13062)

- **Issue**: #13062 (`[research D1-04]`, source finding D1-04 from the
  deep-review run `review-work.2e4cldwkh1`, validated by the three-way
  research gate; source report
  `/var/tmp/deep-review-reports/gemini-4-argon-high-review-performance-cos-fairness-100e100m-and-code-quality-modularity-001.md`
  finding 30).
- **Cause**: `build_cos_batch_from_queue`
  (`userspace-dp/src/afxdp/cos/queue_service/mod.rs`) hardcoded
  `target_bps = u64::MAX` into every `cos_queue_peek_min_bucket` /
  `cos_queue_pop_known_bucket` call and never ran the #917 V_min gate,
  on the assumption it was a non-exact-only path with no rate cap to
  honor. Both halves of that assumption are false:
  1. Lazily-promoted non-exact guaranteed queues (#1735: `!exact &&
     transmit_rate_bytes > 0`) ARE flow-fair, and `submit_local` /
     `submit_prepared` already pay the per-packet
     `account_flow_bucket_tx` cost (flow hash + EWMA, incl. a `u128`
     division per 1 ms window) that maintains
     `flow_bucket_observed_bps` — but the `u64::MAX` target made #1229
     v7 cap-aware bucket selection 100% dead code on this service
     path, so elephant buckets were never deferred in favor of
     cooler/mouse buckets inside the queue.
  2. `shared_exact` queues with `surplus_sharing == true` (#915) reach
     this builder in Phase 3 (`CoSServicePhase::Surplus` via
     `select_cos_surplus_batch_filtered`), where the missing
     `cos_queue_v_min_continue` gate let a worker drain surplus with
     its `queue_vtime` arbitrarily far ahead of the peer
     `vtime_floor` — which `apply_cos_*_result` keeps publishing —
     without ever tripping the cross-worker lag brake.
- **Change** (`userspace-dp/src/afxdp/cos/queue_service/mod.rs`,
  `drain.rs`): `build_cos_batch_from_queue` now samples
  `compute_drain_target_bps(queue)` ONCE per build (stable
  eligible-set, the same contract as `drain_exact_*_to_scratch_*`)
  and threads it into the cap-aware peek/pop in both the Local and
  Prepared arms; each arm consumes one #941 suspension slot after the
  empty-queue preflight and runs the #917
  `cos_queue_v_min_continue` gate before the first pop and every 8th
  confirmed pop thereafter, with the `v_min_pop_count` commit deferred
  to the confirmed pop (#2646 — throttled / budget-missed breaks do
  not burn a cadence position), exactly mirroring
  `drain_exact_{local,prepared}_items_to_scratch_flow_fair`.
  `compute_drain_target_bps` was widened from private to
  `pub(in crate::afxdp)` for the parent-module call. Behavior is
  byte-identical for every queue that was the hardcode's implicit
  scope: non-flow-fair (FIFO) queues and unshaped
  (`transmit_rate_bytes == 0`) queues still get `u64::MAX`
  (`compute_drain_target_bps` returns it directly), and
  `cos_queue_v_min_continue` self-gates to continue on
  non-`shared_exact`, unshaped (#2981), floor-less (#8428) queues.
  A throttle in the build is non-fatal by construction: both
  production selectors (`select_nonexact_cos_guarantee_batch_into`,
  `select_cos_surplus_batch_filtered`) advance their RR cursor BEFORE
  the build and simply move to the next runnable queue on `None` — no
  progress/refund/honor path classifies it as a TX stall (that hazard
  is D1-05's, on the exact direct path, untouched here).
  `userspace-dp/src/afxdp/cos/README.md` documents the unified gating.
- **Regression coverage**
  (`userspace-dp/src/afxdp/cos/queue_service/tests/fairness.rs`):
  `nonexact_flow_fair_build_applies_v7_bucket_cap` — the finding's
  probe 1: a non-exact shaped flow-fair queue (1 Gbps, two active
  buckets → 500 Mbps target) with the elephant bucket observed at
  1 Gbps but LOWER virtual finish (500 B vs 1500 B) must defer the
  elephant and admit the mouse frame first (`batch_bytes == 1500`,
  mouse `src_port`); `shared_exact_surplus_build_is_v_min_throttled`
  — probe 2: a `shared_exact` `surplus_sharing` queue 100 MB past the
  peer floor must build an EMPTY batch in `CoSServicePhase::Surplus`
  (throttle counted, `queue_vtime` frozen, #2646 counter unburned,
  items left resident), and the within-lag control still drains both
  items with the cadence counter at 2.
- **RED evidence**: On pristine `origin/master` (1eb8a44cf) with only
  the test files applied (tests/fairness.rs + the `mod fairness;`
  registration), both tests FAILED:
  `nonexact_flow_fair_build_applies_v7_bucket_cap` panicked at
  fairness.rs:111 `assertion left == right failed: the MOUSE frame is
  the one admitted — left: 500, right: 1500` (the no-cap min-finish
  scan popped the over-cap elephant's 500 B frame), and
  `shared_exact_surplus_build_is_v_min_throttled` panicked at
  fairness.rs:176 `#917: a shared_exact surplus build 100 MB past the
  peer floor must be throttled to an empty batch` (the ungated build
  popped both items and returned `Some`).
- **GREEN evidence**: With the fix, both fairness regressions pass;
  the full `afxdp::cos` filter passes (332 passed / 0 failed / 2
  ignored) and the full `--bin xpf-userspace-dp` suite passes on the
  final tree (see PR validation). `cargo fmt --check` is clean for the
  touched files.
- **Blast radius / risk**: Low. For FIFO and unshaped queues the
  target is `u64::MAX` (identical selection; the no-cap fast path in
  `cos_queue_min_finish_bucket` still skips the `observed_bps` load)
  and the V_min helpers self-gate to no-ops, so the added hot-path
  cost is a couple of not-taken branches. For shaped flow-fair
  non-exact queues the selection becomes cap-aware (the intended #1229
  v7 semantics already paid for by the submit-side accounting);
  work-conservation is preserved by the all-over-cap fallback to the
  min-finish bucket (pinned in `queue_ops/tests/cap_aware.rs`). For
  `shared_exact` surplus queues the new throttle returns an empty
  batch for ONE build call and the selector moves on — the same
  skip-and-revisit shape the exact drains have had since #917/#941.
  Residual (out of scope): D1-05 — the Phase-1 exact waterfill path
  still classifies a V_min throttle as a TX stall
  (`Some(None)` + honor refund); and the cadence gate only reads the
  floor on pops 1, 8, 16, …, so up to 7 pops of a fresh build can pass
  before the next peer-slot read — both inherited from the drain.rs
  wiring this change mirrors, not introduced by it.
