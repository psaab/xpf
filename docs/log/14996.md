# Issue #14996 — Block DHCP clients claiming zone-apex and multi-label FQDNs in DDNS derivation (D40-02)

- **Timestamp**: 2026-10-18
- **Action**: `finalizeFQDN` kept any sanitized client-supplied name that `fqdnWithinDomain` deemed inside the zone, and that helper returned true both for `name == domain` (the zone apex) and for any `.<domain>` suffix (arbitrarily deep multi-label names). An unprivileged DHCP client could therefore publish A/AAAA at the zone apex (`example.com`) or under a delegated/service subdomain (`host.sub.example.com`, `printer.cust.example.com`) simply by offering that FQDN/host-name — provider (DHCP DDNS) leg only; the refuted RFC2136 overwrite sub-leg is not touched. Fixed by replacing `fqdnWithinDomain` with `fqdnDirectChildOfDomain`: only an exactly-single-label `<label>.<domain>` name is kept verbatim; the apex and multi-label claims fall through to the pre-existing first-label relabel (`<first-label>.<domain>`, e.g. apex `example.com` → `example.example.com`, `host.sub.example.com` → `host.example.com`), preserving the never-reject-a-lease posture of the surrounding foreign-name handling. Changed only `pkg/ddns/hostname.go` (`finalizeFQDN` / new helper + docs); the operator-controlled Surface A path (`surfaceAName`/`buildHostRecord`, empty-zone) is unchanged. Updated the three `manager_test.go` expectations that encoded the old multi-label-preservation contract, and added `hostname_apex_multilabel_14996_test.go` covering apex (hostname/fqdn-source/trailing-dot/case/corp-zone), multi-label (2–3 labels, fqdn source, corp zone), single-label controls (`www.example.com`, bare host, foreign relabel, no-domain), and a reconcile-level proof that neither the apex nor a multi-label name is ever published as claimed.
- **File(s)**: `pkg/ddns/hostname.go`, `pkg/ddns/manager_test.go`, `pkg/ddns/hostname_apex_multilabel_14996_test.go` (new), `docs/log/14996.md` (this file)
- **Validation**: New tests are RED on pre-fix `hostname.go` (apex and multi-label kept verbatim / published as claimed) and GREEN after the fix; `go test ./pkg/ddns/ -count=1` full package passes (recorded in the PR). No behaviour change outside DHCP DDNS derivation: bare/single-label/foreign/no-domain derivations are byte-identical controls.
- **Risk**: A client that previously (insecurely) obtained a deep name now gets its first label directly under the zone; two distinct deep names sharing a first label collapse to the same published name, resolved by the existing ownership/reassignment machinery. Operators needing deep names use Surface A (operator-supplied), which is unaffected.
