# 12647 — suppress stamped-fabric PMTUD replies

- **Timestamp**: 2026-10-13

- **Base**: `ab6ab9f7a` (`daemon: stabilize multiport PCI enumeration (#12545)`)

## Why

The forwarded egress-MTU PMTUD path (`compute_forwarded_egress_ptb` in `tx/dispatch/mod.rs`) calls `ptb_reply_suppressed` before building either IPv4 Fragmentation-Needed or IPv6 Packet-Too-Big. The builders reflect the inbound Ethernet source MAC as the reply destination. A V1 zone or V2 fabric-scope stamp is synthetic, not the original client's MAC; sending a PTB to it creates undeliverable backscatter. The reject and SYN-cookie reply paths already use `ingress_has_synthetic_fabric_source` for this exact ingress-and-stamp condition.

## What

The shared PTB suppression predicate now calls `ingress_has_synthetic_fabric_source` using the packet's ingress ifindex and source MAC. This suppresses both V1 and V2 stamped-fabric replies for either address family, without suppressing ordinary unstamped fabric-peer traffic or stamp-shaped sources on native ingress. Existing MTU decision logic is unchanged. Tests cover V1/V2 IPv4 suppression, IPv6 suppression, unstamped-fabric and stamp-shaped-native positive controls, the advertised v4 MTU, and at/below-MTU forwarding.
