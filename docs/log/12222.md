# Issue #12222 — align the disabled AppID UDP/4500 fallback

- **Issue:** The AppID-disabled tuple fallback labeled UDP/4500 `junos-ipsec-nat-t`, which is not a defined application. With AppID enabled, the predefined catalog uses `junos-ike-nat`; a policy cannot reference the old fallback label.
- **Base:** `a714c90d4` (`origin/master`); branch `fix/12222-appid-fallback`.

## Change

The live `pkg/appid` fallback now names UDP/4500 `junos-ike-nat`, matching the predefined application and enabled catalog. Regression coverage compares an AppID-off fallback session with an AppID-on catalog-stamped session, checks the matching UDP/4500 catalog entry, and runs a policy through the strict config compiler with the resolved label. A second guard verifies every live builtin fallback name resolves to an application.

The duplicate CLI and gRPC resolver tables were left unchanged: callsite searches found no live callers, matching the issue's scope note.

## RED → GREEN proof

- **STEP-0 on pristine base:** disabled UDP/4500 resolved to `junos-ipsec-nat-t`; enabled catalog/stamped session resolved to `junos-ike-nat` (AppID `44890`). `ResolveApplication("junos-ipsec-nat-t")` returned `false`, while `ResolveApplication("junos-ike-nat")` returned `true`.
- **RED:** With the fallback mapping restored to the base value, `go test ./pkg/appid/ -run 'Test(UDP4500FallbackMatchesEnabledCatalog|BuiltinFallbackLabelsAreReferenceable)_12222' -count=1 -v` failed: disabled/enabled labels differed, and the fallback name was not referenceable.
- **GREEN:** After the mapping change, the same command passed both regression tests. The UDP/4500 test also confirmed a matching enabled-catalog row and successful strict policy compilation using the fallback label.
