# #16020: Prevent replay of fabric gRPC mutations

- **Timestamp**: 2026-11-02
  - **Action**: Implemented #16020's bounded mutating-RPC replay defense.
    STEP-0: confirmed not already fixed at `fed39c4bc1`: issue OPEN, no merged
    PR for a single-use/nonce fix, and `pkg/grpcapi/fabric_auth.go` (the
    #4107 PSK token layer at HEAD) documents the defect as "Residual 1":
    the token is `HMAC(PSK, domain || method || request-digest || window)`
    (30s window, verifier accepts current ±1) with no nonce/jti/single-use
    store, so a byte-identical captured unary request replays successfully
    for ~60–90s; `fabricAuthCreds.RequireTransportSecurity()` returns false
    and the peer dial uses `insecure.NewCredentials()`.

    Design gate (this lane's decision point):
    - **Route A — server-side single-use cache keyed on the raw token bytes,
      mutating fabric RPCs only (chosen).** The token already binds method +
      request digest + window, so the token bytes themselves are the
      `(window, method, digest)` identity the issue's decisive check names.
      The fabric unary interceptor records the raw token of each token-
      verified mutating call (`ClearSessions`, and `SystemAction` only when
      `isFabricSafeSystemAction` — the allowlist's own mutation gate) and
      rejects a second presentation `Unauthenticated`; read-only fabric RPCs
      and streams are unrestricted; every accepted mutating token remains
      consumed even if its handler returns an error (the operation may have
      partially committed). The cache associates entries with the matched
      mint window and advances a monotone high-water window. It prunes token
      windows outside the accepted skew band while permanently rejecting
      stale windows after wall-clock rollback. The cache fails closed at its
      hard capacity. There is no token-format or proto change, so mixed
      versions can still authenticate; an unupgraded receiver remains
      vulnerable until it installs the cache.
    - **Route B — add a per-call nonce and cache (not chosen for this bounded
      lane).** Unlike Route A, a nonce makes two intentionally identical
      calls distinct while a copied token remains single-use. It therefore
      changes the wire token and needs a versioned token/rolling-upgrade
      policy; that extra client and mixed-version design is unnecessary for
      the issue's explicitly offered `(window,digest)` cache alternative.
    - **Route C — mTLS/TLS on the fabric listener: out of scope for this
      lane.** It is the deferred #4047 direction (per-node cert lifecycle),
      which the issue explicitly does not assert as the fabric owner of this
      claim. The plaintext-disclosure arm of the issue therefore remains
      open; the PR is `Refs #16020`, not `Closes`.

    Gate evidence for Route A: the currently audited mutating callers
    (`clearPeerSessions` and `proxyPeerSystemAction*`) are single-attempt,
    with no automatic retry loop. The token is deterministic within one
    method/request/window, so an intentional duplicate request in the same
    accepted window is indistinguishable from a captured replay; after any
    attempt reaches the fabric interceptor its token is consumed even if the
    handler returns an error, since an error may follow a partial or committed
    side effect. A retry needs a newly minted token (normally after the
    30-second token window changes). This trades same-window retry availability
    for the stated single-use acceptance criterion. The cache is process-local
    to the receiving Server; it does not claim to prevent cross-node replay to
    a different receiver or replay after daemon restart. TLS/plaintext exposure
    also remains.

    Implementation: the fabric unary interceptor consumes a valid token once
    for ClearSessions and the fabric-safe SystemAction verbs. The decoded
    32-byte HMAC is the atomic key; entries are indexed by matched mint window,
    with a monotone high-water window preventing re-admission after clock
    rollback. Entries outside the accepted skew band are pruned, the cache is
    capped at 4096 live tokens, and new mutations fail closed with
    ResourceExhausted at capacity. Read-only calls and streams do not consume
    the cache. Tokens remain consumed after handler errors because a failure
    can follow a committed side effect.

    RED/GREEN evidence:
    - Before the cache, `go test ./pkg/grpcapi -run
      '^TestFabricAuth16020_' -count=1` failed as expected: identical mutation
      replay and handler-error retry were accepted, concurrent copies all
      reached the handler (13 calls), and changed-hex-case replay was accepted.
    - After implementation and gofmt,
      `go test ./pkg/grpcapi -run
      '^(TestFabricAuth|TestSkew|TestMonitorInterface|TestFabricStream)' -race
      -count=1` passed (`ok github.com/psaab/xpf/pkg/grpcapi 29.870s`).

      This includes the controlled two-second backward-edge replay cell and
