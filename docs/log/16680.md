# #16680 - hostname-addressed PSK gateway pins FQDN remote.id

- **Timestamp**: 2026-10-25
- **Action**: For a PSK gateway addressed by a hostname (`address peer.example.test`) with no `remote-identity`, `defaultRemoteID` returned the hostname token and the inline-endpoint arm did the same, so swanctl rendered `remote { id = "peer.example.test" }` and `pskIDSelectorsLocal` scoped the secret by that hostname string. Junos defaults the peer identity to the resolved IP and strongSwan defaults to its own IP, so a default-identity peer was refused in both directions (AUTH_FAILED) and the DNS-addressed tunnel never established. Gate all three sites on `netip.ParseAddr`: `defaultRemoteID` and the inline arm now yield no `remote.id` for a hostname (dial target stays in `remote_addrs`, which strongSwan DNS-resolves; no DNS lookup runs on the synchronous render path), and the PSK peer selector skips non-IP entries so the secret is selected by its local owner (`%any` / pinned local address / local-id) instead of an identity nobody presents. IP-literal gateways/endpoints (v4 and v6), multi-address lists, and explicit `remote-identity` are unchanged. The shared-local-owner isolation concern is tracked separately as #16708 and deliberately not widened/narrowed here.
- **File(s)**: `pkg/ipsec/policy.go`, `pkg/ipsec/policy_hostname_remoteid_16680_test.go` (new), `pkg/ipsec/README.md`, `docs/log/16680.md`
- **Validation**: New `TestHostnameAddressNoRemoteID16680` (9 subtests: hostname gateway, hostname+local-address, inline hostname, IP gateway/inline/IPv6 controls, explicit remote-identity control, mixed hostname+IP list, `defaultRemoteID` helper) — RED on pristine origin/master, GREEN with fix; full `pkg/ipsec` suite green.
- **Risk**: Hostname-addressed PSK secrets now carry only the local owner until #16708 reworks selector scoping; an explicit `remote-identity` remains the per-peer scoping workaround. Lab IKE establishment in both directions against a fixed-IP-identity peer still to be verified on the loss cluster.
