# #19175 — a FIN/RST that materializes a session half never reaches its companion

Lane C3 implementor. Branch `fix/19175-materialize-close-propagation`, on
`origin/landing/19153-18552` a1a429910a (the #19153 + #18552 landing tree, 13
commits on master 06c743e22e). Red and the validation baseline are judged at

## Re-verified at a1a429910a (the issue cites master 06c743e22e)

The issue's mechanism holds in the landing tree; only the file moved
(#19153 fold 1 split the materialize out of `resolve.rs`).

- The materialize is `session_glue/materialize.rs`.
  `apply_deferred_shared_materialization` -> `materialize_capture` -> the core
  `materialize_current_shared_under_permit`, which classifies before it
  installs (`materialize_divergence`). On `MaterializeDivergence::None` the
  core installed with `install.tcp_flags = packet_tcp_flags` (this packet's
  flags); on `Drop` with the row's own carried flags.
  `upsert_synced_with_origin` then derives `closing`/`reset`/`fin_own` from
  the flags (`session/install.rs:1255-1271`), outside the lookup.
- A shared hit resolves with `authority_deferred: false`
  (`shared_ops/lookup.rs` `ResolvedSessionLookup::shared`, carried at
  `session_glue/resolve.rs:722`). The poll site's #13938 Owner replay
  (`poll_descriptor/mod.rs`, the `resolved.authority_deferred` arm) therefore
  never ran for a materialized row. `materialize.rs`'s own doc said so
  ("nothing is replayed").
- Had it run, `stamp_tcp_close` (`session/lookup.rs:1254`) reports progress
  only for `!entry.reset && (rst || (fin && !entry.fin_own))`: no progress on
  a row the install already closed, so `propagate.close`, `state_transition`,
  the companion propagation (`lookup.rs:1163`), the state Update and close
  relay (`lookup.rs:1164`) and the #16489 seed (`became_closing`,
  `lookup.rs:1093`, seeded at `:1131-1133`) would still not run.
- The comment at `promote.rs` (the #13939/#17092 note before
  `promote_synced_with_origin`, :775-777 at a1a429910a) claimed the replay
  re-applies the close; true only for local hits.

## Design (the lead's direction)

The install takes the shared row's carried close state, and the packet's
FIN/RST is applied by the existing Owner replay arm, so the local-hit state
machine runs from one place.

- **Install** (`materialize.rs`, `materialize_current_shared_under_permit`):
  on `None` the packet's flags are stamped unless
  `close_owed_to_owner_replay(key.protocol, tcp_flags)` (TCP and FIN or RST).
  In that case the row keeps its carried flags and close class, as the `Drop`
  path and an `UpsertSynced` replica of the same row install it.
- **Trigger** (`materialize.rs`, `apply_deferred_shared_materialization`):
  when the core INSTALLED a row (`Installed` or `SharedLocal`) with
  divergence `None` and the packet owes its close, it sets
  `resolved.authority_deferred = true`. Guarded by `resolved.key ==
  captured.key` (always true for a shared hit: `ResolvedSessionLookup::shared`
  resolves to `Canonical(entry.key)`; debug-asserted), so the replay can never
  land on a row this packet did not install.
- **Replay**: unchanged. The poll site's arm
  (`poll_descriptor/mod.rs:3198-3207`) runs
  `apply_deferred_owner_hit_with_ack(&resolved.key, ...)`.

### Why the existing replay arm, not a replay inside the materialize

Order. The poll site runs, for an Owner packet:
`maybe_promote_synced_session_with_conntrack` (`poll_descriptor/mod.rs:3114`;
inside it the purge, the materialize at `promote.rs:989` and the promotion at
`promote.rs:999`), then the #19153 Drop recycle (`:3159`), then the
forwarding revalidation, then the replay (`:3198`). That is exactly the
local-hit order, so a materialized row's close is applied:

- after the promotion. The promotion flips F with R (#18552 B1). A replay
  before it would see F still `SyncImport`, and `emit_session_state_update`
  stays silent for a peer-synced forward (`session/mod.rs`, the #9582/#10038
  origin gate), so the HA Update would be lost. It would also publish and
  replicate the promoted row with the close class already set, where a local
  hit publishes the pre-replay row.
- after the forwarding revalidation, so a #9412 close Update carries the
  revalidated route (the poll site's own #12265 comment).
- never for a recycled `Drop` packet (the recycle precedes the arm).

One copy of the logic: the materialize decides only WHETHER a replay is owed.

## Interactions

- **Promotion in the same packet.** `promote_synced_with_origin` strips the
  FIN/RST from its flip (`session/mod.rs`, `is_closing(req.tcp_flags)`), so
  the promotion applies no close; the replay applies it once, with progress
  (the installed row carries no close of this packet's). No double count:
  `stamp_tcp_close` makes a second application of the same flags a no-op.
  The `promote.rs` comment and the `promote_synced_with_origin` comment are
  corrected to say the replay now covers materialized rows.
- **#19153 Drop.** Unchanged. The core still installs a differing row clean,
  the trigger requires divergence `None`, and the poll site recycles a `Drop`
  packet before the replay arm. Cell (f).
- **Refusals and fences.** `Refused`, `CaptureFenced`, `StaleReplayFenced`,
  `SharedAbsent`, `Superseded`, `InstallRefused`: nothing installed, nothing
  owed (the trigger requires an installed row). A #10582 local incumbent is
  `Refused`: the packet is not replayed onto the incumbent (it resolved
  against the shared capture), as before.
- **FabricRedirect rows: replayed, deliberately (disagrees with the lead's
  suggestion).** A local hit replays whatever the disposition (the poll arm
  has no disposition gate), so a materialized row does too, or the two
  shapes would diverge again. What could be "double-applied" is this node's
  own table, and the peer applies the close to the peer's table; they are
  different tables. The HA echo is already prevented by the emit's origin
  gate: a peer-synced forward (the peer owns the flow) stays silent. When
  THIS node owns F (split RG, #16217 reverse-departed redirect), the Update
  is correct and nothing else would send it. Skipping the replay would also
  regress such a row: before #19175 its install at least stamped R's close;
  without the replay it would install open. Cell (h).
- **Non-owner / transient arms.** Unchanged: a foreign packet never runs the
  deferred effects (the poll site discards them) and never reaches the
  replay arm; a transient (owner-RG-inactive) hit never materializes.
- **Non-closing packets.** Unchanged: the install takes the packet's flags
  and nothing is replayed (the flags drive only the timeout and
  `observed_tcp_flags` there).

### A bounded consequence: the fabric wire placeholder arm

A materialized forward row that is itself a fabric wire placeholder sends
every later translated packet back to the shared alias, which re-materializes
it (`shared_ops/lookup.rs`, the local-hit arms; see #19153 fold 3), replacing
the replica in place (`holds_local_row` is false for a replica). That
re-install already discarded the replica's close state on every packet before
#19175 (an ACK after the FIN reopened it). With #19175 every FIN or RST on
that arm replays on a freshly installed row, so a RETRANSMITTED FIN there
re-queues the close relay and the replica's Update, and re-stamps the
companion's close window. The receivers are idempotent (`apply_close_relay`:
"a relay that adds nothing new changes nothing"; the peer's import of the
same class), and it is bounded by retransmissions on that arm. Making that
arm keep its replica's close state is a separate change.

> **Fold 1 correction (codex-d P2-2).** The "receivers are idempotent" claim
> above was too broad, and it missed the emitting worker itself. What holds
> is narrower: a repeated close relay on an unchanged receiver adds no bits
> and does not refresh it (`session/handshake_relay.rs`); a same-id,
> same-class/stage HA re-import keeps its inactivity anchor
> (`session/install.rs`); and the #9412 sender keeps the highest class it
> announced (`pkg/cluster/sync_close_class_9412.go`). That is close-lifetime
> idempotence for STABLE receiver state, not exactly-once transmission, and
> none of it protects the companion in the emitting worker: each
> re-materialized FIN was fresh progress, and F17 set the companion's
> `last_seen_ns` again, moving a RST fuse or a TIME_WAIT window. That was a
> defect, not a bounded cost; fold 1 fixes it (the shared publication plus
> the same-incarnation close carry).

## Sibling shapes (the issue's audit)

- **Forward-direction materialize** (a FIN that materializes F, including
  through the forward-wire placeholder arm): FIXED by the same change. The
  trigger is key-agnostic, and for the placeholder arm `resolved.key` is the
  canonical key the materialize installed (`ResolvedSessionLookup::shared`).
  Cells (g1), (g2).
- **Reverse-synthesis install** (`shared_ops/reverse_synth.rs`,
  `install_reverse_session_from_forward_match`, :736-782; the resolve arm at
  `resolve.rs:876-907`): NOT changed in the first commit. **Fold 1
  correction (codex-d P2-3): the reachability argument below is wrong.** An
  existing R past its strict idle deadline reads `IdleCrossed`
  (`session/lookup.rs`), which
  `lookup_session_across_scopes_with_shared_and_payload` turns into a miss
  without consulting shared R. So a reply FIN/RST on an ESTABLISHED,
  one-direction-active flow falls through to the forward NAT match and this
  synthesis. Fold 1 changes it (see "Fold 1" below). The first commit's
  reasons, kept for the record:
  - Reachability: R must be absent from both the worker table and the shared
    map while a forward NAT match exists. A local forward installs and
    publishes its reverse with it (`poll_descriptor/mod.rs:8241-8256`,
    `:8380-8420`) unless the forward is a fabric redirect
    (`forward_request.rs:31-39`), and an HA import synthesizes R into shared.
    What remains is a punt-seed forward's first reply before the peer's
    import lands (#7770: the seed "admits the peer's fabric-returned reply
    until the peer's HA import lands"). There F is on its opening window, the
    issue's benign "connection refused" shape. I found no path leaving an
    established local F without R in both places.
  - Mechanism: that install runs inside the resolve, BEFORE the authority
    verdict, and publishes and replicates R with the packet's flags (siblings
    take the close from those flags). Moving its close to the Owner replay
    changes what the shared map and the siblings receive and the pre-verdict
    ordering; it is not the drop-in this change is.
  - Note for a follow-up (not filed): the constructor it uses
    (`install_with_protocol_with_origin_and_source_nat_inner`,
    `session/install.rs:747-752`) records a FIN as `fin_peer` on a reverse
    row, which is right for the forward install's companion (the FIN is the
    forward packet's) and wrong here (the FIN is the reverse row's own). A
    replay-based close would record it as `fin_own`.

### Findings, as verified

- **P2-1 (the close never reaches SHARED): confirmed.** The promotion
  publishes the pre-replay, still-open rows (`promote.rs`
  `publish_shared_session` of `promoted_entry` / the partner); the replay
  (`session/lookup.rs`, `lookup_with_origin_inner`) and the relay consumer
  write the worker table only. Nothing raises a shared `tcp_close_class`
  after a worker's close: a shared row carries a class only as it was
  published (an HA import's wire class, or `synced_entry_for`'s snapshot of a
  local row at publish time, as a promotion takes it, before the replay).
  `probe_closing_syn_candidate` (`shared_ops/lookup.rs`)
  recognises a closing shared row only by a nonzero class, so a same-tuple
  SYN on another worker resolved and materialized the old incarnation. Note:
  `shared_ops/restamp.rs` restamps handshake stage, packet counts and
  `last_served_ns`, NOT close classes (the brief said it did); fold 1 adds
  the close-class restamp there.
- **P2-2 (wire-placeholder re-materialization re-arms the companion):
  confirmed, and the shared publication alone does NOT close it for a
  single FIN.** A CLOSING shared class installs with neither FIN bit
  (`upsert_synced_with_origin`: "CLOSING sets NEITHER"), so a re-installed F
  has `fin_own == false` and a retransmitted FIN is progress again; F17 then
  re-stamps R. RST (`reset`) and TIME_WAIT (both bits) survive the
  publication; the single-FIN case needs the replaced row's own bits.
- **P2-3 (reverse synthesis reachable on established flows): confirmed.**
  `IdleCrossed` returns `None` from
  `lookup_session_across_scopes_with_shared_and_payload` before any shared
  probe; the resolver then takes the forward NAT match and
  `install_reverse_session_from_forward_match`. The install replaces the
  idle-crossed R (`remove_entry(.., Replace)`), stamps the reply's flags
  (FIN as `fin_peer`, #19186), publishes and replicates them, all before the
  authority verdict, and returns `authority_deferred: false`.
- **r24 P3-1..3:** documented (READMEs and below).

### Changes

- **F1, shared publication** (`session_glue/resolve.rs::replay_owner_hit`,
  `shared_ops/restamp.rs::restamp_shared_close_classes`,
  `session/mod.rs::shared_close_publications`): the poll site's Owner
  replay arm now calls `replay_owner_hit`, which runs the replay
  (`apply_deferred_owner_hit_with_ack`, which now returns the matched
  canonical key when `stamp_tcp_close` made progress; `lookup_with_origin_inner`
  records it inside the state-transition block only) and then publishes the
  hit row and, when it is in this table, the companion F17 just closed.
  - Where: at the poll site, after the replay, NOT inside the emit: the
    session table holds no shared-map handle, and this is the first point
    where the closed rows and the shared maps are both in hand. It runs after
    the deferred promotion's publish of the pre-replay rows, so it is the
    later writer.
  - Rows: the canonical row in `shared_sessions`, and for a forward row its
    clones under the NAT aliases (`reverse_session_key` and
    `reverse_canonical_key`, `shared_nat_sessions`) and the forward-wire
    alias (`forward_wire_key`, `shared_forward_wire_sessions`).
  - Incarnation guard (`raise_shared_close_class`): the stored row's own key
    (an alias slot another forward took is skipped), the same NAT decision,
    and the same NONZERO session id. Stricter than
    `same_synced_incarnation` (which passes a zero shared id on NAT alone):
    a zero id proves nothing (#19063's rule), so such a row keeps its class.
  - Monotonic: `TcpCloseClass::wire_rank` (open < CLOSING < TIME_WAIT <
    RESET); a late call never lowers a class.
  - Locks and cost: each map locked alone, in turn, none nested, no permit
    held; only on a close transition (a FIN/RST with progress), at most three
    lock acquisitions and six keyed gets.
  - Not published: a companion only in shared or on a sibling (its identity
    is not in hand; a reverse row's shared id need not equal its forward's,
    `restamp.rs` "A pair publishes a distinct session id for its reverse
    row"). The sibling applies the #18520 relay to its table only.
- **P2-2 carry** (`materialize.rs`, `session/mod.rs::same_incarnation_close_progress`
  / `carry_close_progress`): before the materialize core's upsert, the

- **F2, reverse synthesis** (`session_glue/resolve.rs`): the resolver passes
