## Arm evidence and fix — #5297 invalid secure-tunnel bind-interface

`validateSecureTunnelBindInterfaceAST` already owns `lenient`. Its single
`emit` closure formats one message, returns it as an error when `!lenient`,
and appends it to warnings when `lenient`

(`pkg/config/compiler_ipsec_bindiface.go`):

```go
emit := func(format string, args ...any) error {
    msg := fmt.Sprintf(format, args...)
    if !lenient {
        return fmt.Errorf("%s", msg)
    }
    warnings = append(warnings, msg)
    return nil
}
```

Thus the old strict refusal's claim that the VPN "commits successfully" was
false; the same words are true only for the lenient warning. The diagnostic
head is unchanged. One `outcome` now selects:

- strict: `so the route-based VPN commit is refused (#5297)`;
- lenient: `so the route-based VPN commits successfully but carries no
  traffic (silent tunnel down) (#5297)` (the original outcome, scoped to the
  arm where it is true).

No gate decision or compiled configuration changed.

## Arm evidence and fix — #15040 config-sync without RG0

`validateChassisClusterStrict` is a strict builder whose sole production
caller owns the arm split. At `compiler_uniformgates_cluster_zone.go`, the
caller downgrades the SAME error to a warning under `opts.lenientChassisRG`
and otherwise returns it unchanged:

```go
if err := validateChassisClusterStrict(cfg, opts.lenientChassisRG); err != nil {
    if opts.lenientChassisRG {
        cfg.Warnings = append(cfg.Warnings,
            fmt.Sprintf("chassis cluster redundancy-group (downgraded to warning on tolerant path): %v", err))
        // ...
    } else {
        return err
    }
}
```

The builder therefore now takes the caller's `lenientChassisRG` state. Only
its #15040 outcome clause is arm-dependent:

- strict: `without it the commit is refused`;
- tolerant: `without it a commit succeeds but is never pushed to the peer
  and both nodes stay writable` (the original outcome, retained verbatim).

The diagnostic head, remediation text, all other chassis gates, and the
strict-reject/tolerant-warn behavior are unchanged. The caller is the only
production or test call site of `validateChassisClusterStrict`.

## Review fold — earlier schema-leaf #5297 producer (Kimi F1)

- **Timestamp**: 2026-11-03

- **Finding**: `ValidateSecureTunnelBindInterface` in `pkg/config/xfrmi.go`
  unconditionally returned `so the route-based VPN commits but carries no
  traffic`. This validator is registered on the `bind-interface` schema leaf

  offending token.

### Arm reach and shape decision

The leaf signature is `func(raw string) error`; it has no arm parameter and
`schemaNode.checkToken` invokes it directly. The reaches are:

- strict `SchemaValidate` / `SchemaValidateWithDefinitions`, which call
  `schemaValidateImpl(..., collect=false)` and return the error;
- tolerant `SchemaValidateCollectTypedLeaves`, which calls
  `schemaValidateImpl(..., collect=true)`; its configstore callers downgrade
  collected typed-leaf errors to warnings and continue.

**Chosen shape: (a), outcome-neutral wording.** The message now retains the
canonical-name requirement and states only mechanism plus consequence:

```text
resolves to no XFRM interface; the route-based VPN would carry no traffic (silent tunnel down)
```

This is true on both reaches. On strict, the returned error itself is the
refusal and the clause describes what the rejected config would do without
an XFRM device. On tolerant ingress, the warning envelope carries the
continue decision and the tunnel indeed has no XFRM device through which to
carry traffic. No operator signal is lost: the text still names the bad
value, required `st<N>[.<unit>]` shape, absent XFRM device, and silent-down
consequence. It makes no commit/refusal claim of its own.

Shape (b), threading arm state through `schemaValidateImpl` and typed-leaf
invocation, is therefore unnecessary blast radius. In particular, neutral
wording does NOT falsely claim refusal on tolerant ingress. The two compiler
builders fixed initially are untouched by this fold.
