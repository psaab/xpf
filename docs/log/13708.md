# #13708 — serialize in-flight session helper mutations

- **Issue**: #13708 — `SessionDomain::helper_mutation_begin` must reject concurrent duplicate execution and preserve operation-id reuse protection.
- **Branch**: `fix/13708-campaign`
- **Worktree**: `/var/worktrees/campaign-zero/wt-13708`

## Why

`HelperMutationStore` tracked in-flight keys but `helper_mutation_begin` did not consult them. A second request using the same `(epoch, operation_id)` therefore received a second lease while the first mutation was running. Concurrent use of a different `mutation_id` for that operation id bypassed the established `operation-id-reused` rejection; either lease could remove the shared in-flight marker while the other remained active.

## What

- Store the in-flight `mutation_id` alongside each `(epoch, operation_id)` key, retaining the existing in-flight lifetime and LRU exclusion behavior.
- Check the map under the existing store mutex before looking up completed records: return `operation-in-flight` for the same triple and `operation-id-reused` for a different mutation id under the active operation id.
- Preserve behavior for unrelated operation ids, failed/uncompleted lease retry after drop, completed exact-triple replay, and completed operation-id reuse.
- Add `helper_mutation_begin_refuses_concurrent_duplicate_13708`, covering both refusal reasons and the neighboring retry/replay controls.
- Scope cut: no caller or wire/API changes; the existing handler already returns `helper_mutation_begin` errors as the control response error.

## Risk

A concurrent duplicate of the same active operation now receives an explicit `operation-in-flight` refusal instead of executing twice. A different active mutation id for that operation id receives the existing `operation-id-reused` token. No protocol schema or non-helper mutation behavior changes.
