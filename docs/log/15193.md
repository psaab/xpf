# #15193 (D04-01): PSK id selector scopes the secret to the peer ADDRESS only, and no remote.id is rendered for a fixed-address gateway

- **Timestamp**: 2026-10-19
  - **Action**: Rendered the Junos default remote identity (`remote { id = <first gateway address> }`) for fixed-address PSK gateways with no `remote-identity`, and added a local owner to the PSK `id-<n>` selectors so charon's initiator-side shared-key lookup selects the secret. Added RED/GREEN regression plus controls; updated the #9641 render fixtures, `pkg/ipsec/README.md` and `docs/config-schema.md`.
  - **File(s)**: `pkg/ipsec/policy.go` (`defaultRemoteID`, `pskIDSelectorsLocal`, connection + secrets render), `pkg/ipsec/policy_initiator_identity_15193_test.go` (new), `pkg/ipsec/dynamic_hostname_identity_14590_test.go`, `pkg/ipsec/generation_combined_9641_test.go`, `pkg/ipsec/testdata/swanctl_{list_conns,list_conns_localaddr,generation_combined}_source_9641.conf`, `pkg/ipsec/README.md`, `docs/config-schema.md`, `docs/log/15193.md` (this file)

## Mechanism (origin/master `3c577c9ca2`)

- `pkg/ipsec/policy.go` rendered `remote { auth = psk }` with an `id` only when `gw.RemoteIDValue != ""` or `gw.DynamicHostname != ""`, so a fixed-address gateway with no identities (the Junos default shape, accepted by strict commit) got no remote id.
- `pskIDSelectors` scoped the PSK to the peer address only (one selector per address, #14139); the local identity was added only when `gw.LocalIDValue != ""`.
- When charon initiates with no identities configured, its shared-key lookup is keyed by the local side (`(local ip, %any)` in IKEv2; `(%any, <remote ip>)` in IKEv1). A secret carrying only the peer address never matches the local-keyed lookup, so IKE_AUTH aborts — every xpf-initiated path (`establish-tunnels immediately`, the default `trap`, #14140 changed-VPN re-initiation, HA takeover re-initiation) failed; only peer-initiated SAs came up, and two xpf boxes in this shape never established the tunnel in either direction.

## Change

- `defaultRemoteID(gw)`: first address of a fixed-address gateway's `Address` list (empty when an explicit remote-id / dynamic hostname is already configured).
- Connection render: for a PSK, non-responder-only connection with no explicit remote-id/dynamic hostname, emit `remote { id = "<default>" }` (gateway's first address, or the dialed first address for the inline no-gateway shape). Pubkey/cert connections and responder-only gateways are byte-unchanged.
- `pskIDSelectorsLocal(remoteAddr, localAddr, gw)` (render path): peer selectors unchanged, plus a local owner — configured `local-id` when set, else the pinned local address, else `%any` (no pinned address: charon picks the source per attempt, so only the wildcard owner matches whichever local IP it presents). `%any` as one owner among peer selectors preserves #3952/#14591 isolation (selection still requires the peer selector; an extra shared local owner cannot cause a wrong-peer match). Responder-only peers gain no local owner, so the #14591 shape is unchanged. The peer-only `pskIDSelectors` wrapper is retained.

NOT changed: the #14591 responder-only skip/commit gates, dynamic-hostname rendering (#14590), hex PSK rendering (#15027), and certificate/EAP secrets. No new config knob; identities stay optional on fixed-address gateways. Real-charon initiator/lab verification (`verify/v63/lab/psk-v63.sh` shape) is out of scope for this worktree (no charon binary) — the swanctl render contract above is the regression-pinned substitute recorded here.

- Controls staying green: `TestGenerateConfig_PSKIDSelectors_*`, `TestResponderOnlyPSKScoping14591` (#14591), `TestPSKIDSelectorsMultiAddress14139` / `TestPSKEmptySecretSkipped14139` (#14139), dynamic-hostname suite (#14590), `TestGenerateConfig_AddressGatewayStillDials14590` (updated: now also pins the #15193 default id).
- #9641 source fixtures updated to the new renderer output (default `remote.id` + local PSK owner); the charon list-conns/pools captures are unchanged (they record only connections/children/endpoints). Full `pkg/ipsec` suite passes; `pkg/config` IPsec-adjacent suites pass.

## Risk

- A fixed-address PSK connection now pins `remote.id` to the gateway address where previously strongSwan negotiated the peer identity freely; a peer that presents a different explicit identity (FQDN/DN) while using the gateway address will now mismatch — that peer must configure `remote-identity` (Junos parity: its default remote identity is likewise the gateway address). The `%any` local owner is deliberately bounded: it is only ever emitted alongside at least one peer selector on a non-responder connection, never as the sole selector.
