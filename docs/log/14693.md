# Issue #14693: applySSHConfig update-failure revert plus reload-only re-assert permanently enforces the reverted permissive sshd policy

## Why

A hardening commit (`system services ssh root-login allow` → `deny`, or
tighter ciphers/MACs/limits) flows: write the new drop-in, `sshd -t`
passes, `systemctl reload sshd` fails transiently. `applySSHConfig`'s
update path then called `noteSSHDReloadResult(err)` — latching the
`sshdReload` debt — AND `revertDropIn("reload-failed")`, restoring the
prior, more permissive bytes (or deleting the drop-in). Its best-effort
post-revert reload is logged only, never noted, so the debt stayed
latched. The #6800 comment claimed this path "has its own retry owner"
because the file now differs from desired — but the only background
retry owner, `reassertServiceReloadDebtOnce`, did not re-render: it
validated and reloaded whatever was on disk (the reverted file) and on
success called `noteSSHDReloadResult(nil)`, clearing the debt and
logging "sshd reload re-asserted". Net effect after one transient
failure: commit reports success, disk and running sshd both enforce the
old permissive policy indefinitely, telemetry shows no owed reload.
Second arm: the no-change early return (`prior == content &&
!legacyPresent`) did not check `!d.sshdReloadOwed()` (unlike the
removal branch), so a later identical apply would not reload while a
debt was outstanding either.

## What

- `daemon_hostauth_apply.go`: the no-change early return gains
  `&& !d.sshdReloadOwed()` (the issue's named decisive regression).
  Falling through re-runs the idempotent write + `sshd -t` + reload,
  and the reload's noted outcome pays (or re-latches) the debt.
- `daemon_service_reload_debt.go`: when a store is present, the sshd
  arm of `reassertServiceReloadDebtOnce` no longer reloads the on-disk
  bytes. It re-drives the desired config via
  `applySSHConfig(d.liveConfig12169())` under the already-held
  `applySem`: a live ssh stanza rewrites the drop-in to the desired
  bytes; a live config with no ssh stanza re-runs the removal apply
  (re-removing a drop-in a failed update apply restored). Only the
  apply's own `noteSSHDReloadResult` pays the debt. The historical
  validate+reload retry is kept solely for a process with no store
  (direct unit construction), where no desired-state authority exists
  in-process that the disk could disagree with; the #9073 validation
  counter and the #4311 validation gate live on that arm unchanged.
- `pkg/daemon/README.md`: the #6800 paragraph is corrected — the old
  "re-assert re-validates with `sshd -t` before the SIGHUP" claim was
  exactly the behavior that discharged the debt over reverted bytes.
- NOT changed: the #2062 revert itself (defensible — do not leave a
  drop-in the running daemon has not accepted), the removal-branch
  gate, chrony/rsyslog debt handling, metric shapes, and the #9073
  counter split.

## Risk

The re-assert now runs the full `applySSHConfig` (including
`applySSHPAMFaillock` and the #12169 live-config fences) every 30s
while an sshd debt is outstanding, instead of a bare validate+reload:
strictly more work on an already-failing node, bounded by the existing
loop cadence and the apply semaphore. Normal commits are unaffected —
the no-change early return is unchanged when no debt is owed, and the
re-assert's cheap path returns before the semaphore when nothing is
owed. Behavior delta on the failure path is the point: a transient
reload failure during a hardening commit now self-heals to the
hardened policy within one tick instead of silently reverting forever.
