# Apply wildcard zone groups to apply-macro leaves (#13112)

- **Issue**: #13112, source finding D1-08 (deep-review; validated by the three-way research gate).
- **Cause**: `security-zone <name> apply-macro <macro>;` is a valid inert leaf form. Group expansion treated it as a four-key leaf, while wildcard matching requires equal key counts; consequently a `security-zone <*>` group skipped the zone and silently omitted inherited security enforcement. The same extra tail prevented packed exact-name group statements from merging into the inline zone leaf.
- **Change**: `zoneLeafHasApplyMacroTail13112` recognizes only the exact unbracketed macro tail accepted by the zone-tail validator. Wildcard matching compares that leaf's zone identity and strips the inert tail before promotion, so added group children are compiled as zone properties rather than hidden as macro body. Exact-name packed group statements likewise promote and merge into the same macro leaf. Other named instances and malformed/bracketed tails retain their existing behavior.
- **Regression coverage** (`pkg/config/group_merge_zone_leaf_9801_9831_test.go`): wildcard `tcp-rst` and `screen` inheritance on macro leaves, plain-leaf control, no-group control, packed same-name merge, and distinct-zone adoption. `pkg/config/testdata/spelling_gate_members_7484.txt` and its ratchet now record the newly comparable wildcard-inherited `tcp-rst` leaf (flag 195→194; coverage floor 788→789).
- **RED evidence**: On pristine `origin/master` at `d8d98b525` with only the regression tests added, `go test ./pkg/config -run 'Test(WildcardGroupAppliesToApplyMacroLeafZone13112|GroupZoneLeafKeepsIdentityAgainstMacroLeaf13112)$' -count=1` failed because macro-leaf zones compiled `tcp-rst=false` and `screen=""` instead of the inherited values.
- **GREEN evidence**: The focused regression tests and `TestGroupPackedZoneStatementMergesIntoBracedZone9831` pass. `go vet ./pkg/config`, `gofmt` on all touched Go files, and `git diff --check` pass. Full `go test ./pkg/config -count=1` ran and failed only at `TestConfiguredIPv6Prefixes10856` with a different prefix ordering (`2606:4700:2222::2/128` before `2606:4700:1111::/64`); the isolated test passed immediately afterward, consistent with nondeterministic map-order output unrelated to this change.
- **Blast radius / risk**: Only a well-formed exact unbracketed `apply-macro` tail on a `security-zone` leaf is normalized during applicable group merges; this macro is inert at compile time. No dataplane or non-zone named-instance behavior is changed.
