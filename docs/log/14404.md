# #14404 — Kernel-upgrade election hold gates the VRRP promotion path

- **Timestamp**: 2026-10-16
- **Mechanism**: The #1930 kernel-upgrade election hold gated only cluster
  election (`electRG`/`electSingleNode`, wire weight 0). RETH VRRP was a
  parallel promotion path: a held secondary advertised VRRP priority 100
  (`LocalPriorities` had no hold term), so with zero peer adverts for ~3s
  (peer down / VRRP partition during the pre-verification window) the
  instance dead-master-promoted — sync-hold only suppresses preemption, not
  dead-master takeover — and `watchVRRPEvents` set `rg_active=true`,
  removed blackholes, added VIPs and started Kea/RA on an unverified
  kernel. Posture correction was skipped during sync-hold and afterwards
  flap-promoted (resign → 2s reconcile re-drives priority → re-promote).
- **Fix**: Four gates, hold-keyed (non-held behaviour unchanged):
  (1) `cluster.Manager.LocalPriorities` returns 0 for every RG while held;
  `vrrp.CollectRethInstances` preserves an explicit held 0 (absent RG still
  defaults to 100). (2) `vrrp.Manager.SetKernelUpgradeHold` mirrors the
  cluster hold onto RETH instances; `becomeMaster` refuses while held,
  `ForceRGMaster`/`UpdateRGPriority` are no-ops while held; the #8597
  priority clamp preserves held 0 only under the manager hold. (3)
  `rgStateMachine` forces desired=false while held (`SetCluster`/`SetVRRP`
  cannot activate) and `CheckVRRPPosture` stays silent while held, so the
  hold — not the posture timer — is the authority until the marker clears.
  (4) Daemon wiring: `syncRGKernelUpgradeHold` mirrors the cluster hold at
  VRRP bringup, on every `reconcileRGState` pass, and on every
  `reconcileKernelUpgradeHold` release/self-heal path (including holds
  cleared via ResetFailover/rejoin); `handleClusterEvent` skips the
  priority-200/`ForceRGMaster` re-drive while held. Clearing the hold
  promotes normally on the next master-down horizon.
- **Tests**: RED on master — `TestLocalPriorities_KernelUpgradeHeldSuppressesAll14404`
  failed with held priorities 100/100 (want 0/0). GREEN post-fix:
  cluster held→0/both + cleared-restore; vrrp
  `TestKernelUpgradeHold_BlocksBecomeMaster14404` (direct + stepBackup
  dead-master expiry refusal, post-clear promotion),
  `TestCollectRethInstances_HeldPriorityZeroNotDefaulted14404` (explicit 0
  preserved, absent defaults 100); daemon
  `TestRGStateMachine_KernelUpgradeHoldBlocksActivation14404` (MASTER and
  cluster-primary cannot activate while held, activate after clear) and
  `TestRGStateMachine_KernelUpgradeHoldPosture14404` (no NeedsResign while
  held, control resigns). Fail-on-revert: removing any gate re-opens its
  cell (priority, becomeMaster, rg desired, posture).
- **Validation**: `go test ./pkg/vrrp/ ./pkg/cluster/` — vrrp ok; cluster
  fails only `TestInstallTableProducerToResendEndToEnd9752`, base-attributed
  (reproduced on pristine origin/master worktree). Targeted daemon suites
  (`TestRGStateMachine|TestReconcile|TestKernelUpgrade|TestVRRP|...`) ok.
  Full daemon suite exceeded the 300s job cap (no failure output before
  kill) — main agent should run it once.
- **Risk**: Held priority 0 is the RFC resignation value on the wire; a held
  BACKUP never sends it (advert timer runs only as MASTER, and becomeMaster
  refuses), so no spurious peer takeover is injected. Standalone (non-RETH)
  VRRP is never gated (Family check). Non-candidate boots are unaffected:
  every gate keys on the hold flag only.
