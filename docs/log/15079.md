# #15079 — rendersafe accepts a leading `!`, systemd's match-list inversion prefix

- **Timestamp**: 2026-10-18
- **Action**: refuse a leading `!` in the match-slot predicate at all four render sites (networkd `Name=`/`OriginalName=`, linksetup `.link` `OriginalName=`, RETH repair `OriginalName=`); the probe row yields a refusal and no file is written. Add the same dedicated refusal message at the strict commit validator.
- **Files**: `pkg/rendersafe/rendersafe.go`, `pkg/rendersafe/rendersafe_test.go`, `pkg/networkd/networkd.go`, `pkg/networkd/refuse_negated_name_15079_test.go`, `pkg/daemon/linksetup.go`, `pkg/daemon/linksetup_negated_15079_test.go`, `pkg/daemon/daemon_reth.go`, `pkg/daemon/reth_link_negated_15079_test.go`, `pkg/config/validate_interface_name.go`, `pkg/config/validate_interface_name_negated_15079_test.go`.

## Defect

`rendersafe` refused whitespace, control bytes, `*?[]` (at the render belts) and a trailing backslash, but not a leading `!`. systemd.network(5)/systemd.link(5) document `[Match] Name=` (and `OriginalName=`) as a whitespace-separated list of shell-style globs and add: "If the list is prefixed with a `!`, the test is inverted." A single rendered word `!x` therefore matches every device *except* `x`. The unmanaged-netdev census in `pkg/dataplane/compiler_iface.go` (`stripUnmanagedInterfaces`) builds `InterfaceConfig{Name: <raw kernel name>, Unmanaged: true}` from kernel names, and `networkd.Apply` rendered it raw into the first-sorting `10-xpf-!x.network` whose body is the unmanaged always-down stanza (`ActivationPolicy=always-down`, `DHCP=no`). One host-netns netdev named `!x` (root/CAP_NET_ADMIN, or a host tool) would thus claim and down every interface on the appliance including `fxp0`, persistently across reboots. `SafeInterfaceName("!x")` was `true` on the base: `!` is one slot, control-free, and does not end in a backslash, so every existing predicate answered its own question truthfully and still passed the hazard — the same shape as the #10089 glob hole.

## Fix and scope boundary

`rendersafe.IsNegatedMatchPattern` reports exactly the leading-`!` fact (`strings.HasPrefix(name, "!")`; `!!x` is still one inverted test — the parser collapses the run, see #14701). It is deliberately separate from `RendersAsOnePattern`/`SafeInterfaceName`, exactly as the glob class is: `!eth0` *is* one pattern, so those predicates keep passing it and their exhaustive byte tests are untouched in scope (the embedded-byte test now says so explicitly). The four render belts each refuse after their existing glob check and cite `#15079`:

- `networkd.Apply` pre-`expected` belt: `ifc.Name` and (when non-empty) `ifc.OriginalName`. Because the refusal happens before `expected` is built, a stale poisoned `10-xpf-!x.*` unit from an earlier apply is swept like a deleted interface. An empty `OriginalName` remains "unset", never a refusal — the check reads `HasPrefix("") == false`.
- `daemon.writeLinkFile` (`[Match] OriginalName=`), which also covers `writeDeviceMapLinkFile` by delegation.
- `daemon.fixRethLinkFile` (direct RETH repair writer), on its existing warn-and-return fail-closed channel.

`[Link] Name=` targets stay literal on both the glob and negation counts — they are non-match syntax — and a `!` anywhere but the leading byte stays renderable (`eth0!`, `enp9s0!` controls in every new test). `SafeUnitToken` is untouched: it guards single-token slots (`VRF=`, `Address=`, …) that are not match lists and where a leading `!` carries no inversion semantics. The lenient compile scrub (`SafeInterfaceName`) is untouched for the same reason the glob class stays out of it (#10089's lane): a pre-gate tree carrying such a name is dropped only where it already was, and the render belt is the fail-closed backstop.

At commit time `ValidateInterfaceName` already refused `!` (not allowlisted), but only via the generic invalid-character message. It now has a dedicated leading-`!` branch, mirroring the leading-`-` (#9885) branch beside it, naming the inverted-match consequence and citing `#15079`. The bridge-domain validator was considered and deliberately NOT changed: it renders `Name=br-<name>`, so the value never begins with `!` and no inversion can occur (`ValidateBridgeDomainName("!x")` renders the literal device pattern `br-!x`); its existing refusals already cover every dangerous spelling for that sink.

The non-leading-`!` controls pass on the base too, proving they measure the belt and not a blanket `!` ban.
- **GREEN**: all `#15079` cells pass on this branch across `pkg/rendersafe`, `pkg/networkd`, `pkg/daemon`, `pkg/config`; `go vet` is clean on all four packages and the full `pkg/rendersafe` + `pkg/networkd` suites pass. Full daemon/config suite results are recorded in the PR.
- **Scope**: no behaviour change outside the cited mechanism — non-leading `!`, literal `[Link] Name=` targets, `SafeUnitToken` slots, and all previously accepted names render byte-identically (asserted by the sibling/control cells).
