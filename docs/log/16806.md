  - **Action**: Fix management-VRF control/fabric fence losing
    unit-spelled cluster interfaces (#16806, R3-A38-04, residual of
    #15944 H23-02). `mgmtVRFControlFabricInterfaces` in
    `pkg/daemon/mgmtvrf_routes.go` mapped the authored
    control/fabric reference with `config.LinuxIfName`, which only
    converts `/` to `-`: a committed `control-interface em0.0`
    stayed `em0.0`, never matched the `mgmtSet` keys (`em0`,
    `fxp0`, ...), and was silently skipped, so the probe returned
    `[]`. `applyMgmtVRFRoutesTo`
    (`pkg/daemon/daemon_flow.go:512-515`) thus fed
    `mgmtVRFControlFabricLinkIndexes` no links and built no
    control/fabric connected inventory, so the #11362 fence
    ("never cluster control/fabric connected-prefix routes,
    regardless of the classless trust override") had nothing to
    fence. Without the override the generic #11383 connected-subnet
    check still suppressed the route; with
    `XPF_DHCP_TRUST_CLASSLESS_OVERRIDE=1` it yields, so an fxp0
    DHCP option-121 route inside the control link's connected
    prefix (e.g. `10.77.0.42/32` inside em0's `10.99.0.0/24` /
    `10.77.0.0/24`) was installed in management table 999.
    Fix: resolve via `cfg.ResolveKernelIfName(name)` instead of
    `config.LinuxIfName(name)`, exactly as `transportVRFBinding`
    (`daemon_ha_comms_wiring.go`) already does since #15944 —
    `ResolveKernelIfName` collapses declared unit 0 to the bare
    kernel device (`em0.0` -> `em0`), handles slash names, VLAN
    netdevs and device-map aliases, and falls back to
    `LinuxIfName(ResolveReth(ref))` for unmodelled refs. No other
    site or behaviour changes; `LinuxIfName` had no other uses in
    the file (`config` import retained for the other symbols).
