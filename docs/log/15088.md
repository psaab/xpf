# Issue #15088 — userspace-dp: shared-owner EBUSY retry re-created a socket on an unmapped UMEM (A61-02)

- **Timestamp**: 2026-10-18
- **Action**: The EBUSY retry in `try_open_bind` re-created a
  `SharedOwner` socket on the same UMEM after libxdp 1.6.3 had unmapped
  that UMEM's only FILL/COMP ring mapping, so the retried "OK" binding
  wrote its fill ring into stale/aliased memory and never fed the kernel.
  Mechanism, verified against the pinned libxdp 1.6.3 sources
  (`xdp-tools` `lib/libxdp/xsk.c`, the version range enforced by
  `build_support/libversions.rs` `>= 1.6.3, < 1.7`):
  - `Umem::new` hands libxdp the Rust `Umem::fill`/`comp` boxes;
    `xsk_umem__create` saves them as the UMEM's `fill_save`/`comp_save`
    and mmaps the kernel FILL/COMP rings behind them — the UMEM's only
    such mapping.
  - Pre-fix, `SharedOwner` mapped to `XskCreateMode::SharedUmem` exactly
    like a secondary: fresh zeroed per-socket fill/comp boxes went to
    `xsk_socket__create_shared`. In `xsk_create_ctx` libxdp memcpy'd
    `fill_save`/`comp_save` into those boxes (pointers into the one
    mapping), and in `xsk_socket__create_opts` any post-ctx failure —
    canonically `bind()` returning `-EBUSY` from the kernel's deferred
    XSK pool release, the documented reason the 20 x 250 ms retry in
    `try_open_bind` exists — computed
    `unmap = (umem->fill_save != fill) == true` and `xsk_put_ctx`
    munmapped the UMEM's FILL and COMP mappings.
  - The retry allocated another fresh pair, re-copied the now-dangling
    `fill_save` pointers, and on success reported a bound zero-copy
    socket; `prime_fill_ring_offsets` then wrote fill descriptors
    through producer/ring pointers into unmapped (or re-aliased) memory.
  Fixed on both halves of the cited mechanism (fix direction (a) plus
  the no-retry half of (b); a full in-place UMEM rebuild inside
  `try_open_bind` is impossible — it receives only `&mut WorkerUmem`
  while the frame pool lives in the caller — and unnecessary, because
  the outer reconcile loop already rebuilds the UMEM wholesale):
  - `userspace-dp/csrc/xsk_bridge.c`: new
    `bridge_xsk_socket_create_shared_owner` passes `NULL, NULL` for
    fill/comp. libxdp then substitutes `fill_save`/`comp_save`, so a
    failed owner create takes the `unmap == false` path and the UMEM
    mapping survives. The #9726 capture seam now also records whether
    the intercepted shared create received NULL fill/comp
    (`bridge_xsk_captured_shared_fill_is_null`).
  - `userspace-dp/src/xsk_ffi.rs`: new `XskCreateMode::SharedOwnerUmem`
    and `create_xsk_binding_shared_owner(&mut Umem, …)`. The owner's
    `DeviceQueue` BORROWS the UMEM's ring boxes
    (`DeviceQueueRings::BorrowedUmem`, generalized from
    `BorrowedPrivateUmem`; `device_queue_rings_for_create` now decides
    by mode via `borrows_umem_rings()`), exactly like the private
    create, so the primed fill ring is the mapping the kernel reads and
    `xsk_socket__delete` (which unmaps through the ctx's ring pointers)
    remains the single unmap owner. NOT changed: the shared-secondary
    create still passes per-socket structs and owns libxdp's copies.
  - `userspace-dp/src/afxdp/bind.rs`: `SharedOwner` maps to
    `SharedOwnerUmem` and dispatches to the owner constructor; new
    `ebusy_retry_allowed` gates the EBUSY retry — never for the owner
    (a failed owner create fails the group bind closed; recovery is
    the reconcile loop's fresh `WorkerUmemPool` in
    `create_shared_binding_group`, then `fallback_shared_group_to_private`),
    unchanged for private and shared-secondary creates, whose failure
    paths do not unmap a mapping another socket depends on.
  - Known residual (pre-existing, unchanged): a shared-owner failure
    during `open_binding_worker_rings` flag/strategy fallback retries
    the owner create on the same UMEM — now safe because the
    NULL-fill/comp create no longer unmaps on failure — and a retry
    after a *successful* create's post-create failure (identity
    mismatch / non-zerocopy) still cannot happen: that path returns
    terminally, as before (#9904).
- **File(s)**: `userspace-dp/csrc/xsk_bridge.c`,
  `userspace-dp/src/xsk_ffi.rs`, `userspace-dp/src/xsk_ffi_tests.rs`,
  `userspace-dp/src/afxdp/bind.rs`,
  `userspace-dp/tests/shared_owner_ebusy_retry_15088.rs` (new),
  `docs/log/15088.md`
- **Validation**: RED on the pre-fix mechanism: with the production
  files reverted and only the new tests kept, the
  `shared_owner_ebusy_retry_15088` tripwire cannot pass (owner dispatch
  and role gate absent) and the unit cells fail to compile against the
  old single shared mode (`SharedOwnerUmem` / owner constructor /
  NULL-capture symbols do not exist) — the tests name the exact
  mechanism, not a proxy. GREEN after the fix:
  `cargo test --bins -- 15088` — 4 passed
  (`shared_owner_ebusy_is_never_retried_on_same_umem_15088`,
  `shared_owner_uses_owner_create_mode_15088`,
  `shared_owner_bridge_passes_null_fill_comp_15088`,
  `shared_owner_rings_borrow_umem_secondary_rings_owned_15088`);
  `cargo test --test shared_owner_ebusy_retry_15088
  --test bind_identity_verification_9904` — 3 passed;
  controls `private_constructor_rings_borrow_umem_ring_boxes` and
  `socket_create_passes_inhibit_prog_load_to_libxdp_9726` pass.
  A namespaced live-EBUSY test (issue's suggested M1→M2 contrast)
  requires a bound AF_XDP socket on hardware and is not hermetically
  runnable; the hermetic cells above pin every Rust/C decision the
  live path depends on (NULL hand-off, borrowed ownership, no-retry),
  and the live contrast remains a lab-verify item.
- **Risk**: Shared-owner sockets now borrow UMEM rings, so the
  established drop order (socket/`DeviceQueue` before `WorkerUmem`,
  already documented on `open_binding_worker_rings` and enforced by
  `BindingWorker` field order) is load-bearing for owners as it already
  was for private sockets. A transient owner EBUSY that the old code
  would have (corruptly) "recovered" from now fails the group bind and
  recovers via reconcile/private fallback — a delay, not a silent
  dead queue. Secondary and private behaviour is byte-identical.
