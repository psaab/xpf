# #9687 — IPsec teardown debt lost across an xpfd restart

- **Timestamp**: 2026-09-11
- **Action**: persist the swanctl loaded-connection set and the teardown debt, so a restarted daemon still terminates a removed connection's SA.
- **File(s)**: listed under Change.

## Defect

`prevConnNames` (the connection set swanctl last loaded) and `pendingTerminate` (the #6542 teardown debt) lived only in process memory, and xpfd builds a fresh `ipsec.Manager` on every start (`daemon_run_bringup.go`). A restart between one of these and its retry left the restarted daemon with no record of the departed connection:
- a failed `swanctl --terminate` (#6542);
- a failed reload that deferred a removal (#4898);
- a teardown still running.

strongSwan is a separate service, so the child SA survived and kept forwarding under a configuration nothing loads, and the first post-restart apply reported success.

## Change

- `pkg/ipsec/conn_state_9687.go` (new): `DefaultConnStatePath` (`/var/lib/xpf/ipsec-conn-state.json`), `connState`, `seedFromStateLocked`, `persistStateLocked`, and a 1 MiB-bounded `loadConnState`.
- `pkg/ipsec/manager.go`:
  - fields `statePath`, `stateSeeded` and `inflight`; `New()` sets `DefaultConnStatePath`;
  - `promoteConnNames` seeds once, counts its removals in flight and persists;
  - `recordTerminateDebt(removed, failed)` settles the in-flight removals, unions the failures and persists, on success too.
- Cells: `pkg/ipsec/conn_state_9687_test.go`.
- `pkg/ipsec/README.md`: a Gotchas bullet after #6542's.

## Design notes

- **Persist, not reconcile charon at start.** A start-time sweep of live SAs against the rendered set would need to know which connections xpf itself rendered, which is exactly the persisted set. Without it, the sweep would terminate SAs of connections xpf never owned.
- **In-flight counting.** A promotion's removed set is debt until its terminates settle, so a stop mid-teardown leaves the record. It is a per-name count rather than a set, because the commit path and the DHCP-rebind re-render can apply concurrently and carry the same name.
- **Failure posture.** A missing, unreadable or oversized file seeds nothing, with a warning unless it is missing; that is the pre-#9687 behaviour. A failed write is a warning and never fails the apply, since failing an IPsec apply over the restart case would trade a tunnel outage for it.
- **Nothing seeded can terminate a loaded connection.** Seeded names reach `swanctl --terminate` only when `--list-sas` reports them live and the new config does not load them, the filter `promoteConnNames` and `terminateRemovedConns` already apply.
- **The retry is reached.** `applyIPsecTracked` runs on every config apply, including one with no VPNs (`daemon_apply_routing.go`), so the first apply after a start retries.
- **The daemon suite writes nothing under `/var/lib/xpf`.** The two pkg/daemon tests that construct `ipsec.New()` inject `ipsecApply` and never reach `Manager.Apply`.
- **Not established (as in the issue):** how long charon keeps an SA whose connection was unloaded.
