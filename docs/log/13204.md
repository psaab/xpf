# #13204 — exclude warmup traffic from cold-path flooder progress

## Why

`cold-path-flooder` initialized its previous progress counters to zero but waited until one second after warmup to emit the first progress JSON. Since worker slots remained cumulative until final-summary processing, the first interval included warmup packets and reported approximately three times the actual PPS for a two-second warmup. Workers also returned on `total_deadline` before publishing their warmup baseline, so a zero-duration warmup-only run could include warmup traffic in its final totals. The stored shared `start_at` was not honored, allowing workers to transmit before the common measurement window.

## What

Workers now wait for the shared start time and publish their packet/batch warmup baseline before shutdown/deadline exits. Main waits until every worker has published its baseline, then subtracts that baseline from each cumulative progress snapshot before computing deltas and PPS. This keeps the first progress interval and later intervals in the run-phase window. Added regressions for warmup-adjusted first-tick PPS/deltas and baseline publication exactly at the deadline.

## Risk / residual

No live AF_PACKET transmission run was performed; validation is unit-test based. Progress does not emit until all workers have published their warmup baseline, so a delayed worker can postpone the first progress record; its elapsed interval remains measured from the common warmup end.
