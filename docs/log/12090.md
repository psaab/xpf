# #12090 — reject unbound filter spellings

- **Issue**: #12090 — interface and forwarding-options filter spellings could commit clean while no compiler/dataplane consumer used them.
- **Branch**: `fix/12090-silent-filter`
- **Worktree**: `/var/worktrees/12090-silent-filter`
- **Base**: `1c384b9a47ff7d6e567fa50632faa75c3995ae87`

## Why

The existing interface reader consumes a single-name `filter input|output` only below `unit <n> family inet|inet6`. Unit-level `filter`, `simple-filter` aliases, and `forwarding-options family inet|inet6 filter` were accepted by open-world AST subtrees but had no hook, so strict commit gave a false impression that the requested filter was active.

## What

- Extended the interface unsupported-stanza AST gate to reject every `filter` occurrence outside the existing typed family hook and every `simple-filter` occurrence under `interfaces`, including unit-level spellings. Existing #10293 family-level list/multi-value checks remain in place.
- Added a forwarding-options AST gate that rejects `filter` and `simple-filter` anywhere under that subtree. It handles both hierarchical and flat-set family AF tails, including the split `family inet` representation where the unsupported tail is packed into `Keys`.
- Kept tolerant load / peer-sync behavior non-bricking: interface cases use the existing lenient interface gate, and forwarding-options cases warn through a dedicated lenient option.
- Added a population test covering both AST shapes across interface, unit, family, and forwarding-options placements. The supported family `filter input|output` control must compile to its non-empty v4/v6 unit hook; all other tested placements must fail strict commit with an identifying #10293/#12090 diagnostic. Added a lenient forwarding-options warning control.
