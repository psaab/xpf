## Why

On the `defer_workers=true`, NOT-same-plan leg of `snapshot::apply`, the WG (`prune_wg_control_threads_for_snapshot`) and local GRE/IPIP (`prune_local_tunnel_sources_for_snapshot`) thread prunes ran *before* the fallible `replan_queues` binding-plan computation. When the candidate removed a live tunnel and its binding plan was refused (slot cap, wild ifindex, NAT-holder width), the handler restored only `guard.snapshot` and the status fields — but a prune stops, joins, and *removes* the thread-map entry (not a tombstone), so neither the tombstone-only liveness sweeps nor the rollback could resurrect the WG rekey/handshake thread or the local-origin TUN reader. The prior snapshot stayed nominally active while its tunnel threads were dead: an availability loss on a refused (fail-closed) apply.

## What

In `userspace-dp/src/server/handlers/snapshot.rs::apply`, compute the binding plan *before* any side-effecting prune. `replan_queues` is pure (candidate snapshot + worker count + existing bindings + arm flag), so hoisting it ahead of the prunes changes nothing on the success path; on `Err` the handler now returns before the snapshot swap and before either prune, making a refused apply fully side-effect-free — the same discipline the #5171 defer-integrity leg already follows. The successful defer path is unchanged: integrity validation, then replan, then the prunes (still against the candidate snapshot), then the snapshot swap and deferred spawn skip.

Added `apply_snapshot_defer_plan_refusal_keeps_live_tunnel_threads_14131` in `userspace-dp/src/server/tests.rs`: it stands up a live WG + GRE tunnel pair (real threads over TUN stand-ins), then applies a `defer_workers` candidate that removes both tunnels and adds a wild-ifindex (`70_000`) data interface. It asserts the apply is refused with `binding plan refused`, the prior snapshot/generation stays installed, and both thread entries remain live with their deliveries published.

## Validation

- New regression: `cargo test --manifest-path userspace-dp/Cargo.toml --bins -- apply_snapshot_defer_plan_refusal_keeps_live_tunnel_threads_14131` — RED with the handler fix stashed (fails at "refused apply must keep the WG thread live", i.e. prune-before-replan removed the entries), GREEN with the fix.
- Related set of 8 tests GREEN in one run: the new cell, `apply_snapshot_with_wild_ifindex_is_refused_without_install_9900`, the #5171 defer trio (`apply_snapshot_defer_workers_missing_map_pin_fails_closed_5171`, `apply_snapshot_defer_workers_forwarding_integrity_fails_closed_5171`, `apply_snapshot_defer_workers_valid_config_applies_without_spawning_5171`), `wg1866_disarmed_same_plan_apply_does_not_hold_wg_ports`, `wg1866_defer_prune_releases_port_and_sweep_does_not_resurrect`, and `gre1881_defer_prune_removes_only_stale_entries`. The replan success path is identical apart from reading `Some(&snapshot)` instead of the just-swapped `guard.snapshot`.

## Risk

Behavior delta only on the previously-broken refusal path: a refused defer apply now keeps the live tunnel threads it previously killed. No wire/protocol change. The same-plan legs never pruned before replan (they do not replan at all), so they are untouched.
