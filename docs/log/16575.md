# #16575: holder-less import reservation leaked when refused import meets accepted delete

- **Timestamp**: 2026-10-24
- **Action**: `delete_synced_session_gen_marked` (userspace-dp/src/afxdp/ha/session_import.rs) now, after a successful shared removal of a forward entry, releases the coordinator's import-time `Untracked` reservation via the new `release_unadopted_import_reservation_untracked` helper — `release_synced_source_nat_allocation_untracked` plus `release_synced_nat64_allocation_untracked_for_purge` against the same runtime view. Previously the import's `UpsertSynced` fan-out could be refused (repair debt, queue at 4096) while the peer delete's push was accepted before the worker reached the repair boundary; the worker then drained a `DeleteSynced` for a session it never adopted (no local entry, so `handle_delete_synced`'s alias-gated release never ran) and the `holders == 0` record survived for the life of the allocator — no sweep touches `Untracked` records and the #6979 F4 repair runs only on a refused delete push. The untracked release frees only `holders == 0` records (`drop_holder_locked` keeps any adopted record), so an adopted twin is freed exactly once by the last worker's own teardown. An actual free increments `tunnel_purge_reservations_released` so the tunnel purge, which runs the same untracked sweep right after this delete, keeps its #8138/#14961 count when its own attempt no-ops; the counter doc in session_manager.rs was updated to name this second source. No gate was weakened: the release is keyed on the removed forward entry's exact NAT decision and is a no-op for reverse entries, non-NAT decisions, and adopted reservations.
- **File(s)**: `userspace-dp/src/afxdp/ha/session_import.rs`, `userspace-dp/src/afxdp/coordinator/session_manager.rs`, `docs/log/16575.md`
- **Validation**: New tests in `rejected_mirror_reservation_10790_tests` (session_import.rs): `refused_import_then_accepted_delete_releases_untracked_snat_16575` and `refused_import_then_accepted_delete_releases_untracked_nat64_16575` (DEFECT cells: refused import via full 4096 queue, one slot freed so the delete is accepted, assert PORT_HELD=false / NAT64 active_flows 1→0, then drain + repair boundary and assert still free; both RED with the fix disabled — SNAT port held, NAT64 active_flows stayed 1 — GREEN with it), `refused_delete_still_frees_via_dropped_repair_16575` (Control A: refused delete still frees via #6979 F4), `accepted_import_then_accepted_delete_frees_via_worker_16575` (Control B: accepted delete leaves the adopted reservation for the worker drain), `adopted_two_workers_delete_frees_exactly_once_16575` (two worker bits survive the coordinator delete, mask 0b11, last release frees). Related suites re-run green: 16575 + 6979_f4 + 14961 + 6600 filters, 19 passed.
- **Residual**: Multi-worker production frequency still needs every worker's upsert refused and every delete accepted (per the source finding); the fix covers each worker's holder-less case independently because the untracked release is per-delete, not per-worker. The `tunnel_purge_reservations_released` counter now also counts holder-less frees from ordinary (non-purge) synced deletes — honest per its updated doc (a freed reservation is a freed reservation), but operators correlating it strictly with purge events should note the widened source.
