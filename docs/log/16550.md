# #16550: NAT64 `match source-address-name` strict gate rejected only undefined names, admitting IPv4-only closures

- **Timestamp**: 2026-10-24
- **Problem**: `validateNAT64ScopeStrict` rejected a literal IPv4
  `match source-address` ("NAT64 sources are IPv6", #15678) but for
  `match source-address-name` it checked only that the name existed in
  the address book. An IPv4-only address (`10.0.0.0/8`) or an all-IPv4
  address-set therefore committed clean, `buildNAT64Snapshots` shipped
  the IPv4 prefixes unpoisoned as the wire source constraint, and the
  Rust NAT64 matcher (which parses only IPv6 prefixes) matched no
  source for that rule-set — a green commit and an inert NAT64 scope,
  with possible fall-through to a later rule-set sharing the /96.
- **Fix**: In the name arm of `validateNAT64ScopeStrict`
  (`pkg/config/compiler_validate_strict_nat.go`), after the existing
  existence check, resolve the name's static closure and reject when
  it is proven to contain no IPv6 prefix. The new helper
  `nat64NameClosureNoIPv6` expands a single address via
  `UsableValues()` or a set via the existing `expandAddressSetLeaves`
  expander (the same static expander the other NAT strict gates use),
  and returns true only when the closure yields at least one usable
  value and every value parses as IPv4. A mixed v4+v6 set still
  commits (only its v6 members can match). Closures that are not
  statically decidable are not rejected: a direct dynamic-address
  feed binding (prefixes arrive via the live overlay, mirroring the
  `validateNATSourceAddressNameReferencesStrict` carve-out), a
  dns-name entry with no resolver snapshot yet (#15930 deliberately
  admits it; zero answers poison the closure fail-closed at the
  builder), wildcard keywords (already exempted, including the
  deliberately never-match `any4`), and dangling/tainted members
  (already poisoned fail-closed downstream). On the tolerant load /
  peer-sync path the new diagnostic downgrades to a warning via the
  existing `emit` helper (#1960), never bricking. No builder, wire,
  or Rust change.
- **File(s)**: `pkg/config/compiler_validate_strict_nat.go`,
  `pkg/config/nat64_name_family_16550_test.go` (new),
  `docs/log/16550.md`
- **Validation**: New tests in `nat64_name_family_16550_test.go`:
  `TestNAT64SourceAddressNameIPv4OnlyRejected16550` (v4 address,
  all-v4 set, and nested all-v4 set all reject with the #16550
  diagnostic, and the lenient path still compiles),
  `TestNAT64SourceAddressNameMixedSetCommits16550` (mixed v4+v6 set
  and a pure-IPv6 name commit),
  `TestNAT64SourceAddressNameFeedBindingAdmitted16550` (direct feed
  binding commits), and `TestNAT64NameClosureNoIPv6Unit16550`
  (helper verdicts incl. the not-statically-decidable dns case).
  RED evidence: disabling the new gate call makes the
  IPv4-only reject test fail; restored afterwards. Regression:
  `go test ./pkg/config/ -run '16550|NAT64|15930|15678'` passes,
  including the #15930 dns-name admission control.
- **Risk**: Commit-time validation only; no dataplane or wire change.
  A config that previously committed with an IPv4-only NAT64 source
  name now requires correction at strict commit (it never matched);
  on tolerant load it warns and the rule-set stays fail-closed
  exactly as before.
