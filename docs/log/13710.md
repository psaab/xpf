# #13710: retire stale reverse companions on synced NAT replacement

- **Timestamp**: 2026-10-15
- **Action**: Same-key peer-synced forward replacements now detect when a
  changed NAT decision derives a different reverse key. The importer includes
  the old reverse key in its tuple lease and tears down the old synthesized
  companion through the normal conditional delete path before releasing that
  lease. The guard checks reverse flag, inherited generation, zero reverse
  session ID, and forward-key backlink. Same-key/same-NAT refreshes leave the
  live companion untouched.
- **File(s)**: `userspace-dp/src/afxdp/ha/session_import.rs`,
  `userspace-dp/src/afxdp/ha_tests.rs`, this log.
- **Red-before**: The exact generation-1 NAT-A → generation-2 NAT-B regression
  failed when the old-companion teardown was disabled, at the assertion that
  `rev(A)` must be absent after replacement (0 passed, 1 failed). The fixture
  uses nonzero forward session IDs; synthesized reverse entries deliberately
  carry session ID zero and inherit the forward generation.
- **Green-after**: `cargo test --quiet --bin xpf-userspace-dp
  afxdp::ha::tests::` passed all 157 HA tests (0 failed; 7,905 filtered out),
  including the replacement/deletion regression and same-NAT refresh control.
- **Risk**: Old reverse cleanup uses the existing conditional shared-removal,
  conntrack/session-map teardown, and worker-delete fan-out while retaining the
  import's tuple lease. No wire format or NAT decision semantics changed.
