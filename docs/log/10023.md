# 10023 — Characterize rolling-cut TCP stall and stream starvation

## Scope and inputs

Issue #10023 asks where the primary-cut stall goes, why the secondary cut can
starve individual streams, and whether per-stream/sub-200-ms instruments change
the picture. This lane changes no forwarding or HA behavior. It analyzes the
retained Sep-13 #9486 rolling-cut records and runs the new sampler both without
a cut and during one lock-held secondary-node staged rolling cut.

The durable source records are under `docs/log/10023/raw/`; the accompanying
`SHA256SUMS` manifest covers every record. No new evidence is stored under the
review-process `docs/pr/` tree.

## Fine-grained instruments and safety

`scripts/cut_stall_sampler.sh` records:

- `iperf3 -P4 -b25M -i0.1 -J --json-stream --forceflush`, retaining the JSON
  `start` event and every 100-ms per-socket/SUM event;
- `ping -n -D -i0.1`, `ss -tin` snapshots keyed by source port, and a bounded
  `journalctl -f -u xpfd` recorder on each firewall;
- snaplen-96 client and firewall tcpdump files, with stderr and recorder status
  files retained separately; firewall AF_XDP captures may be header-only.

The sampler allocates `cut-stall-10023-<UTC>-<pid>-<random>` independently of
`--out`. Each VM refuses an existing remote run directory before `mkdir`; it
never recursively deletes a basename-derived path. It records the identity of
fw0, fw1, and the LAN host, checks `timeout` inside every VM, and records
start/end wall clock plus `/proc/uptime` for the deploy host, LAN host, and both
firewalls. The final `sampler complete` line is emitted only after all required
pulls, recorder statuses, non-empty data files, pcap headers, and stderr files
pass their gates. Status 124 is accepted only for intentionally time-bounded
`timeout` recorders; iperf, ping, and ss require status 0.

The analyzer accepts human-readable iperf records and JSONL. Human sender and
receiver completion rows are skipped as summaries, headerless bracket-prefixed
text is dispatched to the text parser, and only a final unterminated malformed
line is tolerated (`truncated_final_line`). JSON stream rows carry their event
index so SUM masking does not depend on equal per-socket timestamps. Ping loss
uses ICMP sequence gaps with interpolated epochs, and the CLI default matches
the sampler's 100-ms probe interval. `cut_budget` requires `armed` and reports
both `proc_to_armed` and `armed_to_helper` in addition to the existing phases.

## No-cut baseline

Command: `scripts/cut_stall_sampler.sh --duration 5 --interval 0.1
--parallel 4 --out /tmp/cut-stall-10023-baseline5`.

The run completed with `iperf.status=0`, `ping.status=0`, and `ss.status=0`.
The JSONL contains 50 interval events per stream and SUM. Every stream and SUM
row is non-zero, there are no retransmits or SUM-masked rows, and the analyzer
reports `masked_sec=0`, `sum_zero_sec=0`, and `max_loss=0.0`. The ping log has
48 replies, contiguous sequences 1..48, no qualifying gap, and 0% loss. The ss
recorder produced 35 samples. The client pcap is 304,420 bytes and contains
3,054 decoded packets; firewall pcaps are 24-byte headers with stderr proving
`0 packets received by filter`, the expected AF_XDP visibility limitation.

The exact source files are in `raw/baseline/`: JSONL, ping/ss records and
stderr, metadata, clock offsets, statuses, journals, pcaps, and the complete
client capture. Reproduction commands are:

```text
cd docs/log/10023/raw && sha256sum -c SHA256SUMS
scripts/cut_stall_analyze.py iperf --json docs/log/10023/raw/baseline/iperf.jsonl
```

## Lock-held instrumented secondary cut

The loss-cluster lock was acquired with `test/incus/with-cluster.sh` after
read-only health checks showed both daemons active, all three RGs ready, and
node0 primary/node1 secondary. Inside one lock cell, the sampler was started
for 60 seconds and, after an 8-second recorder warm-up, the staged rolling
command was run on node1:

```text
/usr/local/share/xpf/staged/xpfd upgrade --rolling
```

The driver exited 0 and logged `drain start`, `drain complete`, `STOPPED`,
`STARTED`, `COMMITTED`, re-sync, and election rejoin. The sampler also exited
0 and logged `sampler complete`; its output is retained in `raw/cut/`.

The iperf JSON `start` event records the actual origin as
`Thu, 17 Sep 2026 22:46:08 GMT` (`timesecs=1789685168`,
`timemillisecs=1789685168226`). It contains 600 100-ms interval events for
all four streams and SUM:

| stream | interval rows | zero rows | minimum bitrate | total retransmits |
|---|---:|---:|---:|---:|
| 5 | 600 | 0 | 20.890 Mbit/s | 1 |
| 7 | 600 | 0 | 20.890 Mbit/s | 0 |
| 9 | 600 | 0 | 20.890 Mbit/s | 0 |
| 11 | 600 | 0 | 20.891 Mbit/s | 0 |
| SUM | 600 | 0 | — | — |

The analyzer reports no stream zero gap, no cwnd-floor window, no SUM masking,
and `sum_zero_sec=0`. The matching ping has 571 replies, contiguous sequences
1..571, no qualifying gap, and `max_loss=0.0`. `ss` captured 438 samples; each
iperf source port (52586, 52592, 52602, and 52612) appears in all 438 samples
as an established connection. The client pcap is 3,172,200 bytes with 31,352
decoded packets. Both firewall pcaps are intentionally header-only; their
stderr records the AF_XDP filter result. Recorder statuses are iperf/ping/ss
`0` and all five time-bounded journal/tcpdump recorders `124` (expected
`timeout` completion), and every required artifact passed the gate.

The cut driver's host timestamps were `cut_start=2026-09-17T22:46:12.949197045Z`
and `cut_end=2026-09-17T22:46:22.569570316Z`. `raw/cut/clock-offsets.txt`
contains host-before/after brackets around every remote wall-clock/uptime read,
for both sampler boundaries. At sampler start, deploy-host-minus-fw1 is
bounded by 54.722542..55.135825 seconds (midpoint 54.929184 s); at the end it
is bounded by 54.741208..55.128392 seconds (midpoint 54.934800 s). The LAN

-0.141861..+0.175789 s at end. These bounds, rather than an unsupported point

The fw1 journal shows forced-secondary at local `22:45:18.236Z`, shutdown

## Historical per-stream result

Re-running the analyzer on `raw/historical/iperf.log` reproduces the retained
#9486 result: 271 SUM intervals and four streams in one surviving TCP session.
The final unterminated partial row is reported as `truncated_final_line`; it is
not treated as a completed interval.

| stream | zero-throughput interval | zero time | cwnd-floor interval | retransmits |
|---|---:|---:|---:|---:|
| 5 | t=39..54 | 15 s | t=39..54 (15 intervals) | 730 |
| 7 | t=12..42 | 30 s | t=12..42 (30 intervals) | 295 |
| 9 | t=12..42 | 30 s | t=12..42 (30 intervals) | 326 |
| 11 | t=12..42 | 30 s | t=12..42 (30 intervals) | 364 |

Streams 7/9/11 collapsed after t=11..12 and stayed at 0 bits/sec with
`snd_cwnd=1.41 KiB`; stream 5 continued alone through t=38, then recovered
at t=54..55 with a retransmit burst. The SUM-only view hides the asymmetry:
`any_stream_zero_sec=42`, `masked_sec=39`, `sum_zero_sec=3`, and
`stream_zero_rows=105`. The historical ping has 1,321 replies; its only
cut-sized sequence gap is 190→193 (two missing probes over 0.623602867 s),
with no gap over one second.

The 3-second SUM outage is the overlap of t=12..42 for streams 7/9/11 and
t=39..54 for stream 5: only t=39..42 is an all-flow zero window. It is not
valid to call either stream window an aggregate outage.

## Historical timing limits and budget reconciliation

The old `clock-skew.log` measured deploy-host↔fw0/fw1 offsets only. The LAN
VM clock was not measured, and the old timeline used `19:51:13.215` as an
iperf origin even though that value was the first ping reply epoch; ping and
iperf were launched by separate Incus commands. Therefore the historical
secondary ordering (`1.46 s after forced-secondary`, `1.78 s before shutdown`)
and the historical primary ordering (`SUM` ending about 0.9 s after STOP) are
**CONDITIONAL / UNRESOLVED**, not corrected causal measurements. The new cut
records the missing host/LAN/node calibration and actual iperf JSON start time,
but its healthy result cannot retroactively prove a cause for the Sep-13
starvation.

The historical primary journal excerpt in `raw/historical/fw0-cut-window.log`
pins the marker definitions:

- `:47` has `signal received` at `19:49:49.302Z`;
- `:91` has `starting xpf daemon` at `19:49:52.205Z`;
- `:112` has `cluster manager initialized` at `19:49:52.301Z` and `:114` has
  `vrrp: manager started` at `19:49:52.302Z`;
- `:118` has `dataplane armed` at `19:49:54.054Z`;
- `:198` and `:199` have helper connected/started at `19:49:54.683Z` and
  `19:49:54.840Z`;
- `:454` has sync readiness at `19:49:57.211Z`.

Consequently, the golden test's `stop_to_proc=2.903 s` uses the process-start
marker `52.205−49.302`, while the report's `STOP→new manager=3.000 s` uses the
manager/systemd initialization marker `52.302−49.302`. They are different
milestones, not contradictory measurements. With `armed` required, the pinned
primary phases are:

| phase | seconds |
|---|---:|
| drain→STOP | 2.955 |
| STOP→process-start marker | 2.903 |
| process-start→armed | 1.849 |
| armed→helper-start | 0.786 |
| process-start→helper-start | 2.635 |
| helper-start→sync-ready | 2.371 |
| STOP→sync-ready | 7.909 |

The secondary source markers and exact records are in
`raw/historical/fw1-cut-window.log` (`forced secondary :4`, shutdown `:24`,
process start `:73`, manager initialization `:94`, armed `:100`, helper
`:180-181`, and sync-ready `:432`).

## Characterization and limits

| candidate | evidence | disposition |
|---|---|---|
| Drain/ownership transition | The conditional historical proxy alignment places stream zeros after forced-secondary and before shutdown; new instrumented secondary cut stayed healthy. | Candidate first transition; historical packet-level cause remains unproven. |
| Daemon restart | Historical STOP→process/manager markers are 2.903/3.000 s; new cut records STOPPED/STARTED and full lifecycle. | Real budget, but not proof that restart caused historical starvation. |
| Helper re-resolution/sync | Historical helper/sync markers are 5.38..5.45/7.90..7.91 s; the conditional proxy alignment places historical zeros earlier. | Cannot establish historical start ordering; may affect recovery. |
| VRRP/VIP | Historical ICMP gap is 0.624 s; new cut has no qualifying gap. | The old 60-ms bar was not met or isolated from restart. |
| TCP loss/RTO | Historical zero rows, cwnd floor, and retransmit storms; new client pcap/ss cut run had no zero rows or ICMP loss, with one iperf retransmit on stream 5. | TCP recovery is the observed historical symptom; packet-level blackholing is not proven. |
| Flow/session asymmetry | Historical streams 7/9/11 strand while stream 5 continues; new cut records all four ports continuously. | Defect class remains tracked by #10261; root cause needs more reproductions. |


## Restated acceptance bar

1. **Hard floor:** one established TCP session remains alive across a rolling
   cut with no reset, stream death, or iperf error. The instrumented cut met
   this floor.
2. **Per-stream continuity:** retain 100-ms per-stream intervals and reject any
   multi-second zero-throughput/cwnd-floor window. The instrumented cut had
   600 rows per stream, zero zero-rows, and no cwnd-floor window; the historical
   campaign fails this bar and remains the characterization evidence.
3. **Cut budget:** report forced-secondary→STOP, STOP→process, process→armed,
   armed→helper, helper→sync-ready separately. Both historical and new cut
   records pin these markers. A 60-ms figure may describe a pure VRRP handoff;
   it is not a daemon-restart budget without packet and lifecycle separation.

Follow-up #10261 tracks the historical per-flow defect class with conditional
clock attribution. It must not be conflated with closed #6889's config-ownership
gate correction. The raw source records, exact analyzer commands, and checksum
manifest make both the historical failure and the healthy finer-instrument cut
independently reproducible.
