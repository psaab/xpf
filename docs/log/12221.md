# Issue #12221 — validate shadowed predefined application-set members

## Why

With AppID disabled, the strict application-spec walk visited only user-defined application-sets. A policy referencing the predefined `junos-sip` bundle therefore skipped a malformed user application shadowing its `junos-sip-tcp` member. Commit succeeded even though the userspace resolver would later encounter an unrepresentable port specification.

## What

The strict walk now expands referenced predefined application-sets as well as user-defined sets, collecting only expanded members that are user-defined applications. For the predefined-set fallback it preserves runtime application-before-predefined-set precedence, after checking user-defined application-sets and user applications. The existing fallback still validates direct user members when expansion encounters a dangling or over-nested member. Regression tests cover AppID-off rejection naming `junos-sip-tcp`, the AppID-on control, and user-application precedence over a predefined set.

## Risk / residual

The change is limited to commit-time strict application-spec collection; no dataplane lowering or predefined application behavior changed. Commit now rejects malformed specs on user-defined members shadowing members of a referenced predefined bundle (including invalid ports, protocols, ICMP fields, and inactivity timeouts), even where a runtime lowering path may fall back rather than fail closed. The tolerant-load path continues to downgrade application-spec errors to warnings, so existing malformed configs remain loadable. No live cluster or apply path was exercised.

## Follow-up — PARENT-TO-FILE

**PARENT-TO-FILE (F2; not filed by this change):** reject a policy or NAT reference to a predefined application-set whose expansion errors, or extend the #2217 strict application-set-member gate to cover predefined bundles. That gate currently iterates only user-defined sets, and `validatePolicyMatchApplicationsStrict` returns nil when expansion fails. Consequently a predefined-bundle expansion error can pass commit with an empty strict application set, then fail closed when the runtime expands the reference. Verdict probes P4a/P4b demonstrated this with a user-set chain nested at the maximum valid depth whose expansion overflows when reached through `junos-sip`; both the valid-leaf and malformed-leaf variants commit, while runtime lowering rejects the policy. This predates #12221 and is not made worse by it, but the existing dangling-member rationale in the fallback applies only to user sets because #2217 validates those expansions.
