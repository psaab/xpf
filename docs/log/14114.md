# #14114 - NAT64 non-first fragments dropped on slow path

- **Timestamp**: 2026-10-16
- **Action**: `build_nat64_l3_packet_for_slow_path` now branches on
  `is_non_first_fragment`: non-first fragments take new preserve-TTL
  L3-only twins (`write_v6_to_v4_nonfirst_into_preserve_ttl` /
  `write_v4_to_v6_nonfirst_into_preserve_ttl` in `nat64.rs`, sharing the
  existing translators via a `preserve_ttl` flag) and return before the
  L4 port rewrite, so payload bytes are never rewritten as ports. Whole
  packets keep the existing preserve-TTL path byte-for-byte. Reachable
  when a first fragment commits ForwardCandidate (installing the
  fragment association / session) and its tail is adjudicated NoRoute,
  LocalDelivery, or MissingNeighbor — all slow-path eligible — so the
  tail reaches the builder with the recorded NAT64 decision; previously
  the whole-packet translators returned `None` and the tail dropped as
  `nat64_slow_path_prepare_failed`. ICMP fragments and missing reverse
  metadata still fail closed.
- **Validation**: New regression
  `nat64_nonfirst_no_route_reinjects_after_l3_translation_14114` drives
  the production slow-path reinjector in both directions (translated
  addresses/idents/offset, preserved Hop Limit/TTL, verbatim payload,
  fail-closed missing-reverse control): RED on pristine master
  (panics at the forward delegation assertion), GREEN with the fix.
  All 288 `nat64_` tests pass, including the #11066 NoRoute sibling and
  the #5146/#9957 fast-path fragment tests.
- **Risk**: Slow-path-only; fast-path fragment translation untouched.
  Tails without a recorded NAT64 decision still drop fail-closed.
