# Issue #18821: flush Stage 11 filter counters before reading

## Why

Commit `780e97f955` (#14932) made test builds use the same coalesced filter-counter recording as production. The Stage 11 local-IKE regression reads its packet counter before flushing the current thread's pending record, so it can observe zero even though the input-filter evaluator recorded the packet.

## What

Insert `crate::filter::flush_recorded_filter_counters();` immediately before the packet-counter assertion in `stage11_local_ike_passthrough_honors_ingress_input_filter_13637`. The existing packet, forwarding, and session assertions remain unchanged.

## Validation

- Baseline RED: `CARGO_TARGET_DIR=/var/worktrees/.cache/cargo-18821 cargo test --manifest-path userspace-dp/Cargo.toml --bin xpf-userspace-dp afxdp::tests_embedded_poll_filter::stage11_local_ike_passthrough_honors_ingress_input_filter_13637 -- --exact --test-threads=1` failed at the packet-counter assertion (`left: 0`, `right: 1`).
- With the flush: the same named-cell command passed (`1 passed`).
- Mutant proof: removing the flush made the named cell fail at the same assertion (`left: 0`, `right: 1`); restoring it returned the cell to `1 passed`.
- Neighbor module: `CARGO_TARGET_DIR=/var/worktrees/.cache/cargo-18821 cargo test --manifest-path userspace-dp/Cargo.toml --bin xpf-userspace-dp afxdp::tests_embedded_poll_filter -- --test-threads=1` passed (`142 passed`, `0 failed`).

## Risk

Test-only counter visibility change; production behavior and the test's existing expected outcomes are unchanged. Flushing before the read ensures a zero remains meaningful rather than hiding an unflushed recorded packet.
