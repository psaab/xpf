# Issue #12297 — bind tagged management VLAN devices to vrf-mgmt

## Why

Management VRF membership covered configured parent names only. A tagged unit such as `fxp0.100` is a separate kernel link, so it remained in the default VRF: the published management set omitted it, `BindInterfaceToVRF` bound only the named link, and its networkd model had no `VRFName`.

## What

- `managementVRFIfaceSet` includes tagged-unit Linux device keys for management
  parents while preserving base keys and excluding non-management VLANs.
- `BindInterfaceToVRF` binds VLAN descendants of a management parent, avoids
  redundant master changes, and returns link-list/bind failures to the
  authoritative post-networkd error path.
- Networkd models for management VLAN parents and children carry
  `VRFName=vrf-mgmt` without dropping existing interface controls, descriptions,
  unit MTU, or VRRP address preservation.
- The authoritative rebind skips only a confirmed missing link for a configured
  management VLAN unit that was not materialized (for example, an unzoned
  parent); base-interface and other lookup/bind failures remain commit-failing.
- Regression coverage pins the model fields, strict acceptance and successful
  post-networkd rebind of an unzoned management VLAN, recursive binding,
  non-VLAN child exclusion, and idempotence.

- GREEN: `TestManagementVRFVLANUnits12297`, `TestManagementVRFVLANNetworkdModels12297`, and `TestBindManagementVLANDescendants12297` passed. The routing test also verifies nested VLAN traversal, non-VLAN exclusion, and no repeated `LinkSetMaster` calls; link-list failure propagation is covered.

## Risk

The management rebind enumerates links to find VLAN descendants. Enumeration
and child-binding failures remain commit-failing. A configured tagged
management unit with no kernel device (such as an unzoned parent) is not bound
until it is materialized; only a confirmed not-found for that unit is skipped.
The pre-networkd bind remains best-effort. No live-cluster mutation was
performed.
