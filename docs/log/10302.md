# 10302 — Armed transit forward fence

## Boundary

Issue #10302 reported that a configured-but-unzoned interface or a device-map
leave-alone NIC remained L3-up and could forward kernel transit while the
userspace dataplane was armed. The fix keeps unarmed transit unchanged, retains
a forward default DROP while armed, and admits only provenance-bearing runtime
paths.

## Change

The armed gate now renders the same inet+bridge forward table as policy DROP
plus explicit ingress ACCEPT pinholes. Pinholes come from runtime-tracked XDP
links whose bpf-link ifindex still matches the live netlink interface, plus the
daemon-owned `xpf-usp1` delegated TUN outlet. `xpf-usp0` is deliberately not a
pinhole: it is the LocalDelivery/gated-only outlet and no FORWARD flow was found
for it. `xpf-usp1` is a documented residual: it multiplexes kernel-XFRM / slow-
path reinjection with destination-judged delegated traffic, which are
indistinguishable at the FORWARD hook by iifname today. The kernel's NO-accept
contract for xpf-usp1 is INPUT/delivery-scoped; the armed FORWARD pinhole
preserves the pre-existing delegated behavior while the fence closes unzoned
and leave-alone physical interfaces. A follow-up will add an explicit mark-based
demux for xpf-usp1.

The dataplane owns an XDP read lease across snapshot, fence installation, and
transit-open sysctl actuation; attach/detach writers hold the corresponding
write lease across their kernel transition. Leave-alone/unzoned devices,
unrelated host XDP programs, xpf-usp0, and direct xfrmi ingress remain outside
the allowlist. An all-unresolved XDP census or kernel-list error leaves the gate
closed, and any failed reassert restores the unconditional barrier before
writing zero. A fatal fence-install error keeps both sysctls at zero; a
bridge-only unsupported result is treated as degraded success when the inet
fence installed.
Closing paths restore the unconditional barrier before writing zero.

### Concrete ingress evidence

- Direct route-based IPsec plaintext is delivered by the kernel XFRM stack on
the xfrmi netdev and forwarded without zone policy (`pkg/config/compiler_ipsec_plaintext_warn.go:8-18,102-109`). It is therefore not admitted by an xfrm name in the fence.
- LAN-to-xfrmi egress has no AF_XDP binding and reaches the kernel XFRM stack
through slow-path reinjection (`userspace-dp/src/afxdp/neighbor_dispatch.rs:377-380`). The reinject primitive sends host-authorized LocalDelivery to
`xpf-usp0`, but all unfiltered IPsec/NoRoute/MissingNeighbor/ForwardCandidate
classes to `xpf-usp1` (`userspace-dp/src/afxdp/tx/dispatch/slow_path.rs:150-174,279-295,402-410`; `userspace-dp/src/afxdp/poll_stages.rs:1400-1424`).
- The slow-path source documents `xpf-usp0` as adjudicated-only and
`xpf-usp1` as the delegated outlet with no kernel accept (`userspace-dp/src/afxdp/mod.rs:504-514`; `userspace-dp/src/slowpath.rs:400-406,757-762`). This proves the iifname residual and why xpf-usp1 is the narrow concrete exception.
- SNAT frames passed to the kernel retain the runtime XDP ingress identity; the
SNAT reverse-session publication and `accept_local` requirement are documented
at `userspace-dp/src/bpf_map_tests.rs:1321-1329` and
`pkg/daemon/daemon_run_bringup.go:675-677`. Runtime XDP ifindex pinholes preserve
that path without admitting unrelated host interfaces.
