# Issue #13308: Export SNMP trap delivery telemetry

- Why: The asynchronous trap worker counted drops internally but exposed no accessor and did not count successful sends. As a result, daemon/API consumers and monitoring could not distinguish successful notification delivery from queue or transport failures.
- What: Added atomic submitted/sent counters and `Agent.TrapStats()`, incrementing submissions at enqueue and successful sends only after sender success. The daemon exports `xpf_snmp_traps_enqueued_total`, `xpf_snmp_traps_sent_total`, and `xpf_snmp_traps_dropped_total`; retired agent counters are accumulated across SNMP disable/re-enable and VRF-triggered replacement so Prometheus counters do not reset during process lifetime.
- Validation: The SNMP regression was RED on pristine `origin/master` (compile failure: `Agent.TrapStats` undefined), then GREEN with the fix. `go test ./pkg/snmp/... -count=1` and `go test ./pkg/api/... -count=1` passed; the focused daemon SNMP reconciliation tests passed; `go vet ./pkg/snmp/... ./pkg/api/... ./pkg/daemon/...` and `go build ./...` passed. The combined affected-module test command timed out after 600s after reporting SNMP and API passed; no daemon-package result was returned. `gofmt -l` reported no changed Go files.
- Risk: Metrics are process-lifetime counters and reset on daemon restart, consistent with Prometheus counter semantics. A temporarily in-flight send is reflected after the worker records its delivery/drop outcome.
