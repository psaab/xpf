# #16762 — A term's route-filters render as one first-match FRR prefix-list instead of Junos longest-match

- **Timestamp**: 2026-10-25
  - **Action**: A term's route-filters rendered as one first-match FRR
    prefix-list in authoring order (walkup/OR semantics), so
    `192.168.0.0/16 orlonger` + `192.168.100.0/24 exact` admitted
    192.168.100.128/25 even though Junos' default longest-match selects
    the /24 exact filter, fails it for /25, and stops (xpf does not
    model `walkup`). Fix in `pkg/frr`: the single per-entry permit
    derivation (`renderRouteFilterEntry`'s ge/le and skip logic) was
    factored into `routeFilterDerivation16762.emit` so the term layout
    and the historical seam render the very same permit; the new
    `renderRouteFilterListGroup` then, per term and family, sorts the
    renderable permits by descending base-prefix length (stable) and
    interposes `deny P le <family-max>` after each distinct prefix P
    that another renderable filter's base CONTAINS — a route under P
    whose match type failed first-matches the deny and stops instead
    of falling through to the broader permit. Entries are re-sequenced
    from seq 5 within their group. A stop is interposed only on true
    containment. The initial #16762 implementation nevertheless sorted
    and re-sequenced every group, so unequal-length disjoint lists did
    not actually preserve their historical bytes; #17824 restores
    authored order and original sequence slots when no strict
    containment exists. In the final renderer, single, disjoint, and
    same-base lists (including hierarchical `from` condition copies)
    render byte-identically, as the acceptance requires; the family
    root never gets a stop. The RIP per-group path (#16625) is unchanged:
    it composes its own ordered permit/deny list across terms from
    per-term entry texts and already reproduces first-terminal-wins
    ordering there.
