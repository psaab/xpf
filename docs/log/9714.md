## Re-verified at base (before any change)
- **Install direction: already closed by #9678** (PR #9764, merged at 3dd5064fe).
  `SessionDomain::upsert_synced_session` returns `Applied` before the NAT reservation, the shared publish and the
  worker fan-out when a peer upsert (`entry.origin.is_peer_synced()`) would replace a shared entry with a local origin
  while `!synced_entry_allows_local_replace(ha_state, owner_rg_id, now_secs)`. No #9714 change is needed there.
- **Delete direction: open.** `SessionDomain::delete_synced_session_gen` (userspace-dp/src/afxdp/ha/session_import.rs)
  checks only generation recency, then removes the steering row
  (`delete_session_map_entry_for_removed_session`), the `dnat_table` row (`delete_dnat_table_entry`) and the shared
  forward and reverse rows (`remove_shared_session`), then pushes `DeleteSynced` for the key and its reverse to every
  worker. The worker's #9048 refusal (`handle_delete_synced`) protects only the owning worker's local-origin entry; the
  sibling replicas are `WorkerLocalImport`, which `is_peer_synced()` counts as peer-synced, so they are dropped.
- **Why a refusal cannot simply go into the helper's delete arm.** The sync_session `delete` verb
  (server/handlers/sync_session.rs) serves two populations with identical requests:
  1. peer HA deletes: `pkg/cluster` `deleteClusterSyncedV4/V6` -> `DeleteWithCompanionsV4(key, DeleteReasonClusterStale)`;
  2. local authoritative deletes: `Manager.DeleteSession/V6`, reached from the CLI/gRPC session clear
     (pkg/grpcapi/server_sessions.go), session-store GC and policy revocation (pkg/dataplane/session_store.go) and
     daemon_dp_live.go.
  Go discards the reason before the dataplane call: `DeleteBatchKnownV4(entries, _ DeleteReason)`. `DataPlane`
  (pkg/dataplane/dataplane.go) exposes only `DeleteSession(key)` / `BatchDeleteSessions(keys)` (15 files implement
  `DeleteSession`, most of them test doubles). `SessionSyncRequest` (Go protocol_ha.go, Rust protocol/control.rs)
  has no origin or reason field. A helper-side refusal keyed on origin and RG state alone would therefore also
  refuse an operator `clear security flow session` for a local session on the primary.

### F5 shape: capability gate, DROP rather than journal

The reviewer's fix reads "suppress/journal outgoing deletes to peers that do not
advertise it". Journal is a trap, established by reading rather than inferred:
the delete journal is bounded at 10000 (`sync.go:1560`); an incapable peer never
flushes it, so overflow is certain on a busy node; `journalDelete` then evicts and
arms `forceResync` (`sync_conn_write.go:166`), consumed on the bulk send path

`reconcileStaleSessions` (`sync.go:1884`) deletes every session absent from the
received set, unmarked on an old peer. Suppressing individual deletes to protect
an old peer therefore escalates into a whole-set teardown of exactly the live
local sessions being protected. Dropping instead fails toward KEEPING sessions,
the direction-of-error rule this codebase already states for deletes. The
capability bit, counter and alarm all still land. Reported to the lead, since the
suppress-vs-document ruling predated this.

`IsPrimaryForRGFn` reports only the LOCAL node, and no peer-is-also-primary
signal can be reliable, since a split is definitionally the state where the two
nodes cannot see each other's truth. The gate is unavoidably coarse.
