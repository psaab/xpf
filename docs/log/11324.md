# Issue #11324 — FBF reverse replies and reply-ingress routing

## Root cause

Reverse companions preserve the forward ingress's native routing-domain identity, but route revalidation derived the desired native identity from the reply packet's domain and ingress. A cross-domain reply therefore looked like a route-table transition on every hit. Separately, an inbound service's first reply could match a `then routing-instance` term on its own ingress, but the route transition was treated like a forward hit: discard the packet and tear down both session halves.

## Fix

Route revalidation now receives the hit direction. Reverse native fallback uses
the canonical reverse key's forward-stamped routing domain (or the stored table
identity when no local entry exists), not the reply arrival domain. A matching
reply-ingress PBR term still resolves in its explicit table, but the route and
table identity update the reverse companion and current packet only after the
ordinary input-filter verdict accepts. This preserves later static discard
revalidation instead of letting a route refresh mark a denied flow Fresh.
Forward route transitions retain their pair-revocation behavior.

The old #10467 NAT-alias regression now expects reverse steering without
revocation and checks the reverse entry's stored route and fresh filter stamp.
Added a cross-domain native-identity cell, a poll-path first-reply regression
that verifies the blue-table egress and survival of both session halves, and a
PBR-to-static-discard transition regression that pins the filter verdict.
