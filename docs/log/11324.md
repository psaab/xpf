# Issue #11324 — FBF reverse replies and reply-ingress routing

## Root cause

Reverse companions preserve the forward ingress's native routing-domain identity, but route revalidation derived the desired native identity from the reply packet's domain and ingress. A cross-domain reply therefore looked like a route-table transition on every hit. Separately, an inbound service's first reply could match a `then routing-instance` term on its own ingress, but the route transition was treated like a forward hit: discard the packet and tear down both session halves.

## Fix

Route revalidation now receives the hit direction. Reverse native fallback uses the canonical reverse key's forward-stamped routing domain (or the stored table identity when no local entry exists), not the reply arrival domain. A matching reply-ingress PBR term still resolves in its explicit table, but the resulting route and table identity update only the reverse companion and current packet. Forward route transitions retain their pair-revocation behavior.

The old #10467 NAT-alias regression now expects reverse steering without revocation and checks the reverse entry's stored route and fresh filter stamp. Added a cross-domain native-identity cell and a poll-path first-reply regression that verifies the blue-table egress and survival of both session halves.

## Validation

- On base commit `b745069`, a temporary poll-path reproducer confirmed that a source-based `then routing-instance blue` first reply removed the reverse companion, queued its key for teardown, and incremented the revocation counter. The temporary reproducer was removed after the run.
- On base commit `b745069`, the original #10467 NAT-alias test passed while expecting the reverse companion to be revoked, confirming the testability trap.
