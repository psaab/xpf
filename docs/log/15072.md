# #15072 — cross-family DDNS sibling proof keys on FQDN only (A40-01 residual)

## Why

A different LAN client could attach an AAAA (or A) to a name xpf
published for another client in the other family: the sibling proof
keyed on FQDN only, so any LAN DHCP client could plant its address
in the other family at an internal name owned for a single-family
host (e.g. a v4-only NAS/printer); dual-stack resolvers prefer
AAAA, enabling redirection.

The issue was validated at research base `27b8cba22d`, before
#14995 merged. On current `origin/master` (`323e8a48a0`) most of
the cited mechanism is already fixed by #14995 / PR #15340
(`909e852614`): the store is demoted to a candidate source, a wire
`Used(sibling-DHCID)` proof is required before any guard downgrade,
device-canonicalised DHCIDs, and foreign-claim regressions exist
for `replace-owned` and `skip-existing`.

Residual on current master, verified by reading the anchored code:

- `crossTypeSiblingOwned` (`pkg/ddns/manager.go`) still returned
  ANY opposite-family row at the same canonical FQDN, same scope
  modulo family, and same backend endpoint, regardless of client
  identity — its own doc comment claimed a same-device filter the
  code deliberately omitted. `upsertLocked` therefore still
  stamped `SiblingFamilyOwned=true` + `SiblingClientID` for a
  foreign claimant. The RFC 2136 backend happened to be safe
  because it ignores the flag and re-checks `sameDeviceClient`
  inside `siblingDHCIDRR`, but the manager contract itself was
  still "FQDN(+scope/endpoint) proves sibling" — any present or
  future consumer trusting the flag alone reopens A40-01.
- The RFC 2136 `siblingFamilyOwned` field was dead (set, never
  read after #14995).
- No `strict-fail` foreign-sibling cell existed, and the mirrored
  skip/strict cells the issue's acceptance requires ("refused
  under all three policies") were not covered.

## What

- `pkg/ddns/manager.go` (`crossTypeSiblingOwned`): add the
  client binding the issue directs — a candidate row must satisfy
  `sameDeviceClient(owned.ClientID, r.ClientID)` (verbatim-equal
  identity, or a MAC-based DUID-LL/LLT pairing with the v4
  Ethernet client-id/hwaddr via `pairedIdentityKey`) in addition
  to canonical FQDN + same scope modulo family + same
  `BackendFingerprint`. An unrelated-DUID v6 lease (or unrelated
  v4 client-id) at an xpf-owned name now yields NO sibling
  candidate: neither flag is stamped and every name-level/DHCID
  guard stays in force. Client identity is still not wire
  authorization — the backend's `proveSiblingDHCID` proof is
  unchanged and still required before any downgrade.
- `pkg/ddns/backend_rfc2136.go`: document that the retained
  `siblingFamilyOwned` mirror is never consulted for
  authorization (proof is `SiblingClientID`/`PairedClientID` +
  wire DHCID only).

NOT changed: wire proof, DHCID canonicalisation, delete paths,
`dhcidSharedWithOther`/`dhcidStillWanted`, Surface A, and the
non-RFC2136 backends (production lease DDNS wires only RFC 2136
via `NewProductionManager`; the HTTP backends are Surface-A
self-owned publishes and ignore the sibling signal on upsert).
Opaque cross-family pairings still fail closed, as after #14995.

## Validation

- RED on current master (fix stashed, test file present):
  `TestCrossFamilySiblingBindsClientIdentity15072` FAILS —
  "unrelated-DUID row returned as sibling (ClientID=
  "cid:01000000000001"); sibling proof must bind to the client".
  The all-policy wire cells already passed pre-fix (the #14995
  wire proof held them) — they are the acceptance lock, not the
  RED driver; the binding cell is.
- GREEN after the fix: `TestCrossFamilySiblingBindsClientIdentity15072`,
  `TestCrossFamilyForeignRefusedAllPolicies15072` (6 cells:
  foreign AAAA-at-v4-name and foreign A-at-v6-name under
  replace-owned / skip-existing / strict-fail — no foreign RR,
  no foreign DHCID, no phantom ownership, victim untouched), and
  `TestCrossFamilySameDevicePublishesAllPolicies15072` (same
  device publishes both families under all three policies).
- Controls stay green: `TestDualStackProductionIdentitiesBothPublishReplaceOwned`
  (#14602), `TestCrossFamily*14995`, `TestManagerSkipExisting*14604`,
  `TestY13*14604`, `TestPartialDualStackTeardownKeepsSharedDHCID`.
- Suites: `go test ./pkg/ddns/ -count=1` PASS; `go vet ./pkg/ddns/` clean.

## Risk

Same-device dual-stack clients whose v4/v6 identities cannot be
paired (opaque client-id vs opaque DUID with no embedded MAC)
were already refused by the #14995 wire proof; the manager
binding refuses them one step earlier with the same outcome —
no behaviour change on the wire. Legitimate paired dual-stack
publishes under all three policies (acceptance control above).
