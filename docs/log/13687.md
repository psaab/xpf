# Issue #13687 — Keep deterministic SNAT sessions in their assigned CGNAT block

**Why:** Established source-NAT sessions are revalidated after configuration
commits. The pool matcher checked only global pool-address and port-range
membership, so a session could retain a port that the new deterministic CGNAT
mapping assigns to another subscriber, falsifying stateless subscriber
attribution.

**What:** Added deterministic-v4 revalidation to `source_nat_translation_matches`.
For address-only sessions it checks the subscriber's configured deterministic
pool address before accepting a port-less translation. For PAT sessions it
derives the subscriber's pool index and port block without allocating, then
requires both the retained translated address and port to match that mapping.
Coverage includes valid and invalid address-only mappings plus a PAT in-block
positive case, wrong port block, wrong pool address, and out-of-range subscriber.
The NAT64 deterministic-v6 state is stored on NAT64 prefixes, not
`SourceNatRule`, and is not handled by this matcher.

**Validation:** The regression failed without the matcher guard: the test
accepted subscriber `100.64.0.5`'s address-only translation to the wrong
address. With the fix, the targeted test passed (1 passed), and the NAT pool
module passed (217 passed, 1 ignored). Existing compiler warnings are unrelated.

**Risk:** Existing NAT64 session revalidation is separate and remains outside
this source-NAT matcher change.
