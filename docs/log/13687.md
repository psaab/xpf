# Issue #13687 — Keep deterministic SNAT sessions in their assigned CGNAT block

**Why:** Established source-NAT sessions are revalidated after configuration
commits. The pool matcher checked only global pool-address and port-range
membership, so a session could retain a port that the new deterministic CGNAT
mapping assigns to another subscriber, falsifying stateless subscriber
attribution.

**What:** Added deterministic-v4 revalidation to `source_nat_translation_matches`.
It derives the subscriber's configured pool index and port block without
allocating, then requires the retained translated address and port to match that
mapping. Added coverage for an in-block positive case, wrong port block, wrong
pool address, and out-of-range subscriber. The NAT64 deterministic-v6 state is
stored on NAT64 prefixes, not `SourceNatRule`, and is not handled by this
matcher.

**Validation:** Regression fails without the matcher guard: the test accepts
subscriber `100.64.0.5` retaining port 1024, which belongs to another
subscriber's block. Targeted and NAT pool module results are recorded with the
PR after final validation.

**Risk:** Existing NAT64 session revalidation is separate and remains outside
this source-NAT matcher change.
