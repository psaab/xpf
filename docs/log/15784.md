# 15784 — `DeleteSyncedConditional` companion identity captured after reverse removal; `companion_expected_id == 0` treated as unconditional companion teardown

- **Timestamp**: 2026-10-19
- **Action**: capture the companion incarnation before the reverse shared
  entry is removed on both `DeleteSyncedConditional` producers, and remove
  the `companion_expected_id == 0` wildcard for scoped deletes in the
  worker consumer.
- **File(s)**: `userspace-dp/src/afxdp/ha/session_import.rs`,
  `userspace-dp/src/afxdp/session_delta.rs`,
  `userspace-dp/src/afxdp/session_glue/commands/delete_synced.rs`,
  `userspace-dp/src/afxdp/types/runtime.rs`,
  `userspace-dp/src/afxdp/session_glue/tests.rs`,
  `userspace-dp/src/afxdp/ha_tests.rs`,
  `userspace-dp/src/afxdp/session_glue/pbr_install_table_9752_tests.rs`.

## The defect

All sites present on `origin/master` at filing (`f7c921ce29`):

1. **Coordinator fan-out read after delete.** In
   `delete_synced_session_gen_marked` (`ha/session_import.rs`), the reverse
   shared entry is removed (`reverse_teardown`, retained as
   `removed_reverse_entry` for steering teardown, #14840) *before* the
   per-worker fan-out loop. The fan-out then re-read `shared_sessions` for
   the reverse key — normally finding nothing — and sent
   `companion_expected_id = 0` (uncaptured), despite already holding the
   exact removed incarnation.
2. **Stale-close producer read after delete.** In `flush_session_deltas`
   (`session_delta.rs`), the stale-close branch removed the reverse shared
   entry (`remove_shared_session` under `teardown_ok`) and only afterwards
   looked the reverse key up in `shared_sessions` to capture
   `companion_expected_id` — again normally yielding 0.
3. **Consumer treated 0 as a wildcard.** In
   `handle_delete_synced_with_guard`
   (`session_glue/commands/delete_synced.rs`), the companion teardown fired
   when `live_companion_id == 0 || companion_expected_id == 0 ||
   live == companion_expected_id`. After a forward match, any live
   companion — including a replacement reverse installed during the
   worker-queue delay, whose forward id still matched — was torn down
   unconditionally.

Net effect (acceptance scenario): forward ID unchanged, reverse replaced
during queue delay → the replacement companion was torn down even though
the scoped forward identity matched.

## Fix

1. `ha/session_import.rs`: the fan-out names
   `removed_reverse_entry.session_id` — the incarnation captured before
   (by) the reverse removal. Only when no reverse entry was removed (e.g.
   teardown declined and a reverse row survives) does it fall back to
   naming that surviving row's live id; otherwise 0 (uncaptured).
2. `session_delta.rs`: the stale-close producer captures
   `companion_expected_id` at the top of the non-purge close block, before
   any reverse shared removal, and the replicate below consumes that
   capture. The non-stale path is untouched (it never replicates
   conditionally).
3. `session_glue/commands/delete_synced.rs`: the companion fires only when
   the companion is absent (live id 0, already converged), when the live id
   matches the captured id, or when the delete is unscoped
   (`expected_id == 0 && companion_expected_id == 0`, the legacy
   unconditional path). A scoped delete (`expected_id != 0`) with an
   uncaptured companion id now preserves any live companion — the safe
   direction (bounded leak healed by the delete-drop sweep / age-out,
   the same trade #14666 already documented for uncaptured companions).
   The recursion's inner `expected_id` argument is unchanged: with the new
   gate, a live companion is only recursed into when its id matched (or
   the delete is unscoped), so passing `companion_expected_id` (or 0 when
   absent) remains exact.
4. `types/runtime.rs`: the `companion_expected_id` field doc now states the
   pre-removal capture and the scoped-preserve semantics.

NOT changed: the policy-batch path (`handle_remove_policy_item` already
identity-validates its companion and refuses on `(Some, 0)` shapes — it
never reaches the guard with a scoped companion), the purge path in
`promote.rs` (sends `companion: None`, so no companion teardown is owed),
unconditional `DeleteSynced`/`DeleteLocalControl` (pass `companion: None`),
shared removal predicates, and NAT allocator semantics. No wire-format
change (`WorkerCommand` is in-process only).
