# #12163 — preserve distinct rollback history across repeated config-sync NACKs

- **Issue**: #12163 — identical `SyncApply` retries push duplicate entries into the 50-slot rollback ring and evict distinct rollback targets.
- **Branch**: `fix/12163-history-dedup`
- **Worktree**: `/var/worktrees/12163-history-dedup`
- **Base**: `1c384b9a47ff7d6e567fa50632faa75c3995ae87`

## Why

`SyncApply` promoted the incoming peer tree and pushed the previous active tree into rollback history on every delivery. If the apply failed, `ActiveApplied()` stayed false, so the next identical config-sync delivery retried the apply and repeated the history push. After enough retries, the fixed 50-slot ring evicted distinct rollback targets needed after failover.

## What

- Skip the `SyncApply` history push when the post-processed incoming tree has the same canonical text digest as the current active tree. Promotion, persistence, and apply retry behavior remain unchanged.
- Add a store regression covering repeated identical re-pushes beyond the ring capacity and verifying distinct entries remain while a different config still creates a rollback entry.
- Add a daemon regression that injects a persistent apply NACK through `handleConfigSync`, verifies every unapplied retry runs, and checks that distinct rollback entries survive.

## Risk / remaining acceptance

Dedup is exact to the canonical text digest; different-text pushes still create rollback entries. A legacy primary that re-sends cleartext API-auth values can cause the receiver to generate a fresh verifier on each retry, so those changed-text deliveries do not match this identical-text guard. No live cluster or hardware was mutated; the persistent NACK is injected at the daemon apply seam.
