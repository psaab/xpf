# #12163 — preserve distinct rollback history across repeated config-sync NACKs

- **Issue**: #12163 — identical `SyncApply` retries push duplicate entries into the 50-slot rollback ring and evict distinct rollback targets.
- **Branch**: `fix/12163-campaign-pub`
- **Worktree**: `/var/worktrees/campaign-pub/wt-12163`
- **Base**: `57c849c50c26ea5b2144777ab0f3dd151b5ac467`

## Why

`SyncApply` promoted the incoming peer tree and pushed the previous active tree into rollback history on every delivery. If apply failed, `ActiveApplied()` stayed false, so each config-sync retry repeated the history push. A legacy primary's byte-identical cleartext API-auth payload was especially problematic: the receiver generated a fresh salted verifier before comparing rendered digests, so every retry looked different and could evict distinct rollback targets from the fixed 50-slot ring.

## What

- Capture schema-scoped credential equivalence before hashing, then skip only the history push when either canonical digests match or legacy cleartext credentials match the active verifiers. Promotion, fresh hashing, persistence, and apply retries remain unchanged.
- Keep history pushes for real credential and non-credential changes.
- Cover hostname-only retries at the store seam and legacy cleartext API-auth retries through the persistent-NACK daemon path, including restart retention and changed-credential/non-credential controls.

## Risk

The schema-scoped comparison uses bcrypt to verify matching legacy credentials, adding per-credential work on each failed-apply retry. It does not skip hashing, promotion, persistence, or apply attempts; no cleartext is persisted. No live cluster or hardware was mutated; persistent NACKs are injected at the daemon apply seam.
