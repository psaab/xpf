# Issue #14396 — duplicate `daily` stanza must not clear `DailyExclude`

## Why

`compileSchedulers`' daily arm assigned (`=`) the per-stanza
`win.Exclude` to `SchedulerConfig.DailyExclude` while the neighbouring
`AllDay` flag and every weekday arm's `Exclude` are accumulated with
sticky OR. A second `daily` stanza carrying only a time window therefore
cleared an exclude declared by an earlier stanza:

```text
schedulers { scheduler S {
    daily { exclude; }
    daily { start-time 09:00:00; stop-time 17:00:00; }
} }
```

compiled to `DailyExclude=false` with bounds `09:00:00`–`17:00:00`. The
runtime (`pkg/scheduler`) suppresses a daily window only when
`DailyExclude` is set, so a scheduler Junos treats as never-active
became active in its window — the opposite of the authored semantics,
with a clean commit. The same drop fired for duplicate `scheduler S`
instances (exclude first) under the #5825 reused-map-entry composition.
It did not fire when the exclude stanza came last, nor for
group-provided excludes, because group expansion places the inherited
fragment after the local window stanza so the exclude was assigned
last; those orderings are pinned as regression cells anyway.

## What

- `pkg/config/compiler_system.go` (`compileSchedulers`, daily arm):
  `sched.DailyExclude = sched.DailyExclude || win.Exclude`, mirroring
  `sched.AllDay = sched.AllDay || win.AllDay` directly above it and the
  weekday arm's `w.Exclude = w.Exclude || win.Exclude`. Start/stop
  times keep their existing last-non-empty-wins composition; nothing
  else in the function changed.
- New regression
  `pkg/config/compiler_scheduler_daily_exclude_dup_14396_test.go`
  (`TestSchedulerDailyExcludeDuplicateStanza14396`) covering, for
  scheduler `S`: (a) exclude-then-window in one block, (b) reverse
  order, (c) duplicate `scheduler S` instances in both orders,
  (d) group-provided exclude + local window in both the hierarchical
  (`groups { G { ... } }` + `apply-groups`) and flat-set spellings,
  plus the flat-set reverse, and a window-only duplicate control that
  must not gain an exclude. Every positive cell asserts
  `DailyExclude=true`, bounds `09:00:00`/`17:00:00`, and `Daily=true`.
- NOT changed: the #11358/#12745 window-pair validator
  (`compiler_scheduler_window_pairs_11358.go`). It never reads the
  daily `Exclude` (its daily findings key only on `AllDay` plus a
  complete window), and `exclude` + window is a valid, intended
  combination (#12822), so no validator change is in scope.

## Validation

- RED on `origin/master` (`f8a69b7a4`):
  `go test ./pkg/config -run '^TestSchedulerDailyExcludeDuplicateStanza14396$' -count=1`
  failed the exclude-then-window and duplicate-instances-exclude-first
  cells with `duplicate daily dropped exclude (never-active became
  active): ... DailyExclude:false` (bounds preserved); the
  reverse-order, group, and control cells passed, matching the
  assignment-last-wins mechanism.
- GREEN after the fix: the same command passes all 8 subtests.
- Related suites stay green:
  `go test ./pkg/config -run 'TestSchedulerDailyExcludeCompiled12822|TestSchedulerDailyDuplicate|TestSchedulerDailySingle|TestSchedulerDailyRepeats|TestCompileScheduler|TestSchedulerHierarchical|TestSchedulerAcrossRoots|TestSchedulerDailyPlus|TestSchedulerSingleBlock|TestClosedWorldSchedulerApplyGroups' -count=1`

- `gofmt -l` on both changed Go files: no output. `git diff --check`:

## Risk

The change is strictly sticky: once any `daily` stanza for a scheduler
declares `exclude`, the compiled scheduler stays excluded; no stanza
ordering can clear it, which matches how `AllDay` and every weekday
`Exclude` already compose and how flat `set` lines (one composed path)
behave. There is no spelling that un-excludes a daily window in Junos
short of deleting the statement, and deletion is a config-tree edit,
not a second stanza, so no legitimate configuration loses an intended
active window. Runtime, hash, and display surfaces already consume
`DailyExclude` (#12822) and are unchanged.
