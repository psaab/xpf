# #14695 - deprovisionLoginUser resets interactive login shell to nologin

- **Timestamp**: 2026-10-17
- **Action**: `deprovisionLoginUser` (`pkg/daemon/login_password.go`) now
  resets an xpf-owned login shell to `/usr/sbin/nologin` via
  `usermod -s /usr/sbin/nologin -- <name>` before `forgetProvenance` drops
  provenance, gated on shell ownership: a new `provisioned-shells` marker
  root (sibling of `provisioned-users`, mirroring the #5841 passwords/keys
  split) written marker-first via `claimOwnership` when
  `applySystemLogin` (`daemon_hostauth_apply.go`) actually changes an
  existing account's shell (rolled back if `usermod` fails), plus account
  ownership (`ownsAccount`, from `useradd -s <shell>`) implying shell
  ownership for xpf-created accounts. This covers both arms in the issue:
  xpf-created super-users (`useradd -m -s /bin/bash`) and pre-existing
  accounts elevated to super-user with no password/key marker. A failed
  `usermod` or unreadable shell fails the deprovision and retains markers
  for retry; an already-nologin shell is a no-op (no exec); non-xpf accounts
  (no markers) are never touched. `forgetProvenance` and `provisionedNames`
  now include the shells root, and factory zeroize
  (`pkg/grpcapi/server_diag_zeroize.go`, `zeroizeProvisionedShellsDir`)
  sweeps it so the registry loss cannot resurrect as a re-tenant overclaim.
  NOT changed: no `userdel` on config deletion (account + home are kept, the
  shell grant is revoked instead — factory zeroize remains the only
  `userdel -r` path, per the issue's Junos note); the #14694 apply-ordering
  sibling (separate lane).
- **Validation**: RED on base (prod patch reverse-applied, shell-only
  fixture shim seeding no ownership): `TestDeprovisionLoginUserResetsInteractiveShellToNologin`
  failed with `usermod calls = [], want [[usermod -s /usr/sbin/nologin -- alice]]`,
  `TestDeprovisionLoginUserShellResetFailureRetainsProvenance` failed
  (success reported while shell stayed `/bin/bash`), and
  `TestDeprovisionShellOnlyElevationIsRevoked` failed with zero usermod
  calls. GREEN after fix: all five new cells in
  `login_deprovision_shell_14695_test.go` pass; broader login neighbourhood
  (`TestDeprovision*|TestReconcileAbsent*|TestProvisionedNames*|TestLoginShell*|TestApplySystemLogin*|TestPasswordAction|TestMarkerPath|TestLookupUID|TestClaimOwnership|TestHostAuthCloseout*`)
  passes; `pkg/grpcapi -run TestZeroize` passes (incl. extended
  `TestZeroizeLoginAccountsErasesAllThreeMarkerRoots` asserting the shells
  root). `go vet ./pkg/daemon/ ./pkg/grpcapi/` clean. Existing
  `TestReconcileAbsentLoginUsersRevokesCredentials` needed a no-op fake
  `usermod` staged in `stageDeprovisionEnv` (it drives the real exec seam).
- **Risk**: A pre-existing account whose shell xpf changed before this fix
  has no shell marker, so on removal its shell is not reset unless another
  marker (account/password/key) also fired the deprovision — the account/
  password/key arms still lock/remove as before; only the shell arm waits
  for the next apply that changes the shell to claim ownership. Sudoers
  revocation (`reconcileSudoers`) already removes the NOPASSWD grant on
  deletion, so the residual is the shell grant alone.
