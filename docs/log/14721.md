# #14721 — Runner.rollback omits post-start HelperHealthy gate; resumed StateRollingBack returns nil and rejoins election

## Defect

Two composed arms in `pkg/upgrade`:

1. `Runner.rollback` (`flip.go`) ran Stop → restoreDB → flip →
   `StartUnit` → `clearJournal` with no `HelperHealthy` call, while the
   forward path (`cutover.go` START) and the operator rollback
   (`executeRollback`, `rollback.go`) both gate on
   `HelperHealthy(version, StartHealthDeadline)`. For a `Type=simple`
   unit, start-success says nothing about the dataplane helper, so a
   dead-helper rollback was declared clean and the journal — the only
   resume record — was destroyed.
2. `Runner.Run`'s resume branch for `StateRollingBack` called
   `rollback(j)` / `executeRollback` and then `return nil`. Callers
   treat nil as a completed forward cut: standalone `xpfd upgrade`
   printed "upgrade complete" and exited 0, and `runRollingWith`
   proceeded to sync-wait + `RejoinAndConfirm`/`ResetFailover`,
   logging "cut complete" while the node actually went *backwards*
   to the old version (possibly with a dead helper).

## Fix

- `flip.go`: `rollback()` now calls
  `HelperHealthy(j.PreviousVersion, r.cfg.StartHealthDeadline)` after
  `StartUnit` and before `clearJournal`. On failure it returns an
  error naming helper health and preserves the `StateRollingBack`
  journal so a re-run resumes the rollback. This also covers the
  uninterrupted auto-rollback callers of `rollback()` (forward START
  failure, stale half-cut, flip-failure recovery) — they already
  surface `rollback()` errors as non-nil.
- `cutover.go`: the `StateRollingBack` resume branch now returns a
  non-nil outcome after a completed rollback
  (`resumed an interrupted rollback: rolled back to %s ...`),
  mirroring the uninterrupted auto-rollback error at the START phase.
  Both flavours (operator via `executeRollback`, auto via
  `rollback()`) share this return, so neither can be mistaken for a
  committed cut. `LastCommittedCut` stays empty (reset at Run entry,
  never recorded on this path). Because `stopAttempted` is already
  true for this branch, the rolling driver keeps the drained node
  passive instead of failing back.

NOT changed: `executeRollback` (already health-gated),
`runRollingWith`/`runRollingRollbackWith` sequencing (they now
correctly see a non-nil inner `Run`), and any health-probe semantics.
