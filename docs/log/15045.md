# #15045 — cross-family ICMP protocol with icmp-type passes commit, never matches (A05-01)

- **Timestamp**: 2026-10-18
- **Issue**: `next-header icmp` (proto 1) with `icmp-type` in an inet6 filter, or `protocol icmpv6`/`58` with `icmp-type` in an inet filter, passed strict commit with no warning; the discard/reject term never matches real traffic and falls through to later terms / implicit accept (fail-open; residual of #3723, which covered protocol-vs-field but not the family dimension).
- **Base**: `origin/master` `0c3e014235`.

## Mechanism (verified at base)

- `pkg/config/compiler_validate_strict_filter.go` `validateFilterCrossFieldStrict` icmp arm used family-blind `protocolIsICMPFamily` (1 and 58 both pass in either family); `family` was used only in the error text.
- `compileFilterFrom` (`compiler_firewall.go`) resolves `icmp-type` names with the filter family's table (`resolveICMPTypeToken(v, family)`: echo-request → 8 in inet, 128 in inet6), so inet6+icmp(1)+echo-request pinned protocol 1 with type 128 — no packet satisfies both.
- `userspace-dp/src/filter/compiler.rs` `check_cross_field_satisfiability` accepted proto 1 OR 58 in either family; `engine/matching.rs` gates icmp-type/code on the packet being ICMP/ICMPv6, and a family's packets carry only its own ICMP number (1 in inet, 58 in inet6).

## Fix

- Go: new `protocolIsICMPForFamily(token, family)` next to `protocolIsICMPFamily` (inet: icmp/junos-icmp-all/junos-ping/1; inet6: icmpv6/icmp6/icmp-v6/junos-icmp6-all/junos-pingv6/58; unknown family keeps the #3723 either-ICMP verdict). The icmp arm of `validateFilterCrossFieldStrict` now judges each protocol token with it (strict reject; lenient path warns via the existing `lenientFilterCrossField` downgrade, naming family + offending token). `protocolIsICMPFamily` itself is unchanged (shared with the application gate).
- Rust: `check_cross_field_satisfiability` icmp arm now requires the family's ICMP number (`inet`→1, `inet6`→58, unknown family keeps either-ICMP), reusing `UnsatisfiableFilterCrossField` with predicate `icmp-type/code`.

NOT changed: `protocolIsICMPFamily` and the application gate; port/tcp-flags/no-protocol arms; a wrong-family protocol WITHOUT an icmp predicate (stays accepted, out of scope); `family any` handling (icmp under `family any` already rejected by #4296); the matcher.
