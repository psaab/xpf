  - **Action**: Fix `cli -c` exiting 0 having done nothing when a
    keyword-only node got an unknown or unimplemented subcommand
    (#16798, R3-A54-02). Handlers for keyword-only nodes printed tree
    help and returned nil (`request system software` without
    `in-service-upgrade`, `request chassis cluster` default arm,
    `clear security` default, and 32 census siblings incl. the absent
    `clear security ike …`), and `main.go` maps a nil dispatch error
    to exit 0 — so a scripted IKE SA flush, software add, config sync
    or failover reported success for work that never happened. Fix:
    new `cmdtree.ValidateOperationalLine` consults
    `Canonicalize(OperationalTree)` and, for a line that fails only
    because a trailing token sits under a keyword-only node (keyword
    children, no dynamic/typed/placeholder/AcceptsArgs/Options value
    slot, non-leaf), returns the canonical prefix, the offending
    token and an ambiguity flag; `dispatchOperational` in
    `cmd/cli/shared.go` refuses it before routing as
    `unknown <path> command: <token>` (or `ambiguous …`), which the
    existing `-c` mapping turns into exit 1. Bare keyword nodes
    canonicalize OK and keep their help listing; failures involving a
    value slot (filled/dangling/dynamic/Options) or trailing words
    after a leaf fall through to the existing strict handlers
    (usage / unknown-filter / exact-arity), so no lawful line is
    pre-empted. `?`/`help` client verbs are exempt from the gate.
    The two AST scope guards (`AcceptsArgs`, `Options`) and both
    package READMEs record that `ValidateOperationalLine` reads those
    flags only to classify a node as not keyword-only.
