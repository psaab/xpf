# Issue #15667 — X.509 chain validation in management TLS preflight

## Claim (narrowed, from issue)

`pkg/api/tls_certificate_10827.go` parsed and validity-checked only
`cert.Certificate[0]`, serving expired/invalid intermediates, accepting
CA or non-`ServerAuth` leaves, omitting SAN diagnostics on custom
certificates, and latching `s.tlsDesired = true` on initial load
failure so refresh never recreated the failed listener. Go's handshake
still verifies trust — this is a preflight/diagnostics/recovery
defect, not a crypto bypass.

## Fix

- `managementTLSCertificateChain` parses every DER entry (rejecting a
  `Leaf`/`Certificate[0]` mismatch and any unparseable intermediate);
  `newManagementTLSCertificateState` stores the full parsed chain.
- `managementTLSCertificatePreflightError` (applied at custom load,
  generated load, custom/generated refresh, handshake-time
  `GetCertificate`, and the durable-pair loader in
  `generateSelfSignedCertAtWithStatusMulti` so a bad durable chain is
  re-minted, not served): every entry inside `NotBefore`/`NotAfter`
  (leaf wording unchanged for existing callers), leaf not a CA, leaf
  EKU allows `ServerAuth` when an EKU list is present (absent = any),
  every non-leaf is a CA allowed to sign, and every adjacent
  `CheckSignatureFrom` link verifies. Trust to a public root is not
  required (self-signed/pinned management certs).
- SAN diagnostics: successful custom loads and rotations log
  `sans=dns=[...] ip=[...]` (or the no-SAN marker); the invalid-cert
  error log carries the same field.
- `tlsDesired` latch: split into `tlsDesiredConfigured` (operator
  desire: Config / last `ReconcileHTTPS`) and `tlsDesired` (armed only
  by `installManagementTLSCertificate` on a successful load).
  `NewServer` no longer pre-arms `tlsDesired`. The monitor/refresh is
  gated on either flag so it keeps retrying; on a successful refresh
  with no serving leg, `recoverHTTPSLegsIfNeededLocked` binds and
  serves the configured HTTPS templates directly from the validated
  state (no `buildHTTPSServer` reload, no `lifeMu`→`tlsCertificateMu`
  cycle). `Start` (not legacy `Run`/`serveBound`) gains recovery.

## Regression (`pkg/api/tls_certificate_15667_test.go`)

- `TestPreflight15667` — valid chain passes with SAN diagnostic;
  expired / not-yet intermediate, CA leaf, client-auth-only leaf,
  non-CA intermediate, and bad signature link each rejected with the
  expected substring; leaf expiry wording pinned.
- `TestCustomChainRejectedAtLoad15667` — expired-intermediate custom
  chain: no HTTPS server, selector refuses, invalid counter +1,
  `tlsDesired` false, `tlsDesiredConfigured` true.
- `TestCustomValidChainSANLog15667` — valid chain installs, arms
  `tlsDesired`, and the load log contains the SAN.
- `TestMonitorRecoversAfterFix15667` — boot with a bad chain, fix the
  files in place, one refresh creates the serving leg; a real TLS
  handshake to it succeeds.
