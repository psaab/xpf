# #12144 — bind flat apt packages to the selected release

- **Timestamp**: 2026-10-08
- **Why**: The flat builder's default `dist-deb` glob admitted any xpf-named version, copied into a persistent suite pool without pruning, and indexed the entire pool. `gate_apt` verified the InRelease signature/keyring agreement but did not bind package identity or contents to the release index.
- **Change**:
  - `make dist-repo` now passes its authoritative `DEB_VERSION` as `XPF_DEB_VERSION`. The default builder selects only filenames at that version and checks selected filename Package/Version/Architecture against `dpkg-deb`. Explicit flat input sets reject identity mismatches, mixed versions, and duplicate Package/Architecture entries.
  - A flat rebuild removes every old `.deb` under that suite/component before copying the selected set, so omitted packages are withdrawn from `Packages`. The opt-in reprepro database/pool retention behavior is unchanged.
  - `gate_apt` now checks flat suite indexes against the signed Release checksums (including `Packages.gz`), matches the exact suite pool to indexed paths and dpkg identity, verifies package Size/SHA256 against Packages, rejects duplicate package identities, and binds the target suite version to the verified signed `latest.json` version. Reprepro retains its existing history behavior.
- **Regression tests**: `scripts/dist/test_build_apt_repo_binding_12144.py` covers omitted-package withdrawal, default-glob version binding against a higher extra, fail-closed missing authority, filename/control mismatch, duplicate explicit input, target-version rejection, duplicate pooled identity, and same-identity package-byte substitution.
- **RED (base `a714c90d472a3c3d98a3799831cfef3ec311a61c`)**: Hermetic real `.deb` fixtures reproduced stale retention: after building with `xpf` versions `0.0.4+g0000000` and `0.0.5+g1111111`, then rebuilding with only `0.0.5`, base `Packages` still contained `0.0.4`. A signed base build containing legitimate `0.0.5` (with the matching archive keyring) plus keyring-less `9.9.9+g9999999` indexed both; base `gate_apt` verified InRelease and key agreement and **passed** with the extra. The base default glob also indexed the higher extra.
- **GREEN (same fixture scenarios)**: The flat rebuild withdrew `0.0.4`; the default set pinned to `0.0.5` omitted `9.9.9`; explicit same-Package higher-version selection failed. A signed current repo passed the gate with `0.0.5`; the gate rejected a pooled `9.9.9` extra as outside the verified target version and rejected same-identity substituted package bytes against the signed Packages Size/SHA256.
- **Validation**: `python3 -m unittest discover -s scripts/dist -p 'test_*.py'` — 142 tests, OK. `sh scripts/dist/selftest.sh` — 58 passed, 0 failed. `sh -n scripts/dist/build-apt-repo.sh scripts/dist/selftest.sh`, `python3 -m py_compile scripts/dist/publish.py scripts/dist/test_build_apt_repo_binding_12144.py`, and `git diff --check` passed. `make -n dist-repo` confirmed the Makefile forwards `DEB_VERSION` as `XPF_DEB_VERSION`. No broader reds remained to attribute; no live-cluster mutation.
- **Risk / limits**: Direct default builder invocation now requires `XPF_DEB_VERSION`; the supported `make dist-repo` target supplies it, while callers using `--debs` declare the explicit selected input set. An explicit `publish.py --no-image` run has no signed image `latest.json` authority, but still enforces flat index/pool identity, byte hashes, and single-version-per-package constraints. Reprepro intentionally retains its separate historical-pool semantics.
- **Files**: `Makefile`, `scripts/dist/build-apt-repo.sh`, `scripts/dist/publish.py`, `scripts/dist/selftest.sh`, `scripts/dist/test_build_apt_repo_binding_12144.py`, `docs/log/12144.md`.
