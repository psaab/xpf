# 9517 — the XDP steering map key drops routing_domain and the GRE discriminator

- **Timestamp**: 2026-09-10
- **Action**: demote `PASS_TO_KERNEL` to `REDIRECT` on a node with routing domains,
  at BOTH publish sites; pin the key aliasing with a positive-controlled cell;
  correct the README's false collision-surface completeness claim; state the
  DELETE arm as an unclosed residual with the remedies that were tried
- **File(s)**: `userspace-dp/src/afxdp/bpf_map/mod.rs`,
  `userspace-dp/src/afxdp/bpf_map_tests.rs`,
  `userspace-dp/src/afxdp/session_glue/{mod.rs,promote.rs,tests.rs}`,
  `userspace-dp/src/afxdp/forwarding/{local_delivery.rs,tests.rs,README.md}`,
  `userspace-dp/src/afxdp/{shared_ops.rs,ha/state.rs,poll_descriptor/mod.rs}`

## Scope, decided before any code: two harm arms, and the prescription closes ONE

#9517 names two classes of harm from the aliased row. They are not the same thing
and the issue's prescribed remedy does not close both:

| arm | mechanism | closed by "demote to REDIRECT on a VRF node"? |
| --- | --- | --- |
| **OVERWRITE** | an aliased peer-synced publish replaces a `REDIRECT` row with `PASS_TO_KERNEL`, sending the flow to `cpumap_or_pass` — the kernel forward path, where no zone policy runs | **yes** — both sessions now publish `REDIRECT`, so an overwrite writes `REDIRECT` over `REDIRECT` |
| **DELETE** | either aliased session's ordinary teardown removes the shared row; with an `lo0` filter the survivor's next packet misses, reaches the kernel and skips the filter | **no** — both rows are `REDIRECT` and still share one key |

Landing the demotion while describing #9517 as closed would be a partial fix that
reads as a whole one. So the demotion ships, and the DELETE arm is written into the
predicate's doc, the README residual list and this log as OPEN.

## Two remedies for the DELETE arm were tried and rejected, with reasons

1. **Add `routing_domain` to the key.** The issue rejects it and the rejection
   holds: key SIZE is not the blocker, the SHIM cannot compute the domain. It would
   need a per-packet ifindex->domain lookup plus logical-unit resolution on the
   hottest path, and `userspace-xdp/src/lib.rs` records that a second HASH lookup
   already "pushed `xdp_userspace_prog` over the 1M-insn BPF verifier cap (#1864)".
2. **Put the domain in the key's spare `pad: u16`.** Tempting — it changes no size,
   so no ABI or `make generate`. But the shim still writes `pad = 0` on lookup, so a
   userspace-written `pad = domain` row would make every shim lookup MISS. For a
   LocalDelivery-with-`lo0` flow a miss means kernel delivery and an unenforced
   filter — the very harm being fixed, now on the unaliased flow too. Rejected.

Both rejections reduce to the same fact: identity has to be in the key, and the shim
cannot produce it within budget. That is the residual.

## Why the demotion is still the right thing to ship

The OVERWRITE arm is the one whose harm a clean MISS cannot produce: a miss would
have redirected to the policy engine, while an aliased `PASS_TO_KERNEL` bypasses it
entirely. The gate costs no shim change, no `make generate`, no verifier budget and
no wire change; it is byte-identical on every single-instance deployment; and it
fails SAFE — the worst case is an extra userspace hop for host-inbound traffic on a
VRF node, not a dropped packet.

## Both publish sites, and which of them are LIVE

The issue is explicit that `publish_session_map_entry_for_session_with_conntrack` is
a second publish site that does not go through the `lo0` downgrade, so a fix at the
`session_glue` site alone is partial. The gate therefore lives in the PREDICATE
(`uses_kernel_local_session_map_entry`), which both sites call, and the flag is
threaded to every caller of the chain, each reading its own
`forwarding.has_routing_domains`.

**Correction to an earlier revision of this log.** It said ONE threaded site,
`install_helper_local_session_on_miss`, was inert because it reaches a wrapper that
hardcodes `SessionOrigin::ForwardFlow`. That census was wrong by six. EVERY caller of
`publish_session_map_entry_for_session` reaches that wrapper:
`session_glue/promote.rs`, the three `shared_ops.rs` sites (one of them
`republish_bpf_session_entries_for_owner_rgs`, which the HA RG-activation republish
in `ha/state.rs` calls), the seed publish in `poll_descriptor/mod.rs`, and
`forwarding/local_delivery.rs`. `ForwardFlow` is not peer-synced, so the predicate's
first clause is false there and the flag cannot change what any of them publishes
today. The census is every caller of the predicate and of the `_with_origin` /
`_with_conntrack` entry points; it is positive-controlled by the one caller it finds
that IS live.

That caller is `publish_worker_session_map_entry` (`session_glue/mod.rs`), reached
by `upsert_synced`, `refresh_owner_rgs` and `demote_owner_rgs` with a real
peer-synced origin. It reads the flag three times: for the `lo0` downgrade and the
stale-row delete, for the forced-live-redirect branch, and for the `_with_origin`
publish. That is the wiring a mutation run has to bind. The six inert sites still
thread the real flag, because a constant there becomes the wrong answer the day a
wrapper's origin changes.

## Binding the wiring: the first mutation run's survivor

The first matrix (on `520ad5b89`) removed the predicate's gate (M1) and severed the
flag at the `session_glue` publish (M2). M1 was KILLED by
`routing_domains_demote_kernel_local_to_redirect_9517`. M2 SURVIVED with all 5,689
tests passing. The cause was structural rather than a thin cell: the flag's only
effect is a BPF map write, an unprivileged `cargo test` cannot create a map, and so
the only thing any cell could drive was the predicate. A caller handing the predicate
the wrong flag was invisible.

That is a reason to make the wiring EXERCISABLE, not to excuse the survivor. `bpf_map`
now records, under `#[cfg(test)]`, every steering-map write the dataplane ATTEMPTS
(the key plus the action byte for an update, `None` for a delete), before the
syscall. That is the shape the file already uses for `CONNTRACK_PUBLISHES`.
`session_glue/routing_domain_publish_9517_tests.rs` drives the REAL
`publish_worker_session_map_entry` with a map fd that is non-negative, so it gets past
the `< 0` early return, and is never a map, so every syscall fails harmlessly after
the recorder has seen it. The cell asserts what the path tried to write:

- control, no routing domains: exactly one `PASS_TO_KERNEL` write, so the fixture
  provably reaches the kernel-local branch;
- with routing domains: zero `PASS_TO_KERNEL` writes, a `REDIRECT` write for the
  session's key, and zero deletes. The delete assertion binds the SECOND read of the
  flag: a kernel-local verdict computed without it deletes the live row before
  republishing it, which opens a window with no steering row for the tuple.

A sibling cell asserts the same outcome through the forced-live-redirect branch
(`allow_replace_local`). With routing domains both branches publish `REDIRECT`, so a
mutant at that third read changes which branch runs and not what is written. It is
EQUIVALENT by construction, and it is run below so that claim is measured too.

## The GRE arm: the issue's acceptance criterion the first cut did not meet

Re-reading #9517's acceptance criteria before landing (the body is the spec; it has
no comments) turned up a criterion the routing-domain demotion does not satisfy:
"Two keyed GRE tunnels between the same endpoint pair likewise do not share a row."
The issue calls that arm DETERMINISTIC and the cheapest reproduction: it needs no
routing domains, because two RFC 2890 keyed tunnels between one pair of outer
endpoints are both protocol 47 with no ports. The first cut gated only on
`!has_routing_domains`, so on a single-instance box a peer-synced host-bound session
carrying a `Keyed(k)` discriminator could still publish `PASS_TO_KERNEL` over a
sibling tunnel's `REDIRECT` row — the OVERWRITE arm, open on exactly the
configuration the issue named first.

The same demotion closes it. The predicate now takes the session key and requires
`key.discriminator.is_none()`. EVERY non-`None` class is demoted, `Unkeyed` and
`Unparseable` included: an unkeyed tunnel and a keyed one between the same endpoints
sit on the same bare tuple, so either's `PASS_TO_KERNEL` would overwrite the
other's row. Cells: `tunnel_discriminators_demote_kernel_local_to_redirect_9517`
(every class, with a `None` control) and
`a_keyed_gre_session_is_demoted_on_a_single_instance_node_9517` (through the real
worker publish, with a plain-key control).

## Scope after the extension

| arm | routing domains | tunnel discriminator |
| --- | --- | --- |
| OVERWRITE (`PASS_TO_KERNEL` over a sibling's `REDIRECT`) | closed | closed |
| DELETE (either teardown removes the shared row) | open — #9560 | open — #9560 |

The DELETE arm needs identity in the key, which the verifier budget forbids (the two
rejected remedies are above). It is filed as #9560 with #9517's unrun cluster
control as its acceptance, so landing this does not remove the reason to look.
