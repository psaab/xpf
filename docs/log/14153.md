# 14153 — RA configEqual omits ProtectedPrefixes

`configEqual` (`pkg/ra/ra.go`) compared every field `buildRA` stamps
onto the wire but never `ProtectedPrefixes`. That field is stamped
box-wide by the daemon's `buildRAConfigs` (`pkg/daemon/daemon_ra.go`,
not inside `Manager.Apply`) from `config.ConfiguredIPv6Prefixes`, and
consumed by `sender.delegatedOverlapsProtected`, consulted in
`buildRA` to refuse a delegated PIO overlapping configured space. A
day-2 commit that only changed configured IPv6 space (a new local
subnet, RA or NAT64 prefix) therefore changed only this field, left
`configEqual==true`, and `Apply` kept the running sender filtering
delegated prefixes against the stale set until an unrelated RA edit
or a daemon restart. The issue's claimed `DNSDomains` half is
unsupported: no such field exists on `RAInterfaceConfig`; the RDNSS
wire field is `DNSServers`, already compared. No fix was made for it.

Fix: `configEqual` now compares `ProtectedPrefixes` as set equality
over the effective prefixes — parsed, masked, IPv6-only, with
unparseable/non-v6 (including 4-in-6) entries skipped, matching both
the producer (`ConfiguredIPv6Prefixes` masks) and the consumer
(`delegatedOverlapsProtected` + `IPv6PrefixesOverlap` operate on
masked forms and reject non-v6). Raw or order-sensitive slice
comparison was rejected: the producer iterates the interface map, so
order is randomized per rebuild and a raw compare would
spurious-restart senders on every no-op reconcile. For the same
reason `ConfiguredIPv6Prefixes` now returns a sorted, deduped slice:
the cluster path's `raDesiredHash` JSON-marshals the desired RA set
(including this field), so map-order stamps flapped the digest and
forced a full `ra.Apply` on every ~2s periodic reconcile even with
the `configEqual` fix. The DHCP manager consumer
(`SetProtectedIPv6Prefixes`) only tests overlap, so sorting/dedupe
is behavior-neutral there. Fail-closed direction preserved: a
genuine protected-set change restarts the sender; an effective-equal
re-stamp does not.
