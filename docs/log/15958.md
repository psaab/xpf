# #15958 — split-RG fabric return blackhole at LAN egress

- **Timestamp**: 2026-10-20
- **Action**: fixed the fw1 split-RG return leg that counted
  `forward_candidate` on the fabric binding but never transmitted on
  the LAN egress (no counter, no ring entry), and added the F1
  observability mirror on the flow-cache exits.

## Root cause (instrumented, exit=20)

Session-hit exit instrumentation (temporary `diag15958_hit_exit`,
since removed) showed both the ICMP echo-reply and TCP ACK cells
dying at hit-arm exit 20 = `StaleSourceNat` with all other hit
counters at zero. The exact branch is the companion-less
`NoLocalEntry` reconstruction in
`source_nat_revocation_on_session_hit_with_ingress`
(`poll_descriptor/policy_revalidation.rs`): it reconstructed the
forward decision (`rewrite_src = 172.16.80.8`) from the reverse row,
found a translation present, then demanded
`metadata.forward_ingress_vlan_id`. That field is `None` by
construction for this row class:

- reverse synthesis zeroes the companion's ingress identity, and
  `forward_ingress_vlan_id` is `Some` only when the forward ingress
  ifindex was nonzero — a fabric-admitted forward has
  `ingress_ifindex == 0` (`stamped_ingress_identity` returns `(0,0)`
  for fabric ingress), and
- HA session sync never carries the field
  (`build_synced_session_entry` hardcodes
  `forward_ingress_vlan_id: None`).

So every HA-synced reverse session installed locally without its
forward half was revoked as `StaleSourceNat` on its first
fabric-arriving packet. The forward-counted/never-transmitted shape
follows: the hit counted, the revocation recycled the descriptor,
LAN TX never happened, and no named counter or ring entry moved.

Candidate A was tested directly: the hit path does consult
`interface_nat_local_resolution(172.16.80.8) = LocalDelivery/14`
(via `lookup_forwarding_resolution_for_session_with_cache`), but the
cached LAN `ForwardCandidate` is served first, so that was not the
sink. Candidate B (cross-UMEM pending fallback) was not the sink
either: after the fix, the same cross-UMEM harness transmits via
`enqueue_pending_forwards_with_dynamic` + `drain_pending_tx`.

## Fix

- `policy_revalidation.rs` (fold round 2): in the companion-less arm,
  the provenance-only revocation declines ONLY for a row positively
  proven to be plain dynamic source NAT: fabric row, zeroed ingress
  identity (`ingress_ifindex == 0`), no forward VLAN, a source rewrite
  with NO destination rewrite, and dynamic provenance
  `source_nat_static == Some(false)`. The dynamic marker is minted
  solely by the pool/interface SNAT branch, rides the HA wire
  (`source_nat_provenance`), and is stamped at import. Static
  (`Some(true)`) and unknown/legacy (`None`) provenance keep the
  #13910/#13771 fail-close. That positive proof is what closes the
  Codex NPTv6 wire loss: NPTv6 is a supported HA config, but its type
  bit does not survive the wire (admission mints no provenance for it,
  no BPF flag is stamped, the Go V6 sync request has no field, and the
  Rust import rebuild leaves `nptv6: false`), so a real HA-imported
  NPTv6 row presents as provenance-unknown and stays fail-closed —
  proven by `ha_imported_nptv6_wire_shape_still_fails_closed_15958`,
  which drives the real import path
  (`SessionSyncRequest` → `build_synced_session_entry` → production
  reverse synthesis → revocation). Composed DNAT+SNAT rows are
  excluded by the no-destination-rewrite conjunct, so destination
  validity is still judged inside
  `source_nat_translation_still_valid`
  (`fabric_composed_snat_dnat_without_vlan_provenance_fails_closed_15958`).
  NAT64/NPTv6 type bits remain excluded as defense in depth for
  in-process rows. Both mutating the provenance gate back to
  `!= Some(true)` and dropping the destination conjunct red their
  cells. The V2 scoped shape is proven at decision level by
  `fabric_scoped_synced_companion_without_vlan_provenance_survives_15958`
  and at packet level by
  `split_rg_fabric_return_scoped_tcp_egresses_lan_15958`.
- `flow_cache_hit.rs` (F1): a cached `tx_selection.drop` verdict on
  the early cached-drop arm now records `forward_build_failures` + a
  `transit_output_filter_drop` exception-ring entry, mirroring the
  slow-path twin in `poll_descriptor/mod.rs`. Policer-only drops keep
  existing attribution. (Fold: the cache-fallback builder's `None`
  exit is unreachable for a dropping selection — the cached drop
  returns first — so no counter is claimed for it; an earlier
  revision's dead `else` there was deleted.)

## Older-peer (pre-#12187) compatibility — adjudicated, pre-existing

Question (round-3 ledgers): does a pre-#12187 peer's imported dynamic-
SNAT row (provenance `None`) fail-close on fabric return under this
PR, and did it work before this PR?

- It fail-closes under this PR (pinned by
  `ha_imported_legacy_dynamic_snat_without_provenance_fails_closed_15958`,
  which drives the real `SessionSyncRequest` → import → reverse
  synthesis → revocation path with wire provenance 0).
- It was ALREADY revoked before this PR — not a regression. On
  `origin/master` the identical companion-less row (source rewrite
  present, `forward_ingress_vlan_id: None` by import construction)
  reached the same `let Some(forward_ingress_vlan_id) … else
  StaleSourceNat` arm introduced by #13789 (2026-10-15), with no
  decline in front of it. #15958 only ADDS a decline for positively
  proven dynamic rows (`Some(false)`); the fate of `None` rows is
  byte-identical before and after. Provenance itself (#12187,
  2026-10-12) predates the VLAN demand, and the pre-fold round-1
  `!= Some(true)` decline that briefly admitted `None` was never on
  master.
- No import-time stamping: minting `Some(false)` at import for
  source-only rows would also mint it for wire-lost NPTv6, which is
  indistinguishable at import (no type bit on the wire, import leaves
  `nptv6: false`) and would reopen the #13910 bypass proven by
  `ha_imported_nptv6_wire_shape_still_fails_closed_15958`.
- Supported-pairing boundary: pre-#12187 peers advertise
  `SessionSyncWireVersion` 2 (or none); the 2→3 bump (#15140,
  2026-10-19) makes a v2 peer a mismatched nonzero version, which
  `SessionSyncWireCompatible` / the rolling-upgrade gate refuse — so
  no supported rolling pairing delivers this row to a current node.
  Residual: a manually paired out-of-gate v2/v3 cluster keeps the
  pre-existing fail-close (documented here), unchanged by this PR.

## #15958b follow-up (punt-origin sink, round 6)

- **Timestamp**: 2026-10-20
- **Action**: fixed the fw0 punt-origin return sink identified by
  HuntFreshGLM round 6 / DiagFw0Tx: replies were session-accounted on
  fw0, candidate-counted, then transmitted on the WAN binding (or, in
  the live 19-field extract, never observed leaving fw0) instead of
  crossing the fabric to the LAN owner on fw1.

### Root cause

On fw0 the connected LAN prefix `10.0.61.0/24` is HA-suppressed
(`connected_rg_peer_owned=true` for RG2), so the FIB has no LAN route
and answers the LAN-host target with the default route via the WAN
gateway (`ForwardCandidate` egress reth0.50/ifindex 13, next-hop
172.16.50.1, owner RG1 locally active).

1. `reverse_resolution_for_session_in_table` only redirected when the
   resolved owner RG was *inactive*; the gateway route's owner (RG1)
   is active, so the synthesized reverse companion was stored as a WAN
   `ForwardCandidate`, not `FabricRedirect`.
2. On the WAN-side reverse hit, the stored-`FabricRedirect` guard was
   absent: `lookup_forwarding_resolution_for_session` re-resolved via
   the same FIB (cached arm refuses `FabricRedirect`), yielding the
   WAN gateway candidate again, and `redirect_session_via_fabric_if_needed`
   only converts `HAInactive` — so the reply was built for
   `target_ifindex=6` (WAN binding, `target_binding_index=Some(0)`)
   and transmitted there. Descriptor target, enqueue and drain all
   succeeded — on the wrong binding. No drop counter fires because
   nothing is dropped; it is a wrong-egress transmit (live extract
   read it as "fabric tx Δ0, all counters Δ0").

### Fix

- `reverse_synth.rs`: fabric-ingress reverse resolution now also
  redirects when the resolved `ForwardCandidate` egresses in a zone
  other than the session's LAN (ingress) zone.
- `session_glue/resolve.rs` (hit + synthesized-reverse arms): a stored
  `FabricRedirect` companion is retained when re-resolution yields a
  `ForwardCandidate` egressing outside the companion's destination
  zone, instead of being silently replaced by the gateway route.

### Cells

`split_rg_punt_origin_wan_reverse_{icmp,tcp}_fabric_tx_15958b` install
the forward+reverse pair on the fw0 (punt-origin) shape from
`snap-split-fw0.json`, drive the WAN-side reverse hit through
poll→enqueue→drain over separate WAN/fabric/LAN UMEMs, and assert:
fabric binding `tx_packets=1` (×2 for TCP pkt1), WAN `tx_packets=0`,
`fabric_redirect_unsendable_drops=0`, fabric frame dst MAC = peer
fabric MAC, dst IP = LAN host. RED without the fix (WAN tx=1, fabric
tx=0, egress None on the fabric/LAN siblings); GREEN with it.
