# Issue #12089 — refuse IPsec VPNs sourced from non-default routing-instances

- **Issue**: #12089 — an IPsec VPN's effective local address can belong to a non-default routing-instance, but neither strongSwan nor the xfrmi is scoped to that instance.
- **Branch**: `fix/12089-campaign-pub`
- **Worktree**: `/var/worktrees/campaign-pub/wt-12089`
- **Base**: `83b5c955335f16d8c7835f206b210ce3ae1a5fe5` (`origin/master`)

## Why

An IPsec VPN can select its source from `vpn local-address`, then gateway `local-address`, then an address derived from `external-interface`. The prior gate inspected only the last spelling, so VR-owned addresses set by either `local-address` could still commit, and a default-instance source could be refused merely because the overridden external interface belonged to a VR. strongSwan's IKE socket and xpf's parentless xfrmi are not scoped to the source address's routing-instance, so outer IKE/ESP traffic may use the wrong routing table.

## What

The commit-time gate follows the renderer's per-VPN local-address precedence and maps an explicit address to its declared interface unit, kernel device, and routing-instance owner; when no local-address is configured, it keeps the external-interface-derived selection. It refuses each VPN whose effective source is in a non-default VR, including VPNs using an inline peer endpoint, and tolerantly warns on load / peer-sync. Unused gateway objects retain the gateway-level check. Forwarding instances are not treated as VRF owners, and the gate runs after the routing-instance membership tail gates so #11060 and #11312 retain diagnostic priority.
