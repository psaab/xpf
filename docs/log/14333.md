# Issue #14333 — revalidateSnapshotIfindexesInPlace updates only Ifindex without refreshing HardwareAddr, MTU, Addresses, RXQueues, EgressZone, or attaching XDP

## Why

`revalidateSnapshotIfindexesInPlace` (pkg/dataplane/userspace/interfaces.go)
discarded the live `mtu`, `hardwareAddr` and `addresses` returned by
`buildLinkSnapshot` and refreshed only `Ifindex`/`ParentIfindex`/`LinkUp`.
`stampEgressZones` skips `Ifindex<=0` rows at build time, so an interface
whose kernel link materialized (0 -> N) — or whose metadata changed — in
the build->apply window was published with `EgressZone: ""` (egress zone
0), empty `HardwareAddr`, stale/empty live `Addresses`, build-time
`RXQueues`/`SecureTunnel`, and no XDP program attached for the new
ifindex. `rebuildDerivedSectionsAfterRevalidate` (#14209) rebuilt
Routes/Fabrics/TunnelEndpoints/Mirrors from those rows but never rebuilt
the rows themselves.

## What

- `rebuildDerivedSectionsAfterRevalidate`
  (pkg/dataplane/userspace/apply_snapshot_identity_9520.go): when the
  snapshot's Config actually describes interface rows
  (`snapshotHasInterfaceRows`), rebuild `snap.Interfaces` via
  `buildInterfaceSnapshotsFrom(cfg, liveXfrm)` and refresh
  `snap.wgFanUpBaseRows` — exactly as `RefreshInterfaceRowsForLink`
  (#14133) does — then revalidate the freshly built rows in place before
  deriving Routes/Fabrics/TunnelEndpoints/Mirrors, and re-quarantine as
  before. Hand-built snapshots whose Config describes no interface rows
  keep their author's rows (revalidated only), preserving the #12213
  retained-row isolation contract.
- `prepareSnapshotForApply` records whether revalidation moved a row on
  the new `Manager.revalidateChangedIfindex` field (guarded by `m.mu`);
  `applyCompiledSnapshot` (pkg/dataplane/userspace/manager_compile.go)
  consumes and clears it after `prepareSnapshotForApply` and, when set,
  calls `reconcileInterfaceAttachmentsForRefreshLocked(snap)` before
  plan classification and publish — attaching XDP for a materialized /
  recreated ifindex the Compile shim attach never saw. The detach half
  stays at the post-acceptance `syncInterfaceAttachments` (#5485).
  Direct `prepareSnapshotForApply` callers that self-publish
  (route-overlay, scheduler, capture-authority) do not consume the flag;
  that residual is recorded below.
- Regression tests:
  - `TestRevalidateSnapshotIfindexesRecomputesEgressZoneAndLinkMetadata`
    (new, pkg/dataplane/userspace/revalidate_metadata_14333_test.go):
    link transitions Ifindex 0 -> 12 during `prepareSnapshotForApply`;
    asserts EgressZone "trust", live HardwareAddr, MTU 9000, live
    Addresses and sampled LinkUp.
  - `TestRevalidateChangedIfindexAttachesXDP14333`: asserts the
    prepare->reconcile seam attempts AttachXDP for ifindex 12.
  - `snapshot_derived_revalidate_14209_test.go` fixtures updated for the
    rebuilt base+unit row sets (5 surviving rows; tunnel base+unit rows).

## Risk

- The rebuild runs only when revalidation moved a row and the Config
  describes interface rows, so the common apply path is unchanged. It
  performs the same kernel sampling the full build already does under
  `m.mu`. Fail-closed is preserved: vanished links are dropped with
  their derived rows; quarantined zones stay quarantined; an XDP attach
  failure leaves the interface unshimmed and fence-dropped, never
  fail-open.
- Residual: snapshots published through the direct
  `requestApplySnapshotLocked` partial paths (route-overlay, scheduler,
  capture-authority) rebuild the same interface metadata but do not run
  the pre-publish XDP attach reconcile; a net-new ifindex on those paths
  attaches at the next full Compile or link-refresh, as before. The
  flag is also not consumed there, so it stays set until the next
  `prepareSnapshotForApply` resets it — no cross-publish attach is
  triggered from it outside `applyCompiledSnapshot`.
- No Rust or wire changes.
