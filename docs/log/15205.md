# #15205 (A14-05): within/trigger strict validator read only the first `trigger` sibling while the compiler applies all siblings last-wins

- **Timestamp**: 2026-10-19
  - **Action**: Made `validateEventWithinClause` aggregate every `trigger` sibling of a `within` clause (with a per-sibling empty-trigger reject) instead of validating only `FindChild("trigger")`, so an invalid or contradictory later sibling is rejected strictly exactly as if packed into the first sibling. Added RED/GREEN hierarchical regression plus same-keyword last-wins and lenient controls.
  - **File(s)**: `pkg/config/event_options_within.go` (`validateEventWithinClause`), `pkg/config/event_options_within_15205_test.go` (new), `docs/log/15205.md` (this file)

## Mechanism (origin/master `a3a455d0b2`)

- `pkg/config/compiler_services.go:2694` (`compileEventOptions`, fixed by #6771): `for _, trigNode := range child.FindChildren("trigger")` — every sibling is applied, last assignment wins; a bad later count is silently dropped (Atoi error ignored, earlier value kept) and a later `until` after an earlier `on` fills both fields.
- `pkg/config/event_options_within.go:200` (the #3751 strict gate): `trigNode := w.FindChild("trigger")` — only the first sibling was parsed by `parseEventTriggerSpecs` and checked (unknown keyword, both-on-and-until, missing/non-numeric/out-of-range count).
- So a hierarchical clause such as `within 60 { trigger on 3; trigger on typo; }` or `within 60 { trigger on 3; trigger until 5; }` committed clean on the strict path: the validator saw only the valid first sibling. The runtime #3751 belt fails closed (dead policy), so there was no fail-open shape — this is a strict-gate escape (accepted-but-inert / contradictory config the operator believes is enforced).

## Change

- `validateEventWithinClause` now iterates `w.FindChildren("trigger")`, aggregates `parseEventTriggerSpecs` results from every sibling, and runs the unchanged downstream checks (unknown keyword → both-on-and-until → per-spec count presence/range) over the aggregate. Message texts are unchanged.
- A sibling yielding no spec and no unknown token (bare `trigger;`) is rejected with the existing "trigger requires `on` or `until` with a `<count>`" message rather than being masked by an earlier valid sibling — parity with a lone empty trigger, which `len(specs) == 0` already rejected.
- Same-keyword valid re-sets (`trigger on 3; trigger on 9;`) still pass and keep the compiler's #6771 last-wins value (9); the compiler is untouched. Lenient (load/peer-sync) behaviour is preserved per sibling aggregate: the same messages downgrade to warnings.

NOT changed: `compileEventOptions`, the #3751 seconds/count bounds, the engine's within-matching, or any neighbouring gate.

  - `TestEventWithinSecondTriggerSiblingRejected15205` (8 subtests): second sibling non-numeric count, out-of-range count, contradictory `until` after `on`, contradictory `on` after `until`, unknown keyword, missing count, empty `trigger;`, block-form contradictory sibling. RED on `origin/master` (all accepted / no warning); GREEN after the fix.
  - `TestEventWithinDuplicateTriggerLastWinsControl15205`: valid same-keyword duplicate siblings compile with the last value (on→9, until→11).
  - `TestEventWithinSecondTriggerSiblingLenient15205`: malformed second sibling downgrades to a `cfg.Warnings` entry on `CompileConfigLenient`.
- Controls staying green: `TestEventWithinValidAcceptedAtCommit`, `TestEventWithinRejectedAtCommit`, `TestEventWithinBothOnUntilRejected`, `TestEventWithinLenientDowngradesToWarning` (#3751).
- Pre-existing failure (not introduced here, verified identical with the production change reverted): `TestDuplicateTriggerOnTakesTheLastValue6771`, `TestDuplicateTriggerUntilTakesTheLastValue6771`, `TestSingleTriggerIsUnchanged6771`, `TestMultipleWithinClausesUnaffected6771` fail on `origin/master` because they use event name `ev1`, rejected by the later #14660 known-event gate; `TestContradictoryTriggerStillRejected6771` passes. The new control above re-pins the #6771 last-wins behaviour with a valid event name.

## Risk

- A config that previously committed only because its invalid/contradictory trigger hid in a second-or-later sibling now fails strict commit; that is the intended fail-closed direction. The lenient load/peer-sync path still boots such a persisted config with a warning, and same-keyword re-sets (ordinary Junos override behaviour) are unaffected.
