# Issue #16744: SessionCreate flow-export opens ride the 1000/s dataplane-event limiter

## Why

Since #15946/#16303, `SESSION_CREATE` RT_FLOW frames (type 15) are the
sole open-side input to the Go NetFlow v9 / IPFIX flow exporters: the
daemon's `trackFlowOpen` feed (`pkg/daemon/daemon_flowexport.go`)
registers the flow with the active/inactive tracker and makes the
single 1-in-N sampling decision at SESSION_OPEN, and a close whose open
was shed exports nothing (`CloseFlow` reports no sampled open). Only
`SessionClose` received the #14609 separately sized budget
(8192/s + burst 8192 per zone); `SessionCreate` still rode the shared
per-(kind, zone) GCRA at the production default 1000/s + burst 1024.
Above ~1000 creates/s from one zone the limiter sheds the excess as
`RateLimited` before the frames ever reach Go, so flow export is
systematically missing most flows exactly at ordinary busy-edge
connection rates, and collector scale-ups are wrong by the shed factor.
Enforcement is unaffected.

## What

Give `SessionCreate` a separately sized GCRA budget in the Rust
producer, mirroring #14609 for closes:

- `DataplaneEventRateLimitConfig` gains
  `session_create_events_per_second` / `session_create_burst`
  (production default 8192/s + burst 8192 — `CHANNEL_CAPACITY`, the
  session channel's drain capacity). The shared telemetry fields keep
  their 1000/s + 1024 defaults for PolicyDeny / ScreenDrop / FilterLog.
- `DataplaneEventRateLimiter` keeps one fixed bucket array (no new
  allocation); only the SessionCreate row reads the new limit via
  `limit_for`. GCRA construction reuses `runtime_for`.
- The bounded per-kind queue budget is unchanged and remains the flood
  bound above the rate: any queue-full / disconnected shed is still
  counted per kind and surfaced in
  `ProcessStatus.event_stream_session_create_{sent,dropped,rate_limited,queue_full,disconnected}`
  (#10979) and the
  `xpf_userspace_event_stream_producer_frames_total{outcome="session_create_*"}`
  Prometheus series — i.e. CREATE shed counts stay visible in
  flow-export status (they were already surfaced there; the fix keeps
  that accounting and makes the rate shed below channel capacity zero).
  Below channel capacity a create is never rate-shed, so the Go sampler
  and the IPFIX/v9 sampling metadata run over the true open population
  and the exported fraction at rate N stays the configured 1-in-N.
- Every existing `DataplaneEventRateLimitConfig` literal (all in tests,
  unlimited `0/0`) gains the two fields as `0/0` (unlimited),
  preserving its intent. The one finite close test
  (`test_emit_session_close_rt_flow_rate_limited_is_counted`) gains the
  create fields at the same `1000/s burst 2` values it already sets for
  closes (its shared fields stay unlimited, so only the close limiter
  can shed in that cell).
- NOT changed: the Go sampler, IPFIX/v9 encoders, the wire format, and
  the queue-budget sizing. The close-time fallback alternative was not
  taken: with the open delivered, no Go-side reconstruction is needed.

## Validation

RED on pristine `origin/master` (be343c1e2a + only the new test
transplanted): `cargo test -- test_session_create_survives_production_rate_16744`
failed with `batch 2: no create may be rate-shed ... left: 471, right: 0`
— under the production-default config the shared 1000/s GCRA admitted
the first ~1029 creates and rate-shed the rest.

GREEN after the fix: the same test passes (5000/5000 delivered,
`session_create.rate_limited == 0`, `queue_full == 0`, batched at 500
with production-style queue-budget release between batches so the
in-flight budget is not the gate), plus a counted rate-limit pin for
creates (`test_emit_session_create_rt_flow_rate_limited_is_counted`),
the adapted producer per-kind/zone pin, and the unchanged #14609 close
acceptance cell — 4 passed. The full `event_stream::` suite runs
126 passed / 1 failed, where the single failure
(`pptp_open_frame_carries_the_call_id_pair_13965`) also fails
identically on pristine be343c1e2a (pre-existing, unrelated).

## Risk

A sustained create stream above 8192/s per zone can still shed at the
queue budget when the daemon drains slowly; that shed is bounded,
counted, and operator-visible (above), unlike the previous invisible
1000/s rate shed. The create rate ceiling is now the channel drain
capacity rather than an arbitrary telemetry flood number, matching the
close path's own bound. No wire, Go, or sampler change.
