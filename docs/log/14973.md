- **Timestamp**: 2026-10-18
  - **Action**: SSH password lockout (`applySSHPAMFaillock`, #11492) now enforces faillock on `root`, ignores comment mentions of the module, and is stripped again when the SSH apply that installed it fails (#14973, D31-05). Three legs: (1) the managed `pam_faillock.so` preauth/authfail/authsucc lines carry `even_deny_root`, so root password guessing is locked out after 5 failures instead of being exempt; the pre-#14973 bodies (without `even_deny_root`) are still recognised by `stripPAMFaillockBlock` as known-good variants, so hosts already carrying the old rules are upgraded in place (strip + re-add) and remain strippable on rollback instead of failing every later apply with "managed PAM faillock block was modified" — a tampered body is still refused. (2) `renderSSHPAMFaillock` now decides "admin already has faillock" via `hasActivePAMFaillock`, which only counts non-comment, non-blank PAM lines whose module field is `pam_faillock.so` (or a path ending in it); a comment merely mentioning the module no longer suppresses the managed install, while a real admin rule still suppresses it. (3) `applySSHConfig` records whether its `applySSHPAMFaillockChanged()` call actually changed `common-auth` and, via a deferred check on the final named result, calls `stripSSHPAMFaillockOnRollback` whenever the apply fails — covering drop-in write, `sshd -t` validate, sshd reload, drop-in/legacy removal, and sshd-config render failures without per-site wiring, and never stripping pre-existing admin faillock (no-op when this apply changed nothing).
  - **Validation**: Targeted tests in `pkg/daemon/ssh_faillock_14973_test.go`: managed lines carry `even_deny_root`; comment-mention stack gains the rules (comment preserved, re-render idempotent) while a real admin rule still suppresses install; legacy pre-#14973 rules upgrade to byte-identical fresh install, strip back to stock, and a tampered body is refused; `applySSHConfig` with reload, validate, drop-in-write, and content-build failures all leave `common-auth` at stock, while a successful apply keeps the rules. Existing #11492 tests (stock install, idempotence/reversibility, custom stack untouched, appliance skip) stay green. See PR for full suite results.
  - **Risk**: On non-appliance hosts, a failed SSH apply now also rewrites `common-auth` once more to remove rules it just installed; if that strip itself fails it is logged and joined into the apply error, never masking the original failure. Hosts with an admin-installed faillock, appliance hosts, and unsupported PAM stacks are untouched. No wire/config-schema change.
