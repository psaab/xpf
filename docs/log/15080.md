# #15080 — grpcapi: bound streamDiagCmd's scanDone wait so a parked scanner cannot pin the diag slot (A43-01)

- **Timestamp**: 2026-10-18
- **Mechanism**: `streamDiagCmd` (`pkg/grpcapi/server_diag_ping.go`) waited
  with no select or bound: `cmdErr := c.Wait(); pw.Close(); scanErr :=
  <-scanDone`. `c.Wait()` joins exec's internal copy goroutine, which
  stays blocked in `pw.Write` while the scanner goroutine is parked
  inside `sendFn` (it holds the `io.Pipe` read end and is not reading),
  so Wait never returns and the handler never reaches its
  `defer release()` — the process-wide `diagcmd.DefaultLimiter` slot
  (cap 4, shared with REST) stays held. #14980 bounded the handlers'
  per-line `Send` via `sendDiagFrame`, but `streamDiagCmd` itself kept
  the unbounded wait: a caller whose `sendFn` only parks until its own
  context is done (the A43-01 scanner-goroutine leg), or any direct
  caller with a raw unbounded `Send`, wedged this wait until the full
  exec timeout. Source anchors at filing: `server_diag_ping.go:63-68`
  (Acquire + defer release) and `:72-74` (raw `stream.Send`), since
  re-anchored by #14980; the residual unbounded wait is the same
  mechanism on the surviving leg.
- **Action**: `streamDiagCmd` now runs `c.Wait()` in a worker and
  selects over `waitDone`, `scanDone`, and `ctx.Done()`. The
  `waitDone`-first path is unchanged (`pw.Close()`, drain `scanDone`,
  scan error wins, child exit error delivered as a final line). The
  `scanDone`-first path (send/scanner failure) joins Wait — already
  being reaped by the scanner's deferred `cancel()`+`pr.Close()` —
  and reports `scanErr`, not the internal cancel's ctx error. On
  `ctx.Done()` it closes both pipe ends — `pr.Close()` unblocks the
  copy goroutine's `pw.Write` — joins only Wait under a bounded wait
  (`requestExecWaitDelay`, the existing 5s post-kill pipe-drain
  window), and returns `ctx.Err()` WITHOUT joining `scanDone`: a
  `sendFn` parked independently of ctx (a raw `Send` to a client
  keeping its connection open) cannot be interrupted from here and
  joining it would re-wedge the return; that leg remains bounded by
  the caller's per-write Send timeout (#14980), whose sever ends the
  scanner. NOT changed: the handlers, `sendDiagFrame`, the REST
  surface, monitor handlers, or `buildPrimaryServer`
  keepalive/MaxConnectionAge (the handler-return path already cancels
  the parked Send via grpc-go WriteStatus).
- **File(s)**: `pkg/grpcapi/server_diag_ping.go`,
  `pkg/grpcapi/diag_scan_wait_15080_test.go` (new),
  `pkg/grpcapi/README.md`, `docs/log/15080.md`
- **Validation**: New `diag_scan_wait_15080_test.go` (3 tests). RED on
  unmodified master (`ac543c5b9e`): `TestStreamDiagCmd15080CtxCancelUnblocksParkedSend`
  failed with "streamDiagCmd did not return within 5s of ctx cancel
  while sendFn parked: c.Wait() wedged on the scanner goroutine, diag
  slot pinned (#15080)" and `TestStreamDiagCmd15080SendTimeoutSeversRealPath`
  failed with "streamDiagCmd did not sever within 5s of a parked Send:
  scanDone wait wedged (#15080)"; the draining control passed. GREEN
  post-fix: ctx-cancel returns `context.Canceled` promptly, the
  real-path sever returns `context.DeadlineExceeded` with the slot
  transferred (InFlight=1 while parked) then freed on unblock, and the
  draining control (lines in order + exit error as final line) passes.
  Adjacent suites stay green: `TestDiagSendBound14980*` (6),
  `TestStreamDiagCmd*`, `TestDiagConcurrencyLimitGRPC*`;
  `go vet`/`gofmt` clean. Full-repo suites are the parent's gate.
- **Risk**: Fail-closed only on the already-cancelled path — a healthy
  stream is untouched (the ctx branch fires only when the context is
  done, at which point the RPC is being torn down anyway). On the
  ctx path the scanner goroutine is abandoned to the caller's Send
  bound rather than joined; it exits when that Send unblocks (handler
  return cancels the stream ctx in real grpc-go), exactly the
  #14980/#9891 worker lifetime. No behaviour change outside the
  cited wait.
