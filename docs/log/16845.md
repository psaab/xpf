## Mechanism

`security ike gateway <g> address 0.0.0.0` (or `::`), `ipsec vpn <v> gateway 0.0.0.0`, and `dynamic` + `remote-identity inet 0.0.0.0` compiled to non-empty `Address`/`RemoteIDValue` strings, so every `== ""` gate passed. Render resolved `remote_addrs = 0.0.0.0`, pinned `remote.id = "0.0.0.0"`, and emitted PSK owners `[0.0.0.0 %any]` — all ID_ANY to strongSwan, so any holder of any on-box PSK could authenticate into the tunnel from any address.

## Fix

One predicate family, one place (`pkg/config/compiler_ipsec.go`, importable by both packages with no cycle):

- `IsAnyIPsecSelector(s)`: `"", %any, %any6, *`, or `netip.ParseAddr(s).Unmap().IsUnspecified()`.
- `IsAnyIPsecRemoteIdentity(type, value)`: `*`/`%any`/`%any6` under any type; the IP check for `inet`/`inet6`.
- `HasDiscriminatingIPsecAddress(list)`: at least one non-unspecified IP literal (supersedes `hasIPLiteralAddress`, which counted `0.0.0.0` as discriminating).

Strict gate: responder-only arm requires a discriminating remote-identity; non-responder arm requires a discriminating remote-identity, dynamic hostname, or discriminating address; inline arm requires a discriminating endpoint — ID_ANY spellings get a #16845 diagnostic naming the fix. Render: `pskPeerSelectors` drops unspecified list entries and ID_ANY remote-ids; the selector-empty (#16708) belt and the responder (#14591) belt then skip the VPN with its sibling VPNs unaffected.

## Operator-visible delta

Authoring a wildcard peer (`address 0.0.0.0`, inline `gateway 0.0.0.0`, `remote-identity inet 0.0.0.0`, …) on a PSK VPN now fails strict commit with a #16845 error; tolerant loads warn and the renderer skips that VPN. Real addresses, discriminating remote-identities, mixed `0.0.0.0,<real-ip>` lists (scoped by the real IP only), and pubkey VPNs are unchanged.
