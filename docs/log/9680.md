## Design

The routing domain comes from the one place that already has it, the flow's forward `SessionKey`:
- **Allocate:** the poll path passes `flow.forward_key.routing_domain`.
- **Release** (`release_nat64_allocation_with_mode`) and **synced reserve** (`reserve_synced_nat64_allocation_with_holder`): both already receive that forward key (`is_reverse` returns early), so they read `key.routing_domain`.

The three sites therefore agree by construction. The constant's own comment warned that they must, or a release silently misses its allocation and leaks the pool entry.

`allocate_source` (test-only, `#[cfg(test)]`) keeps its signature and passes 0, the default routing instance, so the 25 existing test callers are unchanged.

**HA:** `routing_domain` is config-derived (`StableRoutingInstanceTableID`) and already on the session-sync wire (#7160). The standby therefore reserves under the same scope the active allocated with, and each node releases with the key it reserved or allocated under.

**Not changed:** reverse keys stay domain-agnostic by #7160 design. Reply demux across tenants is the issue's lab follow-up, not this change.

## Validation

- **New cells** in `userspace-dp/src/nat64_tests.rs` (4):
  - identical tuples in two routing domains get distinct bindings, and the same-domain control reuses its own;
  - release is keyed by routing domain: a wrong-domain release leaves the other tenant's binding live, and the own-domain release frees it (a fresh port on re-allocation, the #4381 idiom);
  - a synced reserve keyed by routing domain: tenant A's reservation is not handed to tenant B's identical tuple, and tenant B's synced reserve joins its own allocation;
  - poll-path wiring: the single production `allocate_source_for_worker` call's last argument is `flow.forward_key.routing_domain`. The cells above call the allocator directly, so without this cell they would pass even if production kept passing 0.
