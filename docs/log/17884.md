# #17884 — Keep the DHCP lease seed behind the restart barrier

- **Timestamp**: 2026-10-26
  - **Action**: The 20-second apply wait used to continue to control-socket readiness and lease-add after its deadline even when the takeover generation had not been applied. The post-start seed is the only backstop after a failed memfile pre-seed, so this could send lease-add to the old Kea, receive `Invalid subnet-id`, and lose the backstop permanently. The wait now logs at the former deadline but continues until the wanted families publish the apply generation or the caller context is canceled. The daemon discards the pre-wait lease values and re-fetches each family's peer snapshot after the apply/socket waits, so peer lease lifetimes age through the wait before re-anchoring; expired rows remain dropped.
  - **File(s)**: `pkg/daemon/daemon_dhcp_lease_sync.go`, `pkg/daemon/daemon_ha.go`, `pkg/daemon/dhcp_seed_order_16855_test.go`, `debian/changelog`, `docs/log/17884.md`
  - **Validation**: The regression failed under a simulated fail-open revert with `oldAdds=1 newAdds=0` while restart was blocked. With the fix restored, the final focused seed/lease suite `GOCACHE=/var/worktrees/.cache/go-build GOTMPDIR=/var/worktrees/.cache/go-tmp go test ./pkg/daemon -run 'TestSeed|TestDHCPLease|TestWait' -count=1` passed, covering survivor lifetime aging, expiry of a two-second peer lease, shutdown cancellation, and existing seed ordering. An earlier full `go test ./pkg/daemon -count=1` did not pass: other package failures included DNS/feed rollback, DHCP config-filter, nft netlink parity, Unix-socket binds rejected with `invalid argument`, and a factory-reset panic; the run also logged permission-denied attempts to mutate `/proc` and `/var/lib/xpf`.
  - **Risk**: If a takeover generation never becomes applied, the sole post-start seed waits rather than seeding an unverified Kea process. The HA caller now uses `applyCancelCtx()`, so daemon shutdown cancels the wait; while the daemon remains live, a permanently unapplied generation can still leave the goroutine waiting indefinitely. The pre-start memfile pre-seed remains the primary protection, and a later successful apply allows the backstop to continue.
