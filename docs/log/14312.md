# Issue #14312 — ports on non-port-bearing application protocols fail closed in the Rust helper

- **Issue:** psaab/xpf#14312 (deep-review D1-01, zone-enforcement-policy-100;
  research-validated MATERIAL, boundary-only severity downgrade).
  Lane branch: `fix/14312-campaign` off `origin/master`
  `5b122dda5ebb23aec9c283ef7cbddca0874b9338`.
- **Scope:** Rust helper boundary only (`userspace-dp`). No Go change:
  the Go strict gate and expansion drop detector already poison these
  terms before the wire (see below).

## Defect (present at base)

`parse_applications` (`userspace-dp/src/policy.rs`) rejected only the
two #3712 ICMP-field combinations (`icmp-code` without `icmp-type`;
`icmp-type`/`icmp-code` on a non-ICMP protocol). It never rejected a
non-empty `source_port`/`destination_port` on a protocol other than
TCP/UDP. `CompiledApplications::from_matches` then compiled such a
term into a wrong-behaving matcher:

- `icmp`/`icmpv6` **with** `icmp_type`: steered to `icmp_constraints`,
  ports silently discarded (the comment claimed "ICMP terms never
  carry ports in practice; … a stray port is irrelevant"). A `Permit`
  broadens to every message of that type/code — arbitrary ICMP Echo
  Identifiers match a term authored as e.g. `destination-port 80`.
- `icmp` without type, `gre`, `esp`, `ospf`, `sctp`, `ah`, `vrrp`,
  `igmp`, `pim`, `egp`, `ipip`, or any numeric non-TCP/UDP protocol:
  a range/exact term keyed on extracted ports the packet never
  presents (portless protocols present `(0,0)`, `l4_present=false`).
  A `Deny`/`Reject` with `destination-port 80` never matches and
  falls through to a later `Permit` / default-permit — fail-open.
  A `0-N` range matches flowless traffic of that protocol.

Reachability is boundary-only: Go `validateApplicationSpecsStrict`
(#3373) rejects port-on-non-port-bearing at strict commit, and
`ApplicationMatchDrops` (#9525) flags the same shapes so the expansion
refuses the reference and lowers the policy to the `__unsupported__`
sentinel, which the helper already rejects whole-snapshot. The gap is
the corrupt / hand-built / mixed-version / leniently peer-synced
snapshot delivered over the control socket — exactly the layer the
#3712 `InvalidApplicationIcmpFields` backstop (whose doc calls itself
"the helper-boundary backstop for the lenient / peer-sync /
corrupt-snapshot path") and the filter-side #3723
`UnsatisfiableFilterCrossField` exist for. The policy side had no
mirror.

## What

- `userspace-dp/src/policy_snapshot_error.rs`: new
  `SnapshotIntegrityError::InvalidApplicationPortProtocol
  { rule_id, application, reason, protocol }` with a `Display` arm,
  documented in the #2124/#3261/#3367/#3711/#3712 fail-closed family
  and as the policy-side mirror of #3723.
- `userspace-dp/src/policy.rs`:
  - `ParsedApplications` gains `invalid_port_protocol:
    Option<(String, &'static str, u8)>` (first offender, mirroring
    `invalid_icmp`).
  - `parse_applications` records it when the **parsed** port ranges
    (so named ports like `dns` count exactly as the matcher sees
    them) are non-empty and the resolved protocol is neither TCP nor
    UDP — the `ip_proto::has_l4_ports` set. Destination is reported
    before source, mirroring Go `ApplicationMatchDrops` ordering.
    SCTP is included (wire ports exist but are never extracted).
    Numeric spellings (`"47"`) are caught because the check keys on
    the resolved protocol number.
  - `parse_policy_state_with_counters` rejects the whole snapshot
    with the new error after the #3712 check (a term violating both
    surfaces the earlier diagnostic first). Rejecting the whole
    snapshot keeps the previous good state on the preflight; a fresh
    boot keeps default-deny — action-agnostic.
  - The stale `from_matches` comment ("a stray port is irrelevant")
    now states the boundary reject instead. `from_matches` itself is
    unchanged: its only production caller is fed by
    `parse_applications`, and direct unit-test construction of
    `ApplicationMatch` remains a test seam.
- `userspace-dp/src/policy_tests.rs`: nine tests via
  `parse_policy_state_with_counters` asserting
  `Err(InvalidApplicationPortProtocol)` with exact
  rule/application/reason/protocol fields —
  icmp typed+dst-port, icmp untyped+dst-port, icmpv6 typed+src-port,
  gre dst-port, esp src-port, ospf dst range `0-1023`, sctp dst-port,
  numeric `"47"` dst-port — plus a guard that tcp/udp with ports and
  portless icmp (typed and untyped)/gre/esp terms still compile.

Precedence / non-goals: a term that is both unparseable
(`dropped_any`) and port-invalid still surfaces
`UnrepresentableApplicationProtocol` first (existing order); a bogus
port string on a non-port protocol surfaces as dropped, not
port-protocol — correct, because no parsed range exists to mis-match.
No special-casing of test inputs; the check is purely
`(parsed ports non-empty) && protocol ∉ {TCP, UDP}`.

## RED -> GREEN proof

- **RED (base `5b122dda5`, tests-only patch applied to a separate
  base worktree):** the eight `*_rejects_whole_snapshot` tests fail —
  `parse_policy_state_with_counters` returns `Ok(state)` (the
  wrong-behaving term compiles) instead of the new error. The
  `valid_port_protocol_terms_still_compile` guard passes on base
  (it pins no-false-reject behaviour, not the defect).
- **GREEN (lane):** `cargo test --bin xpf-userspace-dp --
  rejects_whole_snapshot valid_port_protocol` — all nine new tests
  pass, together with the neighbouring #3712 rejects (17 tests in
  the filtered run, 0 failed).

## Risk

Fail-closed only on snapshots the Go producer never emits: a normal
Go-lowered snapshot carries ports only on TCP/UDP terms, so no
legitimate config changes behaviour. The only new reject path is for
corrupt/hand-built/mixed-version input, where the preflight keeps
the previous good `PolicyState` (fresh boot: default-deny) instead
of compiling a dead deny or a broadened permit. No hot-path change:
validation runs once per snapshot parse, not per packet.
