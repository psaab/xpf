# #16580: DHCPv4 relay-level `active-server-group` rejected, v6 inherits it

- **Timestamp**: 2026-10-24
- **Action**: The Junos relay-level `active-server-group` (global
  default for groups without their own) was rejected for DHCPv4 by
  the #9552 closed-world gate — the schema declared only
  `server-group`/`group`/`dhcpv6` under `dhcp-relay` — with a
  message claiming the rejected config "commits clean … and relays
  nothing", while DHCPv6 accepted and inherited the same
  family-level statement (#9553). On the tolerant path the v4
  default was dropped, so groups without their own server group
  relayed nowhere. Fixed by declaring the v4 relay-level leaf in
  the schema (the #9552 gate reads its permitted set from the
  schema, so it permits the token automatically), recording it as
  `DHCPRelayConfig.ActiveServerGroup` in `compileDHCPRelay`, and
  inheriting it into every v4 group lacking its own — the compiled
  group carries the effective value, mirroring the v6 compiler.
  All spellings are read: braced/flat-set child, singly-elided tail
  on the relay node, fully packed tail on `forwarding-options`
  (new `dhcpRelayV4PackedNode16580` synthesizer plus a packed-run
  expansion for the single-child shape the #8768 splitter declines
  because server addresses are not schema children), with
  `(dhcp-relay, active-server-group)` admitted to
  `compactNormalizeInScope` and `packedStatements` on the relay and
  group nodes. #11693 validation now judges the effective value
  (group's own, else relay default): an undefined default refuses
  strict and warns lenient. The strict #9552 message now describes
  the rejection; "compiles to NOTHING" remains only on the tolerant
  path where it is true. `show` (CLI + API) and the v4 runtime
  (`computeDesired`) fall back to the relay default like v6.

- **Validation**: New tests cover the acceptance row (relay-level
  row commits, compiled group carries `sg`) in braced, flat-set,
  singly-elided, fully-packed and packed-in-brace spellings; the
  decisive override check (global default + group override);
  #11693 on the effective value (undefined default strict-refuses,
  lenient warns and keeps the attempted value; no default anywhere
  still refuses; valueless leaf invents nothing); the tolerant
  inheritance leg (previously only inferred); and the reworded
  strict message. `TestSpellingGateMembersAreRecorded7484` /
  `TestMultisiteAdmissionsAreRecorded8921` were already failing on
  unmodified master at this base (unrelated drift); only the single
  new COMPARED row and the +1 gate floor for this leaf were updated
  by hand — the mass regeneration was reverted.
  `TestDHCPRelayInterfaceRefWarnings9406` and
  `TestCompileGolden4406` fail identically on unmodified
  `origin/master`; base-attributed, unrelated.
- **Residual**: None known. The relay-level default is compiled
  into each group, so existing runtime/show consumers needed only
  the defensive fallback for hand-built configs.
