# #12154 — Restore bootstrap lifeline content on first-commit rollback

- **Issue**: #12154 — first-commit rollback kept the configured `10-xpf-fxp0.network` winner by filename instead of preserving the bootstrap lifeline content.
- **Branch**: `fix/12154-campaign-pub`
- **Worktree**: `/var/worktrees/campaign-pub/wt-12154`
- **Base**: `83b5c955335f16d8c7835f206b210ce3ae1a5fe5`

## Why

A first non-empty config can cause `networkd.Apply` to overwrite the bootstrap lifeline's `10-xpf-fxp0.network` with candidate addressing. Rollback skipped that path solely by name, leaving the abandoned configuration in place while FRR and the dataplane were cleared.

## What

- Capture exact pre-takeover `fxp0.network` bytes on successful bootstrap exit,
  whatever they are — including an absent or unmarked file (captured/present
  flags distinguish the shapes; the marker alone cannot tell console-only
  state from a lost lifeline).
- Restore the snapshot only on genuine first-commit rollback. A later #9615
  safe-state entry never writes fxp0 from stale day-0 state; confirming the
  first-commit window clears the snapshot.
- Stop abandoned DHCP clients on first-commit rollback. Keep `.link` rename
  files and retire other xpf-written `.network` files; reload networkd after
  any successful file removal or lifeline restoration.
- If the daemon restarted inside the first-commit window, its in-memory
  snapshot is unavailable. A marked lifeline may be retained; a missing or
  unmarked file reports DEGRADED rather than claiming restoration.
- Update rollback logging and daemon documentation for the first-commit-only
  restore scope and in-memory snapshot limitation.

## Risk / remaining acceptance

No live cluster was mutated. The regression exercises real config application,
networkd file generation, and rollback timing against temporary files; command
execution is stubbed. It does not prove kernel address reassignment or live
networkd/next-boot behavior on an appliance.

The snapshot is process-local. After a daemon restart during the first-commit
window, a marked file may be retained, while a missing/unmarked file is reported
DEGRADED. Exact restoration of the prior process's snapshot needs durable
persistence and remains follow-up work.
