# Issue #15059 — management-DHCP nameserver rule diverted all host traffic (A36-01 residual)

- **Timestamp**: 2026-10-18
- **Why**: #11385 installed destination-only `iif lo` lookup/shadow rules (2500/2501) into table 999 for every management-DHCP nameserver. #14971 (D31-03, merged before this issue was filed) scoped those rules to `ipproto udp|tcp dport 53` (UDP 2500/2501, TCP 2502/2503), so non-DNS traffic already keeps its main route on current `origin/master` — verified by re-anchoring: `mgmtDNSRulePairs` sets `IPProto`/`Dport`, `managedMgmtDNSRule` classifies unscoped/wrong-proto/wrong-port rules invalid, and `docs/dns-ownership.md` still described the stale unscoped pair. The surviving #15059 leg is the fix direction's second sentence: a nameserver already covered by a main-table connected/static route, or exactly matching a configured control-plane peer, was still steered (DNS-only) into table 999 and published, diverting its DNS from the main route the existing topology selected.
- **What**: `pkg/daemon/daemon_mgmt_dns_rules.go`: `mgmtDNSRefusedNameserver` refuses a nameserver covered by a main-table `RTPROT_KERNEL` connected (via existing `mgmtRouteIsConnected`) or `RTPROT_STATIC` route, or exactly equal (after `Unmap`) to `chassis cluster peer-address`/`fabric-peer-address`/`fabric1-peer-address`; dynamic/default-only coverage does not refuse. `mgmtDNSRulePairsFiltered` (used by new `reconcileMgmtDNSRulesFiltered`, wrapped by legacy `reconcileMgmtDNSRules`) drops refused servers with a `SECURITY:` warning, so no pairs install and stale pairs leave the wanted set and are removed. `Daemon.applyMgmtDNSRules` loads the active config + `mgmtDNSMainRoutes()` (main table, both families) and fails closed (error, no steering) if the inventory cannot be read. `pkg/daemon/daemon_dns.go`: `mergeDNSInputWithMgmtDNSRulesRefused` + `dnsInputLocked` compute `mgmtDNSRefusedSet` (fail-closed: all mgmt servers refused if main inventory unreadable) so a covered/peer server is never published even with a complete installed pair. `docs/dns-ownership.md` updated from the stale #11385 unscoped description to the #14971 scoped pairs plus #15059 refusal. NOT changed: rule priorities/proto/port scope, readiness semantics, non-management leases, static `system name-server` entries.
- **Files**: `pkg/daemon/daemon_mgmt_dns_rules.go`, `pkg/daemon/daemon_dns.go`, `pkg/daemon/mgmt_dns_refusal_15059_test.go`, `docs/dns-ownership.md`, `docs/log/15059.md`.
- **Red-before**: New `TestMgmtDNSRefusesNameserverCoveredByMainRouteOrPeer15059` / `TestMgmtDNSRefusalIsExactPeerNotPrefix15059` on pre-fix tree: build failed (`reconcileMgmtDNSRulesFiltered` undefined — the refusal path did not exist); the scoped-rule mechanism itself was already GREEN on master via #14971, so no duplicate scoping change was made.
- **Green-after**: Targeted `go test ./pkg/daemon/ -run 'TestMgmtDNSRefus|TestMgmtDNSRules|TestMergeDNS|TestMgmtDNSRule'` passes — refused covered/peer servers get zero rules and are unpublished with warnings, uncovered server gets 4 scoped rules and publishes, non-peer neighbour in a peer's /24 still steers, control (no coverage/peer) installs all 12 rules. Live netns `TestMgmtDNSRulesSteerOnlyDefaultContextHostLookups11385` passes under `unshare -rn` (non-DNS `RouteGet` stays on main WAN; `dport 53` steering is the scoped pair).
- **Validation**: `gofmt -w` on changed Go files; targeted daemon tests above; full `pkg/daemon` suite run (see PR).
- **Risk**: A management nameserver that is intentionally main-reachable now resolves via main instead of table 999 — that is the intended #15059 behaviour; operators wanting mgmt-VRF DNS for such an address should use a nameserver not covered by main/peer topology. If the main-table list fails, mgmt DNS steering/publication pauses fail-closed until the next apply/DHCP reconcile. DNS over non-53 transports (DoT/DoH) remains unsteered as before.
