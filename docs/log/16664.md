# Issue #16664: VRF device name for `vrf-`-prefixed routing-instance names

- **Timestamp**: 2026-10-25
  - **Action**: `diagcmd.VRFDeviceName` returned an already-`vrf-`-prefixed
    instance name unchanged (#2143 exactly-once guard, residual via
    #15265/#15594), while the daemon/FRR always realise instance `N` as
    `vrf-`+`N` with no canonicalisation. Instance `vrf-X` therefore resolved
    to sibling instance `X`'s VRF (or a nonexistent device) for
    ping/traceroute (`ip vrf exec`), DDNS `SO_BINDTODEVICE`
    (`pkg/ddns/backend_bind.go`) and HA routing-transfer readiness FRR
    queries (`pkg/frr` `Get*VRF` → `daemon_ha_routing_readiness.go`). Fixed
    by adding `routing.VRFDeviceName` in `pkg/routing/vrf.go` — the package
    that creates the device — prepending `vrf-` unconditionally (empty stays
    empty), migrating every `"vrf-"+name` site inside `pkg/routing`
    (`vrf.go`, `routes.go` `GetVRFRoutes`, `tunnel.go`,
    `tunnel_keepalive.go`, `rib_group_return_9819.go`) to it, and pointing
    `diagcmd.VRFDeviceName` (kept as the diag-surface delegate),
    `pkg/frr` `frrVRFName` and `pkg/ddns` `resolveBindConfig` at it, so an
    instance named `vrf-mgmt` maps to `vrf-vrf-mgmt`, never the management
    VRF `vrf-mgmt`. Ping/traceroute take an instance name (not a device
    name) on all three surfaces, so no configured-instance-set resolution
    is needed; unrelated unconditional `"vrf-"+name` sites outside
    `pkg/routing` (daemon, frr render, rpm, config) already had the correct
    semantics and are unchanged.
