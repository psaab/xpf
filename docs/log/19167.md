# #19167: a transfer pre-activation is not helper-active until its routes are published

Per-issue log (see `docs/log/README.md`).

- **Timestamp**: 2026-11-16 17:40Z
  - **Action**: fix, branch `fix/19167-preactive-routes-ready` on master
    ebb32e817b. It blocks #18705's landing.
    - **Mechanism**, confirmed against the code:
      - `BeginTransferPreActivation` made the RG helper-facing Active at
        once (`effectiveHAGroupLocked`).
      - The status poll (`process_status.go:803`) compares the effective
        signature, then publishes through `syncHAWatchdogOnlyLocked` →
        `syncHAStateLocked` → `update_ha_state`. It runs outside the
        daemon's `applySem`.
      - So it could publish the RG active between Begin and the daemon's
        route republish (`daemon_ha_transfer_preactivate.go`).
    - **Fix**: two-stage entries (`transferPreActivation{until,
      routesReady}`).
      - Begin makes an entry routes-pending. The route builder already
        sees it as locally primary (`transferPreActiveLocked`), so the
        republish carries its prefixes.
      - The helper-facing view requires routes-ready
        (`transferPreActiveForHelperLocked` in `effectiveHAGroupLocked`),
        and every helper publisher and the poll signature read that one
        function.
      - `PublishTransferPreActivation(rgIDs)` marks exactly those RGs
        ready, then publishes. The daemon calls it only after a successful
        republish.
      - Re-beginning a live, routes-ready RG keeps it ready.
    - **Test fixture change, not a weakening.**
      `TestPreActivationSurvivesSecondaryRGActiveWrite18559` opened the
      window with Begin alone, which is exactly what this fix removes. It
      now opens it as the daemon does, Begin then Publish, and asserts the
      same property. A new twin pins that a routes-pending RG does not
      ride a secondary write.
