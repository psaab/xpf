# #15170 — Kernel-arm re-stamp (6d) stranded the standalone daemon offline (B17-01)

- **Timestamp**: 2026-10-19
- **Action**: The #6639 kernel-arm re-stamp (flip step 6d) was not validated
  before STOP and ran again on every rollback path. `loadKernelJournal`
  errors on any non-ENOENT read or parse failure of
  `/var/lib/xpf/kernel-upgrade.state`, so a corrupt or unreadable journal
  made `flip()` fail at 6d — after STOP and after 6a-6c had already
  repointed current/sbin/ExecStart. `recoverFromFlipFailure` (and
  `rollback()`, `executeRollback`, `restoreStaleStoppedPrevious`) then
  re-flipped to the previous version, which ran 6d again against the same
  corrupt journal, so the rollback flip failed before `StartUnit` and the
  standalone daemon stayed offline across the cut, the auto-rollback, a
  STOPPED resume and `upgrade --rollback`. Fixed on both legs the issue
  names:
  - **Pre-STOP probe** (`Runner.probeKernelArmRestamp` +
    `validateKernelArmRestampPreStop`, called from `Run` for any journal
    not yet at STOPPED): reads the kernel journal and, when a candidate is
    ARMED (shared `kernelArmRecordArmed` predicate, also used by 6d), runs
    `validateGateBin` on the xpfd of both the cut target and
    PreviousVersion. Any failure refuses the cut with the daemon still
    running (`refuse-before-STOP: the kernel-arm re-stamp ...`), before any
    journal/DB/current mutation. #6639's forward fail-closed cell is
    preserved exactly — a gate binary that cannot be proved still refuses;
    it just refuses before the STOP. Nothing armed (no journal, terminal or
    pre-ARMED state) remains a byte-identical no-op.
  - **Tolerant rollback re-flip** (`flipToleratingKernelArmRestamp`):
    `flip()` now wraps a 6d-only failure in `restampError` (after 6a-6c
    succeeded), and the three rollback call sites (`rollback()` in flip.go,
    `executeRollback` in rollback.go, `restoreStaleStoppedPrevious` in
    cutover.go) tolerate exactly that failure — logged, old arm record left
    untouched — so `StartUnit` still runs. Genuine 6a-6c failures stay
    fatal everywhere. The direction is safe: the stale record keeps naming
    a retained executable xpfd, so the candidate boot's gate refuses as it
    did pre-#6639 (candidate lost, never an unvalidated promotion), while
    the known-good daemon is back.
  NOT changed: the forward `flip()` stays fail-closed at 6d; no kernel
  journal/sidecar is ever created when nothing is armed; HA rolling keeps
  its operator-driven rollback semantics (its post-STOP tolerance only
  avoids an additional offline stranding).
- **File(s)**: `pkg/upgrade/flip.go` (flip/flipSteps split, `restampError`,
  `kernelArmRecordArmed`, `probeKernelArmRestamp`,
  `validateKernelArmRestampPreStop`, `flipToleratingKernelArmRestamp`,
  auto-rollback call site), `pkg/upgrade/cutover.go` (pre-STOP gate +
  stale-STOPPED recovery call site), `pkg/upgrade/rollback.go`
  (operator-rollback call site),
  `pkg/upgrade/kernel_arm_restamp_15170_test.go` (new), `docs/log/15170.md`

## Risk

The pre-STOP probe adds one journal read + up to two `validateGateBin`
stats per cut that has not yet stopped — pure, read-only, and a no-op when
nothing is armed. The tolerant rollback path trades a lost kernel
candidate (gate refuses on the stale record, as pre-#6639) for a running
known-good daemon; it can never promote an unvalidated kernel because the
record is left byte-identical. Residual: corruption landing between the
pre-STOP probe and 6d on the forward leg is still discovered at 6d, but
now ends with the daemon running on the previous version instead of
offline — that window is the second cell above.
