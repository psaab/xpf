# Issue 10391

## Problem

The armed FORWARD transit fence admitted every packet arriving on `xpf-usp1`, although that interface carried both userspace-adjudicated xfrm/reinject traffic and delegated no-policy traffic. Output-interface identity was not disjoint: delegated capped-`NoRoute` can resolve through the same xfrmi output as an adjudicated `MissingNeighbor`. DSCP was rejected because it is attacker-controlled packet data and changing it would alter QoS/checksums and other chain observers.

## Change

- Open `xpf-usp1` as one multi-queue TUN with queue 0 reserved for adjudicated reinjects and queue 1 reserved for delegated reinjects.
- Attach a TC ingress classifier that clears `skb->mark` for every queue and writes the exact adjudicated mark `0x58465001` only for TUN queue mapping 1. Linux records TUN queue index 0 as `skb->queue_mapping = 1`.
- Route only policy-adjudicated MissingNeighbor and synthetic IPsec passthrough through the marked queue. ForwardCandidate, NoRoute, and other unfiltered paths remain delegated and unmarked. Trusted host-local traffic remains on `xpf-usp0`.
- Replace the armed nftables xpf-usp1 ifname accept with a masked mark pinhole; unresolved/unmarked xpf-usp1 traffic remains under the fence DROP policy.

A bounded privileged attempt succeeded in creating a multi-queue TUN inside `unshare -Urn`. This worker did not have a persistent netns/runtime surface to inject packets and observe nft counters; parent validation must perform the full classifier mark smoke in the isolated datapath namespace.

Post-review correction: nftables mark mask/value encoding uses `NativeEndian`,
matching the kernel's host-order `META_MARK` register representation. The
byte-level fence test now pins the all-ones mask and exact `0x58465001` value.
