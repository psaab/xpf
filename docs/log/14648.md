# #14648 — Missing protocol publishability gate on USERSPACE_SESSIONS steering map (proto 255)

## Mechanism
Protocol 255 is `PROTO_FRAGMENT_NO_L4` / `SHIM_PROTO_FRAGMENT_NO_L4`: the
sentinel the XDP shim substitutes for a non-first/short fragment's protocol
(ports 0/0) on both IPv4 and IPv6 parses. A steering row keyed
`(family, 255, src, dst, 0, 0)` is therefore the tuple the shim probes for
*every* protocol's fragments.

Before the fix, `write_steering_row` / `publish_session_rows` /
`publish_session_map_key` in `userspace-dp/src/afxdp/bpf_map/mod.rs` had no
protocol gate at all (`bpf_map_update_elem(BPF_ANY)` of whatever
`SessionKey` arrived), and `uses_kernel_local_session_map_entry` checked
domain/discriminator/origin/disposition but not protocol. The #6923 guard
`v6_session_key_is_publishable` sits only in `publish_v6_session` on the
`sessions_v6` conntrack *mirror* — a different map from the
`userspace_sessions` steering map the shim probes — and its comment
incorrectly claimed to be the sole path into the shim-probed map.

Two unguarded vectors resulted:
- **HA sync:** `reject_incomplete_synced_key` refuses zero ports only for
  TCP/UDP (`has_l4_ports`), and `reject_unresolved_ipv6_ext_protocol`
  refuses only AF_INET6 traversable extension headers. Protocol 255 is in
  neither set, so a peer-synced proto-255 `LocalDelivery` record with
  ports 0/0 imported cleanly and published a `PASS_TO_KERNEL` steering
  row, kernel-passing every protocol's non-first fragments for that
  src→dst pair with no zone policy evaluated.
- **Live local path:** a wire packet with IP protocol 255 itself could
  form a `LocalDelivery`/live session whose steering publish wrote the
  same sentinel row (`REDIRECT` or `PASS_TO_KERNEL`).

## Fix
- `userspace-dp/src/afxdp/bpf_map/mod.rs`: new
  `steering_key_is_publishable(key)` — false exactly for protocol
  `SHIM_PROTO_FRAGMENT_NO_L4` (255), both families. Stated once at the
  point a key becomes shim-visible:
  - `uses_kernel_local_session_map_entry` now requires it, so a 255 key
    never selects `PASS_TO_KERNEL`;
  - `publish_session_rows` filters unpublishable rows (filtered, not
    errored — sibling legitimate rows still land);
  - `publish_session_map_key` (single-row sibling, covers
    `publish_live_session_key`) returns `Ok(())` without writing.
  These are the only two callers of `write_steering_row`, so every
  present steering writer inherits the gate.
- `userspace-dp/src/server/helpers/session_sync.rs`: new
  `reject_fragment_sentinel_protocol`, called from
  `build_synced_session_key` for `SyncedKeyIntent::Install` on both
  families (a correct peer never builds a 255 session identity).
  Deletes are not refused: a delete only retracts and can at worst
  under-match (#7188 discipline).
- `userspace-dp/src/afxdp/bpf_map/publish_conntrack.rs`: corrected the
  #6923 comment — it is the sole path into the *conntrack mirror*, not
  into the shim-probed steering map; the steering gate is
  `steering_key_is_publishable`.

The conntrack mirror itself is unchanged: it is a display map the shim
does not probe, and gating the steering publish removes the bypass.

## Regression
- `fragment_sentinel_never_publishes_a_steering_row_14648`
  (`afxdp/bpf_map_tests.rs`): synced proto-255 `LocalDelivery` keys on
  AF_INET and AF_INET6 never select `PASS_TO_KERNEL` and produce no
  steering-map writes in the write recorder; TCP `LocalDelivery`
  control still publishes exactly one `PASS_TO_KERNEL` row.
- `fragment_sentinel_never_publishes_a_live_row_14648`: live
  `publish_live_session_entry` of a proto-255 key writes nothing; TCP
  control still writes rows.
- `synced_import_refuses_fragment_sentinel_protocol_14648`
  (`server/tests.rs`): `build_synced_session_key` refuses a proto-255
  Install on both families with `fragment-sentinel-protocol`, while a
  proto-255 Delete still reconstructs.

RED on pre-fix `origin/master`: the synced-import test's `expect_err`
fails (255/0/0 imports cleanly) and the steering tests record a
`PASS_TO_KERNEL`/`REDIRECT` write for the 255 key. GREEN after the fix
(see PR checks).
