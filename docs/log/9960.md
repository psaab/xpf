# #9960: a declined synced delete must preserve the whole session

Base: `origin/master` `05461194f` at implementation start. Worktree: `/home/ps/git/pi-xpf/.claude/worktrees/9960-ha-decline`, branch: `fix/9960-ha-decline`.

## Reproduction and design

The under-lock `SharedRemoval::Declined` decision already preserved the shared forward and reverse rows, but the surrounding delete used the initial clone for steering and DNAT teardown, fanned `DeleteSynced` to every worker, and unconditionally returned `Applied`. That left a live shared session without forwarding state and caused the Go applied-set path to delete the BPF mirror.

A test-only, thread-local hook now sits after the initial snapshot and the #9714 early checks and before the under-lock removal. The concurrent harness synchronizes a publisher thread at that seam, installs a LOCAL replacement under the same key, and waits for publication to finish before the delete takes its lock. The decline is therefore deterministic rather than scheduler-probabilistic.

The implementation pivots on the removal result. For peer deletes (generation 0, the only production `peer_delete=true` caller), `Declined` returns immediately as `RefusedConcurrentLocalOwned`, preserving all rows and incrementing the existing peer-local-owned counter. (The under-lock predicate can also decline stale-generation deletes as `RefusedStaleGeneration`; the `Declined` arm returns whichever reason was recorded.) `Removed(entry)` supplies the exact incarnation to steering, DNAT, reverse-key, prewarm and worker teardown. The handler's `keeps_caller_rows()` classification maps both early #9714 and concurrent ownership refusals to the existing in-band token; stale-generation refusal remains excluded.
