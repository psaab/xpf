# Issue #15123 — userspace-dp: prefer exact same-family WireGuard owner on a shared listen port (A86-04)

- **Issue:** #14326 residual (report `A86-04`, 3-way MATERIAL in research
  run `research-work.AdQvt1jMKw`). Two WireGuard tunnels share listen port
  51820 in one transport instance: one bound to a specific IPv4 source,
  one bound to a specific native IPv6 source. For a native IPv6
  destination, `wg_endpoint_for_listen_port` admitted the v4-bound tunnel
  via the cross-family (#10686) clause (`source.is_ipv4() !=
  dst.is_ipv4()`), and `wg_outer_zone_matches` admitted it on the v6
  destination's owner zone alone (source zone substituted with the
  ingress zone). The first such entry in the unordered `wg_engines`
  FastMap won, so the v6 tunnel's records were fed to the v4 tunnel's
  engine, failed AEAD, returned `None` ("not a drop"), and fell back to
  the kernel/control-socket path, which delivers only firewall-local
  inner traffic and drops transit (`DropDegradedTransit`). Every
  transport record for the v6-bound tunnel on a dual-stack pair sharing
  a port was therefore lost whenever the v4 tunnel iterated first.
- **Fix (userspace-dp/src/afxdp/wg/decap.rs only):**
  - `wg_endpoint_for_listen_port` is now two-pass and order-independent:
    pass 0 returns an exact same-family owner (`endpoint.source ==
    dst_ip`, or an unspecified dual-stack wildcard bound by
    `wg_outer_zone_matches`); pass 1 returns a SPECIFIC cross-family
    candidate (#10686) only when pass 0 found no owner on that
    port/instance. An engine row whose endpoint row is missing is still
    skipped with `continue`.
  - `wg_outer_zone_matches` no longer rejects a specific cross-family
    pair outright (the #14957 hardening, which had deleted the #10686
    fallback entirely); it admits it on the destination's owner zone
    alone, exactly as #14326 specified, because pass 1 is only reached
    when no same-family listener exists. Mapped/compat destinations are
    still rejected outright, same-family destinations must still BE the
    configured source, and both destination-owner and (same-family)
    source-owner zones must still equal the ingress zone. NOT changed:
    socket-layer canonicalisation, inner mapped checks, GRE, or any
    caller signature — all three consumers (`try_wg_decap_*`,
    `is_wg_underlay_frame`, `is_wg_listener_tuple`) funnel through the
    two fixed functions.
  - Why this preserves legitimate behaviour: a v4 peer's records arrive
    as native v4 frames (exact pass, unchanged), a v6 peer's as native
    v6 frames (exact pass — the fix), a lone v4-bound listener serving a
    native-v6 destination keeps its #10686 cross-family admission
    (fallback pass), and an unspecified dual-stack wildcard is still
    bound by the destination owner zone.
- **Regression (userspace-dp/src/afxdp/wg/decap_tests.rs):**
  - `wg_same_port_dual_stack_native_v6_selects_v6_tunnel_15123`: two
    tunnels sharing 51820 (v4-bound 172.16.80.8/ifindex 400, v6-bound
    2001:db8::1/ifindex 401, both outer addresses owned in WAN). In both
    id layouts (v6 tunnel as id 1 and as id 2) the v6 tunnel's real AEAD
    record to the native v6 destination decaps via the v6 engine under
    ifindex 401; controls: the v4 record still decaps via ifindex 400,
    `is_wg_listener_tuple` recognises the v6 tuple, and the v6 record
    misaddressed to the v4 destination fails closed.
  - `wg_same_port_cross_family_only_when_no_same_family_listener_15123`:
    with NO v6 listener on the port, the lone v4-bound listener still
    decaps a native-v6 record via the #10686 fallback (ifindex 400) —
    the named control the exact-first probe must not break.
