# Issue #11765: HA executable attestation uses deployed image

## Disposition

Fixed HA executable attestation to compare live-node readbacks with deploy-time artifact manifests rather than fresh local rebuilds. Manifest schema 2 stores independent node `0` and `1` records, each with its own checkout identity and shipped xpfd/cli/helper hashes. A `NODE=0` or `NODE=1` deploy invalidates and replaces only its target slot, preserving the already-attested peer; `NODE=all` clears prior provenance and records the shared artifact in both slots after the complete deploy. Cluster gates look up each node's own slot and fail closed on a missing, invalid, or stale slot; they never fall back to a local rebuild. Raw deploys record the verified pushed binaries, while package deploys hash the staged binaries inside the exact selected `.deb`. The userspace-helper gate and manual T12/G2 check use the same per-node rules. Ledger schema 2 records the deploy-artifact meaning of `build_exe_sha256`; the additive peer build field records a different peer artifact without changing historical schema-1 rows.

No live loss-cluster deploy or gate was run for #11765 or #11845. The follow-up was verified with hermetic red/green rolling-deploy reproductions and the deploy, gate, and affected-suite selftests below.

## Red-before reproduction

At the same source revision, two `make build` invocations produced different `xpfd` bytes because `BUILD_TIME` is embedded:

- First build, `2026-10-02T04:46:44Z` (simulated deployed artifact): `3d05ccf32aed0cdf04c354638984a6895d2cf75fcac54905f22324a79b17e6fa`
- Second build, `2026-10-02T04:47:43Z` (fresh local rebuild): `93e957e24ca98b9b2ddf45ff3baca1ad949cc138db303ed287ca1010be50dc76`

A hermetic pre-fix harness invocation supplied the first hash as the live readback and the second binary as `--build-exe`. The wrapper returned `rc=0`, but its temporary ledger row was `verdict=VOID exe_check=MISMATCH`, reproducing the attestation void.

## Green hermetic proof

The #11765 harness selftest supplied a matching deploy manifest while the local rebuild differed, then returned that manifest image from both mocked node readbacks. It verified `exe_check=MATCH` and recorded the manifest SHA as `build_exe_sha256`. The #11845 extension now provides distinct node-slot hashes and mocked live readbacks, then verifies both node-specific build hashes and `exe_check=MATCH`; missing peer slots remain fail-closed. Other cases verify helper attestation and missing/corrupt/stale-checkout handling; existing emitter refusal controls remain covered by the same suite.

The deploy library selftest now performs raw `NODE=0` and `NODE=1` writes with different xpfd/helper bytes, proves the first slot survives the second, verifies each reader selects its own artifact, and checks node-scoped invalidation. The `.deb` fixture verifies the staged package payload and node-slot metadata.

## Issue #11845: two-node rolling reproduction

### Red-before cell

The pre-fix hermetic cell deployed distinct `BUILD_TIME`-style bytes to slotless `NODE=0`, then `NODE=1`. The manifest contained only the second image (`c948dd26…`); the live fw0 image (`09f05cec…`) could not match, so a both-node gate would remain `VOID`/`MISMATCH`.

### Green-after cell

The same fixture now writes fw0's build to slot 0, rebuilds different bytes for fw1, then writes only slot 1. It reads both slots back and compares each slot with that node's live fixture image: both match despite different SHA-256 values. The permanent harness selftest separately exercises the gate's per-node manifest lookup/readback path and fail-closed missing-peer-slot control.
