# Issue #12532 — re-authorize nested rollback invalidation debt

## Why

A commit-confirmed rollback restores the original confirmed configuration even when several nested confirmed transitions have landed. Policy-invalidation debt retained a single landed predecessor and a capture merged across transitions. On rollback to the root, the exact-predecessor check therefore missed, and the carry path deleted candidates that the restored root permits.

## What

For nested rollback to a non-immediate predecessor, the bounded landed link
cannot identify which transition introduced each candidate. The retained
helper candidates are judged against the restored configuration using stable
rule provenance instead of inferring authority from that link. Each candidate
keeps the stable rule key that admitted it, separate from positional runtime
policy IDs; when a merge sees one candidate under two keys, the older recorded
key wins. A candidate counts as permitted only when its recorded rule remains
a permit for its zones and the shared `policymatch` evaluator permits its
tuple. Denied, unknown, malformed, and zone-ambiguous candidates stay in debt.

Permitted candidates are not discharged until the restored config lands. The
rollback debt holds them pending until discharge, or the next capture after
that target landed. An authority refusal restores the original debt; a
same-target retry retains pending candidates; a superseding target owes them
again. #12686 extends this to explicit wildcard zones, unpublished rollback
targets, and fresh default-policy captures. Rollback source and intent survive
same-target retries, while fresh candidates retain ordinary invalidation and
log-only `policy-rematch` behavior. Provenance lookups use one runtime-ID
index per capture, keeping capture work linear in candidate count.

Permanent regressions cover C0→C1→C2→C0, a depth-three C0→C1→C2→C3→C0
rollback, a root-denied candidate, one-level intermediate rollback controls,
and review-fold cells below. The nested tests force candidate deletes to fail
at each confirmed commit so rollback exercises retained debt rather than
freshly deleted rows.

## Scope

The one-level exact-undo path keeps its pre-#12532 behavior and drops the target's own candidates at capture time. If that rollback's publish is rejected and a commit that still forbids those rules supersedes it, those candidates are not owed again. This reproduces on master (review probe P2b) and is unchanged here (still open; see #12780).


The P3 shape is fixed for nested chains of exact zone-pair or global rules whose
last confirmed target landed. #12686 extends that re-authorization to three
additional rollback variants: explicit `from-zone any` / `to-zone any` rule
keys, a last confirmed target whose publish was rejected, and a rollback whose
fresh capture classifies retained sessions under a changed default policy.

Rollback re-authorization now treats an explicit `any` zone as a wildcard,
re-checks the original retained obligation when the target never published,
and removes a retained permitted session from a fresh capture if the helper
reclassified it as an orphan/default-policy candidate. Fresh candidates that
were not already owed before rollback remain subject to the ordinary policy
invalidation rules, including log-only `policy-rematch` clears.

The pre-rollback candidate source and rollback intent remain attached through
same-target retry after a rejected rollback publish. Unknown provenance, denied
or ambiguous tuples, and colliding zone IDs remain fail-closed debt.

## Risk

Re-authorization requires sufficient candidate provenance and a well-formed helper tuple with known stable rule and zones. Unknown provenance, malformed tuples, and colliding zone IDs are retained rather than treated as permitted. The helper-capture candidate path is covered; legacy store-only capture has no helper match tuple provenance and is not reinterpreted by this change.

Session tuples carry no ICMP type, so a type-specific ICMP rule ahead of a broad permit can be skipped, as in the existing policy-rename re-check. Re-authorization runs only on the node that owns the commit-confirmed timer; an HA peer receives the rollback target through normal config sync. A nested rollback evaluates each retained candidate with `policymatch.Match` once, on that one apply rather than every commit. As in the pre-#12532 carry path, a nested rollback cuts the debt's landed link before its authority checks, so a refusal restores the debt's candidates but not that link.
