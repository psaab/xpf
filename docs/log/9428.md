- **The issue's stated parity is TRUE today.** Traced end to end:
  - Rust key `(pool_name, pool_addresses_v4, pool_addresses_v6, port_low,
    port_high)` ← `allocator_key_for` ← the rule ← `snap.pool_name`,
    `snap.pool_addresses` (via `expand_pool_address`), `snap.port_low/high`
    (defaulted to 1024/65535).
  - Go builder: `pool, ok := SourcePools[rule.Then.PoolName]`,
    `PoolName: rule.Then.PoolName`, `poolAddresses = SourceNATPoolMembers(pool)`,
    `portLow, portHigh, _ = SourceNATPoolPortRange(pool)`, and both helpers take
    only `(pool *NATPool)`.
  - Go owner: `srcSeen[rule.Then.PoolName]`, one owner per pool NAME.
- **The issue's prescribed MECHANISM rests on a stale premise.** It says "both
  are struct definitions in one file each" and asks for the two FIELD LISTS to
  be equal. The Rust key is a struct. The Go owner identity is NOT the fields
  of a struct: `natAllocOwner` is `{desc, pool, members}`, a descriptor. The
  identity is the enumeration loop's dedupe expression. Compared as lists, one
  name vs five fields differ by construction, so the prescribed positive
  control would red on a correct tree on its first run.
- **The property #5144 actually needs** is two containments:
  (i) Rust never SPLITS one Go owner (every key field is filled only from the
  name-selected pool; violated = under-refusal, the #9062 shape);
  (ii) Rust never MERGES two Go owners (every Go owner-key dimension reaches a
  field the Rust key carries; violated = over-refusal).

## Timestamp: 2026-09-10 — the guard

- **File**: `pkg/dataplane/userspace/snat_owner_key_parity_9428_test.go`
  (placed beside #8901's cross-plane extractor, which reads Rust from Go the
  same way).
- **Chain, all derived from source**:
  - Rust key fields: bounded parse of the struct body, comments stripped.
  - key field → rule field or positional param: the `allocator_key_for` literal.
  - param → rule field or local: every call site's arguments, following
    `pending.Y` into every `PendingPoolAllocator` construction.
  - rule field or local → wire field: the parse loop's three forms.
  - wire field → Go field: `go/ast` on the json tags.
  - Go field → value: the builder's composite literal, plus every assignment
    to that local.
  - Go owner leaves: `go/ast` on the `srcSeen[...]` index.
- Any form it does not recognise is a **LIVENESS** failure naming the field and
  the dead end, never a silent agreement.
- **Positive control** (the part the issue named as most likely to be omitted):
  Rust key fields > 0 and every one traced to the wire; Go owner dimensions > 0;
  pool-scoped Go fields > 0.
- **Fixture cells** run the SAME checker on the REAL sources with one planted
  edit each, and assert the MESSAGE, not just a failure. Each edit is checked
  to apply exactly once, so a fixture cannot silently turn into a copy of the
  real-tree cell:
  - a Rust-only key field → exactly one "RUST HAS IT, GO DOES NOT" naming it;
  - a Go-only owner dimension → exactly one "GO HAS IT, RUST DOES NOT";
  - an inert comment in the key struct → nothing;
  - the key struct renamed → LIVENESS, never agreement;
  - two call sites disagreeing → "RUST DISAGREES WITH ITSELF";
  - an unparseable call site → LIVENESS.

### A blind spot in my own guard, found while designing its mutants

The call-site regex understands only simple path arguments. A call written
`allocator_key_for(pending.port_low + 0, ...)` did not match it and SILENTLY
dropped out of the population, and the guard would have reported agreement over
the remaining three. That is an inventory built by running the pass, blind to
what the pass does not recognise. Fix: every `allocator_key_for(` occurrence
other than the definition is counted independently and must be parsed, or the
guard reports LIVENESS. The last fixture cell above pins it.

### Limits, stated

- The resolver is bounded to the forms listed. A new form is a LIVENESS red,
  and the right response is to teach it, not to rewrite the Rust to fit.
- "Filled only from the pool" recognises a call whose sole argument is `pool`,
  a selector on `pool`, the pool-name expression, and zero values. A
  pool-derived literal under a pool-conditional is NOT recognised.
- **NAT64 owner parity is not covered.** The same #5144 comment makes the
  analogous claim about the NAT64 allocator key `(prefix_bytes, pool_v4)`, and
  it is equally unenforced. #9428 names `SourceNatPoolAllocatorKey`.
