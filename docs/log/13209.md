# Issue #13209 — classify compact firewall prefix lists

## Why

`firewallPrefixListFamilies` classified only prefix-list child keys, while
`compilePolicyOptions` also reads trailing instance values. Consequently,
compact and bracketed prefix-lists were seen as empty by the `family any`
`#4426` gate even though they compiled with actual prefixes. A single-family
list could evade rejection/warning, leaving a dual-compiled filter arm with
incorrect match semantics, including unsafe `except` behavior.

## What

The family classifier now reads `instanceValueTail` as well as child keys,
matching `compilePolicyOptions` for both compact and hierarchical list shapes.
Regression coverage checks compact IPv4, IPv6, bracketed, named-block compact,
`except`, lenient warning, and mixed-family accepted cases.
## Validation

- RED on pristine `origin/master` `dd607606a`: compact v4, bracketed v4,
  compact v6, named-block compact v4, compact `except`, and lenient warning
  tests failed because no `#4426` rejection/warning occurred.
- GREEN after the fix: focused regression tests passed.
- `go test ./pkg/config -count=1` ran all package tests; it failed at the
  unrelated `TestConfiguredIPv6Prefixes10856` assertion: actual prefix order
  began with `2606:4700:2222::2/128` instead of
  `2606:4700:1111::/64`. The new regression tests passed in that run.
- `go vet ./pkg/config` and `git diff --check` passed; changed Go files were
  formatted with `gofmt`.

## Risk

Strict commits now reject single-family compact/bracketed prefix-list
references under `family any`; lenient load behavior remains warning-only, as
with the existing `#4426` contract. Mixed-family lists remain accepted.
