# #16600: Single-family SNAT rule with opposite-family pool commits clean, then every flow is refused WrongAddressFamily

- **Timestamp**: 2026-10-25
- **Action**: `validateSourceNATPoolFamilyStrict`
  (`pkg/config/compiler_validate_strict_nat.go`) now hard-rejects a
  pool-mode source-NAT rule whose authored source match is
  single-family F while the referenced pool has zero family-F
  members, registered as the `sourceNATPoolFamily` NAT registry gate
  (after `sourceNATPoolAddressGrammar`, sharing
  `lenientDestNATAddresses`) and in the #5876 peer-effective SNAT
  view. Previously `pool P address 2001:db8::5` with
  `rule r1 match source-address 10.0.0.0/24 then source-nat pool P`
  committed clean; the Rust allocator splits pool members by
  `IpAddr` variant (`nat/source/expand.rs`), so the rule's
  `pool_addresses_v4` was empty and every v4 flow was refused
  `WrongAddressFamily` (`nat/source/match_rules.rs`) and not
  forwarded — the SNAT twin of the #13922 DNAT/static cross-family
  reject. Single-family determination uses both authored source
  axes: literal `source-address` values and `source-address-name`
  references resolved through their static address-book closure,
  with wildcard keywords contributing their families (`any` both,
  `any-ipv4` v4-only, `any6` v6-only). Unconstrained, dual-family,
  and not-statically-decidable rules (direct feed bindings, dns-name
  or tainted closures) are not rejected. Family classification is
  the colon-strict `natAddrFamily` on un-parsed text, so an
  IPv4-mapped `::ffff:192.0.2.1` pool member is v6 and does not
  satisfy a v4 rule (#10686 identity), while it does satisfy a v6
  rule. Strict on commit; tolerant load / peer-sync warn (#1960),
  and the dataplane already fails such flows closed.

  pool, v6 rule/v4-only pool) reject naming `WrongAddressFamily`;

  v6/mapped-pool and `any-ipv4` controls commit; `any-ipv4` with a
  v6-only pool rejects; lenient warns; v4-only/mixed
  `source-address-name` closures and a direct feed binding behave
