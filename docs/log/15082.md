# #15082 — `top delete … policy allow-all` prints `[edit]`, sends no Delete, returns success (A53-01)

## Why

Both config-mode dispatchers treated `top`/`up` as pure navigation
and never read trailing tokens:

- `cmd/cli/shared.go` (`ctl.dispatchConfig`): `case "top"` cleared
  the cursor, printed `[edit]`, returned nil; `case "up"` popped
  one level and returned nil. `top delete security policies …
  policy allow-all` therefore sent **no Delete RPC** and reported
  success.
- `pkg/cli/cli_dispatch.go` (`CLI.dispatchConfig`): same shape via
  `store.NavigateTop()`/`NavigateUp()`.

The permit policy stayed in the candidate and was committed — a
silent divergence between operator intent and committed
enforcement, bounded to the documented Junos `top`/`up`
command-prefix idiom.

A compounding hazard: `pkg/config.AuthorizeConfigMutation`
(`configMutationPaths`) treated every `top`/`up` line as ungated
navigation. Executing the inner command without unwrapping the
prefix in the gate would have let a `deny-configuration`-denied
delete ride through ungated.

## What

- `pkg/config/authz_config_mutation_9154.go`:
  `ResolveTopUpPrefix15082` / `ParseTopUpPrefix15082` — the one
  shared split of `top <cmd>` / `up [n] <cmd>` (target cursor,
  inner tokens, quote provenance; bare navigation vs malformed
  prefix distinguished, out-of-range prefixed counts fail
  closed). `configMutationPaths` and
  `authorizeConfigMutationDepth9939` unwrap the prefix so a
  prefixed mutation is adjudicated as the inner command at the
  target cursor, including the embedded
  `then change-configuration` payload scan. Bare `top`/`up`/`up n`
  remain ungated navigation.
- `pkg/cli/cli_dispatch.go` (`dispatchTopUp15082`): bare form
  navigates (now including the `up n` count); prefixed form
  installs the target cursor, re-enters `dispatchConfig` with the
  inner line (so coarse perm, lock-holder, `*-configuration`,
  groups, and show gates all re-run), then restores the saved
  cursor and prompt — including on error. Nested `top`/`up`/`edit`
  after a prefix is rejected.
- `cmd/cli/shared.go` (`ctl.dispatchTopUp15082`): same contract on
  the remote surface — the inner re-entry issues exactly the RPC
  the un-prefixed command would issue at the target level
  (exactly one Delete for the acceptance probe), cursor restored
  on success and error.

NOT changed: the gRPC/REST handlers (they receive already-resolved
paths from the remote CLI and now adjudicate prefixed lines via
the shared gate unwrap if one ever arrives), bare navigation
semantics beyond the `up n` count the issue's fix direction
names, and `NavigateTop`/`NavigateUp` store primitives (still
used by tests).

## Risk

- Behaviour delta is confined to lines beginning `top`/`up` in
  config mode: trailing tokens now execute (previously silently
  ignored) and malformed prefixes now error (previously silently
  succeeded). Bare `top`, `up`, and `up n` navigate as before
  (`up n` count is newly honoured — previously the count token
  was ignored and only one level popped, itself a silent
  divergence).
- Inner operational commands (`top show …`, `top commit`, …)
  execute through the normal dispatcher at the target cursor;
  `exit`/`quit` under a prefix terminates the session as the
  un-prefixed command would — no new fail-open direction, and
  denied mutations are refused by the unwrapped gate before
  execution.
