# #12543 — keyring rollback guard overwrites/deletes dpkg payload

- **Timestamp**: 2026-10-10 (PR #12562 review fold 2026-10-12)
- **Action**: Gate keyring rollback on bootstrap file IDENTITY (device:inode) + byte equality, not bytes alone.
- **Base**: `origin/master` `d137348df` (rebased from `f9cb48ed8` for the PR #12562 review fold)
- **Branch**: `fix/12543-campaign-pub`
- **Prior art**: `e67d7707c` / PR #12358 / #12142 (Astra post-merge PC-F1, real-dpkg repro + syscall trace + gpgv proof)
- **Files**: `scripts/dist/install.sh`, `scripts/dist/test_install_keyring_atomic_12142.py`, `docs/distribution.md`, `docs/log/12543.md`; review fold: `scripts/dist/install.sh` (comment only), `scripts/dist/test_install_keyring_atomic_12142.py`

## Why

The #12142 guard passed on byte equality alone. A same-key release ships
the archive key inside the .deb (`debian/rules`), so dpkg unpack renames a
byte-IDENTICAL payload over the live path (new inode). The guard then
misclassified the dpkg-owned inode as "still the installer's file":

- Re-run (backup exists): stale backup renamed OVER the package payload →
  obsolete keyring persists (gpgv NO_PUBKEY after fix + configure).
- First install (no backup): `rm -f` DELETES the package file → keyring
  absent; configure-only recovery never restores it.

Equal bytes ≠ same file — this refutes #12358's "observationally
equivalent" residual. A symlink/file-type conjunct cannot fix it (both
objects are regular non-symlinks); the reviewer direction is identity +
bytes.

## What changed

- `install_keyring`: capture `KEYRING_IDENT=$(stat -c '%d:%i' $TEMP)`
  pre-rename (same-directory rename ⇒ temp identity becomes live identity).
  Dies pre-mutation on stat failure (host untouched; trap cleans temp).
- `cleanup_on_fail`: rollback requires live dev:ino == IDENT **and**
  regular non-symlink **and** byte equality. dpkg replacement (new inode,
  equal bytes) → else branch (leave intact, discard stale backup).
- Runbook one-sentence truthfulness update in `docs/distribution.md`.
- NOT changed: validate, pin/source logic, trap wiring, backup discipline,
  success cleanup. No mtime/uid/dpkg-db checks (reviewer-forbidden). The
  `-ef` witness alternative rejected as non-minimal (extra file + 4
  cleanup sites).

## Review fold (PR #12562)

The Opus review of `dc731cb61` returned NEEDS-FOLD: the identity + bytes
gate is correct (also against real dpkg 1.23.11), but one comment still
stated the old rule, and four of the gate's guarantees were unpinned: a
mutant breaking each one passed all 15 tests.

- **F1** — the `cleanup_on_fail` header said the keyring is restored
  "only while its live bytes still match this installer's write", the
  bytes-only rule behind this issue. It now states identity (the
  device:inode recorded before the rename) AND bytes, and that a dpkg
  replacement (new inode, equal bytes) and an in-place rewrite (same
  inode, new bytes) are both left intact with the backup discarded.
- **F2** — dropping the byte check passed, because every test that
  changed the file also changed its inode. New
  `test_apt_in_place_rewrite_existing_key_is_left_intact_12543` and
  `test_apt_in_place_rewrite_first_install_is_left_intact_12543`: the apt
  stand-in rewrites the live path with a truncating write, the ident trace
  proves the inode is unchanged, and the rewritten bytes must survive (no
  stale-backup restore over them, no first-install removal).
- **F3** — `test_first_install_failure_removes_bootstrap_keyring` was
  vacuous. The default `mv` stand-in compares the live path with
  `keyring.before`, which a first install never has, so it exited 92: no
  rename, and cleanup took the leave-intact branch. The test now uses a
  pass-through `mv`, checks the bootstrap bytes are at the live path
  before the injected failure, and requires rc 1 and the `removing new`
  branch.
- **F4** — nothing pinned that the identity is recorded BEFORE the
  rename; the existing signal test fires after `install_keyring` returned.
  New `test_signal_during_keyring_rename_restores_previous_keyring_12543`:
  the `mv` stand-in does the real rename, then sends TERM to the
  installer. Expect rc 143, the previous bytes restored, and no temp or
  backup left.
- **F5** — the die when the identity cannot be recorded was untested,
  though the Risk lines rely on it. New
  `test_identity_capture_failure_dies_before_rename_12543`: a `stat`
  stand-in fails, or (second subtest) prints nothing, for the bootstrap
  temp. Expect rc 1, `cannot record bootstrap keyring identity`, the
  previous bytes intact, zero renames, and no temp or backup left.
- **F6** — this log and the commit message described the base check as
  stashing `install.sh`, which #8489 forbids. Both now describe the method
  that reproduces it: the base `install.sh` copied beside the test file.

## Risk

- SIGKILL/power bypass shell cleanup (inherited, unchanged).
- Non-GNU stat dies pre-mutation (Debian-family target guarantees coreutils).
- Missing/dangling live path → else branch (same as current missing policy).
- Inode numbers can be reused (review residual, PR #12562): the bootstrap
  file is not held open, so if the keyring path were re-created a second
  time after dpkg freed the bootstrap inode, the new file could take that
  number. Nothing in-tree re-creates the path; `debian/xpf.*` never writes
  the keyring.
