- **Timestamp**: 2026-11-13 16:10Z
  - **Action**: Lane H2 posted the design note, before any code
    (issuecomment-6858271088).
    - **Decision: REMOVE.** On every graceful HA stop, hitless or not,
      xpfd runs the demotion's FRR apply on the shutdown path, before
      `frr.Stop()`, as a full and bounded `frr-reload.py` of a non-owner
      render.
    - **Why not a non-forwarding line.** FRR has no non-forwarding state for
      a gateway static: once the VIP goes, the static either goes inactive
      or resolves through the cluster `Null0` default and stays an active,
      exportable blackhole.
    - **Why removal.** It is the state that a move-away and the restarted
      daemon's first render already reach. It also fixes the owner render
      that is otherwise left on disk.
    - **Hitless.** #19101 says hitless preserves no forwarding on userspace,
      and every HA stop resigns, so hitless stops remove too. The expiry
      condition: revisit if #19101 ever makes hitless keep the helper
      forwarding.
    - **Placement.** After `cluster.Stop()` (ownership frozen, VIPs gone)
      and before the session-sync stop. `frr.Stop()` moves to right after
      the apply.
    - **Lone node.** Statics are forced non-owned. RG-gated protocols follow
      live state, which avoids a flap on every lone-node restart.
    - **What #19050 B adds.**
      - The full reload covers B's running-only lines.
      - A latch: no fast install runs after the apply starts.
      - A join plus a barrier: an in-flight or killed batch settles before
        the reload reads the running config.
    - **Open questions** for the coordinator's review: Q1, the lone node;
      Q2, withdrawing RG-gated protocols on a peered stop; Q3, placement.
  - **Verification for the note**, read at 05b4645749 plus the #19050
    branch:
    - The resign runs on `haMode` (`daemon_run_shutdown.go:395`), and
      direct VIP removal is unconditional on hitless (`:507-511`).
    - `ResignForPlannedShutdown` -> `recalcWeight` -> `runElection` runs
      under `m.mu` (`pkg/cluster/election.go:1335-1350`). With no live peer
      the resign is a no-op (`planned_shutdown_resign.go`).

      its v4 default are both `Installed` via ge-0-0-2.50.
    - **Why Q4 went on-link.** The standby's WAN unit carries
      `169.254.24.4/32`. That is xpf's per-node RETH placeholder,
      `169.254.<cluster-id>.<rg*2+node+1>/32`
      (`pkg/dataplane/compiler_iface*.go`, the VRRP advert source),
      rendered on every RETH device. With the VIP absent, the only IPv4
      address on the unit is a /32, so FRR treats the interface as
      unnumbered and an interface-qualified gateway as on-link. The
      option therefore fails for v4 in this design and works for v6.
    - **Candidate for the no-write design, from FRR 10.5.1 source** (read
      at tag frr-10.5.1):
      - zebra applies a client protocol's NHT route-map to the route that
        resolves the next hop (`zebra_rnh_apply_nht_rmap`);
      - `match tag` reads that resolving route's tag (`route_match_tag`:
        `rm_data->re->tag`);
      - a denied result reports the next hop filtered, so unreachable, to
        the client, and staticd does not install a path whose next hop is
        invalid (`static_zebra.c`, `nh_valid`).

      So `ip nht static route-map` with a deny on tag 2500, the cluster
      `Null0` default's existing tag (#15158), would make a gateway static
      inactive whenever its only resolution is that default.

      This is NOT yet lab-verified. It needs a second udp cell.

      client_proto)`) or from a BGP-running node.
    - **(5) CONFIRMED.** The configs are identical.
  - **Reading.** Reading FRR 10.5.1 source (`zebra_rnh.c`), the mechanism
    is consistent:
    - notify applies the client's map to the resolving route's copied
      state (`rnh->state`) and sets `NEXTHOP_FLAG_RNH_FILTERED`;
    - `rnh_nexthop_valid` treats that flag as invalid;
    - `zebra_send_rnh_update` then encodes 0 next hops;
    - `show` prints `(filtered)` when `filtered[proto]` is set.

    The absent `(filtered)` marker therefore says the deny was not applied
    at +3 s, not that it was applied without effect.
    `ip_nht_rm_add` re-evaluates at once only when the map already
    resolves (`route_map_lookup_by_name`). If it does not yet resolve, the
    re-evaluation waits for zebra's route-map update timer, whose default
    is 5 s (`ZEBRA_RMAP_DEFAULT_UPDATE_TIMER`), which is longer than the
    cell's 3 s wait.
  - **Verdict: INCONCLUSIVE, not refuted.** The observation window was
    shorter than FRR's documented route-map update delay. My predictions
    marked this timing UNSURE, and the cell did not wait it out.
