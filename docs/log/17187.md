# #17187 — R4-Q21-04: scheduler time/date grammar mirrored between pkg/config and pkg/scheduler

- **Timestamp**: 2026-10-27
- **Defect (live on origin/master 59e7f8b74b)**: The scheduler
  time-of-day/date grammar existed twice:
  `parseSchedulerTimeOfDay`/`parseSchedulerDateBound` in
  `pkg/config/schema_validators_scheduler.go` and
  `parseTimeOfDay`/`parseSchedulerDateBound` in
  `pkg/scheduler/scheduler.go` (extended in lockstep by #11305). The
  copies had already diverged: `ValidateTimeOfDay`/`ValidateDate`
  `strings.TrimSpace`d before parsing while the runtime parsed raw, so
  a padded bound (e.g. `" 09:00"`) committed clean and then failed at
  runtime, leaving the scheduler inactive all day — for a scheduled
  DENY the deny never engages. The `schedulerTimeOfDayEqual` doc in
  `pkg/config/compiler_validate_warn.go` misdescribed that outcome as
  bounds "fail closed there".

## STEP-0

Re-verified both parser pairs side by side at 59e7f8b74b (config
:12-47, scheduler :745-755/:841-859, warn comment :2197-2201): live,
not fixed. Sibling R4-Q21-02 (#17177, the family-wide `checkToken`
padding rule) is separately open and was NOT folded in; this PR does
the named #17187 fix direction plus the scheduler-leg padding
alignment that fix direction's own parity acceptance requires
("accept ⇔ evaluable, including the padded rows" — unreachable while
the validator trims).

## What

- `pkg/config/schema_validators_scheduler.go`: exported
  `ParseSchedulerTimeOfDay(raw)` and
  `ParseSchedulerDateBound(raw, loc)` as the single source of truth
  for the grammar. The exported date parser takes a location and uses
  `time.ParseInLocation`, preserving the runtime's local-zone
  semantics (the old config copy used UTC `time.Parse`, sound only for
  its relative comparisons). Untyped in-package spellings
  `parseSchedulerTimeOfDay`/`parseSchedulerDateBound` (UTC) remain as
  one-line delegates for existing compiler callers.
- `pkg/scheduler/scheduler.go`: deleted the local grammar copies;
  `parseTimeOfDay` and `parseSchedulerDateBound` are now thin
  delegates to the config parsers (`parseTimeOfDay` keeps only the
  tod{H,M,S} projection). Acceptance:
  `grep -n 'time.Parse("15:04' pkg/scheduler/*.go` is empty and each
  grammar has exactly one definition in the repo (pkg/config).
- Validators no longer trim: `ValidateTimeOfDay`/`ValidateDate`
  validate the raw bound with the shared parser, so a padded bound is
  rejected at commit instead of committing and going inactive at
  runtime. Empty string still reports "missing value".
- `schedulerTimeOfDayEqual` comment corrected: a padded/unparseable
  bound makes the comparison false and the runtime scheduler
  INACTIVE — fail-closed only for a scheduled permit; for a scheduled
  deny the deny never engages, so the padded form must be rejected at
  commit by the untrimmed validator.
- New parity guard
  `pkg/scheduler/scheduler_parser_parity_17187_test.go`
  (`TestSchedulerValidatorRuntimeParity17187`): one table drives
  `config.ValidateTimeOfDay`/`ValidateDate` AND the runtime evaluator
  `isWithinWindow`, asserting accept ⇔ evaluable for bare, HH:MM:SS,
  leading/trailing/both-padded, malformed and one-digit-hour rows,
  plus a caller-location cell for date-time bounds (a UTC-parsing
  mutant flips it).

## Risk

Low. Parse semantics for every previously-valid (unpadded) bound are
unchanged; date bounds are now parsed in the caller's location in the
runtime (identical to the deleted copy) and in UTC only for the
config-side relative comparisons (start-before-stop), where the zone
cannot change the ordering of two same-form bounds. The one
behaviour tightening is deliberate: padded scheduler time/date bounds
that previously committed and silently went inactive at runtime are
now rejected at strict commit; the tolerant Load/SyncApply path
downgrades schema errors to warnings, so stored configs are not
bricked. The family-wide padding rule for the other typed validators
remains #17177's scope.
