# Issue #16578 — Surface A ambiguous cleanup candidates (R3-A40-03)

- **Issue:** Two lost-reply shapes orphaned a live A/AAAA value indefinitely while status showed a single correct value. Arm 1: a lost UPDATE reply on a *first* publish plus a renumber before the next successful publish — the pending row yields exactly one candidate, and the `len(prevCandidates) > 1` threading gate threaded nothing, so the backend did an Insert-only add and the possibly-live first value was never removed. Arm 2: three renumbers during a provider outage — the single `AmbiguousPriorAddrText` slot was overwritten on each chained ambiguity, losing the earlier desired value(s).
- **Context read:** Read the complete #16578 body. No comments present. Re-verified cited lines at current master (`5b565d8c54`): the `>1` gate, single-slot overwrite, and candidate collection had drifted ~+90 lines from the `d1ea69f9aa` citations but were otherwise identical. No duplicate sibling: no open PRs and no other branch mentions 16578.
- **What:**
  - `pkg/ddns/surface_a.go` (`publishLocked`): dropped the `> 1` gate — `LeaseDNSRecord.PrevAddrs` now carries every candidate that differs from the new value (backends already union `PrevAddr`+`PrevAddrs` and skip `== Addr`, so a single settled candidate is safe). On a chained ambiguous failure the prior desired is *appended* to the bounded candidate list instead of overwriting a single slot. Confirm-save clears the list via `withAmbiguousCandidates(nil)`.
  - `pkg/ddns/state.go` (`ownedRecord`): new bounded append-only `AmbiguousPriorAddrTexts []string` (bound `maxAmbiguousPriorCandidates = 16`, FIFO drop-oldest, dedup) with helpers `ambiguousCandidates` / `withAmbiguousCandidates` / `appendAmbiguousCandidate` / `normalizeAmbiguous`. The legacy single slot `AmbiguousPriorAddrText` is retained for backwards compatibility: folded into the list on load (`normalizeAmbiguous` in `loadDDNSState`) and kept in sync with the first list element on every write, so a downgraded binary still retains one candidate. `validOwnedRecordAddrs` now also validates every ambiguous candidate. `withdrawTargets` deletes every list candidate.
  - `pkg/ddns/README.md`: updated the #15225 A40-02 paragraph for the list, the dropped gate, and the bound.
- **Layer choice:** The candidate set is a property of the publish outcome and its durable row (the #15225 layering), so the list lives on `ownedRecord` next to `PriorAddrText` and is threaded through the existing `PrevAddrs` wire field — no backend changes were needed, as rfc2136/cloudflare/route53 already remove every threaded candidate != the new value.
- **Bound rationale:** Each ambiguous publish leaves at most one extra possibly-live value, so the list grows by at most one per renumber during an outage. 16 covers any realistic renumber burst (Arm 2 needs 3) while keeping the durable row and every UPDATE trivially small; FIFO drop-oldest degrades to exactly the pre-fix behaviour for the dropped value only, never worse.
