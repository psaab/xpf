## The defect

`set snmp community <c> client 10.0.0.0/8` (singular), `clinets …`, or
`client-list-nam L` committed clean on every channel, compiled to an
empty allowlist, and — because `AllowsSource` documents an empty
allowlist as allow-all — the community answered EVERY source. A
one-letter typo in an operator-authored source ACL on a
network-reachable service failed OPEN behind a green commit. Measured
RED on `origin/master` before the fix: strict compile of all three
spellings (flat-set, braced, and Keys-packed) returned no error and no
warning, and the lenient path allowed `8.8.8.8`.

Prior fixes in this family (#4289, #4834, #5472, #5833, #5898, #8778,
#9416, #10687) each repaired a NAMED spelling; none added a default
arm, so the next unmodelled keyword silently reopened the community.
This change is the default arm, not another named spelling.

## Why not `closedWorld` on the community schema

That was the alternative in the fix direction, and it was already
measured and refused (#9265, recorded in
`instance_name_armed_9265_test.go`): the flag INHERITS, so it refuses
the legal flat-set chain `community <c> client-list-name L
authorization read-only` (the inherited walk sees `authorization`
under the terminal `client-list-name` leaf), and it would hard-reject
the deliberate accept-with-advisory `view` knob (#4306). The gate here
is scoped to the community level, inherits nothing, reads its
permitted set from the schema (so a child declared later is permitted
automatically), and permits the inert knobs `view` / `logical-system`,
which keep their existing advisories.

## Shapes covered

The gate judges the same views the compiler reads, so no spelling
escapes it: expanded child statements (braced bodies and flat-set
chains, via `expandFlatRun`), statements chain-nested under the descent
leaves (`authorization`, `routing-instance`), and the Keys-packed run
on the community node itself (`community <c> client 10.0.0.0/8;`),
scanned with schema arity so a declared leaf's values — including a
`clients` value run and a view NAMED `clients` — are never mistaken
for keywords. The strict error names only the offending token, never
the community name (a secret). On the lenient path the quarantine is
sticky across same-name merge blocks, exactly like #5833's, and a
well-formed sibling community is unaffected.

The companion warning covers the other half of the `client-list-nam`
typo: a defined `snmp client-list` that no community references
restricts nothing, and is now named on both paths instead of sitting
silently inert.

## Controls

The `clients` control is unchanged and asserted in the same test run:
a well-formed `clients 10.0.0.0/8` community still admits `10.1.2.3`
and denies `8.8.8.8`, the #9416 flat-set chain still commits, a braced
community carrying every declared child still commits, and the inert
`view` knob keeps its advisory rather than becoming a reject.
