# #9560: the XDP steering map DELETE was identity-blind

## Re-read at `origin/master` `7c494b5ca`

The issue has no comments. Its body is the spec, and every premise holds at this commit.

- `userspace_sessions` (`userspace-xdp/src/lib.rs:419`, HashMap, `max_entries` 262144) is keyed on
  `UserspaceSessionMapKey` (`userspace-dp/src/afxdp/bpf_map/mod.rs:70`). That 40-byte bare tuple carries neither
  `routing_domain` nor the tunnel `discriminator`.
- Every steering write goes through two primitives, `publish_session_map_key` and `delete_live_session_key`. The
  non-test call counts match the handoff exactly: publish_session_map_key 2, delete_live_session_key 6,
  publish_live_session_entry 8, delete_live_session_entry 5,
  delete_session_map_entry_for_removed_session 4, delete_session_map_redirect_for_session 2. Twenty-five production
  functions take `session_map_fd: c_int`.
- `reverse_canonical_key` (`session/key.rs:299`) sets `routing_domain: 0` (#7160). So two domains'
  reverse-canonical rows are identical `SessionKey`s, and a row's owner must be the entry key.
- On a steering-map miss the shim (`userspace-xdp/src/lib.rs` ~697-760) sends a local destination and ICMP to an
  interface-NAT local address to the kernel. Transit and other interface-NAT traffic falls through to XSK redirect.
  So the DELETE arm changes a packet's fate only for host-bound and interface-NAT-ICMP destinations.
- The steering fd path runs: `ReconcileSnapshotFds` (`coordinator/reconcile/snapshot.rs:283`) ->
  `BindingPlan.session_map_fd` (`bringup.rs:316`) -> `BpfMaps` (`bringup.rs:408`) -> worker `create`
  (`worker/mod.rs:420`) -> `WorkerBpfMaps` -> worker setup (`setup.rs:266`). The coordinator and HA-import sites read
  it from `self.bpf_maps.load()`.
- A bringup replays synced sessions (`bringup.rs:496`, `replay_synced_sessions`). Nothing at worker startup
  republishes worker-local sessions.
