# Issue #11405 — Stable ECMP member selection across restart and HA re-resolution

## Root cause

The session ECMP selector fed the forward 5-tuple to `FxHasher` with the per-process `hot_path_hash_seed`. Synced or promoted sessions can be re-resolved under a different process seed, selecting another live member while retaining the stored SNAT rewrite. The resulting path change can break path-pinned NAT after restart or HA promotion.

## Fix

Use a fixed, ECMP-specific domain seed for per-flow member selection. This keeps the same 5-tuple on the same member across restart or peer re-resolution when the ordered live-member set is unchanged, without changing the per-boot secret used by collision-sensitive caches and maps. Changes to the live set, candidate identity, or weight can remap a flow; candidate ordering alone does not. This is not a persisted egress pin. Update the forwarding and multi-WAN descriptions and replace the obsolete archived review guardrail that required ECMP to use the hot seed.

Issue #11686 extends this guarantee to member identity: v4/v6 rendezvous IDs
fold the stable logical interface name, gateway, and tunnel endpoint rather
than the node-local kernel ifindex. This also keeps interface-only members
stable across HA peer enumeration differences and node renumbering. The
dual-enumeration regression checks v4 gateways, interface-only candidates, v6
gateways, and interface-SNAT rewrites.

The two-seed regression models distinct process seeds with different flow-cache placement and confirms the old seeded ECMP choices diverge, while production ECMP uses its fixed domain seed and selects the same live member.
