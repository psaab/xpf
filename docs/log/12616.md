# #12616 — preserve terminal reset after failed retry

- **Action**: Keep a daemon fenced after a successful factory-reset wipe, even if another reset attempt subsequently fails.

## Red before

A successful `factoryReset` left `resetting` true, but the next failed invocation's `resetFailed` unconditionally called `exitResetGeneration` and resumed configstore archival/rescue writes. The new regression performed a successful wipe followed by a failed retry and observed `isResetting()` become false.

## Change

- Added a daemon-lifetime atomic latch set as soon as a wipe succeeds.
- `resetFailed` now performs restoration, resumes feed-history/archive/rescue persistence, and clears the reset generation only if no invocation has already completed a wipe. A failure on the first attempt remains recoverable and still returns its error.
- Added regressions for successful-wipe/failed-retry terminal retention, first-attempt failure followed by success, and existing first-attempt failure behavior.

## Validation

- RED: `go test ./pkg/daemon/ -run TestFactoryResetFailedRetryAfterSuccessfulWipeKeepsTerminalGeneration -count=1 -v` failed before the fix because the retry cleared the reset generation.
- GREEN: the focused reset regressions passed after the fix, including the retry case, first-attempt failure, failure-then-success, and feed-history fence tests.
- Recovery-path regression: `TestReservedAliasManualRecoveryConverges10769` now asserts that a completed wipe followed by verification failure rejects in-band config writes with `errDaemonResetting`; the focused test passed.
- Full module: `go test ./pkg/daemon/ -count=1` passed.
- `go vet ./pkg/daemon/` passed; `gofmt -l pkg/daemon/` returned no files.

## Risk

The latch is per-Daemon and sticky only after a wipe reports success. Failures before any successful wipe retain the existing restoration and recovery path. After success, later failures retain the reset and persistence fences until process shutdown.
