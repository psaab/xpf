# #18771: commit-time gate for un-admitted packed tails — plan review

- **Timestamp**: 2026-11-02
- **Action**: Prepare a design for adversarial plan review before implementation. The issue explicitly says no code until both plan-review seats sign off. This PR contains the proposed hook, decision rule, and tests; it does not implement the gate or admit any `(container, head)` pair.
- **Status**: DRAFT v1 — pending two declared-pool plan-review verdicts.

## Issue framing

A packed Junos statement such as `outer inner leaf value;` may be accepted while the compiler reads only the braced `Children` shape and silently drops the packed tail. The #2419 one-level census did not cover this two-level spelling. The #18763 census expansion measured 1,326 two-level cells: 171 `COMMITS-DIFFERENT`, 26 already refused, and 97 unclassified. #18762 and #18787 are concrete examples of defects found inside that inventory.

The issue asks for a systemic backstop, not bulk admission: report-only first, then a separately reviewed enforcement change. On a strict commit, only a tail proven both meaningful when braced and wholly ignored as packed should eventually refuse. On tolerant load/peer-sync, diagnostics must never prevent boot (#1960). Tails that are consumed in part must warn only. The current first phase is report-only everywhere.

## Existing path and the hook decision

`pkg/config/compiler.go:474` is the single `compileTree` orchestrator for generic, node-aware, strict, and lenient compilation. Its relevant order is:

1. Clone/prune the caller's tree (`:475-489`), hash API-auth secrets (`:494`), then run compact normalization (`:498-509`).
2. Run pre-expansion AST gates (`:566-810`).
3. Expand groups (`:812-853`); generic compilation uses the node0 fallback, while node-aware compilation selects its node-specific group view.
4. Run `compileExpanded` (`:870-889`), append the remaining compile warnings (`:891-966`), and return (`:967`).

The normalizer is deliberately pre-expansion. Its schema walk visits literal `groups` bodies, but that is not the effective tree: an unused group is not compiled, and an applied group can merge with inline content or resolve differently for a particular node. A pre-expansion gate therefore risks warning about an unused group, missing an inherited tail's final shape, or reporting a group fragment rather than the statement that reaches the compiler.

**Proposed placement:** split candidate discovery from adjudication at the `compileTree` level. After the selected group expansion has completed (`:843-853`), discover candidates against that effective tree using the normalizer's own schema walk on a clone. If there are candidates, retain an unmodified snapshot of that expanded tree and its structural site locators. Let the ordinary compile finish; at the end of `compileTree`, use the actual compiled result as **O** and adjudicate the saved expanded snapshot. This puts the scan after the exact effective group view is known, while reusing the real compile result instead of paying for a duplicate O compile. If source inspection/test proves that later compilation mutates the expanded AST, capture the snapshot at the post-expansion boundary only when candidates exist; never derive twins from an already-mutated tree.

This placement is a design decision for review, not yet established by a test. A required hook-order cell must prove: an applied-group packed tail is discovered; the same tail in an unused group is not; `CompileConfigForNode` sees only its selected group view; and the main compile still has exactly its current normalizer and gate order. If the compiler cannot preserve/clone the post-expansion tree at this boundary without unacceptable cost, stop and revise the plan rather than moving the gate blindly to the pre-expansion path.

## Candidate discovery from the normalizer

Do not add a second schema-derived site enumerator. The present `normalizeCompactStanzasWithScope` / `normalizeCompactNodes` seam already receives the exact `(containerKeyword, head)` pair at the point where the production scope predicate is consulted. The design is to add a private observer form of that same walk, preserving the existing seam and callers. When the predicate returns false for a node that still carries the matching residual tail, the observer records:

- the declined `(container, head)` pair;
- the exact effective-tree site locator (child-index path plus key span/identity, not just rendered text, because duplicate siblings can have identical paths);
- a safely rendered diagnostic path with no raw secret values.

The observer is called by the same branch that decides whether a tail is a body, after the existing identity and `compoundKey` descent. It records only pairs the normalizer actually consults and declines; it must not treat arbitrary residual `Keys` as candidates. Existing early declines (e.g. a tail that is not a schema child, or a stranding/leaf-body safety decline before the predicate is asked) remain outside this gate's stated population unless plan review explicitly widens the contract.

Candidate identity and attribution are distinct: normalization widening is a set of pairs, while cap/warning/attribution counts are concrete packed sites. A chain can expose a new inner pair only after the outer pair is admitted to the twin. The braced twin therefore re-runs the same observer walk to a fixpoint, adding newly revealed declined pairs to the widened set until no new candidates appear. The process must be bounded by the site cap; over-cap is never a refusal. Do not key a site only by `(container, head)` when multiple instances share that pair.

## Adjudication semantics

For candidate set **C**, use three views:

| View | Meaning |
|---|---|
| **O** | The actual compiled config returned by this `compileTree` invocation, with the effective expanded tree as authored and the normal production normalizer. |
| **B** | The braced twin: clone the saved expanded tree and run the same compact normalizer with production scope widened by exactly the declined candidate pairs in **C**, re-recording to a fixpoint so two-level tails fold all the way down. Compile with the same mode, node selector, and relevant options, but an internal `skipPackedTailGate18771` option prevents recursion. |
| **R** | The tail-removed twin: clone the same saved expanded tree and remove only the residual tail spans at candidate sites, preserving each container identity, existing children, and unrelated statements. Compile with the same mode and the gate disabled. |

A site is **DROP** only when both conditions hold:

1. **O differs from B**: the braced spelling changes the compiled result.
2. **O equals R**: the packed tail contributes nothing to the compiled result.

Thus `O != B && O == R` is the eventual strict refusal candidate. `O != B && O != R` is **PARTIAL**: some packed content is consumed, so warn but never refuse. `O == B` is clean. This two-condition test is necessary for the shipped reader spelling `redundancy-group 0 node 0 priority 200`: widening that reader's pair would make the braced twin unlike the authored packed reader, and deleting the tail changes O, so it must not be classified as DROP.

The comparison must include diagnostic effects that can themselves be the only consumption of a tail. The issue's initial proposal excludes `Warnings` from `reflect.DeepEqual`; that is not sufficient for a safe `O == R` proof. A tail that causes a warning/validation result but sets no typed field could otherwise look empty and become a false DROP. Compare semantic config fields and diagnostics separately: stable warning/error differences make the verdict non-DROP (at least PARTIAL/indeterminate, warning only). If either twin refuses, panics, cannot be compared deterministically, or exceeds the site cap, the gate must fail open for compilation and must never enforce. It may issue a generic report-only/indeterminate warning, but must not call the result DROP.

**Canonicalization:** `reflect.DeepEqual(*Config)` alone is not yet an acceptable comparator. `HashAPIAuthSecrets` uses salted bcrypt; because the main compile hashes before group expansion, a saved post-expansion clone carries the already-tagged verifier, and the hash helper is idempotent for stored verifiers. This is a candidate way to keep the same verifier across O/B/R, but a determinism control must prove it for realistic fixtures. Any other per-compile nondeterminism must be enumerated by the determinism cell and normalized without erasing meaningful differences. `Secret` values need deterministic, value-sensitive tagged hashes (not one constant “secret present” marker); otherwise O and R could compare equal after a meaningful secret tail was discarded. Never print secret material.

## Phase-one behavior and enforcement boundary

- Phase one has `packedTailGateEnforce18771 = false` as a compile-time constant. It is not runtime configuration.
- Both strict and tolerant paths add one `cfg.Warnings` entry and one `slog.Warn` per adjudicated site per top-level compile for DROP and PARTIAL. The caller's original tree remains unchanged.
- Tolerant compilation only warns in every phase. Strict compilation also warns in phase one.
- A separate enforcement PR may flip the constant only after one full report-only release and green census-agreement/determinism controls. Then strict DROP alone errors; PARTIAL, indeterminate, and over-cap remain warning-only. The enforcement change needs an upgrade note explaining that saved configs continue to load but the next strict commit refuses until the packed statement is braced, and an `xpfd check-config` route should show the sites in advance.
- Do not bulk-admit candidates as part of this backstop. Per-site admissions remain the measured #8690 route.
- Do not include raw packed `text` in `cfg.Warnings` or `slog`: packed tails can contain API tokens, passwords, encrypted passwords, shared keys, and other sensitive values. Prefer a value-free effective path and remediation text; if the final message includes any source tokens, route it through the established `collectSecretValues` / `scrubSecretValuesText` protections and test the redaction. Warning strings must be stable and sorted, and emitted once per site rather than once per twin/loop.

## Cells required before implementation is considered complete

1. **Hook and group expansion:** applied group packed-tail DROP is detected; unused group is silent; generic node0 fallback and each node-aware group view are tested; inline/group merges retain exact precedence. This cell settles the placement question above.
2. **Determinism control:** compile each realistic fixture twice and require canonical equality, including `docs/ha-cluster-userspace.conf`, `test/incus/*.conf` (only hermetic config compilation), and census fixtures. Include an api-auth secret because of the random bcrypt salt. Record any additional nondeterministic fields the comparator must handle.
3. **Census agreement / false-positive controls:** every two-level `COMMITS-DIFFERENT` site and every existing one-level empty/silent site **within the gate's actual declined-pair population** gets DROP or PARTIAL; every measured equivalent site in that population has no verdict. Sites already admitted are out of the gate population and must instead remain normalized with no candidate. Early-declined/unreached tails are tracked separately as uncovered census rows; this gate does not claim to adjudicate them. Existing strict `REFUSED` sites retain their refusal, and `security flow` remains divergence-free. The inventory remains an equals gate and can only shrink when a site is fixed/admitted.
4. **Positive strict/tolerant behavior:** a strict report-only packed DROP still commits and returns a warning; the same config on `CompileConfigLenient` returns a warning and never an error. In the future enforcement-mutant cell, strict DROP refuses while the tolerant call still compiles.
5. **Shipped reader negative control:** compile the shipped HA config with `redundancy-group … node … priority` and require no DROP/PARTIAL warning. Also include a read-tail fixture where deleting the tail changes O, proving `O == R` is required.
6. **PARTIAL control:** a measured partially consumed packed tail is reported but never refused, regardless of the enforcement constant.
7. **Diagnostic-only consumption:** a candidate whose only observable difference is a warning/validation diagnostic must not be classified DROP when the comparator sees no typed field change.
8. **Secret-output control:** construct a valid candidate carrying a distinctive secret and assert that neither `cfg.Warnings` nor captured slog output contains the secret, in raw or quoted form.
9. **Twin fidelity and bounds:** O/B/R use identical strict-vs-tolerant mode, `nodeID`, and effective tree; the tail-removal twin preserves container children; multi-site attribution names the true pair; more than 32 sites produces one aggregate warning and never refuses. Assert the common no-candidate path makes no twin compiles.
10. **Mutants:** comparator-always-equal is killed by a known DROP; comparator-never-equal by equivalent and HA controls; recorder-empty by census agreement; removing condition 2 by the HA reader control; enforcing on tolerant paths by the tolerant cell; skipping diagnostics by the diagnostic-only-consumption cell.

The named package tests belong in `pkg/config` and should exercise the gate through public strict/lenient compile entry points, not only a helper. These are hermetic config tests (U); they must not invoke netlink, `ip`, `nft`, host daemons, or cluster harnesses. The focused `pkg/config` suite and relevant Go build are the implementation validation; no live cluster/iperf gate is justified for this config-only change.

## Risk / open questions for the two plan seats

| Risk | Level | Reason / control |
|---|---|---|
| Wrong placement around group expansion | HIGH | Can warn on unused group text or miss the effective node view. Settle with the hook-order cell and keep the gate after selected expansion. |
| False refusal from comparator blind spots | HIGH | Salted secrets, diagnostic-only validation, and other nondeterminism can make O/R appear equal. Compare diagnostics separately; fail open on uncertainty; require determinism and mutant controls. |
| Sensitive configuration in diagnostics | HIGH | The proposed example message includes packed text, which can contain secrets. Do not emit raw source text; use a value-free path or proven redaction. |
| CPU/allocations on commit | MED | A normal compile pays for a clone/walk; candidate configs pay for twin compiles and possible per-site attribution. Early-exit when no candidates, cap at 32, and test that common path does zero twins. |
| Existing typed reader consumes packed tails | HIGH | Widening can produce a misleading braced twin. O==R is mandatory, and the HA reader is an explicit negative control. |
| Report-only operator noise | MED | A large config can surface many sites. Deterministic once-per-site diagnostics and one bounded over-cap warning; phase one measures volume before enforcement. |

Questions that must be answered before implementation:

1. Does `compileExpanded` or any post-compile helper mutate the expanded AST? If yes, what is the lowest-cost point to save the source snapshot only for candidate configs?
2. Can the existing normalizer walker expose the exact `Node`, structural site locator, path, and tail boundary without introducing a second schema traversal or breaking current test callers?
3. Should a diagnostic-only difference be classified PARTIAL or a separate INDETERMINATE verdict? In either case, confirm it can never refuse.
4. Which warning/error channels are semantically part of O==R, and how are they canonicalized without hiding real validation effects or producing ordering-only noise?
5. Does a post-expansion compile of a clone carrying an API-auth verifier preserve identical credentials across O/B/R, and are there other random/salted compiled fields?
6. What is the exact site-cap accounting when many nodes share one `(container, head)` pair, and can the attribution locator distinguish repeated sibling nodes reliably?
7. Is a generic value-free diagnostic sufficiently actionable, or can the path renderer safely name the site without exposing sensitive node keys?
8. Is a 32-site ceiling acceptable for report-only census coverage, or should the gate report the first 32 and an aggregate count while still never enforcing over-cap configs?
9. Does the same gate need to run for every strict entry variant (`CompileConfigForNode`, `CompileConfigJudgingPlaceholders`, current-cluster-primary variants), and is the single `compileTree` hook sufficient for all?
