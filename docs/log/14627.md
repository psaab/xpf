# #14627 — address-persistent sticky slot seeded per process

- **Timestamp**: 2026-10-17
- **Action**: Replace the per-process `hot_path_hash_seed()` in
  `sticky_pool_index` with the fixed domain seed `STICKY_POOL_HASH_SEED`
  (ECMP precedent), so the same `(src_ip, pool_len)` maps to the same
  pool slot on every HA node and across restarts. Docs/code reconciled.
- **Files**: `userspace-dp/src/nat/allocator.rs`,
  `userspace-dp/src/nat/tests_pool.rs`,
  `userspace-dp/src/hot_hash_seed.rs`,
  `docs/ha-failover-status.md`,
  `docs/userspace-dataplane-architecture.md`,
  `docs/userspace-dataplane-gaps.md`, `docs/log/14627.md`

## Why

#12789 keyed `sticky_pool_index` with the per-process secret
(`hot_path_hash_seed()`, getrandom `OnceLock`, no setter / HA sync) to
defeat offline collision construction against seed-additive FxHash.
That reshuffles the source→pool-address mapping on every restart and
differs between HA peers: after a failover, a host's NEW flows on an
`address-persistent` multi-address pool compute a different slot than
its synced sessions use, splitting the host across two public IPs for
the life of the pre-failover sessions (breaks FTP/SIP/IP-pinned
sessions). `docs/ha-failover-status.md` and
`docs/userspace-dataplane-gaps.md` still promised a pure
`(src_ip, pool_len)` function identical across nodes — docs and code
disagreed.

## What

- `sticky_pool_index` now calls `sticky_pool_index_seeded` with the new
  fixed constant `STICKY_POOL_HASH_SEED = 0x5354_4943_4b59_0001`
  ("STICKY" domain tag, version 1), following the `ECMP_FLOW_HASH_SEED`
  precedent for mappings that must survive restart/HA re-resolution.
  The hasher is unchanged: the keyed multiply-mix
  (`HotPathSeededState`/`KeyedFxHasher`, #12989) whose splitmix64 folds
  destroy the seed-independent v4/v6 collision families — only the seed
  source changes, from per-process secret to fixed domain constant.
  No allocation/copy added; sticky selection stays first-flow only.
- Justification for a predictable seed (documented at the constant and
  in `hot_hash_seed.rs`): the output is the wire-visible translated
  pool address in every packet, and the hash indexes no
  attacker-growable table, so predictable selection enables no
  collision eviction or chain amplification — the ECMP rationale.
- Existing sessions/leases are untouched (they pin their translated
  tuple); only fresh recomputations move, now to the same slot on
  every node. Single-address pools are unaffected (`pool_len <= 1`
  short-circuit unchanged).
- Docs updated to agree: `ha-failover-status.md` (pure function under
  the fixed seed), `userspace-dataplane-gaps.md` (keyed multiply-mix
  under `STICKY_POOL_HASH_SEED`, identical across nodes), and
  `userspace-dataplane-architecture.md` (same).
- New regression `sticky_pool_index_is_cross_process_stable_14627`:
  production `sticky_pool_index` must equal the seeded core under
  `STICKY_POOL_HASH_SEED` for 64 v4 sources (pool 4) and 16 v6 sources
  (pool 8), with a cross-seed control proving the seeded core is
  seed-sensitive (test not vacuous).

## Risk

One-time remap: the first fresh allocation after upgrade may land on a
different pool address than under the old per-process seed — the same
class of move every restart already caused pre-fix, now converging to
one stable mapping. Live sessions/leases keep their pinned address.
Predictable sticky placement is intentional and documented (above);
table-placement hashes keep their per-process secrets.
