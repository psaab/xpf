# Issue #15242 — NDP/ND telemetry: stop counting unconfirmable non-first ICMPv6 fragments as NA frag refusals

## Why

`xpf_userspace_ndp_na_frag_refused_total` (`NDP_NA_FRAG_REFUSED`) is the
RFC 6980 Neighbor Advertisement learn-refusal series. At base,
`parse_ndp_neighbor_advert` (`userspace-dp/src/afxdp/parser.rs`) on an
`ExtChainOutcome::NonFirstFragment` outcome bumped that counter whenever
the readable Fragment header's Next Header named ICMPv6 (58), with no NA
confirmation. A non-first fragment carries no L4 header — there is no
ICMPv6 type byte to confirm type 136 (NA) — so ordinary fragmented
ICMPv6 transit (e.g. a large ping split across fragments, trailing
fragment naming ICMPv6) incremented the RFC 6980 attack series on every
packet. Enforcement was unchanged (the frame was refused for learning
either way, nothing was learned); the defect is operator-visible
telemetry mis-attribution on a security series.

The arm was introduced by #14116/PR #14249 to preserve the pre-existing
count when the ext-chain walk learned to stop at non-first fragments;
the counter's documented contract (#9893) was already "bumped only for
NA-shaped frames (proto 58 + type 136 confirmed)", which a non-first
fragment can never satisfy.

## What

- `userspace-dp/src/afxdp/parser.rs::parse_ndp_neighbor_advert`:
  the `NonFirstFragment` arm now returns `None` WITHOUT counting —
  refused, uncounted, exactly like the existing `Truncated` /
  `OverLimit` / `NoNextHeader` arms. Only the first-fragment path
  below, where proto 58 + type 136 are actually confirmed and
  `walk.fragment.is_some()`, still bumps `NDP_NA_FRAG_REFUSED` once.
  The counter's doc comment is updated to state this explicitly.
  No new counter/series is added (the issue's preferred bounded fix;
  a separate "unconfirmable fragment" series was not introduced).
- `userspace-dp/src/afxdp/parser_tests.rs`:
  - `parse_ndp_na_9893_non_first_fragment_refused_and_counted`
    (name retained for history): now asserts the non-first frame is
    refused AND the counter (and bad-source counter, and the
    coordinator status surface) is unchanged.
  - New `parse_ndp_na_15242_icmpv6_non_first_fragment_transit_does_not_count`:
    the acceptance probe — a trailing ICMPv6 fragment with echo
    continuation payload leaves the counter unchanged.
  - `parse_ndp_na_9893_first_and_atomic_fragments_refused` now also
    asserts counting exactly once per first/atomic frame (the issue's
    "#9893 first-fragment NA cell still counts" control; previously it
    only asserted refusal).
- NOT changed: the walker (`walk_ipv6_ext_chain` /
  `ExtChainOutcome::NonFirstFragment`), any other consumer of that
  outcome (NAT64, forwarding resolvers), the bad-source gate, valid-NA
  learning, fragmented-UDP non-counting, metric names/descriptors, or
  the Rust→Go status wire — the series name and meaning for confirmed
  NAs are unchanged, only unconfirmable transit stops polluting it.

## Risk

Enforcement is unchanged: non-first fragments were and remain refused
for NA learning (never learned, still transit as before through
`poll_stages` classify). The only delta is telemetry: operators will
see the RFC 6980 series stop growing from ordinary fragmented ICMPv6
transit and grow only on NA-shape-confirmed first/atomic fragments.
No wire, descriptor, or config change.
