# #14625 — Removing `port deterministic` strands deterministic ports in the reused allocator (Y23-04)

## Defect
- `SourceNatPoolAllocatorKey` (`userspace-dp/src/nat/source/mod.rs`) is
  pool name + addresses + port range; it excludes allocation mode, so
  removing `port deterministic` reuses the exact same `PortAllocator`
  for round-robin PAT (`resolve_pool_allocators` exact-key reuse).
- Deterministic allocations were released with `free_no_recycle`
  (`recycle = !deterministic` in `free_translated_port`): the occupancy
  bit cleared but no token entered the per-address recycle FIFO. That
  was sound only while the allocator served deterministic rules for its
  whole life, because `claim_in_block` scans the bitmap directly.
- Round-robin `AddressOccupancy::claim()` never scans the bitmap once
  its monotonic fresh cursor is spent — it only drains the recycle FIFO.
  So after a deterministic→PAT flip, every deterministic port freed by a
  draining session (cursor already past its offset) is unreachable:
  the bit is clear, `show security nat source pool` reports it free,
  and PAT returns `AllocatorExhausted`. Bounded by the deterministic
  sessions live at the flip (≤ `max_tracked_flows` per allocator) and
  persists until the pool key changes. The HA-synced variant
  (`synced.rs` deterministic tag → same `free_no_recycle` release) had
  the identical hole.

## Fix
Always recycle on free — the fix direction the issue lists first
("always free with recycle (and let `claim_in_block` ignore the
ring)"):
- `userspace-dp/src/nat/allocator.rs`: `free_translated_port` loses its
  `recycle: bool` parameter and always calls `free_recycle`. Every
  caller updated (live-allocation unlink, persistent-lease teardowns,
  deterministic v4/v6 give-backs, GC lease reclaim, idle-lease-import
  rollback); the `freed` vectors drop their now-constant bool element.
  `AddressOccupancy::free_no_recycle` remains only as the test-only
  out-of-band clear behind `debug_clear_owner`.
- Why this is safe for a still-deterministic pool: `claim_in_block`
  already ignores the ring and scans the bitmap, and since #7174 the
  ring holds at most one token per offset, so deterministic churn can
  grow it to at most `range` tokens per address — bounded, not the
  unbounded growth #4559/#5178 feared (that fear predates the dedup
  bitset). A PAT claim that later pops such a token goes through the
  normal `claim_offset` CAS, so no duplicate identity is possible.
- The `deterministic` flag on `LiveAllocation` / leases is retained:
  BIB/lease identity and overlap checks still depend on it; it simply
  no longer selects the free path.
- Stale comments claiming a deterministic free must not recycle were
  updated in `allocator.rs`, `source/nat64_ports.rs`,
  `source/synced.rs`, `source/overlap.rs`, and `nat64.rs`.

NOT changed: the allocator key (the alternative fix — including mode
in the key so a flip builds a fresh allocator — was rejected because a
fresh allocator would need reseeding of the still-live deterministic
sessions' occupancy and would strand their releases; recycling keeps
one allocator correct for both modes), `claim()` / `claim_in_block`
claim paths, cursor semantics, and the Go #5144/#9428 owner-key
contract (no key field changed, so no Go widening is needed).
