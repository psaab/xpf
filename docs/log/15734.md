# Issue #15734 — RG2 on node1 blackholes IPv6 transit; failback holds past 300s

Recorded 2026-10-19 by the #12495/#13058 gate on the loss userspace
cluster (build `working-20694-g7d95e004cb`): RG2 failed to node1,
neighbor recovery was NA-attributed, IPv6 transit stayed 0/5 (and 0/2
~40 min later), and the failback left node0 in `secondary-hold`
`Manual=yes` past the 300 s deadline. SmokeMatrix restored the cluster
manually (`failover reset` + targeted `... node 0`); this change fixes
the two production root causes. The gate-script evidence trap is
#15733, handled separately.

## Root cause 1 — transit6 blackhole: statics never followed RG ownership

The loss cluster splits RG1 (WAN reth0.50/.80) and RG2 (LAN reth1).
With RG2 on node1 and RG1 on node0, a LAN→WAN v6 packet arrives at
node1 (RG2 owner) and must egress reth0.80 — an RG1 interface node1
does not own. Read-only snapshots in that state (this session,
post-restore, same asymmetry): node1's FRR shows the WAN statics
(`::/0 via 2001:559:8585:50::1 ge-7-0-2.50`, `2602:…::/64 via
…80::1 ge-7-0-2.80`) **inactive**, the cluster blackhole
`::/0 [250] unreachable` **selected**, and no connected
`2001:559:8585:80::/64`; node0 retains the connected WAN /64s and the
active default. During the recorded run the LAN host's default already
pointed at node1's MAC (`02:…:03`, REACHABLE), so transit died at the
first hop's kernel default — discard — while the VIP itself answered
(NA-attributed), exactly the gate's verdict split.

Mechanism: `assembleFRRConfig` HA-filtered dynamic protocols by RG
ownership (#11415 `frrHADemotionState`) but passed static routes
through unfiltered on every node. A demoted node's statics therefore
stayed in the managed section forever, zebra marked them inactive
(their egress connected prefixes leave with the VIPs), and the
cluster-mode Null0 default became the selected route.

Fix: `frrHADemotionState.filterStaticRoutes` (same file as the
protocol filters) now scopes global and per-instance statics in
`assembleFRRConfig`. A route (or individual next-hop) is dropped when
its egress — explicit next-hop interface, inferred v6 next-hop
interface, or the RETH connected prefix containing the next-hop
address — belongs to an RG this node is not primary for. Non-RETH
egress, next-table, and discard/reject routes are kept. Promotion
re-renders the statics through the existing HA FRR reconcile
(`scheduleFRRHAReconcile` fires on ownership edges and the 2 s RG
reconcile), so the new owner gains an active default as its VIPs land.

Regression: `pkg/daemon/frr_static_ha_15734_test.go` — all-primary
control renders everything; the recorded RG1-secondary/RG2-primary
split drops both WAN statics, prunes the mixed route to its LAN hop,
keeps the non-RETH route, and does not mutate the committed config;
promotion restores. Mutant-verified (forcing every hop active reds it).

Residual: per-RG split forwarding still depends on the fabric redirect
for flows whose egress RG is peer-owned; this fix removes the
kernel/FRR blackhole that preceded it. Live re-proof needs the #12495
gate re-run on the converged build (with #15733's evidence
preservation), which remains the #12495/#13058 lab acceptance.

## Root cause 2 — failback stranded: manual hold outlived the commit pin

Sequence (journals + SmokeMatrix's `rg2-failback.log`): the gate's
failback is a plain `request chassis cluster failover redundancy-group
2` on the current primary (node1) — a bare `ManualFailover`, not the
coordinated `RequestPeerFailover`. Node1 demoted to secondary-hold;
node0's dual-resign guard cleared its hold after 2 s, but node1's
committed-transfer pin (`transferCommitRolePinned=primary` from the
original coordinated failover) re-elected node1 primary, and node0's
re-armed `ManualFailover` could never clear again: `electRG` released
a manual hold only when the peer was resigned (weight 0) or itself in
secondary-hold. Node0 sat `secondary-hold Manual=yes` >300 s until an
operator ran `failover reset` and then the targeted form.

Fix: in `electRG`'s manual-failover guard, a hold also clears (same
2 s guard, same weight restore) when the peer is PRIMARY and the local
RG is the committed secondary of a completed transfer
(`transferCommitRolePinned && role == secondary`). The hold is spent
once the peer's committed ownership is stable; clearing it does not
promote the local node (peer-primary arms keep it secondary), it only
removes the phantom hold so no operator `reset` rescue is required
for the cluster to read — and elect — cleanly.

Regression: `pkg/cluster/failback_hold_15734_test.go` — the stranded
shape clears and stays secondary (mutant-verified); without the commit
pin the hold is preserved (deliberate manual failovers are not undone
when the peer takes over); the 2 s guard still applies on the new arm.
