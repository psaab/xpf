# #16711: userspace WireGuard transit ignored underlay path MTU (silent black hole past first hop)

- **Timestamp**: 2026-10-25
- **Action**: Implemented per-peer outer PMTU learning for the AF_XDP
  WireGuard transit path. Before: `wg_encap_frame` sized the outer
  solely to `min(local egress MTU, static route mtu)` and emitted it
  as one unfragmentable datagram; an ICMPv6 Packet-Too-Big from a
  smaller-MTU hop beyond the first reached only the kernel route
  cache, which the AF_XDP path never reads, so large inner packets
  black-holed silently (`encap_mtu_drops` stayed 0, no PTB to the
  inner source). Now a PTB (ICMPv6 type 2, or ICMPv4 3/4 for the v4
  outer) addressed to a local WG outer source is consumed only when
  its quote is a live WG outer — UDP, quoted src port =
  `wg_listen_port`, quoted dst = a peer's configured-or-roamed
  endpoint (address+port, canonicalized), quoted src = the PTB's
  local destination. A validated quote stores a per-peer soft-state
  outer PMTU on the peer (floored at 1280 v6 / 68 v4, shrink-only so
  a forged large PTB cannot inflate the budget, aged out after
  10 min per RFC 8201 §4, counted by `pmtu_learned`). The learned
  value caps `outer_mtu` in `wg_encap_frame` (by selected pubkey)
  and, via the `outer_physical_egress_mtu` SSOT, the
  `post_transform_inner_mtu` PTB advertisement and TCP segmentation
  sizing — so the next oversize inner yields an inner-source PTB
  advertising `wg_inner_mtu(AF_INET6, learned)` (or the encap guard
  drops it) instead of an outer the underlay cannot carry. The IPv4
  DF-clear twin encap is unchanged when no v4 PTB has been learned.
  The PTB packet itself still falls through to the normal flowless
  LocalDelivery handling; no existing gate is weakened.
- **File(s)**: `userspace-dp/src/afxdp/wg/pmtu.rs` (new: floor/aging/
  offer rules), `userspace-dp/src/afxdp/wg/peer.rs` (per-peer
  `pmtu_mtu`/`pmtu_learned_ns` atomics + accessors),
  `userspace-dp/src/afxdp/wg/engine.rs` (`peer_pmtu`/`note_peer_pmtu`),
  `userspace-dp/src/afxdp/wg/counters.rs` (`pmtu_learned`),
  `userspace-dp/src/afxdp/wg/mod.rs` (module registration),

  `userspace-dp/src/afxdp/frame/mod.rs` (re-export),

- **Validation**: `cargo check` clean (pre-existing warnings only).
  Targeted: `cargo test --bins -- wg_pmtu` — 3 passed
  (`wg_pmtu_ptb_learns_and_caps_encap_16711`: valid PTB(1400) →
  `post_transform_inner_mtu == wg_inner_mtu(AF_INET6,1400) == 1320`,
  1320 inner still encaps, 1321 drops; `wg_pmtu_forged_ptb_ignored_16711`:
  wrong dst port / wrong src port / non-peer quoted dst all Ignored,
  larger PTB never raises learned 1400; `wg_pmtu_floor_and_aging_16711`:
  sub-floor clamps to 1280, entry expires after `WG_PMTU_AGE_NS`).
  Pre-fix these cells fail by construction (no `consume_wg_outer_ptb`
  / no learned cap — the 1321 inner encaps at local 1500). Broader
  `wg_` + `post_transform_wg` regression run recorded in the PR.
- **Residual**: (1) The TUN-origin (control-thread) egress guard is
  NOT fed the learned PMTU — it sizes from spawn-time per-peer MTUs;
  kernel-socket traffic does benefit from the kernel's own PMTU
  cache for its socket, but unifying the TUN-origin guard with this
  soft state is follow-up scope, deliberately not folded here.
  (2) `wg_tcp_mss` (SYN clamp via `tunnel_outer_mtu`) is unchanged:
  it already errs smaller than the encap guard, and the learned
  budget reaches TCP through segmentation/PTB sizing; an MSS-only
  consumer would still clamp to the local MTU until the first PTB.
  (3) No outer source-fragmentation (RFC 2473 §7.1(b)) for inner
  packets ≤1280 on a sub-1280 learned path; the floored PTB +
  shrink-only cap is the accepted alternative, and v4-outer
  sub-1280 delivery already exists (#16512).
  (4) Lab verification on a real two-hop reduced-MTU underlay
  remains outstanding (the defect was never lab-observed; component
  cells above are the exercised evidence).
