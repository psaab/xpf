# #9942 — frr: preserve secure-tunnel unit netdev in static routes

- **Timestamp**: 2026-09-17
- **Initial base**: `origin/master` `a2ba528d0`; worktree `9942-frr-st0`; branch `fix/9942-frr-st0`.
- **Publication base**: rebased onto `origin/master` `7edd4aaa5d39` before push.
- **STEP-0 RED (base)**: A temporary reproduction on the clean base ran
  `go test ./pkg/frr -run '^TestStep0Repro9942$' -count=1 -v` and passed only
  because it asserted the existing bug: `XFRMIfNameAndID(st0.0)` created
  `st0.0`, while `render(st0.0)` emitted `ip route 10.99.0.0/16 st0`. The
  reproduction was removed after the RED evidence was recorded.
- **Root cause**: `pkg/routing/xfrm.go` preserves the authored
  `bind-interface` spelling when creating the xfrmi (`st0.0` remains
  `st0.0`). FRR's static-route renderer then applied an unconditional `.0`
  collapse to route operands. The existing `DeclaredNetdevs` map contained
  only interface declarations, so the renderer had no ownership-aware entry
  for a secure-tunnel route reference.
- **Fix**: `frr.DeclaredNetdevsForConfig` is now the shared constructor used by
  both `daemon.assembleFRRConfig` and the production standalone
  `cli.applyToDataplane` path. It keeps ordinary interface declarations and
  collects static-route, IPv6-inferred, and VPN bind references. Secure-tunnel
  references are resolved through `Config.SecureTunnelUnitNetdev`, preserving
  the authored bind spelling and the resolver-selected kernel device. The
  renderer probes this map before its legacy generic `.0` collapse. For an
  explicit `bind-interface st0.0`, the route renders `st0.0`; for a bare
  `bind-interface st0`, the same `st0.0` route reference resolves to `st0`.
  Daemon and standalone CLI therefore share one map-building contract rather
  than maintaining parallel reconstruction logic.
- **Fail-on-revert RED→GREEN**:
  - With the daemon resolver/map call removed, the daemon integration test
    failed because `ApplyFull` wrote `ip route 10.99.0.0/16 st0`, and the bare
    binding control had no `st0.0` map entry. Restoring the shared constructor
    made both pass.
  - With the standalone CLI constructor replaced by an empty map, the CLI
    integration test failed because `applyToDataplane` wrote the same wrong
    `st0` route. Restoring the shared constructor made it pass.
  - The FRR resolver-spy test fails if the helper reconstructs names from the
    route text instead of calling the ownership-aware resolver.
- **Controls**: The FRR renderer still maps an ordinary undeclared `wan0.0`
  to `wan0`, preserves `wan0.50`, and leaves bare `st0` unchanged. The map
  parity test pins explicit `st0.0` to `st0.0` and bare `st1` plus route ref
  `st1.0` to `st1`.
