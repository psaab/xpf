# Issue #12630 — unify AppID on/off fallback precedence

- **Issue:** The AppID-disabled resolver returned the first matching user-application pool winner before consulting the builtin fallback table. The AppID-enabled catalog instead ranked user and predefined applications together by port-constraint tier, then lowest assigned `app_id`. When a user application overlapped a builtin tuple such as UDP/4500, the same session could receive different labels depending on the AppID setting.
- **Why:** The mode toggle must not change the resolved label for a tuple merely because a user app also covers it.

## Change

The disabled tuple fallback now ranks matching user applications together with the existing narrow builtin-fallback application set. Port-constrained applications win over protocol-only applications; ties use the same assigned-ID ordering as the enabled catalog, including the existing collision-aware full-catalog assignment for an uncatalogued candidate. A user definition continues to shadow a same-named predefined application, and the fallback's narrow builtin set is preserved rather than admitting every predefined protocol into heuristic matching.

Added UDP/4500 AppID-on/off parity cells for protocol-only, exact-port, and range user applications, a lower-ID user win, a non-covering user control, and no-user control.

## RED → GREEN proof

- **RED:** Before the runtime change, `go test ./pkg/appid -run '^TestBuiltinPoolOnOffParity_12630$' -count=1 -v` failed the protocol-only, exact-port, and range cases: disabled labels were `my-udp`, `my-natt`, and `my-range`, while enabled resolved to `junos-ike-nat`.
- **GREEN:** After the runtime change, `go test ./pkg/appid -run '^TestBuiltinPoolOnOffParity_12630$' -count=10` passed.

## Risk

The change intentionally aligns disabled fallback selection with enabled catalog ranking only for the builtin fallback candidates already supported by the fallback table. User-defined overrides and unknown/no-match behavior retain their existing handling.

Known split (tracked #12731): the OFF dataplane stamps from the
referenced-only catalog, while this fallback now ranks unreferenced
builtins too, so stamped and unstamped sessions can render different
labels for complementary populations. The runtime comment's
same-label invariant holds only for candidates in the OFF catalog.
