# #14112 stale non-root authorized-key removal — engineering history

Issue: psaab/xpf#14112 ([research D5-10] stale non-root authorized-key
removal). Lane branch: `fix/14112-campaign`, base `origin/master`
7d6ac3b2b.

## Defect (present at base)

`applySystemLogin` (`pkg/daemon/daemon_hostauth_apply.go`) emptied-key
branch for a RETAINED user (base lines 335-382): when the passed config
lists a user with zero SSH keys and the UID-matched key-provenance marker
is present, it removed the managed `authorized_keys` and the marker
without ever consulting the live active config.

`runHostAuthCloseoutOwners` (`pkg/daemon/daemon_apply_hostauth.go:89-125`)
runs each owner in a goroutine under a shared budget; on timeout it
records the owner timed-out and moves on while the goroutine keeps
running. That abandoned owner can resume after a newer commit has
re-presented the same retained user WITH keys and installed them; the
stale empty-keys pass then deletes the newer file and its marker — a
management lockout authorised by a superseded config.

Sibling revocation paths already carried the #12169 live fence
(`liveConfig12169()` in `hostauth_live_fence_12169.go`):
`deprovisionLoginUser` (`login_password.go`), `applyRootAuth` root keys,
`reconcileSudoers`, `applySSHConfig`. Enumerated callers of
`applySystemLogin`: the apply tail (`daemon_apply_tail.go:194`), the
cancel closeout owner list (`hostAuthCloseoutOwners`, the abandoning
path above), first-commit rollback closeouts via the same owner list,
and test seams. Only the retained-user emptied-key branch lacked the
fence.

## Fix

`pkg/daemon/daemon_hostauth_apply.go`, `applySystemLogin`:

- Before removing, re-read live intent via
  `liveDesiredLoginUser12169(user.Name)`; if the live config desires keys
  for this retained user, abstain from the revocation, log
  `staleRevocationSuperseded12169("remove-retained-user-keys", ...)`, and
  converge by re-applying the live config
  (`restoreLiveLoginKeys`).
- After a successful unlink, re-check live intent before dropping the
  key marker (`repair-retained-user-keys`); after marker cleanup,
  re-check again
  (`restore-retained-user-keys-after-marker-cleanup`). Same treatment on
  the already-absent (IsNotExist) path. This closes the check/unlink and
  marker-cleanup races exactly as the root-key path does.
- Marker-removal failures are now accumulated via `fail(...)` instead of
  discarded (`_ =`), so a stale owner cannot silently report convergence
  over an undropped marker.
- Restores run under `applySem` (acquired lazily, released on return,
  mirroring `deprovisionLoginUser`/`applyRootAuth`/`reconcileSudoers`):
  a normal apply already holds the permit and runs cfg == live, so it
  never blocks; only an abandoned stale owner acquires. The permit is
  held through owner return, so a concurrent live-commit removal cannot
  interleave its own apply between this owner's restore and return
  (no delete-after-restore resurrection; cf. `TestZZR3RootKeyRestoreOutrunsRemoval`).

NOT changed: the UID/marker provenance gate (#5841), the unreadable-marker
fail-closed behaviour (#6798 — still reports non-convergence and removes
nothing), the write path for non-empty key lists, and nil-store unit-test
behaviour (`liveDesiredLoginUser12169` returns false with no store, so
direct reconciler tests revoke exactly as before).

## Residuals

- The pre-existing #5106 tests use a nil-store daemon, so they exercise
  the fence-disabled path; the new test covers the fenced path and the
  live-agreeing revocation control.
- A restore that itself fails (e.g. live keys unwritable) is accumulated
  into the owner's returned error, so the closeout reports non-convergence
  rather than clean — fail-visible, retried on next apply.
