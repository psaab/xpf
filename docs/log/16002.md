# #16002 — tolerant L7 `signature` beside tcp/80 stays armed port-wide

- **Timestamp**: 2026-10-23
  - **Action**: Added `signature` to the closed, exact, case-sensitive
    `junosApplicationLeavesNotImplemented9603` table.
    - Mechanism (measured on origin/master 4479260ebe before the fix):
      `application a { protocol tcp; destination-port 80; signature
      custom-http; }` is strict-rejected as an unknown statement, but the
      tolerant compile accepts it with a warning, compiles `tcp/80`, and
      `ApplicationMatchDrops` / `ApplicationReferenceMatchDrops` return
      empty and `ApplicationMatchWidened` returns false. The policy
      therefore stayed armed for every payload on port 80 instead of
      only payloads matching the authored L7 signature. The term form
      (`term t1 { ... signature ...; }`) measured identically via
      `UnknownTermLeaves`.
    - Fix: `signature` is now a table hit in
      `unimplementedJunosApplicationLeaf9603`, so it is an
      `ApplicationMatchDrops` reason whatever its value and wherever it
      stands (direct, term, flat-line, flat-chain, or parked behind a
      stray keyword in the same statement). The existing consumers then
      refuse the reference on the tolerant path: the userspace expansion
      lowers it to the #3261 `__unsupported__` sentinel with one mirror
      reason, `PolicyContentRejectionReasons` names the application and
      the statement, policymatch reports `ContentRejected`, and
      `ApplicationMatchWidened` (via the same helper) keeps the AppID
      catalog and tuple fallback inert.
    - Scope cuts, deliberate: no L7 signature engine is implemented
      (that remains the documented future work in
      docs/services-application-identification.md); the strict path is
      unchanged (it already rejects the unknown statement, naming the
      token); near misses (`signatures`, `SIGNATURE`) stay on the
      #9595 stray line beside a retained port, pinned by controls.
    - NOT changed: `services application-identification application
      <name> over ... signature ...` custom signatures are a separate
      hierarchy xpf does not compile into `applications` at all; this
      issue's evidence and fixture are the `applications application
      <name> signature ...` leaf beside a retained protocol+port.
