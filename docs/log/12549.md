# #12549 — classify landed ARMED journal write

- **Timestamp**: 2026-10-13
- **Action**: Treat a post-rename sync failure from armCandidate's final ARMED journal transition as landed; continue with the already verified trial instead of unwinding its BootNext and watchdog.

## Red before

With a real `fsatomic.SetAfterRenameSyncDirForTesting` failure at the ARMED write, the journal rename was visible as ARMED, but `armCandidate` treated the typed error as an ordinary failure, cleared BootNext, disarmed the watchdog, and returned an error. This left Arm refusing to retry an ARMED journal despite no queued trial.

## Change

- `armCandidate` uses the existing `isPostRenameJournalError` (`errors.As` for `*fsatomic.PostRenameSyncError`, also used by #12162 F1) at its ARMED transition. A landed ARMED rename continues to reboot; other errors still unwind normally. The warning states that directory-sync durability is unknown.
- Added an integration regression using the fsatomic post-rename hook. It checks the visible ARMED journal and matching BootNext, `IsArmed`, retained watchdog and arm record, and proceeding to reboot.

## Validation

- RED: the new regression failed before the fix, returning the `PostRenameSyncError` from the visible ARMED journal write.
- GREEN: `go test ./pkg/upgrade/ -run '^TestArmCandidateArmedPostRenameSyncProceedsToReboot_12549$' -count=1` passed.
- Mutant: forcing the ARMED branch to reject every write error made the regression fail with the post-rename sync error; restoring typed-error classification made it pass.
- Full suites: `go test ./pkg/upgrade/ ./pkg/fsatomic/ -count=1` passed.
- `go vet ./pkg/upgrade/ ./pkg/fsatomic/` passed; `gofmt -l pkg/upgrade/kernel_run.go pkg/upgrade/kernel_watchdog_disarm_12162_test.go` returned no files.

## Risk

The rename is visible, but the directory sync failed, so durability across power loss remains unknown. Proceeding preserves a consistent live ARMED journal, confirmed one-shot, and watchdog rather than tearing down the trial while leaving an ARMED state. Non-`PostRenameSyncError` failures remain fatal and follow existing cleanup.
