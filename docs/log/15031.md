# #15031 — generic-compile `${node}` fallback re-expands a partially merged tree

- **Timestamp**: 2026-10-18 (`fix/15031-campaign`)

## Why

The generic compile (`CompileConfig` — standalone commits and
`xpfd check-config` with nodeID<0) expanded groups without vars first
and, on an `undefined group "${node}"` error, retried with
`node=node0` vars on the SAME tree (`pkg/config/compiler.go`,
`pkg/configstore/store.go` schema view, plus mirrors in
`routinginstanceid.go` and `pkg/configstore/crypto.go`). The failed
first pass had already merged every group applied before the `${node}`
reference and stripped its `apply-groups` node, so the retry never
re-merged it. Its group-adopted stanzas lost their #12823/#12923 merge
provenance (the expansion-local budget is rebuilt per pass), so a later
group's `security policies default-policy` met the first group's
stanza as if authored inline, took the inline-wins override, and the
conflicting pair the #11821/#11367/#12821 gates judge never
materialized. Witness (measured on base): `apply-groups [ GA "${node}" ]`
with GA=`default-policy permit-all;` and node0=`default-policy deny-all;`
compiled generically to `PolicyPermit` with only the fallback warning,
while the fresh node0 compile (`CompileConfigForNode(tree, 0)`) rejects
with `conflicting duplicate stanzas specify "permit-all" and
"deny-all" (#11821)` — permit-first fail-open on exactly the standalone
path. Probe evidence: after the failed plain pass the tree already
carried GA's stanza as an inline-looking `default-policy permit-all;`
and its `apply-groups` node was gone; the retry's Format carried 1
stanza vs the fresh node0 expansion's 2.

## What

- `pkg/config/ast_groups.go`: new `ExpandGroupsNodeFallback15031(tagged)`
  — the single atomic fallback. When no `apply-groups` names a group
  through `${node}` it is one plain pass, bit-identical to before. When
  one does, it probes the plain pass on a throwaway clone only to
  decide: plain success (a group literally named `"${node}"`) and plain
  failures for any other reason (genuinely undefined group, cycle,
  budget) are reproduced exactly on the real tree; only the
  undefined-`${node}` failure expands the real tree, once, with
  `node=node0` vars. The partially merged tree is never re-expanded, so
  group provenance survives and the generic expansion is
  Format-identical to the fresh node0 expansion.
- Call sites migrated to the helper (no same-tree retry remains):
  `compileConfigWithOpts` (tagged, warning preserved via the returned
  flag), its tolerant `expandedPolicySourceTree` clone,
  `schemaValidateExpandedTreeForNode` (nodeID<0), the #9657
  routing-instance generic view, and `effectiveMasterPasswordPRF`.
- `TestTableIDGateMirrorsTheGenericNodeRetry_9657` updated: it pinned
  the retry-injection shape (a group injecting `groups node0` that only
  the same-tree retry would apply). Under the atomic expansion that
  injection never becomes a definition, node0 is undefined, and both
  lenient and strict generic compiles refuse with
  `undefined group "node0"` — the fresh-node0 verdict. The test name is
  kept (it still pins generic-view/compiler mirroring); its comment
  records the #15031 semantics change.
- Regressions: `pkg/config/compiler_default_policy_node_fallback_15031_test.go`
  (five conflict shape/order cells each with a fresh-node0 oracle,
  Format-identity + stanza materialization, controls for identical
  actions / inline override / benign node0 group / genuinely undefined
  group) and `pkg/configstore/node_fallback_15031_test.go` (standalone
  `CheckText` rejects with node0 oracle; benign `${node}` stays green).
- Docs: `pkg/config/README.md` bullet and `docs/config-schema.md`
  "#15031" section; the #9657 paragraph now names the atomic fallback.

NOT changed: node-aware compiles (`CompileConfigForNode*` always
expanded once with vars), the `${node}` -> node0 choice itself, the
fallback warning text, and every non-`${node}` expansion path.

## Risk

Generic compiles of `${node}` configs now produce exactly the fresh
node0 expansion instead of an order-dependent partial merge. Configs
that only "worked" because the retry dropped an earlier group's
content (the injected-`groups` shape, group conflicts resolved by
application order) are now refused or resolved as node0 resolves them;
that is the fail-closed correction the issue requires. No other
expansion, compile, or load behaviour changes; no live dataplane or
cluster was modified.
