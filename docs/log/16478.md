# Issue #16478 — Fabric gRPC listener has no pre-auth connection bound

- **Issue:** The fabric gRPC listener (`<syncIP>:50051`) authenticated per
  RPC (#4107) but bounded nothing at connection admission. A host without
  the PSK that completed the HTTP/2 handshake (preface + SETTINGS) and sent
  no RPC never reached an interceptor, yet held ~73 KiB heap, 3 goroutines
  and an FD per connection, unbounded — the gRPC sibling of the
  session-sync flood #5303 closed. 100k held connections ≈ 7 GB plus FD
  exhaustion: OOM/starved xpfd and loss of the peer-proxy surface
  (cross-node show/clear, MonitorInterface, forwarded failover) on the node
  an operator needs to fail over to. Validated Medium (R3-N04-02,
  codex/smr/wonder MATERIAL×3), probe-executed at d1ea69f9aa (985/1000
  preface-only conns held at t=3s, 886 still open at t=130s).
- **What:** Mirror #5303 on the fabric listener:
  - `pkg/grpcapi/fabric_conn_bound_16478.go`: a Server-wide Accept gate
    shared across both fabric listeners (the protected FD/goroutine pool
    is per-process). At most `fabricMaxConnsTotal` = 32 concurrent
    connections; the last `fabricPeerReserve` = 4 are consumable only by a
    connection whose remote IP is a configured peer fabric address
    (`fabricPeerAddrFn`, IP-only match, read live per Accept so comms
    rebinds are honoured; unparseable sources fall to the general pool —
    fail-closed). Excess connections close immediately at Accept, before
    grpc.Server spawns goroutines/buffers; refusals are counted
    (`Server.FabricConnRefusals()` / `FabricConnActive()`) and rate-logged
    ~1/sec; a refusal returns a temporary `net.Error` so grpc's serve loop
    backs off instead of exiting (no self-DoS). Slots hold for the
    connection's whole life and release exactly once on first Close.
    NewServer installs the gate; bare `&Server{}` fixtures keep a nil gate
    and unwrapped listeners (the #16081 discipline).
  - `buildFabricServer` now sets `grpc.KeepaliveParams{MaxConnectionIdle:
    5m, MaxConnectionAge: 1h, MaxConnectionAgeGrace: 30s}` and
    `grpc.ConnectionTimeout(30s)` (grpc-go defaults: idle ∞ / age ∞ / 120s
    handshake). Idle preface-only connections are GOAWAY-drained in
    minutes; even a ping-ACKing holder rotates hourly. Neither fires under
    an outstanding stream, so long MonitorInterface streams are not
    severed (at MaxConnectionAge an in-flight stream gets the grace
    window; the peer proxy re-dials per operation).
  - Observability: `xpf_fabric_conn_refusals_total` /
    `xpf_fabric_conn_active`, always emitted including at zero (#3464),
    via a new `api.Config.FabricConnStatsFn` hook (daemon wires
    `d.grpcSrv.FabricConnStats()`, read live per scrape since grpcSrv is
    assigned after the HTTP server) → `collectorDeps.fabricConnStats` →
    deferred pre-gate emitter + descriptor family (pkg/api
    `metrics_fabric_conn_16478.go`). api does not import grpcapi.
  - Docs: pkg/grpcapi/README.md "Fabric pre-auth connection bound
    (#16478)" paragraph.

## Notes

- Perf: accept/close path only — one atomic CAS per accepted connection
  and one per close, plus an IP compare against ≤2 configured peer
  addresses per Accept. No per-RPC, per-request, or dataplane cost.
- The peer reserve matches on source IP only (the peer dials from an
  ephemeral port): an attacker who can source-spoof the exact peer IP
  reaches the reserved tail but still cannot pass #4107 PSK auth, and the
  total cap still bounds the cost — the same posture #5303/#14371 took.
- Hostname peer addresses never match the reserve (production peer
  addresses are IP literals; `fabricPeerAddrs` yields literals). Such a
  source stays in the general pool: fail-closed, reserve simply unused.
- Long MonitorInterface streams: unaffected by MaxConnectionIdle (only
  zero-outstanding-RPC connections drain); at MaxConnectionAge (1h) an
  in-flight stream gets the 30s grace window, then the conn force-closes
  and the operator's `monitor interface` re-dials — an hourly reconnect at
  worst, never a mid-stream sever before 1h.
