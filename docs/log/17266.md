# #17266 — Avoid shared ID RMW for atomic tunnel datagrams

- **Timestamp**: 2026-11-07
- **Action**: Unified the three generated-datagram ID sources and skipped the shared sequence for atomic IPv4 tunnel headers.
- **File(s)**: `userspace-dp/src/afxdp/frame/headers.rs`, `userspace-dp/src/afxdp/frame/headers_tests.rs`, `userspace-dp/src/afxdp/frame/mod.rs`, `userspace-dp/src/afxdp/frame/tests_nat_rewrite.rs`, `userspace-dp/src/nat64/translate.rs`, `userspace-dp/src/nat64/icmp.rs`, `userspace-dp/src/nat64/mod.rs`, `userspace-dp/src/nat64_tests.rs`, `docs/log/17266.md`.
- **Why**: All three requested ID mint sites used process-global atomic read-modify-write operations. IPv4 datagrams with DF set are atomic (RFC 6864), so their ID need not advance a shared sequence.
- **What**: Replaced the three issue counters with one `DATAGRAM_IDENTIFICATION` sequence and shared `next_datagram_identification()` helper. Generated IPv4 IDs use one shared nonzero mapping in both tunnel and NAT64 paths, including across 16-bit wrap. DF-set tunnel headers write ID 0 without calling the sequence helper; the NAT64 DF-set branch already writes ID 0 without minting. Generated IPv6 fragment headers use the same raw sequence. The tunnel writer delegates header construction to a raw-ID helper, allowing the wrap regression to exercise the actual emitted tunnel ID with controlled boundary values. Deleted the old `NAT64_FRAG_ID` and `NAT64_V6_FRAGMENT_ID` statics; `IPV4_TUNNEL_ID` is replaced by the shared sequence.

## Worker identity finding

Worker identity exists at higher AF_XDP layers: `WorkerLaunchPlan.worker_id` is passed into `worker_loop_setup(worker_id)`, which pins that thread; `BindingIdentity` and `WorkerContext.ident.worker_id` also carry identity in selected paths. The mint APIs and their builders do not: `write_ipv4_tunnel_header`, `build_nat64_forwarded_frames`, and the NAT64 translator receive no worker ID, and `ForwardPacketMeta` has no worker/queue field. TX dispatch has `worker_id`, but `CopyFallbackInputs` and the builders it invokes do not carry it. Some NAT64 slow-path and ICMP paths also drop identity. GRE local-origin encapsulation is called from the per-TUN `local_tunnel_source_loop`, which has no AF_XDP worker ID. No current-worker-ID TLS/accessor exists; the unrelated `REDIRECT_SAMPLE_SEQ` TLS is only a sampler sequence. A strided scheme therefore requires plumbing identity through several builders plus a defined TUN-thread source/fallback; no per-worker stride or new global/TLS context was introduced.

## Performance and risk

No throughput measurement was made; no throughput claim is made. This removes the global RMW only for DF-set tunnel IPv4 headers (and NAT64's DF-set path already avoids minting); non-DF IPv4 IDs and generated IPv6 fragment IDs still use the shared process-wide sequence. `outer_frag.rs::OUTER_FRAG_ID` remains unchanged as the separate fallback for eligible outer IPv4 fragmentation when the header's ID is zero; it is outside the three enumerated generators. The common IPv4 mapping is nonzero and avoids the cross-site collision that would occur if NAT64 mapped raw 65534 to 65535 while a tunnel narrowed raw 65535 to 65535.
