# #15028 — two DHCP group interface refs resolving to one kernel device stop Kea

- **Timestamp**: 2026-10-18
- **Action**: refuse two DHCP group interface refs of one family that resolve to one kernel device at commit, warn on the tolerant path, and de-duplicate the rendered Kea interfaces list.
- **File(s)**: listed under Change.

## Defect

`pkg/dhcpserver/dhcpserver.go` collected every group's interfaces verbatim
into Kea's `interfaces-config` list (v4 ~:1427, v6 twin ~:1601) with no
de-duplication, and `pkg/daemon/daemon_ha.go` `resolveDHCPRethInterfaces`
resolved each authored ref through `Config.ResolveKernelIfName` with no
dedup either. Different authored refs name one kernel device — `reth1.0`
and its member `ge-0/0/1.0` both resolve to `ge-0-0-1`, a unit-0 ref and
its bare parent collapse identically, and one ref can repeat across
groups — so the rendered list named the device twice. Kea refuses a
duplicate interface and loads nothing, so every pool of the family
stopped while the commit reported `commit complete`. No
dhcp-local-server duplicate-interface gate existed in `pkg/config`.

## Change

- `pkg/config/compiler_validate_strict_dhcp_iface_15028.go` (new):
  `validateDHCPGroupInterfacesUniqueStrict`. Per family, in sorted group
  order, resolves every non-empty ref via `cfg.resolveKernelIfNameWith`
  with one hoisted tunnel map (`tunnelNameMapFn`, #8862) and refuses the
  first kernel device claimed twice, naming server, both `group/ref`
  pairs, and the device.
- `pkg/config/compiler_uniformgates_dhcp_app.go`: gate registered after
  the #14601 pool-values gate; tolerant path warns.
- `pkg/config/compiler_opts.go`: `lenientDHCPGroupInterfaces`, set in the
  tolerant options.
- `pkg/dhcpserver/kea_duplicate_interface_15028.go` (new):
  `dedupKeaInterfaces` — keep-first de-duplication returning the dropped
  duplicates; empty strings pass through (no device to collide on).
- `pkg/dhcpserver/dhcpserver.go`: both generators run the belt over the
  collected list and warn per dropped duplicate.
- Cells: `pkg/config/dhcp_group_interface_unique_15028_test.go` (C1/C1b/
  C2/C6/C6b refusals + three C0 controls + lenient gate),
  `pkg/configstore/dhcp_group_interface_15028_test.go` (same refusal
  through `CheckText`, the Store.Commit composition),
  `pkg/dhcpserver/kea_duplicate_interface_15028_test.go` (v4/v6 render
  belts, no-duplicate control, belt unit semantics).
- `pkg/dhcpserver/README.md`: "Duplicate group interfaces resolving to
  one device — #15028".

## Design notes

- **Resolve, don't compare strings.** Raw-ref comparison would miss the
  defect: `reth1.0` vs `ge-0/0/1.0` share no spelling. Keying on
  `ResolveKernelIfName` output is exactly the device Kea will be given,
  because the daemon resolves with the same function before rendering.
- **Per-family scope.** Dhcp4 and Dhcp6 render separate files with
  separate interfaces lists, so the same device in both families is
  legitimate and commits (pinned by a control).
- **Empty refs skipped** in both gate and belt: they name no device, and
  pre-existing handling of them is unchanged.
- **Node variance is not a false positive.** `ResolveKernelIfName` is
  node-relative for reth members; a commit-check on either node resolves
  both refs through the same member map, so a genuine collision is
  refused on both, and distinct devices stay distinct on both.
