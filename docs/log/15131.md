# #15131 — SYN-cookie SYN-ACK / ACK-RST for a tunnel-decapped inner reflected its synthetic zero-MAC header onto the underlay

## Issue
GRE/WireGuard decap replaces the inner frame with a synthetic Ethernet
header whose MACs are zero and marks it `TUNNEL_DECAP_INGRESS_FLAG`
(0x20) — GRE in `gre.rs`
(`GRE_DECAP_INGRESS_FLAG | TUNNEL_DECAP_INGRESS_FLAG`), WireGuard in
`wg/decap.rs`. #12864 gated `reject` (`enqueue_reject_reply`) and
#14642 gated the ICMP Time Exceeded / Packet-Too-Big builders against
reflecting that fake L2. The SYN-cookie path was missed: both call
sites of `enqueue_syn_cookie_reply` in `poll_descriptor/mod.rs` — the
screen `SynCookieChallenge` SYN-ACK leg and the session-miss
validated-cookie `AckRst` leg — pass the decapped inner frame, and
`cookie_reply.rs` gated only `ingress_has_synthetic_fabric_source`
(#12319 fabric stamp). The builders
(`build_syn_cookie_syn_ack_frame` / `build_syn_cookie_ack_rst_frame`
via `write_reply_eth_header` in `frame/tcp.rs`) copy
`frame[6..12]` -> reply dst and `frame[0..6]` -> reply src, so under a
syn-flood screen with syn-cookie on a GRE/WireGuard tunnel zone every
challenged SYN queued an unencapsulated SYN-ACK (and every validated
ACK an ACK-RST) with dst/src MAC 00:00:00:00:00:00 on the physical
underlay binding — flooded as unknown unicast, counted as sent.

## Fix
#12864/#14642 parity — suppress, do not encap-route (suppression
matches the shipped reject/TE/PTB contract):

- `userspace-dp/src/afxdp/poll_descriptor/cookie_reply.rs`:
  `enqueue_syn_cookie_reply` returns `false` at the top when
  `meta.meta_flags & TUNNEL_DECAP_INGRESS_FLAG != 0`, before the
  #12319 fabric-stamp gate, before the TX-budget gate, and before any
  sent counter. Both cookie legs funnel through this single choke, so
  one gate covers SYN-ACK and ACK-RST; the frame builders have no
  other production caller. The callers already drop the packet and
  recycle the descriptor on either outcome, so suppression fails
  closed with no pending TX and no sent counter.

NOT changed: a shared generated-reply refusal helper across reject /
ICMP / cookie (suggested as "ideally" in the issue). Each path already
checks the same flag constant inline at its choke (`reject_reply.rs`,
`icmp.rs`, `icmp_ptb.rs`); extracting a helper would touch all three
shipped gates for no behavior change, so the cookie gate follows the
existing inline pattern instead. NOT changed: the decap producers,
the screen/session-miss call sites, and native/fabric-stamp cookie
behavior (the #12319 gate and native controls below are untouched).
