## Fix direction

### F-035: new overlap tracker, drop overlapping (RFC 5722/Juniper teardrop semantics)
- New module `fragment_overlap` (sharded LRU, 16x64, 2s idle + 10s absolute, same clocks as FragAssoc).
- Key: `(family, src, dst, ident, proto)` — the RECEIVER's reassembly key, WITHOUT FragAuthority.
  Rationale: receiver reassembles on wire identity, not ingress domain. Including authority would miss
  cross-ingress overlaps that still reassemble together. DoS via cross-key squat is bounded by shard cap
  + TTL, same as FragAssoc.
- Value: small vec of seen `(start,end)` byte ranges (start=offset_bytes, end=start+payload_len), plus
  deadline/created/generation? Generation: overlap is a wire property, not a config verdict — do NOT fence
  on config generation (a commit does not change whether bytes overlap). Owner-RG: also do NOT fence
  (overlap is not an entitlement). Only TTL + absolute bound.
- Range derivation:
  - IPv4: `offset=(frag_off&0x1FFF)<<3`, `len=ip_total_len - ihl*4` (clamped, fail-closed on under-length).
  - IPv6: `offset=frag_off&0xFFF8`, `len=ip_payload_len - frag_data_off` (need frag_data_off: parse ext chain
    up to Fragment header, same as screen extract; fail-closed on over-limit/truncated).
- Check-and-record on EVERY fragment (first and non-first, NAT'd or not, forward or reply), BEFORE
  enforcement (policy/screens/NAT) so enforcement never runs on bytes that will be rewritten.
  - If `new_range` overlaps any prior range for same key (strict overlap: `max(starts) < min(ends)`;
    adjacency `end==start` is NOT overlap; identical retransmit IS overlap -> drop second), drop + counter
    `frag_overlap_dropped`.
  - Else record range (coalesce? No — keep up to 8 ranges, evict oldest on overflow, fail-closed? Need to decide)
    and continue to enforcement.
- Hook point: early in `poll_binding_process_descriptor` loop, right after `meta` + `packet_frame` available
  and before `resolve_flow_session_decision` / `stage_screen_check`? Must cover both flow-backed and flowless
  paths with ONE call. Alternatively hook in `frame` helpers? Prefer ONE site before the `if let Some(flow)` split.
- Positive control: adjacent fragments (end==start) forward; existing teardrop/ping-of-death screens unchanged
  (they are per-fragment malformation, not overlap).
- Docs: update `docs/feature-gaps.md` Force IP Reassembly row + teardrop gap note to record that overlap is now
  detected (stateless screen still does not reassemble, but overlapping datagrams are dropped).

### F-036/F-053: install reply fragment associations on session-hit first fragments
- Root: installs only fire on new-flow commit (`poll_descriptor/mod.rs:3101/3113`). Reply first fragments
  (and forward first fragments of existing flows) hit sessions and never install, so reply tails miss and
  forward untranslated (DNAT) or misdeliver (pool SNAT).
- Fix: on the session-hit path (after `resolve_flow_session_decision` returns `Some`, before TX), if packet
  is a first fragment (offset 0 MF=1) and `decision` carries same-family rewrite (or NAT64) and resolution is
  ForwardCandidate with neighbor, call the existing install helpers with the REPLY's l3_packet + authority.
  - Reuse `nat_install_forward_fragment_assoc` / `nat64_install_forward_fragment_assoc` as-is: they key by
    `(l3_packet, authority)` and store `decision` (which for a reply hit is already the REVERSE decision via
    `NatDecision::reverse`). The `forward` in the name is a misnomer (it means "same-tuple"), no logic change.
  - Authority: `frag_ingress_authority(forwarding, meta, ingress_zone_override)` with the REPLY's meta/override
    (same inputs the reply tail's consult will use). Must verify which `ingress_zone_override` is in scope on the
    hit path (raw stamp vs RG-gated shadow) and match install/consult exactly (same as forward does).
  - Generation/owner-RG stamping unchanged (current generation, owner RG of reply resolution).
  - `reverse: None` stays None for same-family (reverse decision is in `decision`, not in `Nat64ReverseInfo`
    which is NAT64-only). The issue's "give reverse: a producer" is NAT64-specific; same-family replies do not
    need it.
- Consult: no change — `nat_consult_forward_fragment_assoc` already keys by reply tuple + authority and returns
  any same-family rewrite (forward or reverse). Verify it does not filter reverse decisions (it checks
  `!nat64 && rewrite present`, which holds for reverse).
- #6122 discriminator: OUT OF SCOPE for this fix (documented residual). Rationale:
  - In-order (first-then-tail, the realistic case and what the repro cells cover) is fixed by the install.
  - Reorder (tail-before-first) for replies cannot be distinguished from plain traffic via rules alone without
    over-dropping (e.g., plain outbound from a DNAT target's IP would match a naive "src is DNAT pool" check).
    A session-aware L3 check (scan for forward sessions matching reply L3) is a new index + hot-path cost,
    not bounded by this cohort's "named tests only".
  - The existing forward-miss fail-closed remains; reply-miss reorder remains fail-open (leak for DNAT, drop via
    MissingNeighbor for distinct pool) and is recorded as a residual in `docs/log/9950.md` + code comment.
  - If hostile review demands it, fallback is to extend the probe with reverse arms gated on session existence
    (not just rules), but that is a larger change.
