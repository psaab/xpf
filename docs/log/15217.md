# #15217 — fallback session-delta drain discards popped batch on status-apply error (A30-01)

- **Timestamp**: 2026-10-19
- **Action**: Queue fallback-drain deltas before propagating a helper status-apply error, and count/log the episode
- **File(s)**:

## Mechanism (re-anchored at origin/master f7bcca0291)

- `Manager.DrainSessionDeltas` (`pkg/dataplane/userspace/manager_status.go:393-394`) returns `resp.SessionDeltas, status, err` when `applyHelperStatusLocked` fails after the helper response arrived. The helper has already popped that batch, so the deltas are consumed: they will not be offered again incrementally.
- The fallback drain (`drainUserspaceSessionDeltasWithConfigLocked`, `daemon_ha_userspace_stream.go`) returned `total, err` before `queueUserspaceSessionDeltasLocked`, discarding the popped batch. Both production callers in `eventStreamFallbackLoop` (reconcile and fast-fallback arms) discard the error, so nothing logged or counted the loss.
- Consequence is HA standby divergence on the stream-down fast-fallback arm only while `applyHelperStatusLocked` fails: opens are recoverable via LossResync, closes stay stale until peer GC. Severity Low per the source report; consensus MATERIAL (3-way) in validator research run `research-work.AdQvt1jMKw`.

## Change and scope

- **Changed:** only the cited drain error path. A non-empty batch arriving with an error is recorded (schema fingerprint), queued through the existing `queueUserspaceSessionDeltasLocked` (same schema gate and eligibility walk as the success path), counted, warned once per minute, and the error still propagates and stops further batches.
- **Not changed:** `Manager.DrainSessionDeltas` keeps returning deltas with the error (deliberate since #9699: drained deltas are consumed and must reach the caller; the owner-RG export all-or-error contract does not apply here). The optional helper-side latch on drain-response write failure was not added — the daemon-side queue-before-error fully covers the anchored mechanism. Empty-batch errors keep the bare `return total, err` with no count, so transport failures are not reclassified. Callers still discard the returned error exactly as before; no behaviour change outside the cited mechanism.
