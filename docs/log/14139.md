# Issue #14139 — IPsec PSK, selector, and peer-ID rendering

- **Issue:** psaab/xpf#14139 (research-validated D5-06; codex=MATERIAL,
  opus=MATERIAL, spark=NEG → gate passed). Lane branch:
  `fix/14139-campaign`, rebased onto `origin/master` 7173f8ef7.
- **Context read:** Full issue body, all three reviewer lanes
  (codex-b4 / opus-b4 / spark-b4, D5-06 sections). No comments on the
  issue contradicted or narrowed the scope. Two of three sub-claims
  were validated MATERIAL: (a) empty effective PSK renders a live
  `auth = psk` connection with no `secrets{}` entry; (c1) a
  comma-separated gateway address is emitted as ONE comma-joined PSK
  `id` literal. The explicit-selector child-drop arm (b) was refuted
  as the designed fail-visible belt (#10884, strict-gated) and is
  unchanged.

## Defect (present at base)

`renderConfigWithExternalInterfaceFailClosed` (`pkg/ipsec/policy.go`)
only skipped a VPN for a *malformed non-empty* PSK (`normalizePSK`
error). When `authMethod == "psk"` and the effective secret — VPN PSK,
then IKE-policy fallback — was `""`, the connection block rendered
with `local/remote { auth = psk }` while the `secrets{}` loop emitted
nothing, leaving strongSwan to consult another VPN's secret whose
identities overlap. Every neighbouring failure mode (bad gateway,
proposal, DH, AH, section-breaking name, empty selector set) already
skips the VPN; a missing credential uniquely did not.

`pskIDSelectors` added the entire comma-separated `remoteAddr` as one
`id-<n>` value. That string is not an IKE identity, matches no peer,
and silently leaves the secret unscoped for every address in the list
(the same list is rendered verbatim into `remote_addrs`).

## What

- **Render belt (pkg/ipsec/policy.go):** a PSK VPN with no effective
  secret is now skipped by name (same fail-closed class as a malformed
  PSK): no connection, no orphan secret, `rendered` excludes it so
  Apply unloads it and tears down any stale SA. Pubkey (certificate)
  VPNs have no PSK by design and are unaffected.
- **Selector split (pkg/ipsec/policy.go):** `pskIDSelectors` splits
  `remoteAddr` on commas (trimming spaces) and emits one `id-<n>`
  selector per peer address. An explicit `remote-id`, when configured,
  still supersedes the address list; `%any`/empty entries stay
  filtered.
- **Commit gate (pkg/config):** new
  `validateIPsecPSKPresenceStrict`
  (`compiler_validate_strict_ipsec_psk_14139.go`) wired into
  `runUniformGatesIPsecEvent` with `lenientIPsecPSKPresence`, exactly
  mirroring the existing #9495/#4300 doctrine: `CompileConfig`
  (commit) hard-rejects a PSK VPN with no key; `CompileConfigLenient`
  (load / HA sync) warns and keeps the VPN, and the render belt keeps
  the uncredentialed connection from loading. The auth determination
  mirrors `resolveIKESettings` (PSK default; proposal
  authentication-method when the chain resolves), so cert VPNs and
  the IKE-policy-fallback-key case commit cleanly, and a VPN already
  rejected/skipped for a dangling chain is not double-diagnosed.
- **NOT changed:** the explicit-selector child-drop (refuted arm,
  designed #10884 belt), the `%any` + local-id scoping (refuted c2),
  and no config-level multi-address gateway validation (a commodity
  dotted list must first become a renderable endpoint; an unvalidated
  single endpoint still falls to the existing endpoint gates).

## Verification scope note

`pkg/ipsec` contains 54 pre-existing tests that construct IPsec VPNs
with no PSK at all and assert they render. Any fix inside this issue's
acceptance ("a psk VPN with empty effective secret [is] skipped")
necessarily changes those fixtures' outcome: the tunnel they exercise
is exactly the uncredentialed connection the issue removes. Those
tests belong to other issues' render contracts; this lane does not
rewrite their fixtures. Main should run the full `pkg/ipsec` /
`pkg/config` suites and adjudicate those cells (adding a PSK to the
fixtures is the mechanical migration; the security intent — no
uncredentialed `auth = psk` connection ever loads — is the #14139
contract).

## Risk

- A persisted config with a PSK VPN and no key now loses that tunnel
  at render (with a warning naming how to fix it) instead of loading
  an uncredentialed connection; strict commit rejects it outright.
  Operators must configure the key — deliberate, fail-closed.
- Multi-address PSK scoping widens each secret's `id-<n>` set from
  one unmatchable literal to the actual per-address identities; a
  peer at any listed address can now match — that address is already
  in `remote_addrs` for the same connection.
