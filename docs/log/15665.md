# Issue #15665 — `policy-statement` `then community` combined/repeated/bracketed actions dropped

## Claim (narrowed, verified at origin/master d316277cb4)

Single-scalar `CommunityOp` overwrote combined `delete` + `add`/`set`
actions, dropped repeated `community add` statements, and rejected
bracketed multi-community references.

## Live verification (pre-fix, this worktree)

- RED `pkg/frr` 15665 tests on base: `delete C1; add C2` rendered
  neither action (term compiled empty for the value op), repeated
  `add 65000:1; add 65000:2` rendered only `65000:2 additive`, and
  `add [ C1 C2 ]` (defined C1/C2) failed strict compile with
  `uses "C1 C2", which is neither an FRR community literal nor a
  defined community...`.
- RED `pkg/config` 15665 tests on base: repeated add kept only the
  last value; bracketed defined names failed resolution because
  `ResolveCommunityValue` looked up the joined string `"C1 C2"` as a
  single community name.
- Decisive check named by the issue (spark): the typed model at base
  already retained both delete and add values in some orders, but
  `emitTermBody` switched once on the scalar `CommunityOp`, so only
  one action rendered. All three legs (combined, repeated, bracketed)
  reproduced live, so all three are fixed here — not closed as
  already-fixed.

## Fix

- `pkg/config/compiler_routing.go`:
  - `applyCommunityAction`: `delete` only appends to
    `CommunityDelete` and no longer overwrites
    `CommunityOp`/`Community`/`CommunityAdd` (a pure-delete term keeps
    the legacy `CommunityOp="delete"` marker for persisted/legacy
    consumers). Repeated `add` accumulates values in authored order.
    An `add` coexisting with a `set`/bare replace keeps both. `none`
    still clears every other community action.
  - `resolvePolicyCommunityOperands`: resolves `Community` and
    `CommunityAdd` independently (not gated on the scalar op), each
    via the new per-token resolver, each with its own failure flag
    (`CommunityResolutionFailed` / new
    `CommunityAddResolutionFailed`).
- `pkg/config/community_member.go`: `ResolveCommunityValueTokens`
  resolves a multi-token operand per token — defined name expands,
  literal passes through, defined-but-unexpandable and undefined
  tokens fail the whole operand (preserving the #12069 fail-closed
  rule). Splitting uses only FRR's ASCII separators so Unicode
  separators keep being rejected (#12069 separator gate).
- `pkg/config/compiler_validate_strict_routing.go`: strict gate now
  checks every value-carrying action present (add and set/bare) with
  its own flag, instead of switching once on `CommunityOp`.
- `pkg/frr/policy_render.go` (`emitTermBody`): emits one
  `set comm-list <name> delete` line per `CommunityDelete` entry
  whenever non-empty (except under `none`, which clears deletes), in
  addition to the set/add action; a coexisting add renders after a
  set/bare replace. Legacy `CommunityOp="delete"` terms with an add
  value still render the additive line. Per-action resolution flags
  keep a failed add from suppressing a valid set and vice versa.
- `pkg/config/types_routing.go`: documents the decoupled model and
  adds `CommunityAddResolutionFailed` (`json:"-"`, compiler-only).
  `CommunityAdd` stays a space-joined scalar so the REST/helper wire
  shape (`"CommunityAdd":"65000:1"`) is unchanged.

## Regression

- `pkg/config/policy_community_combined_15665_test.go`:
  delete+add, delete+set, repeated add accumulation, bracketed
  `[ C1 C2 ]` defined-name resolution, bracketed undefined rejection.
- `pkg/frr/policy_community_combined_15665_test.go`: FRR route-map
  emits both delete and additive lines (delete first), the combined
  repeated-add additive line in order, and bracketed members.
- Existing 12069 flag assertions updated to the per-action flag.

## Risk

- Render order for a combined term is delete lines first, then
  set/add — FRR applies route-map set clauses in order, matching the
  Junos delete-then-add intent. A term authoring `add` before
  `delete` still renders delete first; the community result is the
  same (delete strips by list, add appends literals).
- `CommunityOp="delete"` is retained only as a legacy marker on
  pure-delete terms; nothing switches exclusively on it anymore.
