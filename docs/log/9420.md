# #9420 — next-table ip rules carry no ingress scope

## Measurement (re-done, not inherited)

The issue's kernel evidence was re-measured on this host (Linux 7.0.13) in a
private `unshare -rn` netns before any code was written. Two `dummy` interfaces
enslaved to `vrf-b` (table 200) and `vrf-c` (table 300), one unenslaved
(`duma`), the prefix `10.9.0.0/16` present only in table 200:

| Cell | Rule | Probe | Result |
|---|---|---|---|
| A | none | `iif dumc` (VRF-C) | Network is unreachable |
| B1 | `to 10.9.0.0/16 table 200 pref 100` | `iif dumc` | **`via 10.20.0.1 dev dumb table 200`** — diverted |
| B2 | same, VRF-C now HAS its own route in table 300 | `iif dumc` | **still table 200** — the VRF's routing is overridden |
| B1b | same | `iif duma` (default) | table 200 — the intended leak |
| B3 | rule removed | `iif dumc` | Network is unreachable (control) |
| F1a | `to 10.9.0.0/16 iif duma table 200 pref 100` | `iif duma` | table 200 — intended leak preserved |
| F1b | same | `iif dumc` | Network is unreachable — **no leak** |
| F1c | same, VRF-C has its own route | `iif dumc` | `dev dumc table 300` — its own table |

The first `ip route get` shape tried (`from <a local address> iif <dev>`)
returned `Invalid argument` on this kernel for every cell, which reads exactly
like a null result. Switching the probe source to a NON-local address made all
eight cells resolve. Recorded because the failing shape produced a uniform
"nothing happens" that could have been read as "the defect does not reproduce".

## Designs measured and rejected

- **`goto` escape band** (one `iif <vrf-dev> goto <band-end>` rule per VRF ahead
  of the band, keeping ONE rule per leak): the kernel requires the `goto` target
  to be a rule at that EXACT priority. With no rule at pref 200 the rule shows
  as `[unresolved]` and is a silent **no-op** — every cell leaked again. It only
  worked when aimed at pref 1000 because the l3mdev rule happens to sit there.
  A mechanism that fails OPEN and silently is the wrong shape for this defect.
- **`iif <vrf-dev> lookup <vrf-table>` escape**: `iif <vrf-dev>` does match a
  packet ingressing an enslaved interface (measured), but the rule is not
  terminating — when the VRF has no route for the prefix it falls through to the
  band and leaks. Fixes B2, not B1, and B1 is the finding.
- **Including `lo` in the scoping set** to keep host-originated traffic on the
  leak: an `iif lo` rule was measured to hijack a socket bound to ANOTHER VRF
  (`ip route get 10.9.0.1 oif vrf-c` → table 200). That is the first exposed
  path the issue names, so `lo` is excluded and the narrowing is documented.
- **Moving the band after l3mdev (pref > 1000)**: fixes B2 only; a VRF with no
  route for the prefix still falls through and leaks.

## Change

- `pkg/routing/rules.go`
  - `nextTableManager.Apply` takes `ingressIfaces []string` and emits one rule
    per ingress interface with `rule.IifName` set — the #5117 shape.
  - Fail-closed gate: an eligible leak with an empty ingress set installs
    NOTHING and returns a degraded error. It runs AFTER `clear()`, so a stale
    unscoped rule from a previous apply is still removed.
  - `hasEligibleNextTableRoute` keeps that gate silent for a config with no
    next-table leaks at all.
  - The window cap is now **leak-atomic** (`prio+len(ingressIfaces) > base+max`)
    and the overflow error names the per-interface multiplier.
  - New exported `DefaultInstanceIngressIfaces(cfg)`.
- `pkg/routing/routing.go`, `pkg/daemon/daemon_apply_routing.go` — thread the
  scoping set through.
- `pkg/routing/README.md`, `docs/rib-group-route-leaking.md` — the band's
  contract, the three operator-visible consequences, and the `lo` narrowing.

## Cells

New (`pkg/routing/rules_9420_test.go`):

- `TestNextTableRulesIngressScope_9420` — TOTAL over the emitted rules: no rule
  may carry an empty `IifName`. A count/presence check cannot tell a correctly
  scoped set from one where a single unscoped rule slipped through, and one
  unscoped rule at pref 100 is the whole finding.
- `TestNextTableRulesFailClosedWithoutIngress_9420` — the refusal, plus the
  control that a config with no eligible leak still applies silently.
- `TestNextTableWindowIsLeakAtomic_9420` — 3 ifaces × 34 leaks must install 33
  whole leaks (99 rules), never a split leak.
- `TestDefaultInstanceIngressIfaces_9420` — the scoping set, plus the control
  where every interface is claimed.
- `TestNextTableIngressScopeOnRealKernel_9420` — the netns cells above, run
  under `go test`. It asserts B1/B2 **reproduce** before it asserts F1b, and it
  scores F1b against F1a in the same run, because "the leak is scoped" and "my
  probe reached nothing" otherwise read the same. Skips (does not fail) where
  `unshare`/`ip`/netns are unavailable, unless `XPF_REQUIRE_NETNS=1` turns
  every skip arm into a failure (#9812 runs it under a forcing leg in
  `make selftest` that sets it).

Re-anchored: the pre-#9420 next-table cells now pass a ONE-interface scoping set
(`testNextTableIifs`), so each leak still costs exactly one rule and every
priority / count / cap assertion those cells make is preserved verbatim.

## Mutation matrix

The scorer was given a two-direction control before being trusted: a deliberate
type error in production code read `VOID(BUILD)`, a deliberate assertion break
in a test read `KILLED`. Every mutant was asserted APPLIED (removals 1 -> 0)
before scoring.

| # | Mutant | Target | Verdict |
|---|---|---|---|
| M1 | drop `rule.IifName = iif` at the emit site | `TestNextTableRulesIngressScope_9420` | KILLED |
| M2 | remove the fail-closed gate | `TestNextTableRulesFailClosedWithoutIngress_9420` | KILLED |
| M3 | restore the non-leak-atomic cap (`prio >= base+max`) | `TestNextTableWindowIsLeakAtomic_9420` | KILLED |
| M4 | stop excluding instance-claimed interfaces | `TestDefaultInstanceIngressIfaces_9420` | KILLED |
| M5 | sever the daemon WIRING (pass a constant instead of `DefaultInstanceIngressIfaces(cfg)`) | whole repo | **SURVIVED** |

M5 survived the first matrix over the ENTIRE repo. The pkg/routing cells prove
the applier scopes what it is GIVEN and say nothing about whether the daemon
derives and passes the right set, so the shipped binary could have scoped every
leak to a constant interface with a green board.
`TestApplyRoutingRulesWiresNextTableIngressScope_9420` (pkg/daemon) now drives
the real `applyRoutingRules` and asserts the emitted rules are scoped to the
DEFAULT instance's interface and not the VRF's, with a positive control that a
leak rule was installed at all. Re-run: **KILLED**.
