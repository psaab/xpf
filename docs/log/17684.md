# #17684 — Order next-table routes alongside kernel leak rules

- **Timestamp**: 2026-10-26
  - **Action**: Replaced the blanket main-table probe with lookup-first next-table rules and configured static main-table carve-out exceptions; retained shared prefix-derived slots and Rust FIB ordering.
  - **Why**: Linux `SuppressPrefixlen` does not turn broad blackhole/unreachable main-table results into misses, so the PR's probe-first rules could prevent a valid more-specific target lookup. The target lookup must precede broad main routes, while Junos still requires a more-specific configured main route to win.
  - **What**: Kept slot algebra `[static main exception, target lookup, unreachable shadow, rib-group]`; emitted destination- and iif-scoped exceptions only for configured non-next-table statics that pass `StaticRouteExcludedReason`, have at least one FRR-renderable ECMP member (using the renderer's shared gateway/interface operand predicates), and are strictly inside admitted config next-table prefixes. Each exception uses `suppress_prefixlen = route_prefix_length - 1`, and exceptions install after shadow/target lookup pairs. Rust promotes main-table LPM outcomes only when a configured `NextTableRoute` covers the destination; rib-group-only leaks remain lookup-first. Dynamic, connected, and learned main-route parity remains tracked by #17971 (follow-up filed by parent). PR #17970 references rather than closes #17684. Snapshot protocol v76 remains the explicit `RouteSnapshot.RulePriority` semantic gate.
