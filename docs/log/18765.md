# #18765: mouse_latency_probe_test persistent-mode cells are load-sensitive

- **Timestamp**: 2026-11-01
- **Action**: Found in the harness triage (group G10, class D). Two cells each
  asserted a minimum completion COUNT in a 0.12 s / 0.2 s window. At loadavg
  ~30 they failed while the property each guards still held.
- **Fix**: judge the property, not the count.
  - `test_min_interval_bounds_persistent_attempt_rate`: a 0.3 s window. It
    asserts `attempted <= duration/interval + 2` (an upper bound),
    `completed >= 2` (so a gap is observable), start-gap `max` and `p50`
    >= 15 ms (lower bounds), and `sleep_overshoot` samples are present. Load
    can only cut attempts and stretch gaps, so every bound holds under load.
  - `test_persistent_mode_reuses_one_connection_per_coroutine`: a 0.5 s
    window. It asserts `max(attempts_per_coroutine) >= 2` (some coroutine
    reused its connection) instead of `completed > 3`. `connection_count <= 3`
    and the remaining assertions are unchanged.
- **File(s)**: `test/incus/mouse_latency_probe_test.py`, `docs/log/18765.md`
- **Validation**:
  - `python3 -m unittest mouse_latency_probe_test`: OK, three runs in a row
    at loadavg ~20.
  - Each cell still fails on its own defect:
    - the min interval quartered in `_respect_min_interval`: the interval
      cell is RED;
    - persistent mode closing its connection after every attempt (no reuse):
      the reuse cell is RED, and so is the interval cell.
- **Risk**: test-only. The suite runs about 0.5 s longer.
