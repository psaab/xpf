# #18765: mouse_latency_probe_test persistent-mode cells are load-sensitive

- **Timestamp**: 2026-11-01
- **Action**: Found in the harness triage (group G10, class D). Two cells each
  asserted a minimum completion COUNT in a 0.12 s / 0.2 s window. At loadavg
  ~30 they failed while the property each guards still held.
- **Fix**: judge the property, not the count.
  - `test_min_interval_bounds_persistent_attempt_rate` runs for 0.3 s and
    asserts the interval-derived attempt upper bound, at least one observable
    gap, start-gap `max` and `p50` >= 15 ms, and `sleep_overshoot` samples.
  - `test_min_interval_bounds_per_attempt_rate` uses the same interval
    properties instead of requiring three completions in 0.12 s.
  - `test_persistent_mode_reuses_one_connection_per_coroutine` checks successful
    connection counts per coroutine and requires one coroutine to make at least
    two attempts on exactly one connection. A skewed-progress regression
    completes at least two attempts on separate connections from one active
    coroutine while delaying the others; the total remains <= 3 connections.
    This satisfies the former aggregate checks but is correctly rejected as
    reuse.
- **File(s)**: `test/incus/mouse_latency_probe_test.py`, `docs/log/18765.md`
- **Validation**:
  - `cd test/incus && python3 -m unittest -v mouse_latency_probe_test`: 37
    tests passed.
  - The skewed-progress regression is GREEN with per-coroutine accounting.
    With the former aggregate predicate substituted, it is RED because the
    regression expected reuse rejection but no assertion was raised.
- **Risk**: test-only; the added regression runs for 0.7 s.
