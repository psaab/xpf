# #14174 grouped delete loses syntax information — engineering history

Issue: psaab/xpf#14174 ([research D8-06] grouped delete loses syntax
information). Lane branch: `fix/14174-campaign`, base `origin/master`
805ac16cd053ca95de0a9b34a38cae2d942c436e.

## Defect (present at base)

`pkg/eventengine/evaluate.go` `classifyPlan` classified a `delete` by
parsing a synthetic `set` with `config.ParseSetCommand`, which returns
only `[]string` and discards per-token bracket grouping. `plannedOp`
stored only `delPath`, and `applyOnce` in `pkg/eventengine/engine.go`
passed `nil` grouping to `DeleteAsGroupedPlantClass`.

The store parser `DeleteFromInputAsPlantClass`
(`pkg/configstore/store_command.go:169-173`) explicitly requires grouping
from `ParseSetCommandGrouped` to navigate a bracketed container key
group — e.g. the wide node built by
`set security zones security-zone [ trust dmz ] host-inbound-traffic ...`
(Keys=[security-zone trust dmz]). Without the grouping, `DeletePathGrouped`
re-splits the wide node at schema arity, reports `ErrPathNotFound`, and
`applyOnce` treats that as the tolerated missing-delete (Junos
change-configuration semantics): the batch commits, counts as committed,
and the configured node survives. Ordinary flat paths have no grouping
requirement, and a truly absent path is intentionally tolerated — both
preserved.

## Fix

- `pkg/eventengine/evaluate.go`: `classifyPlan` delete branch now uses
  `config.ParseSetCommandGrouped("set " + input)` (same grouped pair as
  the interactive delete) and stores the grouping on the planned op.
  Admission still rejects unparsable deletes before any candidate
  mutation (same fail-closed batch rejection).
- `pkg/eventengine/engine.go`: `plannedOp` gains `delGrouped []bool`;
  `applyOnce` passes `op.delGrouped` instead of `nil` to
  `DeleteAsGroupedPlantClass`. No new special-casing of any test input;
  every bracketed delete target now navigates as the CLI delete does.

NOT changed: the set path (already re-parsed with full syntax by
`SetFromInputAsPlantClass`), the tolerated-missing-delete doctrine
(absent grouped/flat paths still tolerated), and `DeletePathGrouped`
itself (already correct given the grouping).
