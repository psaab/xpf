  (#12082 follow-up).
- **Branch**: `fix/12520-campaign-pub`

- **Base**: `ede1dfb3e` (master at the final rebase)
- **PR**: #12593

## Why

Strict `CompileConfig` accepted an explicit tunnel `routing-instance
destination` naming an undefined instance, a `forwarding` instance or the
reserved `mgmt`. The kernel tunnel manager still derives `vrf-<target>` from
the stanza (`vrf-mgmt` for `mgmt`), while the userspace snapshot keeps the
tunnel in the default routing instance and domain, so the planes disagree on
who owns the tunnel (#12082's cross-plane contract).

## What

- `validateTunnelRoutingInstanceTargetsStrict12520` rejects the three classes
  for every interface- and unit-level claim from
  `routingInstanceTunnelDeviceClaims`, on strict compile and `CommitCheck`.
  `runTailGates` calls it last, so #9909, #5162, #10654 and #4785 keep the
  first-error slot.
- Tolerant load/peer-sync (`lenientTunnelRITarget12520`) warns once per claim
  and clears the target (ruled: quarantine, as #11060 does), so both planes
  run the tunnel in the default routing domain.
- Clearing moves a GRE tunnel's #10654 decap identity (source, destination,
  key, transport instance) into the default instance. The #10654 gate ran
  before the clear, and the snapshot builder keeps the first-sorting
  duplicate, so a quarantined `gr-0/0/0` displaced a valid `gr-0/0/1` that
  shared its outer tuple. `skipQuarantinedGRECollisions12520` re-checks
  identities after the clear: non-quarantined endpoints claim first, then
  quarantined ones in emitter order. A quarantined tunnel whose identity is
  already owned is removed from the compiled config with a warning naming
  both: an interface-level tunnel the way #9909 removes one, a unit-level
  tunnel together with its unit (the tolerant #9899 unit skip), because a
  unit without a tunnel would inherit the interface-level tunnel. Duplicates
  among non-quarantined tunnels stay with #10654.
- An earlier, never-pushed fold marked such tunnels with a new
  `TunnelConfig.Quarantined` flag. It was discarded: `pkg/cli/apply.go`, the
  eBPF `compiler_iface.go`, userspace `interfaces.go` and host-inbound code
  read `unit.Tunnel` without consulting the flag. Its `greOuterKeyForTunnel`
  extraction and test cells were kept and revised.
- The #7484 spelling gate lost both tunnel-RI target leaves to the quarantine
  (an undefined synthetic value is cleared, so the value moved nothing). The
  gate now probes them with its own pair (`gate-a`/`gate-b`), defined at the
  root by `gateRootPrereq` in every compile of the leaf. The coverage floor
  tightens 787 -> 788 so either leaf going blind again reds.
- Fixtures define the VRFs they target. debian/changelog, the pkg/config
  README section and this log are updated; the changelog and README note that
  a device an earlier release enslaved to `vrf-mgmt` keeps that binding
  across a restart (restart adopts devices as-is, `pkg/routing/README.md`).

## Risk

Strict commits now reject persisted unsupported targets until the operator
picks a valid VRF. Tolerant loads keep such tunnels running in the default
domain, except a GRE tunnel whose cleared identity another tunnel owns, which
is skipped with a warning. A skipped unit-level tunnel takes its unit's
addresses with it. RI interface-list members that name a skipped tunnel are
left in place and point at a device that is not created. When an RI exists
but is quarantined by #11391, the tolerant warning still calls it undefined.
