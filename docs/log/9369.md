# #9369: the rss-expectation verdict ignored a truncated CoS active-flow snapshot

- **Timestamp**: 2026-09-11T02:05Z
- **Action**: Made a constrained rss-expectation INDETERMINATE when the source snapshot is truncated, and carried that verdict through the CLI and Prometheus.
- **File(s)**:
  - `pkg/dataplane/userspace/fairness.go`
  - `pkg/dataplane/userspace/format/status.go`
  - `pkg/api/metrics.go`, `metrics_descriptors_fairness.go`, `metrics_userspace_fairness.go`
  - tests in all three packages
  - `docs/fairness-regimes.md`, `docs/per-5-tuple/state.md`

## Mechanism (origin/master `e7af251ce`)

`CoSFairnessRSSSummary.SourceRowsTruncated` was written on every summary and read by nothing. The coordinator keeps only the first 4096 sorted `(ifindex, queue_id, worker_id)` triples and flags anything beyond that (`userspace-dp/src/afxdp/coordinator/status.rs`). So a resolved queue can reach `EvaluateRSSExpectation` with part of its distribution missing, or all of it. The verdict computed from that prefix was indistinguishable from one computed on complete data.

A prefix flips the verdict in both directions. Take the issue's witness: complete `[1,3,0,…]` against truncated `[1,0,…]`.
- `cstruct-max:0.1` FAILs on complete data and falsely PASSes on the prefix.
- `balanced` FAILs on complete data and falsely PASSes on the prefix.
- `max-worker-flow-share:0.8` PASSes on complete data and falsely FAILs on the prefix.

The exporter turns the result straight into `xpf_fairness_rss_skew_violation`, so a false PASS showed up as a clean fairness board. The truncation itself was visible, but only globally: the `xpf_fairness_cos_active_flow_counts_truncated` gauge and the `show` warning line.

## Change

- **`EvaluateFairnessRSSExpectations`.** When `summary.SourceRowsTruncated` is set and the kind is not `any`, the result is INDETERMINATE: `Pass=false`, `Indeterminate=true`, and a reason starting "indeterminate: CoS active-flow snapshot truncated". `any` constrains nothing, so it still evaluates. An unresolved interface still FAILs, because resolution does not depend on truncation. This matches the throughput path, which already excludes truncated active-worker counts (`fairness_throughput.go`).
  - The flag is snapshot-GLOBAL, so a queue whose rows were all retained is also held indeterminate. That is conservative and never wrong. The issue records per-queue completeness as the stronger, later form; it needs the coordinator to publish per-queue truncation.
- **CLI.** The `Pass` bool column becomes `Result`: `PASS`, `FAIL` or `INDETERMINATE`.
- **Prometheus.** New `xpf_fairness_rss_expectation_indeterminate{ifindex,queue_id,kind}` gauge, set to 0 or 1 on every resolved expectation. The violation sample is withheld while indeterminate, because a 0 would claim a clean board and a 1 would raise a false alarm.
- **Tests.**
  - `TestFormatFairnessRSS` sets `CoSActiveFlowCountsTruncated: true` to exercise its warning line, and it pinned `balanced false` / `max-worker-flow-share:0.5 true` for that snapshot. Those are exactly the verdicts this issue shows can be wrong, so the cell now expects `INDETERMINATE`. The pinning arrived verbatim in a pure code-motion commit (`10213606d`, #1990) and records no decision that verdicts stay valid under truncation. Its own warning already says "derived values are partial".
  - `TestEmitFairnessRSSExpectationGauges` gains the new descriptor. Its count goes from 7 to 10, and it asserts indeterminate=0 on its complete snapshot.
