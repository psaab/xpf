## Scope decision: negative ids only

The issue says to drop "negative and out-of-range" ids. Ids above 255 are kept on purpose. They saturate onto wire byte 255, which no runnable group uses: strict commit bounds real groups to 0..15. #8337 deliberately keeps and advertises such a group, and `TestPeerRedundancyGroupIsKeyedByLocalConfigID8337` builds exactly that state through the lenient compiler. A negative id is different in two ways: it aliases RG0, a group that does run, and it can never index the dataplane's `rg_active` array. Both nodes load the same synced config, so both drop the same groups.

## Fix

- **Tolerant compile:** `dropNegativeRedundancyGroups` removes groups with a negative id and emits one `... dropped on the tolerant path ... (#9723)` warning per group. The cluster manager never receives RG -1 from a loaded or synced config.
- **`localRGIDForWireByte`:** a local group whose id equals the byte wins; otherwise the smallest id that saturates onto the byte; otherwise `int(b)` as before. With only in-range ids this returns what it always did. With `{0, -1}` it now always resolves byte 0 to 0, and with `{300, 256}` byte 255 to 256.
