# #14573 — Strict commit accepts two units of the same reth with the same `vlan-id`

## Defect
Pass 3 of `validateInterfaceNameCollisionStrict`
(`pkg/config/compiler_validate_strict_ifname_collision.go`, #7795) skipped a
reth ENTIRELY (`ResolveReth(name) != name` → `continue`). That exempted not
only the legal #6722 aliasing (a reth unit landing on its member's device,
also claimed by an authored dotted name) but also two units OF THE SAME RETH
resolving to one device: `reth1 unit 100 vlan-id 100` and `reth1 unit 200
vlan-id 100` both resolve (via the member `ge-0/0/1`) to `ge-0-0-1.100`.
Strict commit accepted it; `pkg/daemon/daemon_reth.go` already called a
duplicate vlan-id "an invalid config the compiler does not reject for
uniqueness". Downstream the two distinct L3 units share one ifindex, so the
forwarding builder's last-wins / contested-zone handling silently drops or
mis-zones one of them (or the logical-only snapshot refusal of #11461).

## Evidence
RED on `origin/master` `a615690ed` (probe since removed): strict
`CompileConfig` on the reth config returned `err=nil` with both units
resolving `ge-0-0-1.100`; the non-reth control
(`ge-0/0/0 unit 100/200 vlan-id 100`) was rejected with "both resolve to the
same Linux device name … give one of them a different vlan-id".

## Fix
Pass 3 no longer skips a reth. A reth's units:

- are checked against EACH OTHER via the sibling `subOwner` registry and the
  IFNAMSIZ bound, and
- are never checked against `firstByLinux` / `derivedOwner`, because a reth
  unit's device is by design also claimed by the member / authored dotted
  alias (#6722 case C stays legal).

`subOwner` is now keyed by owning interface + device: a no-op for non-reth
interfaces (the device embeds the base) and exactly the intra-reth scope for
reths (units of different reths on different members must not collide).
The `dev == base` collapse skip compares against the RESOLVED member base
for a reth so `reth1 unit 0` still collapses onto the member device.
The strict/lenient split is inherited from the existing gate
(`opts.lenientIfNameCollision`): strict rejects, tolerant load/peer-sync
warns naming both units (#1960 no-brick).

NOT changed: cross-reth / reth-vs-authored / reth-vs-member aliasing, pass 1
and pass 2, `ResolveReth`/`ResolveKernelIfName`, daemon_reth.go's runtime
warning (still correct for grandfathered lenient loads).

## Risk
Configs already committed with a duplicate reth vlan-id now fail strict
commit-check until the duplicate is fixed (intended — the config was
silently mis-forwarding); they still load on the tolerant path with a
warning. No dataplane, wire, or resolution behaviour changes.
