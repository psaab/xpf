# #9549: fixed ports in `userspace-dp` unit tests

## Re-read at `origin/master` `e90b9f714`

The issue has no comments, so its body is the spec. At that commit the defect is still live:
`server::tests::wg1866_disarmed_same_plan_apply_does_not_hold_wg_ports` binds the fixed port
`51879`.

The fixed port is incidental; the held port is not. The cell holds the helper's WireGuard listen
port so that a disarmed helper which even attempts a bind fails and records a
`wg_bind_listen_port` exception, and it asserts there are none. So the cell needs a port it HOLDS,
not a particular number. Binding port 0 and reading back the port keeps that detection.

#9502 is still open and is a different mechanism: a 50 ms wall-clock budget in a Go test. It is
linked here, not absorbed.

`coordinator/reconcile/bringup.rs:1102` is production code. The coordinator's section comment said
"Each test uses a unique listen port so the suite can run in parallel". That holds inside one
process, not across two.

## Fix

- `userspace-dp/src/test_ports.rs` (new, `#[cfg(test)]`, registered in `main.rs`) has two helpers:
  - `hold_ephemeral_udp_port()` binds `[::]:0`, reads the port back and returns the holders. The
    v4 holder is kept opportunistic, as the #1866 portability note had it.
  - `reserve_ephemeral_udp_port()` holds an ephemeral port, releases it, and never hands the same
    port out twice in one process. Its retry loop is bounded, so it panics with a reason rather
    than hanging.
- The named server cell and the 51872 rig use `hold_ephemeral_udp_port`; the 51872 rig drops both
  holders. The other eleven coordinator cells use `reserve_ephemeral_udp_port`. The failure
  message now names the test host, not WireGuard.
- Remaining risk, stated: another process can take a released port in the milliseconds before
  the WG control thread binds it. That is far rarer than a fixed port, which collided with every
  second copy of the suite, but it is not zero.
- Docs: `docs/engineering-style.md` gains "Ports in tests (#9549)", beside "Time in tests". The
  coordinator section comment is corrected.

## The named cell could not see the rule it pins

The issue's acceptance says the cell "must still red when the disarmed-same-plan port-hold
behaviour it exists to pin is reverted". The first matrix on `59bf07d15` showed that it does not:

| mutant | what it reverts | verdict on the named cell |
| --- | --- | --- |
| Q1 | `refresh_runtime_snapshot_disarmed` spawns WG threads (`inner(snapshot, true)`) | not killed by the named cell; the only failure is the coordinator test `gre1881_disarmed_refresh_stops_threads` |
| Q2 | the server's disarmed same-plan branch calls the armed `refresh_runtime_snapshot` (the call site) | SURVIVED: 5635 executed, 0 failed |

The port change does not touch that path, so the cell was equally blind at base.

**Mechanism, instrumented.** Temporary probes in a scratch worktree (not committed) showed:

- The server cell's second apply does reach the same-plan refresh branch, with
  `same_plan=true` and `should_run_afxdp=false`.
- That refresh held `wg_endpoints=0 wg_engines=0`.
- A coordinator #1866 cell run in the same binary, used as the positive control, held
  `wg_endpoints=1 wg_engines=1`.

The difference is the transport. `run_request` sends the request over a real control-socket
pair and serializes it with serde. `wg_local_privkey_hex` is `#[serde(default, skip_serializing)]`
so that the key never reaches the state file, so it is dropped on the wire.
`hydrate_wg_identity` then fails to decode an empty key and discards the endpoint. There was
never an engine to spawn from, so "no WG thread spawned" passed whichever variant ran. The Go
control plane writes the key into the JSON it sends, so production is not affected.

Census of the class: this is the only test that puts a WireGuard secret into a request sent
through the socket harness. The coordinator and forwarding-build cells call refresh in memory,
and the one serialization in `wg/tests.rs` is the redaction test itself.

**Fix.**

- `run_request_delivering_wg_secrets` (server tests) serializes the request to JSON and
  re-inserts each endpoint's `wg_local_privkey_hex` and each peer's `wg_preshared_key_hex` from
  the in-memory request before sending. That is what the real control plane delivers.
- The named cell sends both applies through it.
- After the second apply, the cell asserts a liveness precondition:
  `wg_engine_count_for_test() == 1`, a new `#[cfg(test)]` accessor in
  `coordinator/tunnel_supervision.rs`. If the key is ever dropped again, the cell fails loudly
  instead of going vacuous.

**A second survivor in the same run: F2.** F2 makes `hold_ephemeral_udp_port` return `port + 1`,
a port the `[::]` holder does not hold. It exited 0 with the whole bin suite passing. The
opportunistic v4 holder binds after `port` is computed, so it held `0.0.0.0:(port+1)`. On this
dual-stack host (`bindv6only=0`) that made the cell's own `AddrInUse` control on `[::]` fail as
expected, even though the returned port was not the one the v6 holder holds. On a
`bindv6only=1` host that port would be unheld for IPv6. The cell now also asserts that the
returned port equals the `[::]` holder's `local_addr().port()`, which fails F2 on any host.

## Validation

- **`make test`, both legs, on `47377cf2f`** (`origin/master` `fe86a51c8` plus this commit): exit 0. Go: 77 packages `ok`, no `FAIL`. Rust: 5,788 passed, 0 failed, across all 11 test binaries, including all 17 port cells: the 15 converted #1866/#2921/#1881/#9521 cells and the 2 new test_ports cells. No disk-exhaustion lines.
- **Landed via merge commit; master delta since tested base shared no files with this change.** There was no rebase after the green run. Before pushing, the landing script intersects the `origin/master` delta since `fe86a51c8` with this change's files by name, and refuses on any overlap. When master has moved past `fe86a51c8`, it also merges `origin/master` into this commit in a throwaway worktree. The merged tree must pass `go build ./...`, `go vet ./...` (judged against master's own diagnostics) and `cargo check --tests --benches` in `userspace-dp`. Both checks repeat if master moves again before the merge, and the merge is pinned to the checked head commit. The script also refuses if a file the mutants edit differs from the matrix head `e946ac790` or was changed on master. A guard that scans the whole tree (a census, a line count, a golden file) is out of reach of both checks. A full `make test` on master after merges covers that class.
