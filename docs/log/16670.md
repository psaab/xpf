# 16670 — retain source-NAT pool range operands on their leaf

- **Timestamp**: 2026-10-25
- **Why**: Adding the single-port wildcard under source-NAT pool `port`
  made SetPath treat the first operand of `range` as a sibling instance.
  The resulting `port { range; 1024 { to 2048; } }` candidate failed strict
  schema validation on `to`, although compiler-only tests accepted it.
- **What**: Add the explicit `absorbBeforeWildcard` schema opt-in and enable
  it only on the source-pool `range` leaf. Keep the existing wildcard
  sibling rule for every non-opted-in leaf and keep declared sibling
  keywords as value-run boundaries. No compiler or dataplane behavior is
  changed. The existing compiler handling of older split trees remains
  intact for tolerant loading of configurations written before this fix.
- **Files**: `pkg/config/ast_edit.go`, `pkg/config/schema.go`,
  `pkg/config/compiler_nat_source.go` (legacy-shape comments only),
  `pkg/config/schema_security.go`,
  `pkg/config/compiler_nat_source_pool_port_range_16670_test.go`,
  `pkg/configstore/source_pool_port_range_16670_test.go`,
  `pkg/configstore/peer_effective_snat_5876_test.go`,
  `docs/config-schema.md`, `docs/log/16670.md`.
- **Coverage**: Assert the AST before normalization, including default
  wildcard behavior with the opt-in disabled. Compare Junos and legacy
  flat ranges with a hierarchical range. Drive Store.SetFromInput and
  Store.LoadSet through CommitCheck, Commit, and display-set replay;
  verify exact endpoints, single ports, boundaries, allocation modifiers,
  preservation, and strict malformed-spec rejection.
- **Fixture correction**: Once range parsing no longer blocks schema
  validation, both existing #5876 store tests expose their undeclared
  `trust` and `untrust` zones. Declare those zones in both fixtures rather
  than weakening strict source-NAT zone validation.
- **Baseline evidence**: On `d5d254dcadbf6a36ef017b3cbce25cd50562736a`,
  `TestCompileTreeStrict_StandaloneCleanSNAT_5876` failed with
  `unknown configuration keyword "to"`. The separate
  `TestSourceNATPoolHierarchicalRangeBlock_15675` also fails on that base:
  the #16535 block-value gate rejects `range { 5000 to 6000; }` as multiple
  values in one statement. This change does not alter that gate; the
  supported control is `port { range 1024 to 2048; }`.
- **Validation**: Targeted suites passed 145 test/subtest events (121
  config, 24 configstore), including the required
  `TestCompileTreeStrict_StandaloneCleanSNAT_5876` and both new strict store
  test matrices. `go vet ./pkg/config ./pkg/configstore` passed.
  The baseline-attributed nested-block failure above was explicitly
  excluded, not counted as a pass. Commands:

  ```sh
  export GOCACHE=/var/worktrees/.cache/go-build
  export GOTMPDIR=/var/worktrees/.cache/go-tmp
  export TMPDIR=/var/worktrees/.cache/go-tmp
  export GOFLAGS=-p=2
  go test ./pkg/config ./pkg/configstore \
    -run '16670|_3906|_5457|_6688|_15675|_5876|15935|_9685|_2419|_13212' \
    -skip '^TestSourceNATPoolHierarchicalRangeBlock_15675$' -count=1 -json
  go vet ./pkg/config ./pkg/configstore
  ```
- **Risk**: Scope is configuration AST construction, not packet processing.
  Only the source-pool range leaf opts in. Invalid port specifications
  still reach strict compiler validation rather than silently widening
  to the default range. No cluster or full-selftest run is required for
  this parser-only change.
