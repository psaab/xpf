# Issue #16890 — carved export tail must stay within the #5701 sequence bound

- **Issue:** A carved export tail appended after 6552 counted term sequences
  could render `route-map BIG deny 65540`, which FRR rejects and can poison the
  vtysh-batched `frr-reload`.
- **Re-verification:** At base `4cc55c5bee`, the current render belt already
  reserves the carved no-default tail in `carvedSingleExtraSeqs16869` and adds
  it with saturating arithmetic before comparing against
  `config.MaxRouteMapSequences`. At 6552 term sequences the effective count is
  6553, so the belt renders its bounded quarantine deny instead of the carved
  expansion. The missing regression cell was the no-`next policy` form of the
  single-policy carved tail.
- **What:** Add a `buildManagedSection` regression test for the exact originating
  BGP export shape without `next policy`. The one-below-ceiling control (6551
  terms plus the carved pair) must render through sequence 65530; 6552 terms
  must render only the quarantine deny, never sequence 65540. The existing
  render-side reserve is unchanged because it already provides the required
  behavior.
- **RED → GREEN:** Temporarily removing the no-`next policy` +1 reserve made the
  new regression fail: the 6552-term map rendered the full expansion instead
  of a single quarantine deny. Restoring the reserve made the test pass. The
  temporary mutation was reverted; no production source change is part of this
  regression.
- **Validation:** `go test ./pkg/frr/ -run
  TestBGPCarvedNoNextPolicyTailSequenceBoundary16890 -count=1 -v` passes. Full
  package tests, formatting, and vet results are recorded in the PR.
- **Residual:** No live FRR parser or `frr-reload` run; the regression verifies
  rendered sequence bounds and quarantine behavior.
