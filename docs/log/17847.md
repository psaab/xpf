# #17847 — Reject whole-family SNAT wildcard matches with opposite-family pools

- **Timestamp**: 2026-10-26
  - **Action**: `sourceNATRuleSingleFamily16600` now counts every
    explicitly authored literal source match as narrow, including
    whole-family wildcards (`0.0.0.0/0`, `::/0`): a /0 is unconstrained
    only within its own family, so a v4-wildcard rule against a
    v6-only pool is exactly the proven single-family mismatch #16600
    rejects (every matching flow would fail WrongAddressFamily at
    runtime). Before, the literal arm passed
    `!natPrefixIsFamilyWildcard(raw)` as narrowness, so /0 rules
    classified not-single-family and the pool-family gate skipped
    them (regression from PR #17411's #17408 scoping). The #17408
    protection is preserved: it covers rules whose match is not
    authored single-family at all — the v6-host/v6-slash112 and
    unscoped-pool fixtures use dual-family matches
    (`[ 10.0.0.0/24 2001:db8:9::/64 ]`) and still compile. Named
    address-book closures deliberately keep their pre-existing
    narrowness rule (a name resolving to a family wildcard stays the
    #17408 scaffold; only a proper-subset member makes a name narrow).
  - **File(s)**: `pkg/config/compiler_validate_strict_nat.go`,
    `pkg/config/compiler_nat_snat_pool_family_16600_test.go`,
    `docs/log/17847.md`.
  - **Validation**: New rows (v4 wildcard + v6-only pool, v6 wildcard
    + v4-only pool) FAIL pre-fix, PASS post-fix. Controls green:
    `TestSourceNATPoolValidGrammarCompiles`,
    `TestSourceNATPoolUnscopedAddressCompiles`, all 16600 family
    tests. Full `go test ./pkg/config/ -count=1`: 12 failures,
    name-identical to the recorded base set (7bf41933cf).
  - **Risk**: Strict-gate widening: an explicitly authored
    `source-address 0.0.0.0/0` (or `::/0`) SNAT rule whose pool lacks
    that family now refuses at commit instead of committing a rule
    that can never translate — the intended #16600 behavior. Lenient
    loads warn (WrongAddressFamily) rather than fail.
