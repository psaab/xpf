# Issue #15089: A/B ESP slots never refreshed after bake (A57-01)

## Why

The bake copies `shimx64.efi` / `grubx64.efi` / `mmx64.efi` from
`/boot/efi/EFI/ubuntu` into `/boot/efi/EFI/xpf-A` and `xpf-B` exactly
once (`scripts/image/bake.py` slot-staging fragment). Ubuntu's
`shim-signed` / `grub-efi-amd64-signed` updates install only to
`EFI/ubuntu`, while BootOrder keeps booting the xpf slots — so the
Secure-Boot chain stayed on the bake-time bootloader for the life of
the appliance, and a SBAT/dbx revocation would never reach the booted
loader even though dpkg reported the fixed version as installed.
`scripts/image/validate.py` only asserted slot file *presence*, so the
stale state shipped green.

Alternatives considered: holding `shim-signed`/`grub*-signed` like the
kernel (rejected — it would strand bootloader security updates with no
LANE-1-style verified channel to deliver them, the opposite failure);
an apt `Post-Invoke` hook (rejected — runs per apt invocation rather
than per dpkg transaction, misses direct `dpkg -i`, and can fire
before the package is configured).

## What

- `scripts/image/xpf-uefi-slots`: new `sync_ab_slots()` re-copies each
  loader present in `EFI/ubuntu` into both slot dirs, cmp-gated
  (in-sync slots are not rewritten) and atomic per file (temp file in
  the same slot dir + rename, verified by a post-rename cmp). It runs
  on every boot before NVRAM registration, and standalone via
  `--sync-only` (independent of the efivars gate). `xpf.selector` is
  never touched. Failures are logged and non-fatal per the script's
  "degraded, not bricked" contract; the boot-time run retries.
- `debian/xpf.triggers` (new): dpkg file triggers
  (`interest-noawait`) on the three `EFI/ubuntu` loader files, so any
  package unpacking a changed loader invokes `xpf.postinst triggered`.
- `debian/xpf.postinst`: new `triggered` arm runs
  `xpf-uefi-slots --sync-only` when the helper is installed, exits 0
  otherwise (foreign hosts without the bake substrate). `dh_installdeb`
  installs `debian/xpf.triggers` into `DEBIAN/triggers` automatically.
- `scripts/image/validate.py`: new `_AB_SLOT_HASH_PROBE`
  (sha256sums of ubuntu + both slots) and
  `_ab_slot_loader_hash_verdict`, applied in
  `assert_ab_kernel_channel` after the presence verdict. A stale or
  divergent loader now fails the Tier-1 gate by name; a loader absent
  from `EFI/ubuntu` entirely stays the presence verdict's diagnosis,
  and mm absent from both source and slot (the bake fallback shape)
  passes.
- `scripts/image/test_validate_gate_reactions_10770.py`: the
  `assert_ab_kernel_channel` guest mock now also serves the hash probe
  (otherwise every existing gate-reaction cell would fail on the new
  command).
- Docs: `docs/install-images.md` "A/B ESP slot loader refresh" under
  Upgrades.

NOT changed: the bake's one-time staging (still the initial seed),
NVRAM registration / BootOrder logic, `xpf.selector` seeding and
promotion, the kernel hold, and `EFI/ubuntu`'s own contents.

  `scripts/image/test_slot_refresh_15089.py` (19 tests) failed with

  `--sync-only` refresh, no `debian/xpf.triggers`, postinst rejected

- GREEN: `python3 -m unittest scripts.image.test_slot_refresh_15089`

- Adjacent suites green: `test_validate_gate_reactions_10770`,
  `test_validate_ab_substrate_6498`, `test_validate_ab_slots_6494`,
  `test_uefi_slots_6499`, `test_validate_scenarios` (104 tests total

  `xpf-uefi-slots` and `xpf.postinst`.
- Real-dpkg proof (scratch chroot under the worktree, since removed):
  built a scratch `xpf` .deb carrying the real triggers file and a
  `triggered` postinst arm plus a fake shim provider; `dpkg -i` of the
  provider printed "Processing triggers for xpf" and invoked the
  `triggered` arm. The refresh mechanism itself is covered
  hermetically by the unit tests (the chroot's stripped-down toolset
  could not run `cp` without coreutils' shared libraries, an artifact
  of the scratch root, not of the mechanism).

## Risk

- A bootloader update now rewrites ESP files outside a reboot. The
  copy is atomic per file and cmp-verified, and a failed refresh never
  blocks the bootloader package's configure (noawait + best-effort),
  with the next boot's sync as backstop.
- `validate.py`'s new hash probe requires `sha256sum` in the guest
  (coreutils, already relied on by the image); an empty probe fails
  closed rather than passing vacuously.
- Lab verify still outstanding: on a real baked image, `apt install
  --reinstall shim-signed grub-efi-amd64-signed` followed by `cmp`
  across `EFI/{ubuntu,xpf-A,xpf-B}` and a deliberate slot corruption
  failing `validate.py`. The hermetic tests exercise the same sync and
  verdict code paths, but the full bake/validate cycle was not run in
  this lane.
