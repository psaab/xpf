# #15283 — NAT64 honours the source pool's `port range` (V52-S1)

- **Base**: `99b37e805c` (origin/master at branch start)
- **Branch**: `fix/15283-campaign`

## Why

A source pool's `port range` was silently ignored when the pool was used
by a NAT64 rule-set. `NAT64RuleSnapshot` carried no port-range field,
`deterministicNAT64V6Fields` computed mode-2 blocks against the fixed
1024-65535 window, `pkg/nat` mirrored that fixed window, and the Rust
per-prefix `PortAllocator` was built with the fixed
`NAT64_PORT_LOW`/`NAT64_PORT_HIGH` constants — so translated ports spanned
1024-65535 regardless of the operator's range, with no commit error or
warning.

## What

Honour the pool range end to end (the issue's first acceptance arm):

- `pkg/dataplane/userspace/protocol_nat.go`: `NAT64RuleSnapshot` gains
  `port_low`/`port_high`.
- `pkg/dataplane/userspace/nat64.go`: `nat64PoolPortRange` resolves the
  pool range via the shared `config.SourceNATPoolPortRange` SSOT
  (1024/65535 default); `buildNAT64Snapshots` stamps it on usable pools
  only (an invalid range keeps the pool unusable, unstamped);
  `deterministicNAT64V6Fields` computes `blocks_per_ip` against it.
- `pkg/nat/deterministic.go`: mode-2 `poolParams` uses the pool's range
  (via the existing `poolPortRangeV4` delegation), keeping the CLI/gRPC
  deterministic reverse lookup in parity with the wire builder.
- `userspace-dp/src/protocol/nat.rs`: Rust mirror fields.
- `userspace-dp/src/nat64.rs`: `nat64_effective_port_range` (snapshot range
  when valid, else the fixed default — a hand-crafted invalid pair falls
  back rather than building a zero-range allocator); the fresh
  `PortAllocator` is built over the effective range; the #6982 aggregate
  charge follows it (`nat64_prefix_charge_for_range`); allocator reuse
  across a reload is range-aware (`reuse_allocator_for_range`) so a changed
  range gets a fresh allocator (whose #6765 reseed drops out-of-range
  reservations) while a same-range reload still reuses the live allocator.
- Protocol v54 -> v55 (Go `ProtocolVersion` + Rust
  `CONFIG_SNAPSHOT_PROTOCOL_VERSION`, snapshot-shape golden updated): an
  old helper ignoring the fields would keep the fixed range, which is the
  defect, so exact-equality versioning fences the pairing.
- `protocol_wire_v1.json` gains `port_low`/`port_high` on the NAT64
  specimen; `docs/deterministic-nat-cgnat.md` updated.

Deliberate scope: a pool used ONLY by NAT64 still spares its range from
the SNAT aggregate budget (separate NAT64 budget, unchanged); `port
no-translation` pools report PortLow/High 0 from the SSOT and therefore
keep the NAT64 default, as before (ranges are irrelevant in that mode on
the SNAT path too).

## Validation

- Go RED/GREEN: `nat64_port_range_15283_test.go` — snapshot stamps
  2000/3000 (was 0/0 pre-fix), default control stays 1024/65535, mode-2
  blocks-per-IP = 10 for range 2000-3000/block 100 (645 pre-fix).
- Rust RED/GREEN: `nat64_15283_*` — allocator built over 2000..=3000 and
  first flow at 2000 (1024 pre-fix), deterministic block [2500,2599] off
  the pool low, default-range control, range-change reload resets while
  same-range reload reuses.
- Parity: `TestDeterministicParamsMatchWireBuilders`,
  `TestSnapshotProtocolVersionLockstepWithRust`, and the #8892 shape pin
  pass at v55; `go test ./pkg/nat/ -run Deterministic` passes.

## Risk

Pools without an explicit `port range` are byte-identical to before
(default window everywhere). A narrowed pool now exhausts at its real
capacity instead of silently spilling outside the range — the operator-
visible behaviour the config always promised. Rolling upgrade across the
v55 fence refuses mismatched snapshots (keeps the previous-good image)
rather than silently dropping the range.
