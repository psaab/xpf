# #15201 — next-table suffix discarded: wrong-family / nonzero-index targets leak into unicast table (A10-03)

- **Timestamp**: 2026-10-19
- **Action**: Validated the `next-table` table suffix at commit: a suffixed
  target must be exactly the unicast suffix of the route's own family
  (`.inet.0` for IPv4, `.inet6.0` for IPv6, index 0 only). Wrong-family,
  nonzero-index (e.g. Junos `inet.2`, the RPF table), and malformed suffixes
  are now hard-rejected on the strict path, downgraded to a warning on the
  tolerant path, and excluded from the userspace FIB / show verdicts there.
- **File(s)**: `pkg/config/compiler_routing.go`,
  `pkg/config/compiler_validate_strict_routing.go`,
  `pkg/config/static_route_exclusion_reason.go`,
  `pkg/config/compiler_routing_nexttable_family_15201_test.go` (new),
  `docs/rib-group-route-leaking.md`, `docs/log/15201.md`

## Mechanism (verified at base f04747579b)

`parseNextTableInstance` (`compiler_routing.go`) stripped at the last
`.inet` and discarded the suffix entirely, and
`validateNextTableTargetReferencesStrict` checked only that the stripped
instance name was defined. With `blue` defined, `blue.inet6.0` on an IPv4
route, `blue.inet.2`, and an IPv6 route to `blue.inet.0` all committed;
the kernel applier (`pkg/routing/rules.go`) resolves only the bare
instance name to a table id and installs the ip-rule leak unconditionally,
so each leaked into blue's unicast table — a plausible effect for an
operator typo rather than a rejection.

## Fix

- `compiler_routing.go`: new `parseNextTableSuffix` returns
  (instance, suffix, hasSuffix), anchored on the LAST `.inet` (#5632
  semantics preserved verbatim); `parseNextTableInstance` delegates to it.
- `compiler_validate_strict_routing.go`:
  `validateNextTableTargetReferencesStrict` walks the global inet/inet6
  lists and, before the #5693 definedness check, rejects any suffixed
  raw token (`NextTableRaw`) that is not exactly the suffix matching
  the destination's family (`FRRAddrFamily`; a v6 destination under
  bare `static` stays in the inet list, #9820).
  The error quotes
  the raw token and the offending suffix. Bare instance names (no
  suffix) carry no family/index claim and are unchanged — internal
  consumers construct them directly. Per-instance next-table remains
  wholly rejected (#5830). Strict reject / lenient warning split is the
  existing `lenientNextTableRefs` wiring (#1960).
- `static_route_exclusion_reason.go`: `StaticRouteExcludedReason` returns
  an "invalid table suffix" reason for a global route whose raw suffix
  mismatches its destination family (`FRRAddrFamily`), so a tolerantly
  loaded bad-suffix route stays unpublished in the FIB and annotated on
  show surfaces instead of leaking. Bare and matching-suffix controls
  are unaffected.
- Not changed: the kernel applier and Rust FIB. They only ever see
  compiler output; strict configs can no longer carry a bad suffix, and
  tolerant configs are kept out of the FIB by the exclusion predicate
  (the applier's residual tolerant-path leak is the pre-existing #1960
  inert-on-load doctrine for this gate family).

## Risk

Only suffixed `next-table` targets on global static routes change
behaviour: previously-accepted wrong-family/nonzero-index/malformed
suffixes now reject at commit (warning on tolerant load). Bare names,
matching `.inet.0`/`.inet6.0`, dotted instance names, per-instance
rejection, and the definedness gate are unchanged.
