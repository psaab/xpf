# Issue #14709 — D11 attestation PermMaint bypass

## Claim (D15-04)
`d11LedgerPrincipalAllowed` returns true for
`Source==SourcePeerUID && (UID==0 || Superuser || ClassHasPermission(cfg, class, PermMaint))`.
Both consumers document stricter intent:
- `GetD11AttestationLedger` error + handler comment + `authz_command_table.go:145`:
  "requires uid 0 or the configured super-user class"
- `SystemAction userspace-attest:arm:` error: "requires root or configured superuser"

A custom login class holding only Junos `maintenance` (→ `PermMaint`, non-superuser,
UID≠0, local peer-UID) therefore passes both handler gates: reads the attestation
ledger and, worse, re-arms D11 attestation authority via `d11ArmFn(run_id, permit_epoch, marker)`.

## Evidence on current origin/master (1c0cdbf805)
- `pkg/grpcapi/server_d11_attestation_10484.go:14-19` — PermMaint disjunct present.
- `pkg/grpcapi/server_d11_attestation_10484.go:28-34` — doc/error say super-user only.
- `pkg/grpcapi/server_diag_system_action.go:304-307` — same helper guards arm; error says root/superuser.
- `pkg/grpcapi/authz_methods.go:109` — interceptor prices ledger at PermMaint (read arm already PermMaint at coarse layer; inconsistency is two-layer).
- `pkg/grpcapi/authz_methods.go:168,245-250` — SystemAction floor PermMaint; `userspace-attest:arm:...` unlisted → PermMaint default. So coarse layer also admits PermMaint-only class to reach handler.
- `pkg/authz/authz.go:209-211,102-114` — `Superuser` is set only for UID 0. A configured `super-user` class principal (UID≠0) has `Superuser=false`, `Class="super-user"`.
- `pkg/config/login_perms.go:49-60` — `ClassHasPermission(cfg, class, PermAll)` is true iff class holds `PermAll` (super-user built-in `{PermAll}` or custom class mapping `all`/`super-user` token → PermAll). This is the "configured super-user class" check matching the documented contract.
- Existing tests (`server_d11_attestation_10484_test.go`): cover root, `Class:"super-user"` (with nil cfg → currently passes via PermMaint because built-in super-user holds PermAll→PermMaint), credential-denied, read-only. No PermMaint-only non-superuser case.

## Fix decision
Enforce the written contract at BOTH layers (handler is the load-bearing gate;
interceptor must not be looser than handler's documented contract, otherwise
credential-source principals could reach handler — handler still denies them
via Source check, but pricing inconsistency invites future bypass and audit
flags it):

1. `d11LedgerPrincipalAllowed`: drop `PermMaint` disjunct; require
   `PermAll` via `ClassHasPermission(cfg, principal.Class, config.PermAll)`.
   Keeps: UID 0, `Superuser` flag, configured super-user class (built-in
   `super-user` or any custom class holding PermAll). Denies: custom
   `maintenance`-only class, operator, read-only, credential sources.
2. Interceptor pricing: `GetD11AttestationLedger` PermMaint → PermAll.
   This makes `authz.Authorize(cfg, p, PermAll)` admit only UID0/superuser-flag
   or PermAll-holding class. Need check: does any test pin PermMaint for this
   method? Search before change.
3. `SystemAction` verb pricing for `userspace-attest:arm:` prefix → PermAll.
   `systemActionPermission` currently exact-match map + PermMaint default.
   Add prefix check for `userspace-attest:arm:` → PermAll before default.
   Must keep `TestEverySystemActionVerbHasAPermission_5278` green (it enumerates
   handler case labels; prefix verbs handled by default-branch comment).

Note: `Principal.Superuser` is only true for UID 0 in production
(`PrincipalForUID`). Existing tests set `Superuser:true` with UID 0.
The `ClassHasPermission(..., PermAll)` arm covers the "configured super-user
class" test case (`Class:"super-user"`, nil cfg → built-in lookup succeeds).
With a custom maintenance class in cfg, `d11AuthorizationConfig()` needs the
active config — handler tests construct `&Server{}` without store → nil cfg →
built-ins only. Regression test must wire a real store with the custom class
via `authzStore5278`-style helper, or set `store` field. Check how Server.store
is set in tests: `NewServer(..., Config{Store: ...})`.

## Regression (named: TestD11AttestationRejectsNonSuperuserMaintClass)
- Custom class e.g. `maint-only` with `permissions maintenance;` (→ [PermMaint]),
  user assigned to it, principal `{Source: SourcePeerUID, UID: 1001, Class: "maint-only"}`.
- Assert `GetD11AttestationLedger` → PermissionDenied.
- Assert `SystemAction userspace-attest:arm:...` → PermissionDenied and `d11ArmFn` not called.
- Controls stay green: root (UID 0), configured super-user class, credential-denied,
  read-only-denied existing tests.
- Also pin interceptor pricing: `methodPermission(GetD11AttestationLedger)` == PermAll
  and `systemActionPermission("userspace-attest:arm:...")` == PermAll if pricing changed.
- RED on current master, GREEN after fix.
