# #9993 and #9994 — policymatch retention precedence and cross-stanza shadowing

## Scope and verified runtime premise

Both issues were reproduced against `origin/master` at `6dacb080f` before the
source fixes. #9993 follows the existing #4373 advisory pattern: the tuple
verdict remains conservative and independent of policy evaluation, while the
config-wide snapshot-retention state must ride every result. #9994 was checked
against the runtime before changing the advisory: the compiler appends each
same-pair stanza as a distinct `ZonePairPolicies` entry
(`pkg/config/compiler_security_policy.go:137-147`), but the userspace snapshot
builder pushes each rule index into one `(from_id,to_id)` bucket
(`userspace-dp/src/policy.rs:2497-2505`) and the evaluator walks that bucket in
index order, returning the first match (`userspace-dp/src/policy.rs:3052-3074`).
Same-pair evaluation is therefore sequential and ordered; the shadow analyzer
must inspect the concatenated stream.

## STEP-0 RED proof on origin/master

The new fail-on-revert cells were run against the unchanged `origin/master`
implementation before either fix:

```text
go test ./pkg/policymatch -run 'TestUnsupportedTupleStillReportsRetention9993|TestAnalyzePolicyShadowingAcrossSamePairStanzas9994' -count=1

--- FAIL: TestAnalyzePolicyShadowingAcrossSamePairStanzas9994
    expected cross-stanza block-web-second-stanza SHADOWED, got:
--- FAIL: TestUnsupportedTupleStillReportsRetention9993
    ContentRejected = false, want true: unsupported-tuple query must still surface retention
FAIL
```

The #9993 RED result had `UnsupportedTupleFamily=true`, conservative
`Action=PolicyDeny`, and no `ContentRejected` flag/reasons even though the same
config returned content rejection for a same-family query. The #9994 RED result
had an earlier `permit any` in one `trust -> untrust` stanza and a later
`deny web` in a second `trust -> untrust` stanza, but produced no shadow
finding. An independent `trust -> dmz` stanza is retained as the no-false-
positive control.

## Fixes and fail-on-revert cells

- #9993 (`pkg/policymatch/policymatch.go`): the unsupported-tuple gate now
  uses a #4373-style deferred stamp to attach `ContentRejected` and
  `ContentRejectionReasons` whenever the config-wide retention helper rejects
  the config. `UnsupportedTupleFamily` remains true and `Action` remains
  `PolicyDeny`. `DisplayAction` gives `ContentRejected` precedence when both
  flags are set, so the REST/gRPC MatchPolicies action cannot hide retention;
  healthy mixed tuples still render the dedicated unsupported-tuple string.
  `pkg/policymatch/unsupported_tuple_retention_9993_test.go` pins both the
  retention case and the healthy no-over-report control.
- #9994 (`pkg/policymatch/policy_shadowing.go`): stable same-pair groups are
  concatenated in authored order before `analyzePolicyListShadowing` runs.
  Single-stanza groups remain allocation-free and no input policy slice is
  mutated. `pkg/policymatch/cross_stanza_shadow_9994_test.go` pins the
  cross-stanza shadow and the independent-pair control.

After the fixes, the focused run selected 11 passing regression/shadow test
cases, including both new cells. Removing either fix makes its corresponding
cell fail as shown by the RED run above.
