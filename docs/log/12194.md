# Issue #12194 — Guard VLAN-alias binding indices

## Why

On base `8dc3c5624`, `applyAliasBindingRowsLocked` multiplied an alias child's ifindex by the binding stride before checking the ifindex bound. Since the composed index is `uint32`, child ifindex `268435473` with queue 0 wrapped to index 272 (ifindex 17, queue 0), passed the post-multiply dense-cap check, and overwrote that primary row with the parent's slot.

## What

Added the same `bindingIfindexInRange` pre-multiply bound used by the primary apply loop to the alias apply loop. An invalid child fails closed through `failClosedUserspaceCtrlLocked` before index composition; the existing queue and post-multiply cap checks remain unchanged.

Added fake-map regressions for the `268435473` overwrite/fail-closed case, the exact `2^28` slot-zero map case, and ordinary alias acceptance. The slot-zero cell is explicitly map-only: `userspace-xdp/src/binding_index.rs` uses `checked_mul` for packet-side lookup and returns `None` for this high ifindex, so the cell makes no packet-steering claim.

## Risk

The separate watchdog alias-repair loop in `pkg/dataplane/userspace/maps_sync.go:1349` has the same unchecked `uint32` child-ifindex stride-wrap arithmetic followed by the post-multiply cap. Unlike the apply path, it only repairs when lookup finds an all-zero row (`maps_sync.go:1361-1373`); a wrapped key can therefore affect a different zero/stale row, but it is a distinct repair path and was not changed under the explicitly triaged `helper_status_apply.go` scope. This residual was reported to the parent for separate ruling.
