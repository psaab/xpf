# #12067 — strict-reject unconsumed route-filter tokens

- **Timestamp**: 2026-10-08 (stacked on #12070 / `b939ca090`)
- **Action**: reject route-filter tail tokens the match type does not consume during schema validation, before compilation can discard them.

## Red before

The new schema regressions failed on base `b939ca090`: `SchemaValidate` returned nil for every unconsumed tail in flat and hierarchical forms, including `orlonger reject`, `orlonger foo`, `exact 17`, `upto /24 extra`, malformed `upto foo`, and child-block tails. A strict-compile probe confirmed the non-keyword `orlonger foo` case compiled with `Action="accept"`, `UnknownFrom=[]`, and a route-filter containing only `Prefix=10.0.0.0/8` and `MatchType=orlonger`; the `foo` token was lost. The issue's `reject` tail also passed schema validation, although this stack has an independent later #11779 unknown-from gate for that keyword. The required #12067 boundary is the schema walk, before compilation.

## Change

- Wired a route-filter node validator into the existing `from`/`route-filter` schema nodes. It permits only a single trailer for `upto`, `prefix-length-range`, and `through`; rejects unconsumed packed tokens, extra tokens after a supported trailer, and unconsumed hierarchical children. Malformed `upto` lengths are rejected instead of degrading to the open-ended default.
- Added a matching packed-`from` scan for compact hierarchical syntax. It recognizes the five supported `from` leaf keywords as boundaries, respects quoted/bracketed token provenance, and rejects route-filter tails before compiler dispatch.
- Added config schema regressions for flat, hierarchical-child, and compact `from` AST forms, supported tail controls, and an integration check that `configstore.CheckText` rejects an unconsumed route-filter token before compiling.
- The compiler and FRR renderer were not changed; accepted `upto` and `prefix-length-range` operands retain their existing interpretation and output.
