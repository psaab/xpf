# #14606 - DHCPv6-PD deprecated preferred lifetime 0 re-advertised as fully preferred

- **Timestamp**: 2026-10-16
- **Action**: A delegated IAPREFIX `{preferred 0, valid 7200}` (deprecated,
  RFC 8415 §21.22) lost its preferred lifetime at two stacked sentinel
  collisions: `buildRAConfigs` copied it only when `> 0`, and `pkg/ra`
  `buildRA` substituted the 7-day default for every `PreferredLife <= 0`
  (then clamped to valid), so LAN hosts were told the dying prefix was
  fully preferred for its whole valid life — inverting the ISP's
  graceful-renumbering signal (RFC 9096 L-15).
  Added `config.RAPrefix.PreferredLifeSet`, mirroring
  `DefaultLifetimeSet` (#4119): the compiler sets it when the
  `preferred-lifetime` leaf is present (so an operator's explicit
  `preferred-lifetime 0` is also honored), and `buildRAConfigs` sets it
  always on the PD path with the verbatim IAPREFIX value. `buildRA`
  honors an explicitly-set preferred life (0 stays 0; negatives still
  default), while an unset preferred life keeps the 7-day default — so
  an operator prefix with no lifetime leaf is unchanged, and hand-built
  delegated values predating the flag keep legacy behavior.
  `configEqual` and the cluster `sortRAPrefixes` total order now include
  the flag (it is wire-affecting: 0 vs default), and the golden compile
  fixture gained the new field (`PreferredLifeSet: false` on all
  operator prefixes, proving the compiler does not stamp it absent a leaf).
  Valid-lifetime handling is untouched — decay/expiry remains Y12-01's
  separate fix; here the emitted PIO is `preferred=0, valid=7200, A=true`.
  NOT changed: `DelegatedPrefix`/`DelegatedPrefixesForRA` (they already
  carried preferred 0 verbatim; only valid 0 withdraws).

  `PreferredLifeSet=false`. GREEN post-fix, re-verified after rebasing

  14606-targeted tests pass (deprecated grant, 3600 control, no-leaf
  7-day-default control, legacy-unset delegated control, decayed-to-zero

- **Risk**: Operator-authored `preferred-lifetime 0` now also advertises
  deprecated (previously silently defaulted) — this is the RFC-correct
  reading of an explicit leaf and matches the issue acceptance wording;
  configs without the leaf are byte-identical on the wire.
