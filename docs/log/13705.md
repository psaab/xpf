# #13705 — preserve reject verdict and logging on associated fragments

- **Timestamp**: 2026-10-15
- **Action**: Carry the skipped DENY/REJECT action and per-policy log flags into the fail-closed fragment-associated result for both transit and junos-host policy walks.
- **Base**: `origin/master` `52e29404e` (initial Rust fix based on `69094d1bf`)
- **Files**: `userspace-dp/src/policy.rs`, `userspace-dp/src/policy_tests.rs`, this log

## Why

When a flowless non-first fragment skipped an overlapping port-bearing
`reject` rule, the fragment-association path rebuilt the decision as
`PolicyAction::Deny` and cleared both log-selection flags. The policy result
therefore no longer described the configured rule, even though direct rule
matches preserve `Reject` and its flags. Both transit and junos-host walks use
this constructor, so the mismatch affected each guarded path.

## What

`SkippedFragDeny` now retains the skipped rule's action, `log_session_init`,
and `log_session_close`; `frag_associated_deny_result` returns those values
instead of hardcoding `Deny` and `false`. The Go `fragDenyResult` also keeps the
skipped policy's `Action`; the simulator no longer rewrites `Reject` to `Deny`.
Neither change alters forwarding or reply behavior: the fragment is still
dropped silently and attributed to the skipped rule, without incrementing the
skipped rule's L4 hit counter. Regressions cover transit and junos-host reject
metadata and preserve the plain-deny/no-log case.

## Risk

No packet disposition or reply-generation behavior changes. Flowless fragments
remain silent drops; event emission continues to use the actual reply outcome,
so a `Reject` result with no generated reply is rendered as a truthful DENY.
