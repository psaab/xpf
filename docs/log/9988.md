# Issue #9988 — static-NAT non-numeric destination-port

## Finding and STEP-0

Issue #9988 describes a static-NAT `match destination-port` parse failure that
was silently discarded. At `origin/master` commit `0b0fa8f84`,
`pkg/config/compiler_nat_static.go` called `strconv.Atoi` and left the integer
field at zero on error. Zero is the wire-level whole-address wildcard, so the
invalid token became indistinguishable from an absent port.

The pre-fix reproduction used `CompileConfigLenient` and the production
`buildStaticNATSnapshots` path:

```text
nonnumeric http: stored match=0 mapped=0 excluded="" warnings="" snapshots=1
snapshot: MatchDestinationPort=0 MappedPort=0
numeric 443 + mapped 80: snapshot MatchDestinationPort=443 MappedPort=80
absent port: snapshot MatchDestinationPort=0 MappedPort=0
```

Thus `http` installed as the same whole-address row as a genuinely absent
port. The existing #5101 predicate intentionally exempts zero, so it could not
identify this parse failure after the raw token had been discarded.

## Fix

This mirrors the mechanism established by #3446 for source-/destination-NAT:

- `pkg/config/types_security.go:1345-1350` adds the compiler-only
  `StaticNATRule.InvalidDestinationPorts` channel.
- `pkg/config/compiler_nat_static.go:915-925` preserves the raw token whenever
  `strconv.Atoi` fails instead of retaining the zero wildcard sentinel.
- `pkg/config/compiler_validate_strict_nat.go:1512-1530` rejects the first bad
  token by rule-set, rule, and token on strict compile, while the tolerant path
  emits a warning and continues booting. Per-rule exclusion state is reset
  before this gate so deferred multi-address diagnostics retain the drop.
- `pkg/config/compiler_validate_strict_nat.go:1876-1882` suppresses the
  contradictory mapped-port-without-match warning when the zero match value
  came from an invalid token.
- `pkg/config/nat_exclusion_reason.go:72-79` treats preserved invalid tokens as
  a static-NAT exclusion. The snapshot builder already shares this predicate,
  so the lenient path emits no row rather than widening to port zero.
- `userspace-dp/src/nat/static_nat.rs:492-499` now states the actual contract:
  the `(0, _)` arm drops only the port rewrite and retains the intentional
  whole-address match; it is not a fail-closed rule drop. Go must exclude
  malformed source tokens before this wire-level ambiguity.

A genuinely absent destination-port remains the valid 0/0 whole-address shape,
and numeric `443` + mapped `80` remains unchanged. The existing typed schema
continues to handle explicit numeric range validation.

## RED → GREEN evidence

Before the fix, the new fail-on-revert tests were run against the clean master
checkout state:

```text
go test ./pkg/config -run '9988' -count=1 -v
FAIL: TestStaticNATNonNumericMatchPortRejectedByName9988/http
FAIL: TestStaticNATNonNumericMatchPortRejectedByName9988/443-444
FAIL: TestStaticNATNonNumericMatchPortLenientWarns9988/http
FAIL: TestStaticNATNonNumericMatchPortLenientWarns9988/443-444

go test ./pkg/dataplane/userspace -run '9988' -count=1 -v
FAIL: TestBuildStaticNATSnapshotNonNumericMatchPortFailsClosed9988/http
FAIL: TestBuildStaticNATSnapshotNonNumericMatchPortFailsClosed9988/443-444
(the reverted behavior emitted one port-0 wildcard snapshot for each token)
```

After the fix, the same targeted tests passed, including an invalid `http`
match with a valid mapped-port 443. That mapped-port case produced only the
whole-rule exclusion warning, not the contradictory missing-match warning:

```text
go test ./pkg/config -run '9988' -count=1 -v
PASS — 3 issue-specific test functions (3 invalid-token warning subtests,
      strict rejection, and numeric 443/80 positive control)

go test ./pkg/dataplane/userspace -run '9988' -count=1 -v
PASS — 3 issue-specific test functions (3 invalid-token snapshot subtests,
      numeric 443/80 positive control, and absent-port 0/0 positive control)
```

The fail-closed snapshot test observed the operator-visible reason
`destination-port contains non-numeric token(s) ["http"]` and zero snapshots,
including when mapped-port 443 was present.
