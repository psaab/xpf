# #14158 — `awaitPeerFenceLocked` clobbers a heartbeat that arrived during the fence wait

## Why

Under `peer-fencing disable-rg-confirmed` (#7147), `handlePeerTimeout`
checks `peerHeartbeatFreshLocked()` before the fence but not after.
`awaitPeerFenceLocked` (`pkg/cluster/fence_confirm_7147.go`) releases
`m.mu` for the bounded `SendFenceAwait`; during that window
`handlePeerHeartbeat` (a different goroutine) can set `peerAlive=true`
and rebuild peer groups for a live, primary peer. On re-lock, the
unconditional `m.peerAlive = false` re-assertion clobbered that
heartbeat, and `handlePeerTimeout` proceeded to `electSingleNode()` —
promoting the local node while the peer (which never received/acked a
fence when `SendFenceAwait` errored, e.g. fabric sync down while the
control link lives) remains primary: transient dual-active.

The re-assertion exists for the opposite hazard: after a CONFIRMED
fence the peer is dark, and a heartbeat that landed in the window would
re-arm the #7161 readiness gate and strand both nodes secondary. Both
hazards live in the same window; the fence outcome discriminates them.

## What

- `pkg/cluster/fence_confirm_7147.go`: `awaitPeerFenceLocked` now
  returns `bool` — whether the peer-loss takeover may proceed. On
  re-lock, if `m.peerAlive` is set (it was false on entry and only
  `handlePeerHeartbeat` sets it, so this means exactly "a heartbeat
  landed during the wait") AND the fence did not confirm (`err != nil`
  or negative ack), it records the unconfirmed fence as degraded and
  aborts: the heartbeat's peer state and peer-aware election outcome
  stand. Otherwise it keeps the existing behaviour byte-for-byte,
  including the `peerAlive=false` re-assertion on the confirmed path
  (total-outage guard) and fail-open on every unconfirmed path where
  no heartbeat landed. Header docs rewritten to state both arms; the
  prior "does NOT abort on that" doctrine is removed.
- `pkg/cluster/heartbeat_manager.go`: `handlePeerTimeout` returns
  early when `awaitPeerFenceLocked()` reports abort — no
  `electSingleNode`, no disable-rg tail (that tail is unreachable
  under the confirmed policy anyway). If the peer then truly dies,
  the next heartbeat timeout re-runs the whole path.
- `pkg/cluster/fence_confirm_7147_test.go`: comment on the confirmed-
  window hazard test now names the #14158 unconfirmed arm and points
  at the new regression file. No test logic changed.
- Regression: `pkg/cluster/fence_heartbeat_race_14158_test.go` —
  `peerFenceConfirmFn` delivers a valid peer-PRIMARY heartbeat through
  the real `handlePeerHeartbeat` during the await and returns an
  error; asserts the local node does not promote, `peerAlive` survives,
  and peer groups survive. Control cell: same failed fence with no
  intervening heartbeat still fail-opens to primary. No test input is
  special-cased in production code; detection is the general
  `peerAlive`-on-relock invariant.

NOT changed: the pre-fence #2080 freshness recheck, the confirmed-path
re-assertion, `peerHeartbeatFreshLocked` (not used for post-fence
detection — a test-injected heartbeat does not stamp the receiver's
`lastSeen`, and gating on it would both miss that case and risk a
false abort if it raced the next real heartbeat), the `disable-rg`
and no-fencing policies, and election/readiness logic.

## Risk

Narrow: the only behaviour change is under
`peer-fencing disable-rg-confirmed` when a heartbeat lands inside the
≤1s fence wait and the fence fails — previously a dual-active
promotion, now a deferred takeover (next heartbeat timeout retries).
Confirmed fences and silent-peer fail-open are unchanged, so the
fail-closed direction is preserved: the change withholds promotion
only against a peer that just proved itself alive, never against a
silent one. An operator-visible `EventFence` record and the existing
degraded (unconfirmed-fence) status mark the aborted takeover.
