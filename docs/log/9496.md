# #9496: the two IS-IS per-interface routing-auth render sites bypassed the #9050 token belt

- **Timestamp**: 2026-09-11T03:40Z
- **Action**: Routed the IS-IS per-interface `isis password md5|clear` lines through `authTokenOrOmit`, and added a census so no auth-bearing render line in `pkg/frr` can bypass the belt again.
- **File(s)**:
  - `pkg/frr/protocols_render.go`
  - `pkg/frr/auth_token_9050.go` (doc count)
  - `pkg/frr/isis_interface_auth_token_9496_test.go` (new)

## Mechanism (origin/master `daf977dfe`)

#9050 moved the routing-auth render sites to `authTokenOrOmit`, which omits the whole line when the secret is not a single vtysh token. It converted eight sites: OSPF md5/simple, BGP, RIP, and the IS-IS area/domain md5/clear pairs. The two IS-IS per-interface sites (`protocols_render.go:793,795`) still called `sanitizeFRRValue(iface.AuthKey.Reveal())`. That function passes a space through and turns a TAB into one, so it produces a splittable line.

A new commit cannot reach this, because `validateFRRAuthValuesStrict` covers `protocols isis interface <name> authentication-key`. But the gate is downgraded to a warning on the tolerant path (`lenientFRRAuthValues`). So the reachable population is a pre-#2889 persisted config, an older HA peer's synced config, or an old rollback slot, arriving on boot, sync or rollback. FRR then either truncates the secret, which silently weakens it, or refuses the line, which fails the whole `frr-reload`.

## Change

- **Both per-interface sites** now use `authTokenOrOmit("isis-interface-md5"|"isis-interface-clear", …)` and emit only when `ok`. The warning names the protocol and length, never the value.
- **`auth_token_9050.go`'s doc** says "ten sites" rather than "eight".

No module docs describe per-site belt coverage, so no docs change is needed beyond this log. The belt's contract lives in `auth_token_9050.go`.

  - **Reference arm:** a single-token secret is still emitted as `isis password md5|clear goodsecret`.
