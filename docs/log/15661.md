# #15661 — reject rib-group `import-policy` in named-instance, packed, and per-instance shapes

- **Issue**: #15661 — `validateRibGroupImportPolicyStrict` (`#11314`) only walks `ribGroups.Children` and misses named-instance, packed, and per-instance `rib-groups <name> import-policy`, allowing unfiltered route leaks to commit.
- **Branch**: `fix/15661-campaign`
- **Worktree**: `/var/worktrees/wt-15661`

## Why

The #11314 gate walked only the raw children of a global
`routing-options rib-groups` container and probed each child for an
`import-policy` child or a packed `Keys[1] == "import-policy"` tail. Two
authored shapes walked past it on a strict commit:

- the named-instance hierarchical spelling
  `routing-options { rib-groups leak { import-rib inet.0; import-policy BLOCK; } }`
  (no braces around the `rib-groups` container), where the group node
  itself is `rib-groups` with `Keys=["rib-groups","leak"]` and is never a
  child of a `rib-groups` container node; and
- every per-instance definition
  `routing-instances blue routing-options rib-groups leak import-policy BLOCK`
  (flat, braced, named-instance, and packed spellings), because the gate
  never descended into `routing-instances` at all.

Both compile into `RibGroup` definitions (`compileRoutingOptions` reads
global and per-instance `rib-groups` through the same code; per-instance
groups are carried into `RoutingInstanceConfig.RibGroups`, #11782) whose
`import-policy` the route-leak applier cannot evaluate. Accepting them
silently leaks routes the policy excludes — broader than the operator
authored. Measured on master `d316277cb4` with an AST probe over ten
shapes: the flat/braced/packed-leaf global forms rejected, the
named-instance global form and all five per-instance forms committed
clean (`strict err: <nil>`, no warning naming the policy).

## What

`validateRibGroupImportPolicyStrict`
(`pkg/config/compiler_validate_strict_routing.go`) now:

- walks the global `routing-options` root and, for each
  `routing-instances` root, every instance resolved through
  `namedInstances` over the root itself (the dual-shape reader
  `compileRoutingOptions` uses), then that instance's `routing-options`
  children — so flat-set, braced, and brace-elided instance spellings are
  all reached;
- resolves each `rib-groups` container through `namedInstances`, covering
  both the braced container (`rib-groups { leak { ... } }`) and the
  named-instance form (`rib-groups leak { ... }`);
- detects `import-policy` on an instance via `instanceValueTail` (packed
  tail on the instance keys), via `expandFlatRun` over the instance
  children under the rib-group schema (shared by pointer with the
  per-instance grammar, #15065), and via the packed flat-run child shape
  (`import-rib`'s value node carrying `import-policy` in its keys — the
  shape the undefined-import-rib reference gate also rejects; the packed
  global row keeps whichever diagnostic the gate order produces and the
  test accepts the targeted import-policy message from this gate).

The strict diagnostic now names the scope:
`routing-options rib-groups "leak" import-policy is not implemented: ...`
globally and
`routing-instances "blue" routing-options rib-groups "leak" import-policy is not implemented: ...`
per instance. The tolerant path is unchanged in kind: the same error is
downgraded to the existing `rib-group import-policy (downgraded to
warning on tolerant path)` warning (#1960), so persisted configs still
boot and peer-sync.

NOT changed: `compileRibGroup` still does not record an import-policy
field (there is nothing to apply it with), the undefined-import-rib
reference gate and its gate order are untouched, and per-instance
rib-groups remain retained-but-not-consumed by the route-sharing runtime
(the existing #11314 accepted-but-not-applied warning still fires on the
tolerant path).

## Validation

New regression `TestRibGroupImportPolicyRejectedAcrossAllASTShapes`
(`pkg/config/ribgroup_import_policy_15661_test.go`): ten shapes (flat /
braced / named-instance / packed-leaf / packed global; flat / braced /
named-instance / packed / packed-single per-instance) each assert strict
rejection carrying `import-policy is not implemented`, the group name,
and the scope, plus a tolerant-compile warning naming the ignored
policy; a control row asserts rib-groups without `import-policy` still
commit in both scopes. The two single-command packed rows keep the
#11314-pinned undefined-import-rib diagnostic where that earlier gate
fires first (global packed); the per-instance packed row now gets the
targeted import-policy diagnostic from this gate, because no earlier
gate sees a per-instance packed run.

with `strict compile accepted an unsupported rib-group import-policy` —
hierarchical-global-named-instance and all five per-instance shapes

## Risk

- Strict commits that previously (incorrectly) accepted a named-instance
  or per-instance `rib-groups ... import-policy` now reject. That is the
  intended fail-closed direction; the tolerant load/peer-sync path still
  accepts with a warning, so no persisted config bricks.
- The packed global spelling (`... import-rib inet.0 import-policy P` as
  one `set` command) was already strict-rejected by the
  undefined-import-rib reference gate, which runs earlier; this gate now
  also sees it, but gate order means the operator still gets the
  reference diagnostic first on strict commits — unchanged behavior.
