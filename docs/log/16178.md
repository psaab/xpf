# Issue #16178 — Syslog TCP/TLS source-address resolution is unbounded

- **Timestamp**: 2026-10-21
  - **Action**: Bounded the source-address resolution in `dialTCP` and
    `dialTLS` (`pkg/logging/syslog.go`). Both called the package-level
    `net.ResolveTCPAddr("tcp", JoinHostPort(sourceAddr, "0"))` — no
    context, no deadline — before dialing, so a hostname source address
    performed an unbounded DNS lookup. Their 5 s `net.Dialer` /
    `tls.Dialer` timeouts bound only the remote connect that follows,
    not this lookup. Strict config enforces a source IP literal
    (`pkg/config/schema_system.go`), so the exposure is chiefly a
    tolerant/peer-loaded malformed or hostname source value — the same
    class the UDP sibling fix (#14613) already treated as a bug.
    Deferred construction (`NewSyslogClientDeferred`, #9326) keeps the
    TCP/TLS dial off the commit path, so the stall lands on first-Send /
    reconnect rather than commit. Both dials now resolve the source
    under one `syslogDialTimeout` (5 s) context via the new
    `resolveTCPAddrBounded` and dial with `DialContext` under the same
    deadline; `dialTCP` also switched from `Dial` to `DialContext` and
    both dialers now read the shared `syslogDialTimeout` var instead of
    a `5 * time.Second` literal so the branches cannot drift apart.
    `resolveTCPAddrBounded` mirrors `resolveUDPAddrBounded` (#14613):
    IP literals (including `%zone` scoped forms) parse directly with
    the stdlib family filter preserved (`tcp4` rejects IPv6 literals
    and vice versa, erroring `no suitable address found` like
    `net.ResolveTCPAddr`), the empty host yields a port-only address,
    and hostnames go through the existing `lookupSyslogIPAddr` seam
    under the caller's context, preferring the first IPv4 result for
    `tcp` and filtering by family for `tcp4`/`tcp6`. The
    `resolve source …` error taxonomy is preserved verbatim. No caller
    changes were needed.
    Regression tests in `syslog_tcp_srcaddr_bound_16178_test.go`: a
    resolver seam that blocks until its context is cancelled proves
    both `dialTCP` and `dialTLS` return a
    `context.DeadlineExceeded`-wrapping error under the bound with
    taxonomy intact; literal/IPv6/zone/empty-host and family-selection
    cells pin `resolveTCPAddrBounded` against stdlib semantics with no
    external network; a TCP hostname-source control proves the resolved
    source still binds and connects to a real listener, and a TLS
    literal-source control proves the handshake completes against a
    real TLS listener.
  - **File(s)**: pkg/logging/syslog.go,
    pkg/logging/syslog_tcp_srcaddr_bound_16178_test.go,
    pkg/logging/README.md, docs/log/16178.md

## Risk

- Behaviour delta: a TCP/TLS syslog client whose hostname source
  cannot resolve within 5 s now fails that (re)dial fast (message
  dropped, cooldown-gated retry) instead of stalling for the
  resolver's full timeout × attempts × servers. On fast-failing DNS
  (NXDOMAIN/refused) nothing changes; IP-literal sources — the only
  shape strict config admits — take the parser fast path exactly as
  before. Perf: no hot-path change (Send/write paths untouched); the
  dial path replaces an unbounded lookup with a context-bounded one
  and adds no allocation beyond the context/timer the UDP sibling
  already creates per dial.
- NOT changed (per the issue's narrowed scope): the syslog
  send/reconnect accounting-tail, the `writeFrame` datagram/stream
  split, `NewSyslogClientDeferred`'s UDP refusal, the remote-address
  dial semantics (already 5 s dialer-bounded), and every caller.
- No live-cluster syslog smoke was run; the decisive check is the
  in-package bounded-resolver regression above, matching the issue's
  acceptance (black-holed resolver returns bounded, IPv4/IPv6 and
  zone forms covered, no external network).
