# Issue #15704: probeMeasurementIdentity omits destination-port

- **Timestamp**: 2026-10-19
- **Action**: added `strconv.Itoa(test.EffectiveDestinationPort())` to
  `probeMeasurementIdentity` in `pkg/rpm/rpm.go`, so editing a tcp-ping
  test's `destination-port` produces a distinct measurement identity.
  `carryProbeVerdict` therefore no longer copies the old port's
  `LastStatus`, `SuccFail` streak, or RTT/loss counters (`TotalSent`/
  `TotalRecv`, RTT/jitter fields) onto the retargeted test, and the
  downstream `services ip-monitoring` consumer sees a clean `"unknown"`
  series instead of the old port's PASS/FAIL verdict. Using
  `EffectiveDestinationPort()` (not raw `DestPort`) keeps an implicit
  default and an explicit `80` the same measurement.
- **Scope**: only the destination-port identity limb from the issue body.
  The residual compact `probe <p> test <t>` / chained `ip-monitoring
  policy` limbs in the cross-reference comment were not validated to the
  filing bar and are not implemented here.
- **Regression**: `TestProbeMeasurementIdentityDestinationPort_15704`
  pins that port 80 -> 443 changes the identity while implicit-default
  vs explicit 80 does not; `TestApplyDestinationPortChangeReseeds_15704`
  pins that `Apply` reseeds a FAIL/streak-3 verdict and its counters to
  `("unknown", 0)` / 0/0 after a port change.

## RED -> GREEN proof
