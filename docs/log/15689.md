# #15689 — day-2 VRRP timer/hold updates reset MASTER advert and BACKUP master-down timers, drain config tokens, preserve armed holds

- **Issue**: #15689 — Day-2 in-place VRRP timer and hold-time updates (`updateConfigHeld`) fail to reset `StateMaster` `advertTimer` or `StateBackup` `masterDownTimer`, leak unread `configUpdatedCh` tokens across state transitions, and restart active `preemptHoldTimer` countdowns on unrelated edits (V36-03).
- **Files**: `pkg/vrrp/instance.go`, `pkg/vrrp/instance_preempt.go`, `pkg/vrrp/instance_config_update_15689_test.go`, `pkg/vrrp/README.md`, `debian/changelog`, `docs/log/15689.md`.

## Why

Measured at `origin/master` (`9e04c0d989`, synthesis base `f214fac`): `run()`'s `StateMaster` select had no `configUpdatedCh` arm, so an `advertise-interval` shrink on a live MASTER (e.g. 60s → 1s) left `advertTimer` on its old arm for up to the full old interval while BACKUP peers timed out in ~3× the new interval — a dual-MASTER window. The undrained 1-buffered token then sat in `configUpdatedCh` across a MASTER→BACKUP transition and was consumed by `stepBackup` as if fresh. In `stepBackup`, the `configUpdatedCh` case did nothing when no hold was armed (a cold-start BACKUP with no learned master stayed stuck at 3× the old interval, up to ~765s at 255s) and unconditionally disarmed an armed hold on any edit (an unrelated `GARPCount` or priority-raise restarted the full hold countdown). All three blind review lanes (codex-c / smr-c / spark-c) rated V36-03 MATERIAL.

## What

- `updateConfigHeld` now records a before/after snapshot (`configChange15689`: old/new raw `AdvertiseInterval`, old/new effective priority via the new lock-held `effectivePriorityLocked`, old/new `PreemptHoldTime`) into `pendingConfigChange` under `vi.mu` BEFORE the non-blocking `configUpdatedCh` send. Coalesced updates overwrite it, matching the channel's existing coalescing; interval/priority decisions re-read current cfg where required.
- Extracted the `StateMaster` select from `run()` into `stepMaster(masterDownTimer, advertTimer)` (mirrors the existing `stepBackup` test seam; `run()` delegates). New `case <-vi.configUpdatedCh:` consumes the token (no leak into a later BACKUP tenure) and, when the interval or effective priority changed (or no snapshot is pending — fail toward advertising), immediately `sendAdvert(getPriority())` and re-arms `advertTimer` at `vi.advertInterval()`. Unrelated edits leave the running advert timer untouched.
- `stepBackup` `configUpdatedCh` case now consumes the snapshot: with a hold armed it disarms/re-arms ONLY when the hold-time changed or `shouldPreemptObservedMaster()` is now false (preempt disabled / demoted) — preserving the #2900 re-validation — and otherwise preserves the elapsed countdown untouched. With no hold armed it re-arms `masterDownTimer` via `backupConfigUpdateNeedsMasterDownReset` when the no-learned-master fallback horizon shrank (Scenario B) or preemption newly became warranted; with a learned master interval the peer cadence still owns the timer. `preemptHoldArmedAt` is recorded/cleared alongside `preemptHoldArmed` for auditability of the preserved countdown.
- Tests (`instance_config_update_15689_test.go`, driving `stepMaster`/`stepMaster`+`stepBackup` seams deterministically): report acceptance `TestVRRPMaster_Day2AdvertiseIntervalDecrease_ResetsAdvertTimerImmediately` (60000→100ms, advert `MaxAdverInt==10` and advertTimer fire within 250ms), `TestVRRPMaster_ConfigUpdateDrainsToken_NoStaleLeak`, `TestVRRPBackup_StaleMasterConfigUpdateDoesNotDisarmPreemptHold`, `TestVRRPBackup_Day2AdvertiseIntervalDecrease_ResetsMasterDownTimer`, `TestVRRPBackup_UnrelatedConfigUpdate_PreservesArmedHold` (GARPCount / priority-raised), `TestVRRPBackup_ConfigUpdate_HoldTimeChanged_DisarmsHold` (#2900 guard), `TestVRRPBackup_ConfigUpdate_PreemptEnabled_ResetsMasterDownTimer`.
- README: replaced the stale "no explicit timer poke" claim with the #15689 both-states consumption contract.

## Validation

- RED on pre-fix code: the new tests do not compile against the pre-fix tree (`stepMaster` did not exist; StateMaster never consumed `configUpdatedCh`), and the BACKUP legs fail against the old unconditional-disarm / no-op arms by construction (verified by reading the pre-fix handlers at `instance.go:646-666` / run loop `806-836` on base).
- GREEN: `go test ./pkg/vrrp/ -run 'TestVRRPMaster_|TestVRRPBackup_' -count=1` passes (7 tests); neighbours `TestHold*`/`TestPreempt*` pass; `-race` on the new + hold + run-loop subset passes; `go vet ./pkg/vrrp/` clean; `gofmt` clean.
- Full `go test ./pkg/vrrp/ -count=1`: only failure is `TestRethOwnershipCollectorsUseTheSharedPredicate/RethVIPsForRG`, which fails identically on pristine `origin/master` (verified in a separate base worktree) — pre-existing, untouched by this change.

## Risk

Timer behaviour changes only on the day-2 config-update path: a MASTER now emits one extra immediate advert when its interval/priority changes (peers learn the new cadence sooner — the intended Junos behaviour), and a BACKUP may re-arm its master-down timer to the fresh (shorter or newly-warranted) horizon. No wire format, election, or VIP-actuation changes; the #2900 hold-expiry re-validation and #4584 watchdog are unchanged. A preserved hold whose premise silently rotted without a config event is still caught at natural expiry by `shouldPreemptObservedMaster`.
