# #15141 — ipsec: #14589 partial-load recovery accepts a NAME-set match as "candidate loaded" (B02-01)

- **Timestamp**: 2026-10-19
- **Action**: In `recoverPartialLoad14589` (`pkg/ipsec/manager.go`), removed
  the full NAME-set shortcut that returned the candidate hashes when
  `len(loadedSet) == len(rendered)`. `parseListConnsRaw`
  (`pkg/ipsec/list_conns.go`) now fingerprints each loaded connection's
  full reported content (`LoadedConn.Content`: auth subsections,
  proposals, selectors, endpoints — everything inside the connection's
  `list-conn` event). After the candidate subset file is re-filed and
  re-loaded, the confirm step compares before/after `Content` on a
  full-set match: a content change proves charon had been running the
  prior generation's content for a same-name connection (a refused
  changed-existing connection), so recovery diverts to the true
  rollback (prior file restored and re-loaded, prior hashes promoted).
- **File(s)**: `pkg/ipsec/manager.go`, `pkg/ipsec/list_conns.go`,
  `pkg/ipsec/partial_refused_existing_15141_test.go` (new),
  `pkg/ipsec/README.md`, `docs/log/15141.md`

## Mechanism (verified at base 55daac2d46 / 8d78875163)

`manager.go:508-512` pre-fix: `if isSubset14589(loadedSet, rendered) {
if len(loadedSet) == len(rendered) { return rendered, hashes, nil } }`.
`loadedSet` is a NAME set from `ListLoadedConns`; `hashes` are the
candidate's. Report evidence: on `swanctl --load-all` with a changed
existing connection whose new cert fails, charon prints `loaded 1 of 2
connections, 1 failed to load` yet keeps the refused section loaded
under its OLD content (`local-1 {class=pre-shared key ...}`). The
name set therefore equals the rendered set, the shortcut promoted the
refused candidate's hash, `promoteConnNames` saw `oldHash ==
newHashes[name]`, and the SA established under the superseded
PSK/auth was never terminated — the #10878 guarantee lost. On a later
gen3 that makes the connection loadable, the hash still matched the
(gen2) candidate hash, so gen3 entered no teardown either.

## Fix

- The name-only shortcut is gone. The subset path now always re-files
  the reported set and re-loads it. For a genuine subset that is the
  #14589 behaviour, unchanged. For a full set it re-files the candidate
  itself (byte-identical render, marker included).
- `LoadedConn.Content` (new) is a SHA-256 over every token inside the
  connection's `list-conn` event, in wire order. `LoadedConns.Equal`
  is deliberately unchanged (names/children/addresses only), so
  generation validation (#9641) sees no behaviour change.
- Confirm step: on a full-set match, `loadedContentStale15141(loaded,
  confirm)` compares the pre-recovery listing with the post-reload
  listing. Any content change → true rollback via the existing
  `rollbackReload14589` + `priorSet14589`, so `prevConnHashes["a"]`
  keeps the gen1 hash and a later loadable gen3 sees the hash change
  and tears the stale SA down. No content change (summary lied /
  raced to full) → candidate hashes promoted and the stale SA torn
  down on gen2 itself, exactly as the shortcut did. Empty `Content`
  on either side (a listing that never went through the parser)
  cannot prove staleness and does not divert.
- NOT changed: `promoteConnNames`, teardown/re-initiation, the subset
  and prior-set/hybrid recovery arms, `clearConfig`, `LoadedConns.Equal`.
  Production `--list-conns --raw` does not echo the PSK secret itself;
  the comparison keys on the reported auth/proposal/selector surface,
  which is what a refused cert/auth change alters. A refused
  PSK-only rotation with byte-identical reported content remains
  indistinguishable from raced-to-full by any `--list-conns` signal;
  that residual is inherent to the available charon reporting.

## Risk

Recovery on a partial now always performs the subset re-file +
verification reload (previously skipped only on a full name-set
match) — one extra `--load-all`/`--list-conns` pair on that already
rare path. The content comparison only ever diverts a full-set
recovery to the pre-existing true rollback; it never promotes a hash
the old code would not have, and never tears down an SA on gen2 that
the old code kept (the raced-to-full control pins that direction).
