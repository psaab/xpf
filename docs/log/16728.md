# #16728 — SNMP trap-group name is the trap community; redact it everywhere communities are redacted

- **Timestamp**: 2026-10-25
  - **Action**: Since #15052, `snmp trap-group <name>` sends with community
    `<name>` on the wire (`pkg/snmp` `trapCommunityForGroup` returns
    `tg.Name`), but the redaction registry was never updated: the AST
    redactor had no trap-group case, `SNMPConfig.MarshalJSON` passed the
    TrapGroups map through (leaking the name as both key and `Name`
    field), and the CLI/gRPC/REST `show snmp` renders printed the raw map
    key — exposing the query community whenever an operator reuses that
    string as the group name. Now: `secretIndices` masks the identity
    token after `snmp trap-group` (structurally gated on the exact
    `snmp trap-group` adjacency, allowing a `groups <name>` prefix and an
    embedded-command `set` verb, via `isSNMPTrapGroupIdentity`);
    `secretLeafKeywordsByRoot` gains `"trap-group": {"snmp": true}` so
    schema-walk/control-char diagnostics resolve it too; new
    `SNMPTrapGroup.MarshalJSON`/`MarshalYAML` convert `Name` to `Secret`
    and `SNMPConfig` renders TrapGroups as a name-sorted slice via
    `redactedTrapGroupSlice` (dropping the secret map key, mirroring
    Communities); the three operational renders (pkg/cli per login
    class, pkg/api and pkg/grpcapi unconditionally) mask the name with
    the shared `SNMPCommunityDisplayName` helper while targets stay
    visible. The coercion census enrols `SNMPTrapGroup.Name` so the
    AST/typed agreement stays checked. In-memory maps and the
    pkg/snmp lookup-by-name are untouched. JSON shape change (operator
    impact): `SNMPConfig.TrapGroups` now marshals as an array of
    `{Name:"<redacted>",Targets,Version,Categories}` objects instead of
    an object keyed by group name — the same shape Communities already
    used; no in-tree code unmarshals compiled-config JSON.
