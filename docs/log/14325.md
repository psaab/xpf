## Why

The #14129 sticky-fragment fix in `extract_screen_info`
(`userspace-dp/src/screen/extract.rs`) left an inconsistent state for a
chained IPv6 `[Frag#1(offset=0, M=1), Frag#2(offset=65528, M=1)]` packet:
the second non-ATOMIC sighting only downgraded `is_first_fragment` to
false, while `ip_frag_off`/`frag_data_off` kept Frag#1's values (offset
0). `check_tcp_flag_screens` (`stateless.rs`) skips on
`!is_first_fragment` and `check_ping_of_death`/`check_teardrop` require
`(ip_frag_off & 0xFFF8) > 0` (or an oversize computation keyed on that
offset), so the packet evaded BOTH screen families. The second research
leg (non-first fragments evading `icmp-fragment`/`icmp-flood`/
`udp-flood`) was refuted by both lanes -- #9114 already recovers the real
protocol on the non-first break -- and is out of scope.

## What

Fail closed on the duplicated header instead of splitting the fields:

- `userspace-dp/src/screen/extract.rs`: a second non-ATOMIC Fragment
  sighting (tracked by the existing `info.is_fragment`, set by the first
  non-ATOMIC sighting) returns
  `Err(ScreenParseError::MultipleIpv6FragmentHeaders)`. This covers
  reachable duplicates (`[first][non-first]`, `[first][first]`); a lone
  ATOMIC followed by a real header is still governed by the real header
  (#10661), ATOMIC second sightings stay ignored (#14129), and
  `[non-first][*]` is unreachable as a chain (the walk breaks at the
  first non-first header). RFC 8200 allows each extension header at most
  once and receivers key reassembly on the first header, so there is no
  sizing semantics to preserve between two non-ATOMIC headers.
- `userspace-dp/src/screen/packet.rs`: new
  `ScreenParseError::MultipleIpv6FragmentHeaders` variant mapping to the
  existing `ip-malformed` screen reason, so every
  `extract_screen_info` caller (`poll_stages.rs` flow/flowless paths,
  `poll_descriptor/mod.rs`) already drops the packet fail-closed with no
  caller change.
- Regression: `screen/tests_14129_chained_frag.rs` -- the issue's
  decisive `[Frag#1(0,M=1), Frag#2(65528,M=1), 4 bytes]` shape with
  single-header teardrop/ping-of-death controls, a hand-reconstructed
  pre-fix `ScreenPacketInfo` proving both sizing screens pass it, a
  duplicated-first case, a reachable-orderings matrix, and an
  `[ATOMIC][real-non-first]` guard that still parses and drops via
  teardrop. `afxdp/frame/tests_10661_atomic_chain.rs`'s
  `[real-first][real-non-first]` cell now asserts the screen leg rejects
  (tracker/forwarding/shim legs unchanged).

NOT changed: `check_tcp_flag_screens`/`check_ping_of_death`/
`check_teardrop` predicates (the split that made the bypass possible is
now unreachable from the extractor), the forwarding/tracker/NAT64
every-sighting fragment verdicts (screen scope only), and the #9114
protocol recovery (already correct).

## Validation

- RED (pristine `1ea1f8713` extractor + variant-only `packet.rs` so the
  new tests compile, test files overlaid in a scratch base worktree):
  `chained_first_then_max_nonfirst_14325_wording`,
  `chained_duplicate_first_rejected_14325`, and
  `chained_second_header_matrix_rejected_14325` failed -- the pre-fix
  parse returned `ScreenPacketInfo{is_fragment:true,
  is_first_fragment:false, ip_frag_off:1, frag_data_off:8}` (Frag#1's
  offset 0) instead of an error; the updated
  `real_first_then_real_nonfirst_tracker_first_record_10661` also
  failed. The `[ATOMIC][real-non-first]` control passed.
- GREEN: `cargo test -p xpf-userspace-dp --bins -- 14325 10661 14129`
  18 passed. Full `screen::` suite 342 passed (one matrix cell corrected
  during development: `[non-first][non-first]` is unreachable because
  the walk breaks at the first non-first header).
- `cargo test -p xpf-userspace-dp --bins`: 8305 passed, 42 failed --
  byte-identical failure set to pristine master `1ea1f8713` (same 42
  names, extracted from both runs); all 42 are pre-existing
  environment/baseline failures unrelated to this change.

## Risk

Behavior delta: a screened zone now drops any packet with a duplicated
non-ATOMIC IPv6 Fragment header as `ip-malformed` instead of passing it
to the sizing/flag screens. This only fires on RFC 8200-nonconformant
chains (legitimate senders never emit two Fragment headers); unscreened
zones are unaffected (extraction only runs for screened zones). Residual:
the forwarding walk still resolves such chains for overlap tracking /
L4-refusal, so an unscreened deployment's forwarding behavior is
unchanged -- that unification is out of scope and was not part of the
validated defect.
