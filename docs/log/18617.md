# #18617 — neighbour warm-up probes re-enter the RG owner's WAN and are policy-denied

- **Timestamp**: 2026-10-31 07:25 PDT
- **Action**: Localised test-failover's "RG1 Group 4 policy denied packets"
  (node0 5-7 every run, node1 0). Reproduced the manual RG1 failback slice on
  loss (0.0.26316, lock cell `r-g4-probe.sh`, no deploy): node0 policy denies
  3 -> 29, node1 +0. All 27 transit denies on node0 in the window were
  `[2001:559:8585:50::8]:<eph> -> [<LAN host global>]:1 UDP wan->wan default
  deny`, one a second. That is `warmNeighborCache`, run on every synced
  session install (at most once a second): node0 owns the WAN, not the LAN, so
  its probe to the LAN host left through the WAN default route, came back to
  the cluster's own WAN address, and was denied as transit. The soak also
  showed probes to the pool / proxy-ARP address 172.16.80.7 denied on the RG1
  owner.
- **Action**: Fix. `neighbor_warm_plan_18617.go` builds a per-pass plan from
  the active config: an owned set (unit addresses including RETH VIPs, VRRP
  VIPs, SNAT pools, proxy-ARP, kernel-held addresses) and the configured unit
  prefixes this node holds (non-RETH unit or RG primary, AND the kernel holds
  an address in the prefix). `warmNeighborCache` probes only held on-link
  endpoints, from a socket bound to the unit's interface. Routed, owned, and
  not-held endpoints are skipped and counted at Debug. `collectMonitoredNeighbors`
  skips owned addresses. The two once-a-second Info lines are now Debug.
- **Issue filed**: #18621 (a standby cannot pre-warm neighbours on RETH
  prefixes it does not own; predates this fix).
- **Tests**: `pkg/daemon/neighbor_warm_onlink_18617_test.go` (the split shape,
  its twin with the LAN held, the standby, longest prefix, DHCP lease, every
  owned-address source, force-probe owned filter, log level);
  `warmneighbor_bound_5451_test.go` adapted (per-interface socket bound).
