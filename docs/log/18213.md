# #18213: planned xpfd shutdown must not mint helper crash debt

- **Timestamp**: 2026-10-28
- **Problem**: With systemd's default `KillMode=control-group`, stopping or
  restarting xpfd sends SIGTERM to xpfd and its `xpf-userspace-dp` child
  concurrently. The child can exit and reach `superviseHelper` before xpfd's
  orderly `Manager.Close` path retires the generation. That exit is then logged
  as unexpected, increments the daemon-lifetime crash counter and restart debt,
  and can leave FWDD degraded after an otherwise planned deploy restart.
- **STEP-0**: `issue://18213` was OPEN. `origin/master` still accounted an
  exit from the current helper generation as unexpected, and
  `test/incus/xpfd.service` had no `KillMode` override. Its default cgroup-wide
  SIGTERM could reach the helper before `stopLocked` retired its generation.
  Merged PR #7242's #5838 follow-up retires that generation when stop begins.

## Fix

- `test/incus/xpfd.service`: use `KillMode=mixed`, which sends the initial
  systemd stop signal to xpfd alone; remaining cgroup processes receive SIGKILL
  only after xpfd exits or `TimeoutStopSec` expires.
- Keep `stopLocked` as the planned-stop fence, with one ordering repair:
  immediately before advancing `procGen`, it non-blockingly checks the active
  generation's `exited` channel. If the waiter has published the completed wait
  by closing that channel but is blocked on `m.mu`, `stopLocked` accounts the
  pre-retirement exit before advancing the fence. This boundary is publication,
  not physical exit: a helper already dead whose waiter has not yet closed
  `exited` when the check runs is treated as part of the planned stop. In a
  failed supervisor retry, the crash handler owns the failed child's single
  attempt charge and keeps its retry timer on the unchanged generation.
- Named cells cover planned stop with zero crash debt, genuine SIGKILL before
  helper stop without a lock race, SIGKILL reaped while `m.mu` is held before
  retirement, SIGKILL after retirement, a genuine SIGKILL on the next
  generation, and the shipped unit's `KillMode`.

## Risk

There is no daemon-wide helper-crash suppression flag. An exit published by
closing the generation's `exited` channel before `stopLocked`'s non-blocking
check is unexpected and counted even if the waiter is blocked on `m.mu`. The
cutoff is publication, not physical death: a SIGKILL immediately before the
check can remain unobserved if `Wait` has not yet published it, in which case it
is treated as part of the planned stop. This intentionally does not add a
second, racy observation mechanism. A genuine SIGKILL of a later generation
still creates crash accounting and restart debt.
