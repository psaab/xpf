# Issue #14377 — Padded BGP cluster-id passes the validator but is silently omitted by the renderer (RR loop prevention defeated)

- **Issue:** psaab/xpf#14377 (deep-review DR4-H5, validated MATERIAL/CONFIRM
  by both blinded research passes). Lane branch: `fix/14377-campaign` off
  `origin/master` `2b62680633`.
- **Anchors (re-anchored at current master):**
  `pkg/config/schema_validators_network.go` `ValidateBGPClusterID` /
  `ValidateIPAddress`, `pkg/frr/render_validate.go:89-95` `validClusterID`,
  `pkg/frr/protocols_render.go:464-469` cluster-id render,
  `pkg/frr/protocols_render.go` BGP `update-source` render via
  `frrOperandOrOmit` (#9493), `pkg/config/schema_routing.go` BGP
  `cluster-id` + group/neighbor `local-address` leaves.

## Defect (present at base)

`ValidateBGPClusterID` and the generic `ValidateIPAddress` both do
`trimmed := strings.TrimSpace(raw)` and validate the trimmed form. Padding
is authorable through ordinary ingress (quoted strings preserve their
contents verbatim, e.g. `cluster-id " 10.0.0.1 "` — same class as #9820).
The renderer validates the RAW string: `validClusterID`
(`net.ParseIP`/`strconv.ParseUint`, no trim) and `frrOperandOrOmit` /
`config.FRRSingleToken` (any whitespace => not a single token) both reject
a padded value. So:

- `protocols bgp cluster-id " 10.0.0.1 "` / `" 42 "` commits GREEN
  (SchemaValidate nil) and renders NO `bgp cluster-id` line — the route
  reflector falls back to its router-id, defeating RR loop prevention
  when redundant RRs share a cluster.
- `protocols bgp group/neighbor local-address " 10.0.0.1 "` commits GREEN
  and renders NO `neighbor ... update-source ...` line — the BGP session
  sources from the wrong address.

Both omissions were silent (no render warning for cluster-id; only the
generic multi-token warn for update-source).

## What

- `ValidateBGPClusterID`: refuse `trimmed != raw` with a message naming
  the padded value (`leading or trailing whitespace is not allowed; use
  a bare IPv4 dotted-quad or integer`), mirroring `ValidateOSPFArea`
  (#9820). This is an intentional compatibility tightening: migration is
  to remove quotes/padding and use the bare value.
- New `ValidateBGPLocalAddress` in `schema_validators_network.go`:
  refuses padding, then delegates to `ValidateIPAddress`. Wired into both
  BGP `local-address` leaves in `schema_routing.go` (group-level and
  neighbor-level; the routing-instance BGP subtree reuses the same
  `schemaProtocols.children["bgp"]`, so it is covered). The generic
  `ValidateIPAddress` is deliberately unchanged — its many non-BGP leaves
  (GRE tunnel, DDNS, syslog, DHCP, IKE, DNS) keep prior trimmed leniency;
  tightening them is out of this issue's scope (nearest precedent #9820
  also scoped its padding arm to the one validator).
- Render belt (fail-closed, unchanged accept set): `validClusterID`
  already rejected padding on the raw string. Added
  `logOmittedBGPClusterID` (`pkg/frr/render_validate.go`) called from the
  cluster-id render site in `protocols_render.go` whenever a non-empty
  cluster-id is omitted: warns with the sanitized value and the reason
  (distinct message for the padded-but-otherwise-valid case), so a
  leniently-loaded padded value can never again disappear silently.
  The padded value is still NOT rendered (FRR would reject the token and
  fail the whole managed reload — #4919 blast radius).
- NOT changed: `ValidateIPAddress`, `ValidateIPv6Address`, CIDR
  validators, chassis `cluster-id` (different mechanism), the
  `update-source` render belt (already omitted-with-warning).

## Risk

- Compatibility tightening only: a previously-committed padded spelling
  must now be re-entered bare. Such configs were already non-functional
  (value silently omitted), so no working deployment changes behavior;
  strict commit now tells the operator, and lenient load still boots
  (#1960) with a render warning instead of silence.
- No new allocations or hot-path cost: two `TrimSpace` comparisons on
  the commit path; one `slog.Warn` only when a cluster-id is omitted.
