# #16709: web-management on fxp0 (vrf-mgmt) can never bind

- **Timestamp**: 2026-10-25
- **Action**: `web-management http|https interface fxp0.0` resolved the
  interface addresses and then bound them with an unscoped
  `net.Listen`. fxp0 is always enslaved to `vrf-mgmt`, so its IPv4 and
  global-IPv6 addresses exist only in table 999's local table and the
  bind was refused `EADDRNOTAVAIL` on every apply; for HTTP the IPv4
  leg is first, so Start failed with nothing serving. Fixed by
  scoping such legs to the VRF master with `SO_BINDTODEVICE` (the
  grpcapi fabric-listener pattern):
  - `pkg/api`: new `Config.BindDevices` (listen-address -> VRF device)
    and `Server.listenAddr`, the single bind entry for Start,
    reconcile, `Run`/`bindListeners`, and HTTPS cert recovery. Scoped
    addresses bind via `net.ListenConfig` + `SO_BINDTODEVICE`; an
    injected `ListenFunc` always wins. The scope is part of leg
    identity: `SetBindDevices` publishes the desired map, adoption in
    `reconcileLegsLocked` requires the live leg's recorded scope to
    match, and `legDevices` tracks what each live leg was bound with.
  - `pkg/daemon`: `webMgmtBindDevice` resolves the scope from the
    committed config (management-class -> `vrf-mgmt`; tenant
    virtual-router member -> `vrf-<name>`; otherwise unscoped),
    `resolveAPIBinds` stamps `BindDevices` per plane and drops scopes
    for clamp-rewritten loopback addresses, and the management
    endpoint fingerprint carries the map so a scope-only change forces
    a rebind with retry debt on failure.
