## 2026-09-10 — Action: design for the close-state wire field, written before any code
- **File(s)**: `docs/log/9412.md` (this entry only)
- **Spec.** The 2026-09-10 comment on the issue:
  - the sweep cannot re-send a mid-life change;
  - the acceptance must cover install-OPEN -> close on the primary -> failover
    with no traffic;
  - add a field and never reuse `SessionValue.TCPState`;
  - never re-derive from `tcp_flags`;
  - no spurious RT_FLOW SESSION_CREATE;
  - make a volume argument against #8593.
- **Wire value.** `tcp_close_class` is a u8: 0 = not carried or not closing,
  1 = Closing, 2 = TimeWait, 3 = Reset. It mirrors `TcpCloseClass` one-to-one.
  - It is direction-neutral. The delta carries the FORWARD key only, while
    `fin_own`/`fin_peer` are relative to each entry's direction.
  - An old peer reads it as 0, which is today's behaviour.
- **Primary (Rust).** A new `SessionDeltaKind::Update`.
  - Pushed from `lookup_with_origin` only on a close-CLASS TRANSITION (compared
    before and after, companion propagation included), and only for an entry that
    is not peer-synced. It is keyed on the forward entry.
  - It encodes as the open-frame layout on the reserved type 3
    (`MSG_SESSION_UPDATE`), which Go already decodes as an open.
  - RT_FLOW CREATE and close teardown both gate on `kind ==`, so Update is
    excluded from both by construction.
  - Every Open producer also stamps the entry's current class (install,
    bulk-export `emit_open_delta_with_origin`, promote, `ha/export.rs`). Without
    that, the #2442 loss-of-sync resync could not recover a dropped Update.
- **Go.** The same trailing byte is added in four places:
  - after `RoutingDomain` in `decodeSessionEvent`;
  - in `SessionDeltaInfo`;
  - in the walker, where `"update"` is handled like `"open"` so the JSON leg is
    explicit;
  - in the convert step, into a sync-only `SessionValue{,V6}.TCPCloseClass`
    placed after `TunnelDiscriminator`.
  After that it goes on the cluster wire as a trailing length-gated byte (no
  wire-version bump, per the #2170 convention), and into `SessionSyncRequest`.
- **Standby (Rust).** `SessionSyncRequest.tcp_close_class` flows through
  `SyncedSessionEntry` and `SessionInstall` into `upsert_synced_with_origin`:
  - `closing` = class != 0;
  - `reset` = Reset;
  - TimeWait sets both FIN bits;
  - Closing sets NEITHER FIN bit, because the direction is unknown and inventing
    one would mis-classify the peer's later FIN;
  - expiry comes from `tcp_close_window_ns(class)`, not the established window.
- **Volume against #8593.** At most three Updates per session, one per class
  transition, and a repeated FIN or RST in the same class emits nothing. A cell
  pins this. Updates go through the same bounded ring and loss latch as every
  delta; there is no new producer loop.
- **Acceptance, written first, RED at base, compiling at base.**
  - (a) Primary: a local TCP session installed OPEN and drained, then a FIN
    through `lookup`. A close-state delta must be emitted. At base nothing is.
  - (b) Go chain: a type-3 frame carrying the class goes through the real
    functions: decode, walk, convert, cluster encode/decode, then
    `buildSessionSyncRequestV4`. The request JSON must carry `tcp_close_class`.
  - (c) Standby: a `SessionSyncRequest` carrying the class is imported,
    promoted, and given no traffic. It must be reaped after the close window and
    not before. At base it lives for the full established window.
  - (d) A golden type-3 frame shared by the Rust encoder and the Go decoder, the
    #7188 lockstep pattern, so neither side can rename or move the byte alone.
  - `tcp_flags_zero_on_sync_path_9412_tests.rs` stays green under this design
    (`tcp_flags` stays 0). Its doc claim becomes false, so it must be updated by
    hand.

## 2026-09-10 — Action: F1 redesigned. Remove the arrival-order race instead of bounding it. F2 withdrawn
- **File(s)**: `docs/log/9412.md` (design, before code)
- **F1 is the Go sender memo that stops a mirror-sourced resend from regressing a
  close class.**
- **The problem the coordinator raised, and it is correct.** I had bounded the
  reused-tuple residual by queue order at the SENDER. Correctness depends on
  arrival order at the PEER. A stale class landing after a new incarnation's Open
  would early-reap a live session. That is worse than #9412, and no outcome check
  sees it when frames arrive in order.
- **The proposed replacement key does not work as written.** It suggested keying
  by install generation. `stampInstallGenV4` draws `nextInstallGen()` on EVERY
  send, sweep included, so the generation is per-send, not per-incarnation. A
  generation-keyed memo would never match on the sweep path, and F1 would be inert.
- **The identity that exists at both send sites is `SessionValue.SessionID`.**
  - **Delta path:** `adoptedOrLocalSyncedSessionID` returns the helper's stable
    per-session id (`RTFlowSessionID`, #4915) when it is non-zero.
  - **Mirror path:** the conntrack publisher stamps the same
    `SessionEntry.session_id` into the row (`publish_conntrack.rs`), and `fromBPF`
    carries it into `SessionID`.
  - A reused tuple gets a new id from the monotonic, namespaced allocator
    (#6311), so it simply misses the old entry and reads class 0. The race is gone
    in any arrival order.
  - **Id 0 means "no identity".** The memo never records or applies for it, which
    fails toward class 0 (today's window), never toward an early reap.
- **Memo semantics.** Keyed by (tuple, SessionID). Applied in `stampInstallGenV4/V6`,
  the one stamp every session frame passes immediately before encoding: the delta
  path `QueueSessionV4/V6`, the `syncSweep` resend and the `bulkSyncWindow` walk
  (verified by listing the callers: `sync_conn_write.go`, `sync_conn_sweep.go`,
  `sync_bulk.go`, and no other).
  - A non-zero class is recorded. In practice only the delta path supplies one,
    because the mirror row's `TCPCloseClass` is always 0.
  - A frame of the SAME incarnation carrying a lower class is raised to the
    recorded one. A different SessionID drops the record first.
  - Evicted in `takeDeleteGenV4/V6`, before that function's no-stamp early return.
  - Bounded by `genGuardMapCap` like the generation maps. At the cap a NEW record is
    not written, which fails toward class 0.
- **Lock graph.** The memo sits under `genSentMu`, beside `genSentV4/V6`.
  - The record, the lookup and the eviction all happen inside the `genSentMu`
    critical sections `stampInstallGenV4/V6` and `takeDeleteGenV4/V6` already held.
  - There is no separate acquisition and no new lock, so there is no new ordering
    to invert.
  - (A draft of this entry said the sweep took a separate lookup acquisition. The
    implementation has none; corrected here.)
- **F2 (replica workers announce) is WITHDRAWN from this change.**
  - A worker replica's `session_id` is NOT the installer's. Local shared-map
    publishes carry 0, so each replica mints its own on import.
  - An Update from a replica would carry a different id. The standby would
    re-adopt it, flipping the session's id and breaking #5212's cross-node RT_FLOW
    correlation. It would also key the memo by an id the mirror row never has.
  - The prerequisite is replicas sharing the installer's stable id. That is its
    own change, filed as #9582.
  - **Bound meanwhile:** a close seen only by a replica worker, usually the
    server's FIN or RST arriving on the other interface's RSS queue, is not
    announced. The client's FIN reaches the installing worker, so CLOSING is
    announced. TIME_WAIT shares its 30 s default window. A server-only RST stays
    on the old window.
