# Issue #15682: Incremental feed-name path upsert

- **Timestamp**: 2026-10-19
- **Problem**: Incremental `set security dynamic-address feed-server <srv> feed-name <feed>` followed by `feed-name <feed> path <path>` (and the same refinement across merged hierarchical blocks) appended duplicate `FeedEntry` records for one feed name. `validateDynamicAddressFeedNameUniquenessStrict` then falsely rejected a single feed-server (`"s1" and "s1"`), and on the lenient path `feeds.Manager.Apply` could resolve the feed to the first, path-less entry and drop the configured path.
- **Fix (ast)**: In `SetPathQuotedGrouped` (`pkg/config/ast_edit.go`), the generic container find-or-create now also matches an existing leaf by keys: a same-key leaf is promoted (`IsLeaf = false`) and descended into instead of appending a duplicate sibling container. The promotion is scoped to `feed-name <feed>` under a `feed-server` (the issue's named `findOrCreateContainerGrouped` helper does not exist at this revision; the equivalent else-branch loop is the site). The scope is required: a blanket promotion collapsed the meaningful two-node policy shape `then permit` + `then permit application-services …` into one node and broke the #3114/#3115/#3141 specific diagnostics (#3377) — pinned by `TestDynamicAddressSetPathKeepsThenActionSplit15682`.
- **Fix (compiler)**: In `appendFeedEntry` (`pkg/config/compiler_services.go`), entries are upserted by `Name` within the same feed-server: a matching `fs.FeedName` is consumed/promoted, and a matching existing entry has its `Path` updated whenever the new `entry.Path != ""`, instead of appending a second `FeedEntry`. A bare re-statement after a path entry does not clear the path.
- **Fix (bindings)**: In `compileDynamicAddress`, `ab.FeedNames` is deduplicated before append, so repeated `profile feed-name <feed>` statements (flat or across merged `address-name` blocks) name the feed once.
- **Regression check**: full `pkg/config` suite on current origin/master shows 181 failures both with and without this change (pre-existing at this head, incl. the `#14139` IPsec pre-shared-key family); the with/without name-set diff is exactly the three #15682 tests turning green — zero new failures.
- **Not changed**: Cross-server duplicate feed names remain a strict error (#4913) and a lenient warning; the validator is untouched. Servers' genuinely distinct feeds are untouched.
