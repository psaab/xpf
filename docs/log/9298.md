## Timestamp: 2026-09-09 — the fix

- **File(s)**:
  - `userspace-dp/src/afxdp/icmp_embed/parse.rs` — `pub pptp_call_id:
    Option<u16>` on `EmbeddedV4Header` and `EmbeddedV6Header`; both parsers
    call the existing `gre_discriminator::pptp_call_id` extractor when
    `proto == PROTO_GRE`, bounded by `inner_declared_end` (the #2361 rule).
  - `userspace-dp/src/afxdp/icmp_embed/mod.rs` — new
    `resolve_quoted_pptp_discriminator(sessions, quoted, quoted_call_id,
    quoted_dst)`.
  - `userspace-dp/src/afxdp/icmp_embed/nat_match_v4.rs`,
    `nat_match_v6.rs` — the two PRODUCTION arms call it and use the result in
    BOTH the forward key and the reply key.
  - `userspace-dp/src/afxdp/icmp_embed/session_match.rs` — kept in step (no
    non-test caller; see below).
  - `userspace-dp/src/afxdp/README.md` — module doc, in the same change.

- **Three properties the resolver is built around**, each of which is a cell:
  - **Only `Unparseable` is upgraded.** A correctly-parsed RFC 2890 identity
    (`Keyed`/`Unkeyed`) is returned untouched, or the resolve would silently
    re-attribute keyed-GRE errors whenever a call id happened to be present.
  - **A miss stays `Unparseable`.** Never a wildcard, never "whatever
    association is around": PPTP calls between one address pair are
    distinguished by nothing else, so guessing crosses calls.
  - **Non-touching `resolve`, not `resolve_and_touch`.** The transit path
    touches because a data packet IS traffic on the call. An ICMP error is
    traffic ABOUT the call, emitted by a third party on the path, so
    refreshing on it would let errors keep a dead association alive — and the
    association's lifetime is what bounds reuse of a 16-bit call id.

- **Why the discriminator must be a locally derived handle** (the property the
  direction-symmetry cell pins): RFC 2637 §4.1 has each side allocate its OWN
  Call ID naming the peer it sends to, so the two directions of one call carry
  DIFFERENT wire values. A discriminator built from the wire would differ per
  direction and the reverse companion could never match the forward key.

## Timestamp: 2026-09-09 — cells

13 new cells. `PPTP_9298_CLIENT_CALL_ID = 0x0101` and
`PPTP_9298_SERVER_CALL_ID = 0x0202` are deliberately different, so a fixture
that accidentally worked by reading the wire value would work in one direction
only.

**Unit — the resolver** (`icmp_embed/mod.rs`, `mod pptp_embedded_9298`):

| cell | binds |
|---|---|
| `a_quoted_pptp_call_id_resolves_to_the_live_handle_9298` | the resolve itself |
| `both_directions_of_one_call_resolve_to_the_same_handle_9298` | direction symmetry (200 vs 100 on the wire, ONE handle) |
| `an_unresolvable_call_id_stays_unparseable_9298` | 3 miss shapes: wrong id, wrong peer, no id |
| `a_non_unparseable_quote_is_returned_untouched_9298` | `Keyed`/`Unkeyed`/`None`/`Pptp` all inert, WITH a resolvable id present — the guard is the quote's CLASS, not the absence of an id |
| `resolving_a_quote_does_not_refresh_the_association_idle_clock_9298` | the association still ages out on its install time (observable: `expire_idle` still returns 1) |

**Unit — the parser** (`icmp_embed/parse.rs`, `mod pptp_quote_call_id_9298_tests`):

| cell | binds |
|---|---|
| `a_quoted_pptp_header_yields_the_call_id_and_stays_unparseable_9298` | BOTH halves together, plus an explicit `assert_ne!` against `Keyed(payload_len<<16 | call_id)` — the plausible wrong answer |
| `a_version_0_keyed_quote_yields_no_call_id_9298` | an RFC 2890 Key is not a Call ID |
| `a_call_id_in_slack_past_the_declared_quote_is_not_read_9298` | #2361, applied to the quote |
| `non_gre_quotes_carry_no_call_id_9298` | compatibility control, with bytes that WOULD read as a PPTP header |
| `the_ipv6_quote_parser_reads_the_call_id_too_9298` | the v6 parser |

**End-to-end — the WIRING** (`afxdp/tests_embedded_poll_filter.rs`), through the
real `try_embedded_icmp_nat_match_from_frame`:

| cell | binds |
|---|---|
| `embedded_icmp_resolves_a_pptp_call_v4_9298` | `nat_match_v4` — asserts the RECOVERED PRE-NAT SOURCE and the return resolution, not a key hit |
| `embedded_icmp_resolves_a_pptp_call_v6_9298` | `nat_match_v6`, a SEPARATE key constructor |
| `embedded_icmp_session_match_resolves_a_pptp_call_9298` | `session_match`'s forward key, via `try_embedded_icmp_session_match_from_frame` |
| `embedded_icmp_does_not_cross_pptp_calls_9298` | FAIL-OPEN GUARD |

**Why the end-to-end cells exist on top of the unit ones.** The unit cells pin
`resolve_quoted_pptp_discriminator` itself; they cannot see the WIRING. Each key
constructor calls the resolver and drops the result into
`SessionKey.discriminator`, and reverting any one call site back to
`hdr.discriminator` leaves every unit cell green — the function still behaves,
nobody asks it. That is the exact shape that let two mutants survive earlier in
this campaign.

**The one control that does NOT distinguish fixed from broken, and why it is
kept.** `embedded_icmp_does_not_cross_pptp_calls_9298` returns `None` before and
after the fix. It is not the distinguishing control (that is the two resolve
cells, which failed at the base commit above) — it guards the direction a
careless remedy takes: wildcarding the discriminator, or resolving an unknown
Call ID to any live association, would satisfy both resolve cells while
attributing one call's ICMP error to another call's session. Its doc comment
says so, so nobody later reads it as evidence of the fix.

**Two frame builders added** (`afxdp/tests_support.rs`):
`build_icmp_te_frame_v4_pptp` and `build_icmpv6_te_frame_pptp`. Deliberately
SEPARATE from `build_icmp_te_frame_v4`'s GRE arm rather than another
`embedded_proto` branch: version 0's 32 bits after the flags are an RFC 2890 Key
and version 1 re-purposes the same 32 bits as `Payload Length | Call ID`. One
builder emitting both from one `snat_port` argument would make it easy to write
a cell that looks like it is about PPTP and is really about a Key. Both set a
NON-ZERO payload length (`0x05dc`), so a reader that took the whole word as a
Key would produce a different identity per packet.

  figure (four forward keys + three parse-side field inits), confirmed by
  inspection. Raising it rather than leaving it at 5 keeps the non-vacuity
  check as tight as it was.

`hdr.discriminator`, and a non-vacuity total of 4.

local alias of the raw value) gets past it, the same limit #9031's guard
