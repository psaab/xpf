# Issue #15104: shared NAT ambiguity index never forgets aliases (A71-01)

## Why

`SharedNatAmbiguityIndex` (`userspace-dp/src/afxdp/types/mod.rs`) latched
`saturated = true` once its alias map reached 16,384 lifetime keys and
never forgot an alias: `remove_shared_session_if` deleted the shared NAT
map aliases but never touched `nat_ambiguities`. After 16,384 lifetime
forward flows every later shared reverse-NAT lookup failed closed
(`is_unique_for` / `unique_owner` return false/None while saturated)
until a full helper stop, silently losing the shared reverse-NAT
backstop. Publish observed the reverse alias for every non-reverse
entry, NAT'd or not, so ordinary flow churn alone crossed the bound.

## What

- `types/mod.rs`: saturation is now computed from the live size
  (`aliases.len() >= MAX_KEYS`), never latched. The index gains a
  per-alias owner multiset (`owners: alias -> owner -> count`, counted
  per (alias, owner) pair) plus `track_owner` / `forget_owner`:
  forgetting drops the alias record only when its last owner leaves,
  and restores a sole surviving owner of a displaced alias to unique.
  `len()` / `saturated()` are exported for the gauge. The forward-wire
  index (`wire_ambiguities`, same type) inherits the live bound.
- `shared_ops/store.rs`: publish tracks the canonical-alias owner
  (`track_owner`, verdict still driven by the displacement mark);
  `remove_shared_session_if` now calls `forget_owner` for the removed
  forward entry's wire and canonical reverse aliases after dropping the
  NAT map lock. No scan of `shared_sessions` is added (that is #15106).
- Saturation gauge, end to end: `Coordinator::shared_{nat,wire}_ambiguity_{keys,saturated}`
  -> `ProcessStatus.shared_{nat,wire}_ambiguity_{keys,saturated}`
  (additive, `default`) -> Go `ProcessStatus` fields ->
  `xpf_userspace_shared_{nat,wire}_ambiguity_{keys,saturated}`
  Prometheus gauges. `protocol_wire_v1.json` regenerated (it also picks
  up three pre-existing drift fields already in the Rust types:
  `dns_illegal_reply_dropped`, `gre_outer_frag_drops_total`,
  `nat_reverse_ambiguous_total`).

NOT changed: lookup fail-closed semantics, the 16,384 bound itself,
#14383 wire survivor re-resolution, and the #15106 scan (sibling issue).

## Validation

- RED on base (shimmed to pre-fix API, same publish/remove path and
  assertions): all 3 new tests fail — lifetime churn (`last removal must
  forget the alias`), live bound (`saturated index must fail closed`
  via the shimmed proxy plus recovery), survivor (`sole surviving owner
  must be restored to unique after twin removal`).
- GREEN: `xpf_userspace_dp-1e7763e3cb77f9e0 15104` — 3 passed
  (`shared_nat_ambiguity_recovers_after_lifetime_churn_15104`,
  `shared_nat_ambiguity_live_bound_fails_closed_and_recovers_15104`,
  `shared_nat_ambiguity_survivor_controls_15104`), driving the real
  16,384 bound through `publish_shared_session`/`remove_shared_session`.
- Adjacent control: `publish_shared_session_fuses_nat_ambiguity_updates_under_one_lock`
  passes. `publish_shared_session_counts_calls_and_lock_acquisitions`
  fails identically on unmodified base (base-attributed, not this change).
- Go: `go test ./pkg/api/ -run TestUserspaceOperationalAndHACountersEmit13280`
  passes (34 series incl. 4 gauges); `go vet` clean; wire fixture test passes.

## Risk

- Owner-multiset memory is bounded by live aliases x owners per alias,
  the same order as the alias map it mirrors; `clear()` resets both.
- Re-publish of the same owner does not inflate counts (`or_insert(0)`),
  so HA re-sync sweeps cannot strand an alias by over-counting.
- Lab verify still outstanding: live saturation/recovery on the loss
  cluster under >16k concurrent shared NAT flows.
