# #18818 — seed WG peer adjacency in TCP segmentation cells

- **Timestamp**: 2026-11-05
- **Action**: Seeded the WireGuard TCP-segmentation fixtures with the selected peer's route and neighbor adjacency required by #13978, and asserted the emitted outer destination MAC.
- **File(s)**: `userspace-dp/src/afxdp/frame/tcp_segmentation.rs`, `docs/log/18818.md`

## Why

The two WireGuard TCP-segmentation tests constructed a `ForwardingState` with an egress interface and WG session decoy MAC, but no route or neighbor for the peer endpoint. Since #13978 (`fda6cad264`, PR #14071) requires WireGuard encap to fail closed when the selected peer's outer next hop has no neighbor, both tests returned `None` before exercising their MTU and encap-dispatch assertions. The session's neighbor MAC is intentionally not a valid substitute.

## What

The test fixture now installs a route for `203.0.113.0/24` via ifindex 362 and a static adjacency for next hop `203.0.113.1`. Both WG segmentation tests use this shared state seed; the outer-protocol test also verifies every segment's destination MAC is the seeded peer-adjacency MAC. Production code and the 1500-byte MTU premise are unchanged.

## Validation

- Before the fixture repair, both named WG segmentation tests failed at `WG segmentation must produce frames` (0 passed, 2 failed).
- With the adjacency seeded, the complete `mode_aware_segmentation_tests` module passed (15 passed, 0 failed), including both repaired cells. The independent #13978 `wg_encap_outer_dst_mac_never_borrows_unresolved_peer_nexthop_13978` control passed (1 passed, 0 failed).
- Mutant proof: removing the peer-neighbor insertion made both named tests fail again at `WG segmentation must produce frames` (0 passed, 2 failed). Restoring the seed returned both tests to green (2 passed, 0 failed).

## Risk

Test-fixture-only change: the tests now satisfy the fail-closed #13978 outer-route precondition instead of relying on the forbidden session-neighbor fallback. No product behavior changed.
