# IPv4 srcMask/dstMask always 0: RTA_IIF lookup has no source (#14610)

## Why

`fibMatchMask` built `RouteGetOptions{FIBMatch:true, IifIndex}` with no
`SrcAddr`. Production `InIf` is `IngressIfindex`, always >0, so every
IPv4 lookup took the kernel input path, which rejects a zero source as
martian (EINVAL in `ip_route_input_slow`). The error yielded `(0,false)`,
cached for the TTL and exported as an unresolved 0 — indistinguishable
from a real default-route /0. The #2866 feature was dead for every IPv4
record; the unit tests faked the lookup, so nothing exercised the real
netlink call. IPv6 happened to work via the same query.

## What

- `pkg/flowexport/routemask.go`: `fibMatchMask` now performs an OUTPUT
  route lookup — `vrfOifForIfindex` maps the ingress ifindex to its
  l3mdev master (`MasterIndex` via `netlink.LinkByIndex`) and sets
  `RouteGetOptions.OifIndex`. An output lookup needs no source address,
  and `RTA_OIF` set to an l3mdev master selects that VRF's table, so a
  VRF-enslaved iif still resolves in the VRF table. A non-enslaved or
  unresolvable ifindex omits `RTA_OIF` and keeps the main-table lookup,
  bit-identical for single-VRF/default deployments. Package-level seams
  `routeMasterLinkByIndex` / `routeLookupWithOptions` let unit tests
  assert the query shape without a kernel netns. The false "bit-identical"
  comment and the stale `MaskResolver` doc are corrected.
- `pkg/flowexport/README.md`: the #3744 section now documents the OIF
  output lookup and the #14610 EINVAL mechanism.
- Tests: new `pkg/flowexport/routemask_netns_14610_test.go`.

NOT changed: the `MaskResolver` signature, the `(ifindex, IP)` cache key,
the async background-populate path, miss counting, or the wire format.
Route-resolution semantics for fwmark/PBR tables remain the documented
#3744 residual.

## Validation

- Probe (in-process, private netns): the OLD query shape
  (`RouteGetOptions{FIBMatch:true, IifIndex}`) against the kernel returns
  `invalid argument` with no routes, while the production
  `fibMatchMask(192.0.2.5, iif)` returns `(24, true)`.
- RED: the new netns test cannot pass on current master — its unit seam
  does not exist there (build failure), and the behavioral core is the
  probe above: the old IIF query is EINVAL for IPv4 in the same harness.
- GREEN targeted: `unshare -rn go test ./pkg/flowexport/ -run
  TestFibMatchMaskRealNetlink14610 -count=1 -v` passes — IPv4 src and dst
  halves return /24 with a positive ifindex, IPv6 returns /48 unchanged,
  and a VRF-enslaved member resolves to the VRF table's /16 (distinct
  from the main table's /24, so a table leak would be visible).
  `TestFibMatchMaskOifScoping14610` (no netns needed) pins OIF=master,
  IIF=0, no SrcAddr, FIBMatch, plus main-table fallback cells.
- GREEN affected suite: `go test ./pkg/flowexport/... -count=1`,
  `go vet ./pkg/flowexport/`, `gofmt`, `git diff --check`.

## Risk

One extra `LinkByIndex` netlink call per background cache populate
(bounded by the existing 32-inflight cap and 10s TTL cache); no change
on the session-close hot path. A torn-down interface between close and
populate now falls back to the main table instead of failing the lookup
— a mask from the main table is strictly better than an unresolved 0.
No lab deployment was run; the kernel behavior is covered in-netns.
