# 10025 — Pre-break NTP clock-skew alarm and lab time sync

## Why

The loss-cluster firewalls previously had no persistent NTP source. During #9486
validation, one node ran about 125 seconds behind the other; that skew broke
fabric authentication and obscured the configuration-sync diagnosis. The
existing fabric-auth skew path only diagnosed the problem after an RPC had
already failed. This change adds a daemon-resident warning before the clocks
reach the authentication failure band and records the lab remediation attempt.

## What changed

- Added `pkg/clockskew`, a dependency-injected reference-clock sampler and
  stateful monitor. It samples every 5 seconds, raises at a 15-second local
  reference offset (or for no NTP source / an unsynchronized reference), keeps
  state on unavailable samples, and clears numeric offset alarms below 10
  seconds to avoid threshold flapping.
- Bound chrony tracking and `timedatectl` fallback commands by one 5-second
  context deadline. Monitor shutdown cancels an in-flight sampler before
  joining its goroutine.
- Wired the monitor into daemon startup/shutdown and atomically exposed its
  active snapshot to the local CLI and gRPC server, including no-dataplane
  mode.
- Rendered the same alarm in `show system alarms`, `show security alarms
  detail`, and `show chassis cluster status` on both console and gRPC paths.
  Raise/clear transitions emit one `RT_SYSTEM` syslog line each.
- Documented the 15/30/60-second relationship to the unchanged fabric-auth
  replay window in `pkg/cluster/README.md`.

## RED then GREEN

The genuine RED check used a temporary copy of `origin/master` with only the
new test files copied in, then ran:
`go test ./pkg/clockskew ./pkg/daemon ./pkg/cli ./pkg/grpcapi`.
It returned non-zero with `no non-test Go files in .../pkg/clockskew` and
undefined `Sample`, `Monitor`, `New`, and `KindOffset` symbols (plus the
missing daemon/CLI/gRPC wiring). This proves the tests exercised a missing
baseline implementation rather than only asserting already-existing behavior.

After the implementation, the focused cells and complete affected package runs
passed wherever the package was not blocked by the pre-existing #10152 fixture
failure below.

## Lab

- `chrony` was already installed at 4.8-3 and `enabled`/`active` on both
  `loss:xpf-userspace-fw0` and `loss:xpf-userspace-fw1`; the idempotent
  `apt-get install -y chrony` and `systemctl enable --now chrony` checks
  succeeded.
- I configured the source through xpf (`set system ntp server 172.16.100.2`),
  not by editing chrony directly. `sources.d/xpf.sources` converged to
  `server 172.16.100.2 iburst` on both nodes, and the temporary unmanaged
  probe file was removed from both nodes under the cluster lock.
- The running chrony services remained unsynchronized in their normal
  (non-management) VRF: both reported `Stratum 0`, `Leap status: Not
  synchronised`, and no reachable sources. A bounded one-shot probe in the
  always-up `vrf-mgmt` did reach the lab NTP server, but deliberately did not
  step either clock: it reported the clock wrong by **132.855066 seconds on
  fw0** and **54.939820 seconds on fw1**.
- A guarded RG1 failover probe was rejected by fabric authentication because
  the peer was already outside the 60-second token window. The probe restored
  all RGs to node0-primary with manual failover cleared.

**Lab result: SKIPPED (exact reason).** Persistent synchronization could not be
verified without changing the chrony service to run in `vrf-mgmt`; the source
is reachable only there, while the normal service is still bound to the main
VRF. I did not make that service-level mutation in this issue run. The PR's
runtime clock-skew alarm remains the bounded protection for this unavailable
lab path.
