## Does the host-bound path have a reason to differ from #9382? Yes, in two places.

#9382 fixed a pure EVALUATION: the re-derivation computes a verdict and emits nothing.
Copying that shape here — replacing `flow` with a translated flow — would be wrong,
because the host-bound gates are not pure:

1. `junos_host_local_policy` uses the same `flow` for the evaluation AND for its side
   effects. `enqueue_deny_reply` builds the TCP RST / ICMP unreachable from the wire
   frame, and `emit_junos_host_deny` records the wire tuple. The client is talking to
   the pre-translation address; a reply from the translated one is a reply from a
   stranger. So the evaluation takes a separate `policy_dst`, and the reply and record
   keep `flow`.
2. `host_inbound_gated_lo0_action` bundles the coarse service gate with the `lo0`
   filter. The issue is explicit that `lo0` stays pre-NAT (Junos filters are), so only
   the gate's `dst_port` argument moves; the frame and `flow` handed to the filter do
   not.

Two narrower differences, both chosen rather than inherited:

- **Both directions on the hit path**, deliberately NOT #9382's forward-only rule.
  #9382 re-derives forward entries only because a reverse companion carries swapped
  zones; that says nothing about a gate asking what the local listener receives. A
  host-bound reverse companion the AF_XDP path could hit does not arise in practice
  (the firewall's own replies leave through the kernel), so a direction branch would
  have been code no cell can reach. It was written first and removed for that reason.
- **Same-family only.** A NAT64 target changes address family, so the address falls
  back to the wire value (the port still follows the translation). With no translation
  both fall back, so direct-to-local traffic is judged exactly as before.

The flowless twin needs no change beyond naming the destination it already used: the
flowless arm applies no destination translation, and a translated flow's later
fragments follow fragment association, not that arm.

## Behaviour change, stated

The coarse service gate now reads the translated port. A DNAT-to-self service listed
only under its WIRE port is no longer admitted by the userspace gate; the kernel backstop
already matched post-NAT, so end to end it was already dropped. One listed only under the
TRANSLATED port is now admitted where the userspace gate used to refuse it.

## The modularity gate: a recorded crossing, not a split

`make test` on `25fe39c38` failed one Go test,
`pkg/refactoraudit`'s `TestTouchedFileCrossedModularityThreshold`:
`userspace-dp/src/afxdp/mod.rs` went from 1497 to 1501 LOC and crossed the 1500 [WATCH]
floor. The four lines are this change's test-module registration (a comment,
`#[cfg(test)]`, `#[path]`, `mod`); #9519's registration is what put the file at 1497.

Three ways out were considered. Compressing the declaration onto fewer lines would land
at 1499 while growing the file by exactly as much: the count would change, the file
would not. Declaring the module from a submodule with `crate::afxdp::` imports has no
precedent among afxdp's poll-path tests (the only nested test modules, under `frame/`,
use their own local support module) and would exist only to dodge the count. The
gate's own escape is a recorded decision in `docs/refactoring-audit-accepted.txt`, in
the shape the existing entries use: what the crossing is, why it cannot live elsewhere,
the merge-base size, and why the split is owed as its own change. That is what this
change does.
