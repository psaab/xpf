## Root cause

- **Timestamp**: 2026-10-30
- **Action**: traced the cross-worker path through the code, and checked it
  against the live counters seat L captured
  (`/var/tmp/fz/rvL-udp-split/`).
- **File(s)**: read-only.

The chain on the LAN-RG owner (node1) for a NEW punted flow:

1. Worker A takes the LAN probe off its LAN queue. The probe misses, resolves
   `FabricRedirect` (the WAN RG belongs to the peer), and installs a #7770
   `FabricPuntSeed` through `install_helper_local_session_on_miss`
   (`forwarding/local_delivery.rs`). That helper publishes only `LocalMiss`
   to the shared maps (#15950). A seed is never published, never
   replicated (no `replicate_session_upsert`, unlike ForwardCandidate and
   MissingNeighborSeed), never HA-exported, and emits no deltas
   (`SessionOrigin::is_transient_local_seed`).
2. The WAN owner (node0) reverses the hop's error and hands it back over the
   fabric. The fabric NIC RSS-hashes the frame independently of the LAN
   probe, so it usually lands on worker B.
3. Worker B runs `match_outer_v4` / `match_outer_v6`:
   - The forward-NAT arm, `lookup_forward_nat_for_icmp_quote_at`, finds no
     local match. The shared NAT map is empty, so it returns `None` before
     the shared-uniqueness check runs.
   - The #14665 outer-destination gate passes: the outer destination is the
     client, which is the quoted source.
   - The session fallback, `probe_session_across_scopes_with_wire_indexes`,
     misses as-is and by reply key: local, shared, and wire.
   - The result is `NoMatch`.

   The error then takes the flowless path and dies under `wan -> lan`
   default deny. On udp, seat L logged 44 such denies on fw1, with
   `ingress_zone=wan egress_zone=lan`.
4. Once node0's HA delta is imported, the shared maps hold the authoritative
   row and later errors match it. That is why the ICMP mode, one flow, lost
   only the first error, and why UDP mode lost every probe: in UDP mode each
   probe is a new flow.

**Candidate site `shared_ops/lookup.rs:2038-2049`.** It is not on this path.
In the pre-import window the shared NAT map holds nothing, so `shared_match`
is `None` before `shared_forward_nat_candidate_is_unique` is ever consulted.
Separately, the instrument used to refute the ambiguity theory cannot see this
site. `NAT_REVERSE_AMBIGUOUS_TOTAL` is bumped only by the local finders in
`session/lookup.rs`, never by `shared_forward_nat_candidate_is_unique`. So a
silent shared refusal there would also read 0. That has no bearing on the
#18562 chain. It does matter for any future post-import diagnosis.
