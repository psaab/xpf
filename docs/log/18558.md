# #18558: tcp/udp IPv4 internet loss is a duplicate WAN address on the lab segment

Branch `fix/18558-wan-arp`, worktree `/var/worktrees/fix-18558`, based on
origin/master `1c45707447`. Raw data is under `/var/tmp/fz/r-18558/`.
Timestamps are UTC on the orchestrator. On 2026-10-31 the tcp nodes ran about
1.0-1.2 s behind the orchestrator, and fw0/fw1 were within about 0.2 s of
each other (`*/skew.txt`).

## Root cause

VLAN 50 (172.16.50.0/24) is a shared lab network, not an xpf-only one. A
non-xpf device already held tcp's WAN address 172.16.50.10, and another held
udp's 172.16.50.11. The upstream gateway (`00:10:db:ff:10:01`) keeps one ARP
entry per address, so whichever holder ARPed the gateway last received the
replies.

## Post-merge (live config does not follow a deb deploy)

Follow `docs/incus-tcp-udp-plan.md` §3.3, "Renumbering a stack on the shared
segment": tcp .10 -> .42, udp .11 -> .43. It covers committing on the RG0
primary, the hand `ip addr del` on the RG1 owner's `<member>.50` (#18573),
the forced snapshot refresh, the SNAT check, and the coexistence window.

On udp 0.0.26120 the helper kept SNATing to the deleted `.11` until a new
snapshot. The commit's snapshot had captured the stale VIP (evidence on
#18573), and that is the likely cause of tcpval1 run 1's pre-failure FAIL.
