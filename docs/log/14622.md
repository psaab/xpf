#14622: thread pool index through address-only reseed carry and deterministic mint

`reserve_address_only` hardcoded `addr_index 0` when minting the
#5269 reverse-identity token. Its two non-trivial callers computed the
true index and discarded it: `reseed_retained_from` computed `new_index`
(the remapped position of the retained address) for its port-bearing arm
but not for the #8597 K11 address-only carry, and the deterministic-CGNAT
address-only mint in `match_rules.rs` computed `ip_idx` to choose the pool
address but stamped 0. `LiveAllocation.addr_index` is the field the reseed
filter/remap keys on, so a record truly on pool[1] stamped 0 survived one
pool edit under the wrong remap and was dropped by a second edit that
removed pool[0] — silently losing the reverse-identity guard for a
still-forwarding GRE/ESP/`port no-translation` session and admitting a
colliding subscriber (reply misdelivery).

`reserve_address_only` now takes `addr_index` and stores it verbatim
(via `reserve_address_only_maybe_persistent`). The reseed carry passes
`new_index` on both the untracked and per-worker arms; the deterministic
mint passes `ip_idx`; the interface-mode caller passes 0, the true index
of its single-address allocator. Existing test callers pass 0 for their
single-address pools. Stale comments claiming `addr_index` is a hardcoded
0 (allocator teardown doc, round-robin token-shape doc) were corrected.
NOT changed: `reserve_address_only_roundrobin` / `_persistent` already
store the selected index (#13690); the synced path already receives it
from `pool_index_of`; interface-mode records keep 0 (no pool to reseed).
