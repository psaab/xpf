# 14958 — WireGuard TunOrigin ICMPv6 session poisoning (D26-02)

## Summary

`wg_tun_origin_packet_initiates` (tun_origin.rs) matched ICMP
direction only for `PROTO_ICMP` (1). ICMPv6 is protocol 58
(`PROTO_ICMPV6`), so every ICMPv6 TUN packet fell to the
directionless `_ => true` arm. An ICMPv6 Echo Reply (129) — the
kernel's answer to an admitted peer→firewall Echo Request (128) —
therefore counted as initiating and `publish_wg_tun_origin_entries`
minted a `SessionOrigin::TunOrigin` pair. The synthesized reverse is
the peer's Echo Request tuple as a LocalDelivery entry; a later
unsolicited peer Echo Request HITs it and `tun_origin_reverse_exempt`
skips host-inbound + junos-host NEW-session gates — bypassing
security-policy / junos-host tightening that should deny it.

## Fix

One file, one function: split the ICMP arm.

- `PROTO_ICMP` → 8 | 13 (unchanged).
- `PROTO_ICMPV6` → 128 only.

128-only is deliberate: ICMPv6 has no timestamp query (133 is Router
Solicitation), and the identifier-keyed parser yields no forward_key
for 133-137, so those types never reach the gate anyway (test pins
137 → None). Fail-closed: every other ICMPv6 type is
non-initiating; UDP/other protocols keep the documented
directionless behaviour (unchanged residual). Encap unchanged —
the gate only gates publish.

## Regression (RED → GREEN)

- `wg_tun_origin_icmpv6_reply_does_not_initiate_14958`: 128 → Some(true),
  129 → Some(false), 137/1 → None. RED on master (129 → Some(true)).
- `wg_tun_origin_icmpv6_reply_publish_skips_14958`: production
  parse+build+publish of the 129 shape leaves shared/dedup/tombstones
  empty; 128 control creates all three. RED on master (shared gains
  the poison pair).

Controls staying green: full `wg_tun_origin_*` and `_10038` suite
(TCP/ICMPv4/UDP initiates tables, create-gate, idle-sweep, builder,
outer-guard, attachment, dedup), `tun_origin_*` revalidation cells.

unchanged for parse-None). UDP-response residual (documented in
item 4 of #10038) untouched.
