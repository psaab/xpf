# Issue #14719 — DB.writeConfirmCover cleared on return strips confirm encryption (D18-01)

## Why

`commitConfirmedLocked` (store_commit.go) sets
`s.db.writeConfirmCover = {profile: masterPasswordPRF(committedTree)}`
and clears it by `defer` on return. `encodeConfirm` (db.go) resolved
`confirmEncryptionPRF(rec.PrevTree, db.writeConfirmCover)` = PrevTree's
own PRF, else the transient cover, else `""` = plaintext.

In the exact #14172 scenario (PrevTree has *no* master-password; the
guarded commit *adds* one), every later `WriteConfirm` therefore wrote
the full PrevTree (all secret leaves) unencrypted and fsynced it:

- resolution tombstone (`markConfirmResolvedLocked`) — fires on *every*
  confirm resolution in this configuration;
- phase-3 finalization retry (`store_persist.go` `persistRetryLoop`
  re-driving `confirmArmRec`);
- boot rebind/migration rewrites (`store_persist.go:392,438,999`);
- FIRST sentinel (`store_persist.go:1039,1579`).

Crash/delete-failure leaves the cleartext tombstone indefinitely; even
on success cleartext blocks were durably written. The old in-code
comment asserted the false premise ("cleared on return so no later
tombstone/migration/retry write silently inherits it" / "keeps those
records exactly under the PrevTree profile they were armed with"): in
this scenario the record was *not* armed under a PrevTree profile
(PrevTree has none) — it was armed under the cover, so inheriting the
armed profile *is* correct.

Mitigation noted by the research passes (0600 file in the 0700
`.configdb` alongside `master.key`) does not close the defect: #14172's
purpose was at-rest encryption of this record, and backups/snapshots/
support-bundles routinely carry config DB files without keys.

## What

Encryption profile is now re-derived from durable state at every
encode, not only carried in the transient DB field:

- `pkg/configstore/crypto.go`:
  - `confirmEncryptionPRF` is now a `*DB` method with precedence
    PrevTree profile → transient arm-time cover → profile recovered
    from the confirm record already on disk → plaintext.
  - `existingConfirmDiskPRF()` (new): reads the on-disk confirm record
    and, if its body is an AES-GCM envelope, returns the envelope's
    self-describing `env.PRF` (`stripConfirmEnvelope` +
    `unmarshalEnvelope`). Fail-open to `""` on absent/unreadable/
    plaintext/corrupt disk state — a legacy plaintext window stays
    plaintext (no invented encryption, no master.key pressure) and a
    corrupt prior record cannot fail a tombstone/retry write.
  - Cheap fast path: a 256-byte prefix read gates on the
    `xpf-master-password-v1` marker before paying the bounded
    (`MaxConfigSize`) read + envelope parse, so plaintext windows (the
    common case) never re-parse a near-ceiling record on every encode.
    (First revision without the fast path timed out
    `TestCommitConfirmedReservesTombstoneHeadroom_9617`, whose
    `measure()` calls `encodeConfirm` repeatedly over ~16 MiB records.)
- `pkg/configstore/db.go`: `encodeConfirm` calls the method form;
  `writeConfirmCover` field comment now records that it is transient
  and later writers recover the profile from disk (#14719).
- `pkg/configstore/store_commit.go`: arm-site comment corrected — the
  cover is still cleared on return, but later writers recover the
  armed profile from the on-disk envelope, so clearing no longer
  strips their encryption.
- `pkg/configstore/README.md`: new bullet documenting the disk-derived
  recovery, fail-open semantics, and the deleted-before-rewrite
  residual.
- `pkg/configstore/confirm_encryption_cover_persist_14719_test.go`:
  distinct cells per named writer, all driven through the real
  end-to-end arm (`Commit` plaintext base with secret → `CommitConfirmed`
  adding `system master-password`), asserting raw bytes contain the
  encrypted format marker and not the PSK, and that the rewritten
  record still round-trips via `ReadConfirm`:
  - `TestConfirmTombstoneStaysEncryptedAfterArm14719` — ConfirmCommit
    end-to-end (arm encrypted, cover cleared, delete lands).
  - `TestMarkConfirmResolvedKeepsEncryption14719` — tombstone writer
    in isolation with the cover already cleared.
  - `TestConfirmArmRetryKeepsEncryption14719` — direct `WriteConfirm`
    of the stashed record (the `persistRetryLoop` retry write).
  - `TestConfirmRewriteAfterRestartKeepsEncryption14719` — fresh `DB`
    over the same directory (post-restart writer, cover never set)
    rewriting the record.
  - `TestConfirmFirstSentinelRewriteKeepsEncryption14719` — FIRST
    sentinel shape (deadline moved to the past sentinel).
  - `TestConfirmPlaintextWindowStaysPlaintextOnRewrite14719` —
    control: a never-encrypted window stays plaintext on rewrite
    (cover recovery must not invent encryption).

Deliberately NOT changed: `WriteConfirm`'s public signature; the
record schema (persisting the guarded profile inside the record would
strand pre-fix readers); PrevTree-wins precedence when both trees
declare; legacy plaintext readability + warn (not reject).

## Risk

- Residual (documented in code + README): a window armed encrypted
  whose on-disk record was deleted or replaced with plaintext before a
  later writer runs has no disk profile to recover and falls back to
  plaintext exactly as pre-fix. Production ordering (tombstone BEFORE
  delete; retry/rebind/sentinel all rewrite an existing record) makes
  this unreachable on the named paths.
- `existingConfirmDiskPRF` adds one prefix read (256 B) per
  `encodeConfirm` for plaintext windows, and a bounded read + envelope
  parse only when the marker is present. Commit/boot-paced only; no
  hot path.
- Encryption is sticky in one new direction: a record armed encrypted
  whose guarded master-password is later *removed* by a plain commit
  still tombstones encrypted. `ReadConfirm` opens it via the
  self-describing envelope + `master.key` (which is never deleted), so
  recovery is unaffected; the alternative (stripping to plaintext)
  would re-expose secrets.
