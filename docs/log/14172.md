# Issue #14172 — confirmed commit encryption tests the wrong tree (D8-05)

## Why

`confirmRecord` (pkg/configstore/db.go) serializes the whole record JSON —
Deadline, the `PrevTree` rollback target with every secret leaf it carries,
GuardedHash/PreviousHash, flags — but has NO field for the guarded (newly
committed) tree: the guarded tree reaches the record only as GuardedHash.

At origin/master (805ac16cd):

- `encodeConfirm` (db.go) sealed the record via
  `maybeEncryptTreeJSON(data, rec.PrevTree, nil)`; `crypto.go`
  `maybeEncryptTreeJSON` returns the JSON unchanged when
  `masterPasswordPRF(PrevTree) == ""`.
- So `commit confirmed` ADDING a master-password over a previous PLAINTEXT
  config wrote confirm.json — PrevTree secrets plus the record's own safety
  fields — in CLEARTEXT, while active.json from the same commit was AES-GCM
  encrypted. (The research report's literal "GuardedTree" field does not
  exist; the actual exposure is PrevTree's secrets + the record bytes, under
  the guarded commit's encryption expectation. Verified in the three-way
  research: codex/opus MATERIAL, spark NEEDS_VALIDATION on the warn design.)
- `ReadConfirm` (db.go) accepted the plaintext body after magic/version
  strip, enforcing structure/deadline/PrevTree only, and DISCARDED the
  `decrypted` flag from `maybeDecryptTreeJSON` — so a plaintext record was
  indistinguishable from a decrypted one, unlike readTreeMeta's #4579
  unexpected-plaintext warning. confirm.json was the unhardened sibling of
  the active-tree envelope (no guarded-tree opinion, no warn parity).

Access model (documented, not claimed as fixed): confirm.json is 0600 in
the 0700 `.configdb`; the AES-GCM key `master.key` sits in the SAME
directory with no TPM/HSM sealing (#6856). A whole-directory or root reader
can decrypt regardless; the cover defends the body-only reader (backup or
file-disclosure scoped to confirm.json). A keyless body-sha256 / MAC alone
is NOT a security fix (a writer who can rewrite the root-owned file can
recompute it); the encrypted form's integrity comes from AES-GCM. A global
ban on plaintext confirm records was deliberately rejected: it would strand
every pending window written before the cover across upgrade.

## What

- `pkg/configstore/crypto.go`: `confirmEncryptionCover{profile string}` +
  `confirmEncryptionPRF(prevTree, cover)` — PrevTree's own profile when it
  has one, else the guarded tree's cover profile, else plaintext.
  `encryptTreeJSON(data, prf, aad)` split out of `maybeEncryptTreeJSON` so
  the confirm path can seal under a two-tree-resolved profile without
  widening the tree-taking signature other callers share.
  `confirmNeedsEncryption(rec, guardedTree)` helpers the warn decision.
- `pkg/configstore/db.go`: `DB.writeConfirmCover` (empty on every
  non-arm path — tombstones, migration rewrites, retries, FIRST sentinel —
  so those records keep exactly the PrevTree profile they were armed with;
  the public `WriteConfirm` signature is unchanged for compat).
  `encodeConfirm` seals under `confirmEncryptionPRF(rec.PrevTree,
  db.writeConfirmCover)`. `ReadConfirm` retains `decrypted` and warns
  (#4579 parity, issue #14172) when a plaintext record's PrevTree declares
  a master-password; legacy plaintext records stay READABLE.
- `pkg/configstore/store_commit.go`: `commitConfirmedLocked` sets
  `writeConfirmCover = {masterPasswordPRF(committedTree)}` around the
  preflight/provisional/final confirm writes and clears it via defer,
  under s.mu like every other record write.
- `pkg/configstore/store_persist.go`: `recoverPendingConfirmLocked` adds
  the guarded-tree second opinion — warns when PrevTree is plaintext but
  the loaded active (guarded) tree declares a master-password — before
  the Resolved/stale handling, suppressed when PrevTree already warned so
  one record warns once per boot.
- `pkg/configstore/README.md`: new bullet documenting both-tree keying,
  warn parity, legacy readability, and why no unkeyed hash was added.
- Regression: `pkg/configstore/confirm_encryption_guarded_14172_test.go`:
  - `TestConfirmEncryptedWhenGuardedTreeAddsMasterPassword14172` — raw
    bytes: envelope present, secret absent, env.PRF == guarded PRF, and
    ReadConfirm round-trips the rollback target.
  - `TestCommitConfirmedEncryptsConfirmWhenAddingMasterPassword14172` —
    end-to-end Commit (plaintext base with IKE secret) → CommitConfirmed
    adding `system master-password`; active.json encrypted (control),
    confirm.json encrypted, secret absent.
  - `TestConfirmKeepsPrevProfileWhenBothTreesDeclareMasterPassword14172` —
    nested re-arm keeps PrevTree's profile (pre-fix readers still open it).
  - `TestReadConfirmWarnsOnPlaintextRecordWhosePrevDeclaresMasterPassword14172`
    — legacy plaintext record stays readable AND warns.
  - `TestRecoveryWarnsOnPlaintextRecordGuardedByMasterPasswordActive14172`
    — Load warns via the guarded tree and still re-arms the window.
  - `TestConfirmRecordWithoutCoverStaysPlaintextWhenNeitherTreeDeclares14172`
    — control: no encryption (and no master.key creation pressure) when
    neither tree declares.
  - `TestTamperedPlaintextConfirmIsContainedNotRolledBack14172` — a
    GuardedHash-nibble tamper is stale-dropped on Load, never rolled back.

## Risk

- When both trees declare: PrevTree profile wins (unchanged from base).
- Symmetric change the other way (guarded tree REMOVES a master-password
  while PrevTree had one): record stays sealed under PrevTree's profile;
  ReadConfirm opens it via the self-describing envelope + master.key, so
  recovery is unaffected. Removing the last master-password from BOTH
  trees keeps plaintext, as before.
- `writeConfirmCover` is DB-scoped mutable state set/cleared under s.mu
  (Store arm path); direct DB callers (tests, recovery rewrites) never
  set it. A future concurrent-DB-use change would need to revisit it —
  noted in the field comment.
- No hot paths: all changes are commit/boot-paced persistence code; no
  per-packet or compiled-dataplane code touched.
- Tolerant/strict doctrines: records remain fail-closed (unknown fields,
  degenerate shapes, tampered hashes still rejected/stale-dropped);
  plaintext legacy records are warn-not-reject by design (upgrade compat).
