# #14621 — session open/update encoder reserves 2 bytes but writes 10 (Y22-01)

- **Issue**: #14621 — `[Y22-01]` session open/update encoder reserves 2
  bytes after rule_id but writes 10; a 307–314 B (v6) / 367–374 B (v4)
  rule id panics the packet worker.
- **Branch**: `fix/14621-campaign`
- **Worktree**: `/var/worktrees/wt-14621`
- **Base**: `f96f14caf1` (current origin/master at lane start)

## Relationship to #14839 (already merged)

The production guard fix for this exact mechanism already landed as
#14839 (`f9b0268231`, PR #14845): `session_sync.rs` now reserves
`RULE_ID_TRAILER_BYTES = 1 + 1 + 8` and `session_open_rule_id_at_capacity_boundary_14839`
pins the exact-fit edge. Verified in this worktree: the guard at
`session_sync.rs:424-431` is the fixed form and the boundary test passes.

#14621's acceptance is broader than #14839's and was not covered by it:

- a sweep of L in 0..=600 for v4 **and** v6 that never panics (the
  boundary test checks only max-fit and max-fit+1..=10),
- every frame `len <= 512`,
- the trailer decodes in Go `decodeSessionEvent`,
- a mutation restoring `+ 2` turns the sweep red,
- the v4 leg executed (the original probe was v6-only; v4 was
  arithmetic).

This lane therefore adds the decisive sweep regression on both sides
of the wire and changes no production code. NOT changed: the encoder,
the frame capacity, the wire layout, and the Go decoder — all already
correct at base; a duplicate production edit would be churn.

## What

- `userspace-dp/src/event_stream/codec/codec_tests.rs`:
  `session_open_update_rule_id_len_sweep_never_panics_14621` sweeps
  rule_id lengths 0..=600 for v4 and v6 keys on both the OPEN and
  UPDATE encoders (both share `encode_session_record`). The rule_id
  prefix position and the longest-fitting length are derived from an
  empty-id frame of the same key shape (no hard-coded offsets). Each
  cell asserts: frame within 512 bytes, the carried length is the id
  verbatim up to the fit and the zero-length fallback past it, the id
  bytes are intact, and the 10-byte trailer (handshake 3, provenance
  static=2, PPTP pair) sits exactly where Go `decodeSessionEvent`
  reads it.
- `pkg/dataplane/userspace/eventstream_rule_id_len_14621_test.go`:
  `TestDecodeSessionEventRuleIDLenSweep14621` reconstructs the wire
  payload for every length 0..=600 (prefix offset derived from the
  decoder's own gated-field walk, cross-checked: v6 prefix at payload
  194, v4 at 134 — the report's numbers) and asserts
  `decodeSessionEvent` returns the id verbatim-or-empty plus the exact
  handshake/provenance/PPTP values.
  `TestDecodeSessionEventRuleIDPanicWindowFallsBack14621` pins the
  reported panic windows (v6 307..=314, v4 367..=374) to the
  zero-length fallback form with the trailer intact.

## Risk

None to production: test-only change. The sweep derives positions from
real frames, so a future trailer-layout change moves the derived fit
with it instead of silently testing stale offsets; the Go leg derives
its prefix offset from the decoder walk and cross-checks against the
report's 194/134, so a one-sided layout drift fails loudly.
