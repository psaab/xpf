## Token choice

`SessionEntry::install_epoch` (`session/mod.rs`, field of `SessionEntry`).

- It is the per-table counter `next_epoch()` (`session/mod.rs`
  `fn next_epoch`, pre-increment from 0) and is stamped by both and only
  the row constructors: the local install
  (`install_with_protocol_with_origin_and_source_nat_inner`) and
  `upsert_synced_with_origin` (UpsertSynced, UpsertLocal, sibling
  replication, coordinator replay, HA import, primary-liveness frames).
  Every same-key replacement (`RemovalKind::Replace`), a same-session-id
  identical re-import included, and every delete-then-reinstall mints a
  new, larger epoch. Monotonic per table, so no ABA.
- It is write-once per incarnation (#9856, pinned by
  `install_epoch_survives_update_session_9856` and
  `install_epoch_survives_refresh_for_ha_transition_9856`): no in-place
  writer touches it, the packet path included.
- Rejected: the session id (an identical or same-id re-import with a new
  installing-table stamp keeps it; `preserved_install_table_for` shows the
  same-id path applies a nonzero stamp as given), and a new per-row counter
  (unneeded: `install_epoch` already has both properties; bumping it from
  in-place writers is forbidden by #9856's export cursor, so no writer
  below needs it).
- 0 is never minted, so it is `PROBE_ANY_INCARNATION` (no check: entries
  built without the seed, i.e. deny entries, which never reach the probe,
  and tests). `u64::MAX` is `PROBE_NO_BACKING_ROW`, bound when the seed's
  key resolves no record.

Writers that rewrite a row's decision inputs without replacing it, and the
fence that covers each (no token bump anywhere):

|---|---|---|---|

| `demote_owner_rg` + `refresh_for_ha_transition` via DemoteOwnerRGS | origin (local -> SyncImport), resolution, owner RG | No | Same table kept; `rg_epochs` bump for demoted RGs; live HA verdict. | `promote_synced_with_origin` (`update_session`) | origin, owner RG if unset, fabric marker, decision | No | Runs on the packet's own slow path before its seed; the seed reads the (unchanged) epoch after it and carries the promoted decision. |
| `revalidate_forwarding_resolution_with_egress_zone` (forwarding revalidation persist; also from a reverse hit's #8356 pass) | resolution, owner RG, egress zone | No | Runs only for a row whose forwarding generation is stale, i.e. after a config/FIB generation change, which already fenced every older entry; within one generation it writes the same FIB answer the seed used. |
| `update_reverse_route_on_filter_hit` | reverse row's resolution and installing table | No | The reverse packet's own slow path, which re-seeds its slot; the cache entry is keyed by logical ingress, so another ingress's entry keeps its own filter's verdict. |
| `rebind_policy_pair`, `rebind_zones_pair` | policy id/counters, zones | No | Commit time (`adopt_rotated_forwarding`, before any packet under the new view): config-generation fence. |
| `rebind_forward_egress_zone` | egress zone | No | #8356 revalidation after a commit: config-generation fence. |
| Packet-path updates (probe, `lookup_with_origin`, TCP state, handshake relay, keepalive) | counters, timestamps, TCP state | No | Not decision inputs; must not bump (the no-spurious-miss cells, MY3). |

Since no writer needs a bump, there is no per-writer cell; the
no-spurious-miss cells cover the packet-path class.

## What the slow path does with the replacing row

The issue's premise was "the slow path would use the new row's egress". At
`ebb32e817b` that is not what happens on a direct (non-foreign) arrival: a
replacing row carries `filter_revalidated = UNVALIDATED`
(`upsert_synced_with_origin`), so its first slow-path hit runs
`revalidate_static_pbr_route_on_session_hit` (#7212/#10467), which
re-derives the installing table from this node's own ingress filter and
revokes a forward row whose stamp disagrees (`filter_revoked_sessions`).
Measured on the fix tree: the first segment after `UpsertSynced(B)` with
table T's stamp is evicted (`post_hit_session_replaced`), hits B on the
slow path and is revoked (`filter_revoked=1`, no forward). On master the
same segment is a cache hit out E1. So on this path the defect is a #7212
revocation bypass: the cache keeps forwarding a flow whose live row the
slow path would revoke. An accepted replacement cannot change the egress
here: A was accepted only if A's stamp was this node's choice, B only if
B's is, so the tables are equal. Foreign (fabric-zone) arrivals skip the
route revalidation, but they never seed the cache
(`flow_cache_install_failed = .. || foreign_arrival_zone.is_some()`).
(A test-seam attempt that marked B filter-fresh then hit the #8356 zone
policy revocation for E2; dropped rather than stack seams.)

### P3-1: carry the install epoch across an identical re-import

Verified first: primary liveness re-imports every live session on an
adaptive cadence "bounded to [1s, 10s]" (`pkg/cluster/sync.go:1483-1485`);
TUN `UpsertLocal` refreshes at 1 s (UDP) / 5 s (TCP)
(`tunnel.rs` `tun_origin_refresh_after_ns`).

**Rule.** `upsert_synced_with_origin_and_leak` (`session/install.rs`)
builds the replacing row with a placeholder epoch, then keeps the
replaced row's epoch when `replacement_keeps_incarnation` holds, else
mints. The local install path always mints. The compare runs once per
import, never on the hit path. Field classification
(`replacement_keeps_incarnation`, every `SessionEntry` and
`SessionMetadata` field named, no `..`):

| Compared | Why |
|---|---|
| identity: `same_install_incarnation(wire_session_id, stored id)` | both ids known and different = new incarnation; 0 names none (UpsertLocal, legacy peer). Single-sourced with `preserved_install_table_for` (#9752). |
| whole `SessionDecision` | resolution, NAT, installing-table stamp (the #19173 input) |
| every `SessionMetadata` field, `policy_counter` by `Arc::ptr_eq` | zones and vintage, ingress identity, NAT scope, NAT64 reverse, owner RG (seed stamp owner), fabric ingress, direction, alias origin, policy id/idx/counter, logging, idle timeout |
| `source_nat_static` | SNAT revalidation input |
| `origin` | TUN provenance, promotion, export filters |
| #9951 leak incarnation | resolver revocation input; the install now stamps it (`_and_leak`) so it can be compared |
| `fabric_established` | #16217 adoption input to the seed |

`upsert_synced_with_origin` is `_and_leak(.., 0)`.

**#9856 export cursor: no conflict.** Consumers of `install_epoch`:
`iter_export_budgeted` (`install_epoch > kick_epoch` = skip),
`take_tombstones_for_export` (`<= kick_epoch` = push), `current_epoch`
(the kick). The walk emits visit-time content; the epoch only means
"existed at the kick". `remove_entry(.., Replace)` logs no tombstone, and
the slab hands the replacement the slot `remove_entry` just freed
(LIFO vacancy), so a carried row sits in the same slot with the same
epoch: to the walk and the tombstone filter it is the never-replaced row.
Carrying can only keep in the export a row that existed at the kick
(a minting replacement drops it if the walk has not reached it yet),
never hides a change (a changed row never carries; the walk does not
diff), never skips one. A carry does not move `current_epoch`. Pinned by
`identical_reimport_keeps_the_epoch_and_the_slot_19173` (same epoch, same
slab handle, counter unmoved over five liveness re-imports).

**Session-id rule: no conflict.** The carry requires the #9752 identity
rule; a new nonzero wire id always mints (table row "identity").

**Split-RG does not carry, by the field list.** A per-field diff of the
row (temporary diagnostic, not committed) shows the only compared
difference is the decision's resolution: the first slow-path packet of a
redirected flow persists the HA-derived `FabricRedirect` (egress = fabric
parent 4, fabric peer MAC, VLAN 0) into the SyncImport row through the
#12265 Owner-persist (`apply_deferred_forwarding_revalidation`, the
replacement having reset `forwarding_generation`), and every liveness
re-import writes back the handler's raw local `ForwardCandidate`
(egress 14, VLAN 80, the WAN neighbor). So the re-import is not identical
to the row the entry was seeded from, the compare mints, and each
redirected flow still pays one slow-path packet per liveness interval.

The resolution cannot simply be dropped from the compare:
`reresolve_stored_session` reads the stored resolution (a stored
`FabricRedirect` takes the rehome-or-retain branch, #15958b/#16524; a
stored `ForwardCandidate` does not), so the new row's re-derivation can
differ from the cached decision. Design options, for the lead:

- (A) an otherwise-identical re-import keeps the replaced row's resolution
  and `forwarding_generation` when that resolution is fresh in the current
  forwarding generation (the slow path's own derivation from the same FIB),
  and carries the epoch: the resend becomes a forwarding no-op. It changes
  what an import writes (the handler's re-resolve no longer overwrites a
  fresh local derivation), which is HA semantics and wants its own review.
  Prototype (lane `c3-19173-proto`, not committed): split_rg 0 per
  round, upsert_local 0. It reds five fold cells that pin "a
  resolution-only change mints" (the session-level tables run with a
  default forwarding generation, which the prototype read as fresh; a real
  rule would treat the default stamp as never validated), which is the
  semantic change, not a bug in them.
  **Implemented in #19191** (branch `fix/19191-resolution-carry`, stacked on
  this one): the carry requires the handler's stated HA judgment of the
  import to reproduce the row's redirect exactly, and the row's stamp to be
  valid and current, so a default stamp never carries. The five cells above
  stay green UNCHANGED on that branch; the per-cell dispositions, the
  condition and the HA-safety trace are in `docs/log/19191.md`.
- (B) keep the strict rule (this commit): redirected flows on a split-RG
  non-owner re-seed once per liveness interval, now visible as
  `xpf_userspace_flow_cache_replaced_evictions_total`.

TUN-origin rows: the forward leg of a TUN-originated flow is transmitted
from the tunnel thread (`tunnel.rs` `enqueue_tx` of
`build_local_origin_tunnel_tx_request`'s plan), never through the RX poll,
and the reverse leg is `LocalDelivery`, which `is_cacheable` refuses. So
no production TUN row backs a cache entry and the UpsertLocal cadence costs
no cache miss on any tree; the `upsert_local` shape measures the
mechanism (zero wire id) on cache-backed rows.
