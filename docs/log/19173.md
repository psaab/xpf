## Token choice

`SessionEntry::install_epoch` (`session/mod.rs`, field of `SessionEntry`).

- It is the per-table counter `next_epoch()` (`session/mod.rs`
  `fn next_epoch`, pre-increment from 0) and is stamped by both and only
  the row constructors: the local install
  (`install_with_protocol_with_origin_and_source_nat_inner`) and
  `upsert_synced_with_origin` (UpsertSynced, UpsertLocal, sibling
  replication, coordinator replay, HA import, primary-liveness frames).
  Every same-key replacement (`RemovalKind::Replace`), a same-session-id
  identical re-import included, and every delete-then-reinstall mints a
  new, larger epoch. Monotonic per table, so no ABA.
- It is write-once per incarnation (#9856, pinned by
  `install_epoch_survives_update_session_9856` and
  `install_epoch_survives_refresh_for_ha_transition_9856`): no in-place
  writer touches it, the packet path included.
- Rejected: the session id (an identical or same-id re-import with a new
  installing-table stamp keeps it; `preserved_install_table_for` shows the
  same-id path applies a nonzero stamp as given), and a new per-row counter
  (unneeded: `install_epoch` already has both properties; bumping it from
  in-place writers is forbidden by #9856's export cursor, so no writer
  below needs it).
- 0 is never minted, so it is `PROBE_ANY_INCARNATION` (no check: entries
  built without the seed, i.e. deny entries, which never reach the probe,
  and tests). `u64::MAX` is `PROBE_NO_BACKING_ROW`, bound when the seed's
  key resolves no record.

## In-place writers

Writers that rewrite a row's decision inputs without replacing it, and the
fence that covers each (no token bump anywhere):

| Writer | What it rewrites | Bump? | Fence |
|---|---|---|---|
| `refresh_for_ha_transition` via RefreshOwnerRGS | resolution (FIB + HA re-resolve in the row's own table), owner RG, liveness | No | Keeps the installing table (`..decision` in `collect_refresh_owner_rgs_items`). `rg_epochs` bump for every activated RG plus `rg_epochs[0]` (`ha/state.rs`), and the per-hit live HA verdict for entries whose stamp owner did not move. |
| `demote_owner_rg` + `refresh_for_ha_transition` via DemoteOwnerRGS | origin (local -> SyncImport), resolution, owner RG | No | Same table kept; `rg_epochs` bump for demoted RGs; live HA verdict. The origin flip makes the row yield to the peer, and the peer's later import is a Replace, which this fix covers. |
| `promote_synced_with_origin` (`update_session`) | origin, owner RG if unset, fabric marker, decision | No | Runs on the packet's own slow path before its seed; the seed reads the (unchanged) epoch after it and carries the promoted decision. |
| `revalidate_forwarding_resolution_with_egress_zone` (forwarding revalidation persist; also from a reverse hit's #8356 pass) | resolution, owner RG, egress zone | No | Runs only for a row whose forwarding generation is stale, i.e. after a config/FIB generation change, which already fenced every older entry; within one generation it writes the same FIB answer the seed used. |
| `update_reverse_route_on_filter_hit` | reverse row's resolution and installing table | No | The reverse packet's own slow path, which re-seeds its slot; the cache entry is keyed by logical ingress, so another ingress's entry keeps its own filter's verdict. |
| `rebind_policy_pair`, `rebind_zones_pair` | policy id/counters, zones | No | Commit time (`adopt_rotated_forwarding`, before any packet under the new view): config-generation fence. |
| `rebind_forward_egress_zone` | egress zone | No | #8356 revalidation after a commit: config-generation fence. |
| Packet-path updates (probe, `lookup_with_origin`, TCP state, handshake relay, keepalive) | counters, timestamps, TCP state | No | Not decision inputs; must not bump (the no-spurious-miss cells, MY3). |

Since no writer needs a bump, there is no per-writer cell; the
no-spurious-miss cells cover the packet-path class.

## What the slow path does with the replacing row

The issue's premise was "the slow path would use the new row's egress". At
`ebb32e817b` that is not what happens on a direct (non-foreign) arrival: a
replacing row carries `filter_revalidated = UNVALIDATED`
(`upsert_synced_with_origin`), so its first slow-path hit runs
`revalidate_static_pbr_route_on_session_hit` (#7212/#10467), which
re-derives the installing table from this node's own ingress filter and
revokes a forward row whose stamp disagrees (`filter_revoked_sessions`).
Measured on the fix tree: the first segment after `UpsertSynced(B)` with
table T's stamp is evicted (`post_hit_session_replaced`), hits B on the
slow path and is revoked (`filter_revoked=1`, no forward). On master the
same segment is a cache hit out E1. So on this path the defect is a #7212
revocation bypass: the cache keeps forwarding a flow whose live row the
slow path would revoke. An accepted replacement cannot change the egress
here: A was accepted only if A's stamp was this node's choice, B only if
B's is, so the tables are equal. Foreign (fabric-zone) arrivals skip the
route revalidation, but they never seed the cache
(`flow_cache_install_failed = .. || foreign_arrival_zone.is_some()`).
(A test-seam attempt that marked B filter-fresh then hit the #8356 zone
policy revocation for E2; dropped rather than stack seams.)

  and its cells, so a debug build or a test can still split them.
