# 14985 — config confirm required a held lock (D36-05)

## Summary

`POST /api/v1/config/confirm` (and the gRPC `ConfirmCommit`, and the
bare-commit confirm intercept on both surfaces) called
`Store.ConfirmCommitAs(sessionID)`, which gates on
`ensureHolderLocked`. That helper has two deliberate bypasses that are
correct for candidate mutators but fail-open for confirm:

- `!s.configDir` short-circuits to nil, and
- a lock with no recorded holder passes any session.

A pending commit-confirmed window **survives** `ExitConfigure` /
`ExitConfigureSession` (neither clears `confirmTimer`), and leaving
config mode is the routine post-`commit confirmed` state. So after the
owner exited, `configDir == false`, the gate short-circuited, and any
well-formed REST session token (or gRPC connection session) that never
held the lock could confirm the window — cancelling the auto-rollback
and making an unconfirmed, possibly management-stranding config
permanent.

Two sub-claims in the original D36-05 report were excluded as binding
scope narrowing, and remain excluded:

- **Commit lock-turnover TOCTOU** — stale at master: `AuthorizeCommitAs`
  mints a holder-epoch-bound `CommitAuthority` under one lock
  acquisition (#6808) and promotion re-verifies it.
- **Regex-restricted operator confirmation bypass** — `confirm` carries
  no config path, so there is nothing for the `*-configuration` regexes
  to adjudicate (`restConfigRoutesUngated`); the holder requirement is
  the control.

## Fix

One check in `Store.ConfirmCommitAs`
(`pkg/configstore/store_commit.go`), after the existing
`ensureHolderLocked` call:

```go
if sessionID != "" && s.confirmTimer != nil && s.effectiveHolderLocked() != sessionID {
    return fmt.Errorf("%w", ErrConfigLockedByOther)
}
```

Properties:

- Atomic under the same `s.mu` acquisition — no new TOCTOU window.
- Gated on a pending window: with nothing pending, the call still
  returns the existing `no pending confirmed commit` error for holder
  and non-holder alike (nothing to protect, no behaviour delta).
- The internal (`""`) caller keeps its bypass: in-process CLI
  `ConfirmCommit()` and confirm-on-sync are untouched.
- The holder confirming while still holding the lock is untouched
  (`effectiveHolderLocked() == sessionID` passes, as before).
- REST maps `ErrConfigLockedByOther` to 409 via the existing
  `writeConfigMutationError`; gRPC maps it to `PermissionDenied`.

NOT changed: `ensureHolderLocked` itself (its bypasses remain correct
for candidate mutators — once config mode is exited there is no
candidate to protect), the commit/commit-confirmed authority path
(#6808, already sound), and every other `*As` mutator.

Deliberate residual: after the holder exits, **nobody** can confirm the
window until someone re-enters config mode — at which point the new
holder (who owns the candidate and can inspect/confirm it) may confirm.
That is the fail-closed direction the issue requires; the alternative
(any authenticated session may confirm a window it cannot inspect) is
the defect. The window's own rollback timer still fires on schedule if
nobody confirms, which is the safe default.

`TestRESTConfigConfirmRequiresHeldLock_14985`, three cells, all driving

## Risk

Only the confirm path narrows: a non-holder session-scoped confirm of a
pending window now fails closed (409 / PermissionDenied) instead of
succeeding. Legitimate holder confirms, internal confirms, and the
no-pending-window error are byte-identical to before.
