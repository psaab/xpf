# #12146 — pin authPriv response engineTime

- **Timestamp**: 2026-10-07
- **Action**: Capture one authoritative engineTime for each response build and reuse it to form the AES privacy IV and stamp the USM response parameters.
- **Base**: `1c384b9a47ff7d6e567fa50632faa75c3995ae87`
- **Files**:
  - `pkg/snmp/agent.go` — deterministic engineTime clock seam
  - `pkg/snmp/v3.go` — pass the captured response time into `encryptPDU` and reuse it for USM parameters
  - `pkg/snmp/des_salt_boots_5544_test.go`, `pkg/snmp/v3_priv_salt_5032_test.go` — update direct `encryptPDU` test callers
  - `pkg/snmp/v3_resp_time_12146_test.go` — stepped-clock response round-trip regression test
  - `docs/log/12146.md`

## Why

`buildV3Response` encrypted an authPriv response before constructing its USM header. The AES-CFB IV was built with an `engineTime()` read inside `encryptPDU`, then `buildV3Response` independently read engineTime again for `msgAuthoritativeEngineTime`. If the clock crossed a one-second boundary between those reads, a manager rebuilding the RFC 3826 IV from the time carried on the wire got a different IV and could not decrypt the response.

## What

`buildV3Response` now captures `responseEngineTime` once and supplies it to `encryptPDU`; the AES IV and USM parameters use that same value. The stepped-clock regression drives the real authPriv response builder and decrypts the response using only the carried boots/time and salt, as a manager does. A steady-clock round-trip check is retained alongside it. DES encryption continues to ignore engineTime for its IV.

- **GREEN after fix**: `go test ./pkg/snmp -run '^TestResponseAESIV(MatchesCarriedTime|SteadyClock)12146$' -count=1 -v` passed both tests.

## Risk

The AES response IV now matches the time the receiver receives, removing the rare one-second-boundary response loss. DES IV construction and request decryption/timeliness paths are unchanged. No push or PR was created.
