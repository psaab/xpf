# Issue #15676 — HA standby synced persistent-NAT permission recording hashes rule zones instead of resolved flow zones

- **Issue:** psaab/xpf#15676 (V7-04). `reserve_synced_on_first_pool_owner` in
  `userspace-dp/src/nat/source/synced.rs` computed the persistent-NAT grant
  scope from the rule's authored `(from_zone, to_zone)`, while the active
  node mints under the flow's resolved zone pair. For a non-zone-scoped
  rule-set (interface-, routing-instance- or global-scoped; empty authored
  zones) the standby folded `("","")` and the active folded e.g.
  `("trust","wan")` — different grant buckets on the shared lease, so the
  promoted node's inbound persistent-NAT lookup missed the synced grant
  and denied post-failover inbound the active had permitted.

## Fix

- `reserve_synced_on_first_pool_owner` takes a new
  `synced_zones: SyncedNatZones<'_>` parameter (the type already threaded
  into its caller). Both call sites pass it: PASS 1 passes
  `Some((from_zone, to_zone))` from its existing resolved pair; PASS 2
  passes the caller's `synced_zones` verbatim (`None` for an old peer /
  config drift).
- The grant scope now prefers the resolved pair:
  `persistent_rule_scope(eff_from, eff_to, …)` where the effective pair is
  the synced resolved pair when both components are non-empty, otherwise
  the rule's authored pair. `persistent_rule_scope` already replaces empty
  authored zones with the packet pair, so a zone-scoped rule is unchanged
  (authored == resolved), an interface/RI/global rule now folds the
  resolved zones exactly as the active's mint in `match_rules.rs` does,
  and the `synced_zones == None` fallback is byte-identical to the
  pre-fix behaviour. Both the port-bearing and address-only arms share
  the single `flow_egress_scope` computed at the top of the loop, so both
  are fixed by the one site.
- No wire change, no lease-identity change, no new scope encoding: the
  resolved pair already rides the session-sync wire and is already
  resolved by `synced_source_nat_zone_pair` for rule selection (#6211).

## RED -> GREEN proof

- New regression module `userspace-dp/src/nat/tests_synced_persistent_zones_15676.rs`
  (5 cells), driving the real synced-reserve path
  (`reserve_synced_source_nat_allocation`, the call `handle_upsert_synced`
  makes) and probing the promoted node's inbound lookup exactly as
  production admission spells it (`persistent_inbound_lookup_for_rule`
  with packet pair ("trust","wan")):
  - `synced_iface_scoped_persistent_grant_survives_failover_15676` — THE
    cell: interface-scoped rule, port-bearing arm. RED pre-fix (standby
    grant in the `("","")` bucket, lookup Miss/Denied), GREEN post-fix.
  - `synced_address_only_persistent_grant_survives_failover_15676` —
    address-only arm (`rewrite_src_port == None`), same assertion.
  - `synced_global_persistent_grant_survives_failover_15676` — fully
    unscoped (global) rule-set variant.
  - `synced_zone_scoped_persistent_grant_still_survives_15676` — control:
    zone-scoped rules passed pre-fix and must keep passing.
  - `synced_without_resolved_zones_still_reserves_15676` — PASS 2
    fallback guard: `synced_zones == None` still rebuilds the lease and
    holds the reservation (availability unchanged for old peers / drift).
  - The interface-scoped cell also asserts an arbitrary ungranted remote
    is never Permitted (fail-closed guard — the fix moves a bucket, it
    does not widen admission).

## Risk

- Fail-closed only: a grant that previously landed in a bucket no lookup
  consulted now lands in the bucket the active used; no admission widens
  (the arbitrary-remote assertion pins this). Zone-scoped rules and the
  `synced_zones == None` fallback are byte-identical to before, so
  rolling-upgrade / old-peer behaviour is unchanged.
