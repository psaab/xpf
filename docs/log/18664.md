# #18664: operational `show configuration | display set` refused by the #16798 gate

- **Timestamp**: 2026-10-31
  - **Action**: Reproduced the user report on tcp fw0 with the deployed
    `cli` (`show configuration | display set` -> `error: unknown show
    configuration command: |`, exit 1). Ran a census of remote
    `dispatch` on origin/master `eb1a0c052c` with a recording fake
    client. Every `show configuration | <modifier>` was refused before
    the handler: `display set|json|xml|inheritance`, the chained
    `| display set | match x`, and `run show configuration | display
    set`. Output filters alone (`| match`, `| count`) worked, because
    `dispatch` peels them with `cliterm.SplitPipe` first. The local
    console (`pkg/cli`) is not affected: it never got the #16798 gate,
    and the same line renders there.
  - **Root cause (confirmed)**: `dispatchOperational` ran
    `cmdtree.ValidateOperationalLine(parts)` over the whole line.
    `show configuration` is a keyword-only node, so the bare `|` was
    judged as an unknown trailing keyword under it. This is the #9628
    defect class (the pipe is not tree grammar) recurring in the #16798
    gate. The pre-existing #13202 cells call `handleShow` directly,
    below the gate, so they stayed green.
  - **File(s)**: issue filed (no files).

- **Timestamp**: 2026-10-31
  - **Action**: Made the gate pipe-aware. It moved into
    `validateOperationalLine` (`cmd/cli/operational_gate.go`) and now
    validates only the words before the first bare `|`. It finds that
    word with the new `showPipeIndex`, which `splitShowPipe` now also
    uses, so the gate and the handlers share one token rule. To keep
    #16798's protection, a pipe directly under a keyword-only node is
    located by asking `ValidateOperationalLine` about the words up to
    and including the `|`. Such a pipe is admitted only for an
    `operationalPipeConsumers` command (`show configuration`). Every
    other keyword-only node still refuses, as it already did on master
    (exit 1, `unknown <path> command: |`); only the message changes,
    and it now names the modifier. `parseShowDisplay` now names an unknown pipe verb, in the
    console's wording. A `|` glued to a word stays a word, as on every
    other surface, and is refused with a hint showing the spaced form.

- **Timestamp**: 2026-11-01
  - **Action**: Folded the PR #18665 review (seat T clean, seat U minor).
    - The `operationalPipeConsumers` comment no longer claims the
      `show configuration` handler parses `| compare`. It does not.
    - Operational `show configuration [<path>] | compare [rollback <N>]`
      now refuses with ``syntax error: `| compare` is not supported on
      operational `show configuration`; use configuration mode
      (`configure`, then `show | compare [rollback <N>]`)``, instead of
      `unknown pipe command "compare"`. Junos supports the operational
      form, so "unknown" misled.
    - **Prior-behaviour claim corrected.** The copies in the gate
      comment, the test comment, `cmd/cli/README.md`, the PR body and
      the original commit message said such a handler "would print help
      ... exiting 0". That is true only of what would happen if the gate
      ADMITTED the pipe. Read next to "now refuse", it implied the lines
      were not refused before. On the remote CLI at master, a pipe after
      any other keyword-only command was ALREADY refused, exit 1, as
      `unknown <path> command: |`. #18665 keeps that refusal and changes
      only the message. `debian/changelog`, this log and
      `docs/junos-cli-reference.md` now say so explicitly. Printing help
      and returning nil is the LOCAL console's behaviour (#18668).
