# NAT64 deterministic geometry change kept stale allocator and exempted sessions (#15178, C06-01)

## Why

`Nat64State::reuse_allocator` keyed allocator reuse on
`(prefix_bytes, pool_v4)` only, and
`source_nat_translation_still_valid` returned valid unconditionally for
`nat.nat64`. After a `block-size`, host-base, `/32`<->`/64`, or
round-robin<->deterministic edit on a pool a NAT64 rule-set references,
the old allocator — with its deterministic BIB leases minted under the
old geometry — was reused, and established NAT64 sessions were never
revalidated. The stateless reverse map (applied generation) then assigns
the live tuple to a different subscriber, and a same-socket new-remote
flow from the original subscriber joins the stale lease and is refused
`AllocatorExhausted` instead of minting in its new block. That breaks
the deterministic-CGN compliance property (an operator reverse query
names an innocent subscriber for live traffic) for as long as the stale
flows plus the 300 s BIB idle period last.

## What

- `userspace-dp/src/nat64.rs`:
  - `nat64_rule_identity` and `reuse_allocator` now include the derived
    `deterministic_v6: Option<DeterministicV6>` (mode, block_size,
    blocks_per_ip, host_prefix_len, host_base, and the pool-derived
    host_count) in the reuse key. Any geometry/mode change on an
    unchanged pool is a reuse miss; a no-op re-apply derives identical
    params and still reuses, preserving the allocator and EIM.
  - The #6765 retained-address reseed is skipped when either side of
    the change is deterministic: `reseed_retained_from` carries live
    flows lease-less (deterministic leases are excluded there), which
    would re-create the stale-tuple hazard under the new identity.
    Deterministic prefixes start fresh; session-hit revalidation tears
    the old sessions down.
  - New read-only `Nat64State::nat64_source_translation_still_valid`:
    deterministic prefixes validate through
    `PortAllocator::deterministic_v6_tuple_matches` (the predicate the
    synced reserve / idle-lease import already use); round-robin
    prefixes validate by pool membership + the fixed NAT64 port range.
    Missing port / unknown pool address / no matching prefix fails
    closed.
- `userspace-dp/src/afxdp/poll_descriptor/policy_revalidation.rs`:
  `source_nat_translation_still_valid` no longer exempts `nat64`. It
  validates the stored source tuple against the live
  `forwarding.nat64` state (conjoined with the destination verdict,
  which stays `true` for the prefix-driven destination side) and
  returns `StaleSourceNat` revocation for a tuple outside its
  subscriber's current block, so the pair teardown releases the stale
  reservation exactly once and the next packet re-mints under the new
  geometry.

NOT changed: the destination-side NAT64 exemption (Pref64-driven, no
rule table to withdraw), round-robin allocation behaviour, the synced
reserve / HA import predicates, or any Go/wire field — the snapshot
already carries every deterministic parameter.

## Risk

Established deterministic NAT64 sessions whose tuple falls outside the
new geometry are now torn down on their first post-commit hit (one
packet takes the revocation path; the next re-mints in the new block) —
this is the acceptance behaviour, and it replaces silently forwarding
under a reverse map that names another subscriber. Round-robin NAT64
and no-op re-applies are behaviour-identical. Sessions on prefixes
sharing a pool address under different Pref64s (tolerated loads only; a
strict commit rejects the overlap) must validate under every prefix
holding the translated address, so a cross-prefix tuple is revoked
fail-closed.
