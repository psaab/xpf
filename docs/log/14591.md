# Issue #14591 — responder-only PSK VPN accepts another VPN's PSK by claimed identity (Y09-04)

- **Timestamp**: 2026-10-16
  - **Action**: Scoped the fix. A responder-only (`dynamic`, `remote_addrs =
    %any`) PSK VPN whose gateway has no `remote-identity` renders a secret
    with no `id` selector, so strongSwan key selection by the claimed IDi
    lets a holder of another site's PSK authenticate into it. Render belt
    (`pkg/ipsec/policy.go`): such a VPN is now skipped by name (same
    fail-closed class as #14139's missing secret; Apply unloads it and
    tears down stale SAs). Commit gate: new
    `validateIPsecResponderIdentityStrict`
    (`pkg/config/compiler_validate_strict_ipsec_responder_identity_14591.go`)
    wired into `runUniformGatesIPsecEvent` with
    `lenientIPsecResponderIdentity` — strict commit hard-rejects, tolerant
    load/peer-sync warns and the render belt keeps the connection from
    loading. Pubkey VPNs are unaffected (auth determination mirrors
    #14139's `ipsecVPNAuthNeedsPSK`). With a configured remote-identity
    the existing render already emits `remote { id = ... }` and scopes the
    secret to it (#3952); the new regression pins both directions of
    credential isolation. Updated `pskIDSelectors` doc, `pkg/ipsec/README.md`,
    and `docs/config-schema.md`; migrated the pre-existing responder-only
    fixtures that encoded the vulnerable shape to carry a remote-identity
    (`TestGenerateConfig_ResponderOnlyGateway`,
    `TestGenerateConfig_PSKIDSelectors_ResponderWithIDAndCert` renamed from
    `...ResponderAnyAndCert`, `TestSwanctlAddrLegitPreserved_6469`,
    `TestChangedResponderOnlyVPNIsNotReinitiated14140`,
    `TestIPsecResponderOnlyGatewaySetSyntax`).
  - **File(s)**: pkg/ipsec/policy.go,
