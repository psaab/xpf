# #15076 - GetBGPStatus/GetNATRuleStats charged one fixed command whatever the request selects (A41-01)

- **Timestamp**: 2026-10-18
- **Action**: `methodCanonicalCommand` charged `GetBGPStatus` as
  `show bgp summary` and `GetNATRuleStats` as
  `show security nat source rule` for every request. The remote cli sends
  `GetNATRuleStats{nat_type:"destination"}` for
  `show security nat destination rule|rule-set|summary` and
  `GetBGPStatus{type:"neighbor:IP"|"advertised-routes:IP"|"received-routes:IP"|"routes"|…}`
  for the corresponding `show protocols bgp …` lines, so path-scoped
  `allow-commands`/`deny-commands` failed open for those reads (a
  source/summary-only allow admitted them) and over-denied the other way
  (a summary deny hit every BGP read). REST had the same fixed charges:
  `GET /api/v1/routing/bgp` as the summary command whatever `?type=`, and
  `GET /api/v1/security/nat/rules` as the source command. Because the
  fixed strings were the only ones in the advertised command sets, the
  commit-time advisory also stayed silent about destination/neighbor
  denies. Both RPCs are now request-decoded in `rpcCanonicalCommand`:
  `bgpStatusCanonicalCommand` charges
  `show protocols bgp summary|routes|neighbor|neighbor advertised-routes|neighbor received-routes`
  (neighbor IP validated and dropped as an argument value; `""` is the
  handler's summary default), `natRuleStatsCanonicalCommand` charges
  `show security nat source|destination rule` by `nat_type`, and any
  unknown selector — including BGP `groups`, which has no cmdtree
  command, and a malformed `neighbor:` IP — resolves to no command and
  denies for a restricted class. REST mirrors this: `/routing/bgp` and
  `/security/nat/rules` moved from `restRouteCommand` to
  request-decoded entries in `restRoutesNoCommand` resolved by
  `?type=` (and `?nat_type=` for NAT), with unknown selectors denying.
  Both surfaces' advertised command sets now include the new charges so
  the #8189/#9340 advisory can fire on them. NOT changed: handler
  behaviour (unknown BGP/NAT selectors still reach the handler's own
  rejection/default for unrestricted classes), the `show bgp` alias
  spelling (charges use the `show protocols bgp` canonical form the
  issue names), the destination-summary line's sharing of the
  destination-rule RPC, or any coarse permission.

- **Validation**: RED on master (`d6b6b2123b`): gRPC cells showed all 13
  selector cases admitted under a source/summary-only allow, the
  destination/neighbor denies bypassed, unknown selectors resolving to
  the fixed charge, and the advertised set missing all five new
  commands; REST cells showed `?type=routes`, `?type=bogus` and
  `?type=destination` admitted under the same allow and both denies
  bypassed. GREEN after fix: `go test ./pkg/grpcapi/ -run
  'TestBGPAndNAT|TestEveryMapped|TestEveryPriced'` and
  `go test ./pkg/api/ -run
  'TestBGPRoutesAndNAT|TestEveryRESTRoute|TestRESTAndGRPC|TestSystemInfoCharges|TestSixNoCommand|TestNoCommandExempt|TestHeadRequest|TestDeniedCommandIsRefused'`
  pass, including the keyword-prefix census over every cli call site and
  the source/summary controls. Full package suites and `go vet`/`gofmt`
  are the parent's gate.
- **Risk**: A restricted class that relied (unknowingly) on the old
  fixed charge — e.g. an allow of only `show bgp summary` that
  incidentally admitted BGP neighbor reads over the remote cli — now
  needs the neighbor/routes commands in its allow, and a `groups`
  selection denies outright for restricted classes (it has no operator
  command). That is the intended fail-closed correction; unrestricted
  classes are unaffected.
