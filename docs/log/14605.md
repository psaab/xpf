# #14605 — RA default-lifetime below max-advertisement-interval accepted

- **Timestamp**: 2026-10-16
- **Action**: Reject `0 < default-lifetime < effective max` (and `> 9000`)
  at strict commit; derive the unset Router Lifetime as
  `min(3 * effective max, 9000)`; floor inherited RDNSS/PREF64 at that
  derived value.
- **Files**: `pkg/config/schema_routing.go`,
  `pkg/config/types_routing.go`, `pkg/configstore/store.go`,
  `pkg/configstore/ra_lifetime_14605_test.go`, `pkg/ra/sender.go`,
  `pkg/ra/ra.go`, `pkg/ra/sender_lifetime_14605_test.go`,
  `pkg/ra/sender_lifetime_12134_test.go`, `pkg/cli/cli_show_routing.go`,
  `pkg/ra/README.md`, `docs/embedded-radvd.md`, `docs/log/14605.md`

## Why

RFC 4861 §6.2.1 requires AdvDefaultLifetime to be zero or in
`[MaxRtrAdvInterval, 9000]`, defaulting to `3 * MaxRtrAdvInterval`.
`crossCheckRAIntervals` checked only `min <= 0.75 * max` (#4525), the
per-leaf schema allowed `default-lifetime` up to the 16-bit wire ceiling
(65535), and the sender used a fixed 1800s for every unset lifetime.
An explicit `default-lifetime 10` with `max-advertisement-interval 600`
therefore committed and advertised `RouterLifetime=10s` while RAs could
be 600s apart — hosts lost their default route (and, via inheritance,
RDNSS/PREF64) seconds after each RA. With `max 1800` and no lifetime
leaf, the fixed 1800s default equalled a single interval, leaving no
loss tolerance.

## What

- `crossCheckRAIntervals` (strict commit / `commit check` / `CheckText`,
  and the #9619 peer pipeline via the same function) now also rejects an
  explicit positive `default-lifetime` below the effective max (configured
  max, or 600s when unset) or above 9000, naming RFC 4861 §6.2.1. The
  tolerant Load/SyncApply path keeps the #1960 warn-not-reject doctrine.
- New `config` helpers on `RAInterfaceConfig`:
  `EffectiveMaxAdvInterval`, `DefaultRouterLifetime`
  (`min(3*max, 9000)`), and `EffectiveRouterLifetime` (explicit verbatim,
  else derived). Constants `RADefaultLifetimeMaxSeconds=9000` and
  `RADefaultMaxAdvIntervalSeconds=600` live beside
  `RARouterMaxLifetimeSeconds`.
- `buildRA` uses `EffectiveRouterLifetime`; inherited RDNSS/PREF64 use
  `max(router lifetime, DefaultRouterLifetime())`, so explicit 0 and
  short tolerant-ingress lifetimes keep DNS/NAT64 at `>= 3*max`
  (RFC 8106 §5.1). Manager `Status()` and `show` use the same helper.
- NOT changed: the per-leaf `default-lifetime` wire bound (0..65535)
  and `clampRAHeaderSeconds`; explicit PREF64 lifetimes keep their own
  RFC 8781 handling; the Router Lifetime itself is never raised above
  an explicit value (strict commit is the gate for that).

## Risk

- A previously-committable `default-lifetime` in `(0, max)` or
  `(9000, 65535]` now fails strict commit; such configs still load via
  the tolerant path with a warning, and their RDNSS/PREF64 no longer
  flap (floored at `3*max`) while the short Router Lifetime is honored
  verbatim until the operator fixes the config.
- Interfaces with `max-advertisement-interval > 600` and no
  `default-lifetime` now advertise a longer Router Lifetime
  (`3*max`, e.g. 5400s at max 1800) — the RFC default; `show` and
  sender Status report the same derived value.
