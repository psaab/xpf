# Issue #16270 — FIB republication ordering: connected row vs cluster-terminal

## Finding

Post-activation republication of connected RG prefixes was ASYNC
and duplicate-skippable (`daemon_route_listener.go`
`scheduleConnectedRGRepublish`: nonblocking goroutine, applySem,
routes-only publisher, duplicate-skip). Connection publication
itself is primary-gated (`routes.go:344` skips
`ConnectedRGPeerOwned` rows; `forwarding_build/interfaces.rs:1200`
suppresses peer-owned connected transit). There was NO ordering
between "RG reports forwarding-active" (`SetRGActive` in
`handleClusterEvent` / VRRP MASTER) and "the helper FIB holds the
republished /24 transit row". An arriving retransmit in that window
reached the pref-200 cluster-terminal, HA enforcement demoted it to
`DiscardRoute`, and the flow blackholed (FZFixSeed round-2 evidence:
slow path oscillating `ClusterTerminalHAInactive` / demoted
`DiscardRoute`, 9 ForwardCandidate resolutions in 1255).

## Choice: (a) + (b); (c) rejected

- **(a) Synchronous republication in the activation sequence**
  (primary). `republishConnectedRG` is now a synchronous helper
  (same routes-only publisher + FIB bump as the async path);
  `republishConnectedRGSync` runs it under `applySem` BEFORE
  `SetRGActive` on both activation paths (cluster-primary event in
  `handleClusterEvent`, VRRP MASTER in the VRRP watcher). Once the
  RG reports forwarding-active, the helper FIB already holds the
  /24 row — the ordering window is closed by construction, not by
  timing. The async `scheduleConnectedRGRepublish` remains as the
  retry/duplicate-skip backstop for every other edge. Fail-closed:
  a sync republish failure logs and activation proceeds on the old
  FIB (the RG was already primary in cluster state; withholding
  `SetRGActive` would strand the RG entirely), and the async tail
  plus route-listener retry remain armed.
- **(b) FIB connected-win, guarded** (defense in depth for any
  residual window — e.g. republish duplicate-skipped while the FIB
  was mid-rebuild). In `lookup_forwarding_resolution_v4/v6_inner`,
  when the selected route is a NON-cluster terminal (discard/reject)
  and the lookup table also holds a cluster-terminal
  (republication owed), a covering connected prefix in the same
  table wins and resolves to the ForwardCandidate/MissingNeighbor
  egress shape. Without a cluster-terminal in the table, operator
  discards/rejects keep bit-identical pre-fix semantics — this is
  the fail-closed guard that prevents the connected-win from ever
  overriding an operator discard in a settled FIB. Cluster-terminal
  rows themselves are untouched (their HA demotion/fabric logic is
  #15742/#16216/#16269). Runs only on the terminal branch, never
  per forwarded packet; no allocation.
- **(c) Rejected.** A republication-owed flag making demotion defer
  (`HAInactive` instead of `DiscardRoute`) needs new cross-process
  state (Go daemon → Rust helper) threaded through the snapshot
  protocol or HA state, duplicating ownership evidence the FIB
  already carries (`connected_v4` + `cluster_terminal` marks). (a)
  removes the window; (b) covers the residue with evidence already
  in the FIB. (c) would add a third, weaker signal.
