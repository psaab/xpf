(includes #15738): the #12495 gate still FAILs — NA recovery is

## Root cause — the cluster Null0 default never reaches the helper FIB

The cluster-mode blackhole default exists precisely for this shape
(`renderClusterModeDefaults`, pkg/frr): when the WAN VIP moves to the
peer and FRR withdraws the real default, the Null0 makes the kernel
FIB return a terminal negative so the dataplane fabric-redirects
instead of forwarding out a dead egress. Three facts break that
design in the userspace helper:

1. **Kernel form.** FRR installs the Null0 defaults in the kernel as
   `RTN_UNREACHABLE`, proto `static` (RTPROT_STATIC via FRR's
   proto2zebra), metric 20 — zebra `unreachable (blackhole)`,
   `ip route` `blackhole default proto static metric 20`. Not
   `RTN_BLACKHOLE`.
2. **Importer exclusion.** `pkg/routing/fibimport.go`
   (`importableRouteScoped`) adopted only `RTN_UNICAST` and
   `RTN_BLACKHOLE`; `RTN_UNREACHABLE` was deliberately rejected
   (pinned by `TestImportRejectsUnsupportedNegativeRoutes…11398`).
   So the one route that encodes "no local default — terminate here"
   never entered the learned import.
3. **Suppression.** Even a negative row that did arrive was
   suppressed in `addLearnedRouteSnapshots` whenever a same-prefix
   config row was at least as preferred — the config default (pref 5)
   always suppresses an imported row (pref 200).

Net effect on the split node: the helper FIB holds the config
default pointing at the peer-owned WAN egress and **no terminal
default**. The forwarding row resolves through the connected
WAN prefixes that remain in the snapshot (they are config-derived
on both nodes), so the lookup produces a forwarding candidate
against an RG the node does not own instead of the intended
terminal — the exact silent blackhole the gate records, in both
families, while the kernel itself correctly sits on the blackhole
default. The fabric counters read 0 throughout: nothing ever
reached the fabric-redirect disposition because nothing produced
the terminal/HAInactive outcome the redirect keys on in this
snapshot shape.

## Fix

- `pkg/routing/fibimport.go`: adopt `RTN_UNREACHABLE` as a new
  `LearnedRoute.Reject` (no next-hops), alongside `RTN_BLACKHOLE`→
  `Discard`. `RTN_PROHIBIT` stays excluded (administrative refusal,
  not a routing decision). The HA sentinel priority 4242 excludes
  both negative forms — the helper owns that decision via
  `HAInactive`.
- `pkg/dataplane/userspace/routes.go`: map `Reject` onto the
  snapshot (the Rust FIB already implements `RejectRoute` —
  ICMP-unreachable terminal, not slow-path eligible); include
  `Reject` in the dedupe key (a reject and a discard at one prefix
  are distinct rows); never suppress a negative learned row behind
  a same-prefix forwarding row — preference ordering (forwarding 5
  < imported 200) keeps the forwarding row selected while usable,
  and the Rust terminal-row rule (#15098) reaches the negative row
  only when no drivable forwarding member remains.

With both defaults present, the split node's lookup behaves as
designed: RG1 active → `ForwardCandidate` via pref 5; RG1
peer-owned → HA-demoted → `FabricRedirect` to the WAN owner (the
existing `redirect_via_fabric_if_needed` path, unchanged). No FRR
render change: #15738's HA static filtering stays, and the kernel
keeps its blackhole default — the helper now finally mirrors it.

## Failback half — disposition

Not reproduced as a production defect this session: every
targeted failback (`... node 0`, the `RequestPeerFailover` form)
returned RG2 in iter=1 (~5s), matching round-2's diag/matrix. The
gate's stranded shape is the **plain** form
(`request chassis cluster failover redundancy-group 2` on the
current primary = bare `ManualFailover`) issued ~20s after the
failover, while the matrix/diag waited longer and used the targeted
form. #15738's hold-release covers the committed-secondary shape;
the early-plain-request shape is a distinct timing state (the
request lands while the first transfer's commit grace / peer
hold state is still settling). It remains open under #13058's
timing lane — this PR does not widen the deadline and does not
claim the gate's failback cell. The gate re-run below therefore
still exercises it; if it strands again the preserved evidence
(#15737) plus the journal around the request now isolates it.
