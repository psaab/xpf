# Issue #15093 — Rebase stale scheduler lease on re-introduction

- **Timestamp**: 2026-10-18
  - **Action**: Fix A63-02: a scheduler heartbeat lease stamped in an earlier scheduled era no longer makes a snapshot that re-introduces scheduled rules publish already expired. Rust: `SchedulerHeartbeatLease` gains a `prev_snapshot_scheduled` era marker; `note_snapshot_published` rebases the receipt stamp to the monotonic now only on a no-schedule -> schedule transition and only when the existing stamp is already expired (version zero and fresh leases untouched, same-era republication cannot extend the window). The coordinator drives it from `publish_snapshot_policy`, called after the worker-visible `RuntimeView` store in both the same-plan refresh (`snapshot_refresh.rs`) and the full reconcile (`reconcile/snapshot.rs`), so rejected or not-yet-visible snapshots never rebase the live lease. Go: `requestApplySnapshotPreparedLocked` sends a best-effort `scheduler_heartbeat` BEFORE `apply_snapshot` when the snapshot re-introduces scheduled policy (`snapshotReintroducesScheduledLocked`, sharing the `snapshotHasScheduledPolicies` scan with the existing post-apply seed in `recordSchedulerSnapshotAppliedLocked`, whose heartbeat send is factored into `sendSchedulerHeartbeatLocked`). Neighbouring behaviour preserved: continuous scheduled eras get no pre-send, no-schedule snapshots get no heartbeat, stale heartbeats in a continuous era still expire scheduled permits after 300 s, and version-zero (no heartbeat ever) never expires.
