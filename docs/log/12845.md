# #12845 — D3-11 lifeline-shared conntrack coverage

- **Disposition**: Refuted as an actionable flush defect; retain the existing address-only conntrack boundary.
- **Question**: Does `buildHostInboundConntrackFlushFilter` missing `IngressDenyV4/V6` leave newly denied established traffic authorized, or is the conntrack flush intentionally unable to cover these lifeline-shared addresses?

## Evidence

- `pkg/dataplane/userspace/zones_host_inbound.go` moves lifeline-shared addresses out of `V4Addrs/V6Addrs` and into `IngressDenyV4/V6` only for an empty-admit view (#7284/#12229). This preserves the address outside destination-only deny policy.
- `pkg/daemon/daemon_nft.go` emits the #12229 ingress-zone drops before the residual `ct state established,related accept` (the `emitHostInboundZoneIngress` loop at 2195–2197 precedes the accept at 2210). The #12229 regression `TestLifelineSharedDenyAllVerdictsOnRealKernel12229` pins both the rule order and data-zone denial while retaining the fxp0 connection. Thus an established packet entering a denying data-zone does not retain authorization via the later broad accept.
- The conntrack filter matches original destination addresses, not ingress interfaces (`hostInboundConntrackFlushFilter.MatchConntrackFlow`). Adding an `IngressDeny` address to that filter would therefore delete fxp0 management sessions to the same shared IP along with any data-zone session. The builder documentation and `TestFlushFilterExcludesLifelineSharedAddr_7284` explicitly protect the management session from this address-only flush.
- The warning claim's current-only component probe is not the production call shape. `withTighteningWarningsForResponse10752` calls `tightenedScopesHaveAddrs10752` with BOTH `BuildZoneHostInboundViews(oldActive)` and `BuildZoneHostInboundViews(compiled)` at lines 842–845. When a shared address was present in the prior scope, the old generation retains it in `V4Addrs/V6Addrs`, so the matcher sees it even if the new empty-admit view carries it only in `IngressDenyV4/V6`. A synthetic call with only the new view is not evidence that the transition advisory is suppressed.
- The tentative RED probe failed only for that current-generation-only input; it did not reproduce the production old+new call. Its flush assertion ran while a tentative implementation was present and is not claimed as RED evidence.

## Change and validation

Added `pkg/daemon/host_inbound_ingress_deny_coverage_12845_test.go` to pin the counterevidence: IngressDeny-only lifeline addresses do not enter the address-only flush set, ordinary default-deny addresses remain covered, and the warning matcher checks both generations (old address retained, current-only address not treated as an owner).

- On current base `2d42cf2a9`: `go test ./pkg/daemon -run '12845|7284|12229|10752' -count=1` passed after removing the mutation (`ok`, 40.862s).
- On current base `2d42cf2a9`: `go test ./pkg/daemon -count=1` passed (`ok`, 495.025s).
- Mutation check on `2d42cf2a9`: temporarily wiring `IngressDenyV4/V6` into the address-only conntrack filter made `TestIngressDenyOnlyAddressesStayOutsideAddressOnlyFlush12845` fail because the filter covered both lifeline-shared addresses. The temporary mutation was removed.

## Residual

This disposition concerns only the demonstrated D3-11 mechanism. It does not claim that every conntrack lifetime is bounded or that every transition diagnostic is complete. A future defect report must demonstrate a packet path where a stale shared-address flow is accepted on a denying data ingress, or show that the production two-generation advisory is actually suppressed, without compromising lifeline management access.
