# #14604 — skip-existing / strict-fail per-type guard (Y13-05)

## Issue
Under `skip-existing` (and `strict-fail`) a client claimed a forward `A`/`AAAA` with only `RRsetNotUsed` (type/specific, CLASS NONE). That guards the RRset, not the owner name, so:
- foreign AAAA/MX/TXT only at a name → skip-existing/strict-fail client A add succeeded (`err=nil`, planted, ownership recorded) while replace-owned refused and same-type (A against A) already refused (the existing `TestRFC2136SkipExistingConflictSkips` / `TestManagerSkipExistingConflictRecordsNoOwnership` controls passed). A LAN client via option 12/81 could plant one family at an in-zone foreign name lacking that type and the record persisted for the lease lifetime. Requires non-default skip-existing/strict-fail; default replace-owned safe (Medium).

## Design
- `sendAdd` (skip-existing/strict-fail) now uses `NameNotUsed` (ANY/NONE, name-level) for client-claimed adds. skip-existing keeps `errDDNSConflictRefused`; strict-fail keeps its hard-error shape. Foreign RR of any other type (AAAA/MX/TXT) now refuses.
- The sibling problem: a legitimate dual-stack pair (`cid:`/`mac:` v4, `duid:` v6) must both publish on a fresh name even though the second add sees the name as taken by its own sibling. The backend alone cannot see the manager's durable ownership store, so the manager threads `SiblingFamilyOwned` through `UpsertLease`.
  - `crossTypeSiblingOwned` reports whether the manager already owns a record at `owned`'s canonical FQDN under the OPPOSITE family. It is recomputed per settle/delete; sibling state is re-proven per cycle for the duration of the settle. Architecturally the second family reaches the backend after the first's write-ahead intent (#2662), so the durable store view contains the sibling when the second family's add is built. WireRR claims do not capture sibling-family state, so they are not the source.
  - `sendAdd` only downgrades to `RRsetNotUsed` when `selfOwnedSiblingForward(rr)` (the backend-local A/AAAA decision mirroring `rec.SiblingFamilyOwned`). Otherwise `NameNotUsed`.
- `LeaseDNSRecord.SiblingFamilyOwned` carries both the #3738 delete meaning (unchanged) and, as a DIFFERENT predicate, this #14604 upsert meaning: the manager already owns the name under the opposite family. Documented in `backend.go`; deliberately NOT set anywhere on a DeleteLease-construction path for the upsert meaning. The backend field `siblingFamilyOwned` mirrors `rec.SiblingFamilyOwned` for the forward add in flight, set at the top of `UpsertLease`, reset on every call so a stale flag never leaks into a PTR or same-family guard.

### Residual (documented, not silently closed)
A name shared by xpf's own sibling (e.g. AAAA) AND a foreign RR of another type (MX) cannot be distinguished backend-side: with `SiblingFamilyOwned=true` the per-type guard admits the A. The manager-side sibling scan could be abused by two clients sharing one hostname, and a server-side query race remains. This is bounded because (a) the name must already be xpf-owned by the sibling family through the manager's own store, and (b) the alternative — refusing the second family — reintroduces the #14602/Y13-02 dual-stack loss.
