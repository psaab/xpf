# #16859 — Rotation line stays UNKNOWN in fabric-transport mode

> **Correction (#17891, 2026-10-26):** the #16859 implementation and its
> landing assertions incorrectly treated an initiator's accepted PSK as proof
> of the peer's signing key. Noise_NNpsk0 proves the responder accepts that
> PSK but the responder does not sign. Current session-sync reporting passes
> a key ID only on the connect and upgrade responder sides, whose verified
> msg1 identifies the initiator's signing key. Initiators retain the
> process-lifetime authenticated-peer bit but leave the peer signing-key
> observation UNKNOWN. See `docs/log/17891.md`.

- **Issue**: `notePeerControlKeyID` initially had a single producer,
  heartbeat `admitFrame`. With no `control-interface`/`peer-address` the
  heartbeat never starts, so session sync originally left the fabric-mode
  rotation line UNKNOWN. #16859 added a session-sync feed, but its initiator
  path incorrectly inferred the peer's signing identity from PSK acceptance;
  #17891 removes that false observation. The UNKNOWN wording now says there
  is no verified peer signing key, rather than implying the peer is silent:
  a reachable peer may have proved only that it accepts the initiator's PSK.
- **Change**:
  - `Manager.noteSyncPeerAuthenticated` now takes the matched PSK
    (variadic) and, in addition to the process-lifetime bit, feeds
    `notePeerControlKeyID(controlLinkKeyID(matched))`. Only the derived
    ID is stored; the raw key is never logged or retained.
  - `SessionSync.recordAuthenticatedPeer(matched ...[]byte)` threads the
    optional key through `syncPeerAuthRecorder`. The connect responder passes
    `result.matchedPSK`, which identifies the initiator's signing key; the
    connect initiator passes no key because it proves only that the responder
    accepts the initiator's signing key (#17891). Likewise, the #6628 upgrade
    responder passes its matched ring candidate and the upgrade initiator
    passes no key. The #15140 pending gate is untouched: the responder still
    records only after `awaitInitiatorConfirm` succeeds, and replay cells
    still assert zero recordings before confirmation.
  - The UNKNOWN line remains conservative while distinguishing missing
    peer-signing evidence from lack of connectivity (#17891): it reports
    `peer key UNKNOWN — no verified peer signing key observed; unknown, not
    known safe to finalize`. The predicate returns false for UNKNOWN, and the
    `peer is still signing … — do NOT finalize` arm is unchanged.
  - README "Knowing when it is safe to finalize" documents that the key
    observation is fed by heartbeat admission and session-sync responder
    proofs. An initiator-side authenticated handshake arms the process-lifetime
    bit but leaves peer signing identity UNKNOWN (#17891).
- **Tests**: `pkg/cluster/control_key_rotation_16859_test.go` uses real
  `Manager`s as sync auth providers:
  `TestRotationLineFabricTransportConnect16859` verifies the responder gets
  `PeerControlKeyID == id(B)` and can safely finalize while the initiator
  retains UNKNOWN and remains unsafe;
  `TestRotationLineFabricTransportPeerOnRetiredKey16859` verifies the
  responder identifies retired A and refuses finalization, while the
  initiator remains UNKNOWN rather than falsely declaring A;
  `TestRotationLineFabricTransportUpgrade16859` checks the same direction
  distinction for the #6628 exchange. The process-lifetime auth bit remains
  armed on both sides. The #6630 UNKNOWN expectation and #15140 recorder
  signature also reflect the variadic recorder.

  responder accepts the initiator's PSK.
