# #15084 — SIGHUP terminates xpfd with no shutdown sequence, and systemd counts it as a clean exit (A54-01)

## Why

xpfd captured only its shutdown signals — `signal.NotifyContext`
with SIGTERM (interactive) or SIGTERM+SIGINT (daemon mode) in
`startupSignalContext` (`pkg/daemon/daemon_run.go`). Nothing in
`pkg/` or `cmd/` notified or ignored SIGHUP, and the shipped unit
(`test/incus/xpfd.service`, staged into the .deb by `debian/rules`)
had no `ExecReload`, `SuccessExitStatus`, or
`RestartForceExitStatus`; the version drop-in
(`pkg/upgrade/flip.go` `writeUnitDropin`) rewrites only
`ExecStart`/`ExecStartPre`, so no drop-in supplied one either.

A SIGHUP — `systemctl kill -s HUP xpfd`, a closing controlling
terminal, any stray sender — therefore took the process default
action: immediate termination with NO `runShutdownSequence` (no HA
fence, no `rg_active` clear, no priority-0 advert, no RA goodbye).
systemd classifies termination by SIGHUP as a clean exit, so the
unit's `Restart=on-failure` never restarted it. Standalone: an
indefinite forwarding outage. HA: an ungraceful peer-loss failover
after which the node never rejoined.

## What

- `pkg/daemon/daemon_run.go`:
  - `ignoreSIGHUP()` installs an explicit no-op disposition at the
    TOP of `Run` (before the mutating startup phases, same point as
    the #5807 shutdown capture, both modes, deferred release). It is
    a buffered `signal.Notify` channel, not `signal.Ignore`: each
    SIGHUP is logged ("xpfd has no reload-on-HUP; use commit") and
    discarded, and the daemon keeps forwarding. Configuration
    changes go through commit; there is no reload to trigger.
  - `daemonSignals(interactive)` extracts the shutdown set as a
    named seam; `startupSignalContext` now delegates to it. SIGHUP
    is deliberately NOT added to that set — the issue's alternative
    "orderly stop" shape was rejected because an exit-0 stop still
    scores clean under systemd and would not be restarted (the pin
    in the test keeps that shape out).
- `test/incus/xpfd.service`: add
  `RestartForceExitStatus=SIGHUP SIGPIPE` (the issue-directed pair;
  SIGPIPE is the same default-clean death class). Defence in depth:
  even a HUP death in a window the capture cannot cover (before
  `Run` installs it, an older binary running under the upgraded
  unit) is now scored a failure and restarted within `RestartSec`.
  The version drop-in only rewrites `ExecStart`/`ExecStartPre`, so
  the directive survives upgrade cuts.
- `pkg/daemon/README.md`: correct the stale "(SIGHUP reload, …)"
  intro claim (no reload ever existed) and document the disposition
  next to the #5807 early-signal-capture section.
- `debian/changelog`: operator-facing entry.

NOT changed: the shutdown set's surviving behaviour (daemon
SIGTERM+SIGINT, interactive SIGTERM only so the CLI keeps Ctrl-C),
any `applyConfig`/commit path, `flip.go`'s drop-in template (the
directive belongs in the base unit it never rewrites), and SIGPIPE
handling in-process (Go runtime semantics unchanged; only the
supervisor's scoring of a SIGPIPE death changes).

  cut at `4e9e42e494` and master advanced during the lane — the
  rebase onto `6fd1efe432` was conflict-free): the regression
  file alone does not build — `undefined: daemonSignals` /
  `undefined: ignoreSIGHUP` — because no SIGHUP capture seam exists
  there at all; the unit cell additionally fails on the missing
  `RestartForceExitStatus`. The delivery cell's RED is structural:
  without the capture, the first self-delivered SIGHUP takes the
  default action and kills the test process.

  (shutdown set excludes SIGHUP, keeps SIGTERM/SIGINT in daemon

- Suites: `go vet ./pkg/daemon/` clean. Full

## Risk

Operators who habitually sent SIGHUP expecting a reload now get a
logged no-op instead of a dead daemon — strictly safer, and the log
line names the correct action (commit). Interactive sessions no
longer die when their terminal goes away; SIGINT/Ctrl-C behaviour
is unchanged. The one new goroutine per `Run` is released by the
deferred stop on every return path.
