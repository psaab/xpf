# 9875 — unrepresentable/valueless `from` leaf widens term; carry FromUnrepresentable

## The defect

A firewall-filter term whose `from` block carried a match leaf the dataplane
does not enforce (recorded on `term.UnknownFrom`, #3307 — `ttl`,
`source-mac-address`, `ip-options`, `fragment-offset`, `hop-limit`, ...) or a
value-bearing leaf written with NO operand (recorded on the new
`term.ValuelessFrom` — `from protocol;`, #8480) compiled to a term missing an
entire authored constraint. Every downstream mirror then rendered only the
surviving match set — byte-identical to a term authored without the leaf —
so an `accept` term over-permitted and a `discard`/`reject` term over-dropped
with no signal past the boot warning. The strict commit gates
(`validateFilterFromMatchStrict`,
`validateFirewallFilterValuelessFromStrict`) reject both spellings, so a
committed config never carries them; the live ingress is the tolerant load /
peer-sync path (#1960 no-brick), exactly like the #3406/#6459/#6463 family.

## Design record (MEDIUM tier, settled before implementation)

Brief + two plan reviews adjudicated, v2 posted, no further review rounds.
Settled points the implementation holds:

- The marker uses the RAW-NODE view: `firewallTermValuelessFromLeaves` on the
  SAME raw term node the #8480 strict gate walks, so the recorded set can
  never drift from the strict-reject set (mirrors UnknownFrom /
  UnknownAddresses). Do NOT touch the schema — #10073 owns it.
- Refuse-all, not term-skip, on every mirror: poisoning a `discard`/`reject`
  term to match-nothing would let its traffic fall through to the implicit
  accept (fail-OPEN); only refusing the snapshot/install is action-agnostic.
- Wire default-absent = old behavior (Go `omitempty` + Rust `serde(default)`,
  #1961 parity); the version BUMP (19 -> 20) is what refuses a mixed pair,
  because an old helper that ignores the new key enforces the widened term —
  the defect itself (#8892 v10/v11 arm, #5488 v4 rule).

## The fix

- **Record (pkg/config):** `compileFirewall` populates `term.ValuelessFrom`
  via `firewallTermValuelessFromLeaves` on the raw term node; the warn gate's
  unconstrained check and the #8763 census/guard learn the field.
- **#8480 helper fix:** the prefix-list leaves are read through
  `firewallPrefixListRefs` (the reader `compileFilterFrom` uses), not the
  general `firewallMatchValues`: a self-named reference
  (`source-prefix-list "source-prefix-list";`, legitimate per #9029) reads
  EMPTY under the general reader but compiles a real ref, so the gate
  false-rejected it — proven by execution, with the falsifying row in the
  comment. Behavior changes ONLY for self-named references.
- **Userspace snapshot (pkg/dataplane/userspace):** the builder sets the
  `from_unrepresentable` wire bool iff `UnknownFrom || ValuelessFrom`;
  `effective` renders the refusal line; `ProtocolVersion` 19 -> 20 with the
  v20 arm note (v19 taken by #9874, see sequencing); the #8892 cell moves (digest
  `15332c48...f7b65a`) with the v20 entry.
- **Helper (userspace-dp):** `from_unrepresentable` serde field,
  `preflight_term_markers` guard raising the new
  `UnrepresentableFilterFrom` variant, `CONFIG_SNAPSHOT_PROTOCOL_VERSION`
  19 -> 20, regenerated `protocol_wire_v1.json` (one added key alongside #9874\u2019s).
- **Kernel lo0 mirror:** `Lo0FilterTerm.FromUnrepresentable` carried by
  `toNftLo0Term`; the netlink builder fails the whole plan (refuse-all);
  the text oracle emits the CONSTANT refusal rule
  `comment "unrepresentable from" __xpf_refuse_unrepresentable_from__`
  (disposition B — the nft-invalid bareword rejects the atomic load and the
  prior generation stands, #6806 posture).
- **PBR:** `pbrTermL4` reports `ValuelessFrom` as unrepresentable, dropping
  the term's steering with a degraded build (no address-only over-steer).
- **Docs:** `docs/config-schema.md` marker paragraph (mirrors the #6510
  hunk); `userspace-dp/src/filter/README.md` backstop section.
