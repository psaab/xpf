## Pre-registered acceptance bar (written 2026-11-16T07:18Z, before any run)

This applies to each of step 1 and B1, as its own A/B against master.

- **Shape:** a same-window, paired A/B on the **tcp** cluster.
  - Heartbeat `100 ms × 5`, the runtime default.
  - n ≥ 5 crash takeovers per arm, arms interleaved in one window.
  - The two arms are deployed in turn under one lock cell, so neither arm
    measures a build other than its own.
- **PRIMARY:** the time from peer-lost to the last RG active is reduced, in
  both its median and its max.
  - **Source:** the activating node's journal, from the peer-lost line to
    the last `SetRGActive` return or helper activation line. These are the
    timing lines c5b2e06282 added, plus the instrument extension below.
- **GUARD:** per-stream TCP resume is not worse:
  - the median stream resume, and the worst stream's resume, each stay
    within the master arm's own run-to-run spread (its min-max over its own
    n runs);
  - and zero streams never resume.
  - Resume is measured on the data stream, not on ping. A TCP/UDP SNAT miss
    goes to the helper, so ping is a poor proxy (C3).
- **Reported, not gated:** the materialize-burst counters at takeover
  (shared-map fallback hits per worker in the window), the per-RG in-request
  time, and, for B1, the deferred job's duration and any abort.
- **GUARD, planned failover** (added 2026-11-16, between 07:38Z (after step 1's commit) and 07:50Z, before any run;
  coordinator-approved): per-stream TCP resume on a CLI RG move is not worse
  than master.
  - It is measured the same way as the crash guard: the same runs, from
    `test-failover`'s Phase 4b manual failover (`request chassis cluster
    failover`), read from `failback_resume_data_median_s`, `_max_s` and
    `_never`.
  - The median and the max each stay within the master arm's own min-max
    over its n runs, and `_never` = 0.
  - **Why:** under B1, failover-commit readiness
    (`setLocalFailoverCommitReady` → the old primary's commit) reaches the
    old primary before the worker tables are warm.
  - **Fallback, written down in advance:** if B1 regresses planned failover,
    hold `setLocalFailoverCommitReady` until the deferred warm has been
    acknowledged by every worker. That keeps the crash-path saving and gives
    up only the planned-path overlap.
- **Landing:** this bar AND the standard three-machine gate.

### Confounds, written down before the run

1. **The materialize burst at GARP.** Go sends GARP straight after
   `SetRGActive` returns, so deferred installs move first-packet work onto
   the shared-map fallback. That is the one effect that can eat the saving,
   so it is reported, not assumed.
2. **Clock skew between the nodes.** Cross-node timings use one node's
   clock. Peer-lost and activation are both on the activating node; the
   stream timings come from the LAN host. Skew is measured and recorded
   before pairing any cross-node journal.
3. **CoS state.** CoS is OFF on tcp until #19100 lands (standing rule). Both
   arms run with the same CoS state, recorded per run.
4. **Runner gate pauses.** A gate cell can pause its same-host runner. No
   unit-cell run on a tcp-host runner overlaps the A/B window; any overlap
   VOIDs the affected run.
5. **Heartbeat config drift.** The lab config is `200 × 5`. The A/B sets
   `100 × 5` explicitly, records it per run, and restores it afterwards.
