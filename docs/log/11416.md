## Determination: harness fixture bug, not a validator false positive

`validateFabricZoneRoutingInstanceAmbiguityStrict`
(`pkg/config/compiler_validate_strict_zones.go:460`, dispatch
`compiler_uniformgates_cluster_zone.go:331`) rejects a security zone whose
members span multiple routing contexts, because a fabric ingress zone stamp
cannot identify which routing domain owns the packet. The live baseline
(`fw0-pre.set`, archive `xpf-wire-routing-separation-1792136151`) has
`wan = {reth0.50, reth0.80}` in MAIN and the harness added the RI member
`gr-0/0/1.0` (routing-instance `wire-10136`) to that same zone — a genuine
cross-context span, exactly the class #11061 exists to reject. The fix
belongs in the harness fixture; the validator is not relaxed and no
product-policy exception is added (per the 2026-10-16 recommendation).

## What

- `test/incus/wire-routing-separation.sh` — `cli_commit_populated` now
  places the GRE member in a new test-owned `wire-vrf` zone
  (`POPULATED_ZONE`, env-overridable, validated as a non-`wan`/`lan` zone
  token) instead of `wan`, and commits that zone's own
  `lan -> wire-vrf` permit policy plus a `lan-to-wire-vrf` interface-SNAT
  rule-set in the same transaction — mirroring the existing
  `lan -> sfmix` policy/NAT pair for the product GRE fixture
  (`gr-0/0/0.0` in `sfmix`, `routing-instances sfmix`). This keeps
  policy/NAT selection explicit for the actual egress zone: source-NAT
  matching is keyed on the resolved egress interface's zone
  (`zone_pair_ids_for_flow_with_override`), so borrowing `lan->wan` would
  have left the GRE-egress flow without its intended SNAT rule even if the
  commit had passed. Cleanup deletes the owned NAT rule-set, policy pair,
  zone, RI membership, and interface; preflight now also refuses a baseline
  already carrying the zone/policy/rule-set names. Two new `--selftest`
  source-shape cells pin the dedicated-zone placement and cleanup.
- `pkg/config/wire_routing_fixture_11416_test.go` (new) — unit-level
  proof: the exact fixture statement shape (baseline `wan`/`lan` zones +
  FBF term + RI + GRE member + /32 interface next-hop) compiles strictly
  with the member in `wire-vrf`, and the old `wan` placement is rejected
  with the exact `security zone "wan" spans multiple routing contexts`
  error from the live attempt. Fail-on-revert both ways.
- `docs/firewall-validation-harness-design.md` — Routing-Instance
  Separation note records the dedicated-zone placement and why.

## Acceptance boundary (why this does not close #11416)

`Closes #11416` requires the harness to prove positive VRF forwarding
locally at unit level. The populated fixture now compiles and is
structurally incapable of the validator collision, but live positive
forwarding (GRE-encapsulated delivery observed at the peer, route-removal
discrimination) still requires a qualified cluster run, and the IPv6
twin, TCP, and return-path legs remain blocked on the unrecorded
maintainer ruling (Option A/B/C + Safe-RPC close semantics + dual-stack
echo sender, design-v4 review). The PR therefore references #11416
without closing it.

## Risk

Harness-only config change plus a config-package test; no product code
touched, validator unchanged. The dedicated zone adds one zone/policy/NAT
rule-set to the fixture transaction — all test-owned, preflighted absent,
and deleted by cleanup with the existing baseline-restore comparison. Live
behavior of the new zone pair is source-grounded (sfmix precedent) but not
executed; a live mismatch surfaces as VOID/FAIL, never a false PASS.
