# #16683: console `rescue delete` prints success when the delete fails

- **Timestamp**: 2026-10-25
- **Action**: The local console handler for `request system configuration
  rescue delete` (`pkg/cli/cli_request_system.go`) had an empty
  `if err != nil {}` block left by #15897, which removed the `return err`
  while adding the trailing-argument check above it. The handler printed
  `Rescue configuration deleted` and returned nil when rescue.conf was
  absent, could not be unlinked, or its directory fsync failed, while the
  gRPC twin (`pkg/grpcapi/server_request_parity_8597.go`) maps the same
  errors to `codes.Internal`. rescue.conf is a full copy of the active
  config (#4056 secret class), so an operator deleting it to remove
  cleartext secrets was told it was gone while it remained on disk. The
  handler now returns `fmt.Errorf("delete rescue configuration: %w", err)`
  inside the block, matching the gRPC wording; the success line is only
  reached after a successful durable delete. `DeleteRescueConfig` itself
  (#5197 dir-sync, #14722 generation claim) is unchanged.
- **File(s)**: `pkg/cli/cli_request_system.go`,
  `pkg/cli/rescue_delete_error_16683_test.go`, `docs/log/16683.md`.
- **Validation**: New `TestConsoleRescueDeleteError16683` (pkg/cli):
  absent rescue.conf returns a non-nil error wrapping
  `delete rescue configuration` / `no rescue configuration exists` and
  prints no success line; an undeletable rescue path (non-empty directory,
  so `os.Remove` fails even as root) returns a non-nil wrapped error,
  prints no success line, and leaves the path in place; a regular
  rescue.conf still deletes, prints `Rescue configuration deleted`, and is
  gone from disk. RED-on-revert: restoring the empty block makes the
  absent and undeletable rows report success. `go vet ./pkg/cli/` clean.
- **Residual**: None. The dir-fsync failure row is not exercised directly
  from pkg/cli (its seam lives in pkg/configstore and is pinned by
  `rescue_delete_fsync_5197_test.go`); it flows through the same returned
  error this fix now propagates.
