# #14839 — session open/update encoder reserves 2 bytes but writes 10

- **Issue**: #14839 — `[gemini-hostile D6-01]` session_sync.rs guard
  reserves `pos+2+rule_id.len()+2` but the encoder appends a 10-byte
  trailer (handshake 1B + provenance 1B + #13965 PPTP call-id pair 8B)
  after the rule_id.
- **Branch**: `fix/14839-campaign`
- **Worktree**: `/var/worktrees/wt-14839`
- **Base**: `5371f5fe19` (rebased to current origin/master before push)

## Why

`encode_session_record` in
`userspace-dp/src/event_stream/codec/session_sync.rs` admitted a
`policy_rule_id` whenever `pos + 2 + rule_id.len() + 2 <= buf.len()`
(512-byte `EVENT_FRAME_CAPACITY`). That reserves only 2 bytes past the
rule_id, but after the rule_id the encoder unconditionally writes the
#10888 handshake byte, the #12187 provenance byte, and the #13965
PPTP pair (8 bytes) — 10 bytes in total. A rule_id sized to fit exactly
under the old guard therefore passed it and then panicked
(`range end index 513 out of range for slice of length 512`) on the
PPTP write, panicking the session-sync worker mid-frame.

`policy_rule_id` is `StablePolicyRuleID(from, to, name)` =
`"<from>-><to>/<name>"`: zone and policy names flow in from operator
config, and no length cap below the panic window (367–374 bytes for
IPv4 / 307–314 bytes for IPv6 rule_ids, i.e. zone+policy names totalling
>360 bytes) was found in Go or Rust validation, so the window is
reachable with long-but-legal names.

## What

- `session_sync.rs`: the capacity guard now reserves the full trailer
  via `RULE_ID_TRAILER_BYTES = 1 + 1 + 8`:
  `pos + 2 + rule_id.len() + RULE_ID_TRAILER_BYTES <= buf.len()`.
  Either the whole trailer fits and is written, or `rule_id_len`
  falls back to 0 (the established fail-closed "unattributed" wire
  value the Go decoder, `pkg/dataplane/userspace/eventstream.go`,
  already handles by leaving the counter unattributed). No wire
  format change; no new allocation (same stack frame).
- `codec_tests.rs`: new `session_open_rule_id_at_capacity_boundary_14839`
  derives the rule_id field position from an empty-rule_id frame (no
  hard-coded offsets), then for both v4 and v6 keys asserts:
  the longest fitting rule_id is carried verbatim and fills the frame
  exactly to 512 bytes with the trailer intact; rule_ids 1–10 bytes
  past the fit fall back to the zero-length prefix, keep the baseline
  frame length, and still carry handshake/provenance/PPTP bytes; the
  UPDATE path (same `encode_session_record`) falls back identically.

NOT changed: the frame capacity, the wire layout, the Go decoder, and
the zero-length fallback semantics (all pre-existing). The close-frame
encoder has no variable-length field and is unaffected.

## Validation

- RED (fix stashed, encoder at base):
  `cargo test --bin xpf-userspace-dp -- session_open_rule_id_at_capacity_boundary_14839`
  → FAILED, panic at `session_sync.rs:438`:
  `range end index 513 out of range for slice of length 512` —
  exactly the reported defect.
- GREEN (fix applied): the same test passes; the 13 targeted codec
  tests around it (`test_encode_session_open_*`,
  `session_update_carries_*`, `session_open_and_update_*`) pass.
- `cargo fmt --check` scoped to the two touched files: clean (repo-wide
  fmt noise in unrelated benches is pre-existing).

## Risk

- A rule_id within 8 bytes of the old limit is now silently dropped to
  unattributed instead of carried. That is the pre-existing fallback
  for any over-capacity id, is fail-closed (receiver binds no stale
  counter), and only affects rule_ids of roughly 310–380 bytes —
  far beyond any realistic zone/policy name. No operator-visible
  behavior change for normal configs.
