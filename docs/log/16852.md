## Mechanism

The bpfrx->xpf rename (`b67f80edf9`) changed the managed swanctl filename from `bpfrx.conf` to `xpf.conf`. The pre-rename code removed the file only when IPsec was cleared, so an IPsec-configured node carried `bpfrx.conf` (connections + `ike-*` secrets, cleartext PSK) across the upgrade. `swanctl.conf` includes `conf.d/*.conf`, so every `--load-all` kept loading the stale definitions: deleting a VPN rewrote/removed only `xpf.conf`, `promoteConnNames`/`terminateRemovedConns` could tear down its live SA, but the peer could re-initiate against the `bpfrx.conf` definition xpf did not own. A same-named connection merged, so stale children rode along with xpf's connection. `Clear` and factory reset (which removed only the exact `xpf.conf` path) left the file and its PSK in place indefinitely.

## Fix

Delete the exact legacy file (plus its fsatomic crash temps) before every Manager-driven `--load-all` (`applyConfig`/`clearConfig` — covering Apply, ApplyGeneration and Clear), erase it in the factory-reset rendered-config leg with the same symlink/hardlink doctrine as `xpf.conf`, sweep its editor backups, and remove it in the one-shot migration script. Removal failures fail closed on both the commit path and the wipe. Foreign `*.conf` files are untouched.

## Operator-visible delta

Upgraded nodes carrying `conf.d/bpfrx.conf`: the first IPsec apply/clear after this fix logs `removed legacy pre-rename swanctl snippet … (#16852)` at Warn and charon no longer loads the stale connections/secrets — deleted VPNs stay deleted and their peers can no longer re-establish. Factory reset now erases the legacy file and its editor backups. An un-removable legacy file (e.g. a planted directory) fails the commit/zeroize loudly instead of silently leaving the secret authorized; remove it manually and retry. Fresh installs see no change.
