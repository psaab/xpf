## The coordinator's three questions, answered at `3ae82aa49`

| Question | Answer |
|---|---|
| What does "degraded" mean, and which states hand the steered port to the kernel? | Every shim degraded arm runs BEFORE both WireGuard arms (`:678` steer, `:748` claim): ctrl disabled or a meta mismatch (`degraded_ctrl_disabled_action`, `:474`), binding missing or not ready, heartbeat missing or stale. Each passes `is_degraded_local_or_control` traffic to the kernel. Helper down: no control threads, so no TUN write. Snapshot refused: the prior snapshot keeps running; not degraded. |
| Does refusing drop traffic an operator depends on? | Inner **transit** is the bypass (the open forward hook), and its LAN-side counterpart is already dropped at the shim in these windows. Inner **host-inbound** through the TUN meets nftables `hook input`, so it is not a bypass, and dropping it would cut management over the VPN. So the posture mirrors the shim: deliver local, drop transit, count it visibly. |
| Does #9521's refusal cover the steered port in degraded mode? | **No. This is the dangerous case, but not a separate path.** #9521's check is the `kernel_transport` value chosen at spawn from the listen port alone (`wg_kernel_transport_for_endpoint`), and it lets the steered port through on purpose (#8274's residual). It takes no health input, so degraded windows reach the same `Deliver` write. |

The interface-mode SNAT listener is outside the change by construction. Its address
is not local to the shim (`is_local_destination` excludes interface NAT), so every
degraded arm drops it, and on the healthy path it is worker-decapsulated and never
reaches a control thread.

## Decisions

- **Coverage is keyed on ingress, not on dataplane health.** On an ingress the shim
  adjudicates, a healthy shim claims every steered-port transport record for the
  worker, so a kernel arrival there *is* a degraded arrival. No health flag is read,
  so none can race, and a single degraded binding is caught. A global flag was
  rejected: it misses per-binding degradation, and while ctrl is disabled it would
  also cut #8274's uncovered-ingress delivery.
- **The shim's own maps, not a second derivation.** Coverage reads
  `userspace_ingress_ifaces`; locality reads `userspace_local_v4/v6` minus
  `userspace_interface_nat_v4/v6`. These are the maps Go fills, including VRRP VIPs
  from the kernel, which the helper's snapshot-derived `local_v4` lacks.
- **Not a shim change.** Dropping the steered port in the shim's degraded arms would
  be the most exact coverage test, but it drops host-inbound over the VPN. It also
  means a verifier-gated `userspace-xdp` change, and it would hit attached-but-uncovered
  netdevs, which take the ctrl-disabled arm first.
- **Unplaceable ingress fails closed for transit only.** That covers a missing pktinfo
  cmsg, or an ifindex neither adjudicated nor configured (a VRF master, if the kernel
  reports one). Maps that cannot be opened mean nothing is known to be covered; the
  thread says so once.
- **No production loop without the posture.** The viewless `run_wg_control_loop`
  exists only under `cfg(test)`, where it pins the older cells' pre-#9594 behavior.

## Two coverage gaps found while planning the mutation matrix, closed before scoring

- The production locality rule's interface-NAT exclusion lived only in the bpffs
  branch, which no cell can reach. It was factored into `shim_is_local_destination`,
  used by both branches, with `locality_excludes_interface_nat_like_the_shim_9594`.
- The production view's "is this a configured interface" lookup (runtime forwarding
  state) had no cell. A regression there would read every uncovered ingress as
  unplaceable and silently drop #8274's residual transit. Fixed with
  `shim_maps_view_places_configured_uncovered_ingress_9594`, which builds the
  production view from a real snapshot's runtime reader.

## Corrections during the work

- **A setup race in the pktinfo path, found by the mutation matrix.** The first
  matrix ran on `93bc38cac` against a concurrent `make test`. Under that load,
  mutant R7 (covered-ingress gate short-circuited) killed its target cell with the
  WRONG message: the posture had been asked about ingress `[None]`, because the
  test's first datagram was queued before the loop thread's `setsockopt`. R1-R6 had
  each won that race. The same window is real in production. A record queued
  between `bind` and the loop's first line reads as an unplaceable ingress, and is
  counted as a degraded-transit drop on a healthy box whenever a control thread
  spawns under traffic. Before recording anything, I checked two alternatives:
  a mutation left unrestored in the mutation worktree (clean, anchors restored),
  and interference from the concurrent run (the ingress failure is inside one
  process's loopback socket). Fix: `bind_dual_stack_v6` requests pktinfo before
  `bind`, and the IPv4 fallback right after it. The loop harness now waits until
  the option is on before sending. New cell
  `bind_wg_socket_requests_pktinfo_before_any_datagram_9594`, with its call site
  as mutant R11. The stale `make test` was stopped rather than landed on.
- **A merge gate that failed open, and the fixed ports it let through.** A second
  merge of origin/master brought #9606 (#9549, "take test ports from an ephemeral
  source"), which touches `coordinator/tests.rs` and `tunnel_supervision.rs`. The
  merge job's overlap gate extracted the overlap list with a single-line `sed`
  pattern. A multi-line list never matched, so the gate read empty and the merge
  went ahead without the review it was meant to force. Git's auto-merge was
  textually clean. A read of #9606 afterwards showed its rule, "Ports in tests",
  contradicted by two #9594 cells: the end-to-end cell bound 51971/51972, which was
  the #9521 resteering cell's pair in the same binary before #9606, and the
  view-placement cell spawned threads on 51981/51982. Both now reserve ports from
  `crate::test_ports`. A `make test` already running on that merge was stopped, not
  landed on. The landing stage's own gate is path-prefix based and does catch these
  files.
- **R10 scored VOID in the first matrix** (`not applied: 1->1`). Its replacement text
  still contained its own anchor, so application could not be counted. The spec
  was corrected to a non-overlapping replacement. The first matrix is kept as
  `mut9594-pre-racefix.log`: 2 NOOPs survived, 13 cells killed with their
  expected messages, R7 wrong message, R10 void. The full matrix below was rerun on
  the race-fix commit.

- `RuntimeViewReader` was first named through the private `types::runtime_view`

## Not established here

- What `IP_PKTINFO` reports for a VRF-enslaved ingress on the target kernels.
  Asked on the issue. The fail-closed rule for unplaceable ingress bounds the risk
  to transit on such an ingress.
- A pinned-map fd opened before a shim reload keeps reading the old map until the
  control thread restarts.
- A frame the shim cannot parse at L2 (double-tagged, for example) is passed to the
  kernel even when healthy. On covered ingress its inner transit is now dropped,
  which is the safe direction.
- No live-cluster smoke. The change is confined to the helper's control thread,
  with no `userspace-xdp` or steering change. The load-bearing controls, the SNAT
  listener and the steered tunnel passing traffic on the healthy path, are pinned
  by the existing worker-decap cells and by this change's positive controls.
