# #13174 — retain host-inbound coverage for ingress-deny and DHCP targets

## Why

The day-2 nft install-failure coverage accounting ignored `IngressDenyV4/V6`, even though the real host-inbound table denies those lifeline-shared addresses on data ingress. An address newly appearing only in those fields could therefore be absent from the additive gap fence and from the early-input barrier's newcomer check. Separately, the gap-fence install was gated only on uncovered addresses, so a newly unleased DHCP interface had its backstop omitted when no destination address was uncovered. A successful zero-scope teardown also left stale gap retry debt recorded.

## What

- Count `IngressDenyV4/V6` in the real table's desired and uncovered destination sets, including the early-input handoff coverage check.
- Keep cold-boot fence coverage separate: it excludes ingress-only lifeline-shared destinations that the fence does not drop.
- Install the additive gap fence when a DHCP backstop target exists even if uncovered destination lists are empty.
- Discharge gap retry debt after successful zero-scope teardown.
- Update prior tests to assert the address's effective destination-deny scope may be `IngressDeny` rather than destination-only `V4Addrs`.
- Keep a distinct retained set for DHCP-backstop exclusions. Ingress-only main-table drops are tied to old ingress netdevs and must not exempt a new DHCP interface's local-address backstop.

Ingress-only addresses are counted for the real table and gap fencing, but not falsely reported as covered by the cold-boot fence. DHCP-only gaps now install the existing additive backstop rules without replacing the retained table.
