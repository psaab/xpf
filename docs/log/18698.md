# #18698: #10288 PORT-REUSE step fails (a test defect, not a pool leak)

- **Timestamp**: 2026-11-01
- **Classification**: a TEST defect. The allocator does free the port. Since
  #16035 it intentionally refuses a DIFFERENT flow that re-reserves a port
  freed from a small pool, for 60 s after the release. The acceptance step
  asked inside that window.
- **Evidence**:
  1. **Bisect.** The original test PASSES at `9527c76055^` (`56a810334b`) and
     FAILS at `9527c76055` ("nat: quarantine freed ports in small PAT pools
     (#16035)", 2026-10-23), with the issue's panic ("fixture must take the
     reservation"). Each arm ran in its own worktree and target,
     `cargo test --bin xpf-userspace-dp`. #16035's validation ran
     `nat::` only ("nat:: 757 pass"), so this `afxdp::session_glue` test went
     red unseen. The reuse step itself dates from `39fe076599`
     (2026-09-18), before the quarantine existed.
  2. **Mechanism.** #16035 added `port_quarantined(translated.port, now_ns)`
     to the specific-port reserve (`reserve_flow_maybe_persistent_inner`,
     `nat/allocator/mod.rs`). `RecycleRing::quarantined`
     (`nat/allocator/occupancy.rs`) refuses while
     `now - freed_at < PAT_PORT_QUARANTINE_NS` (60 s), only for pools of at
     most `SMALL_POOL_QUARANTINE_MAX_RANGE` (256) ports, and only for tokens
     stamped with a real free time. The fixture pool is ONE port. The sweep
     releases it at `2_000_000` ns. The reuse step reserved at the fixture's
     fixed `1_000` ns, before the release, so inside the window.
  3. **Time-based, not a leak.** The quarantine is a pure time comparison,
     not a token that only a claim path drains. The fixed step on current
     master is refused at release + 1 ns and ADMITTED at release + 60 s,
     after which the port is held as one live flow. That cannot pass if the
     freed port were stranded.
- **Fix (test-only)**: `drop8114_try_reserve_at` reserves at an explicit
  time without asserting. The reuse step now asserts both halves:
  - refused just after the release, and the port stays free;
  - admitted at release + `PAT_PORT_QUARANTINE_NS`, holding the port as one
    live flow.

  The quarantine length is read from the allocator's own
  `PAT_PORT_QUARANTINE_NS_FOR_TEST`. That `#[cfg(test)]` constant is widened
  to `pub(crate)` and re-exported from `nat` (test builds only; no release
  change).
- **Docs**: `docs/feature-coverage.md` (Source NAT row) now states the
  small-pool reuse delay and its capacity effect. It was not documented
  outside a review archive. A pool of at most 256 ports admits at most its
  size in new flows per minute; larger pools reuse a freed port at once. The
  lab HA config's `pool-snat-pool` has 1000 ports (30000-30999), so it is not
  quarantined, and interface SNAT uses large ranges. No lab config exercises
  the quarantine, so there is no lab churn gate; this is a test-only change.
- **File(s)**: `userspace-dp/src/afxdp/session_glue/tests.rs`,
  `userspace-dp/src/nat/allocator/mod.rs` (`#[cfg(test)]` visibility),
  `userspace-dp/src/nat/mod.rs` (`#[cfg(test)]` re-export),
  `docs/feature-coverage.md`, `docs/log/18698.md`

## Validation

- `cargo test --bin xpf-userspace-dp` filtered to
  `delete_drop_sweep_releases_nat` and `14961`: 8/8 pass. That is the fixed
  10288 test and the 7 NAT64 #14961 siblings that share its fixture.
- **Product mutants against the fixed test** (`nat/allocator/occupancy.rs`,
  restored after each run):
  - Q0, a no-op baseline: passes.
  - Q1, the quarantine removed: KILLED by "#16035: inside its quarantine
    the freed port must not go to a different flow".
  - Q2, the quarantine never ending (a simulated leak): KILLED by "#10288
    acceptance: once the quarantine has elapsed, a distinct flow must be
    able to take the freed 203.0.113.1:20000 ... leaked for good".

  The fixed test therefore pins both #16035's delay and the absence of the
  leak #10288 exists for.
