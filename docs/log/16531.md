# #16531: two WireGuard tunnels on one listen-port committed clean, second tunnel dead on bind

- **Timestamp**: 2026-10-24
- **Action**: Added a strict commit gate for WireGuard listen-socket
  collisions. Each WG endpoint's helper control thread binds its own
  `[::]:port` UDP socket with no SO_REUSEADDR/SO_REUSEPORT, pinned to
  `vrf-<instance>` only when its transport table names an instance, so
  two tunnels on one port in the same instance — or one in the default
  instance (wildcard socket) plus one in any VRF — could not both bind:
  the second bind failed EADDRINUSE, the thread exited and respawned
  every 3s, and that tunnel never handshaked, with no commit-time
  signal. The new gate
  (`validateWireguardListenPortCollisionStrict`, run from `runTailGates`
  after the #9909 scope gate) walks `EmitTunnelEndpointNames`, resolves
  each endpoint's effective transport instance the way the snapshot
  builder does (explicit `tunnel routing-instance`, then RI interface-list
  membership), and hard-rejects a colliding pair at strict commit naming
  both tunnels and the shared port/instance. Distinct ports, and two
  different VRFs sharing one port (disjoint `vrf-<instance>` device
  binds), still commit. The lenient load/peer-sync path downgrades to a
  warning (#1960 no-brick). Corrected the comments and docs that
  presented same-port tunnels as an unqualified supported shape
  (steering-gate dedup notes, `tunnelemit.go` merge rationale,
  `wg/decap.rs` #14326/#15123 selection comment,
  `docs/wireguard-interop.md`), and updated
  `TestWireGuardSameListenPortDoesNotWarn_1434`, which asserted the
  colliding shape commits clean, to assert strict refusal plus steering
  silence on the lenient path. SO_REUSEPORT was not used: the kernel
  would hash datagrams to an arbitrary engine and MAC1 under the wrong
  key would drop them.
