# #12832 — validate cross-kind address-set graph depth and cycles

- **Timestamp**: 2026-10-13

## Red before

`validateAddressSetDepthAndCycles` followed only `AddressSet.AddressSets`, while literal expansion follows both those edges and `AddressSet.Addresses` members that name another set. A chain linked only through cross-kind `address` members and a cross-kind cycle therefore passed strict address-book validation even though leaf expansion rejected them.

`TestCrossKindStrictAddressSetBounds12832` reproduces both failures against the unmodified implementation: a six-edge chain expected `address-set nesting too deep (max 5): s6` but strict validation returned nil; a mutual cross-kind cycle expected `cycle detected in address-set "A"` but strict validation returned nil. An overlay replacing the fix with the original same-kind-only traversal reproduced both failures and the strict compile integration's nil error.

## Change

Strict address-set validation now traverses cross-kind `address` members if they name an address-set, while a defined same-named address takes precedence and terminates that edge. The traversal shares one path-local visited set and the existing five-edge depth counter across cross-kind and `address-set` edges, so shared diamond children remain valid and cycles are reported as cycles.

`ExpandAddressSet` remains unchanged: direct cross-kind members are set-ID graph references, as required by dataplane compilation. The test pins this behavior (`ExpandAddressSet(A) == [B]`) rather than flattening it or silently dropping the member. Literal-leaf consumers continue using `expandAddressSetLeaves`.
