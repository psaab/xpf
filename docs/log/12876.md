# #12876 — release stale syn-cookie state across profile edits

- **Base**: `fefd415a5` (origin/master at branch start)
- **Branch**: `fix/12876-campaign-pub`

## Why

`ZoneScreenState::reconcile_substate` carried the per-zone
`syn_cookie_active_until_secs` latch across commits that changed the very terms
the latch was measured under: a `syn-cookie` disable/re-enable cycle or an
attack-threshold (`syn_flood_threshold`) increase. The latch is derived state
("the aggregate crossed the attack threshold while cookies were on"), so after
those edits a zone kept skipping its configured per-source SYN sketch and kept
hard-dropping unrelated session-miss ACKs as `Invalid` for up to the remaining
64 s cookie epoch — on terms the latch was never measured under. Separately,
`syn_cookie_profile_signature` omitted `syn_flood_src_threshold`, so tightening
the per-source cap left already-validated sources certified to keep their
#9945 bypass of that cap for up to the validated-cache TTL; the operator's
commit silently did not apply to exactly the sources most likely to be
flooding.

## What

- `update_profiles` computes an activation-slice change
  (`(syn_cookie, syn_flood_threshold)` — exactly the fields that gate whether
  `syn_flood_gate` may set the latch) and passes it to `reconcile_substate`,
  which clears the latch when it changed, alongside the existing #9425 audit
  clear. Fail-closed in the only direction that matters: a still-real flood
  re-latches on its next over-attack SYN because the count-all aggregate
  counter is carried over untouched.
- `syn_cookie_profile_signature` widens to
  `(syn_cookie, syn_flood_threshold, syn_flood_src_threshold)`, so a
  per-source-cap edit bumps the zone's generation and decertifies validated
  clients (recertification = one fresh challenge). The latch is NOT cleared on
  a src-threshold-only edit: the source cap never gates the latch, and
  cookie-active deliberately skips it (D3/#9945).

## Validation

- **RED** on pristine `origin/master` (`fefd415a5`, wt-12876red) with only the
  three new tests copied in: `cargo test --bin xpf-userspace-dp -- 12876` —
  0 passed / 3 failed with the defect's exact outcomes (stale-latch `Invalid`
  on both the threshold-raise and disable/re-enable ACK paths; stale
  `SynCookieBypass` after src-threshold tightening).
- **GREEN** post-fix: same filter — 3 passed / 0 failed.
- Full screen module suite post-fix: `cargo test --bin xpf-userspace-dp --
  screen::` — 321 passed / 0 failed.

## Risk

Clearing the latch costs at most one packet of cookie-active enforcement when
the activation slice changes under a still-real flood (the next over-attack
SYN re-latches). A src-threshold edit now re-challenges validated clients
(one extra challenge per cached client, the fail-closed direction); the
symmetric generation churn on a loosening edit is accepted because the
signature is not directional. No wire-format, epoch, or key-ring change.
