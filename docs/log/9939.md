# #9939 — a `then change-configuration` payload was authorized against nobody

Work log for issue #9939. See `docs/log/README.md` for why this lives here and
not in the repository-root `_Log.md`.

- **Timestamp**: 2026-09-12
- **Action**: The payload carried by
  `event-options policy … then change-configuration commands "…"` is now
  adjudicated against the PLANTING class's own `*-configuration` regexes.
- **The escalation**: the line that plants the payload is gated as a path under
  `event-options`; the payload itself is DATA and nothing looks inside. At fire
  time `pkg/eventengine` applies the embedded `set`/`delete` and the daemon
  commits with `configstore.InternalCommitter()` — and
  `commit_authority.go` answers `case authorityInternal: return nil`, so no
  authority check runs on that path at all. A class denied `security policies`
  but permitted `event-options` could delete a guard policy autonomously, as
  root, on a routine RPM event.
- **Why the gate is at the PLANT and not in the engine**: at fire time there is
  no principal — the daemon is acting on its own behalf, which is what makes it
  an escalation. The commit that plants the payload is the only moment a class
  is in scope.
- **Why it is inside `AuthorizeConfigMutation`**: all four surfaces and `load`
  already route through it, so one implementation covers gRPC, REST, the on-box
  CLI and `load merge`/`load set` rather than four that agree today. This is the
  same "one evaluator, not N agreeing copies" call as #9892 and #9952.
- **The measurement that decided the fixture, and nearly the whole issue**: with
  an UNANCHORED `security policies` deny the plant is ALREADY refused at master —
  the payload text is part of the outer planting line, so the path gate catches
  it incidentally and the defect does not reproduce. It needs an ANCHORED deny,
  which is the idiom Junos documents for complex expressions. Same condition as
  #9938 F-029, where an unanchored deny also hid the mechanism. The premise is
  ASSERTED in the fixture helper, not commented, because if it stopped being true
  every cell would pass for the wrong reason.
- **Token boundary**: the payload walk uses the SAME rule the compiler's own
  reader applies (`eventChangeConfigCommands`, #6659) — a QUOTED value is one
  command per token, an UNQUOTED tail is a single command that must be re-joined.
  A different rule here would adjudicate a command the engine never runs, or miss
  one it does, which is #9938's defect one layer in. It has its own cell.
- **The recursion bound REFUSES rather than waving through**, and the cell pins
  that direction: running out of budget must not read as having found nothing,
  or the nesting depth at which adjudication stops is chosen by whoever writes
  the payload. Measured while writing it: a nested payload is not expressible in
  the config text at all, because the inner command would carry quotes inside an
  already-quoted value and the lexer terminates the outer string at the first
  inner quote. So the bound guards a shape the grammar does not currently admit —
  which is exactly the kind of guard that rots into "unfalsifiable" unless its
  direction is pinned.
- **NOT closed, filed as #9984**: a payload already persisted before this gate
  still fires as root, because the policy records no planting class. Every
  substitute for a recorded class is unsound (over-denies a superuser's payload,
  or needs the planter it lacks, or breaks every legitimate policy on upgrade),
  and recording it is a config-type change on the HA wire with repo-wide blast
  radius. Bounded: only an ANCHORED deny leaves a persisted payload
  unadjudicated.
- **Validation**: the four escape rows were run against the neutered gate first
  and all four failed; every control passed pre-fix (the unanchored row, the
  allowed payload, the class with no regexes, the token boundary), which is what
  makes them controls rather than decoration.
