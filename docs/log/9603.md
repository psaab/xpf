  - **Action**: Implemented the coordinator decision's option 3.
    - `junosApplicationLeavesNotImplemented9603` is a closed, exact,
      case-sensitive table: `application-protocol`, `ether-type`, `icmp6-type`,
      `icmp6-code`, `rpc-program-number`, `uuid`.
    - `unimplementedJunosApplicationLeaf9603` reads every token of every
      unrecognized run (`UnknownDirectTokens`, `UnknownTermLeaves`). A table
      hit is now an `ApplicationMatchDrops` reason, whatever the value's shape

      - the userspace expansion lowers it to the #3261 sentinel, and the

      - policymatch reports `ContentRejected`.
  - **Action**: The table's source is Juniper's SRX grammar,
    `junos-es-conf-applications@2024-01-01.yang` (github.com/Juniper/yang,
    `24.4/24.4R2/native/conf-and-rpcs/junos-es/conf/models`). I extracted the
    statement lists from the model with a brace-aware parser that expands
    `uses` groupings:
    - `application`: description, term, application-protocol, protocol,
      source-port, destination-port, ether-type, icmp-type, icmp6-type,
      icmp-code, icmp6-code, rpc-program-number, uuid, inactivity-timeout,
      do-not-translate-AAAA-query-to-A-query, do-not-translate-A-query-to-AAAA-query.
    - `term`: alg, protocol, source-port, destination-port, icmp-type,
      icmp-code, icmp6-type, icmp6-code, rpc-program-number, uuid,
      inactivity-timeout.
    - `application-set`: description, application, application-set.

    The two DNS ALG switches stay out of the table: they change translation,
    not the match. A first draft of the table was built from a search summary
    of the MX services grammar. It carried `snmp-command` and `ttl-threshold`.
    Neither is SRX grammar, so the model check removed them before the commit,
    and a stays-armed cell pins `snmp-command` as NOT refused.

  - **Action**: Reading the table.
    - `CheckText` parses hierarchical text only: set-format text fails with
      "unknown configuration stanza set" even for the control. Its flat cells
      are therefore VOID, not rejections. `compileTreeStrict` is measured
      instead, because it is what `CheckText` and `Store.compileTree` (every
      commit and commit check) both run.
    - `SchemaValidate` admits every row, the controls included. Applications
      are opaque to it by design, as documented in `compiler_opts.go`
      `lenientApplicationSpecs` and in the #3352 opaque `term` leaf. Its only
      non-test callers are `pkg/configstore/store.go:769/781` on the strict
      path, and `compileTreeStrict` runs it and then strict `CompileConfig`.
      So its admission is not a commit admission.
    - Assumption, stated: the decision's "all three strict channels" is read
      as "every channel that can commit". Moving application grammar into
      `SchemaValidate` would contradict that documented doctrine, and I did not
      do it.
  - **Action**: Conclusion. Every commit channel rejects rows 1, 2 and 4 in
    every spelling, naming the token. A misspelling beside a retained
    constraint reaches `CompileConfigLenient` only from text a looser build
    committed, such as an older database or an older HA peer. It stays
    installed as the documented residual (option 1 for that class). The
    measurement is pinned by
    `pkg/configstore/app_misspelling_strict_channels_9603_test.go`, so a later
    change that lets one commit reopens the question.
