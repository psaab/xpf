# Nameless `protocols lldp interface { ... }` block panicked compileProtocols (#15138)

## Why

`protocols { lldp { interface { disable; } } }` (and
`interface { ge-0/0/1; }` / `interface { ge-0/0/1 { disable; } }`)
panicked `compileProtocols` with
`slice bounds out of range [2:1]`. Those block spellings carry
`Keys=["interface"]` with the would-be name (or a bare `disable`)
nested as a child. `nodeVal` falls back to that child's name, so the
compiler treated `"disable"` / `"ge-0/0/1"` as an interface name and
then sliced `child.Keys[2:]` on a 1-key node. The panic is reachable
on every ingress that compiles — strict commit / commit-check, the
authenticated `load override` path (`LoadOverrideAsPlantClass` →
candidate → `compileTreeStrict`), the tolerant `Store.Load` boot
path, and the HA `SyncApply` path (`compileTreeLenient`) — with no
`recover` above any of them, so an authenticated config-writer's
malformed but parseable one-line body crashed `xpfd` and systemd
restarted it. The #7568 census
(`TestNoSchemaPathPanicsOnTheBlockForm_7568`) generates
`<path> { probeval; }` with a single child, so it never produced the
two-level nameless LLDP shape and could not see this site.

A bare length guard around only the slice would stop the panic but
silently compile a phantom interface named `disable` (enabled), or
`ge-0/0/1` with no stated properties — so the fix decides the
block-form semantics instead of only guarding the index.

## What

- `pkg/config/compiler_protocols.go` (`compileProtocols`, LLDP
  `interface` case): only a name packed on the statement itself
  (`Keys[1]`, `len(Keys) >= 2`) is a named interface. A nameless
  statement (`len(Keys) < 2`) is rejected on strict compile with
  `protocols lldp interface: an interface name is required`
  (fail closed; Junos requires the name) and, on the tolerant paths
  (`CompileConfigLenient` / `compileTreeLenient` via the existing
  `lenientLLDPInterfaceTokens14616` opt), warned about with the same
  message plus `(ignored on tolerant load)` and dropped, so a
  persisted config still boots (#1960). Never a panic on either
  path. The #14616 packed-`disable` read, the child-`disable` read,
  and the unknown-token gate are unchanged for named statements;
  the guard above them makes `Keys[2:]` provably in range (empty
  when `len == 2`).

NOT changed: `nodeVal` (shared by many compilers; its child-name
fallback is correct for the dual AST shapes it serves), the LLDP
schema node or its #14616 `nodeValidator` (the panic was in the
compiler, and the store's strict path already surfaces the compiler
rejection), `SchemaValidate` behaviour for these spellings (the
`interface { disable; }` spelling already passes it — the compiler
is now the gate that rejects it, exactly as the strict compiler
already rejected the other two spellings via the packed-token
validator), global `protocols lldp disable`, interval/multiplier
handling, or any LLDP runtime/daemon code.

## Validation

- RED (pre-fix, clean `origin/master` probe): all three nameless
  spellings panic `CompileConfig` and `CompileConfigLenient` with
  `slice bounds out of range [2:1]`; controls compile.
- GREEN targeted:
  `go test ./pkg/config/ -run 'TestLLDPNameless|TestLLDPBlockFormCensus|TestLLDPNamedInterfaceControls|TestLLDPInterfacePackedDisable14616|TestNoSchemaPathPanicsOnTheBlockForm_7568' -count=1` PASS (census: 1318 schema paths, 0 panics),
  `go test ./pkg/configstore/ -run 'TestLLDPNamelessBlock|TestLLDPNamedBlockStore' -count=1` PASS,
  `go test ./pkg/config/ -run 'TestLLDP|TestLLDPNameless|TestNoSchemaPathPanics|TestPrefixList' -count=1` PASS,
  and `go vet ./pkg/config/ ./pkg/configstore/` clean.
  Strict rejects naming the missing name, lenient warns + drops
  with no phantom interface, the census probe compiles under
  recover without panicking, and named block/packed/plain/flat
  controls compile exactly as before (including the #14616 packed
  disable and flat `set ... interface ge-0/0/1 disable`).
- FAIL-ON-REVERT (measured): with the production fix reverted and
  the tests kept, `TestLLDPNamelessInterfaceBlockDoesNotPanicStrict15138`
  fails with `panic: runtime error: slice bounds out of range [2:1]`
  at `compiler_protocols.go:84` in `compileProtocols` — the exact
  pre-fix mechanism.
- A bare slice-only guard would also fail: it compiles the phantom
  interface, which the strict-reject / lenient-drop assertions
  reject.

## Risk

Strict commits carrying a previously-panicking nameless LLDP
interface block now reject naming the missing name — intended
(they could never commit before; they crashed the daemon).
Tolerant loads of a persisted nameless block now warn and drop
that entry instead of crashing. No dataplane, wire, or daemon
behaviour changes beyond that.
