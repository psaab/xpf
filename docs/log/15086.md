# 15086 — Non-UTF-8 config identifier no longer panics the metrics scrape (A44-01)

## Summary

A committed config identifier carrying a raw non-UTF-8 byte (the probe's
policy rule `web\xffallow`) reached `prometheus.MustNewConstMetric` as a
label value in `collectPolicyCounters`. client_golang rejects invalid
UTF-8 label values, the `Must*` constructor panics, and `Registry.Gather`
runs collectors in its own goroutine, so the panic killed the whole
daemon (gRPC, CLI, REST, HA control) on the next `/metrics` scrape —
net/http recovery never applies. A monitoring poll turned a
commit-accepted config into a whole-daemon crash.

## What changed

- **Single sanitizing choke point** (`pkg/api/metrics_emit_15086.go`):
  every one of the ~627 `ch <- prometheus.MustNewConstMetric(...)` emit
  sites across the 36 collector files now calls
  `c.emitConstMetric(ch, ...)`, which folds any label value carrying
  invalid UTF-8 to U+FFFD (`strings.ToValidUTF8`) and then uses the
  error-returning `prometheus.NewConstMetric`. Legitimate values pass
  through byte-identical (fast path is one `utf8.ValidString` check per
  value, no allocation). The standalone `emitHistogram` helper uses the
  same builder via `newConstMetric(nil, ...)`. No production
  `MustNewConstMetric` remains in `pkg/api`.
- **Fail closed on residual construction errors**: an arity/descriptor
  error now skips the sample and bumps `xpf_counter_read_errors_total`
  (the existing #3345 omit-plus-error contract) instead of panicking.
- **Two always-emitted health counters** (including at zero):
  `xpf_metrics_invalid_label_values_total` counts label values sanitized
  (one per value, not per byte); `xpf_metrics_collector_panics_total`
  counts collector passes the lane recovered. Both are emitted via
  defers at the top of `collectContext`, beside the existing
  counter-read-errors defer.
- **Lane recover backstop** (`metricsLane.Collect` in
  `metrics_handler.go`): any residual collector panic is recovered,
  counted in `xpf_metrics_collector_panics_total`, and the lane is still
  returned to the pool, so that scrape fails (promhttp answers with what
  Gather returned) instead of crashing the process or leaking the lane
  into a permanent 503. Because a panicking pass unwinds through
  `collectContext`'s deferred emits while Gather may already have
  stopped receiving, the bumped panic count is certified by the next
  scrape's sample; the atomic accumulates regardless.

Out of scope, deliberately: commit-time rejection of non-UTF-8
identifiers was the issue's *optional* leg. The raw-byte ingresses
(CLI file load, day-0, HA sync) feed many surfaces besides metrics, and
changing commit acceptance there is a separate, wider contract change;
the scrape can no longer crash regardless of what any ingress admits.

## RED-then-GREEN proof

RED (on `origin/master`, worktree at `131c402ffb`): a throwaway probe
test driving `collectPolicyCounters` with rule `web\xffallow` panicked
exactly as claimed —

```
panic: label value "web\xffallow" is not valid UTF-8 [recovered, repanicked]
  prometheus.MustNewConstMetric(...) value.go:129
  (*xpfCollector).collectPolicyCounters metrics_counters.go:835
```

GREEN: the permanent regression `pkg/api/metrics_invalid_utf8_15086_test.go`
(4 tests) passes —

- `TestCollectPolicyCountersInvalidUTF8RuleName15086`: the probe spelling
  no longer panics; the sample is published as `web�allow`, no raw byte
  survives, `invalidLabelValues == 1`.
- `TestCollectPolicyCountersValidRuleNameUnchanged15086` (control):
  `web-allow` passes through byte-identical, counter stays 0.
- `TestMetricsScrapeInvalidUTF8RuleName15086`: end-to-end through
  `newMetricsHandler` + a real `Registry.Gather` — two consecutive
  scrapes answer 200 with the sanitized series, `collectorPanics == 0`,
  `invalidLabelValues > 0`.
- `TestMetricsLaneCollectRecoversPanic15086`: a nil-srv collector that
  panics inside `collectContext` yields a failed scrape, not a crash;
  `collectorPanics` goes 1 then 2, and the second scrape is admitted
  (the lane was returned, not leaked into 503).
