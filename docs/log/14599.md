# Issue #14599 — DHCPv6 relay drops RFC-shaped Confirm/Release/Decline replies that carry no IA

- **Timestamp**: 2026-10-16
  - **Action**: Fixed the pending-key dimensionality bug (`Y12-02`).
    The v6 pending key is xid + Client ID DUID + lowest `(IA type,
    IAID)` (`pending6KeyFor`, `pkg/dhcprelay/pending6.go`), so a server
    Reply carrying no IA keys to `(0, zero IAID)` and could never match
    a relayed request that carried an IA — yet RFC 8415 makes the
    IA-less Reply the conformant shape for Confirm (§18.3.3: Server ID,
    Client ID, and a Status Code such as NotOnLink, no IA required),
    Release (§18.3.7: top-level Success, IA only to carry NoBinding),
    and Decline (§18.3.8, same shape). The relay silently converted
    NotOnLink into silence (a roaming client kept a stale address) and
    counted the legitimate reply as `RepliesDroppedNoRequest`.
    `insertPending6` now records, for exactly Confirm/Release/Decline
    (`pending6MayReplyWithoutIA`), a second IA-less alias binding —
    same xid/DUID with IA type 0 and zero IAID, same recorded client
    address and request type — alongside the primary IA-bound key.
    The production client loop (`runDHCPV6ClientLoop`) and the test
    arming helper (`armDHCPV6ReplyFrom`) both insert through
    `insertPending6`, so the alias and primary bindings are always
    recorded together and carried across reconfiguration by the
    existing snapshot/adopt path. No other request type gets an alias:
    an IA-less Reply to a recorded Solicit/Request/Renew/Rebind (or an
    IA-less Advertise to Solicit) is still dropped, and every
    #10699/#14181 forged-reply check (configured server source, outer
    peer-address equality, legitimate server answer type for the
    recorded request, Interface-ID routing) applies on the alias path
    unchanged because the alias entry carries the same payload.
    Regression tests in `relay6_noia_14599_test.go`: Confirm NotOnLink
    and Release/Decline Success IA-less Replies forwarded exactly once
    with `RepliesDroppedNoRequest` staying 0; IA-less replies to
    Solicit/Request/Renew/Rebind/Information-request still dropped;
    IA-echo (NoBinding-shaped) Release Reply still forwarded through
    the primary key; forged cells on the alias path (peer mismatch,
    Advertise inner answering Confirm, unrecorded transaction) still
    drop; key-level test pins the alias to Confirm/Release/Decline
    only. README's DHCPv6 binding section documents the alias.
  - **File(s)**: pkg/dhcprelay/pending6.go, pkg/dhcprelay/relay6.go,
    pkg/dhcprelay/relay6_test.go,
    pkg/dhcprelay/relay6_noia_14599_test.go, pkg/dhcprelay/README.md,
    docs/log/14599.md

## Risk

- Behaviour delta: a Relay-Reply whose inner Reply carries no IA now
  forwards when (and only when) it answers a recorded
  Confirm/Release/Decline from the recorded client with the matching
  xid/DUID — previously it was always dropped. Forged IA-less replies
  gain no new acceptance surface: the alias requires the same
  24-bit xid + exact DUID guess, the configured server source, and
  the recorded peer-address, and the per-request answer-type check
  still rejects Advertise/RECONFIGURE inners on the alias path.
- Capacity: Confirm/Release/Decline transactions occupy two ring
  slots instead of one for their 30-second TTL. Eviction remains
  fail-in-the-availability-direction only (see pending.go); the
  `PendingSize` gauge reads ring slots, so it reflects the alias.
- NOT changed: `pending6KeyFor` and the primary IA-bound key are
  untouched, so IA-echo replies (including Release/Decline NoBinding)
  match exactly as before; Solicit/Request/Renew/Rebind/
  Information-request binding behaviour is unchanged; the drop
  counters and their meanings are unchanged (the fix stops
  mislabelling legitimate replies, it does not add a counter).
- No live-cluster DHCPv6 relay smoke was run (source/fake-conn scope
  per the issue's decisive check, matching the probe
  `TestY12Probe` shape); the regression tests drive the real
  `processDHCPV6ServerPacket` path end to end.
