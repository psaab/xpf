# Issue #12072 — Resolve stable policy IDs for prepublish session reads

## Why

A session stores the policy ID from admission, but that numeric ID is positional and can change when the policy snapshot is reordered. During a three-config commit, a prepublish read for a newly deleted rule could therefore return an unrelated older session that inherited the same number. Unbound peer-synced rows have no stable rule identity with which to disambiguate that read.

## What

Prepublish worker reads resolve bound sessions through their stable policy-rule handle against the active forwarding snapshot, and return the resolved ID. Unbound peer-synced rows are excluded from prepublish ID-keyed reads. The shared-map completeness check applies the same resolution and exclusion, while legacy timestamp-fenced reads retain their scalar behavior. A Go-local expected-config value is checked under the userspace manager lock together with every helper LIST page; reads fail closed on snapshot mismatch or unknown publish outcome. When a prior invalidation target has landed, fresh captures re-anchor to its applied config while retaining already-captured row identities. Earlier incomplete scans remain blocking debt across that re-anchor; only a complete retry of the exact originating pair while its old snapshot remains authoritative can resolve them, because the helper exposes no historical stable-key LIST. Added worker regressions for reorder, renamed aliases, and unbound peer rows, plus daemon tests for three-config renumbering, lost-ACK refusal, scan-debt retention/retry, and delete-identity recovery.
