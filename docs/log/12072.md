# Issue #12072 — Resolve stable policy IDs for prepublish session reads

## Why

Runtime policy IDs are positional. Prepublish reads must resolve bound sessions through their stable rule handle at the helper's known applied snapshot, or a deleted rule's old number can select an unrelated surviving session. An incomplete READ creates a second risk: a missed deleted-rule session can become an orphan after publication and resolve to the default-policy sentinel in later snapshots.

## What

The daemon distinguishes authority refusal from enumeration failure. Unknown
authority blocks publication and preserves the retry plan; a known applied
predecessor re-anchors positional IDs before capture. If the helper already
holds the target, retained candidate identities are reused only when matching
debt proves their capture. A commit-confirmed rollback whose old, applied, and
new configs are the same takes an empty capture instead of refusing. Debt for
a superseded target is retired, not merged, only when it is neither
helper-applied nor store-active and both agree on the same other config; a
store move alone does not discard debt. When that retired target carried
obligations from a landed predecessor, the predecessor debt is restored if it
still matches helper authority. Scan failures and undischarged candidates from
landed transitions therefore remain fail-closed, while candidates belonging
only to the unlanded target cannot be over-deleted.
Deferred recovery proof is keyed to policy and rename identity, so policy-
identical neighbor, fabric, and FIB partial updates do not trigger a fresh
positional read after a lost ACK. Changed policy/rename identity still blocks
publication, and generation checks reject stale callbacks. Rename descriptors
are reused only after validation against the captured config pair.

An incomplete scan surfaces one commit error and one ERROR-level alarm.
Confirmed delete outcomes are pruned from retained candidates, so settled
retries do not resend rows or repeat the error. Independent later commits still
revoke their own affected sessions. A later complete scan clears scan debt when
it proves the same old authority is still active; the target may differ if the
incomplete target never published. A published incomplete target advances
authority, so later scans cannot certify its missed identities. A successful
`clear security flow session` retires debt only when the helper authority and
active store config still identify that target. The clear is serialized by
`applySem` and logs whether retirement occurred at INFO; non-retirement details
are DEBUG so routine clears stay quiet. Its single-shot helper clear fails
closed above 262,144 sessions, so that remedy cannot complete above the cap.

## Risk

The LIST reply contains only the resolved positional ID, not the original stable
rule identity. After a partial scan has published, a missed deleted-rule
session is indistinguishable from a legitimate default-policy session at the
sentinel; sweeping all sentinel rows would over-delete valid sessions. The
daemon retains scan debt and keeps `ActiveApplied` false while those identities
remain unresolved. If publication did not land, retry under the original
authority; a complete scan at that same authority also clears debt when a
superseding target replaces the unpublished one. After a published scan failure,
only a successful full session clear can retire the marker, and only while both
the helper authority and active store config still identify the published
target.

The full-clear path stamps the debt's captured digest through the existing
`MarkAppliedDigest` behavior. An unrelated apply failure before capture can
un-record that marker, after which a later clear can stamp it again despite the
failed stage. This behavior is inherited; [INFERENCE] production reachability
requires a rare pre-capture failure because daemon background applies use a
non-cancellable context. The helper's 262,144-session cap can also prevent the
full clear from completing, leaving scan debt outstanding.
