# Issue #14633 — inet6 `next-header` extension-header values commit clean but never match

- **Timestamp**: 2026-10-16
  - **Action**: Rejected inet6 firewall-filter terms whose protocol value
    is an IPv6 extension-header type at strict commit, instead of
    implementing first-Next-Header matching. `compileFilterFrom` aliases
    `next-header` (and cross-family `protocol`) under inet6 to
    `term.Protocols`; the Rust extension-header walk
    (`walk_ipv6_ext_chain`) traverses 0/43/44/51/60/135/139/140/253/254
    to the terminal protocol, `poll_descriptor/filter.rs` matches on
    `flow.forward_key.protocol` (the terminal), the fragment sentinel
    resolves to the inner protocol, and both nft mirrors emit
    `meta l4proto` (also the terminal protocol). So `next-header 43`
    never fired on an `[nh=43][RH][TCP]` packet (seen as protocol 6
    everywhere) — a discard term was dead with counter 0 and later
    accept terms admitted the traffic. The issue's acceptance allows
    either first-header matching or this strict rejection; rejection
    was chosen because first-header matching would require a new
    first-header field through the Go wire snapshot, the Rust matcher
    (every evaluation path, including session revalidation which has no
    frame), and both nft mirrors (where `meta l4proto` cannot express
    it and an `exthdr` presence match would be needed) — a multi-PR
    change — while rejection is fail-closed and names the dead value.
    New gate `validateFilterNextHeaderExtStrict`
    (`compiler_validate_strict_filter.go`) walks inet6 filters only,
    resolves each token via `protocolNumberForFilterToken` (named `ah`
    plus canonical numerics, mirroring `filterProtocolResolvable`), and
    rejects values in `ipv6ExtensionHeaderNumbers`
    (0/43/44/51/60/135/139/140/253/254, mirroring
    `ipv6_ext_header_is_traversable`). Wired in
    `runUniformGatesFilter` after `validateFilterProtocolsStrict` with
    `lenientFilterNextHeaderExt` downgrading to a warning on tolerant
    load/peer-sync (#1960). Rust backstop in
    `check_cross_field_satisfiability` (`filter/compiler.rs`): an
    inet6 snapshot carrying such a value fails closed with
    `UnsatisfiableFilterCrossField` predicate
    `next-header-extension`, so a leniently-loaded term never silently
    forwards. Family inet is untouched (those numbers are ordinary
    IPv4 protocol numbers); terminal inet6 values (tcp/6/esp/50,
    no-next-header 59, icmp6/58, 255) still commit. NOT changed: the
    cross-family `protocol` spelling under inet6 with a terminal value,
    `payload-protocol` (not implemented — Junos's last-header spelling;
    today's matcher already matches the last/terminal header via
    `protocol`/`next-header` terminal values), and the nft mirrors
    (consistent by construction once the dead values cannot commit;
    a leniently-loaded dead term matches the terminal protocol in both
    mirrors exactly as in userspace).
    Regression tests: Go `firewall_next_header_ext_14633_test.go`
    (strict reject for 0/43/44/51/60/135/139/140/253/254/`ah`, mixed
    `[ tcp 43 ]` list, terminal-value and inet controls, lenient
    warning) and Rust `filter_next_header_ext_14633_inet6_rejected_inet_compiles`.
  - **File(s)**: pkg/config/compiler_validate_strict_filter.go,
    pkg/config/compiler_uniformgates_filter.go,
    pkg/config/compiler_opts.go,
    pkg/config/firewall_next_header_ext_14633_test.go,
    userspace-dp/src/filter/compiler.rs,
    userspace-dp/src/filter/tests.rs, docs/log/14633.md

## Risk

- Behaviour delta: an inet6 `next-header` extension-header term that
  previously committed (and never matched) now fails commit with a
  named reason. Operators relying on the dead term see a commit error
  instead of silent non-enforcement; the error names the terminal
  alternative. `next-header ah` is rejected for the same reason (AH is
  traversed; the separate `ipv6_ah_sighted` flowless identity is not
  what the filter protocol matcher sees for forwarded flows).
- Residual: first-Next-Header matching and a distinct
  `payload-protocol` keyword remain unimplemented Junos parity gaps;
  the strict rejection keeps them from being silently dead.
