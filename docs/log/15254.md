# #15254 — close the abandoned bulk-sync telemetry window on full disconnect (A82-03)

- **Timestamp**: 2026-10-19
- **Action**: stamp an abandoned end when a full disconnect clears a live
  bulk receive window, and key the bulk session counter/progress log on
  `bulkInProgress` instead of the telemetry pair.

## Why

The full-disconnect path in `handleDisconnect`
(`pkg/cluster/sync_conn.go`) cleared `bulkInProgress` but not
`BulkSyncStartTime`/`BulkSyncEndTime`. An accepted `BulkStart` stamps
Start and zeroes End (#9177 V052 — the stores sit on the accepted path);
when every fabric then dropped before the `BulkEnd`, nothing ever set an
end, so `show chassis cluster information` reported "Bulk sync in
progress since …" for the whole peer outage. The session handlers in
`sync_conn_read.go` decided "is this bulk traffic" by testing
`BulkSyncStartTime > 0 && BulkSyncEndTime == 0`, so early incremental
records on reconnect were also counted into `BulkSyncSessions`
(and Info-logged on the 1st/64th) as bulk traffic of a bulk that was
not running. This is the abandoned-**accept** shape; #9177 covered the
refused-**start** shape, #5272 owns completion semantics. Severity Low:
operator-visible status/telemetry lie during the HA failure case, no
enforcement or ownership effect.

## What

- `pkg/cluster/sync_conn.go` (`handleDisconnect`, full-disconnect block):
  gated on the already-captured `hadBulkInProgress`, store
  `BulkSyncEndTime = now` beside the existing reset log. NOT a
  completion: `BulkSyncs`, `bulkEverCompleted` and
  `OnBulkSyncReceived` still belong to `BulkEnd` alone, and the gate
  keeps a later idle disconnect from re-stamping a genuinely completed
  bulk's end/duration. A partial disconnect (survivor fabric) takes the
  other branch and abandons nothing.
- `pkg/cluster/sync_conn_read.go`: new `bulkReceiveProgress` helper; the
  v4 and v6 session arms call it instead of open-coding the telemetry
  pair test (the twin duplication collapses). Counting/logging now keys
  on `bulkInProgress` under `bulkMu` — exactly the set the install arm
  accumulates into `bulkRecvV4`/`bulkRecvV6` — so records arriving
  between the accepted start and its telemetry stores are counted too,
  and none are counted once the window is closed (disconnect included).
  The #9177 comment at the accepted-start stores now points at this
  twin edge.
- `pkg/cluster/sync_bulk_abandoned_15254_test.go` (new): six cells —
  abandoned-status defect cell, miscount defect cell, and load-bearing
  controls (running bulk still counts, completed bulk untouched by an
  idle disconnect, partial disconnect keeps the window, post-abandonment
  `BulkStart` re-opens cleanly). Reuses the #9177 fixture
  (`newIncEnv`, `statusFor9177`) so the observable is the operator
  status text, not internal state alone.
- `docs/sync-protocol.md`: "abandoned-accept twin" subsection next to
  the #9177 V052 statement-ordering contract.

NOT changed: completion semantics (`BulkEnd` still uniquely stamps
end-on-success, increments nothing it did not before, and releases the
hold), the accept/refuse logic, `status.go` rendering, and any sender
path. No wire change.

## Risk

- The abandoned bulk now renders as "Last bulk sync: <disconnect time>"
  rather than "in progress"; its duration spans start-to-disconnect,
  which is the honest bound of what was observed. `BulkSyncs completed`
  is unchanged, so the abandonment stays distinguishable from a
  completion.
- Lab/HA replay (live peer outage mid-bulk on the loss cluster) is not
  exercised here; the `handleDisconnect`-driven cells over installed
  pipe connections are its proxy.
