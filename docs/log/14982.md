# 14982 — Distrust same-UID loopback squatters in VerifyLoopbackServerConn (D36-01, same-UID leg)

## Summary

`VerifyLoopbackServerConn` (`pkg/authz/client.go`, the #14581 client
half used by `cmd/cli` and `pkg/upgrade` via `authz.DialContext`)
accepted a loopback management server owned by `uid 0` **or the
caller's own uid** (`id.UID == uint32(os.Getuid())`). xpfd runs as
uid 0 (its unit has no `User=`; see
`pkg/grpcapi/primary_listener_holder_14581_test.go`: "xpfd runs as
uid 0 (the unit has no User=)"), so the same-uid arm never matches a
genuine xpfd for a non-root caller — it only matches a squatter
running as the operator's own uid that bound `127.0.0.1:50051`
before xpfd started or while it is down. That squatter would be
handed the operator's management RPCs, including `set`/`load`
payloads carrying secrets, exactly the #14581 harm, merely with the
squatter's uid equal to the dialer's instead of foreign.

Scope narrowing (binding, from the issue): same-UID leg only. The
non-loopback bypass leg and the `TCP_SYN_RECV` handshake-race leg
are NOT changed: non-loopback targets remain out of scope for this
gate (authenticated by their own #4107/#4122 chain; the existing
`TestVerifyLoopbackServerConnNonLoopbackOutOfScope_14581` control
stays green), and the server-side `ListenerOwner.Privileged`
(uid 0 or own uid) is untouched — for the daemon that check is
self-referential (the daemon itself is uid 0, so own-uid there
means another root daemon), unlike the client check where the
caller is normally a non-root operator.

## Fix

`pkg/authz/client.go` only:

- `VerifyLoopbackServerConn`: drop the `id.UID == os.Getuid()` arm;
  only `uid 0` is trusted on loopback. Any non-root loopback server
  — foreign or same-uid — is refused with the existing fail-closed
  error naming the holder uid (now citing `#14581, #14982`).
- File/symbol comments updated to state the uid-0-only rule and why
  same-uid is refused; the now-unused `os` import is removed.
- Behaviour for a root caller is unchanged (same-uid == uid 0).

Consumers (`cmd/cli/main.go:58`, `pkg/upgrade/cluster_cli.go:80`,
both via `authz.DialContext`) need no change: they already fail
closed on a `VerifyLoopbackServerConn` error (conn closed before
any byte is written).

## Regression (RED → GREEN)

- `TestVerifyLoopbackServerConnRefusesSameUIDSquatter_14982`
  (`pkg/authz/client_14982_test.go`): renders the ESTABLISHED row
  for a real loopback connection owned by the test process's own
  non-root uid (1000) via the existing `/proc` fixture seam.
  RED on `origin/master` (3d5bc4cd6c): "same-uid (uid 1000,
  non-root) loopback server was accepted". GREEN after the fix.
  Skips when the suite runs as root (same-uid == uid 0 there, so
  the defect is unobservable).
- `TestVerifyLoopbackServerConnRootServerPasses_14982` (same file):
  control — a uid-0 loopback server row passes regardless of caller
  uid, so legitimate xpfd stays reachable.
- `TestVerifyLoopbackServerConnOwnUIDPasses_14581`
  (`listener_14581_test.go`) pinned the old same-uid-pass behaviour
  over a real socket; it now skips for a non-root suite (its premise
  is superseded by #14982, and the refusal is pinned by the new
  same-uid test) and still runs/passes under root.
- Controls staying green: `TestVerifyLoopbackServerConnRefusesForeignUID_14581`,
  `TestVerifyLoopbackServerConnNonLoopbackOutOfScope_14581`, all
  `TestLookupListenerOwner*` / `TestListenerOwnerPrivilegedMatrix_14581`.

## Risk

A non-root process that legitimately serves the loopback management
port as the operator's own uid would now be refused — but no such
legitimate server exists: xpfd is uid 0. Root-run clients are
unaffected. Non-loopback dials are byte-for-byte unchanged.
