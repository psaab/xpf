# #10405 — Preserve TunOrigin across shared-map owner-RG demotion

## Context

`demote_shared_owner_rgs` (`userspace-dp/src/afxdp/shared_ops.rs`) must
preserve `SessionOrigin::TunOrigin` (and transient local seeds, same class)
in the shared, NAT-alias, and forward-wire loops while still retagging
ordinary origins to `SyncImport` — mirroring the
`SessionTable::demote_owner_rg` guard. The three guards are present on
master (commit `5c120e68d`, Refs #10317); this issue pins #10405 with a
dedicated demote→reactivate regression that drives the production
activation/prewarm path after demotion.

## Regression

`afxdp::session_glue::tests::demote_reactivate_preserves_tun_origin_across_shared_aliases_10405`
(`userspace-dp/src/afxdp/session_glue/tests.rs`):

publish (TUN + ordinary `ForwardFlow` control, non-default NAT so all
three aliases populate) → `demote_shared_owner_rgs(&[1])` (failover) →
`prewarm_reverse_synced_sessions_for_owner_rgs(&[1])` (failback; the
shared-map leg of `Coordinator::handle_activated_rgs`, `ha/state.rs`) →
assert per-alias provenance in shared/NAT/forward-wire, no peer-synced
reverse planted for TUN, control reverse planted, and worker
`UpsertSynced` origins (`TunOrigin` / `SyncImport`).

The reactivation leg is load-bearing: prewarm only synthesizes a
`SyncImport` reverse for peer-synced/promoted entries
(`synthesized_synced_reverse_entry` stamps `SyncImport`), so a demote
that destroyed TUN provenance would plant HA-crossing state on failback.
