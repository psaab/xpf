# #16831 — `functional-zone management` was an ordinary transit zone

## Defect
`security zones functional-zone management` compiled into
`sec.Zones["management"]` indistinguishable from a literal
`security-zone management` (#15668): `ZoneConfig` carried no functional
mark and no dataplane consumer special-cased the zone. Global policies
(published as `junos-global`/`junos-global`, evaluated for every zone
pair in `userspace-dp/src/policy.rs`) and any zone-pair permit naming
`management` therefore forwarded traffic into and out of the management
interface, losing the out-of-band isolation Junos guarantees: "Traffic
entering management zones does not match policies; therefore, traffic
cannot transit out of any other interface if it was received in the
management interface."

## Fix
- `pkg/config/types_security.go`: `ZoneConfig.Functional` (`json:"-"`)
  marks a zone compiled from a functional-zone stanza.
- `pkg/config/compiler_security_zones.go`: the functional arm of
  `compileZones` stamps `Functional` via the new `functional` parameter
  of `compileZoneBody15668`; the security-zone arm never clears it, so
  the merged both-spellings zone keeps host-only semantics.
- `pkg/config/compiler_validate_strict_policy.go`: strict commit
  rejects a zone-pair policy naming a functional zone on either side,
  and a global policy whose `match from-zone`/`match to-zone` scopes to
  it. An unscoped global stays legal. The tolerant path downgrades via
  the existing `lenientPolicyZoneRefs` channel (warning; the dataplane
  then fails closed).
- `pkg/dataplane/userspace/protocol_zones.go` + `zones_snapshot.go`:
  `ZoneSnapshot.Functional` (`functional,omitempty`) carries the mark
  to the helper.
- `userspace-dp/src/protocol/snapshot.rs`: matching
  `#[serde(rename = "functional", default)]` field (old Go omits it).
- `userspace-dp/src/policy.rs`: `functional_zone_ids_from_snapshot`
  derives the id set under the `zone_name_to_id_from_snapshot` validity
  rules; `parse_policy_state_with_counters_and_functional` (the legacy
  entry delegates with an empty set) excludes functional ids from
  `concrete_zone_ids` and records them on `PolicyState`;
  `evaluate_policy_result_counted` denies any transit pair naming a
  functional id before every rule tier and before the implicit default
  (also covering unresolved-egress/NoRoute). Production parse sites
  (`PreparedPolicyState::parse_snapshot`, the `forwarding_build`
  fallback) thread the snapshot's set. Host-inbound
  (`evaluate_junos_host_policy_*`, `to-zone junos-host`) does not
  consult the set, so ssh to the management interface address is still
  admitted by `host-inbound-traffic`.

## Validation
- Go: `go test ./pkg/config/ -run TestFunctionalZone` (new
  `functional_zone_transit_16831_test.go`: Functional stamp + merged
  spelling + security-zone twin control; zone-pair reject both
  directions + twin control commits + lenient warning; global-scope
  reject + unscoped global commits) and the pre-existing
  `TestFunctionalZoneManagement*` (#15668) cells.
- Go: `go test ./pkg/dataplane/userspace/ -run TestFunctionalZoneSnapshotWire16831`
  (new `functional_zone_16831_test.go`: wire flag + host-inbound
  services survive; twin control unmarked; unscoped global publishes).
- Rust: `cargo test --bin xpf-userspace-dp 16831` (new
  `policy_functional_zone_16831_tests.rs`: global-permit and
  default-permit transit denial both directions with ordinary-pair
  control; lenient zone-pair permit never fires with twin control;
  `to-zone junos-host` permit still matches on the host path;
  `functional_zone_ids_from_snapshot` validity rules).
- Wire: the new field is serde-default/omitempty, so the default
  `protocol_wire_v1.json` specimens are unchanged; the round-trip is
  pinned by the Rust `functional` field + Go tag agreement through the
  snapshot build above.

## Risk
- A persisted config that names `management` in a zone-pair policy
  (previously accepted) now fails strict commit; tolerant load/peer-sync
  boots with a warning and the dataplane drops that transit (fail
  closed). Operator-visible: such policies must be removed or the
  interface moved to a `security-zone`.
- Rolling upgrade: an old Go binary omits `functional` (helper treats
  the zone as ordinary, pre-#16831 behavior); an old helper ignores the
  field. No fixture regen needed.
- NOT changed: `security-zone management` semantics, NAT/screen/route
  handling of management interfaces, host-inbound admission.
