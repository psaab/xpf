# Issue #10342 — loss-cluster pref-2000 baseline drift

## Scope and issue evidence

Issue #10342 was opened after the locked #10136 preflight on 2026-09-18.
The reported state was a committed `sfmix` virtual-router with `vrf-sfmix`
present but no IPv4 pref-2000 `l3mdev unreachable` rule.  The issue had no
comments.  The earlier #10136 lane log records the same observation and the
important transition: adding the owned temporary RI caused xpfd to self-heal
pref-2000, while deleting only that RI left manager-owned `vrf-sfmix` and
pref-2000 behind (`docs/log/10136.md`, lines 56–67).

The archived configuration snapshots from that run are:

- `/var/tmp/xpf-wire-routing-separation-1789729350`
- `/var/tmp/xpf-wire-routing-separation-1789729374`
- `/var/tmp/xpf-wire-routing-separation-1789729613`

Each contains the committed `sfmix` stanza, including:

```
set routing-instances sfmix instance-type virtual-router
set routing-instances sfmix interface gr-0/0/0.0
```

The normalized pre/post configuration SHA in the owned attempt was
`f40e51f2208fa6e70070e58475501bfc504a108ee04dffd7e415b113baf09d91` on fw0;
the pre/post configuration was unchanged.

## Diagnosis

This is live kernel-state drift, not a product-code regression or a missing
fixture stanza.

The managed implementation is explicit:

- `pkg/routing/vrf_miss_terminator_9819.go` defines pref 2000 as the
  `l3mdev unreachable` terminator.
- `pkg/routing/vrf.go` calls `setVRFMissTerminator(..., true)` before creating
  any desired VRF and on every non-empty `Reconcile`; it removes the rule only
  when no VRF is desired or still owned.
- `docs/log/9819.md` records the same install/reassert/remove contract and its
  real-kernel validation.

The locked #10136 evidence showed the rule absent while `sfmix` remained in
committed configuration, then showed the manager restoring it when a temporary
RI commit forced a reconcile.  That rules out a persistent inability of the
managed component to create the rule.  The exact historical deleting actor is
not recorded; the supported attribution is external/manual kernel-state drift,
with no evidence of a product-code failure.  No raw `ip rule add` repair was
left behind by this lane.

## Baseline repair and clean-state proof

The manager-owned state was present when this lane acquired the lock, and the
#10136 temporary-RI add/delete path re-applied it through xpfd.  A later locked
post-deploy inspection at 2026-09-19T03:14:46Z showed, on **both** nodes:

```
IPv4 pref 2000: 2000: from all lookup [l3mdev-table] unreachable
IPv6 pref 2000: 2000: from all lookup [l3mdev-table] unreachable
vrf-sfmix: ... vrf table 488570 ...
```

The same locked inspection showed `vrf-sfmix` and `vrf-mgmt` in `ip vrf show`,
the committed `sfmix` stanza unchanged, and no `vrf-wire-10342` device.  A
separate locked check showed no `routing-instances wire-10342` configuration
path.  The running xpfd SHA at that clean check was
`3e9c9d14ed1544dca7a61f966f1c71d9eb180d4527af37514e648ad98ddee56c` on both
nodes.  The earlier locked check before the deploy had the same pref-2000,
VRF, and table state (running SHA
`be4dbb87790c6dcf65cebd822b9549d3fce25013468cbdca9379a68c4d0427b5`).

The shared lock owner was absent after each completed lane; no lock file was
removed or force-released.

## Harness repair and #10136 setup verification

The first post-repair run reached the live gate but still emitted
`harness-void`: the CLI actually prints
`commit complete: 1 statement(s) changed (...)`, while
`cli_commit_ri` required an exact bare `commit complete` line.  This was a
harness parser defect, not the #10342 baseline defect.

This branch changes `test/incus/wire-routing-separation.sh` to share a
line-anchored `cli_commit_succeeded` parser that accepts both the bare and
summary forms, rejects an embedded error mention, and is used by both RI
add/delete paths.  The full file selftest passed:

```
wire-routing-separation selftest: 12 passed, 0 failed
```

With that fix, the locked live setup reached the traffic oracle and completed
cleanup without the baseline VOID:

```
make test-wire-routing-separation
archive=/var/tmp/xpf-wire-routing-separation-1789786852
probe=1000 control=1500 probe_observed=0 control_observed=0 cksum_bad=0
pre_fw0_sha=f40e51f2208fa6e70070e58475501bfc504a108ee04dffd7e415b113baf09d91
post_fw0_sha=f40e51f2208fa6e70070e58475501bfc504a108ee04dffd7e415b113baf09d91
WIRE_GATE ... VOID reason=capture-blind
```

The finalizer emitted `capture-blind`, not `harness-void`: therefore the
RULE_SNAPSHOT was restorable and the tree-vs-baseline configuration comparison
was completed and equal.  A second locked run against the known WAN target
`172.16.80.200` produced the same independent capture-blind result while
again restoring successfully; its archive was
`/var/tmp/xpf-wire-routing-separation-1789787769`, with equal pre/post SHA
`51e5e059203f9290f7e22de3aeaa789df9f4b4ac6bff1875b7eb7f188af09a08`.
Those runs are setup/restore evidence, not claimed PASS/FAIL ledger rows.
The remaining capture-blind result is an independent #10136 peer-capture
environment issue; it is no longer the #10342 baseline-restore VOID.

## Verdict

**LAB-REPAIRED:** both loss-cluster nodes have the manager-owned sfmix
pref-2000 baseline, and the #10136 setup now reaches the live oracle with
verified rule/config restoration.  The harness parser correction is included
in this branch and is reported with `Refs #10342`; no product-code change was
made.
