# #15245: userspace-dp — fix cohort hot-path per-packet cost (A64-01)

## Summary

The pre-session screen stage allocated on every packet for a zone whose
screen reference did not resolve to an enforcing profile:

- **Inert** (profile defined, enables no check): `maybe_warn_inert_profile`
  (`userspace-dp/src/screen/unresolved.rs`) cloned the profile name
  (`r.profile.clone()`) and then built an owned map key with
  `entry(zone.to_string())` before consulting the WARN rate limiter — 2
  allocations per packet, even though the WARN is rate-limited to one per
  zone per second and the clone is only used when the WARN actually fires.
- **Missing/undefined**: `maybe_warn_missing_profile` built an owned key
  with `entry(zone.to_string())` on every packet — 1 allocation per packet.

Both are reached per packet via `missing_profile_verdict` from the
`check_packet_with_zone_id_opts` / `check_flowless_screens` `None` branches
(the gate `zone_has_screen_state` in `screen/mod.rs` admits inert and
missing zones), so a misconfigured-but-tolerated zone paid heap cost at
line rate for a once-per-second diagnostic. No enforcement was lost; this
is hot-path cost only.

## Fix (`userspace-dp/src/screen/unresolved.rs` only)

Per the A64-01 fix direction, both WARN helpers now:

- Look the rate counter up with `get_mut(zone)` (borrowed key) and only
  fall back to `entry(zone.to_string())` — allocating the owned key — on
  the first miss for that zone.
- Borrow the profile name only inside the `!limited` branch (the inert
  helper no longer clones it up front; the missing helper already held a
  borrow and keeps it, re-borrowed after the counter insert).

Behaviour is otherwise identical: same rate limiting
(`MISSING_PROFILE_WARN_RATE_LIMIT_PER_SEC = 1`), same WARN texts, same
counters, same substituted-conservative-default verdict from
`missing_profile_verdict`. No neighbouring path changes.

## Regression (`userspace-dp/src/screen/tests.rs`)

`unresolved_warn_steady_state_is_allocation_free_15245` drives the real
`check_packet` path for both states using the existing test-only counting
allocator (`crate::test_alloc::count_allocs`):

- Warms each zone (first packet emits the WARN and inserts the counter
  key), then asserts a second rate-limited packet in the same second
  returns `Pass` with **0 allocations** and no second WARN.
- Control: after a quiet gap (second 10) both zones re-WARN exactly once,
  proving the `!limited` branch still resolves the borrowed profile name.

On the pre-fix code the measured packet allocates (2 for inert, 1 for
missing), so the test is RED on `origin/master` by construction; the fix
makes it GREEN. Existing adjacent controls
(`missing_profile_reference_warns_and_is_rate_limited`,
`inert_profile_gets_the_substituted_default_7888`, the #7888 three-state
cells, `zone_with_no_screen_still_passes_silently_7888`) cover the
legitimate/no-screen and verdict behaviour through the same path.

## Validation

- RED (fix stashed, test present): `cargo test --bin xpf-userspace-dp unresolved_warn_steady_state_is_allocation_free_15245` fails — `left: 2, right: 0` on the inert leg, exactly the A64-01 count.
- GREEN (fix applied): same command passes (`1 passed`).
- Adjacent suite: `cargo test --bin xpf-userspace-dp 'screen::'` — 356 passed, 0 failed.
- At the original base the full test binary did not compile for a pre-existing unrelated reason (`afxdp/mirror/mod_tests.rs` missing new `MirrorConfigSnapshot` fields); rebasing onto latest `origin/master` picked up the upstream fix. The touched hunks are `cargo fmt`-clean (remaining `--check` diffs are pre-existing, outside these hunks).

## Risk

Diagnostic-path only. The one behavioural subtlety is ordering: the
profile name is now read after the rate counter increments rather than
before; both maps are only mutated by config updates on the same worker
thread, so the value read is the same. Rate limiting, WARN text, verdicts,
and exported counters are unchanged.
