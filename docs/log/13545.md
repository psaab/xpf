# Session-sync start exhaustion leaves a published dead object (#13545)

- **Issue**: #13545 — all 30 `SessionSync.Start` attempts can fail, after
  which the constructor still launches auxiliary loops while the failed sync
  object remains published to other daemon paths.
- **Cause**: publication happens before callback wiring and the bounded Start
  retry loop. Exhaustion previously had no unpublish or retry owner.
- **Change** (`pkg/daemon/daemon_ha_sync.go`): on exhaustion, unpublish the
  object only if its epoch and identity still match, then call `Stop` to cancel
  any partial resources from failed starts. Keep auxiliary-loop startup and
  retry bounds unchanged. The regression in
  `pkg/daemon/daemon_ha_comms_race_test.go` now drives `startClusterComms` with
  the loopback session-sync port held open, forcing real `SessionSync.Start`
  bind failures through all 30 attempts before asserting the published object
  was withdrawn.
- **RED evidence**: the original test manually called the cleanup helper and
  did not cover the production call site. Replacing the production exhaustion
  cleanup with a no-op made the constructor-level test fail as intended:
  `session-sync remains published after all Start attempts failed`.
- **GREEN evidence**: constructor-level regression and its three-run race check
  passed:
  `go test ./pkg/daemon -run TestSessionSyncStartExhaustionUnpublishesFailedObject13545 -count=1`
  and `go test -race ./pkg/daemon -run
  TestSessionSyncStartExhaustionUnpublishesFailedObject13545 -count=3`.
  `go build ./...` passed on the implementation PR. The full daemon package
  suite did not complete successfully in the shared environment: listener-
  binding tests reported `address already in use`, Unix socket tests reported
  `bind: invalid argument`, and the run timed out after 10 minutes.
- **Risk**: session-sync readers now observe `nil` after all bind attempts fail;
  a later comms restart constructs a fresh object. Auxiliary loops retain their
  existing behavior.
