# Issue #13957: Allow IPv4 tunnel outers to fragment downstream

## Why

Native GRE and userspace WireGuard outer IPv4 headers carried DF=1, but the
userspace tunnel endpoints do not consume ICMP Frag-Needed feedback and learn
an underlay path MTU. If a downstream path is smaller than the local egress,
large packets are silently lost. The local egress MTU guard cannot detect this
path-only reduction.

## What

WireGuard continues to emit IPv4 outer headers with DF clear. Native GRE now
supports a per-tunnel choice: absent `clear-dont-fragment-bit`, the IPv4
outer copies DF from the inner IPv4 packet (and uses DF=1 for an IPv6 inner);
configuring `set interfaces <gre-if> tunnel clear-dont-fragment-bit` forces
outer DF=0 so a downstream router can fragment. The option is carried through
the Go/Rust tunnel snapshot and the snapshot protocol is bumped to v49 so an
older dataplane cannot silently ignore an operator's choice. The GRE outer
header writer retains its advancing IPv4 Identification and recomputes the
header checksum. IPv6 outer headers and generated ICMP headers are unchanged;
no PMTU cache, reassembly, or extra packet allocation was added.

The original PR #14085's validation observed DF=1 in the GRE and WireGuard
regressions before that change and DF=0 afterward. Its focused suites passed:

- `cargo test --bin xpf-userspace-dp afxdp::frame::headers::tests::` — 27 passed.
- `cargo test --bin xpf-userspace-dp afxdp::frame::tests_nat_rewrite::` — 35 passed.
- `cargo test --bin xpf-userspace-dp afxdp::frame::wg::tests::` — 27 passed.

## Risk

WireGuard IPv4 outers always permit downstream fragmentation. Native GRE
copies the inner IPv4 DF bit by default; operators needing underlay
fragmentation for DF-set IPv4 traffic must enable
`clear-dont-fragment-bit`. IPv6 outers remain subject to IPv6 Packet Too Big
behavior. A two-hop underlay lab verification with reduced path MTU remains
outstanding.
