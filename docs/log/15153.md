# #15153 — userspace-dp: re-derive PPTP association on synced install (B11-01)

- **Timestamp**: 2026-10-19
- **Mechanism**: After a full reconcile / worker respawn, synced PPTP GRE
  sessions were replayed (`UpsertSynced` via
  `Coordinator::replay_synced_sessions` → `replicate_session_upsert`, the
  late replay `replay_late_synced_sessions`, and the #11360/#15105
  session-import repair re-read) but the PPTP call association that makes
  them matchable was not. The only producer of
  `WorkerCommand::InstallPptpAssociation` was the HA import fan-out in
  `ha/session_import.rs`, queued once per import on the old worker
  generation; a respawned worker starts with an empty `SessionTable`
  (`worker/loop_body/setup.rs`), so it held the `Pptp(H)` session but no
  association and the call's GRE data fell to the pre-#7699
  unassociated/flowless handling. The import push also discarded
  `push_bounded`'s refusal, so a queue-full import lost the association
  with no repair obligation.
- **Action**: `handle_upsert_synced`
  (`session_glue/commands/upsert_synced.rs`) now re-derives the association
  from `entry.pptp_call_ids` wherever a synced replica is installed: when
  the key discriminator is `Pptp(handle)`, the pair decodes via
  `PptpCall::from_wire_call_ids_in_domain(key.routing_domain, pair,
  src, dst)`, and the decoded handle equals the key's handle, it installs
  via `install_synced_association` (idempotent, preserves a local control
  binding). This one choke point covers the bring-up replay, the late
  replay, steady-state sibling replication, and the repair re-read, all
  of which funnel through `handle_upsert_synced`. Synthesized reverse
  companions carry `pptp_call_ids: 0`, so they decode to `None` and gain
  no association; a handle mismatch is likewise not re-derived (that
  disagreement is refused at HA import). At import, a refused
  `InstallPptpAssociation` push now records #11360 session-import repair
  debt on the forward key (positioned after the queue prefix at refusal,
  published before releasing the queue lock) and the import reports
  `AppliedRepairPending`/`AppliedRepairOverflow` instead of silently
  collapsing to `Applied`; the repair re-reads the shared entry and the
  re-derivation above installs the association. NOT changed: the queue
  cap, the drain budget, non-PPTP installs, or the local PPTP control
  path (`InstallPptpCall`/`broadcast_pptp_install`).
- **File(s)**: `userspace-dp/src/afxdp/session_glue/commands/upsert_synced.rs`,
  `userspace-dp/src/afxdp/ha/session_import.rs`,
  `userspace-dp/src/afxdp/coordinator/tests.rs`,
  `userspace-dp/src/afxdp/README.md`, `docs/log/15153.md`
- **Validation**: New cells in `coordinator/tests.rs`:
  `v42_b11_01_replay_queues_pptp_association_15153` seeds a PPTP forward
  entry (SyncImport origin + verified pair) in shared authority, drives
  the real bring-up replay into a fresh worker queue, drains it through
  `apply_worker_commands` into a fresh `SessionTable`, and asserts
  `resolve_in_domain` returns `Pptp(H)` in both directions plus controls
  (ordinary session still installs, unrelated call id stays
  unassociated); `v42_b11_01_refused_pptp_push_records_repair_debt_15153`
  fills the worker queue, imports with a PPTP call, and asserts
  `AppliedRepairPending` + repair debt, then drains through the real
  command/repair paths and asserts resolution. RED on unmodified
  `origin/master` (see PR), GREEN post-fix. Adjacent suites are the
  parent's gate.
- **Risk**: The re-derivation runs on every synced install whose key is
  `Pptp(_)`; it is a pure decode plus an idempotent map insert on the
  worker command path (control-plane paced, not per-packet). A pair that
  fails to decode or mismatches the key handle installs nothing, matching
  the import-time withholding discipline. The import-leg debt shares the
  bounded per-worker repair map (8192 keys); past that bound the outcome
  is `AppliedRepairOverflow`, which Go already treats as blocking HA
  takeover readiness.
