# #14137 FRR route-map deny with skipped/invalid route-filter — engineering history

Issue: psaab/xpf#14137 (FRR route-map deny with skipped/invalid
route-filter matches undefined prefix-list, later permit wins —
tolerant inherited-invalid). Lane branch: `fix/14137-campaign`, base
`origin/master` 4adefde7a.

## Defect (present at base)

`renderRouteFilterEntry` (`pkg/frr/prefix_list_render.go`) skips an
invalid route-filter entry — malformed prefix (including a match-type
keyword in the prefix slot, `route-filter longer exact`), unknown or
`through` match-type, malformed prefix-length-range, invalid `upto` —
and writes no inline prefix-list definition. `emitTermBody`
(`pkg/frr/policy_render.go`) nevertheless emitted
`match ip|ipv6 address prefix-list <inline>` against the then-undefined
list, documented as fail-closed because FRR resolves an undefined list
to NOMATCH. That is sound for a permit term (it simply never fires) but
fail-open for a `then reject` (deny) term: NOMATCH means the deny
sequence never terminates evaluation, so the route falls through to a
later accept or the BGP trailing `permit` default. The tolerant path
reaches this state directly (lenient load/peer-sync downgrades the
route-filter gate to a warning), and
`failClosedInheritedInvalidRouteFilters12687`
(`pkg/config/compiler_validate_strict_routing.go`) manufactures it by
turning an inherited invalid term into `Action="reject"` without
making its skipped filter match. The sibling dangling-reference rules
(#9881 as-path, #10822 community, #14136 from-prefix-list) already
rendered reject terms over absent lists as bare deny-all; no analogous
route-filter rule existed. A max-length `longer` (`10.0.0.0/32 longer`)
is NOT part of the defect: it is valid with a legitimately empty match
set, and its undefined-list NOMATCH behaviour must be preserved.

## Fix

- `pkg/config/compiler_validate_strict_routing.go`: new exported
  `RouteFilterEntrySkipped(rf)` — the single source of truth for "this
  entry's match set is unknowable" (malformed prefix, unknown/`through`
  match-type, invalid prefix-length-range via the existing
  `validatePrefixLengthRange`, invalid `upto` mirroring the renderer's
  upto arm including the #2102 max-length exact cases and the #12067
  unset-length case). `failClosedInheritedInvalidRouteFilters12687`
  now consults it, keeping its narrower `through`-operand test (a valid
  `through` stays historically tolerated, #12687) — and thereby also
  quarantines inherited malformed prefixes, which the old switch
  missed. Max-length `longer` is deliberately not flagged.
- `pkg/frr/prefix_list_render.go`: `routeFilterEntrySkipped` wrapper so
  the FRR term rule and the config quarantine share one predicate.
- `pkg/frr/policy_render.go`: route-filter term rule in
  `renderPolicyTermSequencesWithDefinitions`, mirroring
  #9881/#10822/#14136. Per family group (single group, or each half of
  a split mixed-family term): if every route-filter is invalid per the
  shared predicate, a reject term renders one bare deny-all sequence
  for that group and every other action (accept, non-terminating,
  next-policy) emits no sequence for that group — never a dangling
  inline `match ... prefix-list`, never a bare permit. A group with at
  least one non-invalid entry keeps its match line (route-filters are
  OR'd, so the rendered subset is the fail-closed direction), including
  a group whose only entry is a max-length `longer`.

Consumers updated for the changed output contract (previously asserted
the dangling matcher): `TestRouteFilterMalformedPrefixBelt` (lone
malformed / bad-octet / split subtests),
`TestGeneratePolicyOptionsPrefixLengthRangeAtOrBelowBaseSkipped`,
`TestGeneratePolicyOptionsThroughSkipped`, and the two `UptoLen==0`
subtests of `TestRouteFilterUptoFRR` (unset `upto` is strict-invalid
#12067, so its accept term now emits no sequence instead of degrading
to `le 32`; the renderer's degrade arm itself is unchanged for any
still-reachable caller).

## Residuals

- The renderer's `upto` degrade-to-`le maxLen` arm for `UptoLen==0`
  (non-max base) is now unreachable from `generatePolicyOptions` for a
  sole-invalid term, but remains as the belt for mixed groups where a
  valid sibling keeps the group alive; strict commit still rejects the
  form outright (#12067).
- `RouteMapSequenceCount` still counts an all-invalid route-filter term
  by its authored expansion while the renderer may emit fewer (or one
  deny-all) sequences. The bound is an admission upper bound;
  over-counting can only refuse earlier, never admit past FRR's
  ceiling (same posture as #14136).
