# #14851 — shim verifier headroom below the 15% floor

## Defect
The tracked `pkg/dataplane/userspace_xdp_bpfel.o` measured 908732
processed insns (9.13% headroom) on current master and was installed
with `XPF_SHIM_ALLOW_LOW_HEADROOM=1`, so
`pkg/dataplane/userspace_xdp_gate_verdict.json` recorded OVERRIDDEN
instead of a measured PASS. The #4555 floor (15%,
`UserspaceShimMinVerifierHeadroomPct`) existed so the next shim edit
would not discover the 1M processed-insn wall as a REJECT after the
work was done; an OVERRIDDEN verdict masks the true margin.

## Fix
Outline three small map-touching helpers in
`userspace-xdp/src/lib.rs` with `#[inline(never)]`, the
`session_action_for_key` precedent: `incr_fallback_stat`,
`is_interface_nat_destination`, and `live_userspace_session_action`,
plus `try_xdp_userspace` itself so the entry body stays in its own
subprogram (see the stack note below).
Inlined, each pays the per-calling-state verifier walk at every one
of its many call sites; outlined, the key construction and map read
are explored once. Measured on the pinned toolchain
(nightly-2026-05-23, bpf-linker 0.10.2) via `cmd/shimverify`:

- `is_interface_nat_destination` alone: 908732 -> 808826
- plus `live_userspace_session_action`: -> 800010
- plus `incr_fallback_stat`: -> 783950; plus the `try_xdp_userspace`
  outline: -> 813177 (18.68% headroom, PASS)

The tracked object, gate verdict, and freshness manifest were
regenerated with `pkg/dataplane/build-userspace-xdp.sh` (verifier
PASS, no override). Direct `shimverify` on the shipped object
confirms 813177 processed insns.

Alternatives measured and rejected: outlining the IPv6
extension-header walk or `parse_ipv6`/`parse_ipv4` (kernel REJECT —
packet-pointer range is lost across the subprogram boundary);
outlining `is_local_destination` (worse: 972340 with the NAT outline,
REJECT alone); outlining cpumap/session/steer helpers stacked
further (no additional saving, several REJECT).

## Risk
No behavior change: the three helpers keep identical bodies, keys,
and fall-throughs; only their BPF subprogram placement changed.
Each outlined call is one BPF-to-BPF call on paths that already
perform map lookups. The regenerated object must ship together with
the source change (the freshness manifest binds them).
