# Issue #14304 — S1 loaded-generation premise re-expression

- **Issue:** psaab/xpf#14304 (filed by post-merge hostile review of
  PR #14253 / issue #14139). Lane branch: `fix/14304-campaign` off
  `origin/master` 7ade1a12a.
- **Scope:** test-premise repair only. No production behaviour change;
  the #14139 render belt and commit gate are correct as merged.

## Defect (present at base)

`TestIPsecAttributionFollowsLoadedGenerationOnFailedAddition9511`
(S1, `pkg/daemon/ipsec_sa_rg_9511_test.go`) asserts that with loaded
generation C0 and promoted generation C1, the name `blue-red` follows
C0: an RG1-only owner initiates it (it is only VPN `blue`'s child,
selector `red`, anchored on reth1/RG1), and an RG2-only owner skips
it. That premise needs `blue` to RENDER `blue-red` as a child in C0.

`blue` carried no pre-shared key in the shared fixture
`blueOnRG1_9511`. Before #14139 that still rendered a live
uncredentialed `auth = psk` connection (the #14139 defect itself);
after #14139's render belt, a PSK VPN with no effective secret is
skipped by name, so `blue` rendered nothing and `blue-red` resolved
to no candidate — the RG0 default, which RG0-declared fixtures skip
for both owners. The first S1 assertion therefore failed. The #14253
migration had added a key only to the standalone `blue-red` VPN
(which renders in C1), never to `blue`.

The same keyless `blue` silently broke every sibling cell built on
`blueOnRG1_9511` — the #9641 charon-generation cells
(`TestAttributionFollowsCharonsGenerationAfterARestart9641`,
`TestAttributionFollowsCharonThroughTheFailedReloadWindow9641`,
`TestAttributionFallbacksKeepThePromotedAnswer9641`,
`TestCharonsGenerationIsResolvedOncePerWave9641`,
`TestAttributionDropsTheMarkerWhenAnApplyOverlapsThePass9641`,
`TestAttributionAfterAnOverlapReReadsTheRecord9641`,
`TestAttributionResolvesTheLastLoadedGenerationAfterManyFailedWrites9641`,
the last also refusing `blue` at strict commit),
`TestAttributionFallsBackToPromotedConfigBeforeFirstLoad9511`
(fixture guard: `blue-red` must be `[blue,blue-red]`, got
`[blue-red]`), and `TestAmbiguousSANameNeedsDeclaredRG0_9511`
(its inline fixture lists `blue` and `blue-red` without keys; got
`[0]`, want `[0 1]`). In the #9641 cells the hand-written charon
listings already describe the credentialed tunnels, so only the
rendered index disagreed.

## What

- `blueOnRG1_9511` gains
  `set security ipsec vpn blue pre-shared-key fixture-secret`, so the
  credentialed `blue` renders its `blue-red` child in every
  generation that includes it — C0 and C1 alike. This IS the
  re-expression the #14139 log suggested: `blue-red` is rendered in
  C0 only via a child name (blue's), and in C1 additionally as a
- `TestAmbiguousSANameNeedsDeclaredRG0_9511`'s inline `blue` and
  `blue-red` gain the same key, restoring its `[RG0 RG1]` span.
- The adjacent #9139 sa-sync-OFF control
  (`TestApplyRethServicesForRGRespectsSASyncFlag9139`) failed on the
  same base at strict commit for its keyless `vpn-rg1` — the same
  incomplete #14253 fixture migration, found by widening the run to
  `9139`; it gains the same key so its OFF measurement is reached.
- S1 gains FIXTURE guards pinning both index shapes before the
  attribution assertions: C0 renders `blue-red` as `[blue]` only and
  C1 as `[blue,blue-red]`, so a future fixture regression that stops
  `blue` rendering fails at the premise instead of masquerading as an
  attribution change. The #9511 assertions themselves are unchanged
  and unweakened.
