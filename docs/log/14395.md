# Issue #14395 — Feed content-churn guard compares only against the immediate predecessor

- **Issue:** `contentChurnTripped` was called with `fs.prefixes` (the immediate predecessor), so three successive 51%-retained equal-count rotations dropping surviving originals first (51% → 2% → 0% of originals) fully replaced a denylist/allowlist with zero refusals. Count-side epoch (`shrinkHighWater`) already existed; content side had no epoch anchor, and `shrinkHighWaterHash` is rotated on every equal-count install so it cannot serve as one. Origin DR8-H5, validated at `origin/master`.
- **Fix (`pkg/feeds/feeds.go`):** New epoch content baseline `feedState.epochContentPrefixes/epochContentHash` — the exact set installed at bootstrap or at an acknowledged (`guardBypass`) install. `installSnapshot` measures `contentChurnTripped(churnBaseline, candidate)` against the epoch (fallback to installed set only while no epoch exists). Ordinary unacknowledged installs never rebase the epoch; acknowledged installs rebase epoch + count high-water. Churn refusal reason/error now name epoch content overlap; the ack tuple binds epoch hash + epoch count; `AcknowledgeFeedShrink` accepts the live epoch hash as current baseline. Persistence: `ShrinkHighWater.Prefixes` (JSON `prefixes,omitempty`) carries the epoch set through `ShrinkHighWaterSnapshot`/`RestoreShrinkHighWater` (accepted only if canonical, ≤ cap, and digest-matched; pre-fix records restore count-only and re-bootstrap with the existing audit warning) and `carryForwardSnapshot`/Apply history restore. Predicate/thresholds, count guard, #12882 hold-drop pin, and bootstrap warning unchanged.
- **Docs:** `pkg/feeds/README.md` drastic-shrink section updated for epoch content baseline, ack-rebase, and persisted epoch set.
