# Issue #16078 — FA-02: user-identification stanzas inert marker

## Why

User-identification stanzas (`services user-identification …` /
`security user-identification …`: AD, JIMS/identity-management, local
authentication table, device-information, authentication-source) commit
wholly inert — no user-identification engine consumes them — while their
credentials (client-secret / shared-secret / bind password) are stored
for a non-feature. The accepted-only warning (#10947) fires at commit,
but no `show`/`status` surface carried an inert marker, so
`show configuration` displayed the stanza as ordinary (apparently live)
configuration and an operator could believe identity-based policy was
enforced when nothing enforces it. Severity Low: the policy half
(`then permit firewall-authentication`) hard-rejects (FA-01), so no
silent widened permit is constructible; the residual is the
stored-credential + operator-belief gap.

## What

- Shared detection/record in pkg/config
  (`user_identification_status_16078.go`): the stanza walk formerly
  private to `userIdentificationWarnings` is extracted to
  `userIdentificationStanzasIn` (plus `userIdentificationPresent` for the
  bare-stanza generic fallback), so the commit warning and the status
  marker can never disagree. `compileSections` records the deduplicated
  stanza names on the compiled `Config`
  (`userIdentificationStanzas`, `json:"-"`, compile-time only; the
  authored stanza stays in the raw AST). `Config.UserIdentificationConfigured()`
  exposes them.
- Shared renderer `config.RenderUserIdentificationStatus`: lists each
  configured stanza as
  `INERT (accepted-only; no runtime effect)` and states that no
  identity-based policy is enforced and stored credentials are unused.
  Unconfigured renders `No user-identification configured`; nil renders
  `No active configuration`. It never reads enabled/active.
- New operator commands on every surface, all delegating to that one
  renderer: `show services user-identification status` and
  `show security user-identification status` — local CLI
  (pkg/cli), remote CLI (cmd/cli), gRPC ShowText topics
  `user-identification-status` / `security-user-identification-status`,
  REST show-text (same topics). Command tree (pkg/cmdtree) and topic
  registry (pkg/optopic, PermView) gain the two commands; the frozen
  #16136 contract gains their rows by hand.

## Validation

  referenced `UserIdentificationConfigured` / `RenderUserIdentificationStatus`
  before they existed (build failure).
- `go test ./pkg/config/ -run '16078|10947|15943|15655'` — pass

  flat-duplicate collapse, bare-stanza fallback preserved).
- Surface tests: pkg/cli, pkg/api (both topics through the REST handler),
  pkg/grpcapi renderer tests for #16078 — pass.
- Registry/census suites (pkg/cmdtree, pkg/optopic, pkg/grpcapi
  #16136/#5278/#6532) run as part of the PR checks.

## Risk

Additive only: no stanza is newly rejected, no credential handling
changes (redaction is FA-04 / #15981 cohort, untouched), and the
compile-time record is `json:"-"` so no wire/snapshot shape moves.
A config compiled by an older binary and JSON-round-tripped loses the
record and renders "No user-identification configured" — fail-closed
toward not claiming enforcement, matching the other `json:"-"`
compile-time records.
