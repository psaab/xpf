# Issue #16452: dpkg triggers interest dead ESP paths (R3-A57-02)

## Why

`debian/xpf.triggers` declared `interest-noawait` on
`/boot/efi/EFI/ubuntu/{shim,grub,mm}x64.efi`, and the docs promised the
A/B slot loaders refresh "immediately on a bootloader package update
... no reboot needed" (#15089). That never happened: the real
`shim-signed` and `grub-efi-amd64-signed` packages ship only `/usr/lib`
payloads (`/usr/lib/shim/*`, `/usr/lib/grub/x86_64-efi-signed/*`), and
their postinsts run `grub-install`, which writes the ESP outside dpkg's
file tracking. No package unpacks a file under `/boot/efi/EFI/ubuntu`
(`dpkg -S` finds no owner), so the file trigger never fired and
`xpf.postinst triggered` never ran on a bootloader update. The slots
stayed stale until the next boot's `sync_ab_slots`. While #16449's
defect holds the gap is masked (firmware boots `EFI/ubuntu`); once it
is fixed, the first reboot after an update would still run the stale
slot loader once.

## What

- `debian/xpf.triggers`: interest now on what dpkg actually unpacks —
  `interest-noawait /usr/lib/shim` and
  `interest-noawait /usr/lib/grub/x86_64-efi-signed` (directory
  interests covering every present/future loader name in those trees,
  `.signed` and unsigned). dpkg processes file triggers after the
  triggering package is configured, i.e. after its postinst has
  already re-run `grub-install` and refreshed `EFI/ubuntu`, so the
  triggered `--sync-only` copies the NEW loaders into both slots.
- `debian/xpf.postinst`: `triggered` arm comment corrected to the
  `/usr/lib` mechanism (arm body unchanged).
- `docs/install-images.md`: same correction to the "immediately on a
  bootloader package update" bullet.
- `scripts/image/test_slot_refresh_15089.py`: the trigger-wiring cell
  now pins the `/usr/lib` interests and rejects any `/boot/efi`
  interest; new `RealDpkgTriggerTests` cell builds probe .debs
  carrying the REAL `debian/xpf.triggers` + the REAL postinst
  `triggered` arm (extracted verbatim, helper path rewritten to a
  sandbox copy of the real `xpf-uefi-slots`) plus fake shim/grub
  providers whose postinsts mimic grub-install's ESP copy, then
  installs/upgrades them with the system dpkg in a chrootless sandbox
  (private `--root`/`--admindir`, `--force-not-root
  --force-script-chrootless`; no host dpkg state touched) and asserts
  "Processing triggers for xpf" plus byte-equal v2 slot copies with no
  reboot — the issue's VM WITNESS at hermetic scale.

Alternatives considered: an apt `DPkg::Post-Invoke` hook (rejected in
#15089 and here — runs per apt invocation rather than per dpkg
transaction, misses direct `dpkg -i`, and can fire before configure).

## Validation

- RED at the pre-fix triggers: with `debian/xpf.triggers` reverted to
  the ESP interests, the suite fails 2 cells — the shape pin and the
  real-dpkg witness (`'Processing triggers for xpf' not found`, slots
  stay on v1). GREEN after the fix: 20 tests pass
  (`python3 scripts/image/test_slot_refresh_15089.py`).
- Mutant control (#16644's probe, now covered as a side effect): with
  the postinst arm's helper renamed to `xpf-uefi-slots.disabled`, the
  real-dpkg cell fails (`xpf-A still boots the stale shim`). Reverted.
- Host evidence for the payload paths: `dpkg -L shim-signed` lists
  only `/usr/lib/shim/shimx64.efi.signed`; `dpkg -L
  grub-efi-amd64-signed` lists only
  `/usr/lib/grub/x86_64-efi-signed/*.efi.signed`; the provider
  postinsts on disk run `grub-install` on configure.

## Risk

- Directory interests fire on any change under the two payload trees,
  including `fbx64.efi`/`gcdx64.efi` updates that do not change the
  slot loaders; the triggered sync is cmp-gated, so an in-sync slot is
  not rewritten (no needless ESP writes).
- `interest-noawait` + best-effort arm unchanged: a failed refresh
  never blocks the bootloader package's configure, and the boot-time
  sync remains the backstop. No fail-open weakening.
- Residual: the full VM witness on a baked image (`apt install
  --reinstall shim-signed grub-efi-amd64-signed` + `cmp` across
  `EFI/{ubuntu,xpf-A,xpf-B}` without reboot) was not run in this lane;
  the hermetic real-dpkg cell exercises the same dpkg trigger
  machinery, postinst arm, and helper code paths.
