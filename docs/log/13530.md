# Issue #13530: Normalize DNAT prefix lengths

`DnatTable::from_snapshots` parsed destination prefixes and DNAT source-address
constraints directly with `ipnet::IpNet`. The Go NAT gate accepts decimal
prefix lengths with leading zeros, including IPv4 `/024`; Rust rejected these
CIDRs and silently narrowed/fell back the destination or dropped a scoped
source entry. Both DNAT axes now normalize prefix lengths before parsing, and
the static-NAT source-list parser uses the same existing normalization rule.

The shared `testdata/nat_match_prefix_corpus.txt` now includes leading-zero
boundary cases. Rust and Go corpus checks consume this file; a DNAT end-to-end
regression verifies `/024` destination and source scope translate together
without weakening the scope.

Validation:
- RED on pristine `origin/master` (`98d56af14`):
  `cargo test dnat_prefix_length_normalization_applies_to_both_axes_13530`
  failed as expected: both `/024` prefixes were reported unparseable and the
  test's expected translation was `None` instead of `Some(10.0.0.5)`.
- GREEN: the same test passed; full Rust suite passed (7,953 passed, 8 ignored).
  Destination tests passed (67); shared-prefix corpus tests passed (3).
- Go corpus gate and wrapper tests passed:
  `go test ./pkg/config -run 'TestGoGateMatchesTheSharedCorpus7481|TestExportedWrapperAgrees7481'`.
- `gofmt -l` on the Go files returned no output.
- `cargo clippy --bin xpf-userspace-dp -- -D warnings` is blocked by four
  pre-existing Clippy errors in `userspace-dp/build.rs` (three
  `collapsible_if`, one `needless_borrow`); no build-script changes were made.
