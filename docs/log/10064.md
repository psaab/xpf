## Verdict (split — decided with evidence, not by binary)

- **Retry/generation adoption (failure 3): CORRECT, keep.** It is deliberate
  #9642 behavior, pinned by #9642's own update to
  `TestAFailedRetryAfterAConflictStillFailsClosed9520/conflict_then_transport_error`
  — which drives the TICK path — and it implements #10041's repair direction
  #1 ("adopt-or-repair retained generation on failed retry").
- **Same-generation tick adoption (failures 1–2): REGRESSION, narrow.**
  Un-deliberated: zero #9642 cells drive a resampled tick (no
  `partialOutcomeUnknown` in `retry_debt_9642_test.go`). It contradicts the
  drop-the-copy-on-failure norm at the other three resampling publishers
  (overlay/scheduler/worker-arm call `requestApplySnapshotLocked` directly
  and drop `next` on failure). It buys no retry: the tick only publishes
  when `published < last.Gen`, so the gate is already open. Its side
  effects are unmotivated on this path: `m.cfg` rewrite (identity in
  production — see below — clobber in fixtures), an HA-clear obligation no
  Compile tail owes, and a transition Warn for nothing newly retained.

Production invariant behind the Cell-2 half: `lastSnapshot.Userspace ==
m.cfg` holds at every tick in production (builder sets `Userspace: ucfg`;
deferral/success set both; the adopt arm sets both; scheduler/overlay/
worker-arm preserve `Userspace` and never write `m.cfg`; the 9642 harness
obeys via `buildSnapshot`). The 9824 fixture's zero-`Userspace` hand snaps
violate it — latent, and unobservable again after the narrowing (no 9824
cell applies after a tick retry). No fixture change; the wart is noted here
for future lanes: set `Userspace` on hand snaps (production builder always
does) before any apply-after-lost-tick-retry script.
