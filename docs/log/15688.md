# Issue #15688 — Duplicate VRRP instance identities abort the whole node

CompileConfigStrict accepted duplicate `(kernelInterface, VRID, family)`
VRRP groups (same VRID under two addresses of one unit+family, via the
`"<address>_grp<id>"` parse keys) and explicit groups whose VRID equals a
RETH-derived `100+RG` VRID on the same kernel device. Both shapes reach
`vrrp.Manager.UpdateInstances`, which returned a whole-batch error
("duplicate VRRP instance identity" / "overlapping VRRP election domains"),
aborting reconciliation for every VRRP instance on the node on each 2s
reconcile tick.

## Change

- `pkg/config/compiler_validate_strict_vrrp_identity.go` (new):
  `validateVRRPInstanceIdentityStrict` walks the exact keys produced by
  `CollectInstances` (`ResolveKernelIfName`, family derived from the group
  key's parent address mirroring `vrrpGroupFamily`) and
  `CollectRethInstances` (`RethRGOwners`, `rethKernelIface`, VRID
  `100+rgID`, empty family, skipped under `no-reth-vrrp` /
  `private-rg-election` and for out-of-range RETH VRIDs). A duplicate
  `(kernelIf, VRID, family)` or an empty-family RETH `(kernelIf, VRID)`
  overlapping a family-tagged instance hard-rejects naming both groups.
  Dual-stack (same VRID, distinct families) and distinct kernel devices
  stay legal.
- `pkg/config/compiler_uniformgates_cluster_zone.go`: dispatch the gate
  after the #14407 cross-group gate; `pkg/config/compiler_opts.go`:
  `lenientVRRPInstanceIdentity` downgrades it to a warning on tolerant
  load / peer-sync paths (#1960 no-brick).
- `pkg/vrrp/manager.go`: `UpdateInstances` now refuses only the second
  duplicate/overlapping claimant via the existing `rejectedDesired`
  pattern (retains any running instance for that key, records the refusal
  in `unbuiltDesired`, WARN log) instead of returning a whole-batch error,
  so a leniently-loaded collision seats the rest of the desired set.
- `pkg/config/README.md`, `pkg/vrrp/README.md`: documented the gate and
  the per-instance runtime refusal.
- Existing manager tests updated from whole-batch rejection to
  skip-only semantics.

## Regression

- `TestVRRPInstanceIdentityDuplicateSameUnitFailsCommit` /
  `...DuplicateInet6FailsCommit`: duplicate VRID under two addresses of
  one unit+family (inet and inet6 spellings) rejected.
- `TestVRRPInstanceIdentityExplicitVsRethFailsCommit`: explicit group 101
  on `reth0` colliding with RETH RG1 (VRID 101) rejected; not rejected
  under private RG election.
- `TestVRRPInstanceIdentityDualStackSameVRIDCommits`,
  `...DifferentVRIDsCommits`,
  `...DuplicateRethInterfacesFailsCommit` (distinct RETH devices):
  controls commit.
- `TestVRRPInstanceIdentityLenientWarns`: lenient compile succeeds and
  warns naming the duplicate identity.
- `TestUpdateInstancesDuplicateIdentitySkipsOnlyDuplicate15688` /
  `TestUpdateInstancesRethOverlapSkipsOnlyOverlap15688`: the runtime
  batch seats the first claimant and unrelated instances, records the
  refusal, and returns nil.
- `TestManagerUpdateInstances_SkipsDuplicateIdentityKeepingExisting` /
  `..._SkipsRethGenericWireOverlapInEitherOrder`: updated pins for the
  skip-only semantics.

## Validation

- RED on pristine worktree (only new tests): config duplicate/RETH/lenient
  tests and both `15688` manager tests fail as described in the issue.
- GREEN: `go test ./pkg/config/ -run TestVRRPInstanceIdentity -count=1`
  and `go test ./pkg/vrrp/ -run '15688|TestManagerUpdateInstances_Skips|...'`
  pass; neighbouring VRRP/RETH config suites pass.

## Risk

- Operators with duplicate VRID groups on one unit+family or an explicit
  group numbered `100+RG` on its RETH device must renumber or remove one
  group; strict commit now rejects, lenient load warns and seats only the
  first election. Whole-node VRRP outage from such a collision is removed.
