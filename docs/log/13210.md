# Issue #13210 — NAT64 allocator ownership for `+96`

## Root cause

`NormaliseNAT64PrefixForSnapshot` strips a leading `+` from the NAT64 mask because the dataplane accepts it. The NAT64 ownership key used by the #9555 shadow detector and #5144 external-tuple overlap gate instead parsed masks with `strconv.ParseUint` directly, rejecting `+96`. Tolerant-load/peer-synced `64:ff9b::/+96` rules therefore installed as `64:ff9b::/96` in the dataplane but were omitted from both ownership analyses.

## Change

Use `dataplaneAcceptsNAT64Mask` in `nat64PrefixOwnerKey`, so the owner key follows the dataplane's mask grammar while keeping invalid masks and non-/96 values fail-closed. Update the helper comment to distinguish dataplane acceptance from the stricter canonical commit gate. Add a regression covering canonical key equivalence, #9555 shadow ownership, and invalid-mask controls.

## Risk

The change only classifies a NAT64 prefix as an allocator owner when the dataplane accepts its mask and address shape. Invalid and unsupported masks remain excluded; canonical commit validation remains strict.
