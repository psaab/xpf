# Issue #12812 — poison 3-key from-zone policy contexts

## Why

`compilePolicies` handles combined zone-pairs only when the `from-zone` node has
at least four keys. Its nested-to-zone poison path previously covered only the
two-key form. The three-key form, such as
`from-zone A X { to-zone { B { policy p1 { ... } } } }`, reached neither path:
the tolerant compiler created no `MalformedZonePairs` entry, while strict
validation rejected the nested `to-zone`. An omitted deny could therefore fail
open under a permit-all default.

The same tolerant diagnostic also inspected only the first policy-bearing child
under one keyless `to-zone`; later policy-bearing destination children had no
named malformed-pair record.

## What

- Record policy-bearing direct `to-zone` contexts for both two-key and three-key
  `from-zone` nodes using the existing malformed-pair poison carrier.
- Emit a named record for every policy-bearing child below keyless `to-zone`,
  rather than naming only the first child. Keep the existing diagnostic for
  keyed `to-zone` contexts.
- Add tolerant and strict regression tests for 3-key keyless/keyed/nested and
  later-sibling forms, per-destination records, the snapshot poison locator,
  and an unchanged valid combined pair.

## Validation

- RED before the fix:
  `go test ./pkg/config -run '^(TestTolerantThreeKeyFromZonePoison12812|TestTolerantToZoneRecordsEveryPolicyBearingChild12812|TestValidCombinedZonePairNotPoisoned12812)$' -count=1`
  failed because each 3-key shape recorded nothing, and because multi-child
  keyless contexts produced only one named record.
- GREEN after the fix: the same command passed.
- Full package/build checks and delivery evidence are recorded when run.

## Risk

Malformed, strict-rejected nested zone-pair contexts now install the existing
tolerant snapshot poison and may produce additional diagnostics for each
policy-bearing destination. Valid combined zone-pair compilation is unchanged.
