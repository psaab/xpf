# #16719 — non-first commit-confirmed timeout discarding staged edits reported as a successful commit

- **Timestamp**: 2026-10-25
- **Action**: A non-first `commit confirmed` window (active A, confirmed
  C) with staged edits C' let a parked bare `commit` report success for
  edits that were never applied. The handler authorized and summarized
  C→C', the commit parked on `applySem`, the confirm timer's
  `executeConfirmedRollback` won the semaphore, `PromoteRollback` reset
  active/candidate to A and cleared `dirty`, and — because the #15055
  holder-epoch bump was scoped to the first-commit branch — the parked
  commit then bound the reset generation, promoted A as a no-op,
  applied it, and returned "commit complete: N statement(s) changed"
  with the pre-rollback C→C' summary while A ran and no timer remained.

  Fix: `PromoteRollback` now captures `dirty` before the reset and, when
  the rollback actually discarded a dirty candidate, advances a new
  dedicated monotonic `rollbackDiscardGen` counter (deliberately not
  `holderEpoch`: the holder never turns over in this shape, so pre- and
  post-discard mints by the same holder share a holderEpoch and no
  ordering on it separates them — `<` misses the stale mint, `<=` wedges
  every later commit by that holder). Every `AuthorizeCommitAs` mint
  (holder and epoch-bound internal) records `discardGen`;
  `verifyCommitAuthorityLocked` refuses a mint whose recorded value
  differs from the current counter with the new
  `ErrCommitConfirmedRolledBack` sentinel — never a generation conflict
  (the daemon retry would adopt the reset candidate) and never a holder
  turnover (the holder did not change). Directly-constructed
  `InternalCommitter` authorities record no mint value, so the daemon
  fences them at the semaphore: `commitAndApply` /
  `commitConfirmedAndApply` sample `RollbackDiscardGen()` before
  `applySem.Acquire` and `commitWithGenBinding` re-checks it via
  `PromotionStale` before every promotion attempt, refusing with the
  same sentinel. A clean (non-dirty) rollback discards nothing, advances
  nothing, and keeps the holder's authority valid (the #15055 control,
  preserved); a fresh mint after a discard records the new counter and
  commits normally.

  NOT changed: the first-commit #15055 epoch bump and bootstrap
  recheck (unchanged); boot-recovery rollback in
  `recoverPendingConfirmLocked` (no commit can be parked across a
  restart, so no authority can straddle it); the standalone CLI's
  non-Gen `CommitWithDescriptionAs` path (no applySem race — the timer
  executor and the commit are the same goroutine's store).
- **File(s)**: `pkg/configstore/commit_authority.go` (sentinel,

- **Validation**: See PR for the run record. Targeted:
  `go test ./pkg/configstore/ -run '16719|15055'` and
  `go test ./pkg/daemon/ -run '16719|15055|TestCommitWithGenBinding|TestCommitSeam|TestRenameAncestry'`,
  plus the neighbouring commit-authority suites. RED-on-revert: dropping
  the dirty capture in `PromoteRollback` leaves `rollbackDiscardGen` at
  its prior value, so the parked commits promote A and return success;
  dropping the `PromotionStale` fence does the same for the internal
  arm; dropping `verifyRollbackDiscardLocked` does the same for the
  holder arm.
- **Residual**: The gRPC/REST handlers still return the pre-rollback
  diff summary only on success — a refused commit now returns the
  rolled-back error with no summary, which is the acceptance behaviour.
  No lab/cluster smoke in this lane (store/daemon unit race cells are
  the executable substitute).
