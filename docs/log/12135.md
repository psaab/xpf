# Issue #12135 — honor external networkd matching before unmanaged teardown

## Why

`FindExternallyManaged` stored the entire `Name=` value as one literal key, so a matching glob or whitespace-separated list did not identify an unmanaged interface. `Manager.Apply` then emitted an earlier-sorting `10-xpf-*.network` with `ActivationPolicy=always-down`. The compiler also stripped addresses and brought unconfigured interfaces down before `networkd.Apply`, even when an external `.network` file owned the link.

## What

External matching now parses `[Match]` rules from non-xpf `.network` files and supports systemd `Name=` glob lists (including whole-list negation) and normalized `MACAddress=` lists. Name and MAC predicates in one rule are conjunctive; unsupported match keys are conservatively ignored. `Manager.Apply` skips externally matched unmanaged interfaces, and the compiler consults the same matcher before address removal or link-down, so stale xpf units can be swept and the external file can own the link.

Both failures were reproduced on the clean STEP-0 base with the same tests; they concern unrelated import-allowlist / HA wording checks.

## Risk / residual

Only `Name=` and `MACAddress=` match predicates are evaluated. Rules with other `[Match]` keys are conservatively ignored because this compiler path cannot determine those properties; such external ownership still is not recognized. No deployment has been performed.
