# Issue #12135 — honor external networkd matching before unmanaged teardown

## Why

`FindExternallyManaged` stored the entire `Name=` value as one literal key, so a matching glob or whitespace-separated list did not identify an unmanaged interface. `Manager.Apply` then emitted an earlier-sorting `10-xpf-*.network` with `ActivationPolicy=always-down`. The compiler also stripped addresses and brought unconfigured interfaces down before `networkd.Apply`, even when an external `.network` file owned the link.

## What

External matching parses `[Match]` rules from non-xpf `.network` files. `Name=` follows systemd's per-word negation model across repeated assignments and mirrors glibc `fnmatch(..., flags=0)` for the covered pattern forms. Systemd consumes field-level backslashes before `fnmatch`; POSIX named classes containing `:` are rejected by its interface-name parser. Those syntaxes have helper-only coverage, not file-level parity claims. Normalized `MACAddress=` lists include systemd's supported colon-, hyphen-, and dotted EUI-48 spellings. Name and MAC predicates in one rule are conjunctive. `Manager.Apply` skips an unmanaged interface when its supported predicates match, even if other keys are unknown, preventing a potentially external owner from being overridden by a durable `always-down` unit. The compiler uses the stricter matcher and skips address removal/link-down only when its supported predicates establish a match.

## Risk / residual

Apply retains master's conservative durable behavior for conjunctive rules: when supported `Name=` / `MACAddress=` predicates match, an unknown additional key does not cause xpf to write an earlier-sorting `always-down` unit. The compiler cannot prove those unknown keys, so it does not skip teardown for such a rule; runtime networkd may therefore configure a link after the compiler has stripped it. Alternative interface names are not supplied to the matcher, and IPoIB's 20-byte hardware addresses are not supported. The parser accepts IP literals, but production matching uses interface hardware addresses from `net.Interfaces().HardwareAddr`. **NEEDS-OWNER-DECISION:** `Name=*` now exempts matching unconfigured NICs from xpf's strip and durable `always-down` behavior, so an external file (for example DHCP) can bring them up outside xpf zones and host-inbound policy. Do not add a catch-all guard without owner approval.

The hyphen-as-range-start FAMILY (`Name=eth[--0]` on `eth.` plus 861 sibling combos such as `[--9]`, `[!--X]`, `[a-b--c]`) remains an identified glibc divergence family: glibc reads atom-`-` as a range whenever followed by `-`+non-`]` while xpf treats the first hyphen literally. Likewise, collating/equivalence symbols as RANGE ENDPOINTS (`eth[[.a.]-z]`, `eth[a-[.b.]]`) form real C-locale ranges in glibc that xpf does not (harm direction: systemd-owned link misread — e.g. `eth[[.a.]-z]`/ethb owned by systemd via a..z, xpf writes always-down). Both families are pre-existing at parent (overlay set-diff verified) and excluded from the in-scope differential corpus above. Note: the caret/reversed-range fixes flip 261 absurd double-hyphen combos (e.g. `[^--a]`, `[!--z-9]`) from accidental parent-agreement to divergence by unmasking the hyphen mis-parse; direction is safer (withhold always-down), syntax outside realistic configs.

`Name=` field-level escapes such as `\!eth0` and `eth\[!0]` are out of parity scope: systemd's `extract_first_word(..., 0)` removes backslashes before calling `fnmatch`. The direct matcher helper still has tested in-pattern escape behavior, but file assignments do not reach it unchanged. This change adds only six-byte EUI-48 dotted parsing; existing IP-literal handling is unchanged. Other non-IP systemd hardware-address spellings at 4-, 16-, and 20-byte lengths remain out of scope; IPoIB's 20-byte addresses are unsupported.
