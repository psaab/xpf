# #16653: status poll applied a stale reply over a newer disarm

- **Timestamp**: 2026-10-25
- **Action**: `statusLoop` (`pkg/dataplane/userspace/process_status.go`)
  released `m.mu` for its 1 Hz `status` RPC and, on re-lock, fenced the
  reply only on helper process identity (`proc`/`procGen`) and the
  link-cycle lease. A status applied by a concurrent mutator while the poll
  was off-lock — a durable fail-closed disarm
  (`disarmSnapshotProtocolFailureLocked`, `disarmBeforeUnsupportedPublishLocked`),
  an RG update, or a snapshot apply — was then overwritten by the older poll
  reply, so `userspace_ctrl.Enabled=1`, ready binding rows and
  `lastStatus.ForwardingArmed=true` (a TakeoverReady input) returned for up
  to one poll tick, and that tick's `syncDesiredForwardingStateLocked` saw
  no delta to correct it. The poll now snapshots `m.lastStatusSeq` before
  dropping `m.mu` and discards the reply if any other status was applied in
  between (every apply bumps that sequence via `setLastStatusLocked`),
  using the same whole-tick discard shape as the existing link-cycle fence.
  All serviced actions are level-triggered on persistent state, so the next
  tick re-evaluates against the newer cached status. The owner-RG export
  pager sibling (R3-B16-02) needs no change: it was already closed by
  #16518 (`SuppressStatus` on every page, pager never applies a page
  status), verified present on this head.
- **File(s)**: `pkg/dataplane/userspace/process_status.go`,

  `docs/log/16653.md`
