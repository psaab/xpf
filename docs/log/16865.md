# Issue #16865: IS-IS NET only from `protocols isis net`; Junos `family iso address` unmodelled

- **Timestamp**: 2026-10-25
  - **Action**: Modelled `interfaces <if> unit <n> family iso address <NET>`
    (schema leaf validated by `ValidateISISNET`, compiled into
    `InterfaceUnit.ISOAddresses`), derived `ISISConfig.NET` per scope
    from that scope's own interfaces (lo0 first) when no explicit
    `protocols isis net` was authored (`resolveISISNETFromISO16865`
    in P5 derivations; RI scope follows `RoutingInstance.Interfaces`
    ownership, fold F2), and gated an enabled IS-IS scope with
    interfaces but no derivable NET: strict commit rejects, tolerant
    load warns (`lenientISISNETPresence16865`, #1960) and the FRR
    renderer withholds the whole `router isis` stanza. NET identity
    compares canonical bytes (case/grouping equivalents are one NET,
    fold F4); conflicting explicit/ISO or multiple distinct in-scope
    ISO NETs reject as ambiguous. A valueless `address;` no longer
    panics the ISO reader (fold F1). The #16810 cluster exemption
    now recognises node-group ISO NETs (fold F3). Fixtures that
    authored interface-bearing IS-IS without a NET gained an
    explicit NET (#14399, #15990 config+frr+daemon, #12071, #9667,
    #8436 x2, #16572, #6532 grpcapi; fold B1).
