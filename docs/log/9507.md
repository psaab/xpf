# #9507 — the DHCP full-set lease decoder preallocates 42x its frame from a wire count

## 2026-09-10 — Action: re-verify at base (origin/master 48a5177be)

- **File(s):** `docs/log/9507.md` (new),
  `pkg/cluster/dhcp_lease_decode_bound_9507_test.go` (new, acceptance first).
- **The spec.** The issue body; it has no comments.
- **The chain, read at base.**
  - `decodeDHCPLeasePayload` (`sync_protocol.go`) clamps the wire count to
    `len(payload)/4` and then preallocates `count` leases, BEFORE reading a single
    record.
  - A zero-length record is accepted: `decodeOneLease` returns a zero-valued lease
    for empty input.
- **Reachability.** This is what decides DoS or not, so it is read from code, not
  assumed.
  - The `syncMsgDHCPLeaseV4/V6` arms of `handleMessage` do `stripFullSetSeq`, then
    the per-family stale-sequence admit, then decode. There is no connection
    identity, admission or authentication check before the decode.
  - In the receive loop, the auth trailer is verified only `if ac.readAuthed()`,
    and cluster sync authentication is an optional config leaf.
  - So on a cluster with no key, any host with L3 reach to the fabric listener
    reaches the allocation. On a keyed cluster it takes the PSK.
- **RED at base, with the issue's own numbers:**
  - `TestDHCPZeroLengthCeilingFrameIsBoundedAndMalformed_9507`: "decoding a
    1048576-byte zero-length ceiling frame allocated 44056920 bytes (42.0x the
    frame, limit 4x)". At the 16 MiB frame cap that is the issue's ~672 MiB per
    family, measured at 1 MiB rather than executed at the cap.
  - `TestDHCPCeilingFrameDoesNotReplaceTheStoredSet_9507`: "a zero-length ceiling
    frame REPLACED the stored peer set with 0 leases". This is the retention half,
    driven through `handleMessage`: a legitimate two-lease set was lost.
  - `TestDHCPRecordShorterThanAnyEncoderIsMalformed_9507`: a 34-byte record decoded
    as complete.
  - `TestDHCPEmptyAddressRecordIsMalformed_9507`: an all-empty 39-byte record
    decoded as a complete one-lease set.
- **GREEN at base, and they must stay green:**
  - `TestDHCPOldestPeerRecordFormatStillDecodes_9507`, the rolling-upgrade floor.
  - `TestDHCPValidMaximumSizeLeaseSetDecodesCompletely_9507`, the load-bearing
    control: a realistic set encoded to just under the 16 MiB frame cap minus the
    full-set trailer decodes completely, with exact count and both ends compared.
    It ran in 0.63 s.
  - `TestDHCPWorstCaseValidFrameAllocationIsBounded_9507`, a guard: minimal valid
    records allocate at most 6x the frame.
  - The #7175 contract cells `TestDHCPLeasePayload_TruncatedStream` and
    `TestDHCPFullSetStillToleratesAnOverDeclaredCount7175`.

## 2026-09-10 — Action: design, from the sender and the wire history

- **The sender has no cap.** `QueueDHCPLeases` encodes every lease; only the
  receiver's 16 MiB frame refusal limits a set. So "the largest legitimate set" is
  one frame's worth, and a receiver bound derived from the frame cannot refuse a
  set that could actually be delivered.
- **The smallest record any encoder has emitted: 35 bytes.**
  - The first encoder (#2239, af03f04cb) already carried every field through the
    FQDN flags byte, with the same uint16 string prefixes (checked at that commit).
  - #5073 (bc83f828f) appended `PreferredRemaining`, so current records are at least
    39.
  - A rolling upgrade can still deliver the 35-byte form, so the floor stays at 35.
- **Why not refuse an over-declared count, as the #8792 sibling does.**
  - The #7175 cells claim a count of 5, ship 2 whole records, and require `ok=true`
    with 2 leases.
  - The count clamp and its `malformed` semantics therefore stay exactly as they
    are.
  - What changes is that the allocation no longer trusts the count.
- **The rule.**
  - Preallocate at most `(len-4)/(4+35)`.
  - A record shorter than 35 bytes is malformed.
  - A decoded record with no address is malformed.

  Malformed suppresses the full-set REPLACE, so the standby keeps its previous set.
- **The bound, stated.** Every retained lease now costs at least 39 wire bytes, so
  retained lease structs are at most about 4.3x the frame (168/39), versus 42x
  before.
  - A 16 MiB frame of minimal valid records retains about 72 MiB of lease structs
    plus at most the frame's own string bytes.
  - The ceiling and short-record shapes retain nothing.
  - A separate retained-bytes cap would add nothing: with the multiplier bounded
    and the frame capped, its limit could only be chosen above the largest
    legitimate set.

## 2026-09-10 — Action: the fix, a first attempt my own cell refused, and the redesign

- **File(s):** `pkg/cluster/sync_protocol.go`,
  `pkg/cluster/dhcp_lease_decode_bound_9507_test.go`, `pkg/cluster/README.md`,
  `scripts/mutate-9507.py` (new), `docs/log/9507.md`.
- **First attempt: preallocate by bytes, and refuse short or empty-address records
  in the loop.** Six of seven new cells went green. The ceiling-frame cell stayed
  RED: "allocated 4521984 bytes (4.3x the frame, limit 4x)".
  - That was exactly the designed preallocation, `(len-4)/(4+35)` leases × 168.
  - The cell, written before the fix, was right to refuse it: a frame whose FIRST
    record is impossible should allocate almost nothing.
  - Growing from a small start and doubling would have broken the other guard:
    doubling to a full legitimate frame costs about 2x the final size, which exceeds
    the 6x limit for minimal valid records.
- **Redesign: validate, THEN allocate.**
  - A count above `len/4` returns `nil, false` at once. That is the result the old
    clamp-then-loop reached anyway, after its allocation.
  - Pass 1, with no allocation, walks the records the count names. It stops cleanly
    at the buffer end, which is #7175's tolerance for an over-declared count. It
    refuses the frame on a record under the floor, a cut record, or an empty or
    overrunning address, read from the raw address-length bytes.
  - Pass 2 allocates exactly the validated records.
  - The #7175 cut-record cell already asserted a malformed decode returns
    `len(out) == 0`, so discarding the prefix changes no observable result.
  - Result: `pkg/cluster` 970 executed, 0 failed.
- **The floor, corrected from 35 to 36, found while planning the matrix.** With empty
  addresses refused separately, the smallest REAL record is the #2239 layout with a
  one-byte address: 36 bytes. A 35-byte record carrying a one-byte address passed
  a 35 floor and decoded a truncated lease.
  - The short-record cell now tests that exact 35-byte boundary. Its FIXTURE asserts
    the minimal real record is 36.
  - A mutant can now be killed in both directions: 35 accepts the boundary record,
    and 37 refuses the minimal-valid guard's 36-byte records.
- **Two cells added when the matrix plan exposed gaps.** Both were written after the
  fix; the matrix proves their kills.
  - `TestDHCPOverDeclaredCountAllocatesOnlyWholeRecords_9507`: 1000 real records,
    with the count inflated to `len/4`, decode fully (#7175) within 6x the frame.
    Sizing pass 2 from the count would be 42x.
  - `TestDHCPAddressOverrunningItsRecordIsMalformed_9507`: an address length past
    its record refuses the set.
- **After both corrections:** `pkg/cluster` 971 executed, 0 failed, including all nine
  #9507 cells and every #7175 and existing DHCP lease cell.
