# #16563: Address-book `range-address` reuses the NAT-pool per-host expander and its 256-host cap

- **Timestamp**: 2026-10-24
- **Problem**: `applyRangeAddress` expanded an address-book
  `range-address <low> to <high>` through `expandAddressRange` — the
  NAT-pool/proxy-arp per-host expander, which refuses ranges over 256
  hosts (`errNATAddressRangeTooLarge`). The refusal was recorded in
  `Address.OversizedRange` and rejected at strict commit even when the
  entry was unreferenced, while the equal CIDR (e.g. `10.0.0.0/23` for
  `10.0.0.0 to 10.0.1.255`) committed. The policy matcher's cost is
  prefix count, not host count, so the cap was keyed on the wrong
  dimension for address-book entries.
- **Fix**: New `expandAddressRangeToCIDRCover`
  (`pkg/config/compiler_nat_helpers.go`) expands `[low, high]` to the
  minimal CIDR cover — greedy largest-aligned-block, fixed-width byte
  arithmetic, no host-count cap, at most 62 IPv4 / 254 IPv6 prefixes
  for any range. `applyRangeAddress`
  (`pkg/config/address_forms_15673.go`) now uses it, so a range of any
  size commits and matches exactly the range on both strict and
  lenient paths. `expandAddressRange` and its 256 cap are unchanged
  for NAT pools and proxy-arp, which allocate one entry per host
  (pool members / kernel NTF_PROXY neighbours). Malformed ranges
  (bad endpoint, non-host mask, mixed family, reversed) still record
  in `Address.OversizedRange` (field name retained), still reject at
  strict commit, and still resolve to nothing on tolerant load; the
  show taint wording now reads `invalid range-address` instead of
  `oversized range-address`.

- **Validation**: New `TestRangeAddressCIDRCover16563` (512-aligned,
  1026-unaligned, 256-host bound ≤16 prefixes, single host, full
  `0.0.0.0/0`, IPv6 257 and unaligned covers) — each cell strict-commits,
  asserts the exact cover, pairwise disjointness, exact union size, and
  exclusion of both neighbours; direct cover-expander error shapes
  (reversed, mixed family, non-host mask, bad endpoint) mirror the
  per-host expander. `TestRangeAddressExpands15673` updated: the small
  range now expects its cover (`192.0.2.1/32, 192.0.2.2/31`) and the
  former oversized cell is now an invalid (reversed) cell. Show tests
  updated for cover rendering, plus a 512-host `large-range` cell that
  renders enforced (not `NOT ENFORCED`). NAT per-host cap tests
  (`TestExpandAddressRange*`, `TestMalformedRangesStillFailOnBothPaths8814`,
  proxy-NDP) unchanged and passing. Pre-fix probe: 512/1026-host and
  IPv6 ranges rejected at strict commit with `address range too
  large`, CIDR `/23` committed.
- **Risk**: A range entry's enforced prefix set changes shape (e.g.
  `192.0.2.1–192.0.2.3` was three `/32`s, now `/32 + /31`) — the matched
  address set is identical. `show security address-book` prints the
  cover prefixes. Operator-visible delta: previously-rejected >256-host
  ranges now commit (intended). `TestWildcardTypedLeafKeyValidatorInventory_6844`
  fails identically on base and is out of scope.
