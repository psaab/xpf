# Issue #15281: api commit-outcome reporting / journal reset fence (D08-02, D08-03)

## Why

- **D08-02:** REST `POST /config/commit` and `/config/commit-confirmed`
  (`pkg/api/config.go`) blanket-mapped every non-context commit-callback
  error to `400 {"success":false}`. The daemon commit path
  (`commitAndApplyOperator`/`commitConfirmedAndApplyOperator` →
  `applyAndSyncCommittedWithPeerSnapshotAuthorization`) returns a
  non-fatal apply-tail or peer-push error as `errors.Join(localErr,
  peerPushErr)` **alongside** the committed config (`compiled != nil`):
  the config was promoted, persisted and is live, yet the REST client
  was told it was rejected — indistinguishable from a real config
  reject. gRPC already classified this structurally in #5742
  (`commitApplyStatus`); REST never got the twin. A client that
  believes the commit was rejected may re-apply or edit a config that
  is already live (commit-confirmed: it may also abandon a confirm
  window it thinks never armed).
- **D08-03:** after a completed factory reset, a reboot/halt/power-off
  request in the daemon's stop window (~1 s grace + stop time) called
  `Store.LogSystemActionAs` → `journalLog` → `journal.Log`
  (`O_CREATE|O_APPEND`) and **recreated `.config.journal`** with the
  prior tenant's principal (username, UID, login class, session,
  action — audit-only, no secrets). The journal was the one store
  writer the reset did not fence: `daemon.factoryReset` fenced only
  `QuiesceRescueWrites()` and `QuiesceArchival()`.

## What

- `pkg/api/config.go`: new `writeCommitError(w, compiled, err)` used by
  both REST commit handlers, classifying structurally on
  `(compiled, err)` exactly like `grpcapi.commitApplyStatus` (#5742):
  context errors → 503 `commit busy: ...` (unchanged); `compiled != nil`
  → **503** with `success:false`, top-level `error`, and
  `data: {status:"committed_with_error", committed:true, error,
  warnings}` — distinguishable from a reject, still not a clean success
  for clients that only check `success`/status; `compiled == nil` → 400
  (unchanged fail-safe default). No new sentinel, no error-text matching.
- `pkg/configstore`: `Store.journalFenced` + `QuiesceJournal()` /
  `ResumeJournal()`. `journalLog` no-ops when fenced; `QuiesceJournal`
  also fences the journal itself.
- `pkg/configstore/journal`: `Journal.Fence()/Unfence()/Fenced()`; the
  fence is checked under `j.mu` in `appendLocked` (returning the
  swallowed `errJournalFenced`), so an append already past the store
  check cannot recreate the file, and an append past both checks has
  its bytes in the page cache before the fence latches — the wipe then
  erases them. `Log` swallows the fenced error silently (best-effort
  journaling; no warn re-logging the suppressed action).
- `pkg/daemon/daemon_apply_reset.go`: `factoryReset` calls
  `d.store.QuiesceJournal()` alongside the rescue/archive quiesces,
  before the wipe; `resetFailed` calls `ResumeJournal()` alongside
  `ResumeArchival()`/`ResumeRescueWrites()` (only when no prior wipe
  succeeded, so post-success retries stay fenced).
- Docs: `pkg/grpcapi/README.md` REST-twin note under the #5742 contract;
  `pkg/configstore/README.md` journal-writer fence note.
- NOT changed: gRPC handlers (already correct via #5742), the wipe
  primitive, power-action scheduling, or any non-journal store writer.
  The ungated no-daemon zeroize fallback has no stop-window server, so
  no fence is wired there (documented residual, same as pre-#5281).

## Risk

- REST clients that treated any non-200 commit response as "rejected,
  safe to retry the edit" now see 503 + `committed:true` for the
  committed-with-tail-error cell; clients checking only
  `success`/status see the same failure shape as before (503 vs 400 is
  the only delta, and 503 is the retryable reading). No client is told
  a reject succeeded.
- After a successful zeroize, journal appends are silently dropped for
  the daemon's remaining (stop-window) lifetime — deliberate: the audit
  file was just erased and must not be recreated with prior-tenant
  attribution. A failed zeroize resumes journaling via `ResumeJournal`.
