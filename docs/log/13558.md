# Issue #13558: Release edge latch after config-lock timeout

## Why

`runAction` retries a remediation while the config lock is held, then drops
it when the retry deadline expires. That terminal path incremented
`DroppedLockHeld` and returned without clearing the event policy's edge latch.
For a sustained fault, `withinMatches` then suppresses later events at or above
the threshold, so the remediation cannot retry after the lock is free.

## What

Call `releaseEdgeLatch` with the dropped action's policy, event, and semantic
revision when the config-lock retry deadline expires. The existing revision
check prevents this rollback from clearing state belonging to a newer policy
generation. Add a regression that holds the lock through timeout, checks the
latch is cleared, then releases the lock and verifies a sustained fault commits
on its next event.

## Validation

`go test ./pkg/eventengine -run '^TestLockTimeoutDropDoesNotConsumeTheCrossing13558$' -count=1`
failed on the pre-fix branch at the assertion that the latch remained armed
after the lock-timeout drop. `GOCACHE=/var/worktrees/.cache/go-build
GOTMPDIR=/var/worktrees/.cache/go-tmp go test ./pkg/eventengine -count=1`
passed, and `GOCACHE=/var/worktrees/.cache/go-build
GOTMPDIR=/var/worktrees/.cache/go-tmp go vet ./pkg/eventengine` passed.

## Risk

Only the lock-timeout terminal path changes; successful commits and retries
retain their existing latch and cooldown behavior.
