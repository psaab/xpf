# Issue #12778 — key remaining attacker-controlled placement hashes

## Root cause

Three attacker-influenced indexes still used seeded or unseeded Fx hashing after #12603: the PMech directory's 32-way session-key shard selector, the shared HA bare-tuple index, and the neighbor-program limiter's `(ifindex, IP)` bucket selector. A seeded Fx hash does not prevent offline key-pair collision construction, and the limiter's unseeded hash exposes a predictable placement function outright.

## What changed

- Migrated the PMech directory shard maps and shard selector to the shared per-process `HotPathSeededState` SipHash builder.
- Migrated both levels of `SharedSessionBareTupleIndex` (`BareSessionTuple` map and multi-scope set) to the same shared keyed SipHash state.
- Migrated neighbor limiter buckets to `HotPathSeededState`, retaining the fixed 64-bucket mask, set associativity, and program-rate behavior.
- Added IPv6 tuple-distribution and cross-scope lookup regressions for the directory and bare-tuple index.

## Risk

SipHash-2-4 costs more per placement hash than Fx hashing. Hash values are private placement details; equality, map contents, capacities, shard counts, and limiter semantics remain unchanged. The process key is stable locally and not transmitted in HA session data.
