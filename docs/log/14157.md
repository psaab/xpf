# 14157 — resetRecvSessionGen does not clear installTableRecvV4/V6

`resetRecvSessionGen(preserve=false)` (`pkg/cluster/sync_conn_gen.go`,
reached via `resetRecvGen` on a peer reboot / boot-incarnation switch from
`pkg/cluster/sync_conn_read.go`) recreated `recvGenV4/V6`,
`recvGenScopedV4/V6` and `sourceNatICMPRecvV4/V6`, reset the tombstone
orders and the receiver cap, but left `installTableRecvV4/V6` untouched.
Those maps hold the last-RECEIVED installing-table identity per tuple,
matched only on `SessionID` (`recvInstallTable`,
`pkg/cluster/sync_install_table_9752.go`). A rebooted peer may reuse both a
tuple and a sessionID, so the dead incarnation's record then matched the
new session: a stamp-less `(0,0)` install restored the stale
`domain/check` via `restoreInstallTableLocked`, installing the new session
in the dead incarnation's table, and a promoted standby's mirror-sourced
resend restored the same stale stamp via `lookupRecvInstallTableLocked` in
`stampInstallGenV4/V6`. The existing sessionID fence does not help here
because the ID itself is reused; the source-NAT receive memos beside it
were already discarded on this path for exactly that reuse reason
(#11064), and the installing-table memos were the missed sibling.

Fix: the `preserve=false` branch of `resetRecvSessionGen` now also
recreates `installTableRecvV4` and `installTableRecvV6`, with a comment
recording the tuple+sessionID reuse mechanism. The `preserve=true`
same-incarnation reclaim deliberately retains them: that bulk re-primes
the same incarnations, so their received stamps remain valid and dropping
them would reintroduce the pre-#9752 loss where a stamp-less resend falls
back to the default table. No other behavior changes; fail-closed
direction preserved (a post-reset `(0,0)` install applies as `(0,0)`,
never as a wrong-table stamp).

Regression (`pkg/cluster/recv_install_table_9752_test.go`, running the real
`installClusterSyncedV4/V6` and `stampInstallGenV4/V6` paths against the
lossy-mirror double): `TestRecvMemoNamespaceResetDiscards14157` and
`TestRecvMemoNamespaceResetDiscardsV614157` seed a stamped receive record,
call `resetRecvGen()`, assert the memo is gone, then install the same
tuple with the same sessionID stating `(0,0)` and assert no stale
domain/check is restored, and assert a mirror-sourced resend via
`stampInstallGenV4/V6` likewise stays `(0,0)`.
`TestRecvMemoReclaimRetains14157` pins the opposite side: after
`reclaimRecvLiveGen()` a stamp-less resend still restores the stamp.
RED-verified in a separate base worktree at origin/master (55e93ffec)
with only the test file copied: both namespace-reset tests fail there
("namespace reset left the dead incarnation's received installing-table
record in place") and pass with the fix; the reclaim-retains cell passes
on both, by design.

Validation: targeted `pkg/cluster` run
(`TestRecvMemo*`, namespace/reclaim cells plus the pre-existing #9752
receive-memo cells) passes with the fix. Main should run the full
`go test ./pkg/cluster/ -count=1` suite once at normal load. Lab
loss-cluster smoke not run (Go unit scope; no wire-format change — the
only behavior delta is that a post-reboot reused tuple+sessionID no
longer inherits a dead incarnation's installing table).

Closes #14157
