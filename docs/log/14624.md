# #14624 — NAT64 pool keeps duplicate members (Y23-03)

- **Timestamp**: 2026-10-16
- **Investigation**: Confirmed at `origin/master@8316f83a7`: `userspace-dp/src/nat64.rs` build loop (~L885) pushes every `parse_pool_v4(s)` result with no seen-set — `parse_pool_v4` accepts both `X` and `X/32`, so `["203.0.113.1", "203.0.113.1/32"]` yields two pool positions with independent occupancy bitmaps; round-robin then mints the same `(X, port)` BIB for two IPv6 subscribers (RFC 6146 §3.5 violation; #10700 graded this class High). The phase-1 reuse-key helper `nat64_rule_identity` (~L600) has the same shape, so deduping only one loop would make the reuse key mismatch the built pool (allocator wrongly reused/not reused) and `build_deterministic_v6(snap, pool_v4.len())` plus the #6982 aggregate charge also consume the duplicated length (deterministic `host_count = pool_len * blocks_per_ip` inflated). The claims at `userspace-dp/src/nat/source/overlap.rs:149-160` ("The parser stores each pool address only once (#10700)") and `pkg/config/compiler_validate_strict_nat.go:4945` ("the dataplane keeps only the first occurrence … on tolerated loads") are false for NAT64 (true only for SNAT via `expand_pool_address` seen-sets in `nat/source/mod.rs`). Fix direction per issue: give BOTH NAT64 pool loops the same first-occurrence seen-set so identity == built pool (which then makes both operator/comment claims true without editing them), and cover the deterministic NAPT64 arm over a duplicated list (named as remaining validation). Tests must assert: duplicate pool `pool_v4 == [X]`, 16 distinct subscribers via `allocate_source` get unique `(addr,port)` tuples (RED: duplicates on base), control pool `[.1,.2]` unchanged, and deterministic mapping with a dup pool behaves exactly as the deduped single-IP pool (subscriber->block placement uses deduped `host_count`).
