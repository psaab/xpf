# Issue #13267: Remove NAT64 frame-builder allocations

## Why

The NAT64 L2 frame builders allocated a fresh `Vec` for each translated frame, contrary to the userspace dataplane's allocation-free fast-path requirement.

## What

- Added caller-buffer (`*_into`) implementations for NAT64 IPv4/IPv6 frame builders, including non-first fragments and ICMP errors. Retained allocating wrappers only for unit-test compatibility; production callers use the caller-buffer implementations.
- Reused the existing thread-local redirect buffer pool to provide appropriately sized frame buffers through the frame builders and ICMP-error paths.
- Recycled builder buffers after tunnel encapsulation, IPv4 fragmentation, successful TX copy, and relevant queue-drop paths.
- Added a regression test comparing caller-buffer output with the established builder result, checking undersized-buffer behavior and buffer reuse, and asserting zero allocations on a warmed build.

## Validation

- `cargo test -p xpf-userspace-dp build_nat64_frame_into_reuses_caller_buffer_13267` — passed.
- `cargo test -p xpf-userspace-dp nat64::tests` — 204 passed.
- `cargo test -p xpf-userspace-dp` — 7,932 passed, 1 failed, 8 ignored. The sole failure was unrelated `protocol::tests::wire_invariant_default_specimens` due to `protocol_wire_v1.json` wire-format drift; generated `.actual` output was removed.

## Risk

The pool is an optimization only; exhausted pool capacity falls back to a capacity reservation, and output correctness is covered by equivalence testing. Exceptional paths not explicitly recycled safely drop their owned buffer.
