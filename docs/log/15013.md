  - **Action**: Bound `protocols rip authentication-key` to 1..16 characters at commit and added a render belt that withholds RIP enrollment for an over-long key (#15013, A12-01). Previously the schema leaf at `schema_routing.go` had no validator and no compiled gate bounded length, so a key of 17+ characters committed clean through `configstore.CheckText`, rendered verbatim as `ip rip authentication string <key>`, and FRR ripd rejected the line on every frr-reload (its maximum is 16 characters, the same cap Junos applies) — a degraded retry that can never succeed, so every later commit reported non-convergence via `manager.go`'s reload path and RIP stayed down on enrolled interfaces. Fix: `ValidateRIPAuthKeyLength` on the shared `rip` schema subtree (global + routing-instance copies), compiled backstop `validateRIPAuthKeyLengthStrict` wired in `runUniformGatesLogFeedRouting` (strict rejects, lenient warns via `lenientRIPAuthKeyLength15013` per #1960), and `pkg/frr/protocols_render.go` omits RIP enrollment entirely for a key longer than `config.MaxRIPAuthKeyLen` instead of emitting the rejected line or an unauthenticated block. Length counts runes; errors/warnings/logs carry only the length, never the key value. Only the RIP key is capped — OSPF/IS-IS/BGP keys render through different FRR commands and are untouched.
