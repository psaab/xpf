# #15097 (A66-05) — refused kernel NUD_PROBE mints no token; held MAC re-asserted

- **Timestamp**: 2026-10-19
- **Issue**: #15097, follow-up of #10704 (token introduced), #13660 (v6 parity),
  #13661/#13898 (token consumption timing).

## Cause

In `parse_neighbor_msg` (`userspace-dp/src/afxdp/neighbor.rs`, both the IPv4 and
IPv6 `RTM_NEWNEIGH` arms), the kernel's own `NUD_PROBE` notification ran
`record_neighbor_probe(key, now_ns)` *whatever the event's lladdr*, before the
refusal arm. The token in `sharded_neighbor.rs` was keyed by `(ifindex, ip)`
only, valid for `ARP_SOLICITED_WINDOW_NS` (5 s).

Attack: one spoofed ARP reply (or NA) the kernel accepted installs attacker
MAC `A` in the *kernel* table while the dataplane refuses it and holds genuine
`G` (refusal counters report the refusal). The kernel then unicast re-probes
`A` and notifies `NUD_PROBE(A)` — minting a key-only token. The attacker
answers its own probe; the kernel reports `REACHABLE(A)`, which the token now
authorizes, replacing `G` in the dataplane. A refused hijack became an
authorized one (next-hop hijack / MITM or blackhole, e.g. of the WAN gateway).

## Change

Binding the token to the probed MAC, and re-asserting the held MAC on a
refused probe — the issue's two fix directions, on both family arms:

- `sharded_neighbor.rs`: the solicited store now holds
  `ProbedNeighbor { mac: Option<[u8;6]>, probed_at_ns }`.
  `record_neighbor_probe` (locally-issued warmer/resolver/pending-retry/
  poll-descriptor probes) stays key-only (`mac == None`): the caller does not
  know the answer MAC, so any differing reply in the window remains solicited
  (pre-#15097 convergence preserved). New
  `record_neighbor_probe_for_mac` records a MAC-bound token (never downgrading
  an existing key-only token), `peek_arp_reply_solicited_for_mac` authorizes a
  differing update only when the token is key-only or bound to exactly the
  candidate MAC, and `clear_neighbor_probe` drops a key's token. The key-only
  `peek_arp_reply_solicited` is retained for existence-only callers (resolver
  confirmed-insert gate).
- `neighbor.rs` monitor arms (v4 + v6): the peek is MAC-aware
  (`Some(mac)`). On `NUD_PROBE`:
  - lladdr == dataplane's held MAC → record a token bound to that MAC;
  - lladdr != held MAC (kernel probing a refused MAC) → mint **no** token,
    clear any stale token for the key, and re-assert the held MAC into the
    kernel (`add_kernel_neighbor` REPLACE, `NUD_STALE`, rate-limited to one
    per key per second via `should_reassert_refused_probe`) so the kernel
    re-probes `G` rather than `A`. A genuinely moved `G` then fails to
    `NUD_FAILED`, the monitor removes the entry, and fresh resolution
    first-learns the new MAC; a spoofed `A` never answers a probe of `G` as
    `G`, so both tables stay at `G`;
  - no dataplane entry → record a MAC-bound token for the probed MAC (first
    resolution in flight; a differing MAC still cannot ride it).
  The re-assert is split behind the `parse_neighbor_msg_with_reassert` seam
  (production: `reassert_held_neighbor_after_refused_probe`) so the decision
  is testable without a privileged netlink socket, mirroring the #4475
  builder split. `parse_neighbor_msg` keeps its signature for all existing
  callers (steady-state monitor, dump batch, tests).
- `poll_stages.rs`: the direct XSK ARP-reply arm's peek is MAC-aware too, so
  a MAC-bound token cannot be spent by a differing wire reply.

Consequence for the #10704/#13660 positive controls: a kernel probe of the
held MAC no longer directly authorizes a *differing* MAC — that leg was the
vulnerability itself (the kernel probes whatever MAC its table holds, which
the attacker controls). Genuine MAC moves still converge through the paths
production actually uses: a locally-issued probe (warmer/resolver/dispatch,
key-only token) or `NUD_FAILED` removal + fresh first-learn. The two
pre-existing cells were updated to pin exactly this, with all other
assertions (refusals counted, epochs, same-MAC refresh, PERMANENT, FAILED/
DELNEIGH, first-learn, expiry, one-shot) unchanged.

No kernel sysctl hardening (`arp_accept` etc.) was added: the dataplane now
never authorizes the refused MAC regardless of kernel table state, and the
re-assert actively repairs the kernel entry. NOT changed: probe issuance
(warmer/resolver/dispatch callers), the one-shot consumption rule, the 5 s
window, refusal counters/alarm cadence.

  seed `G`; step 1 refused `REACHABLE(A)`; step 2 `NUD_PROBE(A)` mints no

- `mac_bound_probe_token_authorizes_only_the_probed_mac_15097`
  (sharded_neighbor_tests): binding, expiry, no-downgrade of key-only

## Risk

- A genuine MAC move whose only solicitation is a kernel probe of the old
  MAC now converges via FAILED + fresh resolution (or the next local probe)
  instead of the immediate post-probe REACHABLE — a bounded extra resolution
  cycle, fail-closed. Kernel-probe-of-held-MAC same-host confirmations are
  same-MAC no-ops as before.
- The re-assert adds at most one netlink program per refused key per second
  on the monitor thread; bounded map (4096 keys, stale-pruned).
- Deferred lab item (recorded on the issue): a netns run of the attack
  (spoofed reply + kernel re-probe) confirming both kernel and dataplane
  entries stay at `G` on a live system; the unit cells pin the dataplane
  half and the re-assert decision, the kernel half follows from REPLACE
  semantics.
