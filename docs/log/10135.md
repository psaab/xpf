# #10135 — zeroize hardlink attestation

- **Date**: 2026-09-18
- **Branch/worktree**: `fix/10135-hardlink` / `10135-hardlink`
- **Issue context**: #10135 follows #10100's narrowed `CollectInteriorSymlinks` contract. `nlink>1` is observable with `Lstat`, but sibling names are not enumerable from the managed pathname.

## Decision

This lane implements option (a): fail the zeroize closed as incomplete-erasure,
while preserving the established best-effort continuation contract:

1. Attest regular managed files before removal with `Lstat` and capture `nlink`, device, and inode.
2. Continue removing every safe/managed name, as the existing symlink census does; one residual is not a reason to abandon the rest of the wipe.
3. Return a distinct `*configstore.FactoryResetHardlinkError`, so the operation cannot claim a clean zeroize.

Option (b), a bounded sibling-name scan, is rejected: a same-directory scan
misses hardlinks in another directory or mount spelling and cannot prove that
all inode names were found. The managed pathname alone cannot enumerate its
siblings, so a partial scan would create false confidence instead of closing
the erasure gap.

The error names each managed path and its captured `(dev, ino, nlink)`. It does **not** invent sibling names. Because the managed name is removed during the best-effort wipe, the operator remediation is to scan the relevant filesystem for each captured inode, for example:

```text
find <filesystem-root> -xdev -inum <reported-ino>
```

The operator removes every returned hardlink name and reruns zeroize. This is why the error carries inode metadata rather than only a pathname.
