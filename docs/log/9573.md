## What was wrong

The #9386 record accepts a stated fail-open: the frame-independent #8356 re-derivation skips a type-constrained ICMP DENY on established sessions. It said this "is mitigated by the new-flow path … and by `security policies policy-rematch` at commit". The rematch half is false for the most direct way to create the situation: a commit that ADDS the deny ahead of an unchanged broad permit. `changedPolicyRuntimeIDs` (`pkg/daemon/daemon_policy_invalidate.go`):
- returns nil unless `PolicyRematch` is set;
- iterates OLD ids only;
- compares only policies present on both sides.

So an added policy never enters the changed set, and the unchanged permit is not swept.

## Measured table, now pinned

Strict `CompileConfig` fixtures, production `changedPolicyRuntimeIDs`. The old config has `p-first` (junos-http, permit) at id 0 and `p-icmp` (any, permit) at id 1.

| mode | deny inserted before `p-icmp` | deny appended after |
|---|---|---|
| rematch off (default) | nothing swept | nothing swept |
| `policy-rematch` | nothing swept | nothing swept |
| `policy-rematch extensive` | `p-icmp`'s old id swept, only because the insert shifted its positional `policy_id`, which the resolved fingerprint hashes | nothing swept |
| `extensive`, permit at `policy_id 0` shifted by the insert | nothing swept (the id-0 exclusion) | n/a |

Preconditions assert that the insert really shifts the permit's positional id, and that the id-0 case really starts at 0. A levelling control (an identical rebuild sweeps nothing) guards each mode, so a diff that always reports a change cannot satisfy the `extensive` insert cell.

The measurement matches the #9573 research transcript at `5fafce23f`, re-run here at origin/master `6d930698c`.

## Not decided here

Whether `extensive`'s positional-id sweep is intended stays an open question. It also reports every later policy as changed on any insert. The test pins the current table so a change is deliberate; it does not endorse the table.
