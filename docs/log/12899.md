# #12899 - Remote `show security zones` summary: wildcard zone-pair tiers, precedence order, quarantine indicator

- **Timestamp**: 2026-10-14
- **Action**: The remote (ctl binary) standard `show security zones [<name>]` summary (`cmd/cli/show_security.go:showZones`) no longer hand-rolls a literal-name walk over the raw `GetPolicies` response. It now mirrors `policymatch.ZoneDetailPolicySummary` (the SSOT the local CLI and gRPC-text detail surfaces share): (1) a WILDCARD zone-pair side (`any`) selects the set — `any -> zone`, `zone -> any`, and `any -> any` rows were previously dropped entirely by the `FromZone == z.Name || ToZone == z.Name` test; (2) tier-one rows print in runtime precedence order (exact, single-wildcard, both-any; config order within each bucket) instead of raw response order, with global lines collected so the tier block stays ordered regardless of group position; (3) the structured quarantine fields are consumed — `ZoneInfo.QuarantineState`/`QuarantineSurvivorZone` render the shared zone-level indicator (id-line qualifier, `ZoneQuarantineHeadlineFor`, interfaces qualifier, `ZoneQuarantineCountersLine` replacing the traffic block) plus the block-level policies qualifier, and every `[zone-pair]`/`[global]` row appends `config.ZoneQuarantinePoliciesQualifier` when the server-stamped `PolicyRule.Quarantined` scrub verdict is set. Wildcard legs are live-zone-gated exactly like the SSOT: a wildcard side or unscoped global cannot govern a quarantined (builder-omitted) zone; literally-naming rows stay visible, scrub-marked. The tier-2 predicate `globalAppliesToZoneAfterQuarantine` (#12896) is exported as `policymatch.GlobalPolicyAppliesToZoneAfterQuarantine` so the remote summary applies the same SSOT selection instead of a drift-prone copy.
