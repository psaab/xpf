# Recursive multi-pipe dispatch overwrites pendingPipeSuffix (#14714)

## Why

`cliterm.SplitPipe` splits at the LAST `" | "`, so for
`show version | no-more | match xpf` the outer `dispatchWithPipe` frame
owns `match xpf`, installs it in the single scalar
`c.pendingPipeSuffix`, and recurses into `dispatch("show version | no-more")`.
The inner frame overwrote the scalar with `no-more`; its save/restore
defer restored the outer value only on unwind — after
`dispatchOperational → checkCommandRegex` had already run at the
innermost frame. `evaluateCommandRegex` therefore adjudicated only
`show version | no-more`, while both filter goroutines still executed.
Any deny/allow rule inspecting pipe verbs, arguments, or a
`$`-anchored pipeline was defeated by prepending any permitted pipe:
with class allow `^show version` + deny `.*match.*`,
`show version | match xpf` was denied but
`show version | no-more | match xpf` ran and emitted the banner.
The coarse permission bits and a pipe-less anchored deny on the base
command were unaffected; only pipe content was hidden, which defeats
the #7172/#9628 contract that the pipe is part of the matched command.

## What

- `pkg/cli/cli_dispatch.go` (`dispatchWithPipe`): accumulate instead
  of overwrite. Each frame prepends its stage to any suffix an outer
  frame already installed (`stage + " | " + prev`), so at the
  innermost frame `pendingPipeSuffix` is the full chain in original
  order (`no-more | match xpf`). Save/restore on unwind unchanged, so
  no suffix leaks into a later un-piped dispatch.
- `pkg/cli/permissions_regex.go` (`evaluateCommandRegex`): a
  multi-stage suffix now validates every later stage's verb with the
  existing `authorizablePipe` check, fail-closed like the first
  stage (#9628). Without this, a chain whose first stage was
  recognised was matched without checking later verbs.
- `pkg/cli/cli.go`: field comment updated for the accumulated
  semantics.
- Tests: new `pkg/cli/multi_pipe_dispatch_14714_test.go` driving the
  real `c.dispatch` through a committed configstore class (not the
  gate in isolation): single-pipe control denied with no output;
  `| no-more | match` and the reversed `| match | no-more` denied
  with no version output; permitted `| no-more | count` runs; bare
  command after a chain shows no stale suffix; an allow anchored on
  the exact full chain (`^show version \| no-more \| count$`) admits
  only that chain in that order (truncated, single-stage, reversed,
  and extended chains all refused); plus a pure-gate cell pinning
  that a multi-stage suffix reaches `evaluateCommandRegex` whole
  and in order. Note: a `count` filter over a denied (empty) stream
  legitimately prints `Count: 0 lines`, so denial cells assert no
  version banner rather than empty stdout where a count stage is
  the outermost filter.

NOT changed: `SplitPipe` (last-split is what lets a filter argument
contain `|`), `EvaluateForms` precedence tiers, the remote CLI
(`cmd/cli`, non-recursive, different surface), or filter execution
order/semantics.

## Risk

Behavior delta only for restricted login classes: multi-pipe
commands are now judged on the whole chain, so a class whose rules
previously (silently) saw only the leftmost stage may now deny —
or, for a longest-match exception written on a later stage,
admit — chains it misjudged before. That is the fix. Unrestricted
classes (no allow/deny regexes) skip the gate entirely, unchanged.
Residual: `| match "a | b"` — a `|` inside a filter argument can be
read by the new verb check as a stage separator if the argument's
first word is not a filter verb, failing closed for restricted
classes; pre-existing `splitAtPipe` already treats that argument as
pipe text, and the fail-closed direction matches #9628.
