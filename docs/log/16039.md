# #16039 — cap bulk-sync receive window at table capacity with a window deadline

- **Timestamp**: 2026-10-23
- **Base**: `6372394b1b` (detached worktree `wt-t39`)

## Why

Bulk session-sync receive inserted session keys into `bulkRecvV4/V6`
before the install verdict, with no capacity cap and no window deadline
inside an open bulk window; the sets reset only at BulkEnd or connection
teardown. A keyed peer (genuine peer faulting, or any peer in the
unkeyed precondition) could grow receiver memory entry-by-entry at wire
cost for as long as it held the window open. The sibling
`bulkInstallFailedV4/V6` marker sets had the same unbounded shape.

## What

- Admission to the receive accumulators now runs through
  `admitBulkRecvV4/V6` (called where the inline insert used to be, still
  before the install verdict so a transiently failed key counts as
  received). The combined live keys across both families may not
  exceed `bulkRecvCap()` = `maxCap()` — the forward-session table
  capacity: the wired helper capacity when known, else the 200k
  default, ceiling `conntrack.MaxSessions/2`.
- Fold (2) — live occupancy, not cumulative keys: a successful delete
  during the window frees its key's slot (`removeBulkRecvV4/V6` from
  the bare and scoped delete paths), so delete+reinstall churn with
  cumulative distinct keys past the cap stays valid.
- The first live key past the cap invalidates the window
  (`bulkRecvInvalid`): further keys are counted and dropped without
  storing, and the window never reconciles, acks, or releases the
  failover hold. At its `BulkEnd` the window state is torn down and the
  sender's bounded re-drive (35s `BulkAckPendingRetryAfter`, daemon
  prime retry) re-primes a legitimate bulk.
- Fold (1) — readiness debt: any abort (cap, deadline-at-BulkEnd, or
  receive-expiry) latches `bulkIncomplete`. `TransferReadiness`
  reports it as an in-progress bulk with a `BulkIncomplete` reason, so
  `ReadyForManualFailover` stays false until a later bulk reconciles
  successfully (`reconcileStaleSessions` success clears it; a full
  disconnect clears it with the rest of the bulk state). Closing the
  aborted window no longer clears the blocker by itself.
- The failure-marker maps share the same combined cap with the same
  invalidation, so an all-failing peer cannot grow them either.
- An accepted `BulkStart` stamps `bulkRecvStartedAt`. Fold (3) — the
  deadline is enforced on receive: `expireBulkWindowIfStale` runs at
  the top of every `handleMessage`, so a window still open past
  `bulkRecvWindowTimeout` (1h, far beyond the sender's ~35–150s retry
  cadence) is expired, its maps freed, and its debt latched on the
  peer's next frame even when no `BulkEnd` is ever sent. Fold 2 — the
  timer arm: `receiveLoop`'s read-timeout branch (every
  `readDeadlineDuration`, 10s default) calls the same expiry before
  the heartbeat-ack teardown, so a fully silent peer loses its window
  with no inbound traffic at all. The BulkEnd check remains as a third
  enforcement point.
- `reconcileStaleSessions` additionally refuses an invalid window, and
  the new state is cleared on successful reconcile, BulkEnd-abort, and
  full disconnect.
- Observability: `BulkRecvCapped` (keys refused past the cap / dropped
  on an invalid window) and `BulkRecvAborted` (windows aborted, at most
  one counted per window) ride `SyncStats` → `SyncStatsSnapshot` and
  render in cluster status when nonzero. One `Warn` per overflow,
  expiry, and abort, never per record.
- No wire change. Legacy peers complete exactly as before inside the
  cap and deadline.

## Tests

`pkg/cluster/sync_bulk_recv_cap_16039_test.go` — drives the real
`handleMessage` path with a small `genGuardMapCeilingOverride`:

- `TestBulkRecvCapAbortsOverflowingWindow16039`: a window full exactly
  at the cap is legal; one more distinct key invalidates it (counters,
  no growth under a flood, no ack/completion/hold-release at BulkEnd,
  readiness debt latched); a following legitimate at-cap bulk installs,
  acks, completes, and clears the debt.
- `TestBulkRecvDeadlineAbortsStaleWindow16039`: a BulkEnd past the
  deadline aborts; with no BulkEnd at all, the next inbound frame past
  the deadline expires the window on receive (maps freed, debt
  latched); a window closed inside the deadline completes and clears
  the debt.
- `TestBulkRecvSilentPeerExpiresOnReadTimeout16039`: a real
  `receiveLoop` over `net.Pipe` with a 20ms read deadline; the peer
  opens a window, sends one session, then goes silent — the
  read-timeout tick alone expires the window (closed, freed, one
  abort, debt latched, never completed).
- `TestBulkRecvCapIsLiveOccupancy16039`: delete+reinstall churn with
  cumulative distinct keys past the cap stays valid and completes;
  only a genuinely over-cap live set aborts.
- `TestBulkInstallFailedMapsBounded16039`: an all-transiently-failing
  peer cannot grow the marker sets past the cap; the window invalidates
  and withholds the ack.
- `TestBulkRecvDuplicatesAndIncrementalFree16039`: duplicate keys never
  consume cap; incremental installs outside a window never touch the
  accumulators.

The test override (`genGuardMapCeilingOverride`) is the pre-existing
gen-guard ceiling seam; tests using it never open a bulk window, so the
shared ceiling does not perturb them (verified by the full package run
below).
