# #16654 — closed-world gate does not descend into `within`: Junos correlation children commit clean and are dropped (R3-A14-04)

## Defect

The #14660/#15134 closed-world gate (`pkg/config/event_options_inert_14660.go`,
`validateEventPolicyInert14660`) handles only policy-level `events` and
`then` (descending into `change-configuration`). A policy child `within`
passes `permittedPolicy` and its children are never inspected.
`validateEventWithinClause` (`pkg/config/event_options_within.go`) read
only `trigger` siblings, and `compileEventOptions`
(`pkg/config/compiler_services.go`) reads only `FindChildren("trigger")`
inside a `within` clause. `schemaEventOptions` declares `within` →
`trigger` only, and that schema is not closed-world.

Measured on `origin/master` `351427339e` (probe run in this lane, all
`CompileConfig err=<nil>`, `WithinClauses=[{60, on 1}]`): hierarchical
braced `within 60 { events ping_test_completed; trigger on 1; }`,
`within 60 { not events ping_test_completed; trigger on 1; }`,
`within 60 { not { events ping_test_completed; } trigger on 1; }`, and
`within 60 { bogus-token foo; trigger on 1; }`, plus the flat-set
equivalents including the issue's SetPath example
(`set event-options policy p within 60 not events ping_test_completed`).

The negative row is the dangerous one: "fail over only if the path did
not recover in the last minute" committed clean, the `not events`
condition was dropped, and `pkg/eventengine` fired the remediation even
when recovery had just happened — the fail-open direction under the
#2124 doctrine. Positive `events` correlation was likewise dropped.

## Fix

Descend into `within` in the existing #3751 clause validator — same
walk, same strict/lenient split, no new gate, no schema change, no
`compileEventOptions`/engine change:

- `pkg/config/event_options_within.go`: `validateEventWithinClause`
  now first checks every within child keyword via the new
  `withinChildTokens16654` helper and rejects (strict) / warns
  (lenient) any token other than `trigger`, naming the policy, the
  token, the known set (`trigger`), and `(#16654)`. The check runs
  before the seconds/trigger numeric validation, so a correlation
  child is named even beside an otherwise-valid clause.
  `withinChildTokens16654` covers the authorable AST shapes:
  braced/flat children under `Keys=[within <seconds>]` (including the
  flat-set children SetPath files there and `not { events …; }` whose
  keyword is `not`), and the packed tail `Keys[2]` for brace-elided
  `within 60 events X;` / `within 60 not events X;` (any Children of a
  packed node are that child's body, not siblings — mirroring
  `thenChildTokens14660`/`changeConfigChildTokens14660`). Only the
  child keyword is read; `apply-groups*`/`apply-macro` meta keywords
  stay exempt as at every other level of this gate family.
- `pkg/config/event_options_inert_14660.go`: header cross-reference
  only — the `within`-child class lives in the #3751 walk, not the
  #14660 walk (whose `within` case stays permitted-and-uninspected
  because the seconds/trigger numerics already live there).
- Docs: `pkg/eventengine/README.md` "Closed-world commit gate" now
  cites #16654 and the `within`-child rejection.

Packed-tail nuance (measured, not assumed): through the full strict
pipeline a hierarchical packed tail (`within 60 not events X;` with no
braces) is in fact rejected even before this gate by the pre-existing
#8437 fused-sibling SchemaValidate diagnostic (it names the swallowed
`events` token), because CompileConfig runs SchemaValidate first. The
#16654 packed-tail arm still matters on the direct-validator and
lenient paths, where no fused-sibling gate runs: there `Keys[2]=not`
is now named by #16654 itself. Junos's canonical spelling is the
braced block, which was fully open before this fix.

## Risk

- Behaviour delta: configs carrying `within` correlation children
  (including any bogus token beside `trigger`) now hard-reject at
  commit / commit-check instead of silently firing without the
  correlation condition. Already-persisted configs still boot via the
  lenient warning path (#1960); on that boot the clause compiles as
  before (trigger-only), now surfaced.
- Implementing actual correlation semantics remains a possible later
  step; this fix only refuses the unsupported condition loudly.
- Rust/dataplane: untouched.
