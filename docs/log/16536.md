# #16536: shared_exact per-flow BDP floor ignored the per-shard buffer partition

- **Timestamp**: 2026-10-24
- **Action**: The #914 shared_exact per-flow cap
  `max(fair_share*2, bdp_floor).clamp(MIN, buffer_limit)` computed its
  BDP floor from the class-wide `transmit_rate_bytes` over the
  worker-local prospective flow count, while #11768 had already
  partitioned `buffer_limit` by `active_shards`. At 10 Gb/s with 6
  shards and 8 local flows one elephant could therefore hold 75% of a
  worker's admission budget (100% at 4 local flows), defeating the
  mouse protection the cap exists for. Added
  `cos_queue_flow_share_limit_with_active_shards`, which divides the
  rate by `active_shards` before the BDP floor; the legacy
  `cos_queue_flow_share_limit` delegates with `active_shards == 1` and
  is bit-identical, so every existing single-shard #914 cell is
  unchanged. The production enqueue path in `tx/cos_classify.rs` now
  hoists the shard count it already reads from the root lease for
  `cos_shared_exact_buffer_limit` and threads it into the per-flow cap.
  No other gate changes: the aggregate per-worker cap, class rate and
  MQFQ dequeue order are untouched, and the fix only ever lowers the
  per-flow cap on multi-shard queues (never fail-open).

- **Validation**: New cell
  `shared_exact_per_flow_cap_scales_with_active_shards` (10 Gb/s,
  12.5 MB buffer, 6 shards, 8 local flows) asserts
  `cos_queue_flow_share_limit <= buffer_limit / 2`; it fails at 75% on
  the pre-fix formula and passes post-fix, with a single-shard control
  asserting bit-identity with the legacy entry point. Targeted
  admission test run recorded in the PR.
