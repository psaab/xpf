# #12502 — resolve cross-kind address-set references on host deny and static NAT

- **Timestamp**: 2026-10-13

## Red before

The pre-existing dirty `pkg/config/zz_red_12502_test.go` repro was adopted and expanded into `pkg/config/address_set_cross_kind_12502_test.go`. Its base repro logged `ExpandAddressSet(A) = [B]`, `junosHostResolveAddrSet(A) ... ok=false`, and `resolveStaticNATThenPrefixName(A) = "" ... ok=false`. This demonstrated the two independently affected consumers without changing their result into an assertion.

On master `6915a5a8e`, with the `expandAddressSetLeaves` assertions removed (the helper does not exist there), `go test ./pkg/config/ -run '12502|CrossKind' -count=1 -v` fails:

- both `address`-member cells of `TestCrossKindAddressSetResolution12502`: `junosHostResolveAddrSet = v4 [] v6 [] ok false`;
- `TestCrossKindJunosHostDenyRenders12502`: the untrust program is `Representable:false` with empty `RulesV4`;
- `TestCrossKindStaticNATPrefixNameCompiles12502/strict`: the #4290 guard rejects `prefix-name "ALIAS"` as not resolving to a single address-book prefix; `/lenient`: the target prefix is `""`.

The nested `address-set` cell and the unknown-member test pass there as controls.

## Change

The public `ExpandAddressSet` contract remains unchanged: it preserves direct `address B` members as set-ID graph references, matching dataplane compilation. A new private leaf expander resolves those members through the referenced set for consumers that need literal addresses. Junos-host deny and static-NAT prefix-name use that helper; address-first handling is retained for same-name collisions. Existing cycle, depth, unknown-member, and deduplication behavior is preserved, and feed-taint traversal remains unchanged.

Regression coverage checks a referencing set sorting before and after the referenced set, direct `address` and nested `address-set` member shapes, junos-host deny kernel-rule output and rendered-key accounting, strict and lenient static-NAT prefix-name target population, and unknown-member rejection in both resolver paths.

## Validation

- **After fix**: `go test ./pkg/config/ -run '12502|CrossKind' -count=1 -v` passed.
- `go test ./pkg/dataplane/ -run '^TestCompileAddressBookCrossKindSetMemberOrderIndependent12233$' -count=1 -v` passed both `A_before_B` and `Z_after_B` membership-graph cases.
- `gofmt -l` reported nothing for the changed Go files; `go vet ./pkg/config/` passed.

## Risk

The host/NAT-only leaf-expansion helper deliberately does not alter the dataplane set-ID graph or the nat-off shadow caller's feed-bound set-name traversal. Strict commit rejects a same-name `address` and `address-set`. The lenient load path records the collision: junos-host deny then treats the name as unrepresentable, and static-NAT prefix-name resolves it as the address, as before this change. No live-cluster mutation was performed.
