# CoS fairness harnesses: hardcoded fw0, `--symmetric` restore leak, scraper orphaning (#13069)

- **Issue**: #13069 — research D10-14 from the deep-review source report
  `gemini-4-argon-high-review-performance-cos-fairness-100e100m-and-code-quality-modularity-001.md`
  (finding 94, `MATERIAL`, `EXECUTED`).
- **Defects** (all three mechanisms named in the finding):
  1. `test/incus/fairness-cos-throughput-headroom.sh` hardcoded
     `TARGET_VM=loss:xpf-userspace-fw0` and
     `test/incus/fairness-cos-class-sweep.sh` hardcoded
     `DATAPLANE_VM=loss:xpf-userspace-fw0`, with no active-primary
     detection. Whenever fw1 held the active RG (any failover), the
     headroom run applied CoS to — and the sweep snapshotted
     `/run/xpf/userspace-dp.json` and counter deltas from — the STANDBY
     node, yielding unclassified traffic and 0-packet-delta telemetry.
  2. The headroom `restore_strict_if_needed()` re-applied the strict
     fixture with the sweep's `COS_DIRECTION_FLAGS` (`--symmetric` under
     the default reverse sweep), so the reverse source-port
     classification terms (`bandwidth-output-reverse` and its ge-0-0-1
     attachment) stayed installed on the firewall after exit and leaked
     into every subsequent test suite.
  3. `fairness-cos-class-sweep.sh` installed no `EXIT/INT/TERM/HUP/QUIT`
     traps, so an interrupted sweep orphaned the background
     `scrape_equal_flow_metrics` `/metrics` curl loop indefinitely — and
     because bash async commands ignore SIGINT/SIGQUIT, even a terminal
     Ctrl-C on the sweep's own process group left the loop alive.
- **Change**:
  - New shared helper `test/incus/active-fw.sh`
    (`active_fw_detect vm…`): probes each candidate's
    `cli -c 'show chassis cluster data-plane statistics'` and prints the
    first node reporting `Enabled: true` + `Forwarding supported: true` +
    `rgN active=true` — the same probe as the cited positive control
    (`cos-be-contention-harness.sh:detect_active_fw`).
  - `fairness-cos-throughput-headroom.sh`: `TARGET_VM` now defaults to
    detection over `TARGET_VM_CANDIDATES`
    (`loss:xpf-userspace-fw0 loss:xpf-userspace-fw1`), failing closed
    with exit 2 when no active primary answers; an explicitly set
    `TARGET_VM` is honored unchanged. `restore_strict_if_needed()` now
    re-applies the canonical forward-only fixture
    (`"$APPLY_COS_CONFIG" "$TARGET_VM"`) — the flag-less apply's curated
    delete list removes `firewall … bandwidth-output-reverse` and the
    `ge-0-0-1` filter attachment before re-applying the strict sets.
  - `fairness-cos-class-sweep.sh`: `DATAPLANE_VM` now defaults to the
    same detection (only when `CAPTURE_DATAPLANE` is enabled), failing
    closed with exit 2 before any class work is spent; and
    `stop_equal_flow_capture_and_exit` traps on `EXIT/HUP/INT/QUIT/TERM`
    stop the live `EQUAL_FLOW_CAPTURE_PID` on every exit path (a normal
    exit re-stops the already-stopped last pid, a no-op).
  - `cos_port_grid_test.py`: the two headroom apply-args tests now
    install a fake `incus` reporting fw1 active (fw0 standby) and assert
    all applies target fw1 with a `--symmetric`-free canonical restore —
    they previously pinned the buggy fw0 + symmetric-restore behavior.
  - New `test/incus/fairness_cos_active_fw_test.py`: seven hermetic
    e2e regressions running the REAL scripts against fake
    `incus`/`apply-cos-config.sh`/wrapper/curl binaries — active-primary
    dataplane capture (probes fw0, captures from fw1, never from the
    standby), sweep fail-closed before class work, sweep/headroom
    operator-pinned overrides skipping detection, headroom fail-closed
    with the fixture unspent, and SIGTERM-to-script (143) /
    SIGINT-to-group (130) interrupted sweeps leaving no live scraper.
- **RED evidence**: pristine `origin/master` (`f155532aa`, no diff in the
  touched files vs the fix base `ac4dcdfc1`) plus only the new test file:
  6 of 7 tests fail — dataplane telemetry captured via
  `exec loss:xpf-userspace-fw0 -- sh -lc …` with no detection probe, no
  fail-closed (sweep and headroom run to completion, exit 0), scraper pid
  alive after SIGTERM (`-15 != 143`) and after group SIGINT (`-2 != 130`),
  and headroom restore still `--symmetric`. The updated
  `cos_port_grid_test.py` expectations likewise fail 2/2 on pristine
  master (`--symmetric loss:xpf-userspace-fw0` restore vs
  `loss:xpf-userspace-fw1`).
- **GREEN evidence**: with the fix, `fairness_cos_active_fw_test.py` 7/7
  and `cos_port_grid_test.py` 8/8 pass; full
  `python3 -m unittest discover -s test/incus -p '*_test.py'` passes
  553/553 (includes the sweep/headroom e2e legs and the #8136 discovery
  guard confirming the new file contributes).
- **Validation**: `bash -n` on all three shell files;
  `shellcheck -S warning` clean on `active-fw.sh`,
  `fairness-cos-throughput-headroom.sh`, `fairness-cos-class-sweep.sh`;
  `git diff --check` clean.
- **Blast radius / risk**: test harnesses only (`reachability:
  TEST-ONLY` per the finding). Behavior change: an unset
  `TARGET_VM`/`DATAPLANE_VM` now requires a reachable cluster (or an
  explicit override) where it previously guessed fw0 — that is the
  fail-closed doctrine the finding demands; the sweep's own
  `CAPTURE_DATAPLANE=0` hermetic legs are unaffected, and operators who
  pin a node see identical output. The canonical restore means a
  forward-only fixture is left installed after reverse headroom runs —
  exactly the state every other suite expects (`cos-be-contention-harness`
  re-applies `--symmetric` itself when it needs it).
