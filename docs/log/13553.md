# #13553 — normalize monitor flow filter values

- **Timestamp**: 2026-10-15 (`fix/13553-campaign-pub`)
- **Action**: canonicalize protocol and interface values when installing a flow filter, and compare event records using canonical numeric protocol and interface forms.

## Red before

On clean base `5fba34bd2`, `go test ./pkg/cli -run '^TestMonitorFlowFilter13553' -count=1` failed in six regression cases: numeric protocol filters `6`, `17`, `58`, and `41` did not match their rendered event names; named `ospf` did not match numeric-only protocol 89; and `ge-0/0/0` did not match event interface `ge-0-0-0`. The invalid-protocol regression also failed because unresolvable protocol names were accepted into the filter. Literal filters constructed without the CLI handler exhibited the same matching failure.

## Change

Flow-filter construction now resolves protocols through the shared `appid.ProtocolNumber` table and stores the canonical protocol name (or decimal number when the protocol has no display name). Unknown or out-of-range protocol tokens are rejected before committing a filter. Interface filter values are stored in the kernel form produced by `config.LinuxIfName`. Matching uses protocol numbers, preferring the record's raw `ProtocolNum` and falling back to the rendered string only for legacy/hand-built records without a number; interface matching recognizes both Junos and Linux forms. No other monitor path or subscription semantics changed.

## Validation

- **RED before**: focused regressions failed on pristine base `5fba34bd2` as listed above.
- **GREEN after**: `go test ./pkg/cli -run '^TestMonitorFlowFilter13553' -count=1` passed.
- **Package suite**: `go test ./pkg/cli -count=1` passed.

## Residual / risk

None identified. Protocol matching retains compatibility with legacy records whose `ProtocolNum` is unset by parsing their rendered protocol string; raw non-zero protocol numbers remain authoritative.
