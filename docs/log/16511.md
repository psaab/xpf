# #16511: NAT64 tunnel-egress MSS clamp used the pre-translation family

- **Timestamp**: 2026-10-24
- **Action**: `build_nat64_forwarded_frames_with_commit_and_dynamic` in
  `userspace-dp/src/afxdp/frame/mod.rs` selected the TCP MSS clamp with
  the ingress `ForwardPacketMeta`, so a v4->v6 SYN-ACK encapsulated into
  GRE/WG was budgeted as IPv4 (20 bytes too high: 1436 instead of 1416
  on a 1500-byte transport) and the v6->v4 direction was 20 bytes low.
  The builder now computes `nat64_translated_meta` once, selects the MSS
  with that emitted family, and reuses the same translated meta for the
  GRE/WG encapsulation instead of recomputing it. The slow-path twin in
  `userspace-dp/src/afxdp/tx/dispatch/slow_path.rs` flips the family the
  same way when the decision is NAT64 (tunnel-marked frames are not
  reinjected there, so that site is static-only, but the family is now
  correct for consistency). Added `nat64_gre_mss_uses_translated_family_16511`
  (both directions through the real GRE builder, expecting 1436 forward
  and 1416 reverse) and `nat64_wg_mss_uses_translated_family_16511`
  (selection-layer WG twin, 1385 v4 / 1365 v6) to
  `userspace-dp/src/afxdp/frame/tests_nat_rewrite.rs`.
- **File(s)**: `userspace-dp/src/afxdp/frame/mod.rs`,
  `userspace-dp/src/afxdp/tx/dispatch/slow_path.rs`,
  `userspace-dp/src/afxdp/frame/tests_nat_rewrite.rs`, `docs/log/16511.md`
- **Validation**: `cargo test --bin xpf-userspace-dp -- 16511` 2 passed;
  `cargo test --bin xpf-userspace-dp -- 15948 14664 8896` 23 passed.
  Mutation check: selecting with the ingress meta again makes
  `nat64_gre_mss_uses_translated_family_16511` fail (1416 vs expected
  1436 on the forward arm); restored green. Residual: the WG twin is
  pinned at the `select_tcp_mss` selection layer, not end-to-end
  through an established WG session (the plaintext GRE fixture has no
  WG engine/AllowedIPs coverage for the translated destinations).
