# #14640 — Editing one WireGuard peer rebuilds the tunnel engine and discards every other peer's learned (roamed) endpoint

## Defect

`populate_wg_engines` (`userspace-dp/src/afxdp/forwarding_build/wg.rs`)
reuses the prior `Arc<WgEngine>` only when the whole WG identity
(listen port + local privkey + full ordered peer vector, `wg_peers_eq`)
is unchanged. Any one-peer edit (add/remove a peer, change an
allowed-ip, keepalive, PSK, or endpoint) falls through to
`WgEngine::new`, whose fresh `Peer::new` peers start with
`live_endpoint = None`.

The rebuild carried forward only the engine-wide TAI64N high-water
(`seed_tai64n_high_water`, #1432) and each surviving peer's responder
anti-replay high-water (`seed_greatest_tai64n`, #4103). It did NOT carry
the #13664 adopted live endpoint (`Peer::live_endpoint`, documented as
"Lives on the reused Arc<Peer>, so it survives config commits" — but
production never reuses the Arc on the edit path; `reconcile_peers`,
the path that would preserve it, has its only non-test caller in the
constructor).

Consequence: editing one peer reverts every other peer to its stale
configured endpoint. A roamed/NATed peer blackholes hub->peer traffic
until it next sends authenticated traffic; an idle peer without
keepalive stays unreachable. A responder-only peer (no configured
endpoint) reverts to `None`. The control thread re-seeds from the fresh
engine's `peer_endpoints()` (`wg_control::init_consumer_state`), so it
inherits the same loss.

Session loss on rebuild IS documented as intended
(`forwarding_build/wg.rs`, "Live sessions are dropped ... S5 adds
session migration"), so only the endpoint half is in scope.

Witness (regression test): peer A configured `198.51.100.1:51820`,
roamed to `192.0.2.44:61001`; peer B responder-only learned
`192.0.2.55:61002`. Editing only peer B's keepalive (0 -> 25) rebuilds
the engine; pre-fix peer A's `peer_for_dest(10.1.0.9)` returns
`Some(198.51.100.1:51820)` (stale configured) instead of the roamed
endpoint.

## Fix

Mirror the #4103 snapshot/seed pair for live endpoints, in
`userspace-dp/src/afxdp/wg/engine.rs`:

- `WgEngine::live_endpoints_by_pubkey()` — snapshot each peer's adopted
  live endpoint keyed by pubkey, paired with its configured endpoint at
  snapshot time. Peers with no live endpoint are omitted.
- `WgEngine::seed_live_endpoints(snapshot)` — adopt the snapshot's live
  endpoint into the fresh engine's peer ONLY when that peer's new
  configured endpoint equals the snapshot's configured endpoint. If the
  operator edited that peer's own configured endpoint, the new
  configured value wins and the stale live endpoint is dropped (a roam
  adopted against the old configured address must not override an
  explicit endpoint edit; the #13664 blackhole shape is reverting to a
  STALE configured address, not honoring a NEW one).

`populate_wg_engines` now calls
`engine.seed_live_endpoints(&prev_engine.live_endpoints_by_pubkey())`
alongside the existing high-water seeds on the identity-change rebuild
path. `Peer::live_endpoint` doc updated to state the rebuild carry
(replacing the false unconditional "survives config commits").

NOT changed: session migration (documented intended drop, S5), the
identity-unchanged Arc-reuse path (already preserves everything), the
`reconcile_peers` same-engine path (already reuses `Arc<Peer>`), and
control-thread seeding logic (`peer_endpoints()` already returns
live-or-config, so a correctly seeded fresh engine re-seeds the control
thread with no wg_control change).

## Tests

- RED (pre-fix): `wg_live_endpoint_survives_one_peer_edit_rebuild_14640`
  (`userspace-dp/src/afxdp/forwarding_build/tests.rs`) fails —
  `peer_for_dest` for peer A returns `Some(198.51.100.1:51820)` after a
  peer-B-only keepalive edit, want `Some(192.0.2.44:61001)`.
  Positive controls in the same test pass pre-fix: identical re-commit
  reuses the engine Arc and keeps the roam; pre-edit `peer_for_dest`
  returns the roamed endpoint.
- GREEN: same test passes post-fix, including: engine genuinely rebuilt
  (different Arc), `peer_endpoints()` re-seeds roamed/learned endpoints
  (control-thread acceptance), peer B's learned endpoint survives when
  only its keepalive changed, and the negative control — peer A's own
  configured endpoint edited -> new configured value wins over the stale
  live endpoint.
- Suites: `cargo test --bin xpf-userspace-dp wg_` (forwarding_build WG
  pins + wg engine/control suites) — see PR Validation.
