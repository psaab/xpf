# #14136 FRR prefix-list terms fail open — engineering history

Issue: psaab/xpf#14136 (FRR policy terms fail open: undefined/all-skipped
`from prefix-list` in `then reject` term). Lane branch:
`fix/14136-campaign`, base `origin/master` 43ebebd38.

## Defect (present at base)

`pkg/frr/policy_render.go` rendered `match ip|ipv6 address prefix-list
<name>` (or the #5730 inline access-list form) unconditionally for
`from prefix-list`, even when the named list was undefined or every entry
had been omitted by the #10823 malformed-entry belt
(`net.ParseCIDR` skip in `generatePolicyOptionsWithQNH11447`). FRR
resolves a dangling match to NO MATCH, so a `then reject` sequence never
fired; routes fell through to a later accept or the #2998 BGP trailing
`permit`. The sibling as-path (#9881) and community (#10822) guards
already rendered reject terms over dangling lists as bare deny-all; no
analogous prefix-list guard existed.

## Fix

`pkg/frr/policy_render.go`:

- New `prefixListRefMissingAtRender(po, name, matchKW)` — per-family
  mirror of the emission loops: true when the list is undefined or has
  no entry of that family passing `net.ParseCIDR` (same predicate and
  `:` family split as the top-level prefix-list loop and
  `renderFromPrefixListACL`, so predicate and emission cannot drift).
- Term rule in `renderPolicyTermSequencesWithDefinitions`, mirroring
  #9881/#10822: a name is fully dangling when every per-family ref under
  it is missing. Reject terms over any fully-dangling OR-branch render
  one bare deny-all sequence; accept/non-terminating terms skip the
  dangling branch in `emitVariants`. A mixed list with one rendered
  family keeps that family's ref and drops only the dangling family ref
  (no deny-all broadening for partially-rendered lists). No dangling
  `match ... prefix-list` or inline-ACL reference is emitted.

Consumers updated for the changed output contract (previously asserted
the dangling matcher): `TestPrefixListMatch_UnknownName_DefaultsIPv4`,
`TestFromPrefixListEmpty_FailClosed_2607`,
`TestUndefinedPrefixListCountsAsOneFamily7526` (bound stays an upper
bound of 1; rendered term sequences are now 0), and the #12070
prefix-list tail cases now define `PL` so they keep exercising the
retained-match path.

## Verification

- New `pkg/frr/policy_prefixlist_dangling_14136_test.go` (8 tests):
  RED on pristine master (7 fail, valid-list control passes), GREEN
  with the fix. Covers undefined reject→deny-all, all-malformed reject,
  mixed OR (one dangling name), accept subset/empty, non-terminating
  skip, partially-malformed mixed list (both directions), valid control.
- `go test ./pkg/frr/ -count=1`: green except 3 pre-existing
  FRR-binary load failures (`TestFamilylessIPv6NeighborWithoutPolicyIsV6Only11564`,
  `TestFRRLoadInet6OnlyNeighborIPv4Deactivation11374`,
  `TestFRRLoadBGPClasslessRIBSuppression11426`), confirmed failing
  identically on pristine master (stash check).
- `gofmt -l` clean on touched files; `go vet ./pkg/frr/` clean.

## Residuals

- `RouteMapSequenceCount` still counts an undefined/empty referenced
  list as one sequence while the renderer now emits zero for a dangling
  accept term. The bound is an admission upper bound; over-counting by
  one can only refuse earlier, never admit past FRR's ceiling.
