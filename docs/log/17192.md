## ND-to-catalog semantics decision (pinned)

Catalog rule for a PRESENT zone or interface-override view: ND (133-136)
to a catalog multicast group requires an explicit ND positive (`ndp`
token / `protocols all`, which expands to it) or `any-service`; the bare
ND default does NOT open it; `ndp except` denies. An unknown view (no
zone entry, no override) is likewise fail-closed for a catalog
destination.

Kernel posture, stated exactly — the earlier draft of this section
over-claimed parity, and Rev18247Opus F1/F2 caught it:

- SCOPED ingress (view carries `IngressNetdevs`): the kernel denies ND
  to the five v6 catalog groups (`ff02::5`, `ff02::6`, `ff02::9`,
  `ff02::d`, `ff02::12`) unless the view's token set opens that exact
  group, because the ingress-scoped catalog drop
  (`emitHostInboundMulticastIngressGuards` in text `daemon_nft.go`,
  `emitHostInboundMulticastGuardsNetlink` in netlink) precedes the ND
  accepts (`emitHostInboundNDPAcceptsText` /
  `emitHostInboundICMPAcceptsNetlink`). Pin: an `ssh`-only scoped view's
  NS to `ff02::5` hits that drop first, even though a scoped
  `ff02::/16` ND accept exists later in the chain. That scoped kernel
  verdict matches the Rust deny. A bare `ndp` token alone does NOT open
  a catalog group on the kernel either (it emits no catalog accept);
  only `any-service` (catalog accept ahead of its drop) or the exact
  routing-protocol group grant does. Non-catalog `ff02::1` is admitted
  for every ND-retaining scoped view (its scoped ND accept precedes the
  non-unicast guard's service matches and drop).
- UNSCOPED ingress (destination-fallback view — addresses but no
  ingress netdevs — or a wholly scopeless view): the kernel emits its
  ND accept with NO catalog drop ahead of it (destination-fallback is
  unicast-address-scoped; scopeless is a bare unscoped ND accept), so
  the kernel ADMITS an `ssh`-only view's ND to `ff02::5` (destination-
  fallback: via the chain `policy accept`, no deciding rule matches;
  scopeless: via the bare unscoped ND accept directly). There is no
  catalog drop to deny it.

Userspace therefore does NOT claim blanket kernel parity. On scoped
ingress (and for present views generally) the Rust deny matches the
kernel. For unscoped/unknown views userspace has no ingress-scope bit —
it judges only the selected view and the destination — and deliberately
stays STRICTER than the kernel's unscoped fail-open: fail-closed for a
catalog destination on an unknown view, on the rationale that
reproducing the kernel admit would mean admitting catalog ND whenever
scoped-ness is unknown, i.e. precisely where the view cannot be shown
to have authorized it. The deny is kept; the prose now says so.

Kernel truth is pinned by Go rendering cells, not by the Rust cell:
`TestKernelNDCatalogPosture17192` (pkg/daemon, nft TEXT via
`buildHostInboundFilterPayload`) and
`TestKernelNDCatalogPostureNetlink17192` (pkg/nftables, NETLINK via
`buildHostInboundNetlink` + canon rules) render
{ssh-only, ndp-positive, ndp-except, any-service} x {ff02::5, ff02::1}
scoped plus ssh-only destination-fallback and scopeless, and assert
the verdicts above by first-match order. The Rust cell
`ndp_zone_override_catalog_parity_17192` then cites them: it pins
zone==override Rust verdicts, not the kernel's.

Ordinary (non-catalog) ND is unaffected: `ff02::1` and solicited-node
groups are not in the catalog, and the #15671/#15931 ND default (admit
unless `ndp except`) is preserved verbatim there.

## Risk

- One deliberate behaviour change, in the fail-closed direction: ND to a
  catalog multicast group through a ZONE view now requires an explicit
  `ndp` positive (or `any-service`), matching the override arm and the
  kernel chain on SCOPED ingress. Zones relying on the old zone-arm ND
  default to a catalog group (e.g. an OSPFv3 zone without an `ndp` token
  receiving NS to `ff02::5`) lose that admit on the userspace path; on
  scoped kernel ingress it was already denied, so this removes a
  cross-surface inconsistency rather than opening a new one. For
  UNSCOPED/unknown views userspace is now deliberately stricter than
  the kernel (which admits an `ssh`-only view's ND to `ff02::5` there):
  an OSPFv3 zone without an `ndp` token whose ingress userspace cannot
  show as scoped loses that admit where the unscoped kernel would have
  kept it — the fail-closed side of the discrepancy, chosen because the
  alternative admits catalog ND whenever scoped-ness is unknown.
  Unicast and non-catalog ND (including `ff02::1` / solicited-node) are
  unchanged.
- All other verdicts are preserved by construction (single body, same
  order) and pinned by the named regression cells above.
