# Issue #12880 — preserve NAT64 sessions during policy rematch

## Why

An IPv6 session can have a translated IPv4 destination (NAT64). Rename rematching and rollback re-authorization treated the session family as the destination family too, so they rejected the translated destination or queried it as IPv6. A policy that still permitted the translated tuple could therefore lose its session during rename or rollback.

## What

- Helper rename rematch and nested rollback re-authorization now classify the translated destination by its strict textual family, independently from the original tuple family. IPv6 source / IPv4 translated destination remains an admitted NAT64 tuple; malformed or out-of-policy translations remain fail-closed.
- Legacy v6 rename rematch uses the session's NAT64 flag to interpret the left-aligned IPv4 translated destination in the 16-byte ABI. Ordinary IPv6 destinations, including those with twelve trailing zero bytes, remain IPv6.
- Regression tests cover helper rename, legacy v6 rename, rollback candidate re-authorization, an out-of-scope translation, malformed translation, and ordinary IPv6 DNAT.

## Validation

Helper rename and legacy v6 rematch returned `permitted=false`; rollback re-authorization returned `kept=1 permitted=<nil>`.
- GREEN: the same focused command passed (`ok github.com/psaab/xpf/pkg/daemon`).

| Mutant / defect regression | Coverage / result |
|---|---|
| Invert translated-family recognition | Killed by `TestRematchRenamedMatchNAT6412880`; confirmed with an inverted-condition run. |
| Drop translated-destination consultation | Positive rename and re-authorization cases use a wire destination outside the permitting IPv4 destination; tests fail if the translation is ignored. |
| Wrong family on translated query | IPv4 policy destination is required for both helper rematch and rollback; IPv6 treatment cannot match it. |
| Wrong/default permit for out-of-scope translation | Out-of-scope translated destination is asserted denied in helper rematch and retained for deletion in rollback. |
| Swallow invalid translation | Malformed helper NAT destination is asserted denied. |
| Treat zero-tailed IPv6 as left-aligned IPv4 | Legacy test asserts ordinary v6 DNAT to `2001:db8::` still permits when the NAT64 flag is clear. |
| Off-by-one | Not applicable: the fix introduces no range or threshold boundary. |

## Risk

The query family changes only for the translated destination; original tuple validation and the IPv4-source/IPv6-destination fail-closed gate remain intact. Legacy interpretation is gated by `SessFlagNAT64`, avoiding ambiguity with genuine IPv6 translations. The rebound session record continues to carry the original wire tuple, not translated addresses. No live dataplane mutation was performed.
