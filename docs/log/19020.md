- **Issue**: #19020, security.
- **Cause**: The PSK owner model treated `fqdn:^.*$` as an ordinary FQDN string, although strongSwan's credential-owner parser recognizes anchored `fqdn:` regexes and matches a concrete FQDN lookup against the regex owner. Thus a broad regex owner could match every concrete FQDN while the xpf collision detector found no shared owner.
- **Change**:
  - Added an owner-only parser marker for strongSwan's anchored regex-enabled prefixes (`fqdn:`/`dns:`, `rfc822:`/`email:`/`userfqdn:`, and `asn1dn:`). Local identities continue to use the ordinary parser and remain directed lookups, not regex owners.
  - Directly model FQDN/RFC822 `^.*$`, literal-anchored `^literal$` (including escaped ERE metacharacters), and `^prefix.*$`. Their exact/prefix languages are intersected precisely with ASCII case folding on both pattern literals and candidate strings, matching strongSwan's `REG_ICASE`; disjoint anchored prefix patterns remain a positive control. Regex forms outside the decidable subset, non-ASCII comparisons whose `REG_ICASE` behavior depends on charon's locale, nonprintable identities (whose strongSwan `%Y` form replaces bytes with `?`), and DN regexes are treated as possible collisions (fail-closed). Empty presented encodings are excluded, matching strongSwan's `matches_regex` guard.
  - `ipsecLookupSelectsOwner` applies the regex only on the owner/right side and preserves `lookup->matches(owner)` direction. The shared conflict detector also protects the renderer; no separate render rule was added.
  - Added config cells for match-all collisions in both gateway orders, including raw nonprintable FQDN bytes, exact/prefix behavior, mixed-case pattern/candidate prefix overlap, a mixed-case regex-prefix intersection, and concrete disjoint controls. Directed-lookup cells cover the mixed-case owner in both gateway placements; fail-closed checks cover character classes, alternation, and quantified groups. The renderer cell uses a mixed-case regex owner and proves conflicting connections are skipped while an unrelated IP-identity VPN remains.
  - Updated the config-schema and IPsec README collision descriptions.
- **Oracle evidence**: `/var/tmp/fz/rev-AC-18434-oracle/oracle-m` still exists, but its source uses the plain parser; a temporary wrapper built against installed strongSwan 6.1.0 called `identification_create_from_string_with_regex()`. The exact wrapper source is preserved in `docs/log/19020-oracle.c`. With the regex owner first and a concrete FQDN second, `fqdn:^.*$` vs `@vpn.example` reports final matches columns `0/2`; reversed, `2/0`. `fqdn:^vpn$` behaves likewise for `@vpn`, but gives `0/0` for `@other`. `fqdn:^vpn.*$` matches `@vpn.example` one-way (`0/2`) and not `@xvpn.example` (`0/0`).
  For `fqdn:^.*$` vs `fqdn:#780a79` (raw bytes `x`, LF, `y`), matches are `0/2` and `2/0` on reversal: `identity_to_string()` calls `chunk_printable(..., '?')` before regex evaluation, so the candidate becomes `x?y`. The static matcher therefore treats such raw nonprintable encodings as undecidable, never disjoint.
- **Review follow-up**: Prefix matching now folds both the regex literal and candidate, including regex-vs-regex prefix intersection. Strict refusal diagnostics describe matching or overlapping/undecidable selector languages instead of asserting equality of identity strings.

This intentionally favors preventing one peer identity from selecting distinct PSKs over accepting an undecidable regex intersection.
