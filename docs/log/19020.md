- **Issue**: #19020, security.
- **Cause**: The PSK owner model treated `fqdn:^.*$` as an ordinary FQDN string, although strongSwan's credential-owner parser recognizes anchored `fqdn:` regexes and matches a concrete FQDN lookup against the regex owner. Thus a broad regex owner could match every concrete FQDN while the xpf collision detector found no shared owner.
- **Change**:
  - Added an owner-only parser marker for strongSwan's anchored regex-enabled prefixes (`fqdn:`/`dns:`, `rfc822:`/`email:`/`userfqdn:`, and `asn1dn:`). Local identities continue to use the ordinary parser and remain directed lookups, not regex owners.
  - Directly model FQDN/RFC822 `^.*$`, literal-anchored `^literal$` (including escaped ERE metacharacters), and `^prefix.*$`. Their exact/prefix languages are intersected precisely; disjoint anchored prefix patterns remain a positive control. Regex forms outside the decidable subset, non-ASCII comparisons whose `REG_ICASE` behavior depends on charon's locale, and DN regexes are treated as possible collisions (fail-closed). Empty presented encodings are excluded, matching strongSwan's `matches_regex` guard.
  - `ipsecLookupSelectsOwner` applies the regex only on the owner/right side and preserves `lookup->matches(owner)` direction. The shared conflict detector also protects the renderer; no separate render rule was added.
  - Added config cells for match-all collisions in both gateway orders, exact/prefix behavior, disjoint prefixes, and an undecidable pattern; added directed-lookup cells and a renderer cell that skips the conflicting FQDN connections while retaining an unrelated IP-identity VPN.
  - Updated the config-schema and IPsec README collision descriptions.
- **Oracle evidence**: `/var/tmp/fz/rev-AC-18434-oracle/oracle-m` still exists. Its source uses the plain identity parser, so a temporary wrapper was built against the installed strongSwan 6.1.0 library to call `identification_create_from_string_with_regex()`. In the output's final two columns (`x.matches(y)`, `y.matches(x)`), `fqdn:^.*$` and `@vpn.example` produce `0/2`, with reversed operands `2/0`; `fqdn:^vpn$` and `@vpn` likewise produce `0/2` and `2/0`, while `fqdn:^vpn$` versus `@other` produces `0/0`. `fqdn:^vpn.*$` matches `@vpn.example` one-way (`0/2`) and does not match `@xvpn.example` (`0/0`). These confirm the directed matcher behavior used by the owner model.

- **Risk**: Regexes outside the explicit exact/prefix/match-all model may produce conservative collision refusals for owners that are actually disjoint. This intentionally favors preventing one peer identity from selecting distinct PSKs over accepting an undecidable regex intersection.
