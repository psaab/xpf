- **Timestamp**: 2026-10-13

## Why

The #10308 advisory inspected interface-level tunnels and per-unit tunnels
only for explicitly unit-qualified member strings. A bare `gr-*`/`ip-*` member
therefore warned even when its configured unit 0 was a tunnel. A bare secure
tunnel row is only excluded when the VPN authored that exact bare device name;
`bind-interface st0.0` creates `st0.0`, not `st0`, so the advisory must retain
the warning for a bare `st0` member in that case. The advisory also attributed
ambiguous or runtime-quarantined zone/interface claims even though those claims
are not installed in the dataplane.

This was warning accuracy only: userspace ingress exclusion classifies the
snapshot interface itself and deliberately does not infer a lifeline from a
zone label.

## What

- `userspaceMgmtZoneMemberIsData` now checks the unit-0 tunnel when a member is
  bare, without aliasing a dotted secure-tunnel bind to the base netdev.
  Unknown unbound interfaces and unrelated/nonzero units still retain the
  advisory.
- `appendUserspaceMgmtZoneAdvisoryLocked` now skips quarantined zone names and
  interface logical keys using the existing quarantine helpers.
- Regression tests cover bare unit-0 GRE/IPIP tunnels, matching bare and dotted
  `st0` bind/interface spellings, the warning for a bare `st0` member with a
  dotted bind, a quarantined interface claim, a colliding quarantined `mgmt`
  zone, and true-positive unknown/nonzero-unit members.
- NOT changed: dataplane ingress enforcement, strict/tolerant validation, or
  warning suppression doctrine.
