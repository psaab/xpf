# #9785 — duplicate DHCP pool subnets stop Kea

- **Timestamp**: 2026-09-11
- **Action**: refuse two DHCP pools with one subnet at commit, warn on the tolerant path, and render each prefix once.
- **File(s)**: listed under Change.

## Defect

Each pool renders as its own Kea `subnet4`/`subnet6` entry. Kea refuses a second entry for a prefix it already holds and then loads nothing, so one duplicate stops DHCP for every pool on the node. The issue records it on the loss userspace cluster: a second group for `10.0.61.0/24` on `reth1.0` committed clean, `kea-dhcp4-server` exited with `subnet with the prefix of '10.0.61.0/24' already exists`, and a LAN client's DISCOVER went unanswered.

## Design notes

- **Masked key.** `10.0.61.1/24` duplicates `10.0.61.0/24`: one network, one client population. Whether Kea masks before its own duplicate check was not measured. Keying masked refuses the pair under either reading at commit, and the belt keys the same way.
- **Keep-first.** The belt keeps the first pool in the stable (group name, pool) order. That is not necessarily the older pool, but it is deterministic across reloads, and commit refuses the pair, so only a tolerant-path config reaches it.
- **Overlap is out of scope.** Nested prefixes of different lengths keep only the #1778 ambiguity warning.

## Prior cell narrowed

`TestWarnAmbiguousSubnetSelection` rows "same subnet, one multi-interface group warns" and "both groups with selectors do not warn" use identical prefixes and counted every warning through `m.warn`. The belt adds one skip warning to each. The rows now split the warnings: the first asserts one ambiguity warning naming both groups plus one skip warning, and the second asserts no ambiguity warning plus one skip warning. When the ambiguity warning fires, which is what #1778 pinned, is unchanged.
