# #18744: refuse introducing a published placeholder cluster key

Per-issue log (see `docs/log/README.md`). Split out of #18719 (its
"product side"), found while rotating the lab clusters off their published
keys for #18724.

- **Timestamp**: 2026-11-01
  - **Action**: Added `validateClusterAuthKeyPlaceholderStrict`. A strict
    commit over an active config refuses a published placeholder
    (`change-me` / `example-only`, matched without case) that it INTRODUCES
    into `authentication-key` or `additional-authentication-key`.
    "Introduces" is judged byte for byte against the active config's
    accepted set.
    - A pre-existing placeholder keeps committing with the warning,
      including every step of the #6630 rotation off it.
    - Fresh state (no active config: the bootstrap import, check-config,
      day-0, direct CompileConfig) warns only.
    - The tolerant paths downgrade the refusal to a warning (#1960).
  - **Plumbing**:
    - `currentConfigPresent18744` in `compileOpts`, set by
      `currentClusterOpts` whenever configstore supplies an active config,
      with or without a cluster stanza.
    - `clusterKeyIsPublishedPlaceholder` is now the one predicate behind
      the warning and the refusal.
    - The gate runs before the #16858 transition gate.
    - `currentConfigPresent18744` is allowlisted in the #16166
      completeness census. It is presence, not a downgrade.
  - **Validation**:

- **Timestamp**: 2026-11-01 10:40 PST
  - **Action**: Review folds from seats AC and AD on #18754 at `50808e833a`.
    Merged origin/master first (`c7efacb224`, which contains #18732), so the
    census sees the tokenised lab confs.
  - **AC F1 (MEDIUM) and AD's first-commit gap, one fix**:
    - The old decision keyed on `s.compiled != nil`. After a #1922 Item 1b
      first-commit-confirmed rollback and a restart, the store has never
      committed but compiles the empty tree. The bootstrap import there was
      refused, contrary to the documented contract.
    - The interactive first commit on an empty store only warned. That is
      the likeliest way a placeholder gets in, and afterwards it counts as
      pre-existing.
    - Now `Store.placeholderJudgedLocked` decides on the store's commit
      history:
      - a committed store judges every committer against its active config,
        and stops judging only when that config no longer compiles (#1960,
        accepted set unknown, the documented residual);
      - a never-committed store judges every committer except the bootstrap
        import, against an empty accepted set.
    - The bootstrap import is identified by authority: an internal authority
      named `configstore.BootstrapPrincipal`, never a principal string.
    - The decision is threaded through:
      - `CommitWithDescriptionGenAs` → `commitWithDescriptionLocked` →
        `compileAuthSafeCandidate` → `compileTreeAs`;
      - the #9619 peer pipeline, so both views agree;
      - `config.CompileConfigJudgingPlaceholders`, which replaces the
        presence flag.
    - The daemon's bootstrap pre-flight uses `CompileCandidateGenAs` with the
      same authority. Without it a placeholder would fail the pre-flight
      compile and silently switch off the device-map strand check.
    - CommitCheck judges.
