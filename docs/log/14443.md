## Why

Merged firewall policer / three-color-policer `then { discard; loss-priority high; }` (group `then` beside inline `then`, or duplicate policer roots) strict-rejected via #8445, but the lenient arm (`compiler_uniformgates_filter.go`) only appended a warning and returned no error. The compiler's single-valued `ThenAction` is last-wins and the `loss-priority` arms were unfenced, so the group marking won: `ThenAction = "loss-priority high"` → snapshot `DiscardExcess=false` → excess traffic metered and forwarded, the authored discard (the rate limit's only drop) entirely unenforced on lenient load / HA-sync / restore.

## What

Primary poison: new `failClosedPolicerThenConflicts` in `pkg/config/compiler_firewall.go` (mirrors `failClosedFilterTerminalConflicts` #4375) forces `ThenAction = "discard"` for every policer / three-color-policer whose authored `ThenActions` contain both `discard` and a marking action; called from the #8445 lenient arm in `compiler_uniformgates_filter.go`, whose warning now says conflicting policers are forced to discard. The authored set is preserved. Complementary fence: all four `loss-priority` assignments (Keys-tail + children, policer + three-color) now guard with `policerThenSawDiscard9882` like the `forwarding-class` arms. Updated the stale "last-wins drives the dataplane exactly as before" docs in `compiler_opts.go` and `compiler_validate_strict_filter.go`, and updated `TestPolicerThenConflictHarmIsOrderDependent_8445` (pkg/configstore) which asserted the old lenient last-wins survivor. New regression file `pkg/config/policer_then_conflict_lenient_14443_test.go`: group-merged policer + three-color, duplicate-root producer, both authored orders (incl. forwarding-class), and single-action controls on strict+lenient.
