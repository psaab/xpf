# #17139 — NAT64 effective ingress-scope set single-sourced

## Defect (verified live on origin/master e27167e463)

The NAT64 effective ingress-scope set was derived three ways:

1. `validateNAT64ScopeStrict` (`pkg/config/compiler_validate_strict_nat.go`, was :3968-3975) used an inline `FromZones`-else-`FromZone` (and RI twin) fallback under a comment claiming it checks "every authored zone / routing-instance in the union" — with `FromZone="a"`, `FromZones=["b"]` it checked only `b`.
2. `nat64EffectiveZones` / `nat64EffectiveRoutingInstances` (was :6316-6359) repeated the same fallback. The `nat64PrefixOwnerKeyScoped` essay (#15678, claiming `FromZones ∪ {FromZone}`) was detached above `nat64EffectiveZones`, so `go doc -u ./pkg/config nat64EffectiveZones` printed that essay as the helper's doc (reproduced at HEAD before the fix).
3. The snapshot builder (`pkg/dataplane/userspace/nat64.go`, was :251-293) computed the deduped union with inline seen-loops.

No live runtime divergence: the compiler forces `FromZone = FromZones[0]`, so fallback ≡ union on compiled configs. The risk is a future relaxation of that normalisation silently splitting gate, shadow key, and wire.

## Fix

- Exported `config.NAT64EffectiveZones` / `config.NAT64EffectiveRoutingInstances` (#17139) as the single normaliser with the builder's union-and-dedup semantics (list order first, singular appended if absent; RI union then #16604 wire-lowered exactly as before). The owner-key essay is back directly above `nat64PrefixOwnerKeyScoped`; unexported wrappers delegate so internal callers (`nat64ScopeCover`, owner key, tests) are unchanged in behaviour.
- `validateNAT64ScopeStrict` now calls `NAT64EffectiveZones` and a documented `nat64GateRoutingInstances` helper — the same union without wire lowering, because the gate validates authored names (`natRoutingInstanceDefined15278` treats `""`/`"default"` as defined; lowering first would hide an authored member). This is one of two pre-existing intentional representations (authored vs wire), not a third derivation of the set.
- `buildNAT64SnapshotsWithFeeds` calls both exported helpers; the inline seen-loops and the duplicated #16604 stamping loop are deleted (the exported RI helper performs the identical lowering + dedup).
- Review fold (Rev18177Opus F1/F2): distinct authored members can lower to the same wire token — singular `default` beside a `""` list member under the explicit-master flag both become `NATDefaultRoutingInstanceWire` — so `NAT64EffectiveRoutingInstances` dedups again AFTER all lowering (first occurrence wins); previously that shape shipped a duplicated wire token and a non-canonical (double-token) owner/shadow key. The union loop itself is now single-sourced in unexported `nat64UnionRoutingInstances`, used by both the exported helper (which lowers) and the gate twin (which must not lower).
- Review fold (Rev18177bOpus): `NAT64EffectiveZones` copied the authored list verbatim (dedup only singular-vs-list), so `FromZones ["b","b"]` yielded `["b","b"]`, a non-canonical owner key different from `["b"]`, and duplicated snapshot tokens — while the RI side collapsed intra-list duplicates via its post-lowering dedup. `NAT64EffectiveZones` now collapses intra-list duplicates (first occurrence wins), matching RI; the same test gains the `["b","b"]` shape asserting one token and the canonical single-token owner key.
