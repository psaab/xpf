# Issue #13661 — preserve one-shot neighbor probe authorization

## Why

The neighbor monitor consumed the one-shot solicitation timestamp before it
knew whether an `RTM_NEWNEIGH` changed the neighbor MAC. A same-MAC `NUD_DELAY`
refresh therefore spent authorization without using it. A legitimate MAC move
shortly afterward was rejected as unsolicited, interrupting failover forwarding
until another probe.

The RX ARP learn path used the same eager consumption pattern, so it now
preserves evidence across same-MAC refreshes while retaining one-shot behavior
for accepted first learns and actual MAC changes.

## What

The netlink and RX ARP paths peek at recent probe evidence before their
insert, and consume it only after a successful insert that changes the stored
neighbor value. Same-MAC refreshes preserve the token; accepted first learns
and actual MAC changes retain existing one-shot consumption behavior.

Added a fail-on-revert regression for a same-MAC NUD_DELAY refresh followed by
a real MAC move.

## Validation

- RED on pristine master: the retained NUD_DELAY regression failed because
  the subsequent MAC update returned `None` after the intermediate no-op
  event consumed the token. An initial first-learn scope experiment also
  exposed established one-shot behavior on the RX ARP path, so that unrelated
  behavior was intentionally left unchanged.
- GREEN after the final rebase: `cargo test --bins neighbor::` passed
  (93 passed), and the targeted #13661 regression passed (1 passed).
- Full `cargo test --bins`: 8,050 passed, 4 failed, 8 ignored. Each failure
  reproduced on pristine master 026c850a3 with its exact test filter:
  #10659 parked-fragment retry, both GRE local-delivery host-inbound tests,
  and #10591 authority-window expiration. None touch the neighbor changes.

## Risk

The changed-MAC authorization remains one-shot. Unsolicited differing-MAC
updates remain refused, and NUD_PERMANENT continues to authorize its existing
kernel-neighbor updates.
