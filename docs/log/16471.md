# #16471 — test-failover pool phase measured the loss cluster's pool on tcp/udp

- **Timestamp**: 2026-10-24
  - **Action**: `test/incus/test-failover.sh` hardcoded the loss-userspace
    pool (`POOL_SRC` 10.0.61.240, `POOL_NAT_ADDR` 172.16.80.7) and the
    tcp/udp cluster envs did not override it, so a tcp/udp failover run
    bound a source the cluster's `rule pool-snat` (10.0.62.240/28 resp.
    10.0.63.240/28) never matches and reported the resulting zeroes as
    #8280/#8297/#8314 product defects, while never exercising the real
    pools (172.16.80.12/.13). The script now derives both values from
    `$CLUSTER_CONF`'s `rule pool-snat` (pool name → pool address, match
    prefix → source host), following the `persistent-nat-failover.sh`
    `resolve_pool` precedent; explicit env/script values are honoured only
    when they agree with the derivation, and any disagreement — no pool
    rule, unreadable conf, or a stale override — VOIDs the pool phase
    (VOID cells at the allocator, post-failback proxy-ARP, and fresh-flow
    observation points; exit 77 via the summary's VOID precedence) instead
    of emitting false FAILs. The unconditional post-failback
    `check_proxy_arp_ownership` call is likewise VOID-guarded so an empty
    pool address cannot read as a 0/0 owner failure. All three cluster
    envs now state their pool values explicitly (loss 10.0.61.240/.7,
    tcp 10.0.62.240/.12, udp 10.0.63.240/.13).

    `TestClusterConfigKeepsAPoolModeSourceNATRule8280` are extended from

    rule cover, pool membership, and proxy-ARP asserted per cluster via
    `CheckText`), and a new hermetic cell
    `TestFailoverPoolDerivationMatchesClusterConf16471` asserts the
    reporter's probe reports MATCH for all three envs and pins the
    script's derivation/VOID wiring. Verified RED on revert (env/script
    changes stashed: both cells fail naming the missing/mismatched
