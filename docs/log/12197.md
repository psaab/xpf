## Change

`test-failover.sh` now records the failback event timestamp when it observes the last requested RG move, relative to the main iperf start. The oracle receives both crash and failback timestamps. A completed client before manual failback is VOID because it cannot witness that event.

`iperf3_sum_parse.py` accepts optional `--failback-at` and applies the established-stream recovery check at that event as well as the crash. The failback verdict is VOID when the stream telemetry ends before there is post-failback evidence; an observed stream loss is FAIL. `iperf-throughput-selftest.sh` asserts both event arguments, the timestamp capture, and early-completion handling.

## RED then GREEN evidence

Before the fix, the synthetic 120-second JSON shape (brief two-second crash outage, then seven of eight streams stop after failback while one remains at 2.925 Gbit/s) passed both existing checks:

```text
PASS longest outage was 2 consecutive low-throughput intervals (budget 2)
PASS all 8 pre-failover streams (5, 6, 7, 8, 9, 10, 11, 12) resumed data within 3s
```

With the second event wired, the same shape fails at failback while the crash and aggregate checks remain green:

```text
PASS longest outage was 2 consecutive low-throughput intervals (budget 2)
PASS all 8 pre-failover streams (5, 6, 7, 8, 9, 10, 11, 12) resumed data within 3s
FAIL streams 6, 7, 8, 9, 10, 11, 12 carried data before failback but did not resume within 3s
```

A client log ending at 31s with failback at 60s emitted `VOID client telemetry ends at 31.00s, before the failback event at 60s: no failback stream evidence`.
