# #16485 — `show security flow` printed the configured close windows, not the enforced ones, under `time-wait-state session-ageout` / `apply-to-half-closed-state`

- **Timestamp**: 2026-10-24
- **Context**: #15946 wired `time-wait-state session-ageout` and
  `apply-to-half-closed-state` into the dataplane close-window selector
  (`tcp_close_window_ns_with_app` in `userspace-dp/src/session/mod.rs`)
  and taught `RenderFlowTimeouts` (`pkg/config/show_ssot_15649.go`, the
  SSOT all three show surfaces — CLI, gRPC, REST — call) only about the
  `session-timeout` override. With `session-ageout`, closed TCP
  sessions were held for the established/service window (1800s by
  default) while every surface printed the 30-150s TIME_WAIT figure;
  with `apply-to-half-closed-state`, CLOSING sessions reaped on the
  TIME_WAIT window while show printed `closing-timeout`. The Rust doc
  comment also claimed an explicit TW session-timeout "still wins when
  no app override exists", the opposite of the code (ageout wins).
  `session-ageout` + `session-timeout` committed together silently.
- **Fix**: `RenderFlowTimeouts` now derives the closing and TIME_WAIT
  rows from the same selector as `tcp_close_window_ns_with_app`: the
  TIME_WAIT base is the session-timeout override over
  `time-wait-timeout` over the dataplane 30s fallback; `session-ageout`
  renders the effective established window (configured
  `established-timeout`, else the 1800s default, marked `(default)`)
  annotated "service/established timeout (session-ageout)" — per
  session the dataplane uses the session's application inactivity
  timeout, falling back to that window, and the per-session output
  (`timeout_secs_for`) already shows the true per-session expiry;
  `apply-to-half-closed-state` alone renders the closing row as the
  TIME_WAIT window annotated "time-wait window
  (apply-to-half-closed-state)"; both flags together render both rows
  as the established window. Controls are unchanged (40s
  time-wait-timeout and 90s session-timeout render as before, and an
  unset TIME_WAIT still renders "30s (default)").
  `session-ageout` together with `session-timeout` is now rejected at
  strict commit (`validateTimeWaitStateAgeoutStrict`, wired into
  `runUniformGatesClusterZone`) and downgraded to a warning on the
  tolerant load / peer-sync path (`lenientTimeWaitStateAgeout16485`,
  #1960 no-brick), where the dataplane's ageout-wins precedence
  applies and is what `show` reports. The contradicting Rust comment
  on `tcp_close_window_ns_with_app` now states the ageout-wins
  precedence.

  rendering explicit and default TIME_WAIT windows, lenient ageout
  winning over session-timeout, both-flags closing, no-flags control)
  and `TestTimeWaitStateAgeoutSessionTimeoutExclusion16485` (strict

  `time_wait_ageout_wins_over_session_timeout_16485` pins the

- **Residual**: component level only, matching the finding's evidence

  application carries its own inactivity timeout reaps on that
  per-session value, visible in per-session output.
