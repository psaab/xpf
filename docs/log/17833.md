# #17833: BGP-level multihop must be modelled or refused, not silently dropped

- **Timestamp**: 2026-10-27
- **Action**: Closed the three fail-open gaps the retro-review of #17542
  found in the BGP multihop modelling.
  1. **BGP-level `multihop` is modelled** (`schema_routing.go` bgp
     children map): bare `multihop;` commits at the Junos default TTL
     64, `multihop { ttl N; }` / flat `multihop ttl N` / the legacy
     scalar alias pin the TTL, and the statement is inherited by every
     group/neighbor of that bgp subtree — most-specific wins
     (neighbor > group > bgp), seeded exactly like the #16621
     protocol-level authentication-key. Routing instances share the
     same schema node and compile path, so they inherit the fix. The
     generic #10707 "may be silently ignored" advisory is gone for the
     statement, and `neighbor X ebgp-multihop <ttl>` now renders
     (pkg/frr render test).
  2. **Refusal evidence survives group normalisation**
     (`bgpMultihopChildTTL16679`, formerly `bgpGroupMultihop16679`): the
     flat-set normalisation REPLACED the authored node with a
     synthesised child-less `multihop ttl <v>`, discarding siblings
     BEFORE the extractor's refusal check — a hierarchical
     `multihop { ttl 2; no-nexthop-change; }` compiled TTL 2 on the
     direct/lenient paths while the warning said the statement was
     dropped. Normalisation now runs only when the authored node
     carries no refused flag (any position) and every keyed child is a
     `ttl` statement. The shared flag scan
     (`bgpMultihopHasNoNexthopChange16679`) reads every token position
     of the node, its children and grandchildren, closing the fused
     escapes `multihop { ttl 2 no-nexthop-change; }` (flag at child
     Keys[2]) and flat `multihop ttl 2 no-nexthop-change` (flag on the
     value child), which previously strict-committed clean with no
     warning at all. The extractor honours nothing partial: present=
     false keeps the prior/inherited TTL.
  3. **Unknown children and missing values refuse instead of
     defaulting**: `multihop { banana; }` (also beside a `ttl`
     statement, at neighbor and bgp level) is refused by name at
     strict commit and invents no TTL-64 default on tolerant paths;
     the packed missing-value forms `multihop ttl;` / flat
     `multihop ttl` (no value child) are refused as missing values —
     the walk's bare-form early-return no longer accepts the
     `len(Keys)==2` ttl arm without a value child, and `multihop {
     ttl; }` no longer leniently defaults to 64.
- **File(s)**: `pkg/config/schema_bgp_multihop_16679.go` (validator,

  ttl+flag compiling TTL 2 on direct and lenient paths; fused

- **Risk**: Low. The bgp-level node addition only affects configs
  authoring `multihop` directly under `protocols bgp` (previously
  silently dropped — operators migrating Junos configs get the
  documented behaviour instead of a quiet no-op; configs that relied
  on the drop would now render ebgp-multihop, which is the fix's
  intent). Tightened refusals (unknown children, missing values,
  fused flags) reject shapes that previously compiled with invented
  values — strict commit now fails for genuinely malformed input, and
  tolerant loads keep the inherited TTL plus the specific warning.
  Precedence and rendering for existing group/neighbor spellings are
  pinned by the unchanged #16679 suites and the new control arms.
