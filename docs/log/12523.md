# Issue #12523 — exclude transit globals from filtered Junos-host views

## Why

The shared `GlobalPolicyAppliesToZonePair` predicate treated an empty/`any` global scope as applicable to every filtered zone pair. That is correct for transit policy selection, but the Junos-host gate is a separate path: it evaluates exact host pairs, `any -> junos-host` zone-pair policies, and only globals explicitly scoped to `to-zone junos-host`. An unscoped transit global could therefore appear in a host-bound filtered inventory as though it governed local delivery, although runtime never evaluates it there.

## What

The shared global-selection predicate now requires `match to-zone junos-host` to be exactly the Junos-host scope when the filtered destination is `junos-host`. All other scope matching remains unchanged, so unscoped globals remain selected for transit pairs and from-zone scope still selects the applicable ingress. Local CLI, gRPC text, and remote CLI use the same shared predicate.

Tests pin the helper's unscoped/`any` exclusion, scoped host-global inclusion and ingress matching, plus transit unscoped-global preservation. Filtered remote CLI output verifies unscoped transit global exclusion while keeping a host-scoped global and excluding a different-ingress host global. The gRPC hit-count regression verifies the unscoped global is absent from Junos-host results and totals while exact/from-any zone-pair rules and the host-scoped global remain. IPv4/IPv6 does not affect these zone-scope rules; policy scope selection is family-independent.

| Predicate mutant | Regression that rejects it |
|---|---|
| Invert the host-scope condition | The helper cases require host-scoped globals to match and transit-wide globals not to match. |
| Make the host-scope condition always true | Unscoped/`any` host-filter cases and the remote/gRPC rendered-view checks fail. |
| Exclude all globals on host filters | Host-scoped positive controls in helper, remote CLI, and gRPC tests fail. |
| Family-specific zone-scope omission | Not applicable: this predicate receives zone scope only and has no address-family input. |

## Validation

- **RED before:** `go test ./pkg/policymatch -run '^TestGlobalPolicyAppliesToZonePair$' -count=1` failed for unscoped and `any`-scoped globals selected for `trust -> junos-host`.
- **GREEN after:** `go test ./pkg/policymatch ./pkg/cli ./pkg/grpcapi ./cmd/cli -count=1` passed.
- `go vet ./pkg/policymatch ./pkg/cli ./pkg/grpcapi ./cmd/cli` passed with no output.
- `gofmt -l` over all four changed Go files returned no paths.
- The changed-package regression suite also caught and updated an existing gRPC host-filter expectation that previously included the unscoped global.
- No live-cluster or lab mutation was performed.

## Risk / residual

This is a filtered-view selection correction only. Runtime packet-policy enforcement is unchanged; transit global selection remains unchanged. The host path still includes its explicit `from-zone any to-zone junos-host` zone-pair tier, which is distinct from global policy scope.
