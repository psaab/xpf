# #14676 — clear/display persistent-NAT verbs omit deterministic NAT64 allocators

## Defect

In `userspace-dp/src/afxdp/coordinator/idle_lease_sync_8121.rs`,
`export_idle_persistent_leases` already iterates
`forwarding.nat64.prefixes`, naming each deterministic prefix
`nat64-deterministic-{idx}` and tagging its leases
`deterministic` / `DeterministicPortedIdentity::V6(params)`, and the
import path handles that pool name — so HA idle sync covers NAT64.

The two sibling verbs did not:

- `export_display_persistent_leases` iterated only
  `forwarding.source_nat_rules` (`pool_mode`, dedup by pool name), so
  `show security nat source persistent-nat-table` never listed a
  deterministic NAT64 persistent lease.
- `clear_persistent_nat_leases` likewise iterated only
  `source_nat_rules`, so `clear security nat source
  persistent-nat-table` never called
  `prefix.port_allocator.clear_persistent_leases(now_ns)` — the call
  that revokes leases and stamps the `last_persistent_nat_clear_ns`
  replay fence (plus per-key tombstones) in `nat::allocator`. Revoked
  NAT64 leases therefore stayed live, were invisible to SHOW, and an
  older HA re-import was not clear-fenced for NAT64 allocators.

A daemon restart clears the state, but that is not a defence of an
explicit revoke verb violating its own doc ("Revoke every persistent
source-NAT lease owned by the current forwarding snapshot").

## Fix

Same file, mirroring the existing idle-export NAT64 loop exactly:

- `export_display_persistent_leases`: after the source-NAT pool loop,
  iterate `nat64.prefixes`; for each prefix with
  `deterministic_v6 = Some(params)`, export
  `prefix.port_allocator.export_display_leases(now_ns)`, stamp
  `deterministic = true` and `deterministic_identity = V6(params)`,
  and tag the record `nat64-deterministic-{idx}` — the same pool name
  the idle export and the import gate use, so the SHOW wire
  (`server/handlers/idle_leases.rs::to_display_wire`, which already
  renders V6 deterministic fields) needs no change.
- `clear_persistent_nat_leases`: after the deduped source-NAT loop,
  call `clear_persistent_leases(now_ns)` on every prefix with
  `deterministic_v6.is_some()`, adding the revoked count to the total
  the control verb reports. This stamps the same per-key tombstones
  and batch replay fence on the NAT64 allocator, so a stale pre-clear
  HA record re-imported under `nat64-deterministic-{idx}` is refused
  as `skipped_clear_fenced` by the existing import gate.

NOT changed: the allocator, the wire types, and the Go side. The
round-robin NAT64 arm (`allocate_nat64_pool_port`, `persistent_nat:
true`) also creates persistent BIB leases in the same allocator, but
those leases carry no deterministic identity and the HA idle
export/import path has never carried them (export is gated on
`deterministic_v6`, import only accepts `nat64-deterministic-*`
records) — widening SHOW/clear to them is a separate design question
outside this issue's narrowed scope, which both re-review passes
bounded to the deterministic allocators.

## Risks / residuals

- SHOW now lists deterministic NAT64 leases that were previously
  invisible; that is the intended operator-visibility fix. The Go
  renderer already handles `deterministic_mode = 2` display wires.
- Clear now also revokes deterministic NAT64 leases and fences their
  HA re-import for the existing 60 s replay horizon — identical
  semantics to the source-NAT pool path, no new fence machinery.
- Round-robin NAT64 BIBs remain outside this verb pair, as before;
  no behaviour change there.
