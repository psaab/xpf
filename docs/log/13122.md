# Recreate incompatible WireGuard TUN anchors (#13122)

- **Issue**: #13122, source finding D10-04 (deep-review; validated by the three-way research gate).
- **Cause**: `applyWireguardTunLocked` treated every same-name `TUNTAP_MODE_TUN` device as reusable, even when PI headers were enabled or the link was non-persistent. It also treated every `LinkByName` error as absence and attempted `LinkAdd`; transient lookup failures could therefore collide with the still-existing link and fail with `EEXIST`.
- **Change**: Reuse a WG TUN only when shared `anchorReusable` confirms TUN mode, `TUNTAP_NO_PI`, and persistence. Replace incompatible links; preserve the existing ownership-retry sentinel when replacement fails. Return transient lookup errors directly rather than creating a device.
- **Regression coverage** (`pkg/routing/tunnel_wireguard_reuse_13122_test.go`, `pkg/routing/tunnel_reconcile_test.go`): PI-enabled and non-persistent TUN replacement, compatible reuse, genuine not-found creation, fail-closed transient lookup with recovery, and failed incompatible-link deletion retention.
- **RED evidence**: On pristine `origin/master` `55ab81ef0` plus only the regression test, `go test ./pkg/routing -run 'TestWireguard(IncompatibleTunRecreated|CompatibleTunReused|TransientLookupFailsWithoutCreate|NotFoundCreatesTun|IncompatibleDelFailureRetainsSentinel)13122$' -count=1` failed: incompatible TUNs were not deleted, transient lookup did not fail closed, and failed replacement deletion did not return the retention sentinel.
- **GREEN evidence**: The focused regression passed. `go test ./pkg/routing -count=1` passed; `go vet ./pkg/routing` passed; `gofmt` was run on all changed Go files; `git diff --check` passed.
- **Blast radius / risk**: A transient WG link lookup now fails the apply instead of attempting create, so the caller must retry once netlink lookup recovers. Existing persistent `NO_PI` WG TUNs continue to be reused in place; only incompatible links are replaced.
