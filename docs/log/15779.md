# #15779 — Multi-member expanded community lists emit non-POSIX lookaheads

## Defect

`communityExpandedConjunction` (pkg/frr/policy_render.go, from #15008)
rendered a multi-member expanded community definition as one pattern
of Perl-style positive lookaheads:

```
bgp community-list expanded X permit (?=.*65000:.*).*(?=.*65001:.*).*
```

FRR compiles expanded community-lists with `regcomp(REG_EXTENDED)` —
POSIX ERE, which has no lookahead. bgpd rejects the line with
`CMD_WARNING_CONFIG_FAILED`, and one such failure aborts the whole
vtysh-batched `frr-reload`, leaving every dynamic routing change
stale. The trigger is narrow: at least two members AND at least one
regex member forcing the expanded kind (all-literal multi-member
definitions render on the safe standard line). The existing tests
ratified the bug: `policy_community_multi_15008_test.go` asserted
`Contains "(?="` and `frr_test.go` expected the lookahead line
verbatim.

## Fix

POSIX ERE cannot express an unordered conjunction in one consuming
pattern, so the conjunction is rendered as the disjunction of its
ordered sequences:

- `communityExpandedConjunctionPatterns` returns one pattern per
  permutation of the distinct member factors, factors joined with
  `.*`. FRR matches a list when ANY permit entry matches; a sequence
  entry matches only when every factor matches in that order against
  the joined, sorted community string (`community_str`). The entry
  set therefore matches exactly the routes satisfying every member.
- Literal members keep their whole-token anchoring
  `(^| )member( |$)` so `65000:100` cannot match inside `65000:1000`
  or across a token boundary. Regex members are sequenced as
  authored; a single member (or duplicate-collapsed single) renders
  byte-identically to before.
- The permutation count is factorial, so expanded conjunctions are
  bounded at `maxExpandedCommunityConjunctionMembers` = 4 distinct
  members (24 entries). A definition past the bound renders nothing
  (no public entries, no delete backing) and
  `communityListMissingAtRender` reports it missing, so referencing
  terms fail closed per the #10822 posture (reject terms deny-all,
  other terms skip the dangling branch) instead of an unbounded
  render or a silently ANY-widened list. The same predicate is wired
  into `communityDeleteTarget` and `communityListCollision` so all
  renderability views agree. All-literal definitions are unaffected:
  the standard joined line is linear.

NOT changed: the standard (all-literal) render, the per-member
delete backing for renderable definitions, and single-member
expanded rendering.

## Regression

`pkg/frr/policy_community_multi_15008_test.go`:

- `expandedPatterns15779` extracts every rendered expanded pattern
  and asserts no `(?` survives and each compiles under
  `regexp.CompilePOSIX` — Go's POSIX-ERE oracle for FRR's
  `regcomp(REG_EXTENDED)` (the #8449 agreement).
- `assertConjunctiveMatch15779` evaluates the entry set as FRR does
  (ANY entry matches) and pins conjunction: a route string carrying
  both communities matches; either alone, neither, and the
  literal-inside-a-longer-token case (`65000:1000`) do not.
- `TestExpandedCommunityConjunctionPOSIX15779`: three regex members
  render 3! = 6 entries and stay conjunctive; four members at the
  bound render 24; five expanded members past the bound render
  nothing, report missing, and keep the public delete target; five
  literals stay on the standard line.
- `frr_test.go` MIXED expectation migrated from the lookahead line
  to the two permutation lines.

RED pre-fix: with only the test changes on origin/master, the new
assertions fail — the rendered pattern
`(?=.*65000:.*).*(?=.*65001:.*).*` carries `(?` and fails
CompilePOSIX (`missing argument to repetition operator: '?'`), the
entry count is 1 instead of 2/6/24, and the past-bound definition
renders instead of omitting. GREEN post-fix (see PR Validation).
