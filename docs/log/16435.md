# #16435 — `L3ReverseBucket` embeds `[u32; 256]` per NAT identity: 1104 B/slot, ~310 MB/worker (R3-F06-06)

## Defect

#15087 replaced the L3 reverse index's linear `SmallVec` bucket with a
hashed set plus per-protocol counts to make insert/remove/probe O(1)
under same-destination SNAT fan-in. The counts were stored as
`protocol_counts: [u32; 256]` inline in every `L3ReverseBucket`
(`userspace-dp/src/session/mod.rs`), so each distinct NAT
(server, translated-address) identity cost a 1104 B index slot
(`size_of::<(L3ReverseKey, L3ReverseBucket)>()` = 36 + 1064, measured by
the issue's probe) plus a per-bucket `HashSet` heap allocation and a
1 KiB zero-fill on the session-install path, instead of ~60 B pre-fix.
At the default per-worker cap (`DEFAULT_MAX_SESSIONS = 131072`) with
distinct identities the probe measured `l3_index.len=131072`,
`capacity=229376`, `rss_delta_kb=457896` versus the same-identity
control's `rss_delta_kb=148156` — about 310 MB more per worker for the
same session count, multiplied by the worker count and retained (the
outer table does not shrink after a burst). That competes with UMEM on
VM appliances; helper OOM (the #5838 fail-closed restart) is a
potential consequence, not demonstrated.

## Fix

Keep hashed membership and the exact count semantics; make the counts
sparse, per the issue's suggested direction:

- `userspace-dp/src/session/mod.rs`: `L3ReverseBucket::protocol_counts`
  is now `SmallVec<[(u8, u32); 2]>` — one `(protocol, count)` pair per
  protocol with at least one live member. Real buckets carry 1-3
  protocols, so the two inline slots cover the common case with no heap
  allocation and no 1 KiB zero-fill per new identity; only a bucket
  with 3+ distinct protocols spills. `insert` increments the existing
  pair or pushes a new one; `remove` decrements and `swap_remove`s the
  pair when it reaches zero, so no zero-count pair lingers to gate a
  later exact probe; `count_for` is a linear scan over the (tiny) pair
  list; `total()` is unchanged (`handles.len()`), so the 255-sentinel
  probe path is untouched. Insert/remove stay O(1) amortized in the
  member count (the pair scan is bounded by the distinct-protocol
  count, at most 256 and 1-3 in practice); the probe's bounded
  verification walk in `lookup.rs` is unchanged, as are all insert/
  remove callsites — the counts invariant ("exactly the multiset of
  member protocols, zero-count pairs removed") is maintained at the
  same sites as before.

  Deliberately NOT done: the issue's alternative of dropping the counts
  for a total plus verification walk. The counts decide exact probes
  without walking, and `probe_l3_reverse_bucket`'s fail-closed fallback
  compares visited members against `counted`; keeping sparse counts
  preserves that logic byte-for-byte.

## Regression tests

- `userspace-dp/src/session/l3_reverse_bucket_15087_tests.rs`:
  - `l3_bucket_slot_stays_small_16435` — pins the acceptance bound:
    `size_of::<(L3ReverseKey, L3ReverseBucket)>() <= 128` (pre-fix
    1104), plus sparse-pair behaviour: only live protocols are stored,
    a pair is dropped when its count reaches zero, and an emptied
    bucket carries no pairs.
  - `l3_bucket_sparse_counts_beyond_inline_16435` — a bucket with four
    distinct protocols (past the two inline slots) still counts
    exactly, and removing one protocol entirely ungates it without
    disturbing the others.
  - The existing #15087 cells (`l3_bucket_handles_stay_hashed_and_counted_15087`,
    `same_destination_bucket_insert_remove_probe_15087`,
    `mixed_protocol_counts_gate_exactly_15087`,
    `l3_bucket_100k_insert_remove_stays_flat_15087`,
    `same_destination_probe_stays_flat_15087`, and the remaining cells
    in the file) pin the behaviour the sparsity change must not alter:
    exact/255-sentinel gating, removal of one-of-many, mixed protocols,
    NAT64, plain-forwarding exclusion, and flat scaling.

## Validation

- `cargo check --tests --bin xpf-userspace-dp`: clean (only the
  pre-existing warning set).
- `cargo test --bin xpf-userspace-dp -- l3_`: 56 passed, 0 failed —
  all five pre-existing #15087 cells plus the two new #16435 cells
  green. `cargo test --bin xpf-userspace-dp -- 15087
  reverse_nat_fragment`: 7 passed, 0 failed.
- The wider `nat64_` filter run showed 16 failures in NAT64
  allocator/overlap cells (e.g. `tests_nat64_overlap_8115`,
  `interface_then_nat64_is_refused_14367`); the four sampled failures
  reproduce identically on pristine origin/master (479b23c222) in a
  throwaway worktree — pre-existing master-red in the NAT64 port
  allocator, unrelated to this index (this change touches only the
  L3 bucket's counts storage; the failing cells assert allocator
  port selection). No 15087/fragment cell failed.
- `rustfmt --check` on the two touched Rust files reports the same
  diff set as pristine master (the tree is not rustfmt-clean at the
  installed toolchain); the new code introduces no new diffs.
- The size cell fails against the pre-fix `[u32; 256]` bucket by
  construction (1104 > 128), satisfying the issue's acceptance bound;
  the 131072-identity RSS cell follows from the slot size (each
  retained slot drops ~9x) without re-running the release probe.

## Risk

- Behaviour: none intended. Exact and sentinel probe verdicts, insert
  idempotence (#1753 re-assert), and removal semantics are unchanged;
  the only change is the counts' storage shape. A stale-count drift
  (nat decision changed without reindex) degrades to the same bounded
  scan as before — the probe cross-check is untouched.
- Performance: `count_for`/insert/remove now scan at most
  `distinct protocols` pairs (1-3 realistic, 256 worst-case) instead of
  one array index — still O(1) in the session/member count, which is
  the #15087 invariant. Per-identity memory drops from 1104 B/slot to
  the hashed-set header plus two inline pairs (slot <= 128 B pinned by
  test). The outer index's retained capacity after a burst is
  unchanged (pre-existing); each retained slot is now ~9x smaller.
