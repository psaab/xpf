# A configured RETH-unit link-local installed as an RG VIP is a shared router identity (#16624)

- **Issue**: #16624 (R3-A26-02), residual of #14978 (D34-01 leg 1).
- **Cause**: The cluster RA shared-identity predicate `isSharedStableRASource`
  matched only the auto `fe80::…bf72…` stable pattern. A shared-section
  configured link-local such as `fe80::1/64` on `reth0.50` is installed as an
  RG VIP on the primary (`cfg.RethVIPsForRG(1)` contains `fe80::1/64`), yet
  was classified per-node on all three paths: on demotion
  `clearRethRASendersWithoutGoodbye` cleared nothing and the subsequent
  `ra.Apply` attempted a graceful lifetime-0 goodbye from the just-removed
  VIP (bind failure, retry debt, possible lifetime-0 flash racing
  promotion); at cold-boot standby `startupGoodbyeConfigs` kept the config
  so `WithdrawOnce` retried the absent address on every reconcile tick.
  #14978's regression cell used a configured address *inside* the stable
  pattern, so it never exercised this spelling.
- **Change**: `pkg/daemon/daemon_ra_reconcile.go` / `daemon_ha.go`.
  `isSharedRASource(cfg, rgID, source)` classifies a source as shared when
  it matches the stable pattern **or** is installed as a VIP of the
  interface's RG. The production predicate `isSharedRASourceBothViews`
  additionally requires the *peer* node's effective view (compiled from
  the same active tree via `Daemon.peerRAConfig`) to install the same
  address, which is what distinguishes a shared-section address
  (identical on both nodes, silently cleared) from a `groups nodeN`
  per-node address (different on each node, graceful goodbye retained).
  When no peer view can be derived the local verdict stands (fail-safe
  toward silent clear for a locally VIP-managed source). The same rule is
  applied in `clusterRAConfigSets`, `sharedStableRAInterfaces` /
  `clearRethRASendersWithoutGoodbyePeer`, and
  `startupGoodbyeConfigsFiltered` / `runStartupGoodbye`.
  `TestDemotionPerNodeSourceNotSilentlyCleared14978` now uses a genuine
  `groups node0`/`node1` + `apply-groups "${node}"` fixture (node0
  `fe80::face`, node1 `fe80::beef`) instead of the shared-section
  `fe80::face` spelling that pinned the wrong behaviour.
- **Regression coverage**: `pkg/daemon/ra_stable_active_5861_test.go` —
  `TestConfiguredSharedLinkLocalSilentlyCleared16624` (shared `fe80::1/64`:
  reconcile and demotion-edge silent-clear `[[ge-0-0-0.50]]`,
  `startupGoodbyeConfigsForRG`/`Filtered` return nothing,
  `runStartupGoodbye` never calls `WithdrawOnce` and marks cleanup done);
  rewritten `TestDemotionPerNodeSourceNotSilentlyCleared14978` (both
  nodes: local-VIP/peer-not-VIP precondition, no silent clear on the
  demotion edge or via reconcile, startup goodbye retained);
  `TestDemotionNonVIPSourceKeepsGoodbye16624` (non-VIP, non-stable source
  is not shared). Existing #10779/#10789/#14978 cells must stay green.
- **Risk / residuals**: The peer view is compiled (lenient) once per
  reconcile/demotion pass from the active tree; on a config whose peer
  view fails to compile the local-only verdict applies, which can
  silently clear a `groups nodeN` source for that pass (the pre-#16624
  shared-section behaviour, never a goodbye for a non-VIP source). No
  lab failover capture was performed; the mechanism is exercised
  in-process with spy appliers as in the source probe.
