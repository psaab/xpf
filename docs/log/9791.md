# #9791 — takeover pre-seed kept a reused address's stale owner

- **Timestamp**: 2026-09-11
- **Action**: keep one owner per address, the most recent grant, when the takeover pre-seed merges the local and peer lease sets.
- **File(s)**: `pkg/dhcpserver/lease_sync.go`, `pkg/dhcpserver/lease_merge_address_9791_test.go` (new), `pkg/dhcpserver/README.md`, `docs/log/9791.md`.

## Defect

`mergeLeasesByIdentity` builds the memfile a promoted node's Kea loads (#5040). It deduplicated by `SyncLease.IdentityKey()`, which is address + client, and let the local row win only an identity conflict.

A stale local row for `10.0.61.100` (the old client) and the peer's row for `10.0.61.100` (the new client) are different identities, so both were written, local first. In #9729's lease-failover run 6 the promoted node's memfile held three rows for `.100`, all naming the client that had released it, and the client holding the address was refused its renewal.

## Change

- **Pass 1, unchanged:** union by identity; the local copy wins the same binding.
- **Pass 2, new (`oneOwnerPerAddress9791`):** one row per address, keeping the most recent grant:
  - recency is `ValidLife - Remaining`, the seconds since grant at read time;
  - when either row lacks its valid lifetime, the later expiry wins;
  - a tie keeps the local row.
- A v6 key includes the lease type and prefix length, so an IA_PD /56 and /60 on one base address stay separate.

## Design notes

- **The recency error is bounded by the sync interval.** The peer set is as old as its last sync, so the comparison can be off by that much. A re-grant to a new client follows the old lease's release or expiry, which puts the two grants much further apart.
- **Scope.** The issue left two mechanisms open. This change fixes the first: the merge writing both rows. The second is client A's binding never reaching the held peer set before the takeover. The lease-failover harness run against this build is what separates them.

## Lab gate: harness fix

- **Timestamp**: 2026-09-11T15:20Z
- **Action**: The first lab run (ledger `e78044fb0a814822`) was VOID. It aborted
  with `FATAL: cannot read client A's MAC` after client A took its lease and the
  standby header check passed.

    `nsenter --net=/run/netns/<ns> cat /sys/class/net/<if>/address`.
  - `/sys/class/net` lists the devices of the network namespace that mounted
    sysfs, so a netns switch alone cannot see the namespace's macvlan.
  - Measured in a private user and network namespace, with a dummy carrying
    `02:97:91:00:00:01`:

      with `No such file or directory`;
    - the same read after remounting sysfs in the namespace returns the
      address.
  - Step 4b, which asserts the promoted lease file binds the address to client
    A's MAC, was therefore unreachable on master.
  - The client cleanup's interface lookup had the same defect, and failed
    silently.
- **Action**: A second run (ledger `fb4dcd7704a41be9`) with `ip netns exec`
  in place of `nsenter --net` was VOID on the same step. The LAN host is an
  incus container. In a lock cell there, with a temporary namespace:
  - `ip netns exec` printed `mount of /sys failed: Operation not permitted`,
    and so did `ip -n`;

    `nsenter --net=... ip -o link show dev v9791b` returned the MAC set on it
    (`02:97:91:00:00:03`);

  `ns_addr4` already reads the address that way, which is why the lease step
  passed.
- **File(s)**: `test/incus/dhcp-lease-failover.sh`. Both reads now use netlink
