# Connected-stream fallback replay no longer resurrects closed sessions (#16627)

- **Issue**: #16627 (R3-A27-01).
- **Cause**: `flush_session_deltas` pushed every delta to both legs: the
  lossless event stream and the per-binding RPC-fallback FIFO. While the
  stream was connected, Go's 5 s reconciliation drain later popped the
  fallback copy and `QueueSessionV4`/`QueueDeleteV4` re-stamped it with a
  fresh generation. A partial replay (more than 256 pending, or a cap
  hole) therefore resurrected sessions the stream had already closed
  (the replayed open out-ranked the earlier close and survived the
  open-only LossResync until idle timeout) and transiently deleted live
  same-tuple successors.
- **Change**: The two legs are now alternatives, per
  `docs/session-sync-architecture.md`.
  - Per-binding sequence: `SessionDeltaInfo` gains `stream_seq`
    (Rust `stream_seq: u64` + Go `StreamSeq`), assigned by the Rust
    lossless enqueue (`push_delta_lossless_within_seq` returns the wire
    seq; `send_lossless_encoded` now returns the enqueued seq) and
    stamped onto binary-leg deltas by Go's
    `installEventStreamCallbacks` from the frame header. 0 means the
    stream never carried the delta. The field participates in the #7194
    derived schema fingerprint on both sides (both producers derive it,
    so the halves still agree), so a mixed old/new helper-daemon pair
    mismatches and withholds exactly like any prior schema addition.
  - Rust (`afxdp/session_delta.rs`): `flush_session_deltas` mirrors a
    delta into the RPC-fallback buffer ONLY when the lossless enqueue
    did not succeed — never on mere `is_connected` (a connected-but-full
    channel still mirrors, with `stream_seq` 0). CommandExport deltas
    never attempt the stream (#9630) and always mirror. A failed enqueue
    still latches loss-of-sync, so the #2442 owner-RG resync re-exports
    table truth (deliver-or-resync). The prior `is_connected` accessor
    is removed.
  - Go (`full_resync_transaction_9767.go`):
    `discardUserspaceSessionDeltasLocked` now discards ONLY drained
    deltas whose `StreamSeq` is non-zero and at or below the applied
    watermark (`EventStream.LastAppliedSequence`, new accessor over
    `lastAppliedSeq` in `eventstream.go`) — never on mere connected.
    Unsequenced and ahead-of-watermark deltas queue through the normal
    locked path. It records the helper's delta-schema fingerprint ONLY
    on a valid status (err == nil); an error batch still partitions,
    counts via the #15217 counter, and propagates. The connected arm of
    `eventStreamFallbackLoop` passes `es.LastAppliedSequence()`.
- **Regression coverage**: Go
  `TestConnectedDrainDiscardsStreamedReplay16627`
  (`daemon_ha_userspace_stream_live_test.go`) drives open S1 / close S1 /
  open S2 where S2 is the SAME-KEY successor (same SrcPort, differing
  egress) through `handleEventStreamDelta`, applies frames to a real
  receiver, and replays every prefix plus the standalone
  {close S1, open S2} suffix through the production connected fallback
  loop, asserting the receiver stays in the stream-only state;
  `TestConnectedDrainQueuesUnsequencedReplay16627` pins that a
  StreamSeq-0 fallback delta still queues while connected;
  `TestDiscardOnlyCoveredByAppliedWatermark16627` and
  `TestDiscardRecordsSchemaOnlyOnValidStatus16627` pin the watermark
  partition and the valid-status-only schema recording directly.
  RED-on-revert (executed): routing the connected arm back through
  `drainUserspaceSessionDeltasLocked` fails
  replay_open_S1_only / replay_close_S1_only / replay_open+close_S1.
  Rust `stream_delivered_delta_is_not_left_in_fallback_buffer_16627`
  (`session_glue/tests.rs`) asserts a successfully streamed delta
  (incremental and bulk) leaves the fallback buffer empty with seq 1 on
  the stream, a connected-but-full enqueue failure still mirrors with
  stream_seq 0, disconnected / no-handle / CommandExport flushes mirror.
- **Risk / residuals**: A delta flushed in the instant the stream drops
  is mirrored (enqueue failed) rather than lost; that copy carries
  stream_seq 0 so a later connected drain queues it once — the same
  deliver-or-resync contract as #2874, healed by the loss-of-sync
  resync it also triggers. No lab cluster run was performed; coverage
  is daemon-level and helper unit-level as the issue's acceptance
  specifies.
