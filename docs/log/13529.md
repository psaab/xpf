# #13529: distrust stale IPv6 relative L4 offsets

## Trace and finding

`parse_session_flow_from_frame`'s IPv6 arm trusted `meta.l3_offset` only when
its nibble matched, but computed `meta_rel = l4_offset - l3_offset` and applied
it to the wire-resolved L3 regardless of whether the stamp was trusted. This
could pair a corrected L3 with an L4 offset derived from a stale L3 stamp and
parse payload bytes as a session tuple.

The primary production metadata producers include the XDP ingress shim and
logical tunnel ingress. The latter (`logical_ingress.rs`) computes the absolute
offsets by adding the synthetic L3 base to the parser-supplied relative L4
offset. GRE obtains that relative offset from `parse_inner_protocol_and_offsets`
(`gre.rs`), whose IPv6 path uses the shared extension-header-aware byte parser.
These paths establish freshness for the normal packet they parse, but do not
make an independently supplied `UserspaceDpMeta` offset pair authoritative at
every later consumer. The issue is reachable at the frame parser boundary when
an L3 stamp is wrong while its L4 displacement remains plausible. Other
protection patterns already reflect the invariant: `live_frame_ports_from_meta_bytes`
and the `parse_session_flow_from_bytes` last-resort offset fallback derive the
L3 via `nibble_checked_l3` and distrust L4 whenever `stamp_trusted` is false.

## Fix

The IPv6 frame parser now gets `l3` and `stamp_trusted` from
`nibble_checked_l3`. It applies the metadata-relative L4 displacement only
when the stamp pair is trusted; otherwise it derives L4 from the wire via
`frame_l4_offset`. The declared IPv6 end and non-first-fragment checks remain
in place. This adds no allocation or copy on the parsing path.

## Regression

`v6_distrusted_l3_stamp_does_not_reuse_stale_relative_l4` uses a wrong L3 stamp
and stale relative L4 displacement whose payload bytes encode a different
TCP tuple. It verifies that the wire-derived TCP tuple is used instead.

## Validation

- Pristine `origin/master` plus this regression:
  `cargo test -p xpf-userspace-dp v6_distrusted_l3_stamp_does_not_reuse_stale_relative_l4`
  failed as intended: expected source port `0x1234` (`4660`), observed stale
  payload port `0xabcd` (`43981`).
- Fixed worktree, same targeted command: 1 passed.
- Fixed worktree,
  `cargo test -p xpf-userspace-dp inspect_iplen_tests`: 55 passed.
- `cargo fmt --all -- --check` and `rustfmt --check` on the two touched Rust
  files report pre-existing formatting differences in unrelated code/files;
  no formatting was applied to avoid a repository-wide churn.
- Full `cargo test -p xpf-userspace-dp` ran 7,960 tests in the main binary
  and failed in the unrelated `runtime_view_publish_and_read_sites_are_pinned`
  integration test (`tests/runtime_view_publish_canary.rs`), reporting six
  source-canary violations in untouched runtime-view files. The same isolated
  canary fails on pristine master with the identical six violations.
- `cargo clippy -p xpf-userspace-dp --tests -- -D warnings` is blocked by four
  existing clippy errors in untouched `build.rs` (`collapsible_if` twice and
  `needless_borrow` once, plus another `collapsible_if`).
