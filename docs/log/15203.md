# #15203 — classify the benign IS-IS-removal frr-reload failure

- **Timestamp**: 2026-10-19
- **Action**: re-check a failed `frr-reload.py --reload` with
  `frr-reload.py --test` before falling back, so removing IS-IS from an
  interface no longer reports a degraded reload for a correct end state.

## Why

The render places `ip router isis xpf` and `isis circuit-type` /
`isis passive` in one interface block (`pkg/frr/protocols_render.go`).
When the operator removes IS-IS from such an interface, `frr-reload.py`
computes a deletion diff that removes `ip router isis` before the
per-interface `no isis circuit-type`; isisd rejects the dependent
removal (YANG area-tag missing) and the script exits non-zero. The
running end state is already correct — the next retry reports rc=0 —
but xpf fell back to the additive `vtysh -f` path, returned
`ErrFRRReloadDegraded`, set the `xpf_frr_reload_degraded` gauge, armed
the retry loop, and failed the commit: a false failure signal on a
routine removal (A12-06, severity Low).

Verified with the local FRR 10.2.1 `frr-reload.py --test`: deleting the
whole IS-IS stanza emits `no router isis xpf` first, then the
per-interface `no ip router isis` / `no ipv6 router isis` /
`no isis circuit-type` / `no isis passive` deletions — the ordering
that strands the dependent removal.

## What

- `pkg/frr/vtysh.go`: new `FrrReloadPyTest` executor method running
  `frr-reload.py --test --stdout <conf>` with the same process-group
  teardown contract as `--reload`. `--test` exits 0 even when a diff
  remains, so the output is inspected: any content under a
  `Lines To Add` / `Lines To Delete` header is a remaining diff and
  returns an error; an empty diff returns nil.
- `pkg/frr/manager.go` (`reloadLocked`): after a non-pytools-missing
  primary failure, `reloadTestConverged15203` re-checks. An empty diff
  certifies convergence — the QNH metric reconcile still runs (a failed
  reload may have deleted the memory-only overlay before rejecting a
  line, #15183) and the reload returns nil. Any doubt falls through to
  the additive fallback unchanged: fail closed, never certify on an
  unproven re-check. The pytools-missing arm is checked first and never
  reaches the re-check.
- Test doubles (`fakeExecutor`, `RecordingExecutor`, and the
  api/cli/grpcapi/daemon fakes) gain `FrrReloadPyTest` with a
  fail-closed default (a diff remains) so every pre-existing degraded /
  hard-failure cell keeps its behaviour; only the QNH fallback
  operation-order expectation gains the new `reload-test` step.
- `pkg/frr/README.md`: benign-reload re-check bullet next to the
  degraded-mode contract.

NOT changed: the IS-IS render (staging the removal in the render cannot
fix a diff computed by frr-reload.py against the live running config),
the degraded-retry loop (a failed retry attempt is not re-checked — it
keeps its cadence and a later primary success or a newer commit's
re-check converges it), the fallback, and the QNH reconcile itself.

## Risk

- A benign certification requires the live running config to match
  `frr.conf` with zero diff at re-check time; a racing external FRR
  change in the same window could in principle be masked, but xpf is
  the sole writer of the managed section and the window is one reload.
- The re-check adds one bounded (15s) `frr-reload.py --test` invocation
  to a failed primary reload; worst-case apply time grows by that leg
  only on the failure path.
- Lab replay (live isisd rejecting `no isis circuit-type`, commit
  returning nil) is not exercised here; the reload-ordering evidence
  above plus the stateful executor cells are its proxy.
