# Issue #16781: SNMP listener pinned to vrf-mgmt loses in-band polls (R3-A48-04)

## Why

With any management interface configured, `snmpVRFDeviceForConfig`
(`pkg/daemon/daemon_snmp_reconcile.go`) returns `vrf-mgmt` and the agent's
only UDP/161 listener was `SO_BINDTODEVICE`-pinned to it
(`pkg/snmp/socket_vrf.go`, `Agent.Bind`). A socket bound to a VRF device
only receives datagrams whose ingress interface is enslaved to that VRF,
so in-band polls admitted by `host-inbound-traffic system-services snmp`
on data zones (documented as an ordinary per-zone service in
`docs/host-inbound-service-matrix.md`) were never received, let alone
answered. The config committed clean, `show snmp` looked healthy, and the
only workaround was moving the NMS onto the management network. This is a
regression shape of the #11427 fix, which required only the management
leg (management replies leave via vrf-mgmt).

## What

- `pkg/snmp/agent.go`: `Agent.Bind` now opens two listeners when a VRF
  device is set — the `SO_BINDTODEVICE` vrf-mgmt socket first (a missing
  device still fails the bind synchronously, the #11427 risk note) plus an
  unbound main-table socket for in-band polls. Both share `:161` via
  `SO_REUSEPORT`; the kernel demultiplexes by L3 domain under
  `udp_l3mdev_accept=1` (already enabled at daemon bring-up). `Serve`
  fans in over both sockets and each reply is written on the socket that
  received its request. Packet handling is serialized across sockets with
  a new `handleMu` because the v3 `lastPacket` auth state is per-Agent;
  the serve budget is already mutex-guarded. `Stop` closes both sockets.
  Without a VRF device there is a single unbound listener, as before.
- `pkg/snmp/pktinfo_linux.go` (new): listener socket control arming
  `SO_REUSEPORT` + `IP_PKTINFO`/`IPV6_RECVPKTINFO` (exactly one family per
  socket — the other family's option fails `ENOPROTOOPT` on a v4-only or
  dual-stack socket), the VRF+pktinfo combined control, and the
  parse/echo helpers: the request's ingress ifindex and local destination
  are captured per datagram and echoed as the reply's pktinfo control
  message, so an in-band reply is sourced from the polled trust/reth
  address on the ingress interface and a management reply from the fxp0
  address via vrf-mgmt. Traps keep the #11427 VRF-pinned dialer unchanged.
- `pkg/snmp/README.md`: `SetVRFDevice` entry-point contract updated to the
  dual-listener behaviour.
- Tests: `pkg/snmp/agent_inband_16781_linux_test.go` —
  `TestSNMPInbandPollWithManagementVRF16781` (netns: fxp0 in vrf-mgmt +
  trust0 in the main table, two manager namespaces; three polls each way,
  replies must come from the polled address) and
  `TestPktinfoParseOOB16781` (ancillary-data round trip).

No daemon change: `snmpVRFDeviceForConfig`, the reconcile hash, and the
#16626 ifindex tracking keep their meaning (the configured management
leg); the agent now serves both legs for that one setting.

- `go vet ./pkg/snmp/` clean; `gofmt -l pkg/snmp/` empty.

## Risk

Neighbours preserved: #11427 (management reply source/path and trap
routing via vrf-mgmt) green; #11740 bind-name transitions and #16626
ifindex-death restarts untouched (daemon reconcile unchanged); traps
still dial via the VRF-pinned sender, so no trap now leaks in-band.
New surface: the agent now answers on data interfaces where SNMP is
admitted by host-inbound config — that is the documented contract
(`docs/host-inbound-service-matrix.md` lists `snmp` as an ordinary
per-zone service); zones that do not admit `snmp` still drop the packets
in the dataplane before they reach the socket. Residual: REUSEPORT
demultiplexing relies on the kernel's L3-domain socket lookup with
`udp_l3mdev_accept=1` (set by daemon bring-up); the netns test exercises
exactly that configuration, and both legs were verified addressed — a
reply never crosses to the other manager across repeated polls.
