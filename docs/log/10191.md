# #10191 — NAT64 IPv6-to-IPv4 total-length narrowing guard

Worktree `fix/10191-nat64`, based on the current project checkout.

- **Timestamp**: 2026-09-18
- **Context**: Read the full open #10191 body and all comments. The outer NAT64 v6→v4 translator and its non-first-fragment sibling narrowed `20 + L4` into IPv4's 16-bit Total Length without rejecting values above 65535; IPv6 payloads 65516..=65535 consequently emitted wrapped wire lengths. The embedded ICMP quote arm remains bounded by `MAX_EMBEDDED_LEN` and is unchanged.
- **Fix**: Both affected translators now fail closed before narrowing when their translated IPv4 total length exceeds `u16::MAX`. Callers retain responsibility for the RFC 7915 §5.1 packet-too-big/drop policy; the translators never silently truncate or saturate.

## Red → green evidence

- **RED before fix**: `nat64_v6_to_v4_rejects_l4_above_65515_10191` returned `Some(65536)` with wire Total Length `0` for L4 length 65516. `nat64_v6_to_v4_nonfirst_rejects_payload_above_65515_10191` returned `Some(65536)` with wire Total Length `0` for non-first-fragment payload length 65516.
- **GREEN after fix**: All four #10191 boundary tests passed: outer and non-first translators reject 65516+, accept exactly 65515, and normal-size outer translation remains successful.
