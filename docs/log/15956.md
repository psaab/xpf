# #15956 — NAT64 reused-buffer zero-fill; SNAT live-map sharding deferred

## Defect (measured)

NAT64 frame builds on the reused-buffer path paid a `resize(capacity, 0)`
zero-fill over the whole build window on every packet, then overwrote
(or never touched) those bytes: `frame/mod.rs:808,820,866` and
`poll_descriptor/nat64_icmp_error.rs:149,252`. Scratch A/B in
perf-exp-nat.md measured allocation+zero-fill at 44-52% of the
82-206 ns/pkt NAT64 build. Production evidence (perf-newflow.md)
REFUTED the companion SNAT claim at achievable rates: 0.06% contended
at ~259 installs/s, ~3 orders of magnitude below bench saturation.

## Fix (shipped)

- New `redirect_pool::extend_pooled_for_build`: publishes a pooled
  checkout's spare capacity as the Vec length via `spare_capacity_mut`
  + `set_len`, with the builder contract documented at the helper.
  No zero-fill pass.
- All five reused-buffer NAT64 sites now use it instead of
  `resize(capacity, 0)`: forward first/non-first and reverse in
  `frame/mod.rs`, both ICMP-error directions in
  `nat64_icmp_error.rs`. The existing `_into` builders and
  `checkout_with_capacity` are reused unchanged; output is truncated
  to the builder's `written` length exactly as before, and the failure
  path recycles the still-unpublished Vec.
- Safety corpus (fail-on-unwritten-read): every `_into` builder
  (forward, reverse, both non-first, both ICMP-error) is fed a
  0xEE-poisoned destination and must match the zero-filled reference
  byte-for-byte (modulo the process-global fragment Identification);
  the production wrappers are likewise checked over a poisoned pool.
  Any translator that read an unwritten `dst` byte would leak poison
  into the published prefix and fail.

## Measurement

Interleaved ABBA A/B, same `_into` builder and pooled buffer, only
the window publication differs (median of 18 rounds/arm, bench-local
host, release):

| payload | resize (before) | extend (after) | saved |
|---|---|---|---|
| 64B (138B frame) | 141.1 ns/pkt | 129.2 ns/pkt | 11.9 ns (8%) |
| 512B (586B frame) | 164.0 ns/pkt | 143.2 ns/pkt | 20.8 ns (13%) |
| 1460B (1534B frame) | 195.6 ns/pkt | 161.1 ns/pkt | 34.6 ns (18%) |

Direction grows with frame size as expected for eliminating a
whole-window memset; absolute ns/pkt of the full production wrapper
on this shared host is noisier (multi-us under contention) and is
not the comparison — the `_into` A/B isolates exactly the eliminated
pass. Bench: `nat64_15956_build_bench` (wrapper) and
`nat64_15956_resize_ab_bench` (isolated A/B), both `#[ignore]`d
measurements in `tests_nat_rewrite.rs`.

## Deferred: SNAT live-map sharding (allocator unchanged)

Sharding `PortAllocatorShared.live` was NOT landed, because uniform
reserve/release pairing cannot be proven locally:

- `live_by_flow` is one `FxHashMap` in `PortAllocatorLiveState`
  (allocator.rs:1067) together with the persistent-lease maps,
  expiration indexes, address-only/pat owner indexes, and `gc_counter`.
  ~37 production `lock_live()` sites interleave flow-map inserts with
  lease/expiration/index updates in single critical sections (e.g.
  `capture_and_replace` at :2628 holds one guard across capture +
  eviction + installation; `allocate_translation` cap check at :3334
  reads authoritative `live_by_flow.len()` for the exact
  `max_tracked_flows` cap, allocator.rs:24-31).
- The prior attempt in wt-15956 broke tracked-flow accounting across
  ~12 insert sites: sharding splits reserve/release pairing (a flow's
  record and its lease/index side effects would land in different
  shards), the exact-cap check loses its single authoritative length,
  and GC chunking (`gc_expired_chunked`) assumes one sweepable state.
  Making it safe is a redesign of the lease state machine, not a lock
  swap — disproportionate at the measured production contention
  (0.06% at achievable rates).

Allocator code is therefore byte-unchanged in this PR.

## Validation

- `nat64_15956_spare_capacity_build_is_byte_identical_with_poisoned_tail`
  and `nat64_15956_into_builders_byte_identical_with_poisoned_dst`
  pass; existing `nat64_` corpus: 342 passed with 2 failures that are
  present independent of this change (loop_body 2002-LOC ceiling at
  this base; a session-open codec test — neither path is touched here;
  full-suite verification is the main agent's gate).
- `tests_pool` (allocator) untouched and not run as a gate here:
  allocator is unchanged, so its result cannot differ from base.

## Risk

Single unsafe addition (`set_len` in the pool helper), sound only
under the documented builder contract; the poison corpus pins that
contract for all six builders. No allocator, session, or HA behavior
changes. Deferred sharding can be revisited if fw0 new-flow rates
ever approach bench saturation.
