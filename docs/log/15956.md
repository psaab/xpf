# #15956 — NAT64 reused-buffer zero-fill; SNAT live-map sharding deferred

## Defect (measured)

NAT64 frame builds on the reused-buffer path paid a `resize(capacity, 0)`
zero-fill over the whole build window on every packet, then overwrote
(or never touched) those bytes: `frame/mod.rs:808,820,866` and
`poll_descriptor/nat64_icmp_error.rs:149,252`. Scratch A/B in
perf-exp-nat.md measured allocation+zero-fill at 44-52% of the
82-206 ns/pkt NAT64 build. Production evidence (perf-newflow.md)
REFUTED the companion SNAT claim at achievable rates: 0.06% contended
at ~259 installs/s, ~3 orders of magnitude below bench saturation.

## Fix (shipped)

- New `redirect_pool::extend_pooled_for_build`: publishes a pooled
  checkout's spare capacity as the Vec length via `spare_capacity_mut`
  + `set_len`, with the builder contract documented at the helper.
  No zero-fill pass.
- All five reused-buffer NAT64 sites now use it instead of
  `resize(capacity, 0)`: forward first/non-first and reverse in
  `frame/mod.rs`, both ICMP-error directions in
  `nat64_icmp_error.rs`. The existing `_into` builders and
  `checkout_with_capacity` are reused unchanged; output is truncated
  to the builder's `written` length exactly as before, and the failure
  path recycles the still-unpublished Vec.
- Safety corpus (fail-on-unwritten-read): every `_into` builder
  (forward, reverse, both non-first, both ICMP-error) is fed a
  0xEE-poisoned destination and must match the zero-filled reference
  byte-for-byte (modulo the process-global fragment Identification);
  the production wrappers are likewise checked over a poisoned pool.
  Any translator that read an unwritten `dst` byte would leak poison
  into the published prefix and fail.

## Measurement

Interleaved ABBA A/B, same `_into` builder and pooled buffer, only
the window publication differs (median of 18 rounds/arm, bench-local
host, release):

| payload | resize (before) | extend (after) | saved |
|---|---|---|---|
| 64B (138B frame) | 141.1 ns/pkt | 129.2 ns/pkt | 11.9 ns (8%) |
| 512B (586B frame) | 164.0 ns/pkt | 143.2 ns/pkt | 20.8 ns (13%) |
| 1460B (1534B frame) | 195.6 ns/pkt | 161.1 ns/pkt | 34.6 ns (18%) |

Direction grows with frame size as expected for eliminating a
whole-window memset; absolute ns/pkt of the full production wrapper
on this shared host is noisier (multi-us under contention) and is
not the comparison — the `_into` A/B isolates exactly the eliminated
pass. Bench: `nat64_15956_build_bench` (wrapper) and
`nat64_15956_resize_ab_bench` (isolated A/B), both `#[ignore]`d
measurements in `tests_nat_rewrite.rs`.

## Deferred: SNAT live-map sharding (allocator unchanged)

Sharding `PortAllocatorShared.live` was NOT landed, because uniform
reserve/release pairing cannot be proven locally:

- `live_by_flow` is one `FxHashMap` in `PortAllocatorLiveState`
  (allocator.rs:1067) together with the persistent-lease maps,
  expiration indexes, address-only/pat owner indexes, and `gc_counter`.
  ~37 production `lock_live()` sites interleave flow-map inserts with
  lease/expiration/index updates in single critical sections (e.g.
  `capture_and_replace` at :2628 holds one guard across capture +
  eviction + installation; `allocate_translation` cap check at :3334
  reads authoritative `live_by_flow.len()` for the exact
  `max_tracked_flows` cap, allocator.rs:24-31).
- The prior attempt in wt-15956 broke tracked-flow accounting across
  ~12 insert sites: sharding splits reserve/release pairing (a flow's
  record and its lease/index side effects would land in different
  shards), the exact-cap check loses its single authoritative length,
  and GC chunking (`gc_expired_chunked`) assumes one sweepable state.
  Making it safe is a redesign of the lease state machine, not a lock
  swap — disproportionate at the measured production contention
  (0.06% at achievable rates).

Allocator code is therefore byte-unchanged in this PR.

## Validation

- `nat64_15956_spare_capacity_build_is_byte_identical_with_poisoned_tail`
  and `nat64_15956_into_builders_byte_identical_with_poisoned_dst`
  pass; existing `nat64_` corpus: 342 passed with 2 failures that are
  present independent of this change (loop_body 2002-LOC ceiling at

  full-suite verification is the main agent's gate).
- `tests_pool` (allocator) untouched and not run as a gate here:

## Risk

Single unsafe addition (`set_len` in the pool helper), sound only
under the documented builder contract; the poison corpus pins that
contract for all six builders. No allocator, session, or HA behavior
changes. Deferred sharding can be revisited if fw0 new-flow rates
ever approach bench saturation.

## Fix round (triple review, PR #15976)

Codex+Opus convergent NEEDS-FIX: `set_len` on a cold/grown checkout
exposed spare capacity that was never written — a soundness
violation regardless of the builder contract. Folded:

- Per-buffer initialized extent tracked as a parallel stack
  (`POOL_INITIALIZED`, extent = last published length; `recycle`
  pairs it, `checkout_with_capacity` pops it — no shared slot, so
  interleaved copy/build checkouts cannot cross-pair extents).
- `checkout_with_capacity` now zero-fills ONLY the delta past the
  recorded extent, once per growth (counter
  `POOL_GROWTH_ZEROFILLS`, test seam `growth_zerofills_for_test`).
  `extend_pooled_for_build` then exposes only initialized bytes.
  Warm steady state pays only the capacity-minus-written delta
  (~20B eth shrink), never the whole window.
- Reverse-UDP audit: the `dst[l4_off+6..l4_off+8]` checksum read at
  nat64.rs:3646 and the v6 twin `out[26..28]` are inside the verbatim
  L4 copy written before them, bounded by the written prefix; a
  truncated reverse-UDP cell (total_len 24, no checksum field)
  proves the failure path returns None without consulting poison.
- New cells: cold checkout (empty pool, one full delta), dirty
  pre-sized growth checkout (0xEE, one delta, no leak), warm rebuild
  (delta-only), reverse-UDP zero-checksum generation + truncation.

Revised bench (after fix, same A/B): saves ~4-43 ns/pkt across
64/512/1460B payloads run-to-run on this shared host (medians per
run: 15.6/14.2/42.6, 4.1/24.1/30.5, 8.5/11.0/25.5 ns) — smaller and
noisier than the unsound version's margin, as expected: the sound
version still zero-fills the small uninitialized delta. Direction
unchanged (grows with frame size).

## Confirmation fold (Codex2/Opus2)

Two findings folded at the next head:

1. **Extent discarded on successful builds.** `recycle` recorded
   only `buf.len()`, so the checkout's filled window past `written`
   was forgotten and same-size reuse re-filled it (sound, but it
   defeated the purpose and falsified the counter claims). Fix:
   `checkout_with_capacity` inserts the filled window into
   `POOL_FLIGHT_EXTENTS` keyed by the buffer's allocation pointer
   (inserted after any realloc); `recycle` removes it and records
   `max(flight_window, published_len)`. Failure/recycle-without-
   publish (no flight entry — foreign buffers, tests) records
   exactly the published length, keeping the prior conservative
   behavior. Warm same-size rebuilds now pay zero re-fill, pinned
   by the growth counter in the cold/growth cell.
2. **Reverse-UDP truncated cell only proved `None`.** The checksum
   reads are now explicitly bounded by the written prefix in code:
   `dst[..l4_written]` in `write_v4_to_v6_translate` (and the
   `out[..ipv4_total_len]` twin in `write_v6_to_v4_translate`),
   where `l4_written = l4_off + l4_len`. The test fixture now
   retains payload bytes past the declared 4-byte L4, so an
   unbounded read would have found a non-zero baseline at
   `l4_off+6` and could have succeeded — the `None` now proves
   the bound, at both the frame and L3 `_into` levels.

Bench after this fold (2 runs): 12.9/22.2/31.6 and 3.4/17.2/36.3
ns/pkt saved at 64/512/1460B — the purpose (no per-packet
whole-window or delta re-fill at steady size) is now actually
achieved rather than amortized away.

## Wrapper fold (Opus3/Codex3)

The ptr-keyed `POOL_FLIGHT_EXTENTS` thread-local map had an ABA /
cross-thread ownership hole: a buffer checked out on a source
thread is recycled on the OWNER thread, where the map is a
different (empty) map and a reused address could alias a stale
extent. Fix: extent now lives IN the pooled buffer wrapper
(`PooledBuffer { buf, initialized }` in `redirect_pool.rs`);
the side map, parallel extent stack, and checkout slot are all
deleted. `TxRequest.bytes` and `PendingForwardFrame::Prebuilt`
carry `PooledBuffer` (Deref/DerefMut + `From<Vec>` + byte-equality
impls keep the ~66 use sites source-compatible in behavior), so
the extent migrates with ownership across the MPSC hand-off by
construction. `recycle` takes the wrapper and restores
`max(initialized, len)`; foreign Vecs enter via `recycle_vec`
(extent = published length). Pinned by a cross-thread cell:
checkout+extend on one thread, move wrapper, recycle on another —
owner pool's same-size checkout sees `initialized == capacity`
with no new delta fill. Warm-reuse (zero steady-state re-fill)
and the bounded UDP checksum reads are unchanged.

Bench (wrapper head): 14.6/24.5/41.1 and 20.6/71.0/109.7 ns/pkt
saved at 64/512/1460B. Note: `strict_mirror..._10789_f4` (HA lease
counters) fails identically (left 2, right 1) on the pre-wrapper
head `c25ace10b0` binary — pre-existing at this base, unrelated
to the pool change; listed for the main suite run.

## Follow-up: SNAT live-map sharding (this change)

`live_by_flow` moves out of `PortAllocatorLiveState` into
`flows::LiveFlowMap`: 16 shards by FxHash of the flow key, each a
`Mutex<FxHashMap>`. Lease/expiration/ownership-index state stays
in the retained lease mutex. Against the prior attempt's three
objections: (1) reserve/release pairing — every flow record and
its holder mask live in exactly one shard, and lease/index side
effects remain serialized by the retained mutex exactly as
before; (2) exact cap — an atomic count bumped only on actual
insert/remove under the shard write lock is the authoritative
`live_by_flow.len()` equivalent, checked under that lock; (3) GC
chunking never touched `live_by_flow` (lease maps only) and is
unchanged. Lock order on writer paths is `live` -> shard: every
path that needs both for mutation holds the lease write guard
first and the flow's one shard second (the fast-path admission
order is shard -> shared `live` read; see the review fold
below), and no shard guard is ever re-acquired while held
(helpers take the held guard via the `*_in_shard` forms;
`capture_and_replace` carries its shard in the returned guard).
An earlier draft that re-acquired the shard inside
`allocate_translation_locked` (after lease reuse) and inside the
capture/reserve paths self-deadlocked on the non-reentrant std
Mutex — caught by the 15948/pool suites hanging, fixed by
threading the held guard through. #4800 counters also count
counted shard acquisitions. New cells in
`tests_newflow_lock.rs`: a held shard does not block a
different-shard allocation, and the cross-shard cap is exact.
Fw0 perf validation remains the parent's pre-merge perf gate.

Validation (this follow-up): `cargo test --bins --no-run` clean;
`tests_newflow_lock` (6), `tests_det_lock_scope_9130` (12),
`tests_15948` (8), `tests_pool` + `tests_idle_lease_sync_8121`
(325 combined with the shared-notrans pool cells) all pass, and
the full `nat::` module run passes (726 passed, 1 ignored).

## Review fold (PR #16330, Opus)

Three findings folded:

1. **`retire_worker` leaked persistent leases.** Its last-holder
   arm unlinked the flow record but never completed the lease
   (the pre-shard master code called
   `complete_persistent_lease_locked`; the shard rewrite dropped
   it). The lease kept `active_flows == 1`, never entered the
   idle-expiry index, and no GC path could reclaim it or its
   port. Restored the completion call; pinned by
   `retire_worker_completes_persistent_lease_15956`.
2. **New-flow admission still took the global `live` mutex.**
   Narrowed claim, sharded admission: `live` is now an `RwLock`.
   The non-persistent fast path takes only the flow's shard
   (held across reuse/cap/insert via `try_insert_in_shard`), a
   SHARED read guard for the wire-identity check (try-read;
   contended => free the claimed bit and use the locked path),
   a try-read GC skip, and a try-only PAT-owner publish. The
   write guard is taken only by lease-coupled/pressure paths
   (`allocate_translation_locked` now shard-rechecks first) —
   writers remain bounded lease/index critical sections.
   Pinned by
   `new_flow_allocation_completes_under_held_live_read_15956`
   (completes under a held READ guard; pre-fold Mutex design
   serializes there) alongside the held-shard cell.
3. **Displaced-restore cap overshoot.** `restore_displaced`'s
   tail inserted the incumbent unconditionally; after a
   sole-holder rollback the slot is absent, so restoring at
   `max_tracked_flows` pushed the sharded count past the cap.
   It now refuses at cap for an absent slot (handing the
   reserved bitmap bit back) and still replaces a present
   slot in place. Pinned by
   `restore_displaced_refuses_at_cap_15956` (fills the cap with
   bit-less address-only records so the bitmap precheck passes
   and the cap is provably the refusing check).

Fold validation: `cargo test --bins --no-run` clean; the three
new cells pass; `tests_pool`/`tests_idle_lease_sync_8121`/
`tests_det_lock_scope` 337 passed; full `nat::` module 729
passed, 1 ignored (debug).

## Review fold 2 (PR #16330, Opus): exact-cap race

The fold-1 cap checks read `flows.len()` and inserted under a
DIFFERENT shard's lock: at cap-1, a displaced restore and a
fast-path insert on different shards could both pass and land
at cap+1. Fixed with a shared atomic admission counter in
`LiveFlowMap` (`admit_one`: `fetch_add`, roll back on exceed):
every NEW-slot insert now wins the counter first —
`try_insert_in_shard` (fast path), explicit `admit_one` on the
locked allocate / deterministic / reserve / interface /
address-only paths (held across the insert, `unadmit_one` on
abandoned admissions), and `restore_displaced` (absent slot
only; a present slot replaces without consuming). Record
removal releases both the tracked count and the admission
slot, so the counter settles back to `live_flow_count`.
Pinned by
`restore_and_fast_insert_race_at_cap_minus_one_admits_exactly_one_15956`:
cap-1, barrier-synchronized restore vs fast-insert racers on
asserted-distinct shards — exactly one admits, count lands
exactly on cap, counter equals count, loser admits after the
winner releases. Fold-2 validation: bins clean; full `nat::`
module 730 passed, 1 ignored (debug).

## Review fold 3 (PR #16330, Opus): synced-lease admit loser

The fold-2 fresh synced-persistent reserve minted its lease
(`active_flows = 1`, in no expiry index) and only then
discovered the admission loss at insert — a lease that could
never drain or be GC-reclaimed. Fold 3 admits BEFORE the
bitmap reserve and the mint (`admit_one` ahead of both;
bitmap refusal un-admits), so a loser never mints at all, and
the insert lands via the new `insert_admitted_in_shard`
(consumes the caller's claim; no second `admit_one` — the
first fold-3 draft double-admitted and panicked its own
unreachable, caught by the new cell). Pinned by
`synced_persistent_reserve_admit_loser_mints_no_lease_15956`:
at full cap the reserve refuses with NO lease for the source
(neither active nor idle), no bitmap bit, no admission leak;
after a slot frees the same reserve mints cleanly with
`active_flows == 1`. Fold-3 validation: bins clean; full
`nat::` module 731 passed, 1 ignored (debug).
