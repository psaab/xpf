# #14994: feeds — apply shrink and churn guards on cold-restart and recreated feeds without a prior snapshot (D39-01)

## Summary

`installSnapshot` gated both guard predicates on `fs.hasSnapshot`
(`shrinkTripped := fs.hasSnapshot && ...`, `churnTripped := fs.hasSnapshot && ...`)
and gated the refusal block the same way. A feed with no live snapshot but a
remembered shrink baseline — cold restart (`RestoreShrinkHighWater` →
`shrinkHistory` → `Apply`), same-manager delete/re-add (`shrinkHistory` via
`Apply`), or post-hold-drop (snapshot dropped, high-water/epoch remembered) —
therefore installed its first candidate through the deliberate bootstrap path
with only an audit warning, even when that candidate was a drastic shrink
(e.g. 50000→500) or an equal-count wholly-disjoint swap of the remembered
epoch. Worse, that bootstrap install ran the `wasBootstrap` epoch rebase and
`rememberShrinkEpochLocked`, overwriting `epochContentPrefixes` /
`shrinkHighWaterHash` in durable history with the unacknowledged rotated set
and destroying the restored churn anchor.

A second, coupled defect made the churn leg unreachable even in principle on
cold restart: `RestoreShrinkHighWater` accepted a persisted epoch prefix set
only when `hashPrefixes(canon) == record.Hash`. But `record.Hash` is the count
high-water hash (largest installed set), while the epoch set is the last
acknowledged set — after any ordinary equal-count rotation that passes the
floor, the high-water hash has advanced past the epoch set, so every such
record silently dropped its epoch set on restore (`epoch=0` verified by
instrumentation). The content epoch then re-bootstrapped unanchored.

## Fix (`pkg/feeds/feeds.go`)

- `installSnapshot`: a no-snapshot feed with `shrinkHighWaterCount > 0` is a
  remembered-baseline feed, not a true bootstrap. `baselineHash` anchors on
  `shrinkHighWaterHash`; `shrinkTripped` evaluates for live or remembered
  baselines (`baselineHash != res.hash` preserves the identical-content
  exemption); `churnTripped` evaluates whenever a live snapshot or a
  remembered epoch set exists, against that epoch set. The refusal block now
  runs on `shrinkTripped || churnTripped || refusedAfterDrop`, so a tripping
  no-snapshot candidate is refused with the same exact-candidate
  acknowledgement tuple (baseline = restored high-water hash, or epoch hash
  for churn), installs nothing, and publishes nothing — the binding stays
  omitted so referencing policy fails closed (#5645). Candidates at/above
  the floors still install on this path, with the existing bootstrap audit
  warning when they differ from the remembered high-water.
- Epoch non-rebase preserved (#14395, intentional; the epoch-non-rebase-on-
  growth sub-leg of D39-01 was refuted as intentional and is excluded): the
  `wasBootstrap` epoch rebase now requires a true bootstrap
  (`wasBootstrap && !hasRememberedBaseline`) or an acknowledged install.
  Ordinary growth against a remembered baseline still advances the count
  high-water count/hash for display, but no longer moves
  `epochContentPrefixes`/`epochContentHash` ahead of the acknowledged epoch.
  `rememberShrinkEpochLocked` with a nil epoch likewise never erases the
  remembered epoch (unchanged).
- `RestoreShrinkHighWater`: a canonical persisted epoch set is accepted with
  its own digest (`hashPrefixes(canon)`) as the epoch hash; it no longer has
  to equal the count high-water hash. Non-canonical sets are still dropped
  (count epoch still restores, content epoch re-bootstraps under the
  remembered-baseline guard).
- `#12882` pin unchanged in mechanism: the exact refused candidate re-served
  after a hold drop still matches `refusedAfterDrop` first and keeps its
  stored tuple. A *different* post-drop candidate is no longer automatically
  bootstrapped: it is compared with the remembered baseline — tripping
  candidates are refused as fresh candidates, at/above-floor candidates
  still bootstrap with audit and clear the refusal.

## Risk

Behavior change is scoped to feeds with no live snapshot but a remembered
shrink baseline whose first candidate trips the shrink/churn floors: such a
candidate now requires the exact acknowledgement before it can install
(previously it installed with an audit warning). True bootstraps (no
remembered baseline), small feeds below `minOldCount`, identical-content
refetches, and at/above-floor candidates are unchanged. A refused cold feed
installs nothing and its binding stays omitted, so referencing policy fails
closed until the operator acknowledges the exact candidate via
`request security dynamic-address acknowledge-shrink ...` (the refusal tuple
is visible in `show security dynamic-address`). Factory-reset/zeroize still
erases the history file, so a re-tenanted device does not inherit a baseline
(#12170 legs unchanged and green).
