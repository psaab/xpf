# #9697 — test: TestSessionSocketNamesTheResponseCap9322 fails with an i/o timeout under load

- **Timestamp**: 2026-09-10
  - **Action**: Took the issue's first fix direction, a test-only lower cap,
    and applied it to all three socket cells in the file.
    - Cause: the cells streamed a reply past the real 64 MiB cap. Reaching it
      means receiving and decoding 64 MiB of JSON. The round-trip deadline is
      3 s for the session socket (`sessionSyncRoundtripDeadline =
      controlBaseDeadline`), and 3 s for a small control request
      (`controlRoundtripDeadline`, a function of the request size). Under
      load that decode outran the deadline, so the cell reported the deadline
      instead of the cap.
    - A deadline seam would not reach the control-socket sibling:
      `controlBaseDeadline` is a const. The cap has one construction site,
      so it is the one seam that covers the session, control and boot-probe
      cells alike.
  - **Action**: `controlResponseCapBytes` (pkg/dataplane/userspace/socket_trust_9003.go)
    is the cap `boundedResponseReader` enforces and `responseCapError` names.
    - It always equals `MaxControlResponseBytes`. It is a package var only for
      these cells, the same seam shape as `sessionSyncRoundtripDeadline`, and
      nothing in production mutates it.
    - `smallResponseCap9697` shrinks it to 1 MiB for one cell and restores it
      on cleanup. The cells are not parallel, so they finish before any
      t.Parallel test resumes.
    - `oversizeReply9322` streams 256 KiB writes until just past the
      EFFECTIVE cap. The assertion checks that the error names the effective
      cap, and still requires "control-response cap".
  - **Action**: TestResponseCapSeamDefaultsToTheConst9697 pins the default.
    Outside a shrinking cell, the reader budget and the named cap are
    `MaxControlResponseBytes`. TestLimitedResponseReaderReportsOnlyRealTruncation9322
    still exercises exact-size bodies at the real 64 MiB cap.
