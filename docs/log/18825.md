# #18825 — flush cached TX-selection filter counters before reading

## Cause

`cached_tx_selection_records_all_fallthrough_count_terms` replays both cached count terms with `record_filter_counter` and immediately reads their shared counters. Since `780e97f955` (#14932/#14656), filter-hit counters use the production coalescer in test builds: switching from counter A to B flushes A, but leaves B pending until an explicit flush. The second term therefore reads as zero. This is the same stale-observation pattern as #18821.

## Change

Added `flush_recorded_filter_counters()` after replaying the cached counters and before the packet/byte assertions. No expected values, assertions, or product code changed.

## Validation

- **RED before fix:** named test failed at the second term's packet count (`left: 0`, `right: 1`).
- **GREEN with flush:** named test passed (1 passed, 10,279 filtered).
- **No-flush mutant:** removing the flush reproduced the same second-term failure (`left: 0`, `right: 1`). Restored the flush afterward.
- **Neighbor module:** `filter::tests` passed (235 passed, 10,045 filtered).
- Change scope: test-only (`userspace-dp/src/filter/tests.rs`); assertions are unchanged.

## Risk

No runtime behavior changes. The test now flushes the coalesced counter updates before asserting on their shared values, matching the flow-cache counter observation boundary.
