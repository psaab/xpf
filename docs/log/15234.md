# #15234: feeds — fix the cold-restart epoch cohort test (A50-02)

## Summary

`TestEpochContentSurvivesColdRestart14395` (`pkg/feeds/feed_shrink_14395_test.go`)
was the cold-restart cohort of the #15075 (A50-01) epoch-persistence fix, but
it could not turn red when that fix was broken, and it was red on master for an
unrelated fixture reason at the report base (`51d355c1d`, validated at
`27b8cba22d`):

- **Red gate.** Its cold-restart leg built the feed URL as
  `http://127.0.0.1:1/feed`. Since #14385, `Manager.Apply` refuses
  plaintext-http feed servers (no worker, no snapshot), so `Apply` never
  created the feed and the test died at `t.Fatal("Apply did not create cold
  feed")` with the `refusing plaintext-http feed server` warning in the run
  log. The `pkg/feeds` package suite was therefore red on master.
- **Vacuous even when green.** After `RestoreShrinkHighWater`, the test's
  first `installSnapshot` candidate was the restored epoch set itself
  (identical content), followed by a 51% rotation and only then the 2%
  candidate. The installed candidate, not the restored epoch, anchors the
  churn baseline (`churnBaseline` falls back to `fs.prefixes`), so the 2%
  refusal did not isolate the restored epoch: it fired against a set that
  had just been installed through the same cold feed. The cold-restart
  cell therefore did not prove, on its own, that the FIRST post-restart
  fetch is guarded by the restored epoch — a disjoint first fetch (the
  A50-01 attack shape) was never attempted by this cohort. (The
  mutation-sensitive disjoint-first coverage lived only in the #15075
  tests, not in this #14395 cohort; deleting the Apply epoch copy in
  `feeds.go` — `fs.epochContentPrefixes` / `fs.epochContentHash` seeded
  from `shrinkHistory` — is the acceptance mutant quoted below.)

A50-01 itself (#15075) is closed and landed (`8f2bc3a4d5`): `EpochHash` is
persisted separately from the count high-water `Hash`, restore validates the
epoch set against it, and the #14994 guard refuses a churned bootstrap. This
issue is test/gate integrity only — no product code changes.

## Fix (test only — `pkg/feeds/feed_shrink_14395_test.go`)

`TestEpochContentSurvivesColdRestart14395` is rewritten disjoint-first, per
the A50-02 fix direction (`https://` with the lab-TLS question resolved, and
a disjoint set as the first post-restart fetch):

- The cold-restart Apply config uses `https://127.0.0.1:1/feed` (the URL is
  never dialled: producers are cancelled before `Apply` returns and every
  candidate is installed via `installSnapshot`). `New(nil)` keeps system TLS
  roots only, so no `SetLabFeedTLSRoots` is needed for this
  unreachable-URL fixture — that hatch is for fixtures that actually dial an
  httptest TLS server through `Apply` (`trustLabFeedServer` /
  `newShrinkFeed11059`, used for the seed manager here). The comment in the
  test records this so the https choice is not mistaken for a dialled
  endpoint.
- **Surviving leg (mutation-sensitive):** the fresh cold manager's FIRST
  fetched candidate is a wholly disjoint equal-count set (0% of the restored
  epoch, `epochPrefixes14395(21, 0, 100)`). With the epoch restored it is
  refused (0 installed, `ShrinkRefused`), the durable snapshot still carries
  all 100 original epoch prefixes, and the candidate installs only on the
  exact `AcknowledgeFeedShrink` acknowledgement (which rebases the epoch).
- **Control leg:** a second cold manager restored from the same snapshot
  installs the identical epoch set, then the 51% rotation installs without
  rebasing, then the 2%-of-epoch candidate is refused with the installed
  hash unchanged at step 1. Legitimate cold behaviour through the same path
  is unchanged and stays green.
- The snapshot fixture assertions (100 epoch prefixes, all originals present)
  and the seed sequence (epoch install, non-rebasing 51% rotation) are kept
  verbatim.

`pkg/feeds/README.md` is unchanged: it already documents the #15075 epoch
persistence and the #14994 cold-bootstrap guard this test now actually
exercises; no product behaviour changed.

## Regression / RED-GREEN evidence

The acceptance mutant is deleting the Apply epoch copy in
`pkg/feeds/feeds.go` (`feeds.go:1069-1072` at this base):

```go
if len(history.epochPrefixes) > 0 {
    fs.epochContentPrefixes = append([]string(nil), history.epochPrefixes...)
    fs.epochContentHash = history.epochHash
}
```

- **GREEN (fix present):**
  `go test ./pkg/feeds/ -run 'TestEpochContentSurvivesColdRestart14395' -count=1`
  passes. The disjoint-first leg is refused as content churn
  (`guard_reason="epoch retained content overlap below floor"`,
  `previous_prefixes=0`), installs on exact ack, and the control leg refuses
  the 2% rotation.
- **RED (mutant):** the same command fails with
  `cold-restart bootstrap of disjoint set against restored epoch was not refused: prefixes=100 ... ShrinkRefused:false`
  — the disjoint set bootstraps unchecked and rebases the epoch, exactly the
  A50-01 consequence. Restoring `feeds.go` returns the test to green.
- **Pre-fix shape on current master:** the old test passed at this base
  (the https URL had already been substituted by the #14994/#15075 work, so
  only the vacuity remained); the disjoint-first rewrite is what makes the
  cohort able to go red. On the report base the same test was additionally
  red-gated by the plaintext-http URL; the https URL above closes that leg.

Named controls kept green: identical-to-restored and 51%-of-epoch cold
candidates install, acknowledged churn installs and rebases, and the
neighbouring cold/epoch suites (`11755`, `14994`, `15075`) plus the full
`pkg/feeds` suite pass.

## Risk

Test-only change. No product code, thresholds, acknowledgement tuple, hold
policy, true-bootstrap behaviour, or non-feed path is touched. The new leg
reuses the staged helpers (`coldManager14994` shape inlined for the second
manager, `mustParse14994`, `epochPrefixes14395`) and the same cancelled-producer
Apply pattern as #11755/#14994/#15075, so flake surface is unchanged (the
producer-exit wait is the existing 1s `fs.done` select).
