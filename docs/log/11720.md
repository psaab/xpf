# #11720 — NAT64 ICMP non-first fragment MTU preflight

- **Timestamp**: 2026-10-02
- **Action**: Include ICMPv6 in the non-first-fragment size preflight. An ICMPv6 tail has no ICMP header to inspect; the translated IPv4 size is its opaque fragment payload plus the 20-byte IPv4 header. This prevents the NAT64 size decision from misclassifying the tail into the generic IPv6 PTB path.
- **File(s)**: `userspace-dp/src/nat64.rs`, `userspace-dp/src/nat64_tests.rs`, `userspace-dp/src/afxdp/tx/dispatch/tests/nat64_fragment_11353.rs`
- **Validation**: The new preflight and dispatch regressions failed before the change (`None` instead of `Some(28)`; generic PTB decision signalled) and passed after it. An unsupported-protocol negative cell also reproduced and prevented a broad protocol allowance. The `nat64_fragment_11353` tests passed (4 tests); preflight output-length tests passed (3 tests).
- **Risk / remainder**: This is only a size-preflight correction; the ICMPv6 fragment is still dropped later by the translation path (`write_v6_to_v4_translate` rejects real first fragments, and `write_v6_to_v4_nonfirst_into` does not translate ICMPv6 tails). Do not close #11720 on this change. A sound end-to-end implementation needs bounded reassembly (or equivalent full-message checksum context): an ICMPv6 checksum covers the entire message and its pseudo-header includes the full upper-layer length, which a first fragment does not carry. Prove first+tail processing and valid IPv4 output/reassembly after that design is implemented.
