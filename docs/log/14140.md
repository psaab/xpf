# #14140 eager reinitiation after IPsec update — engineering history

Issue: psaab/xpf#14140 (eager reinitiation after IPsec update,
research-validated D5-07). Lane branch: `fix/14140-campaign`, base
`origin/master` c6f058672.

## Defect (present at base)

`Manager.ApplyGeneration` (pkg/ipsec/manager.go) terminates live SAs of
removed/changed connections, then `reinitiateChangedConnections`
initiated **every** child of a changed connection whose old SA
terminated — without inspecting responder-only or on-traffic intent.
The renderer (pkg/ipsec/policy.go, `start_action` arm) deliberately
emits no `start_action` for a `ResponderOnly` gateway
(`remote_addrs = %any`, no fixed peer to dial; #11688) and `trap`
rather than `start` for `establish-tunnels on-traffic`. The
post-change reinitiation therefore contradicted the rendered policy:

- a live responder-only VPN whose security-effective config changed
  (e.g. PSK rotation) was terminated and then eagerly dialed with
  `swanctl --initiate --child <name>` against `%any`;
- the initiate error propagated out of `Apply`
  (`errors.Join(terminateErr, initiateErr)`), turning an unrelated
  config change into a failed commit;
- on-traffic / `responder-only`-mode / unset-mode VPNs were likewise
  eagerly established even though their policy waits for the peer or
  for traffic.

Scope guard (the research refutation): this needs a changed connection
with a live SA whose teardown succeeded; it is not every config apply.

## Fix

- `pkg/ipsec/manager.go`: `reinitiateChangedConnections` now skips any
  changed+terminated VPN whose NEW rendered policy would not itself
  initiate. New helper `vpnEagerlyInitiates` mirrors exactly the
  renderer's `start_action = start` arm — `EstablishTunnels ==
  "immediately"` and a non-responder-only gateway — resolving the
  gateway through the same `resolveRemoteAddr` the renderer uses, so a
  legacy inline-endpoint VPN (no `Gateways` entry, usable literal /
  hostname) counts as initiable, a dynamic-hostname gateway counts, and
  a defined responder-only gateway does not. The NEW config's mode
  governs (an `immediately` → `on-traffic` transition is not eagerly
  reinitiated). Termination of the stale SA is unchanged for every
  mode — only the eager replacement dial is gated. Skipped modes
  re-establish as on a fresh load: the peer (responder-only) or the
  first matching packet (trap).
- Scope cuts, deliberate: the HA failover path
  (`reinitiateIPsecSAs` in pkg/daemon, operator-driven takeover
  re-initiation, #9139/#3764 precedent) is unchanged — it is not the
  Apply path the issue cites, and gating it would need an RG-ownership
  × initiation-intent product decision. `InitiateConnection` itself is
  unchanged (its other caller is that HA path).

## Consumers updated

The four pre-existing tests that asserted reinitiation built their VPN
through `vpnCfg` with `EstablishTunnels` unset — the exact non-eager
default this fix stops dialing. They are pinned to
`establish-tunnels immediately` (their subject is the eager path):

- `TestChangedVPNSecurityTerminatesAndReinitiatesLiveSA`,
  `TestTrafficSelectorOnlyChangeTerminatesAndReinitiatesLiveSA`,
  `TestChangedVPNTerminateDebtIsRetried`
  (pkg/ipsec/delete_terminate_3941_test.go);
- `TestRestartKeepsChangedConnectionDebt10878`
  (pkg/ipsec/conn_state_9687_test.go).

No production consumer relied on the non-eager dial: the only other
`InitiateConnection` caller is the daemon HA path above.

## Verification

- New `pkg/ipsec/reinitiate_intent_14140_test.go` (4 tests, fake
  `swanctl` recorder seam): changed+terminated responder-only VPN (all
  four modes) is terminated, not initiated, and `Apply` succeeds;
  fixed-address `on-traffic`/`responder-only`/unset likewise;
  `immediately` controls reinitiate (defined gateway, inline endpoint,
  dynamic-hostname gateway); `immediately` → `on-traffic` transition
  does not. RED on pristine master (the three non-eager tests fail
  with `got [site-a]` initiate calls; the `immediately` control passes
  both ways), GREEN with the fix.
- `go test ./pkg/ipsec/ -count=1`: green.
- `go vet ./pkg/ipsec/`: clean; `gofmt -l pkg/ipsec/`: clean.

## Residuals

- Live strongSwan behaviour of `swanctl --initiate` against a
  `%any` responder connection (hard error vs queued attempt) is not
  measured on a cluster; the fix removes the call for non-eager modes
  regardless of which it is, and the recorder seam settles the Apply
  contract without a live charon.
- A changed `immediately` VPN whose peer is a responder-only gateway
  by address shape (fixed `Address` set, `ResponderOnly` false) still
  reinitiates — that is the rendered `start` policy, unchanged.
