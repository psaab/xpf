# Issue #14424 — Address-book `address` identity not honoured

## Why

`security address-book global address` (and the zone-local twin) is a leaf
schema node (`args: 2, multi: true, children: nil`), so the group-merge
machinery could not see its name identity at `Keys[1]`:

- Leaf-vs-leaf accidentally kept the inline prefix via keyword override,
  but a different name (`address B` in a group beside inline `address A`)
  was keyword-suppressed and silently dropped.
- Every shape involving a braced container (`address A { 10.2.0.1/32; }`)
  adopted the group node beside the inline node. `parseAddressBookEntries`
  then folded both nodes into one `Address` map entry with
  `mergeAddressNode` last-wins, so the group prefix (adopted after the
  inline node) overwrote the inline prefix. A policy referencing `A`
  matched the group's network instead of the operator's inline one.

Measured on `origin/master` (`1c443e0d0`): C←L, L←C and C←C same-name pairs
all compiled `A` to the group prefix; the different-name L←L pair kept
only `A` and dropped `B`.

## What

- New `pkg/config/group_merge_address_book_14424.go`: registers the two
  address-book `address` schema nodes (global `security address-book
  global` and zone-local `security zones security-zone <z> address-book`)
  as identity sites. `mergeNodes` intercepts address-book `address`
  sources before the generic leaf/container handling:
  - same name: merge the group node into the existing destination node
    with inline precedence (leaf↔leaf scalar inline-wins with disjoint
    prefix/description union; container shapes promote / descend via
    recursive `mergeNodes`, dropping a group bare-prefix child that
    conflicts with an inline bare prefix);
  - different name (leaf): adopt as a new instance instead of the legacy
    keyword suppression. Container adoption already preserved new names.
- `pkg/config/ast_groups.go`: 25-line intercept in `mergeNodes` dispatching
  to the helpers above. No compiler change: `mergeAddressNode` last-wins
  is unchanged and now only ever sees one node per name from group merges.
- Regression `pkg/config/address_book_same_name_inline_14424_test.go`:
  all four shape pairs (L←L, C←L, L←C, C←C) assert `A` compiles to the
  inline prefix; different-name L←L asserts both `A` and `B`; zone-local
  same-name cell; prefix/description disjoint-attribute union controls.

Scope cuts: `address-set` is not changed (its members already union by
name in the compiler and it has a children-bearing schema, so #9859-style
handling differs); non-address-book `address` leaves (interface family
addresses, NAT pools) are excluded by the schema-node registry.

## Validation

- RED on base `1c443e0d0`: C←L, L←C, C←C fail with
  `address A = "10.2.0.1/32", want inline "10.1.0.1/32"`; different-name
  fails with only `A` present; zone-local fails identically. L←L and the
  description-union controls pass on base (behaviour preserved).
- GREEN after the fix: the regression above plus targeted neighbours
  (`TestRepeatedAddressBook*`, `TestGroupNamedLeaf*`, `TestGroupPacked*`,
  `TestGroupBracketed*`) pass.
- Full `pkg/config` suite run after the fix (see PR).

## Risk

- Behaviour delta: group `address` values no longer overwrite a same-name
  inline address, and a group-only name now survives beside a different
  inline name — both are the documented apply-groups precedence. Disjoint
  attributes (group description + inline prefix and vice versa) still
  union, matching the pre-fix braced behaviour.
- Residual: group-vs-group same-name resolution across mixed shapes keeps
  the existing positional adoption order (same limitation as the #9854
  syslog coalescing note); no test enshrines it.
