## Round-4 evidence (the discriminator)

Live acceptance of #15745 (v56) still fails: split placement
RG2@node1 / RG1@node0, transit 0/5. On the split node fw1 the defaults
render `0.0.0.0/0 route discard pref 200` and `::/0 route discard
pref 200` — with #15745's reject wire bit live, these rows are proven
**discard (Null0 / RTN_BLACKHOLE), not reject**. fw1 correctly has no
WAN connected prefixes (#15745 works); the remaining path is:
off-link destination → LPM reaches the default → pref-5 forwarding
row's gateway is not neighbor-live on the non-owner → #15098
terminal-row rule selects the pref-200 discard → `DiscardRoute` →
`enforce_ha_resolution` passes it untouched (only
Forward/Missing/Local are gated) → fabric helpers require exactly
`HAInactive` → packet drops on the split node. No session, no fabric
counter. That is the blackhole.

## Decision

Implement §6 direction (1) with provenance discrimination, per the
assignment: cluster-sourced terminal rows demote to fabric redirect
when the would-be egress RG is peer-owned; operator discard/reject
semantics are unchanged.

Provenance: the FRR tag 2500 does not survive into the kernel route
(netlink `Route` carries no tag), so the import-time discriminator is
the exact shape `renderClusterModeDefaults` installs: **default
prefix + RTPROT_STATIC + kernel priority 20** (FRR AD 250). That
triple marks `LearnedRoute.ClusterTerminal`; near-misses (non-default
prefix, BGP proto, metric 99) stay unmarked and remain ordinary
terminal drops. Residual risk, stated plainly: a foreign daemon's
static default blackhole at metric 20 would be mis-marked; that is
the same trust the importer already extends to RTN_BLACKHOLE, bounded
to configured tables and admitted protocols, and it can only cause a
fabric redirect (policy still adjudicated on the peer), never a
local forward.

## Mechanics

- Go: `LearnedRoute.ClusterTerminal` set in `importableRouteScoped`
  for both RTN_BLACKHOLE and RTN_UNREACHABLE negative rows;
  `clusterNull0KernelPriority = 20`. `RouteSnapshot.ClusterTerminal`
  (`cluster_terminal`, omitempty), dedupe key extended,
  `addLearnedRouteSnapshots` maps it through.
- Protocol v56 → v57 (Go `ProtocolVersion`, Rust
  `CONFIG_SNAPSHOT_PROTOCOL_VERSION`): an old helper drops the
  cluster default terminally — the defect — so exact-version fencing
  is required, as with v56.
- Rust: `RouteSnapshot.cluster_terminal` → `RouteEntryV4/V6.
  cluster_terminal` in `populate_routes`. In `select_v*_route` the
  terminal branch yields the new disposition
  `ForwardingDisposition::ClusterTerminalHAInactive` for marked rows
  (unmarked rows still yield `DiscardRoute`/`RejectRoute`).
- `enforce_ha_resolution_snapshot`: for `ClusterTerminalHAInactive`,
  standalone (empty HA map) keeps the terminal; otherwise
  `cluster_terminal_peer_owned_egress_rg` scans the default
  forwarding sibling in the same default table — peer-owned (RG > 0
  and unknown-or-inactive, mirroring the ForwardCandidate gate)
  keeps the demotion; locally-owned/no-sibling restores the plain
  `DiscardRoute` drop. This is the only place the demotion is
  decided: lookup has no HA map, and sessions/flowless both funnel
  through HA enforcement before the fabric helpers.
- Fabric helpers: `redirect_via_fabric_if_needed` and
  `redirect_session_via_fabric_if_needed` accept
  `HAInactive | ClusterTerminalHAInactive`; fabric-ingress
  suppression unchanged. Non-demoted `ClusterTerminalHAInactive`
  (no fabric route) falls into the existing HA-inactive drop
  handling (status/session-delta/event-wire map it to `ha_inactive`).
- Cached flows are fenced by FIB generation + `cached_flow_decision_
  valid` re-enforcement, so a pre-demotion DiscardRoute cache entry
  cannot outlive the RG ownership that demotes it.
