# #19165: with-cluster.sh refuses a lock tuple and a cluster env that disagree

- **Timestamp**: 2026-11-16
- **Action**: The defect, which I hit myself:
  - `with-cluster.sh` takes the LOCK from `XPF_CLUSTER_LOCK/OWNER/EPOCH`,
    but the FIREWALLS its VM-target guard touches (shims, mark script,
    `systemctl daemon-reload`/`enable`) from `cluster-env.sh`, which defaults
    to loss.
  - My udp cell (creating udp:xpf-testrunner4) set only the udp tuple, so at
    15:43:51Z it guarded loss:xpf-userspace-fw0/fw1 without the loss lock,
    during G6's loss ctl cell. G6 found no disturbance in that sample.
- **Action**: `test/incus/with-cluster.sh`, before taking the lock:
  - map the lock's basename to its cluster: `xpf-cluster.lock` is loss,
    `-tcp` is tcp, `-udp` is udp, and a private path names none;
  - source `cluster-env.sh` early;
  - refuse (exit 2) when `INCUS_REMOTE` names a different cluster, naming
    both and the env to export. The legacy local cluster (no `INCUS_REMOTE`)
    is not compared.
  - `docs/engineering-style.md` now says to export `BPFRX_CLUSTER_ENV` with a
    tcp/udp tuple, and why.
- **Action**: `test/incus/with-cluster-selftest.sh`, cell (k):
  - a udp-named lock with the loss env is refused (2), the command does not
    run, and no owner file is written;
  - the same lock with the udp env runs.
- **Validation** (udp:xpf-testrunner4 via `scripts/vm-test-run.sh`):
  - the cluster-cell selftest (73 cases) and the build-identity selftest (11)
    pass;
  - mutant, the refusal condition replaced with `false`: cell (k) FAILS
    (KILLED: "expected refusal (2) with the command not run, got rc=0
    ran=yes");
  - `shellcheck -S warning` clean.
  - **File(s)**: `test/incus/with-cluster.sh`,
    `test/incus/with-cluster-selftest.sh`, `docs/engineering-style.md`,
    `docs/log/19165.md`
