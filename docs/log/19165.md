# #19165: with-cluster's own actions target the held lock's cluster

- **Incident** (2026-11-16): a udp lock tuple without `BPFRX_CLUSTER_ENV`.
  `cluster-env.sh` defaults to loss, so `with-cluster.sh`'s own VM-target
  guard (shims, mark-vm, `systemctl daemon-reload`) ran on the LOSS
  firewalls without the loss lock, during another agent's loss measurement.
- **History**: four rounds tried to police the targets a cell's COMMAND uses:
  the env label, then the resolved FW0/FW1, then the inherited ones, then a
  "total" target set with a digest. Each round of codex-c's bounded checks
  found another way in. In round five, F1 showed the premise cannot hold:
  commands read their own variables (`HOST`, `CLUSTER_WAN_VLAN*_HOST`,
  `FBF_*_HOST`, `XPF_FW*_VM`, …), and no wrapper can enumerate them. So the
  guard is narrowed to what caused the incident, the WRAPPER's own actions
  (team-lead, 2026-11-17). This commit replaces the earlier branch
  (`fix/19165-with-cluster-env`) and is cut from master.
- **Action** (`test/incus/with-cluster.sh`):
  - A fixed map takes the lock tuple to its cluster's env file (loss, tcp,
    udp).
  - `BPFRX_CLUSTER_ENV` unset: the wrapper exports the lock's env file, so
    commands that source `cluster-env.sh` resolve that cluster too.
  - Set to another file: refused, exit 2, before the lock. A relative path
    is resolved against the repo first.
  - Empty, the legacy local cluster: allowed only with the default (loss)
    tuple. Its own targets are then the bare local names.
  - The wrapper's own targets resolve from that env file alone, in
    `env -i`, ignoring every inherited override, before the lock is taken.
    The resolved targets must lie on the lock's cluster.
  - The VM-target guard and the build-identity probe
    (`cluster-build-identity.sh`, via `XPF_CLUSTER_WRAPPER_TARGETS`) use
    those targets.
  - The command still gets `cluster-env.sh`'s exports as before, as a
    convenience. The wrapper does NOT police variables a command reads on
    its own; that is documented in `docs/engineering-style.md`.
- **Cells** (`test/incus/with-cluster-selftest.sh`; the stub `incus` logs
  every call, so the cells read which instances the wrapper touched):
  - (k) the incident shape: udp tuple, no env. The guard and probe touch
    only `udp:xpf-udp-fw0/1`, and the command gets the udp env file.
  - (l) a udp tuple with the loss env: refused; nothing run, touched or
    locked.
  - (m) inherited `INCUS_REMOTE=loss`, `FW0=loss:…`, bare `FW1` and a
    loss `CLUSTER_LAN_HOST`: the command runs, and the wrapper still
    touches only udp.
  - (n) the legacy empty env with the loss tuple runs on `xpf-fw0/1`; with
    the udp tuple it is refused.
  - (o) the lock's env file named relatively: accepted.
- **Validation** (udp:xpf-testrunner4 via `scripts/vm-test-run.sh`):
  - with-cluster selftest 11/11; cluster-build-identity selftest 11/11;
    shellcheck clean.
  - Mutants KILLED: no lock→env map (k), no mismatch refusal (l), an
    unclean resolution (m), legacy accepted with any tuple (n), the probe
    reading inherited targets (m).
