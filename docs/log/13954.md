# #13954 — SYN-flood destination/source sketches migrated off RateCounter

Why: `destination-threshold`/`source-threshold` sketches used count-all
`RateCounter` cells. A key sustained at the configured SYN/s rate collapsed
to ~half (33% loss at 0.6T, 100% at T) with no recovery without an idle
second, yet a trip is a hard `DropDst`/`DropSrc` — not the "recoverable
security response" the module doc claimed. Residual of #3607 §5b; #5805
fixed the identical defect for ICMP/UDP flood sketches.

What: `SynRateSketch::for_dst`/`for_src` now construct
`SynRateSketch<TokenBucket>` (monotonic-ns cells, all-row prepare/commit
transaction, fail-closed: any drained row blocks, collisions only
over-count, sustained admission bounded to threshold + burst capacity).
`ZoneScreenState.syn_dst_sketch`/`syn_src_sketch` retyped and
`syn_flood_gate` charges them with `now_ns` instead of `now_secs`.
Aggregate/alarm `RateCounter` unchanged. Docs updated
(`syn_rate.rs`, `rate.rs`, `docs/feature-coverage.md`,
`docs/syn-cookie-flood-protection.md`).

Fail-closed re-derivation: no eviction added; AND/transaction requires
every row to admit; over-threshold streams limited to ~T/s; cold-start
burst bounded to T (#2937); validated/cookie-active gating unchanged.

Collision tradeoff (explicit, advisory-resolved): TokenBucket sketches
admit via the all-row prepare/commit transaction, so ONE drained row
blocks a key — stricter than the count-all CMS min-read. This is the
deliberate #10319 bound (phase-staggered rows cannot multiply the
sustained rate); the `(load)^ROWS` false-positive bound applies only
to the retained count-all test seam, production collision false-positive
is ~ROWS*load, still fail-closed (collisions never admit). Pinned by
`syn_sketch_one_drained_row_blocks_admission_13954` on for_dst/for_src;
module and syn-cookie docs state both reductions explicitly.
