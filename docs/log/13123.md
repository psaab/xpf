# Issue #13123 — resolve IPsec external interfaces to kernel device names

- **Issue:** D10-06: `resolveInterfaceAddressFamily` passed Junos interface refs through `config.LinuxIfName`, which only translates `/` to `-`. Unit-0 and VLAN suffixes therefore reached `net.InterfaceByName` unchanged, missing DHCP/SLAAC addresses and causing fail-closed VPN unloads. Configured IPv6 link-local addresses on VLAN/IRB units were also qualified with the unit-less base rather than the unit's kernel device.
- **Base:** `55ab81ef0` (`origin/master` at branch creation).
- **Branch:** `fix/13123-campaign-pub`.
- **Worktree:** `/var/worktrees/campaign-pub/wt-13123`.
- **Source finding:** D10-06 in `gemini-4-argon-high-review-zone-enforcement-001.md`; independently validated by the issue's three-way research gate.

## Change

`resolveInterfaceAddressFamily` now tries `cfg.ResolveKernelIfName` for authored and RETH-resolved refs before the legacy Linux-name fallbacks. This uses the shared config resolver's unit-0, VLAN-ID, IRB, RETH, and tunnel rules. `resolveConfiguredInterfaceAddress` now qualifies link-local addresses with the selected unit's resolved kernel name; for a bare ref selecting a configured unit it resolves that actual unit. It retains a non-empty prior zone if RETH resolution is degenerate.

Added regressions for live `.0` kernel lookup through `PrepareConfig` and fail-closed render behavior, kernel-name derivations for unit-0/VLAN/RETH/IRB/tunnel refs, and unit-specific link-local zones with a unit-0 control.
