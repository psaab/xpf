# #18893 — exercise the strict VRRP identity gate

- **Timestamp**: 2026-11-02 (`wt-17474`, base `fed39c4bc1`)

## Why

The daemon apply-tail test hand-built a `config.Config` containing duplicate
VRRP identities, bypassing the strict commit compiler introduced by #15856. The
runtime apply tail correctly received no compile-validated config and therefore
could not be expected to return the old collision error.

## What

- Re-premise the daemon cell through `ConfigTree` parsing and `CompileConfig`.
  Two IPv4 addresses on one unit carry the same VRID, yielding a duplicate
  `(kernel interface, VRID, family)` identity without an unrelated duplicate
  device-name gate masking the intended validation.
- Assert the commit-time error names `ge-0-0-0`, VRID 5, and `inet`.
- No production behavior changed; the assertion remains specific to the
  #15688/#15856 strict gate.

## Validation

- The old apply-tail expectation was red after #15856 moved rejection to strict
  compilation.
- `TestDuplicateVRRPIdentityRejectedAtStrictCompile5083` passed in the named
  daemon regression run.
- `TestVRRPInstanceIdentity*` passed in the focused `pkg/config` run, including
  duplicate IPv4/IPv6 rejection, dual-stack and distinct-VRID controls, RETH
  identity collisions, and tolerant-load warning behavior.

## Risk

Only the stale test premise changed. Duplicate instance identity remains a
commit-time rejection, and the cell now fails if that validation is removed or
stops naming the colliding identity.
