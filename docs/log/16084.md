# #16084 — SNMPv3 accepts weak passphrases with no length floor

- **Timestamp**: 2026-10-20
- **Action**: strict-compile passphrase length floor (8 runes) for SNMPv3
  auth/privacy passwords, tolerant path downgrades to a warning.
- **File(s)**: `pkg/config/compiler_validate_strict_snmpv3_keys_7530.go`,
  `pkg/config/snmpv3_passphrase_floor_16084_test.go`, plus fixture
  passphrases lengthened in existing SNMP test files (values only; no
  assertions changed in meaning).

## Defect

The #7530 gate was presence-only: a user naming `authentication-sha256`
with a 1-character `authentication-password` compiled clean. The SNMP
agent then answers authentication challenges online (`pkg/snmp/v3.go`
`passwordToKey`, ~1 MiB of hashing per guess — a real but parallelisable
cost) with a 100/s/source + 2000/s global token budget and no per-user
lockout or backoff, so a 1-character credential is recovered after a
handful of guesses. The durable defect identified by the deep-review
cohort (A9-09) is the missing password-length floor; per-user source
scoping/throttling rides the unresolved A9-NV1 host-inbound question
and Junos parity (USM users likewise have no per-user `clients`), so it
is not added here.

## Fix

`validateSNMPv3UserKeyMaterialStrict` now rejects any non-empty
`AuthPassword`/`PrivPassword` shorter than 8 runes
(`snmpv3MinPassphraseRunes`), after the existing presence arms. The
floor follows RFC 3414 §11.2, which recommends pass phrases of at
least 8 characters (Junos enforces the same minimum). Length is
counted in runes, not bytes. The error names the user, the field, and
the observed length — never the passphrase itself. Because the gate
already runs strict-reject / lenient-warn via
`lenientSNMPv3KeyMaterial`, an already-persisted short-passphrase
config still boots on the tolerant path with a warning (#1960).

Scope cuts: no per-user throttle or lockout (rides A9-NV1; severity
re-check owed if NV-1 shows UDP/161 reachable from untrusted zones);
no `Clients` field on `SNMPv3User` (Junos parity — source scoping is
host-inbound/firewall-filter); no runtime floor in `pkg/snmp` (a
config that reaches the agent via the tolerant path is intentionally
still served, exactly as the sibling #7530 partial-credential case).

## Validation

New cells in `snmpv3_passphrase_floor_16084_test.go`: 1-char auth and
privacy rejections (decisive check from the issue), 7/8 boundary,
rune-vs-byte counting, orphan passphrase, tolerant-path warning.
Existing positive-control fixtures across the SNMP test files used
sub-floor placeholder passwords (`s3cret`, `APASS`, `p4ss`, `pw1`, …);
they were lengthened to ≥8 characters without changing what those
tests assert.
