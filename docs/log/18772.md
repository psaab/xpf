# #18772 / #18764: deb deploy plan, and an opt-in lab downgrade path

Per-issue log (see `docs/log/README.md`).

- **Timestamp**: 2026-11-01
  - **Action**: The deb deploy decides every target node's action up front:
    upgrade or fresh, a byte-identical same version (skip), a same version
    with other bytes (refuse), or a downgrade (refuse unless opted in). It
    decides before any push and before the attestation manifest is
    invalidated.
  - **Why**: the monotonic deb counter plus a 1-2 h cargo queue kept
    stranding gate debs as downgrades. A/B cells need an older build that
    can be deployed on purpose. Two shapes failed mid-cell and VOIDed the
    next gate by invalidating the manifest:
    - a downgrade (apt, then the anti-rollback floor);
    - the same version again (#16219).
  - **What refuses a downgrade**:
    1. apt, without `--allow-downgrades`;
    2. the binary anti-rollback floor `/var/lib/xpf/binary-floor` (#10848),
       which refuses both the postinst `publish-generation` and the rolling
       cut's INIT, naming both versions. Its documented escapes are the
       named rollback and `dpkg --purge` (postrm removes the floor).
    - The same-version refusal is the INIT/copy "cannot replace the
      live/rollback version dir" check: a re-staged same version gets a new
      source generation.
  - **Design**: the opt-in lives in the harness, and the product is
    unchanged.
    - With `XPF_DEPLOY_ALLOW_DOWNGRADE=1` (exactly `1`), a downgrading node
      gets a loud `LAB DOWNGRADE` log, has `/var/lib/xpf/binary-floor`
      removed (the purge path's reset), and is installed with
      `--allow-downgrades`. The cut re-enrolls the floor at the deployed
      version.
    - Why not an xpfd flag: a product bypass of the anti-replay floor would
      be a new production surface for a lab need. The floor's own reset is
      already documented, and the harness opt-in is an explicit env var
      that production deploys never set. The cut's config-envelope check
      is not bypassed.
    - Same version: when both the running xpfd and the running userspace
      helper are byte-identical to the deb's, the node is skipped (no apt,
      no cut). The manifest is still written from the deb, so the
      attestation is kept.
  - **Change**:
    - `deploy-lib.sh`: `deploy_running_deb_version`, `deploy_deb_plan`,
      `deploy_allow_downgrade`, `deploy_node_runs_deb`,
      `deploy_deb_node_action`, `deploy_deb_preflight`,
      `deploy_reset_binary_floor`, and `deploy_install_deb`'s
      `allow-downgrade` argument.
    - `cluster-setup.sh`: `cmd_deploy` preflights before
      `deploy_manifest_invalidate`. `deploy_vm_deb` acts on the per-node
      action.
  - **Attestation**: the manifest records `deb_version`, taken from the
    deployed deb. Its `version` and `build_git_sha` describe the deploying
    checkout, not the deb, so in a cross-checkout or downgrade cell only
    `deb_version` names the running build. The binary hashes were already
    the deb's.
