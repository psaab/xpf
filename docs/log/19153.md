## Design (lead: direction 1 plus a re-read; then the core split)

- `promote::same_synced_incarnation(nat, session_id, entry)`: THE identity
  rule, the single place it lives. NAT decision equality is mandatory; the
  session id is compared only when `entry.session_id != 0`. #18552's
  `synced_row_incarnation` now calls it (its `Superseded` arm), and the
  materialize core calls it. The two compare different pairs (worker row vs
  shared; captured shared vs current shared); only the predicate is common.
- `resolve::materialize_current_shared_under_permit(sessions, shared_sessions,
  forwarding, key, expected, install_inputs, permits) -> MaterializeOutcome`:
  the core, for a caller that ALREADY holds the install permits (witness:
  debug-asserts one covers `key`, as
  `update_session_cluster_synced_origin_under_permit`; refuses unless one
  covers the current row's companion). It re-reads `shared[key]` under the
  permits and installs the CURRENT shared content. Outcomes: `Installed`,
  `SharedLocal` (both install), `SharedAbsent`, `Superseded` (only with an
  `expected` capture), `StaleReplayFenced`, `InstallRefused` (change nothing).
  #18552's next cycle is to build its re-materialize-then-promote on it.
- `materialize_shared_session_hit_adopted` (both wrappers reach it):
  1. the #10612 stale-replay fence on the capture, before any claim (a stale
     row costs no claim per packet);
  2. `install_claim_would_refuse` pre-check, then `try_acquire_installs([key,
     reverse_session_key(key, nat)])` on the capture's key and NAT;
  3. the core, with the capture's `(nat, session_id)` as the expected
     incarnation;
  4. drop the permits; map `Installed`/`SharedLocal` -> installed,
     `StaleReplayFenced` -> the #10612 miss shape (`install_failed = false`,
     unchanged), the rest -> `install_failed = true`.

### Why a re-read, not only the permit

The capture is taken at resolve time. The coordinator can remove the shared
rows, probe and drop its lease between that capture and the permit (a
completed batch, peer delete or import). A permit-only fix would then be
granted and install the revoked incarnation. Cell (b) is exactly that gap.

### Zero id (Codex: the sentinel is an identity HOLE for promotion)

Here a shared id of 0 matches on the NAT decision alone, but a match is never
treated as "the capture is the row's state": the core installs what shared
holds NOW. The capture only decides whether this packet resolved against the
current incarnation (same translation, so forwarding this packet on its
resolved decision is equivalent). A legacy peer's same-NAT tuple reuse
therefore installs the current row, not the stale capture. Cell
`a_zero_id_match_installs_the_current_shared_content_19153` pins it (it fails
on the base, which installs the capture).

### Side effects and lock order

- Everything before the persistent-hold acquire is read-only (the stale fence,
  the claim, the re-read, the companion witness, the leak-incarnation
  computation). The acquire is the first side effect, so every non-install
  outcome changes nothing; a refused upsert releases the acquired hold
  (unchanged code). Pinned by
  `refused_materialize_acquires_no_persistent_hold_19153`.
- The permits are held across the core (re-read, install, and this worker's
  own hold release / leak stamp) and dropped before returning, so a promotion
  of the just-materialized row takes its own permit.
- Lock order: the permits, then the shared lock (released before the install).
  Promotion and HA import take a lease, then the shared lock. The permit is
  never waited for, so no cycle.
- Hot path: once per materialize (per flow per worker). A refusal retries per
  packet only while a holder lasts, and the non-allocating pre-check makes
  that lock operations only. No logging added.

### The rule (lead-approved), and what this packet may still do

A promotion may publish only content equal to what the worker row holds after
the materialize. `apply_deferred_shared_materialization` (now in
`session_glue/materialize.rs`) compares the INSTALLED decision and metadata
(the core's returned lookup) with the capture's, on exactly what a promotion
writes (`materialize_divergence`, every `SessionMetadata` field named, no
`..`, so a new field fails to compile until classified):

- equal (`MaterializeDivergence::None`): every capture-derived effect
  describes the installed row and stands;
- `ForwardOnce`: only metadata that cannot change this packet's translation,
  egress or admission differs: `log_session_init`, `log_session_close`
  (session logging), `inactivity_timeout_ns` (idle timeout),
  `policy_counter_idx`, `policy_counter` (hit-counter attribution). The packet
  forwards once on the capture's decision;
- `Drop`: anything in the `SessionDecision` (resolution: disposition, egress,
  next hop; the NAT decision; the install table domain and check), or any
  other metadata field (`ingress_zone`, `egress_zone`, `ingress_zone_check`,
  `egress_zone_check`, `ingress_ifindex`, `ingress_vlan_id`,
  `forward_ingress_vlan_id`, `nat_scope_ifindex`, `nat64_reverse`,
  `owner_rg_id`, `fabric_ingress`, `is_reverse`, `forward_wire_alias_origin`,
  `policy_id`); and also the core's `SharedAbsent` and `Superseded` (the
  captured incarnation is gone, or replaced by another NAT or session id: on
  an `Installed` outcome the NAT is always equal, because the identity check
  rejects a NAT change as `Superseded`).

On `ForwardOnce` and `Drop` the seed is suppressed and the next packet
resolves current state (the installed row as a worker hit, which promotes):
two packets.

### (c) The decision: drop, through the existing post-verdict recycle

The lead ruled: never forward on the capture's decision when the difference
can change the translation or the egress; recycle or drop through a clean
EXISTING path. There is one. In the session-hit branch of
`poll_descriptor/mod.rs`, after the Owner verdict, a denied Owner packet is
dropped by `binding.scratch.scratch_recycle.push(desc.addr); continue;`
(the input-filter non-Accept arm; the pre-verdict transit guards use the same
two statements). The `Drop` arm sits right after
`maybe_promote_synced_session_with_conntrack` returns, with the same two
statements and an internal counter (`MATERIALIZE_DIVERGENCE_DROPS`, no log).
Re-resolving the packet against the installed row would need the poll body to
re-enter the resolve, which has no existing path, so it is not done: the next
packet does it.

`Drop` also covers `SharedAbsent` (the captured incarnation was removed
between the capture and the claim) and `Superseded` (r24's optional
hardening): neither is forwarded on a decision shared no longer names. The
permit refusal (a held pair) and `InstallRefused` keep the pre-fold behaviour:
the packet forwards on the capture with `install_failed`, because shared still
names the captured incarnation (or the worker's own local row stands).

### Every capture-derived deferred effect, on `ForwardOnce` or `Drop`

- `deferred_synced_promotion`: dropped. It carries the capture's decision and
  metadata, which the flip would write over the installed row and publish.
- `deferred_forwarding_revalidation`: dropped. Its resolution, owner RG and
  egress zone were derived from the capture, and
  `apply_deferred_forwarding_revalidation` writes them into the row under
  `resolved.key`, now the installed row.
- `deferred_shared_materialization`: consumed by the materialize.
- `deferred_synced_purge`: never armed together with a materialization (the
  resolve arms one or the other on `keep_transient`).
- The #13938 owner-hit replay (`authority_deferred`): false for a shared hit
  (`ResolvedSessionLookup::shared`), so nothing is replayed.

### D2: the #10582 refusal is judged before the claim

`materialize_capture` checks `SessionTable::holds_local_row` (new; also now
the guard `upsert_synced_with_origin` itself calls, so the two cannot drift)
before claiming, unless the hit is fabric-adopted. Only this worker mutates
its table, so the answer cannot change before the install. A persistent
local-incumbent refusal now costs one table probe, no claim, no shared re-read
(the cell asserts zero allocations). The cost sentences in the core's doc and
in `docs/session-sync-architecture.md` now say exactly what holds: one attempt
per flow per worker unless refused; a held pair costs the non-allocating claim
pre-check; the local incumbent costs one probe; only a refusal inside the core
(an unjoinable hold, a directory conflict, an uncovered companion) pays the
claim, the re-read and the release per attempt.
