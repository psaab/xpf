# Issue #14587: BGP BFD timers ignored for multihop peers

## Why

Junos `bfd-liveness-detection { minimum-interval; multiplier; }` on a BGP
neighbour must set that neighbour's BFD timers single-hop or multihop.
The renderer emitted `neighbor X bfd` plus a single-hop `peer X` stanza
carrying the configured timers. For a multihop neighbour (iBGP over
loopbacks — the most common BGP+BFD design — or ebgp-multihop), bgpd
creates its own dynamic multihop bfdd session (`peer X multihop
local-address L`, local = update-source) at FRR defaults (300ms x3), so
the configured timers never applied and the static peer was orphan noise
in `show bfd peers`.

## What

- `pkg/frr/protocols_render.go`: `bgpNeighborBFDMultihop14587` mirrors
  FRR `PEER_IS_MULTIHOP` (iBGP, or eBGP with `MultihopTTL > 0`, using the
  effective local AS incl. per-neighbor `local-as`). Multihop BFD
  neighbours render `neighbor X bfd profile xpf-<interval>-<mult>` (profile
  registered with the BFD section, so bgpd applies the timers to its
  dynamic session); single-hop neighbours keep plain `neighbor X bfd`
  byte-identical. The BFD accumulator passes multihop/local-address
  through to the peer.
- `pkg/frr/bfd.go`: `bfdPeer` gains `multihop`/`localAddress`; `render()`
  emits `peer X [vrf V] multihop [local-address L]` (local-address through
  the #9493 single-token belt). Single-hop rendering is unchanged.
- `pkg/frr/bgp_bfd_multihop_14587_test.go`: regression covering multihop
  iBGP (900/7), eBGP-multihop, iBGP without update-source, default timers,
  and a single-hop control.

## Validation

- RED on origin/master: `go test ./pkg/frr -run
  '^TestBGPBFDMultihopProfile14587$'` failed (plain `neighbor bfd`,
  orphan `peer 10.255.0.2`).
- GREEN after fix: same command passes; BFD-related tests pass;
  `go vet ./pkg/frr` clean; gofmt clean.
- Full `go test ./pkg/frr`: 5 failures, identical on pristine
  origin/master base (pre-existing, unrelated).

## Risk

Directly-connected iBGP peers are keyed multihop-conservative (render
time cannot know FRR's shared_network); bfdd matching on
(peer, local-address, multihop, vrf) means the static peer is the session
bgpd uses rather than an orphan in both the loopback and direct cases.
No single-hop rendering changes.
