# Issue #14118 — GRO TCP segmenter uses endpoint outer family, not selected WG peer

## Why

`segment_forwarded_tcp_frames_from_frame_with_commit`
(`userspace-dp/src/afxdp/frame/tcp_segmentation.rs`) sized WireGuard
segments with `wg_inner_mtu(endpoint.outer_family,
tunnel_outer_mtu(...))`. For WG the endpoint row's destination is zeroed
(the peer carries the outer hop), so `tunnel_outer_mtu` falls back to the
tunnel LOGICAL ifindex MTU and the row family may differ from the peer
the encap path actually selects (`wg_encap_frame` → `peer_for_dest`
AllowedIPs LPM → `peer_endpoint.is_ipv6()` + physical route to that
peer). Segments could therefore be sized against the wrong family /
wrong underlay and dropped at the encap MTU guard. The dispatcher gate
fences the immediate path, but the deferred neighbor-dispatch caller and
any direct caller reach the segmenter unfenced, and the PTB helper
(`icmp_ptb::tunnel_inner_mtu`) had the same row-family error while
correctly using the per-peer physical MTU.

## What

- `frame/wg.rs`: new `wg_selected_peer_outer(decision, forwarding,
  endpoint, inner_dst) -> (outer_family, outer_mtu)` — resolves the
  selected peer once via `wg_peer_outer_dst`, derives family from the
  canonicalized peer endpoint address and MTU from
  `outer_physical_egress_mtu` (per-peer route MTU included); falls back
  to row family + logical MTU when no peer endpoint resolves (encap
  drops that packet anyway). Re-exported via `frame/mod.rs`.
- `frame/tcp_segmentation.rs`: WG arm now keys on the frame's inner
  destination (post-NAT `rewrite_dst` when present; never the
  pre-translation dst for NAT64) and sizes with
  `wg_inner_mtu(selected_family, selected_mtu)`, still min'd with the
  overlay `route_mtu`. GRE/plain paths unchanged.
- `icmp_ptb.rs`: WG arm of `tunnel_inner_mtu` uses the same helper, so
  PTB and segmentation share one selected-peer SSOT.
- NOT changed: GRE inner-MTU math, unknown/missing-mode fail-closed
  (0 budget → drop), dispatcher admission gate, TX prepared twin (it
  already declines tunnel decisions).

## RED → GREEN

- RED (pre-fix semantics): segmenter at logical-1420/row-family budget
  vs selected-peer physical-1500/v6 budget 1405; PTB at row-family.
- GREEN targeted tests (see PR body for final counts):
  - `wg_segmentation_sizes_to_selected_v6_peer_not_endpoint_v4_row_14118`
    — decrypts every segment, asserting max inner == 1405 exactly.
  - `post_transform_wg_inner_mtu_charges_selected_peer_family_14118`
    — row flipped to v4 after build, selected v6 peer still charges
    1405, not 1425.
- Base-attributed failures (verified on fresh `origin/master` worktree,
  pre-existing): `wireguard_segmentation_uses_wg_inner_mtu_not_gre` and
  `wireguard_segmentation_emits_wg_outer_never_gre` fail identically
  without this change; not touched.

## Validation

- Targeted filters above + GRE/unknown/missing-mode segmenter and PTB
  suites pass at fix head. Full `--bins` suite: see PR body.

## Risk

Single-underlay WG deployments resolve to the same peer/family/MTU as
before (first-peer fallback is byte-identical there). Multi-peer /
mixed-family WG now sizes to the peer that will actually carry the
packet — intended behavior change; oversize segments are no longer
built-then-dropped at encap.
