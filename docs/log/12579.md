# Issue #12579 — publish no-RETH hold reason before release flag

## Root cause

`releaseNoRethSyncHold` stored `false` to the active `atomic.Bool` before storing the reason in a separate `atomic.Value`. The timeout test polled the flag without a lock and, once it saw `false`, immediately read the reason. The flag store did not publish the later reason store, so the reader could observe an inactive hold paired with an empty reason. CI observed exactly this state (`""`).

## Fix

Store the release reason before clearing the active flag. The flag is the lock-free release indicator consumed by `inNoRethSyncHold`; publishing it last ensures a reader that observes the released state can also observe its reason. The timeout regression cell now continuously yields while polling rather than sleeping past the narrow publication interval.

## Validation

- Before the fix: `go test ./pkg/daemon/ -run '^TestNoRethSyncHoldReleasesOnTimeoutWithNoPeer7162$' -count=30 -race -timeout 300s` passed with no reproduction, consistent with the reported narrow window.
- RED mutant: the 100-run race stress with the original flag-then-reason ordering failed; the test observed `hold end reason = ""` at `noreth_sync_hold_7162_test.go:157`.
- GREEN: with reason-then-flag ordering, `go test ./pkg/daemon/ -run '^TestNoRethSyncHoldReleasesOnTimeoutWithNoPeer7162$' -count=100 -race -timeout 600s` passed (`19.278s`).
- Complete daemon package suite: `go test ./pkg/daemon -count=1` passed (`561.721s`).
- Static analysis: `go vet ./pkg/daemon` passed.
