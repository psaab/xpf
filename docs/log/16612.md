# A recovered commit-confirmed window no longer enters bootstrap on a frozen DNS answer (#16612)

- **Issue**: #16612 (R3-N09-04).
- **Cause**: A commit-confirmed window recovered at boot compiles its
  rollback target once, at `Store.Load`
  (`configstore/store_persist.go: recoverPendingConfirmLocked`). If
  dns-name resolution failed at that moment, the target's entries carry
  an empty answer with `DNSLookupFailed` (#16595). At the deadline the
  #9615 fire-time pre-flight consulted that frozen object: where the
  mirror still reported a refusal for the lookup-failed shape (e.g. an
  excluded/per-rule fail-closed side), the only deferral was the
  feed-only predicate, so the fire promoted the store and entered
  `enterBootstrapMode` — takeover files retired, FRR managed section
  cleared, dataplane detached, every RG resigned — even after DNS had
  recovered, and the log misdiagnosed it as "refused by this build's
  dataplane". Nothing re-resolved `confirmPrevCfg`; the periodic
  refresher touches only `ActiveConfig`. (On current master the plain
  permit/deny dns-name shapes are already handled per-entry by #16595
  and no longer refuse; the excluded shape above still demonstrated
  the bootstrap outcome, which is the cell the regression test uses.)
- **Change**: Fire-time DNS attribution in
  `pkg/daemon/confirm_rollback_preflight_9615.go`.
  `rollbackTargetRefusedOnlyForDNS` re-resolves a private clone of the
  pending target with current DNS (`config.RefreshDNSForPreflight`,
  built on `CloneForDNSRefresh` so the frozen target is never mutated):
  if the clone passes, or still fails only with lookup-failed entries,
  the refusal is DNS-caused. Such a target is bounded-deferred exactly
  like the feed case (`DeferConfirmTimer`, 5s × 24), and at the cap the
  rollback **proceeds** — promotion returns the same target object and
  `applyConfigLocked` re-resolves its dns-name entries in place
  (#15673), so a recovered resolver yields the fresh answer and a
  still-down resolver yields the per-entry fail-closed rendering
  (#16595) — instead of entering bootstrap on the frozen Load-time
  answer. The boot alarm (`checkRecoveredConfirmTarget`) now names
  "waiting on dns-name resolution that failed when the target was
  compiled at load" for this class instead of the generic refusal.
  Feed-only, statically refused, and healthy targets are unchanged;
  the arm-time #6707 gate is untouched.
- **Regression coverage**: `pkg/daemon/confirm_dns_rollback_16612_test.go`
  — DNS down at Load then healthy at the deadline applies `dns-target`
  with `inBootstrap=false` for permit, deny, and excluded dns-name
  targets (the probe's acceptance shape, via the real Store.Load
  recovery path); DNS still down is bounded-deferred without promoting
  and applies past the cap without bootstrap; the classifier detects
  lookup-failed entries across global/named books and never classifies
  a healthy target; `RefreshDNSForPreflight` leaves the frozen target
  unmutated. RED is by construction: without the new helpers the test
  file does not compile, and with the classifier removed the excluded
  cell re-enters bootstrap (pre-fix probe behaviour, re-verified on
  the source base shape).
- **Risk / residuals**: The deferral shares the feed counter and cap
  (24 × 5s), so a target waiting on both a feed and DNS is bounded by
  the same two minutes. When DNS is still down at the cap the rollback
  applies with empty/stale answers as per-entry match-none (permit) or
  per-rule fail-closed poison (deny/excluded) — the helper may retain
  previous-good for the deny arm, which is the strongest fail-closed
  the wire expresses and strictly better than resigning every RG into
  bootstrap. No real reboot or lab run was performed; the trigger is
  exercised through Store.Load recovery in-process, as in the probe.
