# Issue #15055 — plain-commit bootstrap gate TOCTOU (A32-02)

- **Issue:** The plain-commit bootstrap gate in `commitAndApply` was tested
  before `applySem.Acquire` and never re-tested. A commit racing the
  first-commit-confirmed timeout committed the reset empty candidate,
  reported success, and the next boot classified NORMAL.
- **Context read:** Read the complete issue body via `issue://15055`. No
  comments were present (`gh issue view 15055 --comments` returned no
  output). No scope withdrawal, narrowing, shipped notice, or contradiction.

## Mechanism (verified at base 73caef9bfb)

- `commitAndApply` (`pkg/daemon/daemon_apply_commit.go:209`) checked
  `d.inBootstrap()` before `d.applySem.Acquire` at :222 and never re-checked.
  A plain commit that passed the gate while a first `commit confirmed`
  rollback was mid-flight parks on `applySem`.
- `executeConfirmedRollback` holds `applySem` across `PromoteRollback` +
  `enterBootstrapModeWithLifeline`. `PromoteRollback`
  (`pkg/configstore/store_commit.go:1281`) resets the candidate to the empty
  rollback tree (`s.candidate = s.active.Clone()`, `bumpCandidateGenLocked`),
  clears `everCommitted`, and persists `committed=0`;
  `enterBootstrapModeWithLifeline` then stores `bootstrapMode=true` — before
  releasing `applySem`.
- When the parked commit acquires `applySem`, `commitWithGenBinding` binds
  the RESET generation and `CommitWithDescriptionGenAs` promotes the empty
  candidate, persisting `committed=1`-empty and setting `everCommitted=true`.
  The commit reports success, the operator's staged edits are replaced by an
  empty config, and the next boot classifies NORMAL — the state #1922 Item 1b
  / #7291 exist to prevent.
- `PromoteRollback` did not bump `holderEpoch` (all bumps were in
  `store_lock.go`), so a holder-bound `CommitAuthority` minted via
  `AuthorizeCommit` before the timeout still verified at promotion and could
  promote the reset candidate under the pre-rollback holder's authority.
  `InternalCommitter` is deliberately unconditional in
  `verifyCommitAuthorityLocked` and is stopped by the daemon gate instead.

## Fix

- `pkg/daemon/daemon_apply_commit.go`: `commitAndApply` re-tests
  `d.inBootstrap()` after `applySem.Acquire`, before any store promotion,
  returning the same bootstrap error. Mirrors the existing post-Acquire
  recheck in `beginBackgroundApply` (#9884).
- `pkg/configstore/store_commit.go`: the first-commit branch of
  `PromoteRollback` bumps `s.holderEpoch++`, scoped to that branch so an
  ordinary (non-first) rollback does not invalidate the holder.

Both fix directions named in the issue are implemented; each is independently
fail-on-revert covered.

The race cell is deterministic: the test holds `applySem` as the rollback
executor's stand-in, parks the plain commit behind it (it passes the
pre-Acquire gate while bootstrap is false), runs the real rollback halves
(`PromoteRollback` + `enterBootstrapModeWithLifeline`), then releases the
semaphore. It asserts the bootstrap error, no apply, in-memory and reloaded
`everCommitted=false`, and that the staged candidate was not promoted.
