# #15020 — `within N { trigger on 1; }` can never re-arm (A14-01)

- **Timestamp**: 2026-10-18
- **Action**: `withinMatches` (`pkg/eventengine/evaluate.go`) decided the #3756 edge-latch re-arm with the in-window count INCLUDING the current event, which `evaluateEvent` appends to the window before calling it. For `trigger on 1` that count is >= 1 by construction on every event, so `counts[i] < wc.TriggerOn` never held: once the first crossing armed `rt.onLatched`, no later event could clear it. The policy fired exactly once per daemon lifetime — `Apply` carries the runtime forward across same-revision applies (`engine.go`), so not even the remediation's own re-apply revived it — and the only other latch release, `releaseEdgeLatch` (`queue.go`), runs only on non-admission. The shipped lab pair in `test/incus/xpf-test.conf` (`failover-on-probe-fail` / `restore-on-probe-success`, both `within 60 { trigger on 1; }`) therefore went dead after its first outage cycle: restore never ran after an outage and failover never repeated. The fix tests the count EXCLUDING the current event (`counts[i]-1 < wc.TriggerOn`): the latch re-arms exactly when the ANDed condition was false before this event arrived — for N=1, when no prior occurrence remains inside the window (window decay) — so each isolated edge fires. Because the old code reached its below-threshold suppression through the re-arm's `return false`, that return is split out into an explicit inclusive count gate (`counts[i] < wc.TriggerOn` → no fire), keeping the latch mutation distinct from the firing decision. For N>1 the observable behaviour is unchanged: between events the in-window count never grows, so a sustained burst's pre-event count stays >= N until it decays and stays latched, and below-threshold events never fire either way — the latch merely clears on the crossing event instead of a preceding below-threshold one.
