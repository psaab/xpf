# Issue #16522: applyEditLine rejects annotate lines containing ';' even inside quotes

- **Timestamp**: 2026-10-24
- **Problem**: `applyEditLine` (pkg/configstore/store_command.go) stripped one trailing `;` and then refused any remaining `;` byte, including one inside a quoted comment or quoted path element. `ValidateAnnotationText` permits `;` and hierarchical `/* primary; backup */` comments create such annotations, so the box's own `show | display set` output (and Junos files with `;` in comment prose) failed `load set` / flat `load merge` atomically with an uninformative "invalid annotate command". `load override` and HA SyncApply (hierarchical parse) were unaffected.
- **Fix**: Lex instead of byte-testing. Added `config.ParseAnnotateCommandStrict16522` (pkg/config/config_command_split_14147.go), which runs the canonical strict lexer `lexConfigMutationLineStrict15167` and applies the shared `splitAnnotateTokens` only when the whole line lexed cleanly: a `;` inside a quoted token is part of that string token and accepted, while any unquoted structural `;`/`{`/`}`/`|`, unterminated string/comment, or TokenError makes it not-ok. `applyEditLine` strips at most one trailing structural `;` and uses the strict parser, so structural-`;` extra statements (`annotate ... "x"; delete ...`, #15167 class) are still refused instead of silently dropping the tail via the lenient parser. `IsFlatLoadLine` body classification is intentionally unchanged (a trailing-`;` annotate line still does not flip a hierarchical #10305 trigger body to flat); the flat replay gate in `replayFlatLinesMode15999` additionally accepts a complete strict annotate line with one trailing `;` via `isFlatAnnotateLine16522`, matching exactly what `applyEditLine` can now replay when such a line arrives via an already-flat body (LoadSet, or LoadMerge/LoadOverride lowering).
- **Tests**: new `pkg/configstore/annotate_semicolon_16522_test.go` — quoted-`;` comment/path cells round-trip through LoadSet and LoadMerge, hierarchical `/* primary; backup */` → `show | display set` → LoadSet/LoadMerge round-trip, structural-`;` controls (extra set/delete statement, `;;`, unquoted tail, pipe, unterminated string) refused with candidate unchanged, and a unit probe that the strict split agrees with the lenient parser on clean lines. Existing #15718 annotation round-trip and #10305 hierarchical-trigger tests still pass.
