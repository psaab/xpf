# #17922 — Use the minted port in the synced inbound NAT regression

- **Timestamp**: 2026-10-26
  - **Action**: Fixed `synced_inbound_hold_with_snat_16619` to construct its inbound `SessionKey` with the actual public port minted by the outbound SNAT fixture (`first.rewrite_src_port`) rather than assuming port 40000. The pool range now starts at 40001, making a return to the stale hard-coded port fail deterministically. The intermittent result was fixture mismatch, not parallel-test contention: the allocator chooses a port in the configured range and the synced lookup searches by the inbound key's translated tuple.
  - **File(s)**: `userspace-dp/src/nat/tests_pool.rs`, `docs/log/17922.md`.
  - **Validation**: Before the fix, 30 fresh-process runs of the exact test produced 24 failures and 6 passes (`Some(0)` vs `Some(1)`), consistent with the old hard-coded port matching only some randomly selected ports. With the regression range set to 40001–40010, temporarily restoring the hard-coded 40000 key failed at the inbound-hold assertion. With the actual minted port used, the exact test passed 20/20 fresh-process runs. `cargo test --bin xpf-userspace-dp nat::tests_pool:: -- --quiet` passed (236 passed, 1 ignored); `cargo test --bin xpf-userspace-dp nat:: -- --quiet` passed (780 passed, 1 ignored).
  - **Risk**: Test-only correction; no production behavior changed. The regression now fails deterministically if it stops using the allocator's minted public port.
