# Issue #14406 — VRRP sync-hold bypassed by cluster promotion + `ForceRGMaster`

RETH VRRP sync-hold only suppressed VRRP preemption (`Preempt=false`).
The cluster takeover-readiness branch for RETH consulted only
`RGVRRPReady` (instance built-ness), so a boot-fresh node with a healthy
peer primary and higher effective priority/preempt was takeover-ready
during the hold, cluster election promoted it to Primary, and
`handleClusterEvent` called `UpdateRGPriority(200)` + `ForceRGMaster` —
whose `forcePreemptOnce` bypasses the hold's `Preempt=false` — before
bulk session sync. The claimed boot exemption was also false: fresh
groups start `StateSecondary` (`group_state.go`), so the first
promotion is `Secondary → Primary` and does fire `ForceRGMaster`.

The NoRETH sibling already gates the identical hold through
`checkNoRethTakeoverReadiness` (#7162); RETH had no equivalent term.

## Change

- `pkg/daemon/daemon_ha_userspace_readiness.go`: `takeoverReadinessForRG`
  RETH branch now ANDs `!vrrpMgr.InSyncHold()`, appending the same
  "session sync startup hold: bulk sync not yet complete" reason as the
  NoRETH path. This is the load-bearing gate: election cannot promote
  while held. Bounded like #7162 — `SetSyncHold` arms once at bringup
  and releases on bulk sync or its own 30s timer; deliberately NOT a
  continuous `IsSyncReady()` conjunct (#110 trap: unbounded while the
  sync channel is down, blocking the degraded-peer case).
- `pkg/daemon/daemon_ha.go`: `handleClusterEvent` backstop — a Primary
  event observed while `InSyncHold()` (RETH path) returns early without
  recording cluster-primary, writing `rg_active`, removing blackholes,
  or forcing VRRP. Covers events already queued / degraded or
  peer-yielded promotions that bypass the readiness verdict. Demotions
  are never gated. Reconcile re-derives promotion after release because
  cluster state stays Primary while `rgStateMachine.clusterPri` was
  never set. Also corrected the stale `SecondaryHold → Primary` boot
  comment.
- `pkg/vrrp/manager.go`: `ForceRGMaster` refuses during sync-hold
  (manager-level backstop for any caller; no queue/replay — the daemon
  reconcile re-derives promotion after `ReleaseSyncHold`, whose
  `triggerPreemptNow` restores normal preemption).
- `pkg/cluster/README.md`: readiness-gate table documents the
  `InSyncHold` term.

Residual bound (accepted, mirrors #7161/#7939 design): the cluster
degraded-promote fallback (2m continuous not-ready) and peer-yielded
fail-open can still promote after their own bounds — both exceed the
30s sync-hold, so bulk sync or the hold's own timeout-degraded release
normally lands first; the `handleClusterEvent` backstop additionally
suppresses activation if such an event arrives while still held.
