# #18696: helper respawn stalls on a quadratic BPF map flush

- **Timestamp**: 2026-11-01
- **Action**: Fixed every BPF map loop that deleted the key it had just
  walked to and then asked for the key after it. For a key no longer in the
  map, the kernel hash map's `get_next_key` (`htab_map_get_next_key`) falls
  back to `find_first_elem`, a scan from bucket 0. So each such loop
  rescanned the map from the start on every row: about
  buckets x rows / 2 bucket checks.
- **Census** (every walk-and-delete, Go and Rust):

  | loop | map | runs at | was |
  |---|---|---|---|
  | `clearStaleSteeringRows` (`pkg/dataplane/userspace/process.go`) | `userspace_sessions`, 8,388,608 buckets | every helper spawn | quadratic |
  | `flushStaleBPFStateOnCtrlEnableLocked` (`helper_status_apply.go`) | `sessions`, `sessions_v6` | ctrl enable | quadratic |
  | `clear_bpf_conntrack_maps` (`userspace-dp/src/afxdp/bpf_map/mod.rs`) | `sessions`, `sessions_v6` | HA mirror clear (`clear_mirror_with_batch`) | quadratic |
  | 43 other Go walks (`pkg/dataplane` sweeps, `maps_sync.go`, `land_screen.go`, `wg_zone_admission.go`, ...) | various | various | read-only, or collect-then-delete: linear |
  | Rust `count_bpf_session_entries` / `dump_bpf_session_entries` (`bpf_map/metrics.rs`) | `userspace_sessions` | status/debug | read-only |

  The Go census was a brace-matched scan of every loop that walks a map
  (an iterator `Next`, or `NextKey`) for a `Delete` in its body: 45 walk
  loops, 2 offenders. That scan is now a test (below). The Rust census
  covered every `bpf_map_get_next_key` and `bpf_map_delete_elem` call; the
  other deletes are single-key.
- **Fix idiom: next before delete.** Read the next key while the current
  one still exists, then delete the current one. Each step then continues
  from the current key's bucket, so a walk is O(buckets + rows), with no
  key buffer to bound and no batch-op fallback to maintain.
  - **Go:** `walkDeleteBPFKeys` (`pkg/dataplane/userspace/bpf_map_walk.go`)
    serves both Go loops; the ctrl-enable flush keeps its keep-synced
    predicate. The walk starts from `NextKey(nil)`: the replaced loops
    started from an all-zero key, which skipped a real all-zero row. Its
    steps are bounded at twice the map's capacity, because a concurrent
    delete of the key under the walk can restart it.
  - **Rust:** `delete_all_map_keys` over a `MapKeyWalk` trait, with an
    fd-backed implementation. It keeps the old error semantics: a scan or a
    delete failure returns `Err`.

## Tests (counts, never time: engineering-style "Time in tests")

- **Kernel model.** A model of the kernel hash map's iteration (present key:
  continue from its bucket; missing key: scan from bucket 0) counts bucket
  checks, in Go (`htabModel`) and Rust (`HtabModel`).
  - **Control:** the replaced loop on 2,048 rows in 32,768 buckets must
    take at least rows x buckets / 8 checks. This proves the model
    reproduces the restart.
  - **Fix:** the new walk must stay within buckets + rows and make rows + 1
    `NextKey` calls.
- **Go:**
  - The keep predicate is honoured, and the keep walk is still linear.
  - The all-zero key is deleted.
  - A map that restarts every walk stops at the step bound.
  - **Census guard:** `TestNoDeleteDuringBPFMapWalk18696` refuses any loop
    in `pkg/` that walks a map and deletes in its body, other than
    `walkDeleteBPFKeys`. It recognises four shapes: `NextKey` in the body,
    `NextKey` in the condition, an iterator `Next`, and a range over
    `Keys`/`All`/`Iterate`. A positive control flags each shape once and
    leaves a collect-then-delete loop alone.
  - **Real map** (privileged only; skipped on the build host, where
    `unprivileged_bpf_disabled=2`): `clearStaleSteeringRows` empties a real
    hash map of 5,001 rows, including the all-zero key. It passed as root
    on udp fw1.
- **Rust:**
  - Scan and delete failures are reported, and no delete happens past a
    failed scan.
  - A negative fd clears nothing.

## Mutants (exact-once edits, files restored; scored by test name)

- **Go, 6/6 killed:**
  - delete before the next read: killed by the linear test;
  - walk from a zero key: killed by the zero-key test;
  - no step bound: killed by the churn test;
  - keep predicate ignored: killed by the keep test;
  - `clearStaleSteeringRows` reverted to the old loop: killed by the
    census guard;
  - a delete-in-walk loop added to the ctrl-enable flush (the `NextKey`-
    in-condition shape): killed by the census guard. That last mutant first
    SURVIVED, because the detector only looked for `NextKey` in the body.
    The detector was widened and the control rows added.
- **Rust, 3/3 killed, plus a no-op baseline that passes:**
  - delete before the next read: killed by the linear and failure tests;
  - delete failure ignored and scan failure ignored: each killed by the
    failure test. The delete-failure mutant first SURVIVED, because the
    test's fake scan also failed and masked it; the fake now ends cleanly.
