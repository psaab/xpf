# #16692: legacy sync-hold mirror refresh drops the post-release service edge

- **Timestamp**: 2026-10-25
- **Action**: In legacy `no-private-rg-election` mode, `watchVRRPEvents`
  never refreshed the #15258 sync-hold mirror, so the preempt MASTER
  event that `ReleaseSyncHold` itself triggers (`triggerPreemptNow` on
  every instance) was judged against `syncHold=true`: `SetVRRP(true)`
  reported `Changed=false`, no `rg_active` write ran, and
  `applyRethServicesForRG` (Kea RG groups, data-RG IPsec re-initiate)
  never ran. The later `syncRGSyncHold()` in `handleClusterEvent` /
  `reconcileRGState` then flipped desired and discarded the transition
  its own `SetSyncHold` produced, so neither path saw `tr.Changed` and
  the RG's service edge was lost until an unrelated edge or commit.
  The fix makes the mirror refresh an edge producer on every path:
  `watchVRRPEvents` and `watchClusterEvents` refresh the mirror scoped
  to the event's RG at the top of per-event handling
  (`syncRGSyncHoldTransition`) and pass the transition in;
  `handleVRRPEvent` / `handleClusterEventMerged` re-refresh scoped and
  merge it into the handler's `tr` (`mergeSyncHoldTransition`, which
  widens only `Changed`, keeping the caller's final
  Active/Epoch/InvalidateSeq); `reconcileRGState` keeps the pass-wide
  `syncRGSyncHold()` result and ORs each RG's transition into its `tr`.
  Scoping matters: a pass-wide refresh inside an event handler would
  consume an unrelated RG's pending release edge, whose services only
  that RG's own event or reconcile can run. The VRRP MASTER/BACKUP arms
  moved verbatim into `handleVRRPEvent` (mirroring the
  `handleClusterEvent` split) so the production handling is testable
  without driving the manager event channel. Ancillary: the two
  connected-RG republish entry points now guard a nil `applySem` like
  their sibling callers (`managementOnlyLeaseRefresh`,
  `rebindWebMgmtForLeaseChange`) — minimal daemon constructions reach
  them through the now-actuating promotion path.

- **Validation**: New `reth_sync_hold_vrrp_16692_test.go` (pkg/daemon),
  services observed by the proxy-ARP nudge `applyRethServicesForRG`
  always sends: (1) post-release VRRP MASTER row — held+mirrored,
  `ReleaseSyncHold`, MASTER event → `rg_active=true` written and
  services run exactly once; (2) release-only reconcile row — held
  reconcile writes/serves nothing (control), after release a
  no-new-event reconcile writes `rg_active=true` and runs services
  exactly once, and a steady-state pass does not re-run them; (3)
  post-release cluster promotion row; (4) scoped-refresh row — RG1's
  event refresh leaves RG2's mirror held until reconcile actuates it.
  Sibling guards `TestRethSyncHold*14406/15258` re-run. RED on revert:
  dropping the VRRP refresh/merge restores services=false with zero
  writes on row (1); dropping the reconcile OR restores it on row (2).
- **Residual**: R3-A34-04 (handleClusterEvent never runs services in
  legacy mode on the cluster leg proper) is a distinct producer and is
  not addressed here; this fix covers the mirror-refresh producer and
  the reconcile/VRRP legs the issue accepts. Private-RG default mode is
  unaffected (`InSyncHold` false, refresh is a no-op merge).
