# #9719: generation tombstones are never evicted, so churn switches the ordering guards off

- **Timestamp**: 2026-09-11T11:25Z
- **Action**: worktree `/var/tmp/wt-9719-gen-tombstone-eviction` on origin/master e1cebdf8b, branch
  `fix/9719-gen-tombstone-eviction`.
- **Action**: research, at e1cebdf8b.
  - Receiver: an applied non-zero delete upgrades the key's entry in `recvGenV4/V6` to a TOMBSTONE
    (#2221) and never frees it. Only a gen-0 delete or the accepted-BulkStart reset removes entries.
  - `putGenBounded` skip-records a NEW key at `genGuardMapCap` (200000). So a long-lived connection
    churning 200k closed sessions leaves every new key unrecorded, and the #2170/#2221 guards are
    off for new sessions until the next bulk.
  - Sender: `stampInstallGenV4/V6` also skip-records above the cap, and `takeDeleteGenV4/V6` returns
    generation 0 for an unstamped key. A live session stamped past the cap is then deleted
    unconditionally on the receiver.
  - Existing cells:
    - `TestGenMapOverflowKeepsLiveKeyV4` and `TestRecordInstalledGenSkipsNewKeyOnFull` fill
      `recvGenV4` directly with synthetic entries, and pin skip-record-on-full plus never clearing a
      live key.
    - `TestGenGuardConcurrentMaps` expects tombstones to stay in `recvGenV4`.
    - None depends on tombstones never being evicted.
- **Action**: design.
  - Keep one map per family, so the existing cells stay valid. Add a FIFO tombstone order
    (`genTombstoneOrder`, `container/list`) under `recvGenMu`:
    - an applied non-zero delete marks the key as the newest tombstone;
    - a re-install or a gen-0 delete forgets it;
    - `resetRecvGen` resets the order with the maps.
  - Recording a NEW key at the cap first evicts the oldest tombstone (`putGenEvictingTombstones`). A
    live entry is never evicted (#2198 F1). The synthetic fills in the existing cells register no
    tombstones, so their skip-record assertions still hold.
  - Evicting the oldest tombstone re-opens only that key's reorder window, the key least likely to
    still have a reordered install in flight.
  - Sender: a per-family sticky `genSentOverflowV4/V6` flag, set when a stamp is skipped at the cap.
    After that, `takeDeleteGen*` draws a fresh generation for an unstamped key instead of 0.
    - The receiver refuses such a delete only while it holds a newer generation for the key, which
      is correct.
    - Before any overflow the legacy 0 is unchanged.
  - Stats: `GenTombstonesEvicted` (stats and snapshot).
- **Action**: change.
  - `pkg/cluster/sync_gen_tombstones_9719.go`: new; `genTombstoneOrder`, `putGenEvictingTombstones`.
  - `pkg/cluster/sync_conn_gen.go`:
    - `recordInstalledGenV4/V6` and `deleteGenGuardV4/V6` evict, mark and forget;
    - `resetRecvGen` resets the order;
    - `stampInstallGenV4/V6` latch the overflow;
    - `takeDeleteGenV4/V6` draw a fresh generation after an overflow;
    - the cap and guard docs are updated.
  - `pkg/cluster/sync.go`: the `recvTombV4/V6` and `genSentOverflowV4/V6` fields, and
    `GenTombstonesEvicted` in stats and snapshot.
  - `pkg/cluster/README.md`: the generation-guard paragraph.
  - **File(s)**: `pkg/cluster/sync_gen_tombstones_9719.go`, `pkg/cluster/sync_conn_gen.go`,
    `pkg/cluster/sync.go`, `pkg/cluster/README.md`, `docs/log/9719.md`
