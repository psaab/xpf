# #12066 — one source protocol per route-map sequence

- **Timestamp**: 2026-10-07 (`fix/12066-proto-seq`, stacked on #12065)
- **Action**: expand each `FromProtocols` value into its own route-map sequence and include that OR dimension in the admission count.

## Red before

Added focused renderer and count regressions before implementation. On the base, `go test ./pkg/frr -run 'TestPolicyProtoSeq' -count=1` failed because the renderer emitted one sequence for a multi-protocol term (and did not cross protocol values with community or family-split variants). `go test ./pkg/config -run 'TestRouteMapSequenceCount_ProtoDimension_12066' -count=1` failed because the count returned 1 for three protocols, 4 instead of 8 for a protocol/community cross-product, and 2 instead of 4 for a protocol/family split. The prior `TestGeneratePolicyOptionsMultiProtocol` passed on the base because it checked only that all match lines existed, not that each occupied a separate sequence.

## Change

- `renderPolicyTermSequencesWithDefinitions` now carries one protocol value into each emitted sequence. It preserves protocol order, normalizes `direct` to `connected`, and sanitizes the single emitted match operand. A missing protocol list still produces one unconstrained sequence without allocating a sentinel slice per cross-product variant.
- `RouteMapSequenceCount` now multiplies by `max(1, len(FromProtocols))` through the existing overflow-checked arithmetic. `ComposedChainSequenceCount` inherits the corrected per-policy count; the strict-bound error now names `from protocol` among the count drivers.
- Added tests for one sequence per protocol with sequence order assertions, exact protocol/community pairings within each body, mixed-family/protocol cross-products, and admission-count parity including near-ceiling strict-gate rejection.
