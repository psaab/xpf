## Why

`LocalLogWriter.SendFromEventReader` called `warnRateLimited(&lw.lastDropWarn, ...)` on its enqueue-failure drop path without holding `lw.mu`, while the async writer goroutine reached the same clock under `lw.mu` via `Send`/`SendBinary` (#9025 made the two concurrent by design). Under log pressure — exactly when the queue is full and the writer is failing — both goroutines read and wrote the `time.Time` clock unsynchronized: a Go data race, flagged by `-race`, with torn `time.Time` reads as the (theoretical) worse tail.

## What

Guard the rate-limit clocks themselves instead of relying on the caller's lock domain. `warnRateLimited` on both `LocalLogWriter` and (same shape, preventively) `TraceWriter` now takes a dedicated leaf mutex `warnMu` around only the clock check/update and releases it before `slog.Warn`, so a re-entrant slog handler can neither wedge it nor deadlock a caller already holding `mu`, and no caller needs to acquire `mu` just to warn. `SendFromEventReader` intentionally still does not take `lw.mu` — holding it on the event reader would park HA session sync behind a stalled writer, the stall #9025 removed. The ≤1/s-per-class semantics and separate drop/rotation clocks are unchanged.

NOT changed: `asyncAuditWriter.warnRateLimited` (already has its own `lastWarnMu`); the syslog event-reader path (never touches these clocks).

## Validation

New regression `TestLocalLogReaderVsWriterDropWarnRace14191` (`pkg/logging/locallog_drop_warn_race_14191_test.go`): concurrent retired-writer `SendFromEventReader` drops against closed-writer `Send`/`SendBinary` drops.

- RED on pristine master `43ebebd38`: `go test -race -run TestLocalLogReaderVsWriterDropWarnRace14191 -count=1 ./pkg/logging/` → `WARNING: DATA RACE` at `locallog.go:64/67` inside `warnRateLimited`, called from `SendFromEventReader` at `locallog.go:262`.
- GREEN with fix: same test `-count=3` passes; full `go test -race -count=1 ./pkg/logging/` passes; `go vet ./pkg/logging/` clean; `gofmt` clean.

## Risk

Behavior delta: none observable beyond race removal — warn rate, messages, counters, and drop accounting are identical; `warnMu` is held only for a `time.Time` compare/store (no I/O, no allocation) on an already-rate-limited warn path. Lock order `mu → warnMu` is one-directional (`warnMu` is never held while acquiring `mu` or while calling `slog.Warn`), so no new deadlock cycle. Residual: `TraceWriter`'s clocks were not racy today (all callers hold `tw.mu`); guarding them is preventive consistency, not a second fix.
